# Contributions schema is underspecified

## Description

The `contributions` field in component YAML is a raw list of dicts with no typed schema. Fields like `preferred-targets`, `config:`, and `content:` have implicit contracts. No validation that `preferred-targets` values are valid surface types. The `agent-jobs.yaml` contributions include `config:` references that point to other YAML files, but there's no model for this.

## Proposed Solution

Define a `ContributionDescriptor` dataclass with typed fields:
- `id` (str, required)
- `owner` (str, required)
- `kind` (enum: `rule`, `content`, `config-reference`, default `content`)
- `title` (str)
- `preferred_targets` (tuple of validated surface types)
- `content` (union: inline body dict, or config reference path)
- `skill_content_file` (str, optional)

Add post-load validation that checks `preferred-targets` against known surface types and that `config:` references resolve to existing files.

## Architecture Standards Assessment

**Standards risk: Aligns with Standard #2 (Config Over Code) and #8 (Error Handling).** The underspecified `contributions` field is the problem — adding a typed schema resolves the gap. Validation must use `AudiaGenticError` with canonical codes (VAL-FDESC-* pattern already registered).

## Resolution Assessment

**Complexity: Easy.** Straightforward implementation.

**Solution:** Define `ContributionDescriptor` dataclass in `foundation/components/` with typed fields (id, owner, kind enum, title, preferred_targets, content union, skill_content_file). Add post-load validation in the component loader that checks `preferred-targets` against known surface types and resolves `config:` references to existing files. Existing YAML still works — just validated.

**Files:** 2-3 — new dataclass module, loader validation hook, tests.

## Effort & Risk

Effort: Medium. Risk if unchanged: Surface drift, silent misconfigurations.
