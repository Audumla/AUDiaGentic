# Recipe migration: replace _run_command() with ProvisionStep and extend matrix YAML

## Description

Migrate Hindsight recipes to the `ProvisionStep` model (TO10) and `CompensatingSequence` executor (TO11), while consolidating duplicate recipe execution code into shared step-list helpers.

This item replaces `_run_command()` string parsing with structured `install_steps` and `configure_steps` from the matrix YAML. It is a single migration path: `install_command` / `uninstall_command` are removed from the Hindsight matrix schema and all rows are migrated atomically. No fallback shim is kept.

Each recipe that participates in automatic provisioning exposes one complete step list:
```python
def provision_steps(self) -> list[ProvisionStep]:
    return [*install_steps, *configure_steps]
```

`ProvisioningRecipe.provision()` uses `CompensatingSequence(recipe.provision_steps()).run(context)` when a recipe exposes `provision_steps()`, then runs `verify(context)`. Recipes without `provision_steps()` continue on the existing primitive-call path until migrated.

**Consolidation target:** eliminate repeated command execution logic in `HooksInstallerRecipe`, `PluginConfigRecipe`, and `_ClaudePluginUrlRecipe` by generating shell steps from row data through shared helpers. Do not introduce `_CommandRecipeMixin`; the command-specific methods disappear once structured steps are the source of truth.

Deferred from this item: `build_hindsight_recipe()` registry refactor. That is orthogonal cleanup and should not be mixed into the provisioning migration unless required to make the migration compile.

## Steps

Execution plan for smaller agents. Complete phases in order; run the listed validation after each phase before moving on.

**Phase A — Contract wiring, no Hindsight behavior change**
1. In `recipe_contract.py`, add optional detection for `provision_steps()` in `ProvisioningRecipe.provision()`.
2. Preserve existing probe/idempotent skip behavior before running steps.
3. If `provision_steps()` exists, run `CompensatingSequence(self.provision_steps()).run(context)`.
4. If sequence succeeds, call `verify(context)` and return verification result.
5. If sequence fails, return a `RecipeResult.fail(...)` that preserves original sequence failure reason and rollback details.
6. Recipes without `provision_steps()` must continue through existing install/configure/verify path unchanged.
7. Add focused tests in `tests/unit/foundation/toolchains/test_recipe_contract.py` using a fake recipe with and without `provision_steps()`.

**Phase B — Matrix schema migration support**
8. In `matrix.py`, replace `install_command` / `uninstall_command` fields with `install_steps`, `uninstall_steps`, and `configure_steps` lists.
9. Update `_load_matrix()` to read only structured step fields. Do not read command-string fields.
10. Update tests that instantiate `HindsightRecipeRow` directly.
11. Do not migrate YAML yet until loader tests for structured fields pass.

**Phase C — Shared Hindsight step helpers**
12. Add `_hindsight_params(backend, provider_id) -> dict[str, str]` in `recipes.py`. Include `URL`, `MCP_URL`, `TOKEN`, `KEY`, and `ID`; use empty strings only where current backend config truly has no value.
13. Add `_steps_from_defs(step_defs, params, *, recipe_id, registry=None) -> list[ProvisionStep]`. It should call `provision_step_from_dict` for each definition and pass registry/recipe_id through.
14. Add small row helper(s), e.g. `_row_install_steps(row, backend, ...)`, only if they reduce duplication. Keep them simple and pure.
15. Unit-test helpers with shell, shell pipe, config-set, managed-block, and write-file definitions.

**Phase D — YAML flag-day conversion**
16. Convert every `install_command` and `uninstall_command` entry in `hindsight_matrix.yaml` into `install_steps` / `uninstall_steps`.
17. Preserve `&&` command order by splitting into multiple shell step definitions.
18. Preserve pipe commands as a single shell step with `shell: true` and full command string.
19. Keep `status_command` unchanged for now; it is probe-only and not part of provisioning rollback.
20. Run matrix-loading tests and search the YAML for `install_command` / `uninstall_command`; there should be none.

**Phase E — Recipe migration and consolidation**
21. Remove `_run_command()` from `recipes.py`.
22. Remove command-run usage of `_parameterize_command()`; keep parameterization only for `status_command` probe if still needed.
23. Implement `provision_steps()` for command-driven recipes (`HooksInstallerRecipe`, wrapper CLI behavior, `PluginConfigRecipe`, `_ClaudePluginUrlRecipe`) using shared helpers. This removes duplicated install/uninstall command execution logic.
24. Implement `provision_steps()` for config-writing recipes where practical: MCP config adapter, rules-only, and composite/hybrid recipes. Composite order must match current lifecycle order.
25. Keep explicit `probe()`, `verify()`, `uninstall()`, and `prune()` methods where they contain recipe-specific behavior.
26. Do not introduce `_CommandRecipeMixin`.
27. Do not refactor `build_hindsight_recipe()` dispatch unless compilation requires it.

**Phase F — Cleanup and compatibility checks**
28. Search code and tests for `.install_command`, `.uninstall_command`, and `_run_command`; remove all remaining references except historical text in planning docs.
29. Update boundary/architecture tests that asserted command-string behavior to assert structured-step behavior.
30. Run focused memory/hindsight tests, foundation toolchain tests, then full unit suite if feasible.
31. Record any deferred cleanup as a new planning item instead of expanding TO12 scope.

## Effort & Risk

Complex because this is a flag-day migration from command strings to structured steps plus lifecycle wiring. Risk is controlled by phase boundaries: contract wiring, schema change, helper consolidation, YAML conversion, recipe migration, cleanup. Smaller agents should stop at phase boundaries if tests fail instead of continuing. Main behavioral risks: preserving command order, shell pipe behavior, source gates, status probes, hybrid/composite ordering, and placeholder substitution.

## Standards

- S1 (Layering): Hindsight backend fields are mapped to a params dict in components/memory/hindsight code before calling foundation factory. foundation/toolchains does not import Hindsight types.
- S2 (Config over code): build_hindsight_recipe() contains a prohibited if/elif chain branching on recipe_kind entity names. Implementation of the (ProviderRecipeKind, builder_fn) registry is explicitly deferred from TO12 as orthogonal to the provisioning migration. A follow-up planning item must be created after TO12 to address this violation. Do not add new branches to the existing chain during migration.
- S8 (Error handling): Invalid step definitions raise AudiaGenticError at the factory boundary.
- S10 (Migration doctrine): No backward-compat shim. install_command and uninstall_command are removed from schema, loader, tests, and all YAML rows in one change.

## Notes

Depends on TO10 and TO11.

This item is intentionally broad but staged. If an agent cannot finish all phases, it should complete through the last passing phase and leave later phases untouched; do not leave mixed schema (`install_command` plus `install_steps`) in committed code.

Optimization intent: consolidate code by making structured ProvisionStep lists the single execution representation. Shared helpers replace duplicate command install/uninstall methods across HooksInstallerRecipe, PluginConfigRecipe, and _ClaudePluginUrlRecipe. Avoid abstractions that only exist to support the old command-string model.

Existing workflow-backed installers (`StepRecipe` / dependency installs) are not forcibly migrated in TO12. After TO12, create a separate cleanup item to evaluate whether StepRecipe should expose ProvisionStep-compatible rollback semantics. This keeps Hindsight migration executable while preserving broader consolidation path.

`build_hindsight_recipe()` registry refactor is intentionally deferred. It may still be useful, but it is unrelated to step execution and should be reviewed as a separate cleanup after migration.

The payoff of this item is a self-describing matrix, precise rollback through committed ProvisionStep instances, and less per-recipe command boilerplate.
