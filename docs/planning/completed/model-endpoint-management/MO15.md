# Provider secret resolution and launch-env contribution seam

## Description

Prerequisite infrastructure identified by RV315: grep confirms NO secret-ref resolver exists anywhere in src (api-key-ref/secret resolver/auth resolver — zero hits), yet the model-sources contract carries `api-key-ref: env:<VAR>` and four items depend on resolving it (MO02 step 5 launch-env recipe, MO04 step 4 Aider env, MO07 steps 3-4 key injection, MO13 step 3 OpenHands env). This item delivers two coupled pieces, provider-component-local (single consumer today — do NOT extract to foundation until a second component needs it, §3 two-consumer rule): (1) a prefix-based SECRET-REF RESOLVER — registry of scheme -> resolver with only `env:` at v1, extensible by registration without touching call sites; (2) the LAUNCH-ENV CONTRIBUTION SEAM — providers/recipes contribute DEFERRED {env-name -> secret-ref | literal} entries; resolution happens only inside the execution launch path immediately before subprocess spawn. Resolved values are never cached, persisted, logged, placed in status/timelines/fragments (beyond the single target config field for config-mechanism injection in MO07), or included in error details. Adds ProviderRecipeKind.LAUNCH_ENV so env projection is a first-class recipe kind instead of the currently missing seam (RV313 finding 1: today's only env injection is LSP's launch_server(env=...) one-off).

## Steps

1. Add src/audiagentic/foundation/secrets.py (FOUNDATION — user decision RV337; shared capability like foundation/logging/redaction.py; domain-neutral §1 naming, no provider/model vocabulary): SecretRef parse/validate reusing the EXISTING auth-ref grammar from provider-config.schema.json — `^env:[A-Z0-9_]+$` is the v1 syntax (RV326: do NOT invent a second convention; auth-ref in provider config and api-key-ref in model-sources are the SAME ref type). A (scheme -> resolver-fn) registry with `env:` registered at v1, resolve_secret_ref(ref) -> str, plus has_ambient_value(ref) -> bool for presence checks that never return the value. Unknown scheme raises VAL-SEC-001; env var unset/empty at resolution time raises CON-SEC-001. Register both codes in src/audiagentic/config/components/foundation/error-resolutions.yaml BEFORE first use (§8). SecretRef repr/str never includes a resolved value; the resolver returns the value to the caller and retains nothing.
2. Migrate the existing ad-hoc consumer in the same change (§10): adapters/local_openai/catalog.py's hand-rolled api-key/apiKey/api_key/OPENAI_API_KEY lookup is replaced by foundation resolve_secret_ref over the provider config's auth-ref/api-key field — no parallel resolution path survives. services/health.py's auth-ref check upgrades from presence-of-field to has_ambient_value (step 6). Hindsight recipes' inline api_key values are OUT OF SCOPE (different flow: value already in backend config; note only). Harness CONFIG-materialization placeholders (__AUDIAGENTIC_*__) currently substitute only the dummy local-rig key; add a guard comment/test that any future REAL credential placeholder must route through resolve_secret_ref. PROMPT templating (foundation/templates.py) is an explicit NON-consumer — secrets are banned from prompt context by the agent_jobs denylist; the prompt renderer must never gain secret resolution.
3. In PROVIDERS (consumer layer): add ProviderRecipeKind.LAUNCH_ENV and a LaunchEnvContributionRecipe pattern: recipes declare contributions as {env-name: SecretRef|literal} WITHOUT resolving; status/dry_run report env NAMES and ref schemes only, never values. Providers whose execution is stub/unsupported hold contributions inert with action_needed ('execution bridge not wired') — a stub provider never receives an active projection (matches MO04 validation 7).
4. Wire the execution launch seam (providers): at provider launch (adapters/base_runner.py or the descriptor-driven execution path), collect the provider's registered launch-env contributions, resolve each ref via foundation resolve_secret_ref, and inject into the subprocess env. Resolution failures surface the canonical error with the ENV NAME and scheme only. No resolution occurs at descriptor load, reconcile, or status time.
5. STANDALONE-STARTUP semantics (RV337): env-indirection config placement (RV332 preference 1) makes the tool depend on the AMBIENT user environment when run outside AG. Provider health/status therefore checks has_ambient_value for every env reference the provider's config/contributions rely on; absence yields action_needed 'set <VAR> in your shell environment — AG-launched sessions receive it automatically; standalone runs require it' — never a silently standalone-broken config. The consent-gated literal-at-rest write (RV332 preference 2, dry-run-flagged) remains the explicit choice for a fully self-contained tool config.
6. Architecture guards: resolver is foundation with zero component imports; no if/elif on scheme (registry dispatch); resolved values are local variables inside the launch/writer call frame only; providers/harness consume foundation — never the reverse.
7. Tests: registry dispatch incl. fixture scheme added without core edit; unknown-scheme and missing-env canonical errors; redaction canary proving a resolved value appears in the spawned process env and NOWHERE else (repr, logs, status, timeline, registry, error details); stub-execution provider contributes nothing active; contribution listing shows names/schemes only; local_openai catalog resolution flows through foundation resolve_secret_ref; ambient-presence check drives action_needed without leaking the value; architecture test proves foundation/secrets.py imports no component/runtime modules and prompt templating has no secrets import.

## Validation

1. env: refs resolve at launch; unknown scheme -> VAL-SEC-001; unset var -> CON-SEC-001 with env NAME only in details.
2. Redaction canary: a sentinel secret value is visible in the spawned subprocess env and absent from every other observable surface (logs, status output, timeline attributes, registries, exception text, dataclass reprs).
3. Fixture scheme registers without modifying foundation/secrets.py core — proves extension point.
4. Stub-execution providers report inert contributions with action_needed and never active projection.
5. Ambient-presence check: env-indirection reference with the var absent from the environment produces the standalone action_needed text and no value leak; with the var present, status is clean.
6. Architecture-boundary tests: foundation/secrets.py imports no components/runtime; templates.py has no secrets dependency; existing provider launch/execution tests remain green.
7. local_openai catalog test proves key resolution flows through foundation resolve_secret_ref (no residual multi-key lookup).

## Effort & Risk

Mid. Small surface but security-sensitive; the redaction guarantee is the deliverable as much as the mechanism. Risk: scope creep toward a general secrets manager — v1 is env-scheme only, provider-local, no persistence, no new config files.
