# Inject vendor credentials into harness-native provider configs for enabled model sources

## Description

Sponsor direction 2026-07-18: for a harness to actually execute a materialized vendor model (OpenRouter free models first), its native config needs the vendor endpoint + credential reference alongside the model entries MO17/MO18 project. This was deliberately excluded from MO17 pending a concrete consumer; the consumer now exists (free-model agents across harnesses). Keep it evidence-gated per harness and reuse the managed-config engine — credentials follow the exact ownership/preservation rules as every other managed fragment.

## Steps

1. FREEZE THE CONTRACT: extend or sibling the ModelProjectionRequest with typed vendor-connectivity desired state (source_id, base_url, auth reference — an env-var NAME or harness-native secret reference, never a literal key). Follow the MA26 pattern exactly: frozen dataclasses, v1 JSON schema, FamilyPin validation, 4-char error prefix registered in error-resolutions.yaml. Decide with the architecture owner whether this is a new small family (managed-provider-connectivity) or additional typed fields on model-projection — test: do connectivity entries and model entries share desired-state semantics, ownership, modes, and result behavior (MA20 step 4)? If yes extend, if no sibling family on the same sync_managed_config engine.
2. HARNESS EVIDENCE GATE (per the capability matrix): Pi first — verified model_config writer exists and Pi supports custom OpenAI-compatible endpoints with env-ref keys. Each additional harness (OpenCode next once its config filename/container blocker resolves; then per-matrix candidates) requires a verified writer contract fact before any adapter code, per the MO04/MO13/MO14 doctrine.
3. SECRET POSTURE: AUDiaGentic stores and projects references only. Where a harness accepts env-var references (Pi, Qwen per matrix), project the reference. Where a harness demands a literal key in config, that harness is BLOCKED for injection until a sponsor-approved secret-materialization decision exists — record the fact, do not silently write secrets. Redaction canary tests on every write path.
4. Wire prune: disabling a source removes its connectivity fragment only when no other enabled source uses it; foreign connectivity entries untouched.
5. End-to-end proof: with MO18's free models projected and connectivity injected, a live Pi invocation against one OpenRouter free model succeeds (Docker or live gate, sponsor account).

## Detailed Solution & Technical Design

CORRECTED (2026-07-25, supersedes this item's earlier detailed_solution written the same day): the typed contract this item's step 1 says to 'freeze' ALREADY EXISTS and is ALREADY WIRED END TO END for OpenCode. Traced the full pipeline:

1. `contracts/model_projection.py::ModelProjectionEntry` already has `endpoint: dict[str, Any]` and `auth_ref: str | None` fields -- exactly source_id-scoped connectivity, already typed, already frozen/validated.
2. `services/models.py` (~line 89-96 and ~140-147) already populates `auth_ref=source.get("api-key-ref")` directly from a model source's config -- the SAME `api-key-ref` field MO18's guidance has you set for OpenRouter. This is not hypothetical wiring, it's live code.
3. `adapters/opencode/model_entry.py::render_opencode_model_entry` already CONSUMES it correctly, proving the exact secret-posture rule this item's step 3 requires:
     if entry.auth_ref:
         if entry.auth_ref.startswith("env:"):
             payload["apiKey"] = "{" + entry.auth_ref + "}"   # opencode's own {env:VAR} template syntax
         else:
             payload["apiKey"] = entry.auth_ref
   This is a real, already-shipped reference-projection (never a literal key) -- the exact SECRET POSTURE section of this item's description, already satisfied for OpenCode.

THE ACTUAL GAP: `adapters/pi/model_entry.py::render_pi_model_entry` never reads `entry.auth_ref` at all -- it wires `base_url`/`compat`/`connector_opts`/`limits` into the payload but has no `apiKey`/credential field anywhere in the function, despite the exact same `auth_ref` data already being available on the `entry` it receives. This inverts this item's own step 2 assumption ('Pi first -- verified model_config writer exists') -- the render function that actually builds Pi's payload is the one missing the credential wiring, not OpenCode's.

REVISED SCOPE (much smaller than 'freeze a new contract'):
1. EVIDENCE GATE (real, still needed, cannot be done from this repo): verify what syntax Pi's OWN models.json schema expects for an env-var-referenced API key -- check Pi's actual docs/config schema (not guessed). OpenCode's `{env:VAR}` template string is OpenCode's own convention; Pi's `providers[id].apiKey` field (see local_rig_config.py::build_models_config, which today always writes the literal string "dummy" as Pi's local-rig placeholder) may expect a different syntax, a literal value only (which would BLOCK Pi per this item's own SECRET POSTURE rule), or something else entirely. Do not assume opencode's syntax carries over.
2. If Pi supports a reference syntax: add the missing block to render_pi_model_entry, mirroring opencode's pattern but using Pi's actual verified syntax from step 1 -- roughly:
     if entry.auth_ref:
         payload["api_key"] = <pi's actual env-ref syntax, from step 1 evidence>
   (field name 'api_key' vs 'apiKey' vs something else -- verify against Pi's real schema, do not assume camelCase carries over from opencode).
3. If Pi does NOT support a reference syntax (only accepts literal keys): per this item's own SECRET POSTURE rule, Pi is BLOCKED for credential injection until a sponsor-approved secret-materialization decision exists -- record this as a fact, do not silently write a literal secret into models.json.
4. Redaction canary test mirroring what likely already exists for OpenCode's render_opencode_model_entry (find and read it first, copy its pattern) -- prove no literal secret ever lands in models.json, only the reference string, for whichever syntax step 1 confirms.
5. Prune/ownership: this item's step 4 (wire prune) and end-to-end proof (step 5) -- check whether these already work for OpenCode's existing wiring (they likely do, since write_opencode_models/the model_config ManagedConfigSpec engine already handles managed_id-scoped prune generically) and only need proving for Pi once step 2 lands.

This item may now be SMALL work (one function, ~5-10 lines, gated on one evidence check) rather than the 'L' effort/new-family-design work originally scoped -- re-assess effort_risk once step 1's evidence comes back.
