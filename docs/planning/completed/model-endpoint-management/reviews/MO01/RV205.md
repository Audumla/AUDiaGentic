# Contract needs a connector taxonomy, not a single openai-compatible protocol

## Notes

Repo confirms the connector dimension is real and only partially modeled: Cline descriptor advertises 'OpenRouter, Anthropic, OpenAI and others'; Pi/OpenCode carry an api/connector field (openai-completions, openai); local-openai lists LiteLLM/Ollama; OpenHands/Aider are LiteLLM-backed; Claude/Gemini are native-vendor. OpenRouter is openai-compatible on the wire but an aggregation gateway (namespaced models, routing prefs, catalog) that most agents expose via a dedicated provider type.

## Findings

1. The managed-model shape's single protocol: openai-compatible is too narrow. Introduce a connector taxonomy (openai-compatible | anthropic | gemini | openrouter | litellm | ollama | native-vendor) as an endpoint field. 2. Each provider descriptor must declare supported-connectors so projection only targets capable agents and renders the endpoint in that agent's native form. 3. Connector-specific endpoint fields (anthropic version header, gemini api-version, openrouter routing prefs / namespaced model-id) are per-agent and mostly FILL. 4. Aggregators (OpenRouter, LiteLLM proxy, Portkey) are openai-compatible wire + extra capability; model them as their own connector with openai-compatible fallback. 5. Reuse machinery is unaffected — the desired-entry builder (MO02) becomes connector-aware and per-adapter rendering (MO03) selects the native connector.

## Conclusion

Incorporate into MO01 (connector taxonomy + supported-connectors), MO02 (connector-aware desired-entry builder), MO03 (native-connector rendering per adapter). Reference doc updated with the taxonomy, connector capability table, and OpenRouter/aggregator section.
