# Reviewer-scenario pass: model-availability channel missing from discovery taxonomy

## Notes



## Findings

1. The model-discovery enum (static-catalog | list-api | none) describes what AG knows about a REMOTE SOURCE's models, but omits the channel that already exists and is authoritative for tool-executing providers: installed-tool CLI discovery via fetch_catalog_fn (repo fact: opencode descriptor declares fetch_catalog_fn -> adapters/opencode/catalog.py runs `opencode models --verbose` and persists a schema-valid runtime catalog). For the first event-driven Reviewer test (OpenCode executing a review), 'which models are available in OpenCode' is answered by that runtime catalog TODAY, independent of any MO materialization.
2. MO01 step 7 mentions 'runtime catalogs' only in passing; the contract must define the relationship explicitly: for providers with a tool catalog, AVAILABILITY = the tool-reported runtime catalog (post-refresh); source materialization ADDS models to the tool; catalog refresh OBSERVES what the tool actually has. A materialized endpoint absent from the next tool catalog is a reconcile discrepancy (action_needed), not silent success.
3. Do NOT widen the source-level model-discovery enum for this — tool-CLI discovery is a PROVIDER property (fetch_catalog_fn already models it), not a source property. Overloading the source enum would conflate the two axes MO01 deliberately separated.

## Conclusion

Amend MO01 step 7 to define provider-level model availability (tool catalog authoritative where fetch_catalog_fn exists; materialized-vs-observed reconciliation surfaced via status/action_needed) and state that agent-profile model validation resolves against availability, not against desired-state materialization.
