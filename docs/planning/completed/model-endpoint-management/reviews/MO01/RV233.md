# Contract lacks model-source classes for external providers

## Notes



## Findings

MO01's contract only models individually-declared local/custom endpoints (`model-endpoints`). It cannot represent (a) frontier vendor accounts (OpenAI/ChatGPT, Anthropic, Google Gemini) where enabling the provider connection enables a family of models as a set, or (b) account-based aggregators (OpenRouter, OpenCode Zen, Qwen portal) where the available model set derives from the user's account — AUDiaGentic configures connectivity only, never the account. Step 7 also says 'Decide the relationship...' which leaves a design decision open for the implementing agent; all decisions must be pre-made since a lesser agent will implement.

## Conclusion

Generalize the contract to `model-sources` with a closed source-class enum (local-endpoint | vendor-account | account-aggregator) and a closed model-discovery enum (static-catalog | list-api | none). local-endpoint keeps the existing endpoint field set unchanged. Implementation of external-source enablement is split to MO07; MO01 designs the schema once so no rework is needed. Pre-decide the aliases/profiles relationship in the reference doc.
