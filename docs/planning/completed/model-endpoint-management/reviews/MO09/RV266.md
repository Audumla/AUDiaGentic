## Findings

1. The first event-driven agent (Reviewer) executes OpenCode; MO09's verification of the OpenCode column is therefore the first cell set with a live consumer, not just matrix hygiene. Step 2's ordering (first-wave providers) is right but does not name an acceptance target.
2. The installed-tool half for OpenCode has a shortcut the protocol should use: `opencode models --verbose` (already wrapped by adapters/opencode/catalog.py) enumerates exactly the models the installed tool can use — including native vendor models unlocked by keys — with per-model capability/limit JSON. That output IS the verification evidence for (a) which vendors are natively supported by the installed OpenCode, (b) model-set granularity, and (c) the availability ground truth for the Reviewer profile.
3. The `opencode provider-vs-providers container` question (already in remaining scope) gates MO03's gate 1; flag that the Reviewer scenario only READS models and does not need that container question resolved.

## Conclusion

Amend MO09: name the OpenCode column as the first acceptance target with `opencode models --verbose` as the primary installed-tool evidence source, and note the Reviewer scenario (reviewer-agent plan) consumes its output.
