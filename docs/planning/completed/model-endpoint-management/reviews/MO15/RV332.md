# Placement preference: tool-native env indirection over resolved literals

## Notes



## Findings

Several target tools natively support env indirection inside their own config, meaning the agent tool resolves the env var itself at runtime: Codex model_providers uses env_key = "NAME" (already in the reference doc's verified TOML snippet — no literal key ever enters config.toml), and OpenCode config supports {env:VAR} substitution (FILL — verify exact syntax/support in MO09). Where indirection exists, resolve-and-write places a secret at rest unnecessarily; writing the reference is strictly safer and makes the structural no-secret-at-rest guarantee cover the AGENT'S config file too, not just AG's.

## Conclusion

Pin config-mechanism placement preference order: (1) tool-native env indirection — the writer emits the ENV VAR NAME/reference in the tool's own syntax and the launch-env seam (or the user's shell) guarantees the var is set; resolve_secret_ref is not called at write time at all; (2) resolved literal value ONLY where the installed tool verifiably lacks indirection support — this is the last resort and the dry-run must flag it ('literal credential will be written to <path>'). MO09's key-mechanism evidence per (provider, vendor) cell must record whether config-level env indirection is supported and its exact syntax. Also record the library stance: v1 env: scheme is dependency-free; future keyring:/vault: schemes use the prebuilt keyring/hvac libraries respectively rather than hand-rolled store access — one registry registration each, not built now.
