# User decision: resolver moves to foundation; template guidance; standalone-startup semantics

## Notes



## Findings

User direction 2026-07-13 overriding RV332's location: the secret resolver is a SHARED CAPABILITY (like foundation/logging/redaction.py) and must live in foundation as a core item, not in the providers component — the single-consumer argument is rejected. Two further questions resolved: (1) template code — harness CONFIG-materialization placeholder substitution (__AUDIAGENTIC_*__) must route any real credential through the resolver; PROMPT templating (foundation/templates.py) must never resolve secrets (agent_jobs prompt-context denylist bans secrets from prompts by design). (2) Standalone startup gap in RV332's env-indirection preference: the launch-env contribution seam only covers AG-launched sessions; agent tools are also run directly by the user, where an env reference in tool config resolves against the AMBIENT shell environment that AG does not control. An env-indirection config is only standalone-correct if the var is user-globally present.

## Conclusion

(a) Resolver relocates to src/audiagentic/foundation/secrets.py (domain-neutral §1); VAL-SEC/CON-SEC codes move to the foundation error-resolutions.yaml; the launch-env contribution seam + ProviderRecipeKind.LAUNCH_ENV stay in providers as CONSUMERS of the foundation resolver. (b) Consumers now include harness config materialization (when a placeholder carries a credential); prompt templating is an explicit NON-consumer. (c) Standalone semantics: env-indirection placement additionally requires an AMBIENT-ENVIRONMENT presence check in provider health/status — referenced var absent from the user environment yields action_needed ('set <VAR> in your shell environment; AG launch sessions receive it automatically') rather than a silently standalone-broken config; the consent-gated literal-at-rest write remains the explicit choice for a fully self-contained tool config.
