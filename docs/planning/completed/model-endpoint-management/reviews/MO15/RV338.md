# Providers run standalone: ambient environment is primary; launch-env is supplementary to the launch capability only

## Notes



## Findings

User clarification 2026-07-13: ALL providers run outside AG in normal operation — AG manages their configuration externally; launching them is a separate capability, not the primary path. The prior framing treated the launch-env contribution seam as a primary key-delivery vehicle (env-mechanism 'native key injection'), which would make a source's enablement depend on AG being in the launch loop — wrong: an enabled source must work when the user starts the tool directly.

## Conclusion

Channel semantics re-ranked: PRIMARY standalone channels are (1) ambient user environment — tool config carries env indirection or the tool reads well-known env vars; AG verifies via has_ambient_value and guides with action_needed to set the var user-globally; (2) consent-gated literal-at-rest in tool config; (3) the tool's own auth store (native vendor login flows) — AG records status only. The launch-env contribution seam is SUPPLEMENTARY: it augments AG-launched sessions (separate launch capability) and may satisfy a var for those sessions, but a pair whose only working channel is launch-env must report status 'works in AG-launched sessions only — set <VAR> user-globally for standalone use', never plain enabled/auto. Status/enablement definitions in MO15/MO07 use ambient verification, not launch-seam presence.
