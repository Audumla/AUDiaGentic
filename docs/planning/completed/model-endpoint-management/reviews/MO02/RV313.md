# Cross-cutting architecture gaps: launch-env recipe, BU01 bus topics, MEP error timing

## Notes

Three cross-cutting issues found during readiness pass (2026-07-12).

## FINDING 1: Launch-env contribution recipe underspecified (step 5)
The item says 'env-projection providers (OpenHands/Aider) are handled by a launch-env contribution capability recipe, NOT via reconcile_fragments.' However:
- ProviderRecipeKind enum has NO value for launch-env projection. Existing values: COMMAND_INSTALLER, MCP_CONFIG, HOOKS, PLUGIN_CONFIG, RULES, WRAPPER_CLI, CONTEXT_PROVIDER, NATIVE_PASSTHROUGH, HYBRID, GUIDANCE_ONLY.
- The only provider-level env injection today is LSP's `launch_server(env=...)` in coding_lsp/lsp_bridge.py:70 — not a reusable pattern.
- MO04 step 4 expects the same mechanism for Aider. Without a defined recipe kind and implementation seam, this item cannot implement step 5.

## FINDING 2: BU01 bus-topic standards dependency unresolved (step 13 + notes)
The notes say 'any new bus topics introduced by model sync must follow the BU01 registration + BU02 constant convention once BU01 lands.' BU01 is pending. Step 13 defines topic names (`model-config.{planned|updated|removed|collision|reload-required}`).
- If BU01 doesn't land before MO02 implementation, the agent will use bare string literals (architecture violation per BU01).
- Need explicit decision: make BU01 a hard prerequisite, or allow temporary literal strings with tracked TODO.

## FINDING 3: MEP error codes reference pre-MO08 guideline (step 8)
The item registers VAL-MEP-001 through CON-MEP-003 and says 'External-connectivity failures follow the classification guideline delivered by MO08.' If MO02 implements before MO08 lands, the remediation text in error-resolutions.yaml won't match the final standard vocabulary (failure_class categories, degradation rules).
- Risk: mismatched classification between implementation and standard.
- Low risk since MO08 is docs-only and can land quickly, but ordering should be enforced.
