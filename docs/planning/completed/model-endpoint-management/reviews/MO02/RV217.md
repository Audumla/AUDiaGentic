# Standards review: provider model sync is valid if dispatch stays config/registry driven

## Notes

Compared MO02 with provider reconciliation, status, model selection, recipe, and standards code. The providers component already owns downstream provider rendering/config projection, matching Creating Components §6 ownership boundary. Reconcile currently calls MCP sync and host extension sync from `services/reconcile.py`; adding a sibling model-sync call is consistent if it delegates to provider-owned services and does not let agents or recipes write provider config directly.

## Findings

1. The approach is valid: model endpoint projection belongs in providers, not agents, because provider adapters own downstream config format and rendering. 2. Config-over-code requires model connector rendering and provider support declarations to be registry/YAML driven; avoid `if provider_id == ...` or `if connector == ...` chains. 3. `ProviderRecipeKind` needs a model-config/model-endpoints value, but recipes should remain lifecycle/status/dry-run surfaces; structured entry reconciliation belongs in the shared managed-config core. 4. Status must extend the existing provider status shape with model-config support fields instead of creating a parallel status API. 5. Observability Standards apply if model sync mutates durable resources: emit redacted timeline events for create/update/remove/collision/reload outcomes and never persist API keys or raw provider config with secrets.

## Conclusion

Approach is valid with strict boundaries: providers own projection, foundation owns generic sync primitives, recipes own lifecycle/status, and connector/provider selection stays data-driven.
