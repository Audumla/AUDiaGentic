# Desired-entry builder must consume sources, not raw endpoints; MEP error codes need YAML registration step

## Notes



## Findings

1) MO02's desired-entry builder is specified against endpoint declarations only. Once MO01 generalizes to model-sources, the builder input is the materialized-endpoint list derived from sources (local-endpoint sources materialize 1:1; external-source materialization arrives with MO07) — the builder contract should say so now to avoid a signature break later. 2) MO02 cites VAL-MEP-*/CON-MEP-* codes but neither family exists yet in any error-resolutions.yaml; per ARCHITECTURE_STANDARDS §8 every code must be registered in the owning component's YAML before use — the item lists the YAML file but does not enumerate the required codes, leaving a lesser agent to invent them ad hoc. 3) No guideline exists anywhere for classifying failures from external remote services (unreachable, auth-rejected, rate-limited) during catalog refresh — flagged as a standards gap (new item MO08).

## Conclusion

Update MO02 to (a) define the builder input as materialized endpoints derived from model-sources, (b) enumerate the canonical VAL-MEP/CON-MEP code set to register, (c) reference MO08 for external-connectivity error classification.
