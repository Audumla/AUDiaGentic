# Add model-source management MCP tools mirroring the lsp_manage pattern

## Notes



## Findings

The design said 'no separate enable-source tool — enabling is a project-config edit + reconcile', but the repo already has an established management pattern this contradicts: coding_lsp/lsp_manage_mcp.py exposes lsp_add_language / lsp_remove_language / lsp_set_language_option / lsp_reset_language_option / lsp_list_languages, which mutate desired-state config and let projection machinery apply it. Model sources need the equivalent (user request: add/disable/delete models via MCP, like languages under LSP but with more configuration), otherwise agents must hand-edit model-sources.yaml with no validation.

## Conclusion

Add a model_source_* management tool group to the providers MCP server: model_source_list, model_source_add, model_source_update, model_source_remove, model_source_set_enabled — all validating against model-sources.schema.json and writing .audiagentic/config/model-sources.yaml (the same file humans may still edit directly), then reconciling (apply/dry_run flags consistent with install_provider). Tools mutate DESIRED STATE only — never provider config files directly (that remains the reconciler's job, same invariant as recipes). Per-model granularity maps to: local-endpoint = one source per model so set_enabled/remove covers it; remote-account custom-entries = model-filter edits via model_source_update; remote-account key-injection = source-level only (all-or-nothing, surfaced in status). Supersedes the 'no separate enable API surface' line in the reference doc.
