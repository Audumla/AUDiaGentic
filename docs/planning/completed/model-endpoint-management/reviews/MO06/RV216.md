# Standards review: foundation extraction is valid but must stay domain-neutral

## Notes

Compared MO06 with current code and standards. Current code has separate provider descriptor specs (`McpConfigSpec`, `LanguageServersConfigSpec`), separate loader builders, a domain-opaque `reconcile_fragments`, and a provider-specific MCP registry/sync wrapper. Architecture Standards §3 explicitly requires shared 2+ file logic to move to foundation and duplicate dataclasses with >80% field overlap to unify. That makes MO06 a valid foundation extraction, not premature abstraction.

## Findings

1. MO06 is the correct prerequisite before model-endpoint work because the current code would otherwise produce a third config-spec clone. 2. The foundation module must use domain-neutral names only: `ManagedConfigSpec`, `ManagedFragmentRegistry`, `sync_managed_config`, not MCP/model/provider vocabulary. 3. MCP-specific fields (`remote`, reload behavior) must survive as optional fields or capability metadata; LSP must not be forced to invent irrelevant values. 4. The extraction must not introduce a generic `ManagedEntryRecipe`; `recipe_patterns.py` records that pattern was removed, so reuse target is the fragment/sync core, while recipes remain lifecycle/status wrappers. 5. Migration must be atomic: old spec classes and registry module references must be removed or reduced to instances in the same change, with whole-repo dotted-path grep and full unit test run, per Standards §10.

## Conclusion

Approach is valid if MO06 stays a behavior-preserving foundation extraction with domain-neutral names, feature-specific optional metadata, and no model-endpoint feature code in the same item.
