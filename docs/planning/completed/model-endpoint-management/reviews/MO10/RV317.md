# Alias fallback condition in resolve_execution_model underspecified

## Notes

Step 3 introduces a precedence helper with an ambiguous alias-fallback condition.

## FINDING: Alias fallback condition in resolve_execution_model is underspecified
Step 3 says: 'Add resolve_execution_model(packet_ctx, provider_cfg): packet_ctx model-id, then packet_ctx model-alias only if already resolved/allowed by caller contract, then provider default. Prefer omitting alias fallback if gateway guarantees model-id.'

The phrase 'only if already resolved/allowed by caller contract' is ambiguous for an agent implementing this:
(a) Should the helper accept a boolean parameter (e.g., `allow_alias_fallback=True`) that callers must set?
(b) Should it trust that the gateway never puts unresolved aliases in packet_ctx and always attempt alias resolution?
(c) What constitutes 'already resolved' — is there a marker in packet_ctx, or is this enforced by the caller?

## RECOMMENDATION
Decide one of:
- Option A: Add `allow_alias_fallback` parameter (explicit contract, type-safe)
- Option B: Omit alias fallback entirely if gateway dispatch (`agents_gateway_dispatch`) guarantees model-id resolution — document this invariant in gateway code
- Option C: Check for a packet_ctx flag (e.g., `model-resolved: true`) before attempting alias lookup
The item text says 'Prefer omitting alias fallback if gateway guarantees model-id.' If the agent can verify that guarantee during implementation, Option B is cleanest. Otherwise, Option A provides explicit control.
