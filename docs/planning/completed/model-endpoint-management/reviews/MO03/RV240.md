# Repo-verified config surfaces contradict Codex/OpenHands/Pi assumptions

## Notes



## Findings

Repo sweep 2026-07-10: (1) Codex — descriptor already manages PROJECT-scoped .codex/config.toml for MCP (remote: false) and LSP; the item assumes user-global ~/.codex/config.toml with consent gating. If upstream Codex honors model_providers in project .codex/config.toml, the consent machinery collapses to the ordinary project-file path (consent only needed for a user-global fallback). (2) OpenHands — descriptor manages .openhands/config.toml for MCP; the item's validation gate targets .openhands/settings.json, which the repo never touches. OpenHands config.toml has a structured [llm] section (model/base_url/api_key), making it a candidate STRUCTURED-FILE adapter through the same TOML surface we already write — potentially demoting env-projection to fallback. (3) Pi — harness template home/agent/models.json is HOME-scoped with verified shape: providers.<id> {baseUrl, api: openai-completions, apiKey, compat, models[] with id/name/contextWindow/maxTokens/cost}; project-vs-home scope is now a confirmed home-side fact, so Pi model writes are user-home writes and need the same care as other non-project surfaces. (4) OpenCode conflict re-confirmed: harness _build_opencode_provider_config writes providers.<id> {api: 'openai', baseURL, apiKey, models{}} to .opencode/config.json while descriptor manages .opencode/opencode.json.

## Conclusion

Re-aim the gates: Codex gate becomes 'verify project-scope model_providers support' (preferred path, consent-gated user-global only as fallback); OpenHands gate becomes 'verify [llm] section semantics in .openhands/config.toml' with structured-file preferred and env-projection fallback; Pi step notes home-scope write semantics with the verified JSON shape. Materialization examples recorded in the reference doc per-provider notes.
