# Add external-service error classification guideline (standards gap)

## Description

Standards gap found during the 2026-07-10 MO critical pass: ARCHITECTURE_STANDARDS §8 fully covers error construction (AudiaGenticError, canonical codes, mandatory error-resolutions.yaml registration, redaction) but no guideline exists for classifying and degrading on failures from EXTERNAL REMOTE SERVICES — exactly what model-source enablement introduces (catalog refresh against vendor/aggregator APIs, connectivity verification). Without a guideline, each adapter will improvise retry/failure behavior. Deliverable: a new §8 subsection (or §8-adjacent section) in docs/standards/ARCHITECTURE_STANDARDS.md plus an OBSERVABILITY_STANDARDS note, then referenced by MO02/MO07.

## Steps

1. Draft the guideline covering: (a) failure classification — transient (unreachable, timeout, 5xx, 429) vs configuration (bad base-url, unsupported wire API) vs authorization (401/403, expired key) vs contract (unparseable/incompatible response); (b) degradation rule — best-effort background operations (catalog refresh, connectivity probes) must degrade to last-known-good/cached state with a warning + action_needed and MUST NOT fail the enclosing sync or reconcile; only explicit user-invoked operations may surface the error as a failure; (c) retry policy — single bounded retry for transient class only, no retry loops, no sleep-loop polling; (d) redaction — never log or embed API keys, Authorization/x-api-key headers, or key-bearing URLs in error details/resolutions (extends existing §8 redaction rule to remote-call context); (e) code convention — remote-service failures use the owning component's CON- prefix with the failure class in details, resolution text names the check to perform (key present, service reachable, plan/entitlement); (f) ASYNC-HANDLER PRECEDENCE (RV277) — when the remote call happens inside an event-bus handler, the established async rules still govern: the handler never raises, the failure is dead-lettered with redacted structural summaries (foundation/logging/redaction.py primitives), and cached-fallback degradation composes with (never replaces) dead-lettering.
2. Add the subsection to docs/standards/ARCHITECTURE_STANDARDS.md following the existing rule-list style; keep it domain-neutral (applies to any remote service, not just model sources).
3. Add a short OBSERVABILITY_STANDARDS entry: degraded-remote-service outcomes emit a redacted timeline/warning event including failure class and staleness of the cached fallback.
4. Cross-reference: MO02 step 8 and MO07 step 3 consume this guideline; verify their wording matches the final text.
5. Pin a domain-neutral degraded-operation result vocabulary: failure_class in {transient, configuration, authorization, contract}; fallback in {cached, none}; stale boolean/age where known; action_needed string; error_code canonical owning-component code. The guideline specifies these semantic fields, not a shared model-specific dataclass.
6. Map current provider catalog behaviors/errors (TO-CAT-001, RES-CAT-002, read/validation errors) to the classes and identify where current raw str(exc) results must be redacted by later implementation items.

## Effort & Risk

Simple, docs-only. Risk is over-specifying (e.g. mandating retry/backoff machinery) — keep it to classification + degradation + redaction rules that any component can follow.

## Standards

- arch-standards — the guideline lands as a §8-adjacent subsection and stays domain-neutral (any remote service); it extends, never contradicts, existing §8 rules (make_error, canonical codes, error-resolutions registration, redaction).
- arch-standards (async boundary) — where a remote failure originates INSIDE an event-bus handler, the existing async rules take precedence and the guideline must say so explicitly: handlers never raise, failures are dead-lettered with redacted summaries, and degradation (cached fallback + action_needed) composes WITH dead-lettering rather than replacing it. (RV277)
- observability-standards — degraded-remote-service outcomes emit a redacted timeline/warning event with failure class and cached-fallback staleness; no keys, auth headers, or key-bearing URLs in any persisted detail.
- component-creation — remediation text lives in each owning component's error-resolutions.yaml, not in the standard itself.
