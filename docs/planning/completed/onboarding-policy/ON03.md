# Interactive first-run policy selection and per-provider prompt

## Description

Covers two related first-run gaps: (a) if this project has never set a `reconciliation-policy` at all, ask the user up front which overall behavior they want (auto-enable everything detected / choose an allowlist / ask me each time something new appears — mapping to mode auto/allowlist/prompt); (b) implements the `prompt` mode itself: on first run (and on any later run where a new CLI appears), when attached to a TTY, ask which of the detected-but-undecided providers to enable, instead of silently auto-enabling everything found on PATH (the behavior that prompted this plan — see the bigcherry first-run log where aider/antigravity/cline/copilot/gemini/openhands/qwen were all silently enabled).

## Steps

1. Add `resolve_reconciliation_policy(project_root: Path) -> None` (renamed from the earlier `resolve_first_run_reconciliation_policy` — see Notes: it is not actually first-run-only logic, so that qualifier was a misleading name) to the providers component. It calls `audiagentic.foundation.interaction.ask()` directly.
2. Inside that function: if `is_reconciliation_policy_configured(project_root)` is False, ask the three-way mode question:
   ```python
   from audiagentic.foundation.interaction import ask
   response = ask(
       "How should audiagentic activate provider harnesses in this project?",
       description="auto = enable anything detected on PATH; allowlist = choose which providers up front; prompt = ask me whenever something new is detected",
       choices=("auto", "allowlist", "prompt"),
       default_choice="auto",
   )
   ```
   `ask()` already returns `AskResponse(status=TIMED_OUT)` immediately when `sys.stdout.isatty()` is false — the non-TTY/CI fallback in step 4 falls out of `ask()` for free. On ANSWERED persist `mode=response.choice` via `set_reconciliation_policy`; on DECLINED/TIMED_OUT persist `mode='auto'`.
3. Whenever the resulting (or already-standing) mode is 'allowlist' or 'prompt' and there are CLI-available-but-undecided providers, call `ask()` once per undecided provider: `ask(f"Enable {provider_id}?", choices=("yes", "no"), default_choice="no")`. Accumulate yes-answers into `allowed_providers` and every asked provider_id into `decided_providers`, then persist both in one `set_reconciliation_policy` call.
4. Non-TTY fallback is inherited from `ask()`'s own behavior (step 2) — nothing extra to implement.
5. **Open design question, must be resolved before implementation, not papered over by naming**: `resolve_reconciliation_policy` needs to run whenever a newly-appeared CLI should be caught (per step 6's intent), but `launch.py`'s existing `_should_reconcile_providers_on_launch` gate only returns True once ever (stamp file at `.audiagentic/runtime/providers/launch-reconciled`), specifically to keep provider auto-enable reconciliation from re-running every launch. If `resolve_reconciliation_policy` is called only inside that same gate (as originally drafted), it will in practice run exactly once per project, ever — step 6's 'asked again on a later run' cannot happen under default settings, contradicting this item's own stated behavior. Two real options, pick one explicitly during implementation:
   (a) Call `resolve_reconciliation_policy` unconditionally on every launch, outside `_should_reconcile_providers_on_launch`'s gate (it's cheap — one config read plus CLI probes for undecided providers only — unlike the full enable/disable/surface-apply sweep that stamp is protecting), and only gate the subsequent `reconcile_all_providers` auto-enable/disable sweep on the existing stamp as today.
   (b) Keep it inside the same gate, and accept that 'newly-appeared CLI gets prompted' only happens when the user explicitly re-triggers reconciliation (removes the stamp, sets `AUDIAGENTIC_RECONCILE_PROVIDERS_ON_LAUNCH=1`, or a future CLI/MCP command), matching the existing 'subsequent reconciliation is internal-only' comment in launch.py — in which case step 6 and the Description above must be reworded to say so, not promise automatic re-prompting.
   Recommend (a): the whole point of `prompt` mode is to catch new CLIs without the user having to know about an env var or a stamp file to delete.
6. In src/audiagentic/commands/launch.py, call `resolve_reconciliation_policy(project_root)` per whichever option step 5 lands on.
7. Add `foundation/interaction/backend.py::use_backend(backend)` — a small `@contextmanager` wrapping the existing `set_backend`/`clear_backend` pair, formalizing the boilerplate `tests/unit/foundation/test_interaction.py`'s `teardown_function` already hand-rolls. Also add `current_backend() -> InteractionBackend | None` to backend.py (returns the module-level `_backend`), and update `api.py` to call `current_backend()` instead of reaching into `_backend_mod._backend` directly (`api.py:11` currently imports the whole sibling module as `_backend_mod` purely to touch its private global — a small encapsulation smell, cheap to fix while `use_backend()` is already being added to the same file).
8. Rename `request()` (api.py:106, the free function that persists a pending interaction and publishes `interaction.requested`) to `request_interaction()`. Rationale: `AskRequest` instances are conventionally named `request` as a local variable throughout this same package (`CliBackend.ask(self, request: AskRequest)`, `mcp.py`'s `_parse_elicit_result(result, request)`) — a top-level exported function also named `request` sitting beside that convention is a latent shadowing risk, not just a style nit. Blast radius is one call site outside this package (`components/agent_jobs/approvals.py:159`, `interaction.request(...)`) plus the `__init__.py` re-export — update both.

## Detailed Solution & Technical Design

**Correction from the previous revision of this item**: it previously proposed a bespoke `ask_fn: InteractionAskFn | None = None` parameter as 'the composable DI surface' for this feature, mirroring `on_progress: ComponentOutputSink | None`. Checked that against the actual test suite and it's solving an already-solved problem: `tests/unit/foundation/test_interaction.py` shows `interaction.set_backend(fake_backend)` / `interaction.clear_backend()` (in `teardown_function`) is already the established, tested way to substitute the entire interaction mechanism — for real alternate front-ends (via `ApplicationHost(interaction_backend=...)` at the composition root) and for tests alike. Adding a second, narrower injection mechanism (`ask_fn`) alongside the existing `InteractionBackend` Protocol + `set_backend()` seam would be redundant, not an improvement — two ways to swap the same thing where one already works and is proven.

**What's actually there today:**
- `InteractionBackend` (`foundation/interaction/backend.py:19`) is a real `Protocol` (`ask`, `push_status`, `respond`) — already the composable/DI surface the user asked about. It just isn't labeled as one anywhere.
- `set_backend()`/`clear_backend()` (backend.py:93-102) is the existing seam: called once at real startup (`ApplicationHost.start()`, application_host.py:62) with the process's real `CliBackend()`, and callable by any test to substitute a fake for the duration of that test.
- The one genuine rough edge: every caller of `set_backend()` for testing has to hand-write the same `set_backend(fake)` — `try/finally: clear_backend()` (or an equivalent `teardown_function`) boilerplate; `test_interaction.py` does exactly this today, and ON03's own new tests would otherwise duplicate it a second time.

**Resolution**: ON03's implementation calls `foundation.interaction.ask()` directly (step 2/3 above) — same as the very first draft of this item, before the 'composition' detour. The only foundation-level change this item makes is step 7: a `use_backend()` context manager that wraps the existing `set_backend`/`clear_backend` pair, so the *already-existing* seam gets a small, genuinely reusable convenience wrapper instead of every caller re-deriving the try/finally by hand. That is the properly-scoped answer to 'should we make interaction more composable/reusable while we're here' — package the existing tested mechanism cleanly, don't add a second, narrower one beside it.

CC54 (providers `_emit` consolidation) remains separate and unaffected: `ComponentOutputSink`/`on_progress` is a structured progress-event stream (progress/total/data, consumed by callers wanting programmatic progress tracking) serving a genuinely different purpose than `InteractionBackend`'s one-way operator notification (`push_status`) or two-way `ask` — merging those two concepts would conflate distinct contracts for no real gain, which is why CC54 keeps its own narrower scope (collapse the 4 duplicate `_emit` glue functions, fix the 2 that silently drop messages) rather than being folded into this item.

## Validation

Unit tests, using `use_backend()` (step 7) instead of manual set_backend/clear_backend: construct `resolve_reconciliation_policy` with `with use_backend(fake_backend_returning_scripted_responses):` and assert (a) the mode question is asked exactly once when unconfigured, never when already configured, (b) the per-provider loop asks only for CLI-available + undecided providers, (c) TIMED_OUT/DECLINED responses persist the safe defaults ('auto' mode / provider left undecided-or-declined) rather than raising or hanging, (d) a provider already in `decided-providers` from a prior call is not asked again, (e) a newly-detected provider not yet in `decided-providers` is asked even after the mode question was already answered in an earlier call.
Separately, add a small test for `use_backend()` itself: backend is active inside the `with` block and cleared afterward, including when the block raises; and for `current_backend()`: returns None with no backend set, returns the set backend otherwise.

Manual/integration test: real terminal, brand-new project, no policy set, several CLIs on PATH — confirm the mode question renders first via the standard `ask()` CLI output, then per-provider yes/no prompts, both persisting through `set_reconciliation_policy`; a second launch re-asks nothing already decided. Non-TTY launch (piped stdout) with no policy set: no prompt shown, `mode='auto'` persisted, process does not hang.
