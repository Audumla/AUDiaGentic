# Event topic standard: naming convention, per-component registry, payload contracts

## Description

Lock down how bus event topics are managed, mirroring the error-code doctrine (§8: canonical code + mandatory error-resolutions.yaml registration). CURRENT STATE (verified 2026-07-12): an envelope schema exists (foundation/contracts/schemas/event-envelope.schema.json) but `event-type` is a free string — there is NO topic registry, no payload contract per topic, and topic literals are embedded across ~13 files / ~62 occurrences (agents.llm.*, planning.item.*, component lifecycle, gateway topics). Planning already uses module constants (components/planning/events.py); agent_jobs and agents mix constants and inline literals. DESIGN DECISION TO ENCODE: the TOPIC IS THE CODE — a dotted, closed-vocabulary name (`<domain>.<resource>.<action-past-tense>`, e.g. planning.item.created, agents.llm.completed) is already stable and machine-readable; do NOT add a parallel EVT-XXX-001 numeric code (dual identity with zero benefit — errors need codes because their messages are freeform; topics have no freeform part). What events LACK versus errors is registration + a declared parameter contract; that is what this item adds.

## Steps

1. Write the standard as a new section in docs/standards/ARCHITECTURE_STANDARDS.md (style-matched to §8): (a) naming — dotted lowercase `<domain>.<resource>.<action>` with past-tense actions for facts (created/completed/failed) and request nouns for commands (requested/cancel-requested); domain = owning component's public domain (planning, agents.llm, component, job); (b) ownership — exactly one component owns a topic and is its sole publisher (documented consumers may be many); cross-component communication uses the owner's published topic, never a private literal; (c) registration — every published topic MUST be declared in the owning component's events.yaml before first publish (same rule as error codes: an unregistered published topic is a defect); (d) code hygiene — publishers and subscribers reference a module-level constant in the owning component's events module, never inline string literals (test-only literals exempt); (e) payload contract — each registration declares required payload keys and guaranteed metadata keys; full JSON-schema per topic is OPTIONAL and added only when a consumer needs strict validation (anti-overengineering guard).
2. Define the registry file shape: src/audiagentic/config/components/<component>/events.yaml — map of topic -> {description, payload-required: [keys], payload-optional: [keys], metadata-keys: [keys], delivery: sync|async|both, since: <version-or-date>}. Add contracts/event-topics.schema.json (schema validating the registry file itself, mirroring how error-resolutions files are shaped/validated).
3. Add foundation/event/topic_registry.py mirroring foundation/contracts/error_resolutions.py: load_all_event_topics(config_dirs) -> {topic: spec}, get_event_topic(topic), is_registered_topic(topic). Pure data loading — the bus does NOT gate publish on registration at runtime (no runtime coupling/perf cost); enforcement is test-time.
4. Enforcement test (the analog of error-resolution registration tests): AST-scan src/**/*.py for get_bus().publish(...)/bus.publish(...)/subscribe(...) first-argument string literals AND module constants assigned dotted-topic-shaped strings that flow into publish; assert every publish-site topic is registered in some events.yaml and matches the naming grammar; report unregistered topics with file:line. Pattern-subscriptions (wildcards like planning.** from trigger config) are consumer-side data, not declarations — excluded from the ownership check but validated against the naming grammar.
5. Optional strict validation hook for tests: a helper assert_event_payload(topic, payload, metadata) that checks required keys against the registry — used inside integration tests (e.g. reviewer-agent RE01's E2E), never in the hot publish path.
6. Seed events.yaml for the owning components with the CURRENT topics as-is (planning.item/review.*, ledger.event.recorded, agents.llm.{queued,started,completed,failed,cancelled,rejected}, agents.llm.gateway.{requested,cancel-requested}, component lifecycle topics) — registration only, zero behavior change; renames are out of scope (a rename is a breaking change needing its own item).
7. Cross-reference from OBSERVABILITY_STANDARDS (events vs logs vs timeline-event-names: JOB_TIMELINE_EVENTS and similar timeline name tuples are NOT bus topics and stay outside this registry — state this explicitly to prevent scope creep; also disambiguate `config/components/<component>/events.yaml` [package-owned topic registry] from `.audiagentic/config/interoperability/event-subscriptions.yaml` [project-local subscriptions — separate concern, renamed to avoid collision]).
8. Loader contract: use get_component_config_dirs() in the same precedence order as component/error-resolution loading. Registry identity is file location (config/components/<owner>/events.yaml). Reject the same topic declared by two different owners with a canonical CON error; same-owner later-overlay replacement is allowed only when the full spec validates.
9. Seed foundation-owned topics in config/components/foundation/events.yaml (lifecycle.component.*, interaction.*). Component-owned files contain only their publishers. Add duplicate-owner and overlay-precedence tests.
10. Conformance detector explicitly rejects publish/subscribe topic f-strings and literals in production. For indirect publisher helpers, require callers to pass exported constants; detector resolves Name/Attribute constants one import hop and reports unsupported dynamic expressions as violations, not as skipped sites.

## Validation

1. Registry loads all seeded events.yaml files; malformed file rejected by schema with a canonical VAL error.
2. Conformance test passes on the seeded tree and FAILS on a scratch module publishing an unregistered topic (detector self-test, same pattern as tests/unit/jobs/test_gateway_boundary.py).
3. Naming-grammar check rejects a deliberately malformed topic in a scratch registry.
4. Standards docs review: registration rule, ownership rule, constant-not-literal rule, payload-contract rule all present.
5. Duplicate topic across two owners fails; same-owner configured overlay follows shared last-wins precedence.
6. Detector self-tests cover literal, imported constant, helper-passed constant, and f-string/dynamic topic cases.
7. Foundation lifecycle and interaction topics load under owner foundation; no component claims them.

## Effort & Risk

Mid. Design risk is over-building: no runtime publish gating, no per-topic JSON schemas by default, no codegen — the registry is data + a loader + a test, exactly like error resolutions. The AST conformance test is the one clever piece; keep it to publish/subscribe call sites and reuse the test_gateway_boundary.py approach.

## Standards

- arch-standards — §1 foundation loader stays domain-neutral; §2 registry is YAML data, no topic if/elif anywhere; §8 sibling doctrine — same registration-before-use rule as error codes; §10 no renames in this item.
- component-creation — each component owns its events.yaml beside its error-resolutions.yaml.
- observability-standards — clarifies bus topics vs timeline event names.
