# Prompt/DOM comparison missed ChatGPT's blank-line padding around fenced code blocks, causing an indefinitely-stuck submission-proof

## Description

Live-diagnosed 2026-08-17 (req_42f9580ebfcd45d6, a design-consultation prompt containing exactly one fenced code block). The gateway's persisted request record stayed state=running with zero attempts recorded, never advancing, even though live DOM inspection proved ChatGPT had received and fully, correctly answered the real prompt (generating: false, completion-control/more-actions-menu/message-finalized all true, a stable 9512-char response) minutes earlier. The underlying CDP polling loop was confirmed genuinely alive (fresh Runtime.evaluate traffic in gp18_trace.log) and the production _SNAPSHOT_FN's dom_signals were confirmed to correctly satisfy response-complete's any-of-groups when evaluated directly -- ruling out both a dead polling task and a completion-policy bug. This pointed at submission-proof (match_prompt) instead: reconstructing the exact submitted prompt text and the exact observed DOM user-message text (scoped the same way production code reads it, via collapsible-user-message-content) and diffing them after the GP43 whitespace-run fix found exactly two residual mismatches, both newline insertions immediately before and after the fenced code block's rendered content.

## Steps

1. Captured the real submitted prompt (reconstructed verbatim from the actual prompt_body sent) and the real observed DOM user-message text (fetched live via CDP, scoped identically to gpt_auto_cdp.py's own userText() extraction) for req_42f9580ebfcd45d6.
2. Ran match_prompt()/normalize_prompt_text() (already GP43-patched) against both; confirmed a residual mismatch (4835 vs 4829 chars).
3. Used difflib.SequenceMatcher to enumerate the exact 2 diff ops: both `insert '' -> '\n'`, located immediately at the fenced code block's open and close boundaries -- ChatGPT's renderer pads a rendered code block with an extra blank line on each side.
4. Verified experimentally that collapsing any run of 2+ consecutive newlines to one closes the gap exactly (byte-for-byte match against the real captured data), the vertical analogue of GP43's horizontal-whitespace-run collapse.
5. Implemented the fix in prompt_fingerprint.py's normalize_prompt_text(), updated the module docstring, and added two new deterministic tests (one reproducing the exact incident shape, one guarding that the collapse only affects RUNS of 2+ newlines and doesn't over-collapse in a way that erases all line-break structure).

## Detailed Solution & Technical Design

prompt_fingerprint.py: normalize_prompt_text() now additionally collapses any run of 2+ newlines (\n{2,}) to a single newline, applied after the existing \xa0-normalization and horizontal-whitespace-run collapse (GP43). This treats any number of consecutive blank lines the same way GP43 treats any number of consecutive horizontal-whitespace characters -- presence is preserved (a line break still separates content from content), but the exact repetition count is not compared, since ChatGPT's renderer was proven live to insert blank-line padding non-deterministically around rendered code blocks. Case sensitivity and all non-whitespace content remain exactly significant; only the vertical whitespace repetition count is now tolerant, matching the same 'correlate content, not formatting fidelity' rationale as GP43.
