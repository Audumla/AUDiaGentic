# Reconciliation logic accepted a single completion witness with no stability window, weaker than normal completion

## Description

Code review found (BLOCKER, gpt-auto-reviewer-agent, 2026-08-17) that chat.py's _reconcile_unresolved_turn() -- the path that decides whether a retained/unresolved prompt from a prior interrupted turn actually reached a real terminal outcome -- was weaker than the normal completion gate (turn.py's _await_response()). It accepted ANY single completion witness via a flat .intersection() (one canvas control alone was enough, not the pair), and its own two-observation 'stability' check (comparing a fingerprint across two calls) had no minimum ELAPSED TIME requirement -- a caller retrying admission shortly afterwards could produce a second matching fingerprint almost immediately, especially exposed by GP34's canvas false-positive risk.

## Steps

1. Replaced the separately-maintained completion_witnesses set with the SAME any_of_groups from config.workflow.policy('response-complete') that the main completion gate uses, so recovery and normal completion can never drift into different terminal semantics again (reviewer's explicit suggestion: 'factor a shared completion witness policy rather than maintaining three subtly different interpretations').
2. Added a real elapsed-time requirement to the fingerprint-stability check: tracks _unresolved_match_fingerprint_at (time.monotonic()) alongside the fingerprint itself, and requires elapsed >= config.turn.response_stability_seconds (the same window the main completion gate's candidate-stability check uses) before clearing the unresolved turn, not just a second matching observation regardless of timing.
3. Since not-generating (GP34) is a derived fact, not a DOM signal, the reconciliation check builds true_facts = dom_signals | ({'not-generating'} if not snapshot.generating else set()) before testing group membership, mirroring turn.py's _facts().
