# Rewrite GptAutoTurn._await_response() to resolve against the request-scoped span, not conversation-latest

## Description

Slice 3 of GP08 (see GP08's notes for the full live design consultation) -- the actual hard problem GP08 exists to solve, and the piece the consultation calls 'probably the most important code change.' Depends on GP29 (unified ordered DOM message sequence) and GP24 (durable provider-correlation record) landing first. _await_response() currently biases toward the conversation's LATEST/current assistant observation, which is exactly wrong once a human or another actor posts a later turn into the same session.

## Steps

- Implement the turn-local resolver: a request owns the provider span beginning at its proven user-message anchor and ending immediately before the NEXT user message of any provenance, regardless of who sent it.
- Rewrite _await_response() to run completion/stability logic against resolver.resolve(snapshot).assistant_refs (the request-scoped span), never snapshot.current_assistant_id or global-latest-assistant text.
- mark_assistant_observed() likewise must receive the request-correlated candidate, not the conversation's global latest.
- Implement the three foreign-user-arrival cases fail-closed: (1) own assistant already proven terminal before boundary -> freeze normally; (2) foreign user arrives with assistant content present but not yet proven terminal -> the arrival can serve as a terminal witness for the PRIOR span but must never let the foreign turn's own evidence validate it, freeze ambiguous if can't establish terminality from request-local evidence; (3) foreign user arrives with zero assistant content yet -> freeze immediately as state='boundary-before-response'.
- Freeze ordering for crash-safety: construct complete FrozenProviderCorrelation -> persist via CAS -> publish compatibility ProviderSessionBindingUpdate FROM the frozen result -> only then clear PersistentChat's unresolved-turn recovery metadata -> return terminal SessionTurnResult. Freeze the actual response TEXT, not just IDs, to close the crash window where the answer finalized but the process died before output transitioned.

2026-08-17 IMPLEMENTED AND VALIDATED -- scoped down from the full GP24+GP30 design to a gpt_auto-only fix per user direction (prioritize functional/bug fixes, avoid shared gateway-store surgery tonight). Implemented the core resolver (_response_ref_for_prompt(), _scope_response_snapshot()) and rewired _await_response() to project every raw snapshot (main loop + verification fetch) onto this request's own prompt-anchored span before evaluating any completion policy, instead of reading ChatSnapshot.latest_assistant_id/_text directly. Once an identity is established it's frozen in-memory (self._response_message_id) and any later conflicting observation raises EXT-GPTAUTO-004 (frozen-response-correlation-conflict) rather than silently following a later turn. dom_signals/generating are deliberately left unscoped (real page-wide liveness evidence, not per-message).

Deferred: the durable CAS persistence (initialize_correlation/bind_prompt_anchor/freeze_correlation on the gateway request store) and the ProviderTurnCorrelationSink -- these are GP24's crash-safety hardening layer, not required to fix the observable bug.
