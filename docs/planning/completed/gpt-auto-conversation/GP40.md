# Stop-control flicker causes real detection lag: independent re-verification can retry indefinitely against a noisy signal

## Description

Live-observed 2026-08-17 (user watching the browser directly): a real ChatGPT turn's stop-answering button visibly flashed to the completed state and then flicked back to 'stop' -- a genuine transient flicker in ChatGPT's own UI, not a data artifact. The user confirmed the chat was ACTUALLY complete for some time before our system detected it. Root cause: once a candidate completion enters CANDIDATE_TERMINAL (turn.py/observation_engine.py), the tracker waits response_stability_seconds then performs ONE independent re-verification via a fresh snapshot; if that fresh check happens to land during a flicker (generating briefly True again), verification fails and -- because response-stall-timeout-seconds=0 makes candidate_max_verification_window_seconds infinite -- the tracker just retries the same check on every subsequent poll indefinitely. As long as the underlying stop-button kept flickering, any given re-verification attempt could land on a bad sample and fail, delaying detection well past when the response was genuinely done. This is the opposite failure mode from tonight's other fixes (GP34/GP39 were about false positives from noisy signals; this is excessive caution/latency from the SAME kind of noisy signal).

## Steps

- Consider whether a single flickered-back-to-generating sample should really restart/extend the wait, or whether a more robust signal is needed -- e.g. requiring not-generating to hold across N consecutive polls (majority-vote) rather than exactly the one fresh re-verification snapshot succeeding.
- Consider whether the independent re-verification step itself should retry a few times in quick succession (sub-second) rather than waiting a full poll_interval_seconds between attempts, since a flicker's own duration is likely much shorter than the current poll cadence.
- Weigh against the opposite risk (GP34's canvas false-positive scenario) -- any relaxation must not reopen that door. A debounced/majority-vote approach to the not-generating fact specifically (not to completion-control/more-actions-menu, which don't have this flicker problem) is the most promising direction since it only changes how noisy a SPECIFIC input signal is treated, not the overall stability/verification architecture.
- Decide whether this only matters when response-stall-timeout-seconds is disabled (0/infinite verification window, as in the current local configs) or whether it's a real risk at any finite setting too.

## Detailed Solution & Technical Design

Implemented 2026-08-17 in observation_engine.py's ObservationTracker.advance(). The CANDIDATE_TERMINAL branch previously only reacted to a genuine PROGRESS observation reopening the candidate (reset to ACTIVE, clear candidate_entered_at/candidate_generation) -- an observation with terminal_candidate=False but no PROGRESS capability was silently ignored, leaving the original candidate_entered_at timestamp running underneath. Added a new elif branch: whenever the state is CANDIDATE_TERMINAL and the current observation's terminal_candidate is False (and it isn't the PROGRESS-reopen case), immediately transition back to ACTIVE and clear candidate_entered_at/candidate_generation, exactly like a PROGRESS reopen. This closes the exact sequence described in this item's description: terminal evidence appears, generation quietly resumes without changing text (no PROGRESS signal), terminal evidence flickers absent then true again -- a fresh terminal observation now always starts a genuinely fresh candidate_stability_window_seconds count from the moment it reappears, instead of being able to inherit an old clock that was running through a period when the candidate was not continuously eligible.

NOT implemented (deliberately, scope-narrowed): the steps section's other proposals (majority-vote/N-consecutive-poll debouncing of not-generating, sub-second retry cadence inside the independent re-verification step, and decoupling candidate_max_verification_window_seconds from response-stall-timeout-seconds when stall detection is disabled) were not pursued. The last one specifically conflicts with an existing, deliberately-written regression test (test_response_stall_timeout_disabled_means_unbounded_across_every_phase, GP15) asserting every disable-sensitive timing property -- including candidate_max_verification_window_seconds -- becomes unbounded when response-stall-timeout-seconds=0. Changing that would need a new, separate config knob for the reverification budget rather than silently overriding the GP15 contract; left as an explicit follow-up rather than done unasked.

Tests: rewrote test_observation_engine.py::test_candidate_terminal_expires_to_suspect_stalled_if_witness_vanishes (renamed test_candidate_terminal_resets_immediately_when_witness_vanishes) to assert the new, correct behavior -- losing terminal_candidate resets to ACTIVE immediately with cleared clock fields, and a subsequent fresh terminal observation must complete its own full candidate_stability_window_seconds before verifying, proving the old clock was actually discarded rather than reused. Full gpt_auto + foundation/workflow suite green (225 tests) after the change.
