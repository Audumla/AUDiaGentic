# Prompt/DOM whitespace-run comparison too strict: ChatGPT's renderer collapses horizontal-whitespace runs non-uniformly, causing false submission-proof failures on large code/diff-heavy prompts

## Description

Live-diagnosed 2026-08-17 (req_c4c7f7b3ac03444b, a 35850-char diff-heavy gpt-auto-reviewer-agent code-review prompt). The gateway's agent_task_status stayed 'running' for ~12 minutes and then surfaced 'failed' with composer-typed-text-mismatch (33866 typed vs 35850 expected) and submission-proof-not-observed-before-deadline (prompt-text-match: false), even though ChatGPT had already received and correctly, fully answered the real prompt -- confirmed by direct DOM inspection of the response and by reconstructing the actual submitted vs. observed prompt text.

Root cause: ChatGPT's renderer re-encodes runs of horizontal whitespace (most visibly leading code indentation, but not exclusively there) using a lossy mix of non-breaking-space (\xa0) substitution and outright collapsing that does NOT preserve run length 1:1. A byte-level SequenceMatcher diff against the real captured DOM text found a run of 9 plain spaces collapsed to a SINGLE \xa0 character -- not a simple 1:1 space<->NBSP swap as prompt_fingerprint.py's own docstring had assumed (and deliberately left unhandled, calling it a KNOWN RESIDUAL GAP found live 2026-08-17 under req_27c9251fa0c54d73). This pattern recurred roughly once every 34 characters across the diff-heavy prompt (992 diff ops out of 35849 chars before the fix), making exact-length whitespace-run comparison fundamentally unreliable for code/diff-heavy prompts, not just an edge case.

## Steps

1. Captured the real submitted prompt (reconstructed from the exact text authored) and the real observed DOM text (fetched live via CDP from the actual conversation tab) for req_c4c7f7b3ac03444b.
2. Used difflib.SequenceMatcher to enumerate every normalization-surviving mismatch between the two, confirming the pattern was whitespace-run collapsing (both leading-indentation and interior), not corrupted/wrong content.
3. Verified experimentally that (a) normalizing \xa0 to a plain space, then (b) collapsing any run of 2+ horizontal-whitespace characters to a single canonical space, produces a byte-for-byte match against the real captured data.
4. Implemented the fix in prompt_fingerprint.py's normalize_prompt_text() and updated its module docstring (previously stated the residual gap as unresolved) plus the two tests whose assertions encoded the now-disproven exact-interior-whitespace-fidelity design goal.

## Detailed Solution & Technical Design

prompt_fingerprint.py: normalize_prompt_text() now replaces \xa0 with a plain space and collapses any run of 2+ [ \t] characters to one, applied AFTER the existing Markdown-stripping steps (fenced-code-marker removal, inline-backtick removal, link-syntax stripping). Case sensitivity and the PRESENCE (not exact width) of indentation remain significant -- an indented line still normalizes differently from an unindented one, since a run of any length collapses to exactly one space, never zero. Only interior whitespace RUN LENGTH is no longer compared, which is deliberately appropriate: this primitive exists solely to correlate 'did the right content reach ChatGPT', not to verify byte-perfect formatting was retained -- the assistant reads and responds to semantic content, not exact indentation width, and ChatGPT's own rendering pipeline has now been shown live to be incapable of preserving that fidelity regardless.
