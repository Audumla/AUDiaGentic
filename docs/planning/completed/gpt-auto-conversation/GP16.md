# Gateway request record's persisted output field truncates near the first backtick/code-formatting

## Description

A completed gpt-auto request's persisted 'output' field (returned by agent_task_status, sourced from store.read_public_status() -> project_public_status()'s allow-listed 'output' field, written via _session_output_from_result() -> SessionTurnResult.final_summary) was truncated to ~29 characters ('I read the full GP08.md on `') even though the real ChatGPT response was 17,746 characters long (confirmed via direct read-only CDP inspection of the actual tab, req_f3d2653b17494f53/GP08 consultation, 2026-08-16). The cutoff happens immediately after the first backtick character in the real text (which continues '`agent-surface-refactor` and traced...').

## Steps

- Rule out the DOM extraction layer first: gpt_auto_cdp.py's boundedText() helper (_SNAPSHOT_FN) already bounds assistant text generously (.slice(0, 20000)), far more than 29 chars, so this is very unlikely to be a DOM-capture bug.
- Check the persistence path: _session_output_from_result() (gateway/session/dispatch.py) returns result.final_summary directly with no truncation logic visible; store.append_owned_attempt()/_transition_owned_attempt()'s JSON write path (atomic_write_json or equivalent) should be checked for any escaping/serialization issue specifically triggered by a literal backtick character.
- Also check whether the truncation happens even earlier, inside turn.py's own response_text capture (_await_response()'s response_text = current.latest_assistant_text) -- confirm what the actual in-memory value looked like right before SessionTurnResult was constructed, not just what ended up on disk.
- Also consider whether this is specific to the MCP tool-result transport/rendering path back to the calling agent (i.e. the durable record on disk might actually be fine, and only what agent_task_status returns through this particular tool call got clipped) -- read the raw persisted request JSON file directly from disk for this exact request-id to disambiguate storage-layer truncation from transport/rendering-layer truncation before assuming which layer is at fault.
- Only one data point exists so far (this GP08 consultation); reproduce with a second real long response containing an early backtick/code-block to confirm the pattern before attempting a fix.

## Notes

2026-08-16 CORRECTION, supersedes this item's original hypothesis: this was NEVER an MCP/transport truncation bug. Direct read of the raw persisted request record on disk (project_root/.audiagentic/runtime/agent-execution-gateway/<request-id>/record.json) proved the 'output' field already contained only 28 characters at WRITE time, before any MCP/transport layer was involved. The real root cause and fix are on GP17 (response-complete's any-of completion-control/message-finalized allowed a premature termination witness through, captured by _await_response() as if it were the final response). GP17 is now fixed (changed to all-of across all four affected local provider configs).

What remains genuinely open and worth keeping on THIS item: (1) the project-scoped-file-vs-global-tmp spill pattern is still a good general idea for any output that legitimately IS large and could hit a real transport/tool-result size limit (confirmed to exist elsewhere in this toolchain tonight, e.g. plan_list_groups's auto-spill behavior) -- just not the explanation for tonight's specific symptom; (2) if a genuine MCP-layer size-limit truncation is ever found for gpt-auto output specifically, this item's spill-to-file + output-ref schema design is still the right shape for that fix. Downgrading this item's urgency accordingly -- it's a speculative future-proofing improvement now, not an active bug fix.
