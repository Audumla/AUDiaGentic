# response-complete's message-finalized signal went dead (ChatGPT DOM change), total block on completion detection

## Description

ChatGPT removed the `[data-is-last-node]` DOM attribute that the `message-finalized` signal selector depended on. Since `response-complete`'s policy required `message-finalized` together with `completion-control` (all-of, GP17's corroborating-pair fix), and message-finalized can now never be true, response-complete became permanently unsatisfiable -- a total block on completion detection, not a degraded state. Live-reproduced tonight (2026-08-17) as a full 600s hang in test_live_t1_scenarios: the real ChatGPT turn had genuinely finished (43092-char assistant message, no stop button, copy+more-actions buttons present) but the adapter never detected it.

## Steps

1. Root-caused via direct read-only CDP DOM inspection against the live gpt-t1 tab, using the EXACT production scoping logic from gpt_auto_cdp.py's _SNAPSHOT_FN (assistantTurn = closest('article') || parentElement.parentElement) -- confirmed [data-is-last-node] absent document-wide, while [data-testid="copy-turn-action-button"] (completion-control) and button[aria-label="More actions"] (the existing advisory-only more-actions-menu signal, added earlier the same night per the user's suggestion) both correctly matched in scope.
2. Swapped message-finalized for more-actions-menu in response-complete's all-of set in defaults.yaml (committed) AND all three local gitignored live configs (.audiagentic/config/providers/gpt-auto.yaml, gpt-auto-t1.yaml, gpt-auto-t2.yaml -- these carry a FULL copy of the workflow policy that overrides defaults.yaml at merge time, not just overrides).
3. Updated turn.py's _TERMINAL_WITNESS_SIGNALS and chat.py's unresolved-recovery any-of set similarly (message-finalized -> more-actions-menu) for consistency, though these are any-of/OR checks so completion-control alone already sufficed there.
4. Updated all affected tests (test_greenfield_config_urls.py's two regression guards, test_greenfield_bridge_turn.py's snap() helper and GP17 regression test, test_runtime_lifecycle.py's error-detail string assertion).
5. Validated purely read-only: ran the REAL production _SNAPSHOT_FN JS and GptAutoConfig/EvidencePolicy code (via turn.py's _facts()) against the already-completed, already-open gpt-t1 tab with zero new ChatGPT interaction -- response-complete now evaluates satisfied=True with matched=[assistant-fresh, completion-control, more-actions-menu, text-present].
6. Did NOT run the full live stress suite again: the same t1 tab is currently showing ChatGPT's real 'Too many requests... temporarily limited access to your conversations' rate-limit dialog (confirmed via direct DOM read), so further live ChatGPT interaction was deliberately deferred per explicit user instruction to avoid tripping the account-level rate limit further.

## Detailed Solution & Technical Design

message-finalized is kept in defaults.yaml/local configs as a DEAD SELECTOR entry (not deleted) for diagnostics in case ChatGPT reintroduces an equivalent marker under a new name -- must not be re-wired into any policy without fresh live confirmation. more-actions-menu's own promotion comment in defaults.yaml documents its live-validation basis (confirmed present alongside completion-control on a genuinely complete turn, both on 2026-08-16's initial advisory addition and again during this item's live read-only check on 2026-08-17).
