# response-complete never fires for ChatGPT's canvas/writing-block response variant (second variant of GP32's failure class)

## Description

Live-reproduced 2026-08-17 running test_out_of_sequence_injection_live.py's E3 scenario (real gpt-t2 ChatGPT session): a real turn's response rendered in ChatGPT's canvas/writing-block mode -- a distinct rendering surface from the standard chat-turn bubble, with its own action bar (Edit / Copy / Open editor, testid writing-block-header-magic-edit-button for Edit) instead of the standard copy-turn-action-button + More actions pair GP32 validated. The user directly observed the browser window looked stuck with no completion indicators visible and flagged it live; investigation confirmed via the exact production DOM-scoping logic that completion-control and more-actions-menu were both genuinely absent (not just out of scope) for this turn, so response-complete's any-of-groups (at the time, a single group) could never be satisfied -- the same permanent-block failure class as GP32, for a second response variant. User noted ChatGPT has more than just these two response variants; this is only the second one confirmed live so far.

## Steps

1. Root-caused via read-only CDP DOM inspection against the live gpt-t2 tab using the exact production _SNAPSHOT_FN scoping logic -- confirmed copyInScope=false, moreActionsInScope=false, while editInScope/openEditorInScope/copyAriaInScope were all true for the SAME turn.
2. Added two new dom-signals to defaults.yaml: canvas-edit-control ([data-testid="writing-block-header-magic-edit-button"]) and canvas-open-editor-control (button[aria-label="Open editor"]), both scope latest-assistant-turn.
3. Added a second any-of-groups entry to response-complete: [canvas-edit-control, canvas-open-editor-control], alongside the existing [completion-control, more-actions-menu] group -- exactly the resilience case any-of-groups (built earlier the same night for GP32) was designed for: a whole response variant's signals going missing degrades to the surviving group instead of blocking completion detection entirely.
4. Updated turn.py's _TERMINAL_WITNESS_SIGNALS and chat.py's unresolved-recovery any-of set to include both new signals (any-of/OR semantics, so any single one already sufficed, but kept in sync).
5. Because .audiagentic/config/providers/gpt-auto*.yaml were trimmed to sparse project-url-only overlays earlier the same night (GP20 follow-up), this fix needed exactly ONE file edit (defaults.yaml) instead of four -- direct payoff of that trim, same night it landed.
6. Added deterministic regression tests (test_greenfield_config_urls.py): a policy-shape guard for the new group, and an integration test exercising turn.py's real _facts() pipeline against the real merged config with only canvas signals present.
7. Validated read-only against the ACTUAL frozen turn that triggered this investigation (zero new ChatGPT interaction): ran the real production snapshot JS + config + _facts() pipeline against the live gpt-t2 tab and confirmed response-complete now evaluates satisfied=True, matched=[assistant-fresh, canvas-edit-control, canvas-open-editor-control, text-present].

## Notes

2026-08-17 hardened per code review. gpt-auto-reviewer-agent confirmed the canvas group's two members are NOT independent completion witnesses (both fire at canvas-panel-creation time, not completion) and recommended finding a genuinely canvas-specific state transition, or failing closed until one is found. Implemented the fix the review's own investigation pointed toward: added not-generating as a THIRD required fact in the canvas any-of-groups entry -- a new derived fact (foundation-agnostic, computed from ChatSnapshot.generating, added to config.py's known_facts and turn.py's _facts()) requiring the document-scoped stop/streaming/thinking/aria-busy check to be absent. This does NOT make the pair independent witnesses of each other, but it DOES require ChatGPT's own busy indicator to agree, which is a genuinely different signal source than the two structural canvas controls.

Also removed canvas-edit-control/canvas-open-editor-control from turn.py's _TERMINAL_WITNESS_SIGNALS entirely (review: 'I would stop describing the canvas controls as TERMINAL_WITNESS at all' -- correct, since that's a flat any-of single-signal check that cannot express the three-fact group requirement; canvas completion is left entirely to response-complete's own properly-guarded group).

Added a deterministic test proving the fix against the review's own concrete failure scenario: canvas signals present + generating=True must NOT satisfy response-complete (previously would have); the same signals with generating=False correctly do (test_real_merged_config_canvas_group_rejects_mid_generation_false_positive).

Residual risk (smaller than before, not zero): this relies on one live data point that ChatGPT's stop-control correctly tracks canvas busy/done state (unlike the standard chat bubble, where stop-control is PROVEN to stick after real completion, GP17) -- not yet proven across multiple trials that canvas's stop-control never sticks the same way. If it does, the mitigation degrades back toward relying on the stability/re-verification window alone, same as before this fix, but no worse. Full deterministic suite passes. Given the fix is real, tested, and principled (removes the confirmed 'total gap, zero protection' state), closing as completed; the residual multi-trial validation is a smaller, follow-on concern rather than a blocker.
