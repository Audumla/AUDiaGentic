# Second code review found the aria-label selector addition did not actually protect against scoping failure

## Notes



## Findings

completion-control's selectors were `['[data-testid="copy-turn-action-button"]', 'button[aria-label="Copy response"]']`. Selectors within one signal are OR'd, so the known-ambiguous bare testid still matched (and won) first if scoping ever picked the wrong container -- e.g. the user's own message action bar, which the user confirmed live also carries the same testid. Adding the role-specific aria-label selector as a second OR'd alternative gave additional false-negative resilience (still detects completion if aria-label wording changes... no wait, the reverse: still detects if testid changes) but provided no false-positive protection when scoping is wrong, which was the actual goal.

## Conclusion

Fixed 2026-08-17: replaced the two OR'd selectors with a single selector requiring BOTH attributes on the same element -- `button[data-testid="copy-turn-action-button"][aria-label="Copy response"]`. This is role-specific by itself (aria-label="Copy response" alone would already be sufficient and unambiguous per the user's live-pasted markup); the testid is kept only as an extra qualifier, not as an independently-sufficient alternative. Reviewed and confirmed no test in the deterministic suite asserted the specific two-selector list (tests use their own synthetic single-selector configs), so no test changes were needed beyond re-running the full suite (225 tests green).
