# Gateway auto-resumes a closed-but-resumable session transparently, instead of relying on the client to call resume

## Description

Today a client must explicitly detect that a session is closed/non-live and call agent_task_session_resume before it can submit against that session again. This session already found the mechanism that makes resume reliable exists (SessionRuntime.rehydrate_session(), the existing gateway-restart recovery contract confirmed correct in GP06's corrected model), but it is only invoked from specific known call sites -- the client still has to know a session needs resuming and remember to ask for it. Instead, if a session's durable state indicates it IS resumable (a live provider conversation can be reattached, not a terminally-failed one), the gateway should attempt that resume transparently the moment ANY client tries to use the session (e.g. submit against it), rather than requiring the client to pre-check state and explicitly resume first.

## Steps

GP review consultation (2026-08-17) refined 4 points before implementation: (1) narrowed auto-resume eligibility from 'closed or expired' to exactly 'closed + close-reason=shutdown' -- the only case with concrete production evidence; (2) verified update_owned_running_session() is already properly fenced (owner_epoch/worker_id/attempt_epoch CAS via _check_expected_identity, requires state=='running') before reusing it for retargeting -- a lost fence propagates as its own error, never silently converted to RES-AGW-003; (3) confirmed only AS49's own known eligibility-refusal error codes map back to RES-AGW-003, everything else propagates as itself; (4) confirmed the response naturally exposes the successor via the existing session-id field (no new schema field needed, since the 'open new session' branch already establishes this precedent of the response's session-id differing from what was requested).

## Detailed Solution & Technical Design

Implemented 2026-08-17 as a DELIBERATELY SCOPED slice of the full design above, per a live GPT design-consultation review (submitted with the full original design, given a go/no-go and 4 required conditions). NOT implemented: SessionActivation service, ActivationKind/ResumePolicy enums, ensure_session_for_use() unification with session-control paths, per-source cross-process reservation locks, response-schema activation projection. Those remain the real fix for the stronger invariants noted below; this patch closes the one concretely-reproduced incident.

What was built, in gateway/session/dispatch.py's _dispatch_session_request() 'continue' branch: when a session's runtime handle is unavailable AND its durable state is exactly `closed` with `close-reason == "shutdown"` (never `failed`, never `expired`, never any other close-reason -- narrower than the original proposal per the GPT review's explicit pushback that 'closed' alone conflates a gateway shutdown with a deliberate user/policy close, and undoing an intentional close is closer to a correctness bug than the restart problem being fixed), a new helper _auto_resume_shutdown_closed_session() reuses AS49's existing runtime.resume_session()/_resume_session() machinery as-is (no new concurrency primitive) with a control_id deterministic in the source session id (f"auto-resume:{source_session_id}"), so concurrent racing continuations against the SAME closed source converge on resume.py's existing idempotency-by-control-id lookup and resolve to one successor. On success it retargets: session_id/session_record become the successor's, and store.update_owned_running_session() (confirmed already fenced on owner_epoch/worker_id/attempt_epoch via _check_expected_identity, and already called a second time later in the SAME function for provider-metadata refresh -- reusing it is not a novel pattern) durably retargets the request to the successor BEFORE any provider submission proceeds. Only AS49's own known eligibility-refusal codes (CON-AGW-110/111/112/113/114/115/116/117, the exact resume.py taxonomy) are mapped back to the ordinary RES-AGW-003 the caller already knows how to handle; every other error (a lost ownership fence from update_owned_running_session, a store failure, an internal resume defect) propagates as itself, never masked as mere ineligibility. The response's session-id naturally becomes the successor's (same mechanism the 'open new session' branch already uses to potentially differ from the caller's requested id), so a caller adopting whatever session-id the gateway returns picks up the successor automatically -- no new response-schema field was needed. Session-control operations (cancel/interrupt/steer/close) are completely untouched, per the original design's own caution that auto-resuming a control action onto a different successor session is not equivalent to performing it on the original.

ACCEPTED, DOCUMENTED LIMITATION (not closed by this patch, matches the go/no-go condition explicitly): control_id-based idempotency converges CONCURRENT AUTOMATIC continuations onto one successor, but an explicit caller session_resume call (a different control_id) racing the same source session could still mint a second, different successor. Full GP13 (the per-source reservation model) remains the fix for that stronger invariant. The tactical patch's safety claim is 'concurrent automatic continuations converge,' not 'there can only ever be one successor for a source session.'

## Acceptance Criteria

A session closed specifically by a gateway shutdown (close-reason=shutdown) is transparently reattached to a new successor generation on the next continuation, without the caller needing to detect RES-AGW-003 and separately call session_resume. Sessions closed for any other reason, and sessions in a failed state, continue to require the caller's own explicit resume. Session-control operations are unaffected. An unexpected error during auto-resume is never masked as ordinary ineligibility.

## Notes

Directly motivated by a live incident this same session: a force gateway_restart() (loading unrelated fixes) closed every live session machine-wide, and a concurrent agent working in a different project (BigCherry) got a hard RES-AGW-003 on its next continuation even though the closed session record had everything needed to resume the same live provider conversation. GP13 was explicitly deferred earlier as 'genuinely large -- multi-file, new abstractions, new concurrency primitives... not responsible to build live against a shared gateway other people are actively using' in favor of this scoped patch, validated via live GPT design consultation before implementation (4 required conditions, all satisfied) rather than implemented speculatively. The full unified-activation design (SessionActivation, ensure_session_for_use, per-source reservations, response projection) remains open for whoever needs the stronger invariants -- this item's own body above still documents that complete design in full.
