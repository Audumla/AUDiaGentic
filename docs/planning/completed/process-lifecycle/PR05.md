# Define first-class managed process and shared-service lifecycle foundation

## Description

Extract process-management lessons from agent sessions, MCP daemon design, shared rig lifecycle, and the approved shared gateway into a reusable foundation/system capability. Define two related foundation contracts: ManagedProcess for an owned/adopted OS process, and ManagedService for a discoverable long-lived process with many independently leased clients. This is generic lifecycle mechanics, not a gateway, rig, MCP, or overseer-specific wrapper; consuming components retain domain policy such as which work counts as drainable and whether a service should be kept warm.

## Steps

1. Characterize existing process primitives: foundation/system/process.py (StartupLock, ports, PID liveness, tree kill), foundation/system/supervised_process.py (supervised_run, Windows Job Object kill-on-close), ACP session transport close semantics, rig registry lifecycle, and direct subprocess/kill callers. 2. Define ManagedProcess scopes: foreground supervised run, live session child, detached supervisor/daemon, shared singleton service host, and external/adopted process; state owner, lifetime, cleanup authority, restart/adoption policy, and whether it may outlive the caller. 3. Define the first-class ManagedService contract: stable service-kind/id/scope identity; lifecycle states starting/running/draining/stopping/stopped/failed; endpoint/protocol identity; readiness and heartbeat; process ownership proof; client lease acquire/renew/release/expiry; safe status; and transition/version rules. 4. Separate responsibilities: foundation atomically stores state, tracks leases, verifies liveness/ownership, coordinates start-or-attach/drain/stop, and emits neutral facts; components supply launch declaration, health handshake, authorization, work/session quiescence facts, and domain shutdown policy. 5. Define durable redacted process/service journals: component, resource kind/id, PID/start/create time, command fingerprint/redacted argv, cwd, env redaction policy, endpoint/token reference, parent/session/group/job identity, ownership proof, heartbeat/status timestamps, lease counts, and cleanup result. 6. Define safe process-tree operations: prefer OS process groups/job objects where owned; psutil is optional for richer inspection; never reap by image name alone; require journal, command fingerprint, endpoint handshake, or lock-held lease proof. 7. Define shared-service coordination: same-lock start-or-attach and lease registration; final quiescence/lease re-check before stopping; stale lease handling; PID reuse protection; incompatibility/version outcomes; detached lifetime from the starter's process group. 8. Specify narrow foundation APIs and observability records, with no MCP or component-domain imports. 9. Add architecture tests prohibiting ad-hoc process/daemon/client-registry lifecycle implementations outside foundation/runtime-owned seams. 10. Review this contract before PR06/PR07 implementation.

## Validation

1. Design explicitly separates ManagedProcess from ManagedService, and supervised child, detached supervisor, shared singleton, and external/adopted lifecycles. 2. Every stop/reap requires ownership proof. 3. Service lifecycle defines exactly one lock/transition authority across start, attach, renew, release, drain, and stop. 4. Windows and POSIX differences are documented and tested. 5. psutil remains optional with safe degraded outcomes. 6. PR04, SH04/SH05/SH10, and AS08 can consume the same contract without inventing journals, discovery records, refcounts, or reapers. 7. Architecture checks catch direct taskkill/pkill, process-name reaping, or component-local shared-service lifecycle implementations.

## Effort & Risk

Complex but bounded when split: PR05 designs the contract, PR06 implements durable service state/leases, and PR07 implements process-backed start-or-attach/shutdown. Avoid a generic workflow engine, remote RPC framework, or component-domain scheduler in foundation.

Architecture Standards §§1,3,4,5,6,7; Observability Standards; AR25 protocol-adapter isolation.
