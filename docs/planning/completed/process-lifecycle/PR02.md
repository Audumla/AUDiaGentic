# Collapse per-MCP-server process chain and stop console-window flashing

## Description

Each stdio MCP server spawns a 4-process chain on Windows: audiagentic.exe (setuptools/uv console-script stub) -> .venv pythonw trampoline -> uv base python.exe, PLUS a conhost.exe (console allocated because the stub is a console-subsystem exe -> visible window flash). With ~16 servers x N providers that is ~64+ processes and repeated console flashes. component_mcp_launch() emits command='audiagentic' which resolves to the exe stub. Base python -m audiagentic cannot be used directly because the package lives in the venv, so the venv interpreter must stay in the chain.

## Steps

1. Change foundation/mcp/launch.component_mcp_launch to emit command=<venv pythonw.exe> and args=('-m','audiagentic','mcp',module,*extra). pythonw is GUI-subsystem -> no console allocated -> no conhost, no window flash; stdio pipes still inherited so stdio MCP works. Drops the setuptools exe-stub layer (and its conhost). Net per-server 4 procs -> 2.
2. Resolve the venv pythonw path at projection time (sibling of sys.executable; fall back to python.exe if pythonw absent, e.g. POSIX).
3. Regenerate provider MCP configs (reconcile) so .mcp.json / opencode.json pick up the new command form.
4. Verify FastMCP stdio server still starts under pythonw (no console) and logging still flows to the log file, not a console.

## Files

src/audiagentic/foundation/mcp/launch.py
src/audiagentic/components/providers/services/mcp_projection.py (consumer — verify args threading)

## Validation

Start a provider; assert each ag-* server is a single pythonw.exe (+venv trampoline) with NO conhost.exe and NO flashing window; tools still callable. Cross-check on opencode + pi.

## Effort & Risk

Simple/low. Pure config-generation change; Job Object teardown (PR01) already reaps whatever spawns. Risk: pythonw path coupling — mitigated by regenerating on launch. POSIX unaffected (no pythonw/console concept; keep python).
