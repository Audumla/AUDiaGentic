# Foundation layering, lease semantics, and atomic state for cross-process coordination

## Notes

Foundation-level design review. Must be resolved before PR06 implementation begins.

## Findings

## Architecture Standards Review — PR05

### Strengths
- Correctly separates ManagedProcess (owned/adopted OS process) from ManagedService (discoverable long-lived with many clients)
- Foundation owns domain-neutral mechanics; consumers own policy — correct layering (§3)
- Ownership proof required for every stop/reap — no ad-hoc kill (§4, §6)
- Durable redacted journals for observability (§7)
- Cross-platform (Windows/POSIX) documented and tested

### Concerns to resolve before PR06 implementation

**1. Foundation vs Component boundary (§3: layering)**
The item says "foundation atomically stores state" — but the foundation currently has no durable storage abstraction outside of file I/O. For cross-process coordination (start-or-attach, leases), the foundation needs a per-service lock and atomic state file. This should use the existing foundation/system/process.py StartupLock pattern or a new foundation/system/atomic_file_store.py. Do not introduce a database or external dependency.

**2. Lease semantics vs session semantics (§4: no domain leakage)**
The item defines "client lease acquire/renew/release/expiry" — but this must not overlap with session-level concepts from AS08. A ManagedService lease means 'this client process is connected/depends on the service', NOT 'this client has a conversation turn pending'. The lease is about process-level dependency, not work-level queuing.

**3. Epoch/version stale-writer rejection (§7: atomic transitions)**
The item mentions "monotonically advancing epoch/version" — this is critical for cross-process correctness. Must use file-based atomic compare-and-swap (write new version to temp file, rename atomically). On Windows, this requires the same StartupLock pattern (open with FILE_SHARE_DELETE=0).

**4. Callback interface design (§5: config-over-code)**
The item says "components supply launch declaration, health handshake, authorization" — these should be declarative callback registrations in the consumer's descriptor, not imperative API calls. Consider having consumers register callbacks via a foundation.register_managed_service() call at startup.

**5. Testability without real processes (§6: test isolation)**
The item needs test fakes for time, liveness, and locks — this is correct but must go further: PR06 should be independently testable with fake process IDs, fake locks, and fake file stores, so the state machine can be exercised without any OS-level process management.

**6. Connection to AS15 concurrency model (§1: consistency)**
The AS15 change (session-aware profile concurrency) introduces a new concept: 'idle' vs 'active' compute. PR05's ManagedService should have an equivalent concept for services: 'draining' state where no new leases are accepted but existing clients remain connected. This maps to the AS15 pattern of releasing capacity while maintaining connection.
