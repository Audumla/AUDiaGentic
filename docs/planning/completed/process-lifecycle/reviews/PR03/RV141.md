# PR03 design review: shared daemon conflicts with self-cleanup; in-process consolidation is the cleaner path

## Notes



## Findings

1. LIFECYCLE CONTRADICTION: the daemon must be detached from PR01's Job Object to survive host teardown, which means nothing kernel-enforced ever reaps it. The spec acknowledges this (challenge 3) but has no crash-recovery or orphan-sweep design — validation (d) demands survival, yet a wedged/leaked daemon has no reaper. A 'cleans up after itself' guarantee is structurally impossible without adding a watchdog or gc command, i.e. more lifecycle machinery to solve a problem PR01 already solved for the stdio path.
2. WRONG MULTIPLIER TARGETED: process multiplication is ~16 ag-* servers x N clients. N is typically 1-2; the 16x per-client fan-out is the dominant factor and does NOT require cross-client sharing. A single combined stdio MCP server per client (one FastMCP process mounting/registering all ag-* component tool sets, lazy-imported) collapses 16xN -> 1xN while remaining a child of the host: kernel teardown via PR01 Job Object still applies, no HTTP surface, no tokens, no idle-exit race, no multi-project root problem (process-scoped root stays valid), no thread-safety retrofit (still one client per process). This option is absent from the spec's Steps and should be evaluated first.
3. SECURITY GAPS in the HTTP design as spec'd: (a) the lockfile advertising {pid, port, token} is a credential leak unless created 0600/user-ACL-restricted — not stated; (b) Streamable HTTP requires Origin-header validation to prevent DNS-rebinding even on 127.0.0.1 — missing; (c) pid-reuse TOCTOU on find_pid_on_port/stale-PID detection — token handshake mitigates but should be stated as the authoritative liveness check.
4. SCOPE REDUCTION IF EVER BUILT: choose option (a) from challenge 1 — one daemon-set per project root — and delete per-session root injection entirely. That removes challenge 1 (multi-project), most of challenge 2's cross-project state surface, and the component_server.py project_root_from_env() per-request rework. Multi-project session-root injection is the single largest risk item and buys little.
5. Secrets concern (challenge 5, GITHUB_TOKEN) is largely moot: the github server is external stdio (gh) and stays per-client per challenge 7; audit which ag-* servers actually carry secrets before designing per-session injection.

## Conclusion

Agree with the item's own Notes: do NOT build the daemon. The cleanest compliant/safe/self-cleaning MCP management is (1) keep stdio children under PR01 Job Object teardown — kernel-enforced cleanup, zero daemon lifecycle; (2) if process count still hurts, add a new item for in-process consolidation: one combined stdio ag-* server per client (16xN -> 1xN) with tool-set filtering per provider config — it keeps every self-cleanup property by construction; (3) retain PR03 as a design record, amended to per-project-root daemon scope only, gated on evidence that concurrent multi-client sharing of expensive state (e.g. coding_lsp language servers) is common.
