# PR07 lifecycle review: lock held through readiness polling; Windows breakaway hard-fail is a deployment blocker for SH05; unprovable-owner wedge; smaller cleanups

## Notes

T3 review of managed_service_start.py, managed_service_shutdown.py, managed_process.py, managed_service_owner.py (RV588 addition) and the lifecycle facade. Positives first: ownership-proof discipline (PID + non-PID evidence) is consistently enforced on every signal path; decoy safety and classified stop outcomes match the PR05 contract; ManagedServiceOwner was correctly placed in foundation and is already reused by the SH04 gateway host instead of being duplicated there.

## Findings

1) LOCK-HOLD: ManagedServiceStarter.start_or_attach (managed_service_start.py:75) holds the per-service cross-process StartupLock for the entire launch + _wait_ready readiness poll. With ManagedServiceDeclaration.readiness_timeout default 15.0 and store lock_timeout default 30.0, a consumer that raises readiness_timeout (a slow model-loading service is the expected case for the shared rig) makes every concurrent attacher fail with a raw StartupLock timeout error — an unclassified failure, not a 'busy/starting' disposition. Nothing validates readiness_timeout against lock_timeout. Implementation-ready fix options (either is fine): (a) validate at start_or_attach that declaration.readiness_timeout + margin <= store lock timeout and raise a classified config error otherwise; (b) release the lock after 'service.process-launched' is written and let waiters observe state=starting with live process evidence, re-acquiring for the running transition. Option (b) matches the contract's epoch/CAS design and removes the serialization; option (a) is the minimal guard. 2) WINDOWS BREAKAWAY: launch_detached (managed_process.py:148) unconditionally sets CREATE_BREAKAWAY_FROM_JOB when detached. PR07's own validation records that client Job Objects on the host deny CREATE_BREAKAWAY_FROM_JOB — and supervised_process.py runs harness children under kill-on-close Job Objects, which is exactly where SH05 auto-launch will execute. On such hosts Popen raises OSError and the record is marked failed: the shared service can never start. Needs a classified path: preflight-query the current job's breakaway policy (QueryInformationJobObject, JOB_OBJECT_LIMIT_BREAKAWAY_OK/SILENT_BREAKAWAY_OK) or retry without the breakaway flag and record a degraded fact ('service dies with starter's job') so consumers can decide; plus an error-resolutions.yaml entry. This should be resolved before SH05 depends on auto-launch. 3) UNPROVABLE-OWNER WEDGE: when a recorded PID is alive but process_creation_identity returns None (OpenProcess denied — e.g. service started from another user session; or /proc read denied), ownership_matches is false: _try_attach raises CON-MSVC-028 forever, stop_if_quiescent returns ownership-unverified forever, and ManagedServiceOwner.claim refuses. There is no guarded operator escape hatch. Recommend a narrow, explicitly-invoked reset operation (record-only: mark failed + clear process evidence, never signal the PID) surfaced later via SH10 diagnostics. 4) ZOMBIE/HANDLE: launch_detached drops the Popen object; on POSIX the detached child remains our child, so its exit leaves a zombie for the starter's lifetime (PR07 classified zombies as dead in pid_alive — correct — but the entry lingers; a double-fork or periodic os.waitpid(WNOHANG) in the starter would remove it). Same function: on identity-unavailable it calls process.terminate() without wait(), leaving the same zombie. 5) MINOR: _wait_ready's declaration=None default (managed_service_start.py:248) with a hidden 0.25s timeout is dead code — every caller passes declaration; make the parameter required. 6) MINOR/DRY: the record-reclaim block (fresh epoch, clear process/endpoint/health/failure, expire leases) is duplicated between ManagedServiceStarter._prepare_restart and ManagedServiceOwner.claim; extract one helper next to the store so restart semantics stay single-sourced. 7) STRUCTURE: starter/shutdown/owner all reach into ManagedServiceStore private members (_lock, _read_unlocked, _write_unlocked, _acquire_lease_unlocked, _check_epoch, _clock). The single-transition-authority invariant would be better expressed as an explicit internal locked-session API on the store; as written, ruff SLF001-style checks can never be enabled for this package and the privacy boundary is fictional.

## Conclusion

Valid and handled. Start validates the readiness window against the lock budget; Windows breakaway denial has an observable session-child fallback; exited children are asynchronously reaped and Windows liveness uses GetExitCodeProcess; _wait_ready requires a declaration; restart-record construction is centralized. Guarded unprovable-owner reset is assigned to SH10 and remains record-only. The proposed public locked-session API was intentionally not added: starter/shutdown/owner are cohesive package-internal transaction coordinators, and exposing a broader lock surface would increase misuse and abstraction without changing the single-authority invariant.
