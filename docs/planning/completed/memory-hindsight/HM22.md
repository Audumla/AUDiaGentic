# Route Goose Hindsight through the standard remote MCP recipe

## Description

Goose was the last provider not reaching Hindsight through the shared remote
MCP recipe. Its provider adapter could only serialize stdio-shaped MCP entries,
so a url-form entry silently lost its endpoint, and the routing fell through to
`hindsight-managed-mcp-stdio.yaml`.

Fixed by teaching the **Goose adapter** Goose's own documented remote extension
format. Hindsight was not involved: it keeps declaring the same
provider-neutral `managed-mcp` step, and the harness manifests it.

## Notes

Superseded scope: this item originally proposed deleting
`hindsight-managed-mcp-stdio.yaml` on the grounds that `hindsight-mcp` does not
exist. That was built on a misread of `INSTALL_MAP.md:69`, which is scoped to
the *local* Hindsight server, not a claim that no stdio MCP exists. The recipe
is left untouched; with Goose fixed nothing routes to it, so if it is genuinely
unused it can be retired later on evidence rather than on inference.

Corrections recorded during this work, all caught by the user:

- Claimed Goose had *lost* `remote: true` in the PC01-PC04 migration. Wrong —
  the flag was present; the survey read the wrong YAML path.
- Claimed pi needed a Docker probe before its transport could be declared.
  Wrong standard: `transports` describes what our own reader/writer implement,
  which is readable from source.
- Claimed Goose's HTTP support was unknown to this repo. Wrong — `INSTALL_MAP.md`
  §9 states it explicitly, with the exact config shape, and carries a
  "Not stdio-only" correction column. The answer was in the component being
  edited the whole time.

## Architecture Confirmed While Doing This

Two directions, both verified rather than assumed:

- **The harness knows nothing about Hindsight.** `adapters/goose/` contains zero
  Hindsight references; `mcp_format.py` translates a provider-neutral
  `McpServerEntry` to and from Goose's spelling and has no idea what server is
  being registered or why.
- **Hindsight edits nothing directly in a harness.** Audited every step across
  all nine recipes: every `path:` is under `~/.hindsight/` — Hindsight's own
  config — and every harness-side change goes through a `provider:` step
  (`managed-mcp`, `managed-hooks`, `generated-surface`), i.e. is manifested by
  the harness adapter. No recipe writes a harness config file.

## What Changed

`src/audiagentic/components/providers/adapters/goose/mcp_format.py`:

- `extensions` is a **mapping keyed by name**, per Goose's documented config
  form. The previous code treated it as a list, which meant `read_goose_yaml`
  would have called `.get()` on a string against a real Goose config — that
  adapter had almost certainly never round-tripped a genuine file.
- Remote entries serialize as `type: streamable_http` with `uri` and `headers`;
  stdio entries keep `cmd`/`args`/`envs`. `sse` is read-tolerated (Goose retains
  it for compatibility) but never written.
- Reads still accept the legacy list shape, because earlier versions of this
  module emitted it into real user configs; writes normalise it to the mapping
  form.
- Unrelated extensions and unrelated top-level settings are preserved.

`src/audiagentic/config/providers/goose.yaml`: `transports: [stdio, http]`,
citing Goose's documented Streamable HTTP extension.
