# Review: split recipe strategies by concern (pending)

## Notes

All line references verified 2026-07-03 against the working tree; HM10/HM11 will shift them — locate by symbol name (Grep) not line number when implementing. Standards references: docs/standards/ARCHITECTURE_STANDARDS.md §2 (registry over if/elif), §3 (god object), §4 (no hardcoded editor paths), §8 (AudiaGenticError only), §9 (module-level logger), §10 (atomic migration).

## Findings

1) JUSTIFIED BUT CORRECTLY LAST: the 1596-line recipes.py confirms the monolith (Standards §3 god object), and the item's guard — don't start as a pure file shuffle while HM10/HM11 duplication remains — is the most important constraint. After HM10/HM11, re-inventory before splitting: if the module lands under ~800 lines, a 2–3 module split (strategy+factories, recipe classes, orchestration/status) is sufficient; do NOT pre-commit to the six-module list in the item.
2) §2 CONFIG OVER CODE — REPLACE THE KIND-BRANCH CHAIN (BINDING): `build_hindsight_recipe` (recipes.py:1017-1093) is an if/elif chain on `row.recipe_kind`, explicitly prohibited by Standards §2. DIRECTIVE: module-level registry `_RECIPE_FACTORIES: dict[ProviderRecipeKind, Callable[[HindsightRecipeRow, HindsightBackendConfig, str, Path | None], Any]]` with one factory function per kind (HOOKS and WRAPPER_CLI may share one; MCP_CONFIG and HYBRID may share one); dispatch is `_RECIPE_FACTORIES.get(row.recipe_kind, _guidance_factory)(row, backend, provider_id, project_root)`. Source gates and platform gates stay as explicit named functions called inside factories — never inline re-implemented per factory.
3) §4 PLATFORM INDEPENDENCE VIOLATION — `_repair_windows_plugin_mcp` (recipes.py:335-393) hardcodes Claude-specific filesystem paths in Python: `~/.claude/plugins/cache/hindsight/hindsight-memory/*/.mcp.json` and `%APPDATA%/Claude/plugins/data/hindsight-memory`. DIRECTIVE: move both path patterns into the claude row of `config/components/memory/hindsight_matrix.yaml` as new row fields (suggested: `plugin_repair_glob`, `plugin_data_dir`; add them to `HindsightRecipeRow` and the YAML loader); make the repair function generic over row data and a no-op when the fields are empty. Move the function-local `import glob/json/os` to module top (§9 style). The repair invocation moves out of `_PluginUrlConfigRecipe.configure` into the plugin recipe module this item creates.
4) §2/§4 — `_platform_supported` (recipes.py:928-948) does substring matching ('macos' in constraint.lower()) over free-text constraint strings. DIRECTIVE: normalize `platform_constraints` in hindsight_matrix.yaml to the canonical `platform_key()` values exactly — 'darwin', 'linux', 'win' — and reduce the function to `return not row.platform_constraints or platform_key() in row.platform_constraints`. Migrate the YAML rows in the same change (§10 atomic migration). Add a unit test that a row with ['darwin','linux'] gates out on win.
5) §8/§9 IN THIS MODULE: recipes.py has NO module-level logger — add `logger = logging.getLogger(__name__)` at module scope; all new modules created by the split get one. `_command_parts` (recipes.py:57-63) raises raw `ValueError` at a public boundary — replace with `make_error()` from foundation.contracts.errors carrying a canonical code (check foundation/contracts/errors.py and canonical_ids.py for the existing prefix convention for the memory component before allocating a new code; follow it exactly — do not invent a new prefix style). `HooksInstallerRecipe.probe`'s `except Exception` (line 143) wraps a subprocess probe (external boundary, allowed by §8) but must log `logger.warning(..., exc_info=True)` before returning the failure.
6) BRITTLE CONFIG PATH: matrix.py:19 locates the YAML via `Path(__file__).resolve().parent.parent.parent.parent / 'config' / ...` — a four-level parent chain that silently breaks if this module moves (which HM12 does to sibling modules). DIRECTIVE: before writing a new mechanism, Grep for how other components resolve `config/components/*` paths (e.g. search `config" / "components` and `importlib.resources` under src/audiagentic) and use the SAME mechanism; only if none exists, use `importlib.resources.files('audiagentic.config')`. Do not leave two config-resolution idioms in the codebase.
7) VALIDATION KEEPERS: the kind-coverage test ('every ProviderRecipeKind used by the matrix has a registered factory or intentional guidance-only fallback') becomes trivial to write against `_RECIPE_FACTORIES` from finding 2 — assert `set(kinds used in HINDSIGHT_RECIPE_MATRIX) <= set(_RECIPE_FACTORIES) | {kinds intentionally falling back}`. Write it as part of finding 2, not at the end.
8) IMPORT-CYCLE RISK is real given matrix.py already imports from providers.services.recipes; keep matrix/base types dependency-light: matrix.py and the recipe base module must not import the orchestration module.

## Conclusion

Keep pending and last (P2 is right), but the standards violations in findings 2–5 are defects, not style preferences — they are the actual content of this item; the file split is secondary and should be re-sized after HM11. Execution order for the implementer: finding 2 (factory registry + coverage test), 3 (config-driven repair paths), 4 (canonical platform keys), 5 (logger/error codes), 6 (config path mechanism), then split modules only as far as the post-HM11 line count justifies.
