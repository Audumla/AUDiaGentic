## Findings

1) PREMISE CONFIRMED AT SCALE: recipes.py is 1596 lines — by far the largest module in memory/hindsight (next is mcp_recipe.py at 257) — and carries its own recipe base, stamping, and provision/teardown loops as described. The duplication is not hypothetical.
2) THE KEY RISK IS THE RIGHT ONE: ProviderRecipeResult's source/action-needed metadata has no home in foundation RecipeResult. Centralize conversion before deleting local flows. If the generic registry lacks hooks, extend the generic contract rather than keeping local orchestration — treat this as BINDING, not optional.
3) ORDERING CONSTRAINT: overlaps HM10 on recipes.py and tests; land HM10 first.
4) EXACT DELETION LIST (line refs verified 2026-07-03; re-verify with Grep after HM10 lands):
   a. `_run_provision` (recipes.py:1170-1205) is a verbatim copy of `ProviderRecipeRegistry.install` (providers/services/recipes.py:274-308). `_run_teardown` (recipes.py:1208-1230) copies `ProviderRecipeRegistry.uninstall` (providers/services/recipes.py:326-333). DIRECTIVE: in `apply_hindsight` call `registry.install(recipe.provider_id, 'hindsight', recipe.backend_id, ctx)`; in `teardown_hindsight` call `registry.uninstall(...)`; DELETE both local functions. The one behavioral difference — `_run_teardown` reads `recipe._row.audia_action` into the failure's action_needed — must move into `to_result`/stamping (see 5b), not stay as a reason to keep the copy.
   b. `apply_hindsight` / `teardown_hindsight` / `prune_hindsight` (recipes.py:1233-1308) triplicate registry construction + provider-filter loop. DIRECTIVE: extract one private helper `_reconcile(project_root, op, *, backend, provider_ids, context)` where op selects registry.install / registry.uninstall / recipe.prune; the three public functions become thin wrappers. Public signatures unchanged.
5) BASE-CLASS UNIFICATION (Standards §3: >80% field overlap must unify):
   a. `_RowRecipe` (recipes.py:66-109) re-declares provider_id/capability_id/backend_id/recipe_kind/display_name/source_url/source_date — the exact attribute set of `ProviderCapabilityRecipe` (providers/services/recipes.py:121-158). DIRECTIVE: make `_RowRecipe` subclass `ProviderCapabilityRecipe`; __init__ calls `super().__init__(row.provider_id, 'hindsight', recipe_kind=…, display_name=row.display_name, source_url=row.source_url, source_date=row.source_date)` and keeps only `self._row = row`.
   b. `_stamp` (recipes.py:90-109) re-implements `ProviderCapabilityRecipe.to_result` (providers/services/recipes.py:181-192) adding only action_needed. DIRECTIVE: delete `_stamp`; override `to_result` ONCE in the Hindsight base to add `action_needed=getattr(base, 'action_needed', '') or self._row.audia_action`; rename all `self._stamp(x)` call sites to `self.to_result(x)`.
   c. DELETE `RulesOnlyRecipe.to_result` (recipes.py:854-855) — it returns base unchanged, silently dropping provenance stamping; inconsistent with every sibling and superseded by 5b.
6) SIX-SITE SOURCE-GATE/STEP-RUN DUPLICATION: the block `if source_status != 'verified': refuse → params = _hindsight_params(backend) → _steps_from_defs → CompensatingSequence(steps).run(ctx) → map ok/fail` appears in HooksInstallerRecipe.install (146-165), HooksInstallerRecipe.uninstall (181-201), PluginConfigRecipe.install (254-270), PluginConfigRecipe.uninstall (286-303), _PluginUrlConfigRecipe.install (489-503), _PluginUrlConfigRecipe.uninstall (541-556). DIRECTIVE: one protected helper on the Hindsight base — `_run_step_defs(step_defs, context, *, ok_state: RecipeState, ok_status: str, fail_prefix: str) -> ProviderRecipeResult` — with the source gate inside it; all six sites call it. Semantic note the helper must preserve: install refuses with FAIL when unverified, uninstall returns OK/ABSENT when unverified (nothing was ever installed) — pass this as a flag, do not flatten it.
7) CLASS MERGE: `_PluginUrlConfigRecipe` (413-567) duplicates `PluginConfigRecipe` (227-332): identical install/uninstall and `_should_run_plugin_command` (251-252 vs 473-474); it differs only in probe/configure/verify/prune around the url-config file. DIRECTIVE: merge into one `PluginConfigRecipe` taking optional `url_config_path` and optional `HindsightTarget`; behavior selected by which is set; delete `_PluginUrlConfigRecipe`. Update `build_hindsight_recipe` call sites.
8) HAND-BUILT RESULTS: `GuidanceOnlyRecipe` (651-713) and `RulesOnlyRecipe` (716-855) construct ProviderRecipeResult inline with source_url/source_date/action_needed repeated across ~12 method bodies instead of stamping. DIRECTIVE: after 5a–b land, route every result in these classes through the base to_result/stamped ok/fail helpers so provenance is set in exactly one place.
9) `_CompositeRecipe` (1381-1539): probe/install/configure/verify/uninstall/prune each repeat the same two-result merge. DIRECTIVE: one `_combine(mcp_result, rules_result, *, state)` helper; the six methods become one-liners.
10) MISSING VALIDATION — DELETION PROOF: add a test asserting `_run_provision`, `_run_teardown`, `_stamp`, and `_PluginUrlConfigRecipe` no longer exist in the module namespace (e.g. `not hasattr(recipes_module, name)`), so partial consolidation cannot pass. Standards §10: no parallel paths may survive the change.
