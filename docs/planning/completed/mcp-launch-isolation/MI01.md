# Freeze MCP projection and launch-isolation semantics

## Description

Characterize every MCP discovery and launch path before changing ownership. Define the current use cases precisely: native harness launch with enabled functional tools, AUDiaGentic bootstrap launch with installed management tools, and internally dispatched jobs with an explicit curated subset. This item is analysis and executable characterization, not a new abstraction or migration.

## Steps

1. Inventory every reader, writer, refresher, and launcher for `.audiagentic/mcp.json`, project `.mcp.json`, `.opencode/opencode.json`, `OPENCODE_CONFIG_CONTENT`, Pi global/project discovery, direct Pi/OpenCode runners, `pi-acp`, and `opencode acp`.
2. Record artifact owner, lifetime, projection, precedence, mutation policy, and launch consumers in a checked-in ownership matrix.
3. Define three distinct projections: `management` (installed component management servers), `functional` (installed and enabled harness-facing servers), and `curated` (an explicit subset supplied by a current job request). Do not infer curated entries from a future role model.
4. Verify installed Pi and OpenCode versions on Windows and in clean Linux containers. Capture actual discovery precedence and whether each launch route can suppress all ambient/global/project servers.
5. Reproduce the reported `ag_project_mgmt_list_components` timeout through the real AUDiaGentic CLI/Pi host path. Compare it with the passing direct stdio server smoke, and identify whether startup, adapter patching, lazy connection, naming, or transport timeout is responsible.
6. Record a capability outcome per provider and launch kind: `exclusive`, `additive-only`, or `unsupported`, with evidence and a safe diagnostic reason.

## Detailed Solution & Technical Design

Treat durable native configuration and ephemeral launch configuration as different lifecycles. `.audiagentic/mcp.json` is currently an AUDiaGentic-owned Pi management file, not a generic provider projection. Project `.mcp.json` and `.opencode/opencode.json` belong to durable provider/native-terminal materialization. A job surface must not mutate either class.

The matrix must state whether a mechanism is native, patched, bridge-forwarded, or unavailable. Documentation alone is insufficient; use installed CLI help/source plus an end-to-end visibility comparison containing a sentinel ambient server that must not appear in the isolated launch.

## Effort & Risk

Medium effort, high diagnostic value. Real CLI probes can mutate user state if home isolation is incomplete; use disposable homes and container gates.

## Standards

Architecture Standards §§1, 3, 4, 6, 7 — evidence-led scope, one artifact owner, provider boundary, proportionate enforcement.

## Notes

Present trigger: Pi-hosted management calls time out while the same MCP server passes direct stdio smoke. Future role assignment is context only and is not implemented here.

## Characterization Outcome

Direct stdio smoke passed for every component MCP server, including
`ag-project-mgmt/list_components`. A real installed-Pi RPC launch initially
failed before its first response because Pi auto-loaded a user adapter in
addition to AUDiaGentic's explicit adapter. With ambient extension discovery
disabled by the isolated surface, Pi returned `get_state` successfully in
under the 15-second probe bound. OpenCode 1.18.3 resolved exactly the requested
management set under its isolated environment. Durable native functional
projection remains separate from both launch mechanisms.
