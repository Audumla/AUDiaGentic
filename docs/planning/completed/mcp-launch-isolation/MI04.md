# Separate Pi native defaults from direct-launch job isolation

## Description

Preserve Pi as a useful native interactive front end while making every AUDiaGentic-owned direct Pi launch use a job-specific MCP file. Remove the current misuse of shared `.audiagentic/mcp.json` as an isolated surface.

## Steps

1. Using MI01 evidence, freeze Pi’s native terminal/default behavior and the exact purpose of `.audiagentic/mcp.json`.
2. Keep durable native functional MCP projection in the provider-owned/default Pi surface required for a user invoking Pi directly. It contains installed-and-enabled harness-facing tools and preserves unmanaged user content according to the managed-config owner.
3. Keep AUDiaGentic bootstrap behavior explicit: `audiagentic launch` selects management entries and requests an isolated surface instead of relying on ambient/default discovery.
4. Change Pi `prepare_mcp_surface` to serialize `request.entries` atomically into `<request-runtime-root>/pi/mcp/<launch-id>.json` or an equivalent provider-owned path.
5. Pass that exact path through `--mcp-config`; load only required extensions and require exclusive discovery for isolated launches.
6. Prepare once and reuse the result in command and environment construction. Remove the duplicate patch/materialization calls in the Pi runner.
7. Make the exclusivity patch version/precondition checked, idempotent, syntactically validated, and concurrency safe. If the installed Pi cannot guarantee exclusivity, report additive-only and fail required-isolation launches before starting Pi.
8. Update Pi request-runtime metadata so `project-mcp-path` is not misrepresented as the active job surface; use a neutral job-surface reference only if an internal consumer genuinely needs it.
9. Ensure cleanup removes only the request-owned file and never native/default or user configuration.

## Detailed Solution & Technical Design

There are two non-overlapping artifact classes:

- Durable native/default Pi configuration: provider-managed, functional projection, usable when the operator launches Pi from a terminal.
- Ephemeral AUDiaGentic launch file: provider-generated from explicit entries, unique per job, immutable after child start, deleted with request runtime.

`.audiagentic/mcp.json` must not be both. If MI01 proves it has no remaining independent native consumer, migrate/delete it rather than retaining a misleading compatibility file. If it remains the intentional bootstrap default, document that it is durable management projection and never use it for isolated jobs.

## Files

- Pi provider `mcp_surface.py`, serializer/patch implementation
- Pi runner command and request-runtime metadata
- Pi install/refresh ownership only where MI01 proves necessary
- Pi unit, integration, concurrency, and real-CLI tests

## Validation

- Native terminal Pi sees enabled functional tools.
- AUDiaGentic bootstrap Pi sees management tools and no functional/global sentinel.
- Two simultaneous launches with disjoint entries remain disjoint on disk and in visible tools.
- Empty curated set yields zero MCP servers, not ambient fallback.
- Patch unavailable/anchor changed produces a pre-launch isolation failure.
- Direct `ag-project-mgmt/list_components` returns within the bounded host timeout.
- Windows path quoting, spaces, cleanup, crash retention/cleanup policy, and Linux Docker behavior pass.

## Effort & Risk

Large. Pi is preferred for lightweight jobs, so additive fallback is not acceptable for internally isolated work. Third-party patch drift is the primary risk.

## Standards

Architecture Standards §§2–7; HA02 remains authoritative for durable Pi runtime/provider artifact ownership.

## Implementation Finding

A real installed-Pi RPC probe on 2026-07-23 initially failed before responding:
Pi auto-discovered a user copy of `pi-mcp-adapter` while AUDiaGentic loaded the
system adapter explicitly, causing duplicate `mcp` tool and `--mcp-config` flag
registration. The isolated provider surface must carry `--no-extensions`
itself, not rely on one interactive runner to add it, so direct and ACP-wrapper
children both suppress ambient extensions before loading the explicit adapter.
