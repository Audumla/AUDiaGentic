# Move neutral MCP projection collection to foundation

## Description

Move the component-descriptor-to-MCP-entry selection primitive out of `runtime.harness` because it now has two independent consumers: interactive launch composition and `components.agents` job dispatch. Preserve projection policy explicitly and prevent provider or harness mechanics from entering foundation.

## Steps

1. Introduce a foundation-owned projection request/result with a small declared projection enum or equivalent typed selector for the evidenced `management` and `functional` cases.
2. Move descriptor traversal, install/enabled gating, external requirement checks, probe-result checks, and `McpServerEntry` construction to foundation.
3. Preserve management semantics: core or installed components contribute `propagate: audiagentic` management servers even when disabled, so disabled components remain manageable.
4. Preserve functional semantics: provider/harness-facing capability servers require installed and enabled state and the matching propagation target.
5. Return a deterministic name-keyed result and reject duplicate conflicting declarations rather than silently accepting order-dependent last-wins behavior.
6. Update all runtime install/refresh/direct-launch consumers and tests to the new foundation API; delete `runtime.harness.mcp_collector` and compatibility imports in the same migration.
7. Add an architecture test proving foundation imports no component, provider, or runtime-orchestration implementation.

## Detailed Solution & Technical Design

Foundation owns only the neutral operation “project component declarations to launchable MCP entries under an explicit projection policy.” It must not know Pi/OpenCode configuration formats, ACP, jobs, roles, provider IDs, CLI flags, or output paths.

Curated subsets are supplied as concrete entries by the requester after collection. Do not add role IDs, allow/deny expressions, or a general policy engine. A later role-capabilities item can select from the deterministic available set without changing provider adapters.

## Code Samples & Guidance

```python
available = collect_component_mcp_entries(
    project_root,
    projection=McpProjection.MANAGEMENT,
)
```

`components.agents` may import this foundation operation. Provider adapters must not call it; adapters materialize entries already selected by their caller.

## Files

- New module under `src/audiagentic/foundation/mcp/`
- Delete `src/audiagentic/runtime/harness/mcp_collector.py`
- Runtime Pi/OpenCode install and runner callers
- Foundation and architecture tests; migrate harness collector tests

## Validation

- Installed-disabled management component remains present.
- Installed-disabled functional component is absent.
- Missing external executable and failed probe are excluded deterministically.
- Duplicate-name conflicts fail with a registered foundation-owned error.
- No `audiagentic.components` or runtime-orchestration import from foundation.
- Existing native install/refresh projections remain byte-for-byte equivalent where ordering is normalized.

## Effort & Risk

Medium. The main risk is conflating management and functional gating; golden tests must cover both explicitly.

## Standards

Architecture Standards §§1–3, 6–7; Architecture Guidelines foundation placement and narrow typed seams.
