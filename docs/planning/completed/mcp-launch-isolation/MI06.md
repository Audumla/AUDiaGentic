# Compose OpenCode native and ACP isolated surfaces

## Description

Preserve OpenCode’s native terminal functional configuration while making direct and ACP AUDiaGentic launches use a fully composed per-process override. Resolve the existing collision where model/provider setup and MCP isolation both write `OPENCODE_CONFIG_CONTENT`.

## Steps

1. Freeze the durable `.opencode/opencode.json` ownership and native terminal projection of installed-and-enabled functional tools.
2. Define one OpenCode provider-private document composer that starts from the required safe project/provider/model snapshot, resolves permitted environment placeholders, removes unsafe/global fallback, and overlays the curated MCP selection.
3. Enumerate every MCP server discoverable from project/default config and explicitly disable all unselected names. Add selected local entries with command, arguments, redacted environment handling, and `enabled: true`.
4. Emit exactly one `OPENCODE_CONFIG_CONTENT` value per process. Direct runner and `opencode acp` call the same composition primitive; generic provider services never merge JSON or environment-key collisions.
5. Confirm behavior for an empty curated set, malformed project config, remote MCP entries if currently supported by the launch contract, and user global config.
6. Keep the operation read-only with respect to durable `.opencode/opencode.json`; no per-job file is needed unless empirical evidence invalidates inline isolation.
7. Report unsupported rather than silently degrading if an installed OpenCode version changes inline-config precedence or disabling semantics.

## Detailed Solution & Technical Design

OpenCode’s job-isolation mechanism is ephemeral environment configuration. Native terminal behavior remains durable provider configuration. The adapter owns both schemas but their lifecycles remain separate.

The composer must preserve the model and enabled-provider whitelist currently created by `acp.py`; the MCP builder must not overwrite it. Conversely, the model builder must not discard MCP suppression. The output is deterministic JSON suitable for exact unit assertions with secret values redacted from diagnostics.

## Files

- OpenCode `acp.py`, `mcp_surface.py`, and provider-private composer
- Direct runner integration

## Validation

- Native terminal OpenCode sees enabled functional tools.
- Bootstrap launch sees only management tools.
- Internal curated/empty launches show exactly the requested/zero tools.
- Model selection, custom provider config, and enabled-provider whitelist remain intact.
- Ambient project/global sentinel servers are disabled and never contacted.
- Two concurrent processes with different inline documents stay isolated.
- Malformed durable config follows existing managed-config error policy without destructive rewrite.
- Host and Docker real-CLI ACP probes confirm actual visibility, not merely environment construction.

## Effort & Risk

Large. Lower filesystem risk than Pi, but configuration merge/precedence mistakes can silently re-enable global tools or break model selection.

## Standards

Architecture Standards §§2–7; HA01 governs durable OpenCode ownership; provider-specific schema remains inside providers.

## Notes

Depends on MI01–MI03. OpenCode remains supported despite higher resource use; resource policy is separate from MCP isolation.

## Implementation Finding

A real `opencode 1.18.3 debug config` probe on Windows confirmed that a
request-local `XDG_CONFIG_HOME`, inline `plugin: []`, explicit disabling of
unselected project MCP names, and explicit selected entries resolves to exactly
the seven requested management servers with no plugins or unexpected enabled
MCP servers. The provider composer retains this concrete mechanism for both
direct and ACP launches.
