# Prove and implement isolated Pi ACP job launches

## Description

Wire curated MCP surfaces into the actual Pi ACP/gateway path. Do not assume direct Pi flags are forwarded by `pi-acp`; select an implementation only after installed-bridge evidence.

## Steps

1. Inspect and probe the installed `pi-acp` command on Windows and the clean container version. Record its child command, supported arguments, environment/config inheritance, and underlying Pi directory behavior.
2. Test candidate mechanisms independently: bridge argument forwarding; isolated `PI_CODING_AGENT_DIR` populated with provider-owned peripheral config; provider-owned wrapper/adapter configuration; or a bounded upstream patch.
3. Choose the least invasive mechanism that proves zero ambient MCP visibility. Prefer native/environment inheritance over patching; reject mechanisms that merely add selected servers while leaving defaults active.
4. Compose the Pi ACP launch inside the Pi adapter using the MI03 request. Do not let agents append Pi arguments or copy files.
5. Materialize any needed MCP file and Pi agent directory beneath the job request-runtime root. Keep session directories and MCP surface ownership distinct.
6. Ensure the public session-transport path and any one-shot ACP path share one provider-private builder so neither can omit isolation.
7. Return unsupported/additive-only when the installed bridge cannot guarantee isolation. Required-isolation jobs fail safely with a provider error and remediation/version detail.
8. Add version/capability probing without modifying the system installation during a read-only status check.

## Detailed Solution & Technical Design

The gateway calls only `providers_api.prepare_provider_session_transport(..., mcp_entries=..., require_isolated_mcp=True)`. The Pi adapter owns bridge-specific composition. A request-local Pi home is useful only if empirical evidence proves `pi-acp` and the underlying Pi process use it for every discovery source.

A wrapper is acceptable only as a provider-owned launch adapter with a narrow lifecycle, not as a second gateway or generic process manager. Any patch must follow the same anchor, idempotence, concurrency, validation, and fail-closed rules as MI04.

## Files

- Pi `acp.py` and provider-private composition helpers
- Provider capability/probe reference and safe diagnostics
- Session transport/conformance tests
- Real Pi ACP Windows and Linux/Docker gates

## Validation

- Sentinel global, project, and default MCP servers are absent from isolated Pi ACP.
- Selected management server responds through a real gateway-dispatched session.
- Empty selection is genuinely empty.
- Concurrent sessions with disjoint selections cannot cross-observe tools or files.
- Model/provider/session configuration survives MCP composition.
- Unsupported bridge version fails before child start with no shared mutation.
- Cancellation, timeout, crash cleanup, and request-runtime deletion remain bounded.

## Effort & Risk

Large and evidence-dependent. This item may conclude “unsupported for this bridge/version”; that is preferable to an ambiguous partial isolation claim.

## Standards

Architecture Standards §§3–7; CREATING_A_HARNESS empirical bridge verification; provider adapter/requester-blind rules.

## Implementation Finding

Probe on 2026-07-23 against published `pi-acp@0.0.31` confirmed that the
bridge accepts `mcpServers` through ACP `session/new` and carries that explicit
list into its Pi RPC session. AUDiaGentic's neutral ACP transport currently
hardcodes `mcp_servers=[]`. Prefer carrying the curated entries through the
existing ACP protocol field over forwarding Pi CLI flags, writing bridge-visible
config, or patching `pi-acp`. Direct Pi remains file/flag based under MI04.
