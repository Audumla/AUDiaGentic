# Wire job-scoped MCP selection through agents and launch modes

## Description

Make every AUDiaGentic-owned job launch carry an explicit MCP selection and isolation requirement while preserving native terminal behavior. Establish the minimal additive seam later role-capability work can use without implementing roles now.

## Steps

1. Identify every internal job/session dispatch route, including session open, one-shot execution, retries/replacements, and bootstrap/interactive `audiagentic launch`.
2. At the product/composition boundary, collect the appropriate available projection and produce concrete selected entries: management for bootstrap; the current explicit job policy for internal agents; functional only for native durable harness configuration.
3. Pass entries, request-runtime root, and `require_isolated_mcp=True` through the approved providers API. Do not import adapters, serializers, ACP launch types, or runtime harness internals.
4. Guarantee a stable selection snapshot for the job/session lifetime. Retries or resumed turns reuse the snapshot unless a new job generation is explicitly created.
5. Store only safe selection metadata needed for reproducibility (names/hash/projection/generation), not commands, secret environment, config contents, or provider paths.
6. Define the future role seam as an injected/product-owned selector from available entries to concrete entries. Do not add role schema, role persistence, implicit defaults, or provider awareness in this plan.
7. Make unsupported isolation a terminal pre-dispatch outcome with clear provider/surface capability information.
8. Remove all internal paths that launch a provider without explicit MCP-surface intent; native operator launches remain outside job dispatch.

## Detailed Solution & Technical Design

Launch modes are policy, not provider mechanics:

- Native terminal: durable provider projection, outside job dispatch.
- AUDiaGentic bootstrap interactive launch: management projection, isolated from native functional defaults.
- Internal job/session: explicit concrete subset, isolated and immutable.

The provider adapter sees entries only. A later role owner can implement `select(role, available) -> entries` without changing Pi/OpenCode materialization or the provider public contract.

## Files

- `components/agents` gateway/session dispatch and request contracts
- Runtime/composition-root bootstrap launch selection
- Request-runtime metadata and safe observability
- Agent/provider boundary and behavioral tests

## Validation

- Every internal launch route supplies an explicit selection and runtime root.
- Bootstrap includes management tools and excludes functional/provider-projected tools.
- Job A/B disjoint subsets remain isolated through concurrent dispatch, retry, cancellation, and cleanup.
- Selection snapshot does not change when components are enabled/disabled mid-session.
- Unsupported provider/surface fails before compute allocation or child start where sequencing permits.
- Architecture scans show no agents-to-provider-internal or agents-to-runtime-harness imports.
- Logs/stores contain no secret entry environments or generated config documents.

## Effort & Risk

Large. The principal risk is missing an alternate dispatch path and creating an isolation bypass; inventory and architecture tests are mandatory.

## Standards

Architecture Standards §§1, 3–8; AGENTS provider public API boundary; evidence-led future role seam only.
