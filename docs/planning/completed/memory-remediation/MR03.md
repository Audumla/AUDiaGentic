# Stage 3 — Correct component-creation doctrine and regression coverage

## Description

Update component authoring guidance so future components do not repeat this layering failure. Add explicit doctrine: non-provider components must not hard-code provider IDs, provider file paths, or provider renderer branching.

## Steps

1. Patch `docs/standards/CREATING_A_COMPONENT.md` with a new ownership-boundary section near MCP/projection guidance.
2. State explicit negative rules: component code outside `providers` must not enumerate provider IDs, write provider instruction/config paths directly, or branch on provider-specific syntax.
3. State the positive rule: generic components expose capability state or provider-agnostic projection data; provider component/adapters own downstream rendering.
4. Update examples/wording around activity servers and projections so `propagate: providers` is not read as permission to encode provider-specific behavior inside any component.
5. Add a remediation note or review checklist item that future component plans must answer: who owns provider adaptation?
6. Add tests or lintable checks if feasible, otherwise record a manual review gate for new components touching provider surfaces.

## Validation

- Guide contains an explicit ownership boundary section.
- Guide distinguishes "provider-consumable capability" from "provider-specific rendering."
- Future plan authors can cite one clear rule forbidding provider hard-coding in non-provider components.
- Manual review checklist or documented gate exists for provider-surface changes.

## Effort & Risk

Risk is fixing docs but not behavior. Mitigation: pair doc update with MR01/MR02 implementation and use the new doctrine as review criteria.
