## Goal

Make one small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, ID, store, queue, cancellation path or recovery system.

## AgentTaskFactory and AgentTask (RV891, 2026-08-04)

Concrete shape for the `AgentTask` API named above:

- **`AgentTaskFactory` is the one composed binding** — the agents component's real
  public surface (Rule 0). It legitimately owns a lifetime because it holds the
  queue manager and session runtime the tasks it mints route through — the two
  candidates AS59's own analysis already flagged as blocked only by the
  free-function-surface barrier, which is exactly what this item fixes.
  `AgentTaskFactory.submit(agent_id=..., ...)` is the primary entry point;
  `AgentTaskFactory.submit_raw(execution_profile_id=..., ...)` is the explicit,
  separately-named lower-level surface on the same factory — not a hidden dual
  route, and not the primary path going forward.
- **`AgentTask` is a freely-constructed handle, not composed and not cached
  state.** It wraps a `request_id` plus delegating methods (`.status()`,
  `.wait(timeout)`, `.cancel()`, `.result()`) that re-read the durable store on
  every call, the same way `get_execution_request` does today. A consumer may
  hold as many `AgentTask` handles as it likes and query them directly without
  going back through the factory, because the durable record stays the one
  source of truth — not the object. Caching live state independently in the
  handle would reintroduce the failure mode `GatewayQueueManager`'s own
  documented caveat already warns about ("process-wide... empty after a
  restart even if persisted records exist"). This is a small delegating
  handle, not the "giant service context object" the Do-not-add list forbids.
- Agent resolution is unchanged from AS62: `AgentTaskFactory.submit(agent_id=...)`
  calls the plain `resolve_agent_definition()` function internally — not
  injected, not composed.

## Application boundary

Expose only current operations, as `AgentTaskFactory` methods returning `AgentTask` handles (RV891):

- submit (primary: `agent_id`; secondary/explicit: `submit_raw(execution_profile_id=...)`);
- status/result — `AgentTask.status()`/`.result()`, delegating to the durable store on every call;
- transport-bounded wait — `AgentTask.wait(timeout)`;
- cancel — `AgentTask.cancel()`;
- operator list/overview — `AgentTaskFactory` method, not per-task;
- existing session open/continue/close;
- existing output/event reads through AS31/AS57.

ACP, A2A, CLI, management MCP, runtime gateway MCP/extensions and internal workflows call scoped adapters over this same `AgentTaskFactory`/`AgentTask` API.

The existing durable request ID is the AgentTask ID initially. One AgentTask maps to one existing request and one session turn. `ExecutionManifest` remains the request-level resolved execution record.

## Gateway projections

### Operator projection

May expose global list/overview and operator-authorized controls.

### Harness runtime projection

May expose only permitted task submission/delegation, owned status/result/wait/cancel, agent/skill description and authorized continuation.

Use one scoped MCP module or two thin modules according to the existing descriptor/auth model. Do not duplicate application logic.

## Composition and legacy boundary

Runtime composition builds `AgentTaskFactory` (RV891) and injects it into `runtime.application-host` and protocol adapters. `AgentTaskFactory` is the one composed binding; `AgentTask` handles it mints are not composed (see "AgentTaskFactory and AgentTask" above).

`AgentTaskFactory`'s own constructor is built from dependencies justified by current code, likely:

- queue manager;
- request/session stores used by the application API;
- dispatcher/provider boundary;
- existing authorization/audit dependencies;
- session runtime/control dependencies actually constructed by the touched startup path.

Execution Profile and Agent Definition resolvers are NOT composition dependencies (RV888/889/890 correction) — `AgentTaskFactory` calls `resolve_execution_profile`/`resolve_agent_definition` as plain functions internally, the same way `ApplicationHost` calls existing legacy code directly today.

Do not create a configured binding for internal helpers with one implementation.

### Legacy exemption interaction

Untouched gateway modules may remain behind the AS59 application-host exemption. Any module materially refactored by AS63 leaves the exemption:

- `_QUEUE_MANAGER` and touched global service selectors are removed;
- touched code has no fallback constructor or global lookup;
- the application host receives the composed AgentTask client/service and may not rebuild it;
- function-local imports may remain only for stateless helpers or untouched legacy paths, not as service lookup for migrated dependencies;
- the legacy host is not exposed as an AgentTask dependency or forwarding façade.

Do not broaden AS63 into a complete repository-wide gateway rewrite.
