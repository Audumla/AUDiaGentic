# Fix planning section handling: silent drops and lossy custom-heading round-trip

## Description

Custom `## Headings` in plan items are supported but the handling has two defects, both found while creating AS72.

**1. `update_item` silently drops unknown section keys.** `items.py:386` accepts a key only if it is in `ITEM_SECTION_HEADING`, is `title`, or *already exists in the file*. Any other key falls through the `elif` chain with no `else` — the value is discarded, no error is raised, and the tool still returns `{"ok": true}`. Calling `plan_update_item(item, {"acceptance_criteria": ...})` on an item lacking that heading reports success and writes nothing. This is the same swallow-the-signal failure mode AS71/AS72 are about, in the planning tool itself.

Consequence: a section can only be *updated*, never *created*, through the API. Since `create_item` emits only the configured heading set, any section outside it can never come into existence through the sanctioned path — while `CREATING_PLANS.md` §7 and AS70's guard require an `Acceptance Criteria` section on every active item.

**2. Custom heading text is corrupted on every round-trip.** Unknown headings are keyed by `_slugify_heading` (`[^a-z0-9]+` → `_`) and rebuilt by `_reconstruct_heading`, so capitalization and punctuation are lost each time the item is written. Live damage in the tree: `## AS59 Disposition` → `## As59 Disposition`; `## Baseline as measured 2026-08-02` → `## Baseline As Measured 2026 08 02`; `## Optional — only if steps 1-8 prove insufficient` → `## Optional Only If Steps 1 8 Prove Insufficient`. The docstring claims keys are "consistent across round-trips"; the *keys* are, but the headings are not.

Scratch item deleted immediately after verification. ## Notes

Found 2026-08-02 while creating AS72: `plan_update_item` returned `{"ok": true}` twice for an `acceptance_criteria` update that wrote nothing, which is why this was noticed at all.

Dynamic sections do work in the sense that matters most — arbitrary headings are preserved through item updates rather than deleted — so this was a defect in creation and fidelity, not a missing feature. **Reviews were worse than items:** `update_review` rebuilt the body from `_parse_review_sections`, which returns only notes/findings/conclusion, so any custom heading in a review was deleted outright on the next update.

### Implemented 2026-08-02

Steps 1-3 are done; the API now behaves as originally expected.

- **Silent drop fixed by making it work, not by erroring.** The `elif` chain in `update_item` gained an `else`: any non-frontmatter key is a body section — configured, existing-custom, or newly created. Chose creation over raising because "add sections generically and dynamically" is the intended contract and `build_sectioned_body` already rendered unknown sections; erroring would have documented the limitation rather than removed it.
- **Heading fidelity fixed** with `parse_custom_headings(body, heading_to_field)` returning `slug -> original heading`, threaded through `build_sectioned_body(..., custom_headings)`. Reconstruction from the slug now happens only for a section being created for the first time, where there is no original to preserve.
- **`update_review` now preserves custom sections** by seeding from all headings before overlaying the known ones (whose last-occurrence-wins parsing is deliberate and retained).

Four regression tests added in `tests/unit/planning/test_planning_api.py`, including a three-cycle round-trip asserting `## AS59 Disposition` never degrades to `As59 Disposition`.

### Confirmed live 2026-08-03: the fix was on disk but not yet running

Between the 2026-08-02 implementation and the 2026-08-03 restart, the fix existed in the codebase but the *running* ag-planning MCP server was still serving the old `items.py` from its own process startup. This was not theoretical: during AS59's Gate 0 closure, three attempts to record real findings under brand-new custom headings each returned `{"ok": true}` and wrote nothing, silently discarding the content until it was manually re-applied to existing headings and independently verified against the file on disk. That incident is recorded in AS59's Notes.

After the restart: verified with a disposable scratch plan item (created solely to probe this, then deleted immediately after) that a brand-new custom section now persists correctly, and that new items now carry an `Acceptance Criteria` section by default. Both confirmations were made by reading the actual file, not by trusting the tool's return value — the whole point of this item is that `ok: true` was never sufficient evidence on its own.

### Step 4 done 2026-08-03: heading repair sweep

Swept `docs/planning/**` for headings matching the corruption signature (Title-Case-every-word, punctuation stripped — confirmed via git history to be the reconstruction artifact, not a legitimate style; every recovered pre-corruption original across the whole corpus uses sentence case). Cross-checked each candidate against git history for the exact pre-corruption text where available, and restored it verbatim; where a heading was corrupted at its very first write (no clean original exists in history), normalized to sentence case and fixed any embedded AS/RV/CC identifier casing (e.g. `As59`→`AS59`, `Rv869`→`RV869`) since that is an objective identifier error, not a style question.

Fixed 20 headings across `AS29`, `AS31`, `AS40`, `AS59`, `AS68`, `AS70`, `AS71`, `AS74`, and `CC52`. Deliberately did **not** touch the many `## Architecture Standards Assessment`-style headings found elsewhere in the tree (CC08-CC19, LSP20-22, ML03/05/06, SL03-08, etc.) — those are byte-identical across a dozen+ files spanning six unrelated plan families, which is the signature of a consistently hand-authored template heading, not per-item slug reconstruction. Broadening the sweep to "any Title Case heading" would have relabeled correct content as corrupted; scope was kept to verified or unambiguous cases only.

**Not yet done:** whether `Acceptance Criteria`'s canonical insertion position (between Standards and Notes) relocates awkwardly on existing items that had placed a similarly-named section elsewhere by hand — not checked, low risk, can be handled on sight if it ever surfaces rather than swept for.
