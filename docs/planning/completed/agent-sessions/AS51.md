# Attach the gateway and Codex TUI to one loopback App Server thread

## Description

Implement Codex App Server as a distinct AS29 surface that lets the gateway and a human Codex TUI attach to the same exact loopback App Server thread. Use the canonical AS19 transport/control contracts, AS30 external/adopted binding semantics, and the existing shared gateway control plane. Codex protocol framing stays provider-private. This plan does not merge Codex ACP, CLI, App Server, TUI, or extension identities.

## Steps

1. Probe the exact installed App Server and TUI versions before fixing the adapter contract. Prove loopback endpoint shape, authentication, frame bounds, protocol/version negotiation, thread identity, simultaneous client behavior, ordering, reconnect, steer, interrupt, resume, and detach.
2. Register `codex-app-server` as an independent AS29 surface. It uses a provider-private App Server adapter that implements AS19 transport/control and returns exact opaque thread refs through `providers_api`.
3. Reuse existing AS19 transport and ownership contracts. Add only missing generic external/adopted capability fields; do not create an App-Server-specific foundation transport or a second agents transport abstraction without another proven consumer.
4. Permit only canonical loopback endpoints. Reject non-loopback, ambiguous hostname resolution, version mismatch, malformed/oversized frames, missing auth, and unsupported topology before binding.
5. Attach by exact opaque thread ref under AS30. Never attach by display name, recency, active window, TUI state, transcript match, or “latest”. Require exact project, identity, execution context, ref namespace, and concurrent-attachment capability.
6. Reuse SH04 service authentication, client leases, application/client methods, and HTTP transport. Add closed generic operations only for controls proven by the App Server probe; provider-native payloads never cross the provider boundary.
7. Persist only protected canonical endpoint identity, surface/version, opaque thread ref via AS30, ownership mode, context fingerprints, and lifecycle outcome. Do not persist tokens, raw frames, TUI state, native event payloads, or command lines.
8. Define ownership behavior:
   - external: gateway close/restart detaches and never signals App Server/TUI;
   - adopted: signals only under explicit transferred authority through AS52;
   - owned: close may terminate through the declared surface and AS52 cleanup.
9. Keep control acknowledgement separate from lifecycle. Start/steer/interrupt/resume responses do not terminalize work; AS19 evidence and SH07 decide effects.
10. Split any current Codex-specific transport binding/ownership logic out of session monoliths into the canonical provider and AS30 seams, deleting duplicate paths in the same change.
11. Add fake-server conformance tests, two-client integration tests, restart/stale-thread tests, and real version-pinned Windows/Linux/Docker probes before platform promotion.

## Validation

- gateway and simulated/real TUI observe the same exact thread/ref;
- deterministic start/steer/interrupt/resume ordering and conflict behavior only where probed;
- loopback, authentication, version, and frame bounds enforced;
- exact attach cannot fall back to latest/name/UI/transcript;
- external close/restart detaches while server/TUI continue;
- adopted/owned modes follow AS52 authority;
- stale thread cannot create duplicate owner or silent replacement;
- public records and logs contain no token/raw frame/provider ref;
- Codex ACP cleanup remains green and independent.

## Effort & Risk

Complex. Main risks are unproven upstream multi-client behavior, external ownership mistakes, and accidental identity collapse across Codex modes.

## Standards

Reuse AS19/AS21/AS29/AS30/AS31, AS47, AS52, SH04 authorization/lease/service, provider API, redaction, and exact platform-probe standards.

## Acceptance Criteria

- Gateway and TUI demonstrably share one exact validated App Server thread.
- Codex App Server remains a separate surface and identity from Codex ACP and CLI.
- External close detaches without signalling the external server/TUI.
- All controls and concurrent attachment are capability-gated and exact-ref based.
- No Codex-native protocol type escapes the provider adapter.

## Deprecated 2026 08 05

**Deprecated as redundant — not superseded. AS98 covers Codex; this second strategy is not carried forward.**

This is a second, substantially larger Codex integration approach (gateway and a human Codex TUI attached to one loopback App Server thread) running in parallel with the Codex ACP bridge approach. Two strategies for one provider, with zero implementation progress on either, is a real source of the circling this rationalization is addressing.

AS98 delivers Codex as a session surface through the existing `codex-acp` bridge — the smaller, better-understood path, using machinery that already works for two other providers. It is sufficient for every Codex requirement currently expressed.

What this item uniquely offered — a human operator sharing a live thread with the gateway — is a genuinely different product capability, not just a different transport. Nobody has asked for it. Its own dependency list (AS47 continuation semantics, AS52 ownership modes, plus an unprobed upstream multi-client protocol) made it the most expensive item in the platform track.

If shared human/agent threads become a real requirement, raise it fresh against that requirement — with the upstream multi-client behaviour probed first, which this item correctly identified as its own top risk and never did.
