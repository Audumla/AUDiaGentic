# Configurable GPT-auto refresh recovery from silence and interruption signals

## Description

Extend AS119 from a one-shot experimental probe into the production recovery workflow requested by the live BigCherry failures. A GPT-auto turn must refresh its existing conversation tab after four minutes without validated real activity, or immediately when a configured provider interruption signal is observed, initially the exact Connection interrupted message. Refresh must never resend the prompt.

## Steps

- Add provider configuration for real-activity silence threshold (default 240 seconds), maximum same-tab refresh attempts (default 15), and final grace after the last refresh (default 600 seconds).
- Add a dedicated interruption DOM signal with exact text matching; keep generic error-alert as a separate terminal/error diagnostic.
- Track last validated real activity, last refresh completion, refresh count, trigger reason, and per-attempt result.
- Reset inactivity and recovery counters on validated request-owned assistant/user/tool/DOM progress activity.
- Share one refresh primitive and one budget across silence, interruption, and correlation-recovery paths.
- After the final grace expires, fail with bounded unresolved evidence; never create a new session or resubmit.

## Detailed Solution & Technical Design

Implement a response-observation state machine in turn.py. Real activity is a correlated message-id/text/count/tool change; generating/stop/busy/static snapshots are advisory only. At each poll, evaluate completion first, then interruption-triggered refresh, then silence-triggered refresh, then provisional failure. The refresh operation navigates the current page to the immutable conversation URL, waits for a fresh snapshot, and returns to observing. A trigger is edge/debounced so a persistent alert cannot consume all attempts in one loop. Completion after refresh wins over the prior interruption. Preserve the unresolved fence on exhaustion.

Clarification from live behavior (2026-09-12): all recovery timing is configuration-driven. Use one configurable inactivity/retry interval (initial default 240 seconds) for both the first no-activity refresh and each subsequent retry after a refresh. The exact `Connection interrupted. Waiting for the complete answer` signal requests recovery but does not veto a response and does not itself permit a tight refresh loop. After each refresh, set recovery_anchor_at to refresh completion; the next attempt is eligible only after the full inactivity interval from that anchor, unless a new edge of interruption evidence is observed. Start with a configurable maximum of 6 attempts. Completion evidence, including completion while the interruption message remains visible, must be evaluated before any refresh or failure decision and must win when request-owned and stable. Keep final-grace timing independently configurable.

## Acceptance Criteria

- No hard response deadline pre-empts validated activity.
- Exact interruption and silence triggers refresh the same tab.
- All recovery counters reset on validated assistant/user/tool/DOM progress activity.
- Maximum attempts and final grace are configurable and shared; packaged defaults are 15 and 600 seconds.
- No prompt resend or implicit session rotation occurs.
- Exhaustion remains unresolved/recoverable with precise diagnostics.
- All inactivity, retry, final-grace, navigation, and stability timeouts are configurable and validated.
- Initial and subsequent refresh eligibility use the same configured inactivity interval by default.
- A persistent interruption marker does not consume all attempts in one poll cycle; retries are serialized and spaced by the configured interval unless new interruption evidence arrives.
- A request-owned stable completion is adopted even when the interruption text remains visible.
- Recovery never treats refresh success as real activity and never refreshes in parallel.
