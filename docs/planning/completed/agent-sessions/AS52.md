## Standards

  seam owns adopt/observe/stop. No global process registry, and managed-service

  external process) are `AudiaGenticError` with stable codes; process command

  platform claims must match passing tests exactly.

## Characterization 2026 08 04

**Characterization pass performed before any implementation, per this item's own instruction ("characterize `foundation/system/adopted_process.py` and the existing architecture test before editing"). Result: 7 of 8 remaining_scope items are already done. Only one concrete, currently-reproducing bug remains.**

Read `foundation/system/adopted_process.py` in full and traced every real caller:

1. **Canonical contract / inline callers** -- DONE. `adopt_child`/`observe_child`/`stop_child`/`close_kill_job` have exactly one real caller in the whole tree: `foundation/transports/acp.py` (`_finish_open` adopts on both `open()` and `open_resumed()`; `close()` calls `close_kill_job` last). Two other files (`providers/protocols/streaming/provider_streaming.py`, `coding_lsp/lsp_bridge.py`) call `process.terminate()`/`.kill()` directly, but on a synchronous, directly-held `Popen` object in the same call stack (spawn-wait-terminate all in one function) -- a different pattern than "already-spawned child adopted later by identity," which is what this seam exists for. Not a migration target.
2. **Identity-safe stop** -- DONE. `stop_child` refuses on `is_external`, then re-verifies via `observe_child` (PID-reuse/mismatch/dead all refuse) before signalling.
3. **owned/adopted/external separated** -- PARTIAL. Only a binary `is_external` flag exists; there is no distinct third "adopted" state anywhere it's actually consumed. No real caller needs a three-way split today -- flagging as evidence-led-scope-satisfied (arch-standards §3) rather than a gap: add the third state only when a demonstrated caller needs it, same discipline as AS64's close.
4. **Protocol ownership stays in transport** -- DONE, structurally guaranteed by (1) -- the only caller is the transport layer itself.
5. **Bounded process facts projected into session diagnostics** -- DONE. `gateway/session/sessions.py`: `child_pid`/`child_creation_identity` captured onto the session handle (lines 187-188, 807-808) and surfaced in diagnostic dicts (`"child-pid"`, `"child-creation-identity"`, lines 666, 777, 780, 885) -- never used as lifecycle authority, just diagnostic facts.
6. **Job Object/handle released last, idempotently** -- DONE. `acp.py` close(): direct `proc.terminate()`/`.kill()` on the live handle first (the transport's own graceful shutdown of the one child it directly holds), *then* `close_kill_job(self._adopted_child)` last (own comment: "AS17: close the foundation adopted-child token last"), then `self._adopted_child = None` -- a second close() call is a no-op, confirming idempotency.
7. **OS guarantees documented honestly** -- DONE, already in the module's own docstring (RV720: POSIX cannot guarantee immediate descendant death after gateway SIGKILL; Windows Job Object can).
8. **Direct-signal architecture boundary preserved** -- DONE and enforced: `tests/unit/foundation/system/test_process_signal_boundaries.py` (3 tests) already forbids `os.kill`/`taskkill`/`os.killpg` outside `foundation/system/`, passing today.

**The one real, currently-open item**: `tests/unit/foundation/transports/test_acp_session_subprocess.py::test_close_kills_child_process_no_orphan` is **failing right now** on this Windows host (`AssertionError: Child process ... still alive after close() -- orphan!`), not merely "documented as a known exception" the way AS59's baseline table describes it. This is a real timing race in `acp.py`'s close() sequence (direct `proc.terminate()`/`wait(timeout=CANCEL_GRACE_SECONDS)`/`proc.kill()` chain) where close() can return before the child is confirmed dead. This is the one concrete bug AS52 should now be scoped down to.
