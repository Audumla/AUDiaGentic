# gpt-auto review of AS88 - correct architecture but 5 HIGH specification gaps

## Notes



## Findings

**Verdict:** Core architecture good (one binding record, §3 compliant). **Not implementation-ready.** Several specification gaps that matter at implementation time.

**Confirmed as correct:** One-record architecture right (existing binding already contains surface/provider/generation/context fingerprints). Execution-profile ID ambiguity correctly resolved (keep session_record top-level as sole ID, add only digest in binding composition block). Fail-closed legacy principle absolutely right.

**HIGH gaps found:**
1. Agent Definition/Role identity not available at AS88 boundary today. Current canonical admission knows execution profile/provider/model/component context but no agent-id/agent-definition-id/role identity reaches gateway. AgentTaskFactory.submit(agent_id) resolves Agent Definition outside gateway and forwards only execution_profile_id, discarding both agent identity and its role. AS85 introduces role selection/transport into authoritative gateway admission. Therefore AS88 cannot satisfy "every post-change generation freezes Agent Definition and Role" or reject changed Agent Definition/Role until that identity exists at admission. Real dependency.

2. Composition snapshot/digest contract undefined. "agent-definition-id, role-id, execution-profile-id, each with generation-or-digest" not concrete enough. Agent Definitions currently have neither generation nor digest. Role resolution will eventually have manifest fingerprint, while execution profiles already participate in several different identities (gateway profile generation/config digest, agent_runtime_digest, request context_fingerprint). Must name which existing authoritative value used for each field and avoid inventing another hash authority.

3. Steps 1 and 3 don't actually match. Step 1 only adds composition identity, while Step 3 says compare project/provider/model/component profile/runtime digest/execution-context fingerprint/surface individually. Current binding/session record directly stores provider/model/profile/surface and context fingerprints, but not project/component profile/runtime digest individually. Existing execution-context fingerprint already hashes project root, execution-profile ID, provider, model-at-admission, component profile and agent runtime digest. Slim design should say which facts compared directly vs covered by fingerprint.

4. "Reusable lifecycle + no active turn" conflicts with existing FIFO continuation model unless ordering specified. SessionRuntime._prompt() deliberately permits multiple continuations to queue FIFO on turn_lock; rejects only bounded backlog. After queued request acquires lock, revalidates handle identity/lifetime/liveness before calling transport. If AS88 literally rejects whenever another turn active, second-client FIFO acceptance criterion becomes substantially weaker or false. Better contract: compatible continuation may queue FIFO while another turn active; after acquiring turn lock, immediately before transport.prompt, revalidate generation/binding/context and require session reusable for that turn.

5. New linked generations omitted from implementation scope. AS89's resume code already creates brand-new session generation and copies two context fingerprints into successor binding. If AS88 changes fresh-open records but not this path, resumed post-AS88 generation lacks new composition snapshot, contradicting "every post-change generation freezes identity." AS88 needs to cover every generation-creation path.

**MEDIUM findings:**
- "Reusable lifecycle state" has no named authority (AS21 SessionLifecycleDecision.session_reusable flag? durable session state? quiescence?)
- Legacy migration needs concrete v3→v4 rule with unknown sentinel handling (existing resume validation demonstrates exact implementation style to reuse)
- "Same open transaction" wording overstates current implementation (record write succeeds but index registration fails leaves written session record unrolled back)
- Capability-resolver sequencing needs named owner and compatibility rule (capability digest absent today cannot be mandatory for exact continuation simultaneously)

**LOW:** Step 7 policy fine as policy, weak as implementation step. "Skill-name substitution" less grounded - current continuation doesn't resolve session by advertised skill at all.

**What required before marking ready (Detailed Solution must establish four concrete rules):**
1. Frozen compatibility tuple: exactly which stored facts constitute tuple and which existing digest owns each derived identity
2. Generation creation: fresh open AND every linked-generation creation path persist tuple in same atomic session-record write
3. Continuation sequence: resolve current requested composition once → compare durable binding context → queue FIFO if necessary → after acquiring turn lock revalidate exact live binding/generation/project/context → only then call transport.prompt()
4. Legacy/dependencies: v3→new-version migration represents composition as unknown; unknown never equality-compatible; AS88 depends on authoritative agent/role admission while effective-capability enforcement names later resolver/integration item that activates it
