# Adversarial gpt review of AS88 session context freeze

## Notes

Adversarial review requested per layering-tranche review pass. Focus: whether freezing context on binding and enforcing on continuation is necessary at all given AUDiaGentic-thin doctrine, or whether provider-native session identity already covers the aim; unknown-context reject semantics; digest-only vs definition-versioning scope.

## Findings

1. **The agents layer does own composition-compatibility, but AS88 frames it too broadly** — verified in a narrower form. Provider-native session identity stays authoritative for the provider session/thread; the gateway must not duplicate identity, lifecycle, transcript or persistence. But a provider session id does not prove the gateway is continuing it under the same agent definition/profile/role composition. The thin invariant is: *given provider session S, the gateway must not reuse S under a different gateway-admitted composition than the one associated with S.* Narrow AS88 to binding a gateway admission/composition identity to a provider session reference, leaving provider session identity entirely provider-owned. A neutral gateway cannot rely on a provider exposing AUDiaGentic-local role/profile semantics.

2. **AS88's current-state analysis is materially stale — much has already landed** — refuted against the current tree; this is a blocker to implementing the plan literally. `gateway/session/bindings.py` already accepts/persists agent-definition-id, agent-definition-digest, execution-profile-id, execution-profile-digest, role IDs, role-set-digest, effective-capability-digest, context-id alongside the provider-owned binding identifiers. `SessionManager.resume_session()` already compares supplied composition against the source generation and raises `session-composition-mismatch` / CON-AGW-124 on difference. The store persists and validates the expanded binding/session shape. The remaining hole is subtle: comparison is only as strong as the authoritative composition supplied to the continuation path; a requested-but-absent (None) field does not establish exact equivalence — which points at AS85, not at more binding machinery.

3. **AS88 is incorrectly sequenced; its role guarantees depend on AS85 and transitively AS84** — verified sequencing defect. AS88 declares no dependencies, but AS85 explicitly depends on AS84, produces the frozen RoleAdmissionResult, requires session open/reuse/continuation to consume it, and explicitly identifies AS88 as depending on AS85's propagation seam. AS88 cannot establish full composition exactness before AS85 without either re-resolving roles (second role authority) or accepting missing role info (fails its own invariant). Recommendation: set `depends: [AS85]`; AS84 is then transitive. Thinner option: fold the small remaining AS88 enforcement slice into the tail of AS85.

4. **Reject-on-unknown is correct; the proposed migration/backfill is not worth its complexity** — policy verified; migration should be slimmed. `resume.py` already rejects an unknown stored execution-context fingerprint rather than treating it as equal. `unknown != proven equal` is sound for an exact-compatibility promise. Reject any attempt to derive a legacy session's historical digest from today's definitions — that creates false provenance while pretending not to introduce definition versioning. Thin migration: legacy binding without trustworthy composition evidence → composition unknown; exact continuation → reject with "composition cannot be verified; start a fresh session"; new sessions get the canonical fingerprint at admission. No eager migration job, no historical reconstruction, no pseudo-versioning. Legacy grandfathering, if wanted for UX, must be an explicitly weaker/non-exact policy.

5. **The remaining exactness bypass is "missing current admission", not missing persistence** — verified against current implementation. Resume already compares requested vs stored composition (agent definition, execution profile, role-set, effective capability), but those checks are conditional on current composition being supplied. The real invariant: once AS85 is active, every exact reuse/continuation must carry the authoritative frozen admission result; absence of that result is not evidence of compatibility and should be treated as an internal contract/admission failure, not "compatible by omission". This prevents an invocation path from becoming a compatibility bypass.

6. **Digest-only is directionally correct, but AS88 risks a miniature versioning system through digest proliferation** — partly verified, partly under-specified. Five independently meaningful version-like tokens (agent-definition digest, execution-profile digest, role-set digest, effective-capability digest, execution-context fingerprint) plus stable IDs risk five subtly different version systems. The current tree treats execution-context compatibility separately from session composition compatibility, so the claimed duplication is not proven. The thinner contract: one canonical composition/admission fingerprint is the equality token for gateway composition, canonically including resolved agent-definition identity, resolved execution-profile identity, AS85's role admission/fingerprint, and the capability surface where it affects continuation semantics. Stable IDs stay for observability/errors. Sub-digests survive only where a concrete consumer exists. The relationship with execution-context-fingerprint must be explicit: either it incorporates the composition fingerprint, or the two are orthogonal with documented inputs and separate purposes — do not leave overlapping canonicalization implicit.

7. **There are already too many places participating in "same enough to continue"** — verified architectural risk (output truncated at dispatch). Compatibility responsibility is distributed across resume.py (execution/runtime context), SessionManager.resume_session() (composition), and likely more; consolidation under one admission-fingerprint authority is warranted as part of the AS85 seam.

## Conclusion

AS88 is substantially overbuilt relative to the current tree: much of the persistence/comparison machinery has already landed, and the remaining guarantees genuinely depend on AS85's frozen RoleAdmissionResult. Thin disposition: **resize AS88 to depends:[AS85]**, narrow its scope to binding the canonical admission/composition fingerprint to the provider session reference, adopt reject-on-unknown for pre-migration bindings with no historical backfill, and consolidate the "same enough to continue" checks under one composition-fingerprint authority. Do not build migration jobs, pseudo-versioning, or per-token compatibility authorities.
