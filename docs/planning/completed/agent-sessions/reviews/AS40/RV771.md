# Replace independent Pi RPC transport with a read-only tee tap over the existing pi-acp launch

## Notes

Session-driven design discussion (see conversation) concluded that a fully independent Pi RPC transport (AG directly spawning and driving `pi --mode rpc` as its own AgentSessionTransport, separate from the `pi-acp` surface) is unnecessary and creates a two-surface bifurcation the user wants to avoid. Pi already ships a maintained ACP wrapper (`pi-acp`); reinventing ACP serving/conversion ourselves was explicitly rejected as unnecessary duplication of native capability.

Key structural finding: OS pipes are single-owner. Whichever process spawns `pi --mode rpc` holds the only live stdin/stdout descriptors. `pi-acp` cannot 'attach' to an externally supplied stream reference -- its `PI_ACP_PI_COMMAND` substitution hook is 'what command do I exec as my child', not 'what socket do I connect to'. So AG spawning Pi RPC directly and having pi-acp attach afterward does not avoid a mediator; it only reverses which side calls exec first, and a full bidirectional router (both AG and pi-acp issuing independently-correlated RPC commands into one stdin) risks request-ID collisions and response cross-contamination.

The actual requirement is observability, not independent command issuance -- AG never needs to drive prompts/abort/control itself when launching for this purpose; `pi-acp` remains the sole driver via the existing ACP transport. That reduces the mediator from a full router to a one-directional tee:

- stdin: pi-acp -> shim -> real `pi --mode rpc` (untouched passthrough, single writer, no multiplexing, no correlation risk)
- stdout: real `pi` -> shim -> fans out to (a) pi-acp unchanged, and (b) an AG-owned per-request Unix domain socket / Windows named pipe, read-only

The shim substitutes at the existing `PI_ACP_PI_COMMAND` hook in `providers/adapters/pi/acp.py::_materialize_pi_command_wrapper` (currently a transparent exec/passthrough script) and becomes a small AG-owned relay component instead. This guarantees structurally -- not just by convention -- that exactly one `pi --mode rpc` process exists per session and both the ACP surface and AG's own observability tap are reading the same physical process, never two separate Pi sessions.

This is Pi-specific: it depends on `PI_ACP_PI_COMMAND` being an available substitution point in Pi's maintained ACP wrapper. Other harnesses must be assessed individually for an equivalent hook; where none exists this pattern does not transfer.

Consequence for AS41: since pi-acp remains the sole command driver, AS41's scope narrows from 'implement independent state/cancel/close capabilities for a new Pi RPC surface' to 'enrich the existing ACP surface's evidence using the tapped RPC stream' -- prompt/cancel/close continue to route through the existing AcpSessionTransport/pi-acp path (see docs/reference/PROVIDER_CAPABILITY_REFERENCE/harnesses/profiles/pi-acp-status-mapping.md for its already-working CANCEL_TURN/CLOSE_SESSION disposition), not a second independently-driven transport.

## Findings



## Conclusion

Revise AS40 to build the tee shim over the existing pi-acp launch instead of an independent Pi RPC transport/surface. Revise AS41 to scope RPC evidence mapping as enrichment of the existing ACP surface rather than lifecycle mapping for a new independent surface. No new plan items required -- this is a design correction to AS40/AS41, not new scope.
