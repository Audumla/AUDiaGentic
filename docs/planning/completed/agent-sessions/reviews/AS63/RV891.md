# Concrete AgentTask shape: composed AgentTaskFactory + freely-constructed AgentTask handles

## Notes



## Findings

AS63's existing text names "AgentTask" as the target API but leaves its concrete shape unspecified -- whether it is a function set, a class, or something else. Design conversation with the user (2026-08-04) settled a concrete shape:

- `AgentTaskFactory` is the one composed binding -- the agents component's real public surface (Rule 0). It legitimately owns a lifetime because it holds the queue manager and session runtime the tasks it mints route through -- the two candidates AS59's own analysis already flagged as blocked only by the free-function-surface barrier, which is exactly what AS63 exists to fix.
- `AgentTask` is the object `AgentTaskFactory.submit(agent_id=...)` returns. It is NOT composed, NOT tracked by the graph, and NOT cached state -- it is a thin handle wrapping a `request_id` plus delegating methods (`.status()`, `.wait(timeout)`, `.cancel()`, `.result()`) that re-read the durable store on every call, the same way `get_execution_request` does today. Consumers can hold as many `AgentTask` handles as they like, pass them around, and query them without going back through the factory, because the durable record stays the one source of truth -- not the object. Caching live state independently in the handle would reintroduce exactly the failure mode `GatewayQueueManager`'s own documented caveat already warns about ("process-wide... empty after a restart even if persisted records exist").
- Agent resolution is unchanged from AS62: `AgentTaskFactory.submit(agent_id=...)` calls the plain `resolve_agent_definition()` function internally, not injected, not composed.
- `agent_id`-based submission (via `AgentTaskFactory`) becomes the primary/target surface; direct `execution_profile_id` submission becomes an explicit, separately-named lower-level surface on the same factory (e.g. `submit_raw`), not a hidden dual route and not the primary path going forward.

AS63's existing "Composition and legacy boundary" section lists "Execution Profile and Agent Definition resolvers" among composition candidates alongside queue manager/session-runtime dependencies -- stale per RV888/889/890 (both resolvers are plain functions, not composed). This section needs correcting to name `AgentTaskFactory` as the actual composed thing and drop the resolvers from that list.

Step 7 ("Delete superseded submit_llm_request, agent_llm_* and related paths") uses pre-SH12 naming; SH12 already renamed these to `agent_execution_*` today. The superseded-path deletion this step actually needs to describe is the direct-`execution_profile_id`-as-primary-entry-point path becoming secondary/renamed, once `AgentTaskFactory`/`agent_id` is primary -- not literal `agent_llm_*` symbols, which no longer exist under that name.

## Conclusion

Update AS63's Goal, Application boundary, Composition and legacy boundary, Work, and Do-not-add sections to name `AgentTaskFactory` (composed) and `AgentTask` (freely-constructed handle) concretely, correct the stale composition-candidate list, and correct step 7's stale pre-SH12 naming. `AgentTask` being a small delegating handle (not a cache, not a giant context object) should be stated explicitly so it isn't read as conflicting with the existing "Do not add: a giant service context object" line.
