# Stage 1 items 1-3 execution review: ground the composition seam in existing code, sequence as one push

## Notes

Reviewed AS59 Stage 1 items 1-3 against the current tree ahead of implementation, per the earlier finding that items 1-2 are design-coupled to item 3 and should not be split across sessions with a guessed contract in between.

What was checked directly:
- `src/audiagentic/foundation/composition/` and `src/audiagentic/runtime/bootstrap/` — neither exists; both are greenfield, no migration burden.
- `src/audiagentic/launcher.py` (320 lines) — `_main()` is one linear function: argparse setup, env propagation, logging bootstrap, interaction backend, `register_harness_status(...)`, then dispatch through two dict registries. The wireable startup block is lines 234-286 only; everything above it is argparse and everything below is dispatch.
- `src/audiagentic/foundation/config/layers.py` — `load_layered_config(pkg_default_path=, project_root=, namespace=)` is the existing precedence API AS59 item 1 says to host the composition schema on. Three tiers: package default, user-global, project-local. Item 1 needs no new loader.
- `src/audiagentic/components/agents/agents_gateway_api.py:28` — `_QUEUE_MANAGER = queue_mod.GatewayQueueManager()` at import time, used at 8 call sites in that module.
- `src/audiagentic/components/agents/agents_gateway_profiles.py:366` — `_gateway_registry` module global behind `get_gateway_registry()`/`set_gateway_registry()`, with `GatewayProfileRegistry` already declared as a `Protocol` at line 140.

Findings:

1. **Item 6's migration slice is already Protocol-shaped, which materially lowers its risk.** `GatewayProfileRegistry` is a Protocol with two concrete implementations (`InMemoryGatewayRegistry`, `EmbeddedCompatibilityRegistry`) and a global setter. That is exactly the 'genuinely replaceable service' the Separate Composition Configuration section says a binding should exist for — and it is the only one in the gateway path that already meets the bar. The queue manager is not Protocol-shaped and needs a narrow Protocol extracted as part of item 6.

2. **There is direct evidence the globals are a real defect, not a stylistic one.** Twelve test sites across `tests/integration/agents/` and `tests/helpers/gateway_provider_conformance.py` reassign `_QUEUE_MANAGER` by hand to get isolation. This is the same class of shared-global churn TE02 step 10 is fighting in `tests/conftest.py`. Item 6 should be judged partly on how many of those twelve reach-ins it lets delete — that is a countable acceptance signal the item currently lacks.

3. **Items 1-2 cannot be validated on their own and should not be committed on their own.** A config schema and a contribution record with no builder consuming them have no test that can fail for the right reason; `arch-standards` §3 (evidence-led scope) forbids shipping shapes whose only justification is that a later item might want them. Confirms the earlier deferral was correct and states the reason in the item rather than leaving it in session history.

4. **Item 5 (route `launcher.py` through the host) is smaller than its phrasing suggests and should not be feared into a later stage.** Only the startup block is in scope; argparse and command dispatch stay exactly where they are. The acceptance test is that CLI behavior is unchanged, which the existing CLI tests already assert.

5. **Gap in the item as written: no stated relationship between the composition roots and the ~20 process entry points.** The Acceptance Criteria already concede 'one production startup path' was never achievable and require a 'recorded adoption owner' for the remaining process kinds, but Stage 1 work items 1-9 never produce that record. Item 9 should own it explicitly, otherwise the criterion has no implementing step.

Conclusion: items 1-3 are ready to implement as one continuous push, with 4-5 following immediately in the same push since item 3's builder is untestable end-to-end without a root to build. Recommend the push boundary be items 1-5 (contracts through launcher routing), leaving 6-9 as the second push. Detail written into the item's `Stage 1 items 1-5 execution design` section.
