# Correction: gateway profile registry lifecycle reasoning, and the binding-vs-composed-singleton shape for its reopening

## Notes



## Findings

Item 6's rejection of `_gateway_registry` (2026-08-03) gave three reasons: (1) `None` is a meaningful value a frozen build-time graph can't express, (2) it is "installed and uninstalled at runtime" by `GatewayServiceHost`, (3) it is hot-swapped live via `reload_profile_registry()`.

Reason (2) does not hold up under inspection. `GatewayServiceHost` is only ever constructed in two places -- `agents_gateway_service_process.py::main()` (the detached automatic-mode entrypoint) and `commands/gateway.py::cmd_gateway` (`audiagentic gateway serve`) -- and in both, exactly once: `set_gateway_registry()` runs at construction before `serve_forever()` admits any work, and `set_gateway_registry(None)` runs once in `finally` at shutdown. This is ordinary constructor/destructor lifecycle for a long-lived process-scoped object, not dynamic mode-switching during operation. Whether the registry is present is fixed for that process's entire operational life, determined by which entrypoint launched it -- exactly the shape a build-time composition choice needs.

Reasons (1) and (3) are real but not disqualifying on their own: (1) the "meaningful None" only exists because one function (`submit_execution_request`) currently branches on a nullable global instead of two composed resolvers each knowing their own role -- there is no "absent" state left to express once that split exists. (3) reload swaps the composed object's *internal* state, not the graph's bindings; composition freezes bindings, not a composed service's internal mutability.

However, AS59's own document already anticipated the correct reopening shape and this finding should not blur it: it explicitly separates a **binding** (genuine choice between implementations, config selects) from a **composed singleton** (one implementation, no choice, but a lifetime worth owning), and warns that conflating them is "the other way a composition root becomes a container." Project-vs-shared-gateway is not a per-deployment config choice -- it is determined by which process is running (CLI harness vs. the dedicated gateway-service process). So the corrected shape is NOT "one binding with two implementation IDs selected by component-profile" (the first proposal considered, which conflates the two categories). It is:

- project-local resolution stays a plain function -- stateless, nothing to own, no composition needed;
- the shared-gateway registry becomes a composed singleton in a *second* composition root specific to the gateway-service process entrypoints, with install/uninstall as that root's construction/shutdown -- the same pattern `runtime.application-host` already uses for `InteractionBackend`.

This second root is not a new mechanism -- `test_the_launcher_is_the_only_caller_of_the_composition_root`'s own docstring says "One process adopts the host in Stage 1; later roots are deliberate." This is that deliberate later root, and its trigger condition (AS60 giving the agents component a composable public surface for profile resolution) is exactly what AS59's own item-6 disposition table already named as the reopening condition ("AS63 / SH11 if the surface is reshaped").

Audited the other three rejected candidates against this same lifecycle-vs-mutability lens -- none are affected. `_QUEUE_MANAGER` and `_SESSION_RUNTIME` were rejected for the free-function-surface barrier (no Protocol, no injection point at all), unrelated to lifecycle. `agents_gateway_client._CLIENT` was rejected on ownership (SH11 Slice B), not lifecycle. The 9 module-global `Registry` instances were rejected on Rule 0 component-internal grounds (AS76), unrelated. Only `_gateway_registry`'s disposition changes.

## Conclusion

Reopen `_gateway_registry` as a composition candidate, but as a composed singleton constructed by a second, gateway-service-process-specific composition root -- not as a binding with project/shared implementation IDs selected by component-profile. AS59's candidate-assessment table, the legacy-exemption register row for `_gateway_registry`, and AS60's public-boundary-and-composition section all need updating to reflect this. AS60 remains the owner: this is exactly the surface-reshaping condition AS59 already named as the trigger.
