# Consolidate observability declarations into the MA20/MA19 provider capability model

## Notes



## Findings

AS19 proposes a new harness_observability schema in separate harness descriptors/registries/harnesses.yaml. This creates a third capability system parallel to MA20 automation_capabilities (executable declarations) and MA19 capability_facts (evidence). AS13 already records ACP capability ids as MA19 capability_facts in provider YAML, so observability capability knowledge is fracturing across two homes with two schemas. AS22 likewise says probes update 'harness descriptors/registry'. AS19 also never states its authority relationship to MA19/MA20.

## Conclusion

Observability declarations must live in the provider descriptor capability model: a typed observability declaration following the MA20 declaration pattern (declaration enables projection features, inert-metadata rules apply), with probe evidence recorded as MA19 capability_facts reusing CapabilityEvidence. No separate harness registry or third schema. AS22 probes update the descriptor declaration + MA19 facts. MA19's evidence catalogue gains a 'harness observability signals' subject. Edits applied to AS19, AS22, MA19.
