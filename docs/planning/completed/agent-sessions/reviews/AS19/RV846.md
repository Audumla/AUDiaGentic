# Align with capability-driven observation: reconcile AS19:115 + AS29 session_surfaces with the provider `launch`/observation capability

## Notes

Raised from the provider-capability-model work (plan provider-capability-model, PC01/RV845). Design steer from the maintainer: OBSERVATION IS CAPABILITY-DRIVEN BY THE PROVIDER — the provider declares how it can be observed and the observer subsystem consumes that declaration. The plans are not fixed; AS19's contracts can change to fit this. This review proposes the alignment, it does not assert AS19 is wrong.

## Findings

1. AS19:115 currently states: 'Use the AS29 resolved surface lifecycle declaration as the sole observer-mechanism source. Do not add ProviderDescriptor.harness_status_observers or a second runtime registry.' Under capability-driven observation this needs revising: the provider CAPABILITY model IS a legitimate declaration source. Specifically the `launch` capability already declares observability channels per intent (descriptor.launches.*.observability = [pipe, acp, rpc, hooks]). That IS the provider declaring its observation surface. AS19 should CONSUME that capability declaration rather than prohibit the descriptor as a source.

2. CONVERGENCE (the real point): the provider's session/launch/observation surface is declared in THREE overlapping places today — (a) the `launch` capability (launches + observability channels), (b) AS29 ProviderDescriptor.session_surfaces (descriptor-local session-surface declarations), (c) AS27 harness_observability_inventory (per-surface facts). AS19:115's 'sole source = AS29 surface' and the capability model's 'launch observability channels' are two declarations of the same thing. Proposal: ONE provider declaration of the session/launch/observation surface — the capability model — with AS29 'resolved surface' being the RESOLVED/validated view derived from it, and AS27 holding the PROOF (probe validation_state / effective_production_level). Split declaration (capability) from proof (AS27), and stop having session_surfaces be a separate orthogonal declaration parallel to the launch capability.

3. DECLARATION vs PROOF is the clean seam and preserves AS19's actual guarantees: the neutral transport/observation CONTRACTS, the observer-cannot-control-lifecycle rule, and 'unsupported surface creates no child' all stay — they operate on the RESOLVED surface. What changes is only the SOURCE of the declaration (provider capability, not a separate descriptor registry / AS29-only). AS19's prohibition on a SECOND registry is satisfied because there is still ONE source — it just becomes the capability model instead of a bespoke session_surfaces field.

4. OPEN sub-questions (for AS19/AS29 owners): is observation a facet of the `launch` capability (recommended — observability is already a launch channel dimension) or a sibling `observation` capability? Does AS29 session_surfaces get absorbed into / derived from the launch capability, or stay as the resolved-surface cache? Where does ACP session-control capability (open/prompt/control/close support) live — launch capability evidence, or AS19/AS54?

## Conclusion

Recommend revising AS19:115 so the provider capability model (launch observability channels) is the observation DECLARATION source, consumed by the AS19 observer; AS29 'resolved surface' becomes the validated view derived from it; AS27 keeps the PROOF. Converge the three parallel declarations (launch capability / session_surfaces / observability inventory) into one capability-driven declaration + proof split. Preserves AS19's neutral contracts and observer-safety guarantees; changes only the source. Cross-plan: coordinate with provider-capability-model PC01 (launch capability + observation), AS29 (session_surfaces), AS27/AS54 (proof). Not started — design reconciliation to do before AS19 implementation locks the 'sole source = AS29' contract.
