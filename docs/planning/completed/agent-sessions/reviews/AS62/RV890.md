# Foundation composition adoption assumes a binding without checking statefulness first

## Notes



## Findings

AS62's "Foundation composition adoption" section, its §1 standards bullet, its Reassess-before-AS63 gate, and its Validation section all assume Agent Definition lookup/resolution is built through the foundation composition graph -- written before ARCHITECTURE_STANDARDS.md §1's "Composition candidates" doctrine existed, and before AS60/AS61 both independently found their analogous storage layers did NOT need composition.

Applying that check to Agent Definition: it is "stable ID, name, description, one Execution Profile reference, one Role reference, optional advertised skills, optional publication flags" -- structurally identical in shape to ExecutionProfile and Role (both project-local, YAML-stored, CRUD-managed, resolved stateless-ly). Its resolver "receives the Execution Profile, Role and AS29 provider APIs explicitly and returns a short-lived resolved value for admission" -- the same pure per-call computation shape project-local execution-profile resolution turned out to be, not a registry with install/uninstall or hot-reload semantics like the shared-gateway registry that DID legitimately need composition.

No consumer described in AS62 (AgentTask, ACP/A2A publication) exists yet -- they are correctly deferred to AS63/AS65/AS66. Nothing in AS62's own text describes genuine runtime state, a live connection, or construction/shutdown ordering worth owning for Agent Definition storage or resolution itself.

## Conclusion

Agent Definition storage and resolution should be plain Python (CRUD store + resolver function), mirroring Role and project-local ExecutionProfile resolution -- not a composition binding. Correct AS62's "Foundation composition adoption" section, §1 standards bullet, Reassess-before-AS63 gate, and Validation section's "fake dependencies supplied through the foundation graph" bullets to plain-Python parameter injection at the call site instead, mirroring the AS61 gate correction already applied. This does not remove the requirement that the resolver receive Execution Profile/Role/providers_api lookups explicitly (still true) -- it only corrects the mechanism by which that injection happens and by which tests substitute fakes.
