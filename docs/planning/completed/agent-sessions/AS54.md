# Implement per-harness observation recipes, probes, and capability evidence

## Description

Classify every known harness surface or mode under one explicit observation recipe and record three independent facts: declared candidate capability, exact validation state, and effective production capability. AS29 `session_surfaces` remains the sole runtime declaration owner. AS19 remains the sole provider-neutral observation/evidence contract and generic mapper. AS21 remains the sole lifecycle/status projector.

This plan creates the reusable probe/evidence matrix and provider-local native adapters required by later surface plans. A documentation claim can create a candidate and probe, but it cannot activate runtime observation, controls, content, or configuration mutation.

## Fixed Recipes

### Recipe A — transport-native observation

Use when the selected authoritative transport exposes machine-readable lifecycle events, including ACP, native RPC, SDK, WebSocket, or server event APIs.

- The provider-local transport adapter maps raw native frames into bounded AS19 `TransportObservation` values.
- The AS19 generic mapper validates ordering, correlation, freshness, declared vocabulary, and produces `StatusEvidence`.
- Do not create a provider-local neutral `status_observer.py`, second observer registry, or `harness_status_observers` descriptor field when the generic mapper is sufficient.
- The AS29 surface declaration uses `lifecycle.source: transport` and records exact declared/effective level, ordering, correlation, installation `none`, version/platform evidence, and validation state.
- No hook/plugin/config write is permitted for this route.

### Recipe B — managed native hook or plugin observation

Use only after an exact version/platform/mode probe proves a supported project-scoped hook/plugin lifecycle.

- Provider code normalizes the provider's raw hook payload to the AS19 neutral vocabulary.
- Reuse the existing provider configuration family such as `manage_hook_entries`, plugin reconciliation, or the provider's established reader/writer/remover. Do not add an agents-owned config writer.
- Stable managed IDs and ownership scope must allow plan/status/apply/prune without deleting operator-owned entries.
- Hook commands receive only bounded per-session ingress endpoint/token/binding context, emit one redacted correlated record, and fail open for provider execution if observation delivery fails.
- Hooks/plugins observe only. They cannot dispatch prompts, cancel, steer, answer permissions, select sessions, or own lifecycle.
- AS29 records the exact installation mechanism and proof. Uninstall/prune and reload behavior are part of the probe.

### Recipe C — structured one-shot or CLI output

Use only when an isolated run proves a stable documented machine schema.

- Parse only the structured schema; never regex prose.
- Map stable records to AS19 `TransportObservation` and then the generic mapper.
- EOF, silence, process exit, final-looking prose, or resource inactivity are not terminal evidence unless the declared machine schema explicitly and verifiably defines them.
- No persisted instrumentation is installed.

### Recipe D — unresolved, external, or unsupported

This is a valid conservative outcome.

- Add no runtime adapter, hook/plugin writer, descriptor capability, or native control claim.
- Record candidate sources, exact version/mode investigated, validation state (`probe-required`, `blocked`, or `unsupported`), effective level `O0` or unsupported, limitation, and the next probe anchor.
- Locally owned/adopted processes may provide process-health evidence only. Remote, cloud-managed, editor-hosted, and external instances do not inherit process evidence.
- UI scraping, terminal scraping, output silence, resource inactivity, EOF, and final-looking prose cannot complete a turn.

## Evidence Record

For every surface/mode record:

- provider ID and surface ID;
- executable/package/extension version and platform triple;
- launch or attachment mode;
- candidate source and date/version;
- recipe A/B/C/D;
- exact lifecycle vocabulary observed;
- ordering and correlation fields;
- freshness/replay behavior;
- ownership and installation behavior;
- declared capability level;
- validation state;
- effective production level;
- supported controls and content channels, each independently probed;
- redacted probe artifact/test anchor;
- limitation or unsupported reason.

Unknown means unsupported. Validation is platform-specific; Linux Docker evidence does not validate Windows and Windows evidence does not validate Linux.

## Probe Implementation

1. Add one provider-neutral probe result schema and validation command under the existing provider capability/reference tooling rather than a runtime registry.
2. Each probe pins exact executable/package/extension version, platform, launch/attach command, project fixture, provider identity, and surface mode.
3. For interactive surfaces, run two turns and stimulate every claimed phase: activity, tool call, permission wait/response where supported, cancellation, terminal/idle, and close/detach.
4. Capture only redacted native-to-neutral traces. Raw payload fixtures may exist in provider-private tests but must be scrubbed and never enter agents/public records.
5. Prove ordering, duplicate/replay behavior, correlation, stale-event rejection, control acknowledgement semantics, and cleanup.
6. Promote AS29 effective capabilities only after the matching implementation is registered and the exact platform probe passes. A candidate remains non-executable.
7. On version mismatch or missing evidence, resolve to unsupported/O0 without modifying provider configuration.
8. Add schema and architecture tests preventing a second observer registry, provider-name branching in agents, and descriptor-only activation.
