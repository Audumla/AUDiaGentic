# Define the compute resource, endpoint and execution lane taxonomy

## Description

**Design item. Produces a decided taxonomy, not code. Needs sign-off before dependent items start.**

The configuration model has no representation of the thing that is actually contended. `ExecutionProfile` carries `max-concurrency` and `queue-max-size`, but a profile is a *selection* (which model, through which harness), not a *resource*. Underneath sits a GPU, shared across every project — **no project owns one**. The gateway is the management layer that abstracts that: projects request work, the gateway coordinates where and when it runs.

Because capacity is attached to the selection rather than the resource, the gateway cannot express the real constraints — including the one that motivated this item: the same model loaded on two GPUs appears under two distinct server names (`m27b1`, `m27b2`), and a profile should be able to use either, running on whichever frees first.

This item defines the missing layer. The resulting model is **smaller** than what it replaces: making the model instance the unit of capacity removes the configured concurrency limit entirely rather than relocating it.

## Validation

This item is validated by a decision, not a test run. The agreed model must express all of these, each with a stated representation:

- The same underlying model loaded on two GPUs as `m27b1` and `m27b2`, with a profile naming both and running on whichever has spare capacity first.
- An instance serving several requests concurrently (`--parallel N`), with capacity counted rather than treated as a single slot.
- Concurrency differing per model on the same instance, since a larger model supports fewer parallel sequences.
- Two profiles whose instance sets overlap, without either being able to exceed the shared instance's capacity.
- Several models behind one swapping instance, including the drain-before-swap constraint and the starvation it can cause.
- A hosted API whose capacity is a rate budget rather than sequences.
- The CLI's embedded rig.

Plus:

- Total concurrency is the sum of declared instance concurrencies — there is no configured number anywhere that could disagree with the hardware.
- A project appears nowhere in capacity, and instances are never partitioned by project.
- The migration for `ExecutionProfile`'s two capacity fields and for `lane_key.public_id()` is stated as a versioned change.

## Effort & Risk

Design risk, not implementation risk.

- **Over-modelling.** Capacity-counted dispatch with a compatibility set is small and well understood — an ordered pending list, an `in_flight` counter per instance, first-compatible-with-room wins. Resist turning it into a general scheduler, a bin-packing optimizer or a bidding system. Swap-avoidance and batching preference are tie-breaks, not an objective function.
- **Under-modelling.** Two specific collapses lose real behaviour: treating an instance as a single slot loses `--parallel` batching, and hanging concurrency off the instance alone loses that a larger model supports fewer sequences.
- **The drain-before-swap starvation case.** Easy to miss and it produces a live hang rather than a wrong number — a swapping instance under steady same-model load never drains, so the other model never runs. Needs a bounded guard, not an optimizer.
- **Migration surface.** This removes two live schema-backed profile fields and likely retires a persisted, logged lane identity. That contract migration is the real cost of the change, not the dispatch logic.

The simplification is genuine: this deletes the concept causing the defect rather than adding machinery around it.

## Standards

- `arch-standards` §3 Ownership and Abstraction — capacity belongs to the resource that is contended, and each durable declaration gets one owner. This item exists because capacity currently has the wrong owner.
- `arch-standards` §3 Evidence-led scope — model the deployment that exists (one swapping endpoint, hosted APIs) with seams for the rest; do not build a general scheduler now.

- `arch-standards` §4 Public Contracts — `lane_key.public_id()` is persisted and logged, and the two `ExecutionProfile` capacity fields are schema-backed; both changes are explicit versioned migrations.

## Acceptance Criteria

- A decided, written taxonomy separating what is **selected** (profile) from what is **contended** (model instance capacity), signed off by the owner.
- An execution profile can name several instances and run on whichever has spare capacity next.

## What the gateway is

The gateway is the **management and coordination layer over shared hardware**. GPUs are shared across all projects; **no project owns a GPU**. Projects submit work and the gateway decides where and when it runs. Every design decision below follows from that.

## The defect this replaces

`ResolvedExecutionProfile.lane_key()` (`gateway/profiles.py:146`) returns `(profile_id, generation, config_digest)` — **`model_id` is a field on the same class and is deliberately excluded.** So concurrency is enforced per *profile configuration*, and two differently-named profiles pointing at the same hardware each get their own `max_concurrency` limit. Together they over-subscribe the GPU.

The root error is that `max-concurrency` sits on `ExecutionProfile`, which is a **selection**, not a **resource**. Under the model below the problem dissolves rather than being patched.

## Concepts

### 1. Model Instance — the unit of capacity

A named, server-addressable place work actually runs. The server already names these: if the same underlying model is loaded on two GPUs, the server exposes it twice under distinct names — `m27b1` and `m27b2`.

| Field | Meaning |
|---|---|
| `instance_id` | the server-side name (`m27b1`) |
| `logical_model` | what it actually is, so `m27b1` and `m27b2` are known to be equivalent |
| `servable_models` | mapping of model → concurrency this instance grants that model when loaded (not a flat list — a larger model leaves less VRAM for KV cache and supports fewer parallel sequences, so concurrency is per (instance, model), never a single instance-wide number) |
| `loaded_model` | which key of `servable_models` is currently loaded |
| `resource_id` | which Compute Resource it occupies |

`servable_models` versus `loaded_model` is what makes this one concept cover every deployment shape:

- **Dedicated instance** — one entry in `servable_models`, always loaded.
- **Same model, two GPUs** — two instances (`m27b1`, `m27b2`), same `logical_model`, both loaded, each with its own concurrency.
- **llama-swap** — one instance, several entries in `servable_models` (each with its own concurrency), one `loaded_model` at a time. Dispatching a request whose model is not loaded costs a swap.

The earlier draft's separate `resident`/`evicting` residency flag is **dropped** — it is expressed by whether `servable_models` has more than one entry. Capacity is a **counted pool**, not a boolean slot: `--parallel N` on llama-server genuinely means N concurrent sequences, and batching them is the efficient case, not a compromise.

### 2. Compute Resource — the physical grouping

The GPU or host that instances occupy. Needed to know which instances contend for the same silicon and for capacity accounting. Deliberately thin: instances carry the concurrency, resources carry the grouping.

Hosted APIs (Anthropic, OpenAI) are a resource whose capacity is a rate budget rather than slots.

### 3. Execution Profile — selection over a *set*

Changed from the current shape: a profile names **a set of acceptable Model Instances**, not one model.

```
profile: fast
  harness: pi
  instances: [m27b1, m27b2]
```

Whichever has spare capacity next is where it runs. The profile keeps its harness binding, launch params and surface selection, and **loses `max-concurrency` and `queue-max-size`** — capacity is no longer its business.

The set may be authored explicitly or resolved from a logical model ("every instance serving `qwen3-27b`"); either way it resolves to a set before dispatch.

## Dispatch

The scarce thing is instance *capacity*, so make that the thing that gates:

1. One ordered pending queue holds pending requests. Each carries its compatible-instance set.
2. An instance has **spare capacity** for a given model when `in_flight < servable_models[model].concurrency` **and** that model is the `loaded_model` (or the instance is idle and can load it).
3. A request is never bound to an instance at admission — only at dispatch, when an instance actually has room. That is what makes "whichever is free next" work: binding early would queue a request behind a busy instance while another had room.

**Over-subscription becomes structurally impossible**: work only ever dispatches into measured spare capacity, so no configured limit can be wrong. `max-concurrency` is not moved to a better home — it stops existing. Total system concurrency is the **sum of declared instance concurrencies**.

Overlapping profile sets (`A: [m27b1, m27b2]`, `B: [m27b2, m27b3]`) are handled correctly by construction — `m27b2` admits work up to its own limit regardless of which profile wanted it.

### The drain-before-swap constraint

This falls out of combining concurrency > 1 with swapping and is easy to miss:

**A swapping instance cannot change its loaded model while requests are in flight.** An instance with `servable_models[qwen3-27b].concurrency = 4` can run 4 concurrent requests *of the currently loaded model*, but can only accept a request for a different `servable_models` entry once `in_flight` has drained to zero for the current one.

So availability is conditional on the request's model relative to what's loaded:

- request model **is** `loaded_model` → available while `in_flight < servable_models[loaded_model].concurrency`
- request model **is not** `loaded_model` → available only when `in_flight == 0` (fully drained)

**The failure mode this produces is a live hang, not a wrong number**: under steady same-model load an evicting instance never drains, so a different model queued behind it never runs — starvation, not miscounting. AS105 requires only that a bounded guard exist (e.g. stop admitting more same-model work once a different-model request has waited past a threshold, forcing a drain-and-swap); building a general fairness optimizer is explicitly out of scope (§3 evidence-led scope) until real contention data shows the simple guard is insufficient.

### Scheduling preferences — tie-breaks, not correctness

When several placements are valid: prefer an instance with the model already loaded (avoids a swap), and prefer filling one instance's parallel capacity over spreading across GPUs (batching is why `--parallel` exists). Both are preferences. Neither affects correctness.

## What happens to the lane

`GatewayExecutionLaneKey` and per-lane concurrency semaphores largely dissolve. What remains of the queue is **admission ordering and fairness**, not capacity. That is where project scoping applies — see below.

This is a simplification, but `lane_key.public_id()` is persisted and logged, so its removal or replacement is a versioned contract change.

## Where the project fits

A project never appears in capacity. It appears in exactly two places:

- **Record separation and visibility** — already correct via `agents_paths.gateway_root(project_root)`.
- **Scheduling fairness** — so one project cannot starve another out of shared instances. Round-robin across projects when selecting the next compatible pending request is sufficient and cheap.

Partitioning instances by project is explicitly wrong: it would idle hardware one project is not using while another queues.

## The rig is not the model infrastructure

The original draft treated `rig.yaml` as a source of the capacity model. That is wrong. **The rig is the AUDiaGentic CLI's own embedded llama-server and nothing more** — it is one consumer, not the general serving layer. Its `parallel: 1` is the capacity of *that one endpoint*, not an authority the taxonomy derives from.

What the rig becomes instead is a **worked example**: the CLI's embedded server is one Compute Resource with one `resident` Model Endpoint serving one model. If the taxonomy cannot express the rig cleanly, the taxonomy is wrong — but the rig does not define it. Use it as a test case, not a source.

(Step 3's "reconcile with `rig.yaml`'s `parallel: 1`" should be read this way: the rig's own endpoint declares its own concurrency like any other endpoint. There is no global reconciliation to perform.)

## Where the declarations live — decided

The AUDiaGentic CLI is the **management plane**; the gateway is the execution plane. The CLI manages configuration globally, and when the gateway later becomes a shared service the CLI updates that service's configuration while continuing to manage project-local resources.

This maps directly onto the layering that already exists in `foundation/config/layers.py::load_layered_config`, which resolves three tiers — package default, **user-global** (`audiagentic_home()/config/<namespace>.yaml`), and **project-local** (`<project>/.audiagentic/config/<namespace>.yaml`). No new tier is needed:

| Declaration | Tier | Why |
|---|---|---|
| Compute Resource | user-global | describes shared infrastructure, not one project's intent |
| Model Endpoint | user-global | same |
| Execution Profile | project-local *(already)* | a project's selection of model + harness |
| Role, Agent Definition | project-local *(already)* | project-owned behaviour |

So resources and endpoints get their own namespace resolved at the **user-global** tier. When the shared service arrives, that same namespace is what the CLI pushes to it — the local file becomes the authored copy and the service holds the deployed copy.

## One hazard this creates, worth closing now

`load_layered_config` merges **project-local over user-global**. Left alone, that means a project could redefine the capacity of shared hardware simply by declaring the same namespace in its own `.audiagentic/config/`, and silently over-subscribe a GPU it does not own.

Security layering is explicitly deferred, and this is **not** proposed as a security control — the concern is an ordinary configuration accident, and it is cheap to prevent: either resolve the resource namespace with `project_root=None` so the project tier is never consulted, or reject capacity fields appearing at the project tier with a registered error. Decide which; do not leave the merge silently permissive.

## Still open, not answered by this input

Endpoint health and liveness. Multi-endpoint dispatch implies knowing which endpoints are up, which is a real subsystem. Recommend keeping it out of the first cut — a single-endpoint deployment does not need it, and the seam is additive.

## Migration Stance No Legacy

**Owner decision 2026-08-05: no legacy is retained. Any refactor here is a lift-all.** This aligns with `arch-standards` §4 ("backward compatibility is not maintained by default") and `ARCHITECTURE_GUIDELINES` §9, and it materially *simplifies* this item — several of the migration questions above dissolve.

**What that means concretely:**

- `ExecutionProfile.params.max-concurrency` and `queue-max-size` are **deleted**, not deprecated. No alias, no dual read, no "honoured if present" fallback, no compatibility test. Every profile config in the repo and in `.audiagentic/config/` is updated in the same change.
- `GatewayExecutionLaneKey` and its per-lane semaphores are **retired**, not kept alongside instance dispatch. `lane_key.public_id()` disappears from records and logs; the schema increments once and old records are not readable under the new contract.
- `ExecutionProfile.model_id` becomes an instance set outright. There is no single-model compatibility shape.
- SH08's `resource_key_for(provider_id)` is **replaced** by instance-derived keys, not extended with a fallback branch.

**What still requires care despite no-legacy** — lift-all removes the compatibility burden, not the correctness one:

- `arch-standards` §7 and `GUIDELINES` §9 both require the migration to search production code, tests, configuration, dynamic imports, patches and dotted-path strings for the old names, and to update all of them in the same change. `lane_key` is referenced across queue, dispatch, records and log fields; that sweep is the actual work.
- Persisted records written under the old contract still exist on disk at cutover. No-legacy means we do not *read* them under the new contract — but the recovery path must fail cleanly on them rather than misparse. Decide: reject with a registered error, or clear the runtime tree at migration.
- The schema version increments once, explicitly. Deleting fields without incrementing is not lift-all, it is silent breakage.

**Consequence for sequencing:** this makes riding with `shared-gateway/SH11` more attractive, not less. SH11 is already a consumer-wide cutover; a lift-all contract change wants exactly one consumer sweep, not two.

## Validation 2026 08 08 Schema Registration Mechanism

**Checked directly, prompted by a second arch-standards question: do the two new declarations need JSON Schema registration (`foundation/contracts/schemas/*.json` + `CANONICAL_SCHEMA_IDS`), the way `ResolvedExecutionProfile` has `resolved-execution-profile.schema.json`? The real dividing line in this codebase, confirmed two ways:

1. **What gets JSON-Schema-validated vs hand-validated.** `role.py`/`execution_profile.py` (project-runtime config, edited live via CRUD tools) both use hand-written `validate_role`/`validate_execution_profile` Python functions — no schema file. `ResolvedExecutionProfile` (a value constructed and persisted into durable execution records that cross process/service boundaries) uses `validate_with_schema(...)` against a real JSON Schema. ## Correction 2026 08 08 Ownership Folded Into Providers

**Self-correction, same day as `closed_2026_08_08`, prompted by the owner (see RV898). The taxonomy in `concepts`/`dispatch` is unchanged and still governs AS101's dispatch-layer implementation. Only `config_placement_decided_2026_08_05`/`code_samples`' storage sketches are superseded.**

Those sections proposed two new user-global files, `compute-resources.yaml`/`model-instances.yaml`, owned by `agents`. AS101 built exactly that (Slice 1), then the owner pointed out that `providers` already owns a master model catalog — `model-sources.yaml`, with its own layering-eligible config and a provider-projection mechanism (`apply_model_sources`) that pushes it into every enabled harness's native config. A Model Instance ("a named, addressable place work runs, with a concurrency figure") and a `model-sources.yaml` local-endpoint source describe the same underlying thing from two different angles — building both is not a richer model, it is two owners for one concept, which `arch-standards` §3's one-owner rule rules out.

**What is superseded:** `compute-resources.yaml`/`model-instances.yaml` as separate files, and their corresponding YAML sketches in `code_samples`. **What replaces them:** `resource-id` and `concurrency` as optional fields directly on a `model-sources.yaml` source (local-endpoint class only), with the *existing* schema/loader (`providers/services/config/model_source_config.py`) extended to resolve at both user-global (`audiagentic_home()/config/model-sources.yaml`, shared hardware) and project-local (existing, unchanged) tiers via `foundation.config.layers.load_layered_config`, exactly the same two-tier resolution this item already specified — just attached to the pre-existing schema instead of a new one. `load_model_sources`/`write_model_sources` deliberately stay project-local-only and unchanged, so a project's own file is never polluted with inherited global sources on a read-modify-write mutation; the merged view is a separate, read-only `load_resolved_model_sources(project_root)`.

**What is unaffected:** `concepts` (Model Instance/Compute Resource/Execution Profile-over-a-set as concepts), `dispatch` (free-instance binding, drain-before-swap, structural over-subscription-impossibility), and `where_the_project_fits` all describe the *dispatch-time* model, which is orthogonal to where capacity is declared. AS101's Slices 2-4 (ExecutionProfile v2, free-instance dispatch, reporting scope) still implement this item's `dispatch` section directly — they now resolve `instances` against `model-sources.yaml` sources instead of a separate Model Instance record.
