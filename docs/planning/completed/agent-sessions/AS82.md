# Add session-surface selection to Execution Profile

## Description

Add a `surface_id` field to Execution Profile so a profile can name which AS29 session surface it launches through, and resolve it at admission.

This is the single field whose absence blocks two other items: AS62's step 3 ("resolve the selected AS29 surface") could not be built because `ExecutionProfile` carries no surface to resolve *from*, and AS60's step 5 deferred it waiting on AS29 — which is now complete.

## Steps

1. Add optional `surface_id: str | None` to the `ExecutionProfile` dataclass, its schema, and its CRUD/validation path. Absent means "provider default", which is the current behaviour — not an error.
2. Extend `resolve_agent_definition` (or the admission resolver, whichever is the single call site) to resolve the surface through `providers_api.resolve_session_surface` when `surface_id` is set. Resolution is a read: it launches nothing.
3. An unresolvable or unvalidated surface fails at admission with a registered error, before dispatch. Do not fall back to the provider default when a surface was explicitly named.
4. Carry the resolved surface identity into the admission value (`ResolvedExecutionProfile`) so downstream consumers read it rather than re-resolving.

## Validation

- A profile with no `surface_id` resolves exactly as today (regression).
- A profile naming a validated surface resolves it and carries its identity into the admission value.
- A profile naming an unknown or unvalidated surface fails at admission with a registered code, and does not silently use the provider default.
- Resolution launches no process — assert by fake that `open`/`prompt` are never called.

## Codebase Verification 2026 08 05

**Verified against the tree. Premise confirmed.**

`models/execution_profile.py:14` — `ExecutionProfile` carries exactly `profile_id`, `provider_id`, `model_id`, `model_alias`, `params`, `is_default`, `description`. There is no `surface_id`, confirming both this item's premise and AS62's recorded reason for deferring its own step 3.

`validate_execution_profile` (line 25) is a plain issue-list validator, so adding an optional field is additive and needs no migration — an absent `surface_id` produces no issue.

**One thing to get right:** `agent-execution-session.schema.json` already persists `surface-id` and `surface-version` on the binding, recorded from the resolved surface at open. That is the *resolved* surface for a live session. The new `ExecutionProfile.surface_id` is the *requested* surface. Keep the two distinct — requested is configuration, resolved is evidence, and conflating them would lose the ability to detect that a profile now names a different surface than a live session was opened with (which is exactly the check AS88 needs).

## Implemented 2026 08 07
