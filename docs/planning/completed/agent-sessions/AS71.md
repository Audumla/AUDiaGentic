## Findings

### 1. RESOLVED 2026-08-02 — it was a production bug, not test pollution

The three `test_as41_observability_tap_threading.py` failures are fixed. The
cause was not test isolation:

`coding_lsp/lsp_session_resolution.py::_refresh_path_after_install()` read the
**user-scope** `HKCU\Environment\PATH` and assigned it directly over
`os.environ["PATH"]`. Two defects in six lines:

1. HKCU holds only the user PATH, so the assignment **discarded the
   machine-scope (HKLM) and inherited entries** — 94 PATH entries collapsed to
   51 and `C:\Program Files\nodejs` disappeared. Every later `shutil.which`
   for node/npx failed for the remaining life of the process.
2. Registry PATH is `REG_EXPAND_SZ`; `QueryValueEx` returns it unexpanded, so
   appended entries arrived as literal `%LOCALAPPDATA%\agy\bin` and were inert.

A function whose docstring says it picks up newly installed directories was
instead removing working ones. In production this means any AUDiaGentic process
that installs an LSP package loses the system PATH for the rest of its life —
so a later provider launch needing npx fails. The test suite merely exposed it,
because `tests/unit/coding_lsp` runs before `tests/unit/providers`.

Fixed by expanding `REG_EXPAND_SZ` and *appending* only genuinely new entries,
case-insensitively deduped, never replacing the existing PATH.

**Two follow-ups this uncovered, both still open:**

- **A swallowed error cost most of the diagnosis time.**
  `services/execution/public_execution.py:621` wraps the launch builder in a
  bare `except Exception:` and returns `PreparedSessionTransport(transport=None)`
  with no logging. The real cause was a registered, perfectly descriptive
  `RES-PIACP-001` ("pi-acp bridge not found... install pi-acp or npx") that was
  discarded, leaving the caller with `assert None is not None`.
  `arch-standards` §4 requires failures to be classified and degraded state
  reported safely — silently dropping a registered `AudiaGenticError` is neither.
  Log it at minimum, and prefer carrying the reason on the returned snapshot.
- **The AS41 tests have an undeclared external dependency.** They reach
  `build_acp_launch`, which requires `npx`/`pi-acp` on PATH; without Node
  installed they fail on any machine, PATH bug or not. They carry no
  `requires_npm` marker or skipif, though the marker exists
  (`pyproject.toml:132`) and `tests/integration/.../test_pi_rpc_tap_real_binaries.py`
  uses it. `BLOCKING decision`: either (a) mark them `requires_npm` with a
  skipif, accepting that CI skips them, or (b) reshape them to assert hook
  threading against a fake builder so the unit tier needs no real binary.
  (b) is likely correct — the assertion is about wiring, not about pi.

### 2. `test_hindsight_provision.py::test_reconcile_populates_pi_host_block`

**Resolved as a decision and handed off to HM22 (2026-08-02).**

Hindsight is HTTP-only (user-confirmed; also documented at
`components/memory/hindsight/INSTALL_MAP.md:69`). That makes this not a pi
question but a Hindsight-provisioning question:

- pi has **never** declared `remote` — verified before and after the PC01-PC04
  migration. The guard rejecting it landed 2026-07-15; `hindsight-pi.yaml` was
  authored 2026-07-26 asking for `transport: http`. The recipe has never
  worked and this test has never passed. Not a regression.
- The apparent fallback is fictional: `hindsight-managed-mcp-stdio.yaml`
  registers `command: hindsight-mcp`, which Hindsight does not ship. Six
  providers (antigravity, claude, cline, continue, gemini, qwen) route to it and
  **silently write an entry that can only fail at launch** — a worse failure
  mode than pi's loud one. Only goose declares `remote: true` and therefore
  actually works.
- The one genuinely open question is narrow: does `pi-mcp-adapter` honour
  `{"type": "http", "url": ...}` in `.mcp.json`? Not answerable from the tree —
  pi's MCP support is an extension and its upstream docs are 404. Needs a Docker
  probe.

Full analysis, routing table and the `BLOCKING` pi decision are in **HM22**
(`docs/planning/active/memory-hindsight/HM22.md`). AS71 does not fix this; it
closes when HM22 lands or when pi is dropped from `_ARTIFACT_RECIPES` in the
interim.

Correction for the record: mid-diagnosis it was claimed goose had *lost* its
`remote: true` in the capability migration. That was wrong — the flag is present
at `capabilities.mcp.mechanism.remote`; the survey reporting otherwise read the
wrong YAML path.
