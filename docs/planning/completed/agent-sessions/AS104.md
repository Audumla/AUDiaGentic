# Role capability policy gates and evidence-derived presets

## Description

**Hardening item — deliberately sequenced last, and additionally gated on real usage evidence.**

Add policy gates preventing silent capability escalation, and introduce role presets derived from measured usage rather than anticipated need.

Being unblocked is not sufficient to start this. It needs a period of roles actually running in practice first — presets created before that encode guesses and cause churn.

## Steps

1. Collect real job and workflow capability usage. Derive candidate presets from that evidence.
2. Approve a minimal preset set only where the evidence justifies each one individually.
3. Add migration and status tooling that reports unresolved or excess capabilities before any behaviour changes.
4. Require explicit authorization for privileged capabilities, with audit and timeline facts recorded.
5. Migrate selected workflows incrementally, with rollback at each step.
6. Remove the role-less compatibility default introduced by the role-selection item, or record an approved external obligation for keeping it. This step is the condition under which that default was permitted — it is not optional cleanup.

## Validation

- Every approved preset traces to recorded usage evidence. A preset with no evidence is not shipped — this is the item's defining constraint, not a preference.
- Migrated workflows run with measurably fewer exposed capabilities, evidenced by a before/after count rather than by continuing to pass.
- Requests for undeclared or privileged capabilities fail closed and are auditable.
- No hidden fallback silently restores all capabilities. Asserted directly — this is the single most important assertion in the item.
- The unrestricted-compatibility role is selectable by explicit name, visible in audit facts, and removable — never an implicit default.
- The role-less default is removed, or its retention is recorded as an approved obligation.

## Two Gates Decided 2026 08 09

**The single "wait for AS85 usage" gate is circular as written. Split into two gates (RV922).**

As written, `blocked_by` says AS85 must have been *running in practice*, while step 1 of this item is "collect real job and workflow capability usage". The item is gated on evidence it is itself responsible for collecting — so "run AS85 for a while, then start AS104" risks discovering at the end that the wrong evidence was collected, or none.

The underlying distinction, which is the sharpest point from the review: **AS85 persists the resolved manifest and fingerprint, which proves what was MADE AVAILABLE to a run — not what was actually USED by it.** Presets derived from availability data would encode exactly the guesses this item exists to avoid.

**Gate A — measurement plumbing.** May start as soon as AS85's role-identity / manifest-fingerprint contract is stable. Does not wait for an evidence period, because it is what makes the evidence period meaningful.

**Gate B — policy.** Presets, escalation gates, workflow migration, and removal of the role-less compatibility default stay gated on real accumulated usage evidence, exactly as before. Unchanged, and still last.

**Measurement scope (M, not L).** Two hooks are already available and cheap:
- *Launch/materialization evidence* — at the point AS85 materializes the frozen manifest, record that capability X was provisioned for role/fingerprint Y. For capabilities like isolation tier or config projection, materialization **is** the meaningful event; there is no later invocation to observe.
- *AUDiaGentic-owned operation evidence* — the shared MCP decorator already centrally observes every decorated tool invocation (identity and timing only, deliberately not arguments), and gateway task/control operations are similarly canonical. Emit bounded facts: `{role-id, manifest-fingerprint, capability-id/tool-id, timestamp}`. No prompts, no tool arguments.

**Explicitly out of scope:** universal provider-native instrumentation — shell execution, native file operations, provider-native tools/plugins/hooks. That is an L+ observability project in its own right, and the adjacent plans confirm it is not close: Pi's `tool_execution_*` tap frames are not transcript-proven (AS96), and OpenCode's real tool-call behaviour is still among AS97's unproven items.

**Governing rule for the evidence period — "not observed" must never mean "unused".** Classify every capability by evidence mode: `materialized`, `observed-use`, `controlled-trial`, or `unmeasured`. Dropping a capability that is unobservable requires **positive** evidence — e.g. a representative workflow demonstrably completing without it — never silence in telemetry. Replace the vague "a period of roles actually running" exit criterion with a per-preset evidence criterion: enough observations to justify each candidate preset individually. Elapsed time is not evidence.

**AS85 gains no scope from this.** It remains responsible only for carrying role/manifest identity; the measurement hooks are this item's Gate A.
