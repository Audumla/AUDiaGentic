# Remove GPT-auto absolute response timeout and separate terminal grace policy

## Description

Replace the current 3600-second absolute response timeout with an unbounded activity-driven observation policy. Failure is governed only by lack of validated activity, configured refresh attempts, and final grace, while submission proof retains its own bounded safety policy.

## Steps

- Set the GPT-auto response total bound to disabled/unbounded by default.\n- Keep submission typing/send and submission-proof limits distinct from response observation.\n- Ensure response completion policy cannot emit response-total-timeout while validated activity continues.\n- Add explicit terminal reason for exhausted refresh recovery rather than reusing generic timeout.

## Detailed Solution & Technical Design

Make _ResponseCompletionPolicy response budget infinite when configured as zero/None and remove any outer timeout that treats elapsed wall time as provider failure. The response observer owns last_real_activity_at and recovery state. Submission proof remains bounded because it protects prompt identity and duplicate-send safety. Diagnostics must state which activity clock or recovery grace expired.

## Code Samples & Guidance

turn.response-timeout-seconds: 0\nturn.response-no-activity-refresh-seconds: 240\nturn.response-refresh-final-grace-seconds: 600

## Acceptance Criteria

- Default response observation has no absolute elapsed-time failure.\n- Submission proof remains bounded.\n- Only validated activity resets the response clock.\n- Exhaustion reports the refresh/grace reason.

- Every bounded timeout remains validated and configurable through provider configuration.
- v3 has no hard response start/stall/total terminal timeout regardless of legacy field values.
- Submission and submission-proof bounds remain active and independently configurable.
- Recovery interval and final grace are controlled by AS122 canonical fields, not hidden constants.
