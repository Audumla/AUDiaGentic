# Reconcile stale non-live active gateway session records

## Description

Gateway session listing can show persisted sessions with state active but live=false after the owning harness process is gone. This is not a live harness leak, but it creates confusing active-session state and can hide cleanup/recovery drift. Add a narrow recovery/status path that classifies or closes stale non-live active records without signalling external/provider processes and without starting a runtime.

## Steps

1. Reproduce with persisted active live=false records only; do not use a live session. 2. Identify the owning state authority: session listing/status may report stale/non-live, while any mutation must use the existing session/recovery ownership seams and must not create a second request recovery authority. 3. Add a conservative transition or diagnostic flag for active live=false sessions that are beyond idle/max lifetime or whose owning runtime epoch is gone. 4. Ensure external/adopted bindings are never signalled. 5. Add tests proving overview/list distinguish live active from stale non-live active, and that cleanup/reconcile does not start runtime or expose provider-session-ref. 6. Record ledger and update docs/reviews after validation.

## Files

src/audiagentic/components/agents/agents_gateway_sessions.py, agents_gateway_sessions_store.py, agents_gateway_recovery.py or a narrow session cleanup helper, agents_gateway_mcp/client diagnostics if exposed, focused unit tests.

## Validation

Focused tests with synthetic persisted records prove stale non-live active records are classified or transitioned without runtime creation, without process signalling, and with redacted public output. Gateway overview after cleanup reports zero live sessions and no misleading active stale records when policy applies.
