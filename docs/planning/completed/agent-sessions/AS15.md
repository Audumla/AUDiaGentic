# Session-aware profile concurrency: release slot when session is quiescent, re-acquire when turn starts

## Description

Profile concurrency currently tracks request-level "running" without regard for session activity. A session idle between turns holds a max_concurrency slot, blocking other sessions from making progress on the same profile. Fix: release the profile concurrency slot when a dispatched request's session is quiescent (turn_lock unlocked, no pending turns), and re-acquire it when the turn actually starts executing on the transport. This allows multiple sessions to share a profile's concurrency capacity proportional to actual compute usage.

## Steps

1. Add session activity query: SessionRuntime exposes whether a session handle is actively consuming compute (turn_lock locked AND pending > 0) vs quiescent.
2. In _dispatch_session_request, after acquiring the turn lock, release pq.running slot if the session was already quiescent before our turn started — the session isn't doing useful work while waiting on its turn_lock.
3. Introduce a two-phase concurrency model: hold pq.running slot only during actual transport execution (between turn_lock release and transport completion). During session-level queuing (waiting on turn_lock), do not occupy profile concurrency.
4. Ensure _drain can start new workers from other sessions while existing workers are idle waiting on session turn locks.
5. Add guard: if a request is in the session-level queue (handle.pending > 0), it must not consume both a session slot and a profile slot simultaneously — count it at the session level only until it acquires turn_lock.
6. Update gateway overview to show per-session compute state (active/quiescent) alongside profile running/pending counts.

## Validation

1. Two sessions on the same profile with max_concurrency=1 can both make progress: when Session A is idle between turns, Session B's request can execute.
2. No concurrency slot leak: profile running count never exceeds max_concurrency during actual compute.
3. Existing single-session workloads behave identically.
4. AS06 test suite exercises multi-session concurrency scenarios.

## Effort & Risk

Mid. Risk: turn_lock timing — ensure the release/re-acquire of pq.running slot is atomic with respect to _drain's read of len(pq.running).
