## Description

Introduce one provider-neutral, transport-independent status projection for request, session, turn, and workflow consumers. It is a read-only projection over AS19 normalized evidence, AS21 lifecycle decisions, SH07 durable request facts, AS28 observations, AS29 capability evidence, and AS30 bindings. It creates no durable state machine and no provider-native status surface.

## Steps

0. Preserve authority: SH07 request state, session-store state, agent-job workflow state, interaction state, and provider mechanics remain their existing durable owners. The new projector never writes or terminalizes them.
1. Add foundation-neutral `AgentStatusScope`, `AgentLifecycle`, `AgentOutcome`, `StatusEvidenceConfidence`, a compact `AgentWaitReason`, `AgentStatusDecisions`, and frozen `AgentStatusSnapshot` in a foundation status contract. Do not add broad `AgentActivity` or generic progress enums until evidence routes prove them.
2. Lock lifecycle to `pending|active|waiting|completing|available|terminal|unknown`. `failed`, `cancelled`, `interrupted`, `rejected`, `timed-out`, `expired`, `abandoned`, and `superseded` are `AgentOutcome` values only. This prevents the existing SH07 interrupted terminal from being lost and avoids competing state authorities.
3. Scope every snapshot explicitly. Initial supported scopes: `execution-request`, `session`, `turn`, and `workflow`. Reject/omit provider-session and interaction until AS30/interaction supplies a protected, correlation-safe source.
4. Materialization rule: a canonical snapshot field/value may exist only when its producing adapter/projector has a named evidence source, correlation rule, freshness/validation rule, redaction rule, and focused proof. If any part is absent, omit the field or return no snapshot dimension; do not emit `unknown`, `none`, placeholder enums, or UI text merely to advertise a future capability. Document future candidate states in comments/reference tables beside the contract, including their required evidence route, but do not instantiate them in runtime enums, serialized schemas, event payloads, or public APIs.
5. Make only evidence-grounded fields canonical in v1: lifecycle/outcome, AS21 decision flags, AS21 evidence acceptance/contradiction, durable reason code, bounded wait reason, current dispatch/progress phase, generation/attempt, and observed/projected timestamps. `activity`, activity detail, generic percentage/items/bytes progress, inferred model thinking, child health, and provider silence are absent unless a resolved AS29 surface declares and validates their route.
6. Extend AS21's pure projector or add a pure adapter that maps AS21 decision/evidence plus SH07 durable terminal facts into the snapshot. Add `service-recovery-interrupted`/equivalent trusted input so SH07 interrupted requests project `lifecycle=terminal,outcome=interrupted`; never treat replay-required as cancellation or failure. `replay-required` is a bounded recovery/decision flag, not lifecycle or wait reason.
7. Add explicit `WaitReason` only for proven inputs: `permission`, `queue-capacity`, `retry-backoff`, `dependency`, `child-work`, `provider-response`, `tool-response`, `operator-action`, `recovery-decision`, `unknown`. Require WAITING to carry a reason when evidence knows one; otherwise retain lifecycle waiting with no fabricated reason.
8. Rename the current runtime `available` boolean to `live-handle-available` or equivalent. Reserve status `available` for AS21's strict reusable-session decision: compatible AS30 binding, validated surface, no active turn, and trusted evidence.
9. Keep health separate and narrow in v1: snapshot may expose `unknown|healthy|degraded|disconnected` only when a durable/validated route provides it. Do not infer unresponsive from silence. Service health and session/turn health remain separate scopes.
10. Add explicit public projection adapters for SH07, session API, and agent-jobs. They consume snapshots/decision flags; they do not parse phase strings, provider event names, or raw status values. Preserve existing serialized workflow states behind versioned compatibility mappings.
11. Add table-driven combination tests: terminal requires non-none outcome; nonterminal requires outcome none; unknown/contradictory never releases dependent work; cancellation request/acknowledgement remains active; terminal cancellation requires durable authority; session available requires all AS21/AS30 prerequisites; interrupted remains distinct from failed/cancelled; no capability-less field appears in a snapshot.
12. Add architecture tests: no `Acp*`, provider-native state name, raw payload, raw provider ref, or descriptor type may appear in status contracts or consumers above providers. Validate equivalent fake ACP/native evidence produces identical snapshots.
13. Maintain a non-runtime future-status catalogue in code comments/reference documentation. Each candidate must name: intended scope, required normalized evidence, minimum AS29 observation level, correlation/freshness rules, redaction limits, owner, and activation test. Promote a candidate only in the same change that adds its evidence-producing code and passing integration proof.
14. Defer broad activity taxonomy and progress model to follow-on work only after AS31 content policy and concrete non-ACP surfaces provide validated evidence. Do not introduce `thinking`, `generating`, `streaming-output`, byte/token progress, or free-text activity detail as canonical v1 status.

## Validation

Equivalent validated ACP/native evidence yields identical snapshots; provider-native terms never leave providers; SH07 interrupted/replay-required projects terminal/interrupted without re-execution; cancellation request/ack remains nonterminal; unknown/contradictory evidence produces conservative flags; session `available` means reusable rather than merely a live handle; every v1 field has a named durable or validated evidence source; no output/thought/byte heuristic is fabricated.

## Effort & Risk

Cross-authority compatibility work. The main risks are creating a second durable state machine, confusing terminal outcome with lifecycle, leaking provider-native values, and promoting UI-friendly but unobservable detail to canonical status.

## Standards

Architecture Standards; Observability Standards; AS19 evidence normalization; AS21 pure projection; AS28 foundation neutrality; AS29 capability/evidence gating; AS30 binding/reuse rules; SH07 durable request authority. Reuse existing foundation contracts and public provider APIs; do not create a generic status registry.

## Notes

Design decision from taxonomy audit on 2026-07-20: approve a layered model, but constrain v1 to evidence-backed dimensions. The attached broad proposal is a useful future vocabulary catalogue, not an implementation mandate. In particular, lifecycle is small and stable; terminal semantics belong in outcome. `interrupted` must be terminal outcome, not an AS21 coarse lifecycle state. `replay-required` is recovery/decision metadata, not an outcome. Activity/progress detail remains absent until validated capability routes exist.
