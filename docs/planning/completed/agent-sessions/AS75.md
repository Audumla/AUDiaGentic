# CI has been red for 15 days and the Docker matrix has never run

## Description

**Zero green CI runs in the last 100** (96 failure, 4 action_required), spanning 2026-07-18 to 2026-08-02. Verified with `gh run list --workflow=ci-tests.yml --limit 100`.

Because the `docker-tests` job declares `needs: tests`, every one of those runs skipped the **entire 15-image Docker matrix**. Confirmed on three separate runs: `tests: failure` / `docker-tests: skipped`. So for at least fifteen days there has been no CI signal at all from provider-CLI, provider-lifecycle, LSP-install, MCP-tools, gateway crash/concurrency/opencode/pi-smoke, pi-rpc-tap or pi-acp-resume coverage.

This is the single most consequential finding of the AS70-AS74 batch: every item closed in that window recorded "full unit suite green" from a *local* run, while the actual CI gate was red the whole time and the Docker tier was not running at all.

Investigated only because AS74 step 5 flagged CI status as unverified. Note the doctrinal gap: `CLAUDE.md` says to use the source-control MCP rather than git/GitHub directly, but no source-control MCP is connected in this session, so CI status was unobservable through the sanctioned path. The user directed using `gh` for this investigation.

## Steps

1. **Push the three local commits first and re-measure.** `af52b905a`, `d58270aba`, `1f7b09d8b` are unpushed; CI's newest run is against `de14198d7`. They already fix a documented slice of the failures (see the categorised list below). Do not triage anything else until the post-push baseline is known.
2. **Close the environment-gating gaps** — the largest coherent category, and the same defect class AS71 just fixed for the AS41 tests. Mark with the existing `requires_*` markers and skipifs, or reshape to fakes where the assertion is about wiring.
3. **Fix the API-drift failures**, which look like real regressions rather than environment issues: `SessionRuntime.open_session() got an unexpected keyword argument 'launch'`; `module 'audiagentic.foundation.interaction' has no attribute 'read_record'` (2 tests); `FakePath has no attribute '_flavour'` (a pathlib internal the test doubles, changed in newer Python).
4. **Fix the substantive product failures:** planning contributions not injected into surfaces (3 tests, `Present: set()`); the pre-commit hook block emitting a literal `_HOOK_BLOCK_ID` placeholder instead of the substituted id; `INT-RELEASE-001: ledger archive event was not handled` (2 tests); scaffold config validation.
5. **Triage the e2e MCP-server failures** — 5 tests failing with `JSONDecodeError` on an empty response plus `KeyError: 'environment'` and `StopIteration`, and 2 lifecycle tests hitting the 30s pytest timeout. These may share one root cause (server not starting in CI).
6. **Then unblock the Docker matrix and confirm each image actually passes.** Until step 1-5 land it cannot run at all. Fifteen days of no signal means image rot is likely; expect failures unrelated to anything above.
7. **Add a guard against silent long-term red.** The failure mode here was not that CI broke — it is that nothing surfaced it for fifteen days while items were being closed against local runs. Consider requiring the CI conclusion in the Definition of Done, or a scheduled report.

## Why The Docker Tests Never Run

Traced 2026-08-03. Four independent reasons, none of which ever produces a red
signal.

**1. CI skips the whole matrix, silently.** `docker-tests` declares
`needs: tests`. The host suite has failed 100/100 runs since 2026-07-18, so the
matrix reports **`skipped`** every time — not `failed`. A skipped job is not a
red X, so nothing ever drew attention to it.

**2. Six images are never referenced by CI at all.** `ci-tests.yml` builds 15
dockerfiles; `tests/docker/` contains 21. Never built by CI: `acp-e2e`,
`consumer-pipeline`, `harness-user-path`, `provider-config-matrix-e2e`,
**`opencode-recipe-live`**, **`rig-recipe-live`**. The last two were added by
the two most recent feature commits (`f3ca583b4` opencode upgrade recipe live
test infrastructure, `e4ca8433e` rig embedded recipe + e2e test
infrastructure) — the infrastructure was built but never wired into the
workflow, so it has never run once.

**3. Locally they self-skip.** 441 tests carry `mutates_host`, and
`tests/conftest.py` skips them unless `AUDIAGENTIC_DOCKER_TESTS=1`. Running
`pytest tests/integration/providers/test_provider_full_lifecycle.py` on the host
reports `99 skipped — provider lifecycle tests run in Docker`. So an ordinary
local run covers none of this and still exits 0.

**4. The main Docker image deliberately excludes them.**
`tests/docker/run_suite.sh` runs
`-m "not mutates_host and not opt_in and not docker and not requires_docker"`.
That is correct by design — the specialised images own that coverage — but it
means the one image most people would think of as "the Docker tests" runs none
of the Docker-only tests.

The mechanism itself is sound: every specialised image does set
`ENV AUDIAGENTIC_DOCKER_TESTS=1`. This is a wiring failure, not a design
failure.

**Two smaller defects found on the way:**

- The `requires_docker` marker matches **0 tests**, while the legacy `docker`
  alias it was meant to replace matches 8. `pyproject.toml` documents
  `requires_docker` as preferred and `docker` as "kept for backward
  compatibility"; the migration never happened, so every exclusion expression
  has to name both, and one naming only `requires_docker` excludes nothing.
- `test_gateway_crash_matrix_docker.py` and `test_gateway_opencode_docker.py`
  each exist **twice**, under `tests/integration/agents/` and
  `tests/e2e/agents/`. The `mutates_host` markers are on the `e2e` copies; the
  Dockerfile CMDs run the `integration` copies.
