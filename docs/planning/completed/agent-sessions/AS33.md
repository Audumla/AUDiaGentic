# Advertise resolved session diagnostics capabilities to clients

## Description

Add the client-facing capability advertisement that RV689 identified without reopening AS16's RV722 diagnostics closure. Gateway callers should be able to inspect what a request/session can do, sourced only from resolved AS19/AS28 session-surface declarations captured at session open. Until declarations are resolvable, the capabilities section must be absent rather than guessed.

## Steps

1. Read RV689, AS19, AS28, AS29, AS30, and the current AS16 diagnostics projection before editing.
2. Define a redacted `capabilities` projection shape for request/session diagnostics: surface id/version, declared controls, observation mechanism, supported statuses, and evidence tier. Use enum/id values only; never infer from adapter behavior.
3. Capture the resolved declaration once at session open when AS19/AS28 resolution is available. If no resolved surface declaration exists, omit the section entirely.
4. Project the section through `request_runtime_status`, MCP diagnostics, remote client/service status rows as applicable, without changing queue authority or persisting prompt/output/tool/provider refs.
5. Add tests for absent-when-unresolved, immutable captured values, redaction, and client stack visibility.
6. Record a ledger event with this plan item id and only mark complete after focused diagnostics/client tests pass.

## Files

Agents gateway diagnostics/session projection modules, session binding/capability projection storage if needed, public client/MCP/service tests. Avoid provider-adapter behavior inference and do not broaden AS16 queue diagnostics semantics.

## Validation

Focused unit/integration diagnostics tests prove absent-when-unresolved, captured resolved capability projection, client/MCP visibility, and no sensitive fields. Existing AS16 request_runtime_status and session tests remain green.
