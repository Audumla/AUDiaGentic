# Keep secrets provider-owned — rename VAL-SEC/CON-SEC error codes to provider-owned

## Description

At the time of the audit, every production consumer of secret resolution was inside the providers component:
- Provider health checks
- Provider launch environment construction
- Model/source catalog handling
- Local OpenAI configuration
- Provider API status

The only consumers outside providers were tests. Under the architecture standard (foundation capabilities require multiple independent consumers), moving secrets into providers was correct based on current evidence.

Future plausible consumers:
- Release credentials
- Source-control tokens
- Memory service credentials
- Remote MCP authentication
- Telemetry exporters

But anticipated reuse alone is not enough to keep a capability in foundation. Otherwise foundation accumulates speculative abstractions whose eventual consumers may need different semantics.

Clean migration rule:
1. Keep provider credential resolution provider-owned today
2. When a second independent component has a concrete requirement, compare semantics: same reference grammar, resolver lifecycle, redaction guarantees, validation/error ownership, registration model
3. If those match, extract a neutral foundation/secrets/ capability and move both consumers to it in one migration
4. Keep component-specific credential policy outside foundation
5. Do NOT restore the old single foundation/secrets.py merely for possible future use
6. Make current provider implementation extraction-friendly and avoid provider vocabulary in its internal reference model where unnecessary

Error code concern: VAL-SEC-* and CON-SEC-* are generic-looking error codes even though they are now provider-owned.
Either:
- Reserve them explicitly as the future neutral secret contract, OR
- Rename them to provider-owned codes before release

Preference: rename to provider-owned codes unless another real consumer is already planned.
