# Confirmed: deprecated NOT in describe_provider — plan must read from descriptor directly; refresh_mode is present

## Notes

Code-verified review of DE03. Checked the actual providers_api code to confirm what describe_provider serializes and what it does not.

## Findings

1. `refresh_mode` IS serialized: confirmed by _serialize_config_surface (providers_api.py:861-895) — it outputs `{kind, configured, format, refresh_mode, capabilities, resolved_path, path_scope}`. The plan's `_mcp_refresh_mode(pid, root)` reading from `describe_provider` is correct.

2. `deprecated` IS NOT serialized by describe_provider: confirmed by reading providers_api.py:911-990 and list_provider_descriptors (722-777) — neither function includes the `deprecated` field. DE03's code sample correctly uses `get_descriptor(pid)` to read it directly, but the `_is_deprecated` helper is hypothetical and should reference `get_descriptor` explicitly.

3. COLLISION DROPPING CONFIRMED: _combine_summary (provision.py:302-335) only reads `action_needed` when `ok=False`: lines 319-324 show `fam_err` is populated only in the `if not ok:` branch. This means collision_ids that arrive with `ok=True` are silently dropped — exactly as the plan identifies.

4. `deprecated_info` ATTR NAME UNCERTAIN: The plan references `dep.get('replacement_provider')` from a hypothetical `deprecated_info` block. base.py line 253 only has `deprecated: bool = False` — there is NO structured deprecation block with replacement_provider/message in the current schema. The plan assumes such a block exists in the YAML but it doesn't in the current dataclass. DE03 must either add this to the descriptor schema (beyond scope) or work with the boolean + `annotations` dict.
