# Verify describe_provider serializes refresh_mode + deprecated

## Notes

The plan is well-scoped and correctly sequenced after DE01. The main verification gap is whether `describe_provider` serializes `refresh_mode` and `deprecated` — the executor should check providers_api.py's `_serialize_config_surface` and `describe_provider` before starting implementation.

## Findings

1. CORE CLAIM VERIFIED: `describe_provider` does return `config_surfaces` with `kind`, `refresh_mode`, `capabilities` per provider. The code_sample's `_refresh_hint` logic is consistent with the data shape. However, the code_sample uses `s.get('kind') == 'mcp'` to find the mcp surface — this is correct per the existing descriptor structure.

2. COLLISION SIGNALS EXIST BUT ARE PARTIALLY DROPPED: ManagedMcpResult (from providers_api) carries `action_needed` and `error_code`. The current `_map_mcp_status` (provision.py:457-461) does surface `action_needed` on success, but `_combine_summary` (provision.py:302-335) only surfaces `error_code`/`action_needed` when `ok=False`. The plan correctly identifies this gap: collision warnings that arrive with `ok=True` are currently dropped.

3. DEPRECATION FLAG LOCATION UNCLEAR: The plan says 'describe_provider exposes provider state/flags; when the descriptor is marked deprecated'. Looking at the codebase, `deprecated` is a boolean field on ProviderDescriptor (base.py:253). The plan's `_is_deprecated` function is hypothetical — the executor needs to check whether `describe_provider` serializes the `deprecated` field or whether the code needs to read it directly from the descriptor.

4. REFRESH MODE NOT YET SURFACED: The plan's `_refresh_hint` reads `s.get('refresh_mode')` from config_surfaces. This is already present in the YAML (e.g., claude.yaml:145 `refresh_mode: 'file-watch'`). Whether `describe_provider` actually serializes `refresh_mode` into the config_surfaces output needs verification — the plan assumes it does but doesn't prove it.

5. POST-DE01 SEQUENCING IS CORRECT: The plan correctly notes it should land after DE01. The current code path (Python family-loop) would need the reporting added in two places if done before DE01. The recipe path adds it once.

6. SCOPE CREEP RISK: The plan says 'main risk is scope creep into a generic reporting framework'. This is honest. The plan should explicitly bound the output shape — e.g., `entry['action_needed']` as a string, not a nested structure — to prevent the generic-reporting temptation.
