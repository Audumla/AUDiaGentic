# DE01 code-sample defects: _combine_summary arg slot and empty env/args drop

## Notes



## Findings

F1 (blocking, verified against provision.py:302-319): the reconcile before/after sample calls `_combine_summary(result, None, "install", ...)`, passing the RecipeResult in the FAMILY slot. _combine_summary computes fam_ok via getattr(fam_result, 'ok', False) but a RecipeResult exposes .success (not .ok), so this always yields ok=False -> every provider reports FAILED. Fix: pass the RecipeResult in the ARTIFACT slot -> `_combine_summary(None, result, "install", "guidance-only")` (art_ok = result.success). Apply to all three loops (apply/prune/teardown).

F2 (correctness, stdio recipe): the empty-value drop in step 2 was specified only for headers, but the stdio path passes env: {HINDSIGHT_BANK_ID: "{BANK_ID}"} and BANK_ID may be ''. ManagedMcpEntry.from_mapping keeps empty env/args entries; an empty HINDSIGHT_BANK_ID env var is emitted. Extend the empty-drop in _build_managed_mcp to env and args, not just headers (drop any k whose substituted value is '').

F3 (minor, teardown path): the teardown loop builds _resolve_recipe with the placeholder backend (base_url='http://removed.invalid'); _resolve_recipe calls describe_provider (read-only, fine) and backend.mcp_url/headers on the placeholder. Prune ignores url/header values so this is safe, but add an explicit test that teardown prune resolves and runs for a compound provider (pi) and a generic one (claude) with the placeholder backend.

F4 (cleanup completeness): after step 5, _run_artifact_recipe and _recipe_params become unreachable (replaced by _run_recipe/_resolve_recipe). Add them to the DELETE list (the current DE01 delete list keeps _recipe_params 'folded' but the fold means deletion). Grep-confirm no residual callers.

## Conclusion

DE01 approach is sound; two concrete sample defects (F1 blocking, F2 correctness) must be corrected in the item before an implementer copies them, plus F3 test and F4 delete-list completeness. Incorporate and close.
