# Critical: Stale codebase assumptions + recipe param mismatch

## Notes

The core design (one recipe per provider, _resolve_recipe decision point) is sound. The main risk is the param-layer confusion in code samples which could lead an executor astray. Recommend rewriting the code_sample section to show the two layers clearly: (a) what _resolve_recipe returns as recipe-level params, (b) what the recipe YAML template produces after substitution, (c) what the step builder receives.

## Findings

1. OWNERSHIP SCOPE TEXTUAL CLAIM WRONG: detailed_solution states `hindsight_ownership_scope(backend) == 'memory/hindsight/hindsight'` — this is only true when `backend.server_name == 'hindsight'`. The function actually returns `f'memory/hindsight/{backend.server_name}'` (mcp_recipe.py:45). The code samples correctly call the function so implementation is fine, but the textual 'VERIFIED FACTS' section is misleading for an executor reading the spec.

2. `_resolve_recipe` PARAM SHAPE DOESN'T MATCH RECIPE STEPS: The code_sample builds params dict with keys URL, MCP_URL, AUTH, TOKEN, BASE_URL — raw backend values. But the managed-mcp step (`_build_managed_mcp` in recipe_steps.py:126) reads data keys `url`, `headers`, `managed-id`, `provider`, `ownership-scope`, `name`, not raw param keys. The recipe YAML uses `{MCP_URL}` etc. as template placeholders that strict_substitute replaces in the YAML dict before the step builder runs. The code_sample conflates two layers: recipe-level params (YAML template vars) vs step-level data (what `_build_managed_mcp` reads). This will confuse an executor — clarify that params flow through YAML template substitution, not direct step-builder args.

3. DELETION LIST INCOMPLETE: The plan lists `build_hindsight_managed_entry` for deletion but not `build_hindsight_entry` (also imported in provision.py:23). The grep-first instruction covers this, but it's worth noting `build_hindsight_entry` is also imported and should be checked.

4. `_run_artifact_recipe` ROOT PARAM MISSING: Step 1 says 'add root param to _run_artifact_recipe; pass context={"project_root": str(root)} into execute_recipe_mode'. But the current `_run_artifact_recipe` signature (provision.py:89) does NOT take root — it only takes provider_id, backend, mode. The plan correctly identifies this as a needed change, but underplays it: this is a signature change touching 3 call sites (apply, prune teardown, prune stale). The plan should enumerate the call sites explicitly.

5. MANAGED-MCP EMPTY HEADER DROP (step 2) is correctly identified as a prereq. `_build_managed_mcp` (recipe_steps.py:126-143) substitutes headers but never filters empty values. Confirmed gap.

6. OWNERSHIP SCOPE DISCREPANCY: The existing `_apply_mcp`/`_prune_mcp` use `_HINDSIGHT_OWNERSHIP = 'hindsight'` as the ownership scope (provision.py:43), but the plan's recipes use `hindsight_ownership_scope(backend)` which returns `memory/hindsight/{server_name}`. The managed-mcp step takes `ownership-scope` from the recipe YAML. This is a SCOPE CHANGE — the recipes would use a different ownership scope than the current Python functions. The plan should call this out as a deliberate change, not an oversight. If it IS deliberate (the longer scope is more precise), note it; if not, the recipe YAML needs to use the short scope or the Python needs to be updated to match.
