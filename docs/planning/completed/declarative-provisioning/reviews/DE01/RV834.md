# Ownership scope inconsistency is pre-existing — recipe cutover must pick one and document the change

## Notes

Code-verified review of DE01. The main addition beyond RV816 is confirming that the two ownership scopes are not a hypothetical mismatch but an ACTIVE inconsistency in the current codebase, which the recipe cutover will expose.

## Findings

1. TWO OWNERSHIP SCOPES ARE ALREADY IN USE — confirmed by code inspection:
- `_HINDSIGHT_OWNERSHIP = "hindsight"` (line 43) is used by managed-hooks and managed-plugin families: _apply_hooks:181, _prune_hooks:194, _status_hooks:207, _apply_plugin:260, _prune_plugin:273.
- `hindsight_ownership_scope(backend)` returns `f"memory/hindsight/{backend.server_name}"` (mcp_recipe.py:45) and is used by managed-mcp family: _apply_mcp:220, _prune_mcp:233.

This means the current system ALREADY registers MCP entries under `memory/hindsight/{server_name}` but hook/plugin entries under bare `"hindsight"`. This is a pre-existing inconsistency, not something introduced by the plan.

2. RECIPE CUTOVER AMPLIFIES THE PROBLEM: DE01's generic recipes use `{OWNERSHIP_SCOPE}` which resolves to `hindsight_ownership_scope(backend)` for ALL families. After cutover:
- managed-hooks: changes from `"hindsight"` → `"memory/hindsight/{server_name}"` (SCOPE CHANGE)
- managed-plugin: changes from `"hindsight"` → `"memory/hindsight/{server_name}"` (SCOPE CHANGE)
- managed-mcp: no change (already uses `hindsight_ownership_scope`)

This means ownership registry entries for hooks and plugins will be RE-REGISTERED under a new scope. The old entries under `"hindsight"` become orphaned. The plan must either:
(a) Accept the scope change as deliberate, document it, and include a migration step to transfer existing registrations from `"hindsight"` → `memory/hindsight/{server_name}`.
(b) Use `"hindsight"` in the generic recipes for consistency with hooks/plugin families, which means MCP would also change scope (opposite direction).

3. `_combine_summary` CONFIRMED: lines 302-335 verify that `fam_ok` uses `getattr(fam_result, 'ok', False)` and `art_ok` uses `art_result.success`. A RecipeResult exposes `.success`, so it MUST go in the 2nd (artifact) slot — the plan's code_sample is correct on this. No issue here.

4. `_run_artifact_recipe` SIGNATURE CONFIRMED: lines 89-102 confirm the function takes `(provider_id, backend, mode)` — NO `root` parameter. The 3 call sites are:
- reconcile apply loop (line 393): `_run_artifact_recipe(pid, backend, "apply")`
- reconcile prune-stale loop (line 400): `_run_artifact_recipe(pid, backend, "prune")`
- reconcile teardown loop (line 387): `_run_artifact_recipe(pid, placeholder, "prune")`
Step 1 must add `root` to all three. The plan correctly identifies this but doesn't enumerate call sites — confirmed gap.

5. DELETE LIST: `build_hindsight_entry` is imported at line 23 (confirmed by grep) and used in `_apply_mcp` via `build_hindsight_managed_entry(backend)` which calls `build_hindsight_entry`. The deletion list should explicitly name it.
