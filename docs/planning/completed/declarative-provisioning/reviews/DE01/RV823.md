# Cross-plan dependency analysis: DE and PC workstreams are independent

## Notes

The two workstreams (DE = Hindsight provisioning cutover, PC = provider capability model restructure) are independent and can proceed in parallel. The main coordination point is that DE01's _resolve_family uses _provider_capability_map which reads automation_capabilities from descriptors — if PC03 changes the shape of automation_capabilities, DE01's _provider_capability_map must be updated. But since DE01 replaces the Python family dispatch with recipes, and the recipe step types read the provider's managed-mcp/hooks/plugin directly (not through automation_capabilities), this coordination is only needed for the family resolution step, not the recipe execution.

## Findings

1. PC01 -> PC02 -> PC03 -> PC04 SEQUENCING IS CORRECT but PC01 has blocking design issues (RV819) that must be resolved first.

2. DE01/DE02/DE03 ARE INDEPENDENT of PC01-04: The DE items consume the existing capability model (through _resolve_family / _provider_capability_map). The PC items restructure the capability model but don't change the family resolution logic. DE items can proceed in parallel with PC items.

3. PC01 DEPENDS ON NOTHING — it's the foundation. But PC01 as designed has the FamilyPin coverage gap. Recommend splitting PC01 into: (a) catalogue authorship + full off-taxonomy audit, (b) enforcement validators.

4. PC02 DEPENDS ON PC01 (catalogue must exist for mechanism parsing).

5. PC03 DEPENDS ON PC02 (dual-read loader must work).

6. PC04 DEPENDS ON PC03 (all providers must be migrated).

7. DE01 DEPENDS ON DE02 (delete-path step needed for codex uninstall conformance).

8. DE03 DEPENDS ON DE01 (lifecycle reporting added once on the recipe path).

9. RECOMMENDED ORDER: DE02 (independent, small) -> DE01 (cutover) -> DE03 (lifecycle reporting). PC01a (catalogue + audit) can run in parallel with DE work. PC01b -> PC02 -> PC03 -> PC04 is a sequential chain.
