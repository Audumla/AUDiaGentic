# Separate Pi native-user and isolated-job configuration completely

## Description

Native Pi launches should discover the durable harness-projected MCP surface.
AUDiaGentic internal jobs should pass a request-specific MCP config and exact isolation flag.

Native durable config must not be reused as job scratch space.
Job config must not be written to ~/.pi, shared .audiagentic/mcp.json, or another global default.

## Steps

['Separate native Pi durable config discovery from isolated job config', 'Ensure internal jobs pass request-specific MCP config and isolation flag', 'Verify native config not reused as job scratch space', 'Verify job config never written to ~/.pi or shared .audiagentic/mcp.json']

## Detailed Solution & Technical Design

### Two distinct modes — two config paths

#### Native Pi launches (user-facing, durable)

- Discover the **durable harness-projected MCP surface** from `~/.pi/` or equivalent default location
- This is the user's persistent configuration — it survives across sessions
- Native launches read this config; they do NOT write request-specific config here

#### AUDiaGentic internal jobs (isolated, ephemeral)

- Receive a **request-specific MCP config** and exact isolation flag from the gateway
- Config lives in an ephemeral runtime root unique to this request
- Config is deleted on job completion (success or failure/quarantine)
- **Never written to** `~/.pi`, `.audiagentic/mcp.json`, or any global default

### Anti-patterns to prevent

1. **Job scratch space in native config**: an internal job writes its MCP config to `~/.pi/mcp.json` and a subsequent native launch picks it up → user sees wrong servers.
2. **Native config as job starting point**: a job reads the native `~/.pi/mcp.json`, mutates it, and uses that as its config → changes leak back to native launches.
3. **Shared .audiagentic/mcp.json as job scratch**: writing job config to a shared file means concurrent jobs overwrite each other.

### Test approach

```
1. Native launch test:
   - Set up durable MCP config in ~/.pi/
   - Launch native Pi session
   - Verify it discovers the durable config
   - Verify ~/.pi/ is read-only from the job's perspective

2. Isolated job test:
   - Launch internal job with request-specific MCP config
   - Verify config lives in ephemeral runtime root (NOT ~/.pi)
   - Verify job uses its own config, not native config
   - After job completes, verify ephemeral files are cleaned up
   - Verify ~/.pi/ is byte-for-byte unchanged

3. Concurrent isolation test:
   - Launch two internal jobs simultaneously
   - Verify they use different ephemeral roots
   - Verify no cross-contamination of MCP configs
```
