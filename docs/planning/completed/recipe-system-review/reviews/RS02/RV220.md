# Registry dispatch inconsistency and unsafe attribute access in fallback

## Notes

Validated registry dispatch inconsistency and unsafe fallback field access. Incorporated into RS02, RS09, and RS10.

## Findings

RS02 correctly identifies the duplication:
1. `ProviderRecipeRegistry.install()` fallback path (lines 318-340) — manual ProviderRecipeResult construction
2. `_RowRecipe._stamp()` (hindsight/recipes.py:119) — duplicates ProviderCapabilityRecipe.to_result() conversion

**Gap: Registry dispatch inconsistency**

`ProviderRecipeRegistry.status()` calls `_stamped(recipe, recipe.probe(ctx))`, and `dry_run()` does the same. But `install()` and `uninstall()` use direct attribute access (`recipe.to_result(result) if hasattr(recipe, 'to_result')`) at lines 308, 356. This means:
- status/dry_run/repair use `_stamped()` helper
- install/uninstall bypass it entirely

The consolidation should normalize ALL registry dispatch through a single stamping boundary (likely `_stamped`), making the fallback path at lines 318-340 unreachable or testable.

**Gap: `ProviderRecipeResult` attribute access in registry fallback**

Lines 318-327 assume `result.source_url`, `result.source_date` exist on any result object. For plain `RecipeResult` these attributes don't exist, which would raise AttributeError. The current code only reaches this path for recipes without `.provision()`, but the safety net should use `getattr(result, 'source_url', '')` like `to_result()` does at line 205.

**Recommendation**: Add to RS02 description: "Normalize registry install/uninstall dispatch through `_stamped()` and fix unsafe attribute access in fallback path (use getattr)".
