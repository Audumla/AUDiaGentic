# Path resolution scope and substitute_params safety concern

## Notes

Validated path anchoring and lenient placeholder behavior. Incorporated into RS04, RS13, and RS14.

## Findings

RS04 correctly identifies the three substitution mechanisms:
1. `_substitute()` (base.py:79) — strict, raises on unknown
2. `substitute_params()` (factory.py:67) — lenient, drops unknown
3. `ShellProvisionStep._render()` (shell.py:181-184) — runtime str.format(**context)

**Gap: Path anchoring inconsistency beyond what's described**

The plan mentions 'inconsistent path anchoring' but doesn't quantify:
- shell.py uses `os.path.expanduser(self.cwd)` for working directory only; the command paths are resolved by PATH lookup (`shutil.which`)
- config_set.py uses `Path(self.path).expanduser()` — no project_root anchoring
- write_file.py same pattern — `Path(self.path).expanduser()`
- managed_block_step.py same pattern
- _absolute_project_path() in hindsight/recipes.py:72 IS project-root aware but is ONLY used by Hindsight, not by the foundation steps

Foundation steps have no access to `project_root` because they're domain-neutral. This is correct per Std §1, but it means all path resolution happens at construction time (in strategies.py where recipes build step definitions). RS04 should clarify: 'foundation steps receive pre-resolved paths; inconsistency risk is in recipe authors constructing YAML with relative paths.'

**Gap: `substitute_params` lenient behavior is a safety concern**

factory.py:75-78 replaces known placeholders silently but leaves unknown ones as literal `{KEY}`. This means an unset optional param (e.g., TOKEN) renders as `{TOKEN}` in the command string, which will fail at shell execution with a cryptic error rather than at validation time. The DeclaredStepRecipe probe() method uses this path (line 124 of recipe_patterns.py).

**Recommendation**: Add to RS04: "Document that substitute_params' lenient behavior produces literal placeholder strings for unset params, causing runtime failures in command execution. Consider whether strict validation is safer for status probes."
