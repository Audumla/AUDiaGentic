# Boundary with RS06 undefined; risk of obscuring direct mutations during consolidation

## Notes

Validated direct file I/O sites and `resolve_ref` seam. Incorporated into RS03 and RS12.

## Findings

RS03 targets consolidation of repeated Hindsight recipe mechanics. The duplication is real:
- `_should_run_plugin_command()` appears at PluginConfigRecipe:87 and _PluginUrlConfigRecipe:361
- Source-gated step execution (install_steps + audia_action check) is repeated in both PluginConfigRecipe.install() and _PluginUrlConfigRecipe.install()
- provision_steps() assembly with `_hindsight_params` + `steps_from_defs` is nearly identical across all plugin recipes

**Gap: Overlap boundary with RS06 not defined**

RS03 says 'consolidate repeated mechanics'; RS06 says 'route common file/config ownership through shared primitives'. But the three direct mutations are INSIDE the same recipe classes that RS03 touches:
- `_repair_windows_plugin_mcp()` (plugin_recipes.py:201-282) — called by _PluginUrlConfigRecipe.configure()
- `self._url_config_path.write_text()` (line 406)
- `self._url_config_path.unlink()` (line 441)

If RS03 refactors these classes into shared helpers, the direct mutations may become obscured. Need explicit boundary: RS03 should NOT extract code that contains file I/O into new helpers — those operations stay inline for RS06's classification.

**Gap: `resolve_ref` seam in _PluginArrayRecipe**

_lines 471-474_ use `resolve_ref` to dynamically load reader/writer/remover callables. This is already a good pattern (config-driven dispatch), but RS03 doesn't mention it as an example of what NOT to consolidate — it's component-specific integration that should remain as-is.

**Recommendation**: Add notes to RS03: "Do not extract file I/O paths into shared helpers (defer to RS06). _PluginArrayRecipe resolve_ref pattern is already config-driven and should not be consolidated."
