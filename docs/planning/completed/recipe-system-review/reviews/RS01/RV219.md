# Dual stamping path (_stamped helper) not covered in contract audit

## Notes

Validated `_stamped()` / `to_result()` dual path. Incorporated into RS01, RS09, and RS10.

## Findings

RS01 covers the ProvisioningRecipe base contract correctly. However:

**Missing impact: `_stamped()` helper at providers/services/recipes.py:211-219**

This function provides a second result-stamping path that operates at registry dispatch time (used by `status()`, `dry_run()`, `repair()`), separate from `to_result()` which runs inside the orchestration. RS01's validation checklist doesn't cover this dual-path stamping model:

- `ProvisioningRecipe.to_result()` — called inside provision()/teardown()
- `_stamped(recipe, result)` — called at registry boundary for probe/dry_run/prune/repair

The two paths serve different purposes (orchestration vs dispatch) but both produce ProviderRecipeResult. Tests should verify that a recipe's `to_result` is the canonical stamp point and `_stamped` doesn't double-stamp when the recipe already implements `to_result()`.

**Recommendation**: Add to RS01 validation: "Tests prove `_stamped()` does not double-apply provenance on recipes that implement `to_result()`".
