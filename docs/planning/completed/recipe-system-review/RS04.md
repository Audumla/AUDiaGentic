# Normalize provisioning step substitution, paths, and artifact ownership

## Description

Normalize provisioning-step substitution, path resolution, and artifact ownership rules. The current step package is reusable and registry-driven, but recipe authors must understand several different mechanics: strict definition-time `_substitute()`, lenient `substitute_params()`, shell runtime `str.format(**context)`, and inconsistent path anchoring.

## Steps

This is the parent/analysis item; execution happens in RS13 (characterize) then RS14 (normalize). Do not implement fixes directly under this ID.

1. Confirmed three distinct substitution mechanisms (RV228/RV229 audit):
   a. `provision_steps/base.py::_substitute()` — strict, regex-validated (`{WORD}` pattern), raises `VAL-PSTEP-002` on unknown placeholder. Used at YAML-parse time by every `_*_from_dict` factory (`shell.py::_shell_from_dict`, `config_set.py::_config_set_from_dict`, `managed_block_step.py::_managed_block_from_dict`, `write_file.py::_write_file_from_dict`) AND again at run-time inside `ConfigSetStep.run()`/`ManagedBlockStep.run()`/`WriteFileStep.run()` against the live `context` dict.
   b. `provision_steps/factory.py::substitute_params()` — lenient, leaves unknown/unset placeholders literal via plain `str.replace`. Used by `hindsight/recipes.py::_parameterize_command` and `foundation/toolchains/recipe_patterns.py::DeclaredStepRecipe.probe()` for building free-form status-probe command strings.
   c. `provision_steps/shell.py::ShellProvisionStep._render()` — a THIRD mechanism: plain Python `str.format(**context)`, applied at `run()`/`revert()`/`dry_run()` time to the already-YAML-substituted command. This means a shell step's command can carry two substitution passes: `_substitute()` at parse time (for `{PARAM}` YAML placeholders) then `.format(**context)` at run time (for `{context_key}` runtime values) — confirm this is intentional (params are known at recipe-build time; context keys are only known at run time) and not an accidental double-substitution bug.
2. Confirmed path handling difference: foundation provision steps (`write_file.py`, `managed_block_step.py`, `shell.py`) only call `Path(...).expanduser()`/`os.path.expanduser(...)` — no project-root anchoring, by design (Std §1: foundation is domain-neutral, has no concept of "project root"). Hindsight's `recipes.py::_absolute_project_path()` anchors relative paths to a caller-supplied `project_root`. This is not a bug to fix by merging — it is a legitimate layering split (foundation stays root-agnostic; the capability owns root anchoring) that RS13/RS14 must document, not collapse.
3. RS13 must characterize both findings above with tests before RS14 touches anything. RS14 must re-check the “used by ≥2 step types” precondition before extracting any shared render helper — as of this audit, `str.format(**context)` runtime substitution exists ONLY in `shell.py`; if RS13 confirms no second consumer, RS14 must document the mechanism instead of extracting a premature shared helper (Std §3 requires 2+ consumers before extraction).
