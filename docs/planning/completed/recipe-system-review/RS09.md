# Characterize provider recipe result stamping

## Description

Small execution slice for RS02. Add tests that capture current provider recipe stamping behavior before simplifying `ProviderRecipeRegistry` and Hindsight `_RowRecipe`.

Dependency: none (characterize phase — must complete before RS10).

## Steps

1. Create `tests/unit/providers/test_provider_recipes.py` (does not exist yet — confirmed in this audit). Import `ProviderRecipeRegistry`, `ProviderRecipeResult`, `ProviderRecipeKind`, `RecipeState` from `audiagentic.components.providers.services.recipes`.
2. Build a minimal fake recipe class in the test file (do not import Hindsight — this test must stay provider-layer-only per Std §1) with `provider_id`, `capability_id`, `backend_id = None`, and `probe`/`install`/`configure`/`verify`/`prune`/`uninstall` methods returning `ProviderRecipeResult.ok(...)`/`.fail(...)` directly (no `to_result` override, no `provision`/`teardown` override) — this exercises the primitive-call fallback path in `ProviderRecipeRegistry.install()`/`.uninstall()`, which is the path RS02 found duplicated.
3. Write `test_install_stamps_provenance_exactly_once`: register the fake recipe, call `registry.install(...)`, and assert the returned result's `source_url`/`source_date` equal what `install()`/`configure()` primitives already set — with a spy/counter on a `to_result` method (add one to the fake recipe that increments a counter and returns `self` unchanged) confirm it is called at most once per `install()` call, or not called at all if the recipe has no `to_result` override beyond the base identity. State explicitly in the test docstring which case you're covering.
4. Write `test_install_action_needed_fallback_order`: three fake recipes whose `install`/`configure`/`verify` return `action_needed=""` except one whose primitive sets `action_needed="do X"` — assert `install()`'s final result carries the non-empty guidance, never `None` (assert `result.action_needed is not None`).
5. Write `test_install_preserves_artifacts_owned_across_install_and_configure`: fake recipe's `install()` returns `artifacts_owned=["a"]`, `configure()` returns `artifacts_owned=["b"]`, `verify()` returns `artifacts_owned=[]` — assert final result's `artifacts_owned == ["a", "b"]` (this locks the exact behavior RS10's `replace()` refactor must preserve).
6. Write `test_install_custom_subclass_result_not_stripped`: fake recipe whose `probe()` returns a `ProviderRecipeResult` with a custom extra value stored in `details={"custom": "value"}` — assert `install()`'s final result `.details` still contains `{"custom": "value"}` after passing through the fallback reconstruction (this is the regression guard for RS10).
7. For Hindsight-side stamping, add to `tests/unit/memory/test_hindsight_recipe.py` (existing file) one test `test_row_recipe_stamp_matches_provider_recipe_result_shape` asserting `_RowRecipe._stamp(RecipeResult.ok(RecipeState.VERIFIED))` returns a `ProviderRecipeResult` instance with `source_url`/`source_date` populated from the row (this is item 2(c) in the original validation list) — only add this if no equivalent assertion already exists in that file; check first.
8. Run `python -m pytest tests/unit/providers/test_provider_recipes.py tests/unit/memory/test_hindsight_recipe.py -v` and confirm everything passes against the CURRENT (pre-RS10) code — these are characterization tests, they must be green before RS10 touches anything.
