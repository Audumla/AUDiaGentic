# Re-scope A7: delegate hindsight rules to the provider surface-contribution propagation instead of a single-block writer

## Notes



## Findings

Investigation 2026-07-08 (user direction 'can hindsight delegate to providers management using the proper propagation mechanisms?'). The provider surface system ALREADY propagates component-declared content into provider instruction files: load_surface_contributions (surfaces/contributions.py:163) aggregates each component's YAML `contributions:` (gated on installed+enabled) → provider renderers produce SurfaceBlocks → apply_provider_surfaces writes them into ONE managed region per file. Eight components already use this (agent-jobs, agent-ledger, agents, memory, planning, release, session, source-control), and memory.yaml ALREADY declares a `memory/process` contribution targeting `instruction`.

This SUPERSEDES the current A7 (add apply_surface_block/remove_surface_block helpers + have RulesOnlyRecipe call them). The better fix: express hindsight's memory-usage guidance (RULE_TEXT) as a memory-component surface contribution — fold it into the existing memory/process contribution or add a sibling memory-usage contribution — and DELETE RulesOnlyRecipe's direct apply_managed_block writing entirely. The block then propagates through the same pipeline as every other contribution: unified ownership (the contribution registry, not a separate ArtifactRegistry write), one managed region (eliminates the dual-writer outright rather than making two coexist), and enabled-awareness for free.

BOUNDARY: this is MORE compliant, not less. The architecture tests forbid memory importing provider surface code (apply_provider_surfaces/providers.services/surfaces.contributions). A declarative YAML `contributions:` entry imports nothing — it is the sanctioned seam. Today's RulesOnlyRecipe reaches into foundation.managed_block and writes directly, which is the dirtier path.

TWO DESIGN DECISIONS (validate-first): (1) CONTENT SCOPE — make the guidance backend-agnostic ('use the memory system when prior context helps'; recommended, it is not hindsight-specific and memory/process already exists) vs hindsight-specific. Contributions gate at COMPONENT level, not implementation level, so hindsight-specific text would need an implementation-scoped gate/feature-binding the contribution system may not natively support — avoid by making it memory-generic. (2) PLACEMENT — contributions render for ALL active surface providers, whereas today the rules block is a per-provider FALLBACK (resolve_hindsight_strategy places it only where MCP/installer is not viable). Decide uniform (recommended — the guidance is universal) vs gated.

KNOCK-ON: with rules as a contribution, there is NO rules recipe writer to keep — RulesOnlyRecipe is deleted (or reduced to nothing). That also simplifies A8 (_CompositeRecipe loses its rules half → becomes MCP-only) and removes the managed_rule_block pattern from any future SL15 config assembler (there is nothing to migrate). Coordinates with [[SL16]] (do not build a managed_rule_block pattern at all) and the RV167 A7 severity note (this is preventive hygiene done as a reduction).

## Conclusion

Replace A7's 'apply_surface_block helper + RulesOnly rewrite' with 'declare a memory surface contribution + delete RulesOnlyRecipe's direct writing', gated on the two design decisions. Net: a reduction (delete the writer) via the existing propagation mechanism, eliminating the dual-writer and respecting the memory↔providers boundary through config. Update A7 (and note the A8 simplification + SL16 managed_rule_block removal).
