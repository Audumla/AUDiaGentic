# Constrain RecipeSpec to avoid single-consumer framework drift

## Notes



## Findings

1. The justification overcounts consumers. “8 kinds” are variants inside one production capability family (hindsight), not independent consumers. After SL14, the plan itself says recipes are effectively hindsight-scoped. A provider-level `SpecDrivenCapabilityRecipe` in `providers/services` risks recreating the speculative-abstraction problem SL13/SL14 are trying to undo. Fix: implement the first RecipeSpec assembler as hindsight-local unless/until a second real capability adopts it; move to providers only with that second consumer.

2. “NO branching logic in the assembler” is too absolute and likely impossible. A registry lookup still dispatches by pattern, and each pattern handler must validate required params and lifecycle behavior. The standard prohibits if/elif chains on entity names, not all control flow. Fix: require pattern dispatch through a registry (`pattern -> builder`) and allow small generic validation branches inside handlers; prohibit provider/capability-specific branches in the assembler.

3. Validation item 2 creates a fake second consumer. A test-only synthetic capability proving “zero new Python classes” can justify new infrastructure without real product pressure, repeating the dead LSP recipe experiment. Fix: make the synthetic test prove only loader/assembler mechanics; do not cite it as consumer justification. Promotion to shared providers layer must require a real second capability.

4. The plan depends on unsettled SL13 outcomes but names concrete targets too early. SL13 may delete or keep `_CompositeRecipe`, may keep plugin classes as bespoke, and will change MCP/rules helper APIs. SL15 should say “re-read post-SL13 code and regenerate the classification table from the landed diff” before defining `RecipeSpec`. Do not design around planned class names.

5. Schema/error handling is missing. A config-driven authoring path needs strict validation for unknown pattern names, missing required param bindings, bad hook dotpaths, hook signature mismatch, source-gate fields, and unsafe file paths. Fix: add a schema-validation step in `matrix.py` or `recipe_spec.py` with canonical `AudiaGenticError` codes and tests for invalid specs.

6. Strategy selection is not only recipe_kind dispatch. Current `strategies.py` also performs platform fallback, source gating, remote-MCP capability fallback, config path resolution, rule-path fallback, and plugin subvariant selection by field presence. SL15 only moves field-presence selection to config. Fix: explicitly list which strategy decisions remain code vs move to spec, and require tests preserving fallback behavior for unsupported platform, blocked source, no MCP config, stdio-only provider with remote backend, and no rule path.

7. “Extend the hindsight matrix schema rather than inventing a new file type” may make rows overloaded and hard to validate. Integration facts and recipe assembly instructions have different lifecycle and validation rules. Fix: allow either a nested `recipe_spec:` block per row or a sibling config file keyed by provider/kind; pick based on clarity after validate-first classification, not up front.

8. Line-reduction gate (`>=300 lines net`) is brittle for a complex migration. It can push implementers to delete useful local code or hide necessary validation. Fix: treat line reduction as expected outcome, not acceptance gate; gate on behavior goldens, absence of provider-specific branches in assembler, and documented reasons for classes that remain.

## Conclusion

SL15 is a plausible follow-up, but only if scoped as hindsight-local first and driven by the landed post-SL13 shape. Current wording risks a new shared framework for one real consumer. Tighten consumer criteria, schema validation, and strategy-decision boundaries before implementation.
