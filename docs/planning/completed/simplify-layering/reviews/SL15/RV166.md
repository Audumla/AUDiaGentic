# Fix hindsight-local scope leaks and RecipeSpec edge contracts

## Notes



## Findings

1. Files list contradicts the new hindsight-local scope. Description/steps correctly say the assembler must live under `components/memory/hindsight`, but Files still lists `src/audiagentic/components/providers/services/recipes.py (SpecDrivenCapabilityRecipe + pattern registry) OR a new providers/services/recipe_spec.py`. That reopens the shared-framework risk RV164 closed. Fix: remove provider/services files from scope; list a hindsight-local module such as `components/memory/hindsight/recipe_spec.py` or equivalent only.

2. Schema validation says “unsafe/absolute file paths” but Hindsight legitimately uses global/tilde paths such as `~/.hindsight/claude-code.json` and provider global config paths. A blanket absolute-path rejection would break real integrations. Fix: define path policy by field/scope: project-local paths must stay under project_root after resolution; global-scope fields may allow `~`/absolute paths; hook dotpaths are not file paths. Test both accepted and rejected cases.

3. Lifecycle parity for migrated classes is under-specified. Goldens cover many status/state/provenance values, but the current classes also expose `dry_run()`, `provision_steps()`, `provision()`/`teardown()` behavior through the registry, source-gated install/uninstall behavior, and artifact aggregation. Fix: add validation that every migrated kind preserves primitive methods used by registry/status/dry-run tooling, not only probe/install/configure/verify goldens.

4. Strategy/spec boundary still needs a concrete artifact. Step 5 says field-presence subvariant selection may become explicit spec selection, but does not require recording the resulting mapping. Fix: require the validate-first classification table to include the final selected `RecipeSpec` per provider/kind and a “stays in strategies.py” column for each non-config decision.

5. Docs scope may overstate default authoring path. `USING_RECIPES.md` is a general standard; saying RecipeSpec is the default for new capabilities would imply shared support even though SL15 is deliberately hindsight-local. Fix: phrase it as “for Hindsight-style matrix-driven integrations in memory/hindsight”; defer global default language to the future second-consumer promotion item.

## Conclusion

SL15 is much safer after RV164, but not ready until provider-layer file scope is removed and RecipeSpec path/lifecycle contracts are tightened.
