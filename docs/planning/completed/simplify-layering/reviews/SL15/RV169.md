# Implementation review: assembler adds ~900 lines without deleting classes (net increase), re-implements logic inline, and crashes on provision() — rework/revert

## Notes



## Findings

Reviewed the landed SL15 implementation 2026-07-08 (recipe_spec.py + recipe_assembler.py, wired into strategies.py:144,250). recipe_spec.py itself is good (hindsight-local, schema validation, scope-based path policy per RV166). But the assembler is a NET NEGATIVE and must not ship as-is:

1. NET CODE INCREASE, NOT REDUCTION (defeats the item's purpose). ~900 lines ADDED (recipe_spec ~207 + recipe_assembler ~706); ZERO removed. SL15 step 4 REQUIRED deleting the migrated classes — but HooksInstallerRecipe, GuidanceOnlyRecipe, RulesOnlyRecipe, _McpConfigAdapter (recipes.py) and _PluginArrayRecipe (plugin_recipes.py) ALL STILL EXIST. The config layer now sits ON TOP of the class layer: pure duplication, the opposite of 'reduce via config'.

2. ASSEMBLER RE-IMPLEMENTS LOGIC INLINE instead of delegating. _SpecDrivenRecipe copy-pastes the full bodies of RulesOnly/Mcp/PluginArray into ~460 lines of _rule_*/_mcp_*/_plugin_* methods — a SECOND copy of logic that already exists in the classes. The assembler was supposed to bind foundation patterns + provider machinery, not re-derive them.

3. LATENT PRODUCTION CRASH (VERIFIED by running it): _SpecDrivenRecipe.provision() raises NotImplementedError for declared_step / managed_mcp_entry / managed_rule_block / plugin_array (only no_automation works). Reached via ProviderRecipeRegistry.install() → recipe.provision(). apply_hindsight() would CRASH for any provider whose strategy assembles to those patterns (i.e. most). The full unit suite passes ONLY because the stamping goldens test the OLD classes directly and the integration/e2e apply_hindsight paths are Docker/live-gated — a coverage gap masking the crash. Root cause: provision() must delegate to super() (base orchestration probe→install→configure→verify, all implemented via dispatch) for non-no_automation; instead it raises.

4. BAKED IN PRE-A7 RULES BEHAVIOUR: _rule_configure uses apply_managed_block (recipe_assembler.py:351) — the standalone dual-writer path A7 is meant to replace. A7 must now be fixed in TWO places (RulesOnlyRecipe AND the assembler). SL15 was explicitly gated on SL13 (incl. A7) landing first (RV164-4); it proceeded before A7.

5. MCP config_path BUG: _build_managed_mcp_entry sets config_path=None ('resolved from descriptor at runtime') but it is NEVER resolved; _mcp_probe artifacts use f'{project_root}::{server_name}' and _mcp_provision_steps uses path=str(project_root) — the ConfigSetStep path and artifact IDs are wrong (project_root, not the mcp config file).

6. MINOR: the per-method dispatch dicts are rebuilt on every call (8 methods); _build_hindsight_params duplicates recipes._hindsight_params; recipe_spec docstrings cite stale error codes (RES-RSP-002/004/005) that don't match the raised VAL-RSPEC-002/004 and CON-RSPEC-005.

SL14 (verified separately): correct — recipe_steps.py/lsp_recipe.py/lsp_recipes.py + tests deleted, StepRecipe dropped from exports, suite green. SL13: A1-A6 correct; A7/A8 still outstanding.

## Conclusion

REVERT or substantially rework the SL15 assembler before it can ship. Required: (a) fix provision() to delegate to super() base orchestration for non-no_automation (the crash); (b) DELETE the migrated recipe classes so this is a reduction, not duplication; (c) make the assembler DELEGATE to foundation patterns + provider machinery, not re-implement inline; (d) do NOT migrate the managed_rule_block pattern until A7 lands (it currently bakes in the pre-A7 writer); (e) fix the MCP config_path resolution; (f) add a test that provisions an assembled recipe THROUGH the registry — that single test would have caught the crash. Process note: SL15 was gated behind SL13 (A7/A8) and goldens/lifecycle-parity gates (RV164/RV166); the schema/path-policy guards were honoured but the delete-the-classes / delegate-not-reimplement / registry-provision-tested gates were not.
