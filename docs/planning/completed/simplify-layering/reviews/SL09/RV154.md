# Validate-first verdict: merge hypothesis disproved — the two step systems differ semantically, not redundantly; close as won't-do

## Notes



## Findings

Side-by-side inventory (workflow/invocation/steps.py vs toolchains/provision_steps/shell.py+sequence.py) performed 2026-07-07:
1. Actual duplication is ~60 lines of subprocess boilerplate (env setup, shutil.which resolution, timeout/exception handling) between ShellStep.run and ShellProvisionStep._run_argv.
2. Everything else differs semantically: ShellStep supports streaming progress callbacks (reader thread), PATHEXT-resolved Popen, dry_run flag, PlatformOverrides, and the run(context, answers) protocol with WorkflowQuestion suspension; ShellProvisionStep supports shell-mode string commands, declared revert_command, empty---flag= dropping, and the run/revert/dry_run protocol. Run signatures and result vocabularies are incompatible (waiting_for_input/questions vs planned/ok/failed with compensation).
3. Sequences are different machines: SequenceStep threads step_results/step_status through context and can suspend for input; CompensatingSequence unwinds compensation callables on failure. A unified sequence must express both — parameter/concept explosion.
4. A merged system therefore requires a unified run signature threading answers into steps that ignore them, a ProvisioningContext, a dual-mode sequence policy, and migration aliases — strictly MORE concepts than the two purpose-built layers, to remove ~60 stable lines.
5. The item's own escape hatch applies: 'If validate-first disproves the workflow-as-core hypothesis, stop and record findings — do not force the merge.'

## Conclusion

Hypothesis disproved; do not merge. Resolution: mark the separation intentional via docstring cross-references in both modules, record this review, and complete SL09 as resolved-won't-merge. The residual 60-line subprocess overlap is accepted — extracting it would trade honest duplication for parameterized indirection.
