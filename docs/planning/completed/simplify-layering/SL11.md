# Boundary provenance stamping + action_needed field promotion to foundation RecipeResult

## Description

User direction 2026-07-07 (scoped by RV157): recipe machinery must be reusable by ANYTHING that installs code (toolchains, component dependencies, future capabilities) — not trapped in the provider/capability layer. ProvisioningRecipe + provision_steps in foundation are already the generic install-lifecycle extension; ProviderCapabilityRecipe adds only thin provider bookkeeping (~150 lines). Boundary provenance stamping and action_needed field promotion to foundation RecipeResult are prerequisites for extracting reusable install patterns.

Current state: ProviderRecipeResult carries action_needed (~30+ construction sites in hindsight, 1 in LSP recipes); foundation RecipeResult does not — this coupling forces foundation-eligible patterns to return the provider type. No serialization consumers of RecipeResult found; dataclass is non-frozen and replace()-safe.

Two structural causes resolved by this item:
1. PER-METHOD PROVENANCE STAMPING: every primitive hand-builds a fully-populated ProviderRecipeResult because ProviderRecipeRegistry.status() calls probe() directly, bypassing the to_result hook. Route ALL registry dispatch through recipe.to_result once at the boundary.
2. action_needed FIELD COUPLING: promotion to foundation RecipeResult makes types structurally aligned so patterns can return plain RecipeResult and _stamp becomes straight attribute copy.

Target: hindsight primitives return RecipeResult.ok/fail; boundary stamping is one site (_RowRecipe.to_result/_stamp); getattr defensive reads become direct access. Pattern extraction follows as SL12.
