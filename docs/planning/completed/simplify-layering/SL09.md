# Unify the two declarative step systems (workflow invocation steps vs toolchains provision steps)

## Description

Foundation carries two parallel declarative step systems that overlap on their core ('run a command list, per-platform, in sequence'):
1. foundation/workflow/invocation/steps.py — ShellStep, SequenceStep (fail_fast), CallableStep, SelectStep, ConfirmStep, ConditionalStep, PlatformOverrides; built from YAML by workflow/invocation/from_spec.build_step_from_spec; executed by WorkflowInvocationRunner. Consumers: provider cli_install (explicit step form), toolchains/loader.build_step (toolchain install/uninstall commands emit ShellStep/SequenceStep).
2. foundation/toolchains/provision_steps/ — ProvisionStep protocol with ShellProvisionStep, WriteFileStep, ConfigSetStep, ManagedBlockStep; CompensatingSequence (rollback/compensation), ArtifactRegistry integration, {KEY} param substitution, provision_step_from_dict factory with pluggable step-kind registry. Consumers: ProvisioningRecipe.provision (recipe_contract.py TO12 path), hindsight recipes, toolchain provisioning.
The duplication is real but partial: both have shell execution, sequencing, platform handling, and a from-dict/from-spec factory; only provision steps have compensation + artifact ownership; only workflow steps have interactive (confirm/select) and conditional composition. Nobody can express 'installer step with rollback' in a workflow pipeline or 'confirm before provisioning' in a recipe without crossing systems.
Goal: ONE step model — workflow steps as the core vocabulary, provisioning concerns (compensation, artifact ownership, param substitution) as an extension layer — without losing either side's capability, and one factory. Reduces two parallel taxonomies to one and removes the shell/sequence/platform triple-implementation.

## Steps

**Validate-first:** inventory both systems' semantics side-by-side (execution context shape, result shape, error propagation, dry-run behavior, platform key handling) and enumerate every consumer with tests: workflow runner suite, provider cli_install goldens, toolchains provisioning tests, hindsight lifecycle tests. Decide direction of merge from evidence — the working hypothesis (workflow core + provisioning extension) must be confirmed by checking that CompensatingSequence semantics (compensate() on prior steps upon failure) can wrap arbitrary WorkflowSteps without changing recipe behavior.

1. Extract a shared step core: single ShellStep implementation (command, platform overrides, timeout, env, cwd, dry_run) and single sequence semantics with a fail_fast/compensate policy knob. Location: foundation/workflow/invocation/steps.py stays canonical; provision_steps imports the core rather than redefining ShellProvisionStep's shell logic.
2. Recast provisioning-only steps (WriteFileStep, ConfigSetStep, ManagedBlockStep) as WorkflowStep implementations that additionally record artifacts/compensation via a ProvisioningContext (registry, recipe_id, params) carried in the step context dict — not via a separate base protocol.
3. CompensatingSequence becomes a sequence policy over the unified steps (runs steps, collects compensation callables, unwinds on failure). Keep its name/import path as a thin alias during migration.
4. Merge factories: provision_step_from_dict's pluggable step-kind registry (base.py _STEP_TYPES Registry) absorbs the workflow from_spec dispatch table — one registry of step kinds, one build function; keep both entry-point names as aliases initially. Param substitution ({KEY}) becomes a factory-level option available to all kinds.
5. Migrate consumers in dependency order: toolchains/loader.build_step (already emits workflow steps — no change), recipe_contract TO12 path, hindsight recipes (post-HM20/HM21 the surface is small), provider cli_install (no change expected). Delete the redundant implementations and aliases last.
6. Contract tests: every step kind round-trips through the unified factory; recipe rollback goldens unchanged; workflow runner suite unchanged.

3. Workflow interactive/conditional steps unaffected (runner suite).
4. Factory contract test: every registered step kind builds from dict/spec via the single factory; unknown kind error preserved (VAL-DESC-002 / provision factory error parity documented).

## Effort & Risk

Complex / medium-high risk, but decomposable into low-risk increments (core extraction → extension recast → factory merge → consumer migration → deletion). The riskiest semantic is compensation-vs-fail_fast interplay; the rollback golden gates it. Do AFTER HM20/HM21 so the hindsight consumer surface is minimal. If validate-first disproves the 'workflow as core' hypothesis (e.g. context/result shapes irreconcilable), stop and record findings — do not force the merge.
