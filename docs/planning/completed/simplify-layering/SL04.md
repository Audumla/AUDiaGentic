# Monolithic state file creates contention

## Description

All components share one runtime state file: `.audiagentic/config/runtime/features.yaml`, read/written via `src/audiagentic/foundation/features/state.py`.

PREMISE CORRECTION vs original draft: the original said 'every mutation acquires the same file lock' and framed this as LOCK contention. THERE IS NO FILE LOCK. `save_yaml_file` (foundation/io.py) writes via atomic temp-file + `os.replace`. There is no advisory/OS lock anywhere in the write path. So the real problem is NOT lock contention — it is:

1. READ-MODIFY-WRITE races: every setter (`set_feature_state`, `set_implementation_state`, `set_implementation_feature_state`, `set_component_state`) does `load_feature_state()` -> mutate one component's subtree -> `save_feature_state()` rewriting the WHOLE file. Two concurrent mutations to DIFFERENT components can clobber each other (last-writer-wins on the whole document), because each loads the full doc, edits its slice, and atomically replaces the entire file. Atomic replace guarantees no torn file — it does NOT prevent lost updates.
2. Write amplification: enabling one LSP language rewrites the entire features.yaml (all components).

This reframes the fix: the goal is ISOLATION of write scope (so a mutation to component A never rewrites component B's data), which incidentally removes the lost-update window between unrelated components. Sharding achieves this.

## Steps

**Validate-first:** Confirm no lock exists (grep `FileLock|flock|lock` in foundation/io.py + features/ — expect none) and that all 5 setters follow load-whole / mutate-slice / save-whole. Confirm `mutate_feature_state` named in the original draft does NOT exist; the real API is the get_/set_ functions in state.py (this is the surface to preserve).

**Approach: shard state by component (parent), keep public API identical.**

1. New layout: `.audiagentic/config/runtime/features/{parent}.yaml`, one file per component. Each holds exactly the dict currently stored under `state[parent]` (its `features` + `implementations` maps).
2. Refactor `state.py` internals so the per-component accessors operate on the shard:
   - Replace `get_component_state(root, parent)` to read `features/{parent}.yaml` (returning {} if absent).
   - Replace `set_component_state(root, parent, component_state)` to write ONLY `features/{parent}.yaml`. This is the key isolation win — a mutation to parent A only ever rewrites A's shard.
   - `load_feature_state` / `save_feature_state` (whole-doc) become legacy/back-compat helpers used by migration only; mark them deprecated or remove if no external callers (grep first).
3. Keep ALL public function signatures unchanged (`get_feature_state`, `set_feature_state`, `get_implementation_state`, `set_implementation_state`, `get_implementation_feature_state`, `get_implementation_feature_enabled_explicit`, `set_implementation_feature_state`, `feature_composite_key`, etc.) so the ~10 consumer files (lsp_config_api, lsp_api, runtime_resolver, provider_config, resolver.py, lifecycle.py, planning_paths/manage_mcp) need NO changes.
4. MIGRATION (lazy, on read): in `get_component_state`, if `features/{parent}.yaml` is absent but the legacy monolithic `features.yaml` exists, read the parent's slice from it, write the shard, and (optionally) leave the legacy file until all parents migrated. Provide a one-shot `migrate_to_shards(root)` that splits every top-level key of legacy `features.yaml` into shards and then renames the legacy file to `features.yaml.migrated` (do NOT delete — keep for rollback). Run nested->flat feature-key migration (`migrate_component_state_to_flat`) per shard during the split, preserving existing behavior.
5. OPTIONAL index file: the original proposed an index `features.yaml` mapping component->shard. NOT NEEDED — shard path is deterministic from parent id (`features/{parent}.yaml`); discovery is `glob('features/*.yaml')`. Skip the index to satisfy Standard #2 (no hardcoded per-component mapping) trivially. Document this deviation from the original draft.
6. Per-shard locking is OPTIONAL and only worth it if true concurrency is observed. Since the codebase currently has NO locking and relies on atomic replace, sharding alone removes cross-component lost updates. Add an OS file lock per shard ONLY if same-component concurrent mutation is a real scenario (likely not at current scale). Default: ship sharding without locks; note the residual same-component race as accepted.

## Files

PRIMARY: `src/audiagentic/foundation/features/state.py` — reroute get/set_component_state to per-parent shard; add migrate_to_shards; keep all public accessor signatures.
POSSIBLY: `src/audiagentic/foundation/io.py` — only if a per-shard lock helper is added (optional; default no).
TESTS: `tests/unit/foundation/test_features.py`, `tests/unit/foundation/test_impl_scoped_features.py` — update fixtures that assert on monolithic `features.yaml` path/shape; add migration test (legacy file -> shards, content preserved, nested->flat applied).
VERIFY-UNCHANGED consumers: lsp_config_api.py, lsp_api.py, runtime_resolver.py, providers/services/provider_config.py, features/resolver.py, features/lifecycle.py, planning/planning_paths.py, planning/planning_manage_mcp.py.

## Validation

1. `pytest tests/unit/foundation/test_features.py tests/unit/foundation/test_impl_scoped_features.py` green with shard layout.
2. Migration test: seed a legacy monolithic features.yaml with 2+ components incl. old nested feature format -> run migrate -> assert each `features/{parent}.yaml` exists with correct flat content and legacy file renamed to .migrated.
3. Isolation test: set state for component A, then component B; assert A's shard file mtime/content is unchanged by B's write (proves no whole-doc rewrite / no cross-clobber).
4. Full provider + lsp suites green (consumers unchanged): `pytest tests/unit/providers tests/unit/coding_lsp tests/integration/coding_lsp`.
5. ENV-CHANGING migration test must be validated in the Docker image, not just host (per project gate).
6. `ruff check` clean.

## Effort & Risk

Effort: MEDIUM. Risk: data migration (mitigated by lazy read-migration + keeping legacy file as .migrated for rollback, never deleting). The original 'contention is theoretical' caveat still holds for the LOCK framing — but the lost-update race between unrelated components is real (no lock exists), so the isolation benefit is concrete, not just theoretical.
