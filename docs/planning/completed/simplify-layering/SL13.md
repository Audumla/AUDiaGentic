# Consolidate hindsight recipes onto existing provider/foundation machinery (delete duplicate recipe logic)

## Description

Follow-on from the SL12 review (2026-07-08). Applying the 'is this operation already owned elsewhere?' lens to every hindsight recipe reveals that most are NOT hindsight-specific — they reimplement config-management machinery that already exists in providers/services or foundation. The genuinely hindsight-specific residue in each case is tiny: a payload, a block of rule text, or a managed-id. Same shape as the MCP dual-writer finding in HM21/RV155, now seen to be systemic.

FINDINGS (per recipe):

1. MCP ENTRY — HindsightMcpRecipe / _McpConfigAdapter / _CompositeRecipe(mcp half). DUPLICATES providers/services/mcp.py (add/remove/list + sync_managed_provider_mcp_subset, ownership-tracked, reload-aware, riding the SL10 reconcile_fragments engine). Current state is inconsistent: configure already uses the generic sync (HM21), but probe/verify still route through HindsightMcpRecipe's own read-compare, and prune calls BOTH _inner.prune() AND the sync (double removal). Hindsight-specific residue: the entry payload (build_hindsight_entry/build_hindsight_mcp_entry) + managed-id 'ag-hindsight'. ManagedEntryRecipe (foundation, SL12) has hindsight as its ONLY consumer — a speculative abstraction; once MCP is rewired it has zero consumers.

2. RULES BLOCK — RulesOnlyRecipe / _CompositeRecipe(rules half). DUPLICATES providers/surfaces (base.SurfaceBlock/apply_managed_blocks/render_managed_region/strip_managed_content + manager.plan/apply/prune_provider_surfaces) — a complete managed-block-into-provider-instruction-file system with contributions, ownership, and plan/apply/prune. RulesOnly hand-rolls apply_managed_block(path, _RULE_BLOCK_ID, RULE_TEXT) + ArtifactRegistry directly. CORRECTNESS RISK (mirrors HM21 MCP dual-writer): surfaces manages a sentinel region in the SAME instruction files (AGENTS.md etc.); a second independent managed-block writer can interfere with surfaces' strip/render region. Hindsight-specific residue: RULE_TEXT + block id.

3. PLUGIN ARRAY — _PluginArrayRecipe. Upserts one owned entry into a provider's plugin-array config via matrix-declared reader/writer/remover (plugin_array_* resolved via resolve_ref). The ownership/reconcile pattern is SL10's reconcile_fragments (same engine providers/services/mcp uses); the per-provider callbacks are genuinely custom. LOWER priority — partial consolidation onto reconcile_fragments possible, but the callback indirection is real. Assess whether this is a provider managed-entry op (like MCP) or genuinely bespoke.

4. OWNED SIDECAR FILE — _PluginUrlConfigRecipe. Writes a hindsight-OWNED file (~/.hindsight/<provider>.json the provider's plugin reads), NOT a provider-shared config — no existing provider home. The generic 'write owned dict to file, prune deletes' is the OwnedFileRecipe shape declined in SL12; the Windows launcher repair (_repair_windows_plugin_mcp) is genuinely hindsight/vendor-specific. Its install/uninstall installer-steps DUPLICATE the DeclaredStepRecipe gated-installer logic (optional-installer variant). MOSTLY LEGITIMATE hindsight, but the installer-steps overlap and the owned-file mechanism are consolidation candidates.

5. DECLARED INSTALLER — HooksInstallerRecipe (uses DeclaredStepRecipe, foundation) + the optional-installer branches in PluginConfig/_PluginUrlConfig. Note a THIRD installer machinery exists: provider CliInstallRecipe (descriptors cli_install, toolchain build_step) installs provider CLIs. Three 'run declared install steps' paths (provider CliInstall, foundation DeclaredStep, plugin optional-installer). Not necessarily wrong (different subjects) but worth a deliberate call on whether DeclaredStepRecipe is the single installer primitive.

6. GUIDANCE — GuidanceOnlyRecipe (uses NoAutomationRecipe, foundation). CLEAN, no duplication. Keep.

META: the hindsight recipe layer largely re-expresses provider config-management (MCP entries, instruction blocks, config arrays) as capability recipes, when the provider layer already owns those operations with ownership tracking and reload. The recipe classes should become thin registry-facing wiring whose BODIES call the provider machinery; the domain residue (payloads, rule text, managed-ids, vendor repair) is what stays.
