# Delete dead recipe scaffolding (StepRecipe + LSP recipe wrappers) and reconcile installer-path fragmentation

## Description

Applying the SL13 consolidation lens to every NON-hindsight recipe implementation (2026-07-08). Finding: the recipe abstraction's intended non-hindsight consumers never adopted it — they kept their own direct paths — leaving ~286 lines of dead-except-tests scaffolding plus a fragmented installer story.

EVIDENCE (grep-verified):

1. DEAD-EXCEPT-TESTS — StepRecipe chain (~286 lines). 
 - foundation/toolchains/recipe_steps.py `StepRecipe` (112 lines): its ONLY consumer is coding_lsp/lsp_recipe.py, which is itself test-only.
 - coding_lsp/lsp_recipe.py `lsp_language_recipe` (49 lines): called ONLY by tests/unit/coding_lsp/test_lsp_recipe.py. The REAL LSP install path is lsp_config_api.py:468 → build_dependency_workflow(action='install') run directly; LSP never uses the recipe.
 - providers/services/lsp_recipes.py `LspRecipeAdapter` + `map_lsp_fields_to_recipe_concepts` (125 lines): called ONLY by tests/unit/foundation/toolchains/test_architecture_boundaries.py; self-described as 'metadata-only adapter... documents how fields map'. Zero non-test src/ imports.
 These are the TO07/RV07 'validate the recipe abstraction fits a real consumer' experiment — the real consumers (LSP install, LSP metadata) declined it and kept build_dependency_workflow. Per §10 (no dead code / no speculative abstraction) they should be deleted with their tests.

2. CliInstallRecipe is a 'recipe' in name only. providers/descriptors/base.py CliInstallRecipe is a WorkflowStep (ShellStep/SequenceStep) data holder; providers/services/lifecycle.py runs recipe.install.run(...) DIRECTLY — not through the ProvisioningRecipe lifecycle. The name implies a lifecycle it does not have.

3. INSTALLER-PATH FRAGMENTATION (the SL13-B3 finding, now concrete): three 'run install steps' mechanisms exist — (a) DeclaredStepRecipe (foundation, provision_steps dicts, gate+probe) used by hindsight Hooks; (b) StepRecipe (foundation, WorkflowStep trees) used only by tests; (c) CliInstallRecipe (WorkflowStep, run directly) used by provider CLI install. (b) is dead; (a) and (c) run the two different step systems (SL09) for two different consumers. After deleting (b), DeclaredStepRecipe is the sole installer RECIPE, and provider CLI install stays on its direct WorkflowStep path.

4. HONESTY note on SL11: the 'second consumer' cited for promoting action_needed to RecipeResult was LspRecipeAdapter:91 — which is dead-except-tests. SL11 still stands (action_needed is a clean generic RecipeResult field, justified by hindsight's 30+ uses), but after deleting lsp_recipes.py hindsight becomes effectively the SOLE RecipeResult.action_needed consumer (services/mcp.py uses the key in a plain dict, not a RecipeResult). No reversal — just record that recipes are currently a hindsight-scoped mechanism until a second capability adopts them.

SCOPE NOTE: this item is REDUCTION (delete dead code) + a naming/clarity fix, NOT new abstraction. Do not build a unified installer to 'fix' fragmentation — that is SL09 territory (closed won't-merge) and would violate the anti-over-engineering guardrail.
