# Options resolution lacks provenance

## Description

`resolve_options` merges layers (descriptor defaults -> component options -> feature/implementation state) but discards which layer provided each value. When debugging why an option has an unexpected value, there's no audit trail.

## Proposed Solution

Return a `ResolvedOption` dataclass `(value, source: str)` alongside the resolved dict, where `source` is one of `'descriptor-default'`, `'component-state'`, `'feature-state'`, `'implementation-state'`. Add an MCP tool `get_option_provenance` for debugging. Keep the existing `dict[str, Any]` return for callers that don't need provenance, but make the enriched version available.

## Architecture Standards Assessment

**Standards risk: None.** Purely additive — foundation-level dataclass + MCP tool. No layer boundary violations, no hardcoded entity names, no config-over-code concerns.

## Resolution Assessment

**Complexity: Easy.** Straightforward implementation.

**Solution:** Add `ResolvedOption(value, source: str)` dataclass in `foundation/features/options.py`. Wrap the merge logic in `resolve_options` to track provenance per key. Add MCP tool `get_option_provenance(component_id)` that returns the provenance mapping. Existing callers receive the dict as before; new callers opt in to the enriched return.

**Files:** 3 — `options.py` (dataclass + merge logic), one MCP tool file, tests.

## Effort & Risk

Effort: Low. Risk if unchanged: Debugging difficulty grows with adoption.
