# Gateway dispatch unconditionally requires full-isolation tier, breaking 11/16 registered providers

## Description

agents_gateway_dispatch._dispatch_one_attempt always calls agents_gateway_worker.execute_isolated_provider_turn (spawns the disposable-worker OS subprocess), regardless of the provider's declared execution isolation tier. The subprocess entry point (agents_gateway_worker_host.py:83-89) hard-rejects any identity whose provider_isolation_tier != 'full-isolation' with UNS-AGW-076. Only 4 of 16 registered providers declare 'full-isolation' (codex, opencode, pi, qwen) — the other 11, including local-openai, claude, cline, gemini, copilot, antigravity, openhands, plandex, roo (no-isolation) and aider, continue, goose (partial-isolation), can therefore NEVER successfully complete a real gateway dispatch. Every real attempt fails immediately inside the worker subprocess before it ever reaches the provider adapter or makes a network call.

Discovered 2026-07-20 while building real concurrent-load Docker tests (tests/integration/agents/test_gateway_concurrency.py) against local-openai through a real gateway subprocess — the very first test that needed a SUCCESSFUL real completion via local-openai through the gateway (rather than a crash mid-flight, which is what every existing local-openai-based test does). The existing crash-matrix Docker suite (test_gateway_crash_matrix_docker.py) uses local-openai too but never actually verifies a successful completion in any of its 4 scenarios — every one kills the process while the request is still 'running', so this bug has been silently masked since it was introduced.

## Steps

1. Confirm intended design: services/public_execution.execute_provider_turn (providers_api.execute_provider_turn) is the direct in-process execution seam already used by non-gateway callers (test_provider_prompt_launch_e2e.py etc). The disposable-worker subprocess (execute_isolated_provider_turn) exists specifically for full-isolation providers that need OS-level process isolation (SH06). Dispatch should branch on provider_isolation_tier: full-isolation -> existing subprocess path; anything else -> direct providers_api.execute_provider_turn(provider_request) call, no subprocess spawn.
2. A first attempt at exactly this branch (in _dispatch_one_attempt, agents_gateway_dispatch.py) was tried and reverted same-day (2026-07-20) after it caused 34 test failures across tests/unit/agents and tests/integration/agents. Root cause of the breakage: a large fraction of the existing gateway test suite monkeypatches `audiagentic.components.agents.agents_gateway_worker.execute_isolated_provider_turn` as its ONLY mock injection point for fake/stub provider behavior. Routing non-full-isolation profiles around that function entirely made those monkeypatches silently inert, so the tests fell through to the real (unmocked) providers_api.execute_provider_turn path and failed on real validation/config errors (missing runner, disabled provider, etc).
3. This means the fix cannot be a same-file, same-session patch — it requires an audit of every test that monkeypatches execute_isolated_provider_turn (grep the whole tree first) and either (a) updating those tests' default fixture profile to declare full-isolation tier so the existing mock seam keeps working, or (b) adding an equivalent second monkeypatch point at providers_api.execute_provider_turn (or a shared internal seam both paths funnel through) so both isolation branches remain mockable from one place, or (c) some combination decided after actually reading how the affected tests construct their fake providers.
4. Whichever approach is chosen, add a regression test proving a non-full-isolation provider (e.g. local-openai) can complete a REAL request through the real gateway dispatch path end-to-end — no test in the current suite does this today; it is exactly the gap that surfaced this bug.
5. Do not close this item without re-running the full tests/unit/agents + tests/integration/agents suite clean, plus the gateway Docker suites (crash-matrix, opencode, concurrency) via real docker build/run.
