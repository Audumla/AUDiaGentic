# Move cross-process gateway triggers onto a durable external event transport

## Description

When a current cross-process trigger requires delivery beyond the shared gateway's local client API, add the smallest durable event ingress transport that meets its evidenced delivery and deployment requirements. Do not assume a broker or vendor in advance.

## Steps

1. Treat this as exploritory. We could look at the simplest methods of api over mcp layering to expose events or propose a light mqtt like server if needed - the event bus was supposed to be capable of having a new underlying implementation - perhaps we could have both?

2. Characterize the concrete trigger, required durability, ordering, acknowledgement/redelivery, offline, and authentication needs. 2. Select and justify the smallest transport behind EventBusProtocol; a broker is an option, not a premise. 3. Map delivery identity to gateway idempotency and keep ingress a thin adapter. 4. Add only failure/recovery tests required by the selected transport and trigger. 5. Preserve direct local IPC for synchronous management/status operations.

## Files

foundation event transport implementation/config; thin gateway event ingress adapter plus public admission API; topic descriptors; dead-letter/replay integration; tests and operations docs

## Validation

A trigger published from a separate process is durably admitted once despite redelivery; broker outage has an explicit degraded outcome; lifecycle events retain correlation and are consumable cross-process; poison messages do not block the queue. Gateway core imports no broker/MQTT implementation; event handlers import no gateway store/queue/dispatch internals.

## Effort & Risk

Complex operational dependency. MQTT is a candidate, not a foregone conclusion; selection must be driven by delivery and deployment requirements.

## Standards

AR25; Architecture Standards §§1,4,5,6,7; Observability Standards.

## Notes

IMPLEMENTED 2026-07-18 (claude). Step-1 characterization: the current cross-process triggers are agents.llm.gateway.requested / cancel-requested published from processes other than the gateway service (agent-jobs, operator tooling); required properties are durable once-only admission despite redelivery, offline publishing while the service is down, single-machine deployment, and poison isolation. Selection (step 2): a broker is NOT justified by these requirements — the smallest transport is foundation DurableSpoolTransport (foundation/event/durable_spool.py): atomic-file spool, ordered consume, ack-by-delete, bounded transient retries, dead-letter with replay_dead_letter, closed allowed-topic set. Step 3: agents_gateway_ingress maps spool event-id → SH07 idempotency key (publisher-supplied key wins) so redelivery returns the original request identity. Step 4: thin adapter uses only the public GatewayApplication (no store/queue/dispatch imports); GatewayServiceHost drains at startup then polls at 1s. Step 5: local IPC (SH04 HTTP client) unchanged for synchronous ops. Validation: separate-OS-process publish admitted by live host (integration), duplicate redelivery reuses the idempotency key, poison dead-letters without blocking the queue, transient failures retry in order and bound out, offline spool drains at startup, correlation metadata survives into the submission. 25 unit + 2 integration tests. Broker-outage degraded-outcome bullet is N/A for the selected transport; the EventBus seam remains the extension point if a future trigger evidences requirements the spool cannot meet.
