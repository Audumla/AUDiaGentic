# Running agent requests lack in-flight turn progress

## Notes

This is an observability defect, not evidence that the workers were dead. Both workers later completed and produced useful output. The issue is that the gateway could not prove or display in-flight turn progress while they were working.

Do not solve this by marking long-running workers failed solely by elapsed time. Add evidence and classification. Unknown remains unknown; stale-progress should be visible without fabricating terminal state.

## Findings

During the 2026-07-19 three-worker delegation exercise, two long-running requests appeared stuck for more than two polling windows even though they later completed successfully. Persisted request status showed only `attempt.started`; gateway overview showed live sessions with `turn-count: 0`; `agent_llm_wait` timed out at the MCP/tool boundary instead of returning a useful latest persisted record. This made healthy long-running model work look indistinguishable from launch failure.

Required repair: add explicit in-flight progress evidence to the request/session status surfaces. The gateway should expose phase/progress markers such as `launching`, `prompt-delivered`, `turn-starting`, `model-active`, `tool-active`, `finalizing`, and `stalled` where those facts are known. The status response should include elapsed running time, last observed worker/session activity, latest redacted session event, and a stale-progress classification derived from age plus turn/session evidence.

`agent_llm_wait` must not surface a tool-call failure on timeout as the primary operator experience. On timeout it should return the latest persisted public record with an explicit `wait-timeout: true`/equivalent marker and latest progress evidence, leaving terminal/failure semantics unchanged.

The live MCP/gateway process also proved stale relative to source: it still rejected continued-session `session_id + session_keep_alive` after the source contract had been changed. Add a live-version/source-version or gateway build fingerprint to overview/status so operators can identify stale process behavior before debugging the wrong code.

## Conclusion

Implemented 2026-07-19 via gateway worker delegation (supp-coder-opencode, req_1086ea802e104a92) with controller repair. Phase vocabulary closed set including terminal 'interrupted'; stale-progress is diagnostic-only and never applies to terminals.
