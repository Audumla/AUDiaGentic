## Findings

The opt-in Docker-backed gateway e2e now gets past npm after live opencode sessions are closed, but fails before gateway execution: installed components produce ('pi','custom-entries') in the observed MCP/provider config set while test expects ('opencode','custom-entries'). Inspect install/component projection and decide whether the test expectation or installed component id is stale. Preserve real Docker/rig validation once setup assertion is fixed. Also note npm/opencode.exe EBUSY occurs while live opencode workers are active; harness cleanup/retry guidance should be documented.

**Root cause (2026-07-19):** When `OPENCODE_CONFIG_CONTENT` is used to pass inline config to the opencode CLI, the config must include `enabled_providers` as a whitelist of provider keys. Without it, opencode falls back to the global config's `enabled_providers` list (e.g., `['brutus','openai','ymir','google','openrouter']`), which blocks our custom 'audiagentic' provider. The fix adds `enabled_providers` derived from the project config's `provider` keys in both `acp.py:build_acp_launch()` and `execution_environment.py:build_execution_environment()`, plus the direct subprocess call in the Docker e2e test.

**npm/opencode.exe EBUSY theory:** The host opencode CLI is installed globally via npm (`~/.npm/opencode.CMD`), not locked by Docker. The EBUSY errors seen earlier occurred when live opencode worker processes were still running during install, not from Docker file locking.
