# Sponsor decision: retain in-process as a scoped 'embedded' variant; SH11 deletes singleton ownership, not the engine

## Notes



## Findings

Decision from 2026-07-18 session (sponsor: user). The in-process engine is never deleted in any outcome — GatewayServiceHost hosts InProcessGatewayApplication around the same queue/dispatch/session modules; what SH11 retires is the unfenced client-side direct-binding path and the assumptions that hold only when exactly one process ever binds. Retain a renamed, scoped variant:

1. Rename mode 'in-process' → 'embedded'; contract = single-process, ephemeral, NO sharing claims. Legitimate uses: unit/CI suites (the whole test suite runs this way), one-shot Docker/CI jobs where a detached machine-wide service is pure overhead, air-gapped single-process CLI use.
2. Hazards and their fences: (a) split-brain over durable records — already largely defused by SH07 v2 fencing (epoch/worker/attempt-fenced dispatch claims make collisions detected-and-refused, not silent); (b) false sharing expectations — addressed by the rename + docs; (c) blanket startup reconciliation — must become embedded-scoped and must never run against records a live shared service owns.
3. Add a coexistence guard: on embedded client creation, read the machine ManagedServiceStore record; if a live provable owner exists, warn by default / refuse when AUDIAGENTIC_GATEWAY_EMBEDDED_ALLOW=refuse.
4. SH11 validation language changes from 'no production caller imports or constructs the old queue/session owner' to 'no caller obtains embedded binding implicitly; embedded is explicit opt-in, fenced, and never default'.

SH11's real goal — no accidental dual ownership, no permanent dual authority — is preserved; only the deletion scope narrows.

## Conclusion

Amend SH11: retire in-process as default and delete singleton-ownership assumptions and stale flags; retain the fenced 'embedded' opt-in variant with the no-sharing contract and coexistence guard.
