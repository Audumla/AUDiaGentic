# Exact-head audit: fresh-session checkpoint creation can be rejected

## Notes

Also note exact-head trace evidence from the reviewer request: CDP showed a fresh assistant response that completed, but gateway observations retained an older response-ref hash while latest assistant and terminal-witness hashes changed. This is a separate response-correlation/completion instrumentation issue; do not conflate it with the checkpoint finding. The review was run in the AUDiaGentic GPT project (ID g-p-69cc8c4cc7648191a009f358113d8dd2-audiagentic), distinct from the BigCherry GPT project ID. No multiple-root assumption.

## Findings

MEDIUM: update_provider_metadata delegates protected writes to update_owned_submission_checkpoint, which currently requires pre-existing unresolved-turn-pending=true and unresolved-turn-id matching the request. A fresh session has no such checkpoint, so its first normally owned prepared/dispatching checkpoint can be rejected. This can break new request submission before Send. Required: owner-validated initial checkpoint transition for empty metadata and regression coverage for fresh submission, durable checkpoint before Send, restart, and successful terminal cleanup.

## Conclusion

Finding accepted and incorporated in the follow-up. Owner-fenced checkpoint writes now initialize the first prepared turn only when the session has no unresolved checkpoint, and the same live owner may advance that unclaimed fresh checkpoint to dispatching. Prepared recovery claims remain mandatory after restart; dispatching is never replay authority. Regression tests cover durable prepared/dispatching states, restart non-replay, and terminal cleanup. Focused gateway/GPT-auto suite passed.
