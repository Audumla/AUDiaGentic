# Gateway worker failures are undiagnosable: exception type discarded, no service log file

## Description

Root-causing a real production failure (req_example_be9aa7068f661319, gpt-auto dispatch, 2026-08-20) hit a dead end: the wrapped exception's str() was empty (a common trait of TimeoutError()/ConnectionResetError()-style exceptions), and the two places that could have told us more were both closed off:
1. dispatch.py's INT-AGW-098 safety-net handler captures type(exc).__name__ into error.details['original-type'] before storing -- but store/_shared.py's _REDACTED_ERROR_KEYS = {code, message, kind} strips the entire details object out of the durable record, so the classname never reaches disk.
2. The gateway service process is launched via DetachedLaunch with stdout/stderr piped to subprocess.DEVNULL (foundation/system/managed_process.py, ~line 257-258), so the full traceback that logger.exception() writes at the INT-AGW-098 boundary is never persisted anywhere -- it's gone the moment it's logged.
Together these mean any dispatch-time failure whose message happens to stringify empty is completely opaque after the fact: no exception type, no traceback, nothing to search for.

## Steps

1. Redirect the gateway service's stdout/stderr to a real rotating log file (or existing project log directory convention) instead of DEVNULL, so operator-side tracebacks survive process lifetime.
2. Reconsider whether 'original-type' (the bare exception classname, not the full details payload) is safe to whitelist alongside code/kind/message in _REDACTED_ERROR_KEYS -- it's not sensitive on its own and would have immediately told us this was e.g. a TimeoutError vs a browser/DOM error without needing the log file at all.
3. Add a regression test asserting a wrapped INT-AGW-098 error's original exception type is recoverable from either the durable record or the service log.

## Acceptance Criteria

A gateway dispatch failure whose exception stringifies empty is no longer opaque: the bare exception classname (e.g. TimeoutError) is recoverable from the durable request record via its error.details.original-type field, and the full traceback logger.exception() writes is recoverable from a real log file (store.root/service.log) instead of being discarded to DEVNULL. No sensitive content (prompt bodies, exception repr/args) is newly exposed in the durable record.
