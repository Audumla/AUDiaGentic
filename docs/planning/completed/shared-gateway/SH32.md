# Machine-policy-driven session-lineage purge

## Description

Add an explicit, machine-global, disabled-by-default retention operation that purges closed provider-session lineage and its exclusively-owned gateway request/chat data after a configurable inactivity period. This is gateway-local deletion only; remote provider conversations are out of scope.

## Steps

1. Complete AS118's authoritative session generation fence, durable retention claim, and last-accepted-turn admission timestamp; AS107 remains the owner of lineage/pin semantics.
2. Extend the machine-global gateway retention policy with session_purge_enabled (default false) and session_purge_inactivity_seconds (positive threshold, recommended 604800 seconds / 7 days when enabled); reject project, agent, profile, provider, request, and MCP overrides.
3. Define eligibility from closed/expired state plus last_accepted_turn_at; require the live provider runtime to be closed/absent and block active, in-flight, admitted-but-unresolved, queued, recovery, reconciliation, pinned, shared, unknown, or ambiguous ownership.
4. Add a durable SESSION_PURGE operation and bounded manifest containing policy identity/digest, session generation, exact lineage closure, per-target dispositions, stage, timestamps, digests, and block reasons.
5. Compute the complete session-to-request closure before deletion. Delete only gateway-local request records, admitted input material, response artifacts, timelines, runtime roots, and other descendants proven exclusively owned by the lineage; preserve shared or uncertain references and remove the parent session/binding last.
6. Revalidate policy, generation, ownership, recovery, and closure under AS118's authoritative session fence immediately before destructive boundaries; make replay and restart recovery idempotent.
7. Expose bounded operation status/diagnostics that say gateway-local session purge only; add the full race, crash, closure, retention, and configuration test matrix before enabling the policy.

## Detailed Solution & Technical Design

SH32 owns the machine-global policy, eligibility scanner, SESSION_PURGE operation, referential closure, manifest, and gateway-local destructive cleanup. AS107 remains the owner of durable session identity, lineage references, retention pins, and transparent resume semantics. AS118 supplies the missing authoritative per-session generation fence, durable retention claim, and accepted-turn timestamp; SH32 must not duplicate those primitives or add a durable retired lifecycle state. Reuse SH24 archival/integrity evidence where its destructive-retention contract applies, without changing ordinary request PURGE eligibility or pinning rules.

The purge clock is only last_accepted_turn_at. It is not close time, provider activity, watchdog activity, polling, heartbeat, cleanup retry, or process state. A session is eligible only when policy is enabled, it is locally owned and closed/expired, the live runtime is absent, no current/in-flight/admitted-but-unresolved turn or recovery exists, the threshold has elapsed, the exact closure is known, and every selected object is exclusively owned. Unknown means BLOCK.

Resume/admit-new-turn and purge must serialize through AS118's generation.lock and durable claim/CAS. Under that fence, reread state, generation, inactivity, recovery, and ownership immediately before deletion; exactly one side may commit against a generation. SESSION_PURGE is one deterministic local cleanup operation, not a configurable archive/delete matrix and not a remote-provider deletion workflow. Persist durable intent/manifest before destructive work, delete request-owned descendants and records, remove binding/session-owned local material, then delete the parent last and finalize evidence. Already-deleted same-operation descendants are successful on replay; newly shared or ambiguous references block. Public semantics must never imply ChatGPT/provider conversation deletion.

## Code Samples & Guidance

Machine-global gateway retention policy:
```yaml
session_purge_enabled: false
session_purge_inactivity_seconds: 604800  # 7 days
```

No per-agent, execution-profile, provider, request, MCP, or project override. Existing execution-profile session-idle-timeout-seconds remains the live-provider resource close policy and is not repurposed.

## Effort & Risk

Size L, closed. Risks: legacy sessions without last-accepted-turn-at are intentionally never eligible; no unattended scheduler exists (a later item may submit this same operation from the retention worker); project code running on the server could not be stopped from deleting its own files by this feature (OS isolation is not claimed); the maintenance locks are taken after the plan is recorded, so admission into a claimed session is prevented by the claim itself.

## Standards

arch-standards §§1,3,4,6,7,8; observability-standards; SH24/SH26/AS107 retention, fencing, redaction, and provider-neutral ownership contracts.

## Acceptance Criteria

- Policy is machine-global, disabled by default, and absent configuration changes no existing retention behaviour or digest (SH32-A)
- session_purge_enabled is explicit; session_purge_inactivity_seconds is a number of at least 3600 and required when enabled; project, agent, profile, provider, request, MCP and caller input cannot override it (machine scope; the operation snapshots the machine policy over any supplied value)
- Existing execution-profile session-idle-timeout-seconds semantics are unchanged
- Only closed or expired sessions with a known last-accepted-turn-at older than the threshold, no live runtime, no claim, no non-terminal or unreadable request, and no request shared with another session are eligible; the dry run and the operation use the same rules
- Resume or new-turn admission and purge are mutually exclusive under the generation fence and the durable claim, which is never released once destruction has begun (CON-AGW-168)
- Deletion uses one shared lineage deletion, removes request records and artifacts, archives, binding, root registration and the session directory, parent last; shared or unknown ownership blocks before any mutation
- SESSION_PURGE is a durable operation; the recorded plan makes a crash or retry resume idempotently; an already-missing session is unchanged, never purged; results carry counts and dispositions without payloads
- SH24 request PURGE, AS107 pinning and resume semantics, and the manual purge-session are unchanged; status states gateway-local deletion only; no retired lifecycle state, archive-vs-delete mode or scheduler is introduced
