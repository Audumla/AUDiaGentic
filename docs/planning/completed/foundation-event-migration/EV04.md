# Strike 'registered callbacks' as a sanctioned decoupling mechanism from ARCHITECTURE_STANDARDS.md; keep events + contribution registries only, and add domain-neutral naming rule

## Description

ARCHITECTURE_STANDARDS.md section 1 (line ~22) currently sanctions three mechanisms for avoiding a forbidden import: 'registered callbacks, events, or contribution registries'. The 'registered callbacks' option is the get_capability/register_capability single-slot RPC pattern (foundation/capabilities.py). Investigation across this entire plan (foundation-event-migration EV01-03/EV05) plus the CP00 review found EVERY real and planned use of this mechanism in the codebase -- harness.config-refresh, harness.runtime-sync, providers.mcp-projector, providers.provider-config.resolve_enabled, providers.descriptors.all_ids, providers.surface-validator, and CP00's six planned CLI-layer additions -- was a misapplication: either a fire-and-forget reaction that belonged on the event bus, logic that never needed indirection at all, a decision runtime orchestration could make and act on itself, or a CLI-composition-root call site that could just check the component registry and import directly (CLI is exempt from the import-direction rule in the first place, so it never needed capability indirection). Zero legitimate uses were found. Leaving 'registered callbacks' on the books as a standards-sanctioned option invites the same misapplication to recur the next time someone needs to avoid a forbidden import and reaches for the easiest-looking tool rather than the correct one. This item removes it as a sanctioned option -- 'events' and 'contribution registries' remain the only two -- separately from the original domain-neutral-naming fix (still needed, and still applies to whatever remains: contribution-registry keys and event-type names should be domain-neutral, not named after one specific component).
