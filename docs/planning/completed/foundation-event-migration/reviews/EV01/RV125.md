# Handler gaps: config_changed not subscribed, has_mcp_servers hardcoded True, RV109's interim/observability asks unaddressed

## Notes



## Findings

The capability deletions themselves are clean (harness.runtime-sync/config-refresh gone, 'sync' field gone, grep confirms zero get_capability/register_capability callers, capabilities.py deleted per EV06). But the replacement subscriber has three gaps. (1) EV01's steps required reacting to install/enable/disable/uninstall/config_changed — the subscription wires on_installed/enabled/disabled/uninstalled but NOT on_config_changed, so harness config refresh on component config changes (previously reachable via the config-refresh capability path) is dropped. (2) action = _runtime_action_for_reason(reason, has_mcp_servers=True) hardcodes has_mcp_servers — the old _component_result computed it from the descriptor (descriptor.mcp_servers or external_mcp_servers); now MCP-less components are treated as reload-worthy, a determination-accuracy regression EV01's validation explicitly listed ('correct reload/refresh action determination'). The descriptor is one get_descriptor(component_id) call away. (3) RV109 (raised on EV01 before implementation, still state=created) asked for the interim-behavior contract and an assertable observable — the handler does push_status/ask paths but since no backend is ever set (RV120), every install currently push_statuses a 'timed out' deferral message; whether that message text should surface at all in headless CLI runs was never decided. Minor: the handler imports the private _runtime_action_for_reason from reload.py.

## Conclusion

Subscribe on_config_changed, derive has_mcp_servers from the component's descriptor, and either export _runtime_action_for_reason properly or move the decision into the handler's own module. Then close RV109 against the actual behavior.
