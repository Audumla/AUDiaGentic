# Scope creep in Step 2, re-raise vs swallow behavior unspecified

## Notes

Standard reference: Section 8 'Error Handling' — `except Exception:` is only permitted at external boundaries. Handler invocation IS an external boundary (third-party/untrusted code), so wrapping is correct per standard.

## Findings

1. **Scope creep in Step 2**: 'Add optional retry config to SubscriberError if future retry logic is desired' — this item is P2/simple. Adding retry configuration infrastructure is a separate concern that belongs in its own item (likely P3/complex). This step should be removed or deferred.

2. **Re-raise vs swallow unspecified**: The critical behavioral question is unanswered: after catching Exception and wrapping as SubscriberError, should `_dispatch_sync` re-raise the SubscriberError (halting dispatch to remaining subscribers) or log-and-swell it (continuing to next subscriber)? Current behavior swallows exceptions silently — matching that would be a no-op behavior change. The item description says 'no behavioral change expected' but wrapping as SubscriberError and logging IS a behavioral change if it gets re-raised.

3. **Logging level unclear**: Should SubscriberError log at warning (non-fatal subscriber issue) or error (dispatch failure)? Standard §9 says warning for non-fatal with exc_info=True.

## Conclusion

EV09 Step 2 is out of scope and should be removed. The re-raise vs swallow decision needs resolution.
