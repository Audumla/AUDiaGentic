# Reconciler-registry move into providers creates a memory→providers cross-component import; the registry may not need to survive at all

## Notes



## Findings

Verified against code (2026-07-05): the ONLY registrant of register_provider_recipe_reconciler is the MEMORY component (components/memory/memory_observer.py:62, registering its own _reconcile for hindsight), and the ONLY production caller of refresh_provider_recipes is the same file (memory_observer.py:59). Three consequences EV03 does not address: (1) Step 2 moves the reconciler registry into components/providers/services/recipe_reconciliation.py — which forces memory_observer.py to import components.providers to register, a NEW cross-component import. ARCHITECTURE_STANDARDS.md section 1 sanctions components importing foundation and runtime; component→component imports are only tolerated as the one documented providers→agent_jobs seam. This trades a naming violation for a layering violation. (2) Step 3's premise ('perform reconciliation locally using in-component calls' inside providers) is wrong for the actual reconciler: _reconcile is memory-domain hindsight provisioning, not providers logic — it cannot 'live inside the providers component'. (3) Since memory is simultaneously the sole publisher and sole registrant, the entire dispatcher indirection currently collapses to memory calling its own _reconcile — the simplest compliant end state may be: memory's observer reacts to the new config-changed event (or calls _reconcile directly) and the registry is deleted outright, OR the registry survives in foundation as a properly domain-neutral contribution registry (contribution registries remain a sanctioned mechanism per EV04) with a neutral name/key vocabulary. Additional smaller issues: the proposed event type 'capability.config_changed' reuses the word 'capability' just as EV06 deletes foundation/capabilities.py — pick a non-overloaded, domain-neutral name (e.g. 'component.config_changed' payload {component_id, project_root}); and the Files list includes foundation/event/lifecycle_observer.py with no step explaining what changes there.

## Conclusion

Redesign steps 2-3 before implementation. Recommended shape: publish 'component.config_changed' from memory's config-mutation path; memory_observer subscribes and runs its own _reconcile (registry deleted, no cross-component import); if genuine multi-component reconciliation is anticipated, keep a domain-neutrally-named contribution registry in foundation instead — either satisfies EV04. Name the concrete publisher (memory config path) in step 1 instead of 'whichever capability component', and either add a step for lifecycle_observer.py or drop it from Files.
