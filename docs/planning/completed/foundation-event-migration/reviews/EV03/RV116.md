# memory→providers direct import fails the repo's own architecture-boundary test (currently red)

## Notes



## Findings

The dispatcher collapse (memory calls its own _reconcile; provider_recipes.py deleted) followed RV108's recommended direction — but the provider-id sourcing was implemented as direct imports of audiagentic.components.providers.descriptors.registry.all_descriptors and providers.services.provider_config.is_provider_enabled inside memory_observer._reconcile. The repo's own guard test tests/unit/foundation/toolchains/test_architecture_boundaries.py::TestMemoryComponentBoundaries::test_memory_core_has_no_provider_imports FAILS on exactly these two imports (verified 2026-07-05). RV108 warned this specific cross-component dependency was the hazard to avoid; the implementation introduced it anyway, undocumented, and shipped with the guard test red. Additional defect: there is no providers-installed presence check before the import — the old get_capability path degraded gracefully to a no-op when providers was absent; now a memory lifecycle event in a providers-less deployment raises ImportError inside an event handler.

## Conclusion

Either (a) route provider-id enumeration through a domain-neutral foundation seam (e.g. a contribution the providers component registers, or an event-carried payload), restoring the boundary the test enforces, or (b) if memory→providers is now deliberately accepted, that is a standards decision the user must make explicitly — update ARCHITECTURE_STANDARDS.md and the boundary test together, not by leaving the test red. Also add a component-registry presence check (get_descriptor('providers')) with graceful skip before touching providers modules.
