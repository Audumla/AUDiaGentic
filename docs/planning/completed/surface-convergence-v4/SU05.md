# Phase 3: audit concept equivalence before canonical capability identity

## Description

Classify existing capability, provider-fact, session-surface, evidence, mechanism, and policy types and prove which concepts are equivalent before introducing a canonical CapabilityId or deleting models.

## Steps

1. Inventory capability catalogue kinds, ProviderDescriptor capabilities, ProviderCapabilityFact, session surfaces, SessionMappingCapabilities, resolver outcomes, and policy fields.
2. Classify each type by owner, lifecycle, validation, semantics, and authority; mark true equivalences, projections, and intentionally distinct concepts.
3. Identify duplicate fields and define one owner for each surviving concept.
4. Update AS84/AS85/AS96-AS104 dependencies and acceptance criteria with the equivalence decisions.
5. Create the canonical CapabilityId item only after this audit is reviewed and the Phase 1/2 gates are green.

## Detailed Solution & Technical Design

Do not unify by field overlap. Capability identity, observed evidence, runtime mechanism, policy, and public projection remain separate until ownership/lifecycle/validation/semantics match. Resolver outcomes must distinguish supported, unsupported, unproven, unavailable, invalid, and failed; provider load must distinguish strict execution from tolerant diagnostics per AS72/run sheet.
