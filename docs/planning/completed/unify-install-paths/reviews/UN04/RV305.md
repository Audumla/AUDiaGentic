# MAJOR: UN04 scope collides with managed-config-consistency plan (MA03/MA05/MA07/MA08) — must reframe to orchestration-only and defer mutation ownership

## Notes

Discovered the managed-config-consistency plan (MA02-MA09) and MANAGED_MUTATION_AUDIT.md own the durable-mutation side of the same modules UN04 targeted.

## Findings

1. DIRECT OVERLAP (must reframe): The MANAGED_MUTATION_AUDIT.md table already assigns owners for the exact modules UN04 listed:
   - release_please/install.py:install and manage.py:update_workflow -> MA05 (Harden component-owned workflow and hook mutations) — atomic owned-file path.
   - runtime/harness/pi/install/config.py:materialize_agent_config + patches.py -> MA07 (Converge Pi harness materialization) and MA03 covers the pattern; opencode materialize_agent_config -> MA03 (Converge OpenCode harness materialization).
   - source_control_bootstrap post-commit hook -> MA05.
   - provider LSP entries (language_servers_sync / lsp_projection) -> MA08 (Adopt managed ownership for provider LSP entries).
   UN04 as written would create duplicate/competing ownership of these mutations — a direct violation of §16 'Every durable mutation has one owner and one lifecycle path.'
2. SEPARATION OF CONCERNS (the correct frame): The MA plan owns *durable mutation ownership* (atomic write, ArtifactRegistry, ManagedConfigSpec, prune) per §16. This plan (unify-install-paths) owns *install-orchestration lifecycle* (probe->install->verify->uninstall recipe contract + step system). These are orthogonal but touch the same files. UN04 must be reframed to: (a) confine itself to the orchestration-lifecycle question only; (b) explicitly DEFER all file-write/prune ownership to MA03/MA05/MA07/MA08; (c) add a sequencing dependency — the MA items should land the §16 owners first (WriteFileStep/ArtifactRegistry/ManagedConfigSpec) so the install-orchestration recipe composes them, rather than the reverse.
3. GENUINELY IN-SCOPE FOR THIS PLAN: the LSP language-server *sync loop* (desired-set vs installed-set reconcile) is orchestration and rhymes with hindsight's prune-stale reconcile in provision.py — that reconcile-pattern question is this plan's, while the *managed entry write* is MA08's. The two reconcile-loop decision (reconcile_provider vs reconcile_hindsight shared helper) is also this plan's.
4. HARNESS INSTALLS: pi/opencode install are mostly §16 (MA03/MA07) plus third-party-repair patches (audit rows, exemption candidates). Almost nothing there is generic install-orchestration; UN04 should EXEMPT harness installs from this plan and point at MA03/MA07.
5. NET: UN04 shrinks to (a) LSP sync-loop orchestration alignment coordinated-with/after MA08, (b) the shared-reconcile-helper decision, (c) a written exemption for harness installs deferring to MA03/MA07, (d) release-please orchestration deferring file ownership to MA05. Retitle accordingly.

## Conclusion

Reframe UN04 substantially: orchestration-only, defer mutation ownership to the MA items, encode the cross-plan sequencing. Do NOT re-own any audit-table row.
