# Stage 5 — Unsupported-provider fallback, validation, and docs

## Description

Finish the memory component with deterministic fallback behavior, test coverage, and contributor docs that explain exactly how to add the next backend after Hindsight. This stage converts design intent into maintenance-safe project guidance.

## Steps

1. Add tests for descriptor loading, implementation discovery, implementation selection, config validation, and provider projection refresh. Cover both active implementation swap and repeated no-op apply.
2. Add provider-facing tests for at least three cases: one official-native integration, one custom-managed-block integration if any exist, and one unsupported provider path.
3. Document exact fallback semantics chosen in ME03 in `src/audiagentic/components/memory/README.md` and component docs: unsupported provider yields warning/no-op or warning/managed note block.
4. Extend contributor docs with a short 'adding a new memory implementation' section that points to `memory.yaml`, implementation descriptors under `config/components/memory/`, and any projection writer registration points.
5. Capture operational prerequisites for external Hindsight server use: required URL format, auth expectations, per-provider limitations, and whether localhost/remote URLs are both allowed.
6. If release/ledger process is in scope for implementation turn, require change-event recording after substantive work; otherwise note it in validation checklist for executor.

tests/** for memory component and provider surface integration

## Validation

- Test suite covers success path and unsupported-provider path.
- Swapping away from `hindsight` removes or updates managed provider memory blocks without stale residue.
- README/doc section explains how to add `memory/<next-impl>.yaml` without changing component core.
- Operational docs name exact config keys and expected user workflow: select impl → set URL/config → reconcile/apply surfaces.
- Residual gaps are listed explicitly if some providers remain unsupported.

## Effort & Risk

Risk is leaving future implementers to rediscover architecture. Mitigation: docs must include exact extension points and one concrete Hindsight example end-to-end.

## Notes

Executor should treat this item as release-readiness gate: no memory component considered done until tests and extension docs exist.
