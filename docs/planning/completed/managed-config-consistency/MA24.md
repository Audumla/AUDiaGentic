# Migrate Hindsight declared integration automation

## Description

Replace Cline/Aider legacy declared-step assembly with frozen Hindsight-owned integration recipe objects parsed from Hindsight config. Hindsight executes its official integration commands through foundation steps. Providers remain unaware of Hindsight; no provider-integration API or provider-side Hindsight handler is created.

## Steps

1. Baseline strategy, recipe-spec, recipe, provision, and provider-file tests. Confirm Cline and Aider are the only generic declared integration rows; Codex/Pi retain custom paths until MA26.\n2. Define frozen Hindsight-owned IntegrationCommand, DeclaredIntegrationDefinition, and HindsightIntegrationDesired objects. Parse matrix step mappings once at the Hindsight boundary.\n3. Add concrete hindsight-integration-recipe/v1 JSON schema for serialized definitions. No Any payload, unchecked nested mapping, provider path, or universal family object survives beyond parsing.\n4. Implement DeclaredHindsightIntegrationRecipe over generic foundation ShellStep/run_steps. Hindsight owns package names, commands, parameter substitution, gates, status, verification, and redaction.\n5. Preserve Cline platform fallback and Aider Python 3.13 block in Hindsight strategy resolution. Providers declare only generic capabilities and contain no Hindsight import, command, registration, or identity.\n6. Replace production declared_step assembly for HOOKS/WRAPPER_CLI rows with typed recipe construction. Codex/Pi custom recipes remain for MA26; rules remain generated surfaces.\n7. Validate typed config parsing, schema roundtrip, command order/substitution, source/platform/Python gates, failure/redaction, lifecycle behavior, packaging, and provider blindness.\n8. Keep legacy RecipeSpec declared_step implementation only if a non-migrated production consumer remains; otherwise MA27 deletes the test-only legacy assembler with the rest of RecipeSpec.
