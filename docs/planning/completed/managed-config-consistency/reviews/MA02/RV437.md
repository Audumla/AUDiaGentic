# Capability-gateway/registered-handler narrative unsupported by providers_api.py; Notes codify disputed RV406 mandate

## Notes

MA02 is a Block-C item (after MA17). Its narrative depends on a 'capability gateway' that neither the code nor the open RV412 supports. The Notes must be reconciled before implementation begins.

## Findings

1. MA02.md:22 (step 3) and MA02.md:57-58 (Notes) describe 'providers public capability gateway' that 'resolves explicit registered handler. No catalog lookup/dotpath' and codify RV406: 'the sanctioned import is ONE module ... the gateway IS the registry dispatch — no new capability request/result types.' This is contradicted by the implemented `src/audiagentic/components/providers/providers_api.py`, which exposes concrete functions (`model_source_add`, `sync_provider_models`, `describe_provider`, etc.) and contains no generic capability-gateway dispatch. No caller resolves handlers through a gateway; they call named functions.

2. RV412 (state `created`, on MA16) rejects the universal-registry/gateway mandate and recommends purpose-built `providers_api` functions — which is what the code already does. MA02's Notes assert the opposite as settled. MA02 therefore describes an architecture the program has not built and that the active review disputes.

3. MA02 step 10 tests 'catalog non-authority' and 'explicit registration' but the actual integration surface has neither a catalog nor an explicit-registration gateway for memory operations — only direct `providers_api` function calls. The validation criteria assume a gateway mechanism that does not exist.

## Conclusion

DISSOLVED by RV412 ratification (2026-07-15). MA02 notes/steps corrected: memory calls purpose-built providers_api functions per operation family (not a universal 'gateway resolves registered handler'); the disputed RV406 universalization is withdrawn. Matches the concrete providers_api surface. Step 3 reworded.
