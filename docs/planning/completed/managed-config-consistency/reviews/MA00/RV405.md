# Codify the platform-component layer rule (RV404 consequence) and sweep stale gateway wording

## Notes

T3 assessment of the RV400-RV404 chain: APPROVED as correct. Rationale recorded for the program: foundation types for capabilities HID a real one-way dependency (requester→providers) instead of removing it; harmful coupling is only reverse imports, deep imports, requester branching, and un-prunable residue — all preserved as guards under the providers-public-API model. The missing piece is codification: the layer rule exists only in closed reviews and a doc banner, so future agents/audits will re-flag sanctioned requester→providers-public-API imports as leakage.

## Findings

WORK ITEMS (implementing agent):
1. ARCHITECTURE STANDARDS — add the layer rule as a standards section: (a) `providers` is a PLATFORM COMPONENT: domain-specific (external tool integration) but positioned BELOW requester components in the dependency order, like foundation; dependency arrows only point downward. (b) Requester components (memory, coding-lsp, runtime bootstrap, release, …) may import ONLY the designated providers public API module — never adapters, services internals, serializers, capability config, or handlers. (c) Providers imports zero requester domains; handlers are requester-blind. (d) Runtime automation authority = explicit composition-root registration ONLY; descriptive capability catalog is soft config (documentation/planning/MA19 views) and can never enable a handler. (e) Foundation placement discriminator: a type belongs in foundation only if its definition contains no provider-domain concepts AND a non-provider-managing component consumes it. Capability request/result fails this test (providers-owned); the agent execution port PASSES it — protocol lives in foundation/execution beside the frozen event contract, providers implements, composition injects into agents so the agents gateway never imports providers.
2. GUARDS — add/adjust architecture tests: requester→providers imports restricted to the single public API module path (allowlist); providers→requester-domain imports zero; no foundation module contains capability vocabulary after foundation/capability_catalog deletion; agents component imports no providers module (execution port arrives via composition).
3. STALE WORDING SWEEP (each via its own item note update): MA02 — 'components submit requests through foundation gateway' becomes 'through the providers public capability API'; foundation owns no capability schema/gateway (steps 2/7 wording). MA08 — gateway references likewise. MO02 — 'MA17 provider capability gateway' remains correct as a providers service; clarify catalog is not runtime authority. MA09 — gate wording 'requesters have zero direct imports/calls to provider handlers' gains the explicit carve-out: the single public API module is the sanctioned edge; everything else stays forbidden. MA16/MA17 already updated through RV404 — verify their notes name the providers public API module once it exists.
4. MA00 — update consolidation doctrine with the layer rule + foundation-placement discriminator; refresh critical path (MA16 re-scoped: rich provider-owned descriptive config + minimal projection; MA17: explicit composition); record RV400-404 in the progress log.
5. EXECUTION PORT — confirm with its actual consumer (agents gateway) per RV404: implement the port protocol in foundation/execution (neutral: invocation in, frozen-contract events out, cancel signal) when MA17 reaches Steps 7-9; do NOT create foundation/ports or bundle capability types with it.

## Conclusion

RV400-404 direction approved. The boundary was correct; its location was wrong — visible narrow requester→providers dependency beats a laundered foundation edge. Codify the layer rule + guards + wording sweep so audits and future agents enforce the new shape instead of re-litigating it.
