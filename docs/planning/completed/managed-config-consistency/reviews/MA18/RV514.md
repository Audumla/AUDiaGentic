# Define ACP capabilities through generic evidence and runtime declarations, not provider heuristics

## Notes



## Findings

['ACP registry entries and provider docs are evidence only; they must not directly authorize runtime behavior.', 'Generic ACP/session capability code must not branch on provider names or encode provider-specific executable, adapter, or native-control behavior.', 'Provider-specific launch commands, environment shaping, adapter packages, native control methods, and session id translation belong in provider descriptors, provider adapters, or explicitly registered handlers.', 'The capability model needs distinct layers: provider capability facts, ACP launch/runtime declaration, foundation event transport, agent/session orchestration, and provider-native live control.', 'Persisted ACP resume is separate from live attach, concurrent clients, active-turn steering, interruption, and out-of-band injection.', 'Missing or unverified capabilities should default to unknown/unsupported, never to assumed support based on provider identity.']

## Conclusion

Use docs/reference/ACP_CAPABILITY_ANALYSIS.md as source evidence, but define implementation around typed capability predicates and runtime probes. The next implementation slice should add schema/tests that enforce generic capability-driven behavior before any provider opts in.
