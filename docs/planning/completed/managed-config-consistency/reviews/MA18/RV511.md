# Gateway cannot execute any task longer than 300s: the worker is a daemon thread in the caller's process, so work is abandoned the moment the caller stops waiting

## Notes

Found while attempting to actually delegate a plan item to the opencode agent (CC41 Activity 5). This is the concrete blocker for using the gateway to coordinate implementation work, and it explains the 3-day orphaned ma18-rv358-worker request. Diagnosed from the gateway's own timeline.ndjson, which turns out to hold the evidence the status API does not surface.

## Findings

['THE MECHANISM, confirmed in code: agents_gateway_api.py line 23 creates a MODULE-LEVEL in-process singleton `_QUEUE_MANAGER = queue_mod.GatewayQueueManager()`. agents_gateway_queue.py line 291-294 dispatches each request on a `threading.Thread(..., daemon=True)`. Daemon threads are killed immediately at interpreter exit with no cleanup. agents_gateway_api.py line 21 caps the blocking wait at `MAX_BLOCKING_TIMEOUT_SECONDS = 300.0`.', 'CONSEQUENCE: any request whose work exceeds the caller\'s wait is abandoned mid-flight. run_llm_request enqueues, the daemon thread starts the attempt, the caller\'s wait expires at <=300s and returns state=running, the caller exits, the daemon thread dies, and the record is frozen at running forever. This is a hard ceiling: >300s work CANNOT complete through the blocking path regardless of the task.', 'TIMELINE PROVES IT. A successful short request (req_1ff1f472630e4cce) emits: request.created, queue.queued, state.changed, queue.started, attempt.started, attempt.recorded, state.changed, queue.finished. BOTH orphans (req_928141cc9d434b24 from 2026-07-13, and req_f9d054fad8994d8d which I dispatched today) emit an IDENTICAL prefix up to attempt.started and then STOP -- no attempt.recorded, no queue.finished. They started work and were killed mid-attempt.', 'THIS EXPLAINS THE 3-DAY GHOST. req_928141cc9d434b24 was an MA18 worker task (\'Implement only RV358 slim baseline...\') with timeout 300s. Its timeline shows attempt.started at 2026-07-13T11:53:52 and nothing after. It was not a mystery hang: it ran, the caller gave up at the 300s cap, and the daemon thread died with the process.', 'THE STATUS API MISLEADS. The persisted record shows `attempts: []` while running, because the attempts list is only populated on attempt.recorded (terminal). So a running request is indistinguishable from a never-started one via agent_llm_status / gateway_overview. I read `attempts: 0` and wrongly concluded \'it never started\' -- the timeline said otherwise. Any operator will make the same mistake.', 'THE OBSERVABILITY ALREADY EXISTS AND IS GOOD. timeline.ndjson per request already records queue.queued, queue.started, attempt.started, attempt.recorded, queue.finished, state.changed with timestamps, provider-id, model-id, attempt-index and correlation-id. It is simply not surfaced through the status/overview API, where it would immediately answer \'is this working or stuck?\'.', 'reconcile_gateway_state exists and correctly resolves orphans (running -> failed, INT-AGW-ORPHANED, idempotent, verified). NOTHING CALLS IT. It sat unused for 3 days while the overview reported a phantom running request.']

## Conclusion

Ownership assigned for implementation: SH04 establishes a standalone control-plane lifetime so MCP submitter exit cannot kill active work; SH07 implements durable admission/recovery, active-attempt/timeline status visibility, and ownership-aware reconciliation. The 300-second limit is now an MCP transport bound rather than a universal core-API cap, but daemon workers remain unsafe until SH04. Keep this review active until SH04/SH07 acceptance gates demonstrate the replacement; do not close merely because the cap moved.
