# Recipe system already exists; fleshed out with concrete evidence-backed scope

## Notes

Major finding: MA35's premise that the recipe schema needs to be 'defined' is stale -- it already exists and is already in production for 7 providers. base_runner.py's execution: block (provider descriptor field, AR12) already implements exactly what step 1 describes: mode, executable, aliases, args-template with {prompt}/{approval-flags}/{model-flags} expansion, model-flag, approval-mode-flags, error-code, extractor-name. services/execution.py's _load_runner already prefers an adapter.py module and falls back to make_runner_from_execution() when absent -- this IS the generic resolver step 2 asks for.

Surveyed all 18 provider adapter dirs: aider, antigravity, continue, goose, openhands, plandex, roo (7) are already pure recipe-driven with no adapter.py at all. claude, cline, codex, gemini, local_openai, opencode (6) have genuinely custom adapter.py (OpenCode's is a custom NDJSON event-extractor mapping; verified in adapter.py -- schema has no way to express custom parsing, only extractor-name selection from pre-registered classes).

pi, qwen, copilot (3) declare BOTH an execution: block AND a hand-written adapter.py -- adapter.py always wins per precedence, so the execution: block is unreachable. Diffed each:
- qwen.yaml's execution: block is byte-for-byte semantically equivalent to adapters/qwen/adapter.py's run() (same executable/alias, error-code, extractor-name, args-template order, model-flag, approval-mode-flags mapping) -- confirmed pure dead duplication.
- copilot.yaml's execution: block is likewise byte-for-byte equivalent to adapters/copilot/adapter.py's run() (identical args-template literal to the hand-built command list).
- pi.yaml's execution: block is NOT equivalent and is dangerous if ever reached: it puts {prompt} in args-template as a CLI argument, but adapters/pi/adapter.py exists specifically because Pi's --print mode loses embedded newlines when the prompt is a CLI arg (SH21) -- the real fix pipes the prompt via stdin (run_streaming_command input_text=). The declared recipe would silently reintroduce the SH21 bug if adapter.py were ever removed without extending the schema first.

tests/integration/providers/test_qwen.py and test_copilot.py both import and call adapter.run() directly (monkeypatching adapter.require_executable/run_streaming_command) -- deleting the adapter.py files requires rewriting these two tests to exercise the generic dispatch path (make_runner_from_execution via services/execution.py) instead, not just deleting the adapter files. Scoped but not done -- test rewrite is real work, not mechanical.

Also directly relevant: HA03 (this session, separate item) built an analogous but distinct declarative-adjacent system for interactive TUI launch (components/providers/adapters/{pi,opencode}/interactive.py) as hand-written Python, explicitly because Pi's interactive flag construction has cascading conditional logic (tools_cfg fallback chain, nested sandbox/lockdown toggles) that the current flat args-template schema cannot express. Any future recipe-schema extension work should design for both one-shot execution AND interactive launch together to avoid a third divergent config format.
