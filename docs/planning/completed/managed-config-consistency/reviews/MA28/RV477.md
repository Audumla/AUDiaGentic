# manage_language_servers bypasses automation registry — direct providers_api dispatch contradicts MA20 design

## Notes

ASSESSED 2026-07-16 by claude. Premise does not hold — closing.

This review states that manage_language_servers bypassing the automation registry 'contradicts MA20 design'. It does not. MA20 step 8 explicitly permits it: 'Descriptor-backed generic capabilities need no requester-specific registration.' MA28 is a Pattern B family (opencode, codex and qwen drive language_servers_config through one identical mechanism with no per-provider behaviour), so a registry handler would add indirection with no per-provider code to bind. The same reasoning clears manage_mcp_entries (MA23) and manage_plugin_entry (MA25), which this review also flags.

The review's observation that these families 'check automation_capability() at call time rather than using pre-validated registry registration' is correct as fact but is the intended Pattern B behaviour, not a defect: the capability check IS the Pattern B gate. See RV485 for the full resolution.

ONE VALID RESIDUE, carried elsewhere: manage_lsp_mcp_projection (MA29) does NOT perform that call-time capability check — it gates on the raw receive_lsp_mcp boolean instead — so it is the one family genuinely failing the Pattern B contract this review assumes. That is tracked as RV501 on MA29 and is being fixed there.

## Findings

['manage_language_servers (language_server_family.py) bypasses ProviderAutomationRegistry — dispatches directly from providers_api', 'manage_mcp_entries (managed_mcp_family.py) bypasses ProviderAutomationRegistry — calls sync_managed_provider_mcp_scope directly', 'manage_plugin_entry (plugin_entries.py) bypasses ProviderAutomationRegistry — reads descriptor/plugin_config directly', 'All three check automation_capability() at call time rather than using pre-validated registry registration', 'providers_api does not route through ProviderAutomationRegistry for these families']

## Conclusion

manage_language_servers in language_server_family.py does not use the automation registry — it dispatches directly through providers_api without going through ProviderAutomationRegistry.dispatch(). MA28 validation requires 'No reverse/direct internal imports' and the handler should be registered through MA20. Additionally, manage_mcp_entries (MA23) and manage_plugin_entry (MA25) have the same pattern: they check automation_capability() at call time rather than being pre-validated through registry registration.
