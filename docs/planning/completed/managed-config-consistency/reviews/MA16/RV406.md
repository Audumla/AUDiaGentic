# Unify all provider operations under existing recipe pattern — no new gateway needed

## Notes

ADDENDUM TO RULING (claude, 2026-07-14, user clarification): the mandatory amendment means ONE dispatch pattern (registry) + ONE common requester-intent declaration format shared by memory/coding-LSP/model-projection, and the hindsight matrix file is RETIRED — but matrix content DECOMPOSES three ways rather than converting wholesale to config recipes: (1) requester INTENT → the common declaration format (target provider, capability kind, payload values, ownership scope, evidence link) — owned per requester; (2) PROVIDER mechanics (config paths/serialization/entry shapes) → provider-owned recipes built from provider descriptors, parameterized by requester payload — once built, any requester (e.g. a second memory library) reuses them; (3) BACKEND mechanics (Hindsight curl installers, ~/.hindsight/* artifacts) → memory-owned recipes that STAY imperative code/steps with third-party gates (pinned version/hash, idempotence, atomic restore) — do not force behavior into YAML (SL15 lesson). Rule of thumb: declarative where content is FACTS (intent/payloads/targets); code where content is BEHAVIOR (installers/serializers). Migration is MA02 Block C2, one capability kind at a time; matrix rows are deleted only when their decomposed replacement proves parity against .audiagentic/evidence/MA02_step1_frozen_behavior_table.md.

## Findings

Current analysis shows that the three future callers of provider operations (MA02 memory, MA08 coding-LSP, MO02 model projection) are all doing the same thing: **configure a provider's X capability**. They share one pattern: requester has a desired state, provider knows how to write it, operation is install/configure/prune/status.

**Memory (MA02) already works this way:**
- Declares operations in YAML matrix (`HINDSIGHT_RECIPE_MATRIX` from `config/components/memory/hindsight_matrix.yaml`)
- Builds recipes from matrix rows at call time
- Registers them in a fresh `ProviderRecipeRegistry()` per invocation
- Dispatches via `registry.install/uninstall/prune` keyed by `(provider_id, capability_id)`
- Registry lifecycle: probe → install → configure → verify (or prune → uninstall)
- **Evidence it works**: live in production; MA02 already migrated to this pattern (RV404)

**LSP (MA08) does the same imperatively — different code, same operation:**
- Currently calls provider adapter writers/removers directly (e.g. `spec.writer`, `lsp_projection`)
- Has no recipe matrix — knowledge is encoded in Python code paths that call providers internals directly
- MA08's desired outcome: "submit a capability request, get ownership-safe result" — that's exactly what `registry.install/uninstall` does with the probe→ops→verify pipeline and `ProviderRecipeResult`
- **Justification for recipe pattern**: LSP currently imports provider adapter internals (writers/removers), which is precisely the coupling MA16 aims to eliminate. The recipe contract abstracts away "how" — LSP just calls `registry.install()`, the recipe handles provider-specific mechanics.

**Model projection (MO02) does the same imperatively — different code, same operation:**
- Currently calls `providers_api.model_source_add/update/remove` → `_mutate_model_sources` → writes YAML, syncs provider configs
- Has explicit recipe-like logic already: dry_run validates + computes diff; apply=True atomically writes; reconcile applies provider-specific config
- The recipe contract already has `dry_run`, `provision`, `teardown` — this maps directly to MO02's existing three-phase flow
- **Justification for recipe pattern**: `ProviderRecipeKind.MODEL_CONFIG` already exists in the enum. No new taxonomy needed.

**The existing infrastructure provides everything MA16/MA17 need — reasoning for each:**

| Need | Exists | Justification |
|------|--------|---------------|
| Explicit handler registration | `registry.register()` + `.get()` | Memory already does this. Two-consumer rule satisfied (memory + LSP). |
| Typed protocol | `ProviderCapabilityRecipe` abstract class | Provides probe/install/configure/verify/uninstall/prune. No duck-typing in the contract itself — recipes subclass a real type. |
| Closed-set vocabulary | `ProviderRecipeKind` enum | 13 kinds already defined including MODEL_CONFIG, MCP_CONFIG. No new frozensets needed. |
| Result with ownership tracking | `ProviderRecipeResult` | Has success, state, artifacts_owned, action_needed — everything MA08 needs for its adoption/collision semantics. |
| Provenance stamping | `recipe.to_result()` | Stamps source_url/source_date/action_needed once at dispatch boundary (SL11). Prevents duplicate provenance logic in every handler. |
| Config-driven registration | `HINDSIGHT_RECIPE_MATRIX` pattern | YAML → matrix rows → build recipes → register. No Python enums or taxonomies generated. Adding a provider's support for a capability is a config change, not code. |

**What MA16/MA17 currently plan that is unnecessary — with justification:**

- **New dispatch registry**: The existing `ProviderRecipeRegistry` keys by `(provider_id, capability_id, backend_id)` and provides register/get/list_for_provider/list_for_capability. Building a second registry creates two things to maintain and reason about. Doctrine: *two-consumer evidence before generic extraction* — we already have the mechanism with two consumers (memory + LSP).

- **New CapabilityRequest/CapabilityResult types**: The existing request shape maps directly: `(provider_id, capability_id, operation="install")` → `registry.install(provider_id, capability_id)`. Result is `ProviderRecipeResult`. Creating new envelope dataclasses duplicates fields already in the result type and adds a translation layer between them.

- **New gateway module in providers_api.py**: Dispatch is already `registry.get() → recipe.provision/teardown()` with provenance stamping. A gateway function that wraps this adds no behavior — just indirection.

**What changes for MA16:**
- Step 2: Move CapabilityRequest/CapabilityResult into providers_api.py — **remove this step**. The types are absorbed by the existing recipe contract or left as thin wrappers if caller ergonomics require a named envelope. No new dataclass taxonomy.
- Step 3: Implement capability gateway — **simplify to**: expose `ProviderRecipeRegistry` + recipe contract from the public-API module as the sanctioned import. The gateway IS the registry dispatch.
- Delete foundation/capability_catalog as planned (step 4) — this remains correct and is the primary value of MA16. The catalog types are unused scaffolding that duplicates what recipes already do.

**What changes for MA17:**
- Steps 3 (provider-operation gateway): the gateway IS `ProviderRecipeRegistry`. Requesters call registry methods via the public API module.
- Step 7 (composition root registration): each domain loads its recipe matrix at composition time and registers recipes. Memory already does this via `register_hindsight_recipes()`. LSP and model-projection do the same from their own matrices.
- No new handler protocol — `ProviderCapabilityRecipe` is the protocol.

**WHAT REMAINS (unchanged):**
- MA10 keep decision: extract shared recipe orchestration from `ProviderRecipeRegistry.install/uninstall` lifecycle methods only if two current consumers need it (memory already does; LSP would be second).
- Arch guards remain: requester→providers imports restricted to public-API module; zero providers→requester imports; no capability symbols under foundation after deletion.
- Agent execution port remains separate (MA17 steps 7-9, MA18) — that's a different concern (agent launch/transport), not config mutation.

---

**ISSUES AND RISKS REQUIRING DISCUSSION:**

**Issue 1: Hard-coded lifecycle pipeline vs individual operation dispatch.**
`ProviderRecipeRegistry.install()` hard-codes probe→install→configure→verify. Memory needs this full pipeline. But MA08's request shape uses `operation="plan"|"apply"|"prune"|"status"` — these are individual operations, not a composite lifecycle.
- If LSP calls `registry.install()`, it gets four steps it may not want (e.g., "plan" just needs probe). 
- **Memory already has a workaround**: in `_reconcile()`, the prune operation bypasses registry.lifecycle and calls `recipe.prune()` directly — proving there's tension between the composite lifecycle and individual operations.
- **Proposed resolution**: The public API exposes both paths: (a) `registry.install/uninstall` for full lifecycle (memory pattern), (b) thin wrapper functions in providers_api that resolve a recipe and call one method (`plan/probe`, `apply/provision`, etc.) for callers who need individual dispatch. Both go through the same registry — just different entry points.

**Issue 2: backend_id dimension.**
Registry keys by `(provider_id, capability_id, backend_id)` triple. Memory uses backend_id to distinguish multiple Hindsight backends per provider (e.g., different memory server URLs). LSP and model-projection likely don't need this — one LSP config per provider per language.
- **Risk**: If callers pass `None` for backend_id and a recipe also registered with `backend_id=None`, collisions are avoided. But the key scheme encourages multi-tenant registrations that may not be needed.
- **Proposed resolution**: Accept current design — `backend_id=None` is valid and works for single-registration-per-provider cases. Document this as the common case.

**Issue 3: Ephemeral vs persistent registry.**
Memory creates a fresh `ProviderRecipeRegistry()` per call, populates it from its matrix, uses it, discards it. MA17 implies a persistent registry at composition root where all handlers are pre-registered and shared across callers.
- **Ephemeral** (memory pattern): Simple, no lifetime management, each caller owns its registry instance. Trade-off: registration cost per call (matrix loading + recipe building).
- **Persistent** (MA17 pattern): Register once at composition root, share across all callers. Trade-off: global mutable state, lifetime questions, cross-caller coupling.
- **Proposed resolution**: Ephemeral is correct for now. Memory already works this way and it's simpler — no shared mutable state to reason about. If performance becomes an issue (recipe building is slow), persisting registration is a measurable optimization with clear cost-benefit. Do not preemptively optimize.

**Issue 4: Public API ergonomics — do callers import the registry or a function?**
The sanctioned import path should be the one module in providers_api.py. Should it expose `ProviderRecipeRegistry` directly (callers instantiate, populate, dispatch), or wrapper functions (`configure_provider(project_root, provider_id, capability_id, operation="install")`)?
- **Registry direct**: Gives callers full control; matches memory pattern. Verbose — requires importing matrix, building recipes, registering.
- **Wrapper functions**: Simple call for callers who don't need the registry's lifecycle orchestration. Adds a translation layer between request and registry dispatch.
- **Proposed resolution**: Both. The public API module exposes the registry (for callers like memory who want full control) AND thin wrapper functions (`apply_provider_capability(...)`, `probe_provider_capability(...)`) for callers who just want "do X for this provider". The wrappers are 5-line functions: instantiate registry, register from matrix, call one method.

## Conclusion

T3 RULING (claude, 2026-07-14): APPROVED WITH ONE MANDATORY AMENDMENT. Unification accepted: ProviderRecipeRegistry + ProviderCapabilityRecipe are the dispatch mechanism for MA02/MA08/MO02; no new CapabilityRequest/CapabilityResult types, no new gateway module; foundation/capability_catalog deletion stays; ProviderRecipeResult becomes the public envelope (§7 status doctrine simplifies to two levels: StepResult → RecipeState/Result). 

MANDATORY AMENDMENT — MECHANICS OWNERSHIP RULE: the registry is dispatch, but recipe IMPLEMENTATIONS for generic capabilities must be PROVIDER-OWNED, built from provider descriptors (mcp_config/language_servers_config/model_config specs) and parameterized by requester payload. Requester-owned declarative files may contain ONLY intent: target provider, capability, payload values, ownership scope. Test: if a provider path, filename, or command appears in a requester-owned file, it is in the wrong place. Memory's hindsight matrix is grandfathered as migration source only — its provider-mechanics step bodies remain MA02 migration debt, NOT the template for LSP/MO02 to replicate. Without this rule the unification silently reverses MA02's boundary while passing every import guard.

DISCUSSION ITEMS RESOLVED: (1) Both entry points accepted; pin plan/probe as contractually zero-mutation (contract test) and prune as ownership-scoped via artifacts_owned; memory's prune bypass becomes the sanctioned individual-dispatch path. (2) Ephemeral registries accepted; record that the MA17 binding-graph audit shifts to inspecting intent files + public-API call sites (statically checkable). (3) Both surfaces accepted; thin wrappers are the RECOMMENDED standard surface, registry export for full-lifecycle callers; RV405's single sanctioned import-module rule applies unchanged. (4) backend_id=None documented as the common single-registration case — accepted as proposed.
