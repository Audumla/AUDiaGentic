# Separate caller operation semantics from recipe mechanics

## Notes



## Findings

RV412 correctly rejected a universal requester payload and treating ProviderRecipeKind as a capability taxonomy. Its replacement—purpose-built public verbs with no shared semantic operation contract—overcorrects. Existing MA16 request modes (`plan|apply|prune|status`) identify caller intent, while `probe/install/configure/verify/uninstall/prune/dry_run/status` are recipe-internal mechanics. Callers do not choose install versus configure; recipes do. Side-effect freedom and ownership/collision/reload are mode/result guarantees, not operation families. Current registry methods cannot be exposed directly as that contract without an adapter because they hard-code a provisioning flow. Provider knowledge remains soft config and explicit registrations remain runtime authority.

## Conclusion

RATIFIED and incorporated (2026-07-15). RV412 was right to reject a universal requester payload, forcing all operations through current registry lifecycle, and treating ProviderRecipeKind as a capability taxonomy. It over-corrected by denying caller-level common semantics. Canonical model: public provider calls use `plan|apply|prune|status`; payloads/results stay family-specific and consumer-sized; recipes privately choose `probe/install/configure/verify/uninstall/dry_run` mechanics. `plan`/`status` are non-mutating; `prune` removes only owned state; collision/reload/ownership outcomes are result properties, exposed only when consumers need them. ProviderRecipeRegistry remains internal provisioning infrastructure and requires a providers-owned mode adapter where used. Provider facts remain MA19 soft config; explicit registrations remain execution authority. Updated MA00, MA02, MA06, MA08, MA09, MA12, MA16, MA17, MA19, MO02, MO13 and both capability reference documents.
