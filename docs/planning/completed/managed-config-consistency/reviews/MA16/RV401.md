# Separate provider knowledge catalog from runtime contracts

## Notes



## Findings

User ruling: deep provider interrogation and complete capability documentation remain valuable, including a config-owned set of documented capabilities. These facts serve research, planning, generated references, audits, and future work. They must not become a large Python taxonomy, public dataclass graph, enum/frozenset set, or runtime selection contract merely because they exist in provider config. Current MA16 conflates descriptive catalog, evidence model, lifecycle schema, and MA17 runtime dispatch. This caused dependent items to require a speculative immutable CapabilityRecord and pre-resolved capability vocabulary. Re-scope MA16 to rich provider-owned config plus a minimal projection containing only fields an implemented consumer reads. New descriptive capability/state/transport fields must be addable without Python changes. Runtime automation must come from explicit registered handlers/ports and provider-owned validation, not descriptive catalog strings.

## Conclusion

Incorporated across MA16, MA17, MA19, MA00, MA02/06/08/09/10/12/13/18, MO02/03/04/07/13/14, HA01/02, and CC35.
