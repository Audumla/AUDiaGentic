# No filename vs provider_id consistency check in loader

## Notes



## Findings

The loader uses `yaml_path.stem` as the catalog key (line 231), but does NOT validate it matches the
`provider_id` field inside the YAML declaration.

**Example:** File `openai.yaml` declares `provider_id: openai-alt`. The catalog maps under "openai" and the internal value is invisible — no records reference it, so MA17 code that reads provider identity from the catalog key gets "openai".

**Risks:**
- Silent mismatch between file identity and declared identity.
- Provider author changes `provider_id` inside YAML without renaming the file (or vice versa), and the loader doesn't catch it.
- If MA17 ever references the internal `provider_id` (e.g., for error messages), it would be inconsistent with the catalog key.

**Question:** Should the loader validate `raw["provider_id"] == yaml_path.stem` and raise a VAL-CAP error on mismatch?

## Conclusion

Incorporated into reduced config integrity rules: provider identity has one canonical source or explicit consistency validation; it is not duplicated into runtime records.
