# Correct the RV412 ratification: LSP (and model/MCP) ARE config-mutation recipes — function is the entry, not a replacement

## Notes

OPERATION VOCABULARY CLARIFICATION (2026-07-15, user question 'is install=configure, uninstall=prune, verify=status?'): NO — none are equalities. The recipe contract is ONE superset (probe/install/configure/verify/uninstall/prune/dry_run/status); a recipe implements the meaningful subset. Distinctions: install=whole-artifact presence (idempotent, no diff) vs configure=scoped managed-entry diff/merge preserving unmanaged content; uninstall=total removal vs prune=remove-only-this-ownership-scope (multiple requesters may share one provider config file — the reason scopes exist); verify=active check (subprocess, can fail) vs status=passive ownership read, with probe=precondition check as a distinct fourth check-verb; dry_run=shared preview. Provisioning recipes use install/uninstall/verify; config-mutation recipes use configure/prune/status/dry_run. Do NOT call install() on a config-mutation recipe (its default dry_run assumes 'would install'). Recorded canonically in CAPABILITY_OPERATION_SCHEMA.md banner. This is WHY LSP/model/MCP use the config-mutation verbs — it reinforces the RV443 synthesis, does not change it.

## Findings

SYNTHESIS (supersedes the over-corrected RV412 framing; preserves its narrow-valid points):

1. EVERYTHING IS A RECIPE (RV406's instinct was right). Recipes are the universal INTERNAL strategy for provider capability mechanics — install (COMMAND_INSTALLER), MCP (MCP_CONFIG), model (MODEL_CONFIG), LSP (add LSP_CONFIG), hooks, plugins. LSP is a config-mutation recipe exactly like MCP_CONFIG/MODEL_CONFIG. Making LSP a special non-recipe function while MCP/model are recipes would be the inconsistency.

2. TWO OPERATION FAMILIES, ONE CONTRACT. The recipe contract already spans provisioning (install/uninstall/verify) and config-mutation (dry_run/configure/prune/status). A config-mutation recipe is a thin lifecycle/status/dry-run WRAPPER; the actual managed-entry diff/collision/reload lives in the MO06 shared managed-config core (the MODEL_CONFIG pattern). Do NOT force a config-mutation recipe through the provisioning install() convenience path — that, and only that, was RV412's real point.

3. PUBLIC FUNCTION IS THE ENTRY, NOT A REPLACEMENT. providers_api exposes a purpose-built named function per operation family (sync_provider_models exists; add sync_provider_language_servers). UNDERNEATH each function is a recipe dispatched via the registry, which calls the MO06 core. Layering: providers_api.fn → <KIND>_CONFIG recipe (lifecycle/status/dry_run wrapper) → MO06 core (diff/collision). RV412 was right that the public entry is a named function; WRONG that it replaces the recipe.

4. NO FORCED COMMON REQUESTER-INTENT SHAPE. The requester-side DECLARATION differs per consumer (memory intent config vs LSP desired-language-set vs model-sources) — RV412 correct here. That is about requester declarations, not the internal recipe dispatch, which IS shared.

5. OPTIONAL SHARED-CONTRACT ENRICHMENT: ProviderRecipeResult keeps collision/reload in `details` today; promoting `collisions` and `reload_required` to first-class fields benefits MCP/model/LSP alike. Do this once on the shared result, not per-consumer. Low priority; only if a consumer needs structured access.

APPLY: correct MA16/MA08/MO02 notes + schema banner + MA00 + memory to this synthesis. MA08 = add an LSP_CONFIG recipe following the MODEL_CONFIG pattern, exposed via providers_api.sync_provider_language_servers; drop the 'registry is the wrong tool' language.

## Conclusion

LSP IS a recipe (config-mutation kind, MODEL_CONFIG pattern). RV406's 'everything is a recipe' stands; RV412 contributes only: (a) use config-mutation ops not the provisioning install() lifecycle, (b) public entry is a named providers_api function over the recipe, (c) requester declaration shapes may differ. My prior 'purpose-built functions NOT recipes' framing is withdrawn.
