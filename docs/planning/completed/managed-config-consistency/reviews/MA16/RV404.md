# Remove provider capability contracts from foundation entirely

## Notes



## Findings

RV403 still retained CapabilityRequest/CapabilityResult/handler protocol in foundation. These types are not generic: capability_id is defined by provider knowledge; ownership/collision/action-needed semantics describe provider operations; MA17 gateway is a providers service. Creating foundation/ports would invent a new package to hide a legitimate one-way component dependency. Provider capability config, types, loader, gateway, handlers, results, and public API belong to providers. Consumers may depend explicitly on the narrow providers public API, while providers must not import requester domains. Foundation retains no capability concept. Agent execution port ownership is assessed separately by its actual consumer/implementation; it must not be bundled into provider capability catalog.

## Conclusion

Incorporated across MA16, MA17, MA00, MA02, MA06, MA08, MA09, MA18, MA19, MO02, HA01, HA02, and reference warnings. Foundation capability ports are forbidden; providers public API owns the full capability contract.
