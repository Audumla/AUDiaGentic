# Error categorization inconsistency: recipe prefix validation raises VAL-CAP-001 instead of VAL-CAP-002

## Notes



## Findings

In `_resolve_capability` (loader.py:160), a malformed operations value that doesn't start with `recipe:` raises `
_val_cap(1, f"unknown core field 'operations.{op_name}'")`. This is VAL-CAP-001 ("unknown core field"), but the value
is present and correctly placed — it's an invalid format.

**Current behavior:** `install: badvalue` → VAL-CAP-001 (unknown core field)
**Expected behavior:** `install: badvalue` → VAL-CAP-002 (invalid value)

**Impact:** Error messages are misleading to provider authors. They'll see "unknown core field" and think the key is wrong, when actually the value format is wrong.

**Question:** Should malformed recipe refs raise VAL-CAP-002 instead of VAL-CAP-001?

## Conclusion

Superseded as broad recipe-ref catalog validation is no longer runtime contract. Any retained config structural error remains categorized by the thin config loader.
