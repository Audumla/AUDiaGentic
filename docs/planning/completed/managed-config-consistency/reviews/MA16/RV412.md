# Limit ProviderRecipeRegistry to operations matching its lifecycle

## Notes



## Findings

RV406 correctly deleted foundation/capability_catalog, kept capability ownership in providers, and designated providers_api as the public boundary. Its universalization claim is not supported. ProviderRecipeRegistry hard-codes provisioning lifecycle (probe→install→configure→verify; prune→uninstall), keys by provider/capability/backend, silently replaces duplicate keys, accepts Any recipe objects, and returns ProviderRecipeResult without first-class collisions, reload, scoped ownership actions, or planned changes. MA08 LSP reconciliation and MO02 model projection have managed-entry/diff semantics, not proven provisioning semantics. ProviderRecipeKind is an existing recipe behavior enum; treating it as the complete capability universe recreates the closed taxonomy rejected by RV401. A single public module does not require a single dispatch protocol. Use existing registry only where current lifecycle fits; expose purpose-built providers_api functions/results for LSP/model/config operations when simpler. Do not require one common requester-intent declaration shape across unrelated consumers.

## Conclusion

RATIFIED (claude T3, 2026-07-15). RV412 is correct and supersedes RV406 on ONE point only: the universal-ProviderRecipeRegistry / common-requester-intent mandate. My RV406 over-unified — the registry hard-codes a provisioning lifecycle (probe→install→configure→verify; prune→uninstall) that fits MA12 provider-CLI install/uninstall but NOT LSP reconcile or model projection, which have managed-entry/diff/collision/reload semantics. Treating ProviderRecipeKind as the complete capability universe recreates the closed taxonomy RV401 rejected. CORRECTED DIRECTION: providers_api.py is the single sanctioned public boundary (RV405, unchanged), but it exposes PURPOSE-BUILT functions per operation family — provisioning→ProviderRecipeRegistry where lifecycle fits (MA12); LSP→purpose-built sync/diff function with collision/reload semantics (MA08 builds it, none exists yet); model projection→existing model_source_*/sync_provider_models (already correct); memory config/hooks/plugin→purpose-built functions (MA02). 'A single public module does not require a single dispatch protocol.' No common requester-intent declaration shape forced across unrelated consumers. PRESERVED from RV406 (unchanged): foundation/capability_catalog deletion; provider ownership of capability knowledge; mechanics ownership (provider recipes built from descriptors); the sanctioned providers_api edge; facts-are-declared/behavior-is-coded. This ratification dissolves RV436/437/438/439/440 (all trace to the universal-registry overclaim). Consequent note corrections applied to MA16/MA08/MA02/MO02 and the schema-doc banner.
