# Modes default to supported when absent — opt-out vs opt-in

## Notes



## Findings

When modes is missing from YAML, `_resolve_modes(raw.get("modes", {}))` applies ModeDeclaration defaults:
plan=apply=status="supported", prune="not-applicable".

**Impact:** A capability that declares no modes silently supports plan/apply/status — even if the provider hasn't implemented handlers for them. This is an opt-out model (assume supported unless declared otherwise).

**Risk:** Provider forgets to declare modes, capability loads successfully with "supported" defaults, and at runtime MA17 dispatches to a missing handler.

**Alternative (opt-in):** Default all modes to "unsupported"; provider must explicitly declare which modes it supports. This is safer but adds boilerplate for common cases.

**Question:** Should the default be opt-out (current: supported) or opt-in (unsupported unless declared)?

## Conclusion

Superseded by explicit registration authority. Missing descriptive modes cannot imply executable support; absent handler/port means unavailable.
