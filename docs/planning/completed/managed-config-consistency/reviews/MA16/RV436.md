# Notes/state misrepresent implemented API; claim validation 'satisfied' while RV412 is open and ⚠️ violations remain

## Notes

MA16 is the linchpin item (foundation capability deletion + providers public-API establishment). Its Notes and validation status are out of step with both the open review on it (RV412) and the actual delivered code.

## Findings

1. MA16.md:56 ('RV406 IMPLEMENTED') states the gateway IS `ProviderRecipeRegistry` and 'no new request/result types or gateway module'. MA16.md:62 claims 'Validation satisfied now' with all 9 criteria — yet marks criteria 4 and 5 as ⚠️ ('allowlist passes for known violations (MA08/MA02/MO02 to resolve)', 'zero reverse imports tracked (MA02/MA08/MO02 to resolve)'). A pending item cannot assert full validation satisfaction while admitting tracked open violations.

2. RV412 (review-of MA16, state `created`) disputes the central premise: `ProviderRecipeRegistry` is lifecycle-bound to provisioning (probe→install→configure→verify→uninstall) and is unsuitable as a universal dispatch for LSP/model/config operations. RV412 recommends purpose-built `providers_api` functions for those consumers. RV412 is unresolved, so MA16's universal-registry premise is not accepted.

3. The implemented `src/audiagentic/components/providers/providers_api.py` already follows RV412, not MA16's Notes: it exposes purpose-built functions `describe_provider` (lines 241-297), `model_source_add/update/remove/set_enabled` (lines 413-494), `sync_provider_models`, `apply_provider_surfaces`, `prune_provider_surfaces`, etc., alongside the recipe-contract re-exports. There is no single 'gateway' dispatch. So the Notes ('no new request/result types or gateway module') misdescribe the delivered surface, which is a concrete dual API.

4. arch §18.3 (ARCHITECTURE_STANDARDS.md:377-384) mandates `registry.register(recipe)` at composition root as the *sole* automation authority. The model-source/surfaces/interrogation functions in providers_api.py use concrete internal service calls, not recipe registration — so the code does not satisfy §18.3 either. This is the exact tension RV412/RV414 raise; it is unresolved.

## Conclusion

DISSOLVED by RV412 ratification (2026-07-15). The 'validation satisfied while registry-universalization open' contradiction is gone: MA16 notes now state the corrected direction (purpose-built providers_api functions per operation family; registry only where provisioning fits) which matches the implemented code. The ⚠️ validation items (pre-existing import violations) are legitimately tracked by owning items and gated by MA09. Notes no longer overclaim.
