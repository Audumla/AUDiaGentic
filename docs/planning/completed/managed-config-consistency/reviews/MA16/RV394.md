# T3 RULING: simplify capability schema module to load-time string validation (Option 2)

## Notes

User queried the implementing agent's capability_catalog build; agent self-reported 17+ enum classes with parallel frozensets and display dicts (each value appearing 3-4×) and proposed either keeping enums or simplifying to load-time-validated strings. T3 review of src/audiagentic/foundation/capability_catalog/schema.py (309 lines) confirms the triplication — including TRANSPORT_KINDS literally defined TWICE in the same module (lines 61 and 70), proof the duplication hazard is real. RULING: Option 2 (strings + load-time validation) is APPROVED. Rationale: (a) §2 config-over-code — identical to the event-topic registry precedent (dotted strings validated at load with canonical errors, no enum per topic); (b) the approved spec's own validation policy (§5, VAL-CAP-002) places enforcement at load time — enum classes re-enforce the same closed set at code level and add nothing the loader doesn't already guarantee; (c) the schema-review gate for new kinds is POLICY (a review + one entry in the validation set), not a Python type system obligation — 'kind names WHAT, never HOW' does not require a Python class per WHAT; (d) MA17's consumer contract (CAPABILITY_GATEWAY_EXECUTION_DESIGN.md) needs an immutable record with comparable string fields for lookup/filter/short-circuit — nothing downstream consumes enum identity. The MA17 design spec is unaffected by this ruling.

## Findings

REFACTOR SPEC (implementing agent):
1. ONE DEFINITION PER VOCABULARY: each closed set (kinds, support states, evidence-review states, operations, modes, request modes, surface/ownership/reload/dry-run/secrets values, transport kinds/session/events/cancel/permissions/launch-class/state) is defined EXACTLY ONCE as a module-level frozenset in schema.py. Delete the duplicate TRANSPORT_KINDS definition. Delete all Enum classes (CapabilityKind, SupportState, EvidenceReviewState, and the ~15 others).
2. RECORD FIELDS BECOME str: CapabilityRecord.kind: str, support: str, etc.; TransportManifestation fields likewise. Dataclasses stay frozen/immutable. OPTIONAL (recommended): define typing.Literal aliases (e.g. SupportState = Literal["supported", "manual", "blocked", "unsupported", "unverified"]) for signature-level static typing — zero runtime cost — plus ONE parity test per alias asserting set(get_args(Alias)) == FROZENSET so the alias can never drift from the validation set. If that parity harness feels heavy, plain str fields are acceptable; do not reintroduce enums.
3. LOADER IS THE SOLE ENFORCER: strict load validates every enum-like field against its frozenset and raises VAL-CAP-002 naming field, offending value, and allowed set. No downstream code re-validates; consumers compare strings.
4. DISPLAY DICT: CAPABILITY_KINDS_DISPLAY is agent-facing manifestation material — per the RV367 split it belongs to MA19's generated views, not the foundation contract module. Either move it to the MA19 side now or, if something already consumes it, keep it as pure data WITH a parity test (keys == CAPABILITY_KINDS) and a comment marking it MA19-bound. It must not remain a third hand-maintained copy without a drift guard.
5. GUARDS/TESTS to add or keep green: (a) no duplicate module-level vocabulary names (the TRANSPORT_KINDS bug class); (b) loader rejects an unknown kind/support/mode value with VAL-CAP-002; (c) Literal/frozenset parity tests if aliases used; (d) display-dict parity if retained; (e) existing tests/unit/foundation/test_capability_catalog.py updated — net LOC should drop substantially.
6. DOC NOTE: append one line to CAPABILITY_OPERATION_SCHEMA.md §9 (Resolved decisions): 'Vocabularies are closed sets validated at load time (VAL-CAP-002); Python representation is plain strings (optional Literal aliases), never enum classes — one definition per vocabulary.'
7. COMPLETION: run tests/unit/foundation/test_capability_catalog.py + full tests/unit (0 failures), record ledger event (plan-item-ids ['MA16'], change-class refactor) summarizing the simplification and LOC delta, close this review, and note the ruling incorporation in MA16's notes. MA17 consumers need no change — verify the immutable-record handoff fields (capability id, support/evidence state, ordered transports, binding id) still expose exactly what CAPABILITY_GATEWAY_EXECUTION_DESIGN.md §2-§4 consumes.

## Conclusion

Approved: config-over-code strings with single-source frozensets and load-time VAL-CAP-002 enforcement; enums removed. New kinds enter by schema review expanding the validation set — policy gate, not type gate.
