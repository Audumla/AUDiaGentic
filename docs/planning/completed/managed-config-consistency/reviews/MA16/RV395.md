# Core-key derivation implicit from dataclass fields

## Notes



## Findings

Core-key frozensets (e.g. _CAPABILITY_CORE_KEYS) are derived from `dataclasses.fields(CapabilityRecord)` via `_core_keys()`. This keeps them in sync automatically, but means unknown-key validation is an implicit consequence of dataclass structure rather than an explicit declaration.

**Risks:**
- A new dataclass field becomes an allowed YAML key automatically — even if the resolve function doesn't read it.
- Renaming a dataclass field silently changes the allowed YAML vocabulary without any diff visible in the loader code.
- The foundation contract is implicitly defined by two coupled artifacts (dataclass + validate against that same dataclass) rather than one explicit source.

**Question:** Should core-key frozensets be explicitly declared (with a sync test that compares against dataclass fields), or is derivation sufficient given that dataclasses are frozen and only MA16/MA19 can touch them?

## Conclusion

Superseded by RV401. Rich catalog no longer derives allowed vocabulary from runtime dataclasses. Minimal runtime types include only consumed fields.
