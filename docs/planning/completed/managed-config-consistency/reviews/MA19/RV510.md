# CORRECTED: capability_id vs family_id is not duplication — MA19 already locks the separation and already permits the linkage

## Notes

CORRECTED AND CLOSED 2026-07-16 by claude (author). I filed this as a finding; MA19 already resolves it. Recording the correction rather than leaving a review that implies an open problem.

WHAT MA19 ALREADY SAYS — this is settled, locked text, not an oversight:
• Description: 'MA19 uses one reusable, typed capability_facts/evidence shape for an open but curated evidence catalogue. MA20 separately enumerates executable automation capabilities. ... Facts may reference recipe ids/families for documentation but cannot satisfy RecipeDefinition, register implementations, select transports, or enable automation.'
• Step 4: 'capability_id is an open stable provider evidence id, not a closed global taxonomy or executable capability enum. It must be unique within a provider and identify one declared descriptor subject/member or documented external:<subject>.'
• Step 6: 'Enforce MA19/MA20 separation. MA20 automation_capabilities explicitly enumerate provider-supported executable family ids, modes, ownership requirements, and typed contract refs. MA19 capability_facts may describe those families and their evidence, but cannot declare a family, add a mode, provide a contract, or select execution.'
• Notes, LOCKED MA19/MA20 ANSWER: 'MA20 ... declarations are the only capability list that participates in family selection, modes, contracts, or registration. MA19 records an open, curated evidence catalogue. Its stable capability ids identify evidence claims ... they are not a global enum and cannot execute.'

SO THE TWO NAMESPACES ARE INTENTIONAL AND CORRECTLY SEPARATED: capability_id identifies an EVIDENCE CLAIM about a descriptor SUBJECT; family_id identifies an EXECUTABLE CONTRACT. They look parallel because they describe the same surfaces from two angles, which is the design, not drift.

MY 'RECOMMENDATION' WAS ALSO ALREADY SANCTIONED: I proposed adding an optional family reference to capability facts. MA19's description ALREADY permits exactly that — 'Facts may reference recipe ids/families for documentation'. It is an allowance that simply is not populated yet, and populating the catalogue is already MA19's stated remaining work ('populate and verify the locked catalogue provider-by-provider'). Nothing new to decide.

WHAT SURVIVES, and it belongs to MA20 not MA19: recipe_id is exactly f'{provider_id}.{family_id}' in 24/24 registrations and is not the registration key (that is the (provider_id, family_id) tuple); recipe_version is '1' across all 24, never varying. Both are deliberate per MA20 step 3/step 8 (recipe_id is knowingly 'diagnostic identity'; recipe_version is reserved for contract evolution), so this is an observation for the envelope owner, not a defect. Carried as a note on MA20 rather than an open review.

FAMILYPIN IS EXONERATED (unchanged from the original finding, and worth keeping on record): its fields are a strict SUBSET of RecipeDefinition's. It invents zero identifiers, deleted four duplicated modules, and added no concept.
