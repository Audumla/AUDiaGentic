# MA19 non-gating status correct but step 3 evidence promotion needs concrete criteria to prevent indefinite quarantine

## Notes



## Findings

MA19's objective to maintain provider capability knowledge and evidence is correct — all capability concepts belong to providers, not foundation. Step 3 defines 'evidence promotion/quarantine process for soft claims' with 'fact-specific anchors required.' However, the process lacks concrete criteria: what constitutes a fact-specific anchor? A help output? An installed version's file listing? A successful execution run? Without specific criteria, evidence remains perpetually in quarantine and MA19 cannot support downstream items (MO03/MO04/MO13/MO14) that need to classify providers as verified vs blocked. Also, step 2 states 'Do not generate Python enums, Literal aliases, frozensets' from the capability-id set — but MA16's RV406 codification already established this rule. MA19 should reference arch §18 and the RV405/RV406 decision rather than restating it.

## Conclusion

INCORPORATED (2026-07-15): MA19 step 3 now defines concrete evidence-sufficiency Tiers (1 installed-artifact round-trip → verified; 2 help/version → existence only; 3 execution proof → transport claims; insufficient anchors stay quarantined) so MO03/04/13/14 classify deterministically. Step 2 now references arch §18 instead of restating the no-codegen rule.
