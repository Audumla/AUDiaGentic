## Conclusion

Decide the order before MA26 implements. Recommended: finish CC41 Activities 4, 5 and 6 first, then have MA26 express the Codex lifecycle as a packaged YAML recipe plus a small Hindsight parameter mapper, exactly as CC41 step 5.8 and MA20's RV493 note describe. That way the Codex/Pi mechanics land as config once, rather than as typed Python recipe classes that CC41's cutover would then rewrite. CC41's remaining work is bounded (dry_run, a catalogue module, a handler factory, and their tests) and MA26 is a complex senior item, so paying CC41 down first is the cheaper order. If the program instead wants MA26 to land sooner, accept explicitly that MA26 writes Python recipes and that a later CC41 migration will replace them, and record that so nobody treats the Python recipes as the target state. Either way, confirm the download mechanic against the schema before committing MA26 to the config route — that is the single expressibility risk. NOTE: this does NOT extend to MA20 RecipeDefinition. CC41 config carries lifecycle mechanics only; the family pin stays in code because register()'s VAL-PREC-009 check validates provider declarations against it (see corrected RV495). Do not read 'CC41 enables config-driven recipes' as 'family definitions can move to config'.
