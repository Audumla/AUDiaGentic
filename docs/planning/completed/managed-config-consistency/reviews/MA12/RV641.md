# MA12 follow-up: the StateMachine-based provider CLI workflow engine survives despite being on MA12's delete list — decide keep-as-engine or collapse

## Notes

Deep-dive 2026-07-18 follow-up to closed RV603 (whose provision_all/repair finding stands separately). Filed fresh because RV603 was closed before this was found.

## Findings

providers/workflow/provider_cli.py — the foundation StateMachine/ItemView-driven install/uninstall workflow — is still the live engine underneath the CLI family: install_provider_cli and uninstall_provider_cli execute through workflow_provider_cli_run (services/lifecycle.py:161, :206), and commands/provider_prompt.py imports its mode mapper. MA12's file list declared '[DELETE] … provider_cli.py when unused' and step 6 targeted the 'private workflow state machine', but it never became unused — it is load-bearing. Two coherent resolutions: (a) accept it as the family's internal engine — update MA12's record (or a successor note) to remove the delete claim, and it stays; or (b) collapse it into the descriptor-recipe/foundation.steps machinery the other automation families use, deleting the StateMachine layer. Option (a) is cheaper and the engine works; option (b) buys one fewer execution model in providers. Either is defensible — the current state (declared deleted, actually essential) is the only wrong one, because the next cleanup agent may delete it on the strength of the item record.

## Conclusion

Small decision, real risk if left ambiguous. Recommend (a) unless CC41's shared declarative recipe loader work naturally absorbs it, in which case fold (b) into CC41's scope.
