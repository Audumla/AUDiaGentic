# MA12 residue: dead provision_all action dispatch and repair path survive deletion step; plan/status state semantics diverge; ValueError at public contract

## Notes

T3 review of the CLI automation family: contracts/cli_lifecycle.py, services/cli_lifecycle_handler.py, services/lifecycle.py, providers_api.manage_cli_lifecycle and its MCP/command callers. The family migration itself is real: providers-MCP and provider_prompt route through one providers_api.manage_cli_lifecycle with semantic-only CliLifecycleResult, and mapping serialization is confined to the MCP boundary as claimed.

## Findings

1) DELETION STEP INCOMPLETE: provision_all_provider_clis (services/lifecycle.py:285) has no production caller — only tests/unit/providers/test_provisioning.py references it — and it is exactly the action-string dispatch table ({'install','uninstall','repair'} → mechanic-named functions) that MA12 step 6 and validation claims 5/7 say were removed. repair_provider_cli (lifecycle.py:235) is reachable only through that dead function; its semantics (probe, install-if-absent) are already what _do_apply does, so it is a duplicate of apply retained under a mechanic name. Delete provision_all_provider_clis, repair_provider_cli, and their orphan test, or record the concrete caller that still needs them. ADDENDUM 2026-07-18 (deep-dive): the 'private workflow state machine' MA12 step 6 also targeted is still the LIVE engine — providers/workflow/provider_cli.py (foundation StateMachine/ItemView based, with plan/run/supports functions) remains what install_provider_cli/uninstall_provider_cli execute through (lifecycle.py:15-16,161,206), and MA12's own file list said '[DELETE] … provider_cli.py when unused'. Since the CLI family reduced the public surface to plan/apply/prune/status, decide explicitly: either the StateMachine workflow is the intended internal engine (then remove it from MA12's delete list and say so in the item), or it should collapse into the recipe/steps machinery the other families use — but the current state (declared deleted, actually load-bearing) is the worst of both. 2) PLAN/STATUS INCONSISTENCY: for an absent CLI, _do_status returns state='uninstalled' but _do_plan returns state='skipped' with changed=False (cli_lifecycle_handler.py:70), so plan cannot express that apply would install — a plan mode that never predicts change fails the item's own intent ('Plan/status do not mutate' but they should still inform). Align plan to report state='uninstalled' with an action_needed/predicted-change signal. Also _do_apply's docstring claims 'repair if broken' but no repair branch exists — either the docstring or the validation claim 3 ('handles absent, broken, configured, and healthy') overstates behaviour; the probe only yields available yes/no, so 'broken' is not a detectable state today. 3) PUBLIC-BOUNDARY ERROR TYPE: CliLifecycleResult.__post_init__ raises bare ValueError (contracts/cli_lifecycle.py:43); this contract crosses the approved providers_api public boundary, where Architecture Standards §4 requires AudiaGenticError with an owning error code. 4) MINOR: cli_lifecycle_handler reaches into lifecycle's private _probe_provider_cli via function-level imports at four sites; if the private probe is the real shared primitive, promote it to a module-level named export rather than repeated deferred private imports.

## Conclusion

Implemented. Deleted the unused provision_all_provider_clis action dispatcher and duplicate repair_provider_cli path; promoted probe_provider_cli as the shared named primitive; plan now reports the absent state with predicted change/action; corrected the apply documentation; and invalid public result state raises VAL-PCLI-001. Validation: 73 focused provider tests passed.
