# manage_lsp_mcp_projection gates on the raw receive_lsp_mcp flag instead of its declared automation capability

## Notes

IMPLEMENTED 2026-07-16 by claude — closing, with one item deliberately deferred.

FIXED: manage_lsp_mcp_projection now checks automation_capability('lsp-mcp-projection') alongside mcp_config/receive_lsp_mcp, matching its Pattern B siblings. Because no provider declared the family, the check alone would have returned RES-PREC-001 for all 13 eligible providers and silently broken LSP-MCP projection — so the declaration was added to exactly the 13 descriptors that previously passed the implicit gate (antigravity, claude, cline, codex, continue, copilot, gemini, goose, opencode, openhands, pi, qwen, roo). local_openai stays undeclared, consistent with its receive_lsp_mcp: false. Participation is now declared, not inferred from a boolean. Verified: every eligible provider resolves the capability and the descriptors validate.

DEFERRED (needs architecture-owner decision): the `_result` shape inconsistency. The real cause is not a careless default — LspMcpProjectionResult has no `supported` field at all, unlike ManagedMcpResult/LanguageServerProjectionResult. Adding one changes a frozen MA29 contract and its published provider-lsp-mcp-projection-result/v1 schema, which is beyond a cleanup. Callers can still distinguish unsupported via error_code=RES-PREC-001. Recommend the owner decide whether the family results should carry a uniform `supported` flag; if yes, it is a coordinated contract+schema change across the LSP families.

FAN-OUT DUPLICATION: also addressed, differently than suggested. Rather than sharing a predicate, the descriptor/enablement fan-out for self-provided-lsp moved behind a new public manage_self_provided_lsp_all, matching manage_lsp_mcp_projection_all. That removed coding-lsp's last two providers-internal imports (see RV500).

TEST STUBS: tests/unit/providers/test_lsp_propagation_suppression.py and test_lsp_enable_propagation.py used hand-rolled _Provider stubs that had drifted from ProviderDescriptor (one lacked automation_capability entirely). Both now model the declaration.

## Findings

['manage_lsp_mcp_projection (lsp_mcp_projection.py lines 47-52) gates on descriptor.mcp_config is None or not descriptor.receive_lsp_mcp. It never calls descriptor.automation_capability(\'lsp-mcp-projection\').', 'Both sibling Pattern B families do check the capability: language_server_family lines 36-40 check automation_capability(\'language-server-projection\'), managed_mcp_family lines 48-52 check automation_capability(\'managed-mcp\').', 'Consequence: a provider participates in lsp-mcp-projection purely by having receive_lsp_mcp: true, with no capability declaration and therefore no declared supported_modes, payload_contract, result_contract, or ownership_scope_required. The declaration that MA20 makes the basis of participation is bypassed.', 'The _result() helper here defaults only {ok: True} while language_server_family and managed_mcp_family default {ok: True, supported: True}, so this family never reports supported=False on the precondition path — it returns ok=False with supported defaulted, giving callers a different failure shape than its siblings for the same class of failure.', 'The fan-out manage_lsp_mcp_projection_all and providers_api.manage_language_servers_all repeat the eligibility predicate in the fan-out loop (filtering on descriptor.language_servers_config is None), duplicating and potentially diverging from the guard inside the family function.']

## Conclusion

Add the automation_capability('lsp-mcp-projection') check to the precondition guard and add the capability declaration to the descriptors of every provider carrying receive_lsp_mcp: true, so participation is declared rather than inferred from a boolean. Align _result() to default supported=True like its siblings so precondition failures report a consistent shape. Fan-out eligibility should be derived from the same predicate the family function enforces rather than re-expressed in the loop — see the shared-preamble review on MA20 for the common guard this should fold into.
