# Pattern A and Pattern B family bodies repeat the same precondition preamble, _result helper, and McpServerEntry mapping

## Notes

SHARPENED 2026-07-16 with a measured finding that strengthens the case and gives the shared scaffolding a concrete first job.

PARTIALLY IMPLEMENTED ALREADY: the dead `_SUPPORTED_MODES` re-check is gone from self_provided_lsp_handler (Pattern A handlers cannot reach it — registry.dispatch validates mode against the definition before calling). FamilyPin now exists (RV495 corrected), which is the natural home for the shared facts.

NEW MEASUREMENT — the `_SUPPORTED_MODES` duplication is worse than 'four copies of a constant'. Every Pattern B family does exactly two things with its declaration:
    descriptor.automation_capability("managed-mcp") is None   # existence check ONLY
    mode not in _SUPPORTED_MODES                               # its OWN module constant
None of managed_mcp_family, language_server_family, lsp_mcp_projection or plugin_entries ever reads `capability.supported_modes`, `capability.payload_contract`, `capability.result_contract` or `capability.ownership_scope_required`. So for Pattern B those four declared fields are unvalidated decoration — a descriptor could declare any modes or contracts it liked and nothing would notice. Only the family_id is load-bearing, as a gate.

THE ASYMMETRY THIS EXPOSES: Pattern A validates the declaration against the code-side FamilyPin via VAL-PREC-009 — verified that a descriptor declaring supported_modes ('apply','status','plan') for self-provided-lsp is REJECTED because the family pins only ('apply','status'). Pattern B has no pin and no validation, so the same typo would sail through.

CHEAPEST FIX, which REMOVES more than it adds: give Pattern B families a FamilyPin too and validate the declaration against it at call time. That (a) deletes the four `_SUPPORTED_MODES` module constants this review already flagged, (b) makes the Pattern B declaration mean something, (c) closes the mode-drift hole, and (d) costs roughly three lines per family because FamilyPin already exists. No new layer — it is the same primitive Pattern A already uses.

SCOPE NOTE: MA26's managed-hooks must inherit this rather than adding a fifth `_SUPPORTED_MODES` constant; recorded in MA26 step 3. And RV509 shows the family BODIES should collapse onto the existing sync_managed_config engine, so the shared scaffolding this review asks for is smaller than originally scoped: the precondition guard + the pin check, not a whole engine — the engine is already built.
