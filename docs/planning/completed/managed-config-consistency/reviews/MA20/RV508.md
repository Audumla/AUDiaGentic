# plugin-entry is the outlier family: untyped options bag, bespoke spec type, singular, no ownership scope, and N=1 provider

## Notes

Raised from the owner's question 'are hooks just plugins in disguise?'. The answer is no — but the question surfaced a real smell, and it points at plugin-entry rather than at hooks. Recorded here because MA20 owns the generic-mechanic rule (step 4) that plugin-entry sits awkwardly against. Companion to RV505 (which collapses lsp-mcp-projection into managed-mcp).

## Findings

['HOOKS ARE NOT PLUGINS — they materialize completely differently. opencode plugin: flat array in .opencode/opencode.json, `{"plugin": ["pkg", ["pkg2", {opts}]]}`, identity = PACKAGE NAME, upsert by name, at most ONE entry per name. codex hook: event-keyed nested lists in ~/.codex/hooks.json, `{"hooks": {"SessionStart": [{"hooks": [{type, command, timeout}]}]}}`, identity = (event, command), MANY entries per event as the normal case.', 'The cardinality difference is decisive and not cosmetic: the plugin array structurally cannot hold two entries under one key, while hooks routinely have several per event — that is exactly the case MA26 step 5 must preserve (our hook AND a user hook on the same SessionStart event). A family whose shape forbids duplicates cannot host a concept that requires them.', 'The semantics differ too. The opencode adapter docstring is explicit: \'Opencode auto-installs packages listed in the top-level plugin array on startup — there is no separate install command.\' A plugin is a PACKAGE TO INSTALL (a dependency declaration). A hook is a COMMAND TO RUN AT AN EVENT (a callback registration). Different lifecycle, different failure modes.', 'NO provider currently has both, and in fact NO provider models hooks in a descriptor at all — codex hooks.json is written directly by memory/hindsight/codex_recipe.py, bypassing the descriptor entirely. That bypass is precisely what MA26 exists to fix. So the two concepts have never been compared side by side in one descriptor.', 'THE REAL SMELL, and why the question was worth asking: PluginEntryRequest is {entry_id: str, options: tuple[tuple[str, str], ...]} — an untyped string bag. A hook COULD be crammed in as entry_id=\'hindsight/session-start\', options={\'event\': \'SessionStart\', \'command\': \'...\', \'timeout\': \'5\'}. That it is even possible is the warning: MA20 step 4 forbids \'a generic capability request, arbitrary configuration blob, generic command runner, or universal request/result\'. plugin-entry already has the blob.', 'plugin-entry is the outlier on every axis: the ONLY family using PluginConfigSpec instead of ManagedConfigSpec (mcp_config, language_servers_config and model_config are all ManagedConfigSpec); the ONLY family with an untyped payload; the ONLY singular family (one entry_id per request, no entry set); the ONLY family with no ownership_scope; and it has exactly ONE declaring provider (opencode).', 'N=1 UNDERMINES ITS CLAIM TO BE GENERIC. MA20 step 4 permits a reusable mechanic only where \'desired-state semantics, ownership, modes, and result behavior are identical\' across providers. With a single provider that identity has never been tested — plugin-entry is a generic family shape derived from one example.']

## Conclusion

PARTLY VALID. Hooks are not plugins; cardinality and lifecycle differ, so MA26 must keep a distinct typed hook contract. Plugin options are not an unchecked Any blob: current contract validates a string map, appropriately opaque to plugin-package semantics. N=1 is insufficient reason to redesign completed MA25 or force PluginConfigSpec into ManagedConfigSpec. MA20 now documents opacity and a proof threshold: revisit only with a second provider or concrete duplicated semantics.
