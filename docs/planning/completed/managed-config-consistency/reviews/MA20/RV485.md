# Design question: must all families route through ProviderAutomationRegistry or are direct providers_api calls acceptable

## Notes

RESOLVED 2026-07-16 by claude. The design question is already answered in MA20's own locked text; no architecture-owner decision is outstanding.

ANSWER: Path (B), scoped. MA20 step 8 states verbatim: 'Descriptor-backed generic capabilities need no requester-specific registration; custom or declarative-backed provider behavior requires explicit family registration.' That is a two-pattern rule, not a registry-only rule. SLIM_IMPLEMENTATION_PATH.md subsequently documented the same split as Pattern A (explicit code registration via ProviderAutomationRegistry, for per-provider custom behaviour) and Pattern B (descriptor-backed generic service, no registry, where semantics/ownership/modes/results are identical across providers).

CONSEQUENCE: manage_mcp_entries (MA23), manage_language_servers (MA28), and manage_lsp_mcp_projection (MA29) are Pattern B and legitimately do not register handlers. build_automation_registry is therefore NOT incomplete — it is the composition point for Pattern A only. RV475 and RV477 are assessed against this answer and closed accordingly.

MA09's 'registration' gate should be read as: every Pattern A family is registered and dispatches through the registry, AND every Pattern B family uses providers_api as its canonical entry point and validates its declared capability at call time. That is the wording already used in the MA09 slim slice (items 3 and 4).

## Findings

["MA20 step 8 says configuration cannot register — but doesn't mandate registry as sole dispatch mechanism", "MA12 notes specify automation_registry.py as the composition location for 'all' families, not just CLI", 'Current implementation: CLI-lifecycle registers through registry; 4 other families bypass it with direct providers_api calls', "MA09 validation requires 'registration' gates to pass — unclear if 'registration' means registry-only or declaration-only"]

## Conclusion

MA12 was the first production registry adopter per MA12 notes: 'create providers-internal services/automation_registry.py with a factory such as build_automation_registry(project_root)'. The other families (MA23 managed-MCP, MA25 plugin-entry, MA28 language-server-projection) were implemented before automation registry adoption was required. MA20 step 8 says 'Configuration cannot register or enable implementation' but doesn't mandate that all family operations must route through ProviderAutomationRegistry.dispatch(). Two design paths exist: (A) all families must register handlers with the registry and dispatch through it — requires migrating manage_mcp_entries, manage_plugin_entry, manage_language_servers to use ProviderAutomationRegistry; (B) direct providers_api calls are acceptable as long as they validate against MA20 declarations — registry is composition point only for CLI-lifecycle. MA09 cannot close until this design question is resolved because MA09 validation requires 'exact export matrix enforced' and 'layering/ownership/mode/registration/deletion gates pass'.
