# build_automation_registry hand-rolls one loop per family and is rebuilt from scratch on every providers_api dispatch

## Notes

PARTIALLY IMPLEMENTED 2026-07-16 by claude — keeping OPEN for the caching half.

DONE — table-driven registration: build_automation_registry is now one FamilyRegistrar table (pin, eligibility predicate, handler factory) and a single registration loop, replacing the four copy-pasted loops and the 40-line aliased import block. This realises MA20's own note that 'build_automation_registry should accept explicit registrar contributions so new declarative-backed families do not require a hardcoded central switch'. A new Pattern A family now costs one table row plus a handler. Composes with the corrected RV495: each row carries the family's FamilyPin, so the pin stays code-owned and VAL-9 keeps validating declarations against it.

Also removed the duplicated eligibility guard where it was safe: the handlers' _SUPPORTED_MODES re-check is gone from self_provided_lsp_handler (registry.dispatch already enforces modes against the definition before the handler runs, so it was unreachable). The descriptor-field guards remain in the table as the eligibility predicate, which is their proper home.

VERIFIED: registration coverage identical before/after (cli-lifecycle 15/15, generated-surfaces 7/7, model-projection 1/1, self-provided-lsp 1/1; Pattern B families correctly 0). tests/unit/providers + tests/unit/coding_lsp: 0 failures.

STILL OPEN — the per-dispatch rebuild: providers_api.manage_model_projection and manage_self_provided_lsp still call build_automation_registry(project_root) on EVERY invocation, reloading descriptors and re-registering every handler to service one dispatch; manage_self_provided_lsp_all now amplifies this once per provider. The fix is a cached, idempotent loader per ARCHITECTURE_GUIDELINES section 8 — fix inside the loader, never by hoisting construction into callers.

WHY DEFERRED: caching build_automation_registry entangles with RV503. The registry reads process-global descriptor state that tests monkeypatch per-test, so a naive lru_cache would serve a stale registry across tests and turn today's order-dependent pollution into permanent cross-test breakage. Do RV503's isolation fixture FIRST, then cache with an explicit invalidation hook. Caching before test isolation would make the suite worse, not faster.
