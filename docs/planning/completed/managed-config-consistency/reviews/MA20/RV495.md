# Collapse the four duplicated family-definition modules into one pin table — but do NOT derive the definition from the descriptor (corrected)

## Notes

CORRECTED then IMPLEMENTED 2026-07-16 by claude — closing.

=== THE CORRECTION (read this first) ===
My original central recommendation was WRONG. I claimed the code-side RecipeDefinition was 'redundant by construction' because register()'s VAL-9 check proves it equals the descriptor declaration, and proposed deriving the definition (and the family contract map) FROM the declaration. That inverts the direction of authority. The code-side definition is the FAMILY'S AUTHORITATIVE PIN; the descriptor is a PER-PROVIDER DECLARATION; VAL-9 is the cross-check that config matches what the family actually implements.

VERIFIED, NOT ASSUMED: registering self-provided-lsp for pi with a descriptor declaring supported_modes ('apply','status','plan') is REJECTED with VAL-PREC-009, because the family pins only ('apply','status'). Had I implemented my own advice, that registration would SUCCEED, dispatch would accept mode='plan', and the handler — which has no plan branch — would fall through to its apply path and RUN THE pi-lens INSTALLER. A config typo would silently turn a planning call into a mutation: the same defect class as RV497, which I had just finished fixing.

=== WHAT WAS ACTUALLY IMPLEMENTED ===
The duplication finding was real; only the proposed fix was wrong. Kept the pin in code, collapsed how it is expressed:
- Added FamilyPin (recipe_definitions.py): a frozen dataclass holding one family's authoritative facts, with .contracts and .definition(provider_id), synthesizing recipe_id f'{provider_id}.{family_id}' and recipe_version '1'.
- The four *_family.py modules now declare a single PIN constant each instead of an X_definition(provider_id) factory plus a one-entry X_family_contracts() dict builder. The three pure pin modules went from ~38 lines to 16.
- build_automation_registry pins contracts from the same table ({r.pin.family_id: r.pin.contracts}), so the contract map is still composition-owned — NOT derived from descriptors, per the correction.
- KEPT VAL-9, as the corrected design requires. It is the only thing validating declarations against family reality, and MA20's notes anticipate external registrars passing their own definitions.
- Renamed generated_surface_family._make_handler -> make_generated_surface_handler (an underscore-private name that was exported in __all__ and imported across modules).

VERIFIED: registration coverage identical before/after (cli-lifecycle 15/15, generated-surfaces 7/7, model-projection 1/1, self-provided-lsp 1/1; Pattern B correctly 0). VAL-PREC-009 mode-drift rejection re-verified AFTER the refactor. tests/unit/providers + tests/unit/coding_lsp: 0 failures.

LESSON FOR THE PROGRAM: 'this code duplicates config, delete it' is a tempting simplification in a config-over-code push, but a code-side pin that config is validated against is not duplication — it is the invariant. Check which side is the authority before collapsing. MA25/MA26 should add their families as table rows with their own pins.

## Findings

['cli_lifecycle_family.py, model_projection_family.py, self_provided_lsp_family.py, and generated_surface_family.py (lines 1-40) are structurally identical: FAMILY_ID, PAYLOAD_CONTRACT, RESULT_CONTRACT, SUPPORTED_MODES constants, an X_definition(provider_id) factory, and an X_family_contracts() dict builder. Only the string literals differ.', 'Every field the X_definition() factory sets is ALREADY declared in the provider descriptor YAML. pi.yaml automation_capabilities declares family_id, supported_modes, payload_contract, result_contract, ownership_scope_required — the exact five fields RecipeDefinition carries (minus recipe_id/recipe_version).', 'ProviderAutomationRegistry.register() (recipe_definitions.py VAL-9 check) rejects the registration unless declaration.payload_contract/result_contract/supported_modes/ownership_scope_required all EQUAL the definition. The code definition can therefore never legitimately differ from config — it is a hand-maintained copy that register() exists to prove is a copy.', 'recipe_id is mechanically f\'{provider_id}.{family_id}\' in all four modules; recipe_version is the literal \'1\' in all four.', 'X_family_contracts() returning {FAMILY_ID: (PAYLOAD, RESULT)} is a one-entry dict builder repeated four times, then merged by four successive family_contracts.update() calls in build_automation_registry.']

## Conclusion

The four *_family.py definition modules encode in Python what the descriptor YAML already declares, and register() enforces that the two agree — so the Python side is redundant by construction. Replace X_definition(provider_id) with a single generic definition_from_capability(provider_id, capability) that builds RecipeDefinition directly from the descriptor's ProviderAutomationCapability (family_id, supported_modes, payload_contract, result_contract, ownership_scope_required already present; synthesize recipe_id as f'{provider_id}.{family_id}'). Replace the four X_family_contracts() functions with one family_contracts_from_descriptors() that derives the contract map by scanning declared capabilities. This deletes ~140 lines, removes the VAL-9 drift class entirely (config becomes the single source), and makes a new Pattern A family cost only a YAML declaration plus a handler — no definition module. Keep the VAL-9 equality check only if an independent code-side definition survives for some family; if none does, it becomes unreachable and should go too.
