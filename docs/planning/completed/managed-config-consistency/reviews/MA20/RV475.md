# Only CLI-lifecycle registered in ProviderAutomationRegistry — 4 other families bypass registry

## Notes

ASSESSED 2026-07-16 by claude. Partly answered by MA20 step 8, partly overtaken by events — closing and carrying the one live residue to RV499.

1. NOT A DEFECT (design answered): managed-mcp (MA23), plugin-entry (MA25) and language-server-projection (MA28) do not register handlers because they are Pattern B families. MA20 step 8: 'Descriptor-backed generic capabilities need no requester-specific registration.' build_automation_registry is the Pattern A composition point, not a universal one. See RV485.

2. STALE FACT: this review states 'model-projection family (MO02) has no contract, no typed types, no registry entry'. That is no longer true as of 2026-07-15 — model_projection_family.py, contracts/model_projection.py, the payload/result JSON schemas, and a registration loop in build_automation_registry all exist, with pi wired and verified.

3. LIVE RESIDUE: the finding 'generated-surfaces (MA21) has contract declaration but no handler registration in build_automation_registry' remains true and is the one real gap this review found. generated_surface_family_contracts() is merged into the contract map while no provider registers a handler, so the family is discoverable but not dispatchable, and providers_api.operate_provider_surface still calls the private _make_handler directly. That is tracked in detail as RV499 on MA21, which also raises the open question of whether generated-surfaces is actually Pattern B (its handler binds only project_root and takes provider_id via ownership_scope).

No further action under RV475; MA20's registration gate should be verified against the two-pattern rule recorded in RV485.

## Findings

['build_automation_registry() registers only CLI-lifecycle handlers (line 47-54)', 'managed-mcp family (MA23) has no automation registry entry — uses manage_mcp_entries via direct providers_api call', 'plugin-entry family (MA25) has no automation registry entry — uses manage_plugin_entry via direct providers_api call', 'language-server-projection family (MA28) has no automation registry entry — uses manage_language_servers via direct providers_api call', 'generated-surfaces family (MA21) has contract declaration but no handler registration in build_automation_registry', 'model-projection family (MO02) has no contract, no typed types, no registry entry']

## Conclusion

build_automation_registry() only registers CLI-lifecycle (5 providers) and generated-surfaces (contract-only, no handler registration). Managed-MCP (MA23), plugin-entry (MA25), language-server-projection (MA28), and model-projection (MO02) are not registered through ProviderAutomationRegistry — they bypass the registry entirely via direct providers_api calls. MA20 validation 4 requires 'Each declared capability resolves to one distinct typed family contract' with registration in the automation registry, but only 2 of 5 implemented families are registered.
