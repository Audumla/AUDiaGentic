# lsp-mcp-projection and managed-mcp are the same family twice — identical entry fields, same descriptor spec, same writer. Collapse to one.

## Notes

Answers the standing question of whether hooks/plugins/MCP/language-servers each need their own family. The answer is not uniform: exactly one pair is provably redundant, the rest are genuinely different CONTRACTS sharing one MECHANIC. Raised on MA20 because it owns the generic-mechanic rule (step 4) that decides this; execution touches MA23 and MA29.

## Findings

['ManagedMcpEntry and LspMcpProjectionEntry have IDENTICAL fields: args, command, env, headers, managed_id, name, transport, url (all 8, verified by dataclasses.fields comparison).', 'Both families gate on the SAME descriptor spec: descriptor.mcp_config.', 'Both convert their entry to the SAME foundation type, McpServerEntry, via field-for-field mappings that RV502 already flagged as duplicated (_desired in managed_mcp_family, _to_mcp_entry in lsp_mcp_projection).', 'Both write the SAME provider file through the same service module: managed-mcp calls sync_managed_provider_mcp_scope, lsp-mcp-projection calls sync_managed_provider_mcp_subset. The only real difference is ownership bookkeeping (scope registry vs an explicit managed_ids subset) — an implementation detail, not a contract difference.', 'Cost of the split: two public families, two contract modules, two JSON schema pairs (provider-managed-mcp-* and provider-lsp-mcp-projection-*), two providers_api route sets, two error-code namespaces (CON-PMCP-* and CON-PLMC-*, the latter only created because RV498 had to break a collision), and 13 duplicate lsp-mcp-projection capability declarations across descriptors.', 'MA20 step 4 permits reuse only when semantics, ownership, modes and result behaviour are identical. Entry type, spec, target file and writer are identical; modes are apply/prune/status for both. The contracts are not distinguishable by anything a caller cares about.', 'By contrast the other families are NOT redundant: LanguageServerEntry is {command, file_extensions, language, settings} over language_servers_config; a Codex hook entry would be {event, command, timeout} over a hooks_config; plugin-entry uses a different spec type entirely (PluginConfigSpec, not ManagedConfigSpec). Those entry types share no fields and cannot merge without a generic blob, which MA20 step 4 forbids.']

## Conclusion

VALID. Both families use identical entry shape, ManagedConfigSpec target, modes, and MCP writer. MA29 rewritten to collapse lsp-mcp-projection into managed-mcp while preserving ownership_scope/scoped prune. Other typed families remain distinct.
