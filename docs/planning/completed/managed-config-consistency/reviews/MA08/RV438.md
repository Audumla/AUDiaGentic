# LSP registry-mapping contradicted by open RV412/RV414; no LSP surface exists in sanctioned API

## Notes

MA08 (Block C3, after MA17+MO06) migrates coding-LSP to the providers gateway. Its Notes lock it to the universal-registry design that the open RV412 disputes, and no such surface exists in code yet.

## Findings

1. MA08.md:59 (Notes, 'RV406 CODIFICATION') states 'LSP operations (plan→probe, apply→install/provision, prune→prune, status→probe) map to registry methods or thin wrapper calls from the public API module' and asserts 'no new capability request/result types.' This directly contradicts RV412/RV414 (both `created`), which hold that `ProviderRecipeRegistry` is lifecycle-bound to provisioning and that LSP reconciliation needs purpose-built `providers_api` functions with managed-entry/diff/collision/reload semantics, not provisioning recipes.

2. The sanctioned module `providers_api.py` contains **no** coding-LSP reconciliation function at all (grep for LSP handlers finds only `adapters/base_runner.py` comment text, unrelated). So MA08's step 3 ('Coding-LSP submits desired payload through providers public capability API') has no target surface, and its Notes' registry mapping is hypothetical.

3. MA08 step 8 says 'RV411 rejected generic membership extraction' and keeps high-level loops local — consistent with RV411 — but its Notes still bind LSP to the registry that RV412 says is the wrong tool. The two positions in the same item are inconsistent.

## Conclusion

INCORPORATED (2026-07-15). RV412 ratified the underlying point: the provisioning registry is the wrong tool for LSP. MA08 rewritten — step 0 now BUILDS a purpose-built providers_api LSP sync/diff function (managed-entry/collision/reload semantics); the plan→probe/apply→install registry mapping is removed; MA08 marked blocked until that surface exists. Matches RV412.
