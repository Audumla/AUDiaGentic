# CON-PLSP-001/002/003 error codes collide across all three LSP families — same code, three different meanings

## Notes

IMPLEMENTED 2026-07-16 by claude — closing.

FIX: Split the shared namespace following the CON-PMCP/CON-PMOD precedent the review identified:
- language-server-projection (MA28): CON-PLSV-001/002/003
- lsp-mcp-projection (MA29): CON-PLMC-001/002/003
- self-provided-lsp (MA30): CON-PSLS-001/002 (+003 for a non-mapping hook result)
CON-PLSP-* is fully retired from the codebase.

ADDITIONAL GAP FOUND AND FIXED: none of these codes were registered in config/components/providers/error-resolutions.yaml — nor were the pre-existing CON-PMOD-001/002/003 and VAL-PMOD-001 from MO02. 13 codes total were emitted by code with no catalogue entry. All are now registered.

WHY IT WENT UNNOTICED: AudiaGenticError rejects unregistered codes at construction, but the automation families carry codes as plain `error_code="..."` strings on their typed results, so that guard never fires for them. Added tests/unit/contracts/test_error_resolutions.py::test_every_provider_error_code_literal_has_a_resolution, which scans providers source for code literals and asserts each has a catalogue entry. Verified non-vacuous by temporarily deleting an entry and confirming the failure names the emitting file.

PARTIALLY CARRIED: the review also noted these codes come from bare `except Exception` blocks that discard the exception. Fixed for self-provided-lsp (detail now surfaced via redact_text into action_needed). The language-server and lsp-mcp families still swallow the exception — left alone here to avoid touching files another agent is actively editing; worth a follow-up on MA28/MA29 if the owner wants parity.

## Findings

['language_server_family.py (MA28) emits CON-PLSP-001 on status read failure, CON-PLSP-002 on apply failure, CON-PLSP-003 on prune failure.', 'lsp_mcp_projection.py (MA29) emits the SAME CON-PLSP-001/002/003 for its own status/apply/prune failures.', 'self_provided_lsp_handler.py (MA30) emits the SAME CON-PLSP-001/002 for its status/apply failures.', 'The three families have distinct payload/result contracts and distinct JSON schemas, but share an undifferentiated error-code namespace. The codes are family-agnostic where every other part of these slices is family-specific.', 'Sibling families already use distinct prefixes: managed_mcp_family uses CON-PMCP-001/002, model_projection_handler uses CON-PMOD-001/002/003. The LSP trio is the outlier.', 'All three modules produce these codes from bare except Exception blocks, so the code is the ONLY signal a caller gets — the underlying exception is discarded, making the collision unrecoverable at the call site.']

## Conclusion

Give each LSP family its own error-code prefix, following the CON-PMCP/CON-PMOD precedent already set by the MCP and model families: e.g. CON-PLSV-* for language-server projection (MA28), CON-PLMC-* for LSP-MCP projection (MA29), CON-PSLS-* for self-provided LSP (MA30). Since the codes are emitted from bare except Exception handlers that discard the exception, also attach the underlying error detail to the result rather than relying on the code alone. This is a prerequisite for MA08 closing: the umbrella claims typed ownership of provider LSP entries, and three families answering with the same opaque code is not typed ownership.
