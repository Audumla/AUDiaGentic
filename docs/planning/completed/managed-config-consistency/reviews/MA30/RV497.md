# self-provided-lsp status mode executes the npm install subprocess — mutating query violates the MA09 non-mutation gate

## Notes

IMPLEMENTED 2026-07-16 by claude — closing.

FIX: Added an optional `lsp_support_probe` descriptor field as the non-mutating companion to `on_lsp_enabled`. pi declares `_pi_lens_present`, which checks for the pi-lens package directory under `<harness_runtime>/agent/npm/node_modules/pi-lens` without shelling out. The install layout was verified against the live harness on this machine rather than guessed, so the probe reports real state.

- `status` now reads the probe and never runs the installer. A provider that declares `on_lsp_enabled` but no probe gets an evidence-only `state='unknown'` with action_needed, matching the MA26 'Pi: non-executing, evidence-only' decision, rather than provisioning to answer a query.
- The two identical status/apply branches collapsed into a single operation lookup once status stopped calling the hook, as this review predicted.
- Hook/probe failure detail now flows into action_needed through redact_text instead of being discarded, so the returncode/stdout/stderr `_pi_ensure_lens` carefully redacts is no longer dropped.
- Also removed the handler's `_SUPPORTED_MODES` re-check: registry.dispatch validates mode against the declaration before the handler runs, so it was unreachable (RV502 finding).
- Error codes moved CON-PLSP-001/002 -> CON-PSLS-001/002 per RV498, and CON-PSLS-003 added for a non-mapping hook result.

TESTS: 6 new in tests/unit/coding_lsp/test_provider_lsp_provision.py, including `test_self_provided_lsp_status_does_not_run_the_install_hook` (asserts the mutating hook is never invoked for a query) and `test_pi_lens_probe_does_not_shell_out` (fails the test if the probe spawns a subprocess). 12 passing in that file.

MA09 IMPACT: the 'six queries are non-mutating' gate item is no longer blocked by this family.

## Findings

['self_provided_lsp_handler._handler_impl declares _SUPPORTED_MODES = {apply, status}, then implements the two modes with byte-for-byte identical bodies (lines 48-78). Both call hook(project_root) and build the same SelfProvidedLspResult. The only difference is the error code on failure (CON-PLSP-001 vs CON-PLSP-002).', 'descriptor.on_lsp_enabled for pi resolves to adapters/pi/hooks.py:_pi_ensure_lens, which runs subprocess.run([pi_bin, \'install\', \'npm:pi-lens\'], timeout=300). Calling status therefore installs the extension.', 'ARCHITECTURE_GUIDELINES section 10 states: \'Classify provider API entries by mutation ownership: queries do not mutate\'. A status mode that installs an npm package is a mutating query.', 'MA09 slim slice item 6 requires \'Verify six queries are non-mutating\' — this handler fails that gate as written.', 'SLIM_IMPLEMENTATION_PATH.md MA26 records the equivalent Pi decision as \'Pi: non-executing, evidence-only (no subprocess calls)\'. MA30 wires the same pi subprocess with no such constraint, so the two Hindsight/LSP pi paths now disagree on whether pi automation may execute.', 'Both branches swallow every exception with a bare except Exception, discarding the subprocess error text that _pi_ensure_lens took care to capture and redact (returncode/stdout/stderr are dropped on the floor).']

## Conclusion

status must not invoke on_lsp_enabled. Split the descriptor contract so the family has a non-mutating probe (does the pi-lens extension already exist?) used by status, and reserve the mutating hook for apply. If pi cannot answer the probe without executing, status must return the evidence-only 'unknown/needs-action' state without running the hook — matching the MA26 'Pi: non-executing, evidence-only' decision. Once status stops calling the hook, the two identical branches collapse naturally. Separately, stop discarding the hook's captured returncode/stdout/stderr: _pi_ensure_lens redacts them specifically so they can surface in action_needed.
