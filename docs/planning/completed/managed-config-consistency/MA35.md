# Retire adapters/pi/adapter.py: prompt goes via stdin when {prompt} is absent from args-template (no new flag)

## Description

Reduced scope (HA04 delivered the rest). The declarative recipe system is fully in place: base_runner's build_launch_spec vocabulary (HA04) builds a ProviderLaunch from an execution: recipe, and the dead qwen/copilot adapter.py duplicates are already deleted (HA04, byte-identical to their recipes; tests rewritten to the recipe path).

The ONE remaining piece: Pi's execute (one-shot) path still uses a hand-written adapters/pi/adapter.py because Pi's --print mode drops embedded newlines when the prompt is a CLI argument (SH21); the real fix pipes the prompt via stdin (run_streaming_command input_text=). Pi's execution: recipe puts {prompt} in args-template, which would reintroduce SH21 if adapter.py were removed. Add a prompt-delivery: argv | stdin option to the build_launch_spec / make_cli_runner path (default argv, preserving every other provider) so Pi can declare prompt-delivery: stdin and retire adapter.py.

## Steps

['Add a prompt-delivery: argv | stdin field to the execution: recipe schema; support it in base_runner.make_cli_runner (pipe the prompt via run_streaming_command input_text= when stdin, instead of appending {prompt} to argv).', 'Set pi.yaml execution: prompt-delivery: stdin and drop {prompt} from its args-template.', "Prove Pi one-shot execution through the recipe path is byte-equivalent to adapters/pi/adapter.py's stdin-piped behaviour via an integration test.", 'Delete adapters/pi/adapter.py once proven; keep the 6 genuinely-custom adapters (claude, cline, codex, gemini, local_openai, opencode).']

## Detailed Solution & Technical Design

ROOT CAUSE (SH21): Pi's --print mode drops the first embedded newline when the prompt arrives as a CLI argument. adapters/pi/adapter.py works around this by never putting the prompt in argv -- it pipes the full prompt via run_streaming_command(..., input_text=prompt_body).

DESIGN CORRECTION (2026-07-25, user pushback): the first version of this plan added an explicit `prompt-delivery: argv | stdin` opt-in key to the execution: schema, defaulted to argv, with Pi setting it to stdin. That reads as a special capability bolted onto one provider -- exactly the kind of per-provider fanciness this codebase avoids. There is a cleaner rule that needs NO new declared key at all:

build_launch_spec's {prompt} token (base_runner.py _resolve_arg_token, ~line 117-118) only puts the prompt into argv if the args-template lists the {prompt} token. Every current provider's args-template either lists {prompt} explicitly or relies on the DEFAULT template (base_runner.py ~line 171-173: `["{approval-flags}", "{model-flags}", "{prompt}"]`), which always includes it -- so today {prompt} is present in argv for every provider with an execution: recipe, with zero exceptions. The fix: the prompt must reach the process somehow, so if {prompt} is ABSENT from the resolved args-template, make_cli_runner pipes it via stdin (run_streaming_command's existing input_text= parameter) instead. This is a fallback derived from what the template already says, not a new capability flag -- any future provider that needs the same thing gets it for free by omitting {prompt} from its own template, no schema change, no per-provider opt-in required.

Current pi.yaml execution: block (src/audiagentic/config/providers/pi.yaml, ~line 199-210):
  execution:
    mode: cli
    executable: pi
    aliases: [pi]
    prompt-title: Pi
    error-code: EXT-PI-001
    extractor-name: pi-plaintext
    args-template: ["--print", "{model-flags}", "{prompt}"]
    model-flag: "--model"
    approval-mode-flags: {yolo: [], auto-edit: []}

Target pi.yaml execution: block -- ONLY the args-template line changes, nothing else added:
  execution:
    mode: cli
    executable: pi
    aliases: [pi]
    prompt-title: Pi
    error-code: EXT-PI-001
    extractor-name: pi-plaintext
    args-template: ["--print", "{model-flags}"]   # {prompt} removed -- goes via stdin automatically
    model-flag: "--model"
    approval-mode-flags: {yolo: [], auto-edit: []}

Current adapters/pi/adapter.py (to delete once proven) builds: command = [executable, "--print"] + (["--model", model] if model) and calls run_streaming_command(command, cwd=cwd, input_text=prompt_body, ...). This is exactly what the recipe path produces once the stdin-fallback rule is wired in.

DISPATCH AFTER DELETION: once adapters/pi/adapter.py is deleted, services/execution.py::_adapter_module_path("pi") returns None, so _load_runner("pi") falls through to _descriptor_runner("pi") -> make_runner_from_execution("pi", pi_descriptor.execution) -- the exact fallback path already proven for qwen and copilot in HA04 (see tests/integration/providers/test_qwen.py, test_copilot.py). No dispatch code changes needed beyond the stdin-fallback in base_runner.py.

NOTE ON SCOPE: this is separate from HA04's launch-profile dispatch (resolve_launch_builder / adapters/<id>/<name>.py::build_launch) -- Pi's ONE-SHOT execution goes through the older, still-live execution:/make_cli_runner pipeline (AR12), which execute_provider calls directly via _load_runner, never through resolve_launch_builder. Do not conflate the two systems.
