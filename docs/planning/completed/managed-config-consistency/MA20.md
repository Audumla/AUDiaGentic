# Implement minimal shared internal provider recipe-definition schema

## Description

Define one minimal provider-owned declarative RecipeDefinition envelope and typed loader for current automation families, plus an explicit provider capability catalogue. A shared internal envelope is justified for definitions with the same ownership, lifecycle, validation, and semantics; it is not a universal request/result or future-proof configuration schema. Public APIs retain family-specific payloads/results and plan|apply|prune|status modes. Resource APIs and agent execution are excluded.

## Steps

1. Derive the envelope from current CLI, managed-config, and generated-surface callers. 2. Freeze only recipe id, provider id, open family id, supported modes, family payload/result contract references, recipe version, ownership-scope requirement, and non-authoritative provenance reference where required. Add a common field only when a concrete owned family needs it. 3. Keep generic mechanics separately named and typed; no generic payload/blob/command runner/universal request/result. 4. Capability facts and annotations remain inert. 5. Add an enumerable isolation-tier fact because SH02/SH06 currently need it for safe isolation decisions; it declares no worker-materialization policy or future scheduler settings. 6. Add schemas, loader, registration guards, and focused fixtures for current families; future families extend through their own plan items.

## Files

[SCHEMA] components/providers/contracts/provider-recipe.schema.json; provider capability-declaration schema if separate from descriptor schema; distinct family payload/result schemas.
[COMPONENT:providers internal] typed capability declaration/loader, RecipeDefinition loader, registry, mode adapter, declaration/contract validation.
[CONFIG] provider descriptors enumerate supported capabilities and typed adapter facts; provider-owned recipe declarations only where current automation exists.
[TEST] schema, loader, declaration, registration, duplicate, unknown/undeclared family, metadata non-authority, generic-mechanic opt-in, exclusion, and distinct family fixtures.
[DOC] docs/reference/PROVIDER_CAPABILITY_REFERENCE/model/capability-operation-contract.md — capability catalogue, open family ids, generic-mechanic, and inert-metadata rules.

## Validation

1. Each provider descriptor lists its supported capability-family IDs explicitly. 2. A declared capability resolves to one distinct typed family contract; undeclared/unknown ids fail deterministically. 3. Generic mechanics are separately named opt-in families with their own Request/Result schemas; no generic payload/blob/command family exists. 4. CLI, managed-config, and surface fixtures validate with distinct payload schemas. 5. annotations/capability_facts cannot enable behavior or carry executable/configuration mechanics. 6. Queries, resource commands, and execution are rejected from recipe registration. 7. Facts/annotations cannot enable behavior; declarative recipe config executes only behind an explicitly registered family adapter. 8. Duplicate provider+family registration fails. 9. Only public modes cross boundary; mechanics remain protocol-private. 10. Foundation has no provider recipe schema/type. 11. No universal public request/result or closed family taxonomy. 12. Each provider declaration carries exactly one enumerable machine-readable isolation-tier fact: full-isolation, partial-isolation, or no-isolation; schema/loader tests reject omission and invalid values, and SH02/SH06 can consume it without provider-name heuristics.

## Effort & Risk

Architecture owner freezes the envelope and registration identity. Strong mid-level agent may implement schema/loader/tests afterward. Stop for review if a family requires provider paths, commands, requester identity, or mechanics in the common envelope.
