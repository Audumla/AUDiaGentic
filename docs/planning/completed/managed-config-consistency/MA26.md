# Migrate Codex and Pi Hindsight recipes to typed ownership

## Description

Fourth MA02 cutover. Replace raw Codex/Pi Hindsight recipe classes with frozen, Hindsight-owned typed definitions and desired-state objects. Hindsight owns its commands, downloaded artifacts, desired integrations, and evidence. Providers remain requester-blind: they expose only generic, descriptor-backed native configuration mechanics. Do not use or extend the MA24 provider-integration family; it was based on the superseded ownership model.

   FAMILY: `managed-hooks`   PATTERN: B (descriptor-backed; no registry registration, per MA20 step 8)

   WHY A NEW FAMILY AND NOT REUSE OF plugin-entry (asked and answered 2026-07-16 — hooks are NOT plugins in disguise; see RV508): they materialize completely differently. An opencode plugin is a FLAT ARRAY entry in .opencode/opencode.json identified by PACKAGE NAME, at most one per name, meaning 'auto-install this package at startup' (the adapter docstring is explicit: 'Opencode auto-installs packages listed in the top-level plugin array on startup — there is no separate install command'). A codex hook is an EVENT-KEYED NESTED LIST entry identified by (event, command), with MANY entries per event as the normal case, meaning 'run this command when this event fires'. The cardinality difference alone is decisive: the plugin array structurally cannot hold two entries under one key, while the whole point of step 5 is that our hook and a user's hook coexist on the same SessionStart event. Modelling a hook as a plugin would also require stuffing event/command/timeout into PluginEntryRequest's untyped `options` bag — the generic-blob path MA20 step 4 forbids. NOTE: no provider currently has both, and none models hooks in a descriptor at all (codex hooks.json is written directly by codex_recipe.py, bypassing the descriptor — which is what this item fixes).

   WHY A NEW FAMILY AND NOT REUSE OF managed-mcp — a hook entry and an MCP entry share NO fields. ManagedMcpEntry is {managed_id, name, command, args, env, url, headers, transport}; a hook entry is {managed_id, event, command, timeout}. MA20 step 4 permits reuse only where 'desired-state semantics, ownership, modes, and result behavior are identical'. They are not, and merging them needs a generic blob, which step 4 forbids. (Contrast RV505: lsp-mcp-projection has FIELD-IDENTICAL entries to managed-mcp and must collapse into it. Different entry type = different family; same entry type = same family.) managed-hooks is a distinct CONTRACT but must sit on the SAME shared engine as managed-mcp/language-server-projection (RV502) — read spec, merge owned entries, prune owned only.

   DESCRIPTOR SURFACE (codex.yaml — config, not code):

       reader:  "...adapters.codex.hooks_format:read_codex_hooks"
       writer:  "...adapters.codex.hooks_format:write_codex_hooks"
       remover: "...adapters.codex.hooks_format:remove_codex_hook"

   FROZEN CONTRACTS (providers/contracts/managed_hooks.py):
     ManagedHooksMode = Literal["apply", "prune", "status"]
     @dataclass(frozen=True) class ManagedHooksEntry:
         managed_id: str            # owner-scoped stable id, e.g. "hindsight/session-start"
         event: str                 # provider-native event, e.g. "SessionStart"
         command: str               # full argv string, quoted by the caller
         timeout: int | None = None
         __post_init__: managed_id, event, command all non-empty; to_mapping/from_mapping
     @dataclass(frozen=True) class ManagedHooksRequest:
         ownership_scope: str       # e.g. "hindsight"
         entries: tuple[ManagedHooksEntry, ...] = ()
         __post_init__: managed_ids unique; to_mapping/from_mapping
     @dataclass(frozen=True) class ManagedHooksResult:
         ok: bool
         supported: bool = True     # INCLUDE IT — RV501 shows omitting `supported` forces a shape divergence from sibling families that then cannot be fixed without breaking a frozen contract
         changed: bool = False
         provider_id: str = ""
         managed_ids: tuple[str, ...] = ()
         removed_ids: tuple[str, ...] = ()
         collision_ids: tuple[str, ...] = ()
         action_needed: str | None = None
         error_code: str | None = None
         to_mapping

   SCHEMAS: provider-managed-hooks-payload.schema.json + provider-managed-hooks-result.schema.json under providers/contracts/, Draft 2020-12, additionalProperties:false, error-code matching the existing repo regex.

   ERROR CODES — USE `PHKS`, NOT `PHK` (corrected 2026-07-16). Every existing provider-family prefix is exactly FOUR characters: PCAP PCAT PCFG PLFC PLMC PLSV PMCP PMOD PPLG PREC PSLS PTAG. PHK would be the only 3-character one. It is otherwise valid (matches the schema regex, no collision), so this is a consistency fix, not a correctness one — but there is no reason to break a 12-for-12 invariant on the newest family.
   Register in config/components/providers/error-resolutions.yaml in the SAME change — enforced by tests/unit/contracts/test_error_resolutions.py::test_every_provider_error_code_literal_has_a_resolution:
     RES-PHKS-001  provider does not declare managed-hooks / has no hooks_config
     CON-PHKS-001  hooks config read failed (status)
     CON-PHKS-002  hooks apply failed
     CON-PHKS-003  hooks prune failed
     CON-PREC-002  reused for unsupported mode (existing shared code)

   OWNERSHIP AND PRESERVATION — the decision that actually matters:
     • ownership_scope_required = TRUE. Entries live under an owned scope keyed by managed_id, exactly like managed-mcp's f"{provider_id}/{ownership_scope}".
     • apply MERGES: read existing hooks.json, replace only entries whose managed_id is in the owned scope, leave every foreign entry byte-identical — including foreign hooks under the SAME event.
     • prune removes ONLY owned managed_ids. Never unlink the file while foreign entries remain.
     • This is what step 5 regression-tests. The current recipe does the opposite (verified data loss).

   DECISION (a) — WHO OWNS `[features] codex_hooks = true`: DECIDED BY OWNER 2026-07-16 — enable the flag when we need it, leave it alone when we prune. The codex WRITER owns it: enabling Codex's hook subsystem is a Codex mechanic, and Hindsight must not know Codex gates hooks behind a feature flag. Writer sets it true when the owned scope is non-empty after apply. Prune NEVER touches it — other tools may rely on hooks, and disabling a global feature flag we did not enable is an unowned mutation. Move the existing surgical upsert (codex_recipe._enable_codex_hooks) into the adapter unchanged; never rewrite config.toml.

   OWNERSHIP TRACKING — NOT A DECISION, REUSE THE EXISTING PRIMITIVE. (This replaces the former 'decision (b) — managed_id scheme', which was a non-question: of course we find and remove exactly the hooks we added and leave the rest. The mechanism for that already exists.)
   `ManagedFragmentRegistry` (foundation/toolchains/managed_config.py) is already the generic 'atomic ownership registry for opaque named fragments', and `mcp_ownership_registry` is nothing more than "the one MCP-scoped instance" of it, keyed `dict[scope, dict[managed_id, str]]` under `.audiagentic/runtime/providers/<filename>`. Do exactly the same for hooks:
       ManagedFragmentRegistry(project_root, "managed-hooks.json", top_level_key="providers")
   RECORD: managed_id -> the exact command string we wrote. PRUNE: for each managed_id in our scope, find the hook entry whose command matches the recorded value and remove that entry only; everything else in hooks.json is untouched by construction because it is not in our registry.
   WHY THE REGISTRY RATHER THAN MATCHING THE FILE: Codex hook entries are `{type, command, timeout}` inside a per-event list — they carry NO id field, so there is nowhere in Codex's own schema to stamp ownership, and inventing an extra key would pollute a foreign schema. The registry keeps ownership on OUR side of the boundary. It also fixes an existing bug: today's probe recomputes the expected command from `sys.executable` and reports 'hook commands absent or stale' whenever the venv changes, orphaning our own hook because it can no longer recognise it. The registry remembers what we actually wrote, so we can still find and remove it after an interpreter change.
   managed_id values are just our registry keys — `hindsight/session-start`, `hindsight/recall`, `hindsight/retain`. No sign-off needed.
   IF hooks need a second ManagedFragmentRegistry instance, that is the fourth caller of the same primitive — fine, it is foundation-generic and designed for exactly this. Do NOT write a hooks-specific ownership store.

   REQUESTER-BLINDNESS GATE: `rg -i "hindsight|vectorize" src/audiagentic/components/providers` returns zero hits. The family knows events, commands, timeouts, managed_ids. It does not know what Hindsight is.

The family_id is load-bearing as the DECLARATION KEY: it is what `automation_capability("managed-hooks")` gates on, so participation is declared rather than inferred from `hooks_config` being present (the anti-pattern RV501 just removed from lsp-mcp-projection).    PATTERN B DECLARATION GAP (RV502, applies to this family): every existing Pattern B family checks only that the capability EXISTS (`automation_capability(id) is None`) and then validates mode against its OWN module-level `_SUPPORTED_MODES` constant — never against `capability.supported_modes`.
