# Maintain provider capability knowledge and evidence

## Description

Maintain provider-owned capability evidence without changing runtime automation contracts. MA19 uses one reusable typed capability_facts/evidence shape for an open, curated evidence catalogue. Operational descriptor fields remain runtime authority; facts are added only when a claim benefits from durable provenance, constraints, uncertainty, or verification history. MA20 separately enumerates executable automation capabilities. Facts cannot register implementations, select transports, or enable automation.

## Steps

1. Preserve the provider-owned frozen CapabilityEvidence and ProviderCapabilityFact types and strict lossless YAML loader.\n2. Keep ProviderDescriptor.capability_facts curated rather than exhaustively mirroring operational descriptor fields. Absence of a fact does not negate a declared operational capability. Once a fact is recorded, unresolved claims remain explicitly unverified/quarantined with action_needed.\n3. Keep capability_id an open stable evidence id, unique within a provider. Reuse one generic fact/evidence shape; do not add commands, paths, serializers, modes, payloads, handlers, or provider-specific fact types.\n4. Preserve HostCapability as the host/editor-extension declaration and keep annotations informational only.\n5. Enforce MA19/MA20 separation: facts may document automation families but cannot declare families, modes, contracts, ownership, registration, or execution.\n6. Validate subject links, ids, evidence tiers/review states, and verified versioned anchors.\n7. Preserve deterministic lossless JSON and concise Markdown serializers as reference projections, never runtime authority.\n8. Maintain focused tests for loading/defaults, invalid fields, validation, deterministic views, authority separation, and runtime/foundation isolation.\n9. Add future provider evidence through normal descriptor/reference maintenance when new evidence is obtained; do not keep MA19 open as an indefinite interrogation queue.

## Files

[COMPONENT:providers/descriptors/base.py] CapabilityEvidence, ProviderCapabilityFact, ProviderDescriptor.capability_facts
[COMPONENT:providers/descriptors/loader.py] capability_facts builder and PROVIDER_SPEC entry
[CONFIG:providers/*.yaml] provider-owned capability facts/evidence
[COMPONENT:providers] validation and deterministic JSON/Markdown serializers
[EVIDENCE/DOCS] current fact anchors and generated reference views
[TEST] loader defaults, validation, evidence linkage, deterministic views, execution/foundation separation
[FORBIDDEN] changes to foundation ManagedConfigSpec for provider evidence, evidence fields on HostCapability as universal model, generated Python taxonomy, runtime imports of generated views

## Validation

1. Every populated fact round-trips from YAML without loss. 2. Recorded unresolved claims are explicit and cannot unlock implementation. 3. Operational descriptors remain runtime authority and need not be duplicated by facts. 4. HostCapability remains limited to host/editor extensions. 5. (provider_id, capability_id) identities are unique and shared ids across providers are accepted. 6. Verified facts require versioned anchors. 7. JSON and Markdown views are deterministic and derived only from provider config. 8. Facts and annotations cannot declare MA20 families, modes, contracts, handlers, registration, transport selection, or runtime behavior. 9. Generated views have no runtime/foundation consumers. 10. Existing provider descriptor/API tests remain green.

## Effort & Risk

Mid. Type/loader work is small; evidence population and subject validation span heterogeneous descriptor declarations. Main risks are treating editor extension ids as universal capability ids, duplicating operational config, and allowing evidence to influence execution.
