# Design provider descriptor YAML schema and probe model

## Description

Design the consolidated descriptor MECHANISM (not a unified registry) plus the provider YAML schema. Per PD08 D2: the recurring pattern across components/features/providers is 'load YAML → resolve dotpath hooks → build step tree → construct typed descriptor'; that mechanism is what we consolidate. Registries stay specialized.

## Modules to create (foundation/descriptors/, zero imports from components/runtime)
1. resolver.py — `resolve_ref(ref: str) -> Any`. Canonical colon dotpath: split on ':' into (module, attr), importlib.import_module + getattr. Raise AudiaGenticError (code VAL-DESC-001) on miss. THE single dotpath home (PD08 D1).
2. steps.py — `build_step_from_spec(spec: dict) -> WorkflowStep`. Registry-dispatched on spec['type'] (PD08 D4): toolchain|shell|callable|sequence|select. Delegates `toolchain` to toolchains.loader.build_step; `callable` -> CallableStep(fn=resolve_ref(spec['ref'])).
3. loader.py — `load_descriptor(path, spec: DescriptorSpec, factory)` + `iter_descriptor_files(dir) -> list[Path]` (glob '*.yaml', Rule 5, no hardcoded list). DescriptorSpec declares per-field handling: data | ref (resolve_ref) | step (build_step_from_spec) | probe (dependencies._resolve_probe) | nested(DescriptorSpec). Validates required fields, resolves, calls factory(**resolved). Type-agnostic — imports no ProviderDescriptor.
4. registry.py — `DescriptorRegistry[T]`: id-keyed store with register/get/all/clear. Reusable by composition; nobody is forced to adopt it.

## Provider field-to-YAML mapping (drives PD03)
Data fields (verbatim): provider-id, display-name, description, url, access-mode, prompt-aliases[], instruction-file, skill-surface-path, receive-lsp-mcp, cli-probe[] (list[str]), permissions{...}, host-capabilities[{host,capability-id,display-name}], agent-files[{rel-path,managed,description}].
ref fields (colon dotpath): fetch-catalog-fn, on-lsp-enabled, mcp-config.{reader,writer,remover,reload-fn}, language-servers-config.{reader,writer,remover}, cli-install.probe-fn.
cli-install: two forms — (a) declarative toolchain form {toolchain,package,executable,uninstall-package?,probe-fn?} maps via cli_recipe()/build_step (13 providers); (b) explicit step form {package-manager,package-name,executable,install:<step-spec>,uninstall:<step-spec>,probe-fn?} for goose & pi (CallableStep via ref).
Note: config-path is a string in ALL current adapters — schema is string-only in v1; callable config_path support deferred (document, not built).

Capability-specific exclusion (reviewed 2026-06-26): provider YAML must not grow
backend-specific sections such as `hindsight`, `memory`, or per-backend installer
recipes. Provider descriptors describe generic provider capabilities and seams
only (`mcp-config`, `cli-install`, `language-servers-config`, etc.). Backend-
specific provider integration facts live with the owning implementation, e.g.
`config/components/memory/hindsight_matrix.yaml` plus
`components/memory/hindsight/`.
