# Codebase review — plan scope inflated; existing architecture covers most of it

## Notes

LSP24's original plan proposes a new `lsp_enablement_config.py` module and updates to 7+ harness adapters. The actual codebase already has the managed-config infrastructure in place; remaining work is much smaller.

### What's already done
- Provider descriptors declare `language_servers_config:` with `reader/writer/remover` pointing at adapter modules (opencode, codex, qwen all have this)
- `ManagedConfigSpec` → `resolve_managed_config_path()` / `apply_managed_config_write()` / `apply_managed_config_remove()` wired through `language_server_family.py`
- `sync_language_servers_to_providers()` projects language bindings via the managed config framework
- The three adapters (opencode, codex, qwen) follow the same pattern

### Remaining work — much smaller than planned
1. **Extract opencode's hardcoded key mapping** from Python (`_LANGUAGE_TO_OPENCODE_KEY` in `adapters/opencode/language_servers.py`) into a YAML-sidecar or provider descriptor field. No other adapter has this problem.
2. **No new `lsp_enablement_config.py` needed** — the existing `ManagedConfigSpec` + provider descriptor architecture already provides centralized, config-driven LSP enablement.

### Plan scope corrections
- The plan lists "pi, claude, cline, copilot, gemini, qwen, roo" as adapters to update. Only 3 adapters (opencode, codex, qwen) have LSP support. Pi and others self-provide LSP — confirmed by `providers_api.py:533` skipping providers where `descriptor.language_servers_config is None`.
- The proposed `LspEnablementMapping` dataclass and default mappings are unnecessary — feature YAMLs already define language specs, and provider descriptors wire reader/writer/remover.
