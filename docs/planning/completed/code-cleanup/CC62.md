# Unify MCP tool error path: redact exception messages, delete report_error(), raise ToolError

## Description

Two competing error conventions exist across the 15 registered MCP servers (143 tools), and one of them lets unredacted exception text reach the client.

**Verified baseline (mcp==1.27.0, pyproject.toml:18):**
- 2 of 15 servers catch and *return* an error dict via `report_error()` in `foundation/mcp/component_server.py` — `project_mcp.py` (19 call sites) and `session_mcp.py` (6 call sites), 25 total. All 25 are inside `except` handlers — verified via AST walk, zero are on a success path.
- The other 13 servers let exceptions propagate uncaught. Probed directly: a raised `RuntimeError('secret token=abc123 leaked')` reaches the client verbatim as `Error executing tool X: secret token=abc123 leaked`. FastMCP 1.27.0 has no `mask_error_details` setting.
- Redaction itself was incomplete even where it ran: `AudiaGenticError`'s `details` are redacted at construction (`errors.py`), but `_Error.__str__` passes `message` through verbatim — verified `str(AudiaGenticError(..., message='login failed: Bearer sk-live-abc123'))` returns the secret unredacted.
- The return-an-error-dict convention actively blocked giving tools real return types (see the sibling item, CC61): a tool annotated with a structured return that got back `{ok: False, error, tool}` would fail schema validation and surface a pydantic ValidationError instead of the real error. Damage was already visible in the tree: `project_mcp.py:42` was annotated `-> list[dict[str, Any]] | dict[str, Any]`, a union that existed only to carry the error dict.
- `@log_tool_call` (in `component_server.py`) already wrapped all 143 tools, exactly 1:1 with `@mcp.tool()` — confirmed by decorator count. It was already the single adapter-boundary interception point for the whole MCP surface (§2: no per-tool migration, no central dispatcher to edit when a tool is added).

**Split from CC61.** CC61 originally bundled this error-path fix together with declaring typed return cores for MCP tools. Split out because this item is self-contained, valuable on its own, and a hard prerequisite for CC61 (a typed tool that still returns an error dict breaks at the boundary) — whereas CC61 does not need to wait on anything else.

**Implemented and verified 2026-08-10.** See Notes for validation evidence.

## Steps

- 1. Add a redaction + error-translation helper `_tool_error_text(exc, tool_name, log)` to `foundation/mcp/component_server.py`, replacing `report_error()`. Behavior: for `AudiaGenticError`, build the redacted envelope via the existing `redact_error_envelope()`, log the full structured envelope at ERROR for operators, and return `"{code}: {redacted message}"` plus `resolution:` and `details:` lines when present. For any other exception, return `redact_text(str(exc))`. Apply the existing fail-closed collapse (from `report_error()`'s tail) to the final text: if any `DEFAULT_REDACT_PATTERNS` still matches, return the literal string `"tool failed"`.
- 2. Explicitly redact the constructed message text before returning it, even on the `AudiaGenticError` branch — do not assume `envelope['message']` is already clean; `_Error.__str__` does not redact it, so this helper must not inherit that gap.
- 3. Fold `_tool_error_text()` into the existing `log_tool_call` decorator (sync and async arms both — kept in step) in `foundation/mcp/component_server.py`, and rename the decorator to `tool_boundary`. On exception, raise `ToolError(_tool_error_text(...))` from the original exception instead of returning a value. On success, keep the existing entry/exit/duration logging unchanged.
- 4. Rename `log_tool_call` → `tool_boundary` at all call sites — mechanical, one rename across every `*_mcp.py` file that imports it from `component_server.py` (§4: no misleading dual name describing only half of what the decorator now does).
- 5. Delete `report_error()` entirely from `component_server.py`.
- 6. In `project_mcp.py` (19 sites) and `session_mcp.py` (6 sites), unwind every `try: ... except Exception as exc: return report_error(...)` block down to the plain call — the decorator now handles translation.
- 7. Drop the `| dict[str, Any]` (or equivalent) error-accommodating arms from any return annotation that existed only to carry the error dict, e.g. `project_mcp.py:42`.
- 8. Update tests that assert `result["ok"] is False` / inspect `result["error"]` to `pytest.raises(ToolError)` with a message-content assertion instead.
- 9. Do not touch domain payloads that carry their own per-item status fields (surface-operation `ok` flags, `managed_config`'s `{ok, method, auto_refreshed}`, etc.) — those are returned data, not error reporting, and are out of scope for this item.

## Detailed Solution & Technical Design

### Governing constraint: §8 Protocol Adapter Boundaries

MCP modules are inbound protocol adapters that "serialize results and errors." Shaping errors belongs in the adapter layer, not scattered per-tool. `tool_boundary` is that one adapter-level seam, and because it already sits on all 143 tools, this item required no per-tool opt-in and no dispatcher edit when a new tool is added (§2).

### The rule after this item

**A tool returns domain data or it raises. It never returns an error-shaped dict.** That is a precondition for CC61 (typed return cores) to be safe: a structured return type describes every value a tool can produce, and an error dict masquerading as a success payload would break that guarantee immediately.

### Error information is split by audience, not discarded

- **Operators** get the full structured envelope (code, kind, message, details, resolution) in the ERROR log record — the durable, redacted artifact the observability standards require.
- **Callers** get a `ToolError` whose text is `code: redacted-message`, plus `resolution:` when the code is registered, plus redacted `details:` when non-empty. This is strictly more than any of the 15 servers gave before: the 13 raising servers gave raw unredacted text, and the 2 using `report_error()` never surfaced `resolution` at all.

### Behavior change, not just refactor

Before this item, `project_mcp` and `session_mcp` returned failures as **successful** MCP results whose body happened to say `ok: False` — the protocol reported success. After this change they raise, and the protocol correctly reports `isError`. This was a genuine behavior change for any caller inspecting `result["ok"]`, which is why step 8 existed.

### What stays untouched

Redaction primitives (`redact_error_envelope`, `redact_text`, `DEFAULT_REDACT_PATTERNS`) are reused unchanged, just moved onto the raise path. `ERROR_ENVELOPE_SCHEMA` and `error-envelope.schema.json` are not touched — this item changes how an error is *delivered* to an MCP caller, not the envelope shape used for the durable log record.

Translation helper — replaces `report_error()`:

```python
def _tool_error_text(exc: Exception, tool_name: str, log: logging.Logger) -> str:
    """Redact an exception into client-safe ToolError text.

    Operators get the full structured envelope in the log record; callers get
    code + message + resolution. Fail-closed: if secret-shaped content survives
    redaction, the text collapses to a generic failure.
    """
    if isinstance(exc, AudiaGenticError):
        envelope = redact_error_envelope(exc)
        log.error("tool failed", extra={"tool": tool_name, "error": envelope})
        parts = [f"{envelope['error-code']}: {redact_text(envelope['message'])}"]
        resolution = envelope.get("resolution")
        if resolution:
            parts.append(f"resolution: {resolution}")
        details = envelope.get("details") or {}
        if details:
            parts.append(f"details: {json.dumps(details, sort_keys=True)}")
        text = "\n".join(parts)
    else:
        text = redact_text(str(exc))
        log.error("tool failed", extra={"tool": tool_name}, exc_info=True)

    for pattern in DEFAULT_REDACT_PATTERNS:
        if pattern.pattern.startswith(r"(https?://"):
            continue  # URL-credential patterns have their own replacement
        if r"api[_-]?key|token|secret|password" in pattern.pattern:
            continue  # already handled by redact_text
        if pattern.search(text):
            return "tool failed"
    return text
```

Folded into the renamed decorator, both arms kept in step:

```python
def tool_boundary(func: Callable) -> Callable:
    """Adapter boundary for an MCP tool: trace the call, redact and translate errors.

    Stacking order — @mcp.tool() outermost, @tool_boundary innermost:

        @mcp.tool()
        @tool_boundary
        def my_tool(...) -> MyResult: ...

    Tools return domain data or raise. A tool must never return an
    error-shaped dict.
    """
    if asyncio.iscoroutinefunction(func):
        @functools.wraps(func)
        async def _async_wrapper(*args: Any, **kwargs: Any) -> Any:
            t0 = time.monotonic()
            try:
                result = await func(*args, **kwargs)
            except Exception as exc:
                raise ToolError(_tool_error_text(exc, func.__name__, logger)) from exc
            logger.info(
                "tool call done",
                extra={"tool": func.__name__, "duration_ms": int((time.monotonic() - t0) * 1000)},
            )
            return result
        return _async_wrapper

    @functools.wraps(func)
    def _sync_wrapper(*args: Any, **kwargs: Any) -> Any:
        t0 = time.monotonic()
        try:
            result = func(*args, **kwargs)
        except Exception as exc:
            raise ToolError(_tool_error_text(exc, func.__name__, logger)) from exc
        logger.info(
            "tool call done",
            extra={"tool": func.__name__, "duration_ms": int((time.monotonic() - t0) * 1000)},
        )
        return result
    return _sync_wrapper
```

`functools.wraps` is load-bearing: it sets `__wrapped__`, which is how `@mcp.tool()` still resolves the wrapped function's real signature and (once CC61 lands) return annotation.

## Effort & Risk

Medium, atomic, net deletion. One decorator, 25 unwound call sites (19 + 6, verified by AST walk — all inside `except` handlers, none on a success path), one mechanical rename across 16 files, `report_error()` deleted outright.

Landed as a single atomic change — it changes error behavior for all 143 tools at once by construction (single shared decorator), which was the intended blast radius, not a defect. `ag-planning`, `ag-ledger`, `ag-agents-gateway`, `ag-lsp` are live in this repo's own `.mcp.json` and consumed by running agent sessions; this session verified the change directly.

## Standards

- **§8 Protocol Adapter Boundaries** — errors are serialized at the adapter boundary, in one place, not per-tool.
- **§4 Public Contracts and Safety** — backward compatibility is not maintained by default: `report_error()` and `log_tool_call` are deleted, not aliased or deprecated. Errors must not expose secrets, which the raise path previously violated for message text in 13 servers and which this item closes.
- **§2 Extensions and Configuration** — adding a tool must not require editing a central dispatcher; folding error handling into the already-universal decorator preserves this.
- **Observability Standards** — the structured, redacted error envelope remains the durable operator-facing record even though the caller receives text, not fields.

## Notes

Split out of CC61 ("Standardize MCP response envelope and schema validation") on 2026-08-10 — see CC61's provenance notes and RV934. CC61 originally bundled this error-path fix with declaring typed return cores for tool results; the two were separated because this item is self-contained and net-positive on its own, needs nothing from CC61, while CC61 depends on this item completing first.

Sizing note on the security framing: this repo's deployment is local/internal with non-hostile users (a shared multi-project gateway, not an internet-facing service), so "secret leak" should not be read as an exploitable external hole. The realistic exposure is indirect but real: tool output lands in agent context and session transcripts, so a credential surfacing in an exception message gets forwarded to a model provider and persisted in logs. That is a real reason to fix this, framed as hygiene and consistency with a security benefit, not as an urgent vulnerability.

Explicitly out of scope, unaffected: per-item status fields already present in domain payloads (surface-operation `ok` flags, `managed_config`'s `{ok, method, auto_refreshed}`) — those are returned data describing partial success within a successful call, not error reporting. A convention for non-blocking warnings on an otherwise-successful call is CC61's `warnings` key, not this item's concern.
