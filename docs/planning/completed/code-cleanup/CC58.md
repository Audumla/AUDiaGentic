# Centralized linting configuration under .audiagentic/config/linting/

## Description

Create shared linting configuration under .audiagentic/config/linting/ so all harnesses and VS Code use the same rules. Project it two ways: native tool config (ruff.toml, pyrightconfig.json, .yamllint) that pyright/ruff/yamllint read directly and which both the CLI harness and VS Code's own extensions consume; and .vscode/settings.json glue for the one part that is genuinely VS Code-only (yaml-language-server workspace settings), written through the existing host-adapter pattern rather than a new .vscode/coding-lsp/ convention.

## Steps

- Create .audiagentic/config/linting/ with shared lint config per language
- Wire coding-lsp to project lint settings to native workspace files (pyrightconfig.json, ruff.toml) — generic projection code, not VS-Code-scoped (RV930: nothing currently writes these, this is greenfield)
- Add yaml-language-server settings to suppress line-length for provider YAML descriptors — via .vscode/settings.json for the VS Code host
- Extend the existing host-adapter pattern (services/host/host_adapter.py + hosts.yaml) with a settings-path method, or add a sibling module beside providers/surfaces/extensions_json.py, for the .vscode/settings.json writer — do not invent a separate .vscode/coding-lsp/ convention
- Validate all harnesses see same rules and no new blocking diagnostics remain

## Detailed Solution & Technical Design

Structure:

  .audiagentic/config/linting/    ← shared lint rules (single source of truth)
    python.yaml                   ← ruff + pyright settings
    yaml.yaml                     ← yaml-language-server settings
    typescript.yaml               ← ts/JS settings

Projection splits into two genuinely different kinds of output — do not conflate them under one .vscode/ folder:

1. Native tool config (generic, NOT VS Code-specific): pyrightconfig.json, ruff.toml at project root. These are pyright's/ruff's own native discovery convention — the same category as Qwen's .lsp.json (see CC60/RV929) — read directly by both AUDiaGentic's LSP-managed harness sessions AND VS Code's own Pylance/ruff extensions. This projection code lives in coding_lsp's own projection module, not gated behind any VS Code-only path.

2. .vscode/settings.json glue — the one part that is genuinely VS-Code-only (yaml-language-server line-length suppression for provider YAML descriptors, any other editor-only keys). This must follow the existing host-adapter isolation precedent (see RV930): providers/surfaces/extensions_json.py already writes .vscode/extensions.json by routing entirely through services/host/host_adapter.py's HostAdapter (host_id, workspace_marker, extensions_manifest, extensions_dir — all sourced from config/components/providers/hosts.yaml, zero VS Code literals in Python). Extend HostAdapter with a settings-path method (or add a sibling module beside extensions_json.py under providers/surfaces/) rather than inventing a new .vscode/coding-lsp/ convention. This code must be imported only by the host-projection call site — never by coding_lsp_bootstrap.py or runtime_resolver.py directly — matching how extensions_json.py is only reached from the reconcile/install path today.

MCP under VS Code needs no new work here: it is already provider-scoped, not host-scoped — Copilot owns .vscode/mcp.json, Cline owns .cline/mcp.json, each declared in its own provider descriptor/adapter (see RV930). Nothing about VS Code as a host requires a centralized MCP surface.

Tree-sitter/ast-grep (pi-agent only): structural rules live in rules/ directory, pi-lens merges with built-ins. These do NOT apply to VS Code — no equivalent needed.

## Notes

Implemented per RV930's split: native tool config (ruff.toml/pyrightconfig.json/.yamllint/tsconfig.json/.prettierrc.json/.editorconfig) lives in coding_lsp/lint_projection.py, generic and not VS-Code-gated. The one genuinely VS-Code-only piece (.vscode/settings.json's yaml.* keys) goes through providers/surfaces/host_settings.py, reusing extensions_json.py's host-adapter-routed isolation pattern -- HostAdapter gained a settings_manifest field (hosts.yaml: vscode.settings-manifest = ".vscode/settings.json") rather than hardcoding the path. "line-length" is not a real yaml-language-server setting (verified against the installed package's settingsHandlers.js/yamlSettings.d.ts) -- it's a yamllint rule, so the error-rules block in yaml.yaml projects to a native .yamllint file (yamllint's per-rule `ignore` glob), not to VS Code settings. TypeScript added on follow-up request: compilerOptions -> tsconfig.json (merged, not overwritten -- a real TS project's include/exclude/references survive re-projection); format.semi/singleQuote/trailingComma -> .prettierrc.json (prettier's real option names); format.tabSize/insertSpaces -> .editorconfig under a [*.{ts,tsx}] section (EditorConfig is a genuine cross-editor standard, not VS Code-specific, so this stays out of the VS-Code-only bucket entirely and avoids a second, driftable source of indentation truth alongside prettier). MCP under VS Code needed no new work, confirmed unchanged.
