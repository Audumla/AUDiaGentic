# COMP-005 — Generic get_config/set_config for implementation-backed management MCPs

## Description

docs/standards/CREATING_A_COMPONENT.md §6 now documents a baseline standard (added alongside CC23/the memory MCP fix): every implementation-backed component (one with swappable implementations registered via the features registry and declaring options-schema) must expose `<comp>_get_config(implementation_id=None) -> {implementation, config, schema, enabled}` and `<comp>_set_config(implementation_id, updates)` on its management MCP server, using the generic `option_schema_to_dict()` helper (foundation/features/options.py) so schema (type/description/required/default/values) is discoverable without implementation-specific tools. memory_mcp.py now follows this (get_config returns schema; the two hardcoded memory_set_hindsight_bank/token tools were removed). Auditing the other two implementation-backed components found: planning_manage_mcp.py has planning_select_implementation but NO get_config/set_config at all, despite planning_api.py already computing implementation_config_status/missing_required for its implementations — there is currently no MCP path to configure a planning implementation (e.g. an API token for a hosted issue-tracker backend). coding_lsp's lsp_manage_mcp.py has lsp_set_language_option/lsp_reset_language_option, but those are scoped to per-language binding options, not implementation-wide config — needs a closer look to confirm it doesn't also need an implementation-level get_config/set_config pair.

## Notes

Follow-up to the memory_mcp.py hindsight-specific-tools fix (this session): user asked whether to standardize the generic get_config/set_config pattern across all implementation-backed components. Standard added to docs/standards/CREATING_A_COMPONENT.md §6: implementation-backed components must expose config generically via get_config/set_config with schema; implementation-specific tools must be registered by the implementation itself via the existing lifecycle-observer/contribution mechanism, never hand-added to the shared <comp>-mgmt file.

RV10 (Codex) reviewed the plan-item-only state and correctly found it incomplete: planning had no get_config/set_config at all, and the coding-lsp audit surfaced a real gap (ag-lsp's mutation-enabled option-schema had no config-write path anywhere — lsp_api.py._is_mutation_enabled() read it but nothing ever wrote it outside hand-editing state files).

Implemented in response to RV10:
- planning_api.py: added planning_get_config/planning_set_config (config+schema+enabled+is_default; VAL-PLN-015/016/017 for unknown-implementation/unknown-option/invalid-type). Wired as planning_get_config/planning_set_config tools on planning_manage_mcp.py. planning_list_implementations now reports is_default via the shared is_default_implementation() helper.
- lsp_config_api.py: added get_config/set_config (dict {ok, error} convention matching this file's existing set_language_option/reset_language_option style, not exceptions). Wired as lsp_get_config/lsp_set_config on lsp_manage_mcp.py. list_implementations now reports is_default.
- foundation/features/registry.py: is_default_implementation() helper (added earlier this session) reused across memory/planning/coding-lsp instead of each component re-deriving desc.raw.get('default').
- docs/standards/CREATING_A_COMPONENT.md §6 and §12 updated to reference the generic get_config/set_config requirement explicitly in the component recipe checklist.
- Tests: tests/unit/planning/test_planning_api.py (TestConfigValidation-equivalent block using a registered synthetic implementation, since planning-local-docs itself has no options-schema) and tests/unit/coding_lsp/test_lsp_config_api.py (registers ag-lsp with its real mutation-enabled schema). Full unit+integration suite for planning/coding_lsp/memory/foundation/lifecycle passes (one pre-existing unrelated test-isolation flake in test_hindsight_provision.py, passes standalone, not caused by this change).

Remaining: planning-local-docs and ag-lsp status-hook payloads were not changed to add details.implementation — that's a separate, smaller consistency nit not required by RV10's findings; left out to avoid scope creep.
