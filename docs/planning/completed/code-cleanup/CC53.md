# Move harness_observability_inventory.py's hardcoded Python entity table into configuration

## Description

src/audiagentic/components/providers/services/session/harness_observability_inventory.py::_build_inventory() hand-authors one HarnessSurfaceCapabilityFact dataclass literal per (provider_id, surface_id) pair -- 20+ entities (opencode x2, codex x2, claude x2, cline, gemini x2, qwen, kilo, copilot, pi x2, goose, openhands, aider, continue x2, antigravity, plandex, roo, zed x2, crush) as a single ~400-line central Python function. This is a direct violation of ARCHITECTURE_STANDARDS.md Section 2 ('Entity declarations belong in configuration, not central Python lists or entity-name conditionals' / 'A descriptor is the canonical source of its component identifier'). Adding a new provider surface today means editing this one Python file rather than declaring it in config where every other provider fact already lives (config/providers/*.yaml).

Worse than a style issue: for the two surfaces that DO have real YAML session_surfaces declarations (opencode-acp in opencode.yaml, pi-community-acp in pi.yaml), this file independently re-declares the SAME category of fact (evidence/validation, lifecycle_source) by hand, with no link to the YAML. This already drifted in practice this session: the pi-community-acp entry here was hand-edited during AS41 work with zero corresponding edit to pi.yaml.

## Steps

1. Introduce a config-owned data source for HarnessSurfaceCapabilityFact entries -- most likely a new YAML file (e.g. config/harness-observability-inventory.yaml) loaded by a small loader function, following the same load-and-validate pattern already used by providers/descriptors/loader.py for provider descriptors. Keep HarnessSurfaceCapabilityFact as the in-memory dataclass; only _build_inventory()'s body changes from a hardcoded dict literal to a loader call.
2. Migrate all ~20 entries verbatim (recipe, candidate_source, probe_anchor, limitations, evidence, lifecycle_source, supported_statuses, platform_evidence) into that YAML, preserving every existing value and inline justification comment as YAML comments.
3. Handle the two surfaces with real session_surfaces YAML counterparts (opencode-acp, pi-community-acp) carefully -- see the Notes section on the deliberate independent-verification role of platform_evidence here. Do not simply fold this file's platform_evidence into the provider's own session_surfaces.validation.platforms; that would make the bypass-prevention check self-referential and defeat its purpose (see session_surface_resolution.py::_get_inventory_proof's own docstring, which explicitly checks this file against what the provider YAML claims). Keep the two declarations in genuinely separate files/owners even after migration, or make an explicit, reviewed decision to merge with a replacement mechanism for that check.
4. Leave get_harness_surface_capability_fact / get_all_harness_surface_facts / is_eligible_transport_observation_publisher / list_eligible_transport_observation_surfaces / validate_harness_observability_conformance / render_harness_inventory_markdown signatures and behavior unchanged -- only the data source underneath _build_inventory() moves.
5. Add a loader-level validation pass (schema/shape check, duplicate (provider_id, surface_id) detection) mirroring existing YAML descriptor loaders in this codebase, so a malformed entry fails fast at load time instead of silently producing a wrong HarnessSurfaceCapabilityFact.
6. Update the two real runtime consumers' tests if data shape changes at all: tests/unit/providers/test_as27_inventory_conformance.py, tests/unit/providers/test_as27_rv770_inventory_gate.py. Confirm harness_status_observer_resolution.py and session_surface_resolution.py need zero code changes (they only call the public functions, never touch _build_inventory directly).

## Detailed Solution & Technical Design

Two real runtime consumers were confirmed by direct grep, not assumed:
- harness_status_observer_resolution.py::resolve_transport_observation_lease() calls is_eligible_transport_observation_publisher(provider_id, surface_id, platform=platform) to gate AS19 Recipe-A observer leases.
- session_surface_resolution.py::_get_inventory_proof() calls get_harness_surface_capability_fact() and checks target_platform in fact.platform_evidence as an INDEPENDENT bypass-prevention gate: 'the surface IS in the inventory but the target platform is NOT listed in its platform_evidence -- meaning YAML claims validation on a platform without local probe proof (the bypass scenario)'. This is the one piece of real design tension in this migration -- it is deliberately checking this file's data AGAINST a provider's own YAML claim (foundation/transports/session_surface.py::SurfaceValidation.platforms / PlatformEvidence, which pi.yaml/opencode.yaml already populate under session_surfaces[].validation). If this file's platform_evidence moves into the SAME YAML the check validates against, the check becomes self-referential (checking a claim against itself) and stops catching anything.

The other ~18 entries (codex, claude, cline, gemini, qwen, kilo, copilot, goose, openhands, aider, continue, antigravity, plandex, roo, zed x2, crush, pi-rpc) have no YAML session_surfaces counterpart at all today -- for those, this file is not 'independently verifying a YAML claim', it is simply the ONLY declaration of the fact, sitting in Python where config belongs. That's the safe, mechanical majority of this migration; the 2-entry overlap is the part needing a documented design decision, not a blocked precondition for the rest.
