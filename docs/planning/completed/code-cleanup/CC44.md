# Remove or re-home the consumer-less foundation workflow.propagation package

## Description

Deep-dive finding 2026-07-18: foundation/workflow/propagation/ (13 modules, ~40KB: engine, rules, rule_evaluator, healing, healing_validator, parents, action_executor, log, log_recorder, propagation_config, workflow_item_api) has ZERO production importers — verified by import grep across src; only its own unit tests (tests/unit/foundation/workflow/test_propagation_*.py) exercise it. Its vocabulary (action_complete_parent, parent_blocking_set) is plan-item parent-completion machinery: domain logic for a planning feature that was never wired. This violates Architecture Standards §3 twice: foundation capability without one consumer (let alone two), and domain-specific (planning) concepts living under a foundation name.

## Steps

1. Confirm no dynamic loading: grep config/ and descriptors for 'propagation' module paths (2026-07-18 check found only an error-resolution string and an unrelated event-bus message). Confirm the planning component has no near-term item that would consume it — if one exists and is real, MOVE the package to components/planning instead of deleting.
2. Default action: delete the package, its tests, and the VAL-WFPROP-003 entry in config/components/foundation/error-resolutions.yaml in one change (migration rule: delete obsolete path + tests together).
3. While in workflow/: verify remaining top-level modules all have consumers (state_machine/transitions/transition_engine/frontmatter/invocation do — verified; actions.py/id_gen.py/interfaces.py/util.py not yet verified — check and include any other orphan in the same deletion).
4. Also delete stale invocation/__pycache__ steps.pyc orphans if a steps.py module was previously removed without its bytecode.
5. Run foundation workflow suite + full unit foundation suite.
