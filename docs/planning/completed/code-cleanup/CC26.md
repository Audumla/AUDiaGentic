# Move free-floating modules into owned packages

## Description

Concrete cleanup plan for free-floating modules in `src/audiagentic/` and `src/audiagentic/foundation/`. This plan applies `ARCHITECTURE_STANDARDS.md` and `OBSERVABILITY_STANDARDS.md` directly: CLI/composition-root code stays CLI-owned, runtime does not absorb optional-component wiring, foundation does not import runtime orchestration/components, tests are exempt from production import constraints, and migration is atomic with no long-lived shims unless explicitly approved.

## Decisions

### 1. Keep `src/audiagentic/launcher.py` as public CLI entry module, but shrink it

Decision: keep `audiagentic.launcher` as the stable executable module for now. Do not move it to `runtime`.

Reasoning: Architecture standards explicitly classify `audiagentic/launcher.py` and `audiagentic/commands/*` as CLI / composition-root code. Composition roots may import any layer and specific optional components. Runtime orchestration must not import specific optional component internals. `launcher.py` currently dispatches command handlers, invokes install/update/refresh flows, and imports component-facing command logic; this is correct composition-root behavior, not runtime behavior.

Concrete solution:

- Leave `src/audiagentic/launcher.py` as the module targeted by `pyproject.toml` and `python -m audiagentic.launcher`.
- Move command implementation functions out of `launcher.py` into command modules under `src/audiagentic/commands/`.
- Keep `launcher.py` responsible only for parser construction, command registration, top-level error handling, and `main()`.
- Add/adjust command modules:
  - `src/audiagentic/commands/install.py` for `_cmd_install` / `_dispatch_install`.
  - `src/audiagentic/commands/update.py` for `_cmd_update` and `_cmd_update_binaries` if no suitable existing update command module exists.
  - `src/audiagentic/commands/mcp.py` for `_cmd_mcp`.
  - `src/audiagentic/commands/job_control.py` for `_cmd_job_control`.
  - `src/audiagentic/commands/session_input.py` for `_cmd_session_input`.
  - `src/audiagentic/commands/release_bootstrap.py` for `_cmd_release_bootstrap`.
  - `src/audiagentic/commands/refresh.py` for `_cmd_refresh` and `_regenerate_provider_configs`.
- If command modules already exist with matching responsibility, extend those instead of creating duplicates.

Options considered:

- Recommended: keep `audiagentic.launcher` stable and split command implementations into `commands/`. Lowest entrypoint risk and aligned with standards.
- Alternative: move all launcher logic to `audiagentic.commands.launcher` and update `pyproject.toml`, MCP launch helpers, docs, and tests. This is more disruptive and only worthwhile if root package must be nearly empty.
- Rejected: move launcher to `runtime`. This violates the runtime/optional-component boundary and misclassifies composition-root logic as orchestration internals.

### 2. Keep `cli_io` reachable from foundation — move it into `foundation`, not `commands/`

Decision: move implementation to `src/audiagentic/foundation/cli_io.py`. **Do not** move it to `commands/io.py` (this reverses an earlier version of this decision after verifying actual callers).

Reasoning: an earlier draft of this decision assumed `cli_io.py` was CLI-boundary-only and proposed `commands/io.py` as the nearest owner. Verified callers (2026-07-09) disprove that: `foundation/contracts/validate_schemas.py`, `foundation/contracts/validate_ids.py`, `foundation/contracts/validate_packet_dependencies.py`, and `foundation/logging/config.py` all import `print_json`/`print_error` directly — i.e. **foundation itself depends on `cli_io` today**. It is also imported throughout `runtime/harness/*` (opencode, pi, rig/embedded), `runtime/update/*`, and `components/providers/*`. Moving it under `commands/` would make foundation and runtime import from the CLI/composition-root layer, which `ARCHITECTURE_STANDARDS.md` §1 prohibits — only the composition root may import downward across layers; foundation and runtime must not import it back. `cli_io` must live at or below the lowest layer that consumes it, i.e. foundation.

The original rejection of `foundation.logging` as a destination still holds — these are `print()`-based CLI-boundary helpers, not logging configuration — so the target is a plain foundation-level module, not `foundation/logging/`.

Concrete solution:

- Create `src/audiagentic/foundation/cli_io.py` containing `print_json`, `print_message`, and `print_error`, moved verbatim from the current top-level module.
- Update all production imports from `audiagentic.cli_io` to `audiagentic.foundation.cli_io`. Known call sites (verified 2026-07-09): `commands/provider_prompt.py`, `commands/launch.py`, `commands/component.py`, `launcher.py`, `runtime/update/runner.py`, `runtime/update/prompt.py`, `runtime/harness/run_common.py`, `runtime/rig/embedded/cli.py`, `runtime/rig/embedded/binaries.py`, `runtime/harness/opencode/install/__init__.py`, `runtime/harness/opencode/runner/__init__.py`, `runtime/harness/pi/runner/agent_run.py`, `runtime/harness/pi/install/__init__.py`, `runtime/harness/pi/install/patches.py`, `runtime/harness/pi/install/config.py`, `components/providers/validate_ids.py`, `components/providers/skill_surfaces.py`, `components/providers/adapters/claude/hooks.py`, `foundation/contracts/validate_schemas.py`, `foundation/contracts/validate_ids.py`, `foundation/contracts/validate_packet_dependencies.py`, `foundation/logging/config.py`.
- Delete `src/audiagentic/cli_io.py` in the same change unless an explicit compatibility exception is approved.
- Tests may import either during migration only if the production module path is still being changed; final production imports should use `audiagentic.foundation.cli_io`.

Options considered:

- Recommended: `audiagentic.foundation.cli_io`, because foundation modules already depend on it, and foundation must not depend on `commands/`.
- Rejected: `audiagentic.commands.io` (the original recommendation in this decision), because it inverts the layer-import direction: foundation and runtime modules would end up importing the CLI/composition-root layer.
- Rejected: `audiagentic.cli.io`, same inversion problem as above, plus unnecessary new package.
- Rejected: `foundation.logging`, because these helpers use `print()` and are explicitly CLI boundary output, not library logging.

### 3. Split `src/audiagentic/paths.py` into foundation path modules

Decision: remove top-level `audiagentic.paths` as production dependency and merge its symbols into the existing `foundation.paths` package.

Reasoning: `foundation/paths/` is not a target to be created — it already exists today as a package with `names.py`, `package.py`, `resolution.py`, `component_paths.py`, and `__init__.py`. This decision is a merge into that existing package (adding `project.py`, adding to `package.py`), not a from-scratch package creation. Project-root and repo-root resolution are shared path capabilities. Existing `foundation.paths` already owns path names, package path resolution, layered resolution, and component path logic. Keeping a parallel top-level `paths.py` creates duplicate ownership and encourages imports outside the foundation path API. The leak is already real, not hypothetical: `foundation/mcp/component_server.py`, `foundation/components/loader.py`, `foundation/logging/config.py`, and `foundation/lifecycle/baseline_sync.py` all currently import `find_project_root`/`find_repo_root`/`REPO_ROOT` from the top-level `audiagentic.paths` module — i.e. foundation code already depends on a non-foundation module for this capability, which is a layering violation independent of the duplication concern.

Concrete solution:

- Add `src/audiagentic/foundation/paths/project.py`:
  - move `find_project_root(start: Path | None = None) -> Path | None` here.
  - keep `.audiagentic` marker behavior using `PROJECT_MARKER_NAME`.
  - keep `AUDIAGENTIC_REPO_ROOT` override behavior if it is still intended to mean active project root.
- Update `src/audiagentic/foundation/paths/package.py`:
  - Note: this file already exists and contains an unrelated function, `find_package_root(start) -> Path` (walks up to a directory literally named `audiagentic`, delegating to `foundation.paths.names.find_package_root`). Do not confuse this with `find_repo_root` (walks up looking for `pyproject.toml` or a `src/audiagentic` layout, i.e. the dev checkout root). Add `find_repo_root` alongside the existing `find_package_root` without disturbing it.
  - move `find_repo_root(start: Path | None = None) -> Path` here if not already present.
  - expose `REPO_ROOT` and `SRC_ROOT` here as import-time constants — confirmed required, not optional: `foundation/contracts/validate_schemas.py`, `foundation/contracts/validate_ids.py`, `foundation/contracts/validate_packet_dependencies.py`, and `foundation/lifecycle/baseline_sync.py` (all foundation) plus `components/ledger/ledger_bootstrap.py`, `components/providers/validate_ids.py`, and `components/providers/adapters/claude/restrictions_loader.py` all import `REPO_ROOT` or `SRC_ROOT` directly from `audiagentic.paths` today.
- Update `src/audiagentic/foundation/paths/__init__.py` to export `find_project_root`, `find_repo_root`, `REPO_ROOT`, and `SRC_ROOT`.
- Update production imports from `audiagentic.paths` to `audiagentic.foundation.paths` or narrower modules. Known call sites (verified 2026-07-09): the eight files listed above, plus `foundation/mcp/component_server.py` (`find_project_root`) and `runtime/rig/embedded/resolution.py` (`find_repo_root`).
- Delete `src/audiagentic/paths.py` in the same change unless compatibility exception is approved.

Options considered:

- Recommended: split project-root and repo-root concerns into `foundation.paths.project` and `foundation.paths.package`. This gives exact ownership.
- Alternative: merge `find_project_root` into `foundation.paths.names`. This keeps file count lower but makes `names.py` less focused.
- Rejected: keep `audiagentic.paths`, because it duplicates foundation path ownership.

### 4. Move `src/audiagentic/foundation/home.py` into `foundation.paths.home`

Decision: move to `src/audiagentic/foundation/paths/home.py`.

Reasoning: `audiagentic_home`, `global_harness_runtime`, `global_log_dir`, and `project_log_dir` are path construction helpers. They are not lifecycle, runtime, or logging behavior. `paths` is the exact package owner.

Concrete solution:

- Create `src/audiagentic/foundation/paths/home.py` with current functions.
- Export functions from `foundation.paths.__init__` if broad path API is desired.
- Update production imports from `audiagentic.foundation.home` to `audiagentic.foundation.paths.home` or `audiagentic.foundation.paths`.
- Delete `src/audiagentic/foundation/home.py` unless compatibility exception is approved.

Options considered:

- Recommended: `foundation.paths.home`, because it preserves focus and avoids overloading `names.py`.
- Alternative: merge into `foundation.paths.names`, acceptable only if team prefers fewer path files.

### 5. Convert `src/audiagentic/foundation/config.py` into a config package

Decision: create `src/audiagentic/foundation/config/` package and move layered config loading to `layers.py`.

Reasoning: `load_layered_config` is a shared foundation capability, but it is not generic path resolution. It combines path conventions, AUDiaGentic home, namespace-to-file mapping, and layered YAML loading. A config package is clearer than placing it under paths.

Concrete solution:

- Create `src/audiagentic/foundation/config/__init__.py` exporting `load_layered_config`.
- Create `src/audiagentic/foundation/config/layers.py` containing current `load_layered_config` implementation.
- Update imports from `audiagentic.foundation.config import load_layered_config` to continue working via package `__init__` if the file-to-package replacement is atomic.
- Ensure no same-name `config.py` file remains beside `config/` package.

Options considered:

- Recommended: `foundation.config.layers`, because config is a distinct foundation capability.
- Alternative: `foundation.paths.config_layers`, if the team views layered config as path resolution. Less preferred because the function loads and validates config content.
- Rejected: keep root `foundation/config.py`, because root already has too many mixed capabilities.

### 6. Keep observability API stable, but package implementation

Decision: create `src/audiagentic/foundation/observability/` package with `timeline.py`, preserving package-level `record_timeline_event` import.

Reasoning: Observability standards require `audiagentic.foundation.observability.record_timeline_event`. Moving to `foundation.event.timeline` would make docs and call sites churn more than needed. A package keeps the public observability capability name while giving room for future observability helpers.

Concrete solution:

- Replace `src/audiagentic/foundation/observability.py` with package directory `src/audiagentic/foundation/observability/`.
- Add `timeline.py` containing `_lock_for` and `record_timeline_event`.
- Add `__init__.py` exporting `record_timeline_event`.
- Update direct file-path assumptions in tests if any.
- No standards doc change required if `audiagentic.foundation.observability.record_timeline_event` remains valid.

Options considered:

- Recommended: `foundation.observability.timeline` plus package export. Aligns with observability standards and gives clear ownership.
- Alternative: `foundation.event.timeline`. Better if timelines are treated as event projections, but conflicts with current standards wording and may confuse event bus vs resource timeline roles.
- Rejected: `foundation.logging`, because timeline records are durable resource history, not logging configuration.

### 7. Split `src/audiagentic/foundation/interaction.py` into package modules

Decision: convert to `src/audiagentic/foundation/interaction/` package.

Reasoning: Current file mixes models, backend protocols, CLI backend, MCP elicitation, persisted request storage, event publication, and public API. This exceeds logic-containment guidance and makes future changes risky.

Note on `cli_io`: do not fold `foundation/cli_io.py` (decision 2) into this package. `cli_io`'s heaviest callers (`print_json` for structured `--json` command output, `print_error` for pre-backend bootstrap warnings in `foundation/logging/config.py`) have nothing to do with ask/respond/push-status semantics and would wrongly couple unrelated foundation modules to the interaction package. Separately, `CliBackend.ask()` and `CliBackend.push_status()` (current `interaction.py` lines 158-211) call raw `print()` (`# noqa: T201`) instead of the shared helper — a real duplication. When splitting into `backend.py`, wire `CliBackend`'s announcement/status lines through `foundation.cli_io.print_message` instead of raw `print()`; leave the `input("> ")` reads as-is since those are genuine stdin reads, not output.

Concrete solution:

- Create `models.py` for `ResponseStatus`, `AskRequest`, `AskResponse`, `PushStatusMessage`.
- Create `backend.py` for `InteractionBackend`, `CliBackend`, `_backend`, `set_backend`, `clear_backend`, and `push_status` backend fallback if cleanly separable. `CliBackend` should import `print_message` from `foundation.cli_io` rather than using raw `print()`.
- Create `mcp.py` for `_mcp_ctx_var`, `_build_elicit_schema`, `_parse_elicit_result`, and `ask_async`.
- Create `store.py` for `interactions_root`, `interaction_path`, `_validate_record`, `read_record`, `write_record`, `_is_expired`, `request`, `respond` persisted-record branch, and `get_response`.
- Create `events.py` or keep internal helper for `_publish` to avoid event import cycles.
- Create `api.py` for public `ask`, `respond`, `push_status` orchestration.
- Add package `__init__.py` re-exporting current public API names so imports like `from audiagentic.foundation.interaction import ask` remain valid as package imports.
- Delete original `interaction.py` file.

Options considered:

- Recommended: split by model/backend/MCP/store/API. This matches responsibilities and keeps public API stable through package exports without a shim file.
- Alternative: smaller split into `models.py`, `live.py`, `store.py`. Less file count, but MCP/backend concerns remain tangled.
- Rejected: move to runtime, because interaction is a foundation capability consumed by runtime/components/CLI.

### 8. Keep `src/audiagentic/foundation/io.py` root for now

Decision: do not move in this cleanup.

Reasoning: `io.py` is coherent and small enough: atomic text/JSON/NDJSON writes plus YAML load/save helpers. It is cross-cutting foundation utility. Moving it now would cause broad churn without enough ownership gain.

Concrete solution:

- Leave `foundation.io` unchanged.
- Do not add unrelated helpers to it.
- Revisit only if it grows into multiple file formats or if a `foundation.files` package is created.

Options considered:

- Recommended: keep root.
- Alternative: create `foundation.files.io`. Not worth churn now.
- Rejected: move to `paths`, because it performs file I/O and parsing, not path resolution.

### 11. Keep `src/audiagentic/foundation/registry_utils.py` root for now

Decision: do not move in this cleanup.

### 12. Dissolve `src/audiagentic/foundation/util.py`

Decision: remove `foundation.util` by moving its two functions to exact owners.

Reasoning: `util.py` is a grab bag and should not survive this cleanup. `deep_merge` already overlaps with path/config merging; `pattern_matches` is event pattern logic.

Concrete solution:

- Move `pattern_matches` to `src/audiagentic/foundation/event/patterns.py`.
- Update event bus imports to use `foundation.event.patterns.pattern_matches` if event bus currently uses or duplicates this logic.
- Move `deep_merge` to `src/audiagentic/foundation/config/merge.py` if config package is created, or use existing `foundation.paths.resolution.deep_merge` only where path-layered mapping requires it.
- Update `foundation.logging.config._deep_merge` to import from `foundation.config.merge` after config package exists.
- Delete `foundation/util.py` after all production imports are removed.

Options considered:

- Recommended: event pattern matching to `event.patterns`, config merge to `config.merge`.
- Alternative: create `foundation.collections` for `deep_merge`. Less clear because current use is config merging.
- Rejected: keep `util.py`, because it invites unrelated helpers.

## Effort & Risk

Medium-high effort because this is an import-surface cleanup across CLI, foundation, and tests. Highest-risk areas:

- `launcher.py`: keep module stable to reduce external entrypoint risk. Extract internals only.
- `foundation.interaction`: behavior risk from splitting async MCP, sync backend fallback, persisted store, schema validation, and event publishing. Split mechanically first; no semantic changes.
- `foundation.config.py` file-to-package conversion: ensure imports from `audiagentic.foundation.config import load_layered_config` still resolve via package `__init__.py`.
- `foundation.observability.py` file-to-package conversion: preserve standards-required API `audiagentic.foundation.observability.record_timeline_event`.
- No long-lived shims: production imports must be updated atomically, and obsolete files deleted in same completed change.

## Standards

Applies:

- `docs/standards/ARCHITECTURE_STANDARDS.md`
  - Layer boundaries: CLI/composition root can import any layer; runtime must not import specific optional components; foundation must not import runtime orchestration/components.
  - Logic containment: split files with too many responsibilities.
  - Migration doctrine: no long-lived backward compatibility shims unless explicitly approved; migrate code atomically.
  - Tests exemption: tests are not constrained by production import boundaries.
- `docs/standards/OBSERVABILITY_STANDARDS.md`
  - Preserve `audiagentic.foundation.observability.record_timeline_event` API or update standards/docs/tests in same change.

Explicit standards conclusion: `launcher.py` is CLI/composition-root code and should not move to `runtime`.

## Notes

Implementation should be done in slices that each leave the system working:

Slice A: CLI and paths cleanup (`cli_io`, `paths`, `home`) plus tests. Do the `cli_io` move first within this slice: `foundation/logging/config.py` and other foundation modules import both `cli_io` and `audiagentic.paths`, so if this slice is applied as more than one commit, sequencing `cli_io` before `paths`/`home` avoids a window where those shared files have been updated for one move but not the other.
Slice B: `foundation.config` package conversion and `foundation.util.deep_merge` relocation.
Slice C: observability file-to-package conversion preserving public API.
Slice D: interaction package split.
Slice E: launcher command extraction, keeping `audiagentic.launcher` public entrypoint.

If reducing risk is more important than reducing root files quickly, do Slice E last because `launcher.py` external command shape is the most visible surface.
