# Make provider descriptor loading resilient to per-provider errors

## Description

Currently, load_providers_from_directory() raises on the first invalid provider descriptor, crashing the entire gateway. One bad YAML (e.g. a malformed ref like '.codex/config.toml') prevents all other valid providers from loading. The loader must wrap each per-provider load in try/except so bad providers are skipped with structured error reporting rather than crashing the process.

Additionally, there is no foundational mechanism for displaying startup errors to the operator. Errors during import go to stderr via logging, but there's no structured way to surface them through MCP or the CLI. A lightweight startup diagnostic registry is needed so that skipped providers and other non-fatal errors are visible.

**Overhead question answered**: Descriptors are loaded once per process at import time (`adapters/__init__.py` calls `load_providers()` at module level). They are NOT loaded per MCP tool call — the in-memory `dict[str, ProviderDescriptor]` is shared across all operations within that process. No per-call overhead exists. The result dict is lightweight (typed ProviderDescriptor instances keyed by provider_id).

**Error display via MCP**: There is no standard MCP protocol mechanism for partial-success responses with embedded errors. The existing error envelope (`ERROR_ENVELOPE_SCHEMA`) is strictly `"ok": False` — failure-only. The closest existing pattern in the codebase is `_config_operation()` in `bootstrap.py`: `{"ok": True/False, "errors": [], "surfaces": [], "provider_configs": []}`. We should extend `gateway_overview()` with a `diagnostics` section carrying residual load errors — this is the operator-facing surface and already aggregates operational state.

## Steps

- 1. Create a module-level _load_errors list in loader.py that collects (path, error) tuples for failed descriptors
- 2. Wrap load_descriptor(path, PROVIDER_SPEC) in try/except in load_providers_from_directory(), appending failures to _load_errors instead of raising
- 3. Log each skipped provider at WARNING level with the file path and error message via the foundation logging module
- 4. Add a get_load_errors() / clear_load_errors() accessor pair on loader.py so other components can query residual errors
- 5. In adapters/__init__.py, after load_providers(), check _load_errors and log a summary if any providers were skipped
- 6. Add an MCP tool (or extend gateway_overview) that exposes residual descriptor load errors to the operator — this is the foundational error display surface
- 7. Update load_providers_from_directory signature/docstring to document the new return contract: returns partial results + logs errors

## Detailed Solution & Technical Design

- **Architecture**: Per-provider try/except in loader.py, central error collector at module level, summary logging in adapters/__init__.py, and a diagnostics section in gateway_overview for operator visibility via MCP.
- **Components**
    - loader.py - per-provider error isolation + _load_errors collector
    - adapters/__init__.py - summary logging after load_providers()
    - gateway_overview() - diagnostics section with residual descriptor load errors
- **Design**: The _load_errors list is a module-level side-channel on loader.py. Each failed descriptor appends (Path, Exception) to it. The load_providers_from_directory function returns partial results (only successfully loaded providers). After loading, adapters/__init__.py logs a summary at WARNING level if any were skipped. gateway_overview() exposes residual errors under a diagnostics key.
- **Mcp Response Pattern**: No standard MCP mechanism exists for partial-success responses. ERROR_ENVELOPE_SCHEMA is strictly {"ok": False}. The codebase precedent is bootstrap.py's _config_operation: {"ok": True/False, "errors": [], "data": ...}. For startup diagnostics, gateway_overview() gains a diagnostics section: {"provider-load-errors": [{"file": "path/to/desc.yaml", "error-code": "VAL-DESC-001", "message": "..."}, ...], "providers-loaded": 12, "providers-skipped": 1}. ok is True when at least one provider loaded successfully — the errors list tells the full story.

## Effort & Risk

- **Complexity**: Low-Medium — the core change is a try/except wrapper, but adding a meaningful error display surface requires choosing where it lives (gateway_overview vs new tool)
- **Risks**
    - Silent failure risk: if we skip too aggressively, operators may not realize a provider was dropped — the MCP diagnostic surface mitigates this
    - Overhead question: descriptors are loaded once per process at import time (not per MCP tool), so the try/except overhead is negligible
