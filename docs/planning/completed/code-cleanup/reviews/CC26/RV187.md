# Evaluate folding cli_io into the interaction package

## Notes

User asked whether foundation/cli_io.py should become part of the interaction package split (decision 7) instead of its own module, so a generic ask/respond/status abstraction isn't tied to the CLI specifically. Read the full current foundation/interaction.py to check. Conclusion: do not merge wholesale -- cli_io's heaviest callers (print_json for structured --json command output in unrelated modules like foundation/contracts/validate_schemas.py, print_error for pre-backend bootstrap warnings in foundation/logging/config.py) are not interaction/ask-response semantics and would wrongly couple unrelated foundation modules to the interaction package. However, found a real, verified duplication while reading the file: CliBackend.ask() and CliBackend.push_status() (interaction.py lines 158-211) use raw print() with noqa: T201 instead of the shared cli_io helper. Added a note to decision 7 so the backend.py split wires CliBackend through foundation.cli_io.print_message instead of duplicating raw print calls.

## Findings



## Conclusion

Decision 7 updated with a note keeping cli_io out of the interaction package but fixing the CliBackend raw-print duplication during the split. No structural change to the package boundaries already decided.
