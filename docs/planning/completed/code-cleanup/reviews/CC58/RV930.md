# Split native tool config projection from genuinely VS-Code-only settings, reuse existing host-adapter isolation pattern

## Notes

Checked current VS Code isolation architecture before assuming CC58's .vscode/coding-lsp/ split needs inventing from scratch. services/host/host_adapter.py already has zero VS Code literals -- workspace-marker/extensions-manifest/extensions-dir all come from config/components/providers/hosts.yaml, with 'vscode' as the only registered host today. providers/surfaces/extensions_json.py (the .vscode/extensions.json writer) sits outside core provider/coding_lsp code, routes everything through get_host_adapter(), and is imported only by the reconcile/install call path -- this is the precedent to copy. MCP under VS Code needs no new surface: it's already provider-scoped (Copilot owns .vscode/mcp.json, Cline owns .cline/mcp.json, each in its own adapter), not host-scoped. Confirmed nothing in coding_lsp currently writes pyrightconfig.json/ruff.toml/.vscode/settings.json -- CC58's projection work is genuinely greenfield, not existing code needing untangling. python-ruff.yaml/yaml-language.yaml's workspace-config-files entries are detection markers today, not write targets.

## Findings

CC58's plan conflates two different things under .vscode/coding-lsp/: (a) pyrightconfig.json/ruff.toml are NATIVE tool config (pyright/ruff's own discovery convention, same category as Qwen's .lsp.json) -- root-level, shared by AUDiaGentic's LSP-managed harness sessions AND VS Code's own Pylance/ruff extensions natively; not VS-Code-specific, so this part belongs in generic coding_lsp projection code, not under a .vscode/ path. (b) .vscode/settings.json glue is the one part that's genuinely VS-Code-only.

## Conclusion

Split the design: generic native-config projection (pyrightconfig.json/ruff.toml) lives in coding_lsp's own projection code, not gated behind a VS Code-only folder. The .vscode/settings.json piece should follow extensions_json.py's existing precedent -- route through the host-adapter (extend HostAdapter with a settings-path method, or add a sibling surfaces/ module) so it's imported only by the host-projection call site, never by coding_lsp_bootstrap.py/runtime_resolver.py directly. This reuses an established isolation pattern instead of introducing a new .vscode/coding-lsp/ convention.
