# CC47 Review — Request changes before implementation

## Notes



## Findings

The architectural direction is sound: moving canonical error text and remediation into a component-owned errors.yaml is a cleaner ownership model than the current split between Python message literals and YAML resolutions. CC47 is also unusually good in its inventorying: it identifies the major construction patterns, the 11 catalogs, the rough static/dynamic split, and the affected standards.

I would not implement CC47 exactly as currently written, though. There are several correctness/design gaps that need to be resolved first. Three are substantial enough that I would treat them as blockers.

Blocking findings
1. The proposed schema assumes one error code has one message, but the codebase does not

This is the biggest issue.

CC47 defines:

VAL-PCAP-010:
  message: "..."
  resolution: "..."

That establishes a functional relationship of:

error code -> exactly one canonical message

But the existing code does not obey that relationship. A concrete example already identified in CC47's own inventory is VAL-PCAP-010. In automation_capabilities.py, the same code is deliberately raised with many different static messages:

automation capability requires family_id
duplicate automation capability family_id
automation capability requires supported_modes
automation capability declares non-public mode
automation capability declares duplicate mode
automation capability requires payload and result contracts
contract-ref/schema variants

All come through the same _error() helper and therefore have the same VAL-PCAP-010 code.

So the proposed "extract each static message into YAML" migration is impossible without either losing information or arbitrarily choosing one message.

CC47 needs an explicit pre-migration code/message-cardinality audit. For every code, determine whether it currently maps to:

exactly one static message;
several static messages;
static + dynamic messages;
only dynamic messages.

Then define policy. My preference would be:

If distinct messages describe genuinely distinct failures, split them into distinct codes.
If they are the same failure with contextual variation, give the code one stable canonical message and put the variation in details.
Only retain an explicit message override where neither of those is reasonable.

That decision needs to precede the ~205-site migration.

2. Phase 1 leaves message required, which undermines the centralization goal

CC47 currently proposes externalizing static messages but postponing optional message parameters until Phase 2.

That leaves migrations such as:

_registry_error(
    1,
    get_error_message("VAL-REG-001"),
)

instead of:

_registry_error(1)

This solves one duplication while creating another: the call now contains both the factory's implicit code identity and a second literal copy of the fully constructed code. Change the factory prefix/component/number and the message lookup can silently point at the wrong entry.

The problem is worse for make_error() because the API already has all the information necessary to construct the code. Current make_error() nevertheless requires a non-empty message, and make_error_factory() also requires the caller to supply one. Direct AudiaGenticError construction likewise requires message.

The optional/canonical-message resolution mechanism belongs in Phase 1, not Phase 2.

I would make the intended contract something like:

make_error(
    prefix="VAL",
    component="REG",
    number=1,
    kind="registry",
)

and:

_registry_error(1)

with the error construction layer resolving the canonical message by the already-computed code.

For direct-code construction, either allow:

AudiaGenticError(code="VAL-PPARSE-001", kind="agent-jobs")

or introduce an explicit error_from_code(...) constructor if keeping the dataclass strict is preferable.

An explicit message= should mean intentional instance override, not be the normal way to obtain the catalog message.

3. CC47 does not handle bootstrap ordering

This becomes critical as soon as errors rely on YAML for their message.

Today the error catalog is loaded near the end of register_all_components(), after component descriptors have already been parsed and validated.

But those earlier operations themselves raise AudiaGenticError. For example, register_from_yaml() uses _component_error(...) for malformed component descriptors before load_all_error_resolutions() has run.

There is another cycle: error_resolutions.py uses the shared load_yaml_file(), while load_yaml_file() itself constructs CFG-IO-* errors through make_error_factory().

So a design where ordinary error construction simply says "look up the message from the loaded registry" has an initialization problem:

load error catalog
  -> load YAML
     -> YAML malformed
        -> construct CFG-IO error
           -> needs error catalog

and components can fail even earlier than that.

CC47 should explicitly define the bootstrap solution. Reasonable options include:

use a minimal catalog parser that does not depend on catalog-backed AudiaGenticError during bootstrap;
load and validate the error catalog before normal component parsing;
retain a very small, explicit bootstrap-error override mechanism.

I would avoid silently falling back to the raw code, because that turns exactly the errors you most need during broken startup into messages like "CFG-IO-001".

Other important changes
4. The claimed backward compatibility is incomplete and currently conflicts with the architecture standard

CC47 says the new loader accepts the old flat format, but it also changes its filename lookup from error-resolutions.yaml to errors.yaml.

Therefore this:

# errors.yaml
VAL-FOO-001: "old resolution"

may be backward-compatible in schema, but an external component still containing:

error-resolutions.yaml

will simply no longer be discovered.

So decide which migration you actually want:

Atomic internal migration: rename all files and callers, do not support the obsolete filename/schema.
Real compatibility window: read both filenames and both schemas, define conflict precedence, test it, and document removal.

The former actually matches the current architecture standard, which explicitly says backward compatibility is not maintained by default and that migrations should remove obsolete aliases/shims unless an external obligation has been documented.

Because custom component-config directories exist, there may be a legitimate external compatibility reason—but CC47 should state it rather than quietly adding permanent compatibility machinery.

5. Catalog loading needs to become strict and transactional

The current loader catches every exception while loading a component's resolution file, logs a warning, continues, and ultimately marks resolutions as loaded.

That was questionable when resolutions were supplementary remediation text. Once errors.yaml becomes the authoritative source of the actual error message, silently ignoring malformed catalogs is much harder to justify.

I recommend:

parse every catalog
        ↓
validate complete entries/codes/ownership
        ↓
validate collisions
        ↓
commit new registry atomically
        ↓
mark registry loaded

A present-but-malformed errors.yaml should be a startup/configuration failure, not a warning followed by a partially populated registry.

Missing errors.yaml can remain legal for a component with no registered errors.

6. Define duplicate-code and configuration-layer semantics

The registry currently effectively has global last-writer-wins behavior.

With structured error definitions, this needs an ownership rule. In particular:

two unrelated components declaring the same code should probably fail;
base + profile definitions for the same owning component may intentionally override one another;
duplicate definitions in the same layer should fail;
loading the same catalog twice should be idempotent.

A small typed entry is preferable to dict[str, dict[str, str]]:

@dataclass(frozen=True)
class ErrorDefinition:
    code: str
    message: str
    resolution: str
    component_id: str
    source: Path

Keeping provenance makes collision diagnostics far better.

7. The proposed _error_code_blocker() example contains dead logic

The plan proposes:

if code in _ERROR_ENTRIES:
    return


entry = _ERROR_ENTRIES.get(code, {})
msg = entry.get("message", code)

After the if, code is guaranteed not to be in _ERROR_ENTRIES, so entry is necessarily {}. The supposedly catalog-derived message can never exist.

The blocker should simply report that no catalog definition exists, including source/config guidance. There is no message to retrieve for an unregistered code.

Also, the sample points to ARCHITECTURE_STANDARDS.md §8, whereas the current public-error rule lives under §4, and ARCHITECTURE_GUIDELINES.md has the YAML-registration rule under §3.

8. to_error_envelope() needs a defined precedence rule, not another lookup

Current _Error.message is mandatory and to_error_envelope() simply serializes error.message. There is therefore currently no concept of "message not overridden."

CC47 simultaneously says:

keep message required in Phase 1;
have to_error_envelope() get a catalog message when not overridden;
keep envelope output unchanged.

Those cannot all describe the same implementation.

I'd resolve the effective message once during error construction:

explicit override supplied?
    yes -> use override
    no  -> require canonical catalog message

Store that resolved value in error.message.

Then:

to_error_envelope(error)["message"] = error.message

remains simple and deterministic. Serialization should not be performing a second configuration lookup.

9. Preserve messages exactly during the migration

The new-schema section prescribes "lowercase, no trailing period."

But many current messages don't follow that convention, and CC47's validation also says to_error_envelope() output remains unchanged.

Those goals conflict.

For CC47, I'd make the migration deliberately behavior-preserving:

Every migrated canonical message initially equals its current emitted static message byte-for-byte.

Do stylistic normalization later, deliberately, where it can be reviewed as an observable-message change.

Testing gaps

The existing tests already do useful code-registration analysis, including AST resolution of make_error/factory codes and separate provider/foundation literal scans.

CC47 should expand its acceptance criteria beyond the proposed generic "schema validation" and "message coverage" tests. I would require one test suite to cover:

one code mapping to multiple current messages is detected before migration;
all emitted public codes across all components/runtime, not just the existing provider/foundation scans, have definitions;
malformed top-level YAML, non-mapping entries, missing fields, empty messages/resolutions, malformed codes;
duplicate codes in different owning components;
available base/profile override behavior;
registry reload/reset behavior so tests cannot leak global definitions;
early-bootstrap errors before normal component registration;
explicit message override versus canonical-message precedence;
exact preservation of migrated static messages;
old filename/schema behavior, only if compatibility is deliberately retained;
no residual static message literals at catalog-backed construction sites except an explicit allowlist;
malformed catalog loading must not leave _ERROR_*_LOADED = True with a partial registry.

The migration script itself should also be tested/idempotent if it is going to remain in the repository.

Phase 2 should probably be smaller than CC47 currently assumes

I would not automatically design YAML string interpolation for all ~107 f-strings.

A lot of:

f"unknown state {new_state} for workflow"

can become:

message: "unknown workflow state"

plus:

details={"state": new_state}

That is better structured, easier to redact, and gives the error code/message greater stability.

Only errors whose variable data genuinely needs to be part of the human-readable message should require templating. If templates are eventually introduced, they need explicit rules around allowed fields, missing substitutions, escaping, and secret/redaction handling.

Recommended CC47 sequencing

I would rewrite the implementation sequence roughly as:

Audit code → message cardinality and classify collisions/dynamic cases.
Define ErrorDefinition, ownership, duplicate/layer semantics, override semantics, and compatibility policy.
Solve bootstrap loading and make catalog loading strict/transactional.
Make canonical-message lookup part of the Phase-1 construction APIs.
Convert the 11 catalogs to errors.yaml, preserving existing text exactly.
Migrate unambiguous call sites to message-less construction; split/generalize colliding codes intentionally.
Add complete coverage/collision/bootstrap tests.
Update normative docs and references.
Run full lint/typecheck/tests plus an explicit residual-message/collision audit.
Create the future item only for genuinely dynamic messages that cannot be represented as canonical message + details.

I would also seriously consider renaming error_resolutions.py and its load_*_error_resolutions APIs to something like error_catalog.py / load_error_catalogs(). Once the module owns canonical messages, resolution-only naming becomes misleading. If there is no documented external API obligation, the project's own migration standard favors updating callers rather than leaving permanent legacy aliases.

Verdict

Direction: approved.
Current detailed design: changes required before implementation.

The centralization itself is worthwhile and feasible. The inventory is strong enough to make the work tractable. But CC47 currently treats the remaining work as mostly a schema/file-rename/mechanical-extraction exercise, when there are three architectural questions underneath it: one-code/many-message semantics, constructor ownership of message resolution, and bootstrap/catalog-loading semantics.

Resolve those three first and CC47 becomes a much safer cleanup rather than a ~300-site migration that risks silently degrading or changing the error contract.

## Conclusion

Request changes before implementation - blocker issues need resolution
