# Bespoke success envelope duplicates MCP-native structured output; redirect to typed return contracts and fix the error path first

## Notes

Verified against the tree at mcp==1.27.0 (pyproject.toml:18). Empirical probes run against the installed FastMCP to establish current outputSchema behaviour rather than reasoning from the plan text. All counts below re-derived directly, not taken from the item.

## Findings

## A. Factual corrections to the item as written

1. **Server count wrong.** Item says "~142 tools across 18 servers". Actual: **143** `@mcp.tool()` functions (tool count is accurate) across **15 registered servers** — enumerated from `mcp-servers:` entries in `src/audiagentic/config/components/*.yaml`. 16 files carry tool decorators; the 16th, `components/agent_jobs/jobs_mcp.py` (1 tool), has no `mcp-servers:` entry in `agent-jobs.yaml` and is unreachable via `_resolve_mcp_server_name`/`all_descriptors()`. Out of CC61 scope, but should be raised as its own item.

2. **`managed_config.py` method name wrong.** Item cites `to_mapping()`. The actual method on `ManagedSyncResult` is `to_dict()` (`foundation/toolchains/config/managed_config.py:188`). `to_mapping()` is a different convention owned by `providers/contracts/*.py`.

3. **`bootstrap.py _config_operation` is not an MCP tool.** It is a CLI command body (`commands/bootstrap.py:86-133`) returning an `int` exit code and calling `print_json()` to stdout, reached from `cmd_config_sync`/`cmd_config_clean`. It is a CLI JSON-output convention, not an MCP-tool precedent, and should not be cited as one. There is no `coding_lsp_bootstrap.py` `_config_operation`.

4. **Step 6 assumes a hook that does not exist — but the framework already provides the capability.** `ERROR_ENVELOPE_SCHEMA` is validated only in `tests/unit/contracts/test_error_envelope.py`; `report_error()` never validates its own output, and neither `log_tool_call` nor `_AutoDescFastMCP.tool()` inspects return values. However, FastMCP's `FuncMetadata.convert_result()` **already calls `output_model.model_validate(result)` on every structured return**. Boundary validation does not need to be built — it needs to be *enabled* by giving tools real return types.

## B. Architectural findings (these change the recommended solution)

5. **The proposed envelope duplicates a protocol-native mechanism (§3 evidence-led scope).** MCP already carries `outputSchema` + `structuredContent` for typed data and `isError` for tool-level failure. `{contract-version, ok, data, errors}` re-implements `isError` + `structuredContent` in the payload body. `contract-version: v1` in every response is ceremony — MCP versions the session, not each result. Rejecting the bespoke envelope also aligns with the standing guidance that the MCP surface must not add capability that already exists a layer down.

6. **Incremental envelope migration violates §4.** "Backward compatibility is not maintained by default. A migration updates all callers and deletes the obsolete API, alias, shim, dual route, and compatibility test." Step 5's incremental rollout across 15 servers, justified by "backward compatible as long as callers look in .data", is precisely the dual route §4 forbids — and these servers are live in this repo's `.mcp.json` (`ag-planning`, `ag-ledger`, `ag-agents-gateway`, `ag-lsp`), so the dual shape would be observable by running agents mid-migration. By contrast, adding a return type to one tool creates no shim and no second route, so typed-return migration *may* legitimately be incremental.

7. **Live secret-leak on the raise path (§4 safety).** Only 2 of 15 servers use `report_error()` (`project_mcp.py` 20 sites, `session_mcp.py` 7). The other 13 let exceptions propagate. Verified empirically: a raised `RuntimeError('secret token=abc123 leaked')` reaches the client verbatim as `Error executing tool X: secret token=abc123 leaked`. mcp 1.27.0 FastMCP has **no** `mask_error_details` setting, so nothing suppresses this. This is a §4 violation ("Errors... must not expose secrets") live in 13 servers today, and is more urgent than the success envelope.

8. **The error-as-return-value pattern blocks typed returns.** Verified: a tool annotated with a TypedDict that returns `report_error()`'s `{ok: False, error, tool}` fails `model_validate` and surfaces as a pydantic ValidationError, not the intended error. The corruption is already visible in the tree — `project_mcp.py:42` is annotated `-> list[dict[str, Any]] | dict[str, Any]`, a union that exists *only* to accommodate the error dict. The error path must be fixed **before** any tool gets a typed return, or the 27 `report_error()` sites break at runtime.

## C. Current baseline is worse than the item states

9. Verified `outputSchema` generation in mcp 1.27.0: bare `-> dict` and `-> list` (the repo's dominant annotation) produce **no `outputSchema` at all**; `-> dict[str, Any]` produces `{"type": "object", "additionalProperties": true}` — a schema that asserts nothing; a TypedDict/dataclass return produces full per-property types with a `required` list. So today essentially all 143 tools advertise either no return contract or a vacuous one. The item's "no validation of MCP return values at all" is correct but understates it: clients are given no return *shape* either.

10. `@log_tool_call` is transparent to this — verified that `functools.wraps` + `inspect.signature(..., eval_str=True)` following `__wrapped__` means a TypedDict annotation under the existing decorator stack produces the full schema and validated `structuredContent`. No decorator rework is needed.

11. Pre-existing duplication worth noting: `ERROR_ENVELOPE_SCHEMA` exists twice — as a Python dict (`contracts/errors.py:201`) and as `contracts/schemas/error-envelope.schema.json` in the registry. Adding a third schema-definition style would compound this.

## D. Ownership constraints on where result types live (§1, §3, §8)

12. §8: "Core and API modules must not import MCP/FastMCP or own MCP-specific constants." A `TypedDict` is a plain typing construct, not an MCP import, so result contracts can and should live with the **owning component's** API/contracts module. §1/§3 forbid parking 143 domain result types in `foundation/mcp` — foundation stays domain-neutral.

13. Do **not** route tool returns through `foundation/contracts/schema_registry.py`. That registry validates *durable records* before persistence; tool returns are transport projections. §3: types unify only on shared ownership, lifecycle, validation, and semantics — these share none of them. (This corrects an earlier suggestion of mine made before the FastMCP behaviour was probed.)

## Conclusion

Do not implement CC61 as written. The direction — standardised, validated, non-blob MCP returns — is right, but the mechanism is wrong: the bespoke `{contract-version, ok, data, errors}` envelope re-implements `outputSchema`/`structuredContent`/`isError`, and its incremental rollout across live servers violates §4's no-dual-route rule.

Redirect to three ordered slices:

**Slice 1 (blocking, atomic, security):** one adapter-level error convention — tools never return error dicts; a single decorator in `foundation/mcp/component_server.py` catches, redacts (reusing the existing `redact_error_envelope`/`redact_text`), and re-raises `ToolError` carrying the stable error code. Delete `report_error()`'s dict-return and the 27 call sites' try/except blocks per §4. Closes the 13-server secret leak and unblocks Slice 2.

**Slice 2 (incremental, legitimate):** per-tool `TypedDict` return contracts owned by each component, replacing bare `dict`/`list`. Yields real `outputSchema` per tool and free boundary validation via FastMCP's existing `model_validate`. No new envelope, no new schema registry, no `wrap_response()`.

**Slice 3 (evidence-led):** partial-success shape modelled explicitly as a field on the specific result contracts that have an evidenced need, not as a universal envelope. §3 forbids the speculative universal `errors: [...]`.

Keep `ERROR_ENVELOPE_SCHEMA` untouched. Correct findings A1-A3 in the item text. Raise the unregistered `jobs_mcp.py` as a separate item.
