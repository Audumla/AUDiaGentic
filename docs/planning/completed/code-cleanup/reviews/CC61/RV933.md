# Slice 2 guidance: required means load-bearing, not always-present; reserve a warnings key and fold Slice 3 into it

## Notes

Third self-review. Corrects guidance introduced by RV932's fold-in.

## Findings

1. **Step 9 encodes the wrong test for `required`.** It says a key that is always present, even as `""`, belongs in the core. That locks in incidental fields: `work` and `skill` are always present on a plan item as empty strings and nothing depends on them, so requiring them converts a harmless frontmatter change into a boundary failure. The test should be whether the caller is broken without the key, not whether it happens to be emitted.

2. **No convention for non-blocking diagnostics.** A tool that succeeded but has something to report currently has nowhere to put it, so 15 components will each invent a name — `warnings`, `issues`, `problems`, `soft_errors`, `non_fatal`. The valuable standardisation here is the *name*, not the shape.

3. **Slice 3 is redundant once that name exists.** Its `failures: list[SurfaceFailure]` field is the same idea with a bespoke type per tool. Fold it in and delete the slice.

4. Asymmetry worth stating explicitly in the item: because extras pass through and the schema is a safety net, adding a key later is free and never breaking. Declaring a key required is the only irreversible move. That single asymmetry is what keeps Slice 2 from ossifying.

## Conclusion

Slim correction, no new machinery. Change the `required` test to load-bearing — the identity and addressing fields a caller needs to act on the response, nothing else. Reserve `warnings` as an optional key for non-blocking diagnostics on an otherwise successful result: never required, omitted rather than empty, loose element shape, no Warning class hierarchy. Blocking conditions raise (Slice 1); non-blocking ones ride in `warnings`. Delete Slice 3 — it is now covered.
