# Reject YAML-driven provider registration and universal lifecycle family

## Notes



## Findings

CC41 proposes generic YAML recipes containing commands/probes/params and automatic ProviderAutomationRegistry registration. This conflicts with the locked boundaries: provider configuration cannot enable execution; RecipeDefinition cannot carry commands/paths/mechanics; there is no universal request/result or lifecycle family; foundation stays provider- and component-agnostic.

## Conclusion

Do not choose declarative-lifecycle, YAML registry extension, or generic CLI adapter. MA20 remains a prerequisite substrate, not dependent on CC41. Reduce CC41 to an optional non-provider, caller-owned typed-step parsing utility only if a concrete component proves repeated need; otherwise cancel it.
