# Keep declarative registrar seam provider-owned and minimal

## Notes



## Findings

['The remaining CC41 Activity 6 wording still risks over-engineering by implying a generic factory could be added to foundation/toolchains. That would cross the boundary if it imports or returns providers RecipeHandler/FamilyRegistrar concepts.', 'Foundation should continue to own only recipe loading/catalogue/materialization/execution primitives. The provider automation adapter that maps typed family requests/results onto those primitives belongs under components/providers/services because RecipeHandler and FamilyRegistrar are provider composition concepts.', 'Harness install policy should stay out of CC41 and MA26 Hindsight recipes. Per owner clarification, each harness manages its own install; Hindsight only configures itself into active harnesses if present/active. CC41 should prove the generic seam only, not implement harness install or production Hindsight/Pi behavior.']

## Conclusion

Narrow Activity 6 to a small providers-side declarative recipe handler adapter/proof. No foundation factory that imports provider types, no universal lifecycle family, no production migrations.
