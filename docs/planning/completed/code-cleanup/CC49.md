# Ledger MCP: get_pending_events with group-by + batch record + fragment lookup

## Description

The ledger MCP server needs improvements to make the "record → sync → commit" workflow efficient and deterministic:

### The core problem — solved by one tool
Every event records `files` (required schema field) and `plan-item-ids` (optional). During commit workflows, the agent must manually read diffs, match files to events, and group commits. The ledger already has all the data to do this deterministically.

### 1. `get_pending_events(group_by="plan-items")` — the one tool that replaces the whole workflow
Returns pending events (fragments + synced current ledger) grouped for commit decisions.

**group_by parameter:**
- **"plan-items"** (default): events sharing plan-item-ids cluster together via transitive closure. A has [PC01], C has [PC01, PC02], B has [PC02] → all three in one group. Events with no plan linkage go to `ungrouped`.
- **"files"**: events touching the same files cluster together. base.py touched by 3 events → one group. Events with unique file sets go to `ungrouped`.
- **"flat"**: no grouping — returns raw list of compact entries.

All modes return de-duplicated file lists per group and compact summaries per event.

### 2. Batch `record_change_event`
The tool already accepts a single event dict. Extend it to accept either a dict or list[dict] — one call returns per-event results. The API already has `record_changes()`; just expose it.

Why: during a recent session, 9 events × 9 syncs → should be 1 call, 1 sync.

### 3. `get_fragment(event_id)`
Retrieve a single fragment by event-id from the fragments dir (before sync) or current ledger (after sync). Returns the full event dict.

Why: inspect what was recorded — "did I include all the files?" — without reading raw JSON.

### What we're NOT adding
- No annotate_commits / git linkage — ledger should not be tightly coupled to git
- No events_for_files — `get_pending_events(group_by="files")` covers this
- No list_fragments — `get_pending_events(group_by="flat")` covers this
- No changes to get_current_summary or get_audit_report — they serve release finalization

## Detailed Solution & Technical Design

### get_pending_events design

**Signature:** `get_pending_events(project_root, group_by="plan-items")`

**Source:** reads current ledger NDJSON only, filters `status == "unreleased"`. This is the single source of truth — after record_change_event auto-syncs, fragments are merged and purged. Reading both would double-count or miss events.

**Return shape (grouped modes):**
```python
{
  "groups": [
    {
      "event-count": int,
      "files": sorted(list(unique file paths across all events in group)),
      "summaries": [
        {"event-id": str, "change-class": str,
         "user-summary-candidate": str,
         "plan-item-ids": [str]}
      ]
    }
  ],
  "ungrouped": [
    {
      "event-id": str,
      "change-class": str,
      "files": [str],
      "user-summary-candidate": str
    }
  ]
}
```

**Return shape (flat mode):**
```python
{
  "events": [
    {"event-id": str, "change-class": str,
     "user-summary-candidate": str,
     "plan-item-ids": [str],
     "files": [str]}
  ]
}
```

**group_by="plan-items" algorithm:**
1. For each event with plan-item-ids, build a frozenset as group key
2. Transitive clustering: if A has {PC01}, C has {PC01, PC02}, B has {PC02} → all merge via union-find
3. Events with no plan-item-ids or empty list go to `ungrouped`

**group_by="files" algorithm:**
1. For each event, build a frozenset of its files as group key
2. Transitive clustering: if A touches {base.py, loader.py}, B touches {loader.py} → they merge
3. Events whose file sets don't overlap any other event go to `ungrouped`

This is purely read-side — no mutations, no schema changes.
