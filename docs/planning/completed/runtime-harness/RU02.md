# Remove components' direct runtime-harness dependency (project + session)

## Description

Product components import runtime.harness directly to call its public forwarding functions (build_runtime_sync, default_config_path, query_rig_server_version, version_info): components/project/project_components.py:27 (now narrowed to a read-only harness_cli_available check), components/project/project_api.py:11, components/session/session_api.py:12, components/session/session_runtime_status.py:18,36,77. This crosses from product components into runtime orchestration -- a layering violation -- even though every call target is already a public facade function in runtime/harness/__init__.py, not an internal.

Use the existing registered capability/composition seam employed by foundation lifecycle, or a narrow composition-root binding, so components depend on a foundation-owned capability rather than the runtime package name directly.
Project and session lifecycle behavior should work when no harness is active.

DESIGN DECISION (this item's own blocker, per its notes: 'Needs a composition-root design decision before this is executable, not a mechanical fix'): TWO CANDIDATE SHAPES, pick one and confirm with the user before implementing broadly -- do not silently choose without discussion, per this session's own established discipline against unreviewed schema churn.

CANDIDATE A -- capability registration (heavier, matches this codebase's existing Registry pattern e.g. source_catalog.py's `_fetchers: Registry[SourceCatalogFetcher]`): define a frozen Protocol/dataclass-of-callables in a new `foundation/capabilities/harness_status.py` (e.g. `HarnessStatusCapability` with fields/methods mirroring the 6 functions above). `runtime.harness` registers its concrete implementation once at process composition time (launcher.py, alongside `register_all_components()`). project_components.py/project_api.py/session_api.py/session_runtime_status.py resolve it via a generic `foundation.capabilities.get_harness_status()` accessor instead of importing `runtime.harness` by name. Pro: matches existing registry idiom, generalizes if a second runtime-orchestration package ever needs the same treatment. Con: real new abstraction layer for 6 functions across 4 call sites -- possibly disproportionate machinery for the actual problem size.

CANDIDATE B -- lighter composition-root indirection: move the boundary INTO foundation as a thin re-export module, e.g. `foundation/harness_status.py` that itself imports from `runtime.harness` (foundation is allowed to depend on nothing, but this would invert that -- so this candidate likely VIOLATES the existing dependency direction foundation/ is supposed to have, since runtime/ sits above foundation/ in this codebase's layering, not below it. Verify this against ARCHITECTURE_STANDARDS.md's dependency table before treating Candidate B as viable at all -- it may be structurally impossible given current layering, in which case Candidate A (or a third option) is the only real choice.

CANDIDATE C (not in the item's original framing, worth considering): question whether this is a real problem at all. The item's own 2026-07-24 audit already concluded 'all current call sites already go through runtime/harness/__init__.py's public forwarding functions, not internals' -- i.e. this is a facade-to-facade import, not a leak into runtime internals. If the ACTUAL architecture rule being enforced is 'no product component may import ANY runtime.* package by name, even its facade,' confirm that rule is written down somewhere authoritative (ARCHITECTURE_STANDARDS.md) before spending effort on Candidate A/B -- if it's not actually a documented hard rule, this item may be lower priority than its P1 suggests, or may warrant being explicitly re-scoped/closed as 'facade access is fine, only internals matter' rather than solved with new machinery.
