# Layering pattern is repo-wide, not a single import; already routes through a public facade

## Notes

Code audit: project_components.py:27 confirmed importing runtime.harness.refresh_harness_config_if_installed as described, but the identical components-importing-runtime.harness pattern also exists in components/session/session_api.py:12,80, session_visibility.py:49,111, session_runtime_status.py:18,36,77, and project_api.py:11. All of these call public forwarding functions exposed by runtime/harness/__init__.py (a facade over runtime/harness/{pi,opencode}/install), not internal module internals -- so the 'violation' is really an open architecture question (should components ever depend on runtime.harness at all, even via its public facade?) rather than a one-line fix. Broadening scope and files to reflect the real footprint; this is not a simple mechanical fix and is left pending for a deliberate composition-root design (e.g. a capability the foundation lifecycle registers into, that runtime.harness populates, so components never import the runtime package name directly).
