# Executed: fixed double-refresh and dishonest return; project_components.py no longer needs the refresh call

## Notes

Fixed both bugs found while investigating this item: (1) refresh_harness_config_if_installed (pi + opencode install modules) always returned True once a harness CLI was on PATH, even when materialize/reload-marker steps raised and were caught -- now returns an honest per-step success boolean. (2) project_components.py's attach_harness_refresh called this function a second time after every install/enable/disable/uninstall -- fully redundant with runtime/harness/__init__.py's own component-lifecycle event subscription, which already performs the identical refresh synchronously during the same call. Removed the redundant call; attach_harness_refresh now does a lightweight harness_cli_available check instead of re-running the refresh, removing project_components.py's need for refresh_harness_config_if_installed specifically (still imports get_harness_type/harness_cli_available, a much narrower read-only dependency). session_api.py's own explicit refresh_harness_config (the user-facing 'mcp-refresh-tool') and session_visibility.py's calls are NOT redundant -- they aren't backed by any lifecycle event -- so they still call the real functions and are unaffected. No test consumed the old harness_config_refreshed key (grep confirmed zero references) so the field was renamed to harness_available without a compatibility shim. Verified via tests/unit/provisioning/test_dynamic_agent_config.py, tests/unit/commands/test_install_core_components.py, tests/e2e/cli/test_mcp_project_server.py -- all green. RU02's remaining scope (session_api.py/session_visibility.py/session_runtime_status.py/project_api.py still importing runtime.harness's facade functions for status/reload/visibility purposes) is unchanged and still needs the composition-root architecture decision from RV775 -- not closing the item, just removing its most consequential example.
