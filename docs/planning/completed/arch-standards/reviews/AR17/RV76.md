# Review AR17: shared runner helpers scope and smoke flow boundary

## Notes



## Findings

Well-scoped follow-up to AR08. The helper inventory (env assembly, log path, JSON envelopes, startup info, supervised run) is specific with signatures — reduces implementation ambiguity.

Concerns:

1. Smoke-check split: Step 4 says both harnesses share "the endpoint check" but keeps per-harness smoke flows separate. Verify before starting that the two endpoint checks (pi's direct-MCP smoke vs opencode's version probe) operate on identical input/output — if they differ in behavior, don't force sharing and document why each retains its own.

2. Error handling surface: run_supervised wraps supervised_run + rig teardown; confirm both runners' process-kill semantics are identical (same timeout, same signal, same tree traversal) before merging into one helper. If pi's teardown differs from opencode's, this helper needs a hook rather than a single implementation.

3. Scope check: after extraction, run_common.py will hold 6+ functions — verify it stays under the ~350-line threshold (std 3). If not, split into sub-modules (e.g. run_logging.py for envelope/path helpers, run_supervised.py for process management).

4. The fixture test (step 5) should capture today's JSON envelope format as a golden file before extraction, not rely on the existing runner code to define expected output.

## Conclusion

Solid scope with clear AR08 dependency. Validate smoke-check equivalence and teardown semantics before extraction; consider module-size guard for run_common.py.
