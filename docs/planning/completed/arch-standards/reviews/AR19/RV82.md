# Review AR19: lifecycle move to foundation with harness seam inversion

## Notes



## Findings

The capability-doctrine realignment is well-argued. Inverting the harness seam first (step 2) is the right atomic-migration approach.

Concerns:

1. **AR02 prerequisite hard dependency** — step 1 says "foundation/capabilities.py exists — created by AR02; if AR02 has not landed, create it here". This means AR19 carries the risk of implementing AR02's capability infrastructure inline, which expands scope from a move to a move+new-mechanism. Resolution: make AR02 an explicit blocking dependency, or define the minimum capabilities.py stub needed (single get_capability dict lookup with registration) as a self-contained 30-line prelude rather than inheriting AR02's full seam design.

2. **Six consumer components re-pointing** — coding_lsp, ledger, memory, project, providers, release all import from runtime.lifecycle. This is a wide blast radius. Risk: regression in one consumer that the test suite doesn't exercise (e.g. lazy imports, optional component paths). Resolution: add an integration-level acceptance check — after move, run each component's bootstrap path and verify lifecycle functions are reachable under new import path.

3. **AR02/AR13 path coordination (step 4)** — these items reference lifecycle files under old runtime/ paths. If they land before AR19, the file references become stale. If after, they reference a deleted location. Resolution: require explicit ordering — AR19 must land first (since it's P1), then AR02/AR13 update their file references to foundation/lifecycle/.

4. **Ledger bootstrap duplication note** — opportunistic check is worth doing but should be a separate item if confirmed, not folded in; keep this PR focused on the move.
