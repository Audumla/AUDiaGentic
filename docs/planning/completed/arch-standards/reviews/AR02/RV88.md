# Review AR02 implementation: provider recipe seam still uses bespoke registry

## Notes

Resolved 2026-07-03. The runtime-local duplicate registry was deleted outright: runtime/lifecycle/provider_recipes.py (and six other stale runtime/lifecycle duplicates) removed; the single reconciler registry now lives at foundation/lifecycle/provider_recipes.py and all test imports were repointed. The reconciler registry intentionally stays separate from foundation/capabilities.py: it is a multi-entry iterate-all collection (refresh_provider_recipes enumerates every registered reconciler), while the shared capability registry is a key -> single-callable lookup with no enumeration API per the RV83-decided SPEC. Converging them would require extending the primitive with prefix enumeration — the contortion AR02 step 6 said to avoid. Rationale recorded in AR02 notes.

## Findings

Bootstrap-order and forbidden fallback import issues appear fixed, but one consolidation gap remains. `runtime/lifecycle/provider_recipes.py` still maintains a private `_reconcilers` registry with `register_provider_recipe_reconciler()` / `clear_provider_recipe_reconcilers()` instead of converging that seam onto the shared `foundation/capabilities.py` mechanism. AR02's design goal was one generic capability registry rather than multiple parallel registration patterns; keeping a second bespoke registry in runtime leaves the codebase with two contribution mechanisms for closely related seams. If the recipe reconciler intentionally stays separate, the item should record why it does not fit the shared capability contract; otherwise fold it onto the shared registry now.

## Conclusion

Core AR02 fixes landed, but seam-consolidation is still incomplete while provider recipe reconciliation keeps its own runtime-local registry.
