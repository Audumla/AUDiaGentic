# Review AR02 implementation: bootstrap order bug and runtime fallback import

## Notes

Verified: RV60/RV83 findings already incorporated into item steps. RV87 issues are active implementation blockers.

## Findings

Two implementation issues found. First, runtime/lifecycle/component_mcp.py resolves `get_capability("providers.mcp-projector")` before `register_all_components()`. In a fresh process this can return `None` before the providers lifecycle observer has imported and registered the capability, so `sync_all_provider_mcp_servers()` exits early and skips first-run MCP projection. `register_all_components()` should run before capability lookup, or bootstrap order must be guaranteed another way. Second, runtime/lifecycle/provider_recipes.py still falls back to a direct import of `audiagentic.components.providers.descriptors.registry` when the capability is absent. That reintroduces the forbidden runtime→optional-component coupling AR02 was meant to remove and weakens the seam by silently bypassing missing registration instead of surfacing or safely no-oping through the capability contract.

Verification (2026-07-03): Both issues confirmed against current code. component_mcp.py:39 resolves capability before line 43's `register_all_components()`. provider_recipes.py:89-96 contains direct fallback import of `audiagentic.components.providers.descriptors.registry` when capability returns None.

Resolution (2026-07-03): Fixed. component_mcp.py reordered to call register_all_components() first. provider_recipes.py returns empty list instead of direct import. Docstrings updated.

## Conclusion

Both issues fixed: (1) bootstrap order corrected — register_all_components() now runs before capability lookup in component_mcp.py; (2) forbidden fallback import removed from provider_recipes.py, returning empty list when capability absent. Docstrings updated to reflect new behavior.
