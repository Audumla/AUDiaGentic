# Cache-invalidation fixture wiring references CP10's fixture, but CP02 is sequenced before CP10

## Notes



## Findings

CP02's MUST FIX step (per RV96) says to wire the new _reset_registration_cache() hook 'into the same fixtures that clear registry state - specifically CP10's planned shared reset fixture and CP05's guard test'. But the agreed implementation order runs CP02 (4th) before CP10 (5th) and long before CP05 (9th) — neither CP10's shared reset fixture nor CP05's guard test exists when CP02 lands. As written, an agent implementing CP02 either blocks on nonexistent fixtures or silently skips the wiring, leaving the exact staleness bug RV96 identified live until CP10 lands. CP10 step 5 already carries the reciprocal obligation ('this reset must also invalidate CP02's cache guard'), so the responsibility is duplicated across items with the ownership boundary unstated.

## Conclusion

Split the responsibility explicitly: CP02 exposes the invalidation hook AND wires it into whatever fixtures clear component/feature registries TODAY (e.g. tests/unit/foundation/conftest.py isolated_features_registry), making CP02 self-consistent at land time; CP10 then re-homes that wiring into its new shared reset fixture (its step 5 already says so). Amend CP02's step to say 'existing registry-clearing fixtures now; CP10's shared fixture takes over later' rather than naming CP10's fixture as the wiring target.
