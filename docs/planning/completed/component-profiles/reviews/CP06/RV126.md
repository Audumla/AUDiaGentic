# CLAUDE.md never regenerated, and the doctrine text documents a profile layout that contradicts the implementation

## Notes



## Findings

Two failures. (1) The doctrine block was added to session.yaml (correct owning component per the item), but CLAUDE.md is unmodified in the working tree — apply_provider_surfaces was never run, so the item's first validation criterion ('Generated CLAUDE.md includes the new doctrine section') is unmet. (2) Worse, the doctrine content is factually wrong about the shipped implementation: it says profile folders live in '.audiagentic/config/component-profiles/' — the code (names.get_profile_component_config_dir + loader) uses '.audiagentic/<profile>/components/'. It also says the profile 'is resolved at harness startup and cannot be changed at runtime', while the actual guard resolves at first register_all_components() call and raises VAL-COMP-010 on mid-process switch — loosely compatible but imprecise. Documentation that names a wrong path is worse than no documentation: an agent following it will create profile dirs the loader never scans. Note RV107 (files-list correction on this item) also remains unaddressed in the completed item's Files list, and RV104 is still open.

## Conclusion

Fix the doctrine body to state the real layout ('.audiagentic/<profile>/components/', or whatever layout survives RV117's cwd fix — coordinate, since RV117 may change where profiles resolve from), then actually run apply_provider_surfaces and verify the CLAUDE.md section renders. Close RV104/RV107 explicitly.
