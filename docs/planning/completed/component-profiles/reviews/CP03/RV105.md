# Profile-root on-disk location is never specified — implementing agent must invent the layout

## Notes



## Findings

CP03 says the profile root 'mirrors the existing config/components/ layout under a subfolder named for the profile' and CP01 hints at resolving '.audiagentic/<profile>/...', but no item in the plan pins WHERE profile roots live on disk: (a) inside the installed package's config/ dir (src/audiagentic/config/components/<profile>/), (b) under the project marker (.audiagentic/<profile>/...), (c) under user home (audiagentic_home()/<profile>/), or some combination. These have very different implications: (a) means profiles ship with the package and aren't user-definable; (b)/(c) mean profile-owned component YAML + Python modules live outside the package, which is exactly why CP03 has the sys.path step — but that step can't be implemented without knowing which root(s) to add. It also interacts with CP04: the existing 3-layer merge (project_local > user_global > package_default) suggests a profile could plausibly exist at multiple scopes — is that supported or explicitly out of scope? An agent implementing CP03 as written must make this load-bearing layout decision alone.

## Conclusion

Blocking depth gap. Before implementation, amend CP03's description/steps to name the concrete profile-root location(s) and search order (recommend: single scope to start — project-level .audiagentic/<profile>/components/ resolved via the CP01 resolver — with multi-scope layering explicitly deferred), and state whether a profile name may resolve at more than one scope. CP04 should then reference the same decision.
