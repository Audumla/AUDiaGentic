# Profile root resolved from os.getcwd(), not project root — breaks any launch where cwd ≠ project root

## Notes



## Findings

loader.py's CP04 layering block builds the profile directory as Path(os.getcwd()) / get_profile_component_config_dir(...) — the profile root silently depends on the process working directory. The launcher explicitly supports running against a different project (--project flag sets project_root = Path(args.project).resolve()), so launching with --project X --component-profile Y from anywhere other than X resolves the profile against the WRONG directory (or none) with no error. names.py even provides resolve_profile_root(project_root, profile_name) taking an explicit project_root, and its docstring says loader.py does the project-root resolution 'so that project root is available' — but loader.py never calls it and never calls find_project_root(); the cwd shortcut contradicts the module's own design. resolve_profile_root() is dead code (zero callers) and additionally has a mkdir side effect — a pure resolver that creates directories on every call, including read-only queries. Secondary: get_profile_component_config_dir() returns a slash-joined string path segment rather than composing Paths, pushing the join (and this bug) onto the caller. The new tests mask all of this by monkeypatch.chdir(tmp_path) in every profile test — they bake the cwd dependence in rather than catching it.

## Conclusion

Thread the real project_root into register_all_components' profile resolution (parameter or the existing find_project_root()), use names.resolve_profile_root(project_root, name) as the single composition point (dropping its mkdir side effect or making creation explicit at install time), and add a test where cwd differs from project root. The doctrine text (see CP06 review) must then be updated to match whichever layout is confirmed.
