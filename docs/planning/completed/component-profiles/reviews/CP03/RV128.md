# RV117's fix was itself wrong (targets[0].parent ≠ project root) — corrected to real project-root resolution; --project-from-outside remains a known limitation

## Notes



## Findings

The change that closed RV117 resolved the profile directory as targets[0].resolve().parent — the parent of the first component-config dir. That only equals the project root when AUDIAGENTIC_COMPONENT_CONFIG_DIRS happens to point inside the project (as the tests arrange via env override); in production with no override, targets[0] is the shipped package config/components dir, so profiles would have resolved to src/audiagentic/config/.audiagentic/<profile>/ — never a user's project. Fixed (2026-07-06): loader.py now resolves the project root via audiagentic.paths.find_project_root() (which honors AUDIAGENTIC_REPO_ROOT, then walks up from cwd to the .audiagentic marker) and composes the profile dir through names.resolve_profile_component_config_dir(project_root, profile); names.resolve_profile_root's mkdir side effect removed (pure resolution); the dead string-segment helper get_profile_component_config_dir deleted. New tests: TestCwdIndependentResolution (AUDIAGENTIC_REPO_ROOT with unrelated cwd; nested-cwd walk-up) plus two subprocess-level CLI tests (tests/integration/runtime/test_component_profile_cli.py) exercising the real entrypoint. Remaining known limitation, deliberate: launching with --project X --component-profile Y from a cwd outside X still resolves the profile against cwd's project (or AUDIAGENTIC_REPO_ROOT), because ~23 lazy register_all_components() call sites have no project_root parameter to thread through. Workaround: set AUDIAGENTIC_REPO_ROOT=X. Threading project_root through the loader API is a design change needing its own item if the --project+profile combination matters.

## Conclusion

Resolved except for the documented --project-from-outside limitation, which is now stated in a loader comment and here. Full unit+integration suite green after the fix (1924 passed).
