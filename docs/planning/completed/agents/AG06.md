# Integration with agent-jobs component

## Description

Wire the agents component into agent-jobs so jobs can reference an agent profile to resolve provider + model for execution.

TERMINOLOGY COLLISION (must resolve): agent-jobs ALREADY uses 'profile' for a different concept. `components/agent_jobs/profiles.py` defines WORKFLOW profiles (profile-id = lite/standard/strict = stage pipelines), and the job request already carries a `workflow-profile` key (see prompt_launch.py:132). This component's 'agent profile' (provider+model binding) is unrelated. Do NOT add a bare `profile-id` key to the job request — it collides with the workflow-profile concept and reads ambiguously. Use a distinct key `agent-profile-id` throughout the request schema, prompt parser, and launch path.

## Steps

['Add `agents` to `depends-on` in `config/components/agent-jobs.yaml`', "Update `prompt_launch.py` to read `agent-profile-id` (NOT `profile-id`) from the job request and call agents_api.resolve_profile; this must coexist with the existing `workflow-profile` handling, not replace it", 'Implement precedence logic: agent-profile-id -> explicit provider/model in request -> default agent profile', 'Add provider enablement check at launch using the existing `is_provider_enabled(project_root, provider_id)` from components/providers/services/provider_config.py (confirmed present — do not reimplement)', 'Add new error codes: `CON-AGJ-001` (no default agent profile), `CON-AGJ-002` (profile references a disabled provider)', 'If the job-request schema is declared in a contract/JSON schema or prompt_syntax, add `agent-profile-id` there too so it parses', 'Validation: launch with `agent-profile-id: default` -> resolves correct provider+model; profile pointing at a disabled provider -> CON-AGJ-002; no agent-profile-id and no default -> CON-AGJ-001']
