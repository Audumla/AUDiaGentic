# record.json vs job.json naming inconsistency; persist provider-id/model-id on transition to running

## Notes

Implementation review of agents_gateway_store.py, runtime/state/paths.py. File layout follows a different convention from agent-jobs.

## Findings

LOW — record.json vs job.json naming: gateway requests store in <request-id>/record.json while agent-jobs uses <job-id>/job.json. The gateway paths (paths.py:86) intentionally diverge from agent-jobs conventions. If future audits compare across stores or if code reuse patches land, this inconsistency is a friction point. Consider renaming to job.json for parity — functionally it doesn't matter but convention matters more than it should.

MEDIUM — provider-id and model-id are set in updates dict via transition_record, but AG10's dispatch sets them inside _dispatch_one_attempt and then calls transition_record in dispatch_request with the outcome dict (which contains provider-id/model-id). The gateway store's transition_record iterates over update keys and redacts error fields — this means provider-id and model-id from the dispatch result ARE persisted. Verified correct: AG10 line 226-228 passes {**outcome, finished-at} as updates to transition_record, and outcome contains provider-id/model-id/output/completion/usage. This is correct.

LOW — append_attempt doesn't check for duplicate profile in the same request: if _try_profile_with_retries fails on a profile and then fallback-profile dispatches, both profiles will appear in attempts list with separate entries. This is the intended behavior per AG10's spec. No issue here.

## Conclusion

No action needed. record.json vs job.json naming divergence is intentional (gateway records are not job records — see AG07 decision notes); not worth unifying names across two deliberately-different schemas. provider-id/model-id persistence on transition confirmed correct by the reviewer's own trace. attempts having multiple profile entries across a fallback sequence is intended behavior.
