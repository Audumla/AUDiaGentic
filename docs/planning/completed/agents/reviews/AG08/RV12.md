# Request contracts — messages field has no consumer; reuse agent-jobs record store

## Notes

Verified adapter input contract across providers/adapters/*/adapter.py and the existing agent_jobs record store.

## Findings

MEDIUM — the request contract's 'messages or prompt-body' field (AG08 fields list, mirrored in AG10) has nowhere to go. Every CLI adapter consumes packet_ctx['prompt-body'] (a string) and synthesizes its own system/envelope text; only local_openai builds an OpenAI messages array, and it builds it INTERNALLY from prompt-body (adapters/local_openai/adapter.py:141 _build_messages). A 'messages' list threaded through the gateway would be silently ignored by 13 of 14 adapters. ACTION for v1: standardize on prompt-body and drop 'messages', OR explicitly flag that supporting 'messages' requires an adapter-contract change first (packet_ctx does not currently carry a messages field).

MEDIUM — AG08 creates agents_gateway_store.py (write_record/read_record/list_records/transition_record/append_attempt_event). agent-jobs already has an equivalent record store + state machine (agent_jobs/records.py, state_machine.py, store). Before adding a parallel store, evaluate reusing/generalizing agent-jobs' store to avoid duplicate persistence + transition logic (Standard 3). See RV11 on AG07.

LOW — schema-registry hedge is appropriate: if component-local JSON schema registration is not cleanly supported, keep validation local for the first slice and note follow-up (as AG08 already says).

## Conclusion

Considered. AG08 updated to drop messages from v1, standardize prompt-body, and require the agent-jobs store/state-machine reuse decision before creating gateway-specific persistence.
