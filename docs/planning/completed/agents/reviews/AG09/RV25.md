# No startup reconciliation for orphaned queued records; thread leak on repeated submit with same profile

## Notes

Implementation review of agents_gateway_queue.py. Confirmed the module-level singleton pattern in agents_gateway_api creates one GatewayQueueManager per process.

## Findings

HIGH — no startup reconciliation: when the MCP/server process restarts (e.g., LSP reconnect, reload), _QUEUE_MANAGER is a fresh empty dict. Persisted queued/running records under .audiagentic/runtime/agent-llm-gateway/<id>/ are completely orphaned — they sit in 'queued' state forever with no worker to pick them up. A future AG13 follow-up or explicit lifecycle step should scan persisted queue depths on startup and either resume workers or transition stuck queued records to failed/rejected. This directly implements the RV15 finding.

MEDIUM — thread accumulation pattern: GatewayQueueManager has no way to be reset or cleared. If the hosting process stays up for days/weeks and thousands of requests are processed, the self._profiles dict grows without bound (each new agent_profile_id creates a _ProfileQueue that is never removed). In practice this is bounded by the number of distinct profiles configured (usually < 10), so it's not a real leak — but for correctness, consider cleaning up _ProfileQueue entries when all running+pending drop to zero.

LOW — resolve_max_concurrency accepts both snake_case and kebab-case via _params_get. agents.yaml params are YAML dicts loaded from config, where keys are typically snake_case. The fallback to kebab-case is defensive but slightly confusing — clarify which case the agent profile schema actually uses.

## Conclusion

HIGH finding accepted and tracked as a separate follow-up item: AG14 (Gateway startup reconciliation for orphaned queued/running records) — same gap RV15 already flagged against AG09, now formally ticketed rather than left as a note. MEDIUM (_profiles dict unbounded growth) accepted as-is per the reviewer's own analysis (bounded by distinct profile count, not a real leak). LOW (dual-case params) intentional — matches the existing execution-policy dual-key convention in adapters/local_openai/adapter.py, documented in the code.
