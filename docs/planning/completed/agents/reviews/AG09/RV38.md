# _publish_lifecycle_event tightly coupled to queue runner; lifecycle event path not test-isolated from dispatch results

## Notes

Implementation review of agents_gateway_queue.py:28-44 and _run_one. Lifecycle events are published inline with queue state transitions, not through a decoupled event facade.

## Findings

MEDIUM — `_publish_lifecycle_event` lives in `agents_gateway_queue.py`, tightly coupling the queue manager to the event bus. It publishes for every state transition: queued (enqueued), started (running), rejected, cancelled (before dispatch), completed/failed (after runner returns). This means every lifecycle event publisher must also be a queue manager, and testing one requires the other.

The event publishing happens inside `_run_one`'s try/except — if `get_bus()` is not initialized or raises on publish, it would bubble up through the worker thread's exception handling. Currently, both `AudiaGenticError` and general `Exception` branches in _run_one transition to 'failed', but they do NOT call `_publish_lifecycle_event('failed')` — they just set state to failed and log. The lifecycle event is only published after a successful runner return (line 251) or for rejected/queued/cancelled-before-dispatch paths.

LOW — If the event bus publish fails silently (no exception but no delivery), there's no way to distinguish 'event lost' from 'worker errored out'. Consider wrapping get_bus().publish() in a try/except that logs but never raises — worker threads should not crash the entire queue because an event subscriber misbehaves.

NOTE — RV18's deferred subscription recommendation was rejected in favor of import-time registration (established convention). This means lifecycle events from MCP-submitted requests work correctly, but if get_bus() is called before initialization, it would crash. No such crash occurs in practice because the event bus is initialized early in the application startup path.

## Conclusion

MEDIUM finding was stale by the time this review ran — verified against current source: the except AudiaGenticError/except Exception branches in _run_one DO call _publish_lifecycle_event('failed', failed) (added in the RV22/RV23 fix earlier this session). The 'tight coupling' framing (queue manager owns event publishing) is an accepted design choice, not a defect — it's the single choke point every request (MCP or event-triggered) passes through, which is exactly why it lives there rather than being duplicated per-caller. LOW finding (publish failure could crash the worker thread) was real and is fixed: _publish_lifecycle_event now wraps get_bus().publish() in try/except, logs, and never raises. Added test_lifecycle_event_publish_failure_does_not_crash_worker (monkeypatches get_bus().publish to raise, asserts the request still reaches its real terminal state). NOTE (import-time registration) already addressed in RV18/RV28's closure — confirmed no crash risk since get_bus() is a lazy singleton with no init-order dependency.
