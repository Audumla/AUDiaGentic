# Queue persistence restart recovery, cancel on running requests, and timeout handling

## Notes

Reviewed against AG09 steps/files, agent_jobs store (jobs_store.py), state_machine.py, and agents_gateway_queue.py stubs. No gateway files exist yet; review is design-only.

## Findings

HIGH — queue persistence across gateway restart: AG09 persists accepted/queued state to disk, but GatewayQueueManager is an in-process Python object. When the MCP/server process exits (e.g., LSP disconnect, reload), all in-memory queues and worker threads are lost while persisted queued records remain orphaned. On restart, there's no mechanism to drain or resume orphaned queued records — they'll sit in 'queued' state indefinitely unless someone manually transitions them. ACTION: add a step to AG09 for gateway startup scan that resumes or rejects orphaned queued records on init.

MEDIUM — cancel of running requests is a no-op with vague semantics: AG09 says 'mark running cancel-requested if provider cancellation is unavailable in first implementation.' This means the run continues even after cancel, but the API returns 'cancelled'. The caller may see unexpected output or side effects from an already-completed run. ACTION: clarify that cancel on running requests is best-effort only; gateway MUST NOT return 'cancelled' for a request that actually completed unless it can detect termination early. Consider adding a cancel-requested flag in persisted record so consumers know the caller intended cancellation, even if provider didn't stop.

LOW — AG09's wait() step covers timeout, but run_llm_request (AG11) also has timeout and neither item discusses what happens to the in-flight worker when the timeout fires. The worker thread will continue until completion; cleanup of orphaned workers on timeout isn't addressed.

## Conclusion

Considered. AG09 now requires startup scan/recovery for orphaned queued/running records, best-effort cancel semantics for running requests, cancel_requested persistence, and timeout behavior where worker continues after wait/run timeout.
