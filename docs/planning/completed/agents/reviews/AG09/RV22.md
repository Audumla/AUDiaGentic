# Gateway queue review — cancel visibility and observability missing

## Notes



## Findings

HIGH — src/audiagentic/components/agents/agents_gateway_queue.py:L246-L257: cancel on running request only updates in-memory pq.cancel_requested and returns the unchanged record. The persisted record does not expose cancel_requested, so status/wait/API callers cannot observe the cancellation intent, and a process restart loses it. Persist cancel-requested=true or an equivalent observable field.

MEDIUM — src/audiagentic/components/agents/agents_gateway_queue.py:L202-L232 runner completion path never checks cancel_requested after provider work finishes. That is okay if completion wins, but tests should assert this explicitly and the returned record should still show cancel_requested was requested.

MEDIUM — src/audiagentic/components/agents/agents_gateway_queue.py has only error logs. The plan requires lifecycle observability logs for submitted/queued/running/completed/failed/cancelled/rejected/stale. Add structured info/debug logs without prompt-body/raw output.

LOW — src/audiagentic/components/agents/workflows.yaml:L14 allows running -> cancelled even though v1 semantics say running cancel is best-effort and should not force terminal cancelled unless execution stops before completion. Either remove that transition or keep it only with a clearly tested early-stop path.

## Conclusion

Fixed. GatewayQueueManager.cancel() on a running request now calls store.mark_cancel_requested() to persist cancel-requested=true on the record (new schema field), not just an in-memory set — observable via read_record/wait/get_llm_request regardless of process/manager lifetime. Added test_cancel_running_request_persists_cancel_requested_flag and test_cancel_running_request_completion_still_wins (explicit 'completion wins' assertion: state ends 'completed', cancel-requested stays true as a preserved-but-not-acted-on intent). Added structured info-level logs (queued, rejected-queue-full, running, finished, cancelled-before-dispatch, cancel-requested) with only request-id/profile-id/state — no prompt-body or output content. workflows.yaml's running->cancelled transition is now genuinely exercised: agents_gateway_dispatch checks the persisted cancel-requested flag between retry attempts and before each fallback profile and transitions running->cancelled itself when set (see RV23 fix) — so the transition stays in the workflow with a real, tested path rather than being removed.
