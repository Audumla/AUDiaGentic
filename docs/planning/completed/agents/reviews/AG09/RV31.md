# Queue lifecycle events can deadlock and record updates can race

## Notes



## Findings

HIGH — src/audiagentic/components/agents/agents_gateway_queue.py:L174-L196 publishes agents.llm.queued while holding pq.lock, and L174-L189 publishes rejected while still in the same lock block. EventBus dispatch is synchronous; a lifecycle subscriber that calls back into gateway cancel/status for the same profile can try to acquire pq.lock and deadlock. Move lifecycle publish calls outside pq.lock after state/pending mutation is complete.

HIGH — src/audiagentic/components/agents/agents_gateway_store.py:L229-L244 mark_cancel_requested and L247-L275 append_attempt both read-modify-write the entire record with no coordination. During a real running request, cancel and dispatch can happen concurrently, so the cancel flag can overwrite attempts or append_attempt/final transition can lose cancel-requested=true. Add a small per-request/thread lock in gateway store or centralize running-request updates through the queue manager so cancel_requested and attempts cannot clobber each other.

MEDIUM — src/audiagentic/components/agents/agents_gateway_queue.py:L28-L44 lifecycle event payload contains only request-id, agent-profile-id, and state. The observability plan asks for provider_id when known, attempt_count, and timing/error summaries. At minimum add provider-id/model-id/error/attempt_count for terminal events so observers can understand what happened without reading record.json.

LOW — src/audiagentic/components/agents/workflows.yaml:L14 still allows running -> cancelled, which is only correct for cooperative cancellation between attempts. Add a test proving a running request that completes after cancel remains completed with cancel-requested=true, while a cancel observed before retry/fallback becomes cancelled.

## Conclusion

Both HIGH findings fixed. (1) enqueue() no longer publishes lifecycle events (queued/rejected) while holding pq.lock — the lock's critical section is now limited to the pending-deque mutation itself; store I/O and event publish happen after release. Verified this was a real reachable deadlock: EventBus dispatch is SYNC by default, so a lifecycle subscriber calling back into cancel()/enqueue() for the same profile would have tried to re-acquire the non-reentrant pq.lock and hung forever. (2) Added a per-request-id threading.Lock (agents_gateway_store._request_lock) wrapping transition_record/mark_cancel_requested/append_attempt's read-modify-write bodies, closing the lost-update race between a concurrent cancel and a dispatch worker's attempt/transition write. Added a 50-iteration x2-thread concurrency regression test (test_concurrent_mark_cancel_requested_and_append_attempt_do_not_clobber) proving neither side's writes are lost. MEDIUM (thin terminal payload) fixed: completed/failed/cancelled/rejected events now carry provider-id/model-id/error/attempt_count. LOW (running->cancelled transition needs a real tested path): now genuinely exercised — agents_gateway_dispatch checks the persisted cancel-requested flag between attempts/fallback candidates and performs that exact transition itself (ties directly into RV23's earlier cancel-aware-retry work); kept in workflows.yaml rather than removed.
