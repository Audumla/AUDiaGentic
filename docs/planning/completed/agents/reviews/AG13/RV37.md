# Gateway docs/status can overstate readiness

## Notes



## Findings

MEDIUM — src/audiagentic/components/agents/agents_api.py:L254-L263 returns configured=True even when there are zero profiles/default_profile_id is None. But src/audiagentic/components/agents/agents_gateway_api.py:L26-L31 will raise RES-AGP-003 for submit without explicit agent_profile_id in that state. Component status should either set configured=False when no default profile exists, or include a clear details.gateway_ready/default_profile_required flag so operators know the default gateway path is unusable.

LOW — src/audiagentic/components/agents/README.md:L38-L40 and src/audiagentic/config/components/agents.yaml:L62 describe the gateway as direct LLM completions. For most providers, execute_provider starts provider adapter/CLI execution rather than a raw chat completion. Reword docs/descriptions to "provider execution through an agent profile" or explicitly call out that only API-style providers behave like a direct chat completion.

LOW — README.md:L57 documents agents.llm.requested as the trigger while final v1 planning expected a gateway-specific topic. If AG12 keeps the broad topic, README should state that publishing agents.llm.requested launches gateway execution.

## Conclusion

Fixed. agent_status's configured now reflects whether a default profile exists (configured = default_profile_id is not None) rather than always True — matches the actual failure mode (submit without an explicit agent-profile-id raises RES-AGP-003 when there's no default). LOW (README/description describe gateway as 'direct LLM completion'): reworded per RV36's identical finding — README now has an explicit CLI-session-vs-API-completion caveat, and agents.yaml's ag-agents-gateway server description changed from 'direct LLM completions' to 'provider execution through an agent profile'. LOW (README documents the broad agents.llm.requested topic): moot — topic renamed to agents.llm.gateway.requested per RV32, README updated to match.
