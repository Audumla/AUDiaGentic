# Cooperative cancellation check only between attempts, not mid-adapter-call; _CancelledDuringDispatch swallowed by queue runner

## Notes

Follow-up implementation review of dispatch.py. AG10 spec says the retry/fallback loop checks cancel-requested between profiles/attempts.

## Findings

MEDIUM — _raise_if_cancelled only fires before each attempt in _try_profile_with_retries (line 182) and before each profile candidate in dispatch_request (line 245). It does NOT fire inside _dispatch_one_attempt, so a long-running HTTP call or subprocess invocation runs to completion even if cancel was recorded mid-flight. The queue runner's finally block discards from cancel_requested (line 273) regardless of what happened — this is safe but the cancelled-flag check only works between retries/candidates. This matches RV15's finding that cancel on running requests is best-effort, but worth explicitly documenting in dispatch_request that in-flight adapter calls are not interruptible.

LOW — _CancelledDuringDispatch is caught by dispatch_request (line 247) and transitions to 'cancelled', but if it fires during _try_profile_with_retries AFTER an attempt has already been appended to the attempts list, the record will show a failed attempt followed by cancelled state. The consumer sees both: one failed attempt AND final state=cancelled. This is correct behavior (the first attempt actually ran before cancel was observed) but worth noting in README/observability docs.

MEDIUM — Model capability check before dispatch still not implemented: resolve_model_selection returns the resolved model dict regardless of whether it matches an actual available model for this provider instance. If profile.model_id='some-nonexistent-model' and resolve_model_selection falls back to provider default (or passes through the unknown ID), the adapter may fail with a provider-specific error rather than a clean validation message.

## Conclusion

MEDIUM (document that in-flight adapter calls aren't interruptible): added to dispatch_request's docstring directly, matching RV15's original best-effort-cancel framing. LOW (attempts list can show a failed attempt followed by cancelled state): correct and intentional — that's an honest record of what actually happened (attempt ran and failed, THEN cancel was observed before the next attempt started); no change needed, already implicitly covered by test_dispatch_stops_retrying_once_cancel_requested's attempts-list assertion. MEDIUM (model capability pre-validation): same conclusion as RV26 — deferred, not blocking, resolve_model_selection already supports an optional catalog= check that isn't wired into dispatch's hot path; adding it means loading/caching a live provider catalog inline, more scope than this slice needs.
