# Model availability check per provider and exception type coverage in retry logic

## Notes

Follow-up review of AG10 after RV13 (Claude). Read providers/services/execution.py, adapters/local_openai/adapter.py, agents_gateway_store.py for record schema.

## Findings

MEDIUM — model availability not validated before dispatch: AG10 resolves model_id from the profile but does NOT check whether the provider actually supports that model. For API-style providers (local_openai), the provider config lists available models; using an unsupported model wastes an attempt and produces a confusing error. ACTION: add a step to validate model_id against provider capability before dispatch, fail early with validation error rather than letting it propagate as a transient failure.

MEDIUM — retry catches only AudiaGenticError but not raw adapter exceptions: AG10 says 'Classify failures from AudiaGenticError code/kind families' and retry on transient. But if an adapter raises a non-AudiaGenticError exception (e.g., JSON decode error, KeyError from unexpected provider response shape), the entire gateway API crashes instead of retrying or marking as terminal failure. The runner in execution.py does catch exceptions internally, but AG10 should explicitly handle unexpected exception types in its dispatch loop.

LOW — packet_ctx source tracking for event path: when a request is created from an event (AG12), the source field will be None by default. Consider whether event-triggered requests need source='event-bus' or similar to distinguish them from direct API/MCP submissions.

## Conclusion

Considered. AG10 now requires model availability/capability validation before dispatch, unexpected exception handling at gateway boundary, source='event-bus' default for event submissions, and tests for those paths.
