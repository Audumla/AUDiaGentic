# MCP blocking tool timeout contract and AG09 cancel-orphan interaction with AG10 retry

## Notes

First review of AG11. Read agents_gateway_api.py (empty stub), agents_mcp.py, foundation/event/event_bus.py for patterns.

## Findings

HIGH — MCP blocking tool timeout: AG11 says 'agent_llm_run blocks until fake completion and returns output.' Through MCP, the client-side transport may have its own timeout (typically 30-60 seconds). A blocking MCP tool that holds indefinitely will either get forcibly cancelled by the client or leave the connection hanging. ACTION: explicitly document a maximum blocking timeout for MCP tools (e.g., 300s configurable) and return 'timeout' terminal state rather than holding forever. The API submit/wait should be recommended over run for long-running requests in MCP contexts.

MEDIUM — cancel-orphan interaction with retry/fallback: AG11's cancel_llm_request is not tied to AG10's retry logic. If cancel fires while a transient failure retry is in progress, the behavior is undefined. Consider whether cancel should interrupt in-flight retries or wait for them to complete (then mark terminal).

LOW — AG12 event path integration: when an external caller publishes agents.llm.requested through the event bus, there's no parallel API call needed. AG11 documents submit/get/wait/cancel/run via MCP tools, but doesn't address how an event-triggered request surfaces its output back to the original publisher (AG12 handles this with lifecycle events, so it's covered — just worth calling out explicitly that run_llm_request is NOT for event-triggered paths).

LOW — agents.yaml direct-tools list needs to include the new tool descriptors before implementation; AG11 steps mention this but it should be part of the validation checklist.

## Conclusion

Considered. AG11 now defines MCP blocking timeout cap, recommends async submit/status for long-running requests, and ties cancel to retry/fallback interruption plus best-effort running semantics.
