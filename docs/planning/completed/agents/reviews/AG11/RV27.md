# MCP tool wrappers not yet implemented in agents_mcp.py; agents.yaml direct-tools list incomplete

## Notes

Implementation review of agents_gateway_api.py and agents_mcp.py. API surface is complete (submit/get/wait/cancel/run/queue_status). MCP tools are the missing piece.

## Findings

HIGH — MCP tool wrappers not yet added to agents_mcp.py: agents_mcp.py still only has resolve_profile, resolve_default_profile, list_profiles. The AG11 spec says 'Extend agents_mcp.py with tools: agent_llm_submit, agent_llm_status, agent_llm_wait, agent_llm_cancel, agent_llm_run' and agents.yaml direct-tools needs updating. The API implementation (agents_gateway_api.py) is complete and ready for MCP wrapping.

MEDIUM — queue_status is a module-level singleton accessor, not project-root aware: _QUEUE_MANAGER.queue_depth(agent_profile_id) takes no project_root and doesn't isolate per-project. If multiple projects' MCP servers share the same process space (unlikely in practice but possible with embedded usage), this would conflate queue state across projects. The status hook in AG13 needs to account for this.

LOW — agent_llm_status (get_llm_request) is a thin wrapper around store.read_record. Per AG08's validation, read_record raises on missing records — MCP tool callers should decide whether 404-style not-found or 'not found' with no state transition is the right UX.

MEDIUM — run_llm_request delegates to submit_llm_request with mode='blocking'. The blocking path in submit_llm_request applies MIN(timeout_seconds, MAX_BLOCKING_TIMEOUT_SECONDS). So a user passing timeout_seconds=600 effectively gets 300s cap. This is intentional (per RV17) but worth documenting in the MCP tool description to avoid confusion about why 'run' returns 'running'/'queued' even when user requested longer.

## Conclusion

HIGH finding resolved: agents_gateway_mcp.py now exists with all 5 tools (agent_llm_submit/status/wait/cancel/run), registered as a new dedicated ag-agents-gateway server in agents.yaml (propagate: audiagentic, per RV20 — not mixed into ag-agents-mgmt or the provider-propagated ag-agents). MEDIUM (300s cap undocumented) already addressed: agents.yaml tool-descriptions for agent_llm_wait/agent_llm_run explicitly state the cap. MEDIUM (queue_status not project-root-scoped) is real — _QUEUE_MANAGER is a single process-wide singleton; deferred to AG13's status-hook design, noted there. LOW (404 semantics) already correct: get_llm_request/read_record raises RES-AGW-001, a proper domain-typed not-found.
