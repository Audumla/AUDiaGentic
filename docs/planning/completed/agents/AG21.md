# Expose enabled component context in agent prompt templates

## Description

Expose enabled component-owned facts to agent prompt templates through a narrow runtime-orchestration seam. A component descriptor declares a context hook; Runtime resolves/invokes it, Foundation sanitizes the returned mapping, and the composed gateway application freezes that mapping at admission. No generic context logic is added to the defunct agent-jobs component, provider adapters, or unrelated component implementations.

## Steps

- Keep context-hook/context-namespace declarative fields on ComponentDescriptor and keep context(project_root) in each owning component.
- Reduce foundation.components.context to pure namespace validation, sanitization, JSON/value validation, and size bounds; it must not discover descriptors, resolve hooks, or invoke component code.
- Add runtime/component_context.py as the generic runtime orchestrator that discovers enabled descriptors and resolves/invokes declared hooks, then applies Foundation validation.
- Inject collect_component_context as a plain ComponentContextReader callable from runtime/bootstrap/gateway_service_composition.py into gateway admission; do not register a configurable service binding for this singleton convention.
- Gateway admission consumes only the injected reader and freezes the returned mapping; retain failure, redaction, and architecture-boundary tests.

## Detailed Solution & Technical Design

Keep descriptor declaration (`context_hook`, `context_namespace`) in Foundation as inert data and keep each `context(project_root)` function in its owning component. `foundation.components.context` owns only pure generic helpers: namespace normalization, section sanitization, and value/JSON/size validation. It must not import the descriptor registry, resolve a dotted hook, or execute a component hook. Add `runtime/component_context.py` to own the generic runtime edge, including `_resolve_context_hook(path)` using importlib, enabled-component discovery, invocation of component public APIs, and application of Foundation validation. Add only a callable type alias/protocol at the gateway admission boundary. Construct `InProcessGatewayApplication` once with `component_context_reader=collect_component_context`; the existing `runtime.bootstrap.gateway_service_composition` is the sole cross-layer import/wiring owner. The gateway application stores the callable and supplies it to internal admission; gateway modules must not import runtime.component_context. This is ordinary fixed process wiring, not a configurable service binding. Admission freezes the reader result as template-context.

## Code Samples & Guidance

Descriptor:
```yaml
context-hook: audiagentic.components.source_control.source_control_api.context
context-namespace: source_control
```

Component API:
```python
def context(project_root: Path) -> Mapping[str, Any] | None: ...
```

Runtime collector:
```python
collect_component_context(project_root) -> dict[str, dict[str, Any]]
```

Gateway handoff:
```python
InProcessGatewayApplication(component_context_reader=collect_component_context)
```

Template:
```text
Repository: {source_control.repository}
Branch: {source_control.branch}
Project: {project.name}
```

## Validation

Prove Foundation context helpers neither import audiagentic.components nor the component registry/hooks and contain no importlib/hook resolution; agents gateway modules do not import runtime.component_context; runtime/component_context.py is the sole generic context-hook resolver; runtime collector honours installed/enabled descriptors, hook failures, duplicate namespaces, redaction and bounds; composed gateway constructs/injects the reader once; fake reader tests prove gateway admission depends only on the callable; no configurable composition binding is introduced; and CREATING_A_COMPONENT documents `context-hook: package.api.context` returning bounded read-only mapping facts or None.

## Effort & Risk

Medium. Valid design with a narrow seam. The schema-closed record is the necessary durability boundary; omitting it would create retry drift. Main risk is accidental code bleed between foundation, gateway, and legacy agent_jobs, controlled with explicit import/architecture tests and one collector call site.

## Standards

Foundation stays component-blind: it owns only descriptor data plus pure context validation/sanitisation. Runtime owns dynamic context-hook resolution and invocation. The gateway composition root is the only cross-layer wiring point; gateway admission consumes an injected callable and freezes one immutable snapshot. Dotted single-brace renderer remains the only renderer. No provider-specific or legacy job/event context enters this seam.
