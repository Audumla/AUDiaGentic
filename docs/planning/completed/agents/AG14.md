# Gateway startup reconciliation for orphaned queued/running records

## Description

RV15 and RV25 both flag the same gap: GatewayQueueManager is an in-process, in-memory singleton (agents_gateway_api._QUEUE_MANAGER). When the hosting process restarts, persisted gateway records left in 'queued' or 'running' state (.audiagentic/runtime/agent-llm-gateway/<request-id>/record.json) become orphaned — no worker will ever resume or fail them; they sit stuck indefinitely. Explicitly deferred out of AG09/AG11's scope per AG09's own effort_risk note; this item is the follow-up to actually implement it.

## Steps

["On agents_gateway_api module init (or an explicit reconcile_gateway_state(project_root) call invoked from a lifecycle/status hook), scan store.list_records() for records in 'queued' or 'running' state.", "For 'running' records: no way to know if the original worker actually finished — transition to 'failed' with a clear 'orphaned after process restart' error (do not silently resume, since the original execute_provider call state is unrecoverable).", "For 'queued' records: either re-enqueue into a fresh GatewayQueueManager (if reconciliation runs at process startup before any real traffic) or transition to 'rejected' with a clear reason, depending on which is safer for the calling context.", 'Add a unit test that seeds a queued/running record on disk (no in-memory queue state) and asserts reconciliation resolves it to a terminal state.', 'Document the reconciliation behavior in the agents README (AG13).']

## Validation

["A record seeded on disk in 'running' state with no matching in-memory queue entry transitions to 'failed' with an orphan-specific error on reconciliation", "A record seeded in 'queued' state is either re-enqueued or transitioned to 'rejected', never left stuck", 'reconciliation is idempotent — running it twice does not double-process already-terminal records']

## Effort & Risk

Mid. Main risk is deciding WHEN reconciliation runs (process startup vs. explicit call) without adding a new always-on background thread — keep it a one-shot function callable from the status hook or an explicit MCP tool, not an automatic timer.
