# Wrap MCP elicitation (ctx.elicit) as the live-ask fast path in foundation.interaction

## Description

The installed MCP SDK (mcp.server.fastmcp.server.Context) already exposes elicit and elicit_url -- the MCP protocol's standard elicitation capability (elicitation/create) for a server to ask the connected client a structured question and get a synchronous answer over the live session. Confirmed via direct inspection (2026-07-05): zero references to 'elicit' anywhere in src/ today. foundation/mcp/component_server.py already wraps the analogous push-side standard methods (ctx.log -> notifications/message, ctx.report_progress -> notifications/progress) via McpOutputBridge, but has no equivalent for the ask side. Elicitation only works while the requesting session is live and willing to block for an answer -- it is not a substitute for FI01's durable store (background jobs, disconnected sessions), it is a faster path to use when a live ctx is available. CORRECTED per review RV113 (2026-07-05, verified against the installed SDK via inspect.signature): Context.elicit's real signature is `elicit(self, message: str, schema: type[ElicitSchemaModelT]) -> ElicitationResult[ElicitSchemaModelT]` -- there is no options= kwarg. MCP elicitation requires a flat, primitive-typed pydantic model (requestedSchema), not a free-form prompt+options pair, and the result carries an action field (accept/decline/cancel) distinct from the answer payload.

## Steps

["Add the elicit-capable branch inside FI01's ask() (same function signature defined there, not a new entrypoint): when called with a live MCP ctx: Context, dynamically build a pydantic model for the request's shape -- an enumerated options list (e.g. ['approved','rejected'] or ['reload-now','later']) becomes a single field typed Literal[*options]; a freeform question (options=None) becomes a single str field. Call ctx.elicit(prompt, schema=<the generated model>) with a bounded timeout.", "Handle ElicitationResult.action explicitly, this is the design-sensitive part: action == 'accept' resolves the interaction as answered with result.data's field value as the answer (no durable record needs to be written -- the whole point of the fast path); action == 'decline' or 'cancel' are REAL ANSWERS, not transport failures -- resolve the interaction as answered-negative/cancelled respectively and do NOT fall back to the durable path (a user declining must not silently re-queue as a still-pending request); only an actual transport error, timeout, or a client that does not support elicitation (client capability check, see next step) triggers the fall back to FI01's request()/get_response() durable path", "Add a capability probe or client-capability check (MCP exposes client capabilities during initialize) so foundation.interaction can decide up front whether to attempt elicitation at all, rather than always trying and catching a failure -- distinguish 'client doesn't support elicitation' (skip straight to durable path) from 'client supports it but errored this call' (log as a real error, still fall back, but do not mask the distinction)", 'Add tests using a mock/stub Context to verify: the accept path returns the answer with no interaction-request file ever written to disk; the decline/cancel paths resolve the interaction record as answered-negative/cancelled without any durable-path fallback; the unsupported-client and transport-error paths correctly fall back to the durable path']

## Effort & Risk

Mid: the elicit/elicit_url API surface is already provided by the SDK, so this is wrapping and fallback-wiring rather than protocol implementation. Main design risk (per RV113) is correctly distinguishing decline/cancel (real answers) from transport/unsupported failures (fallback triggers) -- conflating them would make every user 'no' silently re-queue as a pending request.
