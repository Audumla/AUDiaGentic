# Design and implement foundation.interaction: unified ask/respond/get_response/push_status primitive

## Description

No generic 'communicate with whatever surface is attached' capability exists in foundation today. What exists is scattered and surface-specific: on_progress callbacks (commands/provider_prompt.py, services/lifecycle.py) for CLI push, McpOutputBridge (foundation/mcp/component_server.py:309-331) wrapping ctx.log/ctx.report_progress for MCP push, and agent_jobs/approvals.py's file-backed pending/approved/rejected store for durable job-approval asks -- hardcoded to job-service callers only, not reusable, and binary-only (no open questions). Investigation (2026-07-05) also found MCP elicitation (ctx.elicit / ctx.elicit_url, confirmed present on the installed mcp.server.fastmcp.server.Context) is completely unwrapped anywhere in the repo. This item designs and implements the core foundation module that unifies all of this behind one small API, without yet migrating existing callers (that's FI02-FI05). CORRECTED per review RV112 (2026-07-05): this item must NOT physically move or touch components/agent_jobs/contracts/approval-request.schema.json -- doing so would break approvals.py's still-un-migrated validation before FI03 migrates it, violating ARCHITECTURE_STANDARDS.md section 10's atomic-migration rule (each step must leave the system working). Instead, FI01 CREATES a new, generalized, foundation-owned interaction-request schema (a superset of approval semantics) and touches nothing under components/agent_jobs/; FI03 is solely responsible for retiring/constraining the old agent_jobs schema when it migrates approvals.py onto this primitive.
