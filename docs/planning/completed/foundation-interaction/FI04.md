# Unify push-status across CLI (on_progress/print_message) and MCP (ctx.log/report_progress) surfaces

## Description

Push-side notifications are already correctly implemented per-surface but not unified: CLI code uses ad hoc on_progress callbacks (commands/provider_prompt.py:_print_progress, services/lifecycle.py) calling cli_io.print_message directly; MCP servers use McpOutputBridge (foundation/mcp/component_server.py:309-331) wrapping ctx.log/ctx.report_progress. Callers that want to push a status message today have to know which surface they're running under and call the matching mechanism. foundation.interaction.push_status (added in FI01) should become the one call site, with the surface-specific delivery handled underneath.

## Steps

["Decide the mechanism: either (a) push_status always publishes on the event bus, and each surface (CLI's cli_io, MCP's McpOutputBridge) subscribes and renders, or (b) push_status takes an optional live ctx/sink parameter and delivers directly when one is present, falling back to the event bus otherwise -- prefer (b) for MCP since MCP progress/log notifications are tied to the specific in-flight request's ctx, not a global subscription, matching the constraint already documented in McpOutputBridge", "Migrate commands/provider_prompt.py's _print_progress and its on_progress callback usage in services/lifecycle.py to call foundation.interaction.push_status instead of cli_io.print_message directly", 'Confirm MCP tool call sites already using run_blocking_with_output/McpOutputBridge either keep doing so directly (since it is already ctx-scoped and correct) or route through push_status with ctx passed in -- do not build a second parallel mechanism, converge on one', 'Delete the ad hoc _print_progress/on_progress plumbing once callers are converted, per ARCHITECTURE_STANDARDS.md section 10 (no shims left behind)']
