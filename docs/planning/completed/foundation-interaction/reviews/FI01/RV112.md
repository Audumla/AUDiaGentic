# Schema-ownership move in FI01 breaks approvals.py before FI03 migrates it — violates atomic-migration doctrine

## Notes



## Findings

FI01's step 2 says to 'move schema ownership from components/agent_jobs/contracts/ to a foundation contracts location', and its Files list includes components/agent_jobs/contracts/approval-request.schema.json — yet FI01's own description says it lands 'without yet migrating existing callers (that's FI02-FI05)'. If the schema file physically moves in FI01, approvals.py's validation (still un-migrated until FI03) breaks in the interim, violating ARCHITECTURE_STANDARDS.md section 10 ('Atomic migration — each migration step must leave the system in a working state'). Additionally: FI01's durable store hardcodes '.audiagentic/runtime/interactions/{id}.json'; if CP01 (the .audiagentic name resolver) has landed by then — it is early in the agreed cross-plan order — new foundation code must route through that resolver rather than adding a fresh hardcoded literal that CP01's grep-based validation would then flag.

## Conclusion

Rescope: FI01 CREATES the generalized foundation-owned interaction-request schema (superset of approval semantics) and touches nothing under components/agent_jobs/; FI03 retires/constrains approval-request.schema.json when it migrates approvals.py (its steps already cover this). Drop the agent_jobs schema path from FI01's Files. Add a note that the interactions store path must be built via the CP01 resolver if that item has landed.
