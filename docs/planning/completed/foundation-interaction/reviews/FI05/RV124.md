# Reload triggers on APPROVED status regardless of chosen option — answering 'later' still reloads

## Notes



## Findings

The harness lifecycle handler asks with choices=('reload-now','later') and then triggers request_runtime_reload when resp.status == ResponseStatus.APPROVED. But status does not encode which choice was selected: interaction.CliBackend returns APPROVED for ANY selected choice except the literal string 'rejected' (interaction.py: status = APPROVED if choice != 'rejected' else REJECTED), and McpAskBackend returns APPROVED for any accepted elicitation. So a user answering 'later' produces APPROVED with choice='later' — and the harness reloads anyway, inverting the user's decision. The handler must branch on resp.choice == 'reload-now' (treating everything else — 'later', timeout, no backend — as deferral). Underlying design smell feeding this bug: ResponseStatus conflates 'transport outcome' (answered/declined/timed out) with 'answer semantics' (approved/rejected), and CliBackend's magic-string 'rejected' comparison branches on an entity-ish value (§2 flavor). Mitigating fact: since nothing ever calls set_backend() (RV120), ask() currently always returns TIMED_OUT in production, so the bug is latent — it fires the moment a backend gets wired. The validation scenario 'live MCP session answering reload-now triggers actual reload' was never run and cannot currently pass.

## Conclusion

Change the handler to gate on resp.choice == 'reload-now'. Separately, tighten the ResponseStatus model (transport outcome vs answer) or document that callers must always inspect choice, and add a test covering the 'later' answer path once a testable backend exists.
