# Design gap: sync callers (the harness reload handler) can never reach a live ctx under the stated rules — needs ctx propagation + threadsafe submit

## Notes



## Findings

FI06 as drafted says: sync ask() with a running loop and no ctx returns TIMED_OUT. But the motivating use case for this entire plan — the harness reload ask in runtime/harness/__init__.py _harness_lifecycle_handler — IS a sync caller with no ctx: it runs inside SYNC event-bus dispatch, triggered by install/enable flows that are themselves invoked from MCP tool handlers. Under the drafted rules the reload question never reaches a live MCP client even after FI06 lands — the plan fixes the elicitation mechanics but leaves its primary consumer permanently on the TIMED_OUT path. The missing piece is ctx propagation across the sync boundary, and the codebase already has the right seam: foundation/mcp/component_server.py run_blocking_with_output (verified 2026-07-06, adjacent to McpOutputBridge at component_server.py:309+) already receives ctx and offloads blocking work — meaning sync component code called from MCP tools executes where a threadsafe submit back to the loop is possible. RECOMMENDED RESOLUTION: (1) in run_blocking_with_output, before invoking the blocking callable, stash (ctx, running_loop) in a contextvars.ContextVar owned by foundation.interaction; clear on exit. (2) sync ask() resolution order: explicit ctx arg > contextvar > no ctx. With a contextvar-provided (ctx, loop) and no loop running in the current thread (the worker-thread case), submit the elicit coroutine via asyncio.run_coroutine_threadsafe(coro, loop) and block on future.result(timeout) — this is the standard pattern for sync-in-worker-thread callers. (3) Only if genuinely on the loop thread itself with no way to yield does ask() return TIMED_OUT (that path cannot be awaited without blocking the loop — the drafted rule stays correct for exactly that case). (4) Add a test simulating the harness path: async stub tool handler -> run_blocking_with_output -> sync code calling ask() -> stub ctx elicit answered -> assert the answer arrives.

## Conclusion

Incorporate the contextvar + run_coroutine_threadsafe design into FI06's steps before implementation; without it the item passes its own validation while the feature's reason-to-exist stays dead. Verify at implementation start that the lifecycle MCP tools actually route through run_blocking_with_output (if any invoke sync install_component directly on the loop thread, those call sites must be converted first or the harness ask stays durable-only for them).
