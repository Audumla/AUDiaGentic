# ctx.elicit(prompt, options=...) is not the real SDK API — elicitation takes a schema, and options must map onto one

## Notes



## Findings

Verified against the installed SDK (2026-07-05, inspect.signature): mcp.server.fastmcp.server.Context.elicit has signature (self, message: str, schema: type[ElicitSchemaModelT]) -> ElicitationResult[ElicitSchemaModelT]. There is no options= kwarg as step 1 assumes ('attempt ctx.elicit(prompt, options=...)'). The item needs a concrete mapping layer: FI01's request(kind, prompt, options=[...]) semantics must be translated into a generated pydantic model per ask — e.g. enumerated options become a single field typed Literal[...] (MCP elicitation restricts requestedSchema to flat primitive-typed objects; enum-of-strings is the supported choice shape), freeform questions become a single str field. ElicitationResult also carries an action (accept/decline/cancel) distinct from the answer payload — the wrapper must define how decline/cancel map onto the interaction record (e.g. decline ≠ transport failure: it is a real answer and must NOT trigger the fall-back-to-durable path, or every user 'no' silently re-queues as a pending request). Without this, an implementing agent will discover the API mismatch mid-implementation and improvise the most design-sensitive part of the item.

## Conclusion

Rewrite step 1 to specify: dynamic pydantic-model generation from the interaction request's options/kind (Literal-typed field for enumerated options, str for freeform), and explicit handling for ElicitationResult.action — accept resolves with the payload, decline/cancel resolve the interaction as answered-negative/cancelled (no durable fallback), transport/unsupported-client errors fall back to the durable path. The existing risk note about distinguishing 'unsupported' from 'failed' remains correct and now has a concrete anchor.
