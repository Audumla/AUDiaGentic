# Elicitation wrapper cannot work: run_until_complete on a running loop always fails, and the choice schema is broken pydantic

## Notes



## Findings

Three defects in interaction.py's MCP path. (1) _elicit_sync: when a loop IS running (the normal case — an MCP tool handler inside FastMCP's event loop), it calls loop.run_until_complete(...) on that running loop, which unconditionally raises RuntimeError('This event loop is already running'); the except (asyncio.TimeoutError, Exception) swallows it and returns None → TIMED_OUT. So elicitation fails 100% of the time in exactly the environment it exists for, silently — the precise 'swallow a real error and mask it as timeout' hazard the item's risk note called out. (2) _build_elicit_schema's constrained-choice model raises pydantic ValidationError via ValidationError(_ChoiceSchema, 'msg') — not a valid constructor in pydantic v2 (raises TypeError instead), and validation-in-__init__ is the wrong mechanism anyway; per RV113 the choices should be a Literal[...]-typed field so the elicitation requestedSchema carries the enum and the client can render the options — as written the client sees only a bare string field and never learns what the valid choices are. (3) except (asyncio.TimeoutError, Exception) is redundant (Exception covers TimeoutError) and logs nothing at warning level. Partial credit: decline/cancel are correctly treated as real answers (REJECTED) rather than transport failures, per RV113. But no wiring exists to construct McpAskBackend from a live ctx anywhere (component_server.py untouched, set_backend never called), and there are no tests with a stub Context — both explicitly required by the item.

## Conclusion

Rework _elicit_sync for the in-loop case (the handler is already async in MCP servers — the natural fix is an async ask path, or anyio.from_thread patterns; blocking a running loop cannot work), replace the choice schema with a dynamically-built Literal field model, narrow the exception handling with a warning log distinguishing unsupported-client from real failure, wire McpAskBackend construction into the MCP server plumbing, and add the stub-Context tests. Until then FI02 is not functional.
