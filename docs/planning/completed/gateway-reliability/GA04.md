# Add causal lifecycle decisions and replayable recovery analysis

## Description

Make each request outcome explainable as a causal chain from submission through DOM observations, activity triggers, error conditions, recovery actions, completion proof, or outer timeout. Use the evidence to distinguish provider errors that resolve, false failure decisions, and genuinely unsent requests before changing recovery behavior.

## Steps

- Define decision records for readiness, submission proof, activity classification, completion proof, failure classification, retry/continue eligibility, outer timeout, and terminal lifecycle mutation.
- Correlate provider observations with the current request turn and durable gateway transitions using causal event IDs; record attempted and rejected actions with reasons.
- Design a bounded same-session continuation policy for non-terminal UI conditions such as Stop disappearing, requiring request-owned correlation, no terminal error/auth veto, incomplete response evidence, and an independent retry budget.
- Build an offline analyzer that groups failures by normalized DOM/error pattern and reports resolution rate, missed-completion rate, false-failure rate, time-to-first-activity, and action success/failure.
- Have GPT review the policy and replay traces before implementing automatic continuation.

## Detailed Solution & Technical Design

Treat provider classification as an evidence ledger rather than a boolean. Each decision records inputs, rule/version, outcome, confidence, and causal event IDs. Stop-control disappearance is observation only; completion requires request-owned assistant identity plus completion witness and stable output. If correlation is proven and the UI is recoverable, a bounded same-session continuation may be considered. If identity is ambiguous, remain in observation/reconciliation. Record errors before terminal mutation and retain them if later recovery succeeds.
