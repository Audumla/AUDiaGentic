# Make MCP status and diagnostics compact with explicit detail expansion

## Description

Reduce token waste and client processing by separating cheap lifecycle status, compact request/session summaries, evidence summaries, DOM observation exports, and full historical diagnostics. Defaults return only what an agent needs to poll and decide its next action; verbose evidence and history require explicit opt-in.

## Steps

- Audit gateway MCP tools for duplicated structured/unstructured data, response previews, repeated diagnostics, nullable fields, and historical payloads that are not needed for polling.
- Make status and list tools return compact lifecycle/activity/session correlation fields by default; keep exact response retrieval separate and explicit.
- Add explicit detail controls such as include_evidence, include_observations, include_history, limit, and since_sequence/cursor. Provide a separate observation export tool instead of embedding DOM journals in status.
- Align overview and session/request lists so summaries contain counts and latest bounded facts only; add contract tests measuring omission of large/duplicate fields.
- Document the token-oriented MCP contract and update direct-tool provisioning/catalog tests.

## Detailed Solution & Technical Design

Use three MCP tiers: poll with request id, lifecycle, activity, activity sequence/time, session id, and terminal outcome; summary with bounded failure classification and latest observation facts; evidence with journal pages, DOM artifact references, transition history, and full response only when explicitly requested. Default status should not fetch response content. Cursor-based reads prevent replaying the same large history.
