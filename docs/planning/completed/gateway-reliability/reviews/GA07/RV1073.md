# Trace finding: duplicate durable user DOM node broke request correlation

## Notes

This occurred while obtaining a fresh GPT review. The review answer itself was visible in CDP but the gateway request remains failed and is not counted as a completed review.

## Findings

- CDP inspection of req_example_cab77a75ed58 showed message nodes in visual order: user 00000000-0000-4000-8000-bc2482721aea, assistant 00000000-0000-4000-8000-86b549dd8f11, then a second user node with the exact same durable user UUID.
- The DOM duplicate made the snapshot report a later user turn, so valid terminal answer correlation failed with ProviderBindingIntegrityError / CON-AGW-156 despite the review answer being fully visible and terminal in CDP. The request remains failed and is not counted as a completed review.
- Implemented deduplication only for identical role + durable provider message ID, retaining first conversation-order position and preferring a painted copy over a hidden/virtualized copy. Synthetic IDs are not deduplicated. Distinct durable user IDs remain separate turns.
- Added a Playwright snapshot regression that reproduces user/assistant/duplicate-user order and asserts the duplicate collapses, plus a distinct-ID case asserting the later prompt remains a turn.
- Validation: snapshot fallback DOM suite and focused provider-capture, observability, watchdog, project-discovery, and bridge-turn suites pass; F821 and diff-check pass.
- Preserve the foreign-turn fence; do not treat equal text or synthetic IDs as proof of one message.

## Conclusion

A GPT review reply was visible and complete in the correct AUDiaGentic project conversation, but the gateway correctly refused to associate it after its bound assistant ID changed and ordered ownership could not be proven. The failed attempt shows the trace needs stronger bounded message-order evidence before safely accepting or rejecting such remounts.
