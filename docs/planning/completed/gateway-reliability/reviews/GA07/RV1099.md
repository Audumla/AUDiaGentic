# Shared startup-lock timeout releases another thread's lock and masks timeout errors

## Notes

Final evidence audit2026-10-21 against published254dea369 (implementation2dd0c4bab/35cffe082), retained request records and current tests. Historical incident evidence preserved; closure means finding incorporated/explicitly tracked, not that every historical failed request was rewritten.

## Findings

Current StartupLock.__enter__ calls _release_thread_lock after acquire(timeout) returns false. That helper unconditionally calls lock.release(), releasing the actual holder's in-process mutex. TO-PROC-002 is emitted dynamically by _process_error but has no error resolution registration; persisted BigCherry failures show the resulting ValueError. Add a timed-contender concurrency regression, separate reference release from acquired-lock release, guarantee reference release if filesystem unlock raises, and register process lock timeout in foundation.

## Conclusion

StartupLock timeout reference release no longer unlocks actual holder; mutex released even filesystem unlink failure; TO-PROC-002 and RES-PROC-001 registered. tests timed_out_waiter_preserves_holder_lock_and_reference and filesystem_unlock_failure_does_not_leak_thread_mutex cover primitive. Published35cffe082, source audited and focused primitive suite rerun.
