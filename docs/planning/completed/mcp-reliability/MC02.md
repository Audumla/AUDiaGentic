# Prevent status hooks from introducing future unbounded work

## Description

project_status invokes every installed component's status hook sequentially. One Agents hook caused the Pi timeout by spawning Git in the request path. Other hooks could introduce subprocesses, network probes, locks, or large filesystem scans later.

Status-hook contracts should explicitly require local, bounded, read-only inspection. External probes should be cached or exposed as separate operations.
Add per-hook timing diagnostics and tests that exercise all installed hooks through the canonical MCP launcher.
Do not fix this by merely increasing Pi-mcp-adapter's 60-second request timeout.

## Steps

['Define status-hook contract: local, bounded, read-only inspection only', 'Add per-hook timing diagnostics to project_status', 'Write tests exercising all installed hooks through canonical MCP launcher', 'Document status-hook contract in architecture standards']

## Detailed Solution & Technical Design

### Current failure mode (already fixed, need guardrails)

- The Agents status hook spawned `git rev-parse` inside the status request path
- This caused Pi's 60-second timeout to fire in Git-heavy repos
- `project_status` invokes **every** installed component's status hook sequentially
- If one hook hangs, the entire project_status response hangs

### Future risks from other hooks

Any installed component could introduce:

- Subprocesses (Git, package managers, external tools)
- Network probes (health checks, remote MCP status, API calls)
- Filesystem locks (waiting for exclusive access to config files)
- Large filesystem scans (crawling directories, reading large files)

### Status-hook contract

Status hooks **must** be:

1. **Local**: no subprocesses, no network I/O, no external process coordination
2. **Bounded**: complete within a deterministic time bound (target: <500ms per hook)
3. **Read-only**: no mutations to filesystem, state, or configuration

### What to do with external probes

- Cache results from previous runs (with staleness indicator)
- Expose as separate MCP tools (e.g., `probe_git_status`, `check_remote_mcp`)
- Never block the status path on external dependencies

### Per-hook timing diagnostics

- Log start/end time for each hook invocation
- Include hook name and component ID in timing output
- Flag any hook exceeding 500ms as a warning
- Aggregate total hook execution time in project_status response
