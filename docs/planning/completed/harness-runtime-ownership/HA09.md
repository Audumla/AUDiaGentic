# Add Pi surface.py so component-declared contributions reach SYSTEM.md

## Description

8 components today declare `contributions:` in their component YAML (memory, session, planning, agents, agent-jobs, agent-ledger, source-control, release) -- a fully generic mechanism (components/providers/surfaces/contributions.py::load_surface_contributions walks every installed+enabled component's YAML automatically; zero provider-specific code needed on the contributing component's side). Every one of these contributions is correctly rendered into Claude/OpenCode/Cline/Codex/Aider/Roo/local_openai (the 7 providers with a components/providers/adapters/<id>/surface.py registering render_contributions). Pi has no surface.py, so every one of those 8 components' contributed content is silently dropped for Pi specifically -- never reaches SYSTEM.md. This is live content loss today, not a speculative gap. User directive (2026-07-25): any provider with a matrix of component-contributed needs must expose this surface, matching every other provider -- Pi should not be the exception.

## Detailed Solution & Technical Design

Scope is deliberately narrow -- this is NOT part of HA07's larger materialize-ownership deep cut, and should land independently of whether HA07 proceeds. It's a straight port of an already-proven pattern (7 providers already have it) to the one provider missing it, gated only by the path-resolution wrinkle in step 2. If HA07 lands first and moves materialize ownership into providers/adapters/pi/materialize.py, this item's surface.py registration and wiring call move there too -- either order works, this item doesn't need to wait.
