# Adoption/collision/cross-kind test suite for harness materialize outputs

## Description

HA01's original Detailed Solution called for adoption/collision/cross-kind test coverage of harness config materialization that was never written. Definitions, grounded in this codebase's existing vocabulary (see components/providers' managed-config adoption/collision doctrine, e.g. MA34/managed-config-consistency plan, and the now-deleted tests/integration/harness/test_harness_mcp_lifecycle.py which used exactly this cross-kind pattern for the mechanism this session retired):
  - ADOPTION: when materialize writes into a file/location that already has pre-existing, non-AUDiaGentic content (a user's own customizations, or content from before AUDiaGentic was installed), the write must not destroy it -- either by writing only a clearly-scoped managed region (the pattern operate_provider_surfaces/apply_managed_blocks already uses for AGENTS.md contributions), or by full-rebuild ONLY of files that are exclusively AUDiaGentic's to own (models.json, settings.json, .opencode/config.json -- confirm each is actually AUDiaGentic-exclusive, never hand-edited by a user, before asserting full-rebuild is safe).
  - COLLISION: two different owners (e.g. two components, or two providers) targeting the same file/path must not silently clobber each other. A known LIVE collision risk is already flagged in code: runtime/harness/opencode/install/__init__.py's comment (~line 103-108) notes opencode's would-be .mcp.json target 'collides with pi's PROVIDER mcp_config target' -- this specific comment is what prompted the (confirmed-correct) decision that opencode never writes bare .mcp.json at all. Write a regression test asserting this stays true (opencode materialize never creates a bare .mcp.json at the project root) so a future change can't silently reintroduce the collision.
  - CROSS-KIND: every guarantee above must hold for BOTH pi and opencode uniformly, parametrized -- not proven for one and assumed for the other. Mirror the parametrize/component_sandbox pattern from the now-deleted tests/integration/harness/test_harness_mcp_lifecycle.py (git history has the full file if useful as a structural reference) and tests/integration/providers/test_provider_surface_lifecycle.py (a currently-live example of the same cross-provider parametrization style, still in the tree).

## Detailed Solution & Technical Design

This item is validation-only -- it should not require production code changes unless it uncovers a real adoption/collision bug (in which case, stop and open a review per this project's review-before-fix convention rather than silently patching). Place new tests under tests/integration/harness/ (matching where the now-deleted lifecycle suite lived) or tests/integration/provisioning/ if that fits the existing layout better -- check both directories' current contents first to pick the right home rather than creating a third location.

Gate appropriately: if a test needs to invoke component lifecycle events (install/enable/disable) against a real project sandbox, it likely needs the same Docker gate the deleted test_harness_mcp_lifecycle.py used (AUDIAGENTIC_DOCKER_TESTS=1) -- do not weaken or bypass that gate on the host per this project's standing rule (validate env-mutating tests in Docker, never override the gate on the host). Pure adoption/foreign-content tests that only call materialize_agent_config directly against a tmp_path (no real component lifecycle events, no real harness CLI) likely do NOT need the Docker gate -- most of tests/unit/provisioning/test_dynamic_agent_config.py already runs this way on host. Default to the lighter-weight (non-Docker) form wherever the test doesn't genuinely need a live lifecycle event or a real harness CLI on PATH.

Skeleton for the foreign-content-survives test (both harnesses materialize via the same (target, harness_cfg, *, project_root) shape -- pi's is runtime.harness.pi.install.config.materialize_agent_config, opencode's is runtime.harness.opencode.install.materialize_agent_config -- import path differs, call shape doesn't):

  import json
  import pytest

  @pytest.mark.parametrize("harness_type", ["pi", "opencode"])
  def test_settings_or_config_survives_foreign_keys(harness_type, tmp_path):
      project_root = tmp_path / "project"
      harness_root = tmp_path / "harness"
      project_root.mkdir()
      harness_root.mkdir()

      if harness_type == "pi":
          from audiagentic.runtime.harness.pi.install.config import materialize_agent_config
          target_file = harness_root / "agent" / "settings.json"
          harness_cfg = {"rig": {"model": "qwen3.5-0.8b", "port": 42001, "provider": "audiagentic"}}
      else:
          from audiagentic.runtime.harness.opencode.install import materialize_agent_config
          target_file = project_root / ".opencode" / "config.json"
          harness_cfg = {"rig": {"model": "qwen3.5-0.8b", "port": 42001, "provider": "audiagentic"}}

      # Pre-seed foreign, non-AUDiaGentic content before AUDiaGentic ever writes here.
      target_file.parent.mkdir(parents=True, exist_ok=True)
      target_file.write_text(json.dumps({"userOwnedKey": "do-not-touch"}), encoding="utf-8")

      materialize_agent_config(harness_root, harness_cfg, project_root=project_root)

      data = json.loads(target_file.read_text(encoding="utf-8"))
      assert data.get("userOwnedKey") == "do-not-touch", (
          f"[{harness_type}] materialize clobbered foreign content instead of preserving it: {data}"
      )
