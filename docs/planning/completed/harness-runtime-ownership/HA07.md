# Register the rig as a model source; project it into any AG-CLI-capable provider through the standard pipeline

## Description

The rig (AUDiaGentic's local embedded model) is currently delivered to Pi/OpenCode via a bespoke, per-provider pipeline (components/providers/adapters/{pi,opencode}/local_rig_config.py) that duplicates a schema/rendering/delivery mechanism already built for vendor models (MO17/18/19's ModelProjectionEntry -> render_<id>_model_entry -> write_<id>_models pipeline). This item unifies them: register the rig as a model source (source_id="ag-rig") in .audiagentic/config/model-sources.yaml, so enabling the rig for any provider becomes the identical operation as enabling OpenRouter for that provider -- reusing the existing typed contract, renderers, and managed-config writers rather than local_rig_config.py's separate construction. Delivery stays capability-gated per provider: launch-time isolated injection where a provider supports it (OpenCode's OPENCODE_CONFIG_CONTENT, extended to also carry a "provider" block, not just "mcp"), directory-scoped durable write otherwise (Pi, via its existing per-request PI_CODING_AGENT_DIR redirection for agent/ACP launches, or the shared global harness runtime for interactive launches). local_rig_config.py is deleted once equivalence is proven, not templated or kept as a parallel mechanism. See detailed_solution for the full evidence trail (four converging revisions, all confirmed against real code/CLI behavior this session) and notes for the chronological record.

## Steps

- 1. Treat ag-rig as a standard project-scoped `local-endpoint` source using `connector: openai-compatible`, a declared model id, and the rig’s `/v1` base URL.
- 2. At materialization, upsert that source’s current model/base URL from the project harness configuration, then build the normal ModelProjectionRequest through build_model_projection_request.
- 3. Delete computed catalog discovery and public_materialize’s inline ModelProjectionEntry builder; the rig does not require a catalog resolver or a special source class.
- 4. Align each provider’s registered projection target/renderer with the config consumed by its launch, then remove local_rig_config model writers after equivalence tests.
- 5. Keep adapter install modules only for non-model assets and generated surfaces; add source/projection ownership and preservation tests.

## Detailed Solution & Technical Design

HA07 implementation plan — one OpenAI-compatible endpoint path, no local rig writer:\n\n1. Extend the existing `ModelProjectionRequest` with an optional, request-scoped `config-path` override. This is not a new family: it tells the existing managed model-projection family where the provider’s launch-visible config is for this materialization. Preserve the descriptor path as the default for ordinary source sync/status.\n\n2. Thread that override through `providers_api.manage_model_projection` → model projection handler → `sync_managed_provider_models` → `sync_managed_config`, using a copied `ManagedConfigSpec` with only `config_path` replaced. Ownership registry remains project-owned and unchanged.\n\n3. Each provider adapter declares its own launch-visible target through a small install-adapter hook: Pi returns `<agent_runtime>/agent/models.json`; OpenCode returns `<project_root>/.opencode/config.json`. The generic public materializer discovers the hook; it contains no provider-id conditionals.\n\n4. Make the Pi/OpenCode model renderers and model-config readers/writers emit/read the same native OpenAI-compatible provider blocks that their launches consume. The neutral input is the existing `local-endpoint` ag-rig source, carrying model-id, base-url, and provider override. Preserve non-managed native content and retain collision behavior.\n\n5. Public materialization upserts ag-rig as `local-endpoint`, calls `build_model_projection_request`, applies it once with the adapter-provided config target, and then invokes the adapter only for non-model assets/surfaces.\n\n6. Delete `adapters/pi/local_rig_config.py` and `adapters/opencode/local_rig_config.py`, and remove all imports/calls. No compatibility writer or fallback remains.\n\n7. Prove: request override reaches only the intended config path; Pi/OpenCode native output is launch-visible; user entries survive; collisions fail safely; materialization has exactly one model projection call and no direct model JSON write in adapter installs.
