# Route interactive CLI launch through providers, eliminate harness-specific runner code

## Description

User directive (2026-07-24): the interactive `audiagentic` launch path (bare invocation -> commands/launch.py -> runtime/harness/{pi,opencode}/runner/) should reuse the same providers mechanism already used for ACP and one-shot execution, instead of maintaining a third, harness-specific launch implementation. Providers already: manifest MCP surfaces (prepare_projected_provider_mcp_surface), launch as ACP agents (build_acp_launch), and run one-shot turns (execute_provider_turn). Interactive TUI launch should become a fourth provider-owned launch mode following the same pattern, not a parallel runtime-owned implementation.

Target principle: runtime/harness should contain almost no harness-specific code. It owns only generic, harness-blind concerns -- gathering session/environment state, rig resolution, logging, displaying startup info, process supervision. The actual CLI invocation (which binary, which flags, which env vars a specific harness needs) is a provider concern, expressed the same way ACP launches already are. Harness-specific behavior only exists where a harness has deliberately opted into something extra (e.g. Pi's footer.ts extension, lockdown flags) -- and that code should live under components/providers/adapters/<harness>/, not runtime/harness/<harness>/.
