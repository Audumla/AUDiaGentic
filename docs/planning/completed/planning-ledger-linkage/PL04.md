# Event-driven ledger-to-plan linkage: ledger accepts plan-item-ids, publishes event, planning auto-updates item

## Description

Replace manual ledger-events tracking with automatic event-driven linkage.

**Current flow (PL01-PL02):** Agent records change event, then manually calls `plan_update_item(item_id, {"ledger-events": "..."})` to link the IDs. Burdensome and error-prone.

**New flow:** Agent includes optional `plan-item-ids` in the change event payload. Ledger validates against schema, publishes an event on successful recording. Planning component subscribes and auto-updates the item's `ledger-events` section with the ledger event ID.

### Changes

**Schema (validate first):**
1. `src/audiagentic/foundation/contracts/schemas/change-event.schema.json` — add `plan-item-ids` property: `type: array`, items `type: string`. Do NOT set `additionalProperties: false` (auto-generated keys like `event-id`, `timestamp-utc` are not in schema properties). Agent gets VAL-FRAGMENT-001 with actionable error if type is wrong.

**Ledger side:**
2. `src/audiagentic/components/ledger/events.py` — new constant `LEDGER_EVENT_RECORDED = "ledger.event.recorded"`, publish helper
3. `src/audiagentic/components/ledger/fragments.py:record_change_event()` — after successful record, if `plan-item-ids` present in event payload, publish `ledger.event.recorded` with `{event-id, plan-item-ids}`. Only publish on "created" status (not "exists").
4. `src/audiagentic/components/ledger/ledger_mcp.py` — no change needed; `event: dict` is an open envelope, schema validates all keys.

**Planning side:**
5. `src/audiagentic/components/planning/events.py` — subscribe handler for `ledger.event.recorded`: iterate plan-item-ids, validate each with `require_item()`, call `update_item(item_id, {"ledger-events": ...})` appending the ledger event ID as `- chg_...`. Log error and skip bad IDs.
6. `src/audiagentic/components/planning/item_store.py` — add `"ledger-events"` to `ITEM_SECTION_HEADING` (carries over from PL02)
7. Registration: subscribe via module-level `register()` pattern wired through planning component lifecycle observer (same as `ledger_events.py:26`)

**Instruction side:**
8. Ledger contribution (`agent-ledger.yaml`) adds note: when working on a plan item, include `plan-item-ids` in the change event; linkage is automatic
9. PL01's manual instruction becomes simplified (no longer need to manually track)

### Event delivery
- Use ASYNC delivery for reliability — consistent with all existing planning events (events.py:40). Ledger record already persisted; planning update failure logs error, doesn't lose data.
- Multiple plan items can reference one ledger event (1-to-many from ledger's side). One plan item can accumulate multiple ledger events over time.

## Steps

## Notes

**Decisions:**

1. **Delivery mode: ASYNC** — consistent with all existing planning events (line 40 of planning/events.py). Ledger record succeeded; linkage is best-effort degradation-on-failure.

2. **Validation: deferred to planning** — ledger does NOT validate plan-item-ids exist. Planning's subscription handler uses `require_item()` per ID, logs error and skips bad IDs, links valid ones. No data loss in either direction.

3. **MCP parameter: no change needed** — `record_change_event(event: dict)` is an open envelope. Agent includes `plan-item-ids` key in the dict; it flows through unchanged to fragments.py where publish decision happens. Consistent with how all optional event fields work.

4. **Multiple events per item:** ledger-events section accumulates entries as `- chg_...` list items (one per line). Planning subscription handler appends, never overwrites.

5. **Module location for planning subscription:** reuse `planning/events.py` pattern — add a `_on_ledger_event_recorded` handler and a `register()` function, wired through the lifecycle observer in `planning.yaml` component descriptor (same pattern as `ledger_events.py:26`).

**Implementation order:** PL02 (ITEM_SECTION_HEADING addition) → PL04 ledger side (events.py + fragments.py publish) → PL04 planning side (subscription handler + registration) → PL01 instruction update → PL03 verification.
