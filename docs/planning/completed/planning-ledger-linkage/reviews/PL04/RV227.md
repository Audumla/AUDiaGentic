# Event-driven linkage: registration pattern, idempotency constraint, and accumulation semantics verified

## Notes

Pre-implementation design review of PL04 event-driven linkage approach.

## Findings

**1. Registration pattern alignment** — Planning's subscription handler follows the same module-level `register()` + lifecycle observer wiring as `ledger_events.py:26`. No new modules needed; reuse `planning/events.py` for both publish and subscribe concerns.

**2. Event delivery: ASYNC confirmed** — All existing planning events use ASYNC (events.py:40). Ledger record already atomically persisted. Linkage failure is graceful degradation (missing field), not data loss. No circular sync risk.

**3. Validation deferral to planning layer: correct** — Ledger remains ignorant of planning internals. Planning's `require_item()` handles per-ID validation, logs and skips bad IDs. The one edge case worth noting: if agent includes a plan-item-id that doesn't exist, ledger records normally (correct), planning logs error for that specific ID (acceptable), other valid IDs in the same event still get linked.

**4. Idempotency constraint: documented** — `fragments.py` lines 60-72 return "status: exists" on duplicate content. Publishing only on "created" means a replayed event won't trigger new linkage. This is correct: agents should include all plan-item-ids upfront. If same event needs multiple items, include them all in the initial call.

**5. Accumulation semantics: clear** — Planning handler appends to ledger-events section (one `- chg_...` per line). Multiple calls with different events for the same item accumulate correctly. No overwrite risk.

## Conclusion

Design is sound with the documented constraints. No changes required before implementation.
