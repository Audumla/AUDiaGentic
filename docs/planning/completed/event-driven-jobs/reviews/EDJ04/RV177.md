# Transition ready->running before event publish; no rollback path if dispatch fails

## Notes

Recommended resolution: (a) add a `dispatch-failed` state to workflows.yaml as a terminal state reachable from running; OR (b) reverse the order — publish event first, only transition to running on confirmed gateway acceptance. Option (b) requires EDJ05's outcome handler to also accept outcomes from jobs in 'ready' state.

## Findings

EDJ04 step 2: 'Transition the job ready -> running at dispatch time so all gateway outcomes land from a running state.'

EDJ04 step 3: 'Publish agents.llm.gateway.requested ... with payload ...'

The sequence is: (1) transition to running, (2) publish event. If step 3 fails or the event is dropped on the bus, the job record sits in `running` state forever — no gateway request was created, so no lifecycle event will ever arrive to close it.

Current workflows.yaml has no reverse edge from `running -> ready`. The only exits from running are: awaiting-approval, completed, failed, cancelled. There is no 'dispatch-failed' state.

This is not theoretical — event bus publish can fail (bus not available, subscriber error, serialization failure). The reviewing agent should specify:
1. If transition precedes publish: what happens on publish failure? Roll back to ready? Transition to failed?
2. Should the workflow support a new `dispatch-failed` terminal state, or should failures revert to `ready` for retry?
3. Is there an atomic 'transition-then-publish' unit of work, or is this two independent operations with a window between them?

## Conclusion

MUST-FIX before EDJ04 implementation: step 2 transitions job to running before event publish in step 3. If publish fails or is lost, the job is stuck in 'running' with no gateway request. Add atomic dispatch-or-rollback semantics or reverse transition on failure.
