# awaiting-approval guard assumes an interrupt path that no EDJ item implements

## Notes

This may be intentionally defensive, but defensive code that is unreachable wastes complexity. If approval flow for event-driven jobs is out of scope, remove step 4 and note the limitation.

## Findings

EDJ05 step 4: 'a gateway outcome arriving while the job is in awaiting-approval is out-of-band — log and record a timeline entry, do NOT force a transition.'

The awaiting-approval state can only be reached from `running` (per workflows.yaml). However, EDJ04's dispatch model:
1. Transitions to running (step 2)
2. Publishes gateway event immediately (step 3)

There is no mechanism in this plan for the job to transition from running -> awaiting-approval AFTER dispatch has begun but BEFORE the gateway completes. The current agent-jobs component has an approvals.py module, but none of the EDJ items describe how approval flow integrates with event-driven dispatch.

If awaiting-approval interrupts are not planned, step 4 is dead code. If they ARE planned, the item needs to specify:
- How does the gateway know to pause (cooperative cancellation signal)?
- What happens if the gateway completes before the cooperative pause takes effect?
- Does the `agents.llm.cancelled` event fire when awaiting-approval aborts a running request?

## Conclusion

SHOULD-FIX: The awaiting-approval guard in step 4 assumes a gateway outcome can arrive while approval is pending. But EDJ04 dispatches immediately on job creation, and there's no cooperative pause mechanism — so this scenario may never occur as described. Clarify whether awaiting-approval interrupts execution (requires new agent-jobs <-> agents cooperation) or is purely defensive code.
