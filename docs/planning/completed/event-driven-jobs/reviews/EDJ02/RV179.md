# Idempotent registration claim lacks dedup strategy for repeated register() calls and overlapping patterns

## Notes

Recommended: maintain a set of registered trigger-ids in the observer module; skip subscribe() for already-registered triggers. Document this as the idempotency guarantee.

## Findings

EDJ02 step 1: 'Add agent_jobs/event_observer.py with idempotent registration.'
EDJ02 step 2: 'Load trigger config at registration time and subscribe to enabled patterns.'
The event bus's `subscribe()` does not dedup by caller — it appends a new handler. If `register()` is called multiple times (e.g., process restart, re-initialization), each call adds another subscription for the same pattern.

Additionally, EDJ01 allows both exact patterns (e.g., `planning.item.created`) and wildcard patterns (e.g., `planning.item.*`). If a user configures both for different triggers, one event matches two subscriptions — this is intentional fan-out. But if the same trigger-id is loaded twice (config reload, test harness), duplicates stack.

The 'idempotent registration' claim in step 1 needs a dedup key: either track registered trigger-ids to prevent re-subscription, or maintain one observer instance with a consolidated handler that dispatches to per-trigger logic.

## Conclusion

SHOULD-FIX: Step 1 mentions idempotent registration but doesn't specify dedup strategy. If multiple triggers subscribe to overlapping patterns (e.g., exact `planning.item.created` and wildcard `planning.item.*`), a single event could fire two subscriptions for the same logical trigger. Define subscription identity key to prevent duplicates.
