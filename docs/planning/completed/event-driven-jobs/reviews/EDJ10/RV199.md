# Event payload verification and context key stability

## Notes



## Findings

1. **Missing touchpoint: Event envelope real-world validation** — Step 3 says 'FIRST verify real emitted payload shape of planning.item.created'. The code at `components/planning/events.py` publishes via `publish_planning_event()` which wraps in `EventEnvelope`. The plan should add a test that captures a live `planning.item.created` event and prints its dict representation, to confirm the exact payload structure before coding context builders.

2. **Missing touched file: prompt-launch-request.schema.json** — EDJ10's context object is consumed by `prompt_launch.py`. The existing `prompt-launch-request.schema.json` may need extension to accept the new `context` object shape. EDJ03 and EDJ11 both mention extending this schema; EDJ10 should coordinate to avoid three sequential schema changes. Suggest a single consolidated schema update that covers all EDJ items.

3. **Missing impacted component: Session input store** — Step 1 mentions 'session data (optional)' as an input. The agent-jobs component has `session_input_store.py` for session input persistence. EDJ10 should clarify whether session data is loaded from this store or passed ad-hoc by callers.

4. **Missing touched file: AgentJobPromptContext type definition** — The plan defines context keys as 'stable top-level aliases' but does not specify the typing mechanism. Should `AgentJobPromptContext` be a TypedDict, dataclass, or Protocol? This affects template rendering (EDJ06) and IDE autocomplete for template authors.

5. **Missing validation test: Context key stability** — The plan mentions 'stable key naming before templates depend on it' but does not enforce this. Suggest adding a lint rule or snapshot test that fails if context keys change (to catch accidental renames that break deployed templates).

6. **Missing touched file: prompt_launch.py integration** — Step 6 says 'integrate builder into prompt_launch.py before prompt rendering' but the steps don't specify whether `launch_prompt_request()` is modified or a new entry point is added. The existing flow: parse -> resolve provider -> build job record -> dispatch. EDJ10 inserts context building between parse and render. Clarify the insertion point.

7. **Missing impacted code group: Redaction policy** — Step 5 says 'Preserve only safe/redacted fields; avoid dumping raw large records'. The plan should define which keys are considered sensitive (e.g., event payloads with PII, session tokens). Suggest a denylist approach for known sensitive keys and a size limit (e.g., 4KB per context section).

## Conclusion

Handled: live event envelope capture, consolidated prompt-launch schema update, session_input_store source, explicit context typing, key stability test, prompt_launch insertion point, and redaction policy folded into EDJ10.
