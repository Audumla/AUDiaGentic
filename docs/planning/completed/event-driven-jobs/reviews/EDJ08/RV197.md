# Propagation engine scope and subject model evaluation

## Notes



## Findings

1. **Missing touched file: propagation/engine.py** — The files list uses a glob `foundation/workflow/propagation/*` but should specify which modules are in scope. The key file is `engine.py` (`StatePropagationEngine`) which provides `propagate()` method. EDJ08 must analyze whether this interface can accept job-record subjects (not just planning-item subjects).

2. **Missing impacted code: Propagation subject model** — The existing propagation engine operates on workflow items with parent-child relationships (`parents.py`). Job records and gateway requests have a different relationship model (job owns request, not parent-child). EDJ08 should evaluate whether the propagation engine's subject abstraction can be extended to support job-record subjects or if a new event-driven approach is more appropriate.

3. **Missing touched component: Event bus vs propagation engine** — The plan compares 'explicit event handling against StatePropagationEngine rules' but does not consider a hybrid: use events for real-time reaction and propagation for consistency checks (e.g., orphaned jobs). Suggest evaluating both patterns independently before recommendation.

4. **Missing validation criterion: Performance impact** — The plan should assess whether adding propagation engine calls to the hot path (job state transition) introduces measurable latency. The existing engine loads rules from YAML and evaluates transitions synchronously.

5. **Missing documentation target** — Step 4 says 'Record recommendation and follow-up implementation plan' but does not specify where. Suggest a new document under `docs/architecture/decisions/event-driven-jobs-propagation.md` as an architecture decision record (ADR).

## Conclusion

Handled: propagation engine target files, subject model fit, hybrid event/propagation option, latency criterion, and ADR target folded into EDJ08.
