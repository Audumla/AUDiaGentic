# Executable capability catalogue + enforcement (no descriptor YAML churn)

## Description

Promote the markdown capability taxonomy (docs/reference/PROVIDER_CAPABILITY_REFERENCE/model/capability-id-taxonomy.md) into an authoritative, loadable catalogue and add validation that ties every provider capability declaration to it. Enforcement-first landing: closes the open capability_id namespace and binds each kind to its domain/authority/mechanism-schema WITHOUT changing any provider YAML shape. After this item an ad-hoc capability_id (e.g. pi's 'vendor-key-injection', 'model-config-surface') fails validation instead of silently accreting.

Two new config files: _families.yaml (automation family declarations — replaces Python FamilyPin constants as source of truth) and _capabilities.yaml (kind index). Validation is config-over-code.

## Detailed Solution & Technical Design

TARGET STATE (authoritative; supersedes the originally-shipped catalogue). Config-owned vocabulary; clean-cut with PC02-05.

ONE merged config file config/providers/_capabilities.yaml with two sections (delete _families.yaml):

families:  (the 'pins' — config-owned contracts; code FamilyPin constants retired)
  managed-reconcile:   payload {ownership_scope, entries[]}; result {ok, supported, provider_id, changed, action_needed, error_code, managed_ids, removed_ids, collision_ids}; modes [apply,prune,status]. ONE family for ALL managed-config kinds (mcp, model-endpoints, plugins, hooks, language-servers) — they differ ONLY in the per-entry sub-schema, which the kind's ManagedConfigSpec mechanism already describes. Replaces the 5 near-duplicate managed-* families + ~10 near-duplicate schema files.
  cli-lifecycle:       install/uninstall (steps, not entries). modes [plan,apply,prune,status].
  generated-surfaces:  render managed files/blocks. modes [plan,apply,prune,status]; ownership_scope_required.
  (model-catalog: fetch_catalog_fn is a QUERY not a reconcile — OPEN: classify as operational read, not a provisioned family. Flagged, default operational.)

kinds:  (bare-noun ids; authority tier 'provisioned'|'operational'|'evidence-only')
  see the full table in Code Samples.

BOUNDARY RULE (pinned here): capabilities describe what a provider can do + what the harness manages/reads ABOUT those capabilities. IDENTITY, LIFECYCLE, LAUNCH-ADMISSION WIRING stay orthogonal. Classify by CONSUMER: family handler->provisioned; component decision/listing->operational; only the fact renderer->evidence-only; launch/admission wiring or pure identity->orthogonal.

THREE-DOMAIN NAMING (do NOT unify): 'capability' = (1) provider capabilities [this catalogue], (2) LSP protocol capabilities [coding_lsp/lsp_constants.py], (3) session capabilities [agents gateway AS33]. Only (1) is governed here.

GOVERNANCE VALIDATIONS (config-over-code, each catches a real defect found this session):
  VAL-PCAP-009 capability_id resolves to a catalogue kind.
  VAL-PCAP-011 provisioned kind.family_id in families; instance.modes subset of family modes; contracts from family.
  VAL-PCAP-013 mechanism_schema resolves via MECHANISM_SCHEMA_MAP or is a true primitive.
  provider-neutral kind ids (reject a provider token in a kind id) — catches obs-opencode-*.
  orphaned-family (every family referenced by >=1 kind) — catches managed-hooks gap.
  evidence-vs-consumer (an evidence-only kind whose field is read by non-renderer logic is misclassified) — catches vendor_key_injection.

capability_catalogue.py: authority Literal automation->provisioned (+ the ==checks); load merged families: section; give surfaces-struct/acp-caps-list/lsp-automation-spec real dataclasses in MECHANISM_SCHEMA_MAP so CONCEPTUAL_MECHANISMS shrinks to the 4 primitives (boolean-set, tier-enum, callable-ref, none).
