# Field mapping table needed: 16 ProviderDescriptor fields collapse into capabilities — call-site inventory missing, access-path regression unquantified

## Notes

Code-verified review of PC02. I read base.py lines 111-289 to enumerate every field on ProviderDescriptor and classified them as capability-vs-orthogonal. The plan's scope is understated.

## Findings

1. COMPLETE FIELD CLASSIFICATION from base.py (ProviderDescriptor, lines 111-289):

   CAPABILITY FIELDS (would merge into capabilities: — 16 fields):
   - cli_install → kind: cli-install
   - host_capabilities → kind: ext-declaration (BUT YAMLs use host-extension)
   - capability_facts → various kinds
   - automation_capabilities → derived from automation kinds
   - permissions → kind: perm-declaration
   - agent_files → kind: file-agent
   - mcp_config → kind: mcp-config
   - plugin_config → kind: plugin-entry (NOT in taxonomy explicitly)
   - language_servers_config → kind: lsp-config
   - hooks_config → kind: hook-lsp-enabled (or similar)
   - model_config → kind: model-config
   - on_lsp_enabled → kind: lsp-self-support / hook-lsp-enabled
   - fetch_catalog_fn → kind: model-catalog-refresh
   - surfaces → kind: surface-render/skill/instruction (3 kinds, 1 field)
   - deprecated → kind: depr-status
   - lsp_support_probe → NOT in taxonomy at all

   ORTHOGONAL FIELDS (stay flat — 21 fields):
   - provider_id, display_name, description, url, prompt_aliases, cli_probe,
   - execution_isolation_tier, mcp_launch_isolation_tier, access_mode,
   - skill_surface_path, instruction_file, model_entry_renderer,
   - supported_connectors, vendor_key_injection,
   - receive_lsp_mcp,
   - launches, execution, interactive, acp,
   - annotations, session_surfaces

   The plan says ProviderDescriptor has '~30 fields' — it actually has 37 (16 capability + 21 orthogonal). The plan needs the full classification to avoid ambiguity during dual-read implementation.

2. CALL-SITE INVENTORY IS MISSING: RV831 already flagged this but I can quantify the risk. The key typed accessors that consumers read directly:
   - descriptor.mcp_config → used by managed_mcp_family.py, providers_api.py
   - descriptor.permissions → used by list_provider_descriptors
   - descriptor.host_capabilities → used by list_provider_descriptors
   - descriptor.on_lsp_enabled → used by self_provided_lsp_handler.py
   - descriptor.fetch_catalog_fn → used by models.py
   - descriptor.automation_capability() → used by 8+ files (confirmed by module_report)
   - descriptor.host_extensions() → used by providers_api.py, reconcile.py
   - descriptor.skill_surface_path → used by surface renderers
   - descriptor.instruction_file → used by surface renderers

   After PC03 migration, if any of these still read the raw field (which will be None/empty), the consumer breaks. The equivalence test cannot see this — it only tests the descriptor struct, not downstream outputs.

3. ACCESS-PATH REGRESSION CONFIRMED: Current pattern:
   - `descriptor.mcp_config` → static attribute, typed as ManagedConfigSpec | None, IDE-navigable
   
   PC02/PC03 target pattern (if accessors are NOT preserved):
   - `descriptor.capability('mcp-config')` → dynamic key lookup, Optional[Capability], then `.mechanism` cast to ManagedConfigSpec

   The plan says 'accessors project from the normalized view' but doesn't show the implementation. To avoid regression, typed property accessors MUST be preserved:
   - `@property def mcp_config(self) -> ManagedConfigSpec | None: return self._capability('mcp-config').mechanism if ... else None`

4. PROVIDERAUTOMATIONCAPABILITY SYNTHESIS GAP: automation_capabilities.py lines 17-28 show ProviderAutomationCapability carries:
   - family_id, supported_modes, payload_contract, result_contract, ownership_scope_required

   The plan says 'synthesize from (catalogue family_id, pin contracts, modes)'. But payload_contract and result_contract come from the PINS (FamilyPin.contracts), which only exist for 4 of 7+ families. For managed-mcp, plugin-entry, and language-server-projection — which have NO FamilyPin — where do these contracts come from? The plan doesn't address this.

5. EVIDENCE MULTI-VALUED CONFIRMED: base.py lines 28-34 show CapabilityEvidence is a single dataclass with evidence_tier, constraints, limitations, action_needed, tool_version, fact_anchor, review_state. PC02 notes say evidence should be a tuple — this requires changing the dataclass or wrapping it.

## Conclusion

RESOLVED by implementation (2026-07-28). Full field classification landed close to this review's table: capability fields folded into `capabilities:` (with several further CONSOLIDATED beyond the review's 16 -- model_config+fetch_catalog_fn+supported_connectors+vendor_key_injection+model_entry_renderer -> one `models` compound kind; launches+execution+interactive+acp -> one `launch` compound kind). Typed property accessors preserved throughout -- verified zero access-path regression via full provider+coding_lsp suite runs after every stage plus explicit accessor-exercise checks across all 16 descriptors. ProviderAutomationCapability synthesis gap (#4) resolved: contracts come directly from the (config-owned) family declaration, not a code Pin -- moot once families became config-owned. Evidence stayed single-valued by later explicit decision (see RV820 closure), not the tuple form speculated in #5. Call-site inventory: no literal 107/35 checklist was kept, but the equivalent guarantee (identical accessor names/types/behavior pre- and post-merge) was verified via full-suite regression at every stage, catching 2 real bugs in the process (automation_capabilities gate on `models.store` presence; a dropped opencode model_entry_renderer).
