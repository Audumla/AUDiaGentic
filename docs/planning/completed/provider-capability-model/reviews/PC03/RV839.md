# Sequencing confirmed: off-taxonomy IDs will fail VAL-PCAP-009 before migration — need catalogue soft-accept mode or deferred enforcement

## Notes

Code-verified review of PC03. I verified the specific off-taxonomy IDs that will block validation and the sequencing implications.

## Findings

1. VALIDATION BLOCKER: If PC01 enforcement (VAL-PCAP-009) lands before PC03 migration, the following descriptors will fail validation:
   - pi.yaml: mcp-launch-isolation, vendor-key-injection, model-config-surface
   - codex.yaml: host-extension (vs ext-declaration), surfaces (vs surface-*), model-config-surface, acp-stdio-transport, acp-live-session, acp-session-resume, acp-shared-live-session
   - opencode.yaml: mcp-launch-isolation, host-extension, acp-stdio-transport, acp-live-session, acp-session-resume, acp-shared-live-session
   - cline.yaml: host-extension, surfaces, vendor-key-injection, model-config-surface
   - claude.yaml: host-extension, surfaces
   - 5 more providers with host-extension/surfaces mismatches

   This is 8 of 16 providers that will fail. The plan's sequencing must be:
   (a) PC01 catalogue loads with ALL known IDs (including off-taxonomy ones as transitional entries), OR
   (b) PC01 enforcement is deferred until after PC03 migration completes, OR
   (c) PC01 uses a soft-validation mode that warns but doesn't reject during transition.

2. SURFACES SPLIT DECISION: 8 providers use `capability_id: surfaces` as a single fact pointing at the surfaces field. The taxonomy defines surface-render, surface-skill, surface-instruction as three separate IDs. During migration:
   - If the provider has all three sub-capabilities (surfaces + skill_surface_path + instruction_file), split into 3 facts.
   - If only surfaces is present (renderer + contribution-file), map to surface-render.
   - This requires per-provider judgement, not mechanical translation.

3. HOST-EXTENSION RENAME: 7 providers use `host-extension` as the capability_id; taxonomy defines `ext-declaration`. During PC03 migration, these must be renamed to `ext-declaration` — but only if the catalogue declares `ext-declaration` as the canonical kind. If the catalogue accepts both (as an alias), no rename needed.

4. MIRROR-FACT PRUNING: The plan says 'drop any former capability_fact whose only content re-asserts mechanism field present'. This is correct per MA19 (taxonomy.md:192-201). However, the scope of pruning across 16 providers is not quantified — the plan should estimate how many mirror facts exist total.

## Conclusion

PC03 sequencing with PC01 enforcement is the critical risk. Either PC01 must accept transitional off-taxonomy IDs, or enforcement must be deferred until after PC03 migration.
