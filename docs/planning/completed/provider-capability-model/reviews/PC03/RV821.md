# Sequencing depends on PC01 off-taxonomy resolution + surfaces mapping decision

## Notes

PC03 is well-scoped as a mechanical migration. The blocking dependency is PC01/PC02 resolving the off-taxonomy ID question and the field-mapping table. The `surfaces` vs `surface-render/skill/instruction` mapping decision should be made as part of PC01's catalogue authorship, not deferred to PC03.

## Findings

1. MECHANICAL BUT VOLUME RISK IS REAL: 16 providers, each needing careful mapping from legacy blocks to the capabilities: shape. The plan's migration order (smallest first) is correct. The per-provider equivalence test is the right safety net.

2. OFF-TAXONOMY IDS NEED RESOLUTION HERE, NOT JUST IN PC01: The plan says 'Off-taxonomy id resolution... gets their final catalogue kind here'. But PC01's enforcement (VAL-PCAP-009) would REJECT off-taxonomy IDs at catalogue load time. If PC01 lands before PC03, the off-taxonomy IDs in pi.yaml (`mcp-launch-isolation`, `vendor-key-injection`, `model-config-surface`) and codex.yaml (`acp-stdio-transport`, `acp-live-session`, `acp-session-resume`, `acp-shared-live-session`, `host-extension`, `surfaces`) would fail validation. The sequencing must be: PC01 (catalogue with all known IDs, including临时 accepting off-taxonomy ones) -> PC03 (migrate + rename) -> PC01 enforcement tighten. Or PC01 must be designed to ACCEPT external:-prefixed and known-off-taxonomy IDs during transition.

3. MIRROR-FACT PRUNING IS THE RIGHT DIVIDEND: Dropping capability_facts that merely restate 'mechanism field present' is correct per MA19 population strategy (taxonomy.md:192-201). But the plan should list WHICH facts across ALL 16 providers are candidates for pruning, so the scope is known upfront.

4. `surfaces` CAPABILITY_ID IS USED BY MULTIPLE PROVIDERS: codex.yaml:102, claude.yaml:91 use `capability_id: surfaces`. The taxonomy defines three separate IDs (`surface-render`, `surface-skill`, `surface-instruction`). The plan doesn't specify whether `surfaces` should map to `surface-render` (the closest match) or be split into three separate facts. This is a design decision that should be made before migration.

5. pi.yaml HAS A `mcp-launch-isolation` FACT THAT'S NOT IN THE TAXONOMY: This fact has real execution-tier evidence and constraints. It can't just be pruned as a mirror fact. PC03 needs to decide: add `mcp-launch-isolation` to the catalogue, rename it to an existing taxonomy ID, or keep it as an external: fact.
