# Code review: model source mutation and projection coupling

## Notes

Static audit of model_source_config.py, providers_api.py, source_catalog.py, and model projection code.

## Findings

1. Current model-source CRUD is explicitly desired-state-only: _mutate_model_sources() writes model-sources.yaml and records a planned timeline event; it does not project provider files. Adding apply=False requires a new orchestration result contract.
2. apply=true creates a two-resource transaction (YAML desired state plus multiple provider config files) with no existing rollback boundary. The plan must define whether desired state remains written when projection partially fails, and how retry/status reports that drift.
3. model_source_list() intentionally returns a redacted/partial view; model_source_update() currently accepts arbitrary updates validated only by the broad schema. The new public tool must preserve secret-reference redaction and define immutable/derived fields.
4. model_source_catalog_refresh(source_id=None) does not exist; source_catalog.get_source_catalog() supports one source and static/list-api/none modes, so batch refresh needs per-source error isolation and cache semantics.
5. Vendor enable/disable mutates all matching source records but model projection filters native vendor-key providers out of custom entries. This must be surfaced in apply results rather than treated as missing models.

## Conclusion

PC12 needs a stronger mutation/projection transaction and result design before implementation; the current plan identifies the change but not its failure contract.
