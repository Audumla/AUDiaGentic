# Code review: bootstrap selection and runtime boundary

## Notes

Static audit of launch.py, reconcile.py, lifecycle.py, provider_config.py, and launcher.py against PC10.

## Findings

1. The current implementation has no concrete one-time startup selection input. launch.py calls resolve_reconciliation_policy() and then reconcile_all_providers(); launcher.py exposes no provider-selection launch argument.
2. reconcile_provider() currently calls _should_auto_enable(), which reads persisted reconciliation-policy. The planned runtime boundary therefore requires moving policy consumption entirely into launch/bootstrap and changing reconcile_provider semantics.
3. Launch reconciliation is stamp/feature-state gated, while policy resolution runs every launch. The migration must explicitly define first-install detection, bootstrap selection transport, consumption marker/removal, and behavior when no selection is provided.
4. Existing install_provider_cli() seeds provider enabled=true after install; this may bypass the new bootstrap/explicit activation boundary and must be reconciled with provider_install semantics.
5. Disabled/unsupported providers have different current semantics (auto-disable/prune). The plan should preserve this and test it independently of stale policy data.

## Conclusion

PC10 is directionally correct but not implementation-ready until the bootstrap input and the install/enable boundary are specified at code level.
