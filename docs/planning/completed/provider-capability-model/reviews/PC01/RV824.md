# Modifier/sub-flag capabilities don't fit the kind->mechanism model

## Notes

Several existing capability_ids in the taxonomy are NOT standalone kinds with their own mechanism — they are modifiers ON another capability's mechanism, and the flat 'one kind -> one mechanism' catalogue shape has no clean slot for them:

- mcp-remote: today this is REMOTE_CAPABILITY inside ManagedConfigSpec.capabilities (a frozenset flag on the mcp-config mechanism), consumed by managed_mcp_family.py:68 (`REMOTE_CAPABILITY not in descriptor.mcp_config.capabilities`). It is a property OF mcp-config, not a peer capability.
- cli-probe: part of the cli_install recipe (probe_fn), not a separable mechanism.
- lsp-mcp-receive: the receive_lsp_mcp bool — a modifier on whether the ag-lsp MCP is projected, not its own mechanism.

If PC01 makes each of these a top-level catalogue kind, PC03 will have to invent empty/duplicate mechanism blocks for them, recreating the disorganization we're removing. If PC01 silently drops them, we lose the REMOTE_CAPABILITY signal that managed-mcp actually branches on.

## Findings

Decide, in PC01, how the catalogue models capability MODIFIERS vs capability KINDS. Options: (a) a kind may declare `modifiers: [remote, ...]` whose values live inside the parent mechanism (mcp-config.mechanism.capabilities), keeping REMOTE_CAPABILITY where the family reads it; (b) sub-capabilities expressed as boolean/enum fields on the mechanism, never as peer kinds; (c) a `parent_kind` attribute on the CapabilityKind so mcp-remote/cli-probe/lsp-mcp-receive are catalogued but bind to the parent's mechanism. Recommend (a)/(b): keep the modifier physically inside the parent mechanism so managed_mcp_family's `REMOTE_CAPABILITY in mcp_config.capabilities` check is unchanged. Pin this before PC02 defines the mechanism schemas, because it decides whether mechanism_schema='managed-config-spec' carries a capabilities/modifiers sub-field.

## Conclusion

Blocking-for-design: the catalogue kind model must distinguish kinds from modifiers, or PC03 will manufacture hollow mechanism blocks and/or drop the REMOTE_CAPABILITY flag the managed-mcp family branches on.
