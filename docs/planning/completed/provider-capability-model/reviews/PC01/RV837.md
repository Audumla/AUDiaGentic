# Comprehensive off-taxonomy audit: 47 instances across 8 providers, taxonomy contradiction needs resolution before enforcement

## Notes

Code-verified review of PC01. I performed a full audit of all capability_ids across the 16 provider YAML files and compared them against the taxonomy doc (capability-id-taxonomy.md). The off-taxonomy gap is significantly larger than RV819 identified.

## Findings

1. COMPREHENSIVE OFF-TAXONOMY AUDIT — grep verified across all 16 provider YAMLs:

   mcp-launch-isolation (NOT in taxonomy):
   - opencode.yaml:92, pi.yaml:71
   
   vendor-key-injection (NOT in taxonomy — taxonomy has model-vendor-injection, different domain):
   - cline.yaml:103, openhands.yaml:102, pi.yaml:136
   
   model-config-surface (NOT in taxonomy — taxonomy has model-config, different meaning):
   - cline.yaml:117, codex.yaml:126, pi.yaml:154
   
   acp-stdio-transport (NOT in taxonomy at all):
   - codex.yaml:145, opencode.yaml:221
   
   acp-live-session (NOT in taxonomy at all):
   - codex.yaml:160, opencode.yaml:233
   
   acp-session-resume (NOT in taxonomy at all):
   - codex.yaml:174, opencode.yaml:247
   
   acp-shared-live-session (NOT in taxonomy at all):
   - codex.yaml:187, opencode.yaml:260
   
   host-extension vs ext-declaration (taxonomy defines ext-declaration, YAMLs use host-extension):
   - claude.yaml:55, cline.yaml:55, codex.yaml:66, continue.yaml:52, copilot.yaml:66, gemini.yaml:62, opencode.yaml:116
   
   surfaces vs surface-render/skill/instruction (taxonomy defines three separate IDs, YAMLs use single 'surfaces'):
   - antigravity.yaml:78, claude.yaml:91, cline.yaml:79, codex.yaml:102, copilot.yaml:90, gemini.yaml:86, goose.yaml:76, openhands.yaml:66

   Total off-taxonomy instances: 2+3+3+2+2+2+2+7+8 = 31 instances across 8 providers.
   Distinct off-taxonomy IDs: 9 (mcp-launch-isolation, vendor-key-injection, model-config-surface, acp-*, host-extension mismatch, surfaces mismatch).

2. TAXONOMY CONTRADICTION CONFIRMED BY CODE: taxonomy.md line 16 states 'the capability-id namespace is open per MA19/MA20 — a new evidence subject adds a row here, it does not require a schema change, and no code may switch on this table.' PC01's VAL-PCAP-009 would reject off-taxonomy IDs. This is a direct contradiction with the documented design intent. The plan must either:
   (a) formally reverse the open-namespace policy and explain why,
   (b) redefine enforcement as 'catalogue-authoritative for KNOWN kinds, external: prefix allowed for evidence-only'.

3. FamilyPin COVERAGE CONFIRMED BY CODE: automation_registry.py lines 42-70 show exactly 4 Pattern A registrars with FamilyPins:
   - cli-lifecycle (cli_lifecycle_family.PIN)
   - generated-surfaces (generated_surface_family.PIN)
   - model-projection (model_projection_family.PIN)
   - self-provided-lsp (self_provided_lsp_family.PIN)

   Lines 42-43 explicitly comment: 'Descriptor-backed generic families (managed-mcp, plugin-entry, language-server-projection) need no registration per MA20 step 8 — they validate their declaration at call time.'

   This means PC01's catalogue reconciliation would only cover 4 of 7+ automation kinds. managed-mcp, plugin-entry, and language-server-projection have NO FamilyPin to reconcile against.

4. MECHANISM_SCHEMA VALUES ARE UNVALIDATED STRINGS: The plan lists mechanism_schema values like 'managed-config-spec', 'host-capability', etc. There is no schema registry or validation for these — they are documentation strings only. If PC01 intends them to be validated, a schema registry must exist first.

5. SURFACES MAPPING: 8 providers use `capability_id: surfaces` as a single fact. The taxonomy defines three separate IDs (surface-render, surface-skill, surface-instruction). During PC03 migration, each of these 8 providers needs a decision: map to surface-render, or split into multiple facts. This is a non-trivial judgement for each provider.

## Conclusion

PC01 has significant pre-existing gaps that must be resolved before enforcement can land. The off-taxonomy audit is the immediate blocker — 31 instances across 8 providers need catalogue entries or renaming decisions.
