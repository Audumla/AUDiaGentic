# Bootstrap circularity: catalogue validates descriptors but reconciles against FamilyPins that import descriptors

## Notes

PC01 introduces a load-order knot. The catalogue must be loaded to VALIDATE descriptors (VAL-PCAP-009 checks capability_ids against catalogue kinds). But the catalogue's own validation (reconcile automation kinds against code FamilyPins) needs the family pins, which live in automation_registry._REGISTRARS — and build_automation_registry imports descriptors.registry.all_descriptors() to build the registry. So: descriptors need the catalogue -> catalogue needs FamilyPins -> registry building needs descriptors. Potential circular import / init-order failure, exactly the class of bug that only shows up at real startup, not in a unit test that imports one module.

## Findings

Pin the bootstrap order explicitly in PC01. The FamilyPins themselves (the _REGISTRARS[*].pin objects) are static module-level constants that do NOT require descriptors to exist — only build_automation_registry() (which BINDS pins to providers) needs descriptors. So the fix is to source the pins for catalogue reconciliation from the static PIN constants directly (cli_lifecycle_family.PIN, etc.), NOT via build_automation_registry(). Make catalogue load depend only on those constants; make descriptor validation depend on the loaded catalogue; keep registry-building (which needs descriptors) strictly AFTER both. Add a test that imports the catalogue module in isolation (no descriptor import) and a startup-order test that loads catalogue -> descriptors -> registry in sequence.

## Conclusion

Real init-order hazard. Resolve by reconciling the catalogue against the STATIC FamilyPin constants (no descriptor dependency), not the built registry; document the catalogue->descriptors->registry order and guard it with an isolated-import test.
