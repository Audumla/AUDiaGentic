# Retired-key boundary is under-specified; isolation tiers / launches / execution are capability-adjacent

## Notes

PC04 step 2 lists retired capability keys but hand-waves the boundary ('confirm the final folded set during PC02/PC03'). That boundary is a real design decision, not a confirmation step, and it interacts with fields that are arguably capabilities but were NOT put under `capabilities:` in the PC02 design:

- execution_isolation_tier / mcp_launch_isolation_tier: base.py comments call these provider-wide FACTS consumed by gateway admission and worker materialization, deliberately NOT automation-family properties. They look like capabilities (they have capability_facts with subjects pointing at them — e.g. pi's 'mcp-launch-isolation' fact, subject: mcp_launch_isolation_tier). If they stay top-level, their EVIDENCE (the capability_fact) moves under `capabilities:` while their MECHANISM (the scalar tier) stays out — re-splitting the very thing we merged.
- launches / execution / interactive / acp: HA04 launch declarations. Same question.

So the merge has an unresolved seam: some capability_facts point at fields that will NOT become `capabilities:` entries, leaving orphaned evidence with a dangling subject once the flat capability_facts block is deleted.

## Findings

Pin the kind/orthogonal boundary explicitly in PC01 (catalogue) and honor it in PC02, not PC04. For each field that has an existing capability_fact subject but is NOT becoming a capabilities: mechanism (execution_isolation_tier, mcp_launch_isolation_tier, launches), decide: (a) make it a capability kind with mechanism = the scalar/struct (cleanest — pi's mcp-launch-isolation evidence then co-locates with the tier), or (b) keep it orthogonal AND relocate its evidence to an evidence-only capability kind that references it via an external:-style anchor. Do NOT leave evidence whose subject is a retired-but-not-folded field — VAL-PCAP-013 plus the deleted capability_facts block would strand it. Add a PC01 validation that every catalogued evidence-only kind resolves to either a capabilities mechanism or a declared orthogonal field.

## Conclusion

Blocking-for-design: define the capability-vs-orthogonal partition in PC01 and route isolation-tier/launch evidence accordingly; otherwise PC04's key retirement strands pi's mcp-launch-isolation evidence (dangling subject) and re-splits mechanism-from-evidence for the tier fields.
