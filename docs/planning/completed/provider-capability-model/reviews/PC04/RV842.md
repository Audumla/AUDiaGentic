# Cross-item misalignment: isolation-tier dual-representation, VAL-PCAP-013 collision, hooks retire-without-kind, lsp_support_probe in both lists

## Notes

Traced the earlier findings through PC03->PC04 to answer whether they are factored into later items. Several are NOT, and PC04 is where the gaps become contradictions. Code-checked against shipped _capabilities.yaml/_families.yaml + base.py.

## Findings

1. ISOLATION-TIER DUAL REPRESENTATION (contradiction). PC01 (_capabilities.yaml + PC01 notes lines 169-170) and PC03 (line 102) landed on: execution_isolation_tier / mcp_launch_isolation_tier REMAIN orthogonal fields for runtime access AND ALSO exist as capability_facts (kinds execution-isolation / launch-isolation). But PC04 line 91 still asserts their scalar top-level form is RETIRED and VAL-PCAP-013 rejects them; yet PC04 line 82 KEEPS them in the orthogonal keep-list. Three statements, mutually inconsistent. DECIDE: dual-representation (field for runtime + evidence-only fact) OR retired-and-folded. Given all 16 providers need the tier at runtime for gateway admission/worker materialization, dual-representation (keep field, add evidence-only fact, do NOT retire the key) is the coherent option — then fix PC04 line 91 to stop claiming retirement.

2. HOOKS RETIRED WITHOUT A KIND (compounds RV841). PC04's retire list (line 77) includes hooks_config, but PC03 has no hook-config kind to migrate it into and _capabilities.yaml has none. Net effect after PC04: codex.yaml's hooks_config is rejected by the loader with nowhere to have gone -> hard load failure. Fix RV841 (add hook-config kind) BEFORE PC04 retires the key; add a PC04 precondition: a key may only be retired if a catalogue kind exists to receive it.

3. ERROR-CODE COLLISION. VAL-PCAP-013 is already used by shipped PC01 for mechanism_schema resolution (capability_catalogue.py). PC04 reuses VAL-PCAP-013 for the retired-key guard (PC04 code sample + step 2). Assign the retired-key guard a fresh code (e.g. VAL-PCAP-014) so the two failures are distinguishable.

4. lsp_support_probe IN BOTH LISTS. PC04 line 77 lists lsp_support_probe as a RETIRED capability key; line 89 flags it as used-by-consumers and belonging in the keep-orthogonal set. Resolve: lsp_support_probe is the non-mutating companion to on_lsp_enabled and both fold into the lsp-automation mechanism (lsp-automation-spec) — so it is retired as a top-level key ONLY IF lsp-automation-spec carries it; otherwise keep it orthogonal. Pin one answer and remove it from the other list.

5. CALL-SITE INVENTORY quantified: 107 raw descriptor.<field> occurrences across 35 files (grep of .mcp_config/.model_config/.plugin_config/.hooks_config/.language_servers_config/.permissions/.host_capabilities/.on_lsp_enabled/.lsp_support_probe/.fetch_catalog_fn/.agent_files/.surfaces/.capability_facts/.skill_surface_path/.instruction_file). PC02/PC03 should scope the reroute to typed @property accessors explicitly; PC04 step 3's 'accessors remain' is correct but only safe if every one of those 35 files reads through the property, not the raw field, BEFORE the field is dropped.

## Conclusion

4/5 RESOLVED by implementation (2026-07-28); 1 point carried forward to PC07. (1) Isolation-tier dual-representation: RESOLVED exactly as recommended -- tier VALUES (execution_isolation_tier, mcp_launch_isolation_tier) stay orthogonal fields for runtime admission; evidence-only kinds (execution-isolation, launch-isolation) exist separately for optional provenance (used by pi, opencode). (2) Hooks retired without a kind: RESOLVED, see RV841 closure. (3) VAL-PCAP-013 collision: AVOIDED -- the retired-key guard shipped as a NEW generic mechanism (DescriptorSpec.load rejects any unregistered top-level key, code VAL-DESC-004), not a reuse of VAL-PCAP-013. No collision exists. (5) Call-site inventory: covered via full-suite regression verification at every stage instead of a literal checklist -- equivalent guarantee achieved. (4) lsp_support_probe in both lists: STILL OPEN -- confirmed still a genuine split (on_lsp_enabled lives in capabilities.lsp-self-support.mechanism; its companion lsp_support_probe remains a separate top-level orthogonal field). Also found a SECOND instance of the same pattern: cli_probe (raw shell-probe command) sits outside capabilities.cli-install despite CliInstallRecipe already carrying its own probe_fn. Both carried forward to PC07 (fold each probe into its capability's mechanism as a compound).
