# Unified capability core: one declaration/proof/dispatch abstraction across domains (built to grow)

## Description

Define the ONE capability abstraction that every domain instantiates — provisioning (PC), session (AS29), launch, observation, model, isolation — instead of building parallel typed-family systems (RV847). A capability is a (kind, domain, tier, family?, mechanism, cardinality, evidence-ref) record; the vocabulary is config-owned and OPEN so new kinds/families/domains are added in config (+ a handler for provisioned families) with NO provider-name branches and NO code change to add a declaration. This is the foundation PC01 (provider catalogue) is the first instance of, and AS19/AS29/AS54/RO01 consume. Explicitly built for growth: the set WILL expand (more providers, more session controls, more observation recipes, roles) — the core must absorb that additively.

## Detailed Solution & Technical Design

CORE MODEL (foundation; domain-neutral):
- Capability(kind, domain, tier, family_id?, mechanism, cardinality, modifiers?, evidence_ref?). kind = bare-noun id (stable, provider-neutral — the RO01 reference contract). domain = open string (provisioning|session|launch|observation|model|isolation|...). tier = provisioned|operational|evidence(-ref). family_id set iff provisioned. mechanism = typed value validated against the kind's mechanism_schema. cardinality single|list. modifiers = closed inner value-sets (e.g. mcp remote). evidence_ref = pointer to the owning proof subsystem (AS54/AS27/MI08), NOT inline mirrored evidence.
- Family (the 'pin'; config): {payload_contract, result_contract, supported_modes, ownership_scope_required}. Consolidated set (managed-reconcile, cli-lifecycle, generated-surfaces, + session families).
- THREE ROLES, one seam each: DECLARATION (config catalogue / AS29 surface) -> PROOF (AS54 probe matrix; validation_state/effective_level) -> CONSUMPTION (registry.dispatch for provisioned; component read for operational; AS19 observer for observation; role reference for RO01; gateway for launch/isolation). Declaration never carries proof; capabilities reference the owning proof subsystem.

BUILT-FOR-GROWTH RULES (the point of this item):
1. OPEN vocabulary: add a kind/family/domain = one config row (+ handler for a provisioned family). Validators enforce shape, never enumerate providers.
2. TYPED mechanism registry: mechanism_schema -> Python type (or primitive); adding a structured mechanism = one registry entry. No string-only 'conceptual' escape hatch long-term.
3. STABLE-ID CONTRACT: kind ids are the cross-plan reference surface (RO01 roles, DE recipes). Renames are breaking — additive evolution + deprecation, coordinated with consumers.
4. VERSION/PLATFORM AWARENESS: the session domain (AS29) needs surface/version/platform-scoped, frozen-per-generation capabilities with redaction; the core carries an optional resolution/version dimension so a domain can be version-scoped without a parallel system. Provisioning domain ignores it (project-scoped).
5. DOMAIN SPECIALIZATION without forking the core: AS29 keeps its immutable ResolvedSessionSurface + redaction as a session-domain VIEW derived from the core declaration; PC keeps managed-reconcile. Shared: family/action typing, declaration/proof seam, no-name-branch dispatch, catalogue validation.

RELATIONSHIP: PC01 = the provisioning+launch+model+operational catalogue instance. AS29 = the session domain (resolved view). AS54 = the shared proof matrix. AS19 = neutral observation mapper/consumer. RO01 = capability-id consumer. DE = recipe consumer of provisioned families.

## Notes

INVESTIGATED 2026-07-28 (resolves RV846 + RV847, closed with this finding): spawned a dedicated investigation into AS29 (session_surfaces) and AS19 (observation/evidence) to check whether the proposed domain-neutral Capability(kind, domain, tier, family_id?, mechanism, cardinality, evidence) core actually fits them, per this item's own 'validate by expressing both PC and AS29 as instances before locking' guidance.

FINDING: it does not fit, and should not be forced. AS29's SessionSurfaceDeclaration/ResolvedSessionSurface (descriptors/session_surface_declarations.py, foundation/transports/session_surface.py) is a wide, fixed-shape composite -- identity/controls/lifecycle/content/validation, each a strongly-typed sub-struct with its own enum vocabulary and cross-field validation rules (e.g. O2+ effective levels require validation_state==VALIDATED AND a validated platform). This is NOT a single polymorphic mechanism:Any record. Flattening it into PC06's generic Capability shape would either require 5 separate capability rows per surface (not how it's built) or a generic mechanism blob that loses the typed cross-field validation AS29 depends on -- exactly the 'god-model' risk this item's own effort_risk section already warned about. AS19 has no independent declaration shape to unify at all -- it's purely a consumer/mapper of AS29's declaration producing StatusEvidence, already matching this item's own 'neutral observation mapper' characterization.

NO SHARED CODE EXISTS TODAY between capability_catalogue.py and session_surface_declarations.py/session_surface.py -- they don't import from each other, define entirely independent dataclasses/enums. The similarity RV846/847 identified is naming/vocabulary (kind, domain, cardinality-like concepts, declaration->proof->dispatch language) and a loose conceptual parallel, not shared schema or duplicated logic to eliminate.

DECISION: do NOT build src/audiagentic/foundation/capabilities/ as a shared base class both domains instantiate. Reduce this item's scope to what's genuinely safe and worthwhile:
1. Document the declaration->proof->dispatch SEAM as a cross-domain naming convention (already substantially true in practice), not a shared base class.
2. The one concretely small, safe piece: AS19's StatusEvidence and AS29's PlatformEvidence/SurfaceValidation are conceptually similar evidence records (verification tier, observed_at, source_kind) that COULD share a small foundation-level evidence base type without touching either domain's declaration shape -- optional, low-priority, not urgent.
3. Treat full AS29/AS19 convergence as documentation-only until a SECOND provisioning-like domain actually needs PC01's exact polymorphic per-kind shape -- locking the core around only PC01 today risks over-fitting to provisioning and then forcing AS29 through an awkward adapter later.

RV846 and RV847 (the AS19/AS29 reviews this item was raised from) are closed with this finding -- their proposed convergence is rejected with this rationale, not incorporated as originally written.

CLOSED 2026-07-28 (RV865): checked the one remaining piece (item 2 above -- a shared StatusEvidence/PlatformEvidence base type) against ARCHITECTURE_STANDARDS.md SS3's own bar ('unified only when they share ownership, lifecycle, validation, and semantics; field overlap alone is insufficient'). It fails too: StatusEvidence is a live per-observation stream record (session_id/request_id/sequence/observed_at-correlated); PlatformEvidence is a static per-platform declared fact embedded in a frozen SurfaceValidation, produced once per validation pass with no session/request/sequence correlation. Zero real field overlap -- only a loose 'verification tier' notion expressed through non-interchangeable enums on each side. Rejected on the same grounds as the full unification. PC06 has no further actionable scope; only the documentation-only declaration->proof->dispatch naming convention survives, which requires no code and no tracked item. Full plan closed as superseded -- see RV865.
