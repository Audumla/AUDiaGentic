## Detailed Solution & Technical Design

1. FOLD THE TWO REMAINING PROBE SPLITS (small, mechanical, same pattern as the models/launch merges):
   - cli_probe (raw shell-probe command, e.g. ["aider","--version"]) currently sits as a top-level orthogonal field despite CliInstallRecipe already carrying its own probe_fn (callable-based probe) inside capabilities.cli-install.mechanism. Add a `probe` sub-field to CliInstallRecipe (or a compound wrapper) so cli-install's mechanism carries BOTH probe styles; update the 5 real consumers (registry.py:140, providers_api.py:775-776, lifecycle.py:70, status.py:120) to read the new location; retire the top-level cli_probe key (VAL-DESC-004 catches stragglers automatically, no new guard needed).
   - lsp_support_probe (non-mutating companion to on_lsp_enabled) currently sits outside capabilities.lsp-self-support.mechanism, which only carries on_lsp_enabled (a bare callable). Make lsp-self-support's mechanism a small compound {on_enabled, probe} (mirroring the ModelsSpec/LaunchSpec pattern) instead of a bare callable; update the one real consumer (self_provided_lsp_handler.py's status-mode query) and pi.yaml (the only provider declaring lsp_support_probe); retire the top-level key.
   Only pi.yaml is affected for lsp_support_probe; cli_probe affects most of the 16 providers -- check each before/after with the same per-provider verification discipline used for the models/launch merges (spot-check accessor values match pre-change).

2. NEUTRALIZE obs-opencode-* (RV843, provider-side-only scope -- does NOT require AS19/AS29 changes): replace the two provider-named evidence-only kinds (obs-opencode-acp, obs-opencode-cli-session) with ONE neutral kind (e.g. obs-harness-status); opencode.yaml's two entries become member-scoped evidence instances under that one kind (distinguished by evidence.source, same way the existing evidence note/source pair already differentiates them). Add a provider-neutral-kind-id validation to capability_catalogue.py (reject a kind id containing a known provider_id token) so this class of contamination can't recur -- this is the one net-new governance check from the original RV844 spec that was never added.

3. MANAGED-RECONCILE SHARED-CONTRACT CONSOLIDATION (larger, more mechanical, lower urgency): the 5 managed-* kinds (mcp, hooks, models[curation facet], plugins, language-servers) still have separate JSON schema files (provider-managed-mcp-payload.schema.json, provider-managed-hooks-payload.schema.json, provider-plugin-entry-payload.schema.json, etc. -- confirmed distinct files in src/audiagentic/components/providers/contracts/) with near-identical envelopes ({ownership_scope, entries[]} in / {ok,supported,changed,...,managed_ids,removed_ids,collision_ids} out), differing only in the per-entry sub-shape. Collapse to ONE shared contract pair (provider-managed-reconcile-payload/result) + a per-kind entry sub-schema, OR confirm this is not worth the schema-registry churn and downgrade to won't-do. This is the one item in this list that's a genuine judgment call on ROI, not a clear-cut gap -- surface the tradeoff, don't silently do it.

4. TAXONOMY DOC REGENERATION (originally PC04 scope, not done): replace the hand-maintained capability-id-taxonomy.md with a generator reading _capabilities.yaml + descriptors, plus a drift test (committed doc == generated output). Lower priority than 1-2; do after the catalogue is fully settled (post steps 1-3) so it isn't regenerated twice.
