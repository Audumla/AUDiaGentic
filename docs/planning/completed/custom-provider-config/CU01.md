# Add per-provider customization files to launch configuration

## Description

Allow each provider to own a separate project-scoped customization file and merge its settings into the provider configuration before provider execution or launch.

## Steps

- Define the per-provider file location, loading and validation contract.
- Merge provider-owned customization into the existing runtime provider configuration at the public provider API boundary.
- Ensure existing execution, ACP, interactive, and isolated-worker launch paths receive the merged configuration.
- Add focused tests and documentation, including precedence and secret-handling rules.

## Detailed Solution & Technical Design

Use a provider-owned directory under .audiagentic/config/runtime/providers/<provider-id>.yaml. Keep shared provider fields in providers.yaml and expose provider-specific values under a custom mapping. Load custom files through the providers component, validate safe YAML mappings, merge them into provider_cfg without allowing custom values to override protected shared identity/security fields. Preserve existing adapter hooks and pass the merged configuration through current provider_cfg seams.

## Effort & Risk

Medium: multiple launch paths already consume provider_cfg; incorrect precedence could alter provider selection or secret handling.

## Standards

Architecture standards: config-over-code, one owner/lifecycle per durable artifact, provider-specific behavior stays in the providers component.
