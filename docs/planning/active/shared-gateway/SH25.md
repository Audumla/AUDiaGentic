# Broker-backed agent work queue and scheduler migration

## Description

Replace the current in-process normal agent-execution scheduler/delivery mechanism with a broker-backed implementation behind a provider-neutral gateway queue contract. This is the real MQ migration for requests and session turns of configured agents, independent of the Provider selected by each Execution Profile; it is separate from SH24's advisory maintenance notifier.

## Steps

1. Freeze a backend-neutral work-queue contract for normal agent-execution requests: durable publish acknowledgement, competing-consumer claim, visibility lease, application-controlled ACK after durable claim, redelivery, stable request identity, bounded delivery attempts, backpressure, DLQ/requeue, drain, health, and crash recovery.
2. Preserve the durable gateway request record and existing request/session transition authorities as lifecycle truth; define precisely whether the broker or request store owns pending discovery and how atomic admission/publication is achieved (transactional outbox or equivalent).
3. Implement conformance fakes for loss, duplicates, reorder, broker restart, consumer death, poison delivery, and split-brain ownership.
4. Implement one concrete broker adapter only after capability evaluation. Evaluate MQTT 5 plus a specific broker configuration against every required semantic; MQTT protocol features alone are insufficient evidence. Compare NATS JetStream/RabbitMQ/Redis Streams or another task-oriented broker if needed.
5. Migrate one-shot and session-turn scheduling without provider-ID branches. Agent Definition/Role and Execution Profile selection remain above the queue; the queue schedules the resulting agent execution, not a provider.
6. Add operational management: queue status, pause/drain, retry/requeue, DLQ inspection/purge, redacted metrics, graceful shutdown, and backend replacement/rollback at configuration boundary.
7. Soak under SH11 across configured-agent profiles and providers and remove the in-process scheduler only after repeated green evidence.

## Detailed Solution & Technical Design

Broker delivery is never execution lifecycle authority. Durable request/attempt/owner fencing remains authoritative. ACK occurs only after the application has durably claimed the request; terminal completion remains a request-store transition. A backend must prove its failure semantics through conformance before selection. MCP remains an inbound adapter and never becomes the queue.

## Code Samples & Guidance

Minimum behavioral contract (names may follow existing conventions):
```python
class AgentWorkQueue(Protocol):
    def publish(self, request_id: str, *, attempt_epoch: int) -> PublishReceipt: ...
    def claim(self, consumer: ConsumerIdentity, *, visibility_seconds: int) -> ClaimedWork | None: ...
    def renew(self, claim: ClaimToken) -> ClaimToken: ...
    def ack(self, claim: ClaimToken) -> None: ...
    def nack(self, claim: ClaimToken, *, disposition: NackDisposition) -> None: ...
    def health(self) -> QueueHealth: ...
```
Broker messages contain stable request/attempt identity, not raw prompts, outputs, credentials, provider-native objects, or lifecycle state.

## Files

Provider-neutral queue contract and backend capability model; gateway admission/outbox/scheduler/worker claim path; backend adapters and machine configuration; operator management client plus ag-agents-mgmt/CLI adapters; redacted queue/DLQ timelines and metrics; conformance, integration, crash/restart, migration and soak tests.

## Validation

No accepted request is lost at admission/publish crash boundaries; one request cannot execute concurrently under two owners; consumer death redelivers only unacknowledged work; duplicates/reorder are idempotent; poison work reaches inspectable DLQ; drain blocks new work and allows active work to finish; configured agents using multiple execution profiles/providers pass unchanged; broker replacement does not change public lifecycle/status contracts.

## Effort & Risk

High. Broker-specific persistence and visibility semantics, split brain, admission atomicity, and migration/rollback are the main hazards.

## Standards

arch-standards §§1,3,4,6,7,8; observability-standards; provider-neutral gateway authority; configuration-bound backend selection; MCP adapters own no queue policy.

## Acceptance Criteria

- Every backend passes the same loss/duplicate/reorder/restart/consumer-death/poison/split-brain conformance suite.
- Admission plus publication cannot lose an accepted request; durable request/attempt ownership remains lifecycle truth.
- No request executes concurrently under two owner epochs; ACK follows durable claim and fencing.
- One-shot and session-turn executions for configured agents work unchanged across execution profiles/providers, without provider-ID queue branches.
- MCP is neither broker nor lifecycle authority; management adapters own no queue policy.
- Drain/backpressure/DLQ/requeue/health are operator-manageable and redacted.
- Backend selection and rollback are configuration-bound, and the in-process scheduler is removed only after SH11-style repeated soak.
