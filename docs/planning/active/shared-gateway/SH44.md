# Prove supervised lifetime survives connector exit (SH38 restart-recovery slice)

## Description

Scoped slice of SH38's own acceptance_criteria gap: "supervised lifetime survives connector exit" and disconnect/restart/uncertain-effect recovery, specifically proven over the real two-machine harness (Windows gateway <-> brutus-node over SSH-tunneled WSS+TLS) already used to prove native execution (SH38 notes) and forged-artifact rejection (RV1232, closed). Deliberately split out as its own item instead of folding into SH38 directly, per user direction to slice work and avoid overloading single items/PRs.

## Steps

1. Admit a real request through the real GatewayServiceHost/NodeRecipientHost two-machine harness, then abruptly kill the gateway process (os._exit, not clean shutdown) right after admission -- simulates a connector-exit/crash before dispatch.
2. Start a FRESH gateway process attached to the SAME (uncleared) project/service state, without re-submitting the request, and observe it to completion.
3. Verify the request completes exactly once: single receipt-sequence, single attempt-epoch, and the real node-side fake-executable invocation counter (see notes) shows exactly one invocation -- no duplicate effect.
4. Repeat at a later crash point (after real execution/receipt-terminal but before publication) to additionally exercise the publish-side takeover path (RV1241's unit-level guarantee, now proven live).
5. Record findings in this item's notes; do not claim SH38 acceptance_criteria satisfied until both crash points are demonstrated clean.

## Detailed Solution & Technical Design

Source audit (2026-10-28, branch plan/shared-gateway-execution-nodes): **primarily an unproven live qualification gap, not an identified missing pre-dispatch production mechanism**. `queue/recovery.py::recover_gateway_requests` discovers both hashed active-work records and durable work-index entries (including admission-before-claim). `_takeover_stale_request` calls `store.takeover_nonterminal_owner`, updates work-index ownership and restores active-work; `takeover_nonterminal_owner` preserves queued/running state, request identity, worker/attempt and original node-dispatch. `service/host.py::GatewayServiceHost._serve_forever` invokes this before readiness, orders recovered running then queued work by enqueue ordinal, and delegates node-placed records to `_enqueue_node_recovery`. `NodeServerRuntime.enqueue_recovered` reconstructs immutable descriptor/placement/policy and invokes `QueueManager.enqueue_recovered_node`.

**No node-dispatch**: `enqueue_recovered_node` sets `reconcile_only=False` for recovered queued or running node records. The scheduler requires current node readiness/occupancy/capacity, then `QueueManager._run_one` uses `store.claim_dispatch`; queued records undergo `store.start_owned_attempt`, whereas recovered running records use `claim_dispatch`'s `_recovered-dispatch` path (preserving the existing worker/attempt epoch). `NodeRunner.__call__` checks canonical owner, current placement, immutable admission snapshot, grant/current node slot and readiness before fresh prepare/bind/command; for a recovered running *unbound* record, `resume_unbound=True` permits the strictly fenced bind. No native worker effect is possible merely from an admitted/claimed/unbound canonical record. This is a fresh dispatch of the same logical request, not a duplicate admission.

**Existing node-dispatch**: `enqueue_recovered_node` sets `reconcile_only=True`, and `NodeRunner.__call__ -> _observe -> NodeTerminalReconciler -> publish_owned_node_terminal` reconcile the original command/receipt/artifact. The presence of durable `node-dispatch` is an uncertainty boundary even if command-send was never observed. Do not construct a second command, rerun an effect, or clear custody on missing receipt/connection; defer/reconnect and reconcile exact immutable identity. Original receipt/publication CAS and retained evidence govern terminal outcome; `publish_owned_node_terminal` cannot mint native execution evidence.

**Specific source-level risk to test, not a confirmed bug**: crash after `store.claim_dispatch` or `start_owned_attempt` but before `bind_owned_node_dispatch`; restart must preserve existing attempt identity and successfully reach `NodeRunner` as an unbound running recovery. Distinguish this from a crash after canonical bind but before command delivery; the latter must stay observation-only, and may need manual reconciliation rather than progress automatically. The post-effect test must have a durable terminal receipt + immutable output artifact before killing the gateway; otherwise outcome is uncertain, not provably terminal.

Harness: instrument explicit barriers with machine-readable persisted witnesses rather than timing sleeps: (A) after durable admission/work-index write but before queue claim, (A2) after durable running attempt but before node-dispatch bind, (B) after node receipt custody is durable and original output exists but before canonical publication CAS. Use a truly new gateway OS PID/owner epoch, SAME service/project directory, same request ID and same node-side receipt WAL; do not delete node receipts/outputs between kill and resume. Start gateway before reconnecting node; avoid extra processes from nested shell backgrounding. Reset isolated node test state **only before a fresh logical test**, not across its crash/restart boundary. Confirm exact canonical owner/attempt transitions, dispatch identity, receipt sequence/digest, output bytes, state, trace, authorization and no operator re-submission.

If a barrier reveals an actual defect, patch the *existing* recovery/queue/NodeRunner owner path with a focused regression; never add a second scheduler, auto-resubmit, change receipt authority, or treat unknown effect as unsent. Do not claim success until two independent real-machine runs and negative uncertainty/fence checks pass.
