# Prove supervised lifetime survives connector exit (SH38 restart-recovery slice)

## Description

Scoped slice of SH38's own acceptance_criteria gap: "supervised lifetime survives connector exit" and disconnect/restart/uncertain-effect recovery, specifically proven over the real two-machine harness (Windows gateway <-> brutus-node over SSH-tunneled WSS+TLS) already used to prove native execution (SH38 notes) and forged-artifact rejection (RV1232, closed). Deliberately split out as its own item instead of folding into SH38 directly, per user direction to slice work and avoid overloading single items/PRs.

## Steps

1. Admit a real request through the real GatewayServiceHost/NodeRecipientHost two-machine harness, then abruptly kill the gateway process (os._exit, not clean shutdown) right after admission -- simulates a connector-exit/crash before dispatch.
2. Start a FRESH gateway process attached to the SAME (uncleared) project/service state, without re-submitting the request, and observe it to completion.
3. Verify the request completes exactly once: single receipt-sequence, single attempt-epoch, and the real node-side fake-executable invocation counter (see notes) shows exactly one invocation -- no duplicate effect.
4. Repeat at a later crash point (after real execution/receipt-terminal but before publication) to additionally exercise the publish-side takeover path (RV1241's unit-level guarantee, now proven live).
5. Record findings in this item's notes; do not claim SH38 acceptance_criteria satisfied until both crash points are demonstrated clean.

## Detailed Solution & Technical Design

Harness scripts already exist (not committed -- scratchpad on Windows + /tmp/sh38-qualify on brutus): gateway_crash_dispatch.py (admits then os._exit(137) immediately), gateway_resume_dispatch.py (reattaches to the SAME gw/service dir without clearing it, polls the admitted request-id to completion). First phase already run once this session: admission succeeded (req_project_0921f1d55a0a), crash confirmed (exit 137), but the resume phase was not yet executed before the session pivoted to delegating this work. A fake-pi invocation counter was added (/tmp/sh38-qualify/fakepi/pi appends a line to invocation_count.txt on each real run) specifically to detect duplicate execution across the crash/resume boundary.

Known operational pitfalls from this session, worth avoiding: (1) backgrounding a long-running Windows process via an inner shell '&' inside a Bash tool call reports task completion the instant the launch line returns, NOT when the real process finishes -- this orphaned multiple duplicate gateway processes across context-compaction boundaries. Always let the Bash tool's own run_in_background track the actual foreground command, with no inner '&'. (2) The node must connect to an ALREADY-RUNNING gateway -- starting the node first against a dead port exhausts its retry budget almost instantly ('retry-exhausted'/'node-reconciliation-required', a generic sanitized code that hides the real cause). Always launch gateway first, wait ~5s, then the node. (3) Stale node-side receipts.sqlite3/receipts.lock from a previous run can itself cause an instant 'node-reconciliation-required' failure unrelated to the actual test -- clear /tmp/sh38-qualify/node/state/{receipts.sqlite3,receipts.lock} and state/outputs before each run. (4) gw/service must be rm -rf + mkdir'd before a FRESH run, but must NOT be cleared between the crash and resume phases of THIS specific test -- that's the whole point (the resume process reattaches to the crashed process's leftover state). (5) SSH commands that background a remote process with '&' can hang the local ssh invocation itself unless stdin is also redirected (< /dev/null) -- add that or expect a background-task fallback.
