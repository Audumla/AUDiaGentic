# Replace wall-clock worker kills with activity-renewed execution watchdogs

## Description

Separate caller observation windows from execution ownership and termination policy. Fixed elapsed time is not failure evidence: a real gpt-auto review remained actively streaming beyond 3900 seconds. Long-running agents use reconnectable passive waits; execution ends only on explicit cancellation, definitive provider/process failure, verified sustained stall after diagnostics, or a separately configured and honestly classified absolute safety policy.

## Steps

0. Immediate operational policy: passive wait/status calls use short reconnectable observation windows and never kill execution. For trusted long-running review/design lanes, do not set a destructive elapsed-time ceiling where operationally safe. If a ceiling is mandatory before verified activity leases land, use a machine-owned explicit policy at least 3600 seconds, document that it is only a safety stop, and do not classify it as provider failure. The 3900-second live cancellation proves even 60+ minutes can be insufficient.
1. Split request fields and semantics: max_execution_seconds is optional safety policy; wait_timeout_seconds is caller observation only; introduce activity_lease_seconds and last_verified_activity_at for runtime supervision. Preserve timeout_seconds through an explicit migration; never silently reinterpret persisted requests.
2. Define verified activity sources behind provider capability adapters: isolated-worker heartbeat; owned-process identity/liveness plus fresh structured progress; durable request-correlated patch/test activity; browser DOM streaming/tool-state evidence; ACP/MCP/A2A/provider progress only where its surface declares a validated route. Raw stdout noise, repeated text, wall clock, and uncorrelated changes do not renew.
3. Persist redacted execution-started-at, last-verified-activity-at, activity-source, activity-sequence, activity-lease-expires-at, watchdog-state and watchdog-reason.
4. Replace fixed join-time kills with a watchdog: observe cancellation and positive process/provider failure first; renew only from monotonic verified activity; run bounded diagnostics after lease expiry; terminate for verified repeated stall or explicit configured absolute safety policy. A positive diagnostic renews; silence alone remains UNKNOWN.
5. Reject duplicate/replayed/stale/cross-request/cross-attempt activity. Verify ownership epoch before any signal or terminal mutation.
6. Use distinct terminal classifications: cancelled, worker-process-exited, provider-terminal-error, absolute-safety-policy, verified-stall. Preserve partial evidence and never label a policy stop as provider timeout/failure.
7. Expose redacted activity/watchdog facts in request status. Gateway overview aggregates counts only.
8. Put non-secret limits and disabled/optional absolute ceiling in machine-owned gateway policy; project profiles cannot weaken it. Snapshot policy at admission.
9. Test that passive wait/caller exit never kills; work survives beyond 60 minutes while verified activity continues; long valid tool pauses are not failure; duplicate/stale activity does not renew; explicit cancel/process exit wins; bounded diagnostic behavior; restart/fencing/redaction/no-double-terminal.
10. Docker/e2e across controlled worker plus available browser/ACP/MCP-backed agents: pause, tool-call, resume, then true stall. Prove active work survives old ceilings and only definitive or policy evidence ends it.

## Validation

A worker with validated request-bound activity is not killed because elapsed time passes. A passive observer timeout/caller disconnect never changes execution state. Browser DOM streaming/tool activity, ACP progress, worker heartbeat and other provider signals enter through provider-neutral validated evidence adapters. Silence or long tool pauses alone do not prove failure. A stalled worker terminates only after lease expiry, bounded diagnostics and ownership fencing, exactly once, while an explicit absolute ceiling is reported as policy termination—not provider failure.

## Effort & Risk

Worker activity signals can be spoofed, duplicated, stale, or noisy. Treat activity as evidence with correlation/sequence validation; do not renew from text output alone. Preserve a policy-controlled absolute ceiling for runaway processes.

## Standards

SH07 durable request authority and fencing; AS29 capability/evidence gating; AS36 suspicious-output classification; AS37 status materialization rule; foundation process supervision; redaction and event authority standards. Reuse existing request work-index/attempt ownership and provider public APIs; do not add a second scheduler.

## Acceptance Criteria

- A worker actively emitting validated, monotonic request-bound activity is never killed merely because elapsed wall-clock time passes.
- A passive wait/observation timeout (`agent_llm_wait`, MCP client wait caps) never signals or kills the worker — it only stops waiting.
- A stalled worker is terminated only after lease expiry plus a bounded diagnostic probe failure, exactly once, with a terminal reason distinct from `TO-AGW-076`.
- Duplicate, replayed, stale, or cross-request/cross-epoch activity signals never renew a lease — only a genuine sequence advance or new categorized activity event does.
- An absolute safety ceiling remains as an explicit, policy-controlled fallback for a genuinely runaway process, distinguishable in the terminal classification from a verified stall.
- Two concurrent projects/requests cannot renew each other's lease.
- Status/overview expose redacted watchdog facts (last-verified-activity-at, source kind, lease expiry) with no provider-native payload, prompt, or file content — and gateway overview aggregates counts only.
- `timeout_seconds` compatibility is explicit and migrated, never silently reinterpreted on a persisted request.

## Implemented 2026 08 07 Core Watchdog

**Core mechanism implemented and tested (step 4's central fix). Several steps deliberately deferred, recorded honestly below — this is a real first slice, not full-item completion.**

## What's real and working

The single blocking `child.communicate(timeout=timeout_seconds)` hard-kill in `gateway/queue/worker.py::execute_isolated_provider_turn` is replaced by `_wait_with_activity_watchdog`: `communicate()` runs in a background thread (reusing its own correct write/drain-without-deadlock handling rather than reimplementing that by hand), while the calling thread polls a **real, verified activity signal** — process CPU-time delta, read via a new foundation helper `managed_process.process_cpu_time_seconds(pid)` (Windows: raw `GetProcessTimes` via ctypes, matching this module's existing `process_creation_identity` pattern rather than introducing psutil as a new production dependency; POSIX: `/proc/[pid]/stat` utime+stime). Verified directly: CPU time increases under real load and returns `None` for a dead process.

Behaviour: `timeout_seconds` (the caller's own number) becomes a **grace period**, not an immediate kill. Once it elapses, the child is only killed if CPU time has stayed flat for `_STALL_GRACE_POLLS` (2) consecutive polls — a **verified stall**. Genuine, CPU-consuming progress extends the wait indefinitely, up to `_ABSOLUTE_SAFETY_CEILING_SECONDS` (2700.0, matching step 0's already-adopted operational ceiling), which always wins regardless of activity. `TO-AGW-076`'s error details now carry `watchdog-classification` (`verified-stall` / `absolute-safety-ceiling`), `requested-timeout-seconds`, and `elapsed-seconds` for real diagnosis — same error code, richer detail, no breaking change (checked: no test asserts the exact old message string against this real call site).

**Directly fixes the exact failure class SH16 hit**: a legitimately-still-running worker killed at an arbitrarily tight caller-supplied number.

## Verified against the one scenario that could have silently broken

`tests/integration/agents/test_sh06_worker_isolation.py::test_worker_timeout_reaps_the_provider_descendant_tree` — a genuinely hung worker (blocks forever, zero CPU) — **still passes**, confirming a real stall is still caught promptly (grace period + a few flat polls, not 2700s). This was the load-bearing regression risk of any naive "just make the ceiling bigger" fix, and it does not regress.

`test_provider_crash_reaps_the_detached_descendant_tree` fails in this suite — confirmed via `git stash` to fail **identically with zero code changes**, i.e. fully pre-existing and unrelated to this work.
