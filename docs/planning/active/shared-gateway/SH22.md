# Replace wall-clock worker kills with activity-renewed execution watchdogs

## Description

Separate worker observation timeouts from worker termination policy. Until verified in-progress activity is available, long-running delegated coding work receives a 45-minute provisional execution ceiling. Once activity signals are trustworthy, a watchdog renews a lease on verified progress and terminates only explicit cancellation, proven worker/process failure, or sustained verified inactivity.

## Steps

0. Immediate operational policy: delegation callers submit coding/review jobs with `timeout_seconds=2700` (45 minutes). This is a provisional hard safety ceiling, not a status/wait timeout. `agent_llm_wait` and MCP client wait caps remain passive observation timeouts and never kill the worker.
1. Split request fields and semantics: `execution_deadline_seconds`/`max_execution_seconds` is a safety ceiling; `wait_timeout_seconds` is caller observation only; introduce `activity_lease_seconds` and `last_verified_activity_at` for runtime supervision. Preserve backwards compatibility for `timeout_seconds` through an explicit migration, never silently reinterpret persisted requests.
2. Define verified worker activity sources in priority order: isolated worker lifecycle heartbeat; harness process liveness with fresh structured progress/event sequence; durable file/patch/test-process activity tied to the request; provider-native progress only when AS29 surface declares a validated route. Raw stdout noise, repeated text, wall clock, and uncorrelated filesystem changes do not renew a lease.
3. Add durable request fields: `execution-started-at`, `last-verified-activity-at`, `activity-source`, `activity-sequence`, `activity-lease-expires-at`, `watchdog-state`, `watchdog-reason`. Redact all payloads; persist only source kind, monotonic sequence/timestamp, and bounded reason code.
4. In isolated worker execution, replace one `join(timeout)` kill with a watchdog loop. It must: observe cancellation/process exit first; refresh lease only from monotonic verified activity; keep a 45-minute hard ceiling until a profile/policy supplies an approved absolute maximum; and on lease expiry run a bounded diagnostic probe before termination. A positive probe renews once; only repeated no-progress probe failure produces a stalled-worker terminal error distinct from TO-AGW-076.
5. Detect false progress conservatively: require sequence advance or a new categorized activity event; reject duplicate/replayed heartbeat, stale timestamps, repeated identical output, and heartbeat from a different request/attempt epoch. Verify ownership epoch before any kill.
6. Add explicit terminal classifications: cancelled, worker-process-exited, provider-terminal-error, absolute-safety-ceiling, and verified-stall. Do not call a healthy long-running worker timed out. Preserve partial-artifact review metadata when a kill occurs; do not claim completion.
7. Status/API: expose `last-verified-activity-at`, source kind, watchdog state/reason, and next lease expiry in request-scoped status only. SH15/AS37 may project this as health/evidence later, but status availability must not depend on an LLM. Gateway overview must aggregate counts only and leak no project roots, prompts, files, or provider payloads.
8. Profile policy: add gateway-owned non-secret limits for provisional max runtime, activity lease, diagnostic-probe interval/count, and absolute ceiling. Project-local profiles cannot weaken a shared gateway policy. Snapshot these values at admission under SH07 lane semantics.
9. Tests: passive wait timeout does not signal/kill; 45-minute execution budget is passed to isolated worker; verified monotonic heartbeat renews beyond the old deadline; duplicate/stale/unrelated activity does not; process exit fails immediately; explicit cancel wins; first failed probe does not kill active worker; repeated verified stall terminates once; restart/recovery retains watchdog facts; two projects cannot renew each other's lease; redaction and no-double-terminal-event proofs.
10. Docker/e2e: use a real Pi/ACP harness or controlled isolated worker that emits structured heartbeats, pauses without progress, resumes, then stalls. Prove active work survives past the old 20-minute-equivalent test budget, a true stalled worker terminates only after diagnostic probes, and status shows lease progress without model interpretation.

## Validation

A worker actively emitting validated, monotonic request-bound activity is not killed merely because elapsed time passes. A passive wait deadline never affects execution. A stalled worker is terminated only after lease expiry plus bounded diagnostic failure, exactly once, with a distinct terminal reason. Absolute ceilings remain explicit policy safety limits. Recovery and status expose redacted watchdog facts without provider-native payloads.

## Effort & Risk

Worker activity signals can be spoofed, duplicated, stale, or noisy. Treat activity as evidence with correlation/sequence validation; do not renew from text output alone. Preserve a policy-controlled absolute ceiling for runaway processes.

## Standards

SH07 durable request authority and fencing; AS29 capability/evidence gating; AS36 suspicious-output classification; AS37 status materialization rule; foundation process supervision; redaction and event authority standards. Reuse existing request work-index/attempt ownership and provider public APIs; do not add a second scheduler.

## Acceptance Criteria

- A worker actively emitting validated, monotonic request-bound activity is never killed merely because elapsed wall-clock time passes.
- A passive wait/observation timeout (`agent_llm_wait`, MCP client wait caps) never signals or kills the worker — it only stops waiting.
- A stalled worker is terminated only after lease expiry plus a bounded diagnostic probe failure, exactly once, with a terminal reason distinct from `TO-AGW-076`.
- Duplicate, replayed, stale, or cross-request/cross-epoch activity signals never renew a lease — only a genuine sequence advance or new categorized activity event does.
- An absolute safety ceiling remains as an explicit, policy-controlled fallback for a genuinely runaway process, distinguishable in the terminal classification from a verified stall.
- Two concurrent projects/requests cannot renew each other's lease.
- Status/overview expose redacted watchdog facts (last-verified-activity-at, source kind, lease expiry) with no provider-native payload, prompt, or file content — and gateway overview aggregates counts only.
- `timeout_seconds` compatibility is explicit and migrated, never silently reinterpreted on a persisted request.

## Implemented 2026 08 07 Core Watchdog

**Core mechanism implemented and tested (step 4's central fix). Several steps deliberately deferred, recorded honestly below — this is a real first slice, not full-item completion.**

## What's real and working

The single blocking `child.communicate(timeout=timeout_seconds)` hard-kill in `gateway/queue/worker.py::execute_isolated_provider_turn` is replaced by `_wait_with_activity_watchdog`: `communicate()` runs in a background thread (reusing its own correct write/drain-without-deadlock handling rather than reimplementing that by hand), while the calling thread polls a **real, verified activity signal** — process CPU-time delta, read via a new foundation helper `managed_process.process_cpu_time_seconds(pid)` (Windows: raw `GetProcessTimes` via ctypes, matching this module's existing `process_creation_identity` pattern rather than introducing psutil as a new production dependency; POSIX: `/proc/[pid]/stat` utime+stime). Verified directly: CPU time increases under real load and returns `None` for a dead process.

Behaviour: `timeout_seconds` (the caller's own number) becomes a **grace period**, not an immediate kill. Once it elapses, the child is only killed if CPU time has stayed flat for `_STALL_GRACE_POLLS` (2) consecutive polls — a **verified stall**. Genuine, CPU-consuming progress extends the wait indefinitely, up to `_ABSOLUTE_SAFETY_CEILING_SECONDS` (2700.0, matching step 0's already-adopted operational ceiling), which always wins regardless of activity. `TO-AGW-076`'s error details now carry `watchdog-classification` (`verified-stall` / `absolute-safety-ceiling`), `requested-timeout-seconds`, and `elapsed-seconds` for real diagnosis — same error code, richer detail, no breaking change (checked: no test asserts the exact old message string against this real call site).

**Directly fixes the exact failure class SH16 hit**: a legitimately-still-running worker killed at an arbitrarily tight caller-supplied number.

## Verified against the one scenario that could have silently broken

`tests/integration/agents/test_sh06_worker_isolation.py::test_worker_timeout_reaps_the_provider_descendant_tree` — a genuinely hung worker (blocks forever, zero CPU) — **still passes**, confirming a real stall is still caught promptly (grace period + a few flat polls, not 2700s). This was the load-bearing regression risk of any naive "just make the ceiling bigger" fix, and it does not regress.

`test_provider_crash_reaps_the_detached_descendant_tree` fails in this suite — confirmed via `git stash` to fail **identically with zero code changes**, i.e. fully pre-existing and unrelated to this work.

## Tests

`tests/unit/agents/test_agents_gateway_worker_watchdog.py` (5 new, fast, deterministic — fake child + monkeypatched CPU-time reader, no real subprocess needed): normal completion before timeout; genuine activity extends past `timeout_seconds` and completes (the core fix, proven directly); flat CPU after the grace period raises `verified-stall`; the absolute ceiling wins even with activity; an unreadable CPU-time fact (`None`) doesn't crash the loop. `python -m pytest tests/unit/agents -q` and `test_sh06_worker_isolation.py` (minus the one confirmed-pre-existing failure) both green.

## Deliberately NOT done in this pass — real remaining scope, not silently dropped

- **Step 1/3 (durable request-field split)**: `execution_deadline_seconds`/`wait_timeout_seconds`/`activity_lease_seconds`/`last_verified_activity_at` as separate persisted record fields. The caller-facing `timeout_seconds` parameter is unchanged (still one field, wire-compatible) — internally it now means "grace period" rather than "hard kill", which is the behavioral fix, but the schema/API still presents one field where the item specifies several. A real, separate migration.
- **Step 2's tiers 1/2/4 activity sources**: isolated-worker lifecycle heartbeat, harness structured progress/event sequence, provider-native progress. Only the most conservative tier (process liveness, strengthened with CPU-time verification) is implemented — explicitly the floor signal, not the full priority list. Named blind spot: a process blocked on a remote network call (hosted-API wait) shows no local CPU signature and would currently read as a stall after the grace period; that needs a real heartbeat/progress channel from the worker, which needs worker-protocol changes.
- **Step 6's full terminal-classification set**: `cancelled` and `worker-process-exited` (as their own explicit classifications) and `provider-terminal-error` are not added — only `verified-stall` and `absolute-safety-ceiling` exist today, carried in error details rather than as durable record fields.
- **Step 7 (status/API exposure)**: `last-verified-activity-at`, watchdog state/reason are not surfaced on any read API — they exist only inside the raised error's details today.
- **Step 8 (profile-owned policy)**: no gateway-owned config for the grace/stall/ceiling constants — they are Python module constants in `worker.py`. Project-local override and profile-snapshot-at-admission are unbuilt.
- **Step 5's stronger false-progress detection**: (ownership-epoch verification, sequence-based replay rejection) doesn't apply yet since there is no external heartbeat channel to spoof — becomes relevant once step 2's richer sources land.
- **Step 10 (Docker/e2e)**: not attempted — SH16's own Docker smoke test is the natural place to eventually re-verify this against the real flaky scenario that motivated it.
