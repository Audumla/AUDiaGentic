# Join externally owned Claude Codex Pi and OpenCode sessions as persistent gateway targets

## Description

Design-only follow-on to SH35: a current running Claude Code, Codex, Pi or OpenCode session can explicitly register itself with the central gateway and receive a durable authenticated routing handle that other authorized clients can target. Registration grants bounded management, not process ownership: the gateway must not terminate an externally owned harness. Four harnesses only; no implementation until scenario mapping, real capability qualification and round-table design review complete. Current onboarding release prerequisite met by published v0.6.0; broader CI remains separately observable.

## Steps

1. Inventory actual current APIs and owner contracts for external ownership, attach-existing, resume-by-ref, prompt delivery, steer, interrupt, detach and process cleanup; reconcile superseded/deprecated session plans and capability claims against installed-version evidence.
2. Map all local/remote/multi-client/owner-human/queued/steered/disconnect/restart scenarios before choosing contracts. Review map with Dev GPT, record disagreements and resulting decisions.
3. Specify self-registration verification, durable public routing identity versus provider/native session/turn/transport/process incarnation, authorization, lifecycle and non-termination invariants; review proposed code seams with GPT.
4. Specify prompt delivery and ownership-aware FIFO/steer policies, busy/idle evidence, cancellation, human input and exact result correlation; review failure/ambiguity matrix with GPT.
5. Define per-harness capability probes and minimal provider-owned bridges only where native APIs cannot meet requirements; freeze explicit unsupported cases rather than pretending launch/resume proves attachment.
6. Define CLI/MCP/config/schema/help/descriptions/instruction/docs and installed two-machine qualification, then obtain terminal code-level design review before creating implementation slices.

## Detailed Solution & Technical Design

### Scope, evidence and prior decisions
Only Claude Code, Codex, Pi and OpenCode are eligible for the first release. Common gateway/session/node contracts remain provider-neutral; protocol behavior stays in Provider-owned adapters selected by existing surface capability resolution. Audit AS29 surface declarations, AS30 bindings, AS95 controls, AS101 authorization, AS117 durable-session versus provider-transport split, current push/delivery work and optional collaboration rollout before extending seams. Do not revive retired work merely by its title: the Codex shared-TUI/App-Server proposal AS51 is deprecated because the shared-human-thread use case had not previously been requested; that use case is now explicitly requested and requires fresh exact-version proof. Pi steering AS44 is deprecated, and external-controls AS58 is superseded; trace their current successors and unfinished paths. Folder placement under completed does not mean implemented/qualified.

Current local inventory does not prove attachment: codex-acp, pi-community-acp and opencode-acp descriptors mark attach-existing/steer unsupported, while native app-server/RPC/SDK/serve/plugin routes may differ. Launching an ACP child, loading a stored conversation, observing a transcript and attaching to an already-running human TUI are distinct capabilities. Validate the user's ASA/ACP terminology against actual existing contracts and upstream APIs; never assume a universal attach/steer protocol. Prefer native supported surfaces; approved Provider-owned bridges may be required. Do not promise external control of all four until probes prove it. Unsupported bindings may be visible as non-routable, but must never be advertised as ready targets or accept prompts they cannot deliver.

### Ownership and registration
Reuse existing SessionOwnership.EXTERNAL for joined user-owned processes. ADOPTED means actual transferred lifecycle authority and is not the default or an implicit side effect of registration; ownership transfer is out of MVP. Model gateway-owned child workers separately. Joining, idle/tab timers, queue cancellation, session close, node disconnect, gateway restart/upgrade, shutdown, unregister and local config removal must only detach/revoke the joined binding; they must not kill the harness, its terminal, parent process, provider daemon or OS process tree. Turn interruption is a separate capability/policy and never implies process termination. A gateway-created observation/control sidecar can be shut down only if doing so cannot kill or corrupt the external session.

Self-registration is initiated from the current harness through its local MCP/provider integration, with explicit user consent and node/provider verification of the native session, workspace and local instance. A model-supplied native ID, PID, display title, transcript match or 'latest session' is insufficient proof of self identity. Bind enrolled principal, node ID, node boot epoch, approved workspace ID and exact Provider surface/version/native session reference to a canonical gateway record. Keep local process PID plus creation identity local as evidence, not a cross-machine kill handle. Registration is idempotent and duplicate MCP children for one native session must not create competing writers. Define revocation, allowed callers and project permissions; possession of the public session ID is not authorization.

Separate durable public routing handle, canonical Agent Context/Work/session IDs, native conversation/thread ID, current runtime/transport and incarnation/generation. Prefer existing canonical stores/context binding to a second session authority. A stable handle may reconnect to the same proven living instance. Process exit, provider restart or native resume may require a new linked immutable generation and explicit disposition; never retarget an old handle to an unrelated 'latest' session or mutate existing binding provenance. Resolve where client-supplied session_id reaches existing submit APIs and preserve agent/profile/provider/workspace identity checks. Do not silently replace the existing gateway durable-session semantics with native IDs.

### Coordination topology
Reuse the SH35 outbound node-control channel and central queue; do not misuse stdio as universally supported server-initiated reverse RPC. Node I/O/control progresses independently while the caller's MCP request waits. Node owns local provider control, filesystem/terminal callbacks, credentials and process identity; gateway owns authenticated routing, admission, scheduling, durable request state and result delivery. Joining the same interactive harness that is awaiting the MCP result can create recursive self-dispatch/deadlock: map/reject/defer that case explicitly unless a proven native control route safely supports it. Registration must not turn every submission into an ACP launch or spawn another copy of the running harness.

A protocol-level prompt-accepted acknowledgement is not turn completion. Persist command/idempotency/attempt/native-turn correlation before side effects. Lost acknowledgement or reconnect never authorizes duplicate prompt submission. Results must correlate to the gateway request's native turn, not capture whatever response is currently last in the shared conversation. Human turns not admitted by the gateway remain externally authored observations; do not manufacture gateway Work ownership for them. Server restarts and stale node epochs are fenced, with local receipts/results reconciled before resuming delivery.

### Queue, steer and human concurrency
Initial policy belongs to the joined harness/surface configuration. Default queue serializes submissions until native evidence proves readiness; steer is available only when the exact live surface proves safe in-flight steering. Native provider busy/ready/terminal evidence must be qualified; absence of a stop/control button, a connection heartbeat or synthetic activity is not completion. Unsupported steer must not silently become a new chat, process, interrupt/retry or prompt in another session. Choose and document explicit queue fallback versus rejection when the configured policy is unavailable; the decision is visible in a compact delivery receipt. A client per-request delivery-policy override is a later extension with capability/permission validation, not an unreviewed MVP tool parameter.

Map human input overlapping remote prompts, two remote submitters, two clients on one node, local native queues, in-flight steer plus queued follow-up, permission dialogs, mid-turn unregister, cancellation of queued versus active requests, and 'cancel only my request' versus interrupting a shared turn. Define ordering/deduplication/queue fairness and interaction with SH25 without another scheduler. Steered requests may share one provider turn: specify output attribution, combined-result semantics and which requests a completion settles. Never attribute unrelated human output as a remote request's successful result. Do not assume multiple simultaneous native controller connections are allowed or that a new connection can steal an existing stdio owner.

### Capability matrix and scenario gates
For each of the four harnesses and each relevant Windows/Linux version, record native API/transport, ability to self-identify current running session, attach without new process/conversation, enumerate/verify exact ref, subscribe activity, determine busy/ready, submit prompt, steer, interrupt, detach without termination, reconnect and preserve human UI continuity. Verify upstream primary documentation and actual version-pinned probes; keep advertised/implemented/validated distinct. Provider capability metadata must expose accurate unsupported states and use existing declaration/evidence machinery.

Scenario matrix must cover: same-machine gateway/node/harness; remote gateway with local files; multiple machines same repo name; multiple callers sharing one external harness; caller blocked in MCP; same-harness self-route; human plus remote turn; queue and steer; node or MCP exit; network loss before/after accepted/start/complete; gateway/node reboot; harness exits normally; provider daemon survives UI exit; stale PID reuse/epoch; lost acknowledgements; permission prompts; external user changes workspace/model/profile; unregister/close/timeout; credentials revoked; stale native IDs; detached then rejoined; artifacts local-only; observer/control sidecar failure; and explicit unsupported attachment. Define persisted state transitions and no-kill invariants for every case.

### Tooling, documentation and round-table process
Keep stable task/session tool names where existing contracts can express routing. Propose only necessary join/register/detach/capabilities operations through approved Agents public API; source-to-wire parameter descriptions must match signatures (use the current release's strict metadata tests). Update owner CLI keyword help/config, direct MCP tool metadata, schemas/error resolutions, short owned instruction contributions, client/node installation and service docs, dashboard ownership badges and safe detach controls, compact status and explicit diagnostic/history expansion. Do not hand-edit managed agent files or return provider tokens/raw protocols/local PIDs/native snapshots by default.

Round 1: code/plan inventory and full scenario map; GPT challenges unsupported assumptions. Round 2: candidate identity/ownership/protocol/delivery contracts and state tables; independently trace deadlock, duplication, attribution and no-kill failures. Round 3: provider-specific capability probe evidence and code-level integration plan, with GPT re-review of corrected findings. Only then split implementation into bounded items and mark the design ready. A queued/active review or a generic architecture endorsement is not qualification. Keep all open decisions and follow-ups recorded, not silently settled by optimistic capability claims.

## Effort & Risk

Large and validate-first. Joining an existing human-owned transport is a different capability from launching managed ACP children. Highest risks are unsupported native attachment, inherited process cleanup killing external owners, self-MCP deadlock, competing native controllers, duplicate prompts after reconnect, and misattributed human/steered output. Keep other providers, automatic ownership transfer, keystroke automation and blind cross-machine failover out of MVP.
