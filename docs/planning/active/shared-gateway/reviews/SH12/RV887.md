# Pre-implementation review: mapping completeness, RV737 gaps, agent_jobs assumption

## Notes



## Findings

## N1: agent_jobs has NO stale LLM vocabulary — cross-component mirror steps are outdated

The plan repeatedly references "agent_jobs event/control mirrors" as consumers that need updating:
- Step 4 mentions "`agent_jobs/control.py` + `event_observer.py` mirror constants via their own event contract"
- Files section: "CROSS-COMPONENT CONSUMERS — agent_jobs event/control mirrors"

**Current state**: A grep of `src/audiagentic/agent_jobs/` for `agent_llm`, `agents.llm`, `agent-llm`, `Agent LLM`, `GW_OUTCOME`, and any `_TOPIC` constants returns **zero hits**. Agent_jobs does not carry stale LLM vocabulary and has no topic mirrors to rename.

**Action**: Remove the agent_jobs mirror references from Step 4 and the Files section. Do not invent work that doesn't exist — this reduces risk, not increases it. If a future plan adds mirrors, SH12's enforcement test (Step 7) will catch them.

## N2: Frozen mapping is incomplete — missing API/Protocol/Client method signatures

The step-0 mapping covers MCP tools, topics, schemas, service key, runtime path, and prose. It does NOT enumerate the full Python symbol surface:

**GatewayApplication Protocol** (`agents_gateway_application.py`) — 9 methods to rename:
- `submit_llm_request` → `submit_execution_request`
- `get_llm_request` → `get_execution_request`
- `wait_llm_request` → `wait_execution_request`
- `cancel_llm_request` → `cancel_execution_request`
- `run_llm_request` → `run_execution_request`
- `list_llm_requests` → `list_execution_requests`
- `list_llm_sessions` → `list_execution_sessions`
- `close_llm_session` → `close_execution_session`

**InProcessGatewayApplication** — same 9 methods (delegates to API).

**StandaloneGatewayClient** (`agents_gateway_remote_client.py`) — same 8 methods (no `gateway_overview`).

**API functions** (`agents_gateway_api.py`) — 8 public functions matching the above.

**ServiceApplication invoke router** — operation strings already listed, but the `if` chain has 10 LLM operations (not just the MCP ones).

**Action**: Expand the frozen mapping to include every Python symbol (Protocol methods, Application methods, Client methods, API function names) before starting implementation. Step N10 from RV737 calls for this but it hasn't been done.

## N3: Runtime path migration design is sound but lacks both-roots resolution detail

Step 2 proposes the `_LEGACY_GATEWAY_ROOT` pattern with `StartupLock` + `os.replace`. This is correct. However, RV737 N6 identified that "both roots exist" silently strands old records.

The current `agents_paths.py` already has a partial precedent: `_migrate_legacy_sessions_root()` detects both-roots and logs a warning but leaves the legacy tree in place. The plan says to "fold this into the project migration" but doesn't specify whether the gateway root migration should:
1. **Validated merge** — copy old records into new, then delete legacy (complex, error-prone)
2. **Fail requiring operator recovery** — refuse to start if both roots exist (safer, requires intervention)
3. **Warn + proceed with new only** — same as current sessions behavior

**Action**: Before implementation, decide which conflict strategy applies to the gateway root migration (not just sessions) and encode it in Step 2.

## N4: Machine service root migration is implicit via ServiceKey change — make explicit

Step 2 mentions "Same one-shot pattern for the machine service root (`<global-runtime>/machine/agent-llm-gateway` → `agent-execution-gateway`)" but the plan's code sample only addresses the **project-level** runtime path.

The machine-level service root is resolved by `ManagedServiceStore(GATEWAY_SERVICE_KEY)` — when the ServiceKey changes from `("agent-llm-gateway", "default")` to `("agent-execution-gateway", "default")`, the store's root path automatically shifts. **No one-shot migration code exists for the machine root** and none is proposed in the plan.

This means: after cutover, `ManagedServiceStore` reads from a new path. If the old service record exists at `<global-runtime>/machine/agent-llm-gateway/default/service.json`, it will be silently orphaned — the bootstrap won't find it, and will try to claim a new owner.

**Action**: Add explicit machine-root migration logic to Step 2: after changing `GATEWAY_SERVICE_KEY`, detect the old record under `_LEGACY_MACHINE_ROOT` and migrate it (under lock) to the new location before the first v2 start. This is critical because a stale owner record would trigger `conflict_error(22)` or force an unnecessary re-claim.

## N5: Bootstrap resolves GATEWAY_SERVICE_KEY before host starts — central resolver needed

RV737 N4 identified that bootstrap, host, ingress, and lifecycle all resolve the service key independently. The plan says to create "one gateway-owned service-root/key resolver" but the implementation is deferred to Step 2.

**Current resolution chain**:
- `agents_gateway_bootstrap.py` imports `GATEWAY_SERVICE_KEY` directly from host module
- `agents_gateway_ingress.py` imports `GATEWAY_SERVICE_KEY` directly
- `agents_gateway_lifecycle.py` imports `GATEWAY_SERVICE_KEY` directly
- Each constructs its own `ManagedServiceStore(GATEWAY_SERVICE_KEY)`

During migration, if the key changes but the migration hasn't run yet, these callers will construct stores at the new path before the legacy data is migrated.

**Action**: The central resolver from RV737 N4 must be implemented in Step 1 (before any caller uses the key), not Step 2. The resolver should:
1. Read the current `GATEWAY_SERVICE_KEY` constant
2. Check for legacy root existence
3. Migrate if needed (under lock)
4. Return the canonical root path
5. All callers go through this single resolver

## N6: Ingress spool topic migration needs more detail

RV737 N7 calls for "translate the two known old gateway trigger topics under lock preserving event IDs/idempotency" but Step 2 only says "Ingress spool moves with the directory" — which handles the **directory path** but not the **topic strings inside persisted spool events**.

If spool entries contain `agents.llm.gateway.requested` as the topic, they must be rewritten to `agents.execution.gateway.requested` before the new service processes them (otherwise the new subscriber won't match).

**Action**: Add explicit spool topic translation logic in Step 2: read each spool entry, rewrite known old topics → new topics under lock, preserve event IDs. Test crash/restart mid-migration.

## N7: File inventory is stale — re-grep before implementation (already planned but worth flagging)

The plan's own notes say the 58-file count from 2026-07-20 will shift. Current grep confirms:
- **18 source files** with stale LLM vocabulary in `src/audiagentic/components/agents/`
- **2 schema files** (`agent-llm-record.schema.json`, `agent-llm-session.schema.json`)
- **2 foundation files** (`canonical_ids.py`, `topic_registry.py` docstring)
- **13+ test files** across unit and integration suites
- **90 total hit lines** (not files, hits are concentrated in MCP tools + API + tests)

The two new modules from SH18 (`agents_gateway_store/_shared.py`, `agents_gateway_profiles.py`) are confirmed present. The plan's note about SH12 being "untouched by implementation" is correct.

## N8: Consider scope of `agent-llm-gateway` in resource_kind fields

Step 2 says "Records inside need no rewrite (no self-referencing paths); resource-kind fields inside timeline files are historical evidence and stay as written." This is defensible — `_RESOURCE_KIND = "agent-llm-gateway-request"` in `_shared.py` and `_RESOURCE_KIND = "agent-llm-gateway-session"` in `agents_gateway_sessions_store.py` will be renamed, but the **already-persisted timeline entries** keep the old value.

This is fine for historical evidence, but if any consumer (e.g., a future audit query) filters on `_RESOURCE_KIND`, it won't match legacy records. No current consumer does this, so the risk is low — but worth documenting.

## N9: Validation criterion needs to include machine-root migration test

The validation section doesn't explicitly mention testing the **machine-level** service root migration (from `<global-runtime>/machine/agent-llm-gateway/default/` to `agent-execution-gateway/default/`). This is a distinct path from project-level runtime and its own failure mode.

**Action**: Add machine-root migration test to Step 8: populate old machine root → assert one-shot rename to new path, idempotent, concurrent-safe.

## Conclusion

The plan is architecturally sound — the frozen mapping covers the right categories, the one-shot cutover strategy is correct, and the enforcement test design is good. However, three issues must be resolved before implementation:

1. **agent_jobs mirror references are stale** (N1) — remove this work from the plan; there's nothing to mirror.
2. **Frozen mapping is incomplete for Python symbols** (N2) — enumerate Protocol/Client/API method names before starting.
3. **Machine-root migration has no implementation design** (N4) — `ManagedServiceStore` auto-shifts with the ServiceKey, but the old service record will be orphaned without explicit migration.
4. **Central resolver ordering** (N5) — must be Step 1, not Step 2; all callers depend on it.
5. **Ingress spool topic translation** (N6) — directory move is not enough; persisted event topics need rewriting.

These are design gaps, not blockers. The item can proceed after the mapping is expanded and the machine-root/spool details are encoded in Steps 1-2.
