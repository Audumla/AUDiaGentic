# Standalone gateway deployment and multi-machine keyword CLI

## Description

Design and qualify a centrally hosted gateway serving multiple client machines, with the same keyword CLI/help doctrine as MP03-MP10, complete owner metadata/tooling/instructions/docs, and reuse of the existing gateway lifecycle/client/host rather than a parallel server. Planning only until reviewed design is approved for implementation.

## Steps

1. Audit existing serve, managed lifecycle, client endpoint validation, project identity, discovery, dashboard and package seams; map SH04-SH11/GA recovery and MP03-MP10/MP02 dependencies.
2. Agree command grammar and ownership boundaries with Dev GPT using actual source. Preserve shipped CLI/wire contracts and identify intentional versioned changes.
3. Define server-owned config/state, client connection binding, stable project identities and remote admission/authentication, operator scope and browser/CDP placement.
4. Define minimal installed package/service deployment, graceful drain/restart/upgrade and recovery, documentation/help/tool/schema/contribution changes.
5. Specify cross-machine Windows/Linux installed-package, protocol, reconnect, isolation and recovery qualification; split execution slices if warranted after review.

## Detailed Solution & Technical Design

### Current verified baseline
launcher.py already exposes gateway serve with --host restricted to 127.0.0.1, --port and --token-file; lifecycle status/drain/resume/stop/recover exist. GatewayServiceHost.create and GatewayHTTPServer independently enforce loopback; remote_client._validate_endpoint accepts only loopback HTTP. SH04 v1 sends absolute canonical client project-root; docs/design/gateway-shared-service.md explicitly excludes multi-machine access. This use case intentionally extends that prior boundary rather than relabeling v1 as remote-compatible.

### Proposed command contract for review
Follow established word-based management syntax: audiagentic gateway help; gateway serve help; gateway serve config FILE; gateway status/drain/resume/stop with explicit endpoint/token-file or a canonical configured connection; output json and non-interactive clauses. Retain old gateway serve --port/--host/--token-file and existing lifecycle flags through one parser/normalization path. Consider an explicit gateway connect config FILE command for client-owned persisted endpoint/credential-reference/remote-project-id binding; avoid an implicit active connection map. Decide whether minimum server-side project registration needs a command or configuration-only path. No new daemon/start alias duplicating serve; foreground serve is supervised by the OS service manager. Help/list/config validation must avoid application/browser initialization or probing.

### Ownership and shared-server contract
Agents/gateway owns hosting, connection/transport contracts, admission, principal/lease identity, durable queues and process lifecycle. CLI/MCP are thin adapters to approved owning public API; refactor current CLI imports of service internals rather than multiply them. Foundation stays neutral; Providers owns browser/CDP and model/execution integration; Project owns canonical project facts. Reuse current GatewayClient and standalone host and managed-service contracts, with explicit remote transport selection and no embedded/local fallback on failure.

Separate client-local provenance/project paths from server-owned execution roots. A stable server project identifier maps through an operator-controlled registry to an existing server checkout/config root; never interpret a Windows client path as a Linux server path or accept arbitrary client roots. Freeze project/profile/principal/context identity at admission, preserve existing client logical-session isolation and FIFO/idempotency/owner epochs. Define repository synchronization and code visibility explicitly: no implicit upload, git pull or executing arbitrary client-provided roots. Preserve existing single-process component-profile containment; specify whether differing client component profiles require isolated workers and approved server-side configurations rather than switching host-global environment.

Propose a versioned network transport/admission capability rather than weakening loopback-v1 guards. Evaluate HTTPS reverse-proxy front door versus built-in TLS, authenticated per-client identity/project permissions, separation of operator lifecycle/dashboard actions, payload bounds and timeout/lease/reconnect semantics. Tokens remain file/secret-store references; no inline credentials in URLs, args, logs, help or compact MCP responses. SSH/VPN forwarding may be a deployment option but does not solve project identity or silently make the current protocol remote-safe. Do not expose unauthenticated browser CDP or assume an HTTP endpoint implies browser readiness.

Server configured by owning versioned schema with bind/advertised endpoint, durable service root, credentials, project bindings, permitted providers and resource limits. Client config uses existing agents standalone implementation owner fields with a coherent remote binding extension; endpoint/token precedence and installation/MCP environment propagation explicit. Shared service must outlive disconnected clients and zero leases: service-manager mode differs from local auto-start idle shutdown. Remote clients never kill/restart their own host when operating on a server PID; local recovery helpers remain local or dispatch authenticated semantic server operations. Reuse GA/SH browser reconnect and request restart recovery, never duplicate ambiguous submitted prompts.

### Deployment/tooling/documentation closure
Inspect current pyproject packaging; define a gateway-oriented entry/extra/component set without claiming MP02 slim distributions already exist. Distinguish initially supported application wheel+gateway dependencies from genuinely reduced distributions; one source implementation and honest installed size/dependency evidence. Linux systemd and Windows supervision examples use foreground serve, least necessary service identity and durable state/credentials. Document browser placement and logged-in browser lifecycle, remote CDP readiness, headless/interactive limits (especially Windows session-0), startup time, health vs readiness, upgrade/drain/rollback compatibility, logs/traces/retention and backups.

Inventory/update launcher help, owning command metadata, agents implementation schemas/options/error resolutions, direct MCP tool descriptions/signatures, client connection installation propagation, short owned instruction contributions, deployment guide, architecture/non-goal documents and examples. Prefer existing agent task/status/recovery/operator tooling and compact structured outputs; add remote diagnostics only when an existing owner operation cannot express it. No generated AGENTS hand edits, duplicate tool catalog fragments, provider-specific control logic in CLI, or unchanged docs falsely claiming remote support.

### Caller-local execution extension (user clarification)
Support two explicit topologies in one gateway architecture: server-hosted execution against server checkouts, and central control-plane with caller-local execution nodes. The latter executes against the caller's approved existing worktree/files without file mirroring. Remote project identity binds (principal, node-id, workspace-id); the execution node resolves its local root. Server-side root canonicalization must not reinterpret a foreign path. Local provenance remains local provenance; central routing identity is not a fictitious server path.

The local stdio MCP is the tool boundary used by a harness. It is not a generally available reverse-control transport and does not prove permission/capability to drive its parent interactive harness. Prefer a separate node-owned execution/control channel with an outbound authenticated long-lived connection (candidate WebSocket/stream transport, exact choice subject to review). The local MCP can register/attach a node or proxy through a separately supervised local node service; choose a minimal MVP and define its lifetime explicitly. Support same-machine shared node service versus MCP-scoped node host as explicit choices, not competing implicit authorities. Running gateway commands must not bootstrap a second local gateway when a remote gateway is configured.

Use existing gateway/provider execution seams and frozen attempt manifests rather than parallel harness logic. Identify node by enrolled stable node-id and fresh boot/connection epoch; identify local client and each harness runtime independently. An opaque harness-instance ID is bound to owning principal, node, workspace, provider/surface, logical context/session, request/attempt epoch and local OS process identity. PIDs are node-local evidence, never global handles. Advertise capability/version and workspace bindings, not environment/credentials. Allow execute/start, inspect, activity/output streaming and cancel/close only through declared provider capabilities. Driving an already-running interactive caller requires supported explicit attachment/control; spawning a managed child session is the baseline. Prevent recursive self-dispatch into a caller harness waiting on its own MCP result.

The node command loop runs independently of synchronous MCP submit/wait handling: separate async task/worker/process and bounded queues, with no shared blocking read loop or stdio protocol pollution. Central gateway owns durable admission, queue/FIFO/fairness, request IDs, attempt leases, cancellation intent and compact client-facing status; node owns provider process creation, local paths/secure config and execution side effects. Write-ahead local command receipt/attempt correlation and central idempotency keys distinguish accepted/started/terminal. A lost acknowledgement is ambiguous, not permission to launch a duplicate. On reconnect reconcile local owned instances/results and central intent under fencing before resuming; never reassign or replay an execution that may still be running without proving disposition. Define artifact upload/output transfer without handing server-local filesystem paths to clients; local-only large artifacts need explicit bounded availability/transfer policy.

Machine disconnect, MCP exit and provider/harness exit are distinct. Session/node liveness is not synthetic work progress. Define queue-affinity (wait for required node), offline/paused/reconcile-required states, reconnect budgets and outer request timeouts, retained results and cancellation delivery on reconnect. Central server stays alive with no clients. Node daemon can outlive a particular stdio MCP; an MCP-scoped host cannot promise availability after caller exits. Late completions and stale commands must be attempt/epoch-fenced. Cross-node retry/failover is opt-in only where workspace, provider state and execution semantics prove it safe; no automatic switch to another machine/worktree. Multi-client same-machine shared node, multiple machines with same repo name, multiple sessions per node and conflicting shared-worktree mutations need explicit routing/ownership and concurrency policy.

CLI/help candidates must distinguish gateway hosting from node hosting/connection (for example gateway serve ..., gateway connect ..., execution node serve ... or another reviewed domain word). Do not freeze a proliferating grammar before reviewing existing runtime/surface/worker ownership. Provide named machine/node and harness-instance status/control through approved owner APIs, compact defaults and explicit detailed diagnostics. Avoid adding a new tool if current Agent Context/Work/session operations can carry the binding. Configuration, enrollment, credential references, permissions, provider availability, browser location, OS service examples, installation/MCP launch propagation, rich tool descriptions and owned instructions must document both execution locations. Packaging must allow a thin remote MCP connector and execution-node capability set without claiming unimplemented MP02 slim distribution work.

Required qualification extends to two client nodes with separate local files behind a central gateway, proving execution locality and client/node/instance isolation; independent reverse-control processing during blocked MCP waits; stdio cleanliness; duplicate/lost-ack fencing; no accidental parent/self control; node disconnect/reconnect/reboot, persisted local results and cancellation; mixed OS/path spelling; capability/profile mismatch; shared-worktree contention; local process ownership verification and stale PID/epoch refusal. Actual native harness attachment evidence must be distinguished from managed child-process simulation.

### Scenario matrix and release prerequisite
Runtime implementation starts only after current MCP-onboarding features are committed/pushed, merged, built and released successfully. Until then SH35 remains pending and design-only.

| Scenario | Execution/location decision | Required coordination/evidence |
|---|---|---|
| Gateway and harness on one machine | Existing local execution | Preserve current behavior and ownership |
| Remote gateway, caller-local managed child | Node-local workspace and provider | Explicit principal/node/workspace binding; outbound control channel |
| Multiple callers on one machine | Shared node service or explicitly scoped hosts | Independent logical clients/instances; no competing local authorities |
| Multiple machines with same repo name | Explicit node/workspace affinity | No name-only project collision or foreign path canonicalization |
| MCP call awaiting result | Independent node command loop | Cancellation/progress/control still serviced; clean stdio |
| Caller MCP exits | Node lifetime policy decides continuation | No false promise if MCP owns node; retained output and reconnect |
| Network/ack lost after start | Preserve ambiguous active attempt | Local durable receipt plus server attempt fence; no duplicate start |
| Node reboots | Reconcile local processes and central intent | New boot epoch; distinguish dead process from surviving provider chat |
| Cancel while node offline | Persist cancellation intent | Delivery on reconnect; stale completion and delayed commands fenced |
| Attach to existing interactive caller | Only declared provider control capability | No automatic parent UI control/self-recursive dispatch |
| Two sessions mutate same worktree | Explicit concurrency/resource policy | Local ownership/resource arbitration, conflict reporting |
| Browser/CDP on another host | Provider-owned remote browser session | Browser readiness/login independent of gateway and node heartbeat |
| Gateway restarts/upgrades | Durable central queue plus node reconciliation | Existing work continues without replay; version negotiation |
| Outputs reference local artifacts | Explicit node-owned transfer/availability | No unusable server path exposed as caller output |

Map these cases to existing SH25/SH28 queue work and optional collaboration rollout pull requests #32 and #29 before introducing another push bus or scheduler. Existing generic outbound result delivery is not automatically a remote execution transport.

### Source-level review corrections and topology-specific authority
Initial Dev GPT audit of f5680885e requires plan corrections; it predates SH36 and is not approval of caller-local or externally joined sessions. Actual current protocol constant is gateway-service-v3; local routes/contract remain explicit and tested. A candidate shared ingress is /v2 with a new protocol version/capability (illustratively gateway-service-v4), not relaxed old endpoint validation. Authenticate principal before lease/project/operation authorization; principal-bound logical client IDs and idempotency namespaces prevent cross-client session capture. Keep gateway recover local-only, remote service lifecycle/dashboard operator-only, and protect every remote read/write. Reuse endpoint/token-file and extend the existing agents standalone implementation with a validated shared transport and remote-project-id binding; connect explicitly selects that owning implementation, with complete-set environment override rules and no implicit connection registry. The current resolver must actually consume selected owner options, not only environment variables. Server projects are configuration-only for the initial server-hosted lane; no new project add CLI is required.

A supervised server has machine-owned config/durable state, foreground OS supervision and idle shutdown disabled. Keep TLS termination in a supported front door, backend loopback binding and scoped credential validation in the application; never forward existing unauthenticated dashboard routes as public APIs. Keep browser/CDP secrets and login on the execution side. Gateway CLI dispatch/help/config validation needs its own approved public/composition path before interactive application-graph startup.

Freeze execution authority as a tagged topology, not one universal server-root field. Server-hosted work resolves authorized project ID to operator-owned server checkout before manifest creation. Node-local work resolves principal/node/workspace identity on the execution node; the server must not canonicalize a foreign root or fabricate a host-local manifest. Exact attestation/fingerprint/manifest authority for the node case remains a round-table decision under SH36. The initial review's illustrative idempotency_key under metadata is invalid under current reserved metadata rules; canonical admission controls must remain explicit fields. Review the actual public/service/worker schema before adding any wire fields or MCP parameters. No implementation until this topology distinction, external ownership and prompt-delivery scenarios are resolved.
