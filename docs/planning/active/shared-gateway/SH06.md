# Execute multi-project jobs through context-isolated workers

## Description

Ensure one shared control plane can safely execute jobs for projects with different roots, startup directories, component profiles, MCP sets, provider configs, and credentials. Because component profiles are one-per-process and several providers have fixed or partial config isolation, use context-isolated worker/provider processes instead of attempting to switch global process state inside the gateway service.

## Steps

1. Define worker isolation and reuse policy keyed by the resolved execution-context fingerprint; start with one-job/one-worker where pooling safety is unproven. 2. Materialize provider configuration using the documented full/partial/no-isolation tiers, preferring inline or alternate config and never mutating unrelated user config concurrently. 3. Pass only the allowlisted environment and secret references needed by the worker. 4. Define worker handshake, capability verification, MCP/component materialization, cwd/workspace enforcement, and cleanup. 5. Define safe pooling/eviction criteria and prohibit reuse across incompatible fingerprints. 6. Add adversarial two-project tests with conflicting component profiles, MCP configs, model/provider settings, and fixed-config providers.

## Files

gateway worker supervision and execution-manifest modules; provider public launch/materialization APIs; component-profile/runtime integration; tests and provider evidence docs

## Validation

Concurrent jobs for two deliberately conflicting projects observe only their own roots/config/MCPs/secrets; process-global component profile never switches; unsupported provider isolation produces an explicit policy outcome; worker cleanup satisfies no-orphan guarantees.

## Effort & Risk

Highest execution risk. Fixed-config providers may require serialized access, disposable homes/config roots, or an explicit unsupported mode rather than unsafe reconciliation.
