# ACP wire negotiation and live client qualification (SH62b)

## Description

Pinned ACP wire/SDK negotiation and live-client qualification for the SH62a adapter. Split from SH62 because it needs a real ACP client (and the pinned agent-client-protocol 0.11.0 behaviour for JSON-RPC error mapping) that is not available in the hermetic environment.

## Steps

1. Pin ACP wire version 1 (integer) and the tested SDK; confirm initialize negotiation advertises only implemented capabilities (loadSession today) and refuses unsupported protocol versions.
2. Verify how the SDK serializes the registered errors (CON-ACP-001 prompt outstanding, CON-ACP-002 work failed/rejected, VAL-ACP-003 prompt without text, CON-AGW-167): they are AudiaGenticError, not RequestError, so confirm the JSON-RPC error a client actually sees and map them to RequestError with the registered code in data if needed.
3. Qualify with a real ACP client: prompt concurrency (second prompt refused), cancel races, late output after cancel, reconnect/reload behaviour of load_session/resume_session against durable Work, close_session cancelling outstanding Work.
4. Decide and document the reconnect story: ACP 0.11 has no client retry identity, so a transport retry is a new prompt.

2026-11-02 SH66a (audiagentic2), measured with agent-client-protocol 0.11.0 installed in a worktree venv and the SDK's OWN client driving the adapter over a real asyncio stream pair (run_agent + connect_to_agent; note the SDK names the writer `input_stream` and the reader `output_stream`). FINDINGS: (1) initialize negotiates wire version 1 and our loadSession=True. (2) The SDK converts any non-RequestError into JSON-RPC -32603 with data {details: str(exc)}: registered codes never reached the client (the code survived only inside message text), a plain client mistake such as a cwd outside the project was reported as an internal error, and an unexpected exception's text went on the wire. (3) Stable v1 routes initialize, session/new, load, list, set_mode, prompt, cancel, authenticate and set_config_option; session/close, session/fork and session/resume are UNSTABLE-only (use_unstable_protocol), so a stable client gets -32601 for them and cannot close a session or resume one; our close/resume/fork implementations only work when the host enables unstable methods. FIXED in this change: every protocol method is wrapped (protocols/acp/agent.py _rpc/_request_error) so failures become the right JSON-RPC error with the stable code in data: validation (VAL-*) and bad arguments -> -32602, precondition not met (CON-ACP-001 outstanding prompt, CON-AGW-16x/167) -> -32600, failed prompt Work (CON-ACP-002) -> -32603 with code and state only, unsupported method -> -32601, anything unexpected -> -32603 {code: INT-ACP-000} with no text. The code-to-JSON-RPC-class mapping is OUR choice (ACP defines none). UnsupportedAcpArgument (ValueError) now distinguishes an unsupported argument (client MCP servers, extra directories) from an unsupported method. tests/unit/agents/test_acp_sdk_wire.py (9 tests) use the SDK client; test_acp_external_adapter.py asserts the new boundary. OPEN: (a) no ACP session close/resume for stable clients means a Context opened by session/new has no stable way to end; decide whether to enable unstable methods, close on disconnect, or expire idle ACP Contexts (needs the user or SH66b); (b) no stdio/socket transport entry point or gateway mounting exists for ACP yet; (c) a run from an independent ACP client (for example a real editor client) is still required before claiming interoperability.
