# Dashboard row actions: cancel, close, archive, purge

## Description

Add one-click operator actions to the gateway dashboard (dashboard.py) for the most common cleanup operations on requests and sessions, instead of requiring a separate MCP/CLI call. Reuse the gateway's existing authenticated primitives rather than inventing new mutation logic:
- Cancel a queued/running request -> existing agent_task_cancel(request_id) / GatewayQueueManager cancel path.
- Close a live session -> existing agent_task_session_close(session_id) / close_execution_session.
- Archive a terminal request -> existing gateway_create_operation(kind='archive', scope={project-root, request-ids}) via GatewayArchiveExecutor (operations/archive.py), already fenced to TERMINAL_STATES only.
- Purge (hard delete) an archived request -> existing gateway_create_operation(kind='purge', ...), already gated by the retention policy's minimum-archive-age-seconds.
No new backend mutation logic needed for the actions themselves -- only new dashboard-facing routes/UI that call into this existing, already-guarded machinery.

## Steps

1. Add POST routes on the dashboard's HTTP surface (http_transport.py) for cancel/close/archive/purge, scoped to accept only a request-id or session-id and dispatch to the existing application-layer functions (application.py already has invoke() wired to gateway operations -- likely just needs thin dashboard-specific handlers that call the same underlying application methods used by CALL_ROUTE).
2. Add confirmation UI in the dashboard JS: each session/request row gets action buttons appropriate to its state (Cancel only for queued/running, Close only for live sessions, Archive only for terminal states not yet archived, Purge only for already-archived + past minimum-archive-age-seconds). Buttons POST and then re-fetch the snapshot to reflect the new state.
3. Surface action results/errors inline (e.g. a toast or inline row message) rather than silently failing.
4. Add integration tests in test_gateway_standalone_service.py covering: cancel via dashboard route, close via dashboard route, archive via dashboard route (including the terminal-state guard rejecting a non-terminal request), purge via dashboard route (including the retention-age guard).

## Detailed Solution & Technical Design

Auth is explicitly deferred per user direction (2026-08-20): this is an internal, single-operator, non-hostile-network dev deployment (see project memory: deployment threat model). The new POST action routes should sit in the same unauthenticated loopback tier as the existing GET /dashboard and /dashboard/snapshot routes in http_transport.py's dispatch carve-out, NOT behind the bearer-token CALL_ROUTE fence used by the rest of the RPC surface. This is a deliberate, temporary trust boundary weakening that must be flagged in code comments and revisited before any non-single-user or non-loopback deployment. When revisited, the recommended direction (from the design discussion) is a narrowly-scoped dashboard-action token distinct from the full RPC bearer token, minted at service start, only valid for cancel/close/archive/purge -- never for arbitrary RPC.
