# Machine-policy-driven session-lineage purge

## Description

Add an explicit, machine-global, disabled-by-default retention operation that purges closed provider-session lineage and its exclusively-owned gateway request/chat data after a configurable inactivity period. This is gateway-local deletion only; remote provider conversations are out of scope.

## Steps

1. Verify AS107/current session locking, generation/CAS, lineage references, and resume/new-turn admission already provide a safe purge-vs-resume fence; create a minimal AS follow-up only if that seam is insufficient.
2. Extend the machine-global gateway retention policy with session-purge-enabled (default false) and closed-session-retention-seconds (default 86400 when explicitly enabled); reject non-positive thresholds and all project/profile/provider/request overrides.
3. Define eligibility from closed/expired state plus last accepted turn timestamp, with active/live/queued/recovery/unresolved/pinned/unknown ownership states failing closed.
4. Add a durable SESSION_PURGE operation and bounded manifest containing policy/session generation, exact lineage closure, per-target dispositions, stage, digests, and block reasons.
5. Enumerate the exact session-to-request closure; delete only request records/artifacts/timelines/runtime roots exclusively owned by the target lineage, preserve shared or uncertain references, and delete the parent session/binding material last.
6. Revalidate policy, generation, ownership, recovery, and closure under the authoritative fence immediately before each destructive boundary; make replay idempotent and restart-safe.
7. Expose bounded operation status/diagnostics and explicit gateway-local deletion wording; add the full race/crash/configuration test matrix before enabling the policy.

## Detailed Solution & Technical Design

SH owns the machine retention policy, candidate sweep, SESSION_PURGE operation, manifest, and destructive gateway-local cleanup. AS107 remains the owner of durable session identity, lineage references, and resume semantics; do not weaken its pins or add a new lifecycle state solely for purge. Reuse SH24 archive/integrity primitives where applicable without changing ordinary request PURGE eligibility. The inactivity clock is the last accepted session turn, not close time, polling, heartbeat, provider activity, or process status.

Eligibility requires a closed/expired session, elapsed retention threshold, no live runtime or active/queued turn, no unresolved recovery/reconciliation, unchanged session generation/revision, known exact closure, and exclusive ownership of every selected request/material. Shared or unknown ownership blocks the operation. Resume/new-turn and retirement must serialize through the same session mutation fence/CAS; whichever wins first determines the safe outcome.

Deletion order: capture/revalidate closure; persist intent/manifest; delete request descendants and records; remove binding/session-owned local material; delete parent session last; finalize manifest. Generic status may claim only local gateway lineage deletion, never ChatGPT/provider conversation deletion.

## Code Samples & Guidance

Machine-global policy extension:
```yaml
session-purge-enabled: false
closed-session-retention-seconds: 86400
```
No per-agent, execution-profile, provider, request, MCP, or project override. Existing session-idle-timeout-seconds remains runtime-resource policy and is not repurposed.

## Validation

Configuration: absent/disabled policy causes zero new destructive behavior; enabled policy requires a positive threshold; policy digest changes block deletion; overrides are rejected. Eligibility: active/live/queued/recovery/pinned/unknown sessions block; closed sessions below threshold remain resumable; last accepted turn resets the clock; polling/heartbeat/provider activity does not. References: exclusive request closure is removed; shared or unknown ownership blocks with no partial deletion; ordinary SH24 request PURGE still refuses session-pinned requests. Races: resume/new-turn versus purge are fenced; only one outcome wins. Crash/restart after every destructive stage replays idempotently from the manifest. Semantics: old idle-close and transparent resume work before retirement; post-purge gateway session identity cannot reappear; no provider-specific branch or remote-delete call. Observability: bounded stage/disposition/block evidence contains no prompts, outputs, paths, or secrets.

## Effort & Risk

Large blast radius and destructive data-loss risk. The main hazards are session/request lineage races, shared references, recovery uncertainty, crash-mid-delete, and accidental claims about remote provider deletion. Default-off policy and fail-closed unknown handling are mandatory.

## Standards

arch-standards §§1,3,4,6,7,8; observability-standards; SH24/SH26/AS107 retention, fencing, redaction, and provider-neutral ownership contracts.

## Acceptance Criteria

- Existing configurations and an absent policy produce zero new destructive behavior; the feature is disabled by default.
- Enabled policy requires a positive closed-session-retention-seconds value and cannot be overridden by project, agent, execution profile, provider, request, or MCP input.
- Only closed/expired sessions past the last-accepted-turn threshold with no active, queued, unresolved, pinned, shared, or unknown references are eligible.
- Purge deletes only the proven exclusive session→request closure, with the parent session deleted last; shared/unknown ownership blocks without partial deletion.
- Resume/new-turn and purge are fenced so exactly one valid outcome wins; ordinary idle-close and transparent resume remain unchanged before retirement.
- Durable SESSION_PURGE manifests make crashes and retries idempotent and auditable without storing prompts, outputs, paths, or secrets.
- Existing SH24 request PURGE and AS107 pinning semantics are unchanged.
- Public status states gateway-local lineage deletion only and never claims remote provider conversation deletion.
