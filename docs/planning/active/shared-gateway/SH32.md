# Machine-policy-driven session-lineage purge

## Description

Add an explicit, machine-global, disabled-by-default retention operation that purges closed provider-session lineage and its exclusively-owned gateway request/chat data after a configurable inactivity period. This is gateway-local deletion only; remote provider conversations are out of scope.

## Steps

1. Inspect AS107/current session serialization, generation/CAS, lineage references, and resume/new-turn admission; create a narrowly scoped AS prerequisite only if the authoritative fence is insufficient.
2. Extend the machine-global gateway retention policy with session_purge_enabled (default false) and session_purge_inactivity_seconds (positive threshold, recommended 86400 when enabled); reject project, agent, profile, provider, request, and MCP overrides.
3. Define eligibility from closed/expired state plus last_accepted_turn_at; require the live provider runtime to be closed/absent and block active, in-flight, admitted-but-unresolved, queued, recovery, reconciliation, pinned, shared, unknown, or ambiguous ownership.
4. Add a durable SESSION_PURGE operation and bounded manifest containing policy identity/digest, session generation, exact lineage closure, per-target dispositions, stage, timestamps, digests, and block reasons.
5. Compute the complete session-to-request closure before deletion. Delete only gateway-local request records, admitted input material, response artifacts, timelines, runtime roots, and other descendants proven exclusively owned by the lineage; preserve shared or uncertain references and remove the parent session/binding last.
6. Revalidate policy, generation, ownership, recovery, and closure under the authoritative session fence immediately before destructive boundaries; make replay and restart recovery idempotent.
7. Expose bounded operation status/diagnostics that say gateway-local session purge only; add the full race, crash, closure, retention, and configuration test matrix before enabling the policy.

## Detailed Solution & Technical Design

SH32 owns the machine-global policy, eligibility scanner, SESSION_PURGE operation, referential closure, manifest, and gateway-local destructive cleanup. AS107 remains the owner of durable session identity, lineage references, and transparent resume semantics; do not weaken pins or add a durable retired lifecycle state solely for deletion. Reuse SH24 archival/integrity evidence where its destructive-retention contract applies, without changing ordinary request PURGE eligibility or pinning rules.

The purge clock is only last_accepted_turn_at. It is not close time, provider activity, watchdog activity, polling, heartbeat, cleanup retry, or process state. A session is eligible only when policy is enabled, it is locally owned and closed/expired, the live runtime is absent, no current/in-flight/admitted-but-unresolved turn or recovery exists, the threshold has elapsed, the exact closure is known, and every selected object is exclusively owned. Unknown means BLOCK.

Resume/admit-new-turn and purge must serialize through the same authoritative per-session mutation fence or generation CAS. Under the fence, reread state, generation, inactivity, recovery, and ownership immediately before deletion; exactly one side may commit against a generation. If AS107 already supplies this primitive, no AS item is needed. If not, add only the minimal AS fencing prerequisite—no retention policy, deletion, or new lifecycle state.

SESSION_PURGE is one deterministic local cleanup operation, not a configurable archive/delete matrix and not a remote-provider deletion workflow. Persist durable intent/manifest before destructive work, delete request-owned descendants and records, remove session binding/local material, then delete the parent last and finalize evidence. Already-deleted same-operation descendants are successful on replay; newly shared or ambiguous references block. Public semantics must never imply ChatGPT/provider conversation deletion.

## Code Samples & Guidance

Machine-global gateway retention policy:
```yaml
session_purge_enabled: false
session_purge_inactivity_seconds: 86400
```

No per-agent, execution-profile, provider, request, MCP, or project override. Existing execution-profile session-idle-timeout-seconds remains the live-provider resource close policy and is not repurposed.

## Validation

Configuration: absent/disabled policy causes zero new destructive behavior; enabled policy requires a positive threshold; policy changes or stale policy digests block deletion; all lower-scope overrides are rejected. Eligibility: active/live/queued/in-flight/admitted-but-unresolved/recovery/reconciliation/pinned/shared/unknown/ambiguous sessions block; closed sessions below threshold remain durably resumable; only a new accepted turn resets the clock.

References: compute the complete closure before mutation; exclusive request records and all request-owned descendants are removed; shared or unknown ownership blocks without partial deletion; ordinary SH24 request PURGE still refuses session-pinned requests. Races: resume/new-turn versus purge use the authoritative session fence and exactly one generation outcome wins. Crash/restart after every destructive stage replays idempotently from the manifest, with parent deletion last.

Semantics: existing idle-close and transparent resume are unchanged before purge; after purge, old gateway-local identity cannot transparently resume and normal admission creates a new binding. No provider adapter or remote-delete call is involved. Observability: bounded stage/disposition/block evidence contains no prompts, outputs, filesystem paths, or secrets and says local gateway purge only.

## Effort & Risk

Large blast radius and destructive data-loss risk. The main hazards are session/request lineage races, shared references, recovery uncertainty, crash-mid-delete, and accidental claims about remote provider deletion. Default-off policy and fail-closed unknown handling are mandatory.

## Standards

arch-standards §§1,3,4,6,7,8; observability-standards; SH24/SH26/AS107 retention, fencing, redaction, and provider-neutral ownership contracts.

## Acceptance Criteria

- New policy is machine-global, disabled by default, and absent configuration changes no existing retention behavior.
- session_purge_enabled must be explicit; session_purge_inactivity_seconds must be positive when enabled and cannot be overridden by project, agent, execution profile, provider, request, MCP, or caller input.
- Existing execution-profile session-idle-timeout-seconds semantics are unchanged.
- Only locally-owned closed/expired sessions past the last_accepted_turn_at threshold with no live runtime, active/in-flight/admitted-but-unresolved work, recovery, pinned references, shared references, or unknown ownership are eligible.
- Resume/new-turn and purge are fenced by the authoritative session generation so exactly one valid outcome wins.
- Purge computes complete referential closure before deletion and removes only exclusively-owned gateway-local descendants; shared or unknown ownership blocks without partial deletion.
- Request artifacts, timelines, runtime roots, records, bindings, and session material are removed consistently, with the parent session deleted last.
- Durable SESSION_PURGE manifests make crashes and retries idempotent and auditable without retaining deleted payloads.
- Existing SH24 request PURGE and AS107 identity/pinning/resume semantics remain unchanged.
- Public status and audit evidence describe gateway-local lineage deletion only and never claim remote provider conversation deletion.
- No durable retired lifecycle state or archive-vs-delete mode is introduced solely for this feature.
