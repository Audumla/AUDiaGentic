# Supported stop and restart for the shared gateway service

## Description

There is no supported way to stop or restart a running shared gateway service. P7 (#160) retired gateway drain/stop/recover from the CLI and `status` is read-only, so an operator can only kill the process. On 2026-10-29 a shared service (automatic mode) kept running code loaded hours earlier while its editable install moved to newer main twice; it became a mixed-version process and every gpt-auto request failed with TO-PROC-002 (journal file lock timeout). Agent sessions could not restart it: one was blocked by its safety check from signalling a process it did not start, and no owner-side route exists.

## Steps

1. Add an operator command (keyword CLI, e.g. `audiagentic gateway restart` / `stop` for the local managed service) that asks the owning service to drain and exit through the managed-service record, never by PID guessing.
2. Restart = graceful drain, exit, then the next client starts a fresh service on current code.
3. Refuse when the caller is not authorized for that service record; report what holds the port otherwise.
4. Document that moving the runtime install under a live service requires a restart.

## Notes

2026-10-29 correction (audiagentic session): a supported restart does exist. management_api.gateway_restart (also the admin MCP tool agent_gateway_restart) asks the running service over an authenticated lease to drain and hand off; the retiring host launches its own replacement on the installed code, with no external signal. The service application also implements service_drain, service_resume and service_stop operations (remote client service_drain/service_stop). What P7 retired is only the public CLI keyword route. Remaining scope of this item: a keyword CLI route for these existing operations and the operator documentation (move the runtime install only together with a restart). In the 2026-10-29 incident, agent sessions' own permission checks declined to restart a shared service they had not started, which is correct; the operator runs it.

2026-10-29 operator findings from two real restarts of the shared service through management_api.gateway_restart:
1. Handoff port race: the retiring host launches its replacement while it still holds the service port, so the replacement fails with EADDRINUSE and the restart reports CON-MSVC-029 (did not become ready); the next client then starts a fresh service normally. The handoff must wait for the port to be released (or the replacement must retry bind) before reporting failure.
2. Runtime moves need restarts on both sides: moving the editable runtime install under a live service makes it mixed-version (TO-PROC-002 journal lock timeouts on every gpt-auto request), and harness MCP server processes started before the move fail lazily with ImportError. The operator procedure is: move the runtime, restart the shared service, restart harness sessions' MCP servers. Agent sessions' permission checks require an explicit operator request for each restart, which is correct.

2026-10-30 handoff port race fixed (CON-MSVC-029 after a restart that worked). Cause: the replacement binds as soon as it starts while the retiring owner may still hold the listening socket, and the bind had no retry. Fix: (1) the retiring host closes its listening socket explicitly (`_release_port`) before launching the replacement; (2) the replacement is started with `--bind-wait 30` (an argument, not an environment variable) and GatewayServiceHost.create retries the bind only on EADDRINUSE, bounded, via `bind_with_wait`; a first start has wait 0 and still fails at once on a held port, so a different service holding it is never papered over. Tests: bounded retry with an injected clock, non-EADDRINUSE never retried, a real held socket released by a timer is taken over, the launcher adds the argument exactly once, close-before-launch ordering. Operator procedure documented in docs/guides/shared-gateway.md (move the runtime only together with a restart; restart harness MCP servers; the agents.gateway-code and agents.gateway-port doctor checks). NOT done, left as a decision: a keyword CLI route for restart/stop. P7 (#160) retired drain/stop/recover from the CLI on purpose and `gateway status` is documented as read-only, so re-adding a local control route reopens that decision; the supported route is the admin MCP tool / management_api.gateway_restart.

2026-10-30 keyword CLI route added: `audiagentic gateway restart [non-interactive] [output json]` (commands/gateway.py), a thin adapter over management_api.gateway_restart (the same function the admin MCP tool calls), so the operator action is no longer split across surfaces. It asks first unless non-interactive, waits for the replacement via the existing bounded wait, and reports old and new owner epochs. drain/resume/stop/recover stay retired (the rejection tests are unchanged). Earlier note on this item over-claimed that the CLI exclusion was a deliberate design decision; the only trace is a help-text line from the SH37 shared-connector CLI, with no recorded rationale. Acceptance: an operator can restart the local shared gateway service without kill (met); stop is not provided (not needed for the update procedure); in-flight work drains or is recovered by the existing restart recovery (unchanged); the command never signals a process (met, it asks the owner over the managed lease).
