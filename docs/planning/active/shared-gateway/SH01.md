# Freeze the shared gateway target architecture and staged migration gates

## Description

Turn the approved multi-instance requirement into the authoritative shared-gateway program boundary. Define a single machine-wide control-plane service used by many harness sessions and projects, while allowing isolated provider/worker processes where execution context cannot safely coexist in one process. Re-open the deferred rows in docs/design/gateway-shared-service.md and specify ownership across shared-gateway, agent-sessions, agents, providers, foundation process lifecycle, MCP servers, and future external event transport.

## Steps

1. Inventory current in-process gateway entry points, singleton state, persisted records, event contracts, session runtime, and reconciliation assumptions. 2. Record the target topology: thin clients/MCP facades -> local shared gateway control plane -> context-isolated execution workers/providers. 3. Define phase gates and rollback points from in-process facade through explicit standalone service, self-managed discovery, shared default, and removal of obsolete ownership paths. 4. Define component ownership and cross-plan dependencies, explicitly preserving AS ownership of session semantics and PR05 ownership of reusable process primitives. 5. Define compatibility policy, protocol/version negotiation, security boundary, and non-goals. 6. Review the design before implementation items advance.

## Files

docs/design/gateway-shared-service.md; docs/planning/active/shared-gateway/; architecture documentation identified by the inventory; no implementation in this item

## Validation

Design review proves every current same-process assumption has an owning migration item; topology supports two projects with different execution contexts; each phase has entry, exit, rollback, and deletion criteria; no duplicate ownership with AS08, PR03, or PR05. The layer map explicitly shows MCP/event/CLI/local-service transports as inbound adapters over framework-neutral public APIs, and defines automated dependency checks.

## Effort & Risk

High architectural leverage. The main risk is treating one shared service as one homogeneous execution process despite process-global component-profile state and provider config limitations.

## Standards

Architecture Standards §§1–7; CREATING_A_COMPONENT §2 and §6 thin-MCP boundary; AR25 protocol-adapter enforcement; Observability Standards.

## Notes

This is the program boundary/tracker, not a permanent bucket for implementation. Depends on the existing EDJ13 decision record as baseline evidence and AR25 for the enforced MCP/protocol-adapter boundary.
