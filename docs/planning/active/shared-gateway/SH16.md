- **Run 1: PASSED.** `test_gateway_dispatches_real_pi_provider_via_full_isolation_worker` completed cleanly — real llama-server binary install, real GGUF download, real Pi CLI + MCP adapter + embedded rig dispatch, real completed output. This is the first ever recorded clean pass of this test.

The durable record shows the attempt ran `05:26:00.179254Z` → `05:29:05.791990Z`, ~185.6s against the test's own hardcoded `timeout_seconds=180` (`tests/integration/agents/test_gateway_pi_smoke.py:174`). Model/binary provisioning (`start_or_attach_embedded_rig`) completes *before* this window starts, so the 180s is spent entirely on Pi CLI startup plus one real inference call for the trivial smoke prompt (`"Reply with exactly: OK"`) — not on prompt complexity, which the earlier investigation's opaque failure could never establish.

**Root cause is narrowed, not fully identified:** this is consistent with normal timing variance on a resource-constrained Docker Desktop host (WSL2/Hyper-V, CPU-only inference, no dedicated GPU, `--rm` so nothing is warm across runs) crossing a fixed wall-clock ceiling — not a functional defect, since run 1 proves the exact same path can complete correctly. Whether Pi CLI startup overhead, MCP handshake, or first-token latency dominates the 180s budget is unconfirmed; not investigated further because the correct fix is systemic, not a bigger magic number here.

**Deliberately not bumping the test's `timeout_seconds=180` as a band-aid.** SH22 ("Replace wall-clock worker kills with activity-renewed execution watchdogs") exists precisely to replace fixed-ceiling kills with activity-verified ones — this test hitting `TO-AGW-076` under real timing pressure is a second, independent confirmation of SH22's premise (the first being the `req_0313ab00126c4e32`/2700s incident already recorded there). Picking a new fixed number now would just move the flake threshold and could mask a real regression; SH22 is next in this session's own build sequence and is the real fix.
