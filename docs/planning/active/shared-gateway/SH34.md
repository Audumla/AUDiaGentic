# Close provider-session restart recovery and watchdog gaps

## Description

Make restart recovery truthful and resilient for running gpt-auto provider-session requests. Preserve no-resubmit safety, keep recovered work visible to watchdog supervision, persist proven-unsent checkpoint clears durably, honor admission-frozen activity leases, and isolate watchdog failures per request.

## Steps

1. Register recovered running provider-session requests with the watchdog before invoking recovery, and re-register each scheduled recovery attempt under the existing owner fence. 2. Centralize persist-clear-before-memory-clear for proven-unsent, staged timeout, and cancellation/quiescence paths; emit explicit not_started/non-ambiguous evidence. 3. Resolve and pass the frozen request watchdog lease into provider-session activity relays. 4. Isolate watchdog-pass exceptions per registry entry and continue diagnosing later requests. 5. Add focused crash/recovery, two-restart exact-once, durable-clear, lease-policy, and multi-record watchdog tests. 6. Run GPT audit and live CDP restart validation.

## Detailed Solution & Technical Design

Keep SessionRuntime/ durable request records authoritative. Recovery must remain observation-only whenever provider side effects are ambiguous. Only positive proven-not-started evidence may reload admitted-prompt.txt. Recovered running requests need the same request-owned watchdog registry identity as normal starts without reusing the queued-to-running CAS. Durable checkpoint clear must be written before in-memory checkpoint mutation is exposed. Relay lease duration must come from the admission-frozen watchdog policy, not a default constant.
