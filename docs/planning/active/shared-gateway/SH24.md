# Workflow-driven gateway reconciliation and retention operations

## Description

Build provider-neutral, durable gateway operations for RECONCILE, ARCHIVE, and PURGE. The workflow declares only gateway-operation transitions; the operation store is authoritative, target evidence and dispositions remain separate, and all destructive effects fail closed. SH24 does not own service drain/stop, live session control, provider-specific recovery, or the normal agent work queue.

## Steps

Slice A — workflow and durable operation authority
1. Add gateway-operation to agents/workflows.yaml with accepted -> running|failed and running -> completed|failed; state sets dispatchable=[accepted], active=[accepted,running], terminal=[completed,failed].
2. Add immutable command intent plus durable operation record/store with operation-id, kind, normalized scope, state, revision, expected owner epoch, correlation-id, timestamps, result summary and safe error. Same ID+intent is idempotent; same ID+different intent conflicts.
3. Write a per-operation timeline.ndjson for created/claimed/completed/failed and optional notification-deferred/recovery-invalidated.

Slice B — SH10 admission/drain correction
4. Land RV952 in SH10 before destructive operations: draining rejects every work-producing call even through an existing lease; read/control/gateway-operator calls remain allowed. Include admission-in-progress and active gateway operations in quiescence.

Slice C — runner and advisory notifier
5. Claim ACCEPTED operations with CAS, execute from the durable store, and recover abandoned RUNNING operations only with owner-epoch evidence. Define GatewayOperationNotifier as best-effort wake-up only; the durable ACCEPTED record is the outbox. Loss, duplicates, reorder, and restart are safe because consumers reread and CAS the store.

Slice D — reconcile
6. Build provider-neutral evidence projection LIVE|PROVEN_DEAD|UNKNOWN. Dry-run never mutates. Apply revalidates evidence and owner epoch at the effect boundary and changes only PROVEN_DEAD targets through the existing request/session transition authority. UNKNOWN is blocked, never inferred dead from age, empty queues, missing page/process, silence, or timeout.

Slice E — archive
7. Archive only terminal gateway request records selected through store queries. Archive is orthogonal metadata/storage, not a new execution workflow state. Preserve session lineage, bindings, runtime roots, provider continuation references, and timelines.

Slice F — purge
8. Purge only already-archived, retention-qualified, unpinned records, after revalidation. AS107 owns session retention pins; SH26 owns machine policy. Missing policy or any referential pin yields BLOCKED with a safe reason. Do not purge session/binding/provider/runtime-root material in v1.

Slice G — public surfaces and soak
9. Expose typed operations and query through GatewayOperationsClient and operator-only ag-agents-mgmt MCP plus CLI. Adapter -> public operations client -> GatewayServiceApplication -> GatewayOperationsApplication. Do not add these methods to the activity GatewayClient and do not expose them through gateway_mcp.py.
10. Add workflow/store/runner/evidence/archive/purge/parity/boundary/restart/race tests. SH11 requires only Slices A-D before shared-mode soak; E-F do not block cutover.

## Detailed Solution & Technical Design

Place the cohesive implementation under gateway/operations/: contracts.py, operation_store.py, application.py, notifier.py, pump.py, then evidence.py and archive.py in their owning slices. This avoids collision with gateway/management_api.py, which manages component implementations/configuration.

Authority and state:
- Management operation lifecycle: ACCEPTED, RUNNING, COMPLETED, FAILED.
- Evidence: LIVE, PROVEN_DEAD, UNKNOWN.
- Per-target outcome: CHANGED, UNCHANGED, BLOCKED.
These are deliberately separate types. A blocked target does not fail or extend the workflow state machine.
- The existing gateway request/session stores remain the only execution lifecycle authorities. SH24 orchestrates through them and never creates a second execution-state repository.
- Every destructive boundary rereads current durable state and ownership evidence; stale census results cannot authorize mutation.

Crash semantics:
- Operation creation durably commits ACCEPTED before notifier publication. That record is the transactional outbox.
- A notifier carries only operation-id and is advisory. A periodic/startup pump scans dispatchable operations.
- A claimant CASes ACCEPTED -> RUNNING using revision/owner epoch. Duplicate, reordered, or lost notifications cannot cause duplicate execution.
- Recovery never guesses: an abandoned RUNNING operation is failed/requeued only under an explicit policy with positive owner-epoch evidence.

Agent/provider/MCP boundaries:
- An Agent Definition combines role behaviour/capabilities/instructions with an Execution Profile. The profile selects a Provider, which supplies the provider-specific transport/runtime.
- SH24 operates on requests and sessions as agent executions, independent of the provider backing the configured agent. Browser gpt-auto, ACP, and MCP/A2A-backed execution are provider/runtime variants—not agent definitions—and receive no provider-specific branches in gateway operation code.
- MCP is an inbound adapter, never a lifecycle authority, store, worker queue, or provider transport. Destructive tools belong only on ag-agents-mgmt and are not propagated into provider tool contexts.
- Formalize a narrow GatewayOperationsClient protocol, implemented initially by the same loopback/standalone clients. Keep the activity GatewayClient stable.

Retention:
- Archival preserves resumable conversation identity. A missing tab, runtime handle, or local process is normally UNKNOWN, not proof of death.
- Any request referenced by resumable session lineage or a durable session runtime root is REFERENTIALLY_PINNED until AS107 supplies a safe release path.
- SH26 supplies machine-scoped retention policy. No hard-coded purge age or project-local weakening is allowed.

## Code Samples & Guidance

Workflow configuration:
```yaml
gateway-gateway-operation:
  initial-state: accepted
  transitions:
    accepted: [running, failed]
    running: [completed, failed]
  state-sets:
    dispatchable: [accepted]
    active: [accepted, running]
    terminal: [completed, failed]
```

Closed contracts:
```python
class ManagementOperationKind(StrEnum):
    RECONCILE = "reconcile"
    ARCHIVE = "archive"
    PURGE = "purge"

class WorkEvidence(StrEnum):
    LIVE = "live"
    PROVEN_DEAD = "proven-dead"
    UNKNOWN = "unknown"

class TargetDisposition(StrEnum):
    CHANGED = "changed"
    UNCHANGED = "unchanged"
    BLOCKED = "blocked"

class GatewayOperationNotifier(Protocol):
    def notify(self, operation_id: str) -> None: ...

class GatewayOperationsClient(Protocol):
    def create_management_operation(self, command: ManagementCommand) -> ManagementOperation: ...
    def get_management_operation(self, operation_id: str) -> ManagementOperation: ...
```
The notifier payload contains only operation-id. The pump always rereads the authoritative store and CAS-claims before effects.

## Validation

- Workflow rejects undeclared transitions; evidence and target dispositions are not workflow states.
- Operation intent idempotency and conflict behavior are durable across restart.
- Lost/duplicate/reordered notifier messages and caller exit cannot lose or duplicate work.
- Dry-run makes no mutation; apply changes only positively proven-dead targets and rechecks owner epoch at mutation.
- Persisted stale-looking records without sufficient evidence remain UNKNOWN/BLOCKED.
- Archive accepts terminal request records only; purge refuses live, nonterminal, unarchived, under-retention, unknown-evidence, or referentially pinned targets.
- A closed gpt-auto tab resumes the same provider conversation after request archival; provider-neutral tests also cover generic fake and ACP/MCP-backed agent paths without provider-ID branches.
- Per-operation timeline has redacted correlation-linked milestones; notification failure is observable but does not roll back durable admission.
- Application/service/client/MCP/CLI return canonical parity results, and architecture tests prove adapters import no gateway-operation store/workflow/notifier/provider transport.
- Drain/reconnect/restart races, mixed live/stale multi-project data, and bounded batch behavior are covered.

## Effort & Risk

High. False orphan classification, stale ownership evidence, destructive retention, multiprocess CAS, and session lineage loss are the main hazards. Default outcomes are UNKNOWN/BLOCKED and dry-run; broker migration is explicitly separated into SH25.

## Standards

ARCHITECTURE_STANDARDS §§1-8: inward dependencies, config-declared transitions, single durable authority, stable redacted contracts, timeline-vs-event separation, provider-neutral boundaries, automated enforcement, thin protocol adapters. OBSERVABILITY_STANDARDS: per-operation timeline.ndjson through record_timeline_event, correlation-id propagation, bounded redacted attributes, best-effort timeline writes after primary mutation. Evidence-led scope: no generic workflow-engine enhancement, full broker, tombstone, or provider branch without an owning item and evidence.

## Acceptance Criteria

- The generic workflow engine is unchanged; gateway-operation is config-declared with only ACCEPTED/RUNNING/COMPLETED/FAILED transitions.
- Durable operation creation precedes advisory notification; restart/loss/duplicate/reorder cannot lose or duplicate effects.
- Evidence, target disposition, gateway-operation state, and request/session lifecycle remain separate closed contracts.
- Reconcile mutates only positively PROVEN_DEAD targets after boundary revalidation; UNKNOWN is BLOCKED.
- Archive/purge preserve resumable provider-session lineage; pinned or policy-ineligible records cannot purge.
- SH24 handles configured-agent executions through request/session contracts, independent of the selected execution-profile/provider; no provider-ID branches exist.
- Gateway operator MCP tools are operator-only in ag-agents-mgmt and adapters contain no domain/store/queue/provider policy.
- Durable redacted per-operation timelines and parity/architecture/race/restart tests pass.
- Before cutover, the new implementation passes isolated and shadow/contract validation against the existing durable request/session history and a rollback rehearsal.
- Cutover is one explicit configuration transition to the new sole gateway authority; it preserves request/session status and visibility.
- After successful cutover evidence, delete the predecessor implementation selection, superseded scheduler/status path, compatibility shims, and their production tests. No permanent dual-run or fallback remains.
