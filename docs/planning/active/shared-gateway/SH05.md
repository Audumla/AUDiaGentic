# Add race-safe gateway discovery and self-managed startup

## Description

Implement the initial self-managed operating mode through the framework-neutral gateway client/bootstrap API: a harness, MCP adapter, CLI, or other caller discovers the machine-wide gateway; if none is healthy and compatible, exactly one contender starts a detached standalone service while all other contenders converge on it. Protocol adapters do not implement discovery, locking, process identity, retry, or startup policy themselves.

## Steps

1. Define well-known per-user/per-install discovery records, endpoint identity, ownership proof, protocol compatibility, and stale-record rules. 2. Use PR05 startup locks and verified process identity for single-winner startup across concurrent harnesses. 3. Detach service lifetime from the starting harness and its process group/job object. 4. Add bounded connect/start/retry behavior and clear errors for incompatible or unhealthy gateways. 5. Handle upgrade/version skew without killing an unrelated active service. 6. Add concurrent cold-start, stale record, PID reuse, starter crash, and reconnect tests on Windows and POSIX.

## Files

shared gateway public client, discovery, and bootstrap modules; thin CLI/MCP wiring that calls the public client; PR05 public APIs only; tests

## Validation

A barrier-start test with multiple harness processes creates exactly one gateway; later clients reuse it; killing the starter does not kill the service; stale or forged discovery records cannot cause unsafe process termination; version mismatch is explicit. Architecture tests prove MCP/CLI adapters contain no lock, PID, discovery-record, process-launch, or retry policy.

## Effort & Risk

Complex due to cross-process races and Windows lifetime semantics.

## Standards

AR25; Architecture Standards §§1,3,4,6,7.

Depends on SH04, AR25, and PR05. Discovery identifies a control plane, not a project; project identity is carried in every SH02 execution envelope.
