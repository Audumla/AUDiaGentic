# Isolated worker swallows real exception detail on unexpected failure (INT-AGW-076 opaque)

## Description

agents_gateway_worker_host.py:118-129's bare `except Exception` catch-all reports every unexpected worker-side failure as the same generic message ("isolated provider worker failed unexpectedly", code INT-AGW-076) with zero diagnostic detail — no traceback, no exception type/message. Compounding this, `with redirect_stdout(sys.stderr)` (line 96) discards the provider's stdout entirely, and agents_gateway_worker.py's spawn_supervised call captures the child's stderr but discards `_stderr` unconditionally (line 186) instead of persisting it on error. When a real bug happens inside providers_api.execute_provider_turn, there is currently no way to diagnose it after the fact — not from the gateway record, not from any log file.

Discovered 2026-07-20 while live-testing the gateway MCP surface (agent_llm_submit) against the pi/mid-coder profile: a short, simple prompt succeeded normally, but a longer (~4KB), code-fence-heavy prompt asking the agent to implement a real feature failed in under 1 second with exactly this opaque error. The failure is almost certainly a real bug somewhere in prompt encoding/handling for that size/content class (candidates: worker_protocol message encode/decode with embedded backticks or multi-line content, or a pi-adapter command-line/argument-length limit), but it cannot be root-caused today because the exception detail never survives past the worker process boundary.

## Steps

1. Reproduce: submit a large, backtick/code-fence-heavy prompt via agent_llm_submit against a full-isolation provider (pi/mid-coder reproduced it 2026-07-20) and confirm the near-instant INT-AGW-076 failure.
2. Capture real diagnostics safely: in agents_gateway_worker_host.py's `except Exception` handler, capture traceback.format_exc() and the exception type/message, and persist them somewhere redacted-safe for operator diagnosis (NOT across the public protocol pipe, which must stay a clean data channel) — e.g. persist the child's captured stderr in agents_gateway_worker.py on any non-zero/error outcome instead of discarding it.
3. Once real diagnostics are visible, root-cause the actual reproduction case from step 1 and fix it (likely a prompt-size/content encoding issue).
4. Add a regression test using a similarly-shaped large/code-fence-heavy prompt through the real gateway to prevent recurrence.
