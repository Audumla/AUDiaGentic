# Define provider operation semantics and retain provider-owned capability knowledge

## Description

Keep provider capability knowledge, evidence, ids, validation, and reference tooling under providers; foundation owns no capability concept. Define one providers-owned caller vocabulary — `plan|apply|prune|status` — while keeping recipe lifecycle methods private mechanics. Requesters import only `providers_api`; explicit provider registration, never catalog data, enables behavior.

## Steps

0. Confirm `foundation/capability_catalog` remains absent; inventory every `providers_api` export, caller, providers-MCP tool, test patch seam, and external compatibility obligation.
1. Keep rich provider capability knowledge/config validation and lossless catalog/reference tooling under providers/MA19. It documents facts; it never dispatches.
2. Define public semantic modes: `plan` (preview, no durable mutation), `apply` (make desired state real), `prune` (remove only owned state), and `status` (read/check, no durable mutation).
3. Replace provider-facing recipe re-exports with providers_api family operations/adapters. Requesters cannot construct registries, select ProviderRecipeKind, or call recipe lifecycle methods. Internal provider/MCP compatibility code may adapt legacy tool names only after consumer inventory proves need.
4. Preserve family-specific minimal payloads: CLI desired state/repair flag, model desired state, LSP desired entries/ownership scope, MCP/hook/plugin desired data. Do not create universal CapabilityRequest/CapabilityResult/CapabilityRecord merely to share modes.
5. Providers public adapters map modes to recipe/config mechanics. `probe/install/configure/verify/uninstall/dry_run` remain internal. Current ProviderRecipeRegistry is internal provisioning infrastructure; add explicit duplicate-registration/error behavior before depending on it as composition substrate.
6. Move ProviderRecipeKind and recipe construction behind providers internals; retain it only as an implementation classification while migration consumers exist. It is never public taxonomy or documentation schema.
7. Inventory `ProviderRecipeResult.details` consumers before adding fields. Promote collision/reload/ownership action/changed paths only where actual callers parse them; otherwise preserve redacted provider detail.
8. Codify one sanctioned requester edge: `audiagentic.components.providers.providers_api`. Forbid provider internals/config/catalog imports and providers→requester imports.
9. Preserve execution separation: provider operation modes do not select execution adapters/transports. MA17 owns provider execution entry.
10. Tests: public export allowlist; failed requester imports of recipe types/registry; legacy provider-MCP compatibility where retained; no foundation capability concept; explicit registration; plan/status non-mutation; scoped prune; catalog non-authority.

## Validation

1. Foundation contains no capability package/type/protocol/facade. 2. providers_api public export list contains no ProviderRecipeRegistry/Kind/CapabilityRecipe or recipe lifecycle entry. 3. Every requester provider operation has only plan/apply/prune/status semantics. 4. plan/status cause zero durable mutation; prune preserves unmanaged/other-scope state. 5. Payload/result fields have current consumer. 6. Registry/provisioning mechanics are not forced onto config operations and duplicate registration cannot silently replace a composition binding. 7. ProviderRecipeKind is not capability taxonomy. 8. Approved requesters import providers_api only; providers import zero requester domains. 9. Explicit registration alone enables behavior; catalog cannot dispatch. 10. Agent execution remains separate.

## Effort & Risk

Mid correction. Main risk is deleting metadata needed for research; prevent loss by preserving rich provider config and lossless catalog output. Opposite risk is reintroducing config facts as runtime types; anti-overengineering tests and explicit consumer proof prevent that.
