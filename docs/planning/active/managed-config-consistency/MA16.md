# Lock provider public API families and semantic modes

## Description

Authoritative provider-boundary plan. Provider automation uses family-specific operations through audiagentic.components.providers.providers_api; each operation accepts a supported mode from plan|apply|prune|status. Payloads and results remain family-specific. Provider resources and agent execution are separate APIs. Recipes, lifecycle mechanics, registries, provider facts, and requester identities never cross the boundary.

## Steps

1. Inventory every production caller and classify each providers_api entry as: provider resource/query API, provider automation family operation, or agent execution. No entry may remain unclassified.
2. Lock modes: plan previews without durable mutation; apply makes declared desired state real; prune removes only caller-owned scope; status reads without durable mutation. A family exposes only its supported subset. No fifth mode or public recipe verb.
3. Lock current automation families and clients:
- CLI desired state: providers MCP and runtime/harness composition.
- Managed MCP entries: memory/Hindsight, coding-LSP, and runtime/harness composition.
- Rules/hooks: memory/Hindsight.
- Plugin configuration: memory/Hindsight.
- Provider-specific configuration: memory/Hindsight and runtime/harness composition.
- Language-server projection, generic LSP-MCP projection, and self-provided LSP support: coding-LSP.
- Model projection: model management and runtime composition.
- Generated provider surfaces: runtime/composition callers.
Each family has its own function and payload. Providers register provider+family implementations explicitly and remain requester-blind.
4. Keep resource/query APIs separate. Model-source CRUD, catalog reads/refresh, descriptor reads, and similar AUDiaGentic-owned resource management do not become operation modes unless they invoke provider-specific automation.
5. Keep agent execution separate. MA17 defines one provider-owned execution entry; it has no operation mode, ownership scope, recipe selection, or catalog dispatch.
6. Derive each family payload/result only from current callers. Ownership/correlation scopes are opaque. Do not add a universal request, result, capability record, action taxonomy, desired_present, repair, requester id, binding id, or recipe kind.
7. Keep probe/install/configure/verify/uninstall/dry_run and repair decisions private. Apply probes current state and selects install, repair, configure, verify, or no-op internally.
8. Replace old public lifecycle/reconciliation/surface verbs atomically with family operations and migrate every in-repository caller in the same change. Delete install_provider, uninstall_provider, repair_provider, reconcile_provider, reconcile_all_providers, split apply/prune surface APIs, aliases, shims, dual routes, and compatibility tests when replacements land. Backward compatibility is not maintained unless a documented external obligation is approved before implementation.
9. Keep ProviderRecipeRegistry internal. Define deterministic duplicate-registration failure; never silently replace a provider+family binding. Provider facts/config remain rich evidence only; explicit registration alone enables automation.
10. Add contract tests for export allowlist, caller/family coverage, supported modes, plan/status non-mutation, scoped prune, duplicate registration, absent handler, API-category separation, forbidden imports, and catalog non-authority.
11. Close MA16 only when every providers_api entry is classified, all family signatures are caller-derived and frozen, old public lifecycle routes are gone, dependent plans reference this contract without redefining it, and stale-term/import audits pass.

## Validation

1. Every providers_api export is classified. 2. Every automation caller appears in the matrix and uses only its family function. 3. Modes are a supported subset of plan/apply/prune/status; mechanics remain private. 4. No universal payload/result/taxonomy or CLI-derived field leaks across families. 5. Foundation is component-agnostic; requesters import providers_api only; providers import no requester. 6. Explicit provider+family registration is sole authority and duplicates fail. 7. Plan/status do not mutate; prune is scoped. 8. Legacy APIs, aliases, shims, and compatibility tests are absent. 9. Execution and resource APIs remain separate. 10. Stale-term and focused tests pass.

## Effort & Risk

High-impact migration. Freeze one family signature from caller evidence, migrate every caller of that family atomically, validate, then delete its old route. Do not batch unrelated families or invent fields for future callers.
