# Define common declarative capability-operation schema

## Description

Define one foundation-owned, component-neutral capability-operation contract plus a provider-owned, schema-validated capability catalog. Every provider declares canonical capabilities once: present support, technical mechanism/constraints, managed ownership, and agent-facing manifestation fields. Descriptor-derived facts are compiled into this catalog. MA16 schema remains domain-neutral and must not contain provider, Hindsight, memory, LSP, harness, or package-manager vocabulary. Execution transport structure is gated by MA18: ACP is an optional evidence-backed transport manifestation alongside CLI/HTTP, never assumed from generic streaming.

SCOPE AFTER RV367 SPLIT: MA16 is the minimal Block B1 gate — schema, strict loader, machine catalog, and the immutable capability record MA17 consumes. Evidence-provenance process machinery, generated agent-facing references, and schema versioning/migration policy live in sidecar MA19. MA16 retains one evidence rule: every support state references an evidence-record id with review state, and unknown/unverified support cannot auto-select.

## Steps

0. PRE-SCHEMA GATE — define and generate canonical provider capability catalog. Provider-owned declaration is sole editable source for provider-specific capability facts; descriptor-derived fields compile into it, never copied by hand. Each capability record has: stable neutral `capability-id` and `kind`; lifecycle operations; support state (`supported|manual|blocked|unsupported|unverified`); technical contract (request payload schema/ref, config/launch surface class, constraints, managed ownership, reload/rollback/dry-run semantics, secret/ref rules); handler binding owned by provider; agent manifestation fields (short description, when to use, invocation affordances, user action/action-needed, limitations — data only; generated reference views are MA19); evidence-record id + review state (process owned by MA19); optional extension fields under namespaced provider-owned metadata. Initial taxonomy must cover current capabilities: install/probe, execute, config mutation, managed MCP, managed LSP, skills/surfaces/instructions, host extension, hooks, plugin, catalog/model discovery, model projection, launch environment, and launch-time overrides. Do not claim support from absence; unknown is explicit. Generate deterministic machine JSON/YAML from the declarations. Reconcile descriptor/docs/runtime mismatches, assign owner/gap, obtain review approval before immutable schema design. No runtime gateway or behavior change.
1. Inventory existing declarative dialects: provider `cli_install`, Hindsight matrix recipe rows, toolchain recipes, workflow invocation specs, LSP/provider config specs, harness installers, release/hook definitions. Map each to catalog capabilities and record lifecycle semantics/component owner.
2. Define immutable foundation contract and YAML schema: capability id, kind, constraints, parameter bindings, operations (`install`, `configure`, `verify`, `uninstall`, `prune`), step definitions, managed ownership declarations, result/outcome overrides, optional opaque custom-adapter reference. Use only neutral terms. Operation modes plan|apply|prune|status are the standard lifecycle contract — they implement dry-run safety and clean component/provider extraction (scoped prune) — but a capability may declare a mode not-applicable, yielding the canonical unsupported result instead of a handler obligation (RV367).
3. Add provider-capability request section: provider id, generic capability id, operation, typed neutral payload, constraints, ownership/correlation metadata. Requesters cannot specify provider paths, serializers, handler refs, or provider metadata keys.
4. Strict load-time validation: canonical errors, unknown core fields fail, defaults explicit, namespaced extension fields validate against provider-owned schema/ref. No silent coercion/component-name branches. Single-version strict loading; versioning/migration policy is deferred to MA19 until a second schema version actually exists.
5. Define composition boundary: each component owns declarations and registers through neutral foundation loader/registry. Components request provider work through gateway only; provider owns handler/custom mechanics. Providers cannot inspect requester/domain ids. Providers contains no memory/Hindsight declaration; memory owns memory-library intent.
6. Make MA11 steps sole operation body vocabulary. MA10 consumes schema. MA12 converts provider `cli_install`; MA02 converts memory intent; MA05/MA08 and HA01/HA02 migrate only after characterization.
7. Define custom extension rules: provider adapter refs implement neutral handler protocol. Requesting components define payload/templates only; no gateway/ownership bypass.
8. Add fixtures: provider CLI, managed MCP, launch override, plugin/hook, memory-library intent, harness, LSP—all same contract. Assert adding provider capability requires only provider declaration/handler; adding requester uses catalog discovery and neutral request.
9. Architecture guards: zero component-local operation-schema clones; zero provider/Hindsight vocabulary in foundation schema/loader; no requester→provider implementation imports; one schema loader; machine catalog generated from the declarations; legacy dialects explicit expiry.
10. Publish authoring guide and migration table (generated agent capability reference is MA19).
11. EXECUTION-TRANSPORT INPUT (MA18): before freezing schema, consume MA18's reviewed evidence and keep/map/delete table. Model execution as a capability with one or more declared transport manifestations, not as ACP-specific core vocabulary. Required neutral fields cover transport kind, protocol/version, session/resume, incremental events, cancellation, permissions, tool/file/terminal/plan events, framing/launch requirements, limitations, evidence state, and preference/selection constraints. ACP, CLI stream, HTTP stream, and blocking CLI are declaration values or extensions—not foundation branches. Do not mark streaming support as ACP support. Transport manifestation data fields (interactive, live output/cancel/permission, session persistence, caller delivery modes) are declared here; generated agent-facing views are MA19.
12. EVIDENCE RULE (mechanics in MA19): every support state carries an evidence-record id + review state. Reopened MO09 provider×vendor facts remain quarantined until RV353 correction completes; descriptor-derived repo facts may compile, but external support state/mechanism/granularity cannot be promoted from a provider-wide anchor, help absence, config parser acceptance, or expected behavior. Unknown/unverified cannot auto-select.

## Validation

0. MA18 Step 7 evidence checkpoint—not final MA18 completion—is recorded before schema freeze. 1. Every shipped provider emits exactly one catalog entry; structural fields equal descriptor facts. 2. OpenCode execution declares verified ACP protocol 1 and CLI stream as separate manifestations; no streaming⇒ACP inference. 3. Unverified fixture cannot auto-select. 4. Foundation schema/loader contains zero provider/memory/Hindsight/LSP/harness/package-manager vocabulary/imports. 5. Requester cannot supply handler/binding/dotpath/provider metadata. 6. Provider-owned opaque binding resolves only at MA17 composition root through typed protocol. 7. Unknown/malformed declarations fail canonical error; loader is single-version strict. 8. Guards reject duplicate schemas/catalogs and support states lacking a reviewed evidence-record id; quarantined evidence cannot promote. 9. Generated machine catalog distinguishes provider execution transport from caller delivery transport. 10. MA17 can consume immutable record without importing ACP/OpenCode or reparsing provider YAML. 11. A capability declaring a mode not-applicable returns the canonical unsupported result through the generic path.

## Effort & Risk

Complex foundational contract. Prevent over-abstraction by extracting only common operation/config lifecycle fields; component-owned policy and custom adapter semantics remain out of schema. Migrate one vertical slice at a time behind characterization/golden tests.

## Standards

- arch-standards — neutral foundation schema; config-over-code; typed composition; no arbitrary string registry; strict errors; one canonical catalog.
- component-creation — provider declarations and provider-owned bindings; generated agent-facing capability docs.
- observability-standards — capability evidence and selection outcomes contain no secrets.
