# Define common declarative capability-operation schema

## Description

Define one foundation-owned, component-neutral configuration contract for declarative installable/reconcilable capabilities. Provider CLIs, memory-library integrations, harnesses, LSP, release/hooks, and future installs use the same operation/constraint/ownership/outcome shape while retaining declarations and domain policy in their owning component. The schema must not contain provider, Hindsight, memory, LSP, harness, or package-manager vocabulary.

## Steps

1. Inventory existing declarative dialects: provider `cli_install`, Hindsight matrix recipe rows, toolchain recipes, workflow invocation specs, LSP/provider config specs, harness installers, release/hook definitions. Record fields, lifecycle semantics, and component owner.
2. Define immutable foundation contract and YAML schema: capability id, kind, constraints, parameter bindings, operations (`install`, `configure`, `verify`, `uninstall`, `prune`), step definitions, managed ownership declarations, result/outcome overrides, optional opaque custom-adapter reference. Use only neutral terms.
3. Define schema versioning, strict load-time validation, canonical errors, unknown-field policy, defaults, and migration/read compatibility policy. No silent coercion or component-name branches.
4. Define composition boundary: each component owns files declaring its capabilities and registers them through neutral foundation loader/registry. A component may reference opaque provider/context inputs, but no component can declare another component's domain policy. Specifically providers contains no memory/Hindsight capability declaration; memory owns any memory-library integration declaration.
5. Make MA11 step definitions the only operation body vocabulary. MA10 recipe engine consumes this schema for binding, constraints, factory dispatch, and outcome mapping. MA12 converts provider `cli_install`; MA02 converts memory integration declarations; MA03/MA05/MA07/MA08 convert applicable durable lifecycle declarations only after characterization.
6. Define custom extension rules: adapter refs implement neutral protocol; use only for format/API semantics impossible in declared steps. Custom adapter receives typed context, returns neutral result, never owns generic orchestration or bypasses managed ownership.
7. Add fixture declarations for provider CLI, memory-library integration, harness, and LSP using identical schema shape. Assert adding a fixture capability requires only component config plus optional adapter—not foundation/provider/memory edits.
8. Add architecture guards: zero component-local RecipeSpec/operation-schema clones; zero provider/Hindsight vocabulary in foundation schema/loader; no cross-component declaration imports; one registered schema loader; legacy dialects have explicit migration status and expiry.
9. Publish authoring guide and migration table. Update architecture standards to require this schema for new install/configure/verify/uninstall work.

## Files

[FOUNDATION] declarative capability-operation schema, loader, validator, registry, errors, public exports
[CONFIG] component-owned capability declaration directories/files
[CONSUMERS] MA10 recipe engine, MA11 steps, MA12 provider CLI, MA02 memory integration, later owner migrations
[TEST] schema conformance, fixture cross-component declarations, boundary/duplicate guards
[DOCS] Architecture Standards + Creating a Component + migration matrix

## Validation

1. One schema parses and validates fixture provider CLI, memory-library integration, harness, and LSP declarations with identical lifecycle field shape.
2. Foundation schema/loader contains zero provider/memory/Hindsight/LSP/harness/package-manager vocabulary or component imports.
3. Providers has zero memory-library/Hindsight declaration, branch, import, or test; memory integration fixture is owned entirely by memory.
4. New fixture component adds declared capability without changing foundation or another component.
5. Unknown/malformed/version-incompatible declarations fail at load with canonical error; no silent fallback.
6. Operations plan through MA11 and mutations use managed ownership primitives; dry-run has zero side effects.
7. Architecture guards reject parallel local operation schema/registry clones.
8. Existing behavior parity established per migrated consumer; Docker-only tests for real installs.

## Effort & Risk

Complex foundational contract. Prevent over-abstraction by extracting only common operation/config lifecycle fields; component-owned policy and custom adapter semantics remain out of schema. Migrate one vertical slice at a time behind characterization/golden tests.
