# Move complete provider capability system into providers

## Description

Move the entire provider capability system into providers: knowledge config, capability ids, validation, evidence linkage, loader/catalog generation, request/result types, gateway, and public status/reference API. Capability is provider-specific (CapabilityRequest contains `capability_id`, a provider-domain concept). Delete `foundation/capability_catalog` entirely. Designate one narrow providers public-API module as the sanctioned requester import path — never adapters, services internals, config loaders, matrices, or handlers. Foundation owns no capability concept; do not create `foundation/ports`.

## Steps

0. Inventory `foundation/capability_catalog` and all imports. Confirm production consumers are zero outside the package (only test code imports it).
1. Move provider capability knowledge/config validation and lossless catalog/reference tooling into existing providers config/service structure.
2. Move capability request/result types into a designated providers public-API module beside gateway implementation. Size fields from concrete future callers: MA02 (memory → install/configure guidance, MCP, plugin, hooks), MA08 (coding-LSP → plan|apply|prune|status with `coding-lsp/language-server/<language-id>` ownership scope), MO02/MO03 (model projection → explicit handler registration via MA17).
3. Implement provider capability gateway as providers-owned public service over explicit handler registrations. Descriptive catalog is soft config — never enables a handler.
4. Delete `foundation/capability_catalog` completely: schema, loader, errors, exports, tests. Do not create `foundation/ports`, foundation capability protocols, or foundation capability facade.
5. Codify the single sanctioned edge: requester components may import ONLY the designated providers public-API module (allowlist one path). Forbid all other providers imports — adapters, serializers, config loaders, matrices, internal registries.
6. Providers must not import requester domains; handlers are requester-blind. Requests contain desired data and opaque ownership/correlation metadata only.
7. Composition root owns provider handler registration/lifetime. Public gateway resolves from explicit registrations.
8. Keep agent execution separate — its boundary is decided by MA17 from actual call sites. Capability contracts own no ExecutionPort.
9. Move tests to providers. Add arch guards: (a) no capability symbols under foundation; (b) requester→providers imports restricted to the single public-API path allowlist; (c) zero providers→requester-domain imports; (d) no compatibility re-export.

## Files

[CONFIG:providers] capability knowledge, ids, evidence references
[COMPONENT:providers public API module — designated sanctioned import] request/result types, gateway over explicit registrations
[COMPONENT:providers services/internals] config loader, catalog generation, status/reference tooling, handlers/adapters/serializers
[DELETE] foundation/capability_catalog entirely
[TEST] providers capability tests; arch guards: no-foundation-capability, public-API allowlist for requester imports, zero providers→requester imports
[FORBIDDEN] foundation/ports wrapper, requester imports of provider internals, catalog-driven dispatch

## Validation

1. `foundation/capability_catalog` absent; no capability symbols under foundation. 2. No `foundation/ports` capability abstraction exists. 3. Request/result/gateway live in the designated providers public-API module with only consumed fields. 4. Approved requesters import ONLY that public-API module; allowlist passes, all other providers imports fail. 5. Providers import zero requester domains; handlers are requester-blind. 6. Explicit handler registration is sole automation authority; catalog strings cannot enable dispatch. 7. Rich provider facts and generated references remain complete. 8. Adding descriptive capability data changes providers config/tooling only. 9. Old foundation imports fail; no compatibility shim.

## Effort & Risk

Mid correction. Main risk is deleting metadata needed for research; prevent loss by preserving rich provider config and lossless catalog output. Opposite risk is reintroducing config facts as runtime types; anti-overengineering tests and explicit consumer proof prevent that.

## Standards

- arch-standards — neutral foundation schema; config-over-code; typed composition; no arbitrary string registry; strict errors; one canonical catalog.
- component-creation — provider declarations and provider-owned bindings; generated agent-facing capability docs.
- observability-standards — capability evidence and selection outcomes contain no secrets.
