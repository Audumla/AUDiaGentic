# Migrate provider CLI lifecycle to recipe registry

## Description

Replace provider CLI private state machine/workflow with ProviderCliRecipe on MA11 steps and MA10 declarative recipe/registry infrastructure while preserving public API payloads and caller-owned managed side effects.

## Steps

1. Snapshot `provider_cli_plan` and install/uninstall/repair result dicts for every cli_install descriptor; inventory consumers of status strings, workflow-events, commands/output, and provider-cli events.
2. Add ProviderCliRecipe(ProviderCapabilityRecipe), capability id `cli`, recipe kind command-installer. Build declaration from existing CliInstallRecipe descriptor authoring shape; do not change provider YAML format in this item.
3. Build registry by iterating descriptors; no provider-name branches. No installable recipe uses NoAutomationRecipe-compatible skipped result with exact existing reason.
4. Probe maps cli_probe/probe_fn; verify preserves Windows PATH-settle retry (3×1s); timeout install counts success only if post-probe succeeds; repair short-circuits when current probe passes.
5. Add one provider_result_dict boundary adapter preserving keys: provider-id, action, status, package metadata, executable, command, returncode, stdout, stderr, probe, reason, workflow-events, surfaces. State/status mapping is declaration/action based, never provider-id based.
6. Command/stdout/stderr arrive redacted from MA11; adapter asserts/defensively redacts without retaining raw values.
7. Rewire install/uninstall/repair/plan/provision-all to registry. After successful recipe call, lifecycle.py retains caller-side config seed, provider surface apply/prune, managed MCP/config reconcile. Recipes never own those durable mutations.
8. Preserve/rebuild provider-cli operational events only if step-1 consumer inventory proves use; otherwise remove field/event with explicit public-contract decision and tests.
9. Delete provider_cli.py private state machine/config/context/action helpers and old workflow adapter. Whole-repo grep; no shim.
10. Docker-only real npm provider install/uninstall smoke; never mutate host tooling.

## Files

[COMPONENT:providers] services/cli_recipes.py, lifecycle.py, provider API/result adapter
[DELETE] providers/workflow/provider_cli.py private orchestration
[FOUNDATION reuse] MA11 steps, MA10 recipe engine, ProviderRecipeRegistry
[TEST] payload goldens, quirks, side-effect ownership, Docker smoke

## Validation

1. Golden public dict parity or explicitly approved removal for unused workflow-events.
2. No provider-id branches; fixture provider added via descriptor only.
3. Timeout+probe, settle retry, repair short-circuit, no-recipe skip, vscode reconcile skip tests pass.
4. Managed side-effect call order remains seed→surfaces→managed reconcile outside recipe; recipe mutation guard proves no direct writes.
5. Raw secret absent from command/stdout/stderr/results/logs.
6. Old private state-machine symbols/imports absent repo-wide.
7. Provider unit/integration suites and Docker smoke green.

## Effort & Risk

Complex public contract migration. Goldens and call-order spies protect behavior. Do not begin before MA11/MA10 stable to avoid throwaway adapters.
