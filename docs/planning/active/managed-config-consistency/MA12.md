# Migrate provider CLI automation to semantic operation

## Description

Implement the CLI automation family using the MA20 RecipeDefinition schema. Derive one CLI-specific public payload from providers-MCP and runtime callers. Public modes are supported members of plan|apply|prune|status; lifecycle mechanics remain private.

## Steps

1. Inventory every caller and consumed result for install_provider, uninstall_provider, repair_provider, CLI planning/status, and provision-all orchestration.
2. Freeze one CLI-family signature from those callers. Payload may describe CLI desired state and CLI-specific options, but must not expose repair, recipe methods, recipe kinds, or fields borrowed by other families.
3. Implement one providers_api CLI operation using existing recipes and foundation.steps; add no recipe abstraction.
4. Apply probes and internally selects install, repair, configure/PATH settle, verify, or no-op. Prune removes only owned CLI state. Plan/status do not mutate.
5. Migrate providers MCP and every runtime/composition caller atomically. Provision-all remains orchestration over family calls, not a public reconcile mode.
6. Delete old lifecycle functions, MCP compatibility routes, aliases, shims, dual dispatch, obsolete tests, and private workflow state machine after parity.
7. Preserve only caller-consumed results and canonical errors; redact command/stdout/stderr.
8. Run focused unit/integration tests and Docker-only real-install smoke.

## Files

[PUBLIC] providers_api CLI family operation
[CALLERS] providers MCP and runtime/composition
[INTERNAL] services/cli_recipes.py, lifecycle.py, foundation.steps
[DELETE] lifecycle/reconcile public routes, wrappers, provider_cli.py when unused
[TEST] caller goldens, modes, ownership, redaction, Docker smoke

## Validation

1. All old callers use one CLI family operation. 2. Public payload has no repair flag or recipe mechanic. 3. Apply handles absent, broken, configured, and healthy states internally. 4. Plan/status do not mutate; prune removes only owned state. 5. No compatibility alias, dual route, or mechanic-named public function remains. 6. Current callers retain consumed behavior and errors. 7. No provider-id dispatch branch. 8. Focused tests and Docker smoke pass.

## Effort & Risk

Complex public contract migration. Completed MA11 substrate and existing recipe infrastructure are available; no prerequisite remains. Goldens and call-order spies protect behavior.

LOCKED IMPLEMENTATION HELP (RV470):
1. Public operation and breaking migration: replace install_provider, uninstall_provider, repair_provider and their MCP tools with one manage_cli_lifecycle(provider_id, mode). Modes are plan|apply|prune|status. Delete old names, aliases, dual routes, and tests in the same change. No backwards compatibility.
2. No public dry_run flag: callers use mode=plan. dry_run remains a private lifecycle mechanic only. No public repair flag/tool: apply probes state and privately chooses install/repair/configure/verify/no-op.
3. Frozen payload/context split: CliLifecycleRequest is a serializable, family-specific desired-state object. project_root is invocation context, not request data or schema field; an internal handler closure captures it. Do not add provider_id to request—it is the registry dispatch key. With no current caller-specific desired field, use an empty typed request (additionalProperties false) rather than inventing flags.
4. Frozen result boundary: CliLifecycleResult reports semantic state/outcome only (for example ok, supported, changed, state, action_needed, error_code). It must not expose action/install/uninstall mechanic labels, command, returncode, stdout, stderr, workflow-events, or probe: dict. Repository production callers do not consume those raw fields; tests that assert them are legacy implementation tests. Keep detailed diagnostics internal/redacted logs only; do not add a public verbose/debug payload.
5. ownership_scope_required is false. CLI lifecycle is provider-scoped through dispatch provider_id, not caller-owned partial external state. prune removes the provider CLI state; it does not accept an ownership scope.
6. Registry composition location: create providers-internal services/automation_registry.py with a factory such as build_automation_registry(project_root). It loads descriptors, collects capability declarations and open family contract contributions, and registers executable handlers. Do not put a singleton in recipe_definitions (keep pure) or providers_api (keep public facade). Build lazily per invocation/context or cache only with explicit descriptor/profile invalidation; handler closures capture provider_id and project_root.
7. MA12 is first production registry adopter. Register only CLI handlers now; managed-mcp/plugin-entry remain descriptor-backed generic services until their owning migration explicitly adopts registry composition. Family modules contribute contract maps; configuration alone never binds handler code.
8. Reconcile is not CLI lifecycle. reconcile_provider/reconcile_all_providers remain MA22 explicit orchestration/composition work. MA12 migrates direct CLI install/uninstall/repair call sites only; launch/refresh/provider_prompt reconciliation callers must not be forced into CLI modes.
9. YAML declarations: add cli-lifecycle only to descriptors with cli_install (including custom Pi lifecycle if present), with modes [plan, apply, prune, status], payload_contract provider-cli-lifecycle-payload/v1, result_contract provider-cli-lifecycle-result/v1, ownership_scope_required false. Do not declare it for unmanaged descriptors.
