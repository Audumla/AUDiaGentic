# Migrate provider CLI lifecycle to recipe registry

## Description

Replace provider CLI private state machine/workflow with ProviderCliRecipe on MA11 steps and MA10 declarative recipe/registry infrastructure while preserving public API payloads and caller-owned managed side effects.

## Steps

1. Snapshot `provider_cli_plan` and install/uninstall/repair result dicts for every legacy `cli_install` descriptor; inventory consumers of status strings, workflow-events, commands/output, and provider-cli events.
2. Define MA16 canonical provider CLI declaration mapping. During one explicit migration window loader accepts legacy `cli_install` only through a compatibility translator that produces canonical schema and emits test-visible deprecation metadata; no consumer reads legacy shape directly. Set removal milestone in this item.
3. Add ProviderCliRecipe as provider-owned handler for generic `cli` capability, built only from canonical declaration. Register by provider descriptor; no provider-name branches. Unsupported/no-automation uses canonical skipped/action-needed result.
4. Probe maps canonical probe definition; verify preserves Windows PATH-settle retry (3×1s); timeout install counts success only if post-probe succeeds; repair short-circuits when current probe passes.
5. Add provider_result_dict boundary adapter preserving keys: provider-id, action, status, package metadata, executable, command, returncode, stdout, stderr, probe, reason, workflow-events, surfaces. State/status mapping is declaration/action based, never provider-id based.
6. Command/stdout/stderr arrive redacted from MA11; adapter asserts/defensively redacts without retaining raw values.
7. Rewire install/uninstall/repair/plan/provision-all through canonical provider CLI handler/registry. After successful handler call, providers lifecycle retains provider-owned config seed, surface apply/prune, and managed reconcile; recipes never bypass managed ownership.
8. Convert all shipped provider YAML to MA16 canonical schema; delete `CliInstallRecipe`, `_build_cli_install`, legacy YAML field, and translator in same item after migration tests. No permanent dual dialect or shim.
9. Preserve/rebuild provider-cli operational events only if step-1 consumer inventory proves use; otherwise remove with explicit public-contract decision/tests.
10. Delete provider_cli.py private state machine/config/context/action helpers and old workflow adapter. Docker-only real npm install/uninstall smoke; never mutate host tooling.

## Validation

1. Canonical schema is sole runtime authoring shape after completion; legacy `cli_install` field/classes/translator absent repo-wide.
2. Golden public dict parity or explicit approved removal for unused workflow-events.
3. No provider-id branches; fixture provider added through canonical declaration only.
4. Timeout+probe, settle retry, repair short-circuit, no-recipe skip, vscode reconcile skip tests pass.
5. Managed side-effect call order remains provider-owned and uses approved primitives; recipe guard proves no raw direct writes.
6. Raw secret absent from command/stdout/stderr/results/logs.
7. Provider unit/integration suites and Docker smoke green.

## Effort & Risk

Complex public contract migration. Goldens and call-order spies protect behavior. Do not begin before MA11/MA10 stable to avoid throwaway adapters.
