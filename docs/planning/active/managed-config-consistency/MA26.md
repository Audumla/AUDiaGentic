# Migrate Codex and Pi Hindsight recipes to typed ownership

## Description

Fourth MA02 cutover. Replace raw Codex/Pi Hindsight recipe classes with frozen, Hindsight-owned typed definitions and desired-state objects. Hindsight owns its commands, downloaded artifacts, desired integrations, and evidence. Providers remain requester-blind: they expose only generic, descriptor-backed native configuration mechanics. Do not use or extend the MA24 provider-integration family; it was based on the superseded ownership model.

## Steps

1. Preconditions and inventory. Start only after MA25 is complete. Run and record the current Codex and Pi focused tests. Inventory each read/write/delete target, command, user-file preservation rule, ownership marker, redaction rule, and current failure/status result. Split work into two independently reviewable batches: Codex first; Pi second. Do not edit Pi while Codex is unvalidated.

2. Freeze Hindsight contracts before moving behavior. Add Hindsight-owned, frozen typed definitions and desired values for Codex and Pi. Include only Hindsight semantics: integration identifier, Hindsight artifact/version/source metadata, explicit desired state, evidence/status, and action-needed. Add concrete v1 JSON schemas for every serialized definition/desired object. Matrix/config parsing happens once at the Hindsight boundary; recipes, strategies, and tests exchange typed objects only. No raw matrix rows, Any payloads, unchecked nested dictionaries, universal request/result, or compatibility constructors.

3. Freeze native Codex configuration boundary before implementation. Classify each Codex write as either (a) Hindsight-owned artifact/configuration, handled by the Hindsight typed recipe, or (b) native Codex JSON/TOML configuration, handled only through a new or existing minimal descriptor-backed provider configuration capability. Reuse MA23/MA25 mechanics only where their exact typed family semantics fit. Otherwise define one narrowly scoped typed family for managed native configuration contributions, with frozen request/result objects and concrete v1 JSON schemas before any handler exists. Its request must identify a provider-native contribution and explicit scope; provider descriptor adapters map it to paths/formats. It must not carry requester identity, Hindsight names, arbitrary command blobs, or a universal payload. Record this classification in the plan notes/review before coding.

4. Codex batch — Hindsight recipe. Implement a typed Codex Hindsight recipe that owns Hindsight download/verification, Hindsight artifact state, desired integration data, and plan/apply/prune/status decisions. It may use generic foundation shell steps for Hindsight-owned work. Route native Codex hooks JSON/config.toml mutation through the typed provider configuration capability from step 3, never through a provider handler that imports Hindsight or a direct Memory file serializer. Preserve current integrity checking, redaction, atomic write behavior, unrelated JSON/TOML keys, current failure reporting, and caller-owned scope.

5. Codex batch — migration and deletion. Migrate strategies/lifecycle callers to typed Hindsight definitions and public provider capability adapter(s). Delete CodexHindsightRecipe plus raw-row/path/serializer/provider-adapter compatibility seams only after parity tests pass. No shell-installer fallback, provider-internal import, public provider function named for Hindsight, or backward-compatible wrapper.

6. Pi batch — evidence-first, non-executing. Implement a typed Pi Hindsight definition whose status exposes the existing unconfirmed evidence and action-needed. While evidence is unverified, plan/apply/prune perform no install, removal, config mutation, or subprocess execution. Move verified/unverified facts and anchors to MA19 capability_facts. Delete PiHindsightRecipe, _run_pi, and raw JSON path/config mechanics; remove tests that assert unverified execution. A future execution path requires a new review that supplies verified facts, a concrete typed Hindsight desired contract, and any necessary provider-generic configuration capability.

7. Boundary and schema tests. Add tests for schema parsing/rejection, typed-only handoff, and requester blindness (providers contain no Hindsight import/name/path). Codex tests cover artifact verification, plan/apply/prune/status, JSON/TOML round trip, unrelated-key preservation, scoped ownership/removal, failure/redaction, and no direct Memory serializer. Pi tests prove status/action-needed and zero writes/subprocesses for every mode.

8. Validate and hand over. After Codex batch run focused Hindsight/provider tests, architecture-boundary tests, ruff, and stale-symbol/path search; require review before Pi. After Pi batch rerun those checks plus relevant full memory/provider suites. Update MA26 notes with exact public capability family selected in step 3, deleted symbols, tests run, and any deferred evidence. Mark complete only when both batches meet their stop conditions.

READY AFTER MA25 AND STEP 3 CONTRACT FREEZE. Done when: (1) Hindsight owns all Codex/Pi recipe semantics and typed desired state; (2) every serialized contract has concrete v1 schema and invalid shapes are rejected at boundary; (3) any Codex native config write uses a narrow descriptor-backed provider capability, never provider Hindsight logic or Memory direct serializers; (4) provider source has no Hindsight import/name/path; (5) Codex behavior parity, preservation, scoped prune, integrity, redaction, and failure tests pass; (6) Pi is status/action-needed only with no write or subprocess in any mode while unverified; (7) old recipes/raw seams/wrappers are absent; (8) focused and relevant full suites, ruff, architecture boundaries, and stale path/symbol searches are green.

## Effort & Risk

Complex; suitable for senior implementation agent. Main risk is ambiguous ownership of existing Codex user files. Stop Codex work if a write cannot be classified in step 3 or exact typed capability/schema cannot be named. Do not solve ambiguity with a generic blob, provider-Hindsight handler, direct Memory file access, or compatibility shim. Pi is deliberately small and non-executing; stop if evidence changes and open a review instead.

## Notes

Supersedes MA26's original MA24 provider-integration approach. Locked terminology: caller contract is plan | apply | prune | status; recipe methods stay private probe/install/configure/verify/uninstall/dry_run. Hindsight (and other requester components) owns requester-specific recipes and commands. Providers declare only generic capabilities/config mechanics; foundation is component-agnostic. Common RecipeDefinition envelope remains metadata only; it is not a universal public request/result schema. All family requests/results are frozen typed objects with concrete schemas; configuration/API mappings parse once at boundary. No backwards compatibility by default: cut callers to canonical typed route and remove old route after parity. Depends on MA25; MA19 owns Pi evidence. RV466 records the correction.
