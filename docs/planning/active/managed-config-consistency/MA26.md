# Migrate Codex and Pi Hindsight recipes to typed ownership

## Description

Fourth MA02 cutover. Replace raw Codex/Pi Hindsight recipe classes with frozen, Hindsight-owned typed definitions and desired-state objects. Hindsight owns its commands, downloaded artifacts, desired integrations, and evidence. Providers remain requester-blind: they expose only generic, descriptor-backed native configuration mechanics. Do not use or extend the MA24 provider-integration family; it was based on the superseded ownership model.

## Notes

Pattern A — two separate families: Codex (file-based hooks) and Pi (subprocess npm install). They have no meaningful connection beyond "both are providers that need Hindsight integration." They are separate items in hindsight_matrix.yaml. Codex: downloads Python scripts, writes ~/.codex/hooks.json, patches ~/.codex/config.toml, writes ~/.hindsight/codex.json. Pi: subprocess-based npm install of npm:@walodayeet/hindsight-pi. Supersedes MA26's original MA24 provider-integration approach. Locked terminology: caller contract is plan | apply | prune | status; recipe methods stay private probe/install/configure/verify/uninstall/dry_run. Hindsight (and other requester components) owns requester-specific recipes and commands. Providers declare only generic capabilities/config mechanics; foundation is component-agnostic. Common RecipeDefinition envelope remains metadata only; it is not a universal public request/result schema. All family requests/results are frozen typed objects with concrete schemas; configuration/API mappings parse once at boundary. No backwards compatibility by default: cut callers to canonical typed route and remove old route after parity. Depends on MA25; MA19 owns Pi evidence. RV466 records the correction.
