# Standardize allowed component integration ports and events

## Description

Document and enforce component dependency direction without blocking legitimate provider integration. Components managing providers may consume provider descriptors/services; providers own provider-specific mechanics. MA17 implements gateway resolution against MA16's canonical provider capability catalog: requesters use neutral capability+operation intents, provider-specific handler bindings remain hidden. Prohibit foreign removable-domain policy/vocabulary, especially memory/Hindsight in providers. Standardize generic events so release can request ledger actions without direct coupling. Keep provider capability operations separate from agent prompt/session execution; both remain transport-neutral. ACP stays behind provider execution port, while MCP remains caller exposure.

## Steps

0. INPUT GATE: require MA16 strict catalog/loader tests and immutable execution capability record. Read MA18 neutral transport contract. Do not redesign schema, ACP framing or provider launch binding here.
1. Generate machine-checked import graph plus resolved binding graph. Registry indirection counts as real edge. Classify direct allowed import, typed composition binding, typed event, descriptor/data consumption, or forbidden leakage.
2. Audit string/dotpath/service-locator registries. Delete any crossing component/layer boundary solely to conceal coupling. Typed registries require protocol owner, key owner, declaration source, composition root, deterministic duplicate/unknown behavior and replacement lifetime.
3. Implement provider capability gateway for configuration/lifecycle operations: validate typed request against MA16, resolve provider-owned handler at providers composition root, reject manual/blocked/unverified, return neutral outcome. Requester cannot specify handler, dotpath, serializer, provider path or extension metadata.
4. Implement DISTINCT provider execution resolver: input is validated provider/model/profile needs plus MA16 execution capability facts; output is typed neutral execution binding/port. Provider composition maps selected manifestation to provider-owned binding. Agents gateway sees neither binding key nor provider mechanics.
5. Transport selection algorithm: filter supported+verified; satisfy required session/live/cancel/permission features; apply declaration preference; return canonical unsupported/blocked result when none match. No `if provider`, `if ACP`, command names or protocol versions in gateway/foundation resolver. Test ACP preferred, CLI fallback, unverified rejected, required-feature mismatch.
6. Connect OpenCode binding: providers composition adapts existing `build_acp_launch`/CLI runner into neutral execution port. No arbitrary importlib/dotpath lookup from catalog. Explicit typed composition registration is allowed and visible in binding graph.
7. Connect agents gateway: retain profile/model selection, retry/fallback, queue/request persistence. Invoke neutral execution port; pass authoritative working root and stream controls; forward neutral events through callback. No provider capability gateway recursion.
8. Project events into existing gateway timeline/event persistence: redact first; enforce MA18 bounds; preserve sequence/session/kind/terminal metadata; no raw ACP/stdout payload store. Define cursor as after-sequence + bounded limit with stable exhausted/next cursor semantics.
9. Expose caller delivery: MCP cursor polling portable baseline; optional progress notification from same event callback; CLI renderer/future SSE read same sequence. No provider-specific MCP execution tool.
10. Preserve provider-specific LSP/job/config mechanics behind provider capability handlers. Remove memory/Hindsight vocabulary from providers; memory owns intent. Provider handler remains requester/domain blind.
11. Implement generic release→ledger event through typed event contract only if BU topic standards permit; no direct implementation import/string service lookup.
12. Tests in order: selection unit table; binding graph; OpenCode ACP mocked integration; CLI fallback; gateway event ordering/redaction/bounds; cursor replay; optional progress failure isolation; retry/fallback unchanged; cancellation; forbidden import/string registry guards; provider domain-blindness; release/ledger event.
13. Documentation/ledger: update standards, component guide, capability authoring and execution diagram. Record exact retained/deleted edges and migration shims with expiry.

## Files

[PROVIDERS] MA16 catalog consumer, capability gateway, execution resolver/composition, OpenCode ACP+CLI binding adapters
[AGENTS] neutral execution-port invocation; existing request/timeline persistence; cursor/progress projection
[TEST] selection table, resolved binding graph, gateway event/cursor/cancel/fallback/boundary guards
[DOCS] dependency graph, authoring guide, execution/caller-delivery diagram
[FORBIDDEN] importlib/dotpath handler loading from declarations; gateway provider/transport branches; new ACP-only store; requester-selected binding keys

## Validation

1. Import and resolved-binding graph exposes every cross-layer edge. 2. No arbitrary string/dotpath handler lookup crosses boundaries. 3. Capability gateway and execution resolver remain distinct typed contracts. 4. Transport selection is declaration-driven and rejects unverified/manual/blocked. 5. Fixture provider needs declaration plus explicit provider composition binding only; agents gateway unchanged. 6. Agents gateway contains zero ACP/CLI/HTTP/provider branches or executable/protocol logic. 7. OpenCode ACP and CLI fallback both emit same neutral ordered/redacted event model. 8. Existing queue/profile/retry/fallback/request ownership remains agents-owned. 9. Cursor replays same persisted sequence; progress is optional and failure-isolated. 10. No second event/session store. 11. Providers contain zero memory/Hindsight vocabulary/branches. 12. Foundation imports zero components. 13. Cancellation produces one terminal state and stops in-flight ACP child.

## Effort & Risk
