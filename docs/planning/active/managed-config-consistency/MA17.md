# Expose provider execution and enforce component boundaries

## Description

Implement the separate agents-to-providers execution boundary and enforce providers_api layering. Agent execution does not use RecipeDefinition, operation modes, ownership scopes, or recipe registration.

## Steps

1. Inventory agents_gateway_dispatch imports, packets, results, errors, cancellation, retry/fallback, and timeline tests.
2. Freeze one providers_api execution signature from current calls: project root, provider id, agent-selected model id/alias, and provider-neutral packet data.
3. Providers check enablement, load config, resolve model, and invoke explicitly composed execution adapter. No operation mode, ownership scope, recipe, provider-fact lookup, or catalog dispatch.
4. Agents retain profile selection, packet construction, retry/fallback, cancellation, correlation, and timeline persistence.
5. Rewire _dispatch_one_attempt and tests; delete direct provider service imports and obsolete routes in the same change.
6. Preserve normalized results, canonical errors, ordered redacted events, and cancellation.
7. Add guards for approved public edge, forbidden internals/reverse imports, and operation/resource/execution separation.

## Files

[COMPONENT:providers public] execution invocation function plus semantic operation functions
[COMPONENT:providers internal] provider config/model resolution/execution adapters/registrations
[COMPONENT:agents] profile resolution, packet construction, retry/fallback/cancel/timeline only
[TEST] execution seam goldens, monkeypatch migration, import graph, events
[FORBIDDEN] agents imports of providers.services, foundation capability ports, catalog dispatch, public recipe methods

## Validation

1. agents_gateway_dispatch imports providers_api only. 2. Execution entry imports no agents domain. 3. RecipeDefinition rejects execution registration. 4. Packet/result/error/retry/fallback/cancel parity. 5. Explicit execution-adapter composition only. 6. Provider facts cannot select execution. 7. No foundation provider facade.

## Effort & Risk

Mid. Do not remove provider integration merely for graph purity. Refactor only foreign-domain leakage and event coupling; preserve provider-specific adaptation where it is real.

## Standards

- Architecture Standards: Dependency Boundaries; Approved cross-component APIs; Extensions and Configuration; Public Contracts and Safety.
- Architecture Guidelines: Provider Platform API; Extension Registries; Async Failure Handling.

## Notes

Depends on MA18 for proven transport requirements. Explicitly excluded from MA20 recipe schema; MA17 must not create an execution recipe family.
