# Recipe-backed provider execution resolution

## Description

Make managed harness recipes the authoritative source for declarative provider execution settings while preserving provider descriptors as the capability and contract registry. The gateway must resolve recipe-backed execution through the existing generic runner without breaking custom Python adapters or providers that have no managed recipe.

## Steps

Resolve the provider's recipe by explicit recipe id or provider_id, apply the existing harness override precedence, validate the merged execution mapping, and produce the same normalized execution contract currently consumed by base_runner.", 'Change Pi and OpenCode to reference their recipes while retaining only provider contract metadata in provider descriptors. Keep live ACP discovery through adapters/<provider>/acp.py and do not conflate ACP launch metadata with one-shot CLI execution.', 'Preserve precedence and compatibility: hand-written adapters remain authoritative for providers with adapter.py; descriptor execution remains a legacy fallback only when no recipe-backed execution is declared; providers without recipes remain honest unsupported/stub/none states.', 'Add diagnostics for missing recipe, malformed recipe, provider/recipe id mismatch, and unsupported recipe execution mode.
