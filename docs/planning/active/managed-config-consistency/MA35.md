# Retire dead-duplicate provider adapters; extend recipe schema for stdin prompt delivery

## Description

The declarative recipe system this item originally proposed building already exists and is in production (base_runner.py's descriptor execution: block, AR12) -- 7 of 18 providers (aider, antigravity, continue, goose, openhands, plandex, roo) already run purely off it with no hand-written adapter.py. This item's real remaining scope, per a full audit (2026-07-24, RV795), is narrower and concrete:

1. pi, qwen, copilot each declare BOTH an execution: block and a hand-written adapter.py -- adapter.py always wins (services/execution.py prefers it), so the execution: block is dead/unreachable in all three cases.
2. qwen's and copilot's execution: blocks are confirmed byte-for-byte equivalent to their adapter.py -- pure dead duplication, safe to delete adapter.py once dependent tests are rewritten.
3. pi's execution: block is NOT equivalent and is a landmine: it puts {prompt} in args-template as a CLI argument, which would reintroduce the SH21 newline-loss bug (Pi's --print mode drops embedded newlines when the prompt is an argv token, not stdin) if adapter.py were ever removed without first extending the schema.
4. claude, cline, codex, gemini, local_openai, opencode's adapter.py are genuinely custom (verified: OpenCode's is a custom NDJSON stream-event extractor with no declarative equivalent) and should stay hand-written -- not a migration gap.

## Steps

['Delete adapters/qwen/adapter.py and adapters/copilot/adapter.py (confirmed dead duplicates of their already-correct execution: blocks).', "Rewrite tests/integration/providers/test_qwen.py and test_copilot.py to exercise the generic dispatch path (make_runner_from_execution via services/execution.py's _load_runner, using the real qwen.yaml/copilot.yaml execution: blocks) instead of importing and calling adapter.run() directly -- this is real test-authoring work, not a mechanical deletion.", "Add a prompt-delivery: stdin | argv field to the execution: block schema (default argv, preserving current behavior for every other provider) and support it in base_runner.py's _build_command/make_cli_runner (pipe prompt via run_streaming_command's input_text= instead of appending {prompt} to args-template when stdin is declared).", "Update pi.yaml's execution: block to declare prompt-delivery: stdin and verify args-template drops {prompt} accordingly, matching adapters/pi/adapter.py's actual SH21-safe behavior.", "Decide and document whether pi's adapter.py can then be deleted (recipe becomes correct and reachable) or must stay for other reasons -- do not delete pi/adapter.py without first proving stdin delivery through the recipe path in an integration test.", "Document the final adapter-vs-recipe split (which providers are recipe-driven, which are genuinely custom and why) in the provider capability reference doc, so this doesn't silently drift again.", "Add diagnostics for malformed/unknown execution: block fields (missing recipe, bad mode) if not already covered by make_runner_from_execution's existing VAL-EXEC-001 unknown-mode error."]
