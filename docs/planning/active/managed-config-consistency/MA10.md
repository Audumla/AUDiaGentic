# Extract declarative recipe engine into foundation

## Description

Promote domain-neutral recipe specification, binding, constraints, factory dispatch, and assembly from Hindsight into discoverable foundation toolchain APIs. MA10 consumes MA16 common declarative capability-operation schema; components own declarations/policy/custom implementations only.

## Steps

1. Characterize memory/hindsight/recipe_spec.py and strategy helpers: RecipeSpec, ParamBinding, StatusOverride, assemble_hindsight_recipe, pattern dispatch, source/platform/Python gates. Mark each field/mechanic generic vs Hindsight/provider-specific.
2. Add foundation/toolchains/recipe_spec.py with domain-neutral immutable types: ParamBinding(param_name, source_field|literal, required/default), MethodOutcomeOverride(method, state, status_text), RecipeSpec(pattern, params, outcomes, constraints), and RecipeConstraints(platforms, python_min/max, execution_allowed/trust state). Names contain no provider/Hindsight/MCP/plugin vocabulary.
3. Add RecipeFactoryRegistry keyed by pattern string using shared Registry lazy-loader. API: register(pattern,factory), build(spec, declaration, context), keys(). Duplicate pattern rejected unless explicit composition-root replace for tests/plugins.
4. Add assemble_recipe(spec, declaration, context) resolving row/declaration fields, validating required bindings, evaluating constraints, invoking registered factory, and applying outcome overrides. Unknown pattern/field/ref raises canonical registered foundation errors.
5. Keep component implementation refs resolved at component/config boundary using foundation refs; foundation engine receives callable/factory, never imports component module or interprets capability ids.
6. Move generic no-automation and declared-step factory assembly to foundation only where vocabulary-neutral. ProviderCapabilityRecipe wrapping/stamping stays providers; Hindsight backend construction stays memory/provider contribution adapter.
7. Rewire Hindsight as first consumer with exact behavior parity. Delete moved classes/helpers/import paths—no compatibility shims. MA02 then moves declarations/ownership using foundation engine.
8. Add public exports/docs and a Creating a Component recipe section showing config-declared pattern plus optional custom implementation ref.
9. Update Architecture Standards §3: clearly domain-neutral orchestration with foreseeable cross-component use belongs in foundation even before second consumer; require stable contract/tests and forbid component vocabulary. This supersedes ‘wait for duplication’ interpretation, not the ban on speculative domain abstractions.
10. Add architecture guards: foundation recipe modules import no components/runtime orchestration; components cannot define duplicate RecipeSpec/ParamBinding/factory registry classes.

## Files

[FOUNDATION] foundation/toolchains/recipe_spec.py, recipe factory registry/public exports/error resolutions
[COMPONENT:first consumer] memory/hindsight recipe_spec/strategies rewiring and deletions
[DOCS] Architecture Standards §3/§16; Creating a Component
[TEST] foundation recipe spec/binding/constraint/factory tests + Hindsight parity + duplicate-type architecture guard

## Validation

1. Foundation unit matrix covers binding source/literal/default/missing, constraint allow/block, unknown pattern, duplicate factory, outcome override, custom callable.
2. Hindsight pre/post recipe type/status/gate/action behavior identical for every current row.
3. Whole-repo grep old memory-owned generic class/helper paths empty.
4. Foundation recipe modules contain zero Hindsight/provider/MCP/LSP/model/plugin vocabulary or component imports.
5. Fixture second capability registers pattern/declaration without editing engine, proving discoverability/reuse contract.
6. Architecture test rejects a component-local RecipeSpec/factory registry clone.
7. Full recipe/toolchain tests zero new failures.
