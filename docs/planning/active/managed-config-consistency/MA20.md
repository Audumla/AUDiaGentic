# Implement universal internal provider recipe schema

## Description

Define one provider-owned declarative RecipeDefinition schema and typed loader for automation families, plus an explicit provider capability catalogue. Each provider enumerates the capability-family IDs it supports and declares typed facts/configuration for those capabilities. Reusable generic mechanics are allowed only as independently named, schema-backed typed families selected by an explicit provider descriptor declaration. Public APIs retain family-specific payloads/results and plan|apply|prune|status modes. Resource APIs and agent execution are excluded. Schema validation describes recipes; only explicit provider+family code registration enables execution.

## Steps

1. Characterize ProvisioningRecipe, ProviderCapabilityRecipe, ProviderRecipeResult, ProviderRecipeKind, every current recipe declaration/registration, and every existing provider descriptor capability/mechanic. Produce a migration inventory mapping each caller family to: enumerated provider capability id, typed family contract, descriptor facts/configuration, and explicit executable registration if any.

2. Freeze the capability model. A provider descriptor explicitly enumerates each supported capability-family id; each declaration has a stable id, supported public modes, typed descriptor facts/configuration reference, and contract references where it is automatable. The global family-id namespace remains open: no closed central taxonomy or catch-all enum. Unknown ids fail unless a provider declares them and the relevant typed family contract/registration exists.

3. Freeze the minimal RecipeDefinition envelope: recipe id, provider id, open family id, supported modes, family payload/result contract references, recipe version, ownership-scope requirement, and non-authoritative provenance reference where required. Do not add requester identity, provider paths, commands, serializers, handler dotpaths, or a closed family taxonomy.

4. Freeze the generic-mechanic rule. A reusable mechanic (for example managed MCP entry, plugin entry, model-source, generated surface, or a future native-config contribution) is a separately named provider capability family with its own frozen Request/Result and concrete schemas. A provider opts in by explicit descriptor declaration and supplies typed adapter facts. Reuse only when desired-state semantics, ownership, modes, and result behavior are identical. Do not make a generic “capability request”, arbitrary configuration blob, generic command runner, or universal request/result.

5. Freeze metadata boundary. annotations and capability_facts may carry free-form evidence/provenance only. They are inert: they cannot name/enable a handler, add a mode, supply commands/paths/serializers, or bypass a typed family contract. Validation rejects executable/configuration fields in free-form metadata.

6. Add provider-owned JSON schemas and typed internal representation/loader for the RecipeDefinition envelope and capability declarations; keep provider vocabulary out of foundation. Resolve all contract refs during loading.

7. Keep private lifecycle mechanics in the typed recipe protocol. The schema records supported public modes; callers and declarations never select probe/install/configure/verify/uninstall/dry_run.

8. Change explicit registration identity to provider+family with recipe id as diagnostic identity. Capability facts/annotations cannot register implementation. A CC41 declarative recipe may define private executable mechanics, but it becomes reachable only through an explicit family registrar/adapter binding whose provider declaration, modes, and Request/Result contracts validate here. Descriptor-backed generic capabilities need no requester-specific registration; custom or declarative-backed provider behavior requires explicit family registration.

9. Make duplicate registration and unknown provider/family/mode fail deterministically with canonical provider errors. Reject undeclared family use, undeclared generic-mechanic use, missing contract refs, and metadata-driven execution.

10. Migrate fixture recipes for CLI, managed config, and generated surfaces; prove family payload schemas remain distinct. Add descriptor fixtures proving: declared capability accepted, declared generic mechanic accepted, unknown capability rejected, and annotation-only capability cannot execute.

11. Guard every automation registration with a valid definition; queries, resource commands, and execution cannot register; facts cannot execute; recipe types remain private. Document schema and the catalogue/mechanic distinction without creating a public request/result schema.

## Validation

1. Each provider descriptor lists its supported capability-family IDs explicitly. 2. A declared capability resolves to one distinct typed family contract; undeclared/unknown ids fail deterministically. 3. Generic mechanics are separately named opt-in families with their own Request/Result schemas; no generic payload/blob/command family exists. 4. CLI, managed-config, and surface fixtures validate with distinct payload schemas. 5. annotations/capability_facts cannot enable behavior or carry executable/configuration mechanics. 6. Queries, resource commands, and execution are rejected from recipe registration. 7. Facts/annotations cannot enable behavior; declarative recipe config executes only behind an explicitly registered family adapter. 8. Duplicate provider+family registration fails. 9. Only public modes cross boundary; mechanics remain protocol-private. 10. Foundation has no provider recipe schema/type. 11. No universal public request/result or closed family taxonomy.

## Effort & Risk

Architecture owner freezes the envelope and registration identity. Strong mid-level agent may implement schema/loader/tests afterward. Stop for review if a family requires provider paths, commands, requester identity, or mechanics in the common envelope.
