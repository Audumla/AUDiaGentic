# Implement universal internal provider recipe schema

## Description

Define one provider-owned declarative RecipeDefinition schema and typed loader for every automation family. Public APIs retain family-specific payloads/results and plan|apply|prune|status modes. Resource APIs and agent execution are excluded. Schema validation describes recipes; only explicit provider+family code registration enables execution.

## Steps

1. Characterize ProvisioningRecipe, ProviderCapabilityRecipe, ProviderRecipeResult, ProviderRecipeKind, and every current recipe declaration/registration.
2. Freeze the minimal RecipeDefinition envelope: recipe id, provider id, open family id, supported modes, family payload/result contract references, recipe version, ownership-scope requirement, and non-authoritative provenance reference where required. Do not add requester identity, provider paths, commands, serializers, handler dotpaths, or a closed family taxonomy.
3. Add provider-owned JSON schema and typed internal representation/loader; keep provider vocabulary out of foundation.
4. Keep private lifecycle mechanics in the typed recipe protocol. The schema records supported public modes; callers and declarations never select probe/install/configure/verify/uninstall/dry_run.
5. Change explicit registration identity to provider+family with recipe id as diagnostic identity. Configuration cannot register or enable implementation.
6. Make duplicate registration and unknown family/provider/mode fail deterministically with canonical provider errors.
7. Migrate fixture recipes for CLI, managed config, and generated surfaces; prove family payload schemas remain distinct.
8. Guard every automation registration with a valid definition; queries, resource commands, and execution cannot register; facts cannot execute; recipe types remain private.
9. Document schema without creating a public request/result schema.

## Validation

1. One schema validates all automation recipe definitions. 2. CLI, managed-config, and surface fixtures validate with distinct payload schemas. 3. Queries, resource commands, and execution are rejected from recipe registration. 4. Config/facts cannot enable behavior. 5. Duplicate provider+family registration fails. 6. Only public modes cross boundary; mechanics remain protocol-private. 7. Foundation has no provider recipe schema/type. 8. No universal public request/result or closed family taxonomy.

## Effort & Risk

Architecture owner freezes the envelope and registration identity. Strong mid-level agent may implement schema/loader/tests afterward. Stop for review if a family requires provider paths, commands, requester identity, or mechanics in the common envelope.
