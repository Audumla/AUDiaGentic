# Delegate memory integration intent through providers public API

## Description

Move memory provider-operation intent through providers_api. Memory depends only on that public API and submits family-specific desired data with semantic mode `plan|apply|prune|status`; it imports no adapters, serializers, loaders, matrices, recipes, or internal services. Providers own mechanics and remain unaware of Hindsight/memory.

## Steps

1. Freeze behavior by provider and family: caller, desired input, implementation, mutation, ownership/adoption, mode/result, fallback/guidance, and tests.
2. Memory keeps Hindsight backend desired values. Providers own provider paths, serializers, managed MCP/hook/plugin/config mechanics, platform repair, and recipes. Neither side imports the other's domain types.
3. Replace memory recipe-kind/factory dispatch with MA16 family operations and explicit provider+family registration. No Hindsight gateway or capability catalog.
4. Migrate sequentially: managed MCP; rules/hooks; plugin configuration; provider-specific Codex/Pi configuration; guidance/status reads.
5. For each family, add provider implementation, migrate all memory callers/tests, prove behavior and ownership, then delete old memory mechanics in the same change. No temporary public adapter, alias, or dual route.
6. Remove register_hindsight_recipes, ephemeral registry construction, direct lifecycle calls, and provider-internal imports.
7. Plan/status do not mutate; apply adopts only absent or exact legacy state; prune uses opaque ownership scope; collisions/reload are returned only where consumed; secrets are redacted.
8. Move provider-mechanics fixtures under providers, patch providers_api in memory tests, add import guards, and delete obsolete matrix/factory/recipe files when final consumers migrate.

## Files

[COMPONENT:memory] Hindsight backend desired-state builders, opaque ownership scopes, providers_api calls, memory-only status projection
[COMPONENT:providers public] family operations/adapters with plan/apply/prune/status and caller-sized results
[COMPONENT:providers internal] migrated MCP/hook/plugin/Codex/Pi mechanics, explicit registrations, provider config/path/serializer/repair code
[CONFIG:memory] Hindsight desired values only
[CONFIG:providers] provider mechanism facts/evidence, not runtime dispatch
[DELETE after parity] memory.hindsight matrix/factory/recipe classes that encode provider mechanics
[TEST] per-family golden parity, public-boundary/reverse-import guards, plan/status non-mutation, ownership/adoption/redaction

## Validation

1. Per-provider/family behavior parity. 2. Memory imports providers_api only and owns no provider recipe/factory dispatch. 3. Providers have no memory/Hindsight imports or identity branches. 4. Every call maps to an MA16 family; no universal or Hindsight-specific API. 5. Explicit registration only. 6. Non-mutation, scoped prune, adoption, collision, reload, and redaction proven. 7. Old routes and compatibility artifacts absent.

## Effort & Risk

Complex boundary migration. Preserve behavior with frozen per-provider table and migrate one recipe kind at a time: guidance/MCP, plugin, then hooks/custom.
