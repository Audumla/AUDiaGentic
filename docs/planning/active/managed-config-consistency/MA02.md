# Move Hindsight provider integration to provider contributions

## Description

Remove provider ids, provider config paths, recipe selection, and provider-service imports from memory/Hindsight generic strategy code. Memory owns neutral backend state/export; providers owns downstream capability recipe declarations and adapter selection through its generic ProviderCapabilityRecipe registry.

## Steps

1. Characterize current matrix resolution for every provider: selected recipe kind, source gate, platform gate, fallback, action_needed, and artifact list. Freeze as parameterized behavior table before moving ownership.
2. Add generic provider descriptor field `capability_recipes: dict[capability_id, CapabilityRecipeSpec]`. Spec fields: recipe_kind, implementation_ref (optional custom adapter), source metadata, constraints, config/artifact metadata, and fallback mode. No Hindsight-named field/type in generic provider loader/services.
3. Move rows from config/components/memory/hindsight_matrix.yaml into provider-owned declarations under config/providers/*.yaml (or one providers-owned capability recipe descriptor directory if loader overlay requires it). Capability id is `hindsight`; provider files own provider-specific facts.
4. Providers recipe registry loads declarations by capability id and dispatches through recipe_kind registry or implementation_ref. Unknown kind/ref raises canonical config error during descriptor load. Generic builder has zero provider-name branches.
5. Memory/Hindsight retains HindsightBackendConfig and a narrow neutral export boundary containing base_url, bank_id, transport, and secret reference—not resolved secret. It emits the existing neutral provider-refresh lifecycle hint when state changes.
6. Providers-owned boundary observer consumes the neutral refresh event, obtains export through one documented boundary adapter, and builds/reconciles provider recipes. Provider core never imports memory internals; memory never imports provider descriptors/services.
7. Move Codex/Pi/plugin custom recipe classes to provider adapter contribution packages, or keep implementation code in memory/hindsight only behind provider-owned implementation refs and one architecture-approved boundary module. Pick one layout consistently; no generic module imports custom classes.
8. Remove HINDSIGHT_RECIPE_MATRIX and strategies provider dispatch after parity tests. Whole-repo grep provider ids/matrix paths/imports.
9. Strengthen architecture test: non-provider components cannot contain provider-id matrices, config paths, or imports of providers services; provider recipe declarations add via YAML only.

## Files

[FOUNDATION/GENERIC CONTRACT] neutral CapabilityRecipeSpec location chosen without provider/Hindsight vocabulary leakage
[COMPONENT:providers] descriptors loader/base + services/recipes registry + boundary observer
[CONFIG:providers] config/providers/*.yaml or providers-owned recipe descriptors
[COMPONENT:memory] memory/hindsight neutral export/event only; remove matrix/strategy provider selection
[TEST] parameterized recipe parity + architecture boundaries

## Validation

1. Pre/post table identical for every shipped provider: recipe kind, gates, fallback, status/action_needed.
2. Adding fixture provider + Hindsight recipe requires config and optional adapter ref only; no generic Python edits.
3. memory/ tree has zero provider ids, provider paths, providers-service imports, or provider recipe matrices.
4. Provider generic loader/services have zero Hindsight-specific symbols/imports.
5. Refresh event contains no resolved key/token; redaction canary absent from event/log/result.
6. Missing/invalid recipe ref fails at descriptor load with registered canonical error.
7. Existing provider recipe and Hindsight tests pass; known Pi source-gate failure corrected from moved authoritative data.

## Effort & Risk

Complex boundary migration. Preserve behavior with frozen per-provider table and migrate one recipe kind at a time: guidance/MCP, plugin, then hooks/custom.
