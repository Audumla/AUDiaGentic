# Delegate memory integration intent to provider capability gateway

## Description

Move memory integration intent to a provider capability gateway. Memory owns provider-target selection and desired integration data; providers owns all provider-specific execution behind generic named capabilities. Components submit requests through foundation gateway, never call/import provider implementation. Providers receives opaque ownership/correlation metadata, never requester/domain identity, and never learns the memory library.

## Steps

1. Characterize current matrix resolution per provider: requested integration effect, selected provider mechanism, gates, fallback, action_needed, artifacts, and whether each artifact is memory-owned or provider-owned. Freeze behavior table before moving ownership.
2. Define foundation-neutral request/result contract. Request: stable request_id/idempotency_key, target_provider_id, capability, mode (`plan|apply|prune|status`), typed neutral payload, opaque ownership_scope, constraints, correlation_id, and redacted secret reference. Result: status, changed/planned paths, ownership actions, collision/action_needed, reload request, diagnostics, and correlation_id. Neither type contains requester/domain names or provider file-format details.
3. Define gateway dispatch: resolve exactly one `(target_provider_id, capability)` handler; reject unknown/unsupported pairs with canonical neutral error/result; invoke handler in requested mode; enforce correlation/redaction; map exceptions to deterministic result; no fallback direct call. `plan` invokes no durable mutation, `apply` is idempotent/atomic, `prune` affects only request ownership_scope, `status` is read-only.
4. Define provider-exposed capability vocabulary from actual common mechanisms only: managed MCP entry, plugin entry, config fragment/key, hook registration, instruction contribution, external-command request, and status/probe. Each payload and result has ownership/dry-run semantics. Do not create a capability for one memory-library detail.
5. Providers registers per-provider `(capability, handler)` implementations. Handler is sole executor of provider config paths, serializers, plugin/hook mechanics, reload requirements, adoption/collision, and durable provider mutations. Handler receives no requester/domain id and cannot branch on it.
6. Move Hindsight matrix rows into memory-owned declarations that express target provider, generic capability, neutral payload, constraints, and opaque ownership scope only. Memory may own provider-target selection facts, but contains no provider config paths, adapter refs, serializer details, or execution imports.
7. Memory submits gateway request and consumes neutral result/status. Composition root wires gateway to provider registry. No import from memory to `components.providers`; no direct provider service call; no provider import of memory.
8. Move Codex/Pi/plugin custom execution into provider handlers. Keep only Hindsight-specific desired values/templates in memory payload. Provider maps generic payload to its own format without knowing payload origin.
9. Remove HINDSIGHT_RECIPE_MATRIX strategy/factory/provider dispatch after parity tests. Grep direct memory→providers imports; providers Hindsight vocabulary; memory provider config-path/serializer refs.
10. Add architecture tests: exact handler dispatch/mode semantics; collision/idempotency/plan/prune isolation; components submit only through gateway; handler cannot branch on requester/domain; fixture memory integration changes declaration only; fixture provider customizes handler only.

## Files

[FOUNDATION] provider-capability request/result contract, gateway, typed capability payloads
[COMPONENT:providers] capability registry and provider-specific capability handlers/adapters
[COMPONENT:memory] Hindsight intent declarations, neutral backend export/event, gateway submission only
[CONFIG:memory] memory-owned capability request declarations
[TEST] behavior parity, gateway delegation, bidirectional vocabulary/import guards

## Validation

1. Pre/post table identical per provider: requested effect, selected provider mechanism, gates, fallback, status/action_needed.
2. Memory has zero imports/calls to `components.providers`, provider config paths, provider serializer refs, or provider implementation classes; memory retains only provider-target/capability/payload intent.
3. Providers has zero Hindsight/memory-library vocabulary, paths, config, imports, declarations, requester branches, or tests.
4. Gateway resolves exactly one handler; unsupported pair has canonical action-needed result; no direct fallback.
5. Plan/status cause zero durable mutations; apply idempotent/atomic; prune touches only opaque ownership scope; handler result has stable correlation/status schema.
6. Every provider-specific custom config/plugin/hook implementation lives in provider handler/adapter and receives neutral request only.
7. Adding fixture memory integration changes only memory declaration/payload; adding fixture provider behavior changes only provider handler/declaration.
8. Redaction canary absent from persisted request/log/result; existing provider/Hindsight tests pass.

## Effort & Risk

Complex boundary migration. Preserve behavior with frozen per-provider table and migrate one recipe kind at a time: guidance/MCP, plugin, then hooks/custom.
