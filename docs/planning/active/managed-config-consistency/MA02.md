# Delegate memory integration intent through providers public API

## Description

Move memory provider-operation intent through providers_api. Memory depends only on that public API and submits family-specific desired data with semantic mode `plan|apply|prune|status`; it imports no adapters, serializers, loaders, matrices, recipes, or internal services. Providers own mechanics and remain unaware of Hindsight/memory.

## Steps

1. Freeze behavior by provider/operation before extraction: provider set, desired input, current recipe class/factory, config/path mutation, ownership/adoption rule, dry-run/prune/status result, fallback/guidance, and tests. Existing frozen table is baseline; extend it with source file and public-target function.
2. Split ownership before moving code. Memory keeps Hindsight backend configuration and builds desired content/endpoint values. Providers own provider paths, serializers, managed-config/MCP/hook/plugin mechanics, platform repair rules, and recipe construction. No provider code imports Hindsight types/config or branches on Hindsight identity.
3. Replace memory matrix `recipe_kind`/factory dispatch with provider-owned operation declarations/explicit registrations. Move provider mechanism facts from `matrix.py`, `strategies.py`, `recipe_spec.py`, and recipe subclasses only when represented as provider internal configuration/code; retain memory-specific desired data in memory. Do not recreate a global capability catalog.
4. Migrate operation families in evidence-backed order: (a) managed MCP desired entry, (b) rules/hooks desired contribution, (c) plugin URL/array/config and Windows repair, (d) Codex and Pi provider-specific mutations, (e) guidance/status. Each uses providers_api family function plus semantic `plan|apply|prune|status`; no universal payload.
5. For each family add providers-owned adapter/recipe with explicit registration, then move its path/serializer/subprocess implementation out of `memory.hindsight`. Keep legacy behavior behind a temporary provider-side adapter only until golden parity passes.
6. Replace `register_hindsight_recipes`, ephemeral ProviderRecipeRegistry construction, direct registry lifecycle calls, and direct provider MCP imports with providers_api calls. Memory never constructs recipes, imports ProviderRecipeKind, or passes capability/recipe binding ids.
7. Preserve user safety: plan/status make no file/registry/network/subprocess mutation; apply adopts only exact/absent legacy state; prune removes only memory-owned scope; collisions/reload/action-needed become structured only where memory consumes them; redact secrets.
8. Migrate tests by seam: retain behavior goldens, move provider mechanics fixtures under providers, patch providers_api public functions in memory tests, and add import guards for every former internal import. Delete obsolete matrix/factory/recipe files only when no remaining consumer.
9. Remove old matrix dispatch after parity. Test allowed public edge, forbidden internals/reverse edge, explicit registration, semantic modes, ownership, and descriptive-config non-authority.

## Files

[COMPONENT:memory] Hindsight backend desired-state builders, opaque ownership scopes, providers_api calls, memory-only status projection
[COMPONENT:providers public] family operations/adapters with plan/apply/prune/status and caller-sized results
[COMPONENT:providers internal] migrated MCP/hook/plugin/Codex/Pi mechanics, explicit registrations, provider config/path/serializer/repair code
[CONFIG:memory] Hindsight desired values only
[CONFIG:providers] provider mechanism facts/evidence, not runtime dispatch
[DELETE after parity] memory.hindsight matrix/factory/recipe classes that encode provider mechanics
[TEST] per-family golden parity, public-boundary/reverse-import guards, plan/status non-mutation, ownership/adoption/redaction

## Validation

1. Behavior parity against per-provider/operation frozen table. 2. Memory imports providers_api only; zero `providers.services.*`, recipe types, registry, or ProviderRecipeKind imports. 3. Providers have zero memory/Hindsight imports/branches. 4. No memory-owned matrix/factory chooses provider recipe kind or handler. 5. Explicit provider registration only. 6. Payload/result fields have current consumers and expose only plan/apply/prune/status. 7. Plan/status no durable mutation/network/subprocess; prune ownership safe; collision/adoption redaction pinned. 8. Provider docs/config change without memory runtime change. 9. Secrets redacted.

## Effort & Risk

Complex boundary migration. Preserve behavior with frozen per-provider table and migrate one recipe kind at a time: guidance/MCP, plugin, then hooks/custom.

## Notes

RV447 deep-audit result: ten Hindsight modules directly import providers internals: provision, lifecycle, status, matrix, strategies, recipes, recipe_spec, plugin_recipes, codex_recipe, pi_recipe. This is deeper than an import rewrite: memory owns `_RECIPE_FACTORIES`, `ProviderRecipeKind` dispatch, recipe classes, and provider path/serializer/repair mechanics. Migrate by operation family, moving mechanics provider-side and retaining only Hindsight desired values in memory. `mcp_recipe.py` is likely first seam because it already builds desired entry data; validate exact provider inputs before extraction. Avoid a Hindsight-specific provider gateway — use narrow generic provider operations with family payloads.

TIERING — High-value agent: classify each family, freeze desired payload/ownership/adoption/collision/result contract, decide destination/provider registration, and approve deletion. Mid-level: migrate exactly one approved family with its golden fixtures and focused tests; report any unmatched behavior. Easy: move approved static fixtures, update exact imports/patch paths, delete code only after high-value sign-off. Never assign factory redesign, plugin repair, Codex/Pi path mutation, or cross-family cleanup to low-tier agent.
