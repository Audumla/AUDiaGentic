# Comprehensive Docker e2e capability-matrix + negative-path tests for managed provider config

## Description

The existing Docker e2e suite (test_provider_full_lifecycle.py, test_provider_surface_lifecycle.py) only exercises mcp_config and skill/instruction surfaces, and only positive-path (install -> apply -> disable -> prune -> uninstall). plugin_config (opencode), hooks_config (codex), and model_config (pi) have zero Docker/mutation coverage — hooks/model use HOME-relative paths (~/.codex/hooks.json, ~/.pi/agent/models.json) never exercised outside unit tests. There is no negative/adversarial coverage anywhere: no test for corrupted pre-existing config files, foreign-content preservation under repeated cycles, purge idempotency, purge completeness across all capability kinds at once, or duplicate/conflicting entry handling. A real defect was found while surveying this: adapters/codex/hooks_format.py:_load_hooks silently treats a JSON-corrupt hooks.json as empty ({}), so the next managed write silently discards the corrupted (possibly user-authored) file content instead of raising a canonical error.

## Steps

1. Build tests/integration/providers/test_managed_config_capability_matrix_e2e.py: for every provider x every declared ManagedConfigSpec kind (mcp_config, plugin_config, hooks_config, model_config, language_servers_config), run apply -> verify -> prune -> verify-gone through the real service layer (add_provider_mcp_server/manage_plugin_entry/manage_hook_entries/spec reader-writer-remover directly for model_config), inside Docker with real CLI installs where installable.
2. Add negative-path tests: corrupted/malformed pre-existing config file (invalid JSON/TOML/YAML) must raise a canonical error and leave the file byte-for-byte unchanged, never silently discard content.
3. Add foreign-content preservation tests: pre-seed each config file with unrelated user-authored entries, run multiple apply/prune cycles, assert foreign entries survive every cycle untouched.
4. Add purge completeness + idempotency tests: install entries across every capability kind a provider supports simultaneously, purge everything, assert zero managed residue in every touched file; run prune twice back-to-back, second call must be a clean no-op.
5. Add HOME-relative path isolation tests for hooks_config/model_config: monkeypatch HOME to a tmp dir, assert nothing is ever written outside it.
6. Add duplicate-entry and remove-nonexistent-entry tests (idempotent, not error, not duplicated).
7. File a review against adapters/codex/hooks_format.py for the silent-corruption-discard defect found during the survey (do not fix inline as part of this test-building item; the fix belongs to hooks_format.py's owner and needs its own review/validation).
8. Wire the new module into a new tests/docker/Dockerfile.provider-config-matrix-e2e and register it alongside the existing provider-lifecycle-e2e image.

## Validation

New suite runs green in Docker (AUDIAGENTIC_DOCKER_TESTS=1, AUDIAGENTIC_REAL_PROVIDER_CLI_TESTS=1). Every provider-declared capability kind gets at least one full apply/verify/prune/verify-gone cycle. Negative tests fail loudly (not silently pass) against the current hooks_format.py corruption bug, proving the suite actually catches real defects rather than only exercising happy paths.

## Effort & Risk

Complex — real CLI installs per provider are slow (parametrized across ~10 providers x 5 capability kinds); keep the matrix data-driven off descriptor declarations rather than hand-enumerated so new providers/capabilities are covered automatically. Do not silently skip a provider/capability combination without an explicit, named reason.
