# Adopt managed ownership for provider LSP entries

## Description

Migrate coding-LSP provider configuration requests from direct writer/remover calls to MA02/MA17 provider capability gateway and MO06 managed-config core. Coding-LSP owns desired language-server intent; providers owns provider-specific config mutation, adoption, collision, and reload behavior.

## Steps

1. Characterize current sync/prune behavior per LSP-capable provider: result shapes, file bytes/structures, enabled/disabled behavior, failures, and provider config mechanism.
2. Define stable opaque ownership scope `coding-lsp/language-server/<language-id>` with provider target. Registry storage/managed ids remain provider-handler-owned; coding-LSP sees only request/result ownership actions, not provider config paths or writers.
3. Coding-LSP builds neutral language-server desired payload and submits `provider-capability` request in `plan|apply|prune|status` mode. It never calls `spec.writer`, `spec.remover`, `lsp_projection`, or provider managed-config service directly.
4. Provider LSP capability handler converts neutral payload into provider-specific entry, invokes MO06 managed core, and owns exact-match adoption: exact existing entry adopts without rewrite; absent entry writes/owns; same-name differing payload collides; unrelated entries survive.
5. Disabled first run submits no adopt/remove request. Disabled after ownership submits prune scoped to coding-LSP ids only. Provider handler ensures subset isolation.
6. Result adapter preserves public `ok/synced/skipped/servers/details` keys and adds neutral adopted/updated/removed/collisions/action_needed/reload fields. Coding-LSP aggregates provider results without inspecting config path/container.
7. Provider handler declares reload behavior per provider; no default reload invented. Status/describe-provider reads handler-managed ownership counts through provider API.
8. Remove direct writer/remover and coding-LSP→provider implementation imports. Update MA01 audit/guard. MA14 may later replace only high-level membership loop.

## Validation

1. Coding-LSP has zero direct provider writer/remover/serializer/handler imports; all provider config mutations traverse gateway.
2. Exact existing entries adopt without config byte change; differing entry remains byte-identical and reports collision; disabled-first-run preserves all entries.
3. Provider handler preserves unrelated entries and prunes only scoped owned entries.
4. Public aggregate/result keys remain compatible; collision/reload semantics pinned.
5. Gateway plan/status are side-effect free; handler atomic/corrupt-registry behavior inherited/tested.
6. All coding-LSP/provider LSP tests green; full unit zero new failures.

## Effort & Risk

Mid. Biggest risk is claiming pre-existing user entries. Exact payload equality and disabled-first-run rule prevent destructive adoption.
