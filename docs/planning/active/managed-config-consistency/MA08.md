# Adopt managed ownership for provider LSP entries

## Description

Migrate coding-LSP requests from direct writer/remover calls to providers-owned public capability gateway and MO06 managed-config core. Coding-LSP explicitly depends on narrow providers public API, not adapters/config internals. Providers own mutation/adoption/collision/reload and remain coding-LSP-domain blind.

## Steps

1. Characterize current sync/prune behavior per LSP-capable provider.
2. Define opaque ownership scope `coding-lsp/language-server/<language-id>`.
3. Coding-LSP submits desired payload through providers public capability API; no direct writer/remover/internal service calls.
4. Provider handler maps payload into provider-specific managed entry and owns adoption/collision/reload.
5. Disabled first run does nothing; later disable prunes owned coding-LSP entries only.
6. Preserve public aggregate/result compatibility through thin adapter.
7. Status uses providers public API and handler-owned ownership counts.
8. Remove direct writer/remover and internal imports. Keep high-level loops local; RV411 rejected generic membership extraction.

## Files

[COMPONENT:coding_lsp] desired payload and providers public capability API calls
[COMPONENT:providers public] capability gateway/results/status
[COMPONENT:providers internal] LSP handlers and managed config adapters
[FOUNDATION reuse] MO06 managed core/registry only—no capability gateway
[TEST] adoption/collision/disable/result compatibility and import-boundary guards

## Validation

1. Coding-LSP has zero direct provider writer/remover/serializer/handler imports; all provider config mutations traverse gateway.
2. Exact existing entries adopt without config byte change; differing entry remains byte-identical and reports collision; disabled-first-run preserves all entries.
3. Provider handler preserves unrelated entries and prunes only scoped owned entries.
4. Public aggregate/result keys remain compatible; collision/reload semantics pinned.
5. Gateway plan/status are side-effect free; handler atomic/corrupt-registry behavior inherited/tested.
6. All coding-LSP/provider LSP tests green; full unit zero new failures.

## Effort & Risk

Mid. Biggest risk is claiming pre-existing user entries. Exact payload equality and disabled-first-run rule prevent destructive adoption.

## Standards

- Architecture Standards §10 and §16.
- MO06 domain-neutral managed core; coding-lsp/provider ownership boundary.

## Notes

RV404: no foundation capability protocol. Coding-LSP may import providers public API only.

RV406 CODIFICATION (2026-07-14): the sanctioned import is `audiagentic.components.providers.providers_api` only (arch §18). The gateway IS `ProviderRecipeRegistry` dispatch — no new capability request/result types. Provider recipe contract (`ProviderCapabilityRecipe`, `ProviderRecipeResult`) provides adoption/collision semantics via ownership tracking in result. LSP operations (plan→probe, apply→install/provision, prune→prune, status→probe) map to registry methods or thin wrapper calls from the public API module. All other providers imports and reverse providers→coding-LSP imports remain forbidden.
