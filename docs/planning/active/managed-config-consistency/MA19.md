# Maintain provider capability knowledge and evidence

## Description

Providers-owned capability knowledge program: deep provider interrogation, evidence, config, capability-id index, loader/validation, machine/reference generation, and status guidance. It records facts for future work and soft activities. Runtime public operation semantics live in providers_api only as current callers require; capability knowledge never enables handlers or expands into code taxonomy.

## Steps

1. Maintain consolidated provider capability knowledge config and evidence index: provider/tool version, capability id, mechanism, constraints, ownership notes, limitations, support assessment, action-needed guidance, transport observations, fact anchor, verification/review state.
2. Maintain a config-owned index/set of all documented capability ids. Detect duplicates/typos/orphans in config tooling. No codegen from this set and no runtime dispatch.
3. Evidence promotion/quarantine process with CONCRETE SUFFICIENCY TIERS (RV426): Tier 1 = installed-tool artifact proof (config-schema output, installed file/dir listing, isolated write→read round-trip that the tool reflects) → promotes to `verified`. Tier 2 = help/version output or docs matching installed version → `supported` for existence claims only, never mechanism/granularity. Tier 3 = execution proof (real run exercising capability) → required to verify execution/transport claims. INSUFFICIENT: absence, help silence, parser acceptance without round-trip, analogy, or provider-wide anchor promoted to pair. Record tier, fact anchor, and version.
4. Generate lossless machine catalog and agent/human views from provider config. Views may group/filter strings but cannot become runtime authority.
5. Add overlay/compiler only when a real soft consumer needs it. Preserve unknown/provider-specific fields losslessly.
6. Guard separation: runtime modules do not import catalog generator/output; catalog values cannot register handlers, select transports, or claim executable automation.
7. Continue deep provider interrogation, including execution transports, model/config surfaces, launch isolation, permissions, hooks/plugins, MCP/LSP, and future capabilities. Store findings even when no code consumes them.
8. When runtime implementation begins, owning plan selects its minimal providers_api payload/result fields and `plan|apply|prune|status` semantics. Do not promote catalog shape or recipe mechanics into code.

## Files

[CONFIG:providers] rich provider capability knowledge and capability-id index
[COMPONENT:providers] lossless loader/validation, evidence linkage, machine/reference generation, status presentation
[EVIDENCE/DOCS] versioned fact anchors and generated views
[TEST] config integrity, evidence linkage, deterministic views, no foundation/runtime coupling
[FORBIDDEN] foundation catalog package, generated Python taxonomy, requester imports of providers matrix

## Validation

1. Every provider fact retained with evidence. 2. Capability ids/config/loader/generator owned by providers. 3. Foundation contains zero capability symbols or facade. 4. New descriptive values require no non-provider runtime change. 5. Views deterministic/lossless. 6. Explicit registrations, not catalog, drive runtime. 7. Requesters access provider behavior/status only through providers_api. 8. Catalog does not dictate public payloads, results, recipe kinds, or caller verbs.

## Effort & Risk

Mid, elastic. Rich knowledge can grow freely because it is isolated from runtime design. Main risk is accidental promotion into code; import/codegen guards prevent coupling.
