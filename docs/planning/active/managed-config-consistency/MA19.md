# Maintain provider capability knowledge and evidence

## Description

Maintain provider-owned capability knowledge and evidence without changing runtime automation contracts. MA19 uses one reusable, typed capability_facts/evidence shape for an open but curated evidence catalogue. MA20 separately enumerates executable automation capabilities. Existing descriptor fields remain operational declarations; capability facts record support, provenance, constraints, and review state. HostCapability remains an editor-extension declaration only. Facts may reference recipe ids/families for documentation but cannot satisfy RecipeDefinition, register implementations, select transports, or enable automation.

## Steps

1. Preserve the existing provider-owned frozen types in components/providers/descriptors/base.py: CapabilityEvidence(evidence_tier, tool_version, fact_anchor, review_state) and ProviderCapabilityFact(capability_id, subject, mechanism, constraints, limitations, support_assessment, action_needed, evidence). Use optional/default values so providers can be populated incrementally. Do not add provider evidence fields to foundation ManagedConfigSpec or recipe types.

2. Preserve ProviderDescriptor.capability_facts and its strict loader builder/PROVIDER_SPEC entry. Load capability_facts losslessly from provider YAML. Keep annotations free-form and informational; do not treat annotations as authoritative capability evidence.

3. Lock the MA19 catalogue. Each provider is interrogated against these evidence subjects when applicable: CLI probe/lifecycle; managed MCP configuration; plugin-entry configuration; language-server configuration; model-endpoint configuration; model catalogue fetch/refresh; supported connector projection; vendor-key injection; host/editor extension; execution transport and constraints; managed surfaces/instruction files; permissions; deprecation/migration; and explicitly documented external capability facts. Populate only claims with current evidence. An inapplicable subject has no fact; an unresolved claim is an explicit unverified/quarantined fact with action_needed, never a guessed “supported” fact.

4. Lock identifier and generic-shape rules. capability_id is an open stable provider evidence id, not a closed global taxonomy or executable capability enum. It must be unique within a provider and identify one declared descriptor subject/member or documented external:<subject>. Reuse the one ProviderCapabilityFact/CapabilityEvidence shape across all subjects; do not invent provider-specific fact records. mechanism, constraints, limitations, support_assessment, action_needed, and evidence are the only generic extensibility. No free-form capability definitions, arbitrary nested data, commands, paths, serializers, modes, payloads, or handlers belong in facts.

5. Preserve HostCapability exactly as the host/editor-extension declaration. A host-extension fact references its stable subject from capability_facts; evidence for model config, connectors, vendor injection, catalog, execution, surfaces, transport, and permissions uses the same capability_facts shape rather than overloading HostCapability.

6. Enforce MA19/MA20 separation. MA20 automation_capabilities explicitly enumerate provider-supported executable family ids, modes, ownership requirements, and typed contract refs. MA19 capability_facts may describe those families and their evidence, but cannot declare a family, add a mode, provide a contract, or select execution. annotations are weaker still: informational metadata only.

7. Populate provider YAML from current model-source-evidence documents and PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md. Verified claims require evidence appropriate to the claim; unresolved or FILL claims remain pending/unverified and must not unlock implementation.

8. Validate capability_facts across all descriptors: capability_id is non-empty and unique within one provider; (provider_id, capability_id) is the global identity; subject resolves to a declared descriptor field/member or an explicitly documented external fact; evidence_tier is one of unverified/documentation/installed-artifact/round-trip/execution; review_state is one of pending-review/verified/quarantined; verified facts require tool_version and fact_anchor. Shared capability ids across different providers are permitted.

9. Add provider-owned deterministic serializers for the capability_facts collection: lossless JSON machine view and concise Markdown human view. Do not reuse list_provider_descriptors as the lossless source because its public projection is intentionally selective. Generated views are references, never runtime authority.

10. Add tests for YAML loading/defaults, invalid subject/id/metadata fields, validation failures, deterministic JSON/Markdown output, MA19/MA20 authority separation, and absence of imports from generated views into runtime/foundation code.

11. Continue provider interrogation by adding facts/evidence only. New evidence fields extend CapabilityEvidence/ProviderCapabilityFact deliberately; do not create provider-specific evidence shapes or promote annotations into logic-driving state.

## Validation

1. Every populated fact round-trips from YAML without loss. 2. Applicable catalogue subjects are either evidenced or explicitly unverified/quarantined with action_needed; no inferred support. 3. HostCapability remains limited to host/editor extensions. 4. (provider_id, capability_id) identities are unique; valid shared ids across providers are accepted. 5. Verified facts require versioned anchors and claim-appropriate evidence. 6. FILL/unverified facts cannot unlock implementation. 7. JSON and Markdown views are deterministic and derived only from provider config. 8. capability_facts cannot declare MA20 automation capabilities, modes, contracts, or handlers; annotations cannot declare facts or behavior. 9. No fact or generated view is accepted as RecipeDefinition, registration, transport selection, or runtime authority. 10. Foundation remains provider-agnostic. 11. Existing provider descriptor and API tests remain green.

## Effort & Risk

Mid. Type/loader work is small; evidence population and subject validation span heterogeneous descriptor declarations. Main risks are treating editor extension ids as universal capability ids, duplicating operational config, and allowing evidence to influence execution.
