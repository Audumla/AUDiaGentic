# Maintain provider capability knowledge and evidence

## Description

Providers-owned capability knowledge program: deep provider interrogation, evidence, config, capability-id index, loader/validation, machine/reference generation, and status guidance. All capability concepts—including request/result vocabulary used by provider gateway—belong to providers, not foundation. Soft knowledge never enables runtime handlers.

## Steps

1. Maintain consolidated provider capability knowledge config and evidence index: provider/tool version, capability id, mechanism, constraints, ownership notes, limitations, support assessment, action-needed guidance, transport observations, fact anchor, verification/review state.
2. Maintain a config-owned index/set of all capability ids documented across providers. Detect duplicates/typos/orphans in config tooling. Do not generate Python enums, Literal aliases, frozensets, dataclasses, or dispatch branches from this set.
3. Define evidence promotion/quarantine process for soft claims. Fact-specific anchors required; absence/help/parser acceptance/expectation cannot become verified support without matching proof.
4. Generate lossless machine catalog and agent/human views from provider config. Generated views may group/filter strings but cannot become runtime authority.
5. Add overlay/compiler only when a real soft consumer needs it. Preserve unknown/provider-specific fields losslessly. Schema evolution applies to config/document output only; avoid speculative compatibility layers.
6. Guard separation: runtime modules do not import catalog generator/output; catalog values cannot register handlers, select transports, or claim executable automation.
7. Continue deep provider interrogation, including execution transports, model/config surfaces, launch isolation, permissions, hooks/plugins, MCP/LSP, and future capabilities. Store findings even when no code consumes them.
8. AG-CLI host candidacy remains research-only: record isolated config roots, MCP-set control, permission lockdowns, and session separation per provider/version. Create implementation plan only when scheduled.
9. When implementation begins for a documented capability, create/update owning runtime plan and explicitly choose minimal fields/interfaces it needs. Do not promote the whole catalog shape into code.

## Files

[CONFIG:providers] rich provider capability knowledge and capability-id index
[COMPONENT:providers] lossless loader/validation, evidence linkage, machine/reference generation, status presentation
[EVIDENCE/DOCS] versioned fact anchors and generated views
[TEST] config integrity, evidence linkage, deterministic views, no foundation/runtime coupling
[FORBIDDEN] foundation catalog package, generated Python taxonomy, requester imports of providers matrix

## Validation

1. Every provider fact retained with evidence. 2. Capability ids/config/loader/generator owned by providers. 3. Foundation contains zero capability symbols or facade. 4. New descriptive values require no non-provider runtime change. 5. Views deterministic/lossless. 6. Explicit registrations, not catalog, drive runtime. 7. Requesters access provider behavior/status only through providers public API.

## Effort & Risk

Mid, elastic. Rich knowledge can grow freely because it is isolated from runtime design. Main risk is accidental promotion into code; import/codegen guards prevent coupling.
