# Sidecar: capability evidence process, generated references, and schema evolution policy

## Description

Non-gating sidecar split out of MA16 (RV367). Owns the capability research/evidence process and the generated human/agent-facing views of the MA16 catalog: the evidence-provenance overlay and quarantine/promotion mechanics, the generated agent-facing capability reference and transport-manifestation views, the schema versioning/migration-read-compatibility policy, and a consolidated research reference doc. Also the parking place for SOFT-CAPABILITY research tracks (RV370) — forward-looking provider capability profiles (e.g. ag-CLI host candidacy) that inform future catalog declarations without growing the MA16 gate. MA16 keeps only the minimal hook: declarations carry an evidence-record reference plus review state, and unverified support cannot auto-select. Nothing in Blocks B–E waits on this item; pick it up when more capability information is needed.

## Steps

1. Create consolidated research/evidence reference doc (docs/reference/, alongside AGENT_EXECUTION_TRANSPORTS.md and model-source-evidence/) that indexes per-provider capability evidence: tool version, fact anchor, verification state, review linkage. Fold in corrected MO09 matrix linkage and the RV353/RV356 quarantine ledger so quarantine mechanics live here, not in schema.
2. Define the evidence-record format and promotion process: fact-specific anchors only; provider-wide anchors, help-output absence, config-parser acceptance, and expected behavior are never promotion evidence. Promotion of a support state requires an independently reviewed evidence record; MA16 declarations reference records by id.
3. Implement the evidence overlay compiler only when a consumer needs it: verified external facts layered onto descriptor-derived catalog entries without hand-copying.
4. Generate agent-facing capability reference from the same provider declarations as the machine catalog: short description, when to use, invocation affordances, limitations, action-needed guidance. Include transport-manifestation view (interactive, live output/cancel/permission, session persistence, caller delivery modes). Zero hand-maintained duplicate matrix.
5. Define schema versioning and migration/read-compatibility policy when (and only when) a second schema version is actually required; until then MA16 stays single-version strict-load.
6. Keep generated views reproducible: same declaration input yields identical machine catalog and reference output; guard against divergence.
7. SOFT-CAPABILITY RESEARCH — AG-CLI HOST CANDIDACY (RV370, speculative, research only): investigate per provider whether it can serve as the ag CLI in place of the ag pi launcher. Candidacy facts, per installed provider version with evidence records: (a) startup with a fully customizable or alternative config — isolated config root/profile so an ag-CLI session's configuration is disjoint from the user's normal provider config; (b) MCP-set control at launch — management MCPs are attachable to the ag-CLI session ONLY and never pushed into user-started provider sessions; (c) launch-time permission lockdowns — restrict tool/file/command permissions for the ag-CLI role; (d) any session/identity separation needed to distinguish ag-CLI from user use. Express findings as ordinary MA16 catalog declarations under the existing launch-environment/launch-time-override kinds (new facts, not new schema); providers missing (a) are disqualified as ag-CLI candidates and recorded as such. No launcher implementation, provider selection, or MA16 schema growth in this item — output is evidence records plus a candidacy view in the research doc; an implementation item is created only if/when the launcher replacement is scheduled.

## Validation

1. Research doc indexes every provider capability evidence record with version/anchor/review state; no orphan quarantined facts.
2. No support state anywhere promotes from a non-fact-specific anchor; known-false pre-RV353 classifications cannot surface in generated views.
3. Agent reference and machine catalog derive from the same declarations; parity test proves no second matrix.
4. Versioning policy exists only if a second schema version exists; MA16 loader remains single-version strict otherwise.

## Effort & Risk

Mid, elastic. This item deliberately absorbs the process/documentation weight so MA16 stays a minimal gating contract. Risk of drift if evidence updates bypass the doc — promotion rule makes the record mandatory.
