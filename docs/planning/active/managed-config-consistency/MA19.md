# Maintain provider capability knowledge and evidence

## Description

Implement provider-owned capability facts and evidence without changing runtime automation contracts. Preserve existing descriptor fields as operational declarations; add a separate typed capability_facts collection for evidence/status metadata. HostCapability remains an editor-extension declaration only. Facts may reference recipe ids/families for documentation but cannot satisfy RecipeDefinition, register implementations, select transports, or enable automation.

## Steps

1. Add provider-owned frozen types in components/providers/descriptors/base.py: CapabilityEvidence(evidence_tier, tool_version, fact_anchor, review_state) and ProviderCapabilityFact(capability_id, subject, mechanism, constraints, limitations, support_assessment, action_needed, evidence). Use optional/default values so providers can be populated incrementally. Do not add provider evidence fields to foundation ManagedConfigSpec or recipe types.
2. Add ProviderDescriptor.capability_facts and a loader builder/PROVIDER_SPEC entry. Load capability_facts losslessly from provider YAML. Keep annotations free-form and informational; do not treat annotations as authoritative capability evidence.
3. Preserve HostCapability exactly as the host/editor-extension declaration. A host-extension fact references its stable subject from capability_facts; evidence for model config, connectors, vendor injection, catalog, execution, surfaces, transport, and permissions uses the same capability_facts shape rather than overloading HostCapability.
4. Populate provider YAML from current model-source-evidence documents and PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md. Verified claims require evidence appropriate to the claim; unresolved or FILL claims remain pending/unverified and must not unlock implementation.
5. Validate capability_facts across all descriptors: capability_id is non-empty and unique within one provider; (provider_id, capability_id) is the global identity; subject resolves to a declared descriptor field/member or an explicitly documented external fact; evidence_tier is one of unverified/documentation/installed-artifact/round-trip/execution; review_state is one of pending-review/verified/quarantined; verified facts require tool_version and fact_anchor. Shared capability ids across different providers are permitted.
6. Add provider-owned deterministic serializers for the capability_facts collection: lossless JSON machine view and concise Markdown human view. Do not reuse list_provider_descriptors as the lossless source because its public projection is intentionally selective. Generated views are references, never runtime authority.
7. Add tests for YAML loading/defaults, unknown-field preservation where supported, validation failures, deterministic JSON/Markdown output, and absence of imports from generated views into runtime/foundation code.
8. Guard execution boundary: capability facts can describe recipe ids/families, support, and evidence, but cannot construct RecipeDefinition, register handlers, select transports, or execute plan/apply/prune/status. MA20 owns RecipeDefinition; MA16 family items own public payload/results and explicit registration.
9. Continue provider interrogation by adding facts/evidence only. New evidence fields extend CapabilityEvidence/ProviderCapabilityFact deliberately; do not create provider-specific evidence shapes or promote annotations into logic-driving state.

## Files

[COMPONENT:providers/descriptors/base.py] CapabilityEvidence, ProviderCapabilityFact, ProviderDescriptor.capability_facts
[COMPONENT:providers/descriptors/loader.py] capability_facts builder and PROVIDER_SPEC entry
[CONFIG:providers/*.yaml] provider-owned capability facts/evidence
[COMPONENT:providers] validation and deterministic JSON/Markdown serializers
[EVIDENCE/DOCS] current fact anchors and generated reference views
[TEST] loader defaults, validation, evidence linkage, deterministic views, execution/foundation separation
[FORBIDDEN] changes to foundation ManagedConfigSpec for provider evidence, evidence fields on HostCapability as universal model, generated Python taxonomy, runtime imports of generated views

## Validation

1. Every populated fact round-trips from YAML without loss. 2. HostCapability remains limited to host/editor extensions. 3. (provider_id, capability_id) identities are unique; valid shared ids across providers are accepted. 4. Verified facts require versioned anchors and claim-appropriate evidence. 5. FILL/unverified facts cannot unlock implementation. 6. JSON and Markdown views are deterministic and derived only from provider config. 7. No fact or generated view is accepted as RecipeDefinition, registration, transport selection, or runtime authority. 8. Foundation remains provider-agnostic. 9. Existing provider descriptor and API tests remain green.

## Effort & Risk

Mid. Type/loader work is small; evidence population and subject validation span heterogeneous descriptor declarations. Main risks are treating editor extension ids as universal capability ids, duplicating operational config, and allowing evidence to influence execution.
