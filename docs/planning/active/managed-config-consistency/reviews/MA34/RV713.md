# foundation/io.py:load_json_file conflates missing-file with corrupt-file (returns {} for both), causing every managed JSON config writer built on it to silently destroy corrupted content on next apply

## Notes



## Findings

ROOT CAUSE IDENTIFIED (supersedes the earlier per-adapter framing): src/audiagentic/foundation/io.py:65 load_json_file's own docstring states the contract plainly -- 'Missing file or malformed content returns {}.' It catches (json.JSONDecodeError, OSError) and returns {} exactly like the missing-file case, with no way for a caller to tell the two apart. This is a shared foundation primitive, not an isolated adapter mistake: adapters/opencode/plugin_array.py (read_opencode_plugins, write_opencode_plugins), adapters/opencode/mcp_json-style readers, and other JSON-format adapters route through it directly. Separately, codex/hooks_format.py:_load_hooks reimplements the identical missing-file-or-malformed-returns-{} pattern by hand (json.JSONDecodeError -> {}) rather than calling the shared helper, so the same defect exists twice: once at the foundation layer for every caller of load_json_file, and once independently in codex's hand-rolled hooks reader. mcp_opencode.py, continue_/mcp_format.py, and openhands/toml_format.py (TOMLDecodeError variant) each have their own local copies of the same swallow-and-return-empty shape, whether or not they route through load_json_file. Concretely: any managed JSON config file that becomes corrupted on disk (partial write, manual edit gone wrong, disk fault) is silently treated as an empty/fresh config by the very next managed write, which then overwrites it with only the newly-desired managed entries -- permanently destroying whatever was there, including foreign/user-authored content that a corrupted-but-partially-valid file might still have held. By contrast, ManagedFragmentRegistry.load() in foundation/toolchains/managed_config.py raises canonical CON-MCFG-001 on the same failure mode, and adapters/codex/mcp_format.py:69 / adapters/opencode/execution_environment.py:34 already raise AudiaGenticError on parse failure -- proving corrupt-must-raise is the codebase's own established pattern for TOML and for at least two JSON sites, just not applied at the shared load_json_file level or in the hand-rolled JSON readers that predate/bypass it. Found while building MA34's negative-path Docker e2e coverage, which has a test asserting a corrupted config file must raise a canonical error and leave the file byte-for-byte unchanged rather than being silently replaced; that test is marked xfail(strict=True) against current code pending this fix.

## Conclusion

Recommend fixing at the foundation layer first: split load_json_file's missing-file and malformed-content cases -- keep returning {} for FileNotFoundError/missing path (legitimate 'nothing here yet'), but raise a canonical error (mirroring CON-MCFG-001) for json.JSONDecodeError specifically. That single fix propagates correctness to every caller of load_json_file automatically (config-over-code, not a per-adapter patch). Then separately fix the hand-rolled duplicates that don't go through load_json_file: codex/hooks_format.py:_load_hooks, mcp_opencode.py, continue_/mcp_format.py, openhands/toml_format.py (TOML variant, would need the equivalent tomllib fix), codex/language_servers.py -- ideally by routing them onto the shared corrected helper instead of keeping their own try/except. Before changing behavior, confirm no test currently relies on malformed-content-returns-{} as intended behavior (as opposed to missing-file-returns-{}, which must be preserved). Fix belongs to whoever owns foundation/io.py and adapter-serializer correctness next; do not fold into MA34, which is scoped to building the test suite that found this.
