# The managed-config engine already exists — hooks needs no service, and plugin-entry is the one family bypassing it (an existing test already fails on exactly that)

## Notes

Raised from the owner's question 'can hooks and plugins just be removed if we use managed config'. Investigated properly rather than defending the current shape, and the answer is largely YES. Supersedes the assumption in MA26 step 3 that managed-hooks needs a hand-rolled service. Sharpens RV502 (shared scaffolding) and RV508 (plugin-entry outlier) with the decisive evidence: the engine is already built and already has adopters.

## Findings

['THE ENGINE ALREADY EXISTS, in foundation, and is entry-type-agnostic: sync_managed_config(spec, project_root, owner_scope, desired_entries: dict[str, tuple[str, Any]], *, registry: ManagedFragmentRegistry, managed_ids) is a thin binding over reconcile_fragments. The `Any` is the opaque native entry — the engine never inspects it. It already does exactly the merge-owned/preserve-foreign/prune-owned-only semantics MA26 step 5 needs.', 'MO06 ALREADY DID THIS COLLAPSE for two families. services/mcp.py: \'Thin MCP binding over the shared sync_managed_config core (MO06)\'. services/models.py: \'Thin binding over the shared sync_managed_config core (MO06) — no...\'. So the pattern is established and proven; managed-mcp and model-projection are already thin bindings, not hand-rolled services.', 'PLUGIN-ENTRY IS THE ONLY FAMILY THAT BYPASSES THE ENGINE. plugin_entries.py calls spec.reader(...), spec.writer(...) and spec.remover(...) DIRECTLY, doing its own read/compare/write with no ownership registry and no fragment reconciliation.', 'AN EXISTING TEST ALREADY FAILS ON EXACTLY THIS. tests/unit/foundation/toolchains/test_managed_mutation_boundaries.py::test_direct_managed_spec_calls_are_core_or_recorded_violation fails with \'Extra items in the left set: src/audiagentic/components/providers/services/plugin_entries.py\'. managed_config.py\'s own docstring states the invariant it breaks: \'exactly two places in the codebase ever touch .writer/.remover: this module and the fragment-based sync_managed_config above\'. I had previously mis-attributed this red test to MO02 audit noise — it is not; it is flagging plugin-entry.', 'PluginConfigSpec IS REDUNDANT WITH ManagedConfigSpec. The only difference is keyed access: PluginConfigSpec.reader is (Path, entry_id) -> dict|None and writer is (Path, entry_id, dict), versus ManagedConfigSpec.reader (Path) -> dict[str, Any] and writer (Path, dict[str, Any]). The opencode plugin array IS a name-keyed collection — read_opencode_plugin already scans it by package name and write_opencode_plugin already preserves other entries. Expressing it as reader(path) -> {package: options} is trivial and unlocks the engine, the registry, and ownership scoping it currently lacks.', 'HOOKS NEED NO SERVICE EITHER. hooks.json is expressible as a ManagedConfigSpec if the codex adapter presents it as a name-keyed dict (key = the command string, value = {event, timeout}), which pairs exactly with the ManagedFragmentRegistry mapping managed_id -> command that MA26 already adopts. Then hooks are: a descriptor spec + an adapter + sync_managed_config with owner_scope=\'hindsight\'. No new service module.', 'LANGUAGE-SERVER-PROJECTION is a deliberate partial exception, documented in managed_config.py: it uses apply_managed_config_write because it \'upserts the whole desired language set each time with no managed_id registry\'. That is a real design choice (whole-set ownership, not per-entry), not an oversight — do not force it onto the per-entry engine without deciding whether it should own entries individually.']

## Conclusion

Answer: YES for the SERVICE layer, NO for the typed contracts — and the distinction is what makes this a real simplification rather than a generic blob.\n\nREMOVE: (1) the hand-rolled plugin-entry service — convert PluginConfigSpec to ManagedConfigSpec (reader(path) -> {package: options}) and route through sync_managed_config, which deletes PluginConfigSpec entirely, fixes the failing boundary test, and gives plugins the ownership registry and scoping they currently lack; (2) the planned managed-hooks SERVICE — never build it. MA26 step 3 shrinks to a hooks_config ManagedConfigSpec in codex.yaml, a codex hooks_format adapter, and a thin binding.\n\nKEEP: the typed Request/Result contracts. They are the public API and the JSON-schema boundary, and MA20 step 4 locks them ('no universal request/result'). But they are ~40-line dataclasses plus a ~15-line binding — not families. A caller must still be able to construct a typed hook rather than a dict; that is the line between 'one engine' and 'a generic blob'. Note plugin-entry has no typed contract to preserve anyway: its payload is an untyped options bag (RV508), which is precisely why it drifted off the engine.\n\nRESULTING SHAPE, repo-wide: ONE engine (sync_managed_config, already built) + ONE spec type (ManagedConfigSpec, delete PluginConfigSpec) + N per-provider format adapters + N thin typed facades. Combined with RV505 (collapse lsp-mcp-projection into managed-mcp), the family count goes from 5 hand-rolled services to 3 typed facades over shared machinery.\n\nORDER: do the plugin-entry conversion FIRST — it is small, it turns a currently-failing test green, and it produces the worked example that MA26's hooks binding then copies. That is cheaper than MA26 inventing the pattern and plugin-entry being retrofitted later.
