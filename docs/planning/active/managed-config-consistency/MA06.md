# Migrate Hindsight config and artifact ownership

## Description

After MA02 moves memory integration intent into memory-owned declarations and provider-specific execution into provider capability handlers, replace remaining direct memory mutations with gateway requests, ConfigPatcher, WriteFileStep, ArtifactRegistry, and managed-config core while preserving user-home state. Memory never calls provider implementation directly; providers remains unaware of Hindsight.

## Steps

1. Freeze golden fixtures and classify every current artifact exactly once: memory-owned backend artifact (for example Hindsight backend settings/state), provider-owned artifact/config (Codex/Pi/plugin/provider config), or third-party unowned repair. Record owner, path, prior bytes, adoption rule, request capability, and prune behavior.
2. Memory-owned backend artifacts use foundation ConfigPatcher/WriteFileStep/ArtifactRegistry directly with stable memory-owned ids. They may not contain provider format/path policy beyond their own backend home/config.
3. Provider-owned artifacts are expressed only as MA02 gateway requests with opaque ownership scope. Provider handler performs ConfigPatcher, WriteFileStep, managed-config, download, or artifact registry operation as appropriate; memory neither imports nor invokes these provider mechanisms.
4. Define adoption centrally: whole file adopts only when created this run or exact canonical bytes; nested key adopts only absent or exact legacy desired value. Differing value/file remains user-owned collision. Provider handler returns adoption/collision result; memory does not interpret provider file shape.
5. Migrate Pi generic config request, Codex hook/config request, plugin URL/array request, and managed MCP request one capability at a time. Provider handlers preserve unrelated keys/tables and use stable opaque ownership scope.
6. Windows dynamic plugin repair is a provider handler third-party-repair capability. It must validate pinned upstream version/hash or structural precondition, be idempotent/atomic/redacted, restore original bytes on failure, and return unsupported when precondition fails. Remove it if no generic bounded capability can satisfy these rules.
7. Dry-run submits gateway plan only: no file/registry/network/subprocess mutation. Prune reports removed/restored/skipped/collisions; memory-owned prune and provider gateway prune remain separately observable under same operation result envelope.
8. Update MA01 audit actions/allowlists after each migration; remove obsolete exemptions and direct memory provider-write helpers.

## Validation

1. Every artifact classified memory-owned, provider-owned, or approved third-party repair exactly once.
2. Memory has zero direct writes/removals to provider-owned paths and zero provider implementation imports; provider artifacts mutate only inside gateway handler.
3. Pre-existing differing user values/files remain byte-identical and report collision; exact legacy values adopt and prune safely.
4. Provider handlers preserve unrelated provider config keys/tables; memory-owned backend artifacts preserve unrelated backend keys/tables.
5. Dry-run changes no file/registry mtime and performs no network/subprocess call; secret canary absent from requests/results/logs.
6. Windows repair either passes pinned-precondition/idempotence/atomic restoration tests or is removed.
7. Golden probe/configure/verify/prune outputs preserve behavior except normalized gateway/collision fields; known Hindsight failures fixed; zero new failures.

## Effort & Risk

Complex user-home adoption. Implement per integration with isolated fixtures; never bulk-adopt based only on filename.
