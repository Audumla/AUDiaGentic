# Migrate Hindsight config and artifact ownership

## Description

After MA02, migrate remaining Memory/Hindsight-owned and provider-owned artifacts to their established owners and primitives while preserving user state. Provider artifacts use MA16 family operations; memory artifacts use foundation mutation primitives directly.

## Steps

1. Freeze golden fixtures and classify every current artifact exactly once: memory-owned backend artifact, provider-owned artifact/config, or third-party unowned repair. Record owner, path, prior bytes, adoption rule, desired data, ownership scope, and prune behavior.
2. Memory-owned backend artifacts use foundation ConfigPatcher/WriteFileStep/ArtifactRegistry directly with stable memory-owned ids. They may not contain provider format/path policy beyond their own backend home/config.
3. Provider-owned artifacts are expressed only through MA02 providers_api calls using family-specific desired data, opaque ownership scope, and `plan|apply|prune|status`. Provider internal mechanics perform ConfigPatcher, WriteFileStep, managed-config, download, or artifact registry as appropriate; memory neither imports nor invokes them.
4. Define adoption centrally: whole file adopts only when created this run or exact canonical bytes; nested key adopts only absent or exact legacy desired value. Differing value/file remains user-owned collision. Provider result returns adoption/collision outcome; memory does not interpret provider file shape.
5. Migrate Pi generic config request, Codex hook/config request, plugin URL/array request, and managed MCP request one operation at a time. Provider mechanics preserve unrelated keys/tables and use stable opaque ownership scope.
6. Windows dynamic plugin repair is a provider third-party-repair operation. It must validate pinned upstream version/hash or structural precondition, be idempotent/atomic/redacted, restore original bytes on failure, and return unsupported when precondition fails. Remove it if no generic bounded operation can satisfy these rules.
7. `plan` and `status` perform no file/registry/network/subprocess mutation. `prune` reports removed/restored/skipped/collisions and removes only owned state. Memory-owned and provider-owned operations remain separately observable.
8. Update MA01 audit actions/allowlists after each migration; remove obsolete exemptions and direct memory provider-write helpers.

1. Every artifact classified memory-owned, provider-owned, or approved third-party repair exactly once. 2. Memory has zero direct writes/removals to provider-owned paths and zero provider implementation imports. 3. Provider calls expose only plan/apply/prune/status; recipe methods do not cross boundary. 4. Pre-existing differing user values/files remain byte-identical and report collision; exact legacy values adopt and prune safely. 5. Provider mechanics preserve unrelated provider config keys/tables; memory-owned artifacts preserve unrelated backend keys/tables. 6. Plan/status change no file/registry mtime and perform no network/subprocess call; secret canary absent. 7. Windows repair passes bounded precondition/idempotence/atomic restoration tests or is removed. 8. Golden behavior preserved except normalized outcome fields; zero new failures.
