# Reduce end-to-end CI latency with measured sharding, deduplicated triggers and reusable tooling

## Description

Measure and optimize merge/build/release validation without skipping required behavior or weakening isolation. Baseline runs39901999238/39904427048/39906670207: end-to-end20.0-23.6min; complete Docker clean-suite test phase10.2-19.0min plus1.1-1.4min image build; host parallel9.8-12.7min plus0.7-0.9min serial; host dependency setup0.5-8.0min. Logs show slow Azure apt mirror/font downloads dominate8min setup, not pip itself. Duplicate push+PR run cancellation held latestPR for~5min. Most independent real-provider/recipe lanes complete within3-6min; Pi generative lanes variable and must remain authentic.

## Steps

1. Emit per-job setup/build/parallel/serial timings, pytest durations and JUnit artifacts always, including failures. 2. Deduplicate branch push versus PR event coverage while preserving main/release/fork validation and ensuring required checks are actually created. 3. Shard full suite by deterministic test-module assignment, use module-safe scheduling, preserve global serial phase; assert collection union equals baseline and no duplicate/empty shards. 4. Isolate small browser-dependent set so generic host tests do not install browser OS/font packages; cache immutable tooling by OS/Python/dependency/browser versions. 5. Use buildx layer caching for final images, not just repeated shared-base build; avoid redundant cache writes to one shared scope across matrix. Keep real install/uninstall recipe environments disposable. 6. Assess host/Docker overlap from collection manifests before narrowing either lane; keep required hermetic and host-specific coverage on every PR/main/release. 7. Compare fresh/cache-hit PR and postmerge critical paths before accepting improvement; consider exact-head artifact reuse only with persisted provenance and fail-closed identity/inputs checks.

## Detailed Solution & Technical Design

Separate safe quick wins from medium-risk scheduling changes. Dedup triggers and timing visibility first; module-level sharding second; browser/tool/image caching third. Do not substitute fewer assertions, bigger timeouts, synthetic success, soft failed jobs, arbitrary sleeps or removal of real provider tests. Keep main CI green gate before publishing; release publication jobs are comparatively short and are not primary bottleneck. Treat model latency separately: explicit native smoke tool policy and genuine turn completion, no protocol emulation in live proof. Proposed latency target8-12min warm-cache PR/main validation is provisional, not a measured result.
