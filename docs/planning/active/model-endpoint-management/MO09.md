# Deep-dive verification: agent provider × vendor support and key-injection matrix

## Description

Research/verification item (no production code): verify, provider by provider, which upstream vendors/aggregators each agent provider supports and how, filling every ⟨FILL⟩ cell in the 'Agent provider × vendor support matrix' of docs/reference/PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md. For each (agent provider, vendor) pair record: (a) projection mode — native support (agent knows the vendor and needs only a key) vs custom-entries (explicit model entries in config) vs none; (b) key mechanism — exact env var name or config field path, verified against the INSTALLED tool version and its docs, not assumed; (c) model-set granularity — all-models-per-vendor (no filtering possible) vs per-model selectable (model-filter applicable); (d) base-url override support where relevant (OpenRouter, local gateways). Output feeds MO07's vendor-key-injection declarations in provider YAML — a pair is only automatable once its cell is verified with a recorded source. This is the running reference the whole external-provider capability depends on; it must be kept current per the documentation gate.

## Steps

1. Establish the verification protocol: for each provider, check (in order) the repo's own adapter/descriptor/harness code, the installed tool's config surface on disk, and upstream docs for the installed version; record the source (file path, doc URL + version, or CLI inspection) alongside each verified cell. No cell is verified from memory or training knowledge.
2. SCOPE ORDER (RV316): verify the OPENCODE COLUMN FIRST — it is the acceptance target because the first event-driven agent (Reviewer, RA01) executes OpenCode, and its primary evidence is one command: `opencode models --verbose` (already wrapped by adapters/opencode/catalog.py::_fetch_opencode_catalog), which enumerates native-vendor support, key-unlocked models, and per-model capability/limits. Then verify remaining P1 vendor columns (OpenAI, Anthropic, Google, OpenRouter) for whichever other first-wave tools are actually installed (pi, openhands, codex, qwen), in parallel where convenient; tools that are not installed get `blocked: tool not installed (probe result)` cells immediately — do not chase installations. The long tail (continue, aider, goose, cline, roo, plandex, gemini, claude, copilot) is verified opportunistically or left blocked.
3. For each verified native pair, record the exact key mechanism (env var name or config field path) and whether base-url override is supported; for each custom-entries pair, record the entry shape and whether per-model selection exists (filter applicability).
4. Replace matrix ⟨FILL⟩ cells in the reference doc as verified, and update the upstream mapping table (connector, discovery mode, auth scope) where the same investigation settles those FILLs.
5. Record unresolvable cells explicitly as 'not supported' or 'blocked: <missing evidence>' — never leave a guessed value; blocked cells keep that pair manual in MO07 (MO07/MO13/MO14 consume only VERIFIED cells).
6. Summarize per-provider findings in that provider's adapter README (adapter-local detail + link to the matrix, per the MO04 docs-consistency rule).
7. Evidence format per matrix cell: {provider-id, upstream-id, tool-version, verified-at, evidence-kind: repo|installed-cli|upstream-doc, source: path|command-name|URL, sanitized-summary}. Store detailed evidence in docs/reference/model-source-evidence/<provider-id>.md and link cells to anchors; never paste raw config/env/CLI dumps.
8. If tool is absent or account/key prevents verification, record blocked with exact missing evidence and tool version/probe result; continue other cells.
9. Do not write vendor-key-injection/provider descriptor declarations until MO01's descriptor fields/loader tests exist. If research lands first, update evidence/reference only; MO07 applies declarations later.

## Validation

1. Every matrix cell is either a verified fact with a recorded source, 'not supported', or 'blocked: <reason>' — zero remaining bare ⟨FILL⟩ in the P1 vendor columns.
2. Spot-check: each verified env/config key mechanism demonstrated against the installed tool (config file inspection or launch-env dry run) for at least the first-wave providers.
3. Docs lint if available.
4. Each verified cell links one structured evidence record containing tool version/date; blocked cells name missing evidence.
5. Secret scan of evidence/docs finds no API keys, auth headers, home-specific credential paths, or raw tool output.
6. Config declarations, if written, load through MO01 DescriptorSpec and match evidence exactly.

Research output feeds provider YAML declarations only for VERIFIED pairs — this item must not write unverified vendor-key-injection declarations. §8 redaction: verification steps that inspect config files or launch envs must never copy key values, auth headers, or key-bearing URLs into the reference doc, READMEs, or recorded evidence — record the KEY NAME/mechanism, never the value.
