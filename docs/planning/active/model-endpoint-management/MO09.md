# Deep-dive verification: agent provider × vendor support and key-injection matrix

## Description

Research/verification item (no production code): verify, provider by provider, which upstream vendors/aggregators each agent provider supports and how, filling every ⟨FILL⟩ cell in the 'Agent provider × vendor support matrix' of docs/reference/PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md. For each (agent provider, vendor) pair record: (a) projection mode — native support (agent knows the vendor and needs only a key) vs custom-entries (explicit model entries in config) vs none; (b) key mechanism — exact env var name or config field path, verified against the INSTALLED tool version and its docs, not assumed; (c) model-set granularity — all-models-per-vendor (no filtering possible) vs per-model selectable (model-filter applicable); (d) base-url override support where relevant (OpenRouter, local gateways). Output feeds MO07's vendor-key-injection declarations in provider YAML — a pair is only automatable once its cell is verified with a recorded source. This is the running reference the whole external-provider capability depends on; it must be kept current per the documentation gate.

## Steps

1. Establish the verification protocol: for each provider, check (in order) the repo's own adapter/descriptor/harness code, the installed tool's config surface on disk, and upstream docs for the installed version; record the source (file path, doc URL + version, or CLI inspection) alongside each verified cell. No cell is verified from memory or training knowledge.
2. Verify the P1 vendor columns first (OpenAI, Anthropic, Google, OpenRouter) across all agent providers, starting with providers already slated for first-wave adapters (pi, opencode, openhands, codex, qwen) then the rest (continue, aider, goose, cline, roo, plandex, gemini, claude, copilot).
3. For each verified native pair, record the exact key mechanism (env var name or config field path) and whether base-url override is supported; for each custom-entries pair, record the entry shape and whether per-model selection exists (filter applicability).
4. Replace matrix ⟨FILL⟩ cells in the reference doc as verified, and update the upstream mapping table (connector, discovery mode, auth scope) where the same investigation settles those FILLs.
5. Record unresolvable cells explicitly as 'not supported' or 'blocked: <missing evidence>' — never leave a guessed value; blocked cells keep that pair manual in MO07.
6. Summarize per-provider findings in that provider's adapter README (adapter-local detail + link to the matrix, per the MO04 docs-consistency rule).

## Validation

1. Every matrix cell is either a verified fact with a recorded source, 'not supported', or 'blocked: <reason>' — zero remaining bare ⟨FILL⟩ in the P1 vendor columns.
2. Spot-check: each verified env/config key mechanism demonstrated against the installed tool (config file inspection or launch-env dry run) for at least the first-wave providers.
3. Docs lint if available.

## Effort & Risk

Mid, research-heavy, code-free and parallel-safe (can run alongside MO06/MO01 like the MO03 validation gates). Risk is treating training-knowledge expectations as facts — the matrix already seeds expected values, so the work is confirmation/refutation with sources, not invention. Provider tools move fast; record the verified version with each cell.
