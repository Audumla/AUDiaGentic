# Provider secret resolution and launch-env contribution seam

## Description

Prerequisite infrastructure identified by RV315: grep confirms NO secret-ref resolver exists anywhere in src (api-key-ref/secret resolver/auth resolver — zero hits), yet the model-sources contract carries `api-key-ref: env:<VAR>` and four items depend on resolving it (MO02 step 5 launch-env recipe, MO04 step 4 Aider env, MO07 steps 3-4 key injection, MO13 step 3 OpenHands env). This item delivers two coupled pieces, provider-component-local (single consumer today — do NOT extract to foundation until a second component needs it, §3 two-consumer rule): (1) a prefix-based SECRET-REF RESOLVER — registry of scheme -> resolver with only `env:` at v1, extensible by registration without touching call sites; (2) the LAUNCH-ENV CONTRIBUTION SEAM — providers/recipes contribute DEFERRED {env-name -> secret-ref | literal} entries; resolution happens only inside the execution launch path immediately before subprocess spawn. Resolved values are never cached, persisted, logged, placed in status/timelines/fragments (beyond the single target config field for config-mechanism injection in MO07), or included in error details. Adds ProviderRecipeKind.LAUNCH_ENV so env projection is a first-class recipe kind instead of the currently missing seam (RV313 finding 1: today's only env injection is LSP's launch_server(env=...) one-off).

## Steps

1. Add providers/services/secret_refs.py: SecretRef parse/validate (scheme:payload), a (scheme -> resolver-fn) registry with `env:` registered at v1, resolve_secret_ref(ref) -> str. Unknown scheme raises VAL-SEC-001; env var unset/empty at resolution time raises CON-SEC-001. Register both codes (plus resolution text) in src/audiagentic/config/components/providers/error-resolutions.yaml BEFORE first use (§8). SecretRef repr/str never includes a resolved value; the resolver returns the value to the caller and retains nothing.
2. Add ProviderRecipeKind.LAUNCH_ENV and a LaunchEnvContributionRecipe pattern: recipes declare contributions as {env-name: SecretRef|literal} WITHOUT resolving; status/dry_run report env NAMES and ref schemes only, never values. Providers whose execution is stub/unsupported hold contributions inert with action_needed ('execution bridge not wired') — a stub provider never receives an active projection (matches MO04 validation 7).
3. Wire the execution launch seam: at provider launch (adapters/base_runner.py or the descriptor-driven execution path), collect the provider's registered launch-env contributions, resolve each ref, and inject into the subprocess env. Resolution failures surface the canonical error with the ENV NAME and scheme only. No resolution occurs at descriptor load, reconcile, or status time.
4. Architecture guards: resolver and seam live in the providers component; no foundation extraction (single consumer); no if/elif on scheme (registry dispatch); resolved values are local variables inside the launch/writer call frame only.
5. Tests: registry dispatch incl. fixture scheme added without core edit; unknown-scheme and missing-env canonical errors; redaction canary proving a resolved value appears in the spawned process env and NOWHERE else (repr, logs, status, timeline, registry, error details); stub-execution provider contributes nothing active; contribution listing shows names/schemes only.

## Validation

1. env: refs resolve at launch; unknown scheme -> VAL-SEC-001; unset var -> CON-SEC-001 with env NAME only in details.
2. Redaction canary: a sentinel secret value is visible in the spawned subprocess env and absent from every other observable surface (logs, status output, timeline attributes, registries, exception text, dataclass reprs).
3. Fixture scheme registers without modifying secret_refs.py core — proves extension point.
4. Stub-execution providers report inert contributions with action_needed and never active projection.
5. Existing provider launch/execution tests remain green.

## Effort & Risk

Mid. Small surface but security-sensitive; the redaction guarantee is the deliverable as much as the mechanism. Risk: scope creep toward a general secrets manager — v1 is env-scheme only, provider-local, no persistence, no new config files.
