# Enable remote-account model sources (key injection + filtered custom entries)

## Description

Implement enablement of `remote-account` sources per the MO01 contract: any keyed external service — frontier vendors (OpenAI/ChatGPT, Anthropic, Google Gemini) and account aggregators (OpenRouter, OpenCode Zen, Qwen portal, LiteLLM proxy) behave identically in code; vendor-vs-aggregator is documentation grouping only. The account and its model entitlements are never managed by AUDiaGentic. Two independent axes from MO01: DISCOVERY (static-catalog data files / best-effort list-api with cached degradation / none) feeds AG-side aliases, defaults, and status; PROJECTION per (agent provider, source) is selected from provider YAML declarations — native-key-injection preferred (env mechanism rides the existing launch-env contribution seam with no fragments; config mechanism writes a managed fragment model-connections/<source-id> through the normal reconciler; the agent then enables ALL the vendor's models and model-filter is surfaced in status as not-applicable, never silently ignored), custom-entries fallback (materialize explicit model entries from the discovered set with model-filter applied — mandatory in practice for list-api aggregators), or none. Materialization feeds the SAME desired-entry builder input as local-endpoint sources (MO02 step 1) — sources are an input layer, not a second sync path. All taxonomy and semantics are pre-decided in docs/reference/PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md (Model Source Classes + provider×vendor matrix); per-pair support facts come only from MO09-verified matrix cells — the implementing agent applies decisions, it does not re-decide them or guess unverified cells.

## Steps

1. Add the remote-account materializer: (source declaration + verified projection mode per target provider) -> desired entries / connectivity fragment / launch-env contribution. ONE materializer for remote-account (no vendor/aggregator split); projection-mode selection reads provider YAML `vendor-key-injection` + `supported-connectors` declarations — no if/elif on class, vendor, or provider (§2).
2. Add curated static catalogs as data files: src/audiagentic/config/providers/model-catalogs/<source-id>.yaml (model id, display name, context window, max output, capability flags). Updating a vendor's family is a data change, no code change.
3. Add list-api discovery with a per-connector fetcher registry (openai-compatible /v1/models, openrouter /models; others FILL until verified). Refresh is best-effort: on failure keep the last cached catalog under .audiagentic/runtime/providers/source-catalogs/<source-id>.json, emit warning + action_needed, classify the failure per the MO08 guideline, and NEVER fail the sync.
4. Implement native key injection: env mechanism contributes {env-var: resolved key-ref} through the existing launch-env contribution recipe seam (no fragments, no persistence of the key value anywhere); config mechanism renders the agent's connectivity block (key/base-url fields) as managed fragment model-connections/<source-id> with dry-run support. Key VALUES are resolved from api-key-ref only at write/launch time and never appear in registries, status, timelines, or logs.
5. Implement custom-entries projection: apply model-filter (include/exclude globs) to the discovered set, then materialize entries keyed model-endpoints/<source-id>/<model-id> through the MO02 builder; same ownership/preserve-unmanaged/collision rules.
6. Wire alias/default resolution against the union of enabled sources' materialized models per the DECIDED rule (MO01 step 7): disabled source -> canonical VAL-MEP-003, never a silent fallback.
7. Extend provider status with per-source fields: source-class, grouping label, discovery mode, projection mode per provider (key-injection env/config | custom-entries | none | filter-not-applicable), enabled, materialized-model count, last catalog refresh outcome (fresh/cached/failed), action-needed text.
8. Update the reference doc's mapping table and provider×vendor matrix as each FILL is verified — same change, per the documentation gate.

## Validation

1. Unit tests: each (discovery mode × projection mode) combination produces the expected entries / fragment / env contribution; disabling a source removes only owned entries and env contributions.
2. Unit tests: list-api failure (unreachable, 401, 429) degrades to cached catalog + action_needed and the sync still succeeds; no secrets or key-bearing URLs in logs, registries, or status.
3. Unit tests: model-filter include/exclude applied on custom-entries path; status reports filter-not-applicable on key-injection path instead of silently ignoring it.
4. Unit tests: static-catalog data-file change alters materialized set without code change; undeclared (provider, vendor) pair projects nothing.
5. Unit test: alias resolving to a disabled source raises VAL-MEP-003.
6. Run focused provider model-source/catalog/status tests.

## Effort & Risk

Complex. Risks: re-deciding taxonomy at implementation time (forbidden — the reference doc is authoritative); guessing unverified matrix cells instead of consuming MO09 output; letting catalog refresh failures fail sync; leaking key values into fragments/status/logs; if/elif on source-class, vendor, or provider instead of declaration-driven selection. Network access happens only during explicit list-api refresh — never during descriptor load or ordinary reconcile of unchanged state.
