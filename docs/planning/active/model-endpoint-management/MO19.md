# Inject vendor credentials into harness-native provider configs for enabled model sources

## Description

Sponsor direction 2026-07-18: for a harness to actually execute a materialized vendor model (OpenRouter free models first), its native config needs the vendor endpoint + credential reference alongside the model entries MO17/MO18 project. This was deliberately excluded from MO17 pending a concrete consumer; the consumer now exists (free-model agents across harnesses). Keep it evidence-gated per harness and reuse the managed-config engine — credentials follow the exact ownership/preservation rules as every other managed fragment.

## Steps

1. FREEZE THE CONTRACT: extend or sibling the ModelProjectionRequest with typed vendor-connectivity desired state (source_id, base_url, auth reference — an env-var NAME or harness-native secret reference, never a literal key). Follow the MA26 pattern exactly: frozen dataclasses, v1 JSON schema, FamilyPin validation, 4-char error prefix registered in error-resolutions.yaml. Decide with the architecture owner whether this is a new small family (managed-provider-connectivity) or additional typed fields on model-projection — test: do connectivity entries and model entries share desired-state semantics, ownership, modes, and result behavior (MA20 step 4)? If yes extend, if no sibling family on the same sync_managed_config engine.
2. HARNESS EVIDENCE GATE (per the capability matrix): Pi first — verified model_config writer exists and Pi supports custom OpenAI-compatible endpoints with env-ref keys. Each additional harness (OpenCode next once its config filename/container blocker resolves; then per-matrix candidates) requires a verified writer contract fact before any adapter code, per the MO04/MO13/MO14 doctrine.
3. SECRET POSTURE: AUDiaGentic stores and projects references only. Where a harness accepts env-var references (Pi, Qwen per matrix), project the reference. Where a harness demands a literal key in config, that harness is BLOCKED for injection until a sponsor-approved secret-materialization decision exists — record the fact, do not silently write secrets. Redaction canary tests on every write path.
4. Wire prune: disabling a source removes its connectivity fragment only when no other enabled source uses it; foreign connectivity entries untouched.
5. End-to-end proof: with MO18's free models projected and connectivity injected, a live Pi invocation against one OpenRouter free model succeeds (Docker or live gate, sponsor account).

## Files

[CONTRACT] providers/contracts (typed connectivity request/result + schema). [REUSE] sync_managed_config, ManagedFragmentRegistry, Pi descriptor/adapters, MO18 source config. [MA19] per-harness key-reference acceptance facts. [TEST] contract validation, ownership/prune, redaction canaries, live free-model smoke.

## Validation

1. Typed contract with schema; no raw secret accepted or persisted anywhere. 2. Pi executes an OpenRouter free model end-to-end using projected config only. 3. Ownership/preservation/prune proven per managed-config guarantees. 4. Unverified harnesses are recorded blocked, not guessed. 5. Focused suites + ruff pass.

## Effort & Risk

Complex due to the secret posture and per-harness variance. Stop and open a review if any harness requires literal-secret materialization or if the family-vs-extend decision is contested.
