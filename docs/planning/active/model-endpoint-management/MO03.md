# Add first-wave local model provider adapters

## Description

Implement first-wave model endpoint adapters, annotated by config mechanism because the mechanism determines the reuse vehicle. Structured-file providers with confirmed or strongly-shaped config surfaces (Pi, OpenCode after path unification, Codex, Qwen) contribute a reader/writer/remover trio to the consolidated ManagedConfigSpec and reconcile via fragments. OpenHands is env-projection (a launch-env capability recipe, NOT the fragment reconciler). Goose is validate-first in the current repo state: its descriptor currently confirms `.goose/config.yaml` for MCP and a stub execution bridge, not a JSON custom-provider model config. local-openai is the AG-side catalog bridge (MO05 fixes its schema). Per-provider adapter spec fields (config path, container keys, active-model pointer, auth, refresh, sources) with FILL placeholders are in docs/reference/PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md.

## Steps

1. PARALLEL VALIDATION GATE: resolve OpenCode config target — harness installer writes `.opencode/config.json` with top-level `providers` (shape repo-verified: api/baseURL/apiKey/models map), while descriptor/MCP/LSP use `.opencode/opencode.json` with `provider`. Reconcile before writing any OpenCode model config. If unresolved after the first implementation pass for MO06/MO01, keep OpenCode model management blocked/manual and move only verified providers forward.
2. PARALLEL VALIDATION GATE (re-aimed per RV240): confirm OpenHands `[llm]` section semantics in `.openhands/config.toml` — the file this repo ALREADY manages for MCP (the old settings.json gate targeted a file the repo never touches). If `[llm]` is confirmed, OpenHands becomes a structured-file adapter on the existing TOML surface (single active model); env-projection (`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY`) remains fallback and the launch-time key-injection vehicle. Execution is currently a stub — env path stays inert until the bridge is real.
3. PARALLEL VALIDATION GATE: confirm Goose model-provider config path/schema/reload behavior. Current repo only confirms `.goose/config.yaml` for MCP; do not assume a JSON custom-provider file. If unresolved, expose guidance/env projection through a capability recipe and defer structured writer support to MO04/follow-up scope.
4. Pi (structured-file, HOME-SCOPED per repo template): reconcile `providers.<source-id>.models[]` by model id inside the AG-owned provider block, preserve unmanaged providers/models. Shape is repo-verified (baseUrl/api/apiKey/compat/models[] with contextWindow/maxTokens/cost) — see reference doc materialization snippet. Home-dir writes get the same dry-run care as other non-project surfaces; verify project override + reload.
5. OpenCode (structured-file after gate 1): custom provider entry + model map + top-level/default model selection in the unified file; note casing `baseURL` (vs Pi's `baseUrl`) per repo harness shape.
6. OpenHands (after gate 2): structured `[llm]` writer on `.openhands/config.toml` if confirmed, else env-projection recipe only (`openai/<model-id>` LiteLLM prefix).
7. Codex (structured-file, PROJECT-SCOPE PREFERRED per RV240): repo already manages project `.codex/config.toml` for MCP/LSP — verify installed Codex honors `model_providers` there; if yes, model config rides the same project TOML writer with NO consent machinery. User-global `~/.codex/config.toml` is the consent-gated + dry-run fallback only if project scope is ignored. Validate `wire_api` compatibility either way. Materialization snippet in reference doc.
8. Qwen (structured-file): `settings.json` `modelProviders` after path/scope and merge/replacement behavior are verified (no model surface exists in repo yet — MCP is `.mcp.json`, LSP `.lsp.json`).
9. Goose (mechanism TBD after gate 3): implement structured writer only if a safe file contract is verified; otherwise expose guidance/env projection through a capability recipe.
10. Wire each provider's model kind into its YAML via the consolidated ManagedConfigSpec (MO06).
11. Golden tests per adapter preserving unmanaged entries.

## Validation

1. Golden tests for each provider config writer.
2. Roundtrip tests: read existing unmanaged config, apply two managed local models, update one, remove one, preserve unmanaged.
3. Reload/action-needed tests per provider refresh mode.
4. Integration-ish tests using temp project roots only, no real provider launch needed.
5. OpenCode path-unification test proving MCP, LSP, and model entries share the intended file.
6. Goose validation test that either confirms a model config file/schema or keeps the adapter blocked/manual.
7. Run provider adapter test subset.

## Effort & Risk

Complex. OpenCode path mismatch, OpenHands settings schema, and Goose model-provider config shape are prerequisites, not implementation details. Codex user-level config is sensitive (project config ignores provider keys). Do not force env-projection through the reconciler.

## Standards

- arch-standards — §1 keep provider config logic in providers and only use runtime/harness for bootstrap seams; §2 reader/writer/remover refs and support declarations come from provider YAML/registries, not provider branches; §8 user-global write consent failures use canonical errors; §10 OpenCode path unification is one atomic migration across MCP/LSP/model.
- component-creation — adapter support is declared in provider descriptors/YAML and exposed through provider component APIs.
- observability-standards — provider config mutations and blocked/manual outcomes should be visible through redacted model-sync timelines when sync runs.
