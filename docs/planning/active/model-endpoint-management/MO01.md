# Define provider-owned model source & endpoint contract

## Description

Define the provider-owned model source contract: the project-level `model-sources` desired-state shape and how it binds to the consolidated managed-config machinery (MO06), not a new bespoke spec. A model source has a closed two-value source-class enum — `local-endpoint` (individually configured local/custom models, the original model-endpoints shape) and `remote-account` (any keyed external service: frontier vendors like OpenAI/ChatGPT, Anthropic, Google Gemini AND account aggregators like OpenRouter, OpenCode Zen, Qwen portal; AUDiaGentic holds only a key reference and never manages the account). Vendor-vs-aggregator is a descriptive grouping column in the reference doc's mapping table, NEVER a schema class or code branch — connector + model-discovery drive all behavior. Discovery (`static-catalog` | `list-api` | `none`) is what AG knows about a source's models; projection per (agent provider, source) is a separately declared capability: native-key-injection (env or config mechanism; agent enables ALL vendor models, model-filter not applicable), custom-entries (model-filter applies), or none. This item designs the full schema once; MO02/MO03 implement local-endpoint materialization only, MO07 implements remote-account enablement, MO09 verifies the per-provider vendor matrix. Scope stays under providers; agents continue to bind jobs to provider/model only. The full contract + capability matrix + taxonomy lives in docs/reference/PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md — this item points at it rather than restating it.

## Steps

1. Validate current provider config, model catalog, agent profile, recipe, and managed-config (MCP/LSP) ownership flows.
2. Define the canonical project config as `model-sources` (contract-version v1): required `source-class` (local-endpoint | remote-account) and `model-discovery` (static-catalog | list-api | none) enums; for local-endpoint the full endpoint field set (endpoint id, display name, connector, base URL, api-key-ref, model id, context window, max output tokens, capabilities, provider-overrides, default selection); for remote-account connectivity fields (connector, base-url where applicable, api-key-ref, enabled) plus optional `model-filter` (include/exclude glob patterns — applies to custom-entries projection and AG-side alias exposure only; schema description must state it does NOT constrain native key injection). Both enums are closed: a new upstream service is a new mapping-table row, never a new class.
3. Define the CONNECTOR taxonomy as a source/endpoint field (openai-compatible | anthropic | gemini | openrouter | litellm | ollama | native-vendor), replacing the single protocol: openai-compatible. Include connector-specific fields (anthropic version, gemini api-version, openrouter routing prefs / namespaced model-id) — many are FILL until confirmed per agent.
4. Add per-provider capability declarations on the descriptor: `supported-connectors` (custom-entries path) AND `vendor-key-injection` map ((vendor-id) -> {mechanism: env|config, key: env-var-name-or-config-path}) for the native path. Projection targets only agents whose declarations carry the source (native key injection preferred, custom-entries via supported connector as fallback). Values start FILL and are populated from MO09 verification — an undeclared pair projects nothing.
5. Define the model kind as a consumer of the consolidated ManagedConfigSpec from MO06 (config path, reader/writer/remover, format, refresh mode, supports flags) — do NOT add a third *ConfigSpec dataclass.
6. Fix the ownership mapping explicitly: owner_scope = provider id (matches MCP); managed ids — `model-endpoints/<source-id>` (local-endpoint), `model-endpoints/<source-id>/<model-id>` (custom-entries, post-filter), `model-connections/<source-id>` (config-mechanism key injection); env-mechanism key injection is a launch-env contribution with no fragment; define collision behavior for provider-visible names.
7. Apply the DECIDED relationship to default-model, model-aliases, runtime catalogs, and agent profiles (see reference doc 'Relationship to profiles, aliases, and defaults'): agents keep provider/model binding; aliases/defaults resolve against the union of models materialized by enabled sources; disabling a source invalidates its aliases with a canonical VAL error, never a silent fallback. Do not re-open this decision.
8. Keep docs/reference/PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md authoritative for the finalized contract, source-class mapping table, provider×vendor matrix, and connector decisions.

## Effort & Risk

Complex. Main risk is conflating AUDiaGentic provider ids with upstream model provider ids, for example opencode provider vs OpenAI/OpenRouter/OpenAI-compatible backend. Keep terminology explicit and schema names unambiguous.

## Standards

- arch-standards — §1 keep foundation-facing ManagedConfigSpec/connector language domain-neutral; §2 connector taxonomy, endpoints, and supported-connectors must be YAML/JSON-driven, never provider-name branches; §8 use make_error with canonical VAL-MEP-* codes for invalid endpoint/connector data; §10 migrate contract/schema changes atomically with tests.
- component-creation — provider descriptors own component config shape; provider YAML remains the declaration surface for supported connectors and model_config metadata.
