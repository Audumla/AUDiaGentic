# Define provider-owned model endpoint contract

## Description

Create the provider-owned model endpoint management design and contract. This decides where model endpoint state lives, how multiple local/custom models are represented, how aliases/defaults interact with agent profiles, and how provider adapters declare read/write/remove/reload capabilities. Scope must stay under the providers component; agents continue to bind jobs to provider/model only.

## Steps

1. Validate current provider config, model catalog, agent profile, recipe, MCP sync, and fragment ownership flows.
2. Define canonical project config for multiple model endpoints, including endpoint id, display name, protocol, base URL, API key ref, model id, context window, max output tokens, capabilities, provider overrides, and default selection.
3. Add provider descriptor metadata for model config support: config path, reader/writer/remover refs, format, refresh mode, supports flags, auth mode, catalog mode, and config scope.
4. Define managed ownership ids using `model-endpoints/<endpoint-id>` and collision behavior for provider-visible names.
5. Decide relationship to `default-model`, `model-aliases`, runtime catalogs, and agent profiles.
6. Update `docs/reference/PROVIDER_MODEL_ENDPOINT_CAPABILITIES.md` with finalized contract decisions.

Complex. Main risk is conflating AUDiaGentic provider ids with upstream model provider ids, for example opencode provider vs OpenAI/OpenRouter/OpenAI-compatible backend. Keep terminology explicit and schema names unambiguous.
