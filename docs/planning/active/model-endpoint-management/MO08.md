# Add external-service error classification guideline (standards gap)

## Description

Standards gap found during the 2026-07-10 MO critical pass: ARCHITECTURE_STANDARDS §8 fully covers error construction (AudiaGenticError, canonical codes, mandatory error-resolutions.yaml registration, redaction) but no guideline exists for classifying and degrading on failures from EXTERNAL REMOTE SERVICES — exactly what model-source enablement introduces (catalog refresh against vendor/aggregator APIs, connectivity verification). Without a guideline, each adapter will improvise retry/failure behavior. Deliverable: a new §8 subsection (or §8-adjacent section) in docs/standards/ARCHITECTURE_STANDARDS.md plus an OBSERVABILITY_STANDARDS note, then referenced by MO02/MO07.

## Steps

1. Draft the guideline covering: (a) failure classification — transient (unreachable, timeout, 5xx, 429) vs configuration (bad base-url, unsupported wire API) vs authorization (401/403, expired key) vs contract (unparseable/incompatible response); (b) degradation rule — best-effort background operations (catalog refresh, connectivity probes) must degrade to last-known-good/cached state with a warning + action_needed and MUST NOT fail the enclosing sync or reconcile; only explicit user-invoked operations may surface the error as a failure; (c) retry policy — single bounded retry for transient class only, no retry loops, no sleep-loop polling; (d) redaction — never log or embed API keys, Authorization/x-api-key headers, or key-bearing URLs in error details/resolutions (extends existing §8 redaction rule to remote-call context); (e) code convention — remote-service failures use the owning component's CON- prefix with the failure class in details, resolution text names the check to perform (key present, service reachable, plan/entitlement).
2. Add the subsection to docs/standards/ARCHITECTURE_STANDARDS.md following the existing rule-list style; keep it domain-neutral (applies to any remote service, not just model sources).
3. Add a short OBSERVABILITY_STANDARDS entry: degraded-remote-service outcomes emit a redacted timeline/warning event including failure class and staleness of the cached fallback.
4. Cross-reference: MO02 step 8 and MO07 step 3 consume this guideline; verify their wording matches the final text.
