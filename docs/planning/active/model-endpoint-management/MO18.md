# Enable OpenRouter as a managed vendor model source with a free-model slice

## Description

Sponsor direction 2026-07-18. Make OpenRouter a working configured vendor source end-to-end: declared model source with api-key-ref, explicit catalog refresh through the MO12 openrouter connector, a free-tier filter, and materialization of the filtered models into provider configs through MO17's projection path. This is configuration plus evidence plus tests over existing machinery — no new fetcher, cache, family, or store.

## Steps

1. EVIDENCE FIRST (MA19): verify against a live OpenRouter account how free models are marked — ':free' model-id suffix, pricing.prompt=='0', or both — and record a provider capability fact with a versioned anchor. Verify the /models response shape still matches the MO12 connector.
2. Declare an 'openrouter' model source instance (model_source_add path): connector 'openrouter', api-key-ref naming an env reference (never a raw key — MO12 redaction canary applies), include filter for the free slice (evidence-driven glob, expected '*:free'), plus an unfiltered variant behind the same source config if the sponsor wants paid models later (do not build paid-model handling now).
3. Explicit refresh + cached read through the MO17 catalog surface; assert no-network reconcile still holds with the source enabled.
4. Materialize the filtered free models through manage_model_projection into the one currently verified projection provider (Pi). Assert source-scoped managed ids, prune-on-disable, and foreign-entry preservation — all existing engine guarantees, just proven for this source.
5. Do NOT add key injection into harness configs here (successor item), and do NOT add usage/limits reads here (PT01).

## Detailed Solution & Technical Design

MECHANISM ALREADY EXISTS -- this item is config + evidence + tests over already-working machinery, confirmed by reading the code (not just the description's claim):
  - The openrouter fetcher is already registered: components/providers/services/source_catalog.py:153 `_fetch_openrouter(base_url, api_key)` calls the generic `_normalize_openai_models` (OpenAI-shaped /models list), registered at line 163 as `_fetchers.register("openrouter", _fetch_openrouter)`.
  - The glob include/exclude filter is already implemented and pure: `apply_model_filter(models, model_filter)` (source_catalog.py ~line 236-254) -- `model_filter = {"include": [...], "exclude": [...]}`, fnmatch-based, exclude wins, empty include means all, stable-sorted by model-id.
  - `_refresh_from_list_api` (source_catalog.py ~line 273+) reads `source.get("connector", "")`, `source.get("base-url", "")`, `source.get("api-key-ref")` from the source config dict -- these are the exact keys `model_source_add`'s `config` argument must carry.
  - `providers_api.model_source_add(project_root, source_id, config)` (providers_api.py ~line 1279) already exists and works -- it just writes `config` under `sources[source_id]` in the model-sources document, rejecting a duplicate id (use `model_source_update` to modify an existing one).

IMPORTANT: `_normalize_openai_models` (source_catalog.py ~line 130-144) currently extracts only `model-id`, `display-name` (from `name`), and `context-window` (from `context_length`) -- it drops the `pricing` field entirely from OpenRouter's response. This means the ':free' MODEL-ID-SUFFIX filter path (`include: ["*:free"]`) needs ZERO fetcher code changes -- it works purely through `apply_model_filter` against `model-id`, already captured. A `pricing.prompt=='0'` filter, by contrast, WOULD require extending `_normalize_openai_models` to also capture pricing data and extending `apply_model_filter`'s vocabulary beyond glob-on-model-id (a real code change, more risk). Prefer the model-id-suffix filter if step 1's evidence confirms it's a reliable marker -- it's the zero-code-change path this item's own risk note anticipates ('filter is config so a marker change needs no code edit').

EVIDENCE GATE (step 1) CANNOT BE DONE FROM THIS REPO -- it requires a live OpenRouter account/API call. Whoever executes this item must actually hit OpenRouter's /models endpoint (or check current published API docs) and confirm: (a) do free models carry a ':free' suffix in their id, consistently, right now; (b) does the response still match the OpenAI-list shape `_normalize_openai_models` expects (`{"data": [{"id":..., "name":..., "context_length":...}]}`). Record the finding as a dated capability fact (matching this codebase's existing MA19/AS27-style evidence-fact pattern) before writing the source config -- do not assume the suffix convention without checking it live.

2) Explicit refresh (never implicit/reconcile-triggered -- check source_catalog.py's public refresh entry point, likely `refresh_source_catalog(project_root, source_id)` or similar; grep source_catalog.py's __all__ / providers_api.py's refresh_provider_catalog for the exact name before writing the test) followed by a cached read -- assert a second call with no explicit refresh does NOT hit the network (mock/patch the fetcher and assert zero calls).

3) Materialize into Pi via the existing MO17 projection path (manage_model_projection / apply_model_sources per MO17's own notes) -- do not write a new materializer; call the same function MO17's tests already exercise for other sources, just pointed at 'openrouter' as source_id, and assert: (a) resulting Pi model entries carry the free-filtered model-ids only, (b) managed ids are scoped to the 'openrouter' source, (c) disabling the source prunes only those ids and leaves other sources' entries untouched (foreign-entry preservation -- reuse the exact test pattern MO17's own test suite already proves for its other fixtures).

4) Redaction canary test: assert 'OPENROUTER_API_KEY' (the reference name) may appear in config, but no resolved literal key value ever appears in the source-catalog cache file, the timeline (source_catalog.py's `_timeline` helper writes to `.audiagentic/runtime/providers/source-catalog-timeline.jsonl`), or any test snapshot/log.
