# Bind model projection through explicit provider handlers

## Description

Implement the model-projection automation family using MA20 RecipeDefinition and explicit provider+family registration. Preserve model-source CRUD/catalog as separate resource APIs. Model payload/result remain model-specific.

## Steps

1. Characterize model-source CRUD, sync, config-status, reload, MCP callers, result fields, ownership scopes, and tests.
2. Keep model_source_list/add/update/remove/set_enabled as resource APIs. Add/update/remove/set_enabled persist desired state only and return their resource diff/result. Apply/dry_run parameters remain until this item completes — they are the migration target.
3. Remove apply and dry_run parameters from model-source CRUD and migrate providers MCP/tests. Resource preview is not part of v1; add it later only for a proven consumer.
4. Removing a source is resource deletion, not automation prune. Enabling/disabling is resource update. Callers explicitly invoke model projection afterward when external provider state must change.
5. Freeze one model-projection family payload/result and supported plan/apply/prune/status modes under MA16/MA20.
6. Replace sync_provider_models with the model-projection family operation. Delete the public export; the family operation is the only path.
7. Fold list_provider_models_config into model-projection status because it has no independent production consumer.
8. Delete reload_provider_models publicly; apply performs required reload internally and reports reload_required/action_needed only when consumed.
9. Register implementations explicitly through MA20 and delegate ownership/diff/collision/reload to the shared MO06 core.
10. Migrate providers MCP and all projection callers atomically; delete old routes, flags, aliases, and compatibility tests.
11. Rebase downstream MO items and validate resource/automation separation.

## Files

[RESOURCE] model-source CRUD/config store and providers MCP tools
[AUTOMATION] model-projection family, MA20 definitions/registrations, MO06 adapter
[DELETE] sync_provider_models, list_provider_models_config, reload_provider_models public routes; CRUD apply/dry_run flags
[TEST] resource persistence, explicit projection sequencing, modes, ownership, reload, callers, stale names

## Validation

1. CRUD mutates desired state only and accepts no automation mode, apply, or dry_run flag. 2. Resource remove is not prune. 3. Projection uses MA20 with plan/apply/prune/status. 4. Config listing is projection status. 5. Reload is private apply mechanic. 6. Catalog resources remain separate. 7. Explicit registration only. 8. Ownership/collision/reload behavior and caller results pass. 9. No old route or compatibility artifact.

## Effort & Risk

Complex boundary migration. Main risks: cloning reconciliation, confusing the common internal RecipeDefinition with a universal public payload/status taxonomy, or letting descriptive config enable writers. Keep model services neutral, handlers provider-owned, and registration explicit.

- Architecture Guidelines: Provider Platform API; Writing External Artifacts; Lazy Initialization and Discovery; Error, Logging, and Redaction Practice.
- Observability Standards: redacted timelines for durable provider-config mutations.
