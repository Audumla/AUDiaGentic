# Bind model projection through explicit provider handlers

## Description

Preserve neutral model-source CRUD/catalog work and implement provider model projection behind providers_api semantic modes and explicit provider-owned handlers. Model payload remains model-specific; no foundation capability types or universal request envelope. Provider knowledge config documents support/evidence but cannot register handlers.

## Steps

1. Inventory retain/rework/delete: keep neutral model-source CRUD/materialization/catalog/status and shared managed ownership; identify direct provider mutation paths.
2. Define minimal model desired-state payload/results from current callers; public operation mode is `plan|apply|prune|status`. Explicitly register provider automation only where implemented.
3. Move sync/list/reload operations behind provider adapters. Requesters call providers_api, never serializers/sync internals.
4. Provider adapter maps semantic modes to MODEL_CONFIG recipe/MO06 reconciliation; renderer/config/reload/registry stay provider-owned. No universal CapabilityRecord or second registry.
5. Preserve public results through thin adapter; promote collision/reload fields only if callers need structured access.
6. Delete direct projection wiring; test plan/status/apply/prune/collision/disabled-provider lifecycle and absent-handler behavior.
7. Rebase downstream MO items: documented blocked/manual facts need no runtime recipe unless a current status API consumes them.

## Files

[COMPONENT:providers] neutral model desired-state services and provider-owned projection handlers
[PROVIDERS composition] explicit `(provider_id, model-projection)` registrations only for implemented automation
[FOUNDATION reuse] MO06 managed ownership/atomic primitives and MA17 minimal request/result
[CONFIG:providers] rich model capability/evidence/action-needed facts; not runtime registration
[TEST] ownership, collision, dry-run, absent-handler, boundary, and catalog-non-authority tests

## Validation

1. Projection occurs only through explicit provider registration. 2. Provider config cannot enable runtime projection. 3. Minimal payload/result fields have current consumers. 4. Public calls use only plan/apply/prune/status; MODEL_CONFIG methods remain internal. 5. No MA16 taxonomy/manifestation/transport dependency. 6. Ownership/dry-run/collision lifecycle remains correct. 7. Provider-specific rendering stays provider-owned.

## Effort & Risk

Complex boundary migration. Main risks: cloning reconciliation, inventing universal recipe/status taxonomies, or letting descriptive config enable writers. Keep model service neutral, handlers provider-owned, registration explicit.
