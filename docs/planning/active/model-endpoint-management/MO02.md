## Description

Rebased migration item. Preserve validated neutral model-source desired-state/config/catalog work, but reimplement provider model projection as a providers-owned capability handler declared in MA16 catalog and invoked only through MA17 gateway. MO02 must not retain a parallel recipe/gateway/config dialect or expose requester-facing direct provider mutation path.

## Steps

1. Inventory current MO02 code and classify retain/rework/delete: retain only neutral model-source schema/config CRUD, neutral MaterializedModelEntry, validated catalog/status primitives, and shared managed-config registry use; identify direct provider sync/recipe/timeline paths to rewire.
2. After MA11/MA16/MA17, declare `model-projection` provider capability in provider catalog with operations plan/apply/prune/status, neutral payload, support state, evidence, ownership, and agent manifestation. Provider handler owns renderer/config/reload/registry behavior.
3. Move sync/list/reload operations behind gateway handler. Existing provider API/MCP tools mutate desired model-sources only then request gateway reconciliation; no requester or MO07 code directly calls model serializer/sync handler.
4. Keep services/models neutral: materialization and provider-neutral desired payload only. Move provider handler binding/renderer/config path mechanics to provider-owned catalog/adapter declaration. No second recipe registry.
5. Rewire reconcile/status/timeline to handler results; preserve existing public response fields through thin boundary adapter only.
6. Delete superseded direct projection/recipe wiring and add import/vocabulary/duplicate guards. Re-run dry-run/apply/prune/collision/disabled-provider lifecycle tests.
7. Rebase MO03/MO04/MO07/MO13/MO14 dependencies onto this handler; unverified support remains blocked/manual.
