# Bind model projection through explicit provider handlers

## Description

Implement the MA16 model-projection family using explicit provider+family registration. Preserve model-source CRUD/catalog as separate resource management. Model payload remains model-specific; provider knowledge is evidence, not execution authority.

## Steps

1. Inventory model-source resource CRUD/catalog/status separately from provider-specific projection.
2. Freeze model-projection payload and consumed results under MA16; do not alter resource APIs merely to match operation modes.
3. Implement model projection with supported plan/apply/prune/status modes and explicit provider+family registration.
4. Delegate managed ownership/diff/collision/reload to MO06 and retain provider-specific rendering.
5. Migrate all projection callers and delete direct sync/reconcile routes, aliases, and compatibility tests in the same change.
6. Preserve only caller-consumed results; absent registration means unsupported/no automation.
7. Rebase downstream MO items; documented blocked facts need no runtime object.

## Files

[COMPONENT:providers] neutral model desired-state services and provider-owned projection handlers
[PROVIDERS composition] explicit `(provider_id, model-projection)` registrations only for implemented automation
[FOUNDATION reuse] MO06 managed ownership/atomic primitives and MA17 minimal request/result
[CONFIG:providers] rich model capability/evidence/action-needed facts; not runtime registration
[TEST] ownership, collision, dry-run, absent-handler, boundary, and catalog-non-authority tests

## Validation

1. Resource CRUD/catalog stays distinct from projection. 2. Projection executes only through explicit registration. 3. Config cannot enable behavior. 4. Payload/results are model-specific and caller-derived. 5. Non-mutation, scoped prune, collision/reload proven. 6. No universal taxonomy/request or old compatibility route. 7. Rendering stays provider-owned.

## Effort & Risk

Complex boundary migration. Main risks: cloning reconciliation, inventing universal recipe/status taxonomies, or letting descriptive config enable writers. Keep model service neutral, handlers provider-owned, registration explicit.

## Standards

- Architecture Standards: Dependency Boundaries; Approved cross-component APIs; Extensions and Configuration; Public Contracts and Safety; Ownership and Abstraction.
- Architecture Guidelines: Provider Platform API; Writing External Artifacts; Lazy Initialization and Discovery; Error, Logging, and Redaction Practice.
- Observability Standards: redacted timelines for durable provider-config mutations.
