# Bind model projection through explicit provider handlers

## Description

Preserve neutral model-source CRUD/catalog work and implement provider model projection inside providers behind its public capability gateway and explicit provider-owned handlers. No foundation capability types. Provider capability config documents support/evidence but cannot register handlers.

## Steps

1. Inventory retain/rework/delete: keep neutral model-source CRUD/materialization/catalog/status and shared managed ownership; identify direct provider mutation paths.
2. Define minimal `model-projection` request payload from current callers. Explicitly register provider handlers only where automation exists. Provider capability config separately records support, evidence, limitations, and action-needed guidance.
3. Move sync/list/reload operations behind registered handlers. No requester calls serializers/sync implementations directly.
4. Keep services/models neutral. Provider handler owns renderer/config/reload/registry and validates its payload. No universal CapabilityRecord or second recipe registry.
5. Preserve public results through thin adapter.
6. Delete direct projection wiring; test dry-run/apply/prune/collision/disabled-provider lifecycle and absent-handler behavior.
7. Rebase downstream MO items: documented blocked/manual facts need no NoAutomation runtime recipe unless a current status API explicitly consumes one.

## Files

[COMPONENT:providers] neutral model desired-state services and provider-owned projection handlers
[PROVIDERS composition] explicit `(provider_id, model-projection)` registrations only for implemented automation
[FOUNDATION reuse] MO06 managed ownership/atomic primitives and MA17 minimal request/result
[CONFIG:providers] rich model capability/evidence/action-needed facts; not runtime registration
[TEST] ownership, collision, dry-run, absent-handler, boundary, and catalog-non-authority tests

## Validation

1. Projection occurs only through explicit provider handler registration. 2. Provider capability config cannot enable runtime projection. 3. Minimal payload/result fields have current consumers. 4. No MA16 taxonomy/manifestation/transport dependency. 5. Ownership/dry-run/collision lifecycle remains correct. 6. Provider-specific rendering stays provider-owned.

## Effort & Risk

Complex boundary migration. Main risks: cloning reconciliation, inventing universal recipe/status taxonomies, or letting descriptive config enable writers. Keep model service neutral, handlers provider-owned, registration explicit.

## Standards

- arch-standards — §1 providers may consume foundation sync primitives but foundation names stay domain-neutral; §2 connector/provider dispatch must be registry/YAML driven with no if/elif on provider_id or connector; §8 use canonical VAL-MEP-*/CON-MEP-* errors and keep remediation in error-resolutions.yaml; §9 module logger and no secret logging; §10 no cloned reconcile loop or parallel model-sync API; §11 use shared lazy registry utility.
- component-creation — provider component owns downstream projection/status surfaces; providers MCP exposure waits until service tests pass.
- observability-standards — model sync mutates durable provider config, so emit redacted timeline events for create/update/remove/collision/reload outcomes.
