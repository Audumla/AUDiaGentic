# Cross-harness model availability overview: one read-only introspection surface

## Description

Sponsor direction 2026-07-18: 'introspect the providers and then the models exposed'. Compose the reads that already exist into one coherent overview instead of forcing tool-by-tool assembly: enabled providers/harnesses, their execution + model-projection capability state, configured model sources (local endpoints and vendors) with enablement, cached catalog contents (with freshness), and which models are currently materialized into which harness configs. Strictly read-only, derived entirely from existing stores — no new persistence, no network (cached catalog data only), no scheduling logic.

## Steps

1. Inventory the existing reads to compose: list_providers, describe_provider, list_provider_models, model_source_list, MO17's catalog read, projection ownership registry contents, and MA19 capability facts (including blocked-evidence facts so the overview honestly shows WHY a harness has no models).
2. Define one typed overview result (frozen dataclass + schema per the locked typed-contract rule): sources → catalog summary (count, freshness, filter) → materialized-to (provider, managed-id count) → provider execution/enablement state. Include blocked reasons from evidence facts verbatim.
3. Implement as one providers_api read composing existing service reads; expose one providers-MCP tool. AR25: the MCP tool translates and serializes only.
4. Do NOT include usage/limits (PT01 owns; leave a typed placeholder field only if PT01's contract already names it — otherwise nothing), and do NOT read live networks.
5. Tests: overview against fixtures with a vendor source (fresh/stale/missing cache), a local endpoint, a blocked provider, and a disabled source.

## Detailed Solution & Technical Design

PURE COMPOSITION -- every read this item needs already exists in providers_api.py, confirmed by reading their signatures:
  - `list_providers(project_root) -> dict` (providers_api.py:700) -- delegates to services/status.py::build_provider_status(include_probes=False); enabled/installed providers + status.
  - `describe_provider(project_root, provider_id)` -- (grep providers_api.py for exact line; known from this session's HA04 work to include `descriptor['launches']` = {profile_name: {interaction:[...], observability:[...]}}, surfaced ~providers_api.py:941) -- execution + launch capability state.
  - `list_provider_models(project_root, provider_id) -> dict` (providers_api.py:780) -- reads the cached catalog only (docstring: 'Read one provider catalog without fetching or writing durable state'); explicitly does NOT hit network -- exactly the read-only property this item requires.
  - `model_source_list(project_root) -> dict` (providers_api.py:1049) -- reads services/model_source_config.py::load_model_sources; per-source class/display-name/vendor-id/enabled state.
  - MO17's catalog freshness/vendor-grouping read (MO17 is COMPLETED -- grep providers_api.py and services/provider_catalog.py for the exact function MO17 added; its own file list names services/source_catalog.py, services/models.py as the landing spot) -- reuse, do not reimplement freshness computation.
  - Managed-projection ownership registry contents -- the same registry model_source_add/MO17's projection reads to compute 'source-scoped managed ids' (grep for ManagedFragmentRegistry usage in services/models.py or the model-projection family module) -- reuse its read path, don't hand-roll a second traversal of the same underlying store.
  - MA19/AS27-style capability facts, INCLUDING blocked ones -- for providers this session's work touched, the equivalent evidence source is harness_observability_inventory.py's `get_all_harness_surface_facts()` (components/providers/services/harness_observability_inventory.py) for observability, but MO20 needs the MODEL-capability equivalent -- grep for an MA19 fact-store module (likely components/providers/services/ or contracts/) rather than assuming it's the same module as AS27's observability one; they are almost certainly separate stores (different domain -- model execution vs session observability).

DESIGN: define one frozen dataclass (matching this codebase's locked typed-contract rule -- see MA19-family contracts, or MO17's ModelProjectionRequest as the pattern to mirror) shaped roughly:
  ProviderModelOverview:
    providers: list[ProviderOverviewRow]  # from list_providers + describe_provider per id
    sources: list[SourceOverviewRow]      # from model_source_list, each with its catalog freshness/count from the MO17 read
    materialized: list[MaterializedRow]   # provider_id, source_id, managed_id count, from the projection ownership registry read
  Each row is itself a frozen dataclass, not a raw dict -- follow the MA16/typed-contract discipline already enforced everywhere else in providers_api.py (see the 'Universal internal recipe schema' framing in docs/reference/PROVIDER_CAPABILITY_REFERENCE/model/capability-operation-contract.md for the general pattern this codebase expects, even though that doc's own automation-family schema is a different, unrelated layer -- confirmed by this session's HA04 audit).

IMPLEMENTATION: one new providers_api.py function (e.g. `model_availability_overview(project_root) -> dict`) that calls the reads above and assembles the typed result; one new providers_mcp.py tool exposing it (AR25 boundary: the MCP tool layer only translates/serializes the already-composed typed result, it does not itself call multiple services -- confirmed pattern from every other tool in that file, read 2-3 existing tool wrappers in providers_mcp.py before writing this one to match the exact translate-only shape).

DO NOT touch: usage/limits (explicitly PT01's territory per this item's own text -- leave no field for it unless PT01's contract already names one), any network call (this item is cache-only), any new persistence (compose existing reads only).
