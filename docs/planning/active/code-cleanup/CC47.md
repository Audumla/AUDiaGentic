# Unify error message schema — centralize messages + resolutions in errors.yaml

## Description

Externalize all hardcoded error `message` strings from ~312 call sites into per-component YAML files. Rename `error-resolutions.yaml` to `errors.yaml` with a structured schema holding both `message` and `resolution` per error code. Currently, the resolution text lives in YAML but the developer-facing `message` is hardcoded at every make_error / make_error_factory call site. This creates maintenance drift and violates the single-source-of-truth principle.

NOTE: Based on review RV970, three blocker issues must be resolved before implementation:
1. Code-to-message cardinality: Some error codes are used with multiple different messages (e.g., VAL-PCAP-010)
2. Phase 1 message requirement: Keeping message required undermines centralization goals
3. Bootstrap ordering: Error catalog loads after components that may need to raise errors during init

See review RV970 for detailed findings and recommendations.

## Detailed Solution & Technical Design

CC47 Revised Implementation Plan

Key revisions from original plan:

1. TEMPLATES SUPPORTED: Messages use catalog-owned templates with named parameters (e.g., `message: "Provider {provider_id!r} failed"`). Rendered messages may vary through named template values, but prose ownership stays in errors.yaml.

2. REVISED INVARIANT: One code → one canonical message template. Different values → template parameters. Different sentence semantics/invariants → different error codes.

3. TEMPLATE VALIDATION: Templates validated at catalog load time (syntax, field names, no traversal/indexing). Missing parameters raise ErrorTemplateRenderError immediately.

4. BOOTSTRAP ERROR DOMAIN: General BootstrapError hierarchy (not just ErrorCatalogLoadError). Compiled-in BOOT-* registry. Zero dependencies on errors.yaml. Two explicit domains: bootstrap (BOOT-*) before catalog ready, runtime (VAL-*/RES-*/EXT-*) after.

5. OPTION A API: Same kwargs serve both template rendering and details. Catalog knows which keys are message parameters.

6. REVISED ErrorDefinition: Uses message_template field, cached_property for message_parameters, render_message(values) method.

7. REVISED make_error: message=None is transitional/override; normal path renders template from details.

Implementation phases:
- Phase 0: Cardinality audit (revised rule: different values → params, different semantics → codes)
- Phase 1: ErrorDefinition (templates) + ErrorCatalog + BootstrapError + optional APIs
- Phase 2: Populate errors.yaml catalogs with validated templates
- Phase 3: Bootstrap barrier (catalog before components)
- Phase 4: Migrate static call sites

## Detailed Implementation Plan Addressing Blocker Issues

Based on review RV970, this plan resolves the three blocker issues before proceeding with the error message unification.

### Blocker Resolution Strategy

**Blocker 1: Code-to-Message Cardinality Issue**
*Problem:* Schema assumes one error code → one message, but codes like VAL-PCAP-010 are used with multiple different static messages.

*Resolution:*
1. **Pre-migration audit phase:** Analyze every error code to determine its message pattern:
   - Exactly one static message
   - Several static messages (same code, different messages)
   - Static + dynamic messages
   - Only dynamic messages
2. **Apply resolution policy:**
   - **Split codes** when distinct messages describe genuinely distinct failures (create new error codes)
   - **Consolidate with details** when messages represent same failure with contextual variation:
     - Keep one stable canonical message in errors.yaml
     - Move variable data to `details` field
   - **Retain explicit override** only where neither approach is reasonable
3. **Update all call sites** to reflect the new code/message relationships

**Blocker 2: Phase 1 Message Requirement**
*Problem:* Keeping message as required in Phase 1 undermines centralization goals.

*Resolution:* Move optional/canonical-message resolution to Phase 1:
1. **Revise API constructors:**
   - `make_error(prefix, component, number, kind)` → resolves message automatically from errors.yaml
   - `_registry_error(number)` → works without explicit message
   - Direct construction: `AudiaGenticError(code="VAL-PPARSE-001", kind="agent-jobs")` or new `error_from_code(...)`
2. **Make message parameter optional** in all error constructors
3. **Explicit message= means intentional override**, not normal way to obtain catalog message
4. **Update all call sites** to use the new message-less construction where appropriate

**Blocker 3: Bootstrap Ordering**
*Problem:* Error catalog loads after components that may need to raise errors during initialization.

*Resolution:* Implement strict bootstrap sequence:
1. **Early catalog loading:** Load and validate error catalog BEFORE normal component parsing
2. **Strict transactional loading:**
   - Parse every catalog
   - Validate complete entries/codes/ownership
   - Validate collisions
   - Commit new registry atomically
   - Mark registry loaded
3. **Handle boot-time errors:** Present-but-malformed errors.yaml → startup/configuration failure (not warning)
4. **Missing errors.yaml:** Legal for components with no registered errors

## New YAML Schema

Replace flat `code: resolution` with hierarchical:

```yaml
# errors.yaml — per-component error catalog
# Each error code maps to its message and resolution text.
VAL-COMPLETE-001:
  message: "provider completion data failed schema validation"
  resolution: "The provider completion data failed schema validation. Check the required fields in the completion."
```

- `message` (required): Short developer-facing description. Lowercase, no trailing period.
- `resolution` (required): User/agent-facing remediation guidance. Sentence case, trailing period.

Backward-compat: loader also accepts flat `code: string` (treats string as resolution, generates message from code). This lets incremental migration happen.

## Registry Changes (errors.py)

Replace `_ERROR_RESOLUTIONS: dict[str, str]` with:
```python
_ERROR_ENTRIES: dict[str, dict[str, str]] = {}  # code -> {message, resolution}
```

Add functions:
- `register_error_entry(code, message, resolution)`
- `get_error_resolution(code) -> str | None` (backward compat, returns resolution)
- `get_error_message(code) -> str` (returns message, falls back to code)

Update `_error_code_blocker` to include the message from YAML when available:
```python
def _error_code_blocker(code: str) -> None:
```
