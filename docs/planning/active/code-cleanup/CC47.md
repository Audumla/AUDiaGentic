# Unify error message schema — centralize messages + resolutions in errors.yaml

## Description

Externalize all hardcoded error `message` strings from ~312 call sites into per-component YAML files. Rename `error-resolutions.yaml` to `errors.yaml` with a structured schema holding both `message` and `resolution` per error code. Currently, the resolution text lives in YAML but the developer-facing `message` is hardcoded at every make_error / make_error_factory call site. This creates maintenance drift and violates the single-source-of-truth principle.

## Current State
- 11 `error-resolutions.yaml` files with flat `code: resolution` mapping
- ~312 hardcoded error message strings across ~70 source files
  - ~80 sites in foundation, ~160 in components, ~40 in runtime/rig, 1 in commands
  - ~205 static messages (fully externalizable), ~107 f-strings (deferred to Phase 2)
- 57 `make_error_factory` definitions, ~100 `make_error()` inline calls, ~90 `AudiaGenticError()` direct constructors, ~25 rig error factory calls
- `CREATING_A_COMPONENT.md` lines 49-50 currently say 'do not overload error-resolutions.yaml with messages' — this will be updated
- `get_error_message()` exists but returns the raw code string for unregistered codes
- 67 references to `error-resolutions.yaml` across code, tests, docs, and planning files

## Scope
- Errors only (not action_needed, status, or reason fields on result dataclasses)
- Phase 1: schema + loader + static message migration
- Phase 2 (future): optional message param in make_error/make_error_factory for dynamic f-strings

## Detailed Solution & Technical Design

## New YAML Schema

Replace flat `code: resolution` with hierarchical:

```yaml
# errors.yaml — per-component error catalog
# Each error code maps to its message and resolution text.
VAL-COMPLETE-001:
  message: "provider completion data failed schema validation"
  resolution: "The provider completion data failed schema validation. Check the required fields in the completion."
```

- `message` (required): Short developer-facing description. Lowercase, no trailing period.
- `resolution` (required): User/agent-facing remediation guidance. Sentence case, trailing period.

Backward-compat: loader also accepts flat `code: string` (treats string as resolution, generates message from code). This lets incremental migration happen.

## Registry Changes (errors.py)

Replace `_ERROR_RESOLUTIONS: dict[str, str]` with:
```python
_ERROR_ENTRIES: dict[str, dict[str, str]] = {}  # code -> {message, resolution}
```

Add functions:
- `register_error_entry(code, message, resolution)`
- `get_error_resolution(code) -> str | None` (backward compat, returns resolution)
- `get_error_message(code) -> str` (returns message, falls back to code)

Update `_error_code_blocker` to include the message from YAML when available:
```python
def _error_code_blocker(code: str) -> None:
    if code in _ERROR_ENTRIES:
        return
    # ... existing blocking logic, but now with message from YAML
    entry = _ERROR_ENTRIES.get(code, {})
    msg = entry.get("message", code) if isinstance(entry, dict) else code
    raise ValueError(
        f"Error code {code!r} is not registered in any component's errors.yaml. "
        f"Message: {msg}. "
        f"Before use, add it to src/audiagentic/config/components/<component>/errors.yaml. "
        f"See ARCHITECTURE_STANDARDS.md §8."
    )
```

## Loader Changes (error_resolutions.py)

1. Rename file search from `error-resolutions.yaml` to `errors.yaml`
2. Accept both old flat format (backward compat) and new hierarchical format
3. Load both message and resolution into `_ERROR_ENTRIES`
4. Keep `register_error_resolution()` backward-compatible by wrapping `register_error_entry()`

For ~107 f-string messages: leave as-is in Phase 1. Design a future pattern (template interpolation via get_error_message(code, **ctx)).

## Code Samples & Guidance

### Error Construction Patterns Found in the Codebase

**Pattern 1: `make_error_factory` + factory call (~57 factories, ~190 call sites)**
```python
# Definition
_registry_error = make_error_factory("VAL", "REG", "registry")
# Usage
raise _registry_error(1, "registry is unreadable")
```
→ Code: `VAL-REG-001`. Message: `"registry is unreadable"`.

**Pattern 2: `make_error()` inline (~100 call sites)**
```python
raise make_error(prefix="CFG", component="MCP", number=2, kind="mcp",
                 message="MCP module does not expose a callable main().")
```
→ Code: `CFG-MCP-002`. Message: `"MCP module does not expose a callable main()."`.

**Pattern 3: `AudiaGenticError()` direct constructor (~90 call sites)**
```python
raise AudiaGenticError(code="VAL-PPARSE-001", kind="agent-jobs",
                       message="boolean directive must be true or false")
```
→ Code: `VAL-PPARSE-001`. Message: `"boolean directive must be true or false"`.

**Pattern 4: Rig error factories (~25 call sites)**
```python
raise make_rig_http_error("EXT", 1, f"Rig health failed: {url} -> HTTP {status}")
raise make_rig_resolution_error("RES", 5, f"Model not found: {candidate}")
```
→ Codes: `EXT-RIGHTEPT-1`, `RES-RIGRES-5`.

**Pattern 5: Custom `_error()` helpers (agents contracts)**
```python
# _worker_protocol_validation.py
def protocol_error(code, message):
    return AudiaGenticError(code=code, kind="agents", message=message)

raise protocol_error("VAL-AGW-074", "worker protocol envelope fields do not match")
```

| Type | Count | Examples |

### New errors.yaml Schema Example

```yaml
# config/components/agents/errors.yaml
VAL-AGW-001:
  message: "mode must be 'async' or 'blocking'"
  resolution: "Provide mode as 'async' or 'blocking' in the gateway request."

VAL-AGW-007:
  message: "prompt_body is required and must not be empty"
  resolution: "Include a non-empty prompt_body in the gateway request."

CON-AGW-001:
  message: "illegal gateway request state transition"
  resolution: "The request cannot transition to the requested state from its current state."
```

### Backward-Compat Loader Pattern

```python
# error_resolutions.py — new loader accepts both formats
def _parse_entry(code: str, raw) -> dict[str, str]:
    if isinstance(raw, str):
        # Old flat format: code: "resolution string"
        return {"message": code, "resolution": raw}
    # New hierarchical format
    return {"message": raw["message"], "resolution": raw["resolution"]}
```

## Notes

Key design decision: rename `error-resolutions.yaml` to `errors.yaml` because the file now holds both message and resolution — 'error-resolutions' no longer describes the content. The hierarchical schema is cleaner than flat strings and makes the relationship between message and resolution explicit.

The `CREATING_A_COMPONENT.md` line 49-50 currently says 'do not use error-resolutions.yaml as both the raised message source and the remediation source' — this was written before the user requested unification. The new schema resolves this by making the file explicitly structured for both purposes.

Phase 2 (future item): make `message` parameter optional in `make_error()` / `make_error_factory()`. When omitted, look up from YAML by constructed code. This eliminates the remaining ~107 f-string messages that need interpolation at the call site.
