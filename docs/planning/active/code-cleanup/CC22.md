# COMP-003 — Generate harness tool catalog from mcp-server declarations

## Description

Component descriptors duplicate their tool catalog. The `harness-instructions` 'What you can do' section (see planning.yaml, coding-lsp.yaml) re-lists each MCP server's `direct-tools` and a one-line description that already exist on the `mcp-servers[].direct-tools` / `tool-descriptions` / `instructions` fields. The two are hand-synced and drift (a tool added to direct-tools but not the harness list, or vice versa). Generate the 'What you can do' catalog from the mcp-server declarations so there is a single source of truth.

Scope/caution: harness-instructions also carry free-form operating doctrine that is NOT derivable from tool lists (e.g. coding-lsp's notes about generated lsp.json, install gating). The generator must only own the per-tool catalog lines; hand-written doctrine must remain authorable. Design a clear seam between generated and authored content.

## Steps

1. Inventory how harness-instructions are currently consumed/rendered (find the surface/projection code that emits the harness prompt from descriptors). Identify where the 'What you can do' section is assembled.
2. Define the generation rule: for each mcp-server with direct-tools, emit '### <server-name>' followed by '- `<tool>` — <description>' lines, sourcing the description from tool-descriptions[tool] (fallback: first line of instructions, else the server description).
3. Choose the authoring model. Option A: drop the hand-written catalog blocks; generator injects them. Option B: keep a marker (e.g. a `generated: tool-catalog` section type) the renderer fills. Prefer A if free-form doctrine can live in a separate, clearly-authored harness-instruction section.
4. Implement the generator in the descriptor→harness rendering path (config-over-code: no per-component branching).
5. Migrate planning.yaml and coding-lsp.yaml (and any others with a 'What you can do' tool list) to remove the duplicated catalog, keeping only authored doctrine.
6. Snapshot the rendered harness output before/after to prove byte-for-byte (or intentional-diff-only) equivalence.
7. Update docs/CREATING_A_COMPONENT.md §7 to say the tool catalog is generated and authors only write doctrine + per-tool descriptions on the mcp-server decl.

## Validation

1. Before/after snapshot of the generated harness prompt for planning and coding-lsp: differences must be intentional only (e.g. ordering/whitespace) — review each.
2. Add a test asserting every direct-tool appears in the generated catalog (drift guard) and no orphan catalog entry references a non-existent tool.
3. Full suite green.
4. Confirm propagate semantics preserved — generated catalog respects each server's propagate (audiagentic vs providers).

## Effort & Risk

Complex. Risk: harness-instructions mix generated catalog with authored doctrine; a naive replacement loses doctrine. Risk: propagate filtering must be honored per server. Mitigate with the generated/authored seam (step 3) and before/after prompt snapshots. Lowest-priority of the three — do CC20 and CC21 first.
