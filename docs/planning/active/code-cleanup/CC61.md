# Declare typed return cores for MCP tools (opportunistic, not a migration)

## Description

Give MCP tools a real, load-bearing return shape instead of an untyped `dict`, so a caller-breaking change (a renamed key, a dropped field, an error returned where domain data belongs) fails at the boundary instead of reaching the client silently.

**Verified baseline (mcp==1.27.0, pyproject.toml:18).** Every one of the 143 `@mcp.tool()` functions across 15 registered servers returns an untyped container — counted by AST walk of every `*_mcp.py` return annotation: 78 `dict[str, Any]`, 48 bare `dict`, 6 `list[dict[str, Any]]`, 5 bare `list`, 3 error-dict unions, 1 `dict[str, list[...]]`, 1 three-way union, 1 `str`. Probed against the installed FastMCP: bare `dict`/`list` produce **no `outputSchema` at all**; `dict[str, Any]` produces `{"type": "object", "additionalProperties": true}`, which asserts nothing. Zero of the 143 tools declare a single field. FastMCP's `FuncMetadata.convert_result()` already calls `output_model.model_validate(result)` on every structured return — boundary validation does not need to be built, it needs to be *enabled* by giving a tool a real return type.

**What this item is not.** The original proposal here was a bespoke `{contract-version, ok, data, errors}` envelope plus a `wrap_response()` helper. Withdrawn — see RV931 and Rejected Alternatives in Notes. MCP already carries the equivalent of every field in that envelope natively (`structuredContent`/`outputSchema` for `data`, `isError` for `ok`, session-level protocol version for `contract-version`), and wrapping an untyped dict in an envelope still advertises an empty schema, so it doesn't fix the actual defect.

**What the schema is for.** A safety mechanism, not a committed foundational surface. Its job is to catch a tool silently returning the wrong shape. It is not a frozen public contract — no versioning, no migration obligation, no requirement to reach all 143 tools. That framing is why this item's scope is opportunistic rather than a campaign (RV933).

**Depends on CC62.** A tool with a declared return type that still returns an error-shaped dict fails `model_validate` and surfaces a pydantic ValidationError instead of the real error. CC62 ("Unify MCP tool error path") removes the error-dict return convention; this item cannot safely start on a given tool until that tool's server no longer returns error dicts. CC62 needs nothing from this item.

## Steps

The governing asymmetry: **adding is free, requiring is forever.** Extras pass through untouched and the schema is a safety net, so a key can be added later without breaking anything. Declaring a key required is the only irreversible move. Every rule below follows from that.

- 1. Declare **only load-bearing keys** as required — the identity and addressing fields a caller needs to act on the response (e.g. `id`, `path`, `state`). The test is "is the caller broken without this?", **not** "is this always present?". A plan item's `work`/`skill` fields are always emitted, even as `""`, but nothing depends on them — requiring them would turn a harmless frontmatter change into a boundary failure.
- 2. Everything else rides as an extra, undeclared. When unsure, leave it out — under-declaring costs nothing later (adding is free); over-declaring breaks a working tool immediately.
- 3. Reserve `warnings` as the one shared optional key for non-blocking diagnostics on an otherwise successful result. Never required; omit the key entirely rather than emitting `[]`. Keep elements loose (a string, or a small mapping) — no `Warning` class hierarchy. What's being standardized is the *name*, so components stop each inventing `issues` / `problems` / `soft_errors`. Blocking conditions raise (CC62); non-blocking ones ride in `warnings`. That split is the whole partial-success story — there is no separate partial-success slice.
- 4. Use the functional `TypedDict("Name", {...})` form wherever payload keys are hyphenated — `created-by`, `review-of`, `contract-version` are not valid Python identifiers, and the `class` form of `TypedDict` cannot express them.
- 5. Where a payload legitimately carries config- or content-driven extras (planning items/reviews, provider descriptors), declare the core on a pydantic model with `model_config = ConfigDict(extra="allow")` instead of a closed `TypedDict`. Do not enumerate a config-owned vocabulary in Python to force closure (§2).
- 6. Derive each core from the producing API function's actual return construction — not its docstring, not its callers, not what "seems" always present.
- 7. **Scope: opportunistic, not a migration.** Declare a core when a tool is touched for other reasons, plus one deliberate pass over the four servers live in this repo's `.mcp.json` (`ag-planning`, `ag-ledger`, `ag-agents-gateway`, `ag-lsp`), where a wrong shape reaches running agents today. There is no requirement to reach all 143 tools — completeness is a property of contracts, and this is a safety net.
- 8. Reuse one shared `Page` core for the `{items, total, returned, offset, limit, has_more}` shape already repeated by `plan_list_items`, `plan_list_reviews`, and the gateway list tools — ≥2 independent consumers meets §3's bar for a shared type. Do not generalize beyond this one case.
- 9. Guard with one assertion, applied only to tools that have declared a core: a non-empty `required` list. Do not assert on `additionalProperties` (open extras are legitimate), and do not fail a tool for not having declared a core yet (opportunistic scope, not a checklist).

## Detailed Solution & Technical Design

### Governing constraint: §8 Protocol Adapter Boundaries

MCP modules are inbound protocol adapters. "Core and API modules must not import MCP/FastMCP or own MCP-specific constants." A `TypedDict` or a plain pydantic model is not an MCP import, so declaring one in a component's own contracts module does not violate this — the MCP tool module imports it purely to annotate a return.

### Where cores live

Follows §1 and §3:

- **Component-owned.** Each component declares its own result cores next to the API that produces them, e.g. `components/planning/contracts/results.py`. Not the MCP module itself, and not shared across components.
- **Not foundation.** Parking 143 domain result cores in `foundation/mcp` would make foundation domain-aware, violating §1's "Foundation names... are domain-neutral."
- **Not `schema_registry.py`.** That registry (`foundation/contracts/schema_registry.py`, `SCHEMA_DIR`, `validate_with_schema()`) validates *durable records* before persistence — a committed surface with a migration obligation, currently backing ~13 domain record types (job records, change events, provider configs, etc.). Tool returns are transport safety nets validated by pydantic at egress, a different owner, lifecycle, and validator. §3 unifies types only when both match — they don't here.
- **One narrow shared shape is justified:** the pagination core, because it already has ≥2 independent consumers with identical semantics.

### Why required means load-bearing, not always-present

A field can be always-emitted and still not load-bearing — `work`/`skill` on a plan item are always present as `""` but nothing in any caller depends on them. Declaring them required only creates a way for a harmless config or frontmatter change to break a working tool at the schema boundary. The only question that should decide `required` is whether a caller is broken without the key, not whether the field happens to always be there today.

### Config-driven payloads cannot be closed, and should not be

Planning is the concrete case: `FRONTMATTER_FIELDS`, `ITEM_SECTION_HEADING`, and `METADATA_KEYS` are loaded from `planning.yaml` at import time (`components/planning/item_store.py:83-111`), and `build_item_body` accepts arbitrary `custom_headings`, so a plan item can carry any section someone wrote a markdown heading for — CC47 returns `new_yaml_schema`/`file_rename_plan`, CC50 returns `architecture_constrained_enum_design`. Enumerating that vocabulary in a Python `TypedDict` to force a closed schema would freeze configuration into code, which §2 forbids. The schema validates presence and type of the declared core, never the value vocabulary of what's beyond it — which strings are legal for `state` stays CC50's problem, not this item's.

The distinguishing property of a blob is not openness, it's an *empty* schema:

| | `properties` | `required` | verdict |
|---|---|---|---|
| `-> dict` (today, 91 of 143 tools) | — | — | no schema at all |
| `-> dict[str, Any]` (today, 78 of 143 tools) | `{}` | none | blob — asserts nothing |
| declared core, open extras | typed | populated | real safety net |

### Validation comes free

No boundary validator needs to be written. `FuncMetadata.convert_result()` in the installed `mcp` package already runs `self.output_model.model_validate(result)` on every structured return before serializing `structuredContent`. Declaring a return type gets schema advertisement *and* egress validation from one annotation. Verified this survives the decorator stack in place today: `functools.wraps` sets `__wrapped__`, and `inspect.signature(..., eval_str=True)` follows it, so `@mcp.tool()` sees the real return annotation through the intervening decorator and produces the full schema plus validated `structuredContent`. No decorator rework required for this item.

## Code Samples & Guidance

### Declaring a load-bearing core

Hyphenated keys need the functional `TypedDict` form:

```python
from typing import NotRequired, TypedDict

# Required: what a caller needs to act on the response.
# Everything else about a plan item rides as an extra — including
# work/skill, which are always emitted but load-bearing for nobody.
PlanItemRef = TypedDict("PlanItemRef", {
    "id": str,
    "plan": str,
    "state": str,
    "path": str,
    "warnings": NotRequired[list[str]],
})
```

### Open-core variant for config-driven payloads

`plan_get_item` is the canonical case — its section keys come from `planning.yaml` plus per-item custom headings:

```python
from pydantic import BaseModel, ConfigDict

class PlanItem(BaseModel):
    """Load-bearing core of a plan item. Body sections are config-driven
    (planning.yaml item-section-headings, plus per-item custom headings),
    so they pass through as extras rather than being enumerated here.
    """
    model_config = ConfigDict(extra="allow")

    id: str
    plan: str
    state: str
    path: str
```

Verified output — typed core, populated `required`, extras allowed:

```json
{"type": "object",
 "properties": {"id": {"type": "string"}, "plan": {"type": "string"},
                "state": {"type": "string"}, "path": {"type": "string"}},
 "required": ["id", "plan", "state", "path"],
 "additionalProperties": true}
```

### Success with non-blocking warnings

One reserved name, no machinery. Omit the key entirely when there is nothing to report:

```python
@mcp.tool()
@tool_boundary
def operate_provider_surfaces(mode: str) -> SurfaceOperationResult:
    result = providers_api.operate_provider_surfaces(project_root_from_env(), mode=mode)
    payload: SurfaceOperationResult = {"mode": mode, "surfaces": result.surfaces}
    skipped = [f"{s.provider}: {s.reason}" for s in result.surfaces if s.skipped]
    if skipped:
        payload["warnings"] = skipped
    return payload
```

If the caller cannot use the result at all, that is not a warning — raise (CC62 turns it into a redacted `isError`).

### Applying a declared core

```python
@mcp.tool()
@tool_boundary
def plan_get_item(item_id: str, include_history: bool = False) -> PlanItem:
    return planning_api.get_item(project_root_from_env(), item_id, include_history)
```

### Regression guard

Applies only to tools that have declared a core — not a completeness check across all 143:

```python
@pytest.mark.asyncio
async def test_declared_cores_stay_declared():
    """A tool that has declared a core must not regress to a blob."""
    for tool in await mcp.list_tools():
        schema = tool.outputSchema
        if schema is None:
            continue  # not yet declared — opportunistic, not required
        assert schema.get("required"), f"{tool.name} declares no load-bearing core"
```

## Validation

- A tool omitting a declared load-bearing key fails at the boundary via FastMCP's existing `model_validate` rather than reaching the client — assert this explicitly, it is the point of the item
- A tool emitting extra keys beyond its declared core passes untouched, and those keys survive into `structuredContent`
- `plan_get_item` keeps working for items carrying custom sections (CC47's `new_yaml_schema`, CC50's `architecture_constrained_enum_design`) — config-driven keys are neither required nor stripped
- `warnings` is absent from the payload when there is nothing to report, and is never listed in any tool's `required`
- Tools that have not declared a core are not flagged by the regression guard — opportunistic scope is not a completeness checklist
- An architecture test asserts no result core is declared under `foundation/` (§1 domain-neutrality)
- No MCP/FastMCP import appears in any component API or core module (§8)
- The four live `.mcp.json` servers are exercised end-to-end once their pass is done, since running agents consume them directly
- Full unit suite, lint, and typecheck green for whichever tools were migrated. Declared cores must typecheck against what the producing API function actually returns — treat any mismatch surfaced by the typechecker as a real defect found, not friction to widen away with `Any`

## Effort & Risk

Small per declared core, deliberately unbounded in aggregate because scope is opportunistic rather than a migration — there is no fixed finish line, and that's intended (RV933: the schema is a safety net, not a contract requiring completeness). Sizing this M rather than L because the committed portion — the pagination core plus a first pass over the four live servers — is bounded; anything beyond that happens opportunistically as other work touches a tool.

Each declared core is independent: no shim, no dual route, no cross-tool coupling, so nothing here can be half-migrated in a way that breaks another tool. The real cost per tool is not writing the annotation, it's reading the producing API function closely enough to know what it actually, always returns.

**Risks**
- *Over-declaring.* The one irreversible mistake this item can make. A key marked required but sometimes absent turns a working tool into a boundary failure the moment that key is omitted. Mitigated by the load-bearing test (above) and by defaulting to omission when unsure — adding a key later is free, removing a required one is not.
- *`warnings` drifting into an error channel.* If a caller starts branching on `warnings` to decide whether the operation actually worked, the raise/warn split has broken down and the condition should have raised instead. Warnings are only for things a caller can ignore and still safely use the result.
- *Scope creep back into a schema catalogue.* Resist registering declared cores in `schema_registry.py` as canonical durable schemas — see Rejected Alternatives.
- *Blocked per-tool, not per-item, on CC62.* A given tool cannot safely get a declared core until its server no longer returns error dicts for that tool's failures — relevant today only for `project_mcp.py` and `session_mcp.py`; every other server can be migrated independently of CC62's timing.

## Standards

- **§8 Protocol Adapter Boundaries** — declared result cores are plain typing/pydantic constructs owned by the component; the MCP module only imports one to annotate a return.
- **§1 Dependency Boundaries** — foundation stays domain-neutral: component result cores must not land in `foundation/mcp` or any other foundation module.
- **§3 Ownership and Abstraction / Evidence-led scope** — build only what a current use case requires: no universal partial-success field beyond the one reserved `warnings` key, no speculative completeness target. Types unify only on shared ownership, lifecycle, validation, and semantics — which is why tool returns do not go through the durable-record schema registry, and why only the pagination shape currently clears the shared-type bar.
- **§2 Extensions and Configuration** — entity declarations belong in configuration, not central Python lists; config-driven payloads (planning) use the open-core pattern instead of enumerating their vocabulary in Python.

## Notes

### Provenance

Rewritten from RV931 (verified the original envelope proposal against the tree at mcp==1.27.0 and found it factually and architecturally wrong), corrected by RV932 (guard was asserting closure, which config-driven payloads can't satisfy; sample used unhyphenatable `class`-form TypedDict) and RV933 (`required` had been defined as always-present rather than load-bearing; added the reserved `warnings` key and folded the former partial-success slice into it). RV934 split the error-path fix out to CC62, leaving this item as typed-return-cores only.

Findings were established by probing the installed FastMCP directly rather than reading the plan text or the framework's docs — the `outputSchema` produced by bare `dict` vs `dict[str, Any]` vs a declared core, the `model_validate` call inside `convert_result()`, and confirmation that a declared return survives the existing decorator stack.

### Rejected alternatives

**Bespoke `{contract-version, ok, data, errors}` envelope + `wrap_response()`** — the original proposal. Re-implements `structuredContent`, `isError`, and session versioning inside the payload, and does not fix the stated defect: wrapping an undeclared dict still advertises an empty schema for `data`. Its incremental rollout across live servers is also the dual route §4 forbids.

**Registering declared cores in `foundation/contracts/schema_registry.py`** — rejected. That registry validates durable records before persistence, a committed surface with a migration obligation. Tool return cores are transport safety nets validated by pydantic at egress — different owner, lifecycle, and validator (§3).

**A closed schema per tool** — unachievable for config-driven payloads like planning items; would require enumerating configuration in Python.

**A tier taxonomy (closed-contract tools vs open-contract tools)** — considered and dropped as over-built. One rule — declare the load-bearing core, leave the rest open — covers both cases without any taxonomy to maintain.

**A typed `Warning` class hierarchy** — dropped. The value being standardized is the reserved key name; the shape of each entry doesn't need one.

**A campaign to reach all 143 tools** — dropped per explicit direction ("do we already have return schemas... or is that what we were proposing" / "are we over-engineering"). The schema is a safety net, and safety nets don't need completeness; scope is opportunistic plus the four live servers.

**Declaring return cores in component YAML instead of Python annotations** — considered, since `tool-descriptions:` already carries a `parameters:` block and it would be one config-driven code path (§2). Rejected: FastMCP's `mcp.tool()` has no `output_schema` parameter — schemas derive from the return annotation — and a YAML declaration is not typechecked, so it would drift from the API silently. For a safety net, the version pyright enforces is worth more than the version that reads better in config.

### Design principles carried forward

- **Adding is free, requiring is forever.** Extras pass through, so a key can always be added later. Declaring one required is the only irreversible move — which is why cores stay minimal and are derived from what the API actually, always returns.
- The schema is a safety net, not a committed surface. No versioning, no migration obligation, no requirement to be complete.
- Required means load-bearing, not always-present. Validate presence and type of the core, never the value vocabulary — vocabularies stay config-owned.
- Blocking conditions raise (CC62); non-blocking ones ride in the reserved `warnings` key. No separate partial-success mechanism.
- Keep the MCP surface narrower than the API beneath it.
