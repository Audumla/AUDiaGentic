# Wire the workflow propagation engine to its first real consumer (plan-item parent/child state consistency)

## Description

Sponsor direction 2026-07-18: the foundation workflow.propagation package (passive parent/child state propagation, hierarchy validation, opt-in healing) is wanted and was restored after the dead-code cleanup deleted it for having zero consumers. This item closes the Architecture Standards §3 gap by giving it its first wired consumer instead of leaving it unconsumed in foundation. The natural host is the planning component: plan items already have parent/child relationships (umbrella items like MA08 with children MA28-MA30) whose state consistency is today maintained by hand and by review (RV564-style state reconciliations).

## Steps

1. Confirm the intended consumer with the sponsor: plan-item hierarchies in the planning component (umbrella → children completion propagation, e.g. auto-flag an umbrella as ready-to-close when all children complete) is the assumed target — verify before wiring.
2. Define the planning-side propagation config (YAML per propagation_config loader): semantic state sets mapped to planning states (pending/completed/closed), one or two rules to start — rule_all_children_in_set to surface 'all children complete' on the parent, and validate_hierarchy for the state-reconciliation checks reviews currently do manually.
3. Implement the planning host binding: planning item store implements the WorkflowItemAPI protocol; call propagate() after plan_set_state transitions; surface results as advisory facts (notes/review suggestions) FIRST — do not auto-transition parent items until the advisory mode has proven trustworthy.
4. Keep foundation untouched except bug fixes the wiring surfaces; the engine stays passive (host-called, no event subscription) per its design.
5. Tests: planning-side config load, all-children-complete detection on a fixture hierarchy, hierarchy validation catching a child-active/parent-completed inconsistency (the exact class of drift RV564 hand-fixed).

## Detailed Solution & Technical Design

CC45 Full Implementation Plan (from gpt-auto-agent, 2026-08-17)

Architecture:
- Advisory-only v1: no apply_propagation(), no auto-transition. Propagation suggestions returned as structured metadata from plan_set_state.
- Hierarchy: single parent_ids field on children. No child_ids. No migration needed.
- Completion: complete: [completed] state-set (not terminal). Fixes foundation validator mismatch.
- Call path: MCP plan_set_state → planning_api.set_state → items.set_state (mutation) + evaluate_state_change (advisory)

New files:
- planning/hierarchy.py: normalize_parent_ids, parent_ids_for, child_ids_for, validate_parent_ids, _has_ancestor
- planning/workflow_propagation.py: PlanningWorkflowItemAdapter (WorkflowItemAPI impl), evaluate_state_change, _build_advisories, _validate_affected_hierarchy
- planning/propagation.yaml: rule_all_children_in_set config for umbrella completion
- tests for propagation fixtures

Foundation bug fixes:
- parents.py: linked_child_ids() same-kind confusion — nested umbrella parent mistaken for child
- healing.py: completed-parent check ignores child-side references — use linked_child_ids()

Modifications:
- item_store.py: iter_item_paths() safe iterator
- items.py: parent_ids in create/update/list
- planning_api.py: set_state wrapper calling evaluate_state_change after mutation
- workflows.yaml: add complete: [completed]
- planning.yaml: parent_ids in frontmatter-fields

Failure semantics: propagation failures return status: unavailable with warning, never roll back state.
Effort: ~16-23 engineering hours across 6 phases.
