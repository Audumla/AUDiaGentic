# Enumerate hardcoded string states and return values across the codebase

## Description

Establish and apply a codebase-wide vocabulary policy for closed string values. The work distinguishes configuration/schema-owned values, plain-string wire contracts, and internal runtime domain values so that each vocabulary has one owner, one validation path, and an appropriate representation rather than requiring all strings to become StrEnum values.

## Steps

- Apply the universal representation policy: declarative YAML/JSON-schema values remain source-owned; plain-string wire contracts use narrow Literal aliases plus validation; StrEnum is reserved for parsed internal runtime domain values
- Audit candidates by owner, canonical source, serialization boundary, callers, and existing validation; exclude free-form diagnostics/log messages
- Providers are owned by CC51, including the remaining streaming/catalogue triage from CC52
- Treat workflow state machines as workflows.yaml plus TransitionEngine owned; add generation/CI freshness only if static symbols are evidenced
- Treat agent-job stage, approval, review recommendation, aggregation, and bundle decision values as JSON-schema-owned; resolve schema/runtime mismatches before new types
- Assess foundation wire contracts including ACP raw transport status; distinguish tool-status and turn stop-reason vocabularies at ingress
- Assess agents internal runtime projections/reasons: ProgressPhase, ToolStatus, recovery metadata, profile-slot labels, and session/evidence reasons
- Assess planning and ledger validation against owning configuration/contracts
- Record every accepted vocabulary with owner, source, representation, validators, and consumers; split implementation by source/owner when needed
- Add owner-scoped serialization, validation, architecture, and type-checking tests; do not use global grep-zero checks for common words

## Detailed Solution & Technical Design

Universal vocabulary policy:

1. Declarative source-owned values — workflows.yaml and JSON Schema remain canonical. Use the existing transition/schema validators. Generate named Python symbols only when needed, and verify freshness in CI.

2. Plain-string boundary contracts — mapping, YAML, JSON, MCP, and persisted values remain strings with narrow Literal aliases and central validation/parsing. This preserves wire compatibility.

3. Internal runtime domains — use StrEnum only after explicit ingress parsing when member identity, enum-derived sets, or domain behavior provide value. Serialization emits the enum value.

4. One owner, not one spelling — consolidate only where ownership, lifecycle, semantics, and validation all match.

CC52 absorption:

- Foundation: ACP transport values remain ingress-validated wire strings and tool-status must stay distinct from turn stop-reason.
- Agent jobs: review/approval/aggregation/bundle values are schema-owned. Resolve the all-pass versus majority-pass schema/runtime discrepancy before changing types.
- Agents: gateway mode, profile-slot labels, and recovery metadata require corrected inventories and owner-scoped validation; do not create a generic ErrorKind enum.
- Boolean parsing strings remain a utility concern, not a domain-vocabulary migration.

CC51 owns all provider streaming, descriptor catalogue, and source-catalog work; this item retains cross-codebase policy and non-provider triage.

## Architecture Constrained Enum Design

### Boundary Rule (from ARCHITECTURE_STANDARDS.md §1, §3)
- Types are unified only when they share **ownership, lifecycle, validation, and semantics**. Field overlap alone is insufficient.
- Foundation types must be domain-neutral. Component-specific concepts stay in their owning component.
- Provider-specific types stay with providers; foundation only gets what is independently consumed outside that domain.

### Where Each Enum Lives (by ownership)

#### Gateway Request Lifecycle — OWNED BY: agents_gateway_store
**Module**: `agents_gateway_store._shared` (alongside existing `TERMINAL_STATES`)
**New StrEnum: `GatewayRequestState`**
- QUEUED, RUNNING, COMPLETED, FAILED, CANCELLED, REJECTED, INTERRUPTED
- Derive `_TERMINAL_STATES` from the enum itself instead of a frozenset literal.
- **Not in foundation**: this is agents-gateway domain logic only.

**Why not share with agent_jobs?** Both use similar words ("running", "failed") but have different lifecycles, different transition rules, and different owners. Sharing would couple the agents component to the agent_jobs component — a violation of §1 dependency boundaries.

### Workflows.yaml Alignment (Architecture-Safe)

Workflows.yaml is the canonical state machine definition. The Python enums must be derived from it, not duplicated independently.

**Strategy**: Each component's workflow YAML is loaded at module init and validated against its corresponding StrEnum. A mismatch raises a startup error — this ensures the YAML and enum stay in sync without coupling components to each other.

For example, in `agents_gateway_store._shared`:
```python
_WORKFLOW = load_workflow(...)
_GATEWAY_REQUEST_STATES = states_in_set(_WORKFLOW, "all")
# Validate at load time that enum values match YAML
GatewayRequestState._validate_against_yaml(_GATEWAY_REQUEST_STATES)
```

Each component owns its own workflow YAML and its own enum — no cross-component coupling.

### What NOT to Do (Architecture Violations)

1. **Do NOT put GatewayRequestState or AgentJobState in foundation.** They are component-domain state machines, not domain-neutral primitives.
2. **Do NOT unify "failed" across components.** GatewayRequestState.FAILED and AgentJobState.FAILED have different semantics, different transition rules, and different owners.
3. **Do NOT create a shared `State` or `Status` base enum.** That would be an abstraction without evidence — two consumers need the same *contract*, not just similar field names.
4. **Do NOT move event topic strings to enums unless they are already exported as module constants from their owning component.** Event topics follow the AGENT GUIDELINES §5: "Use an owner-exported module constant rather than an inline literal." The agents_event_topics.py module already does this — no enum needed, just ensure callers import from there instead of hardcoding.
5. **Do NOT create enums for transient/diagnostic reason strings that appear only in log messages or error details.** Only materialize vocabularies that are compared against in code (if/elif chains, frozenset membership checks, state transitions).

### Migration Order (respecting dependencies)

1. **Foundation-first layer** (no component dependency):
   - foundation.service: ServiceState, LeaseState, StartDisposition, StopOutcome
   - foundation.workflow: StepStatus
   - foundation.bootstrap: ComponentInstallState, ComponentHealthStatus
   - foundation.providers: IsolationTier, McpLaunchIsolationTier, CapabilityAuthority

2. **Component layer** (each independently):
   - agents_gateway_store._shared: GatewayRequestState, CancelAckActor
   - agents_gateway_sessions_store: GatewaySessionState
   - agent_jobs.state_machine: AgentJobState
   - planning.items/reviews: PlanItemState, PlanReviewState
   - agents_session_lifecycle_projection: EvidenceKind, CoarseSessionState, ValidationState, EvidenceState (as StrEnum)
   - agents_harness_status_evidence: EvidenceRejectionReason
   - agents_gateway_turn_events: ToolStatus
   - agents_gateway_work_index: WorkIndexPhase
   - ledger.fragments or change_classes: LedgerChangeClass

3. **Replacement layer** (after enums exist):
   - Replace raw string comparisons in each component's internal code
   - Validate workflows.yaml against new enums at startup
   - Remove frozenset literals that can be derived from enums
