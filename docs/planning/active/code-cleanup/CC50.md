# Enumerate hardcoded string states and return values across the codebase

## Description

Establish and apply a codebase-wide vocabulary policy for closed string values. The work distinguishes configuration/schema-owned values, plain-string wire contracts, and internal runtime domain values so that each vocabulary has one owner, one validation path, and an appropriate representation rather than requiring all strings to become StrEnum values.

## Steps

- Publish and apply the representation policy: YAML/JSON-schema values remain source-owned; plain-string wire contracts use narrow Literal aliases plus validation; StrEnum is reserved for parsed internal runtime domain values
- Audit each candidate vocabulary by owner, source of truth, serialization boundary, and callers; exclude free-form diagnostics/log messages
- Providers: CC51 owns provider automation modes, isolation, result-state validation, MCP entry reason typing, and observer timing
- Workflow state machines: retain workflows.yaml plus TransitionEngine as authority for gateway request/session, agent-job, and planning states; add generated definitions plus CI freshness only if static symbols are evidenced
- JSON-schema vocabularies: retain stage-result and next-stage-recommendation schemas as authority; generate/check types only if needed
- Foundation wire contracts: assess OutputLevel/OutputKind, service/lease/lifecycle values, and StepResult for shared validation without unnecessary enum-instance migrations
- Agents runtime projections: assess ProgressPhase, ToolStatus, evidence rejection, and session close/failure reasons for internal StrEnum suitability
- Planning and ledger: assess state/change-class validation against their owning workflow/config contracts
- Add owner-scoped tests for validation and serialization; do not use global grep-zero checks for common words
- Record the final taxonomy, owners, and representation rules; split implementation into independently testable owner/source slices

## Detailed Solution & Technical Design

Universal vocabulary policy:

1. Declarative source-owned values — workflow YAML and JSON Schema remain canonical. Runtime code uses the existing transition/schema validators. Do not hand-maintain matching enums. If named Python symbols become necessary, generate them from the declarative source and enforce generated-file freshness in CI.

2. Plain-string boundary contracts — values received from mappings, YAML, JSON, MCP, or persisted records remain strings with narrow Literal aliases and one central validator/parser. This preserves existing wire compatibility and avoids silently requiring callers to instantiate StrEnum members.

3. Internal runtime domains — use StrEnum only where the owner deliberately parses ingress values into enum instances and code benefits from member identity, enum-derived sets, or domain methods. Serialization must emit the enum value.

4. One owner, not one spelling — identical strings are consolidated only when ownership, lifecycle, semantics, and validation match. Similar words in separate domains remain separate.

## Naming Conventions Aligned With Existing Codebase

**Enum class**: CamelCase + domain suffix (State, Kind, Reason, Status) — e.g., `AgentLifecycle`, `TransportObservationKind`
**Members**: UPPER_SNAKE_CASE matching the string value — e.g., `PENDING = "pending"`  
**String values**: lowercase; hyphens for multi-word (e.g., `CANCELLED = "cancelled"`)  
**Existing StrEnum**: TransportObservationKind, AgentLifecycle, RecipeState, Phase, TerminalQualityLabel

### Issues Found & Fixes

1. **EvidenceRejectionReason → RejectionReason** — "Evidence" is redundant; the enum lives in the evidence sink module, context is already clear.
2. **SessionCloseReason / SessionFailureReason → CloseReason / FailureReason** — "Session" prefix adds noise; these are internal to the session runtime where the word "session" is implicit.
3. **GatewayProgressPhase → ProgressPhase** — shorter, same meaning. Must not conflict with existing `Phase` in agents_gateway_work_index (different module, different concept: work-index vs operator display).
4. **StageResult → StageStatus** — consistent with StepStatus pattern; "Result" is an outcome container, "Status" is a state value.
5. **ControlAction / ControlResult → JobAction / JobResult** — "Control" is too generic (session control exists). These are agent-job specific: job control actions and results.
6. **StepStatus.OK → StepStatus.SUCCESS** — "ok" as a string is informal; "success" matches AgentOutcome.SUCCESS convention. **However**, this changes the serialized value from "ok" to "success" which breaks NDJSON compatibility. Keep `OK = "ok"` for backward compat.
7. **McpEntryStatusReason → EntryStatus** — shorter, same meaning; "MCP" and "Reason" are redundant (lives in mcp.py).
8. **NextStageRecommendation → Recommendation** — shorter; context already implies "next stage".
9. **ValidationState / EvidenceState** — keep as-is (matches existing StatusEvidenceConfidence pattern).
10. **ProviderIsolationTier stays** — this is the authoritative name in the providers API contract.

### Terminology Inconsistencies Found

1. **State vs. status naming**: Some modules use `state` (gateway store), others `status` (StepResult, component health) — these are different concepts but the naming overlap causes confusion.

2. **Hyphen vs. underscore inconsistency**:
   - "in_progress" (planning items) vs "tool-calling", "model-thinking" (turn events)
   - "full-isolation" vs "no_isolation" patterns

3. **Duplicate meaning across modules**:
   - "active" means different things in gateway sessions, planning items, queue profiles, and isolation tiers
   - "failed" appears in gateway requests, agent jobs, sessions, StepResult, ServiceState — all independent

4. **Workflows.yaml as single source of truth vs. string references**: The YAML defines state machines but Python code hardcodes the same strings independently — no compile-time check that they match.

## Architecture Constrained Enum Design

### Boundary Rule (from ARCHITECTURE_STANDARDS.md §1, §3)
- Types are unified only when they share **ownership, lifecycle, validation, and semantics**. Field overlap alone is insufficient.
- Foundation types must be domain-neutral. Component-specific concepts stay in their owning component.
- Provider-specific types stay with providers; foundation only gets what is independently consumed outside that domain.

### Workflows.yaml Alignment (Architecture-Safe)

Workflows.yaml is the canonical state machine definition. The Python enums must be derived from it, not duplicated independently.

**Strategy**: Each component's workflow YAML is loaded at module init and validated against its corresponding StrEnum. A mismatch raises a startup error — this ensures the YAML and enum stay in sync without coupling components to each other.

For example, in `agents_gateway_store._shared`:
```python
_WORKFLOW = load_workflow(...)
_GATEWAY_REQUEST_STATES = states_in_set(_WORKFLOW, "all")
# Validate at load time that enum values match YAML
GatewayRequestState._validate_against_yaml(_GATEWAY_REQUEST_STATES)
```

Each component owns its own workflow YAML and its own enum — no cross-component coupling.

### What NOT to Do (Architecture Violations)

1. **Do NOT put GatewayRequestState or AgentJobState in foundation.** They are component-domain state machines, not domain-neutral primitives.
2. **Do NOT unify "failed" across components.** GatewayRequestState.FAILED and AgentJobState.FAILED have different semantics, different transition rules, and different owners.
3. **Do NOT create a shared `State` or `Status` base enum.** That would be an abstraction without evidence — two consumers need the same *contract*, not just similar field names.
4. **Do NOT move event topic strings to enums unless they are already exported as module constants from their owning component.** Event topics follow the AGENT GUIDELINES §5: "Use an owner-exported module constant rather than an inline literal." The agents_event_topics.py module already does this — no enum needed, just ensure callers import from there instead of hardcoding.
5. **Do NOT create enums for transient/diagnostic reason strings that appear only in log messages or error details.** Only materialize vocabularies that are compared against in code (if/elif chains, frozenset membership checks, state transitions).

### Migration Order (respecting dependencies)

1. **Foundation-first layer** (no component dependency):
   - foundation.service: ServiceState, LeaseState, StartDisposition, StopOutcome
   - foundation.workflow: StepStatus
   - foundation.bootstrap: ComponentInstallState, ComponentHealthStatus
   - foundation.providers: IsolationTier, McpLaunchIsolationTier, CapabilityAuthority

2. **Component layer** (each independently):
   - agents_gateway_store._shared: GatewayRequestState, CancelAckActor
   - agents_gateway_sessions_store: GatewaySessionState
   - agent_jobs.state_machine: AgentJobState
   - planning.items/reviews: PlanItemState, PlanReviewState
   - agents_session_lifecycle_projection: EvidenceKind, CoarseSessionState, ValidationState, EvidenceState (as StrEnum)
   - agents_harness_status_evidence: EvidenceRejectionReason
   - agents_gateway_turn_events: ToolStatus
   - agents_gateway_work_index: WorkIndexPhase
   - ledger.fragments or change_classes: LedgerChangeClass

3. **Replacement layer** (after enums exist):
   - Replace raw string comparisons in each component's internal code
   - Validate workflows.yaml against new enums at startup
   - Remove frozenset literals that can be derived from enums

## Implementation Strategy

1. **Phase A — Foundation enums**: Create new StrEnum types in the appropriate foundation/contract modules (e.g., GatewayRequestState in agents_gateway_store._shared alongside TERMINAL_STATES).

2. **Phase B — Workflow YAML alignment**: Keep workflows.yaml as the canonical source of truth. Generate or validate that enum values match YAML state definitions. Consider a validation step that cross-checks.

3. **Phase C — Literal → StrEnum conversions**: For existing Literal[] types, convert to StrEnum where they represent closed vocabularies used at runtime (not just type annotations).

4. **Phase D — Replace string literals**: Systematically replace raw string comparisons and assignments with enum members throughout the codebase.

5. **Phase E — Terminology cleanup**: Align naming (e.g., normalize hyphen/underscore usage within each enum; document when "state" vs "status" is appropriate).

## Risks

- **Breaking API contracts**: Enum values serialize to strings in NDJSON/YAML — StrEnum preserves this, but any client code expecting raw strings must be verified.
- **Migration complexity**: Each group should be its own commit/PR with full test coverage before moving to the next.
- **Workflows.yaml coupling**: The YAML and Python enums must stay in sync. Consider a runtime validation that loads YAML and compares against enum values.
