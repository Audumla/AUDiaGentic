# External review: config/cache standard wording contradicts implementation

## Notes

Independent review obtained through the agents gateway (gpt-auto provider, ChatGPT via CDP), request req_9f75b7de0b0c4ddd. Implementation itself was assessed as sound with no blocker; findings are about the documented standard and validation wording, which is why this is a review rather than a reopen.

## Findings

1. The stated config standard is too absolute. "Config under .audiagentic/config/" directly conflicts with three paths the item itself deliberately keeps elsewhere: .pi/mcp.json, .vscode/mcp.json and root .lsp.json. Restate as two rules: AUDiaGentic-owned internal configuration lives under .audiagentic/config/; integration files required at harness-native discovery locations stay where the harness looks for them.

2. The cache standard contradicts the implementation. The Description says cache belongs under .audiagentic/runtime/cache/, but Validation records the coding-LSP cache at .audiagentic/runtime/coding-lsp/. One of the two must change. .audiagentic/runtime/cache/coding-lsp/ is preferable if that content is genuinely safe to delete; otherwise amend the Description to describe the per-component runtime layout actually in use (runtime/providers/, runtime/harness/, runtime/ledger/).

3. Validation bullet is literally incorrect. "Bare pi CLI invocation outside AUDiaGentic" is wrong because .pi/mcp.json is project-relative — Pi discovers it when its working directory is the project. Reword to "bare pi launched from the AUDiaGentic project root, without the AUDiaGentic launcher".

4. Missing negative test for the hard-fail contract. The item states paths resolve from foundation.paths constants "with hard fail if config missing", but no validation exercises it. Add a case asserting that an absent required AUDiaGentic config produces a deterministic startup error naming the resolved path, while optional harness-native files (.lsp.json, .vscode/mcp.json) are not treated as mandatory.

## Conclusion

Implementation sound and correctly reasoned about Pi/Qwen native discovery paths; CC60's documentation and validation should be amended before the architectural standard is treated as settled. No code change required for items 1-3; item 4 is a test gap.
