# Design and implement rate-limit-dialog recovery (auto-dismiss + backoff)

## Description

ChatGPT's 'Too many requests' hard rate-limit dialog is now detected (rate-limit-dialog dom-signal, added 2026-08-16) but only as advisory diagnostics -- proven live that the panel can be visible while the underlying generation is still executing and completing correctly behind it, so it is deliberately NOT wired as a response-failed trigger or response-complete veto. No recovery behavior exists yet: nothing dismisses the dialog or backs off before retrying.

## Steps

- The dialog pops on ALL open tabs simultaneously once the account-level limit is reached, not just the triggering tab (confirmed live, seen on multiple gpt-t2 tabs at once). Any dismiss design must either (a) sweep every open tab bound to the affected project when a rate-limit is detected, or (b) dismiss lazily on whichever tab is next actually interacted with (simpler, avoids touching idle tabs, and is harmless since the panel doesn't block real completion).
- No CDP click action exists yet in the adapter for adapter-driven dialog dismissal ('Got it' button) -- needs to be added.
- Open design questions to resolve before implementing: per-turn vs adapter-level backoff scope; cooldown duration (fixed vs. reading a hint from the dialog text, which currently just says 'wait a few minutes'); cross-project queue independence (a rate limit on one project's ChatGPT account is unrelated to other projects sharing the gateway process, so backoff must not block unrelated projects' turns).
- Given the panel can coexist with real progress, any design must NOT assume the panel's presence alone means the turn is stuck -- it needs genuine stall evidence (e.g. no progress for N seconds) in addition to the panel, never the panel alone.
