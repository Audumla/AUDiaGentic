# Design and implement rate-limit-dialog recovery (auto-dismiss + backoff)

## Description

ChatGPT's 'Too many requests' hard rate-limit dialog is now detected (rate-limit-dialog dom-signal, added 2026-08-16) but only as advisory diagnostics -- proven live that the panel can be visible while the underlying generation is still executing and completing correctly behind it, so it is deliberately NOT wired as a response-failed trigger or response-complete veto. No recovery behavior exists yet: nothing dismisses the dialog or backs off before retrying.

## Steps

- The dialog pops on ALL open tabs simultaneously once the account-level limit is reached, not just the triggering tab (confirmed live, seen on multiple gpt-t2 tabs at once). Any dismiss design must either (a) sweep every open tab bound to the affected project when a rate-limit is detected, or (b) dismiss lazily on whichever tab is next actually interacted with (simpler, avoids touching idle tabs, and is harmless since the panel doesn't block real completion).
- No CDP click action exists yet in the adapter for adapter-driven dialog dismissal ('Got it' button) -- needs to be added.
- Open design questions to resolve before implementing: per-turn vs adapter-level backoff scope; cooldown duration (fixed vs. reading a hint from the dialog text, which currently just says 'wait a few minutes'); cross-project queue independence (a rate limit on one project's ChatGPT account is unrelated to other projects sharing the gateway process, so backoff must not block unrelated projects' turns).
- Given the panel can coexist with real progress, any design must NOT assume the panel's presence alone means the turn is stuck -- it needs genuine stall evidence (e.g. no progress for N seconds) in addition to the panel, never the panel alone.

Clean split: ObservationEngine answers 'what is happening to this turn' (turn-local); a new RateLimitGate answers 'may this account start another provider-side action yet' (account-local).

**1. Backoff state scope**: per-account, owned on GptAutoProviderRuntime (not per-turn, not per-project) -- runtime_registry._shared_key() already keys shared runtimes by browser executable/port/CDP URL, ignoring project_root, so runtime is already the natural cross-project authority. Introduce RateLimitMode(CLEAR/COOLDOWN/PROBE) + RateLimitState(mode, blocked_until, strikes, first_seen_at, last_seen_at, incident_generation, probe_owner) behind an AccountRateLimitGate on GptAutoProviderRuntime. Name it runtime.rate_limit_gate/rate_limit_scope (not runtime.retry_delay/rate_limited -- avoid baking in 'runtime==account forever'; if multiple authenticated browsers are ever attached to one runtime, add an explicit account-scope-id/instance-id config key rather than using project ID as the throttle key). Do NOT put this in ProviderState -- a provider can be AVAILABLE while the account is throttled; AVAILABLE->FAILED/RECOVERING would wrongly conflate an operational quota condition with browser/CDP failure.

**2. Dialog dismissal**: add dismiss_rate_limit_dialog() to GptAutoCdpBrowserController (same abstraction level as existing stop_generation()/submit()), scoped strictly to a confirmed dialog element (find the role=dialog matching the rate-limit text first, THEN find its 'Got it' button inside that dialog -- never search globally for a 'Got it' button). Safe to dismiss immediately, no stall evidence required -- dialog presence and turn failure are different questions; clicking 'Got it' only removes a presentation modal. Adopt GP10's own originally-proposed lazy policy: record the account-wide throttle when detected, dismiss lazily on whichever tab is next actually interacted with, never sweep all tabs.

**3. Cooldown strategy**: circuit-breaker CLEAR/COOLDOWN/PROBE (half-open), not a flat sleep-and-retry -- a flat approach breaks because the same DOM modal is visible on every tab simultaneously, so naive per-observation strike-counting would hit max strikes instantly across 10 polling tabs. Suggested defaults: initial-cooldown-seconds:180, multiplier:2.0, max-cooldown-seconds:900, jitter-ratio:0.10 (~3/6/12/15min-capped backoff). Only a NEW incident (CLEAR->COOLDOWN transition) or a fresh PROBE rejection should add a strike; repeated observations of an already-open COOLDOWN update last_seen_at only. On cooldown expiry, exactly ONE account-wide submission permit is granted (PROBE state) via acquire_submission_permit(turn_id) -- all other same-account requests wait; probe succeeds (PROBE->CLEAR) on genuine submission-proof/PROGRESS evidence (not the CDP click itself), or reopens a longer COOLDOWN with strikes+=1 on a fresh rate-limit rejection. Prevents the thundering-herd failure mode of releasing every waiting project simultaneously at cooldown expiry.

**4. Relationship to ObservationEngine/EvidenceCapability**: explicitly do NOT add EvidenceCapability.RATE_LIMITED -- PROGRESS/SOFT_LIVENESS/TERMINAL_WITNESS is turn-local causal evidence; rate-limiting is account-local admission control, a categorically different question. Mixing them risks generic-tracker logic branching on account scheduling policy. If a typed representation is wanted, use a separate ProviderCondition/ProviderConditions concept, not an EvidenceCapability member. A turn already generating when the dialog appears can (and did, live) complete successfully while the account gate independently opens a cooldown for FUTURE submissions -- no contradiction, both facts coexist.

**5. Hook point**: gate consumed as close as possible to the actual CDP submit side effect, not several seconds earlier -- sequence should be: reconcile existing unresolved-send state first (ensure_ready()'s existing reconciliation must stay ahead of the throttle gate; rate limiting must never block AUDiaGentic from determining whether a prior side effect already happened) -> acquire_submission_permit() -> persist unresolved-send checkpoint -> CDP submit. Rate-limit waiting must NOT consume an ObservationTracker lease (don't instantiate a submission-phase tracker and then burn its clock sitting in a 3-minute cooldown). Detection should be centralized in PersistentChat.snapshot() (route all decoded ChatSnapshots through a small _accept_snapshot()/_record_snapshot() helper that calls runtime.rate_limit.observe_dialog() when 'rate-limit-dialog' is in dom_signals) rather than sprinkled per-consumer, since submission proof, response waiting, reconciliation, and readiness checks all need to discover it.

**Critical safety rule (the most important GP10 acceptance criterion after account scoping)**: GP10 must NEVER introduce an automatic submit retry after the provider-side send may already have happened -- this directly interacts with the existing unresolved-send/no-double-submit barrier (see GP06's admission-recovery wording fix, already landed). Concrete rules: rate-limit BEFORE Send -> wait/backoff then retry admission safely; rate-limit AFTER Send with submission definitively absent -> retry may be safe; rate-limit AFTER Send with outcome ambiguous -> do NOT resubmit, retain the unresolved-turn barrier, cool down the account, reconcile the existing turn later; rate-limit while response is progressing -> current turn continues normally, only future submissions are blocked; rate-limit + genuine stall -> classify for recovery but still never infer not-submitted.

**Bonus finding, worth doing alongside GP10**: submission-proof's SOFT_LIVENESS grant currently considers ANY change in snap.dom_signals (broader than response-observation's explicit _SOFT_LIVENESS_SIGNALS allowlist of stop-control/streaming-indicator/thinking-indicator/busy-indicator), so rate-limit-dialog appearing/disappearing can currently, indirectly, renew submission-proof's bounded grace period. Recommends tightening submission-proof to use the same explicit allowlist so rate-limit-dialog has zero authority over ObservationEngine's clocks in either phase.
