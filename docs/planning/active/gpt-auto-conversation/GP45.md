# Make agents.yaml (execution-profiles/agent-definitions/roles) machine-scoped with sparse project overlay, not project-owned

## Description

Direct user requirement, 2026-08-17: 'we need to not have that in the project configuration - it has to be in the global - and the global also needs to have project and session limits that can be overridden by a projects config.' Confirmed via code: AgentsConfigRepository.read()/replace() resolve exactly one file, agents_config_path(project_root) = <project_root>/.audiagentic/config/agents.yaml, with zero merge/overlay/machine-tier logic anywhere in the chain. Every project on the machine maintains a fully independent copy of execution-profiles (including capacity policy: global-capacity/project-capacity/session-capacity), agent-definitions, roles, and prompts, even though the gpt-auto GATEWAY SERVICE itself is one shared machine-scoped process. This is the exact class of problem GP09/GP20/GP21 already solved -- but ONLY for provider settings (.audiagentic/config/providers/*.yaml: dom-signals/evidence-policies/turn timers), via a packaged-defaults.yaml + machine-override + sparse-project-overlay pattern. That fix never covered agents.yaml (a different component: agents, not providers) -- this item extends the same proven pattern there.

Additional live-discovered nuance (2026-08-17): ScopedCapacityAuthority's explicit global-capacity dimension is a SINGLE unqualified 'global' bucket, gateway-wide, shared across every provider/profile that sets it (not even provider-scoped, let alone project-scoped) -- with effective limit computed as the MIN of all currently-active leases' declared values (dynamically shifts as leases open/close, not a fixed per-project contract). unlimited/omitted opts a caller OUT of the bucket entirely (invisible to it, never blocked by it, never tightens it for others). This existing runtime behavior is being kept as-is by this item (it is a genuine intentional shared-ceiling design, not a bug) -- what changes is WHERE the numbers that feed it are configured, not how the reservation authority itself behaves.

## Steps

MANDATORY TEST SCENARIOS called out by the consultation (in addition to this item's original steps 1-7, now superseded in approach but not in intent by the design above): two projects sharing one execution profile with different project-capacity limits; one genuinely shared global-capacity limit correctly NOT duplicated per project; project-A-only override invalidation (A's override changes -> only A goes stale); global invalidation affecting both A and B together (machine profile changes -> both go stale); an invalid project-A overlay leaving project B completely unaffected; the same project reached through path aliases resolving to the same ProjectKey (symlinks/case/mount variations must not fragment identity).

SUGGESTED FIRST SLICE (not yet chosen/committed -- decide in a future session before implementing): the consultation's own phrasing suggests the natural incremental order is (1) define ProjectKey and the typed override schema shape first as pure data structures with no runtime wiring, (2) build EffectiveExecutionProfileResolver + the two-store split as a standalone, fully-tested module against synthetic data, (3) wire it into queue.py behind the existing get_gateway_registry() seam (still opt-in, not yet required), (4) build the shadow-mode comparison harness and run it against this machine's real current projects to surface drift before touching real admission, (5) only then flip shared-mode to REQUIRED (no silent embedded fallback) and retire the per-project agents.yaml execution-profile/agent-definition duplication. AgentCatalog (agent-definitions/roles/prompts) machine-scoping is a separate, likely-later slice given it has no queue-time re-resolution urgency.

## Detailed Solution & Technical Design

SUPERSEDES the earlier multi-Protocol sketch below with a SIMPLER implementation of the SAME architecture, per a live follow-up verification pass (2026-08-17, req_af73f0c6acf945ba) that checked the original design against a real survey of this codebase's foundation/ layer (see notes for the survey findings). Four explicit verified decisions: (a) GP26's fail-semantics win for authoritative config; (b) reuse schema_registry.py for structural validation only, not semantic validation; (c) reject foundation/registry_utils.Registry[T] as the catalog's backing store; (d) no fundamental architectural change, but far fewer new abstractions than first proposed.

**(a) Failure semantics -- GP26 wins, refined with a startup-vs-live-reload table.** No real conflict between known_projects.py's 'advisory, never fails' pattern and GP26's 'invalid machine config fails startup': known_projects.py is a discovery CACHE (doesn't define what the gateway may execute), the new catalog is AUTHORITATIVE control-plane config (agent definitions, provider/profile bindings, shared capacity policy) -- failing open on the latter could make the gateway execute under configuration the operator never authorized. Concrete table:
| Situation | Behavior |
|---|---|
| Cold-start, machine catalog missing/invalid, shared mode | Fail startup |
| Live reload, candidate machine update invalid | Reject candidate; retain last-known-good published catalog; report unhealthy |
| Project override invalid | Does not affect other projects; that project is marked config-invalid and rejects NEW work only |
| Existing admitted work from a now-config-invalid project | Continues running under its already-accepted immutable snapshot -- never killed by a reload |
| No previously valid machine state exists at all | Fail closed (nothing safe to fall back to) |
Technical correction: foundation/io.py's atomic_write_text/json/ndjson give DURABLE FILESYSTEM replacement (temp file + fsync + os.replace), not the in-memory 'atomic pointer swap' for the PUBLISHED runtime catalog -- those are different concerns. Keep the in-memory publisher small and gateway-specific: candidate = load_machine_catalog(); validate(candidate); compiled = compile_catalog(candidate); with publish_lock: _published_catalog = compiled. Never independently mutate agent/role/profile sub-registries during reload -- that creates a mixed-revision window.

**(b) Reuse foundation/contracts/schema_registry.py's validate_with_schema() for STRUCTURAL validation of the project-override document, but it cannot replace semantic validation.** Add a new schema file (e.g. foundation/contracts/schemas/gateway-project-overrides.schema.json) with additionalProperties:false throughout, expressing the whitelist declaratively (only execution_profiles.<id>.params.{project-capacity,session-capacity} allowed -- global-capacity/provider_id/instances/agents/prompts/roles etc. are simply absent from the schema, not imperatively rejected in code). Three validation gates in order: (1) STRUCTURAL -- JSON Schema on the raw project document, BEFORE any merge; (2) CROSS-LAYER POLICY -- profile ID exists globally, requested value <= machine-defined maximum, other semantic invariants; (3) EFFECTIVE-PROFILE -- construct the canonical effective profile, validate its normal execution-profile invariants, compute the effective digest. Critical warning: do NOT call load_layered_config() directly for this -- it already deep-merges package->user->project by the time it returns, discarding the authority provenance this system needs to know which layer a value came from. Either reuse the lower-level path/YAML loading machinery without its merge step, or (recommended, judged generally useful) add a small new foundation primitive: `@dataclass(frozen=True) class ConfigLayers: package_default: Mapping; user_global: Mapping; project_local: Mapping` -- existing generic config consumers keep calling deep_merge(layers...) themselves; gateway policy code gets the raw, unmerged layers and applies its own authority-aware validation per layer.

**(c) Reject registry_utils.Registry[T] as the published catalog's backing store** (more firmly than the first pass, having now read its actual implementation). Registry[T] provides incremental MUTABLE registration, optional ALIASES, LAZY loading, register()/pop()/reset() -- nearly opposite of what a machine catalog needs: whole-state IMMUTABLE publication, eager full validation, canonical (non-aliased) IDs -- identity here affects capacity counters, profile references, and stale-snapshot checking, so alias semantics need an explicit architectural reason, not incidental reuse of a tool that happens to support them. Use a plain frozen dataclass instead: `@dataclass(frozen=True) class PublishedGatewayCatalog: revision: str; prompts: Mapping[str, Prompt]; roles: Mapping[str, Role]; execution_profiles: Mapping[str, ExecutionProfile]; agents: Mapping[str, AgentDefinition]` (mappings ideally immutable/read-only at runtime). Compilation/validation catches duplicate IDs, missing role/profile/prompt references, and bad execution-profile shapes BEFORE the catalog becomes visible. Bonus finding: foundation/io.py's shared YAML loader already uses `_UniqueKeySafeLoader`, rejecting duplicate YAML mapping keys at parse time -- reduces the marginal value Registry's own collision detection would have added anyway. If one namespace genuinely acquires alias semantics later, Registry[T] could be used internally for JUST that namespace after compilation -- not as the catalog's overall architecture.

**(d) Fewer new abstractions than originally proposed -- evolve the EXISTING ExecutionProfileRegistry Protocol rather than building three new ones.** Do NOT create MachineExecutionProfileStore/ProjectExecutionProfileOverrideStore/EffectiveExecutionProfileResolver as separate public Protocols/classes now -- they were useful for explaining responsibility boundaries in the first design pass, but don't currently earn their own interfaces. Instead: evolve the ALREADY-EXISTING ExecutionProfileRegistry Protocol (it has already earned its existence -- queue/runtime code has a legitimate backend-independent need to resolve effective execution policy) by adding a required project_key keyword parameter: `def resolve_snapshot(self, profile_id: str, *, project_key: ProjectKey) -> ResolvedExecutionProfile`. The machine catalog and project-override YAML repository become IMPLEMENTATION DETAILS inside that one resolver's concrete implementation, not new public interfaces built in anticipation of hypothetical future backends -- that anticipation is premature until the real admin API/DB arrives, which IS the natural point for another backend-boundary Protocol to earn its existence.
Data flow: gateway catalog YAML -> parse + JSON Schema -> graph/policy validation -> PublishedGatewayCatalog (one immutable revision) -> {AgentCatalog read facade, ExecutionProfileRegistry/EffectiveProfileResolver} -- the latter additionally takes ProjectKey -> project override YAML -> schema validation -> policy validation -> ResolvedExecutionProfile.

**ProjectKey: defer building real identity infrastructure entirely for this work.** Use the EXISTING canonical-root convention already established in gateway/service/known_projects.py's _canonical_root() (os.path.abspath) as the interim ProjectKey -- do NOT switch only this subsystem to realpath() and risk the same project acquiring two different identities relative to existing records elsewhere in the gateway. Wrap it in a semantic type so raw path strings don't leak through the API: `ProjectKey = NewType("ProjectKey", str)` with `def project_key(root: Path) -> ProjectKey: return ProjectKey(_canonical_root(root))`. Document explicitly: 'ProjectKey is currently the canonical absolute project-root string. It is an opaque tenant key to consumers; its representation may later become a persistent project ID.' A hash of the path was explicitly considered and rejected -- it would still change when the project moves and would only make debugging harder, with no compensating benefit. This buys the architectural boundary (queue/profile APIs depend on an opaque ProjectKey, not a raw Path) for near-zero infrastructure cost now; a later real project-identity registry can change how the key is produced without touching queue/profile call sites.

ORIGINAL FIRST-PASS DESIGN (still valid at the conceptual/responsibility level, superseded above at the concrete-abstraction level): [see change history / first design consultation req_2380a607ae6a4b9a for the full original text -- one machine catalog + two read-models, typed whitelisted overrides never raw deep_merge, global-capacity always machine-only with project defaults+maxima for project/session capacity, compound staleness identity (profile_id+project_key+machine_revision+project_override_revision+effective_config_digest), the critical warning to never key ScopedCapacityAuthority's scope-keys by the post-overlay effective digest (would silently fragment a shared global-capacity bucket into independent per-project buckets), shadow-mode migration methodology reconciling existing per-project drift before cutover, and the explicit list of rejected approaches -- ALL of this remains architecturally current; only the IMPLEMENTATION SHAPE (how many new Protocols/classes to build right now) was simplified by the follow-up pass.]
