# Output-capture truncation recurred (14,386-char CC47 review persisted as 'CC') despite GP17's fix

## Description

req_73cd33bd26c344e0 (2026-08-17, a CC47 code-review consultation submitted by a concurrent agent session, unrelated to this session's own work) persisted output='CC' -- 2 characters -- even though the real ChatGPT response was 14,386 characters ('CC47 Review — Request changes before implementation...'), confirmed by direct live CDP read of the actual conversation tab (chat-url in the session record: https://chatgpt.com/g/g-p-69cc8c4cc7648191a009f358113d8dd2-audiagentic/c/6a82ef03-fa40-83ec-a13b-a780c89891f7).

This is the same symptom SHAPE as GP16 (superseded, 2026-08-16): a completed request's persisted output was truncated to a tiny fragment of a much longer real response. GP16 was conclusively explained by GP17 (a premature completion witness -- completion-control/message-finalized alone, without corroborating evidence -- let _await_response() capture a still-streaming response as if final) and GP17's fix (requiring corroborating any-of-groups together, not a single witness alone) has been live and validated multiple times since. Yet this incident recurred with the identical symptom shape after GP17 landed.

Ruled out this session (2026-08-17), by direct code reading, NOT reproduction: (1) MCP/transport-layer truncation -- the raw persisted record.json on disk already contains output='CC' at write time, before any status/transport layer is involved (same disambiguation method GP16 itself established); (2) schema-level truncation -- the output field's JSON schema (agent-execution-record.schema.json) has no maxLength/pattern constraint, just type:[string,null]; (3) an obvious bug in the read-side extraction code (_scope_response_snapshot/_response_ref_for_prompt/_facts in turn.py) -- none of it does any string slicing/truncation that could produce a 2-char result from a 14K-char source. The timeline.ndjson for this request shows a realistic ~3m35s duration (11:22:40 to 11:26:15) matching how long the real 14K-char response actually took to generate, NOT an immediate/premature completion -- which argues against a simple 'captured too early' explanation and suggests something more specific: either a transient DOM state (a brief React re-render that momentarily cleared/reset the message content) that happened to coincide with BOTH the initial-candidate AND the independent 6-second-later stability-verification snapshot, or a different, not-yet-identified mechanism entirely.

## Steps

- This cannot be root-caused by further static code reading alone -- it requires either (a) live reproduction with temporary instrumentation added around _await_response()'s terminal-candidate and independent-verification branches (log the exact response_text length/content at every tracker.advance() call, not just the final accepted value), or (b) a second real incident captured with that instrumentation already in place.
- When reproduced, specifically check: does 'CC' appear as a real, momentarily-stable DOM state (e.g. from a citation/reference auto-link collapsing '47' or similar into a widget, transiently changing innerText), or is 'CC' never actually present in the DOM at all (meaning the bug is in Python-side string handling despite this session's read not finding it)?
- Cross-reference against GP38/GP40's candidate-timer reset fixes (also 2026-08-17, later in this session) -- those changed ObservationTracker's CANDIDATE_TERMINAL handling; verify this specific incident predates or postdates those fixes in the gateway process's actual running code (check dispatch-claimed-at against any gateway restart timestamps) since a stale-code-vs-fixed-code distinction could be relevant.
- Consider whether _scope_response_snapshot's message_refs correlation (keyed on prompt_message_id, walking forward to the first assistant ref before the next user ref) could be matching the WRONG assistant ref if messageRefs itself was transiently incomplete on one specific poll -- would require live evidence of messageRefs' actual content at the moment of capture, not available for this historical incident.
