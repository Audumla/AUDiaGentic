# Reconcile abandoned gpt-auto requests to interrupted without touching session lifecycle

## Description

Slice 3 of GP06 (see GP06's notes for full design), depends on the P0 instrumentation slice landing first. A request actively executing when its gateway owner vanishes should become 'interrupted' (the correct terminal state for lost execution ownership -- not 'provider failed', not 'prompt definitely did not complete'). Its durable SESSION must remain active-but-detached, eligible for the EXISTING lazy rehydration mechanism (SessionRuntime.rehydrate_session()) -- do NOT blanket-close active sessions on owner loss, which was the original, now-explicitly-rejected proposal.

## Steps

- Implement request-side reconciliation to 'interrupted' for provably-dead owners, independent of session state.
- Explicitly do NOT modify session-closing logic as part of this slice -- SessionRuntime.shutdown()'s blanket-close-all-sessions behavior (GP06's live-reconfirmed finding C1) is a separate, deliberately deferred problem.
- Only positive evidence the provider conversation itself cannot be reattached should ever terminalize a session -- runtime-owner-loss alone is not that evidence.

## Standards

Keep request and session lifecycles separate, require positive evidence before destructive state transitions, preserve durable-record consistency, and make recovery behavior deterministic and observable.

## Acceptance Criteria

Only requests with positive evidence that their runtime owner is dead are reconciled to interrupted; active or ambiguously owned provider sessions are left untouched. Reconciliation is idempotent, independent of session lifecycle closure, and covered by restart, stale-owner, live-owner, and ambiguous-owner tests.
