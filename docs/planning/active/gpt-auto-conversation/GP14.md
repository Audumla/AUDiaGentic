# Review and clean up the gateway status/state response schema

## Description

The status/state payloads returned by the gateway (agent_task_status, agent_task_gateway_overview, agent_task_session_list, etc.) have grown organically and are messy: odd/inconsistent field naming (mixed hyphen-case and terms that don't clearly convey meaning), duplicated information appearing under multiple keys, and poor functional grouping (related fields scattered rather than nested together by concern -- e.g. timing, provider metadata, watchdog/diagnostics, correlation identifiers). This makes the schema harder to consume correctly and easier to misread during live debugging, which this session did repeatedly tonight.

## Steps

- Inventory the actual current response shapes for agent_task_status, agent_task_gateway_overview, agent_task_session_list, agent_task_list_requests, and agent_task_session_close/control -- collect real examples (this session has several in its transcript/GP04 notes) rather than working from documentation alone.
- Identify duplication (the same fact exposed under two different keys/paths) and inconsistent naming (hyphen-case vs different terminology for the same concept across endpoints).
- Propose a cleaner grouping by functional concern (e.g. identity/correlation, lifecycle/state, timing, provider metadata, watchdog/diagnostics, error) and a consistent naming convention.
- This is a public/consumer-facing contract (MCP tool responses) -- any change needs a compatibility plan (versioned response, deprecation window, or a documented breaking-change contract-version bump) rather than silently changing field shapes under existing callers.

V3 vs V4: response-version 3 is already live (gateway/api.py:560) and includes the progress-disposition/interruptibility vocabulary (AS56). It CANNOT be repurposed. Do NOT reinterpret V3 fields under the same version (project's no-silent-reinterpretation rule).

V4 PUBLIC INFORMATION ARCHITECTURE:
- One-level functional grouping: identity, lifecycle, execution/provider, progress/activity, session, result/error, timing. Group by public use, NOT to mirror storage.
- Remove from V4: persistence contract-version, dispatch fencing (dispatch-owner-epoch/claimed-at), worker ownership/attempt internals, admission-policy internals, retired lane/queue fields (gateway-execution-lane-key, resolved-queue-limits — confirmed build_record drops them at _records.py:418), unless a demonstrated public use case exists.
- Resolve duplicate semantics: exactly ONE public provider-turn-pending (currently 3 paths: _records.py:548-600, progress.py:301-313, session provider.metadata); exactly ONE authoritative transition concept (durable timeline {event,state,timestamp} OR separately-named synthetic e.g. progress.last-observed-at — they must not both be latest-transition); runtime attachment (live) vs durable lifecycle are independent facts (never call runtime-attached 'active').
- Bring ALL gateway response families under explicit projection contracts: status, list-request item, session-list/close/resume, overview, control ack. Control ack stays purpose-specific — must NOT return a session persistence record merely for consistency.
- Every projection passes through AS102's sanitizer. _sparse() (gateway_mcp.py:28-47) removes only None/''/{}/[] — it is NOT a sanitizer; AS102 operates before it.

MIGRATION (own it in GP14; AS92 supplies the request-status schemas):
- Phase A: formalize existing V3 (AS92 declares agent-status; V3 meanings frozen).
- Phase B: explicit V4 opt-in at API boundary; V3 stays compatibility default; selected version explicit in result; unsupported versions FAIL (no silent fallback).
- Phase C: extend versioning discipline across list/session/overview surfaces.
- Phase D: deprecation window — equivalence tests for preserved facts, recorded deliberate removals/renames.
- Phase E: remove V3 only after known consumers migrated.
- NUANCE: security redaction does NOT wait for V4 — a real secret-bearing field is removed as documented hardening, not version evolution.

OVERVIEW: active-count is live-attachment count (sum of s['live'], api.py:1020-1058), not durable-active — real misnomer. V4 uses explicitly-named runtime-attached-count vs durable counts. snake_case keys (total_requests/by_state/recent_failures/providers_loaded/skipped_count) mixed with hyphen-case — normalize to hyphen-case in V4. Do not rename V3's active-count under the same version.

ENVELOPE / SIDECAR PATTERN (2026-08-17 decision — OpenCode-independent):
- The gateway MCP surface returns the canonical response as a named section plus a sibling metadata section: {"result": {canonical V3/V4 response}, "metadata": {allowlisted sidecar}}. This is a transport-surface envelope, NOT a field inside the canonical schema.
- The `result` section stays the strict, versioned AS92/GP14 schema (additionalProperties:false, independently validateable). Harness/deeper metadata must NEVER extend the canonical contract from inside.
- The `metadata` sidecar is a surface-layer concept owned jointly by AS102 (allowlist governs its contents) and the gateway MCP layer. AS92's canonical schema does not know about it.
- Surface-neutral: nothing tied to OpenCode. agent_task_* MCP tools return the envelope; A2A/ACP consume canonical ports as before.
- This is a BREAKING change to MCP tool OUTPUT SHAPE (tools today return the projection dict directly). It is a deliberate, versioned surface change under GP14's endpoint-family cleanup: wrap as {"result", "metadata"} in the same train that formalizes V3/V4, and version it (response-version applies to the `result` section; the envelope wrapper itself is the transport contract).
- Supersedes any earlier plan to carry harness data by extending the canonical V3 schema with a metadata field.

OTHER FINDINGS: gateway_overview's active-count is actually a live-runtime-attachment count (sum of live==True), not a count of durably-active sessions -- misleadingly named 'active'. gateway-execution-lane-key and resolved-queue-limits are explicitly constructed as None under the current architecture (retired concepts) but remain on the public allow-list. overview's total_requests/by_state/recent_failures/providers_loaded/skipped_count are snake_case inside an otherwise hyphen-case API.

RECOMMENDED SHAPE: one-level functional grouping (not deep nesting) -- request/lifecycle/timing/dispatch/admission/provider/session/cancellation/liveness/recovery/result/attempts/metadata as top-level groups. Explicitly warns against over-grouping (e.g. don't dump every timestamp under 'timing' -- dispatch.claimed-at/cancellation.acknowledged-at/liveness.last-activity-at should stay with their functional concept, not get shoved into one giant timing bucket, or you've just relocated the scattering problem). provider-id vs resolved-provider-id should become STRUCTURALLY distinct (admission.provider-id = admission-time candidate vs provider.provider-id = actual execution-time resolved identity) rather than two same-level near-duplicate keys. agent-status's nested identity fields (request-id/session-id/turn-id/etc, already present at top level) should be removed from the nested projection, keeping only its genuinely unique semantic content (lifecycle/outcome/wait-reason/decisions) under lifecycle.canonical.

MIGRATION PATH (explicitly answers the 'is nesting worth the breaking-change cost' question): do NOT ship both flat and grouped representations simultaneously in every response ('technically additive but makes the core problem WORSE during migration -- every fact now has two apparently authoritative locations'). Instead: add an optional response_version parameter at the MCP boundary (None/3 = exact legacy response, 4 = new grouped response), existing callers stay byte-for-byte compatible by default, new callers explicitly opt into V4, only after a documented deprecation window does the default switch, only in a later breaking release does V3 actually get removed. Centralize the V4 projection into explicit functions (project_request_status_v4(), project_request_runtime_status_v4(), project_session_v4(), project_gateway_overview_v4()) rather than ad hoc per-endpoint dict assembly -- this is itself a fix for HOW today's duplication happened (endpoints independently reimplementing similar projections).
