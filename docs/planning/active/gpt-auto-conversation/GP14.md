# Slim canonical gateway status contract

## Description

The status/state payloads returned by the gateway (agent_task_status, agent_task_gateway_overview, agent_task_session_list, etc.) have grown organically and are messy: odd/inconsistent field naming (mixed hyphen-case and terms that don't clearly convey meaning), duplicated information appearing under multiple keys, and poor functional grouping (related fields scattered rather than nested together by concern -- e.g. timing, provider metadata, watchdog/diagnostics, correlation identifiers). This makes the schema harder to consume correctly and easier to misread during live debugging, which this session did repeatedly tonight.

## Steps

- Make agent_task_status and request status/list projections use one compact V4 projector with no response-version negotiation.
- Keep routine status limited to task_id, lifecycle, activity, activity_seq, activity_at, and outcome; diagnostics are explicit and bounded, full response is server-side artifact dereference.
- Reject the retired response-version argument at service/API boundaries; do not emit V3 or dual shapes.
- Add payload-budget, no-preview, no-diagnostics, and endpoint-convergence tests.
- Keep session/overview/control surfaces purpose-specific and migrate callers in the same change.

## Detailed Solution & Technical Design

Current target (2026-08-25): public request polling has one fixed V4 projection. The gateway computes the provider-neutral AS92 snapshot internally, then projects only task_id, lifecycle, activity, activity_seq, activity_at, and outcome. agent_task_status, get_execution_request, list_execution_requests, and timeout status all use this projector. There is no response_version parameter, no V3 fallback, and no dual payload.

Diagnostics are owned by GP48/AS102 and exposed only through the bounded diagnostics operation. Full terminal text is owned by the request artifact store and exposed only through agent_task_response; no path, URI, preview, or artifact locator crosses MCP. Blocking in-process APIs may retain their terminal control record for internal orchestration, but that is not the polling contract.

Durable/session contract versions named v3 are separate persistence protocols and are not public task-status versions. Do not remove them without a storage migration plan.
