# Make gateway restart recover active requests in place

## Description

Make the managed machine gateway restart-safe for non-terminal work. A restart must preserve request IDs and states, transfer owner fencing, rehydrate sessions, and resume queued/running provider work without fresh provider submission.

## Steps

- Add recovery-required to the canonical request record and schema migration path.
- Implement owner-epoch CAS takeover for durable records and active-work index entries.
- Return recovered queued/running work from startup recovery and schedule it before ingress.
- Add provider-session resume_existing plumbing; implement GPT-auto zero-send observation recovery.
- Change managed dashboard restart to lifecycle handoff and preserve retained provider runtimes.
- Update restart/recovery tests and verify migration keeps historical dashboard records readable.

## Detailed Solution & Technical Design

Use durable request ownership epochs plus recovery-required metadata. On startup, atomically take over queued/running records whose owner lease is stale, update the active-work index, and return them to the scheduler. Queued requests are reinserted once; stale worker-backed running work is deferred because it cannot be safely reattached. Running provider-session work remains running and is resumed observation-only through a durable provider-session transport. GPT-auto recovery validates the retained binding while READY, never calls Send again, preserves the original pre-Send baseline, waits through renderer lag for prompt identity, and treats missing checkpoint/capability evidence as nonterminal rather than replaying. Managed restart uses one launch authority: the retiring host launches the replacement, management waits attach-only for a changed owner epoch, and the initiating lease is released before retirement. Historical records migrate missing recovery-required to false on read.
