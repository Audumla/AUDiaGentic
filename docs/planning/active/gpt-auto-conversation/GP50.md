# Accept structurally proven assistant DOM-ID replacement without false request failure

## Description

Live BigCherry request req_8cd2c709a567455c reproduced EXT-GPTAUTO-004 even though the bound conversation contained one user turn, one completed assistant response, 30K+ response text, completion controls, and generating=false. The expected assistant DOM ID was replaced by another ID. Treat the ordered response slot after the exact prompt as authoritative; assistant DOM IDs are mutable renderer identity.

## Steps

- Add a structural same-response-slot replacement predicate requiring the exact prompt anchor, unchanged request user boundary, one assistant in the slot, old ID absent, new ID current, and the bound provider conversation URL.
- Use the predicate in normal response polling and independent terminal verification; adopt and persist the new assistant ID without resubmission or consuming a refresh.
- Keep ambiguous cases in the existing bounded same-conversation recovery path and fail closed for intervening users, multiple assistant nodes, or wrong conversations.
- Add deterministic regression coverage for replacement, terminal verification replacement, foreign/intervening turn, ambiguous coexistence, wrong conversation, and single-submit preservation.

## Detailed Solution & Technical Design

Use message_refs and _response_ref_for_prompt() as the correlation authority. The first assistant after this request's exact user prompt, before any subsequent user, is the request-owned response slot. A replacement is safe only when the snapshot remains on the bound provider conversation (stable project ID plus provider conversation ID), latest_user_id is the exact prompt ID, the prompt occurs exactly once, no user follows it, exactly one assistant follows it, that assistant is the new ID, and the old ID is absent. Do not use global mounted user counts because long conversations virtualize older user nodes. On proof, update GptAutoTurn._response_message_id, PersistentChat's observed assistant identity, and published binding metadata in that order. Do not clear the frozen ID after refresh; do not require the physical CDP target; do not use response-text similarity, counts alone, or fuzzy matching. ID-only churn must not renew model activity or bypass the existing recovery budget: re-establish terminal stability while still executing recovery accounting.
