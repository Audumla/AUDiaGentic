# Rewrite GptAutoTurn._await_response() to resolve against the request-scoped span, not conversation-latest

## Description

Slice 3 of GP08 (see GP08's notes for the full live design consultation) -- the actual hard problem GP08 exists to solve, and the piece the consultation calls 'probably the most important code change.' Depends on GP29 (unified ordered DOM message sequence) and GP24 (durable provider-correlation record) landing first. _await_response() currently biases toward the conversation's LATEST/current assistant observation, which is exactly wrong once a human or another actor posts a later turn into the same session.

## Steps

- Implement the turn-local resolver: a request owns the provider span beginning at its proven user-message anchor and ending immediately before the NEXT user message of any provenance, regardless of who sent it.
- Rewrite _await_response() to run completion/stability logic against resolver.resolve(snapshot).assistant_refs (the request-scoped span), never snapshot.current_assistant_id or global-latest-assistant text.
- mark_assistant_observed() likewise must receive the request-correlated candidate, not the conversation's global latest.
- Implement the three foreign-user-arrival cases fail-closed: (1) own assistant already proven terminal before boundary -> freeze normally; (2) foreign user arrives with assistant content present but not yet proven terminal -> the arrival can serve as a terminal witness for the PRIOR span but must never let the foreign turn's own evidence validate it, freeze ambiguous if can't establish terminality from request-local evidence; (3) foreign user arrives with zero assistant content yet -> freeze immediately as state='boundary-before-response'.
- Freeze ordering for crash-safety: construct complete FrozenProviderCorrelation -> persist via CAS -> publish compatibility ProviderSessionBindingUpdate FROM the frozen result -> only then clear PersistentChat's unresolved-turn recovery metadata -> return terminal SessionTurnResult. Freeze the actual response TEXT, not just IDs, to close the crash window where the answer finalized but the process died before output transitioned.

## Notes

2026-08-17 LIVE CODE-LEVEL DESIGN CONSULTATION (same session as GP24's, see GP24's notes for the CAS/sink half). Key finding: changing only the one `current.latest_assistant_id != baseline.latest_assistant_id` check would NOT actually fix this item -- _await_response() reads global-latest in at least four more places (progress_edge, terminal_candidate, response_message_id/response_text assignment, and the final verification fetch). All of them need to go through a request-scoped projection, not just the one comparison.

**Core primitive** -- define the request's assistant as 'the first assistant message after this request's prompt anchor and before the next user-message boundary' (preserves the GP08 actor-boundary invariant: a later user turn means later assistants cannot belong to this request):
```python
def _response_ref_for_prompt(snapshot: ChatSnapshot, prompt_message_id: str) -> ChatMessageRef | None:
    refs = snapshot.message_refs
    prompt_index = next((i for i, ref in enumerate(refs) if ref.role=='user' and ref.message_id==prompt_message_id), None)
    if prompt_index is None:
        return None
    for ref in refs[prompt_index + 1:]:
        if ref.role == 'user':
            return None  # hard boundary -- belongs to a later turn
        if ref.role == 'assistant':
            return ref  # first assistant in this request's span
    return None
```
Given `userA(ours) -> assistantA(ours) -> userB -> assistantB(later/unrelated)`, this always returns assistantA even once assistantB becomes conversation-global-latest.

**Projection helper** -- rather than rewriting the whole policy engine (which consumes latest_assistant_id/text throughout), project each raw snapshot onto a turn-scoped ChatSnapshot via dataclasses.replace(), so _facts()/existing workflow policies keep working unchanged but see turn-scoped facts:
```python
def _scope_response_snapshot(baseline, snapshot, *, prompt_message_id):
    response_ref = _response_ref_for_prompt(snapshot, prompt_message_id)
    if response_ref is None:
        return replace(snapshot, latest_assistant_id=baseline.latest_assistant_id, latest_assistant_text=baseline.latest_assistant_text), None
    return replace(snapshot, latest_assistant_id=response_ref.message_id, latest_assistant_text=response_ref.text), response_ref
```

**_await_response() rewrite**: every `current = await self.chat.snapshot()` becomes `raw_current = await self.chat.snapshot()` followed by `current, response_ref = _scope_response_snapshot(baseline, raw_current, prompt_message_id=prompt_message_id)`. The first time response_ref becomes non-None, call the new `_publish_correlation_freeze(response_ref)` (GP24's freeze_correlation via the sink) BEFORE setting self._response_message_id -- freeze durable truth first. If response_ref.message_id ever DIFFERS from an already-set self._response_message_id, raise EXT-GPTAUTO-004 with failure-reason='frozen-response-correlation-conflict' -- once frozen, identity is immutable, never silently 'follow latest'. The final verification fetch must ALSO go through _scope_response_snapshot, not a raw snapshot. On terminal, do NOT reassign self._response_message_id again -- verification validates the already-frozen identity, it doesn't assign it.

**Bonus cleanup enabled by the same primitive**: _await_submission_proof() currently sets `self._prompt_message_id = snap.latest_user_id` -- another global-latest read. Should instead select from ordered message_refs via a new `_matching_prompt_ref(baseline, current, expected_text)` helper that finds the first NEW (not in baseline) user ref whose text matches via the existing _matches()/_normal() functions, then calls `_publish_correlation_prompt_anchor(prompt_ref)` (GP24's bind_prompt_anchor) when found. This makes GP30 start response observation from an actual request-specific anchor rather than a global 'last user message' approximation -- closes a second, related global-latest bias in the same file, not just the one this item was originally scoped around.

Depends on GP24's plumbing landing first (needs initialize_correlation/bind_prompt_anchor/freeze_correlation and the sink to exist before turn.py can call them), but GP30 is what actually calls freeze_correlation() for the first time -- see GP24's notes for the critical sequencing constraint (GP24 must NOT wire freeze from the current buggy logic).
