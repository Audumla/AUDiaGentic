# P0: reproduce and instrument the gpt-auto request-record-loss transition

## Description

Slice 2 of GP06 (see GP06's notes for full incident detail), and explicitly the item's own stated highest priority -- must be done BEFORE any general reconciliation mechanism is built. The bigcherry incident showed an admitted request record (constructed and atomically persisted in 'queued' state before enqueue(), per the queue's own contract) becoming absent/unaddressable after a provider-side effect occurred. This is a genuine data-loss defect, not a reconciliation gap, and its exact mechanism is still unknown.

## Steps

- Reproduce the admission -> provider-side-effect -> durable-request-becomes-absent transition deliberately (may require deliberately killing the gateway process mid-turn at controlled points).
- Instrument every step between admission's atomic persist and enqueue() to find exactly where/how the record becomes unavailable.
- Do NOT build a general orphan sweeper until this exact mechanism is understood and fixed at its source.

2026-08-17 CRASH POINT #1 RULED OUT (zero shared-gateway/Brave risk -- disposable child process against a temporary project_root/service_root, per live design consultation). Built a real reproduction harness calling the actual store.build_record()/admit_record()/claim_dispatch()/bind_and_start_owned_attempt() choreography, wrote a durably-fsynced fake provider-side-effect marker, then os._exit(197) immediately after -- the exact production invariant boundary ('admitted request existed -> provider side effect occurred -> durable request became absent') this item exists to explain.

Result: record.json survives completely intact. store.read_record() succeeds (state=running) from a fresh verifier process. Running the REAL recover_gateway_requests() against it correctly transitions it to state=interrupted -- exactly the GP06-designed correct outcome for a request whose owner died mid-flight, not data loss.

This rules out 'process death during/immediately-after the provider side effect, before any post-provider record mutation' as the mechanism -- record persistence and recovery both worked exactly as designed for this specific timing window. Per the consultation's own prediction ('I expect it to survive... at that point, turn the harness into a provenance detector rather than doing more crash timing'), the remaining atomic_write_json os.replace-boundary crash points are lower priority (the consultation predicts they'd survive too, since fsync-before-replace already gives atomicity) and were not run tonight.
