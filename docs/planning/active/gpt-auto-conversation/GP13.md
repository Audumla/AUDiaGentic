# Gateway auto-resumes a closed-but-resumable session transparently, instead of relying on the client to call resume

## Description

Today a client must explicitly detect that a session is closed/non-live and call agent_task_session_resume before it can submit against that session again. This session already found the mechanism that makes resume reliable exists (SessionRuntime.rehydrate_session(), the existing gateway-restart recovery contract confirmed correct in GP06's corrected model), but it is only invoked from specific known call sites -- the client still has to know a session needs resuming and remember to ask for it. Instead, if a session's durable state indicates it IS resumable (a live provider conversation can be reattached, not a terminally-failed one), the gateway should attempt that resume transparently the moment ANY client tries to use the session (e.g. submit against it), rather than requiring the client to pre-check state and explicitly resume first.

## Steps

- Identify every entry point where a client currently submits/controls against a session-id (agent_task_submit with session_id, agent_task_session_control, etc.) and determine where a resumability check + auto-resume could be inserted transparently before dispatch.
- Reuse the existing rehydrate_session() mechanism (GP04/GP06 already document its contract: live handles are process-local, the durable session remains active across a gateway restart, the same provider conversation is reattached in place) -- this item is about WHERE it gets triggered from, not inventing new resume logic.
- Must distinguish 'closed but resumable' (auto-resume is safe and desirable) from 'terminally failed / not resumable' (must still surface as an error, not silently create a new session pretending to be a resume) -- do not blur those two outcomes together.
- Consider whether auto-resume should be opt-in per caller (a flag) or the default behavior for all session-scoped calls -- some callers may want to know explicitly that a resume happened (metadata on the response) even if they didn't have to ask for it.
- Interacts with GP06's session/request reconciliation work -- review together so the two don't duplicate or conflict on what counts as 'resumable'.

2026-08-16 LIVE DESIGN CONSULTATION (gpt-auto-agent):

Critical correction: submit continuation already auto-rehydrates non-live active sessions in _dispatch_session_request(). GP13 must unify activation, not blur two distinct operations:

**Rehydrate** = durable generation active, only process-local handle lost; same gateway session_id, same binding, same provider conversation.
**Resume** = durable generation terminal (closed/expired/failed); creates new gateway session generation with new session_id and RESUMED_FROM binding.

**Architecture (a): Single choke point via SessionActivation service**
Extract activation logic into gateway/session/activation.py with SessionUse enum (NEW_TURN, TURN_CONTROL, CLOSE), ResumePolicy enum (AUTO, REQUIRE_LIVE), ActivationKind enum (ALREADY_LIVE, REHYDRATED, RESUMED), and SessionActivation dataclass tracking kind, requested_session_id, effective_session_id, source_state, source_binding_id, effective_binding_id.

Implement ensure_session_for_use(project_root, requested_session_id, runtime, use, resume_policy, execution_context, operation_id) -> SessionActivation. Both submit and session-control paths call it:
- submit: agent_task_submit → submit_execution_request → queue → _dispatch_session_request → ensure_session_for_use(NEW_TURN)
- controls: agent_task_session_control → control_execution_session → execute_once() → ensure_session_for_use(TURN_CONTROL/CLOSE)

For controls, activation must occur inside execute_once()'s dispatch closure for idempotency; a replay returns original activation+outcome.

**Classification (b): Durable state without duplicating GP06 validation**
Classify from: active→LIVE (if runtime available) else REHYDRATE; closed/expired→TRY_AUTO_RESUME; failed→TERMINAL_FAILURE; closing→NOT_USABLE_YET. Do NOT duplicate validate_resume_eligibility(); once classified as auto-resume candidate, delegate to existing resume path which checks: usable provider binding, RESUME_BY_REF capability, validated evidence, surface/ref compatibility, identity/execution context.

Key policy: automatic resume eligible only for closed/expired; failed requires explicit resume (hides meaningful terminal failure). Do not use close_reason for eligibility (diagnostics only); GP06 says gateway restart should not terminalize active sessions. Separation: GP06→rehydrate same generation; normal close/expiry→validate+resume successor; provider failure→no transparent resume.

**Control exception (b cont.)**: For session-control actions (cancel-turn, interrupt-turn, steer-turn, respond-permission, close-session) against closed session: steer-turn(X) on ses_B (auto-resumed from ses_A) is not equivalent to X on ses_A. Activation policy is operation-sensitive:
- active+handle_missing → REHYDRATE (safe for all)
- closed/expired+NEW_TURN → AUTO_RESUME_SUCCESSOR
- closed/expired+CLOSE_SESSION/other controls → ALREADY_TERMINAL (reject)

**Policy (c): Auto by default, with require-live opt-out**
For new-turn against explicit session_id: session_resume_policy = "auto" (default, unconditional). Add strict mode: enum with "auto" (default) and "require-live" (never create successor transparently). Prefer enum over boolean for extensibility. Persist policy on durable request (not transient option only); after gateway restart, same request retains same side-effect policy. Explicit agent_task_session_resume API remains for intentional failed-source retry, operator-directed resume, explicit generation control, diagnostics.

**Response (d): Expose successor activation**
Rehydration: session-id=ses_A, effective=ses_A, same binding. Resume: session-id=ses_B (effective), session-activation projection with kind ("resumed"), requested-session-id (ses_A), effective-session-id (ses_B), source-state ("closed"), binding-relation ("resumed-from"). Include public binding projection with binding-id, relation, predecessor-binding-id. Do NOT alias ses_A→ses_B; preserves immutable-generation model. For rehydration, only expose kind/requested/effective if rehydration occurred (not all responses need activation).

**Critical ordering constraint**: When auto-resume creates ses_A→ses_B, durably retarget owned running request to ses_B before sending prompt. Use update_owned_running_session() (or sibling retarget_owned_running_session) with requested_session_id, effective_session_id, activation_kind fencing under owner_epoch+worker_id+attempt_epoch. Sequence: (1) durable request admitted, (2) resolve activation, (3) resume provider→ses_B, (4) durably retarget to ses_B, (5) persist activation/lineage, (6) send prompt through ses_B. Async agent_task_submit initial response cannot expose auto-resume yet; later status/wait/final results can after dispatch resolves it.

**Concurrency fix (AS49 weakness)**: Resume's idempotency has check-then-act gap; two simultaneous resume requests can race. With GP13, two clients submitting same closed source must not create ses_new_1 and ses_new_2. Implement per-source cross-process activation/resume reservation in ensure_session_for_use(): with source_session_resume_reservation(source_session_id), check successful_successor(source_session_id), reuse if exists, else resume+persist. Binding index already rejects duplicate owned bindings as defense-in-depth; converge concurrent requests onto one successor.

**Acceptance invariant**: "A caller may address the last known gateway session generation. The gateway may transparently restore runtime attachment to that same active generation, or—only for new-turn against safely resumable closed/expired generation—create exactly one RESUMED_FROM successor. It never automatically resumes failed, never aliases predecessor session_id to successor, always exposes effective generation used." Meshes cleanly with GP06: GP06 decides durable session lifecycle after runtime loss; GP13 decides how attempted use materializes runtime/provider attachment. Share durable lifecycle facts, no reconciliation duplication.
