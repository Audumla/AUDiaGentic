# Gateway auto-resumes a closed-but-resumable session transparently, instead of relying on the client to call resume

## Description

Today a client must explicitly detect that a session is closed/non-live and call agent_task_session_resume before it can submit against that session again. This session already found the mechanism that makes resume reliable exists (SessionRuntime.rehydrate_session(), the existing gateway-restart recovery contract confirmed correct in GP06's corrected model), but it is only invoked from specific known call sites -- the client still has to know a session needs resuming and remember to ask for it. Instead, if a session's durable state indicates it IS resumable (a live provider conversation can be reattached, not a terminally-failed one), the gateway should attempt that resume transparently the moment ANY client tries to use the session (e.g. submit against it), rather than requiring the client to pre-check state and explicitly resume first.

## Steps

- Identify every entry point where a client currently submits/controls against a session-id (agent_task_submit with session_id, agent_task_session_control, etc.) and determine where a resumability check + auto-resume could be inserted transparently before dispatch.
- Reuse the existing rehydrate_session() mechanism (GP04/GP06 already document its contract: live handles are process-local, the durable session remains active across a gateway restart, the same provider conversation is reattached in place) -- this item is about WHERE it gets triggered from, not inventing new resume logic.
- Must distinguish 'closed but resumable' (auto-resume is safe and desirable) from 'terminally failed / not resumable' (must still surface as an error, not silently create a new session pretending to be a resume) -- do not blur those two outcomes together.
- Consider whether auto-resume should be opt-in per caller (a flag) or the default behavior for all session-scoped calls -- some callers may want to know explicitly that a resume happened (metadata on the response) even if they didn't have to ask for it.
- Interacts with GP06's session/request reconciliation work -- review together so the two don't duplicate or conflict on what counts as 'resumable'.
