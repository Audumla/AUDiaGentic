# Correctly correlate responses when multiple actors submit into the same session serially

## Description

CORRECTED 2026-08-16 (same reused session, gpt-auto's own account of the incident): the original hypothesis -- that the coordinating agent misdiagnosed a perfectly complete response as truncated -- is FALSE. The AS36 premature-halt flag was correct; the response to the original GP04-GP07 review request genuinely terminated prematurely at "Progress lease:". What actually happened, in order: (1) original review request answered, truncated mid-response; (2) the user's manual "recheck against the new push" message arrived as a separate user turn, acted on immediately; (3) the coordinator's "continue from where you left off" request arrived as a THIRD, later user turn; (4) because that message explicitly named the cutoff text ("Progress lease:"), gpt-auto could unambiguously resolve which earlier thread to resume. Had the message just said "continue", it would have been genuinely ambiguous which of two candidate continuations was meant. gpt-auto has NO actor provenance -- it cannot distinguish a gateway-submitted turn from a human typing directly into the tab; both are just user messages in the same conversation. So the real, confirmed problem is not that the human's message caused confusion by coincidence -- it's that natural-language/recency-based continuation resolution is fundamentally unsafe once more than one actor can post serially into a session, and request-ID-based machine correlation is required instead of relying on conversational deixis ("continue", "that response", etc).

## Steps

gpt-auto's own recommendation (2026-08-16, live consultation): BUILD THIS NOW, but only a deliberately small serial-correlation substrate -- not general multi-writer/concurrent-session machinery, not human-input interception, not preemption. Those remain an explicit, documented future limitation, not this item's scope.

Define "serial" precisely: a subsequent actor may submit only AFTER the provider has actually terminalized the preceding turn (the gateway need not yet have finished retrieving/processing that result). This supports: A submitted -> A finishes at provider -> H submitted manually -> H processing -> gateway asks "what was A's result?" and must still get it. It explicitly does NOT support: A still generating -> human submits H concurrently -- that overlap must be detected and marked `external-interleaving-during-active-turn` / `correlation-ambiguous` with evidence preserved for later reconciliation, never guessed at.

Minimum architecture (moderate extension of existing machinery, not a new subsystem):
1. Provider conversation cursor: gpt-auto currently exposes only `latestAssistantId`/`latestAssistantText` for assistants (though it already tracks an array of recent user message IDs) -- extend this to a bounded ORDERED sequence of provider messages for both roles: {role, provider-message-id, ordering/index, text digest/availability}.
2. Persist a turn-correlation envelope PER gateway request (not one mutable "current unresolved turn" slot as today): provider-session-id, prompt-message-id, baseline preceding message IDs/cursor position, correlated assistant message ID(s), terminal correlation state. Much of this is already tracked as session-recovery metadata; make it explicitly request-addressable.
3. Treat any user-message ID not issued by this gateway/session as `external-turn-observed` -- classify it as foreign, don't attempt to identify who/what it was.
4. Correlate a response to its PROMPT SPAN, not to "whatever is the latest DOM node right now" -- and do not assume one logical response equals exactly one assistant DOM node (E3 already proved a single logical turn can produce multiple/transient assistant nodes; GP04's "last assistant node" selection can latch onto a transient/empty one).
5. Once a gateway response is terminal, FREEZE its result. Subsequent turns from any actor must have zero effect on retrieving request A's result -- `get_result(req-A)` must read from A's own immutable correlated result, never by re-querying "what does the live conversation currently show as latest."
6. Resynchronize before every new gateway submission: observe the provider cursor first, advance the baseline past any external turns observed since the last gateway turn, record them as foreign history, then begin the new request from that exact provider position.

Split acceptance criteria into two cases (this bounds the scope): Case A -- result already terminalized and captured by the gateway before any later turn arrived: must be near-trivial, no live-DOM lookup needed at all, later provider activity must never alter the stored result. Case B -- provider completed request A's turn, but the gateway had not yet finished correlating/capturing it when a later serial turn (from any actor) arrived: this is the actual hard problem GP08 exists to solve, via the conversation cursor + correlation envelope above.

Share one new primitive with GP07 rather than building this independently: `ProviderConversationObservation` (conversation_id, observation_generation, ordered_message_refs[] with role/message_id/sequence/content_fingerprint/structural_fingerprint). GP07 uses it to judge whether the current correlated turn is still progressing vs terminal; GP08 uses it to determine which historical turn belongs to which request; GP04's unresolved-turn recovery and E3-style multi-assistant-node handling both benefit from the same representation. Building these independently would mean reworking the same message-identity layer twice.

Relationship to PC14 (resumability): keep these as two INDEPENDENT capabilities/invariants, not one. PC14 answers "can I reconnect to this conversation?" GP08 answers "after reconnecting, can I correctly identify which provider messages correspond to each of my requests?" A session can be perfectly resumable (PC14=yes) even though a human added five turns since the gateway last saw it -- resumability does not imply the gateway's cached view of history is current. Sequence on resume/rehydration: prove provider conversation exists -> resumable=yes (PC14) -> reconcile provider conversation cursor -> discover external turns -> establish new baseline -> admit next gateway prompt (GP08).

Correct the incident record before using it as motivating evidence: the truncation was real (AS36 correct); the human's message did not CAUSE it -- it exposed the correlation gap by becoming an intervening serial turn before the coordinator's own continuation request arrived. Still worth inspecting the actual provider message-ID/DOM sequence (as originally planned) -- not to re-litigate whether the response was complete, but as concrete implementation evidence for how three interleaved user/assistant spans actually appear at the provider layer.

## Detailed Solution & Technical Design

This item exists because a real production incident, not a synthetic test, showed the gap: this session's own coordinating agent had no way to detect that a third actor (the human user, via direct browser interaction) had inserted a message into the same conversation between two of the agent's own gateway-submitted requests, and misdiagnosed the resulting conversation state as a bug (premature response truncation) rather than correctly attributing it to legitimate multi-actor interleaving. The synthetic E2/E3 out-of-sequence-injection tests earlier this session probed a related but narrower case (foreign injection during a single turn's lifecycle); this item is broader -- it is about correlation and retrieval identity across an entire session's lifetime when more than one actor can legitimately post into it, serially, at unpredictable times.

## Notes

2026-08-16 LIVE DESIGN CONSULTATION (gpt-auto-agent, session ses_b2b8867d882649d2, req_f3d2653b17494f53, completed cleanly in 475.9s -- first successful long consultation after the GP15 stall-timeout fix + gateway restart). Concrete slice 2/3 design:

Ownership split: the GATEWAY REQUEST RECORD owns correlation truth (not PersistentChat, not the session binding, not another mutable 'current turn' field). GptAutoTurn owns the live resolver. PersistentChat keeps mark_prompt_submitted()/mark_assistant_observed()/clear_unresolved_turn()/_reconcile_unresolved_turn() but their MEANING changes to 'session-level recovery hint,' no longer the authoritative correlation answer.

Slice 2 data shape -- provider-neutral dataclasses (ProviderMessageRef{role,message_id,sequence}, ProviderCorrelationBaseline{provider_session_id,message_refs,prompt_digest,captured_at}, ProviderPromptAnchor{provider_session_id,message_id,sequence}, ProviderCorrelationBoundary{role='user',message_id,sequence,reason='unexpected-user-message'}), persisted as a new internal top-level 'provider-correlation' field on the gateway request record (components/agents/gateway/store), with three write-once slots (baseline -> +prompt_anchor -> +frozen_result) each mutated via compare-and-set (initialize_correlation/bind_prompt_anchor/freeze_correlation: write if absent, no-op if idempotent replay, raise CorrelationConflict otherwise) -- no 'update frozen correlation' operation exists at all once frozen. Dependency direction preserved via a new ProviderTurnCorrelationSink callback (mirrors the existing ProviderSessionBindingUpdate pattern) injected by the gateway when building the transport, so gpt_auto never imports gateway internals directly. Handy existing fact: SessionRuntime.prompt_in_session() already sets SessionPrompt.turn_id=request_id, so GptAutoTurn.turn_id IS the gateway request ID already -- no new correlation identifier needed.

Real gap found in the ALREADY-MERGED slice 1 (via direct code reading, not speculation): ChatSnapshot's user_message_ids/texts and assistant_message_ids/texts are two SEPARATE per-role arrays, not one true DOM total order -- so slice 1 cannot currently distinguish 'A-A then U-human' from 'U-human then A-A' when both appear in the same poll, which is exactly the ordering slice 3's boundary rule depends on. Recommended small extension: walk user+assistant DOM nodes together in one pass (_SNAPSHOT_FN in gpt_auto_cdp.py) producing a single ChatMessageRef{role,message_id,text,sequence} sequence; ChatSnapshot gains message_refs: tuple[ChatMessageRef,...] with the existing 4 arrays derivable from it for compatibility. Also fixes a second latent bug: IDs and text are currently collected via separately-filtered passes, so an empty/transient text node can desync the id/text array pairing.

Slice 3 resolver -- turn-local (owned by GptAutoTurn, not a second durable state machine; restart just needs the durable envelope + a fresh observation). Core rule: 'a request owns the provider span beginning at its proven user-message anchor and ending immediately before the NEXT user message of any provenance' -- you never need to classify WHO sent the boundary message, just that it's not this request's own prompt. Algorithm: find prompt_message_id's index in the unified ref sequence, walk forward collecting assistant refs until the next user ref (the boundary) or end-of-sequence. Baseline is captured via a forced-fresh snapshot BEFORE the browser side effect (durable-write-before-side-effect ordering: request admitted -> correlation baseline durable -> THEN browser submission), which also naturally handles a human posting before request B: B's resync baseline just includes those messages already. Prompt-proof tightened: match only a NEW user message (not in baseline) whose text fingerprint equals the prompt digest -- prevents an old identical prompt elsewhere in the conversation from being misattributed; 0 matches keeps observing, 2+ matches fails ambiguous.

Three foreign-user-arrival cases, all fail-closed by construction: (1) own assistant already proven terminal before the boundary appears -> freeze normally, the foreign message is irrelevant; (2) foreign user arrives with assistant content present but not yet proven terminal -> the foreign arrival CAN serve as a terminal witness for finalizing the PRIOR assistant span (since a new user turn structurally proves the provider moved on), but must never let signals derived from the human's OWN turn retroactively validate the prior response -- if terminality can't be established from request-local evidence, freeze as ambiguous rather than borrow the foreign turn's evidence; (3) foreign user arrives with ZERO assistant content yet for this request -> freeze immediately as state='boundary-before-response', assistant_message_ids=(), the foreign turn's own assistant response is NEVER a candidate regardless of content.

Critical code-level correction, called out as 'probably the most important code change': _await_response() currently biases toward the conversation's LATEST/current assistant observation (fine when AUDiaGentic is the only actor, exactly the bug when a human posts later) -- must be rewritten to run completion/stability logic against resolver.resolve(snapshot).assistant_refs (the request-scoped span), never snapshot.current_assistant_id or global-latest-assistant text. mark_assistant_observed() likewise must receive the request-correlated candidate, not the conversation's global latest.

Freeze ordering (crash-safety): (1) construct complete FrozenProviderCorrelation, (2) persist the freeze via CAS, (3) publish a compatibility ProviderSessionBindingUpdate FROM the frozen result, (4) only then clear PersistentChat's unresolved-turn recovery metadata, (5) return the terminal SessionTurnResult -- freeze truth BEFORE clearing the recovery hint, so a mid-sequence crash still leaves durable correlation intact. Recommends freezing the actual response TEXT too (not just IDs) -- closes a crash window where the provider answer finalized, IDs got frozen, but the process died before the gateway's own output transitioned; also preserves ALL assistant DOM node ids/texts (multi-node turns, per E3) separately from canonical_response_message_id/response_text (the ONE logical answer the completion engine actually selected) -- don't make future consumers reconstruct the logical answer by concatenating arbitrary nodes.

Concrete modification points handed to an implementer: gpt_auto_cdp.py (_SNAPSHOT_FN/GptAutoCdp.snapshot() -- add unified ordered observation), snapshot.py (ChatSnapshot -- add message_refs, derive existing arrays from it), chat.py (PersistentChat.snapshot()/find_prompt_snapshot() carry the unified sequence through; mark_prompt_submitted/mark_assistant_observed/clear_unresolved_turn/_reconcile_unresolved_turn become recovery-only), turn.py (GptAutoTurn -- initialize baseline pre-submission, bind anchor on prompt proof, rewrite _await_response() to resolve only the post-anchor/pre-boundary span, freeze before clearing unresolved state, _publish_message_ids() becomes a projection of the frozen result).
