# Correctly correlate responses when multiple actors submit into the same session serially

## Description

A real live incident (2026-08-16, session ses_caaace36a7be4c88) demonstrated this directly: the coordinating agent submitted a review request through the gateway, then submitted a follow-up "continue from where you left off" request believing the prior response had been truncated. In between, the user independently pushed the repo and manually typed a message directly into the same ChatGPT tab (outside the gateway entirely) telling gpt-auto to recheck against the new commit. The agent had no visibility into that manual, out-of-band message and misdiagnosed the review's ending ("...Progress lease:") as a premature cutoff (reinforced by the AS36 terminal-quality classifier's automated premature-halt-suspected flag) when the user believes it may actually have been the complete, correct end of the response to the ORIGINAL request -- with the user's own message and the agent's own "continue" follow-up both landing afterward, into the same conversation, from two different, uncoordinated actors. This is not a hypothetical -- it happened during this session's own real work.

## Steps

- Document the constraint explicitly: for now, do NOT attempt to interrupt or preempt an ongoing/in-flight response -- this item is about correlation and retrieval across SERIAL multi-actor submissions into one session, not concurrent/interrupting access. Concurrent interruption handling is explicitly out of scope for this pass and may be revisited later.
- Core requirement (the user's own framing): must still be able to correctly retrieve the response to a specific previously-submitted request, even if a NEW task (from any actor -- the same agent, a different agent/session, or a human typing directly into the tab) has since been submitted and is now being processed in the same session/conversation. Losing or conflating that correlation is the failure mode to prevent.
- Distinguish two related but different sub-problems: (a) the gateway's OWN turn serialization (README already documents: "the Gateway serializes turns within one session; the provider adds no second queue") only governs turns submitted THROUGH the gateway -- it has no visibility into or control over a human manually typing into the same underlying browser tab, which is a real, uncontrolled second write path into the same conversation. (b) even for gateway-submitted turns, when a new request is submitted while a caller is still trying to retrieve/wait-for the response to an earlier one (e.g. the agent's "continue" follow-up landing while it hadn't yet fully processed the outcome of the original request), correlation must not get confused.
- Assess whether the existing prompt-message-id / assistant-message-id correlation machinery already built for GP04's unresolved-turn reconciliation (prompt-ID-first, bounded prompt-text fallback) is sufficient to solve this, or whether it needs extension to handle a THIRD-PARTY message landing between a submitted prompt and its retrieval, not just between submission and completion of the same request.
- Live evidence to gather: re-examine the actual DOM/message sequence in ses_caaace36a7be4c88's underlying ChatGPT conversation (provider-session-id 6a80580a-d590-83ec-be33-dea358026731) to determine what really happened -- was the "Progress lease:" ending genuinely the complete answer to the original request, with the user's manual message and the agent's continuation request both arriving afterward as separate, later turns? This is directly answerable by inspecting the real message sequence/IDs, the same technique used to correct the E1/E2/E3 misdiagnoses earlier this session.
- Ask gpt-auto directly (via the same reused session, since it is a live participant in the exact incident) whether this is something worth building support for now, or should remain a documented known-limitation for later, and what design it would recommend given it has first-hand context on how the interleaving actually looked from its side.

## Detailed Solution & Technical Design

This item exists because a real production incident, not a synthetic test, showed the gap: this session's own coordinating agent had no way to detect that a third actor (the human user, via direct browser interaction) had inserted a message into the same conversation between two of the agent's own gateway-submitted requests, and misdiagnosed the resulting conversation state as a bug (premature response truncation) rather than correctly attributing it to legitimate multi-actor interleaving. The synthetic E2/E3 out-of-sequence-injection tests earlier this session probed a related but narrower case (foreign injection during a single turn's lifecycle); this item is broader -- it is about correlation and retrieval identity across an entire session's lifetime when more than one actor can legitimately post into it, serially, at unpredictable times.
