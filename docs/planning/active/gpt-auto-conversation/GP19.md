# Submission-proof starves after one failed text-match, even while real generation is visibly happening

## Description

Real live incident reported 2026-08-16 from a DIFFERENT concurrent agent session: EXT-GPTAUTO-003 submission-proof-not-observed-before-deadline fired while the error's own diagnostic details showed generating:true and assistant-text-length:3690 (growing) -- unambiguous proof the prompt WAS submitted and ChatGPT was actively writing a real, substantial answer at the exact moment our own automation gave up waiting for submission proof. The answer was not lost -- it kept generating after the tool call already returned an error to the caller.

## Steps

Root cause traced via static code reading of _await_submission_proof() (turn.py:517+), same night as GP15's closely related discovery: this is the SAME level-vs-edge-triggering starvation class, in the submission-proof phase instead of response-completion.

- new_msg = _new_user_message(baseline, snap) compares against the FIXED baseline (never resets across polls) -- so it stays true forever once a new user message appears, contributing nothing further by itself.
- user_id_changed = snap.latest_user_id != previous_user_id IS correctly edge-triggered against the previous poll -- so EvidenceCapability.PROGRESS (which requires new_msg AND user_id_changed together) can only ever fire ONCE, on the exact poll where the new user message first appears.
- text_matches = new_msg and _matches(expected, normalized submitted text) is an EXACT text comparison against the originally-requested prompt body. If this fails on that same first poll (plausible for long prompts: ChatGPT's own UI renders long user messages as collapsible/truncated, and _normal()'s text extraction may not perfectly reconstruct what the DOM actually shows for a long collapsed message -- see the existing userText() comment in gpt_auto_cdp.py about collapsible user-message content), EvidenceCapability.TERMINAL_WITNESS is never granted.
- From the SECOND poll onward: new_msg stays true (useless, compared to stale baseline) but user_id_changed is now false (previous_user_id was updated to match at the end of the first iteration) -- PROGRESS never fires again. If snap.generating stays continuously True with no toggling (exactly what real, sustained generation looks like), soft_changed is also false on every subsequent poll -- SOFT_LIVENESS never fires again either. Capabilities are permanently EvidenceCapability.NONE from poll 2 onward, starving the tracker into AWAITING_EVIDENCE/SUSPECT_STALLED timeout even while the assistant is visibly, genuinely writing a real answer.
- Likely connects to the 'composer-typed-text-mismatch' pattern observed earlier the same night across multiple real failures on long prompts (3400-7300 chars) -- worth confirming this is the SAME underlying text-matching gap, not a coincidence, by comparing the exact typed-text-length vs expected-prompt-length deltas already captured in those earlier incidents against what _matches()/_normal() would actually produce for that text.
- Fix direction, mirroring GP15's fix shape: (a) _matches()'s exact-comparison requirement is too strict for long/collapsible prompts -- consider a more tolerant match (e.g. prefix/fingerprint match, or matching against the collapsed/truncated DOM representation ChatGPT actually shows rather than the full original text) as an alternative TERMINAL_WITNESS path; (b) independently, fix the starvation itself -- sustained (not just newly-appearing) generating=True should count as at least SOFT_LIVENESS on every poll while it remains true, not just on the one poll where it first became true, so a real, continuing generation can never be mistaken for silence regardless of whether text-matching ever succeeds.

ROOT CAUSE RANKING (revises this item's own earlier hypothesis): ranks Markdown-source-to-rendered-DOM-text transformation HIGHER than the collapsible-wrapper theory as the likely cause -- _matches()/_normal() require the DOM-extracted text to equal the submitted source character-for-character, but gpt_auto_cdp.py extracts innerText/textContent from the RENDERED message, and ChatGPT's renderer strips Markdown presentation syntax (backticks, emphasis markers, link syntax leaving only link text, etc.) -- 'Call `execute_campaign_lane()` and use **exactly** this:' renders as 'Call execute_campaign_lane() and use exactly this:'. Directly matches this item's own real incident: RE16-style prompts are exactly the kind with heavy backtick/identifier/Markdown content. Whitespace-collapse (the digest fallback) cannot repair deleted Markdown delimiters, explaining why BOTH matchers failed. The collapsible-wrapper theory remains a real secondary suspect (innerText vs textContent priority may still expose only a partial/visible projection for a collapsed message) -- recommends instrumenting innerTextLength vs textContentLength to confirm live.

THIRD, INDEPENDENT LATENT BUG FOUND: boundedText()'s .slice(0, 20000) in gpt_auto_cdp.py applies to text used for CORRELATION, not just display -- a >20K prompt can never satisfy exact-equality correlation even with otherwise-perfect DOM extraction. Didn't cause tonight's specific 3400-7300 char incidents but is a real latent defect GP19 should fix while in this code.

RECOMMENDED DESIGN (large, three-part, NOT to be treated as a single matcher tweak):
1. Complete-content acquisition: prefer the collapsible-content node, read BOTH innerText and textContent (don't let innerText silently win when non-empty), remove the 20K truncation from the correlation path (display truncation can stay separate), expose extraction evidence (contentNodeFound, visibleLength vs contentLength) for diagnostics.
2. ONE shared prompt-correlation primitive (new gpt_auto/prompt_correlation.py) replacing the THREE currently-inconsistent 'same prompt' definitions found live in the code: turn.py's _matches() (strict equality), chat.py's _same_prompt() (stripped equality, used by find_prompt_snapshot()), and chat.py's _prompt_text_digest() (whitespace-collapsed SHA-256, used by unresolved recovery). Proposed: PromptFingerprint (versioned: raw_digest, token_count, token_digest, head_digest/tail_digest of first/last ~16 lexical tokens, bounded 5-token shingle-hash sketch) + PromptMatchQuality (EXACT/STRUCTURAL/INCOMPLETE_VIEW/MISMATCH) + PromptMatch.proves_identity property. Structural tokenization strips Markdown presentation delimiters (backticks/asterisks/#/etc.) while keeping words/identifiers/numbers -- NOT fuzzy edit-distance. Explicitly rejects prefix-only or suffix-only matching as a TERMINAL_WITNESS-grade signal (a false positive here is worse than an unresolved turn, especially given GP08's concurrent-actor requirements -- two different prompts sharing a long common prefix must never cross-match). Head+tail+internal-shingle triple defends against three distinct false-match shapes (unrelated-but-overlapping-opening, dangerous-long-common-prefix, same-opening-different-middle-same-footer). Persist the fingerprint (not the prompt body) at the SAME point turn.py already marks the checkpoint before Send, so restart-recovery has the same evidence live observation had -- keep prompt-text-digest temporarily for backward compatibility with already-persisted sessions. Recovery's matching loop should use the SAME match_prompt()/find_unique_prompt_match() primitive, preserving the existing good invariant that repeated identical prompts stay ambiguous rather than guessed.
3. INDEPENDENT starvation fix (do this regardless of matcher quality, it's cheap and correct on its own): sustained generating=True should grant SOFT_LIVENESS on every poll (not just the edge), AND growing assistant text (latest_assistant_id/text changing) should count as PROGRESS -- because unlike a stuck stop-button, actually-changing provider output is real evidence of continued activity. Explicitly NOT identity proof though (GP08 boundary: a human typing in the same tab could also produce generating=True + growing text, so activity evidence must never by itself set _prompt_message_id or otherwise claim the turn's identity is resolved). This turns the incident chain from 'one failed match -> all evidence NONE forever -> false timeout' into 'prompt matcher imperfect but activity lease stays alive -> eventually the matcher succeeds (or the turn is still correctly reported as unresolved-but-alive rather than falsely dead)'.

EXTENSIVE validation case list provided (15+ scenarios: plain short prompt exact match, RE16-style heavy-markdown prompt, fenced code blocks, headings/lists/blockquotes/links, 7-10K collapsed message, innerText-vs-textContent-partial simulation, 20K prompt, shared-long-prefix-different-ending must-not-false-match, shared-head-tail-different-middle shingle-rejection, repeated-identical-prompt-stays-ambiguous, foreign-message-not-associated (GP08 boundary), restart-recovery-finds-same-fingerprint, sustained-generating-does-not-starve, growing-text-is-progress-not-identity) -- use these directly when implementing.
