# Submission-proof starves after one failed text-match, even while real generation is visibly happening

## Description

Real live incident reported 2026-08-16 from a DIFFERENT concurrent agent session: EXT-GPTAUTO-003 submission-proof-not-observed-before-deadline fired while the error's own diagnostic details showed generating:true and assistant-text-length:3690 (growing) -- unambiguous proof the prompt WAS submitted and ChatGPT was actively writing a real, substantial answer at the exact moment our own automation gave up waiting for submission proof. The answer was not lost -- it kept generating after the tool call already returned an error to the caller.

## Steps

Root cause traced via static code reading of _await_submission_proof() (turn.py:517+), same night as GP15's closely related discovery: this is the SAME level-vs-edge-triggering starvation class, in the submission-proof phase instead of response-completion.

- new_msg = _new_user_message(baseline, snap) compares against the FIXED baseline (never resets across polls) -- so it stays true forever once a new user message appears, contributing nothing further by itself.
- user_id_changed = snap.latest_user_id != previous_user_id IS correctly edge-triggered against the previous poll -- so EvidenceCapability.PROGRESS (which requires new_msg AND user_id_changed together) can only ever fire ONCE, on the exact poll where the new user message first appears.
- text_matches = new_msg and _matches(expected, normalized submitted text) is an EXACT text comparison against the originally-requested prompt body. If this fails on that same first poll (plausible for long prompts: ChatGPT's own UI renders long user messages as collapsible/truncated, and _normal()'s text extraction may not perfectly reconstruct what the DOM actually shows for a long collapsed message -- see the existing userText() comment in gpt_auto_cdp.py about collapsible user-message content), EvidenceCapability.TERMINAL_WITNESS is never granted.
- From the SECOND poll onward: new_msg stays true (useless, compared to stale baseline) but user_id_changed is now false (previous_user_id was updated to match at the end of the first iteration) -- PROGRESS never fires again. If snap.generating stays continuously True with no toggling (exactly what real, sustained generation looks like), soft_changed is also false on every subsequent poll -- SOFT_LIVENESS never fires again either. Capabilities are permanently EvidenceCapability.NONE from poll 2 onward, starving the tracker into AWAITING_EVIDENCE/SUSPECT_STALLED timeout even while the assistant is visibly, genuinely writing a real answer.
- Likely connects to the 'composer-typed-text-mismatch' pattern observed earlier the same night across multiple real failures on long prompts (3400-7300 chars) -- worth confirming this is the SAME underlying text-matching gap, not a coincidence, by comparing the exact typed-text-length vs expected-prompt-length deltas already captured in those earlier incidents against what _matches()/_normal() would actually produce for that text.
- Fix direction, mirroring GP15's fix shape: (a) _matches()'s exact-comparison requirement is too strict for long/collapsible prompts -- consider a more tolerant match (e.g. prefix/fingerprint match, or matching against the collapsed/truncated DOM representation ChatGPT actually shows rather than the full original text) as an alternative TERMINAL_WITNESS path; (b) independently, fix the starvation itself -- sustained (not just newly-appearing) generating=True should count as at least SOFT_LIVENESS on every poll while it remains true, not just on the one poll where it first became true, so a real, continuing generation can never be mistaken for silence regardless of whether text-matching ever succeeds.
