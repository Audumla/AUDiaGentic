# Fix false-positive response-stall-timeout during long silent tool/connector-use phases

## Description

GP07's response-completion observation engine (shipped and closed 2026-08-16) correctly handles the cases it was designed and validated against, but tonight's live use surfaced a real gap: when ChatGPT is genuinely working via a tool/connector (e.g. its @github connector browsing multiple files) for several minutes BEFORE any assistant text or even an assistant-turn DOM node appears, the observation engine has no evidence to classify as PROGRESS or SOFT_LIVENESS during that window -- stop-control alone only grants a small BOUNDED grace extension (SOFT_LIVENESS cap), not enough to cover a multi-minute silent tool-use phase -- so response-stall-timeout fires and the gateway marks the request FAILED while ChatGPT is genuinely still working and later completes correctly.

## Steps

- Concrete live reproduction (2026-08-16, req_177d9c3c24e94aed, session ses_f7c913eb31e54656): a GP06 design-consultation prompt asking gpt-auto-agent to use its GitHub connector to read a plan item and several source files. Gateway status showed assistant-text-length:0, observed-assistant-count:0, generating:true, dom-signals:['stop-control'] continuously for the full ~3min840s run, then hit EXT-GPTAUTO-002 response-stall-timeout and was marked failed at 10:01:49 UTC (194.8s in). Direct read-only CDP inspection of the SAME real tab afterward showed: assistant text was still 0 chars as late as several checks after the reported failure, then began appearing and grew from 3518 -> 8691 -> 14702 -> 19960 -> 23167 chars over the next ~90 seconds, then stabilized (stop-button gone, text unchanged across 2 consecutive checks) -- a genuine, complete, high-quality 23,167-character response, produced correctly, that the gateway had already discarded as a failure roughly 5 minutes earlier.
- This directly answers the open empirical question GP07's own design notes flagged and left unresolved ('does ChatGPT's real transport actually go quiet mid-turn during tool/backend work') -- confirmed YES, for several minutes at minimum, with zero assistant-text evidence and zero assistant-turn DOM node during that window.
- Also confirms (independently) that the config's existing thinking-indicator dom-signal could not have helped here even if reliable: it is scoped to latest-assistant-turn, but during this silent phase observed-assistant-count was 0, so there was no assistant-turn container for a latest-assistant-turn-scoped selector to search inside at all -- the scoping assumption itself breaks down before any assistant turn exists.
- Design direction to evaluate: (a) a distinct, more generous grace window specifically for the pre-first-assistant-turn phase (tool/connector-use latency is structurally different from mid-response staleness and arguably deserves its own timer, not sharing response_stall_timeout_seconds), (b) detect tool/connector-use activity directly if a reliable DOM signal for it exists outside the latest-assistant-turn scope (needs a live discovery pass, not scoped selectors that assume an assistant turn already exists), (c) at minimum, raise response_stall_timeout_seconds enough to tolerate observed real-world tool-use latency (this incident's real total completion time was ~8 minutes end to end).
- Whatever the fix, it must not regress GP07's actual validated case (a genuinely stalled/stuck turn must still eventually be caught) -- this is exactly the BUDGET_EXHAUSTED / absolute-ceiling distinction GP07's design already has; the fix likely belongs in tuning/extending the SOFT_LIVENESS and progress-lease semantics for this specific pre-first-turn phase, not weakening the overall safety net.

## Notes

2026-08-16 STALE-PROCESS THEORY RULED OUT: git log shows the last commit touching turn.py/observation_engine.py (f2f65e9, 'rewire response-completion through the shared observation engine') landed at 2026-08-16T07:44:23+10:00 = 07:44:23 UTC. The gateway process that served req_177d9c3c24e94aed has runtime-fingerprint.started-at=2026-08-16T08:10:08Z -- 26 minutes AFTER that commit. The running process should have current code. Re-tracing with that ruled out finds the REAL mechanism, and the numbers now match closely:

The submission-proof phase's confirming snapshot (passed into _await_response() as `proof`, becomes the initial `previous`) is taken AFTER the browser has already started generating -- i.e. stop-control is very likely ALREADY present in that very first `previous` snapshot, not absent. If stop-control then stays present continuously for the whole silent tool-use phase (never toggling off and back on), soft_edge = (current_soft != previous_soft) is FALSE on every single poll from the start, so caps stays EvidenceCapability.NONE for the entire phase -- SOFT_LIVENESS is never granted even once, despite stop-control being visibly, continuously true the whole time. This is the exact same LEVEL-vs-EDGE-TRIGGERING bug class fixed earlier tonight for submission-proof's _new_user_message (see turn.py's edge-triggering fix history) -- but this instance, in response-wait's very first poll of a phase, was not caught.

With caps permanently NONE, the tracker never leaves AWAITING_EVIDENCE via the caps path (line 127), so it times out via response_start_timeout_seconds=120 (a SEPARATE, legitimately-finite config value, NOT disabled by response-stall-timeout-seconds:0) into SUSPECT_STALLED at t=120s, then suspect_grace_seconds (=60.0, the hardcoded fallback used whenever response_stall_timeout_seconds is falsy -- NOT itself given the _or_infinite() 0-means-disabled treatment) elapses at t=180s, producing UNRESOLVED_STALL -> turn.py's _raise_response_timeout('response-stall-timeout'). 120+60=180s, closely matching the observed 194.8s (poll-interval/overhead accounts for the remainder). This fully explains the exact error code, message, and timing.

THE REAL BUG, now confirmed with high confidence: response-stall-timeout-seconds:0's '0 = disabled' intent was only applied via _or_infinite() to progress_lease_seconds and absolute_ceiling_seconds (and start_bound_seconds uses its OWN separate, legitimately-finite config value) -- but soft_grace_cap_seconds, candidate_max_verification_window_seconds, and suspect_grace_seconds all fall back to a hardcoded 60.0 when stall is falsy, NOT infinite. So 'disabling' the stall timeout only disables the ACTIVE-state progress-lease check; it does NOT disable the AWAITING_EVIDENCE/SUSPECT_STALLED fallback path, which still bails out at a fixed ~180s regardless of operator intent. Compounding this: SOFT_LIVENESS is purely edge-triggered, so a persistently-true-but-never-toggling stop-control (exactly what a long silent tool-use/connector phase looks like) provides literally zero ongoing evidence, guaranteeing the AWAITING_EVIDENCE/SUSPECT_STALLED path is the one that governs in this scenario, not the (correctly infinite) ACTIVE-state path.

FIX DIRECTION (supersedes the earlier framing -- this is a code bug in the shipped GP07 engine, not a missing feature/design gap): (1) make soft_grace_cap_seconds/candidate_max_verification_window_seconds/suspect_grace_seconds respect the same disabled-means-infinite intent as progress_lease_seconds when response_stall_timeout_seconds is 0 (or make the fallback-to-60.0 behavior an explicit, separately-configurable value rather than an implicit side effect of falsy-stall), and/or (2) fix the edge-triggering gap so a SUSTAINED (not just newly-appearing) SOFT_LIVENESS signal counts as at least minimal ongoing evidence rather than requiring a literal state change on every single poll -- level-triggered presence, not just edge-triggered change, should prevent AWAITING_EVIDENCE from ever timing out while the widget is continuously showing activity. Needs a regression test asserting that response_stall_timeout_seconds=0 truly means unbounded patience (bounded only by the absolute ceiling) across ALL of AWAITING_EVIDENCE/ACTIVE/CANDIDATE_TERMINAL/SUSPECT_STALLED, not just the ACTIVE-state path -- this was exactly the kind of test gap that let this ship without being caught.
