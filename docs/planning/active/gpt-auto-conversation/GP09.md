# Resolve per-project vs machine-scoped config drift for the shared gpt-auto gateway

## Description

The gpt-auto gateway SERVICE is machine-scoped (one shared process serving every project on the machine), but provider SETTINGS (dom-signals/evidence-policies/turn timers in .audiagentic/config/providers/*.yaml) are project-local with no coordination mechanism. Spun off from GP04's 2026-08-16 bigcherry incident: a schema-affecting code change (two new required TurnConfig fields) plus a gateway restart broke a DIFFERENT project (bigcherry) on the same machine whose local config still had the old schema, immediately after having broken THIS project the other way (old code rejecting the new config) moments earlier. Both directions of the same structural hazard were reproduced live in one session. User's own framing: 'we may need to move the config when running shared to the global config for the agents and related config - otherwise projects will conflict - this is already an issue.'

## Steps

- Decide between two directions: (a) move provider settings that must stay in lockstep with the shared gateway's own code version to a genuinely global/machine-scoped location (matching the gateway's own scope), or (b) add explicit schema-version negotiation/migration so an old-schema project config degrades gracefully (or the shared gateway serves multiple schema versions) instead of hard-failing every request.
- This is a broader instance of the same machine-vs-project scoping mismatch already known from GP05's runtime work (GptAutoProviderRuntime is machine-scoped while project semantics live elsewhere) -- review together, not as two unrelated gaps.
- No tooling exists today to detect config/code schema drift across projects sharing one gateway, enumerate affected projects, or apply an update centrally -- whichever direction is chosen should close that gap too.

## Notes

2026-08-16 LIVE DESIGN CONSULTATION (gpt-auto-agent): Recommends hybrid approach combining architectural fix (move code-coupled config machine-scoped) + compatibility (schema-version migrations). Problem: machine-wide gateway with project-local GPT-auto settings; prepare_provider_session_transport() reads per-project while runtime_registry.get_runtime() shares browser/CDP machine-wide. Solution: Three-tier layering: (1) packaged defaults at src/audiagentic/components/providers/adapters/gpt_auto/defaults.yaml; (2) machine override at ~/.audiagentic/config/providers/gpt-auto.yaml; (3) sparse project overlays specifying only overrides. Schema versioning: Use contract-version as real contract. Currently v1 unchanged despite schema growth (GP07 added two new TurnConfig fields). Introduce CURRENT_CONTRACT_VERSION="v2", SUPPORTED_CONTRACT_VERSIONS=("v1","v2"), migrate_v1_to_v2. Do NOT implement multi-version service branches in turn.py/chat.py. Add provider-level config resolver hook in get_provider_runtime_config_state() to ensure gateway fingerprinting and session creation see same effective config. Configuration flow: load defaults -> load optional machine override -> migrate to current schema -> deep_merge(defaults, machine, project) -> strict GptAutoConfig.from_dict(). Project files become sparse overlays (example: specify response-timeout-seconds: 1800 without repeating entire turn block). Drift detection: Add machine-level known-projects.json at ~/.audiagentic/services/machine/agent-execution-gateway/default/known-projects.json with last-seen/last-config-check timestamps. Run compatibility scan in GatewayServiceHost.serve_forever() startup before ready=True. Invalid MACHINE config fails gateway startup; invalid PROJECT config blocks only that project. Validation: distinguish missing vs unknown fields; missing in overlays=inherit, missing after resolution=error; unknown field=typo fail with exact path; config version > gateway=reject project as incompatible, not silent degrade. Write-time guard: patch_provider_config() validate before persist, not after. Test fixtures: load_packaged_gpt_auto_defaults() + patch needed values, stop maintaining separate valid_config() copies. Prevents both incident halves: upgraded gateway supplies new fields from own versioned defaults (no simultaneous project edits), and project config newer than gateway detected as project-scoped incompatibility before destabilizing shared service.
