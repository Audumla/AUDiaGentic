# Isolate multi-project GPT-auto concurrency so one project's failure cannot degrade others

## Description

In production, running gpt-auto across multiple concurrent projects does not hold up: the shared browser/CDP runtime and its recovery path are blunt instruments that couple every project's session to the health of every other project's session. This item hardens project isolation within the intentionally-shared browser runtime. Requirement (2026-08-15, user-stated): each project must be able to operate with its own concurrency, and no global limit or shared-fault path may block or degrade one project because of another project's activity or failure.

## Steps

- Scope `GptAutoProviderRuntime.recover()` so a single disconnect/crash event does not force every registered chat across every project into RECOVERING; distinguish a page-local fault from a genuine bridge/browser-level fault.
- Audit `_lifecycle_lock`, `_dedicated_window_lock`, and any other process-wide locks for whether they serialize unrelated projects' operations that do not need to contend.
- Establish per-session/per-project blast-radius boundaries for CDP bridge calls so one project's hung or slow call cannot stall another project's turn.
- Confirm (do not assume) that the gateway's existing project-capacity/global-capacity split is actually sufficient in practice for concurrent gpt-auto projects under the current execution-profile config; only add explicit project-capacity tuning if live testing shows a real gap.
- Add explicit concurrency test coverage: N concurrent PersistentChat sessions across simulated distinct projects, inject a fault (page crash, disconnect) in one, assert the others remain READY/unaffected.
- Re-validate GP04's live single-session runbook still holds once multi-project concurrency changes land.

## Detailed Solution & Technical Design

GptAutoProviderRuntime (runtime.py) is machine-scoped by design (runtime_registry.get_runtime keys only on browser executable/port/cdp_url, explicitly not project_root) so that multiple projects share one browser process. Per-project/session isolation is meant to be provided by PersistentChat plus the runtime's _page_owners/_conversation_owners maps (claim_page/claim_conversation, keyed by ag_session_id). That per-session ownership layer is sound. The gap is in shared-fault handling: recover() (runtime.py:274-300) responds to a single browser_disconnected/helper_disconnected event by acquiring _lifecycle_lock, clearing _page_owners for all chats, and calling chat.bridge_replaced() on every registered chat regardless of which project's page actually faulted, then reconciling all of them serially. Under concurrent multi-project load this means one project's transient page issue interrupts and re-serializes every other project's live turn. _dedicated_window_anchor/_dedicated_window_lock (single shared status-dashboard anchor) is a secondary, lower-risk shared-state point worth auditing for contention under load, though it is observability-only today.

Capacity/queue layer already checked and is NOT the primary suspect: src/audiagentic/components/agents/gateway/queue/capacity_policy.py already models global-capacity, project-capacity, and session-capacity as independent dimensions (resolve_capacity_limits). .audiagentic/config/execution-profiles.yaml's gpt-auto profile only sets virtual-capacity: 8 (global); project-capacity is unset and therefore unbounded by default, so 2+ concurrent projects should not be capacity-starved today. The fault-recovery blast radius in runtime.py is the confirmed target, not the queue/capacity model -- but this must be verified live (see validation), not just assumed from reading the config.

## Notes

Raised 2026-08-15 from live production feedback: "as soon as we try to use this in prod it barely lasts - we need multiple projects to be able to operate concurrently while they each maintain their own session conversation." Found while investigating GP04 flakiness: recover() in runtime.py is global/blunt across all registered chats on any single disconnect event, which is the most likely concrete cause of one project's instability taking down others.

2026-08-15 LIVE CONFIRMATION (tests/gpt_auto/test_dual_project_runtime_live.py, scenario L3, real gpt-t1/gpt-t2 ChatGPT projects): called runtime.recover() directly (the exact path a real browser/CDP disconnect triggers) while both chats were healthy and idle. chat-b-reconcile-was-called was true and both chats' page handles changed as a side effect, even though only chat-a's disconnect was simulated. The hypothesis is empirically confirmed, not theoretical: recover() unconditionally forces every registered chat through bridge_replaced()+reconcile(), serialized behind _lifecycle_lock. Cost was modest in this run (recover() itself: 0.69s wall-clock; both post-recover turns completed normally at ~14s) but nothing in the code bounds that cost as session count/load scales -- this is the concrete risk to fix, not a worst-case-only concern.

Also confirmed live: L1 (concurrency, two real concurrent sessions, 3 turns each) passed with distinct stable provider-session-ids throughout, but turn-3 on BOTH projects independently slowed to ~866-879s (vs ~12-17s for turns 1-2) at nearly the same moment, coinciding with an organic (not researcher-induced) 'gpt-auto page recovery failed' TimeoutError logged from runtime.py:266 -> chat.py:731 (page_lost -> reconcile -> CDP Runtime.evaluate timeout). Isolated correctly (caught, logged, did not crash), but the near-simultaneous slowdown on two unrelated sessions is worth investigating for a shared-CDP-bridge resource-contention angle distinct from the recover() blast-radius fix -- may be a second, related GP05 finding rather than noise.

L2 (isolated page loss via direct CDP close of gpt-t1's tab only) passed: gpt-t2 (control) was completely unaffected -- state unchanged, page handle unchanged, control turn succeeded normally. gpt-t1 recovered via ensure_ready()'s stale-handle detection path (not the event router, which didn't fire within the test's 10s observation window -- likely a bridge-closing-its-own-page quirk, not a product bug since the underlying recovery worked).

Documentation/runbook gaps found alongside this (relevant to GP04 too): (1) README.md's "one project-scoped GptAutoProviderRuntime" claim is factually wrong -- runtime is genuinely machine-scoped by design (runtime_registry.get_runtime's explicit del project_root); README should be corrected. (2) resume_execution_session requires identity_context_fingerprint/execution_context_fingerprint that are NOT settable via agent_task_submit/MCP directly -- they are auto-derived at session-open time (dispatch.py:219) and must be read back via sessions_store.read_session_binding() to resume at all; this is load-bearing for GP04's documented resume runbook and is currently undocumented there.
