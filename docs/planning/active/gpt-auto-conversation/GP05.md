# Isolate multi-project GPT-auto concurrency so one project's failure cannot degrade others

## Description

In production, running gpt-auto across multiple concurrent projects does not hold up: the shared browser/CDP runtime and its recovery path are blunt instruments that couple every project's session to the health of every other project's session. This item hardens project isolation within the intentionally-shared browser runtime. Requirement (2026-08-15, user-stated): each project must be able to operate with its own concurrency, and no global limit or shared-fault path may block or degrade one project because of another project's activity or failure.

## Steps

- Do NOT simply scope recover() to only the faulted chat -- a live gpt-auto code review (submitted via standard MCP agent_task_submit with real @github repo access) correctly identified that this would be unsafe: when the shared CDP WebSocket genuinely dies, ALL bridge-local page handles become invalid for every chat, since PythonCdpBridge.stop() clears the page/session maps and a replacement bridge starts a fresh _pages map (potentially reusing handle names). Keeping another chat's old handle across a bridge replacement risks that handle silently referring to something else after reconnect.
- Correct split (per the review): keep TWO recovery scopes distinct.
  1. Chat-local recovery (already substantially correct today): page_closed/page_crashed route only to the owning chat via page_lost()/_validate_page_binding(). Leave this as-is.
  2. Shared-bridge recovery (browser_disconnected/helper_disconnected, i.e. today's recover()): the bridge replacement and page-handle invalidation must stay global (this part of current recover() is correct), but EAGER reconciliation of every idle chat should become LAZY instead -- only actively-faulted/in-use chats reconcile immediately; unaffected idle chats mark their binding stale and reconcile lazily on their own next ensure_ready() call (PersistentChat already has this RECOVERING -> list_pages -> reconcile lazy path; reuse it instead of driving every chat through reconcile() inside recover() itself).
- Do not clear _conversation_owners on bridge replacement -- conversation identity is durable and correctly independent of the CDP bridge; current code already gets this right (only _page_owners is cleared).
- A targeted/lazy chat recovery must not reset the shared dedicated-window anchor/window ID -- only genuine bridge/window replacement should do that.
- Preserve the existing conservative unresolved-turn/checkpoint rules for any chat whose turn was active when the shared socket died -- never auto-replay a prompt because the page was rebound.
- Add explicit concurrency test coverage: (a) chat-local fault test -- A faults locally, A reconciles, B remains READY with zero reconciliation/snapshot/navigation calls and an unchanged page handle; (b) shared-bridge test -- simulated socket death invalidates both bindings, but only the actively necessary session reconciles eagerly while an idle session remains untouched until its own next admission.
- Re-validate GP04's live single-session runbook still holds once multi-project concurrency changes land.

## Detailed Solution & Technical Design

GptAutoProviderRuntime (runtime.py) is machine-scoped by design (runtime_registry.get_runtime keys only on browser executable/port/cdp_url, explicitly not project_root) so that multiple projects share one browser process. Per-project/session isolation is meant to be provided by PersistentChat plus the runtime's _page_owners/_conversation_owners maps (claim_page/claim_conversation, keyed by ag_session_id). That per-session ownership layer is sound.

Live-confirmed gap (2026-08-15, tests/gpt_auto/test_dual_project_runtime_live.py scenario L3, real gpt-t1/gpt-t2 sessions): recover() (runtime.py:274-300) responds to a single browser/CDP disconnect by forcing EVERY registered chat through bridge_replaced()+reconcile(), not just the one that faulted -- confirmed empirically (chat-b-reconcile-was-called: true when only chat-a's disconnect was simulated).

REVISED FIX DIRECTION (2026-08-15, from live gpt-auto code review via standard MCP path with real repo access -- see GP04 notes for the same review's other findings): the initial framing ("scope recover() to only the faulted chat") is architecturally wrong and would be unsafe, because a genuine shared-CDP-socket death really does invalidate every chat's bridge-local page handle -- there is only one CDP connection multiplexing all chats (CdpClient/PythonCdpBridge). The correct fix keeps global bridge/handle invalidation on a true shared-bridge fault, but decouples that from EAGER reconciliation: idle, unaffected chats should mark themselves stale and reconcile lazily on their own next ensure_ready() (this lazy RECOVERING path already exists in chat.py), rather than being driven through reconcile() synchronously inside recover() for every registered chat regardless of whether they're about to be used. This removes the blast radius (an idle project no longer pays an immediate reconciliation cost or risks a serialization delay from another project's fault) without weakening the real invariant that bridge-local handles cannot survive a bridge replacement.

_dedicated_window_anchor/_dedicated_window_lock (single shared status-dashboard anchor) is a secondary, lower-risk shared-state point worth auditing for contention under load, though it is observability-only today.

Capacity/queue layer already checked and is NOT the primary suspect: src/audiagentic/components/agents/gateway/queue/capacity_policy.py already models global-capacity, project-capacity, and session-capacity as independent dimensions. gpt-auto's execution profile only sets virtual-capacity: 8 (global); project-capacity is unbounded by default, so 2+ concurrent projects should not be capacity-starved today -- confirmed live via L1 (two real concurrent sessions, 3 interleaved turns each, no serialization observed except one organic, isolated CDP timeout unrelated to capacity).

## Validation

Deterministic: two SEPARATE test contracts (per 2026-08-16 review correction), not one:
1. Page-local fault: A faults locally (page_lost), A reconciles, B stays READY with unchanged page handle and zero reconciliation/snapshot/navigation calls. (Covered.)
2. Shared-bridge fault: simulated CDP socket death invalidates BOTH A and B's bindings; only the actively-demanded chat (has active_turn_id, or per the boundary-case tests below, is mid-open/mid-admission/mid-identity-acquisition) reconciles eagerly; the idle chat goes to stale/RECOVERING and performs zero DOM work until its own next ensure_ready() call -- it must NOT be asserted as remaining READY. (Covered for the active_turn_id case; boundary cases below not yet covered.)
Additional boundary-case tests needed before closing: shared-bridge failure during _open_impl() (pre-turn), during ensure_ready() admission, and around provider-identity-acquisition/submitted-turn-reconciliation windows -- confirm each either recovers itself or fails cleanly and retryably without corrupting state.
Existing GP04 live single-session runbook must still pass unmodified.
