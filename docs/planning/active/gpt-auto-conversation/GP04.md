# Harden GPT-auto lifecycle, diagnostics, and agent testing operations

## Description

Document and complete the GPT-auto reliability work carried out across the CDP adapter, persistent conversation/session lifecycle, gateway status projection, and live operational test process. The item is the durable runbook for diagnosing a retained ChatGPT project/chat lineage, recovering an unresolved prompt without resubmitting side effects, and continuing multi-stage reviews through one long-lived agent session.

Work completed so far:
- Added durable unresolved-turn checkpoints with provider session URL, prompt/assistant markers, prompt-text digest, baseline counts, and recovery state.
- Fixed checkpoint persistence to use ChatSnapshot.user_count/assistant_count rather than nonexistent user_message_count/assistant_message_count.
- Added lazy READY admission recovery and quiescence gating; failed/cancelled turns retain the tab by default.
- Added prompt-ID-first reconciliation with bounded prompt-text fallback; missing IDs are evidence gaps, not automatic proof of failure.
- Added request-status reconciliation so provider-turn-pending is recovered from the durable session checkpoint.
- Classified provider surface probe/adapter-resolution failures as unavailable with typed reasons.
- Added allow-listed GPT-auto error.details projection so recovery reasons and safe next-step evidence survive gateway persistence without prompt contents, tracebacks, or secrets.
- Restarted the shared gateway safely, closed the orphaned durable source record, and resumed the same ChatGPT project/chat as successor session ses_c8e35e2ef75c42e3; the retained provider chat URL and turn markers were preserved.
- Pushed implementation to branch agent-surface-refactor at commit 4cd32b1c1.

## Steps

- Keep one gateway process and one live GPT-auto session per review lineage; never create parallel review sessions for polling or recovery.
- Before any new GPT prompt, inspect gateway overview, session list, request list, and the target request status; distinguish queued/running/provider-turn-pending from terminal failure.
- For a timed-out or ambiguous turn, do not resubmit automatically. Reconcile the existing provider conversation using prompt marker, assistant marker, prompt-text digest, prompt text, URL/project/chat identity, and DOM quiescence evidence.
- If the gateway dies, verify the exact process and durable session state, restart only the shared gateway process, close only an orphaned non-live source record, and call session_resume with the stored identity/execution fingerprints; retain the browser tab.
- After each substantive fix, run focused unit/lifecycle tests, lint/type checks, commit and push the branch, then use the same GPT session for a narrow adversarial review of the pushed commit.
- Use live monitoring as a state machine: provider-turn-pending means the provider may still be processing; only explicit terminal state plus response evidence permits a new turn.
- When a request fails, capture request-id, session-id, attempt, error code/message/details, recovery reason, watchdog state, last transition, provider metadata, and suggested next action; never collapse these into a generic unexplained error.
- Close the item only when deterministic simulation coverage, live submit/reconcile/resume coverage, tab-retention behavior, gateway restart recovery, and multi-stage same-session review all pass.

## Detailed Solution & Technical Design

Layering and state invariants:
- GPT-auto adapter owns DOM/CDP observation, prompt proof, response policy, prompt/assistant correlation, quiescence, and provider-specific error diagnostics.
- PersistentChat owns project/chat binding, page ownership, unresolved-turn checkpointing, recovery admission, and READY/RECOVERING transitions.
- Session runtime/transport owns durable provider binding and lazy session recovery; gateway owns queue, request lifecycle, persistence, watchdog observations, and shared process coordination.
- Project/session identity is the ChatGPT project URL plus conversation/chat URL. A prompt/response cycle is a turn within that conversation and may have a provider message id; the id is optional and must not be treated as the session id.
- READY is admitted only after page binding is valid, provider state is quiescent across stable observations, and no unresolved side effect remains. RECOVERING is alive but not prompt-admissible until ensure_ready proves the invariant.
- EXT-GPTAUTO-002 means response policy timeout after submission was confirmed; retain the tab and do not resubmit.
- EXT-GPTAUTO-003 means provider submission/DOM proof or provider failure policy could not be confirmed; inspect structured evidence and treat side effects as ambiguous.
- EXT-GPTAUTO-004 means a prior side effect may have started but outcome is unproven; reconcile lazily and report recovery-reason/recovery-details. It is not evidence that the tab or conversation is lost.
- RES/CON gateway errors describe session/request lifecycle, not provider DOM state; use the stored provider binding and close-reason to decide resume versus fresh session.
- Public errors expose only bounded allow-listed GPT-auto evidence; prompt bodies, exception messages, stdout/stderr, and secrets remain private.

2026-08-15/16 LIVE TESTING WITH REAL gpt-t1/gpt-t2 PROJECTS -- three real EXT-GPTAUTO-002 timeouts, each independently diagnosed by direct DOM re-inspection (production PersistentChat.snapshot() plus raw DOM queries against the still-open tabs). IMPORTANT CORRECTION: an earlier pass mischaracterized these as silent stalls; the user correctly pushed back that the tabs were not stuck, prompting the re-diagnosis below, which found three DISTINCT real causes:

1. gpt-t1 @github review turn: NOT a stall. The same assistant messageId that showed 54 chars at timeout later showed 23,995 chars -- it was genuinely still generating past response-timeout-seconds (3600s). This is a config-tuning gap: heavy @github/tool-connector reviews can legitimately need well over an hour. ACTION NEEDED: raise response-timeout-seconds substantially (or make it configurable per-purpose) for @github-augmented review turns; 3600s is not enough headroom for this use case.

2. gpt-t1 trivial baseline turn: CONFIRMED REAL BUG, precisely located. The correct short reply rendered almost immediately, but ChatGPT's own composer submit/stop toggle button (id=composer-submit-button, data-testid=stop-button, aria-label='Stop answering') never reverted from its 'stop' state -- confirmed still stuck hours later on direct re-inspection. turn.py's response-complete gate (`complete_satisfied = complete.satisfied and not current.generating`, ~line 558) is an unconditional veto: response_stability_seconds (text-unchanged-for-N-seconds) is only consulted AFTER complete_satisfied is already true, so a stuck generating=true blocks completion detection for the FULL response-timeout-seconds no matter how long the text has actually been stable. Simultaneously-observed composer-editable=true (which should be false during genuine active generation) is a plausible corroborating override signal. PROPOSED FIX (not yet applied -- touches the core completion-safety gate, needs review before changing): add a stable-text override path -- if latest_assistant_text has been fingerprint-stable for response_stability_seconds AND response-complete's other conditions (assistant-fresh, text-present, completion-control, no error signals) are satisfied AND composer-editable is true, allow completion even if the document-scoped stop-control/generating signal is still (spuriously) matching. Needs a second real observation before committing to this exact shape, since it's inferred from one incident.

3. gpt-t2 mid-generation-injection turn: ORIGINAL diagnosis confirmed correct. DOM now shows a transient EMPTY assistant message followed by the real full answer, with message IDs differing from what was captured at the timeout -- confirms near-simultaneous real-turn + injected-foreign-message sends caused genuine message branching/multiplicity in the conversation, and the adapter's simple 'last assistant node in DOM order' selection picked a transient/empty node at an unlucky poll moment. This is the real, valuable out-of-sequence-interference finding GP04 needed: concurrent human+adapter sends into the same conversation CAN desynchronize latest-assistant selection. Not yet fixed; worth its own investigation into whether message-id-based correlation (already used for other reconciliation paths in this file) should also gate live in-turn assistant selection, not just post-hoc unresolved-turn reconciliation.
