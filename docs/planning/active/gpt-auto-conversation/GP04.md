## Description

Document and complete the GPT-auto reliability work carried out across the CDP adapter, persistent conversation/session lifecycle, gateway status projection, and live operational test process. The item is the durable runbook for diagnosing a retained ChatGPT project/chat lineage, recovering an unresolved prompt without resubmitting side effects, and continuing multi-stage reviews through one long-lived agent session.

## Steps

- Keep one gateway process and one live GPT-auto session per review lineage; never create parallel review sessions for polling or recovery.
- Before any new GPT prompt, inspect gateway overview, session list, request list, and the target request status; distinguish queued/running/provider-turn-pending from terminal failure.
- For a timed-out or ambiguous turn, do not resubmit automatically. Reconcile the existing provider conversation using prompt marker, assistant marker, prompt-text digest, prompt text, URL/project/chat identity, and DOM quiescence evidence.
- CONCRETE SAFE GATEWAY RESTART PROCEDURE (validated live, 2026-08-16): (1) locate the machine service record at `<user home>/.audiagentic/services/machine/agent-execution-gateway/default/service.json` -- read its `endpoint.address` (e.g. 127.0.0.1:8765) and confirm `state`/`process.pid`; the sibling `auth.token` file in the same directory is the token. (2) set `AUDIAGENTIC_GATEWAY_ENDPOINT=http://<address>` and `AUDIAGENTIC_GATEWAY_TOKEN_FILE=<path to auth.token>` in the shell, then run `audiagentic gateway stop` (no flag) first -- it correctly refuses with CON-AGLC-001 if sessions are still live/non-quiescent, which is the intended safety check; only add `--force` once you've confirmed it's safe/necessary to interrupt live work. (3) confirm the old PID has actually exited (process no longer found). (4) relaunch by calling `start_or_attach_gateway()` from `audiagentic.components.agents.gateway.service.bootstrap` in a fresh short-lived Python process (this is the same function `get_gateway_client()`'s 'automatic' mode calls internally on a cache miss) -- do NOT use the foreground-blocking `audiagentic gateway serve` CLI form for this. (5) verify via `agent_task_gateway_overview` that `runtime-fingerprint.process-instance-id`/`started-at` reflect the new process. Code changes to the adapter (chat.py/runtime.py/etc) do NOT take effect in an already-running gateway process -- a restart via this procedure is required after such changes for them to actually be live.
- RESTART DISCIPLINE (GP31 correction, 2026-08-17): never splice the managed-restart path with the manual start_or_attach path. GP04's procedure is a CLEAN stop (gateway stops cleanly, PID exits) followed by start_or_attach_gateway(). The dangerous GP31 incident happened when a manual poll-and-retry workaround was spliced into gateway_restart()'s own stop-then-start sequencing mid-drain, which killed the running Brave browser. If a managed `gateway_restart()` / `gateway stop` fires CON-MSVC-028 ('service process remains live while draining'), do NOT switch to a hand-rolled two-step replacement -- wait and retry the whole managed call (or ask the user). Only use GP04's manual procedure from a fully quiescent starting state. Never bypass the documented sequencing while a managed restart is already in progress.
- KNOWN GAP (see GP06): after a restart, any MCP client process that had already cached a gateway connection (via get_gateway_client()'s per-process _CLIENT cache) will NOT automatically recover -- it keeps failing with NET-AGSV-002 indefinitely since the cache is never invalidated/retried on failure. Until GP06's fix lands, a gateway restart may require manually re-running the relaunch step (4) above even when a client appears to already exist, and any other concurrent MCP client (including other projects/agents sharing this machine's gateway) will need their own client to somehow re-attach -- currently only achievable by that client happening to make its very first-ever gateway call after the restart, or by the same manual bootstrap procedure.
- If the gateway dies, verify the exact process and durable session state, restart only the shared gateway process (per the procedure above), and retain the browser tab. DEFAULT RECOVERY IS IN-PLACE REHYDRATION (CORRECTED 2026-08-17, per GP06): an active durable session whose process-local owner disappeared must remain active and be reattached in place via the existing lazy rehydration mechanism (SessionRuntime.rehydrate_session()); do NOT close it and do NOT create a successor. Only positive evidence that the provider conversation itself cannot be reattached ever terminalizes a session; runtime-owner-loss alone is never that evidence. `agent_task_session_resume` with stored identity/execution fingerprints is a FALLBACK for when the durable lifecycle genuinely requires terminalization, not the default path. Close an orphaned non-live source record only when it is confirmed non-live AND terminal, never merely because its owner process is gone.
- After each substantive fix, run focused unit/lifecycle tests, lint/type checks, commit and push the branch, then use the same GPT session for a narrow adversarial review of the pushed commit -- attempt to RESUME the same session_id first (this is exactly what PC14 exists to make reliable) rather than opening a new chat, even across a gateway restart; only fall back to a new session if resume is genuinely unavailable.
- Use live monitoring as a state machine: provider-turn-pending means the provider may still be processing; only explicit terminal state plus response evidence permits a new turn.
- When a request fails, capture request-id, session-id, attempt, error code/message/details, recovery reason, watchdog state, last transition, provider metadata, and suggested next action; never collapse these into a generic unexplained error.
- Close the item only when deterministic simulation coverage, live submit/reconcile/resume coverage, tab-retention behavior, gateway restart recovery, and multi-stage same-session review all pass.

## Detailed Solution & Technical Design

Layering and state invariants:
- GPT-auto adapter owns DOM/CDP observation, prompt proof, response policy, prompt/assistant correlation, quiescence, and provider-specific error diagnostics.
- PersistentChat owns project/chat binding, page ownership, unresolved-turn checkpointing, recovery admission, and READY/RECOVERING transitions.
- Session runtime/transport owns durable provider binding and lazy session recovery; gateway owns queue, request lifecycle, persistence, watchdog observations, and shared process coordination.
- Project/session identity is the ChatGPT project URL plus conversation/chat URL. A prompt/response cycle is a turn within that conversation and may have a provider message id; the id is optional and must not be treated as the session id.
- READY is admitted only after page binding is valid, provider state is quiescent across stable observations, and no unresolved side effect remains. RECOVERING is alive but not prompt-admissible until ensure_ready proves the invariant.
- EXT-GPTAUTO-002 means response policy timeout after submission was confirmed; retain the tab and do not resubmit.
- EXT-GPTAUTO-003 means provider submission/DOM proof or provider failure policy could not be confirmed; inspect structured evidence and treat side effects as ambiguous.
- EXT-GPTAUTO-004 means a prior side effect may have started but outcome is unproven; reconcile lazily and report recovery-reason/recovery-details. It is not evidence that the tab or conversation is lost.
- RES/CON gateway errors describe session/request lifecycle, not provider DOM state; use the stored provider binding and close-reason to decide resume versus fresh session.
- Public errors expose only bounded allow-listed GPT-auto evidence; prompt bodies, exception messages, stdout/stderr, and secrets remain private.

## Code Samples & Guidance

Operational status fields to preserve:
request-id, session-id, state, provider-turn-pending, latest-transition, attempt-epoch, watchdog-state, watchdog-reason, error.code, error.message, error.details.failure-reason, error.details.recovery-reason, error.details.recovery-details, metadata.provider-session-id, metadata.chat-url, metadata.prompt-message-id, metadata.assistant-message-id, metadata.unresolved-turn-pending.

Single-session recovery outline (default: in-place rehydration, corrected 2026-08-17):
1. agent_task_gateway_overview({})
2. agent_task_session_list({state:"active"})
3. agent_task_status({request_id})
4. If the durable session is active but detached from a live runtime (owner gone), re-submitting via the same session_id lets the existing lazy rehydration reattach the provider conversation in place. `agent_task_session_resume(source_session_id, stored identity/execution fingerprints, new control id)` is the FALLBACK only when the durable lifecycle genuinely requires terminalization; do not close a merely detached session.
5. agent_task_submit(agent_id:"gpt-auto-agent", session_id:<the durable session id>, session_keep_alive:true, timeout_seconds:3600, one focused prompt)
6. Poll status; do not infer completion from watchdog inactivity alone.
