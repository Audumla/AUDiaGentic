# message-finalized fires prematurely on a still-generating turn, causing false-positive early completion

## Description

response-complete's evidence policy accepts message-finalized ([data-is-last-node]) as sufficient on its own via its any-of clause (paired with completion-control, but either one alone satisfies it). Proven live tonight, twice in a row, in the same session: GP10's and GP11's design-consultation responses were both reported by the gateway as genuinely completed (stop-reason:end-turn) while the real ChatGPT response had only produced 35 and 7 characters respectively -- confirmed stable/non-growing across repeated read-only CDP checks with real elapsed time between them, not a mid-stream observation race. Direct DOM inspection confirmed the mechanism: message-finalized was present (last_node_count_in_article:1) on the near-empty response while completion-control was absent (copy_button_count_in_article:0) -- exactly the scenario the config's own inline comment already flagged as an open risk ('its exact lifecycle (transient vs persistent, per turn type) is not yet fully characterized -- must never be relied on alone').

## Steps

- This is a false-POSITIVE completion, the opposite and more severe class of bug than GP15's false-negative stall (per GP07's own stated risk assessment: 'a false-positive completion... is worse than a slow correct detection' -- a caller can receive and act on genuinely incomplete/wrong content believing it is the full answer).
- Reproduce deliberately and isolate the trigger: does message-finalized fire early on EVERY turn, or specifically after this session's history of repeated resubmission/retry/resume attempts (GP10 alone was resubmitted 4 times, including a session close+resume) -- i.e. could residual/stale DOM state from the earlier failed attempts be contaminating message-finalized's detection for the NEXT turn, distinct from a universal per-turn bug.
- If message-finalized genuinely cannot be trusted as sufficient evidence on its own (matching the code comment's original caution), demote it from response-complete's any-of clause -- require completion-control specifically, or require BOTH message-finalized AND completion-control together (all-of, not any-of) rather than either alone.
- Consider whether a minimum-length or minimum-stability heuristic is also warranted as a sanity check (a 7-35 character 'complete' response to a design question is implausible on its face) -- though this should not become the primary fix, since a legitimately short real answer (e.g. 'Reply with exactly RECOVERED') must not be penalized.
- Any fix must be validated against GP07's own already-shipped test coverage (test_observation_engine.py, the response-complete policy tests) to ensure this doesn't reintroduce the ORIGINAL stop-control-veto bug GP07 fixed -- these are now three interacting concerns (stuck stop-control, false stall-timeout, false early-completion) that must all be satisfied together, not fixed one at the expense of another.

## Notes

2026-08-16 ROOT CAUSE CONFIRMED AND FIXED. Direct disk read of the raw persisted request record (project_root/.audiagentic/runtime/agent-execution-gateway/req_f3d2653b17494f53/record.json) proved the 'output' field ALREADY contained only 28 characters at write time -- this is NOT an MCP/transport truncation bug (GP16's original hypothesis is WRONG for this symptom; corrected there too). The response really was captured at 28 characters by _await_response(), and it happening to end near a backtick was coincidental, not causal. This directly connects GP16's original finding (GP08's 'truncated' output) and the later GP10/GP11 short-response findings as the SAME bug, discovered in two different guises the same night.

FIX APPLIED: response-complete's evidence-policy previously used any-of: [completion-control, message-finalized] -- either alone was accepted as sufficient corroboration for a done response, reasoning that the response_stability_seconds window would catch a premature signal. That reasoning was wrong: if EITHER signal fires early and then simply stays true (does not flap) for the whole stability window, the stability check is satisfied vacuously even though the response is genuinely incomplete -- and both signals were independently already proven live-unreliable (completion-control fires early mid-stream per the original GP07 finding; message-finalized fires on a 7-35 char response per tonight's GP17 finding). Changed to all-of: [assistant-fresh, text-present, completion-control, message-finalized] (require BOTH corroborating signals together, not either alone) across all four affected local configs: this project's gpt-auto.yaml/gpt-auto-t1.yaml/gpt-auto-t2.yaml, and H:\development\projects\bigcherry\.audiagentic\config\providers\gpt-auto.yaml (a different project sharing the same machine-scoped gateway, whose own agent was reportedly hitting this same truncation issue live tonight). All four configs verified to still parse via GptAutoConfig.from_dict() after the edit.

Deployment note: confirmed via runtime_registry.get_runtime() that workflow/evidence-policies config is NOT cached at the shared gateway-process level -- only browser/CDP config is machine-cached; each PersistentChat loads its own GptAutoConfig fresh from disk at session-open time. So this fix takes effect for any NEW session opened from now on, including in other already-running agent processes (like bigcherry's), without requiring another gateway restart or disrupting any currently-live session.

STILL OPEN: this is a fast, conservative mitigation, not a full fix -- it reduces but does not mathematically eliminate the risk (both signals could theoretically still false-fire in exact simultaneous coincidence). The deeper investigation this item's steps originally called for (is this triggered specifically by this session's heavy resubmission/retry history, or does it happen on any turn; is a minimum-length/stronger-stability heuristic also warranted) remains valid future work. No deterministic regression test added yet for the all-of change itself -- worth adding one mirroring the existing GP07 config-shape lock-in tests (test_greenfield_config_urls.py) in a future session.
