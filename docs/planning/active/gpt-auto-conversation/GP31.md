# Gateway restart workaround (manual poll + start_or_attach bypassing service_stop drain race) killed the running Brave browser process

## Description

2026-08-17 live incident: after gateway_restart(force=True) hit CON-MSVC-028 ('service process remains live while draining') a second time tonight, instead of waiting for the documented graceful path, a manual workaround was used -- polling for the old gateway PID to disappear via Get-CimInstance, then calling start_or_attach_gateway() directly (skipping gateway_restart()'s own stop-then-start sequencing). Shortly after, the actual Brave browser process (PID 2060280, launched fresh at 08:30:41, confirmed via Get-CimInstance with no --type= flag = the main process, not a helper) was found to have been relaunched from scratch -- 56 tabs restored via Brave's own session-restore, but the live gpt-auto test conversations in the 'audiagentic' project tabs from earlier in the session were lost. The user directly confirmed this was caused by the gateway actions, not a coincidental crash or manual close on their end.

## Steps

- Root cause not yet found: neither GptAutoProviderRuntime.shutdown()/shutdown_browser() nor BrowserProcessController.shutdown() have any caller in the gateway stop/restart path (confirmed by grep -- shutdown_browser() has zero callers anywhere in src/), so the mechanism is not obviously in gpt_auto's own code.
- Prime suspect: the manual bypass of gateway_restart()'s documented stop-then-start sequencing. The Get-CimInstance process check used to confirm the old gateway PID had exited may have been unreliable (a near-identical query earlier the same night returned false matches against the querying shell's own command line due to substring matching), so start_or_attach_gateway() may have been called while the prior gateway generation was still mid-teardown, producing an unintended interaction -- possibly a Windows job-object/process-group side effect where the old gateway process (or its shutdown sequence) had implicit ownership/cleanup responsibility over the browser process it had reattached to.
- Needs deliberate reproduction with process-tree instrumentation (e.g. Get-CimInstance ParentProcessId chains, or Process Explorer) BEFORE and DURING a deliberately-forced CON-MSVC-028 race, to catch the actual mechanism live rather than reasoning about it after the fact.
- Until root-caused: never bypass gateway_restart()'s own stop-then-start sequencing with a manual poll-and-retry workaround. If CON-MSVC-028 fires, wait and retry the whole gateway_restart() call (or ask the user), not a hand-rolled two-step replacement.

## Notes

2026-08-17 STATIC INVESTIGATION EXHAUSTED, root cause still not found. Ruled out via direct evidence, not assumption: (1) process ancestry -- Get-CimInstance chain-walk showed Brave's parent is cmd.exe->explorer.exe (a normal user-launched tree), while the gateway process's parent had already exited independently; completely separate process trees, no shared Windows Job Object possible. (2) gpt_auto's own shutdown code -- shutdown_browser() and BrowserProcessController._stop_matching() (the only functions anywhere in the codebase that call kill_pid/kill_process_tree on a browser) both have zero callers, confirmed by grep across all of src/. (3) The generic foundation adopted_process.py process-supervision system (which does use Windows Job Objects for hard-kill guarantees) -- gpt_auto has no imports of or references to this module at all; the browser is not tracked through it. (4) Read ensure_browser_for_cdp()'s ExistingBrowserPolicy.RESTART branch in full (previously only skimmed) -- even that branch never kills anything; it explicitly raises 'restart refused because process ownership cannot be proven' rather than acting, by deliberate design (comment: 'must never terminate unrelated user windows'). Every reachable code path in ensure_browser_for_cdp() either reconnects, launches fresh only when NO existing process is found at all, or raises -- never kills a live browser.

Conclusion: the mechanism cannot be found through further static reading. Confirming it requires live instrumentation (temporary logging in ensure_browser_for_cdp()/_connect_bridge()/_cdp_available()) during an actual deliberate reproduction, which needs another restart cycle -- explicitly deferred per the user's direction to investigate first rather than restart again immediately. Next session should add that instrumentation BEFORE the next restart attempt, not after.
