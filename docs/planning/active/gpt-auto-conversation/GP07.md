# Replace single-signal completion veto with tiered evidence and activity-lease timeouts

## Description

Live testing on 2026-08-15/16 against real gpt-t1/gpt-t2 ChatGPT projects produced three real EXT-GPTAUTO-002 timeouts, each independently diagnosed via direct DOM re-inspection. One (gpt-t1 baseline turn) is a confirmed real bug: ChatGPT's own composer submit/stop toggle button did not revert from its 'Stop answering' state after the response genuinely completed, and turn.py's response-complete gate has an unconditional single-signal veto (`complete_satisfied = complete.satisfied and not current.generating`) with no override path -- so the turn burned the full response-timeout-seconds (3600s) despite the correct answer having rendered almost instantly. A second turn (gpt-t1 @github review) was NOT a bug -- it was genuinely still generating past the flat timeout ceiling, which cannot distinguish 'still legitimately working' from 'actually stuck'. This item replaces the single hard-veto DOM signal with tiered, cross-corroborated evidence and replaces the flat end-to-end timeout with a renewable activity lease, so both failure modes are handled correctly without conflating them.

## Steps

REVISED 2026-08-16 per live review (reused session ses_caaace36a7be4c88) -- the original "Tier 1 network > Tier 2 text-stability > Tier 3 DOM" ranked model is WRONG and is superseded by the two-dimension model below. Do not implement the ranked-tier version.

- Model evidence as two INDEPENDENT dimensions, not a ranked stack:
  1. ACTIVITY/PROGRESS evidence -- can VETO completion (prove "still going"), can NEVER by itself PROVE completion.
  2. TERMINAL/COMPLETION evidence -- required to declare done; absence of a specific DOM affordance (completion-control) should no longer veto forever, but presence of a strong active-generation DOM signal (stop-control, thinking-indicator, streaming-indicator, busy-state) still vetoes completion, exactly as today. Only the WEAK positive-only signal (completion-control) gets demoted to corroborating; DOM signals that indicate active generation stay authoritative negative evidence.
- Rule of asymmetry (the key correction): an active signal may veto completion even when its absence is not trusted to prove completion. Do not flip false-negatives into false-positives.
- Decision logic: strong activity evidence present -> definitely not complete, renew lease. No strong activity evidence -> if authoritative terminal/protocol evidence exists, verify final snapshot/message identity and complete. Otherwise require CONVERGING fallback evidence together (not any single one alone): same assistant message identity, fingerprint-stable for a completion dwell, no correlated network progress during that dwell, generating==false, no strong active DOM signals, no provider error, a second independent observation, and completion-control (if present) as a confidence booster only.
- Text-fingerprint stability must NEVER independently complete a turn (this is the concrete false-positive risk the reviewer identified: a real tool-call/backend gap can leave visible text unchanged while the turn is still genuinely active -- the existing unresolved-turn reconciliation code already warns about exactly this pattern for a different scenario). It is corroboration only.
- Network-activity evidence needs real scoping work before it's trustworthy, not just a turn.py change: the CDP bridge currently doesn't enable/expose the Network domain at all (only Page/lifecycle events today). A network signal used to renew a lease must carry bridge generation + target/page + attached CDP session + current turn/generation + relevant response-stream identity -- otherwise gpt-t2 traffic could renew gpt-t1's lease, or unrelated ChatGPT background/analytics/polling traffic could falsely renew any lease. This is a real cross-session contamination risk given the concurrent multi-project design (GP05).
- Separate three independent clocks explicitly (per review, not yet fully specified -- continuation pending): (1) start bound -- how long submission may remain accepted-but-no-response-start-observed; (2) progress lease -- renewed by proven activity, short, fires on genuine silence; (3) absolute ceiling -- ...to be captured once the review continuation completes.
- Absolute-ceiling expiry must preserve unresolved-turn semantics (submitted-but-outcome-unproven), matching the machinery this codebase already has to prevent duplicate side effects after ambiguous sends. It must never silently return the last partial text as a successful response.
- Fingerprint must include stable message identity and relevant response structure (tool cards, citations, attachments), not just plain text -- same-text structural changes are a real edge case the plain text fingerprint would miss.
- Explicitly distinguish error/abort/connection-reset network termination from protocol-terminal success -- a network request ending is not automatically a successful completion.
- Add a finalization-race guard: capture an activity generation/sequence counter at candidate completion and require it unchanged through final confirmation, to close the race where a network delta or text mutation arrives just before success is returned.
- Consider integrating the existing AS36 terminal-quality classifier (classifier_version 1.0.0-as36, already flags premature-halt-suspected patterns like TQ-ENDS-WITH-PREAMBLE/TQ-REPETITION on completed output) as an additional corroborating signal -- it already exists in this codebase for a related purpose and caught a real truncated response during this very review's own output, which is a good practical validation of its usefulness here.
- Deterministic test coverage for the explicit failure modes the reviewer enumerated: long legitimate quiet phase during a tool call (must NOT complete, must go to stalled/ambiguous, not false-success); background network chatter continuously renewing the lease (absolute ceiling must still bound it); lost network instrumentation while ChatGPT keeps generating (must NOT become terminal evidence by omission); concurrent gpt-t1/gpt-t2 cross-session lease contamination (must be impossible by construction, not just untested); the finalization race described above; same-text structural changes; error-vs-success network termination; absolute-ceiling-hit-with-unproven-outcome must preserve unresolved-turn semantics, never fabricate success.

## Detailed Solution & Technical Design

Root cause of the E2 incident: response-complete evaluation in turn.py (~line 557-559) computes `complete = self.chat.config.workflow.policy('response-complete').evaluate(facts)` then `complete_satisfied = complete.satisfied and not current.generating`. `current.generating` (gpt_auto_cdp.py's _SNAPSHOT_FN, ~line 55-56) is a raw document-wide query for `[data-testid="stop-button"], [data-testid="stop-generating"], .result-streaming, .result-thinking, [aria-busy="true"]` with no corroboration from any other signal. Live evidence (2026-08-15/16): ChatGPT's composer submit button (id=composer-submit-button) matched `[data-testid="stop-button"]` and remained visibly in 'stop' state for hours after the actual response had fully rendered and stabilized -- confirmed by direct re-inspection of the still-open tab well after the timeout fired. Because `current.generating` gates entry into the entire stable-text/response_stability_seconds verification branch (~line 557-576), the turn never even began measuring text stability; it simply waited out the full response_timeout_seconds (3600s) and failed with EXT-GPTAUTO-002, even though the correct, final answer had been sitting on screen the whole time.

Separately, the E1 incident (same error code, different cause) showed the flat response-timeout-seconds ceiling cannot distinguish 'genuinely still working' from 'stuck' -- both hit the identical wall-clock limit and fail identically, even though only one of them is actually a problem. An activity-based renewable lease (already a proven pattern in this codebase at the gateway-watchdog layer, watchdog-policy.activity-lease-seconds) resolves this: extend automatically while real activity is corroborated, fire promptly once it genuinely stops.

Design principle carried over from chat.py's ChatState machine (independently praised by both the live gpt-auto reviewer and this session's own audit as well-designed): no single fragile signal should have unilateral authority over a safety-critical decision. The turn-completion gate currently violates this; chat.py's session-lifecycle machine does not. This item brings the turn-completion layer up to the same standard.

## Code Samples & Guidance

Tiered evidence resolution (illustrative shape, not final):
```python
network_idle = self._network_observer.idle_for(now, threshold=network_idle_seconds)  # Tier 1, new
text_stable = stable_since is not None and now - stable_since >= response_stability_seconds  # Tier 2, existing
dom_says_generating = current.generating  # Tier 3, existing -- no longer a sole veto

if network_idle and text_stable and complete.satisfied:
    if dom_says_generating:
        logger.warning("gpt-auto Tier 3 DOM signal disagreed with Tiers 1+2 at completion", extra={...})
    return stable_text  # Tiers 1+2 agreement wins regardless of Tier 3
```
Activity-lease timeout (illustrative shape):
```python
lease_deadline = last_corroborated_activity_at + activity_lease_seconds
absolute_deadline = started_at + absolute_ceiling_seconds  # hours, circuit-breaker only
if now >= lease_deadline and now < absolute_deadline:
    raise ... # EXT-GPTAUTO-002, short inactivity lease expired
if now >= absolute_deadline:
    raise ... # distinct code/reason: absolute ceiling hit despite ongoing (but uncorroborated) activity
```
