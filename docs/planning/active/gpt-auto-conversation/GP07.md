# Replace ad hoc completion/submission-proof timeouts with a formal observation state machine

## Description

Live testing on 2026-08-15/16 against real gpt-t1/gpt-t2 ChatGPT projects produced three real EXT-GPTAUTO-002 timeouts, each independently diagnosed via direct DOM re-inspection. One (gpt-t1 baseline turn) is a confirmed real bug: ChatGPT's own composer submit/stop toggle button did not revert from its 'Stop answering' state after the response genuinely completed, and turn.py's response-complete gate has an unconditional single-signal veto (`complete_satisfied = complete.satisfied and not current.generating`) with no override path -- so the turn burned the full response-timeout-seconds (3600s) despite the correct answer having rendered almost instantly. A second turn (gpt-t1 @github review) was NOT a bug -- it was genuinely still generating past the flat timeout ceiling, which cannot distinguish 'still legitimately working' from 'actually stuck'. This item replaces the single hard-veto DOM signal with tiered, cross-corroborated evidence and replaces the flat end-to-end timeout with a renewable activity lease, so both failure modes are handled correctly without conflating them.

## Steps

REVISED 2026-08-16, second pass (same reused session, live continuation) -- refines the two-dimension model further. Do not implement the earlier illustrative code sample as-is.

- FOUR independent clocks, not three: (1) start bound -- no response begins -> timeout/ambiguous (existing). (2) progress lease -- maximum permitted silence between corroborated progress observations once a response is active; renewed by a correlated network delta or an actual assistant-content/structure change; expiry means "may be stalled or observation may be insufficient," NEVER by itself successful completion. (3) completion dwell -- the period a CANDIDATE final response must remain unchanged with no newer correlated activity before terminal verification may succeed; this is POSITIVE VERIFICATION EVIDENCE, conceptually different from a timeout -- not a reason to abort, a reason to trust. (4) absolute safety ceiling -- circuit breaker for pathological cases (endless background traffic, non-terminating provider, faulty instrumentation continually renewing the lease); hitting it must preserve unresolved-side-effect/recovery semantics, never return partial text as if successful.
- Classify evidence by PROPOSITION, not by "technology tier" (this supersedes the network>text>DOM ranking entirely): PROGRESS/ACTIVITY evidence (correlated network response bytes, assistant fingerprint/structure changed, a RELIABLE provider busy indicator if one exists, a response-stream event) vetoes completion. TERMINAL evidence (protocol terminal event for the correlated response, stable assistant message, no new correlated activity during completion dwell, final assistant identity unchanged, provider terminal affordance when present) is required to declare done. ANOMALY/ADVISORY evidence (the specific PROVEN-unreliable signals -- the stuck stop-button test-id, the flaky completion/copy control, generic document-wide UI state) is logged but never authoritative either way. Critically: this does NOT mean all DOM signals are weak -- a genuinely reliable busy/generating indicator, if one exists, stays in PROGRESS/ACTIVITY with real veto power. Only the specific signals already proven unreliable in this incident get demoted.
- Keep the observation state machine (AWAITING_START -> ACTIVE -> STABLE_CANDIDATE -> VERIFIED_COMPLETE / SUSPECT_STALLED) -- confirmed as a substantial improvement over boolean-flag-soup.
- PRESERVE the existing double-verification-before-return behavior (snapshot again after the stability window, re-run completion policy, require identical text) -- do not replace it with a direct `return stable_text`, that was an oversimplification in the first draft. Strengthen it with an activity-sequence-number guard: capture `candidate_seq = activity_seq` at candidate completion; require `activity_seq == candidate_seq` PLUS same assistant message identity PLUS same response fingerprint PLUS no correlated network progress PLUS no provider failure evidence, all still true at final confirmation. This closes the finalization race (new activity arriving during terminal verification).
- Network evidence needs explicit correlation requirements, not just bridge Network-domain scoping: lease-renewing traffic must be correlated to at minimum the physical target/page, bridge generation, the relevant ChatGPT response stream/request, and ideally the current provider conversation/turn -- otherwise unrelated ChatGPT requests, or (now that GP05 intentionally supports multiple concurrent conversations through one shared runtime) another concurrent session's traffic, can falsely renew the wrong lease.
- MANDATORY discovery stage before coding the terminal resolver: capture correlated network + DOM + assistant-message evolution for real plain-generation, thinking, web/tool-use, @github-connector, and long-running turns. Do not assume "no response bytes for N seconds" has the same semantics across all of them -- this is exactly the open question the reviewer flagged as empirically unresolved (does ChatGPT's real transport actually go quiet mid-turn during tool/backend work; the biggest remaining false-positive scenario depends entirely on this).
- Deterministic test coverage: same list as before, plus explicit correlation-scoping tests (gpt-t1 network activity must never renew gpt-t2's lease) and a finalization-race test using the activity-sequence-number guard.

## Detailed Solution & Technical Design

REVISED 2026-08-16 (third pass) after a real gpt-auto-reviewer @github/inline-diff design critique (session ses_30929da2c615470b, req_e31817929ad746c6) -- this revision supersedes the two-tier CONCLUSIVE/WIDGET model in the immediately preceding entry. The reviewer confirmed the core direction (activity-driven progress accounting over fixed action-start deadlines) but found a real, serious hole: if soft/widget evidence renews the SAME lease that gates stall detection, a flapping widget (e.g. a UI element re-rendering stop/submit state every ~30s from some React/extension interaction) can keep a turn ACTIVE forever -- directly contradicting the goal that widget evidence must never block a FAILED-class transition, since renewing the very lease that prevents entry into stall detection IS blocking it, just indirectly.

FOUR REQUIRED CHANGES (all accepted, all to be implemented):

1. THREE evidence capabilities, not a binary tier -- one observation may carry more than one:
   - PROGRESS (authoritative): proves the causally-scoped turn actually changed -- normalized current-turn assistant text changed, a new current-turn message/id appeared, the submitted user message appeared matching baseline+prompt. Authority: resets the real inactivity clock (last_conclusive_progress_at), increments a monotonic progress_generation counter, reopens CANDIDATE_TERMINAL, recovers from SUSPECT_STALLED.
   - SOFT_LIVENESS (inferred UI widget state): stop-control transition, streaming/thinking/busy-indicator transition, generating flag. Authority: may grant a small BOUNDED extension anchored to the ORIGINAL progress-lease expiry (e.g. +60s once), never a repeated reset ("widget changed -> another 5 min" is exactly the bug pattern to avoid); diagnostic/logging value only beyond that; must NEVER reset last_conclusive_progress_at.
   - TERMINAL_WITNESS (corroborating): completion-control, message-finalized ([data-is-last-node]). Authority: can contribute to entering/verifying CANDIDATE_TERMINAL/VERIFIED_TERMINAL (already how response-complete's any-of works); does NOT count as progress; cannot reopen an already-entered terminal candidate.
   'Changed message text' only counts as PROGRESS if it is normalized, semantic, current-turn-scoped content change -- explicitly NOT streaming-cursor blinks, hidden a11y text, timestamp mutations, DOM remounts, markdown-renderer restructuring, or React-regenerated message IDs. Use a monotonically increasing progress_generation, incremented only for authoritative PROGRESS; when entering CANDIDATE_TERMINAL record candidate_generation = progress_generation; verification requires progress_generation still equal to candidate_generation (race-resistant, replaces the earlier informal 'nothing conclusive changed since' rule).

2. Separate, non-conflatable clocks (all monotonic): phase_started_at, last_conclusive_progress_at (the ONLY clock gating SUSPECT_STALLED entry), last_soft_activity_at (bounded-extension only, capped, anchored to original expiry not repeatedly pushed forward), candidate_entered_at, candidate_generation, suspect_entered_at. The absolute ceiling is a SEPARATE, orthogonal, much more generous wall-clock budget ("how long is this process allowed to consume resources regardless of progress") -- NOT the same concept as the inactivity lease ("is this turn still making meaningful progress"); conflating them lets a pathological one-character-every-4m59s stream renew authoritative progress forever right up to the ceiling. Hitting the ceiling produces a distinct BUDGET_EXHAUSTED outcome, never a claimed PROVEN_FAILURE.

3. CANDIDATE_TERMINAL gets its own bounded, non-widget-extendable verification window (candidate_started_at + max_candidate_verification_window). If terminal proof cannot be re-established within it (e.g. the terminal witness disappears and text doesn't change and nothing conclusive arrives), transition to SUSPECT_STALLED -- not an indefinite dead-end, and not silently reopened by nothing. SUSPECT_STALLED must be a genuine bounded, ACTIVE, reconciliation phase, not merely 'wait even longer': on entry, take a fresh authoritative snapshot (not incremental), re-bind/re-identify the current turn, re-evaluate terminal criteria from scratch, distinguish 'DOM readable and static' from 'the observer itself is failing', optionally invoke the EXISTING _reconcile_unresolved_turn() path, ignore soft-liveness renewals entirely, and allow PROGRESS to recover immediately. SUSPECT_STALLED needs BOTH recovery edges: -> ACTIVE (new progress) AND -> CANDIDATE_TERMINAL (a TERMINAL_WITNESS becoming valid while text is already stable is legitimate terminal proof even though the witness alone is 'weak' -- do not discard a real terminal proof just because the triggering signal type is individually distrusted). Give SUSPECT_STALLED its own non-resettable grace period distinct from the original progress lease (avoid accidentally turning a 5-minute stall detector into a 20-minute failure detector by chaining budgets naively).

4. SAFETY-CRITICAL RENAME: separate 'we proved this failed' from 'we failed to prove what happened' -- the live bug (submission-proof-not-observed-before-deadline on a genuinely-succeeding turn) IS case 2 misreported as case 1. Conflating them risks a real duplicate-submission bug on retry (observer says FAILED -> caller retries -> original prompt actually existed -> duplicate). Terminal/exit outcomes become: VERIFIED_TERMINAL, UNRESOLVED_STALL (feeds the EXISTING _reconcile_unresolved_turn() path, never authorizes an automatic resubmit -- this is the fix for tonight's exact incident), OBSERVATION_FAILURE (an exception during observation, distinct from a proven negative), BUDGET_EXHAUSTED (absolute ceiling hit), PROVEN_FAILURE (reserved for genuine negative evidence only -- error-page/error-alert/auth-required, not silence).

SHARED MECHANISM, NOT SHARED MEANING (reviewer's phrasing, adopted verbatim): implement as ObservationEngine(policy=SubmissionProofPolicy()) and ObservationEngine(policy=ResponseCompletionPolicy()) -- one reusable state-machine/clock engine, with per-phase policy objects supplying classify_observation() [returns the set of capabilities an observation carries], is_terminal_candidate(), is_terminal_verified(), and the timing constants (start_bound, progress_lease, soft_grace_cap, candidate_stability_window, candidate_max_verification_window, suspect_grace, absolute_ceiling). Do NOT force one hardcoded universal interpretation across both phases -- they have real semantic differences (see below).

SUBMISSION-PROOF-SPECIFIC FIX (the acute, currently-broken phase; root cause of tonight's live incident): the observation clock must begin at submit_dispatched_at (after typing/CDP-submit completes), NOT when the overall submission action started -- today's bug is exactly 7000 characters of typing time silently consuming the 15s submission-proof budget before DOM polling even begins. Track typing_started_at / submit_dispatched_at / observation_started_at as distinct timestamps. Submission-proof's terminal criteria can also be a stronger, faster shortcut than response-completion's: a genuinely new user-message node matching the normalized submitted prompt (today's exact check, unchanged) is very strong PROGRESS+TERMINAL_WITNESS evidence together -- it may still want one confirming re-snapshot to guard against DOM churn, but does not need the same multi-second stability dwell response text needs. A new assistant-turn node appearing causally after submission is independently strong evidence submission occurred even if the user-message selector is briefly unavailable.

RESPONSE-COMPLETION APPLICATION: re-express the EXISTING three-timer logic (response_start_timeout_seconds / response_stall_timeout_seconds / response_timeout_seconds, already fundamentally sound and already close to this model) through the SAME ObservationEngine instead of its current bespoke inline loop -- removing the risk of the two phases silently drifting inconsistent, which is exactly the gap that let submission-proof fall behind response-wait's already-better design in the first place. response-complete's any-of (completion-control OR message-finalized) evidence is TERMINAL_WITNESS-capability evidence in the new model; text-changed is PROGRESS; stop-control/generating stays SOFT_LIVENESS (bounded, non-authoritative) -- this is a direct re-framing of the already-shipped fix (commits 7bd5643/c2d2636/17e7ab8), not a reversal of it.

NOT to be implemented here: network-level (Tier 1) correlation, the reasoning-turn 'Worked for Ns' label, the full-toolbar-render hypothesis -- still future corroborating TERMINAL_WITNESS signals pending their own discovery pass, orthogonal to this state-machine restructuring.

## Code Samples & Guidance

Capability-based evidence (flags, not a mutually-exclusive enum -- one observation may carry several):
```python
class EvidenceCapability(Flag):
    NONE = 0
    PROGRESS = auto()          # authoritative: resets last_conclusive_progress_at, bumps progress_generation
    SOFT_LIVENESS = auto()     # bounded bonus only, never resets the real clock
    TERMINAL_WITNESS = auto()  # can enter/verify a terminal candidate, cannot reopen one

@dataclass(frozen=True)
class Observation:
    capabilities: EvidenceCapability
    terminal_candidate: bool
    terminal_verified_ok: bool  # re-checked at candidate-verification time
```

Outcome enum replacing the old single FAILED (safety-critical split -- 'proved failed' vs 'failed to prove'):
```python
class ObservationOutcome(StrEnum):
    VERIFIED_TERMINAL = "verified-terminal"
    UNRESOLVED_STALL = "unresolved-stall"        # -> feeds _reconcile_unresolved_turn(), never auto-resubmit
    OBSERVATION_FAILURE = "observation-failure"  # exception during observation
    BUDGET_EXHAUSTED = "budget-exhausted"         # absolute ceiling, orthogonal to progress
    PROVEN_FAILURE = "proven-failure"             # only genuine negative evidence (error/auth-required)
```

Separate, non-conflatable clocks + monotonic generation guard:
```python
@dataclass
class ObservationClock:
    phase_started_at: float
    last_conclusive_progress_at: float | None = None
    last_soft_activity_at: float | None = None
    soft_grace_used_seconds: float = 0.0   # capped bonus, anchored to original expiry
    progress_generation: int = 0
    candidate_entered_at: float | None = None
    candidate_generation: int | None = None
    suspect_entered_at: float | None = None
```

Per-phase policy protocol (mechanism shared, meaning is not):
```python
class ObservationPolicy(Protocol):
    start_bound_seconds: float
    progress_lease_seconds: float
    soft_grace_cap_seconds: float
    candidate_stability_window_seconds: float
    candidate_max_verification_window_seconds: float
    suspect_grace_seconds: float
    absolute_ceiling_seconds: float

    def classify(self, baseline, previous, current) -> Observation: ...
```

SubmissionProofPolicy specifics: clock epoch = submit_dispatched_at (NOT typing start -- root cause of the 7000-char live failure); classify() treats a new user-message node matching the normalized prompt as PROGRESS|TERMINAL_WITNESS together; stability window can be short/near-zero (one confirming re-snapshot, not the multi-second dwell response text needs).

ResponseCompletionPolicy specifics: re-expresses the already-shipped response-complete fix -- text-changed => PROGRESS; completion-control/message-finalized any-of => TERMINAL_WITNESS; stop-control/generating => SOFT_LIVENESS only (bounded, logged on disagreement, never authoritative) -- consistent with commits 7bd5643/c2d2636/17e7ab8, just reframed through the shared engine instead of the current bespoke inline loop.
