# Replace single-signal completion veto with tiered evidence and activity-lease timeouts

## Description

Live testing on 2026-08-15/16 against real gpt-t1/gpt-t2 ChatGPT projects produced three real EXT-GPTAUTO-002 timeouts, each independently diagnosed via direct DOM re-inspection. One (gpt-t1 baseline turn) is a confirmed real bug: ChatGPT's own composer submit/stop toggle button did not revert from its 'Stop answering' state after the response genuinely completed, and turn.py's response-complete gate has an unconditional single-signal veto (`complete_satisfied = complete.satisfied and not current.generating`) with no override path -- so the turn burned the full response-timeout-seconds (3600s) despite the correct answer having rendered almost instantly. A second turn (gpt-t1 @github review) was NOT a bug -- it was genuinely still generating past the flat timeout ceiling, which cannot distinguish 'still legitimately working' from 'actually stuck'. This item replaces the single hard-veto DOM signal with tiered, cross-corroborated evidence and replaces the flat end-to-end timeout with a renewable activity lease, so both failure modes are handled correctly without conflating them.

## Steps

REVISED 2026-08-16, second pass (same reused session, live continuation) -- refines the two-dimension model further. Do not implement the earlier illustrative code sample as-is.

- FOUR independent clocks, not three: (1) start bound -- no response begins -> timeout/ambiguous (existing). (2) progress lease -- maximum permitted silence between corroborated progress observations once a response is active; renewed by a correlated network delta or an actual assistant-content/structure change; expiry means "may be stalled or observation may be insufficient," NEVER by itself successful completion. (3) completion dwell -- the period a CANDIDATE final response must remain unchanged with no newer correlated activity before terminal verification may succeed; this is POSITIVE VERIFICATION EVIDENCE, conceptually different from a timeout -- not a reason to abort, a reason to trust. (4) absolute safety ceiling -- circuit breaker for pathological cases (endless background traffic, non-terminating provider, faulty instrumentation continually renewing the lease); hitting it must preserve unresolved-side-effect/recovery semantics, never return partial text as if successful.
- Classify evidence by PROPOSITION, not by "technology tier" (this supersedes the network>text>DOM ranking entirely): PROGRESS/ACTIVITY evidence (correlated network response bytes, assistant fingerprint/structure changed, a RELIABLE provider busy indicator if one exists, a response-stream event) vetoes completion. TERMINAL evidence (protocol terminal event for the correlated response, stable assistant message, no new correlated activity during completion dwell, final assistant identity unchanged, provider terminal affordance when present) is required to declare done. ANOMALY/ADVISORY evidence (the specific PROVEN-unreliable signals -- the stuck stop-button test-id, the flaky completion/copy control, generic document-wide UI state) is logged but never authoritative either way. Critically: this does NOT mean all DOM signals are weak -- a genuinely reliable busy/generating indicator, if one exists, stays in PROGRESS/ACTIVITY with real veto power. Only the specific signals already proven unreliable in this incident get demoted.
- Keep the observation state machine (AWAITING_START -> ACTIVE -> STABLE_CANDIDATE -> VERIFIED_COMPLETE / SUSPECT_STALLED) -- confirmed as a substantial improvement over boolean-flag-soup.
- PRESERVE the existing double-verification-before-return behavior (snapshot again after the stability window, re-run completion policy, require identical text) -- do not replace it with a direct `return stable_text`, that was an oversimplification in the first draft. Strengthen it with an activity-sequence-number guard: capture `candidate_seq = activity_seq` at candidate completion; require `activity_seq == candidate_seq` PLUS same assistant message identity PLUS same response fingerprint PLUS no correlated network progress PLUS no provider failure evidence, all still true at final confirmation. This closes the finalization race (new activity arriving during terminal verification).
- Network evidence needs explicit correlation requirements, not just bridge Network-domain scoping: lease-renewing traffic must be correlated to at minimum the physical target/page, bridge generation, the relevant ChatGPT response stream/request, and ideally the current provider conversation/turn -- otherwise unrelated ChatGPT requests, or (now that GP05 intentionally supports multiple concurrent conversations through one shared runtime) another concurrent session's traffic, can falsely renew the wrong lease.
- MANDATORY discovery stage before coding the terminal resolver: capture correlated network + DOM + assistant-message evolution for real plain-generation, thinking, web/tool-use, @github-connector, and long-running turns. Do not assume "no response bytes for N seconds" has the same semantics across all of them -- this is exactly the open question the reviewer flagged as empirically unresolved (does ChatGPT's real transport actually go quiet mid-turn during tool/backend work; the biggest remaining false-positive scenario depends entirely on this).
- Deterministic test coverage: same list as before, plus explicit correlation-scoping tests (gpt-t1 network activity must never renew gpt-t2's lease) and a finalization-race test using the activity-sequence-number guard.

## Detailed Solution & Technical Design

Root cause of the E2 incident: response-complete evaluation in turn.py (~line 557-559) computes `complete = self.chat.config.workflow.policy('response-complete').evaluate(facts)` then `complete_satisfied = complete.satisfied and not current.generating`. `current.generating` (gpt_auto_cdp.py's _SNAPSHOT_FN, ~line 55-56) is a raw document-wide query for `[data-testid="stop-button"], [data-testid="stop-generating"], .result-streaming, .result-thinking, [aria-busy="true"]` with no corroboration from any other signal. Live evidence (2026-08-15/16): ChatGPT's composer submit button (id=composer-submit-button) matched `[data-testid="stop-button"]` and remained visibly in 'stop' state for hours after the actual response had fully rendered and stabilized -- confirmed by direct re-inspection of the still-open tab well after the timeout fired. Because `current.generating` gates entry into the entire stable-text/response_stability_seconds verification branch (~line 557-576), the turn never even began measuring text stability; it simply waited out the full response_timeout_seconds (3600s) and failed with EXT-GPTAUTO-002, even though the correct, final answer had been sitting on screen the whole time.

Separately, the E1 incident (same error code, different cause) showed the flat response-timeout-seconds ceiling cannot distinguish 'genuinely still working' from 'stuck' -- both hit the identical wall-clock limit and fail identically, even though only one of them is actually a problem. An activity-based renewable lease (already a proven pattern in this codebase at the gateway-watchdog layer, watchdog-policy.activity-lease-seconds) resolves this: extend automatically while real activity is corroborated, fire promptly once it genuinely stops.

Design principle carried over from chat.py's ChatState machine (independently praised by both the live gpt-auto reviewer and this session's own audit as well-designed): no single fragile signal should have unilateral authority over a safety-critical decision. The turn-completion gate currently violates this; chat.py's session-lifecycle machine does not. This item brings the turn-completion layer up to the same standard.

## Code Samples & Guidance

Tiered evidence resolution (illustrative shape, not final):
```python
network_idle = self._network_observer.idle_for(now, threshold=network_idle_seconds)  # Tier 1, new
text_stable = stable_since is not None and now - stable_since >= response_stability_seconds  # Tier 2, existing
dom_says_generating = current.generating  # Tier 3, existing -- no longer a sole veto

if network_idle and text_stable and complete.satisfied:
    if dom_says_generating:
        logger.warning("gpt-auto Tier 3 DOM signal disagreed with Tiers 1+2 at completion", extra={...})
    return stable_text  # Tiers 1+2 agreement wins regardless of Tier 3
```
Activity-lease timeout (illustrative shape):
```python
lease_deadline = last_corroborated_activity_at + activity_lease_seconds
absolute_deadline = started_at + absolute_ceiling_seconds  # hours, circuit-breaker only
if now >= lease_deadline and now < absolute_deadline:
    raise ... # EXT-GPTAUTO-002, short inactivity lease expired
if now >= absolute_deadline:
    raise ... # distinct code/reason: absolute ceiling hit despite ongoing (but uncorroborated) activity
```
