# Reconcile the ambiguous follow-up-submission finding and wire checkpoint persistence into live testing

## Description

During live L5 testing (2026-08-16), an immediate follow-up prompt sent right after a turn resolved failed with EXT-GPTAUTO-003 'composer action was not confirmed by the browser' -- but the error's own details showed enter-dispatched:true (send-button-clicked:false), a FALSE NEGATIVE on submission confirmation, not necessarily garbled input. Enter was likely really dispatched and the browser was observed still generating a response afterward. Read-only reconciliation attempts (CDP inspection of open tabs, no new sessions) could not resolve what actually happened -- the specific conversation's tab was already closed by the time it was checked, and durable checkpoint persistence was not wired into the test harness that hit this (build_session_transport was called without a checkpoint_sink), so there was nothing to reconcile from even in principle.

## Steps

- Wire a real checkpoint_sink into tests/gpt_auto/test_live_stress_scenarios.py's _open_transport() so future live ambiguous-submission cases can actually be reconciled via the existing unresolved-turn checkpoint mechanism (GP04's durable design) instead of being unrecoverable once a tab closes.
- Reproduce the immediate-back-to-back-prompt scenario deliberately (with checkpointing wired in this time) to determine whether ensure_ready()'s DOM/composer-quiescence check has a real gap after a turn resolves, or whether this was purely a test-harness artifact (immediate back-to-back transport.prompt() calls with zero settle gap is not how a real caller would normally behave -- check whether the gateway/session layer already serializes with enough latency to make this moot in production).
- Only implement a fix (e.g. a real DOM-settle wait in ensure_ready()) if reproduction confirms a genuine production gap, not blind.

## Notes

2026-08-16 CODE-CONFIRMED GAP, per user's direct questions ('do we have confirmation the submit button hit has been accepted or worked? do we have a retry or ability to detect if it ends up here again? what state change indicates a real submission'). Read the actual submit() implementation (gpt_auto_cdp.py:124-169): (1) composer clearing IS already correct -- select-all (range.selectNodeContents) + execCommand('insertText') replaces any existing content, so stale leftover text from a prior failed attempt is NOT a corruption risk for a subsequent retry, contrary to an initial worry raised live tonight. (2) 'Click confirmation' is weak by design and explicitly documented as such in the code's own comments: the only proof is 'a matching, non-disabled send-button was found and .click() was called on it' -- there is no verification afterward that the composer actually emptied or that React genuinely processed the click. The REAL authoritative proof of submission is deliberately deferred to the separate submission-proof phase (a new matching user message appearing in the DOM, matched against baseline) -- correct in principle, but that phase is never reached if BOTH the click AND the Enter-dispatch fallback fail to register, which is exactly what happened in tonight's clean GP10 reproduction (send-button-clicked:false). (3) CONFIRMED GAP: there is NO bounded retry of the type-and-click sequence itself within a single turn -- one click attempt, one Enter-dispatch fallback (itself explicitly unverifiable: 'CDP has no proof that ChatGPT accepted it'), and if both fail the turn fails immediately with composer-action-not-confirmed. No re-attempt loop exists at this layer. Given composer-clearing is already safe, a bounded retry (e.g. 2-3 attempts with a short settle delay between them) of the click+Enter sequence before declaring composer-action-not-confirmed would likely resolve a meaningful fraction of these failures without any risk of duplicate submission (since each retry re-clears the composer first) -- worth adding as a concrete, low-risk fix once this item's broader reproduction work confirms the timing window that causes the initial failure.
