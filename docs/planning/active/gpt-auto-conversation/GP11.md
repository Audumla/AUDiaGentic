# Reconcile the ambiguous follow-up-submission finding and wire checkpoint persistence into live testing

## Description

During live L5 testing (2026-08-16), an immediate follow-up prompt sent right after a turn resolved failed with EXT-GPTAUTO-003 'composer action was not confirmed by the browser' -- but the error's own details showed enter-dispatched:true (send-button-clicked:false), a FALSE NEGATIVE on submission confirmation, not necessarily garbled input. Enter was likely really dispatched and the browser was observed still generating a response afterward. Read-only reconciliation attempts (CDP inspection of open tabs, no new sessions) could not resolve what actually happened -- the specific conversation's tab was already closed by the time it was checked, and durable checkpoint persistence was not wired into the test harness that hit this (build_session_transport was called without a checkpoint_sink), so there was nothing to reconcile from even in principle.

## Steps

- Wire a real checkpoint_sink into tests/gpt_auto/test_live_stress_scenarios.py's _open_transport() so future live ambiguous-submission cases can actually be reconciled via the existing unresolved-turn checkpoint mechanism (GP04's durable design) instead of being unrecoverable once a tab closes.
- Reproduce the immediate-back-to-back-prompt scenario deliberately (with checkpointing wired in this time) to determine whether ensure_ready()'s DOM/composer-quiescence check has a real gap after a turn resolves, or whether this was purely a test-harness artifact (immediate back-to-back transport.prompt() calls with zero settle gap is not how a real caller would normally behave -- check whether the gateway/session layer already serializes with enough latency to make this moot in production).
- Only implement a fix (e.g. a real DOM-settle wait in ensure_ready()) if reproduction confirms a genuine production gap, not blind.

Read the actual submit() implementation (gpt_auto_cdp.py:124-169 at the time): (1) composer clearing IS already correct -- select-all (range.selectNodeContents) + execCommand('insertText') replaces any existing content, so stale leftover text from a prior failed attempt is NOT a corruption risk for a subsequent retry. 2026-08-16 PARTIAL FIX IMPLEMENTED: added a bounded retry (3 attempts, 200ms apart) around the send-button-click + Enter-fallback sequence in GptAutoCdp.submit() (gpt_auto_cdp.py). Composer clear-and-retype was already confirmed safe for retries. Locked in with two new deterministic tests: test_gpt_provider_submit_retries_and_recovers_from_transient_send_failure and test_gpt_provider_submit_gives_up_after_bounded_retries. Full gpt_auto suite passes.

2026-08-16 ROOT-CAUSE FIX IMPLEMENTED (the DOM-quiescence gap this item's own steps flagged as needing investigation): _run() (turn.py) took a baseline snapshot at the very start of every turn but never checked it before proceeding straight to _submit_once() -- even when baseline.generating was True or baseline.composer_editable was False, meaning the PREVIOUS turn was still visibly active. ensure_ready() only re-reconciles a chat in RECOVERING state; an already-READY chat's composer state is never independently re-verified at admission time. This is precisely the immediate-follow-up-prompt race reproduced live multiple times tonight.

Added GptAutoTurn._await_composer_settled(): if the baseline isn't settled, poll (bounded by submission_timeout_seconds, paced by poll_interval_seconds) until it is, or give up and proceed anyway once the budget expires -- this does NOT introduce a new failure mode; submit()'s own bounded retry (the earlier GP11 fix) remains the final safety net if the composer still isn't truly ready when we do attempt to type. Locked in with three deterministic unit tests exercising _await_composer_settled directly: already-settled returns immediately (no extra snapshots), settles-after-N-polls correctly waits and picks up the settled state, never-settles gives up cleanly after the bounded budget without hanging. Full gpt_auto suite passes.

This is now a genuine two-layer fix for the same root problem: Layer 1 (this) avoids the race in the common case by waiting for the composer to actually be ready before attempting anything; Layer 2 (the earlier bounded retry in submit() itself) catches the residual case where the wait budget expired or a transient DOM hiccup still occurs. Together these should substantially close the gap, though live validation is still blocked by GP18's CDP instability -- deterministic coverage only tonight.
