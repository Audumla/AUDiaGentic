# Reconcile the ambiguous follow-up-submission finding and wire checkpoint persistence into live testing

## Description

During live L5 testing (2026-08-16), an immediate follow-up prompt sent right after a turn resolved failed with EXT-GPTAUTO-003 'composer action was not confirmed by the browser' -- but the error's own details showed enter-dispatched:true (send-button-clicked:false), a FALSE NEGATIVE on submission confirmation, not necessarily garbled input. Enter was likely really dispatched and the browser was observed still generating a response afterward. Read-only reconciliation attempts (CDP inspection of open tabs, no new sessions) could not resolve what actually happened -- the specific conversation's tab was already closed by the time it was checked, and durable checkpoint persistence was not wired into the test harness that hit this (build_session_transport was called without a checkpoint_sink), so there was nothing to reconcile from even in principle.

## Steps

- Wire a real checkpoint_sink into tests/gpt_auto/test_live_stress_scenarios.py's _open_transport() so future live ambiguous-submission cases can actually be reconciled via the existing unresolved-turn checkpoint mechanism (GP04's durable design) instead of being unrecoverable once a tab closes.
- Reproduce the immediate-back-to-back-prompt scenario deliberately (with checkpointing wired in this time) to determine whether ensure_ready()'s DOM/composer-quiescence check has a real gap after a turn resolves, or whether this was purely a test-harness artifact (immediate back-to-back transport.prompt() calls with zero settle gap is not how a real caller would normally behave -- check whether the gateway/session layer already serializes with enough latency to make this moot in production).
- Only implement a fix (e.g. a real DOM-settle wait in ensure_ready()) if reproduction confirms a genuine production gap, not blind.
