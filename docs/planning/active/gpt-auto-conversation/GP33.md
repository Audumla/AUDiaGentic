# Composer submission times out / prompt-text mismatch on a second turn shortly after a very long first response in the same conversation

## Description

Live-reproduced 2026-08-17 running test_live_t1_scenarios (real gpt-auto-t1 ChatGPT session) as the deliberate live validation of tonight's GP18 (CDP self-heal + session-cache invalidation) and GP32 (response-complete any-of-groups) fixes.

L1 (long-generation scenario) completed successfully: the assistant's response reached 39345+ chars and response-complete correctly fired using the NEW any-of-groups policy -- observation-markers included both completion-control and more-actions-menu, confirming GP32's fix works end-to-end live, not just read-only/deterministically. No CDP-level hangs, stale-session errors, or -32001 'Session with given id not found' errors occurred anywhere in the ~148s run -- GP18's self-heal + session-generation-invalidation fix also held up cleanly across many Target.*/Runtime.evaluate cycles (confirmed via gp18_trace.log).

L4 (mid-turn tab-close scenario), which shares the SAME session/conversation immediately after L1 (by design, to conserve ChatGPT session creation), then failed during SUBMISSION of its own prompt -- before the deliberate tab-close interference ever got a chance to run: EXT-GPTAUTO-003 'gpt-auto composer operation timed out before submission was proven', failure-reason=composer-operation-timeout, submission-ambiguous=true, chat-state=busy, composer-editable=true. Critically: observed-user-text-length=242 vs expected-prompt-length=166, prompt-text-match=false -- the DOM-observed submitted text did not match what was actually typed, a genuine correlation/content mismatch, not just a slow response.

## Steps

- Root-cause whether the mismatch is REAL corrupted/concatenated composer content (e.g. residual text from the prior 39K-char turn's UI state bleeding into the new prompt) or a text-extraction/scoping bug reading the wrong DOM node after a very large prior turn.
- Check whether this is a timing issue specific to submitting a second prompt very soon after ChatGPT finishes rendering a very large (39K+ char) response -- e.g. the DOM is still reflowing/settling and the composer-typing dispatch races that reflow.
- Determine if this is a fresh manifestation of GP19's known residual submission-proof gap (composer-typed-text-mismatch family, seen in gateway_overview's recent_failures earlier tonight) rather than something new -- compare failure shapes.
- The CDP transport itself was proven healthy throughout (gp18_trace.log shows fast, clean command/response cycles right up to the failure) -- this rules out GP18's mechanism as the cause; investigation should focus on the submission/typing layer (gpt_auto_cdp.py's submit()/_submit_once()), not the CDP client.
