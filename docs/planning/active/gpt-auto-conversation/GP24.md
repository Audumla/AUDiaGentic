# Add durable provider-correlation record + ProviderTurnCorrelationSink to the gateway request store

## Description

Slice 2 of GP08 (see GP08's notes for the full live design consultation), depends on slice 1 (unified ordered DOM message sequence) landing first. Establishes the gateway REQUEST RECORD as the owner of correlation truth (not PersistentChat, not the session binding). Adds provider-neutral dataclasses and a new internal 'provider-correlation' field on the gateway request record with three write-once slots (baseline -> +prompt_anchor -> +frozen_result), each mutated via compare-and-set, no update-frozen-correlation operation once frozen.

## Steps

- Add ProviderMessageRef{role,message_id,sequence}, ProviderCorrelationBaseline{provider_session_id,message_refs,prompt_digest,captured_at}, ProviderPromptAnchor{provider_session_id,message_id,sequence}, ProviderCorrelationBoundary{role='user',message_id,sequence,reason} dataclasses.
- Add the 'provider-correlation' field to the gateway request record store, with initialize_correlation/bind_prompt_anchor/freeze_correlation CAS operations (write-if-absent, no-op on idempotent replay, raise CorrelationConflict otherwise).
- Add a new ProviderTurnCorrelationSink callback (mirroring the existing ProviderSessionBindingUpdate pattern) injected by the gateway when building the transport, so gpt_auto never imports gateway internals directly.
- Note: SessionRuntime.prompt_in_session() already sets SessionPrompt.turn_id=request_id, so GptAutoTurn.turn_id IS already the gateway request ID -- no new correlation identifier is needed.
- PersistentChat keeps mark_prompt_submitted()/mark_assistant_observed()/clear_unresolved_turn()/_reconcile_unresolved_turn(), but their meaning changes to 'session-level recovery hint' only, no longer the authoritative correlation answer.

**A) provider-correlation stays on the SAME request record** -- one additional top-level key, not separate storage. Concrete reason: atomicity. The three mutations (baseline/prompt-anchor/frozen-result) are properties of exactly one gateway request with no independent lifecycle/lookup key; _records.py already gives the correct linearization domain (request-id -> mutation.lock -> request JSON -> revision/state/.../provider-correlation). Separate storage would need a second file + either a second lock or cross-file transaction problem, creating crash states like 'correlation frozen but request record not yet updated'. Bump CURRENT_CONTRACT_VERSION from v5 to v6 (current), add `migrated.setdefault('provider-correlation', None)` to _migrate_v1_payload, add the fast-path check `and 'provider-correlation' in payload` to read_record()'s already-current-version branch -- exactly mirrors the existing migration pattern already in the file.

**Critical persistence constraint**: NEVER persist ChatMessageRef.text. _redact_for_persistence() only strips prompt-body today; naively dataclasses.asdict(ref)-ing message_refs would leak text straight to disk. Correlation projections must be built explicitly as `{'role': ref.role, 'message-id': ref.message_id, 'sequence': ref.sequence}`, never asdict(). prompt-digest is already persisted separately; no reason to duplicate prompt text here.

**B) Three CAS functions in _records.py**, matching the file's existing mark_cancel_requested()/acknowledge_cancel() style exactly (lock -> reread under lock -> check current durable value -> idempotent-return or mutate -> revision++ -> write_record -> record_gateway_timeline): initialize_correlation(project_root, request_id, *, baseline_message_refs), bind_prompt_anchor(project_root, request_id, *, prompt_anchor), freeze_correlation(project_root, request_id, *, frozen_result). Deliberately do NOT add expected_revision fencing -- the compare value is the write-once correlation SLOT itself, not the whole record's revision (which changes for unrelated mutations like watchdog/activity/cancellation; a callback that captured revision 17 must not fail merely because unrelated activity bumped it to 18). Each op's CAS predicate: not-yet-set -> install; identical value already present -> idempotent success (returns record unchanged); different value -> raise a new CON-AGW-<N> conflict error. bind_prompt_anchor requires correlation already initialized and not yet frozen; freeze_correlation requires prompt-anchor already bound. Full concrete implementations provided in the consultation transcript (see gp24_gp30_response.txt in this session's scratchpad, or re-fetch if needed) -- copy nearly verbatim, they already match file conventions.

**D) ProviderTurnCorrelationSink** mirrors ProviderSessionBindingUpdate's frozen-value-object + Protocol-callback pattern exactly, but typed strictly (not an untyped metadata: Mapping) since correlation has strict write-once-stage semantics. Recommended home: foundation/transports/turn_correlation.py (beside the existing transport contracts). Shape: ProviderTurnCorrelationOperation(StrEnum: INITIALIZE/BIND_PROMPT_ANCHOR/FREEZE), ProviderCorrelationMessageRef(role, message_id, sequence -- deliberately NO text field), ProviderTurnCorrelationUpdate(turn_id, operation, baseline_message_refs=(), message_ref=None) with strict per-operation field validation (INITIALIZE requires message_ref=None; BIND_PROMPT_ANCHOR requires message_ref.role=='user'; FREEZE requires message_ref.role=='assistant'). turn_id is sufficient routing identity since SessionPrompt(turn_id=request_id) already exists. The gateway-owned sink implementation maps each operation directly onto the three _records.py CAS calls -- gpt_auto still never imports gateway internals directly.

**Sequencing with GP30 (critical ordering constraint)**: GP24 lands the schema/CAS/sink plumbing, baseline initialization (before browser-side submit), and prompt-anchor binding (after submission proof) -- but must NOT call freeze_correlation() from the CURRENT (still-buggy) latest_assistant_id logic in _await_response(), since that would make GP30's bug durable instead of fixing it. GP30 lands the request-scoped span selection and is what makes the FIRST legitimate freeze_correlation() call. Land GP24's plumbing first, wire the actual freeze call only as part of GP30's rewrite.
