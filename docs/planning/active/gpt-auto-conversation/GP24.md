# Add durable provider-correlation record + ProviderTurnCorrelationSink to the gateway request store

## Description

Slice 2 of GP08 (see GP08's notes for the full live design consultation), depends on slice 1 (unified ordered DOM message sequence) landing first. Establishes the gateway REQUEST RECORD as the owner of correlation truth (not PersistentChat, not the session binding). Adds provider-neutral dataclasses and a new internal 'provider-correlation' field on the gateway request record with three write-once slots (baseline -> +prompt_anchor -> +frozen_result), each mutated via compare-and-set, no update-frozen-correlation operation once frozen.

## Steps

- Add ProviderMessageRef{role,message_id,sequence}, ProviderCorrelationBaseline{provider_session_id,message_refs,prompt_digest,captured_at}, ProviderPromptAnchor{provider_session_id,message_id,sequence}, ProviderCorrelationBoundary{role='user',message_id,sequence,reason} dataclasses.
- Add the 'provider-correlation' field to the gateway request record store, with initialize_correlation/bind_prompt_anchor/freeze_correlation CAS operations (write-if-absent, no-op on idempotent replay, raise CorrelationConflict otherwise).
- Add a new ProviderTurnCorrelationSink callback (mirroring the existing ProviderSessionBindingUpdate pattern) injected by the gateway when building the transport, so gpt_auto never imports gateway internals directly.
- Note: SessionRuntime.prompt_in_session() already sets SessionPrompt.turn_id=request_id, so GptAutoTurn.turn_id IS already the gateway request ID -- no new correlation identifier is needed.
- PersistentChat keeps mark_prompt_submitted()/mark_assistant_observed()/clear_unresolved_turn()/_reconcile_unresolved_turn(), but their meaning changes to 'session-level recovery hint' only, no longer the authoritative correlation answer.
