# CDP Target.getTargets hangs (30s timeout) on the test immediately following a concurrent-session close

## Description

tests/gpt_auto/test_live_stress_scenarios.py's live suite reproducibly fails on the SECOND and THIRD tests in a run (test_live_t1_scenarios, test_live_cancel_mid_turn_leaves_session_usable) but not the first (test_live_concurrent_turns_on_both_test_projects_stay_isolated), across two consecutive full runs tonight (2026-08-16) with identical timing both times (~81s total, both failures hitting the exact same 30.0s CDP client default_timeout on client.command('Target.getTargets') inside runtime.py's ensure_dedicated_window_anchor -> bridge.call('list_pages') -> _refresh_pages()). Closing the 4 leftover ChatGPT tabs this session had accumulated made no difference between the two runs (identical failure, identical timing) -- ruling out simple CDP target-count/enumeration slowness as the cause.

## Steps

- Investigate runtime.py's unregister_chat(): when the last chat releases its page (self._dedicated_window_anchor set and self._bridge present), it fires `asyncio.create_task(self.refresh_status_page())` -- fire-and-forget, not awaited, not tracked. The concurrent-isolation test (L3) closes TWO transports back-to-back at teardown, spawning two of these concurrently. If either is still in-flight (making its own CDP calls) when the very next test immediately opens a fresh transport and issues Target.getTargets, the two could contend for the same underlying CDP client's request/response correlation (e.g. a shared request-id counter or websocket read loop), plausibly explaining why the next command never receives its response and times out at exactly the configured 30s.
- Reproduce in isolation: run test_live_concurrent_turns_on_both_test_projects_stay_isolated alone, then IMMEDIATELY (same process) try a bare Target.getTargets call and confirm whether it hangs -- versus waiting a few seconds after L3 finishes before trying, to see if it's purely a race window vs a permanent broken state.
- If confirmed, fix direction: track refresh_status_page()'s task explicitly (store the task reference, await/cancel it during shutdown or before the next command that needs a clean CDP round-trip) rather than leaving it truly fire-and-forget; or serialize it behind the same lock/queue other CDP commands already go through if one exists.
- Also worth checking whether this could affect PRODUCTION multi-session usage, not just this test file's specific back-to-back pattern -- any real caller that closes a session and immediately opens another against the same shared runtime could hit the same race.

## Notes

2026-08-17 STRONG NEW HYPOTHESIS from live design consultation (gpt-auto-agent), ranked above the correlation-bug theory: event-loop ownership mismatch across pytest-asyncio test functions. Each test typically runs on its OWN asyncio event loop by default, but GptAutoProviderRuntime (and its singleton CdpClient/websocket/reader-task/asyncio.Lock/asyncio.Queue/pending-futures-map) is a MACHINE-SCOPED SINGLETON persisting across tests. PythonCdpBridge.start() only checks `if self._client is not None: return` -- it does NOT verify the current event loop still matches the loop the client's reader task actually belongs to. If test 1's loop is torn down after that test completes, the reader task object still technically exists (not garbage collected, not explicitly cancelled) but is no longer being driven by any running loop -- it neither delivers new messages nor exits through its own finally block (since nothing is pumping it). Test 2 (a NEW event loop) creates a new command() future on ITS loop, sends through the stale connection, and waits 30s for a reader task that is merely pending forever, not actively running or dead -- this fits the exact observed symptom (30s timeout, not immediate CdpError, TCP connection remains Established throughout) precisely.

Recommended single remaining live cycle (not yet run, deferred -- growing lateness + GP31 restart-risk budget): instrument CdpClient.start() to record owner_loop/owner_thread identity at socket creation, log loop/thread identity comparisons on every start() call (including the early-return path) and inside command()'s begin/pending-registered/send-lock-acquired/send-returned/timeout-or-completed points, and instrument _read_loop()'s very first line after `async for raw in socket:` to log every raw inbound message before _pending lookup (plus retain timed-out request-ids in a short-lived debug map to catch a late response arriving after the 30s timeout already gave up). Also recommended: passive TCP packet capture (Wireshark/Npcap/pktmon on the one CDP 4-tuple) as a decisive cross-check, since it turns the result into a near-binary verdict (bytes never left the client vs. bytes sent but no response vs. response received but mis-delivered vs. response genuinely late).

Consultation also explicitly deprioritized Nagle/TCP-buffering and WebSocket-frame-fragmentation as low-probability (both would not produce a delay matching exactly the 30s application-level timeout), and flagged _send_lock as worth instrumenting only for completeness, not as a likely cause (since send()/lock-acquisition happen before the 30s wait_for begins, so a clean ~30s interval measured from send.returned already excludes it).

Suggested minimal defensive fix regardless of root-causing further: start() should detect `_socket exists AND current_loop != socket/reader owner loop` and refuse silent reuse (force a reconnect) rather than treating `_socket is not None` alone as proof the async transport is still usable -- this only requires the SAME loop-ownership tracking the instrumentation above would add anyway.
