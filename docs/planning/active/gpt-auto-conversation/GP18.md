# CDP Target.getTargets hangs (30s timeout) on the test immediately following a concurrent-session close

## Description

tests/gpt_auto/test_live_stress_scenarios.py's live suite reproducibly fails on the SECOND and THIRD tests in a run (test_live_t1_scenarios, test_live_cancel_mid_turn_leaves_session_usable) but not the first (test_live_concurrent_turns_on_both_test_projects_stay_isolated), across two consecutive full runs tonight (2026-08-16) with identical timing both times (~81s total, both failures hitting the exact same 30.0s CDP client default_timeout on client.command('Target.getTargets') inside runtime.py's ensure_dedicated_window_anchor -> bridge.call('list_pages') -> _refresh_pages()). Closing the 4 leftover ChatGPT tabs this session had accumulated made no difference between the two runs (identical failure, identical timing) -- ruling out simple CDP target-count/enumeration slowness as the cause.

## Steps

- Investigate runtime.py's unregister_chat(): when the last chat releases its page (self._dedicated_window_anchor set and self._bridge present), it fires `asyncio.create_task(self.refresh_status_page())` -- fire-and-forget, not awaited, not tracked. The concurrent-isolation test (L3) closes TWO transports back-to-back at teardown, spawning two of these concurrently. If either is still in-flight (making its own CDP calls) when the very next test immediately opens a fresh transport and issues Target.getTargets, the two could contend for the same underlying CDP client's request/response correlation (e.g. a shared request-id counter or websocket read loop), plausibly explaining why the next command never receives its response and times out at exactly the configured 30s.
- Reproduce in isolation: run test_live_concurrent_turns_on_both_test_projects_stay_isolated alone, then IMMEDIATELY (same process) try a bare Target.getTargets call and confirm whether it hangs -- versus waiting a few seconds after L3 finishes before trying, to see if it's purely a race window vs a permanent broken state.
- If confirmed, fix direction: track refresh_status_page()'s task explicitly (store the task reference, await/cancel it during shutdown or before the next command that needs a clean CDP round-trip) rather than leaving it truly fire-and-forget; or serialize it behind the same lock/queue other CDP commands already go through if one exists.
- Also worth checking whether this could affect PRODUCTION multi-session usage, not just this test file's specific back-to-back pattern -- any real caller that closes a session and immediately opens another against the same shared runtime could hit the same race.

## Notes

2026-08-16 RECOVERY DESIGN, per user, to be implemented once the actual hang mechanism is found (not blindly implemented tonight): the fix has two distinct layers, and conflating them is why the EXISTING partial recovery logic isn't helping tonight.

Layer 1 (the actual blocker, still unsolved): ensure_dedicated_window_anchor() ALREADY has a fallback to create a brand-new window when no existing anchor is found (bridge.call('create_window_page'), runtime.py:186-199) -- but that fallback is only reached AFTER list_pages() -> Target.getTargets succeeds. Tonight's hang happens IN that very first list_pages() call, before the recovery path can ever run. A 30s hard timeout with no distinguishable 'genuinely no window exists' signal means the existing recovery logic is unreachable in exactly the scenario it exists to handle (the window is gone). Fix direction: make the initial page-discovery call itself bounded and resilient -- e.g. a much shorter timeout specifically for this discovery call (not the general 30s default), with an explicit fallback to 'assume no anchor, attempt to create one' rather than propagating a raw TimeoutError up through the whole open() chain. Do not conflate 'CDP call timed out' with 'definitely no window' without distinguishing evidence, though -- a spurious short timeout could trigger an unnecessary new-window creation while the real one is just slow to respond, so this needs care, not just a smaller number.

Layer 2 (the recovery behavior once Layer 1 works): once a new dedicated window/anchor is created, every session that was tracking a page in the now-gone OLD window needs to re-locate or reopen its own tab to keep monitoring an in-flight turn -- this is the SAME class of recovery PersistentChat already has for a single closed tab (GP04's tab-close recovery: reconcile via the durable provider chat-url/conversation-id, reopen/navigate to the exact same ChatGPT conversation rather than starting fresh), just triggered at the WINDOW level (all of a project's tabs gone at once) instead of a single tab. Should reuse that existing per-chat reconciliation mechanism rather than building a second, parallel recovery path -- the window-level trigger is new, the actual reconnection logic should not be.

Scope check before implementing: confirm whether this whole class of failure (window-level loss, not just single-tab loss) is realistic in PRODUCTION use (an operator closing the shared dedicated window, or a browser crash/restart) versus being specific to tonight's unusual test environment (manual close mid-live-testing, multiple deliberate Brave restarts) -- worth designing for the real production scenario, not just tonight's artificial one, but don't over-build for a scenario that turns out to be rare.
