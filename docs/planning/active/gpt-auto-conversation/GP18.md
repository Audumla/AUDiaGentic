# CDP Target.getTargets hangs (30s timeout) on the test immediately following a concurrent-session close

## Description

tests/gpt_auto/test_live_stress_scenarios.py's live suite reproducibly fails on the SECOND and THIRD tests in a run (test_live_t1_scenarios, test_live_cancel_mid_turn_leaves_session_usable) but not the first (test_live_concurrent_turns_on_both_test_projects_stay_isolated), across two consecutive full runs tonight (2026-08-16) with identical timing both times (~81s total, both failures hitting the exact same 30.0s CDP client default_timeout on client.command('Target.getTargets') inside runtime.py's ensure_dedicated_window_anchor -> bridge.call('list_pages') -> _refresh_pages()). Closing the 4 leftover ChatGPT tabs this session had accumulated made no difference between the two runs (identical failure, identical timing) -- ruling out simple CDP target-count/enumeration slowness as the cause.

## Steps

- Investigate runtime.py's unregister_chat(): when the last chat releases its page (self._dedicated_window_anchor set and self._bridge present), it fires `asyncio.create_task(self.refresh_status_page())` -- fire-and-forget, not awaited, not tracked. The concurrent-isolation test (L3) closes TWO transports back-to-back at teardown, spawning two of these concurrently. If either is still in-flight (making its own CDP calls) when the very next test immediately opens a fresh transport and issues Target.getTargets, the two could contend for the same underlying CDP client's request/response correlation (e.g. a shared request-id counter or websocket read loop), plausibly explaining why the next command never receives its response and times out at exactly the configured 30s.
- Reproduce in isolation: run test_live_concurrent_turns_on_both_test_projects_stay_isolated alone, then IMMEDIATELY (same process) try a bare Target.getTargets call and confirm whether it hangs -- versus waiting a few seconds after L3 finishes before trying, to see if it's purely a race window vs a permanent broken state.
- If confirmed, fix direction: track refresh_status_page()'s task explicitly (store the task reference, await/cancel it during shutdown or before the next command that needs a clean CDP round-trip) rather than leaving it truly fire-and-forget; or serialize it behind the same lock/queue other CDP commands already go through if one exists.
- Also worth checking whether this could affect PRODUCTION multi-session usage, not just this test file's specific back-to-back pattern -- any real caller that closes a session and immediately opens another against the same shared runtime could hit the same race.
