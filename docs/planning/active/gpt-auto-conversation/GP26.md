# Add machine-level gpt-auto config drift detection scan at gateway startup

## Description

Slice 3 of GP09 (see GP09's notes for the full live design consultation), depends on slices 1-2 (config loader, schema migration) landing first. Closes the remaining GP09 gap: no tooling exists today to detect config/code schema drift across the multiple projects sharing one machine-scoped gateway process. Adds a known-projects.json registry and a startup compatibility scan.

## Steps

- Add ~/.audiagentic/services/machine/agent-execution-gateway/default/known-projects.json tracking last-seen/last-config-check timestamps per project.
- Run a compatibility scan in GatewayServiceHost.serve_forever() startup, before ready=True.
- Invalid MACHINE-level config fails gateway startup entirely (correct -- it's the shared foundation); invalid PROJECT config blocks only that project (per the schema migration slice's per-project rejection).
- Write-time guard: patch_provider_config() validates before persisting, not after.

## Detailed Solution & Technical Design

Implemented in four coordinated pieces:

1. known-projects registry (new): src/audiagentic/components/agents/gateway/service/known_projects.py. REGISTRY_SCHEMA_VERSION=1; KnownProject/KnownProjectsRegistry/ProjectConfigScanResult dataclasses; load_known_projects() tolerant of missing/corrupt/unsupported-schema files (warns, returns empty, never overwrites an unsupported schema); record_known_project() merges latest on-disk then atomically writes (temp + fsync + os.replace); scan_known_gpt_auto_projects() revalidates every known project, marks missing project dirs as project-dir-missing, captures validation error codes, and never fails the scan or the gateway itself.

2. gpt_auto/config.py validation façades: machine_gpt_auto_override_path(provider_id) -> ~/.audiagentic/config/providers/<provider>.yaml (via global_config_dir); _load_machine_override() returns {} when absent/corrupt; resolve_gpt_auto_config(project_settings) merges packaged defaults -> machine override -> project overlay through deep_merge; GptAutoConfig.from_project_dict now routes through the three-tier resolver; validate_machine_gpt_auto_config() is startup-fatal for invalid machine config; validate_project_gpt_auto_config(project_root) returns the effective config and raises VAL-GPTAUTO-001 for incompatible projects (isolated to that project).

3. host.py wiring: GatewayServiceHost.serve_forever() runs validate_machine_gpt_auto_config() then scan_known_gpt_auto_projects(self.service_store.root / known-projects.json, check_project=validate_project_gpt_auto_config) after durable request recovery (correctness-critical) and before the ready heartbeat (SH07).

4. Write-time guard: patch_provider_config() validates the candidate through resolve_gpt_auto_config() BEFORE persisting for any provider_id.startswith('gpt-auto'); non-AudiaGenticError validation failures are wrapped as VAL-PCFG-004 (resolution added to providers/error-resolutions.yaml).

Registry population: GatewayServiceApplication.invoke() records last-seen on every work-producing operation via _record_project_encounter() (best-effort, never affects admission), so the registry fills between boots.

## Effort & Risk

Machine config corruption path is intentional fail-closed for the shared foundation; corrupt/unsupported registry never blocks startup (advisory). Per-project isolation verified by unit tests. Live ChatGPT not required for deterministic coverage.

## Standards

Respect machine-versus-project configuration ownership, use atomic durable registry updates, redact sensitive configuration from diagnostics, and cover startup failure and recovery paths with deterministic tests.

## Acceptance Criteria

Gateway startup performs the machine-level project compatibility scan before advertising readiness, fails closed for invalid shared configuration, records last-seen/check timestamps atomically, and applies sparse project overlays without mutating project-owned configuration or unrelated projects.
