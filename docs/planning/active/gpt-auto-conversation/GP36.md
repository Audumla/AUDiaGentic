# Formalize DOM-recovery of the last request/response pair as a first-class capability

## Description

Tonight (2026-08-17) repeatedly hand-recovered a turn's actual content by writing a throwaway CDP script to read the live DOM directly, whenever the gateway's own reported status was stuck, stale, or ambiguous (GP19's original gap, tonight's frozen-status review request, the earlier GP33/GP34 canvas investigations). This is a real, recurring operational need, not a one-off debugging trick: formalize it into an actual API/tool rather than an ad-hoc script every time.

## Steps

- Add a read-only recovery operation (e.g. GptAutoSessionTransport.recover_last_exchange() or a gateway-level tool) that, given a live or recently-live session/page handle, re-derives the last user/assistant message pair directly from the current DOM snapshot using the SAME production _SNAPSHOT_FN + ChatMessageRef machinery the adapter already uses internally -- not a bespoke script.
- Decide the trigger surface: an MCP tool callable when a request's reported status looks stuck/ambiguous, and/or an automatic fallback path inside the gateway's own status-reporting when it detects its own status hasn't advanced in N seconds despite a live session (ties into GP24/GP18 status-tracking gaps found tonight).
- Scope to READ-ONLY recovery of the most recent exchange only -- this is distinct from and narrower than a full browsable history index (see the separate item for that).

## Detailed Solution & Technical Design

GP24 explicitly does NOT persist ChatMessageRef.text (only role/message-id/sequence, for correlation purposes) -- this capability is different: it retrieves the actual response CONTENT, live, from the DOM, on demand. It does not require any new persistent storage; it only formalizes read access to state that already exists in the live browser tab. Also directly relevant: tonight's review-request status tracking gap (agent_task_status stayed frozen at state=running/activity-sequence=0 for 10+ minutes despite the underlying ChatGPT turn genuinely completing) -- this capability would let a caller self-recover from exactly that situation instead of needing manual DOM scripting.
