# Gateway leaves abandoned requests/sessions in non-terminal state indefinitely

## Description

The gateway's session/request bookkeeping has no sweep or reconciliation mechanism for records whose owning process has exited without a clean close. They simply accumulate as non-terminal (running/active) forever. Discovered while auditing GP04's "never leave a request non-terminal after real completion/failure" requirement, but this is a gateway-wide gap, not specific to the gpt-auto adapter -- it likely affects every provider that goes through the same session/request store.

## Steps

- Confirm scope: check whether other providers (not just gpt-auto) also accumulate stale running/active records, or whether this is somehow gpt-auto-specific (e.g. tied to its long-lived session_keep_alive usage pattern).
- Design a reconciliation sweep: on gateway startup (and/or periodically), detect requests with state=running whose worker/process no longer exists and no longer has an active watchdog lease, and transition them to a terminal state (interrupted or failed) with an honest close-reason -- never silently drop them, never silently mark them completed.
- Do the same for sessions: state=active with runtime-state=stale-non-live should transition based on policy (idle-timeout-seconds/max-lifetime-seconds if set, or an explicit sweep) rather than staying active indefinitely.
- Respect cancel-requested=true specifically: a request that was cancelled days ago and never reconciled is a clear, unambiguous case that should resolve to cancelled/interrupted, not require guessing about intent.
- Add regression coverage: a request/session record simulating an exited owning process must be swept to a terminal state on the next reconciliation pass, with an audit trail of why.

## Detailed Solution & Technical Design

Live audit evidence (2026-08-15/16, via agent_task_list_requests(state='running') and agent_task_session_list(state='active')): 5 gpt-auto requests dated 2026-08-06 through 2026-08-10 are persisted as state=running with cancel-requested=true and watchdog-state=not-started -- cancellation was requested 5-10 days before this audit and never reconciled. Separately, 6 more gpt-auto sessions dated 2026-08-12 through 2026-08-14 are persisted as state=active despite runtime-state=stale-non-live (owning process long gone). None of these are related to any live testing performed today; they predate it. This strongly suggests there is currently no sweep/reconciliation pass that runs against the persisted store to close out records whose owning process/worker has disappeared -- the gateway only reconciles state when something actively touches a given record (e.g. a status query or a resume attempt), not proactively.
