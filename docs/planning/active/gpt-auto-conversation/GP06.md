# Reconcile durable gateway records against runtime ownership on restart (extend existing reaper, don't build a new sweeper)

## Description

The gateway's session/request bookkeeping has no reconciliation pass for records whose owning process has exited without a clean close. They accumulate as non-terminal (running/active) indefinitely. Discovered while auditing GP04's bulletproof-completion requirement. 2026-08-16 live review (reused session ses_caaace36a7be4c88): this codebase already has the right pattern to extend -- SessionRuntime's existing periodic reaper plus AS91's deliberate separation of pure observation/classification (is_proven_owned_turn_dead(), which accepts ONLY positive ownership/death evidence -- silence and elapsed time are explicitly declared insufficient) from lifecycle mutation. Do not design a new stale-record sweeper; extend that reaper+classifier+workflow-transition+locked-mutation model instead.

## Steps

- Reframe internally as "reconcile durable in-flight gateway records against current runtime ownership," not "sweep abandoned records to terminal state" -- the word sweep is fine as an implementation action, it should not be the semantic model (this was the reviewer's explicit correction).
- The safety boundary per the review: do NOT use `updated-at older than N seconds -> abandoned` or `no recent event -> abandoned`. That contradicts the existing ownership discipline and is actively dangerous for long gpt-auto tool/search turns that can legitimately go quiet for a while. Instead ask: `record says non-terminal AND does this runtime generation currently own it?` -- a new process cannot own an old process's in-memory session handle/turn task; that is a stronger, immediately-available fact, not a timeout inference.
- Requests: converge orphaned running requests (record says running, no current owner) to the EXISTING terminal state `interrupted` with a bounded reason such as runtime-owner-lost/gateway-restarted. Do NOT mark them failed unless failure was actually observed -- interrupted already means exactly "was executing, owning generation disappeared, no terminal outcome recorded."
- Sessions: do NOT map orphaned active sessions to failed -- a gateway restart does not prove a durable provider conversation failed (for gpt-auto specifically, the browser conversation may still be perfectly usable). Two defensible options per the review: (a) minimal -- transition to closed with a precise close-reason (runtime-owner-lost), preserving the provider binding for explicit resume via existing resume machinery (which only requires the source session to be terminal, not specifically failed); (b) cleaner -- add a new terminal `interrupted` state to gateway sessions too, mirroring requests, since closed ordinarily implies intentional completion and this is involuntary owner loss. Reviewer slightly prefers (b) long-term but (a) is lower-impact and already compatible with existing resume machinery -- start with (a).
- Run the reconciliation pass at gateway ownership establishment/startup (this directly automates the manual workaround GP04's runbook currently documents: close the orphan source, then resume with stored fingerprints), plus whatever periodic repair pass handles crashes that aren't clean restarts.
- Use the existing per-record cross-process mutation locking (StartupLock, already used because multiple service processes can mutate session records) for the reconciliation writes.
- Add regression coverage: a request/session record simulating an exited owning process converges to interrupted (requests) / closed-with-runtime-owner-lost (sessions) on the next reconciliation pass, with an audit trail; a record with a genuinely live, provable owner must NOT be touched regardless of its age.

## Detailed Solution & Technical Design

Live audit evidence (2026-08-15/16, via agent_task_list_requests(state='running') and agent_task_session_list(state='active')): 5 gpt-auto requests dated 2026-08-06 through 2026-08-10 are persisted as state=running with cancel-requested=true and watchdog-state=not-started -- cancellation was requested 5-10 days before this audit and never reconciled. Separately, 6 more gpt-auto sessions dated 2026-08-12 through 2026-08-14 are persisted as state=active despite runtime-state=stale-non-live (owning process long gone). None of these are related to any live testing performed today; they predate it. This strongly suggests there is currently no sweep/reconciliation pass that runs against the persisted store to close out records whose owning process/worker has disappeared -- the gateway only reconciles state when something actively touches a given record (e.g. a status query or a resume attempt), not proactively.

## Notes

2026-08-16 GATEWAY CLIENT AUTO-BOOTSTRAP GAP CONFIRMED WITH DIRECT REPRODUCTION: performed a real gateway restart (audiagentic gateway stop --force via the standalone CLI client, then start_or_attach_gateway() from a fresh out-of-process script -- both necessary since tonight's code fixes to runtime.py/chat.py could not take effect in the already-running process, and the graceful stop path correctly refused while sessions were live, confirming that safety check works). After the restart, three consecutive MCP tool calls (agent_task_gateway_overview, agent_task_session_list, agent_task_submit) all failed identically with NET-AGSV-002 (gateway service unavailable) -- with NO self-healing retry -- until a fresh out-of-process script explicitly called start_or_attach_gateway() to relaunch the service.

Root cause, precisely located: get_gateway_client() (src/audiagentic/components/agents/gateway/client.py, ~line 243-309) in 'automatic' mode DOES call start_or_attach_gateway() (line 300-304) -- but only on a cache miss. The result is cached process-wide in module-level _CLIENT/_CLIENT_CONFIG globals (line 259-262): `if _CLIENT is not None and _CLIENT_CONFIG == config: return _CLIENT`, with NO liveness check and NO invalidation on a subsequent request failure. Once any process (e.g. this session's MCP server) makes its first gateway call and caches a client, that cache is never revisited for the lifetime of the process -- if the underlying gateway service later dies, every subsequent call just fails against the dead endpoint forever, never re-invoking start_or_attach_gateway() to recover. The client's HTTP-based statelessness means it LOOKS like it self-heals once some other process independently relaunches a service on the same port (as happened here via manual intervention) -- but there is no actual retry/recovery logic on the failing client's own side.

ACTION: on a NET-AGSV-002-class failure (or any confirmed-unreachable-endpoint failure), get_gateway_client() should invalidate its cached _CLIENT (mirroring reset_gateway_client(), which already exists for exactly this purpose but is never called automatically) and retry via start_or_attach_gateway() -- which is itself already designed to safely attach to a proven live owner or start fresh, so this is a low-risk, well-scoped fix: call the existing reset+retry path automatically on failure instead of only manually. This directly explains and fixes the user's reasonable expectation that 'the gateway is supposed to start via MCP on first call' -- it does, but only literally the first call of a process's lifetime; every gateway restart thereafter currently requires manual out-of-process intervention exactly like what was needed here tonight.

Separately confirmed during this same restart: the previously-live session ses_caaace36a7be4c88 correctly transitioned to state=closed (not left dangling) as a direct result of the forced stop, and the durable request store correctly survived the restart intact (total_requests unchanged at 315, by_state counts preserved) -- the persistence layer itself is sound; this finding is specifically about the CLIENT-side reconnection gap, not data loss.
