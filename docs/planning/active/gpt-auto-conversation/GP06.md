# Reconcile durable gateway records against runtime ownership on restart (extend existing reaper, don't build a new sweeper)

## Description

The gateway's session/request bookkeeping has no reconciliation pass for records whose owning process has exited without a clean close. CORRECTED 2026-08-16 (final full-pack review): this is now split into request-ownership reconciliation and session-ownership reconciliation, which must be handled INDEPENDENTLY and differently -- do not treat them the same way, and do not close active sessions merely because their runtime owner is gone.

## Steps

CORRECTED 2026-08-16, final review -- supersedes the earlier 'sessions -> closed with runtime-owner-lost' proposal, which was WRONG and is now explicitly rejected:

CRITICAL CORRECTION: gateway runtime death does NOT prove provider-session death -- it proves only that the former in-memory transport owner is gone. This codebase ALREADY has a deliberate, working gateway-restart recovery contract for sessions: production session dispatch calls `runtime.rehydrate_session()` when it encounters an active durable session whose process-local handle is absent, and `SessionRuntime.rehydrate_session()` explicitly documents that live handles are process-local, the durable session remains active across a gateway restart, and the same provider conversation is reattached in place (not a successor generation). GP06 must NOT blanket-close active sessions on owner loss -- that would turn an intentionally recoverable state into a terminal one, contradict GP04's own recovery semantics, and undermine PC14's resumability work. PRESERVE the existing active-session-plus-absent-local-handle-equals-lazily-rehydratable model.

CORRECTED MODEL: reconcile REQUEST ownership and SESSION ownership independently:
- A request that was actively executing when its gateway owner vanished CAN correctly become `interrupted` (already the right terminal state for 'AUDiaGentic lost authoritative execution ownership/outcome evidence' -- explicitly NOT 'provider failed' or 'prompt definitely did not complete').
- Its durable SESSION should remain active-but-detached from a process-local runtime, exactly as today, eligible for lazy rehydration via the EXISTING mechanism. Only positive evidence that the provider conversation itself cannot be reattached should ever terminalize a session -- runtime-owner-loss alone is not that evidence.
- If a more explicit durable representation is wanted later, an orthogonal `runtime-attachment = detached/lost` marker (separate from the provider-session lifecycle) would be cleaner than overloading session state -- not required for the initial fix.

NEW HIGHEST-PRIORITY SUB-PROBLEM (P0, do this first, before any general reconciliation mechanism): the bigcherry incident is not simply 'a stale record' -- it means a durability invariant was violated AFTER admission. Normal admission constructs and atomically persists the request record in `queued` state BEFORE enqueue() is called (the queue contract requires this). So 'admitted request existed -> provider side effect occurred -> durable request became absent/unaddressable' is a genuine data-loss defect, not just a reconciliation gap. Before implementing any general sweep: reproduce/instrument this exact transition and establish precisely how/where the record becomes unavailable. Do not paper over this with a generic orphan sweeper until the actual loss mechanism is understood.

IMMEDIATE, SEPARATE, SAFE QUICK FIX (do this now, independently of the rest of GP06): the current admission-recovery error wording ('the conversation remains recoverable and no prompt was sent') is actively FALSE/unsafe given the confirmed incident -- a prior unresolved turn may already have been sent and may even have completed. Correct the wording to only claim what is actually known: 'this new admission attempt did not submit another prompt; the previous unresolved turn's outcome is not yet proven.' This is a small, low-risk, high-value patch independent of the rest of GP06's design work.

Cache invalidation on NET-AGSV-002 (confirmed correct by the reviewer via direct code inspection of get_gateway_client()), WITH an important safety refinement: separate 'reacquire a live gateway client' from 'is it safe to replay the RPC that failed.' NET-AGSV-002 covers URLError/TimeoutError/OSError -- a timeout does NOT prove the RPC never reached the server; the request may have committed with only the response lost. So: automatic mode should invalidate the dead cached client and reacquire/bootstrap a live gateway unconditionally (safe), but a SEPARATE retry policy must decide whether the original failed RPC is replay-safe -- reads/status/list calls may be retried freely, but mutating operations (submit, resume, control, close) need either proven idempotency for that specific request identity or transport-level proof the failure occurred before server acceptance, before being replayed. Do not blindly replay arbitrary RPCs after reconnecting. StandaloneGatewayClient._call() already has a bounded reattach precedent for a specific owner/lease conflict (CON-AGSV-018) worth reusing as a pattern, though NET-AGSV-002 itself is less semantically precise than that case.

Deterministic duplicate-tab selection (GP04's finding): confirmed safe and correct to implement as proposed, with one addition -- if a candidate tab is already claimed by a different LIVE gpt-auto chat (per the existing conversation/page ownership maps), do not silently hop to it; that would bypass the ownership invariant those maps exist to enforce.

Overall priority within GP06 itself: (1) the false-error-wording quick fix, immediately; (2) reproduce/instrument the request-record-loss mechanism and fix request-side reconciliation to `interrupted` for proven-dead owners, WITHOUT touching session lifecycle; (3) the gateway-client cache invalidation + replay-safety split. Do not implement the original session-closing proposal at all.

## Detailed Solution & Technical Design

Live audit evidence (2026-08-15/16, via agent_task_list_requests(state='running') and agent_task_session_list(state='active')): 5 gpt-auto requests dated 2026-08-06 through 2026-08-10 are persisted as state=running with cancel-requested=true and watchdog-state=not-started -- cancellation was requested 5-10 days before this audit and never reconciled. Separately, 6 more gpt-auto sessions dated 2026-08-12 through 2026-08-14 are persisted as state=active despite runtime-state=stale-non-live (owning process long gone). None of these are related to any live testing performed today; they predate it. This strongly suggests there is currently no sweep/reconciliation pass that runs against the persisted store to close out records whose owning process/worker has disappeared -- the gateway only reconciles state when something actively touches a given record (e.g. a status query or a resume attempt), not proactively.
