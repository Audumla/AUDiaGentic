# Migrate shared embedded rig lifecycle to the managed-service foundation

## Description

The embedded rig is a machine-scoped shared OpenAI-compatible service: exactly one GPU-backed rig may run, while multiple generic harness launches can attach safely. The generic harness and HA07 model projection work now correctly separate provider configuration from runtime lifecycle, but `runtime/rig/registry.py` still carries a pre-foundation lifecycle island (`rig.json`, PID-named client files, local lock, image-name reaper, and destructive model read). That conflicts with the completed PR05–PR07 ManagedService foundation, which is the sole reusable authority for shared-process ownership evidence, start-or-attach, leases, guarded stop, stale recovery, and detached-process behavior.

Migrate the rig to a thin domain adapter over `ManagedServiceLifecycle`. Retain rig-specific facts only: model profile launch declaration, `/v1/models` readiness and model compatibility handshake, endpoint/port configuration, and rig-specific error wording. The adapter must not reintroduce a second registry, PID counter, reaper, lock, or watchdog. The completed early PR04 fixes (single shutdown authority, lock-held attach, atomic write, adoption model check) remain behavioural regressions to preserve until the old registry is deleted.

## Steps

**Validate first:** characterize the current registry defects with focused tests: an unrelated `llama-server` must never be killed; a compatible second harness attaches without a second rig; the starter may exit while an attached client continues; an incompatible model request does not disrupt active clients; and an abruptly terminated client lease eventually permits safe cleanup.

1. Define the rig's machine-scoped `ManagedServiceDeclaration` and `ManagedServiceHooks` at the rig composition seam. Use a stable service key, detached `shared-service-host` process evidence, the configured endpoint/port, bounded `/v1/models` health and identity handshake, and a launch declaration derived from the selected rig model profile.
2. Replace `launch_rig_if_needed`'s direct `rig.json`/registry flow with foundation `start_or_attach`. Acquire the caller's renewable lease before returning the endpoint. A compatible live rig is attached; no service record or process-name scan may be used to discover or kill an external server.
3. Replace `shutdown_rig_if_last` with lease release followed by foundation guarded shutdown. Preserve one transition authority and final lease/quiescence/ownership re-checks. The rig adapter supplies only its domain quiescence and graceful-stop callbacks; foundation owns the lock, record mutation, expiry, escalation, and cleanup.
4. Express model compatibility in the handshake/declaration. A different requested model with active leases returns a classified busy/incompatible outcome and leaves the existing rig untouched. With no active leases, the controlled drain/stop/relaunch path is used only after ownership proof succeeds. Reads and probes are side-effect free.
5. Use foundation lease expiry/recovery for hard-killed harnesses. Do not build a rig-local PID-file lock or detached polling watchdog. Choose a bounded renewal interval and expiry policy that releases a crashed client without stopping a healthy leased rig.
6. Remove `runtime/rig/registry.py` and all callers/tests once the adapter covers its behaviour. Remove legacy `rig_pid`/`manages_rig` lifecycle semantics if they no longer carry useful non-lifecycle presentation data; do not retain compatibility wrappers. Keep the generic OpenAI-compatible endpoint projection from HA07 independent of the service lifecycle record.
7. Add architecture coverage rejecting component-local shared-service state/reaping for the rig, and verify generic provider launch paths still consume the same projected endpoint/model contract.

## Detailed Solution & Technical Design

The rig becomes a consumer of the existing `foundation.system.managed_service` façade, not a special runtime lifecycle framework. Its declaration identifies `(service_kind='embedded-rig', service_id=<configured profile/model compatibility key>, scope='machine')`; the exact identity/keying must permit one physical rig while the handshake decides whether a requested model is compatible. The service record contains foundation-owned process evidence, endpoint identity, owner epoch, readiness facts, and renewable client leases. It must not duplicate `rig.json` or a clients directory.

The rig adapter maps the existing embedded launch command into `ManagedServiceDeclaration`, probes `/v1/models` for readiness and served-model identity, and maps foundation outcomes to established AUDiaGentic errors. Harness code remains generic: it asks for a rig endpoint/model and releases its lease at its existing lifecycle boundary. Provider adapters and model-source projection remain configuration-only; neither writes lifecycle state.

Stop/reap is permitted only through the managed-service guarded shutdown path after current process ownership proof, zero active leases, and rig quiescence. External OpenAI-compatible endpoints are never adopted as killable embedded rigs merely because they use the port or executable name.

## Validation

1. Focused unit tests prove the adapter calls foundation start-or-attach/release/guarded-shutdown and does not read/write legacy registry files.
2. Two generic-provider harnesses attach to one compatible rig; terminating the starter leaves the attached client functional; releasing the final lease stops the owned rig and clears the managed-service record.
3. Concurrent cold starts yield one owned rig, one owner epoch, and leases for all clients.
4. A decoy `llama-server` and an external OpenAI-compatible endpoint are never terminated or adopted as owned; no image-name reaping remains.
5. A different model request while a lease is active returns the classified busy/incompatible outcome and leaves the rig alive; after all leases are released, a controlled model change succeeds only with ownership proof.
6. Force-killing the final harness expires its lease under the configured bounded policy and reclaims the owned rig; prove Windows and Linux/Docker paths.
7. Existing generic harness facade, model projection, and provider materialization tests remain green; run focused managed-service lifecycle tests and architecture policy tests; ruff clean.

## Effort & Risk

Medium scope, high integration sensitivity. The foundation is complete and platform-tested, so the risk is migration fidelity rather than inventing synchronization. Preserve the current user-facing embedded/external endpoint behaviour, keep raw process details out of records, and avoid overloading model-source configuration with lifecycle state. Any missing generic capability must be proven by the rig adapter and added to foundation with its own tests rather than patched locally.

## Notes

Review RV855 (2026-07-28) supersedes the remaining pre-foundation implementation shape. The current code preserves earlier PR04 fixes: provider-specific unconditional rig teardown is gone, attach/release are lock-serialized, rig-state writes are atomic, and adoption verifies the served model. It still has the critical remaining defects: PID-file liveness, image-name reaping, and destructive mismatch handling in `read_rig_state`.

PR05, PR06, and PR07 are completed. Their ManagedService contract now owns the mechanisms PR04 had proposed to build locally: durable state, cross-process lock/epoch/revision, renewable leases, ownership proof, detached launch, start-or-attach, guarded shutdown, recovery, and platform validation. Therefore PR04 must consume that foundation and delete the legacy registry rather than complete old steps 3–6 in place.

HA07's local OpenAI-compatible source projection is intentionally orthogonal: it publishes the model connector config used by providers, while PR04 owns only the embedded rig process lifecycle.
