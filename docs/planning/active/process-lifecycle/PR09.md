# Add an explicit upgrade lifecycle to provisioning recipes

## Description

Add `upgrade` as a first-class, explicit provisioning lifecycle operation. Today recipes provide probe/install/configure/verify/uninstall/prune; reapplying a recipe can be idempotent, but the contract has no standard way to compare a present dependency with its declared target, expose upgrade availability, stage a replacement, or preserve rollback evidence. This leads consumers such as the embedded llama.cpp rig to invent imperative update paths.

`upgrade` means a deliberate reconciliation of an already-present owned dependency to a declared desired version/provenance. It is not a background updater, a mutable upstream discovery mechanism, or a synonym for configuration update. Install remains the absent-artifact path; upgrade must be safe to call when current, report no change, and never mutate a dependency that the recipe does not own.

## Steps

1. Audit and classify every current recipe family before changing the contract. For each, record: ownership boundary, installed artifact/version probe, whether an upgrade is meaningful, desired-version/provenance source, safe staging/rollback possibility, explicit user trigger, and whether it is install-only/configuration-only/external-managed. Do not force an upgrade implementation where the provider/package manager already owns it or where version evidence is unavailable.
2. Extend the foundation recipe contract, result/state vocabulary, lifecycle orchestration, execution modes, materialization, schema, registries, public APIs, and tool-facing capability metadata with `upgrade` and `upgrade-status`/plan semantics. Preserve backward compatibility for existing install/configure/verify/prune callers.
3. Define generic upgrade invariants: explicit invocation; declared desired version/provenance; probe-only status is non-mutating and offline unless the caller explicitly requests refresh; idempotent current result; owned-only mutation; staging before activation; verification after activation; bounded retained rollback state; clear distinction among absent, current, drifted, upgrade-available, upgrading, upgraded, and failed.
4. Reuse existing generic primitives (recipes, declared steps, download, toolchain/package manager, fragments, atomic file/directory activation) and add a reusable primitive only where at least two consumers need it. Do not add a provider- or rig-specific lifecycle branch to foundation.
5. Add `upgrade` support only to audited recipes where it is both meaningful and safely implementable. For package-manager-owned provider CLIs, delegate to the package manager's supported upgrade command/version mechanism. For configuration-only recipes, explicitly classify as not applicable. Keep provenance and version facts visible in recipe status.
6. Make PR08 the first artifact-binary consumer: its pinned llama.cpp manifest drives deterministic upgrade status/apply. Integrate active service replacement only through PR04's managed-service drain/guarded-start path.
7. Update recipe authoring standards, schemas/examples, generated/public capability surfaces, and clean-room tests. Add an architecture test that a dependency upgrade does not bypass the recipe lifecycle through imperative component-local downloader/updater code.

## Detailed Solution & Technical Design

The foundation contract gains an `upgrade(context)` primitive and orchestration mode, with a structured result that distinguishes absent (install required), current, upgrade available, upgraded, skipped/not applicable, and failed. A recipe supplies desired-version/provenance through its declared data and current evidence through its probe; it must not consult mutable upstream 'latest' on normal status. Optional explicit metadata refresh is a separately named action and must return evidence used for the decision.

Upgrade execution follows the same ownership and compensation rules as install: materialize declared steps, stage an owned replacement, verify its identity, atomically activate it where supported, and retain enough prior state for recovery. A generic package-manager adapter may perform supported upgrades for package-owned CLIs; it must capture the resolved version/provenance after success rather than treating exit zero as verification.

Recipe-level classification avoids false uniformity. `upgrade: not-applicable` is correct for recipes that only project configuration or delegate to an external provider without owning an installed artifact.

## Validation

1. Contract/schema/API tests prove `upgrade` is discoverable, explicit, backwards compatible, and rejects undeclared or unowned upgrades.
2. Status is non-mutating and distinguishes absent/current/drifted/upgrade-available/not-applicable; repeated current upgrade is idempotent.
3. Staging, verification, activation failure, rollback/recovery, and provenance recording are tested with fixtures.
4. Each audited recipe family has a recorded classification and a test or documented non-applicability rationale.
5. A package-manager-owned provider CLI upgrade is tested in clean Docker where feasible; configuration-only recipes prove no artifact mutation occurs.
6. PR08 llama.cpp upgrade proves pinned checksum/version selection, safe activation, and no mutable latest lookup at ordinary status/launch.
7. Full declarative recipe schema validation, recipe test suite, public capability tests, and ruff pass.

## Effort & Risk

Large cross-cutting contract evolution. The central risk is pretending all recipes own versioned binaries. The audit gate is mandatory: upgrades may be delegated or not applicable, but every current recipe must have an explicit classification. Do not add automatic scheduling; automation policy belongs above the lifecycle and requires an explicit user/operator choice.
