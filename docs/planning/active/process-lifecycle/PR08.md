# Provision llama.cpp through verified declarative recipes and managed updates

## Description

Replace embedded/bundled llama.cpp binaries with a recipe-managed external dependency. The embedded rig remains an OpenAI-compatible local endpoint, but its `llama-server` executable is installed into the configured global or project-local rig runtime by a declared recipe. A verified release manifest—not GitHub 'latest' at runtime—is the source of truth for platform asset, version, URL, SHA-256, and supported architecture. This removes package-shipped binaries and the ad-hoc updater that directly downloads/extracts files and kills every matching process.

Coordinate with PR04: the ManagedService rig lifecycle must drain and stop only the proven owned service before a binary replacement; provisioning must never manage a live rig by PID/image name.

## Steps

1. Characterize the current binary resolution and update paths (`embedded/bin`, `runtime_bin_dir`, `update_binaries`, session `update_rig`, test-only provisioning). Record expected global/project precedence and failure modes.
2. Define a config-owned llama.cpp release manifest/descriptor with an explicit supported release version, platform/architecture asset names, immutable release URLs, SHA-256 checksums, executable layout, and provenance. Do not use `latest`, mutable branches, unauthenticated release discovery, or an unverified checksum fallback.
3. Add a declarative provisioning recipe (plus a narrowly registered rig-specific extraction/atomic-swap step only if existing download/extract steps cannot express it). The recipe probes the installed binary and version, downloads to a staging directory, verifies checksum, extracts safely, verifies `llama-server --version`, and atomically activates the complete payload in the selected runtime location. It is idempotent and supports plan/status/apply/prune.
4. Replace package-bundled binary lookup with recipe-owned global/project runtime locations. Delete `runtime/rig/embedded/bin` from source and remove the current ad-hoc update/download implementation once consumers use the recipe.
5. Make updates explicit and reconciliation-based: compare the installed version/provenance manifest with the declared release manifest; status reports current/declared version and a drift/update-available fact; apply performs the staged verified upgrade. No automatic background update and no network check at every launch. A recipe-manifest change is the controlled update trigger.
6. Route `session.update_rig` and bootstrap/provisioning through the recipe lifecycle. Before replacing an active embedded rig, call PR04's managed-service drain/guarded-stop path; after activation, start only through its managed-service start-or-attach path. External endpoints and unowned processes are never stopped.
7. Update clean-room Docker recipe tests and add platform-focused fixture tests for manifest selection, checksum failure, safe archive extraction, atomic replacement/recovery, version drift, project/global precedence, active-owned rig upgrade, and decoy-process safety.

## Detailed Solution & Technical Design

The recipe is the sole binary artifact owner. A versioned manifest under component configuration declares a known-good llama.cpp release per supported platform/architecture. The managed recipe writes an ownership/provenance record alongside the installed payload: recipe id/version, release version, asset URL/digest, installed binary version, and activation timestamp. Its probe reads this record plus executes the binary version probe; it reports drift rather than silently replacing a working tool.

A staged install uses a sibling temporary directory, checksum verification before extraction, safe archive-member validation, complete payload verification, and an atomic directory activation/rollback strategy. The recipe must not target package source files. `runtime_bin_dir` only resolves configured recipe-owned locations.

Update is not a separate imperative implementation: it is a recipe apply/reconcile against the declared manifest. Changing the declaration creates an observable pending upgrade; an explicit bootstrap/session update action performs it. This gives deterministic releases and avoids surprise model-service restarts.

## Validation

1. A clean global and project-local install runs the declarative recipe and verifies the activated `llama-server --version` against the declared manifest.
2. Status distinguishes absent, verified-current, provenance/version drift, and update available; it makes no network mutation.
3. Apply of the same manifest is idempotent; changing the release declaration performs a staged verified update and preserves the old payload until activation succeeds.
4. Bad checksum, malformed archive, unsupported platform/architecture, failed version probe, and interrupted activation fail safely with no partially active payload.
5. Global/project precedence is deterministic and no package-bundled binary is used.
6. Updating a live owned rig follows PR04 drain/release/ownership checks and then restarts through the managed service; an external endpoint or decoy llama-server is untouched.
7. Clean-room Docker recipes prove actual install/upgrade on Linux; Windows platform selection/extraction tests run in CI or a suitable Windows gate. Ruff and architecture policy tests are green.

## Effort & Risk

Medium. The main risk is treating a mutable upstream release lookup as an update mechanism. Keep the manifest pinned, checksummed, and reviewed; release-manifest refresh is a deliberate repository/config change. Coordinate sequencing with PR04 so no updater retains the old unsafe process-kill behaviour. The model file remains separately configured and is not bundled or implicitly downloaded by this binary recipe.
