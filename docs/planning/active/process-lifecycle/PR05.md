# Define reusable managed process lifecycle foundation

## Description

Extract the process-management lessons from agent sessions, MCP daemon design, and shared rig lifecycle into a reusable foundation/system capability. The goal is a generic process ownership contract for components that launch long-lived or child-spawning processes, not an overseer-specific wrapper.

## Steps

1. Characterize existing process primitives: `foundation/system/process.py` (`StartupLock`, ports, pid liveness, tree kill), `foundation/system/supervised_process.py` (`supervised_run`, Windows Job Object kill-on-close), ACP session transport close semantics, rig registry lifecycle, and any direct subprocess/kill callers.
2. Define a foundation-owned managed process contract with explicit scopes: foreground supervised run, live session child, detached supervisor/daemon, shared singleton service, and external/adopted process. Each scope must state owner, lifetime, cleanup authority, restart/adoption policy, and whether it may outlive the caller.
3. Add an ownership journal/state shape for launched processes: component, resource kind/id, pid, start time/create time where available, command fingerprint/redacted argv, cwd, env redaction policy, parent/session/group/job identity, ownership proof, heartbeat/status timestamps, and cleanup result. Never persist secrets or raw prompts.
4. Define safe process-tree operations: prefer OS process groups/job objects where the launched process is owned; use `psutil` as optional/enhanced cross-platform inspection when available; never reap by executable name alone; require ownership proof via journal, command path fingerprint, port token/handshake, or lock-held lease.
5. Define lock-held liveness/lease helpers in foundation/system for cross-process refcounts: Windows `msvcrt` and POSIX `fcntl` implementations, with stale PID body only diagnostic. Reuse for rig clients, daemon sessions, and future worker supervisors.
6. Define detached supervisor semantics separately from supervised child semantics: how to escape provider-host Job Objects intentionally, how to advertise/discover the supervisor, how it proves ownership of children, how it shuts down at idle, and how callers reconcile dead supervisors.
7. Specify MCP/API surfaces that components may expose: summarized process status, last heartbeat age, cleanup verification, orphan reconciliation, and bounded terminate/kill operations. Components own policy; foundation owns primitives.
8. Add architecture tests prohibiting new ad-hoc process tree kill/reap logic outside foundation/runtime-owned seams unless explicitly reviewed.
9. Implement only after the contract review is accepted; first code slice should be tests for lock-held liveness and ownership-scoped reaping using fake/stub processes, not real agent providers.

## Validation

1. Design explicitly separates supervised child, detached supervisor, shared singleton service, and external/adopted process lifecycles. 2. No process kill/reap operation is allowed without ownership proof. 3. Windows and POSIX lifecycle differences are documented and tested with platform-specific helpers. 4. `psutil` is optional: used for richer inspection/tree enumeration when present, but foundation has safe fallbacks or clear degraded status. 5. Existing AS11/AS08/PR04 can reference this item instead of inventing local process management. 6. Architecture tests catch new direct `taskkill`, `pkill`, process-name reaping, or unowned tree-kill logic in component code.

## Effort & Risk

Mid. The risk is overbuilding a mini supervisor framework. Keep the first contract small: ownership evidence, liveness leases, safe tree cleanup, and status. Do not introduce a daemon until AS08/PR03 prove a caller needs independent lifetime.

## Notes

Library scan 2026-07-17: `psutil` is the practical Python library for cross-platform process inspection/tree operations; Microsoft Windows Job Objects are the correct OS primitive for kill-on-owner-close semantics. AUDiaGentic already has a ctypes Job Object implementation in `foundation/system/supervised_process.py`, so the likely direction is to extend existing foundation primitives, optionally using psutil for inspection, rather than depend on a heavyweight external supervisor library.
