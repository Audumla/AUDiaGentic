# Shared HTTP MCP daemon (detailed design and implementation spec — do NOT implement yet)

## Description

DESIGN-ONLY spec. Goal: stop per-client/per-provider/per-session multiplication of MCP server processes by running each ag-* server ONCE as a shared, long-lived Streamable-HTTP server that many clients connect to, instead of today's stdio (one subprocess per client). Complements — does not replace — PR01 teardown and PR02 windowless-collapse, which remain necessary for the stdio path and for any third-party (uvx/gh) servers that cannot share. This item exists to capture the full challenge surface BEFORE any code is written. Implementation gated on an explicit go decision.

## Steps

Candidate architecture (singleton daemon + broker), to be chosen during design:
1. Transport: add a Streamable-HTTP run mode to component MCP servers (FastMCP supports it) bound to 127.0.0.1 on an ephemeral port.
2. Discovery/lifecycle: a singleton daemon per (project-root[, server]) advertises {pid, port, token} in a well-known lockfile; reuse existing StartupLock (atomic O_CREAT|O_EXCL + stale-PID detection), choose_free_port, find_pid_on_port from foundation/system/process.py.
3. Auto-start on connect: a thin stdio<->HTTP broker shim is what providers actually spawn (configs stay stdio-shaped); the shim connects to the daemon, starting it under the startup lock if absent. (Alternative: POSIX socket activation — rejected, no Windows support.)
4. Idle shutdown: daemon ref-counts active MCP sessions (Mcp-Session-Id) and self-exits after a grace window at 0 sessions; re-checks count under the lock before exiting to avoid the start/stop race.
5. Provider projection: emit URL/remote form per provider where supported; fall back to stdio (PR02 form) for providers that lack remote-MCP support.

## Validation

Design review sign-off required before implementation. Prototype must demonstrate, on Windows AND POSIX: (a) two providers sharing ONE server process; (b) clean idle self-exit at 0 sessions with no lost-connection race under concurrent connect/exit; (c) correct project-root isolation when two projects use the daemon concurrently; (d) the daemon surviving provider-host teardown (NOT killed by PR01's Job Object); (e) graceful fallback to stdio for non-HTTP-capable providers.

## Effort & Risk

Complex / high risk. Trades the orphan problem for a daemon-lifecycle problem. CHALLENGES & LIMITATIONS:
1. MULTI-PROJECT (biggest): component servers resolve project root from CWD/AUDIAGENTIC_REPO_ROOT per-process (component_server.py:184). A shared daemon serving multiple projects breaks this — root must move from process-scope to request/session-scope, but MCP has no standard 'project root per call'. Options: (a) one daemon-set per project root (less sharing, more processes) or (b) inject root per session at initialize + key all state by root. Compounds [[SL04]] monolithic-state-file contention — concurrent multi-project access to one process now contends on shared state that was previously process-isolated.
2. CONCURRENCY/THREAD-SAFETY: stdio gave free per-process isolation. Shared process must make every component API reentrant/thread-safe; today they assume single-client.
3. PR01 INTERACTION: the daemon MUST NOT be a child of the provider host or PR01's Job Object kills it on host exit. Must be detached/independent-lifetime — directly contradicts the teardown model; needs its own supervised lifecycle + crash recovery.
4. START/STOP RACE: 0-connection exit vs new connect. Mitigate with grace window + StartupLock serialization + exit re-check under lock; cannot fully eliminate, needs client retry-on-connect.
5. SECURITY: HTTP introduces a local network attack surface absent in stdio. Must bind 127.0.0.1 + per-session bearer token; secrets (GITHUB_TOKEN) currently passed via per-spawn stdio env must become per-session injection.
6. PROVIDER SUPPORT GAP: not all providers support remote/HTTP MCP; mixed stdio+HTTP model unavoidable, with per-provider fallback.
7. THIRD-PARTY SERVERS: git (uvx mcp-server-git) and github (gh) are external stdio servers we cannot convert — they stay per-client regardless.
8. COLD-START vs IDLE latency tradeoff in tuning the idle timeout.
9. OBSERVABILITY: logs/correlation move from per-client to centralized multi-tenant; need request/session correlation IDs across clients and projects.
10. WINDOWS: no socket activation; singleton-lock pattern only.

## Notes

Recommendation: do NOT build unless concurrent multi-provider/multi-session usage is common. For single-host-at-a-time usage, PR01 (done) + PR02 (done) already remove the pain. Revisit if process counts remain a problem after PR01/PR02 land in practice. Related: [[SL04]] (state-file contention worsens under sharing).
