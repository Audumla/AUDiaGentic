# First event-driven Reviewer: plan-item-created review via OpenCode

## Description

The first end-to-end test of the event-driven agent machinery: when a new plan item is created, a Reviewer agent reviews it. Flow (every link already implemented by the event-driven-jobs plan): planning publishes `planning.item.created` (components/planning/events.py:14, fired from items.py::create_item with subject {kind: planning-item, id: <item-id>} and payload containing id/title/plan/state/path) → an agent-jobs event trigger fires → a durable job is created with event provenance → the prompt template renders with the plan-item id injected → the job dispatches via `agents.llm.gateway.requested` → the gateway executes the `reviewer` agent profile bound to provider=opencode + a model verified available via the MO10-extended list_provider_models tool → OpenCode (real execution adapter: `opencode run --format json --model <model>`) performs the review and records it through the ag-planning MCP tools it already has access to → gateway outcome propagates job state. PLAN-ID INJECTION: uses the EXISTING shared renderer foundation/templates.py — the generic identifier marker is the dotted-path placeholder; prompt_context.py already injects `event.plan_item.id` for planning.item.created events, so the template writes `{event.plan_item.id}` (fallbacks `{subject.id}` and `{event.payload.id}` also resolve). DECISION — no new template library: Jinja2-class engines add conditionals/loops/filters this project deliberately excluded (EDJ15 rejected expression languages; EDJ21 characterization locked renderer contracts), a new dependency, and a larger prompt-injection surface; the shipped renderer already does exactly the required value injection with strict unresolved-placeholder errors (VAL-TPL-001).

## Steps

1. FIX provenance at the consumer boundary: planning/event foundation metadata canonically uses source_component (underscore). EventObserver normalizes metadata.get("source_component") or metadata.get("source-component") into persisted job event-source["source-component"]. Do not change planning publisher away from EventEnvelope convention. Add both-spelling compatibility tests, with underscore as canonical input.
2. Define the Reviewer agent profile in .audiagentic/config/agent-profiles.yaml: profile_id `reviewer`, provider_id `opencode`, model_id chosen FROM the MO10-extended list_provider_models(opencode) output (record the chosen model + catalog snapshot date in this item's notes at implementation time); not is-default. Depends on MO10 for the availability listing and for `opencode run --model` actually honoring the profile model.
3. Author the review prompt template as a FILE (event-trigger prompt-template-file, EDJ11 path containment applies): .audiagentic/prompts/jobs/events/plan-item-review.md. Content contract: instruct the agent to (a) read the plan item `{event.plan_item.id}` via the ag-planning MCP tools (plan_get_item), (b) review it critically against docs/standards (architecture, observability) and implementability, (c) record findings with plan_create_review(review_of={event.plan_item.id}) including a conclusion, and (d) NOT modify the item itself. CAPABILITY-ONLY PROMPT (RV280): the prompt references only MCP tool capabilities and repo doc paths — it must not name provider internals, config file paths of the executing tool, keys/env vars, or gateway machinery. Correlation context available as `{metadata.correlation_id}` and job id as `{job.id}` for traceability lines in the review notes.
4. PROVE the planning MCP surface reaches the reviewer through DECLARED propagation, not assumption (RV280): verify how the ag-planning MCP server is projected into OpenCode's managed MCP config (the descriptor-managed .opencode/opencode.json surface written by the existing managed-MCP sync) and add an assertion — in the E2E setup or a dedicated test — that the projected OpenCode MCP config contains the ag-planning server entry via that propagation path before the job runs. If the sandbox project's surface apply does not project ag-planning to opencode by default, the item documents the required component/surface configuration rather than hand-editing the provider file (provider config files are never the mutation surface).
5. Add the event trigger to .audiagentic/config/agent-jobs/event-triggers.yaml: trigger-id `plan-item-review`, kind event, event-pattern `planning.item.created`, agent-profile-id `reviewer`, workflow-profile lite, prompt-template-file from step 3. LOOP GUARD (EDJ15 filter, equality/membership only): reviews are recorded via plan_create_review which publishes planning.review.created (different topic — no direct loop), but Reviewer-created plan ITEMS would re-trigger; filters have no negation, so the prompt forbids item creation (step 3d) AND the acceptance test asserts exactly one job per created item. If a real loop risk emerges, raise a follow-up item for a filter exclusion extension rather than widening scope here.
6. E2E integration test (mock execution, no real OpenCode): temp project with the trigger + profile + template; patch execute_provider to capture packet_ctx and return a completed result; call planning items.create_item; assert — one job created with event-source {event-type: planning.item.created, trigger-id: plan-item-review, subject.id: <item-id>, source-component: agent-planning}; rendered prompt-body in the job's launch-request contains the literal item id (injection proof); packet_ctx carries model-id from the reviewer profile; job reaches `completed` on the gateway outcome; trigger-audit has one `fired` entry; correlation_id identical across event → job event-source → gateway metadata → timeline; plus the step-4 propagation assertion.
7. Renderer unit test pinning the injection contract: render the actual template file against a context built by build_prompt_context_from_event for a synthetic planning.item.created envelope; assert the item id appears and no unresolved placeholder remains (render raises VAL-TPL-001 otherwise — the test IS the template lint).
8. Live smoke procedure (documented in this item's notes at implementation time, not automated): create a throwaway plan item in a sandbox project with OpenCode installed and a key configured; verify the review file appears under docs/planning/active/<plan>/reviews/<item>/ and the job timeline shows completed; record model used and duration.
9. Document the scenario in src/audiagentic/components/agent_jobs/README.md's worked-example section as the canonical live configuration (replacing or augmenting the current illustrative example — keep the README-example test in sync).
