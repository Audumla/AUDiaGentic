# Add recipe standards and architecture regression tests

## Description

Add a focused standards gate for the recipe system and dependants. The goal is to prevent future duplication of lifecycle orchestration, provider-specific branches in generic code, foundation layer leaks, unsafe shell output, and untracked direct mutations.

## Current findings

- Foundation recipe/provision-step modules are intended to be domain-neutral and component-free.
- `provision_steps.base` uses the shared `Registry` utility, which aligns with lazy initialization and config-over-code standards.
- Provider recipe registry dispatch is dictionary/key based, but fallback lifecycle logic still duplicates base orchestration and should be guarded by tests.
- Hindsight strategy selection uses a dict factory keyed by `ProviderRecipeKind`, which is valid; broad provider/capability if-chains should remain prohibited.
- Migration doctrine requires whole-repo dotted-path grep when deleting/renaming recipe modules/classes.
- Dynamic assembled recipes in `recipe_spec.py` bind lifecycle primitives through closures; tests must ensure all expected primitives remain bound and status overrides do not bypass delegates unexpectedly.
- `_RECIPE_FACTORIES` must cover every `ProviderRecipeKind` present in the Hindsight matrix; missing mappings silently fall back to guidance-only.
- Existing matrix source metadata tests live under `tests/unit/foundation/toolchains/test_architecture_boundaries.py`; RS07 should extend/reference that gate rather than create a disconnected duplicate.

## Proposed solution

1. Add architecture tests focused on recipe layers:
   - foundation recipe modules must not import `audiagentic.components` or runtime orchestration,
   - components may import foundation recipe primitives,
   - provider recipe layer may import foundation but must not import specific optional component implementations.
2. Add static checks/allowlisted grep tests for entity-specific dispatch in generic code.
3. Add duplication guard tests for `provision()` / `teardown()` overrides: allow only documented exceptions such as `NoAutomationRecipe.provision()` and any class with an explicit test/rationale.
4. Add redaction tests from RS05 to the standards suite.
5. Add migration grep tests for removed recipe names when RS02/RS03/RS04 delete or rename helpers.
6. Add dynamic recipe assembly and factory completeness guards for Hindsight recipe construction.

## Options considered

| Option | Decision | Reason |
|---|---|---|
| Rely on code review only | Rejected | Recipe layer is cross-cutting and easy to regress. |
| Broad regex ban on all `if` statements | Rejected | Too noisy; use targeted checks for provider/capability/entity dispatch. |
| Architecture tests only | Insufficient | Need behavior tests for stamping, redaction, direct mutation and override duplication too. |
| Full static analyzer | Defer | Targeted tests are cheaper and more maintainable for now. |

## Implementation steps

1. Extend `tests/unit/foundation/toolchains/test_architecture_boundaries.py` or create `tests/unit/foundation/toolchains/test_recipe_architecture.py`.
2. Add import-boundary assertions using AST or text scanning for foundation recipe modules.
3. Add allowlisted override scan for classes defining `provision()` / `teardown()` outside `recipe_contract.py`.
4. Add targeted grep test for `ProviderRecipeKind` / provider-id / capability-id `if/elif` dispatch outside approved strategy-selection modules.
5. Add redaction regression tests once RS05 lands.
6. Add migration grep checks to implementation PRs that remove old names; do not permanently hardcode every historical name unless needed.
7. Add tests proving `_RECIPE_FACTORIES` covers matrix recipe kinds and assembled recipes bind `probe`, `install`, `configure`, `verify`, `uninstall`, and `prune`.

1. `python -m pytest tests/unit/foundation/toolchains tests/unit/providers tests/unit/memory/hindsight`
2. Architecture-boundary tests prove foundation remains domain-neutral and dependency-safe.
3. Static/golden tests catch accidental provider-specific recipe dispatch in foundation or generic providers code.
4. Redaction tests fail if stdout/stderr/secrets are emitted in structured results.
5. Override tests fail if a dependant reimplements `provision()` / `teardown()` without allowlist and rationale.
6. Factory completeness tests fail if a matrix recipe kind would silently fall back to guidance-only.
7. Assembled recipe tests fail if a lifecycle primitive is not delegated or status overrides orphan delegate calls.
