# Consolidate Hindsight recipe patterns and plugin recipe duplication

## Description

Consolidate repeated Hindsight recipe mechanics while preserving provider-specific integration policy. Hindsight already moved guidance-only and declared-step recipes into `RecipeSpec` assembly. Remaining plugin recipes still duplicate source-gated step execution, plugin install/uninstall handling, probe→verify patterns, dry-run strings, and managed MCP status/sync logic.

## Current findings

- `_McpConfigAdapter` correctly writes/removes via provider managed MCP sync and should remain the reference path for provider-owned MCP entries.
- `PluginConfigRecipe` duplicates much of `_McpConfigAdapter` when `_config_path` is present, but currently passes `project_root=None` in configure/prune, causing a `Path.cwd()` fallback.
- `_PluginUrlConfigRecipe` and `PluginConfigRecipe` both implement source-gated install/uninstall step execution.
- `_PluginUrlConfigRecipe` has direct JSON write/delete because optional JSON fields cannot be cleanly represented by simple YAML substitution; this may be intentional but should be registered or documented.
- `_PluginArrayRecipe` correctly delegates provider-specific array read/write/remove to matrix-provided refs; keep that pattern.

## Proposed solution

1. Extract Hindsight-local helpers, not foundation abstractions, for repeated mechanics:
   - `_run_verified_steps(row, backend, steps, context, *, phase, subject)`
   - `_probe_expected_config(current, expected, *, artifact, present_status, absent_status)`
   - `_verify_from_probe(recipe, context, failure_message)`
   - `_sync_hindsight_mcp_entry(...)` stays the shared managed MCP bridge.
2. Reuse `_McpConfigAdapter` or a tiny managed-MCP helper inside `PluginConfigRecipe` instead of duplicating status/sync semantics.
3. Preserve `_PluginUrlConfigRecipe` as a separate class because its optional JSON key behavior and Windows plugin repair are real one-offs.
4. Preserve `_PluginArrayRecipe` as a separate class because it uses configured reader/writer/remover refs and has a different probe/configure/prune shape.
5. Add a classification comment/table in `plugin_recipes.py` explaining which direct operations are intentional.

## Options considered

| Option | Decision | Reason |
|---|---|---|
| Recreate generic `ManagedEntryRecipe` | Rejected | Previous code says it was removed after zero consumers; current provider MCP sync is the correct reuse target. |
| Merge all plugin recipes into one class | Rejected | URL config, plugin array, and MCP config have distinct persistence semantics. |
| Extract local Hindsight helpers | Preferred | Reduces duplication without over-generalizing one-off provider history. |
| Move plugin array renderer into providers | Defer | The matrix-provided refs already keep provider-specific shape out of generic code. Reassess only if multiple components need it. |

## Implementation steps

1. Add characterization tests for each strategy path before refactor: guidance, hooks/declared-step, mcp-config, plugin-config, plugin-url-config, plugin-array.
2. Fix/confirm project-root threading for `PluginConfigRecipe` managed MCP configure/prune; avoid `Path.cwd()` fallback when caller supplied a project root.
3. Extract the source-gated step runner and use it from `PluginConfigRecipe` and `_PluginUrlConfigRecipe`.
4. Extract probe/verify helper only if it reduces repeated code in at least two classes.
5. Update strategy tests to prove `resolve_hindsight_strategy()` and `build_hindsight_recipe()` return the same effective behavior.
