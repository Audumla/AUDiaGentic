# Remove dependant duplication of managed config and artifact primitives

## Description

Audit recipe dependants for direct reimplementation of primitives already provided by foundation or providers. Hindsight/plugin recipes currently mix provider managed MCP sync, direct JSON writes, direct file deletion, source-gated step execution, plugin array reader/writer/remover dispatch, and custom Windows repair. Keep genuinely component-specific logic, but route common file/config ownership, managed config, and lifecycle concerns through shared primitives.

## Current findings

- `_McpConfigAdapter` correctly uses provider managed MCP sync and should be the model for provider-owned MCP entries.
- `PluginConfigRecipe` duplicates managed MCP status/sync and step execution behavior.
- `_PluginUrlConfigRecipe` directly writes/deletes `~/.hindsight/<provider>.json`; this may be legitimate because optional fields are data-dependent, but ownership/dry-run/prune behavior should be explicit.
- `_PluginArrayRecipe` uses matrix-provided reader/writer/remover refs, which is good config-over-code, but should still have ownership/collision behavior documented.
- `ArtifactRegistry` already handles files, config keys, blocks, dry-run prune, and missing artifacts; dependants should not duplicate those unless they need provider-specific semantics.
- `_sync_hindsight_mcp_entry()` writes through provider managed MCP sync. Classify it as the sanctioned shared primitive, not an ad hoc direct write.
- `ProviderRecipeRegistry` and Hindsight lifecycle fallback result construction are not file mutations, but they are direct result-construction duplication and should be cross-linked to RS02/RS10.
- `_PluginUrlConfigRecipe` returns URL config paths in `artifacts_owned`, but the direct write is not registered with `ArtifactRegistry`; classify as needs registration or documented exemption.

## Proposed solution

1. Produce a small classification table in the implementation PR for every direct mutation in recipe dependants:
   - replace with foundation step,
   - replace with provider managed-config/MCP sync,
   - explicitly register in `ArtifactRegistry`,
   - keep as intentional one-off with comment and test.
2. Route provider MCP entry writes/removals through provider managed sync only.
3. For plugin URL config direct writes, either:
   - register the written file in `ArtifactRegistry`, or
   - implement a JSON write-file/config step that can omit optional keys, only if a second consumer exists.
4. For plugin repair direct writes, keep local unless a second component needs repair semantics; add redaction/tests and comments.
5. Remove any duplicated direct file deletion if `ArtifactRegistry.prune()` can express it safely.

## Options considered

| Option | Decision | Reason |
|---|---|---|
| Replace all direct writes with provisioning steps | Rejected | Optional JSON key and repair logic may not fit current step primitives. |
| Keep all direct writes | Rejected | Ownership/prune/dry-run behavior becomes inconsistent. |
| Add new generic JSON object writer step | Conditional | Only if plugin URL config plus another consumer need it. |
| Use provider managed config for all Hindsight writes | Rejected | Some writes are Hindsight plugin settings, not provider harness config. |

## Implementation steps

1. Whole-repo grep recipe dependants for `write_text`, `unlink`, `json.loads`, `read_text`, `run_steps`, `steps_from_defs`, `sync_managed_provider_mcp_subset`, and provider config writes.
2. Add the classification table to PR notes or `docs/planning/active/recipe-system-review/RS06-CLASSIFICATION.md` if it becomes large.
3. Include direct `ProviderRecipeResult(...)` construction in the classification table and point those rows to RS02/RS10.
4. Replace duplicated managed MCP behavior with the existing `_sync_hindsight_mcp_entry` / provider managed sync path.
5. Add artifact registration or explicit comments for plugin URL config writes/deletes.
6. Add tests proving prune does not remove unrelated user config and missing files are skipped, not failures.

## Validation

1. Whole-repo grep documents every remaining direct write/delete in recipe dependants and why it remains.
2. Tests prove provider-managed MCP entries still use provider ownership sync, not ad hoc config writes.
3. Tests prove plugin URL config and plugin array config are pruned without deleting unrelated user config.
4. No new foundation primitive is added for a single consumer unless the code comment justifies why local helper is worse.
5. Tests prove direct mutation paths are covered by dry-run/verify/prune behavior.

## Effort & Risk

Complex. Some direct writes may be legitimate because optional JSON keys or provider plugin repair logic cannot be expressed by existing steps. The goal is clarity and reuse, not abstraction for its own sake.

## Standards

Std §3: consolidate repeated logic used by multiple files. Std §10: remove duplicate paths atomically with tests. Creating Components §6: provider-specific rendering belongs in providers unless the component is only supplying provider-agnostic backend data.
