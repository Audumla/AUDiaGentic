# Remove dependant duplication of managed config and artifact primitives

## Description

Audit recipe dependants for direct reimplementation of primitives already provided by foundation or providers. Hindsight/plugin recipes currently have direct JSON writes, direct file deletion, source-gated step execution, plugin array reader/writer/remover dispatch, and managed MCP status/sync calls. Keep genuinely provider-specific logic, but route common file/config ownership, managed config, and lifecycle concerns through the shared primitives.

## Steps

1. Inventory recipe dependants across components for direct use of `write_text`, `unlink`, `json.loads/read_text`, `run_steps`, `steps_from_defs`, and provider config writes.
2. Classify each direct operation as: foundation primitive exists, provider managed-config primitive exists, component-specific one-off, or needs new shared primitive.
3. Replace duplicated operations with `ArtifactRegistry`, provisioning steps, managed config sync, or provider adapter functions where appropriate.
4. Add comments/tests for intentional one-offs that should not be generalized.
5. Update Hindsight strategy docs/comments after removing duplicate logic.

## Validation

1. Whole-repo grep documents every remaining direct write/delete in recipe dependants and why it remains.
2. Tests prove provider-managed MCP entries still use provider ownership sync, not ad hoc config writes.
3. Tests prove plugin URL config and plugin array config are pruned without deleting unrelated user config.
4. No new foundation primitive is added for a single consumer unless the code comment justifies why local helper is worse.

## Effort & Risk

Complex. Some direct writes may be legitimate because optional JSON keys or provider plugin repair logic cannot be expressed by existing steps. The goal is clarity and reuse, not abstraction for its own sake.

## Standards

Std §3: consolidate repeated logic used by multiple files. Std §10: remove duplicate paths atomically with tests. Creating Components §6: provider-specific rendering belongs in providers unless the component is only supplying provider-agnostic backend data.
