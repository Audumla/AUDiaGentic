# Normalize provisioning step substitution, paths, and artifact ownership

## Description

Normalize provisioning-step substitution, path resolution, and artifact ownership rules. The current step package is reusable and registry-driven, but recipe authors must understand several different mechanics: strict definition-time `_substitute()`, lenient `substitute_params()`, shell runtime `str.format(**context)`, and inconsistent path anchoring.

## Current findings

- `base._substitute()` strictly validates `{WORD}` placeholders against params and preserves non-matching braces, which is useful for JSON literals.
- `factory.substitute_params()` is lenient and leaves unknown placeholders literal; it is used for free-form commands/status probes.
- `ShellProvisionStep._render()` performs another `str.format(**context)` at runtime, which can fail differently from `_substitute()` and makes substitution two-phase.
- `ConfigSetStep`, `ManagedBlockStep`, and `WriteFileStep` use `Path(self.path).expanduser()` and do not consistently anchor relative paths to `project_root`.
- Hindsight has its own `_absolute_project_path()` helper; foundation steps do not receive `project_root` unless recipe authors pass it through context or pre-resolve paths. This is domain-neutral, but the contract must be explicit.
- `substitute_params()` preserves unknown placeholders as literal `{KEY}` strings. This is useful for free-form commands but can defer missing-param failures to shell/probe runtime.
- `ArtifactRegistry` supports files, config keys, and managed blocks, but direct plugin writes/deletes may bypass it.

## Proposed solution

1. Document the two intended phases:
   - definition params: `{KEY}` values resolved when constructing steps from YAML (`steps_from_defs`).
   - runtime context: only allowed for explicitly declared runtime placeholders, or removed from shell if no consumers need it.
2. Prefer one safe renderer helper for runtime values if runtime context substitution remains. It should handle missing keys with `AudiaGenticError` or a clear `StepResult.failed`, not raw `KeyError`.
3. Add optional `project_root` path anchoring convention to step contexts. A helper such as `_resolve_step_path(path, context)` should handle absolute paths, `~`, and project-relative paths consistently while keeping foundation domain-neutral.
4. Ensure each mutating step can register ownership through `ArtifactRegistry` when `registry` and `recipe_id` are supplied.
5. Leave direct plugin JSON writes alone until RS06 classification decides whether they should be converted to steps or explicitly registered.

## Options considered

| Option | Decision | Reason |
|---|---|---|
| Keep current mixed substitution | Rejected | Easy for recipe authors to get wrong; errors differ by step type. |
| Remove runtime context formatting entirely | Defer | Need grep/tests to confirm no recipe uses runtime-only placeholders. |
| Add one path resolver helper for all steps | Preferred | Small foundation utility, multiple current consumers. |
| Force all direct writes through provisioning steps | Rejected for now | Some plugin JSON writes need optional key behavior not expressed by current steps. |

## Implementation steps

1. Add tests around `_substitute()` for JSON braces, unknown placeholders, list/dict recursion, and optional empty values.
2. Add tests around `substitute_params()` for status-command/free-form behavior.
3. Add tests documenting that unknown `substitute_params()` placeholders remain literal, then decide whether status probes need stricter validation.
4. Add tests showing current `ShellProvisionStep._render()` runtime context behavior; then decide whether to keep, wrap, or remove.
5. Implement `_resolve_step_path(path, context)` if tests confirm inconsistent path behavior.
6. Apply the resolver to `ConfigSetStep`, `ManagedBlockStep`, and `WriteFileStep`; consider `ShellProvisionStep.cwd` only if it is intended to be project-relative.
7. Ensure registry ownership is asserted in tests for file/config/block steps.
