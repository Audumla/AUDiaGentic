# Consolidate provider recipe result stamping and registry dispatch

## Description

Consolidate duplicated provider recipe result stamping and lifecycle dispatch. `ProviderCapabilityRecipe.to_result()` and `_stamped()` already establish the intended boundary, but `ProviderRecipeRegistry.install()` still has a fallback primitive orchestration path that manually reconstructs `ProviderRecipeResult`, and Hindsight `_RowRecipe._stamp()` duplicates much of the provider-layer conversion.

## Current findings

- Provider layer already defines `ProviderRecipeResult`, `ProviderCapabilityRecipe.to_result()`, and `_stamped()`.
- Registry methods use `provision()` / `teardown()` when present, but still contain fallback primitive orchestration for non-`ProvisioningRecipe` recipe-like objects.
- Registry dispatch is inconsistent: `status()`, `dry_run()`, and `repair()` stamp through `_stamped()`, while `install()` and `uninstall()` call `to_result()` directly when present.
- The `install()` fallback path reads `result.source_url` / `result.source_date` directly, which is unsafe for plain `RecipeResult`; any fallback retained must use provider conversion or `getattr`.
- Hindsight `_RowRecipe._stamp()` overlays row/action guidance and source data; that is valid, but it duplicates provider result construction.
- `recipe_spec.py` dynamically assembles classes and stamps delegate results, so any provider-layer change must preserve those assembled recipes.

## Proposed solution

1. Keep `ProviderCapabilityRecipe.to_result()` as the primary provider-layer stamping hook.
2. Add a small helper in `providers/services/recipes.py`, for example `provider_result_from(base, *, recipe, action_needed_default="")`, if tests prove `to_result()` alone cannot express Hindsight fallback semantics.
3. Normalize registry `install()` / `uninstall()` dispatch through the same provider stamping boundary used by `status()` / `dry_run()` / `repair()`.
4. Reduce `ProviderRecipeRegistry.install()` fallback primitive path to either:
   - call a small shared helper that mirrors `ProvisioningRecipe.provision()` without reconstructing `ProviderRecipeResult`, or
   - remove the fallback if all registered recipes are guaranteed to implement `provision()` after tests confirm.
5. Make Hindsight `_RowRecipe.to_result()` delegate to `super().to_result(base)` first, then overlay row-specific `action_needed` fallback only. Avoid rebuilding every field manually.
6. Add tests to prove no double-stamping and no loss of `source_url`, `source_date`, `action_needed`, `details`, or `artifacts_owned`.

## Options considered

| Option | Decision | Reason |
|---|---|---|
| Keep duplicate stamping | Rejected | Easy to drift and already exists in provider registry + Hindsight. |
| Move Hindsight row semantics into foundation | Rejected | Hindsight matrix semantics are component-specific. |
| Remove provider registry fallback path immediately | Conditional | Only safe if tests prove every registered recipe implements `provision()` / `teardown()`. |
| Add one provider-layer conversion helper | Preferred if needed | Keeps provenance conversion in providers, not components/foundation. |

## Implementation steps

1. Add tests for `ProviderCapabilityRecipe.to_result()` preserving provider fields from both plain `RecipeResult` and `ProviderRecipeResult`.
2. Add registry tests for `status`, `install`, `uninstall`, `dry_run`, and `repair` using both a `ProvisioningRecipe` subclass and a legacy recipe-like object if such objects still exist.
3. Refactor `_RowRecipe._stamp()` to call provider-layer conversion first, then apply row fallback guidance.
4. Replace raw `ProviderRecipeResult(...)` reconstruction in registry fallback path with helper or remove fallback after inventory. If fallback remains, use `getattr` for provider-specific fields.
5. Update dynamic recipe assembly tests to ensure `status_overrides` and delegate dispatch still return provider-stamped results.

2. Tests prove `action_needed` fallback order: primitive result guidance > row/provider default guidance > empty.
