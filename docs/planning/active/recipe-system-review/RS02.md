# Consolidate provider recipe result stamping and registry dispatch

## Description

Consolidate duplicated provider recipe result stamping and lifecycle dispatch. `ProviderCapabilityRecipe.to_result()` and `_stamped()` already establish the intended boundary, but `ProviderRecipeRegistry.install()` still has a fallback primitive orchestration path that manually reconstructs `ProviderRecipeResult`, and Hindsight `_RowRecipe._stamp()` duplicates much of the provider-layer conversion.

## Steps

This is the parent/analysis item; execution happens in RS09 (characterize) then RS10 (simplify). Do not implement fixes directly under this ID — use this item only to record the audit finding and confirm RS09/RS10 close it.

1. Confirmed root cause (RV228/RV229 audit): `ProviderRecipeRegistry.install()` in `src/audiagentic/components/providers/services/recipes.py` has two branches (success-loop failure at ~line 317-328, and the post-verify success branch at ~line 329-340) that manually reconstruct a `ProviderRecipeResult(...)` field-by-field instead of using `dataclasses.replace()` the way `recipe_contract.py::ProvisioningRecipe.provision()` already does for the identical problem (folding accumulated `artifacts_owned` into a later result). This is duplicated construction logic, not a stamping/provenance bug — no double-stamping was found; primitives already self-stamp via `_RowRecipe._stamp()`/`ProviderCapabilityRecipe.to_result()` before reaching the registry.
