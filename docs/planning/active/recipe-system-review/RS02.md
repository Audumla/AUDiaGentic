# Consolidate provider recipe result stamping and registry dispatch

## Description

Review provider recipe wrappers for duplicate result-stamping and lifecycle dispatch. `ProviderCapabilityRecipe.to_result()` and the `_stamped()` helper already establish the intended provenance boundary, but Hindsight-specific recipes also implement `_stamp()` and several registry paths manually reconstruct `ProviderRecipeResult`. Consolidate where possible so provider provenance, source URL/date, and action-needed handling are uniform.

## Steps

1. Compare `ProviderCapabilityRecipe.to_result()`, `_stamped()`, `ProviderRecipeRegistry.install()`, `uninstall()`, `dry_run()`, and Hindsight `_RowRecipe._stamp()`.
2. Identify duplicated `ProviderRecipeResult(...)` construction and replace with one helper/boundary where semantics match.
3. Ensure `action_needed` precedence is consistent: primitive result guidance > row/provider default guidance > empty.
4. Add tests for provider result stamping across status, install, uninstall, dry_run, repair, and custom recipe results.
5. Keep provider registry keyed by `(provider_id, capability_id, backend_id)` and avoid entity-specific branches.

1. Tests prove provider provenance is stamped exactly once at the boundary.

4. No raw `ProviderRecipeResult(...)` duplication remains where `to_result()` or a shared constructor can express it.
