# Harden shell step output, secret redaction, and recipe observability

## Description

Harden shell-based provisioning and recipe result output. `ShellProvisionStep` currently captures combined stdout/stderr into `StepResult.outputs["stdout"]` and failure `reason`. That is useful for diagnostics but conflicts with standards if raw output contains secrets, prompts, API keys, tokens, or noisy logs. Recipe operations that mutate durable resources should also emit redacted timeline events where useful.

## Steps

This is the parent/analysis item; execution happens in RS15 (characterize) then RS16 (implement). Do not implement fixes directly under this ID. This is the HIGHEST PRIORITY item in the whole plan — a confirmed, unmitigated secret-leak surface.

1. Confirmed exact leak locations (RV228/RV229 audit) in `src/audiagentic/foundation/toolchains/provision_steps/shell.py`:
   a. `ShellProvisionStep._run_argv()` (~line 88-96): `StepResult(outputs={"command": command, "returncode": proc.returncode, "stdout": proc.stdout.rstrip("\n")}, reason=None if ok else proc.stdout.strip() or None)` — full, unredacted process stdout (stderr is merged into stdout via `stderr=subprocess.STDOUT`) goes straight into the structured `StepResult`.
   b. `ShellProvisionStep._run_shell()` (~line 137-145): identical pattern for the shell-mode execution path.
   c. From there, `StepResult.outputs`/`.reason` flow into `RecipeResult.details`/`.error` via `recipe_contract.py::run_steps()` (`details={"steps": seq_result.outputs.get("steps", [])}`) and ultimately into `ProviderRecipeResult` via `to_result()`/`_stamped()` — there is no redaction anywhere on this path today.
   d. `command`/`revert_command` themselves may also carry secret-shaped values (e.g. `--api-key=sk-...` passed as a literal step param) and are stored verbatim in `outputs["command"]`.
2. Confirmed an existing but non-reusable redaction precedent: `foundation/logging/audit.py::_RedactionFilter` (regex-substitute matched patterns with `[REDACTED]`, patterns supplied via `cfg.ai_audit.redact_patterns`, config-driven). RS16 must generalize this into a shared module rather than reinvent redaction logic.
3. RS15 must characterize every leak path above with a failing-by-design test (proving the leak exists today) before RS16 implements the fix. RS16's fix must not change command execution semantics — only what is captured into `StepResult`/`RecipeResult`/logs.
4. Once RS15/RS16 land, update this item's Notes with the final list of redacted fields and cross-reference OU01 for the cross-cutting fan-out to non-recipe modules.

## Validation

1. Tests prove shell outputs are redacted according to policy: token-like strings (>20 chars, base64 patterns), API key prefixes, and bearer tokens are masked with `[REDACTED]`.
2. Tests prove env secrets (vars containing KEY, TOKEN, SECRET, PASSWORD) are never emitted in `StepResult.outputs`, `RecipeResult.details`, logs, or timeline attributes.
3. Std §8 compliance: tests prove `recipe_contract.run_steps()` does not propagate raw shell outputs into `RecipeResult.details` on failure — only redacted summary.
4. Observability Standards compliance: recipe timeline events include component/resource/event/state fields when durable resources are changed; attributes are pre-redacted by caller.
5. Existing recipe dry-run tests remain readable and produce meaningful (not blank) output after redaction.
6. Whole-repo grep for `stdout` in recipe result detail assignments confirms no raw propagation path remains.
7. Std §9 compliance: probe exceptions produce safe summaries without logging MCP/tool args.

## Effort & Risk

Mid. Tightening output can affect diagnostics, so preserve enough information for operators while complying with standards.

## Standards

Std §8: raw stdout/stderr and secrets must not be in error details. Std §9: library code uses module loggers and never logs MCP/tool args. Observability Standards: durable timelines for long-running or async resources, redacted attributes only.
