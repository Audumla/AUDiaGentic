# Harden shell step output, secret redaction, and recipe observability

## Description

Review shell-based provisioning for security and observability. `ShellProvisionStep` captures stdout/stderr into `StepResult.outputs` and failure `reason`; standards prohibit raw stdout/stderr, tokens, or user prompts in error details. Recipe operations that mutate durable resources should also have timeline events where useful, not only transient logs/status strings.

## Steps

1. Audit shell/config/plugin recipe outputs for raw stdout, command arguments, env values, API keys, tokens, URLs with credentials, and prompt text.
2. Add a redaction helper or result-summarization policy for shell step outputs and recipe result details.
3. Decide whether `ShellProvisionStep` should keep full stdout in debug-only logs, truncated summaries, or no stdout in structured outputs.
4. Add durable timeline events for recipe install/configure/prune/uninstall where resources are modified or long-running operations occur.
5. Ensure timeline attributes are small, structured, and caller-redacted.

## Validation

1. Tests prove shell outputs are redacted/truncated according to policy.
2. Tests prove env secrets are never emitted in `StepResult.outputs`, `RecipeResult.details`, logs, or timeline attributes.
3. Tests prove recipe timeline events include component/resource/event/state fields where durable resources are changed.
4. Existing recipe dry-run tests remain readable and useful after redaction.

## Effort & Risk

Mid. Tightening output can affect diagnostics, so preserve enough information for operators while complying with standards.

## Standards

Std §8: raw stdout/stderr and secrets must not be in error details. Std §9: library code uses module loggers and never logs MCP/tool args. Observability Standards: durable timelines for long-running or async resources, redacted attributes only.

## Notes

This is a cross-cutting safety cleanup. It should not change command execution semantics, only what is persisted or surfaced.
