# Harden shell step output, secret redaction, and recipe observability

## Description

Harden shell-based provisioning and recipe result output. `ShellProvisionStep` currently captures combined stdout/stderr into `StepResult.outputs["stdout"]` and failure `reason`. That is useful for diagnostics but conflicts with standards if raw output contains secrets, prompts, API keys, tokens, or noisy logs. Recipe operations that mutate durable resources should also emit redacted timeline events where useful.

## Current findings

- `ShellProvisionStep._run_argv()` and `_run_shell()` return full command and full stdout in structured outputs.
- Failure `reason` may contain raw stdout text.
- `CompensatingSequence` copies step outputs into aggregate `outputs["steps"]`, so one unsafe shell output can propagate into recipe results.
- `recipe_contract.run_steps()` copies sequence `outputs["steps"]` into `RecipeResult.details["steps"]` on failure, pushing raw per-step output up to provider-facing results.
- `DeclaredStepRecipe.probe()` can surface unredacted command/probe exception text through `RecipeResult.fail(...)`.
- `ArtifactRegistry` and plugin recipes mutate durable files but do not uniformly record timeline events.
- Observability standards require redacted attributes and durable timelines for long-running/asynchronous resource state.

## Proposed solution

1. Add a domain-neutral redaction/summarization helper in foundation, either under `foundation/toolchains` or a shared redaction utility if one already exists.
2. Change `ShellProvisionStep` structured outputs to include:
   - command summary with executable and redacted args,
   - return code,
   - stdout/stderr summary or truncated redacted tail,
   - no raw env values.
3. Keep enough diagnostics for operators: full stdout should not be persisted in `StepResult`; if absolutely required, log redacted/truncated debug output through module logger.
4. Add recipe/timeline helper hooks only where resources are durable and mutation is non-trivial: install/configure/prune/uninstall start/end/failure for provider/hindsight recipe actions.
5. Ensure dry-run output follows the same redaction policy.
6. Apply redaction/safe summarization to propagation points: `CompensatingSequence` aggregate outputs, `recipe_contract.run_steps()` failure details, and `DeclaredStepRecipe.probe()` failure messages.

## Options considered

| Option | Decision | Reason |
|---|---|---|
| Keep full stdout in `StepResult` | Rejected | Violates standards risk; stdout often contains tokens, prompts, paths, or logs. |
| Drop stdout entirely | Defer | Might hurt diagnostics; prefer redacted/truncated summaries first. |
| Add redaction only in provider layer | Rejected | Unsafe output originates in foundation shell step and propagates upward. |
| Timeline every provision step | Defer | Could be noisy; start with recipe-level durable resource events and add step-level only if needed. |

## Implementation steps

1. Add tests that simulate stdout containing `token=...`, `Authorization: Bearer ...`, API key-looking strings, and prompt-like content.
2. Add a redaction helper and use it in `ShellProvisionStep` outputs and failure reasons.
3. Update `CompensatingSequence` tests to ensure aggregate outputs are safe after shell failure and rollback failure.
4. Add a tiny recipe timeline helper if one does not exist, using `record_timeline_event` and caller-redacted attributes.
5. Add timeline calls at recipe registry boundaries or concrete recipe mutation points, choosing one layer only to avoid duplicate events.

## Effort & Risk

Mid. Tightening output can affect diagnostics, so preserve enough information for operators while complying with standards.

## Standards

Std §8: raw stdout/stderr and secrets must not be in error details. Std §9: library code uses module loggers and never logs MCP/tool args. Observability Standards: durable timelines for long-running or async resources, redacted attributes only.
