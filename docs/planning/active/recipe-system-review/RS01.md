# Audit and tighten recipe lifecycle contract semantics

## Description

Review the foundation recipe contract for lifecycle clarity, result semantics, and maintenance safety. The current contract is a strong base: `RecipeResult`, `RecipeState`, `ProvisioningRecipe`, `run_steps`, default `provision()`, and default `teardown()` are domain-neutral and reusable. This item makes the contract implementation-ready for downstream cleanup by locking semantics with tests and documentation.

## Current findings

- `ProvisioningRecipe.provision()` already supports verified fast-path, `provision_steps()` execution through `run_steps()`, primitive install/configure path, artifact accumulation, verify failure to `RecipeState.ERROR`, and `to_result()` conversion.
- `ProvisioningRecipe.teardown()` already uses prune → uninstall → cleanup hooks → post-uninstall probe.
- `run_steps()` adapts `CompensatingSequence` to `RecipeResult`, but failure details may include raw per-step outputs and should be evaluated with RS05.
- `dry_run()` is not in the foundation abstract contract; it exists on provider recipes and provision steps.
- Provider `_stamped(recipe, result)` is a second provider-layer stamping path used outside base orchestration by registry `status()`, `dry_run()`, and `repair()`. RS01 must coordinate with RS02/RS09 so base `to_result()` remains canonical for orchestration and `_stamped()` does not double-apply provenance.

## Proposed solution

1. Add an explicit lifecycle semantics table in `recipe_contract.py` docstring or nearby tests documenting each primitive's expected state and mutation behavior.
2. Keep `dry_run()` optional in foundation for now. Do not add it to `ProvisioningRecipe` until at least two non-provider foundation consumers need it; provider recipes already supply a dry-run boundary.
3. Add tests around current intended behavior rather than changing orchestration.
4. Route cleanup hook failures through a safe `RecipeResult.fail(...)` that does not expose unredacted exception payloads. If details are needed, use summarized type/message only after RS05 redaction helper exists.

## Options considered

| Option | Decision | Reason |
|---|---|---|
| Leave contract as-is | Rejected | Too much behavior is implicit; downstream agents may duplicate orchestration. |
| Add `dry_run()` abstract method to foundation now | Defer | Provider layer is current consumer; adding an abstract method would force churn without a second foundation-level consumer. |
| Replace primitive path with steps-only path | Rejected | Existing recipes use primitive methods for work steps cannot express, and `provision_via_steps=False` is intentional. |
| Keep cleanup hook exception text verbatim | Rejected | Standards prohibit leaking raw details/secrets in structured results. |

## Implementation steps

1. Add `tests/unit/foundation/toolchains/test_recipe_contract.py` if missing.
2. Add fixtures: `AlreadyVerifiedRecipe`, `PrimitiveRecipe`, `StepRecipe`, `FailingVerifyRecipe`, `FailingCleanupRecipe`, `NoStepRecipe`.
3. Assert `to_result()` is called for: verified fast-path, step path success, step path failure, primitive path failure, verify failure, teardown prune failure, uninstall failure, cleanup failure, post-uninstall success/failure.
4. Document `provision_via_steps=False` as the supported way for introspection-only steps.
5. If redaction helper from RS05 exists, use it for cleanup hook failure strings; otherwise add a TODO comment and a test that prevents obvious secret-like values from being surfaced.
6. Add cross-layer tests in RS09/RS10 proving `_stamped()` does not double-stamp results already converted by `to_result()`.
