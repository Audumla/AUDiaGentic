# Audit and tighten recipe lifecycle contract semantics

## Description

Review the foundation recipe contract for lifecycle clarity, result semantics, and maintenance safety. The current contract is a strong base: `RecipeResult`, `RecipeState`, `ProvisioningRecipe`, `run_steps`, default `provision()`, and default `teardown()` are domain-neutral and reusable. The audit should tighten edge cases and document exact expectations so dependants do not duplicate orchestration.

## Steps

1. Review `ProvisioningRecipe.provision()` and `teardown()` for consistent state transitions, artifact accumulation, and conversion through `to_result()`.
2. Define a small lifecycle contract table covering `probe`, `install`, `configure`, `verify`, `prune`, `uninstall`, `provision`, `teardown`, `dry_run` where applicable.
3. Decide whether all recipe families should expose `dry_run()` at the base contract level or whether it remains an optional provider-registry concern.
4. Confirm cleanup hook failures should not leak unredacted exception text into user-facing details.
5. Add tests for `provision_via_steps=False`, verified fast-path, verify failure, cleanup hook failure, and teardown post-uninstall verification.

## Validation

1. Unit tests cover primitive path and provision-step path.
2. Tests prove `to_result()` is applied to every public orchestration result.
3. Tests prove failed verify produces `RecipeState.ERROR`.
4. Tests prove cleanup hook failure returns a safe structured failure.
5. No dependant recipe reimplements `provision()` or `teardown()` unless it has documented, tested semantics.

## Effort & Risk

Mid. Core semantics are already good, but changing the base contract can affect every dependant recipe. Keep behavior-preserving unless a failing test proves an ambiguity.

## Standards

Std §1: foundation names stay domain-neutral. Std §3: shared orchestration stays in foundation. Std §8: public failures use structured errors/results and redact details. Std §10: test-driven migration.

## Notes

Do not add component/provider vocabulary to foundation. This item is about clarifying and hardening the existing domain-neutral contract, not introducing new provider-specific lifecycle APIs.
