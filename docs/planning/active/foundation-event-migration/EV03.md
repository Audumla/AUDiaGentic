# Delete provider_recipes.py from foundation; move capability->provider reconciliation into providers component as event reaction

## Description

foundation/lifecycle/provider_recipes.py hosts a capability->provider-recipe reconciliation dispatcher whose entire vocabulary (ProviderRecipeReconciler, _all_provider_ids, _enabled_provider_ids, refresh_provider_recipes, capability keys providers.descriptors.all_ids and providers.provider-config.resolve_enabled) is providers-component domain language living in foundation. It passes the import-direction check (no static import of components.providers) only because it goes through get_capability() lookups instead -- that is a workaround for the layering rule, not compliance with its intent. REDESIGNED per review RV108 (2026-07-05, verified against code): the ONLY registrant of register_provider_recipe_reconciler is the MEMORY component (components/memory/memory_observer.py:62, registering its own _reconcile for hindsight), and the ONLY production caller of refresh_provider_recipes is the same file (memory_observer.py:59). Since memory is simultaneously the sole publisher and sole registrant, the original plan (move the reconciler registry INTO providers, have providers subscribe and reconcile) was wrong on two counts: it forces memory_observer.py to gain a new cross-component import of components.providers just to register (trading a naming violation for a layering violation -- component-to-component imports are only tolerated for the one documented providers->agent_jobs seam, not memory->providers), and the reconciliation logic (_reconcile) is memory-domain hindsight provisioning, not providers logic, so it cannot actually 'live inside the providers component' as originally described. The dispatcher indirection collapses to memory calling its own function -- the registry can be deleted outright rather than relocated.
