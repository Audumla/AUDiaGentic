# CompensatingSequence executor and provision() rollback

## Description

Add `CompensatingSequence` to `foundation/toolchains/provision_step.py`.

The executor runs a `ProvisionStep` list forward; on failure it reverts only committed steps in reverse order. Revert is best-effort: failures are logged and captured in result details, but never mask the original run failure.

This item is executor-only. It does not change `ProvisioningRecipe.provision()` lifecycle behavior yet. TO12 wires recipes into the executor after recipe classes can produce complete provision step lists.

**Rollback semantics:**
```
Step 1 -> ok (committed)
Step 2 -> ok (committed)
Step 3 -> failed
Rollback: Step 2.revert(), Step 1.revert()
Returns: Step 3 failure as primary result, rollback results in details
```
Step 3's revert is never called because it did not commit.

**Why `SequenceStep` is not extended:** `SequenceStep` lives in `foundation/workflow/` and is used by non-provisioning orchestration. Mixing rollback semantics there violates the boundary. `CompensatingSequence` lives in `foundation/toolchains/` and is only used by provisioning recipes.

## Steps

1. **Implement `CompensatingSequence`** in `foundation/toolchains/provision_step.py`.

2. `run(context)` executes steps forward. A step is considered committed only when it returns `StepResult(status='ok')`. On the first non-ok result, call `_rollback(committed)` and return the original failure with rollback results attached in outputs/details.

3. `_rollback(committed)` iterates committed steps in reverse order. It catches Exception per revert step, logs every caught exception at `logger.warning(..., exc_info=True)`, and continues. Revert failures are represented as failed StepResult entries in the rollback result list.

4. `revert(context)` reverts all configured steps in reverse order. It is best-effort and returns an aggregate StepResult with per-step results.

5. `dry_run(context)` calls each step's `dry_run()` in forward order and returns an aggregate StepResult without mutation.

6. Export `CompensatingSequence` from `foundation/toolchains/__init__.py`.

## Validation

- `CompensatingSequence.run()`: 3 steps, step 2 fails -> step 1 revert called, step 3 not run, original step 2 failure returned.
- `CompensatingSequence.run()`: 3 steps, step 3 fails -> step 2 and step 1 revert called in reverse order.
- Revert failure does not raise; it is logged with exc_info=True and captured alongside original failure.
- Non-ok statuses such as `failed` or `skipped` stop forward execution unless explicitly documented otherwise.
- `CompensatingSequence.revert()`: all steps' reverts called in reverse.
- `CompensatingSequence.dry_run()`: all steps' dry_run methods called in forward order, no run/revert methods called.
- Existing unit tests pass.

## Effort & Risk

Low to mid. This item is pure executor logic around already-defined ProvisionStep primitives. Main risk is unclear status handling; define committed as status == 'ok' and stop on any other status unless future callers need a different policy.

## Standards

- S8 (Error handling): _rollback() catches Exception at external-boundary revert calls. It never re-raises and always captures exception details.
- S9 (Logging): Every caught exception in _rollback() MUST be logged at logger.warning level with exc_info=True before continuing to the next revert step. Silent exception swallowing is a violation.

## Notes

Depends on TO10. TO12 depends on this item.

Do not add `prune()`-on-configure-failure to `ProvisioningRecipe.provision()` in this item. That rollback is imprecise because it can remove config without reversing install work. Precise rollback happens through committed ProvisionStep instances in CompensatingSequence.
