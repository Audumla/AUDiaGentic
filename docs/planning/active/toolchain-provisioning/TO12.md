# Recipe migration: replace _run_command() with ProvisionStep and extend matrix YAML

## Description

Migrate Hindsight recipes to the `ProvisionStep` model (TO10) and `CompensatingSequence` executor (TO11), while consolidating duplicate recipe execution code into shared step-list helpers.

This item replaces `_run_command()` string parsing with structured `install_steps` and `configure_steps` from the matrix YAML. It is a single migration path: `install_command` / `uninstall_command` are removed from the Hindsight matrix schema and all rows are migrated atomically. No fallback shim is kept.

Each recipe that participates in automatic provisioning exposes one complete step list:
```python
def provision_steps(self) -> list[ProvisionStep]:
    return [*install_steps, *configure_steps]
```

`ProvisioningRecipe.provision()` uses `CompensatingSequence(recipe.provision_steps()).run(context)` when a recipe exposes `provision_steps()`, then runs `verify(context)`. Recipes without `provision_steps()` continue on the existing primitive-call path until migrated.

**Consolidation target:** eliminate repeated command execution logic in `HooksInstallerRecipe`, `PluginConfigRecipe`, and `_ClaudePluginUrlRecipe` by generating shell steps from row data through shared helpers. Do not introduce `_CommandRecipeMixin`; the command-specific methods disappear once structured steps are the source of truth.

Deferred from this item: `build_hindsight_recipe()` registry refactor. That is orthogonal cleanup and should not be mixed into the provisioning migration unless required to make the migration compile.

## Steps

1. **Add recipe step-list contract**: Define an optional `provision_steps() -> list[ProvisionStep]` convention on provisioning recipes. Do not require separate `install_steps()` and `configure_steps()` interfaces.

2. **Add shared Hindsight step helpers** in `recipes.py`: `_hindsight_params(backend, provider_id) -> dict[str, str]`, `_steps_from_defs(step_defs, params, *, recipe_id, registry=None) -> list[ProvisionStep]`, and small row helpers for install/uninstall/configure step definitions. These helpers are the consolidation point replacing duplicated `_run_command()` call sites.

3. **Wire `ProvisioningRecipe.provision()` to CompensatingSequence**: If `self` has `provision_steps`, run those steps through `CompensatingSequence`. On success, call `verify(context)`. On failure, return the sequence failure with rollback details. Recipes without `provision_steps()` keep the existing probe/install/configure/verify path.

4. **Migrate command rows to structured shell steps**: Extend `HindsightRecipeRow` with `install_steps: list[dict]`, `uninstall_steps: list[dict]`, and `configure_steps: list[dict]` as needed. Remove `install_command` and `uninstall_command` from `HindsightRecipeRow`, `_load_matrix()`, tests, and YAML.

5. **Migrate ALL matrix rows atomically**: Convert every `install_command` / `uninstall_command` in `hindsight_matrix.yaml` to structured shell step dictionaries in the same change. Preserve command order and behavior. Pipe commands use `shell: true`.

6. **Replace `_run_command()` call sites**: Recipe classes build steps via the shared helpers and `provision_step_from_dict(data, params)`. Remove `_run_command()` and `_parameterize_command()` command-run usage entirely; keep status-probe parameterization only if still needed for `status_command`.

7. **Implement `provision_steps()` for migrated recipes**: Hooks, wrapper CLI, plugin config, MCP config adapters, rules-only, and hybrid/composite recipes should return a complete ordered list for their provisioning work where practical. For composite recipes, concatenate inner recipe step lists in execution order.

8. **Consolidate common no-op lifecycle methods where natural**: Keep `_RowRecipe._stamp`, and add small shared helpers for repeated success/no-op results only if they reduce duplicate code without hiding recipe-specific behavior. Avoid broad inheritance reshuffles.

9. **Keep unrelated refactors out**: Do not replace `build_hindsight_recipe()` dispatch in this item unless required to make the migration compile. Track it as a separate cleanup item if still valuable after migration.

## Files

- `src/audiagentic/foundation/toolchains/recipe_contract.py` — optional `provision_steps()` path in `ProvisioningRecipe.provision()`
- `src/audiagentic/components/memory/hindsight/recipes.py` — remove `_run_command()`, build ProvisionStep lists, implement `provision_steps()` where migrated
- `src/audiagentic/components/memory/hindsight/matrix.py` — replace command fields with structured step fields
- `src/audiagentic/config/components/memory/hindsight_matrix.yaml` — migrate all command rows to structured steps
- `tests/unit/memory/test_hindsight_recipe.py` and related strategy/boundary tests — update schema and behavior expectations

## Validation

- All existing Hindsight matrix rows load with structured step fields; no row uses `install_command` or `uninstall_command`.
- `HindsightRecipeRow` has no `install_command` / `uninstall_command` attributes.
- Shared step helpers are covered by unit tests: params contain URL/MCP_URL/TOKEN/KEY/ID, shell step defs build expected ProvisionStep objects, registry/recipe_id pass through to config/file steps.
- A migrated multi-command row executes steps in the same order as old `&&` command behavior.
- A migrated pipe command produces a shell=True `ShellProvisionStep` and preserves the full command string.
- Placeholder substitution uses params built in components layer; foundation factory does not import Hindsight types.
- `ProvisioningRecipe.provision()` uses `CompensatingSequence` when `provision_steps()` exists and rolls back committed steps on failure.
- Recipes without `provision_steps()` continue using existing primitive lifecycle path.
- Hybrid/composite recipe step order matches previous behavior.
- Command install/uninstall duplication is removed from HooksInstallerRecipe, PluginConfigRecipe, and _ClaudePluginUrlRecipe; behavior remains covered by migrated step tests.
- All existing unit tests pass after expectation updates for the new schema.

## Effort & Risk

Mid to high because this is the flag-day migration from command strings to structured steps. Risk is controlled by keeping consolidation focused on step generation and command execution removal: no mixin extraction, no builder registry refactor, no optional dual schema. Main behavioral risk is preserving command order, shell pipe behavior, source gates, and placeholder substitution.

## Standards

- S1 (Layering): Hindsight backend fields are mapped to a params dict in components/memory/hindsight code before calling foundation factory. foundation/toolchains does not import Hindsight types.
- S8 (Error handling): Invalid step definitions raise AudiaGenticError at the factory boundary.
- S10 (Migration doctrine): No backward-compat shim. `install_command` and `uninstall_command` are removed from schema, loader, tests, and all YAML rows in one change.

## Notes

Depends on TO10 and TO11.

Optimization intent: consolidate code by making structured ProvisionStep lists the single execution representation. The shared helpers should replace duplicate command install/uninstall methods across HooksInstallerRecipe, PluginConfigRecipe, and _ClaudePluginUrlRecipe. Avoid adding abstractions that only exist to support the old command-string model.

`build_hindsight_recipe()` registry refactor is intentionally deferred. It may still be useful, but it is unrelated to step execution and should be reviewed as a separate cleanup after migration.

The payoff of this item is a self-describing matrix, precise rollback through committed ProvisionStep instances, and less per-recipe command boilerplate.
