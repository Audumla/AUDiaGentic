# Make --project drive profile resolution: propagate AUDIAGENTIC_REPO_ROOT from the launcher (closes the RV128 limitation)

## Description

Closes the known limitation documented in RV128: launching `audiagentic --project X --component-profile Y` from a cwd outside X resolves the profile against cwd's project (find_project_root walks up from cwd) instead of X. DECIDED SOLUTION -- no loader API change: the loader already resolves the project root via audiagentic.paths.find_project_root(), which honors the existing AUDIAGENTIC_REPO_ROOT env override (paths.py:22-23) before walking from cwd. The launcher already propagates --component-profile to env the same way (launcher.py, 'Propagate --component-profile to env' block after parse_known_args). Do the identical thing for --project: when args.project is given, set os.environ['AUDIAGENTIC_REPO_ROOT'] = str(resolved project_root) in the same post-parse block. Explicit flag beats ambient env, so set unconditionally when the flag is present (argparse default is None when absent -- never clobber a user's env var with cwd). This makes every env-driven consumer (profile resolution, MCP server env forwarding tested in tests/unit/providers/test_component_mcp_launch_shape.py:53-63, logging discovery) agree with --project, not just the code paths that thread project_root explicitly. Also update the loader comment in foundation/components/loader.py that documents the limitation ('Known limitation: launching with --project X ...') to state it is now handled by the launcher's env propagation.
