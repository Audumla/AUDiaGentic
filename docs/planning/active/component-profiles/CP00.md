# Replace commands/ hardcoded optional-component imports with capability-registry lookups

## Description

commands/ is the correct composition-root layer per docs/standards/ARCHITECTURE_STANDARDS.md:13 (it is explicitly the one layer permitted to import specific optional components) - the earlier idea of moving commands/ under runtime/ was wrong and has been dropped. The real defect found while tracing commands/'s imports: four call sites hardcode a direct import of a specific optional component (components.providers.*, components.project.project_api) wrapped in an ad hoc try/except ImportError, rather than going through the capability registry (get_capability/register_capability, foundation/capabilities.py) already used elsewhere for exactly this purpose (e.g. foundation/lifecycle/component_mcp.py, foundation/components/loader.py:279-282's providers.surface-validator lookup). This violates ARCHITECTURE_STANDARDS.md rule 2 ('if/elif chains that branch on entity names are prohibited - use a registry of (key, handler) pairs') and rule 5 ('never maintain a Python import list that enumerates pluggable modules'), and would silently break under component-profiles once a profile can legitimately omit the providers/project component - an ImportError guard on a still-installed-but-unloaded package is not a reliable absence signal.

## Notes

Supersedes the deleted original CP00 ('move commands/ under runtime/'), which was based on a misreading of ARCHITECTURE_STANDARDS.md - commands/ is correctly a distinct composition-root layer (later revised further by CP09, which merges the two layers after this item removes the raw imports that were the reason they were kept separate). Expanded (2026-07-04) to include launcher.py's own two instances of the identical anti-pattern, found via a follow-up grep sweep - launcher.py and commands/ are the same composition-root layer, so both needed the same fix. Should land before CP03/CP04/CP09 touch the same files. Per review RV93 (2026-07-05, verified against code): adding a lazy register_all_components() call at each converted site means those sites gain a re-glob of component config dirs on every invocation - this makes CP02's cache guard a soft prerequisite for CP00's performance (not correctness), worth landing CP02 first or accepting the interim cost.
