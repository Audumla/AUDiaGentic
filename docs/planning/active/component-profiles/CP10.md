# Extract generic keyed-registry utility with lazy-load + alias support; migrate ad hoc registries with no shims

## Description

Six ad hoc registries found during investigation are structurally identical or near-identical - a module-level dict keyed by string, a register_X() function, a lazy _loaded/_LOADED guard, and a getter - with inconsistent collision behavior: components/coding_lsp/language_registry.py:26-27,167-173, components/providers/services/host_adapter.py:71-72,75-91, components/providers/tags/registry.py:6-7,22-28, foundation/toolchains/provision_steps/base.py:41-46 (_STEP_TYPES), components/providers/surfaces/registry.py:7-9,20-38, foundation/lifecycle/provider_recipes.py:19,22-37. CORRECTED per review RV95 (2026-07-05, verified against code): foundation/components/registry.py's register() (registry.py:17-23) does NOT destructively strip a DIFFERENT component's aliases on collision - it only clears aliases owned by the SAME incoming component_id, which is correct idempotent-re-registration cleanup. The real latent defects there are (a) cross-component alias collisions are silently last-wins (_aliases[alias] = id with no conflict check against a different existing owner) and (b) an alias can silently shadow-collide with a real component_id already in _registry, with no check either way. Per ARCHITECTURE_STANDARDS.md:96-97 ('No backward compatibility shims... do not create shim functions... migrate code as we refactor, always'), this is a direct call-site migration, not a wrapper-preserving one: every caller of the old register_*/get_* functions is updated to call the new generic registry instance directly, and the old module-level functions are deleted in the same change. To make the utility capable enough to genuinely absorb more than the bare minimum, it supports two features beyond a plain dict: a built-in lazy-loader (invoked once on first access, replacing five separate hand-rolled _ensure_loaded() implementations) and an optional alias index (register(key, value, aliases=[...]) that raises/warns on cross-component alias conflict and alias-vs-primary-key shadowing, while same-owner re-registration stays a silent no-op) - correct alias semantics proven here first is what lets foundation/components/registry.py (see CP08) adopt the same utility internally later without becoming a shim. ADDITIONAL CORRECTION per RV95: components/providers/surfaces/registry.py is NOT a 1:1 fit - it holds TWO separate dicts (_renderer_registry, _contribution_renderer_registry) behind ONE shared lazy-load flag (_providers_imported). Its migration needs two Registry instances that share a single loader callable (or one loader that populates both instances), not the simple one-dict-one-instance mapping the other five registries get.
