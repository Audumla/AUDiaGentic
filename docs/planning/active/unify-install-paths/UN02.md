# Migrate provider CLI install/uninstall onto the ProvisioningRecipe contract and ProviderRecipeRegistry

## Description

The provider CLI install path is a hand-rolled duplicate of the recipe contract. Today it consists of:

- `components/providers/workflow/provider_cli.py`: a private hardcoded state machine (`_PROVIDER_CLI_STATES`: missing/installing/installed/failed/uninstalling/uninstalled/skipped — semantically `RecipeState` under different names), a `_ProviderCliConfig` shim to satisfy the generic `StateMachine`, a fake `ItemView`/context (`ProviderCliWorkflowContext`), and `workflow_provider_cli_run/plan` orchestrating one step + probe.
- `components/providers/services/lifecycle.py`: `install_provider_cli` / `uninstall_provider_cli` / `repair_provider_cli` / `provision_all_provider_clis` with hand-built result dicts (`_result`), status strings ('installed'/'uninstalled'/'planned'/'skipped'/'failed'/'ok'), a Windows PATH-settle probe retry (`_probe_provider_cli_after_install`), and post-install side effects (config seed, surfaces apply, MCP sync).
- `descriptors/base.py` `CliInstallRecipe`: install/uninstall as raw invocation steps + probe metadata.

Every concept here already exists in the recipe lane: probe/install/verify/uninstall lifecycle = `ProvisioningRecipe`; declared install+uninstall steps behind a gate with a status probe = `DeclaredStepRecipe`+`InstallManifest`; dry-run = `dry_run()`; dispatch/registry = `ProviderRecipeRegistry` keyed `(provider_id, capability_id, backend_id)`; repair (prune+reinstall) = `registry.repair`.

**Solution:**

1. **Adapter recipe.** Introduce `ProviderCliRecipe(ProviderCapabilityRecipe)` registered as `(provider_id, 'cli', None)`, `recipe_kind=COMMAND_INSTALLER`, built from the existing `CliInstallRecipe` descriptor data. Descriptor YAML/dataclass stays the authoring format — only the execution engine changes. Mapping: `recipe.install/uninstall` steps → `InstallManifest.install_steps/uninstall_steps` (as step dicts once UN01 lands; `CallableStep`-based installs keep a callable-step type); `descriptor.cli_probe`/`probe_fn` → the recipe's `probe`; probe-after-install retry (3×1s Windows shim settle) → inside `verify()`.
2. **Registry construction.** A `build_provider_cli_registry(project_root)` helper mirrors hindsight's `register_hindsight_recipes`: iterate `all_descriptors()`, register a recipe per provider with a `cli_install` block; providers without one get `NoAutomationRecipe` semantics (status 'skipped', reason 'provider has no installable CLI recipe' — preserve exact strings).
3. **Result adaptation at the API boundary.** The MCP/API/CLI callers currently receive dicts with keys `provider-id`, `action`, `status`, `package-manager`, `package-name`, `executable`, `command`, `returncode`, `stdout`, `stderr`, `probe`, `reason`, `workflow-events`, `surfaces`. Write ONE adapter `provider_result_dict(ProviderRecipeResult, ...)` that reproduces this shape (command/stdout/stderr come from `result.details` populated by the shell step). Status mapping: VERIFIED→'installed'/'ok', ABSENT after teardown→'uninstalled', ERROR→'failed', dry-run→'planned', no recipe→'skipped'. Public payload shape must not change in this item.
4. **Post-install side effects stay caller-side.** `_seed_provider_config`, `apply_provider_surfaces`/`prune_provider_surfaces`, `_sync_provider_mcp` remain in `lifecycle.py` install/uninstall wrappers, invoked after a successful recipe provision/teardown. They are provider reconciliation, not recipe internals — do NOT fold them into the recipe.
5. **Delete** `provider_cli.py`'s private state machine, `_ProviderCliConfig`, `ProviderCliWorkflowContext`, `_action_config`, `_probe_matches`, and `_invocation_result_from_workflow` once callers are on the registry. `workflow-events` in the result: keep as an empty-list-compatible field or synthesize from recipe state transitions — check actual consumers first (grep for 'workflow-events'); if only tests read it, simplify them.

**Behavioral quirks to preserve deliberately (each gets a test):**
- Timeout-tolerated-as-success: an install whose shell step timed out still counts as installed if the post-install probe finds the CLI (`provider_cli.py` lines ~221-222).
- Windows PATH-settle retry: up to 3 extra probes at 1s intervals after install.
- vscode-package-manager providers are skipped by `reconcile_all_providers` subprocess probing — unchanged.
- `repair` short-circuits to 'ok' when the CLI probe already passes, without reinstalling.
