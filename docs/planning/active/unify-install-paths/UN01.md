# Unify step primitives: single compensating step system for provisioning and workflow invocation

## Description

AUDiaGentic has two parallel step systems expressing the same 'run a declared unit of install work' concept:

1. **foundation/workflow/invocation/steps.py** — `ShellStep` (with `PlatformOverrides`), `CallableStep`, `SequenceStep`, `SelectStep`, `ConditionalStep`, `ConfirmStep`, plus `planned_commands()` for dry-run, executed by `WorkflowInvocationRunner` producing `WorkflowInvocationResult`. Consumers: provider CLI install (`components/providers/workflow/provider_cli.py`; `descriptors/base.py` `CliInstallRecipe.install/uninstall` are typed as these steps), component dependencies (`foundation/components/dependencies.py`), toolchains loader (`foundation/toolchains/loader.py` `build_step`/`raw_step`).

2. **foundation/toolchains/provision_steps/** — `ProvisionStep` base with a registered step-type factory (`steps_from_defs`, `provision_step_from_dict`, `substitute_params`), concrete `ShellProvisionStep`, `ConfigSetStep`, `WriteFileStep`, `ManagedBlockStep`, executed by `CompensatingSequence` (structured rollback) producing `SequenceResult`. Consumers: the ProvisioningRecipe contract (`recipe_contract.run_steps`), `DeclaredStepRecipe`, and via those only memory/hindsight.

The duplication is concrete: two shell-step implementations, two sequence types, two dry-run mechanisms (`planned_commands` vs recipe `dry_run`), two result shapes. Every future capability recipe or installer must pick a lane, and bridging code already exists (toolchains loader emits invocation steps while recipe_patterns consumes provision steps).

**Chosen solution (direction to implement):** make the compensation-capable step model the single system, hosted at the foundation layer, and have the invocation runner consume it.

- Define ONE step protocol: `run(context) -> StepResult`, optional `compensate(context)` (rollback), optional `plan(context) -> list[list[str]]` (dry-run command enumeration). This is a superset of both current protocols.
- Port `ConfigSetStep`, `WriteFileStep`, `ManagedBlockStep` unchanged — they already implement compensation.
- Merge the two shell steps into one `ShellStep` that carries `PlatformOverrides`, timeout, cwd, progress_callback (from invocation) AND declarative-dict construction + param substitution + optional compensation command (from provision_steps).
- Keep `SequenceStep`/`SelectStep`/`ConditionalStep`/`ConfirmStep`/`CallableStep` from invocation; `CompensatingSequence` becomes a sequence variant (or runner mode) that invokes `compensate()` in reverse order on failure.
- Unify result vocabulary: a single `StepResult`/`SequenceResult`; `WorkflowInvocationResult` either becomes an alias or a thin adapter kept for API stability of the provider dicts (removed in the provider CLI migration item).
- Home: prefer `foundation/workflow/invocation/` as the canonical package (kernel-ward layer); `foundation/toolchains/provision_steps/` becomes re-exports during migration, deleted at the end. If architecture standards (standard-0014 / doctrine v2 layering) argue toolchains must not depend on workflow, the fallback is a new `foundation/steps/` package both import — decide at implementation start against the arch boundary tests.
- The step-type registry (`register_step_type` / `steps_from_defs`) is the YAML/dict-driven construction path and must survive — hindsight matrix specs and InstallManifest step dicts depend on it.

## Effort & Risk

Effort: 2-3 sessions. Risk: MEDIUM-HIGH — this touches the execution substrate of every installer. Mitigations: compat shims during migration, behavioral parity fixtures captured before any move, arch-boundary test run before choosing the package home. The riskiest merge is ShellStep (two different substitution styles — invocation steps take context dicts at run time, provision steps substitute {KEY} params at construction); resolve by supporting both substitution points explicitly and testing each.

## Notes

Decision record: direction chosen is 'compensation-capable model wins, invocation package hosts it'. Rejected alternative: building ShellProvisionStep as a wrapper over ShellStep (keeps two protocols alive indefinitely and does not kill the duplicate sequence types). This item is a prerequisite for the provider-CLI migration item — CliInstallRecipe manifests translate cleanly to InstallManifest step dicts only once there is one step vocabulary. Related layering notes: SL11/SL12/SL13 in providers/services/recipes.py docstring; SL13 A6 already removed ManagedEntryRecipe/ConfigEntryTarget as zero-consumer — do not reintroduce.
