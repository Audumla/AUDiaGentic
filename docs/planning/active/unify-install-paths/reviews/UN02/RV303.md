# Standards reconciliation: §15 redaction of result-dict stdout/stderr, §8 codes, §2 no provider-id branching, §16 scope note

## Notes

Cross-checked UN02 against ARCHITECTURE_STANDARDS.md and MANAGED_MUTATION_AUDIT.md.

## Findings

1. §15 Output Redaction (must add, current path already non-compliant): the provider result dict carries raw stdout/stderr (lifecycle.py:90 puts invocation stdout/stderr straight into the payload with no redaction). The new provider_result_dict boundary adapter MUST apply redact_text() to command/stdout/stderr before returning. If UN01's ShellStep already redacts at capture, the adapter inherits it and only needs to avoid re-exposing raw output; state that dependency explicitly. This aligns with the 2026-07-12 OU01 audit that motivated §15.
2. §2 Config Over Code (must assert): the status mapping (VERIFIED->installed, etc.) and recipe selection must NOT branch on provider id anywhere — selection is by iterating all_descriptors() and by recipe_kind, never `if provider_id == ...`. Add an explicit no-branch assertion to validation. The verb switch (install/uninstall) in _action_config is acceptable (verb, not entity).
3. §8 Error Handling: preserve existing codes exactly (VAL-PLFC-001 unknown provider, VAL-PLFC-002 unsupported action, VAL-PROVCLI-001 unknown CLI action). Any new code from the recipe path must be registered in providers' error-resolutions.yaml first. Do not silently drop the existing codes when deleting the workflow glue.
4. §16 Managed Mutation scope (clarify): provider CLI *package* install/uninstall is EXPLICITLY EXCLUDED from §16 (audit 'Explicit exclusions': package installation/uninstallation and temporary execution files). So the install commands themselves are not §16-governed. BUT the post-install side effects (surfaces apply/prune, MCP sync) already route through managed owners and must continue to — do not inline any file writes into the recipe. Add this as an explicit non-goal so a lesser agent doesn't 'helpfully' move surface writes into the recipe.
5. §10: deleting provider_cli.py internals requires whole-repo grep (incl tests/) for the removed symbols (_PROVIDER_CLI_STATES, ProviderCliWorkflowContext, workflow_provider_cli_run/plan, _action_config, _probe_matches) and a green full suite.
6. Observability: provider_cli.py currently emits workflow_ctx.events; if any observer/ledger consumes the 'provider-cli' resource events, replicate emission from the new path before deleting (already flagged in notes; elevate to a validation gate).

## Conclusion

Incorporate into UN02. Item 1 (redaction) is the highest-value addition; item 4 prevents a likely misimplementation.
