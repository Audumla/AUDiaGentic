# Sponsor direction 2026-07-18: usage/limits visibility has a concrete first consumer — make OpenRouter key-limits the PT01 v1 vertical slice

## Notes

Sponsor wants to see usage/limits per vendor/provider as part of cross-harness model management (MO18-MO20 created today for the OpenRouter free-model chain).

## Findings

PT01 should stay the owner of the telemetry capability model, but it now has a concrete, cheap, verified first probe to build the model around instead of designing in the abstract: OpenRouter's authenticated key endpoint (GET /api/v1/auth/key) returns limit, usage, limit_remaining, and is_free_tier — verify the exact response shape against a live account and record it as MA19 evidence with a versioned anchor before freezing the PT01 contract fields. Recommended v1 slice: one typed per-source usage/limits read (source_id → {limit, usage, remaining, free_tier, fetched_at, freshness}), explicit refresh only (same no-network-on-reconcile rule as MO12 catalogs), cached with the same freshness vocabulary, surfaced through the MO20 overview only once PT01's contract names the field. The capability-matrix telemetry table then gains its first 'verified via AUDiaGentic probe' row rather than remaining documentation. Per-harness scraped telemetry (Claude Code CLI display etc.) stays out of the v1 slice — matrix tier 4 rows are explicitly not probeable without fragile interception (open question in the reference doc).

## Conclusion

Anchor PT01's contract on the OpenRouter probe as the worked example; keep everything else in the model declarative until a second verified probe exists.
