# Provider Telemetry Capability Model

## Description

Design and implement a multi-dimensional provider telemetry model that replaces the binary 'supports credits' flag. Each provider declares which telemetry categories it can expose: balance (account credits), quota (rate limits), subscription (usage windows), session (remaining context/tokens), runtime (GPU/VRAM/local metrics), cost_estimation, and observability (streaming token counts, billing events). This becomes the foundation for cross-provider scheduling and budget management.

## Notes

V1 SLICE (RV636, sponsor direction 2026-07-18): the original 16-provider telemetry design below is the eventual model but has no verified probe yet — build the capability model around a concrete, cheap, already-verified first source instead of designing in the abstract. OpenRouter's authenticated key endpoint (GET /api/v1/auth/key) returns limit, usage, limit_remaining, is_free_tier. Before freezing PT01's contract fields: verify the exact response shape against a live account and record it as an MA19 evidence fact with a versioned anchor.

Recommended v1 vertical slice: one typed per-source usage/limits read (source_id -> {limit, usage, remaining, free_tier, fetched_at, freshness}), explicit refresh only (same no-network-on-reconcile rule as MO12 catalogs), cached with the existing freshness vocabulary, surfaced through MO20's overview only once this contract names the field. This gives the capability-matrix telemetry table its first 'verified via AUDiaGentic probe' row instead of remaining documentation-only.

Out of v1 scope: per-harness scraped telemetry (e.g. Claude Code CLI display) — matrix tier 4 rows are not probeable without fragile interception; stays an open question. Broader multi-dimensional telemetry (balance/quota/subscription/session/runtime/cost_estimation/observability categories, all 16 provider YAMLs) remains the eventual full design in the description/steps below but should not be built until a second verified probe exists — keep it declarative/deferred, not implemented speculatively (Architecture Standards §3 evidence-led scope).

Depends on MO18 (OpenRouter source enablement) landing first for the account/key context this probe needs.
