# Make Hindsight MCP provisioning honest about HTTP-only

## Description

Hindsight ships an **HTTP MCP server only** (user-confirmed, 2026-08-02, and
already documented at
`src/audiagentic/components/memory/hindsight/INSTALL_MAP.md:69`:
"The currently documented local MCP server is an HTTP server, not a generic
`hindsight-mcp --base-url ...` stdio command" — the real server is
`uvx --from hindsight-api hindsight-local-mcp` on `http://localhost:8888/mcp/`).

The provisioning code does not reflect that. It has a stdio fallback that
registers a command Hindsight does not ship, and it is the **default route for
six providers**, which silently write an MCP entry that can only fail when the
harness later tries to launch it.

Found while diagnosing the last remaining unit-test failure under AS71.

## Current routing, measured 2026-08-02

`_resolve_family` + `_resolve_recipe` in
`components/memory/hindsight/provision.py:120-180`:

| Route | Providers | State |
|---|---|---|
| artifact recipe | aider, codex, copilot, openhands, roo | works |
| artifact recipe | **pi** | **fails** — recipe asks for `transport: http`, pi declares `remote: false`, guard rejects with `CON-PMCP-001` |
| `hindsight-managed-mcp.yaml` (HTTP) | **goose only** | works |
| `hindsight-managed-mcp-stdio.yaml` | antigravity, claude, cline, continue, gemini, qwen | **silently broken** — registers `command: hindsight-mcp`, which does not exist |
| plugin-entry | opencode | works |
| guidance-only | crush, gpt-auto, kilo, local-openai, plandex, zed | correct |

Only `goose` declares `remote: true`
(`config/providers/goose.yaml`, `capabilities.mcp.mechanism.remote`, justified
"streamable_http extension support"). Every other provider defaults to `false`
— which is almost certainly *unpopulated*, not *probed*: `claude`, `gemini`,
`cline` and others do support HTTP MCP entries in their real config formats.

## Work

1. **Delete `hindsight-managed-mcp-stdio.yaml` and its branch**
   (`provision.py:171-176`). Hindsight is HTTP-only, so a non-remote provider
   cannot integrate over MCP at all; it must fall through to the existing
   guidance-only path (`return None, {}`), not to a fictional command.
   Per `arch-standards` §4 this is a deletion, not a deprecation — no shim.
2. **Probe each currently-`false` provider** for HTTP/remote MCP entry support
   in its own config format, and set `remote: true` with a citing comment where
   proven, following goose's precedent. This is what actually restores Hindsight
   for claude/gemini/cline/etc. Unknown stays `false` — `arch-standards` §3.
3. **Decide pi** (see below).
4. Add a test asserting no recipe registers a command that is not on the
   documented Hindsight surface, so a fictional binary cannot be reintroduced.
5. Reconcile `INSTALL_MAP.md` with whatever the code ends up doing — today the
   doc is correct and the code is wrong, which is the right way round to fix.

## The pi decision — `BLOCKING`

`hindsight-pi.yaml` registers a `managed-mcp` step with `url` + `transport: http`.
pi declares `remote: false`, so `managed_mcp_family.py:66-78` rejects it.

pi has **never** declared remote — verified before and after the PC01-PC04
capability migration, so this is not a regression. The recipe was authored
2026-07-26; the guard rejecting it landed 2026-07-15. The recipe has therefore
never worked, and `test_hindsight_provision.py::test_reconcile_populates_pi_host_block`
has never passed.

The open question is narrow: **does `pi-mcp-adapter` honour
`{"type": "http", "url": ...}` in `.mcp.json`?** pi's MCP support is an
extension, not native, and pi's upstream docs are 404
(`docs/reference/PROVIDER_CAPABILITY_REFERENCE/harnesses/profiles/pi.md`), so
this must be probed against the installed adapter — in Docker, per repo
doctrine, never by mutating the host.

- If **yes**: set `remote: true` on `pi.yaml`'s mcp mechanism with the probe
  cited, and the recipe and test pass unchanged.
- If **no**: pi cannot integrate Hindsight over MCP while Hindsight is
  HTTP-only. Remove `pi` from `_ARTIFACT_RECIPES` so it falls to guidance-only,
  and delete or rewrite `hindsight-pi.yaml`'s `managed-mcp` step (its
  `config-set` host-block steps are independently useful and should survive).

Do not flip the flag without the probe: a capability declaration is a factual
claim under `arch-standards` §3, and "the shared mcp-json writer can emit a url"
proves only that AUDiaGentic can *write* the entry, not that pi *reads* it.

**Interim, until the probe runs:** the failing test should be `xfail` with this
item's ID as the reason, or pi dropped from `_ARTIFACT_RECIPES`. Prefer the
latter — a recipe that always fails is worse than no recipe. Do not mark it
skip without a reason string.

## Acceptance criteria

- No recipe registers an MCP server that Hindsight does not ship.
- Hindsight's HTTP-only reality is expressed in the routing, not just the docs.
- `remote` flags are probe-backed; unknown remains `false`.
- The pi decision is recorded with its evidence before any flag change.

## Standards

- `arch-standards` §3 Evidence-led scope — `remote` is a factual capability
  claim; declare it from a probe, never from the writer's ability to serialize a
  URL.
- `arch-standards` §4 Public Contracts — delete the stdio route outright; no
  shim, alias or dual path. Failures must be explicit rather than a silently
  written entry that fails later at launch.
- `arch-standards` §2 Extensions and Configuration — provider capability lives
  in the descriptor YAML, not in a branch in the memory component.
