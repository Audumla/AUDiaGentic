# Harden planning MCP schemas and error contracts

## Description

Harden the qualification-workflow planning MCP component's generated schemas and public error contracts. This item was moved from the gpt-auto-conversation project; its canonical owner is qualification-workflow. Scope covers planning item/review CRUD, state/list tools, and management/config tools exposed by the planning MCP server.

## Steps

1. Establish a canonical inventory of every planning MCP tool and caller, recording request fields, nullability, aliases, output shape, owner, and compatibility status. 2. Introduce typed FastMCP/Pydantic request models for item/review CRUD, state transitions, list filters, and management/config operations; preserve supported aliases and omitted-vs-null update semantics. 3. Add runtime validation for enums, bounds, tags, unknown fields, non-empty updates, duplicate append entries, and cross-field relationships; keep persisted-state legality in the domain layer. 4. Register stable planning error codes and remediation text, including VAL-PLN-027/028, with bounded and redacted public details. 5. Add schema snapshots plus runtime, error-envelope, redaction, compatibility, persistence, and routing tests. 6. Run live MCP validation only after explicitly selecting this Audiagentic project; record the exact project/session identity in test evidence.

## Detailed Solution & Technical Design

Use FastMCP/Pydantic models with optional-in-presence update fields, Literal/Enum constraints, and model_fields_set for append subset validation. Do not set extra='forbid' globally until the inventory classifies existing callers; choose reject, ignore, or compatibility alias per field and document the decision. Transport models enforce shape and bounds; items/reviews/domain code enforce persisted-state transitions and project policy. Use AudiaGenticError with registered planning codes. Public errors expose only stable code, actionable remediation, and bounded safe details—never raw malformed values, prompts, credentials, PII, or filesystem paths. The planning server must resolve the explicit project context rather than infer another repository.

## Code Samples & Guidance

### Append contract

`append` is a list of section names, not content. The content must be in
`updates`:

```json
{
  "item_id": "GP06",
  "updates": {"notes": "new text"},
  "append": ["notes"]
}
```

The broken call that motivated this item was:

```json
{
  "item_id": "GP06",
  "updates": {},
  "append": ["DIAGNOSTIC PROBE ec9f1a"]
}
```

That previously returned success while making no visible change because
`updates` was empty and the append value was treated as a section key. The
same behavior was reproduced across GP01, GP06, HI18, HI138, and TO01.
The workaround was fetch-then-concatenate into `updates.notes`.

The implementation now rejects malformed calls with bounded, actionable
errors:

- `VAL-PLN-027`: append supplied without update content.
- `VAL-PLN-028`: an append entry is absent from `updates`.

Raw append values are deliberately excluded from error details because they
could contain prompts, credentials, or PII.

### Proposed typed request model

Use FastMCP/Pydantic models with optional-in-presence update fields:

```python
AppendField = Literal[
    "description", "steps", "detailed_solution", "code_samples",
    "files", "validation", "effort_risk", "standards",
    "acceptance_criteria", "notes",
]

class PlanItemUpdates(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: str | None = None
    description: str | None = None
    steps: str | None = None
    detailed_solution: str | None = None
    code_samples: str | None = None
    files: str | None = None
    validation: str | None = None
    effort_risk: str | None = None
    standards: str | None = None
    acceptance_criteria: str | None = None
    notes: str | None = None
    work: Literal["S", "M", "L"] | None = None
    skill: Literal["basic", "intermediate", "advanced"] | None = None
    state: Literal["pending", "in_progress", "completed", "superseded", "deprecated"] | None = None
    priority: Literal["P0", "P1", "P2", "P3"] | None = None
    order: Annotated[int, Field(ge=0)] | None = None
    tags: list[NonEmptyString] | None = None
```

Runtime validators must additionally enforce non-empty supplied fields,
unique tags, unique append entries, and
`append ⊆ updates.model_fields_set`. Legal state transitions and persisted
project policy remain domain-layer checks.

`additionalProperties=false` is a potentially breaking change because the
current API may accept arbitrary custom body sections. Audit real callers and
existing payloads before enabling it.

## Notes

Handoff context: append previously accepted updates={} with append=[raw text] and reported success. The implementation now rejects this as VAL-PLN-027/028 with bounded details. Dev GPT review approved typed models with changes and identified the need for runtime validators beyond JSON Schema metadata. Prior gateway requests were accidentally routed to BigCherry because the gateway inferred the active repository; the next chat must explicitly use the Audiagentic project context.

Dev GPT's full review verdict was **APPROVE WITH CHANGES**. It confirmed that
FastMCP supports nested Pydantic models, Literal/Enum constraints, optional
values, and generated schemas, but warned that `json_schema_extra` alone does
not enforce `minProperties` or `uniqueItems` at runtime. It recommended
runtime validators and `model_fields_set` for partial-update semantics.

Current schema gap inventory: `plan_update_item` only structurally declares
`item_id` as a string, `updates` as an unrestricted object, and `append` as a
nullable array of strings. It does not currently enumerate update keys or
validate `work`, `skill`, `priority`, `order`, or `tags`. `plan_create_item`
also uses a generic object despite documentation describing `work` and
`skill` values.

Error-management audit: public domain failures must be raised as
`AudiaGenticError` with stable owning-component codes; remediation belongs in
`config/components/planning/error-resolutions.yaml`; the two files must not
be conflated. `tool_boundary` translates and redacts public errors. Errors,
logs, results, and timelines must not expose secrets, credentials, raw
prompts, or unredacted process output. The first append patch briefly violated
the spirit of this rule by echoing malformed append values in `details`; that
was corrected to counts and generic expectations only.

Gateway-routing correction: requests sent while the active repository was
BigCherry were inferred by the gateway as the BigCherry project even when
`workspace_name` was omitted. Future Dev GPT validation must explicitly select
the Audiagentic project/session and verify the returned project metadata before
trusting results.
