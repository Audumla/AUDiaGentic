# Broaden ACP: adapters for more providers; design the rich multi-channel launch/observability capability model

## Description

Two related directions surfaced during HA04's launch-model design (2026-07-24):

1. ACP BROADENING. AUDiaGentic only has acp.py builders for pi and opencode, but most of the CLIs it wraps (claude, gemini, codex, etc.) actually support ACP or an ACP mode. Add agent-intent acp.py adapters for those providers so they get live agent sessions. Also evaluate making ACP the PREFERRED transport for the execute intent too: structured ACP JSON-RPC events are far more reliable than the current pipe path's heuristic stdout-scraping (try_extract_json_from_stdout + synthetic fallbacks in base_runner/completion.py are fragile). Native pipe stays as the universal floor and the lean single-turn option for CLIs that lack ACP.

2. RICH CAPABILITY MODEL. HA04 established the principle that the CALLER expresses an intent (execute|interactive|agent) and the HARNESS assembles its richest transport/channel surface -- the caller never selects transports. It also added a role-based, queryable launches capability (descriptor.launches = {intent: {interaction:[...], observability:[...]}}). Deepen this: a harness should be able to combine MULTIPLE channels on one launch (e.g. pi agent = ACP interaction + native RPC hooks for observability + plugins), declaring its full surface and choosing its most feature-rich combination. Wire the observability channels to the existing AS19 harness-status-observer subsystem so 'observability' declarations are actually consumed. Support querying capabilities and requesting a constrained subset for a customized launch, while defaulting to the harness's fullest surface.

## Detailed Solution & Technical Design

DO NOT RE-RESEARCH WHICH CLIS SUPPORT ACP -- IT'S ALREADY DONE. src/audiagentic/components/providers/services/harness_observability_inventory.py (AS27) is an authoritative, evidence-gated per-provider-surface inventory already covering candidate ACP routes for codex, claude, cline, gemini, qwen, kilo, copilot, goose, openhands, pi (two routes: pi-rpc primary, pi-community-acp fallback) plus recipe-B/C/D entries for providers with no ACP route (aider, continue, antigravity, plandex, roo, zed, crush). Each entry carries a `candidate_source` (the actual flag/package, e.g. "npx @google/gemini-cli --acp", "copilot --acp --stdio or loopback TCP") and a `probe_anchor` (what must be proven before promotion). Only ("opencode","opencode-acp") is currently `validation_state=VALIDATED` -- every other ACP candidate is `PROBE_REQUIRED`. HA06's job is to PROMOTE entries from PROBE_REQUIRED to VALIDATED (by actually running the candidate_source and proving the probe_anchor claim, per each provider's own note) and, for each promoted entry, add the corresponding hand-written adapters/<id>/acp.py (or a declarative acp: recipe block if it fits build_launch_spec's vocabulary) plus a `launches: {agent: {...}}` declaration in that provider's config/providers/<id>.yaml descriptor -- mirroring the pattern already proven for pi/opencode/codex.

ADAPTER TEMPLATE (pattern established by 3 existing implementations -- read all three before writing a new one, they show the range):
  - src/audiagentic/components/providers/adapters/pi/acp.py -- native --mode rpc launch, no bridge package, materializes a request-owned MCP isolation document (genuinely custom, stays hand-written).
  - src/audiagentic/components/providers/adapters/opencode/acp.py -- native `opencode acp` stdio subcommand.
  - src/audiagentic/components/providers/adapters/codex/acp.py (full file, ~40 lines) -- BRIDGE PACKAGE pattern for CLIs with no native ACP mode: prefer a locally-installed bridge binary (shutil.which), fall back to `npx -y <package>` so the adapter works without a global install. This is almost certainly the pattern needed for gemini (`npx @google/gemini-cli --acp`), qwen (`npx @qwen-code/qwen-code --acp --experimental-skills`), and cline (`npx @cline/cline-acp --mcp --acp`) per their candidate_source strings above -- codex/acp.py can likely be adapted near-verbatim (swap package name + executable id) for those three. Every build_acp_launch(project_root, *, model_id=None) returns AcpLaunch(executable, args, environment) -- the same ProviderLaunch shape from foundation/transports (AcpLaunch is its alias).

DESCRIPTOR WIRING (per provider, e.g. config/providers/gemini.yaml): add
  launches:
    agent:
      interaction: [acp]
      observability: [acp]
  (add more observability channels, e.g. rpc, only if that provider ALSO has a validated non-ACP observation route in the AS27 inventory -- e.g. pi declares both acp and rpc because it has pi-community-acp AND pi-rpc as separate surfaces). This makes resolve_launch_builder(provider_id, "agent") resolve via the existing _LAUNCH_BUILDERS["agent"] = ("acp", "build_acp_launch") mapping in services/execution.py -- no dispatch code changes needed, the mechanism already generalizes across providers.

AS19 OBSERVABILITY WIRING (the second half of this item, separate from adding acp.py files): once a surface's `validation_state` flips to VALIDATED with `effective_production_level >= O1` and `lifecycle_source = LifecycleSource.TRANSPORT` in harness_observability_inventory.py, it AUTOMATICALLY becomes eligible via `is_eligible_transport_observation_publisher()` -- consumed today by services/harness_status_observer_resolution.py::resolve_transport_observation_lease (AS19 stage-2 Slice A). No new integration code is needed for the transport-observation (Recipe A) path itself; HA06's job here is purely the EVIDENCE work (prove the probe_anchor, flip validation_state) plus updating _build_inventory()'s entry (validation_state, effective_production_level, platform_evidence, supported_statuses) to reflect what was actually proven -- do not hand-wave a promotion without a real probe artifact (a passing test at the stated probe_anchor path, or a new one if the anchor doesn't exist yet).

MULTI-CHANNEL LAUNCHES (harness assembling MULTIPLE channels on one launch, e.g. pi agent = ACP interaction + RPC observability simultaneously): pi's descriptor already declares this shape (`agent: {interaction: [acp], observability: [acp, rpc]}`) but adapters/pi/acp.py's build_acp_launch only actually wires the ACP transport -- it does NOT currently also start the RPC observability channel alongside it. Before generalizing this pattern to other providers, first make Pi's own multi-channel declaration real: extend build_acp_launch (or add a second call the caller makes alongside it) to also produce whatever launch/env changes are needed to expose the pi-rpc surface (see the pi-rpc inventory entry's candidate_source: "JSONL agent/turn/message/tool events via pi --mode rpc --no-session") concurrently with the ACP session. This is the concrete proof-of-concept the rest of the multi-channel design should generalize from -- do not design the abstract N-channel mechanism before this one concrete case works.

EXECUTE-VIA-ACP (the other stated direction, lower priority / separable): base_runner.py's default_parse_completion/try_extract_json_from_stdout (protocols/streaming/completion.py) is the current stdout-scraping fallback used by every execution: recipe provider without a hand-written parser. Evaluate, for providers that now have a validated ACP adapter, whether execute_provider could dispatch through the ACP transport instead for more reliable structured results -- this is a distinct, separable sub-task; do not block ACP broadening on it. Native pipe (the current execution: recipe path) MUST remain the universal floor for CLIs without ACP -- never remove it.

CAPABILITY QUERY / SUBSETTING: describe_provider already surfaces descriptor.launches (providers_api.py ~line 941). Confirm/extend it to also surface the AS27 inventory's per-surface detail (validation_state, effective_production_level) for introspection, so a caller can distinguish "declared" from "proven" -- check current describe_provider output shape before adding fields; this may already be sufficient as-is via the two data sources being queried separately.

## Code Samples & Guidance

Reference implementations to read first, in this order: adapters/codex/acp.py (bridge-package pattern, shortest, ~40 lines) -> adapters/opencode/acp.py (native subcommand pattern) -> adapters/pi/acp.py (most complex, request-owned MCP isolation document -- do not copy this complexity for providers that don't need it).

Example new adapter (gemini, bridge-package pattern, closely mirrors codex/acp.py):
  # src/audiagentic/components/providers/adapters/gemini/acp.py
  from __future__ import annotations
  import shutil
  from pathlib import Path
  from audiagentic.components.providers.adapters.cli import require_executable
  from audiagentic.foundation.transports import AcpLaunch

  _GEMINI_ACP_PACKAGE = "@google/gemini-cli"

  def build_acp_launch(project_root: Path, *, model_id: str | None = None) -> AcpLaunch:
      direct = shutil.which("gemini")
      if direct:
          return AcpLaunch(executable=direct, args=("--acp",), environment={})
      return AcpLaunch(
          executable=require_executable("gemini", "npx"),
          args=("-y", _GEMINI_ACP_PACKAGE, "--acp"),
          environment={},
      )
  (VERIFY the exact flag/package against gemini.yaml's own candidate_source note and actual `gemini --help`/npm registry before trusting this sketch -- it is illustrative, not proven.)
