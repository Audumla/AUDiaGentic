# Broaden ACP: adapters for more providers; design the rich multi-channel launch/observability capability model

## Description

Two related directions surfaced during HA04's launch-model design (2026-07-24):

1. ACP BROADENING. AUDiaGentic only has acp.py builders for pi and opencode, but most of the CLIs it wraps (claude, gemini, codex, etc.) actually support ACP or an ACP mode. Add agent-intent acp.py adapters for those providers so they get live agent sessions. Also evaluate making ACP the PREFERRED transport for the execute intent too: structured ACP JSON-RPC events are far more reliable than the current pipe path's heuristic stdout-scraping (try_extract_json_from_stdout + synthetic fallbacks in base_runner/completion.py are fragile). Native pipe stays as the universal floor and the lean single-turn option for CLIs that lack ACP.

2. RICH CAPABILITY MODEL. HA04 established the principle that the CALLER expresses an intent (execute|interactive|agent) and the HARNESS assembles its richest transport/channel surface -- the caller never selects transports. It also added a role-based, queryable launches capability (descriptor.launches = {intent: {interaction:[...], observability:[...]}}). Deepen this: a harness should be able to combine MULTIPLE channels on one launch (e.g. pi agent = ACP interaction + native RPC hooks for observability + plugins), declaring its full surface and choosing its most feature-rich combination. Wire the observability channels to the existing AS19 harness-status-observer subsystem so 'observability' declarations are actually consumed. Support querying capabilities and requesting a constrained subset for a customized launch, while defaulting to the harness's fullest surface.
