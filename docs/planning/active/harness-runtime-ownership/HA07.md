# Register the rig as a model source; project it into any AG-CLI-capable provider through the standard pipeline

## Description

The rig (AUDiaGentic's local embedded model) is currently delivered to Pi/OpenCode via a bespoke, per-provider pipeline (components/providers/adapters/{pi,opencode}/local_rig_config.py) that duplicates a schema/rendering/delivery mechanism already built for vendor models (MO17/18/19's ModelProjectionEntry -> render_<id>_model_entry -> write_<id>_models pipeline). This item unifies them: register the rig as a model source (source_id="ag-rig") in .audiagentic/config/model-sources.yaml, so enabling the rig for any provider becomes the identical operation as enabling OpenRouter for that provider -- reusing the existing typed contract, renderers, and managed-config writers rather than local_rig_config.py's separate construction. Delivery stays capability-gated per provider: launch-time isolated injection where a provider supports it (OpenCode's OPENCODE_CONFIG_CONTENT, extended to also carry a "provider" block, not just "mcp"), directory-scoped durable write otherwise (Pi, via its existing per-request PI_CODING_AGENT_DIR redirection for agent/ACP launches, or the shared global harness runtime for interactive launches). local_rig_config.py is deleted once equivalence is proven, not templated or kept as a parallel mechanism. See detailed_solution for the full evidence trail (four converging revisions, all confirmed against real code/CLI behavior this session) and notes for the chronological record.

## Detailed Solution & Technical Design

NAMED (2026-07-25): the rig's model-source id is `ag-rig`, matching this codebase's established ag-<name> convention (ag-planning, ag-ledger, ag-session-mgmt, ag-agents, ag-lsp, ag-providers-mgmt -- all ag-, never audiagentic-). This is a SEPARATE identifier from `provider_id` (harness_cfg.rig.provider, already "audiagentic" throughout existing fixtures/local_rig_config.py callers) -- provider_id is harness-facing (the key inside Pi's models.json / OpenCode's config.json, and what --provider <id> on the launch command line references); source_id is AUDiaGentic-facing (model-sources.yaml, source enablement/management only). Do not conflate or rename provider_id to match -- that would ripple into every harness's native config and the launch flag itself; ag-rig as source_id touches nothing external, purely internal to the source-management layer.

FINAL GENERALIZATION (2026-07-25, completes the direction from all four prior revisions): don't construct the rig's ModelProjectionEntry inline in materialize_agent_config per-provider. Register the rig as a MODEL SOURCE (.audiagentic/config/model-sources.yaml, source_id="ag-rig", the same file OpenRouter's MO18 entry lives in), so 'launch with rig for provider X' becomes the IDENTICAL operation as 'enable OpenRouter for provider X' -- the same source -> catalog -> ModelProjectionEntry -> render_<id>_model_entry -> capability-gated delivery pipeline, zero rig-specific code anywhere, zero per-provider hardcoding of the rig's own facts.

CONFIRMED (source_catalog.py, read this session): a non-network discovery mode already exists -- `model-discovery: static-catalog` loads a curated data file via load_static_catalog(source_id), no fetcher needed. This is close to what the rig needs but not exact: the rig's model isn't a static FILE, it's COMPUTED at materialize time from harness_cfg.rig.model + the rig's profile config (config/provisioning/harness/ag.yaml's rig section, resolved via runtime.rig.embedded.config.resolve_profile_definition -- the exact same resolution local_rig_config.py's callers already do today). Port can also vary (harness_cfg.rig.port).

SMALL, LEGITIMATE EXTENSION NEEDED: add a new discovery mode (e.g. `model-discovery: computed`, or extend static-catalog to accept a registered callable instead of only a data-file path) to source_catalog.py, resolving ag-rig's single model entry from harness_cfg + rig profile config instead of a file or network fetch. This is an addition to the EXISTING generic pipeline's vocabulary (source_catalog.py already distinguishes list-api / static-catalog / none discovery modes via `source.get("model-discovery", "none")`) -- not a new parallel mechanism. Keep the new mode's resolver function generic (takes a source config dict, returns model list) so it could theoretically serve ANY other 'computed from local config, not fetched or static-filed' source in the future -- the RIG-SPECIFIC part is only the one small function that reads harness_cfg.rig.* and returns a model list, registered the same way _fetch_openrouter is registered as a connector today.

END STATE: model-sources.yaml gains an `ag-rig` entry with `discovery-mode: computed` (or whatever the new mode is named), `connector: openai-compatible`, and a `base-url` template resolved from harness_cfg.rig.port at materialize/read time. Enabling the rig for a given provider becomes the SAME model_source_add / manage_model_projection / apply_model_sources calls MO18/19 already exercise for OpenRouter -- 'which providers get the rig' becomes a normal per-source, per-provider enablement question, not something requiring any provider-specific runtime code. This directly closes the loop with HA10's capability-driven harness principle: a new AG-CLI-capable provider automatically becomes rig-eligible the moment it has a render_<id>_model_entry function and a declared model_launch_isolation_tier capability -- no new rig-specific code needed for it at all.

RELATIONSHIP TO PRIOR REVISIONS (all still valid, this is additive precision, not a reversal): ModelProjectionEntry stays the canonical schema (rev 1). Delivery stays capability-gated per provider -- launch-time injection where supported (OpenCode's OPENCODE_CONFIG_CONTENT), directory-scoped write where not (Pi's PI_CODING_AGENT_DIR redirection) (rev 2+3). Rev 4 only changes WHERE the rig's ModelProjectionEntry gets constructed FROM -- a registered model source (ag-rig) feeding the standard projection pipeline, instead of a bespoke inline construction in materialize_agent_config.
