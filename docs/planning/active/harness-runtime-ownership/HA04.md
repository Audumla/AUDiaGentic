# Unify provider launch on an intent-based mechanism (ProviderLaunch + recipes + capability)

## Description

AUDiaGentic launches providers in several shapes with duplicated, drifting machinery. This unifies them onto one layered, intent-based mechanism and removes harness customization from the AG CLI path.

Final model (evolved via live design 2026-07-24):
- LAUNCH INTENTS (caller-facing, dispatched): execute (run one turn, capture result -- the gateway task path), interactive (live human tty session), agent (live programmatic agent session). The caller picks an INTENT only; the provider's builder assembles its richest transport/channel surface to fulfil it -- the caller never selects transports (ACP/RPC/tty/hooks are the harness's choice, not the caller's).
- CONTRACT: one ProviderLaunch(executable, args, environment) value (foundation/transports), replacing the byte-identical AcpLaunch + InteractiveLaunch dupes (AcpLaunch kept as an alias for the ACP subsystem).
- SPEC BUILDER: build_launch_spec(spec_decl, context, config) -> ProviderLaunch (base_runner) with a small, frozen two-axis vocabulary -- runtime context tokens ({prompt}/{model-flags}/{approval-flags}/{mcp-args}/{runner-args}) + config->flag algebra (enum-flags/value-flag/repeat-value-flag/boolean-flags). No conditional mini-language; config data models are fixed instead (e.g. Pi tools.mode enum).
- DISPATCH: resolve_launch_builder(provider, intent) -- hand-written adapters/<id>/<submodule> builder (escape hatch) wins, else the declarative recipe block; execute via _load_runner. One shared _adapter_hook collapses the former 5 near-identical loaders.
- CAPABILITY: descriptor.launches = {intent: {interaction:[...], observability:[...]}} -- a queryable, role-based channel surface (surfaced in describe_provider). Source of truth for support: undeclared intent = unsupported; declared-but-no-builder = fail closed; empty = probe (migration).
- HARNESS CUSTOMIZATION REMOVED (AG CLI must not customize harnesses): deleted Pi's footer.ts + follow_up_actions.ts extensions (follow_up_actions.ts was vestigial -- its follow_up_executor module was already deleted), the --extension injection, extension materialization, and the settings.json extensions list. Pi launches stock. Only the MCP surface's adapter extension remains (it delivers AG's projected MCP servers -- the core purpose).
- DEAD CODE removed: qwen/copilot hand-written adapter.py (byte-identical to their execution: recipes); opencode/interactive.py (now a declarative recipe); Pi's dead config knobs (sandbox/custom_header/extensions.load/extra_flags/tools.allow) and a broken startup 'Tools:' line that read the wrong config namespace.
