# Eliminate runtime/harness/<type>/ packages — move materialize into provider adapters

## Description

runtime/harness/pi/ and runtime/harness/opencode/ are redundant when we launch the harness through the provider natively. The provider adapters already own config shape builders (local_rig_config.py), MCP surface preparation, runner arg translation, and model projection. The remaining runtime code is orchestration that delegates into adapters anyway.

End state: no per-type install/ or runner/ submodules under runtime/harness/. Config materialization, lifecycle refresh, and runner bootstrap all route through providers_api — the same path a new AG-CLI-capable provider would use with only a descriptor YAML declaration.

## Steps

1. Move materialize_agent_config into components/providers/adapters/<id>/ as materialize_provider_config (Pi: writes agent/models.json, settings.json; OpenCode: writes .opencode/config.json and AGENTS.md).
2. Wire providers_api.materialize_provider_config(project_root, provider_id, harness_cfg) as the single entry point — replaces runtime/harness/<type>/install.materialize_agent_config.
3. Move refresh/cleanup/lifecycle hooks into a shared runtime/harness/lifecycle.py generic path that calls providers_api — delete per-type install.__init__.py lifecycle scaffolding.
4. Move runner bootstrap (build_global_context, run_agent) into the provider adapter's interactive.py or a shared launch.py — runtime/harness/__init__.py forwards through providers_api.prepare_interactive_provider_launch.
5. Move templates from runtime/harness/<type>/templates/ into the provider adapter package (or inline if short).
6. Update runtime/harness/__init__.py _mod() to no longer require importlib of per-type submodules — resolve against providers_api capability queries instead.
7. Delete runtime/harness/pi/ and runtime/harness/opencode/ packages entirely.
8. Update all remaining callers (tests, commands, lifecycle hooks) to use the new providers_api path.

## Detailed Solution & Technical Design

MATERIALIZE:
The install modules currently do two things:
  - Call adapter-owned shape builders (local_rig_config.py::build_models_config / build_provider_config)
  - Apply provider surface contributions via providers_api.operate_provider_surfaces

Neither requires a per-type runtime module. The materialize function belongs in the adapter where it has direct access to its own config shapes, templates, and surface renderers.

New signature (in adapters/pi/install.py or adapters/pi/__init__.py):
  def materialize_provider_config(project_root: Path, harness_cfg: dict) -> None:
      # Pi: write agent/models.json, settings.json; apply surfaces

New signature (adapters/opencode/install.py):
  def materialize_provider_config(project_root: Path, harness_cfg: dict) -> None:
      # OpenCode: write AGENTS.md, .opencode/config.json; apply surfaces

providers_api adds:
  def materialize_provider_config(project_root: Path, provider_id: str, harness_cfg: dict) -> None:
      adapter = _load_adapter(provider_id, "install")
      adapter.materialize_provider_config(project_root, harness_cfg)

RUNNER:
The runner modules currently do:
  - build_global_context → delegates to shared run_common._build_global_context (already generic)
  - translate_agent_args → delegates to adapter-owned interactive.py (already provider-owned per HA03)
  - run_agent → calls providers_api.prepare_interactive_provider_launch + shared run_supervised

The run_agent logic in opencode/runner/__init__.py is the most complex — but it's already calling providers_api for launch preparation. The same pattern should apply to Pi.

Generic runner (runtime/harness/run_common.py or new runtime/harness/launch.py):
  def run_provider_agent(ctx: AgentContext, project_root: Path, provider_id: str, agent_args: list[str], *, smoke: bool) -> int:
      # Generic: MCP surface prep via providers_api, launch via providers_api, supervised run

This replaces _mod("runner") entirely. runtime/harness/__init__.py's runner forwarding becomes a single generic call through providers_api.

LIFECYCLE HOOKS:
install_to, refresh_materialized_agent_config, cleanup_runtime, etc. — these are thin wrappers around materialize + rig provisioning. Move them into the adapter and/or a shared lifecycle module that calls providers_api.

TEMPLATE OWNERSHIP:
templates/pi/home/agent/AGENTS.md, SYSTEM.md, APPEND_SYSTEM.md → move into adapters/pi/ as bundled assets (pkg_resources or __file__-relative Path).
same for opencode templates.

CALLER MIGRATION:
Key callers to update:
  - runtime/harness/__init__.py _forward("install", ...) → providers_api.materialize_provider_config
  - commands/launch.py → generic run_provider_agent via providers_api
  - lifecycle event handler (_harness_lifecycle_handler) → refresh through providers_api
  - component install lifecycle (test_dynamic_agent_config.py:173) → providers_api path
  - All test imports of runtime.harness.pi.install / runtime.harness.opencode.install

## Effort & Risk

High blast radius — every caller of runtime.harness.<type> must be updated. Risk is mitigated by the fact that adapter-owned shape builders already exist (local_rig_config.py) and the materialize logic is thin delegation. Proving byte-for-byte equivalence before deleting old path follows MA35's own discipline.

## Notes

This is the natural conclusion of HA01 slices 1-3 (which already moved shape builders into adapters) and HA07 (which will register the rig as a model source through the standard pipeline). Once materialize routes through providers_api, a new AG-CLI provider needs only:
  - an adapters/<id>/install.py with materialize_provider_config
  - a descriptor YAML declaring launches + materialize capability
No runtime/harness/<type>/ package required — satisfying HA10's principle without needing HA06/HA07 as prerequisites.

The user explicitly directed this: 'completely lose the harness/pi and opencode folders under runtime — those are redundant when we are launching the harness using the provider natively.'
