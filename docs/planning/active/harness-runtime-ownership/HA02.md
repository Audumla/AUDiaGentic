# Converge Pi harness materialization on managed owners

## Description

Relocated from managed-config-consistency MA07 (RV363) — deferred runtime/harness migration, unchanged in scope. Separate Pi harness-owned runtime assets from provider/project config. Generic provider/surface managers own project MCP/instruction configuration; runtime retains binaries, installed package patches, models, and agent-runtime assets.

## Steps

1. Characterize runtime/harness/pi install/config outputs with path, scope, lifecycle, source, and owner: cli/, agent/, rig/, logs/, generated settings/system prompt/MCP files, project files, copied extensions, patches, reload marker.
2. Mark each output harness-runtime, provider-managed-config, provider-surface, or third-party patch in golden ownership manifest. Any project/provider config goes through MO06/surface manager.
3. Define/use same neutral composition operation as HA01: provider reconcile → surface apply → reload. Pi install/refresh calls it after runtime asset installation; no provider config fallback writer.
4. Pi runtime-home agent settings/system prompt/models remain runtime assets when consumed only by embedded Pi. Their generators register through harness asset registry/virtual asset mechanism with lifecycle modes; avoid raw scattered writes.
5. Move Pi MCP serializer to provider adapter if Pi-specific (`lifecycle`, `settings` semantics). Runtime consumes contribution output or generated runtime asset; delete duplicate runtime management wrappers. Do not move Pi vocabulary into foundation.
6. Existing project `.mcp.json` or provider config entries adopt only on exact desired equality; mismatches collide and survive.
7. Classify every Pi package patch from MA01: dynamic third-party repair exemption requires pinned upstream version/hash or structural precondition, idempotence, atomic write, and failure restoration. Consolidate common patch application mechanics; patch bodies stay Pi-specific.
8. Uninstall removes registered harness runtime assets only; large/user models and logs remain per existing doctrine. Refresh uses same generators and composition path.
9. Delete stale wrappers/serializers/paths with whole-repo grep; update MA01 inventory.
10. Add Pi harness install README doctrine: package/runtime install and third-party patches are harness-owned; provider/project durable mutations compose through the owners above; reusable command sequencing uses MA11.

6. Uninstall preserves models/logs/user assets and removes only registered runtime assets.
7. Runtime harness has no project provider-config lifecycle wrappers/literals after migration.
8. Focused Pi/runtime/provider tests green.
