# Assess collapsing the RecipeSpec assembler back to two concrete subclasses (does config-driven assembly earn its keep?)

## Description

DECISION item (do NOT implement without maintainer direction). Follows SL15 completion (2026-07-09, RV188). SL15 landed a HINDSIGHT-LOCAL config-driven recipe assembler (recipe_spec.py) that replaces two per-kind recipe classes (GuidanceOnlyRecipe, HooksInstallerRecipe) with declarative RecipeSpec data. It is correct, tested, and doctrinally clean — but it does not pass SL15 gate 7 (net LOC down), and the reason is structural, not fixable by more trimming.

THE TENSION (measured 2026-07-09):
- Current assembler footprint: recipe_spec.py = 341 lines + tests/unit/memory/test_recipe_spec.py = 145 lines = ~486 lines, plus the _GUIDANCE_SPEC constant + inline hooks spec + 8 assemble_hindsight_recipe call sites in strategies.py, plus duplicate spec construction in the goldens.
- The concrete-class alternative it replaced: GuidanceOnlyRecipe (~40 lines) + HooksInstallerRecipe (~68 lines) = ~108 lines in recipes.py, no recipe_spec.py, no test_recipe_spec.py, goldens instantiate classes directly.
- So the assembler costs roughly +380 LOC over two hand-written subclasses to serve exactly TWO kinds.

WHY STRUCTURAL: a config/assembler layer only pays for itself when the number of config-shaped consumers is large or growing. Per SL15's own post-SL13 classification table, the remaining kinds (_McpConfigAdapter, PluginConfig, _PluginUrlConfig, _PluginArray) are all >~30% custom logic and EXPLICITLY STAY AS CODE. There is no pipeline of future config-shaped kinds to amortize the assembler — it is a 2-consumer generic mechanism, exactly the regime where two small subclasses win on LOC and readability (no runtime type() synthesis, no VAL-RSPEC validation of developer-authored constants, directly steppable classes).

THE OTHER SIDE (why keep): the user explicitly chose the config-driven direction in SL15; RecipeSpec is declarative and could later be sourced from YAML (matrix rows) so non-programmers add integrations; and the schema validation catches spec-authoring mistakes. If any of those becomes real, keep the assembler. This item is the deliberate call between the two, made on evidence not taste.
