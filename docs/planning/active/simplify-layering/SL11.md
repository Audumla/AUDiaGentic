# Boundary provenance stamping + action_needed field promotion to foundation RecipeResult

## Description

User direction 2026-07-07 (scoped by RV157): recipe machinery must be reusable by ANYTHING that installs code (toolchains, component dependencies, future capabilities) — not trapped in the provider/capability layer. ProvisioningRecipe + provision_steps in foundation are already the generic install-lifecycle extension; ProviderCapabilityRecipe adds only thin provider bookkeeping (~150 lines). Boundary provenance stamping and action_needed field promotion to foundation RecipeResult are prerequisites for extracting reusable install patterns.

Current state: ProviderRecipeResult carries action_needed (~30+ construction sites in hindsight, 1 in LSP recipes); foundation RecipeResult does not — this coupling forces foundation-eligible patterns to return the provider type. No serialization consumers of RecipeResult found; dataclass is non-frozen and replace()-safe.

Two structural causes resolved by this item:
1. PER-METHOD PROVENANCE STAMPING: every primitive hand-builds a fully-populated ProviderRecipeResult because ProviderRecipeRegistry.status() calls probe() directly, bypassing the to_result hook. Route ALL registry dispatch through recipe.to_result once at the boundary.
2. action_needed FIELD COUPLING: promotion to foundation RecipeResult makes types structurally aligned so patterns can return plain RecipeResult and _stamp becomes straight attribute copy.

Target: hindsight primitives return RecipeResult.ok/fail; boundary stamping is one site (_RowRecipe.to_result/_stamp); getattr defensive reads become direct access. Pattern extraction follows as SL12.

## Steps

**Validate-first:** (a) golden-capture current ProviderRecipeResult outputs (status/apply/dry_run) for one row per pattern via existing unit fixtures — boundary stamping must be field-identical; (b) enumerate every ProviderRecipeRegistry caller (status/install/uninstall/dry_run/repair) and every direct primitive caller (lifecycle._reconcile calls recipe.prune directly!) to place the to_result boundary correctly.

1. BOUNDARY STAMPING (prerequisite, own commit): ProviderRecipeRegistry.status/dry_run/repair route results through recipe.to_result (install/uninstall already do); lifecycle._reconcile's direct recipe.prune(ctx) call routes through to_result. Then strip per-method stamping from hindsight primitives incrementally, one class per commit, asserting golden equality — each primitive returns RecipeResult.ok/fail with status (+action_needed after promotion); _RowRecipe.to_result/_stamp remains THE stamp.
2. RecipeResult.action_needed promotion in recipe_contract (with replace()-safety). Validated consumer inventory: writers are hindsight recipes.py (30+ sites via row.audia_action/row.notes), services/lsp_recipes.py:91 ('provider has no LSP integration'), services/mcp.py:166 (plain dict result); readers are hindsight status.py:60, _RowRecipe._stamp and ProviderCapabilityRecipe.to_result via getattr-with-default, registry legacy dispatch field-by-field copy (services/recipes.py:301,313), integration test direct read. Mechanics: RecipeResult is non-frozen dataclass, adding `action_needed: str = ""` with ok()/fail() kwargs is constructor-compatible and replace()-safe; ProviderRecipeResult is standalone-frozen and keeps its own field — no inheritance change, types become structurally aligned so to_result/_stamp are straight attribute copies. §10 cleanup in same change: replace defensive `getattr(...,'action_needed','')` with direct attribute access in _stamp, ProviderCapabilityRecipe.to_result, and status.py; run_steps() gains gate-refusal guidance capability. New test: RecipeResult round-trips action_needed through orchestration replace() paths and run_steps.

## Effort & Risk

Mid / medium. Land steps 1-2 in order — boundary stamping FIRST (it changes what every status consumer receives; goldens gate it). The action_needed promotion is low-risk: non-frozen dataclass, all kwargs callers, replace()-safe, no serialization consumers. Biggest risk is step 1's incremental primitive stripping — one wrong golden could mask a behavior change. Mitigate by doing one class per commit with immediate test run.
