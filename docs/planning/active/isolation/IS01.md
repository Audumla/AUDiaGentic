## Detailed Solution & Technical Design

### Matrix cells and what they test

- **Native default**: agent sees all MCP servers from the harness's native/default configuration (no filtering)
- **Curated subset**: agent sees only a specific subset of MCP servers (others are hidden)
- **Empty subset**: agent sees **zero** MCP servers — complete MCP isolation
- **Concurrent jobs**: two or more isolated jobs run simultaneously without cross-contamination
- **Ambient MCP blocked**: ambient/global MCP configuration (e.g., `~/.pi/mcp.json`) is not visible to the job

### Test approach — inspect actual contacts, not JSON

Tests must verify that the agent actually sees/contacts only the declared MCP servers, not just that the generated `mcp.json` or CLI arguments are correct. Methods:

- Use a sentinel MCP server that logs when contacted
- Verify the agent can call tools from visible servers and **cannot** call tools from hidden servers
- For ambient blocking: place a known sentinel in `~/.pi/mcp.json` and verify the job doesn't contact it
- For concurrent jobs: launch two jobs with different MCP slices simultaneously and verify no cross-contamination

### OpenCode ACP capability/version proof

The bridge must be tested for:

- Exact config-home isolation (does every launch get its own isolated config?)
- Whether `exclusive=true` actually works in the current bridge version
- What happens when global MCP sentinels are placed — does the bridge leak them?
