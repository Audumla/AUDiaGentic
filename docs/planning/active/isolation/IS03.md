# Keep role slicing separate from component profiles

## Description

Component profiles are process-wide and locked on first registration — unsuitable for selecting different MCP slices for concurrent jobs.

Future roles should resolve into immutable per-request launch manifests that select MCP entries without mutating component registries or changing the process component profile.

## Steps

['Design per-request launch manifest schema', 'Separate role resolution from component profile selection', 'Ensure manifest selects MCP entries without mutating registries', 'Test concurrent jobs with different role manifests']

## Detailed Solution & Technical Design

### Component profiles — why they can't do role slicing

- **Process-wide**: a single component profile is selected at first component registration and locked for the entire process lifetime
- **One-profile-per-process constraint** (VAL-COMP-010): requesting a different profile later in the same process raises an error
- To switch profiles, you must stop the current session and restart with a different `--component-profile` value
- This is fundamentally incompatible with concurrent jobs needing different MCP slices

### Role slicing — what it needs to do

- Select different MCP entries for **different concurrent requests** within the same process
- Not mutate component registries or change the process-wide component profile
- Be immutable per-request once resolved
- Be independent of agent profiles (which bind provider+model) and workflow profiles (lite/standard/strict pipelines)

### Per-request launch manifest

The manifest should contain:

```yaml
role: "reviewer"  # or "developer", etc.
required_capabilities:
  - "mcp:ag-planning"
  - "mcp:ag-ledger"
optional_capabilities:
  - "mcp:project_status"
isolation_tier: "exact"  # exact / additive / unsupported
ephemeral_root: "/tmp/request-abc123/"
mcp_document: "/tmp/request-abc123/mcp.json"
```

### Resolution flow

1. Gateway receives request with role hint
2. Resolve required + optional capabilities into an immutable manifest
3. Materialize exactly that MCP slice in the worker's ephemeral root
4. Pass manifest to provider for materialization (provider owns serialization)
5. **Do NOT** mutate component registries or change process component profile
6. Clean up only this request's ephemeral surface on completion

### Why not use component profiles for roles?

Component profiles are designed for alternative sets of **component configurations** (enabled/disabled components, overridden MCP servers). They are not designed for:

- Per-request resolution
- Immutable manifests that survive process lifetime
- Concurrent different profiles in the same process
