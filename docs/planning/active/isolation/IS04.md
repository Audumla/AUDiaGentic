# Complete the role-capability program (RO01-RO04)

## Description

Define role semantics independently of agent, workflow, and component profiles.
Resolve required and optional capabilities into an immutable manifest.
Persist the manifest and fingerprint with the gateway request.
Materialize exactly that MCP slice in the worker.
Introduce presets only after real usage evidence exists.
Fail closed when required capabilities or exact isolation cannot be proven.

Design direction:

- Foundation owns MCP declaration selection
- Providers own harness-specific materialization
- Runtime and gateway consumers supply the requested entries
- Job MCP files are request-owned rather than shared/default files
- Isolation is represented as a concrete provider capability tier

## Detailed Solution & Technical Design

### Role semantics — independent of other profiles

Roles are defined independently of:

- **Agent profiles** (which bind provider to model with execution parameters)
- **Workflow profiles** (which define lite/standard/strict stage pipelines)
- **Component profiles** (which select alternative component configurations)

A role is a declaration of: "this job needs these capabilities, at this isolation level."

### Immutable manifest schema

```
{
  "role": "reviewer",
  "required_capabilities": [
    {"type": "mcp", "server": "ag-planning", "tools": ["plan_list_items", "plan_get_item"]},
    {"type": "mcp", "server": "ag-ledger", "tools": ["get_current_summary"]}
  ],
  "optional_capabilities": [
    {"type": "mcp", "server": "project_status"}
  ],
  "isolation_tier": "exact",
  "fingerprint": "sha256:abc123..."
}
```

### Resolution and persistence

1. Gateway receives request with role hint (or resolves from request metadata)
2. Resolve required + optional capabilities into immutable manifest
3. Compute fingerprint (SHA-256 of manifest content)
4. Persist manifest and fingerprint **with the gateway request** — they travel together
5. Worker reads manifest and materializes exactly that MCP slice
6. Verify fingerprint matches before proceeding (tamper detection)

### Provider ownership of materialization

```
Foundation: selects which MCP entries are needed (declaration selection)
Providers: serialize and materialize the config for their harness (Pi, OpenCode, etc.)
Runtime: passes manifest to provider, doesn't carry provider-specific formatting
```

This means:

- One generic foundation projection selects entries
- Each provider has one serializer/materializer implementation
- Runtime does NOT carry a second version of provider config formatting

### Fail-closed conditions

The system must fail closed (reject the job) when:

1. A required capability is unavailable or cannot be proven
2. Exact isolation cannot be guaranteed for this harness/provider combination
3. The manifest fingerprint doesn't match (tampering detected)
4. The provider reports unsupported for the requested isolation tier

### Presets — defer until real usage evidence

Do NOT introduce role presets (e.g., "reviewer" = specific MCP set) until:

- Real usage patterns are observed from actual jobs
- A role is needed multiple times with the same capability set
- The preset can be validated against the observed pattern
