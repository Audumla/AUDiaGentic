# Prove request-owned cleanup and non-interference for isolated jobs

## Description

Every isolated job must receive a unique runtime root and MCP document. Concurrent jobs must not share or overwrite launch configuration.

Success cleanup should remove only that request's ephemeral surface.
Failure and timeout quarantine must not touch:

- Native harness configuration
- Another job's configuration
- User/global MCP configuration
- Provider defaults

Native terminal configuration should remain byte-for-byte unchanged before and after isolated jobs.

## Steps

['Verify unique runtime root per request', "Test concurrent jobs don't share or overwrite config", "Prove success cleanup only removes that request's ephemeral surface", "Prove failure/timeout quarantine doesn't touch native/harness/global/provider config", 'Byte-for-byte comparison of native terminal config before/after']

## Detailed Solution & Technical Design

### What "request-owned" means

Each isolated job gets its own ephemeral surface:

- **Unique runtime root**: a temporary directory for this request's artifacts, logs, and state
- **Unique MCP document**: the `mcp.json` or equivalent is per-request, not shared
- **No cross-contamination**: concurrent jobs don't share or overwrite launch configuration

### Success path — cleanup scope

On successful job completion:

1. Remove only that request's ephemeral runtime root and MCP document
2. Leave all other files untouched: native config, other jobs' config, user/global config, provider defaults
3. Verify no orphaned files remain from this request

### Failure/quarantine path — what must NOT be touched

When a job fails or times out:

1. Quarantine that request's ephemeral surface (don't delete — preserve for diagnostics)
2. **Do NOT touch**:
   - Native harness configuration (`~/.pi/mcp.json`, `~/.audiagentic/mcp.json`)
   - Another job's configuration or runtime root
   - User/global MCP configuration
   - Provider defaults (model catalogs, provider configurations)
3. Quarantined files should be cleaned up by a separate sweep mechanism (not the failing job itself)

### Test approach

```
1. Take byte-for-byte snapshot of native terminal config before test
2. Launch isolated job with its own runtime root and MCP document
3. Verify unique runtime root was created (different from native config path)
4. For concurrent jobs: launch two simultaneously, verify they use different roots
5. After job completes (success/failure/timeout):
   - Verify native config is byte-for-byte identical to before
   - Verify only this request's ephemeral files were modified/deleted
   - Verify other jobs' files are untouched
6. For timeout: verify quarantine doesn't affect anything outside this request
```
