# Register make_error codes and close the conformance scan gap

## Description

38 of 70 statically-resolvable `make_error(...)` error codes are absent from the error catalogue. Every one of them raises `ValueError: Error code '...' is not registered` instead of the intended AudiaGenticError whenever error resolutions are loaded — so the framework that exists to enforce arch-standards §4 is itself failing, silently, at 38 sites.

Found while closing AS71's first follow-up, which disproved its own premise. AS71 recorded that a "registered, perfectly descriptive `RES-PIACP-001`" was discarded by a bare `except Exception`. `RES-PIACP-001` is not registered; constructing it raises `ValueError`, and *that* was what the bare handler swallowed. The pi-acp-missing path has therefore never produced its intended error message.

The reason no guard caught this: `tests/unit/contracts/test_error_resolutions.py` scans for **quoted code literals** (`"RES-PIACP-001"`). `make_error` assembles the code from `prefix`/`component`/`number` kwargs, so no literal exists anywhere and the scan never sees it. The guard's own docstring claims to cover codes "carried as plain `error_code=` strings" — `make_error` is a third construction path nobody scanned.

## Steps

1. Register the 38 unregistered codes in the owning component's `error-resolutions.yaml`, with real resolution text (what the operator should actually do), not placeholders.
2. Extend `test_error_resolutions.py` with an **AST pass** over every `make_error` call site, resolving `prefix`/`component`/`number` constants into a code and asserting registration. This is the guard that would have caught all 38.
3. Decide the policy for the 22 call sites that compute `number=` dynamically (mostly `runtime/rig/errors.py`, `coding_lsp/lsp_bridge.py`, `language_registry.py`) — they derive the number from a caller-supplied value and cannot be resolved statically. Likely a declared per-component number range validated at registration, so a dynamic code is provably inside a registered block.
4. Fix the code-format validator: `CFG-session-001` and `VAL-release-001` show lowercase component segments pass validation. Decide whether to uppercase the codes or the validator, then enforce one.
5. Re-verify with the full unit suite.

## Files

## Validation

- A new conformance test fails on any unregistered `make_error` code; verified by temporarily adding one.
- The 38 known codes are registered and the new test passes.
- Each registered resolution is checked to actually describe a remedy — a catalogue full of restated codes satisfies the test while defeating its purpose.
- Constructing `RES-PIACP-001` succeeds and produces the intended message rather than `ValueError`.
- Full unit suite green.

## Effort & Risk

Low risk, moderate volume. Steps 1-2 are mechanical and independently verifiable. Step 3 is the only design decision and can be deferred without blocking 1-2. Main risk is registering 38 codes with hollow resolution text, which would pass the test while leaving operators no better off — the validation criteria call this out explicitly.

## Standards

- `arch-standards` §4 Public Contracts — error codes are a stable public contract; a code that cannot be constructed is a broken contract, and 38 of them are.
- `arch-standards` §7 Enforcement — "architecture rules must have proportionate automated checks". The existing check is disproportionate to the rule: it covers two of three construction paths and silently passes the third.
- `arch-standards` §3 Evidence-led scope — the 38/70 and 22-dynamic counts come from an AST sweep of every call site, not from sampling.

## Acceptance Criteria

- Every statically-resolvable `make_error` code is registered; the new AST-based
  conformance pass fails if one is not.
- `RES-PIACP-001` and the other pi/openhands/surface/release codes construct
  successfully and carry their intended messages instead of raising `ValueError`.
- The policy for dynamically-numbered `make_error` sites is decided and recorded,
  so the remaining 22 sites are either covered or explicitly exempted with a
  rationale.
- Error-code format validation is consistent: either all component segments are
  uppercase or the validator accepts lowercase deliberately, not by omission.
- Full unit suite green.
