# Implement the compute-resource taxonomy: declarations, ExecutionProfile v2, and free-instance dispatch

## Description

Complete the AS105-approved free-instance scheduler. Current code remains hybrid: resource gating is layered over profile lanes, semaphores, and queue limits; mixed candidates fail; source identity is not durable; recovery synthesizes profile identity. Passing targeted tests does not satisfy the architecture.

## Steps

1. Reopen scheduler/persistence slices and remove _lanes, _ProfileQueue, profile semaphores, max-concurrency/queue-size resolvers, compute_slots, and retired aliases.
2. Extract one pending authority with canonical project keys, per-project FIFO deques, fair project rotation, one lock/condition, and no I/O under lock.
3. Extract source-capacity ownership with reservations, declared/unbounded capacity, waiter cleanup, injected monotonic clock, and drain-before-swap reconfiguration.
4. Use one placement algorithm for mixed bounded/unbounded candidates.
5. Bind a source only at acquired dispatch; atomically persist resolved-instance-id/model-id before provider invocation.
6. Bump the durable schema; remove lane/queue/admission fields; fail closed on dispatched old records lacking source identity.
7. Add session turn callbacks so capacity is held only during compute.
8. Replace sleeps with fake clock/controlled dispatch and assert exact source IDs.
9. Sweep old names and make reporting project-scoped.
10. Gate SH11 soak/default flip on completion.

## Detailed Solution & Technical Design

Split queue/pending.py (PendingRequest, project deques, fair rotation, cancellation) and queue/capacity.py (immutable capacity snapshot and idempotent reservation token) from queue.py lifecycle orchestration. Cancellation atomically removes waiter indexes/timestamps. Persist source binding with compare-and-set immediately before dispatch. Recovery accepts pending unbound records or exact bound records; it never substitutes execution-profile ID. Session runtime acquires/releases a source reservation around each active turn, not keep-alive lifetime.

## Code Samples & Guidance

SourceReservation should carry request_id, canonical project_key, source_id, model_id, and capacity generation. Store mark_dispatched must compare expected pending state and persist source/model identity before dispatcher.dispatch(source_id=...). Event publication occurs outside the scheduler lock.

## Files

agents gateway queue.py; new queue pending/capacity modules; session runtime/dispatch seam; durable execution-record schema and store/recovery; execution-profile schemas/loaders; reporting; scheduler/persistence/session tests; SH11 soak.

## Validation

No legacy lane/semaphore/queue-limit names remain. Mixed sources use one scheduler. Same-model sources are proven by exact persisted IDs. Fake-time tests cover fairness, FIFO, cancellation, source loss, reconfiguration, and crash points. Old dispatched records without source fail with a registered error. Session capacity releases between turns. Run focused tests, schema validation, full agents suite, then SH11 soak.

## Effort & Risk

Large and highest architectural risk. Land reviewable slices but do not call a hybrid intermediate state complete.

## Standards

AS105 binding design; single authority; mechanism/policy separation; durable explicit contracts; fail-closed migration; no legacy by default; deterministic testing.

## Acceptance Criteria

- Capacity is declared once on resolved model sources and ExecutionProfile names acceptable instances without profile queue/concurrency policy.
- One scheduler handles bounded, unbounded, and mixed candidate sets; no profile lanes, semaphores, or queue-limit aliases remain.
- Requests bind only at dispatch and exact source/model identity is atomically durable before provider invocation.
- Shared sources cannot be oversubscribed across profiles/projects; project fairness and FIFO are deterministic.
- Cancellation, reconfiguration, crash recovery, and old-record failure leave no stale waiter or synthetic identity.
- Session reservations cover active compute turns, not idle keep-alive lifetime.
- Public reporting is project-scoped and the durable schema migration removes retired fields.
- Focused/full agents tests and SH11 soak are green without sleep-based correctness.

## Corrected 2026 08 05 The Project Dimension Fix Is Wrong

**Stop. This item's steps 1-3 describe adding a project dimension to the lane key. That is the wrong fix, and implementing it would make things worse.** Rewrite this item against AS105's decided taxonomy before starting.

**Why it is wrong:** underneath every execution profile is a model running on a GPU, and that GPU is genuinely shared by everything wanting that model. Two projects contending for the same hardware *should* share a lane — that is the resource telling the truth. Partitioning lanes by project would give each project its own `max-concurrency` over the *same* physical GPU, over-subscribing it by exactly the number of projects.

**The real defect is the inverse one.** `lane_key()` returns `(profile_id, generation, config_digest)` and **`model_id` is deliberately excluded** — it is a field on `ResolvedExecutionProfile` but never reaches the key. So two *differently-named* profiles pointing at the same model already get separate lanes with separate concurrency limits, and together over-subscribe the GPU today. The lane is keyed on configuration identity where it should be keyed on contention identity.

**What survives from this item, unchanged:**

- Steps 2 and 4: in-memory queue reads (`all_queue_depths()`, `queue_depth()`) report across all projects while disk reads are correctly project-scoped. That inconsistency is real and still needs fixing — as a *reporting* filter.
- Step 4's rule that cross-harness visibility within a project stays. Confirmed correct by the owner.
- Step 6: the README's "fine in practice (one project per process)" limitation is stale.
- The effort/risk note that `lane_key.public_id()` is persisted and logged, so recomposing it is a versioned contract change.

**What this item becomes**, once AS105 decides the taxonomy: key lanes by contended resource, and add **per-project scheduling fairness within a shared lane** so one project cannot starve another. Fairness, not partitioning — the resource stays shared because it genuinely is shared.

Retitling and resizing deferred until AS105 lands, so this item is not rewritten twice.

**Blast radius exceeded the steps text above, confirmed by tracing before coding (not guessed):** beyond `gateway/api.py` and `gateway/profiles.py`, two call sites read `profile.get("model_id")` directly by re-resolving the profile fresh, bypassing the record entirely -- `gateway/queue/dispatch.py` (`_extract_model_id`, `_build_packet_ctx`, `_dispatch_one_attempt`, `_try_profile_with_retries`, 5 read-sites) and `gateway/session/dispatch.py` (AS15 session open/continue/cancel/complete paths, 4 read-sites). `contracts/execution_context.py`'s `ManifestIdentity.__post_init__` hard-required a non-empty `model_id` at admission time -- structurally blocking "bind at dispatch, not admission" until relaxed (now `str | None`; `agent_runtime_digest` already covers the profile's `instances` content, so identity/fingerprint strength is unchanged). `agent_jobs/prompt_launch.py` had its own separate `_resolve_agent_provider_model` resolver with the same `model_id` contract (legacy launch path, pending its own rework per project memory -- fixed here since it would otherwise hard-crash, not deep-integrated).

**What was built:**

- `models/execution_profile.py`/`execution_profile_api.py`: `ExecutionProfile.instances: tuple[str, ...]` replaces `model_id: str`; `execution-profiles.yaml` bumps to `contract-version: v2`; every project's own file updated, including this repo's (`rig-tester` -> `instances: [ag-rig]`, `gpt-auto` -> `instances: [chatgpt]`).
- `gateway/instances.py` (new, small): `resolve_instance_facts(project_root, instance_ids)` -- the one seam agents uses to read `resource-id`/`concurrency`/`model-id` off `providers`' resolved model-sources view. **Graceful, not required:** an instance id that doesn't match a declared model-sources source is treated as a plain, ungated model-id (the exact pre-pivot `ExecutionProfile.model_id` behavior) rather than raising -- discovered necessary because `gpt-auto`'s `chatgpt` target is a browser/CDP session with no HTTP endpoint or vendor account, and can never be a model-sources source under that schema's `connector` enum.
- `gateway/profiles.py`: `ResolvedExecutionProfile.instances` replaces `model_id`/`max_concurrency`/`queue_max_size`/`admission_policy_digest` (all retired -- capacity is instance-scoped now, not profile-scoped). `GatewayExecutionLaneKey` class deleted outright. `InMemoryExecutionProfileRegistry`/`snapshot_from_resolved_profile`/`load_gateway_registry_from_config` updated to carry `instances` instead of capacity fields. `snapshot_from_record` implements AS105's decided old-record fail-mode: raises `VAL-EXP-006` (new code) when a record has shared-gateway snapshot identity (`gateway-profile-id` set) but no `resolved-instance-ids` -- a pre-pivot record -- rather than silently reconstructing a broken snapshot.
- `gateway/queue/queue.py` (the core rewrite): **hybrid gating, a deliberate scope decision not in the original design.** A profile's resolved instances are either fully gated (every instance's source declares `resource-id`+`concurrency`, dispatched via the new `_ResourceCapacityTracker`) or fully ungated (none do, exact legacy `params.max-concurrency` per-lane-semaphore behavior preserved byte-for-byte) -- a mixed set raises `VAL-AGW-024` (new code). This was necessary for backward compatibility: requiring every existing profile to first declare a model-sources entry would have been a disruptive breaking requirement for something that previously worked by typing a bare model-id string.
  - `_ResourceCapacityTracker`: one per `resource-id`, tracks `in_flight` per source-id and which source is currently `active`. `try_acquire` implements drain-before-swap (a different source may start only once the active one's `in_flight` reaches 0) plus a bounded anti-starvation guard (`_STARVATION_THRESHOLD_SECONDS = 30.0`; once a different-source request has waited past it, admission of more same-source work stops so `in_flight` can drain).
  - `_drain_gated`: candidates are the FIFO head of each lane (intra-lane order preserved), grouped by the resource they'd use, then by `project_key` (`str(project_root)`) for round-robin selection -- a shared resource cannot be monopolized by one project.
  - Binding happens only in `_drain_gated`/`_drain_ungated`, never at admission (`enqueue`); the bound instance's `model-id` is injected into the in-memory record dict passed to the runner (`resolved-model-id`), never persisted before dispatch -- the durable record's admission-time `resolved-model-id` stays `None` for a genuinely multi-instance profile, exactly as AS105 specified.
  - **AS15 session two-phase concurrency scope limitation (named, not a bug):** session requests still gate via the legacy per-lane semaphore (`pq.compute_slots`) regardless of gated/ungated, because reconciling AS15's blocking per-turn acquire with the fairness-selected non-blocking resource-tracker bind is a separate, larger design not attempted here. For a gated+session profile, the resource-tracker slot is held for the whole dispatch lifetime rather than released between turns (less optimal utilization, not incorrect).
- `agent-execution-record.schema.json`: additive `resolved-instance-ids` field (nullable array). `resolved-model-id`/`gateway-execution-lane-key`/`resolved-queue-limits`/`admission-policy-digest` stay in the schema (so an old value remains readable) but are always written `None` going forward.
- `resolved-execution-profile.schema.json`: `instances` (array, minItems 1) replaces `model-id`/`max-concurrency`/`queue-max-size`/`admission-policy-digest` in both `required` and `properties`.
- 4 new tests in `tests/unit/agents/test_agents_gateway_free_instance_dispatch.py` proving the actual load-bearing properties from this item's own `validation` section against gated `model-sources.yaml` sources: the m27b1/m27b2 scenario (same model, two GPUs, dispatch to whichever is free), over-subscription structurally impossible under concurrent load, overlapping profile instance-sets sharing one instance's capacity correctly, and the drain-before-swap anti-starvation guard actually firing (not just existing in code).
