# Implement the compute-resource taxonomy: declarations, ExecutionProfile v2, and free-instance dispatch

## Description

Implement AS105's decided design. Make execution capacity live on the Model Instance that is actually contended, not on the Execution Profile that merely selects it.

**Rewritten 2026-08-08 against AS105's finalized design**, which replaced this item's original two prior framings: not "add a project dimension to the lane key" (wrong — would over-subscribe shared hardware by construction), and not "key lanes by resource, add project fairness" (superseded — AS105's final design has no lanes at all).

**One atomic unit of work, confirmed by tracing the blast radius before writing steps:** `ExecutionProfile.instances` (replacing `model_id`) cannot be released on its own. `gateway/api.py:360`'s `resolved_model_id = resolved.model_id` flows directly into the durable request record and is what `providers_api.ProviderExecutionRequest` actually dispatches with. Nothing can turn `instances: [m27b1, m27b2]` into a concrete `model_id` string without the free-instance dispatch mechanism existing to resolve *which* instance answered. The schema change and the dispatch rewrite are one change, not two.

## Steps

### Slice 1 — declarations and loader (safe, self-contained, no existing-code changes)

1. `compute-resources.yaml` / `model-instances.yaml` at the user-global tier, with hand-written `validate_compute_resource`/`validate_model_instance` Python validators (AS105's confirmed convention — not JSON Schema; see AS105's `validation_2026_08_08_schema_registration_mechanism`).
2. A small loader module calling `foundation.config.layers.load_layered_config` directly (AS105's confirmed convention — there is no component-descriptor `files:` mechanism for the user-global tier; see AS105's `correction_2026_08_08_user_global_declaration_mechanism`). Resolve with `project_root=None` so the project tier is never consulted for these two namespaces (AS105's closed hazard).
3. CRUD API mirroring `execution_profile_api.py`'s shape, management MCP tools mirroring the AS82/AS83 pattern.

### Slice 2 — ExecutionProfile v2 (breaking, versioned, atomic with Slice 3)

4. `ExecutionProfile.model_id: str` → `instances: tuple[str, ...]`. Remove `params.max-concurrency`/`params.queue-max-size` outright — no alias, no dual read (no-legacy, AS105's `migration_stance_no_legacy`). `execution-profiles.yaml` bumps to `contract-version: v2`.
5. Update every real call site (confirmed by direct grep before this item started: `gateway/api.py:360`, `gateway/profiles.py:145,328,472`, `models/execution_profile_api.py:211,235` — 6 sites, not the whole tree) plus every project's own `.audiagentic/config/execution-profiles.yaml`, including this repo's own (`rig-tester`, `gpt-auto`).

### Slice 3 — free-instance dispatch (the correctness-critical rewrite, same atomic change as Slice 2)

6. Replace `GatewayExecutionLaneKey`/per-lane semaphores in `queue/queue.py` with `InstanceCapacityTracker` (one per Model Instance, tracking `in_flight` per `servable_models` entry and `loaded_model`) plus one ordered pending queue carrying each request's resolved compatible-instance set.
7. Bind a request to an instance only at dispatch (when that instance has spare capacity for the request's model), never at admission.
8. Per-project round-robin fairness when multiple pending requests are compatible with a freed instance.
9. The drain-before-swap guard: an instance may not switch `loaded_model` while `in_flight > 0`; add the bounded anti-starvation guard AS105 requires (stop admitting more same-model work once a different-model request has waited past a threshold).
10. Migrate every real `lane_key`/`GatewayExecutionLaneKey` reference (`queue/queue.py:380,402,571` and its schema/record fields) to the resolved `instance_id`, recorded post-dispatch. Old persisted records fail with a registered error on read, never silently misparsed (AS105's decided fail-mode).

### Slice 4 — reporting scope (independent, safe, can land any time)

11. `all_queue_depths()`/`queue_depth()` (`queue/queue.py:903,861`) and `gateway_overview()` (`gateway/api.py:806`) currently mix project-scoped disk reads with unscoped in-memory queue state. Scope both to the requesting project — a pure reporting fix, independent of Slices 2–3.
12. Cross-harness visibility **within** a project stays unfiltered by caller — confirmed correct by the owner; do not narrow it.
13. Update the README's "Not project-scoped ... fine in practice (one project per process)" entry, stale on both counts under a shared multi-project gateway.

### Sequencing

Coordinate with `shared-gateway/SH11` per AS105's own note — SH11 is already sweeping every gateway consumer for the declarative-implementation cutover; Slices 2–3 touch the same consumer surface. Sequence together, not as two separate sweeps.

## Detailed Solution & Technical Design

**What is already correct — do not change:** everything read from disk is already project-scoped. `agents_paths.gateway_root(project_root)` roots the whole tree per project; `list_execution_requests`, `list_execution_sessions`, and `gateway_overview`'s record reads all take and honour `project_root`. Only the reporting layer (Slice 4) and the capacity model itself (Slices 2–3) are not.

**Why the old "add project dimension to lane key" framing was wrong, restated from AS105:** the GPU underneath an execution profile is genuinely shared across projects — partitioning would over-subscribe it by exactly the number of projects contending. The real defect was the inverse: `lane_key()` excludes `model_id`, so *differently-named* profiles on the *same* model already get separate lanes and separate concurrency limits today, over-subscribing the GPU without any project involved. AS105's free-instance dispatch removes the concept of a per-profile concurrency limit entirely rather than patching its key.

## Validation

**Slice 1:** declarations load, validate, and CRUD correctly; `project_root=None` resolution confirmed not to consult the project tier.

**Slices 2–3 (the load-bearing proofs):**
- The same underlying model loaded on two instances: a profile naming both dispatches to whichever has spare capacity, proven with a fake clock/fake instances — no real GPU needed.
- Over-subscription is structurally impossible: a request never dispatches to an instance without measured spare capacity, asserted directly under concurrent load.
- Two profiles with overlapping instance sets share the shared instance's capacity correctly — asserted, not just "both succeed."
- Drain-before-swap: a swapping instance under steady same-model load eventually admits a different-model request via the bounded guard, not never.
- Old persisted records (pre-migration `lane_key`/`max-concurrency` shape) fail with a registered error on read, not a misparse.
- `python -m pytest tests/unit/agents` green, including the existing SH07 crash-recovery suite — this is the regression risk this item's own effort_risk section names.

**Slice 4:**
- Two projects each defining a same-named profile: `all_queue_depths()`/`gateway_overview()` report only the requesting project's state.
- A harness can still enumerate other harnesses' requests/queue state within its own project — asserted, so a later change does not silently narrow it.

## Acceptance Criteria

- A decided Model Instance/Compute Resource declaration exists, loaded from the user-global config tier, validated by hand-written Python validators.
- `ExecutionProfile` names a set of acceptable instances; `max-concurrency`/`queue-max-size` no longer exist on it.
- Concurrent projects on one shared gateway cannot over-subscribe a shared instance, whether contending through the same profile or different ones — the actual defect this item and AS105 exist to fix.
- A request binds to an instance only at dispatch, never at admission; over-subscription is structurally impossible, not policy-limited.
- Drain-before-swap is enforced, with a bounded anti-starvation guard, not a general scheduler.
- Per-project fairness at the dispatch-selection step, so one project cannot starve another out of shared instances.
- In-memory queue reporting (`all_queue_depths`, `gateway_overview`) is project-scoped, consistent with the already-project-scoped disk reads.
- Cross-harness visibility **within** a project is preserved and asserted — harnesses are peers, not isolated from one another.
- Every persisted/schema-backed change (`lane_key` retirement, `ExecutionProfile` v2, record schema) is an explicit versioned migration with a full-tree reference sweep, not a silent reshape.
- The README's project-scoping limitation reflects the shared multi-project reality.
- The existing SH07 crash-recovery and stale-generation-rejection test suites stay green — this migration must not silently weaken guarantees that predate it.

## Corrected 2026 08 05 The Project Dimension Fix Is Wrong

**Stop. This item's steps 1-3 describe adding a project dimension to the lane key. That is the wrong fix, and implementing it would make things worse.** Rewrite this item against AS105's decided taxonomy before starting.

**Why it is wrong:** underneath every execution profile is a model running on a GPU, and that GPU is genuinely shared by everything wanting that model. Two projects contending for the same hardware *should* share a lane — that is the resource telling the truth. Partitioning lanes by project would give each project its own `max-concurrency` over the *same* physical GPU, over-subscribing it by exactly the number of projects.

**The real defect is the inverse one.** `lane_key()` returns `(profile_id, generation, config_digest)` and **`model_id` is deliberately excluded** — it is a field on `ResolvedExecutionProfile` but never reaches the key. So two *differently-named* profiles pointing at the same model already get separate lanes with separate concurrency limits, and together over-subscribe the GPU today. The lane is keyed on configuration identity where it should be keyed on contention identity.

**What survives from this item, unchanged:**

- Steps 2 and 4: in-memory queue reads (`all_queue_depths()`, `queue_depth()`) report across all projects while disk reads are correctly project-scoped. That inconsistency is real and still needs fixing — as a *reporting* filter.
- Step 4's rule that cross-harness visibility within a project stays. Confirmed correct by the owner.
- Step 6: the README's "fine in practice (one project per process)" limitation is stale.
- The effort/risk note that `lane_key.public_id()` is persisted and logged, so recomposing it is a versioned contract change.

**What this item becomes**, once AS105 decides the taxonomy: key lanes by contended resource, and add **per-project scheduling fairness within a shared lane** so one project cannot starve another. Fairness, not partitioning — the resource stays shared because it genuinely is shared.

Retitling and resizing deferred until AS105 lands, so this item is not rewritten twice.
