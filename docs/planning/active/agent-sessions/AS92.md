# Canonical request status projection

## Description

Finish canonical provider-neutral lifecycle projection and its public contract. Mapping mostly exists, but rejected outcomes, schema ownership, duplicated attachment/time logic, and unrestricted metadata remain unresolved.

**RV936 assessment (gpt-auto review validated against tree):**

The item's "only schema/version/tests remain" assumption is factually incorrect. Steps 1–3 and cross-path agent-status wiring are still real implementation work.

## Steps

1. Map durable rejected to AgentOutcome.REJECTED with exhaustive tests.
2. Replace local _now_iso with foundation.time.now_iso_z.
3. Consolidate session lookup and status attachment into one agents gateway function used by submit/get/wait/list.
4. Wire async submit and list through the same agent-status projector (currently only blocking submit, get, and wait include it).
5. Add an agents-owned public request/status response schema at response version 3; do not put derived agent-status in the private durable-record schema.
6. Define status snapshot fields explicitly.
7. Omit unrestricted metadata or route it through AS102's single allowlist.
8. Add tests proving all response paths share the projector and provider-native states never escape.

## Detailed Solution & Technical Design

Keep durable record, ephemeral runtime facts, and derived public response separate. One project_request_response function obtains runtime facts once, invokes the pure status projector, and applies AS102 metadata sanitization. The agents-owned schema references a reusable status definition and excludes raw exceptions, provider states, lane fields, and free-form metadata.

**Already done, do not rebuild:**

- `components/agents/status/status_projection.py::snapshot_for_request(record, *, decision=None)` is fully implemented with every mapping this item lists: `_DURABLE_OUTCOME_MAP` covers completed/failed/cancelled/interrupted -> TERMINAL, queued -> PENDING, the decision path delegates to `snapshot_from_decision`, and the no-evidence fallback is UNKNOWN. Durable-terminal-wins is implemented as case 1, ahead of the decision branch.
- `snapshot_to_mapping()` in the same module serializes the snapshot for the wire.
- **It is already wired.** `gateway/api.py:234` and `gateway/api.py:532` both set `result["agent-status"] = snapshot_to_mapping(snapshot_for_request(...))`. The field is on responses today.
- `tests/unit/agents/test_agents_status_projection.py` has 21 tests covering every mapping, both interrupted invariants (`test_interrupted_is_not_cancelled`, `test_interrupted_is_not_failed`), and durable-beats-decision (`test_completed_ignores_contradictory_decision`, `test_interrupted_ignores_cancelled_decision`).

**Not ambiguous — deliberate, and covered by a test. Do not "fix" it:** a record in durable state `running` with no live decision projects to `UNKNOWN`, not `ACTIVE`, even though `AgentLifecycle.ACTIVE` exists. `test_running_no_decision_unknown` and `test_dispatching_no_decision_unknown` pin this. It is the conservative reading of "no durable terminal fact and no decision -> unknown" and is intentional.

**Step 4 is largely already satisfied.** A scan for independent status inference found only internal control flow — `gateway/api.py` list filtering, `queue/queue.py` transition checks, `queue/recovery.py` reconciliation, `session/bindings.py` index reads. Those read durable `state` for dispatch and recovery decisions, which is correct; none of them is a second *public status* projector. No consumer migration appears to be outstanding, but confirm before closing.

**The one real remaining gap, and the actual scope of this item:** `agent-status` is written onto responses but is **declared in no schema**. `grep -rl agent-status src/audiagentic/foundation/contracts/schemas/` returns nothing, and `agent-execution-record.schema.json` still pins `contract-version: "v2"` with no `agent-status` property. So the field exists in practice as an undeclared, unversioned addition to a public contract — exactly what §4 requires to be explicit. Remaining work is: declare the field in the appropriate response schema, increment the contract version explicitly, and add the serialization/compatibility tests.
