# Replace the gateway work API with AgentTask

## Goal

Make a small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, store, queue, cancellation path or recovery system.

## Service boundary

Expose one application service/port, such as `AgentTaskService`, with only the operations currently needed:

- submit;
- get status/result;
- cancel;
- optionally read existing events through AS57.

The service depends on existing gateway/request/session services through injected interfaces or explicit dependencies. ACP, A2A, MCP and CLI adapters call this service rather than stores or providers directly.

## Initial mapping

- one AgentTask maps to one existing gateway request and one session turn;
- task, request and turn IDs may remain distinct fields but need no new persistence model initially;
- existing request/queue/turn storage remains the implementation beneath AgentTask.

## Work

1. Characterize current submission, request, queue, dispatch and session-turn paths.
2. Add the small task contract and application service over those paths.
3. Select an Agent Definition before admission.
4. Update all agent-work callers to use `AgentTaskService` in the same change.
5. Delete `submit_llm_request` and other superseded agent-work APIs, handlers, schemas, fixtures and tests.
6. Reuse existing cancellation, status, output and recovery owners.
7. Keep raw model-completion APIs separate only if they are genuinely model APIs rather than agent-work aliases.
8. Keep protocol types outside the task service.
9. Add architecture/search checks proving no second agent-work entry path remains.

## Do not add

- a multi-turn task coordinator;
- task workflows;
- artifact stores beyond existing needs;
- task snapshots or revisions;
- provider or protocol branching in the service;
- global service lookup;
- compatibility adapters, aliases, legacy handlers or dual submission paths.

## Reassess before AS64

Prove the one-task/one-turn mapping works for current gateway use and local delegation. Add more only when an actual A2A or workflow case cannot fit safely.

## Acceptance criteria

- One task application service fronts existing machinery.
- All agent-work callers use it directly.
- It can be injected/faked for protocol adapters and tests.
- No new durable coordinator exists.
- Superseded LLM-request agent APIs and compatibility paths are deleted.
