# Replace the gateway agent-work API with AgentTask

## Goal

Make one small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, ID, store, queue, cancellation path or recovery system.

## Existing machinery to retain

Refactor in place:

- `agents_gateway_api.py` submission/admission/status/cancel orchestration;
- `agents_gateway_client.py` public client boundary;
- request store, queue, dispatch, progress and recovery;
- `SubmissionEnvelope` and `ExecutionManifest`;
- session request/turn/runtime stores and controls;
- gateway MCP adapters.

## Application boundary

Expose only current operations:

- submit;
- status/result;
- transport-bounded wait;
- cancel;
- operator list/overview;
- existing session open/continue/close;
- existing output/event reads through AS31/AS57.

ACP, A2A, CLI, management MCP, runtime gateway MCP/extensions and internal workflows call scoped adapters over this same API.

The existing durable request ID is the AgentTask ID initially. One AgentTask maps to one existing request and one session turn. `ExecutionManifest` remains the request-level resolved execution record.

## Gateway projections

### Operator projection

May expose global list/overview and operator-authorized controls.

### Harness runtime projection

May expose only permitted task submission/delegation, owned status/result/wait/cancel, agent/skill description and authorized continuation.

Use one scoped MCP module or two thin modules according to the existing descriptor/auth model. Do not duplicate application logic.

## Composition and legacy boundary

Runtime composition builds the touched AgentTask/gateway services and injects them into `runtime.application-host` and protocol adapters.

The migrated graph should include only dependencies justified by current code, likely:

- Execution Profile and Agent Definition resolvers;
- queue manager;
- request/session stores used by the application API;
- dispatcher/provider boundary;
- existing authorization/audit dependencies;
- session runtime/control dependencies actually constructed by the touched startup path.

Do not create a configured binding for internal helpers with one implementation.

### Legacy exemption interaction

Untouched gateway modules may remain behind the AS59 application-host exemption. Any module materially refactored by AS63 leaves the exemption:

- `_QUEUE_MANAGER` and touched global service selectors are removed;
- touched code has no fallback constructor or global lookup;
- the application host receives the composed AgentTask client/service and may not rebuild it;
- function-local imports may remain only for stateless helpers or untouched legacy paths, not as service lookup for migrated dependencies;
- the legacy host is not exposed as an AgentTask dependency or forwarding façade.

Do not broaden AS63 into a complete repository-wide gateway rewrite.

## Work

1. Characterize every submit/status/wait/cancel/run/list/session caller and transport.
2. Rename/generalize the existing public contract and client in place.
3. Resolve an Agent Definition before admission.
4. Reuse `SubmissionEnvelope` and `ExecutionManifest`; rename only fields whose meaning changes.
5. Remove direct provider/model execution from AgentTask or retain it as a separately named operator/raw-execution API.
6. Update all callers, MCP projections, schemas, descriptors, tests and docs directly.
7. Delete superseded `submit_llm_request`, `agent_llm_*` and related paths after callers migrate.
8. Reuse current cancellation, output, idempotency, redaction and recovery owners.
9. Compose and inject the touched stateful dependencies.
10. Remove touched global lookup/fallback construction.
11. Update the AS59 legacy exemption list to remove migrated gateway paths.
12. Add architecture/search tests proving one agent-work path, no container lookup in core services and no legacy fallback for touched services.

## Do not add

- a second task service;
- workflow/artifact machinery;
- task snapshots, revisions or new IDs;
- provider/protocol branching in the application API;
- request/session DI scopes;
- a giant service context object;
- compatibility adapters, aliases, legacy handlers or dual routes.

## Validation

Retain and extend tests for:

- submit/status/wait/cancel and MCP wait caps;
- durable request ID continuity;
- redaction, digesting, idempotency and manifest behavior;
- queue admission, concurrency, stale-profile rejection and recovery;
- persistent session FIFO, close and timeout;
- operator/runtime projection authorization;
- fake composition bindings without global mutation;
- startup/shutdown of owned gateway resources;
- direct provider/model bypass removed or isolated;
- application host not reconstructing migrated AgentTask dependencies.

## Reassess before AS64

Prove current gateway use and local delegation work through the existing request/turn lifecycle. Add no new task machinery or DI scope unless a later protocol proves the current mapping insufficient.

## Acceptance criteria

- One application API owns agent-work submission/status/cancel.
- Existing durable request/session machinery remains authoritative.
- Operator and harness runtime surfaces are scoped adapters over one client.
- Touched services are config-selected, composed and injected with no legacy fallback.
- Untouched gateway code remains only behind the bounded application-host exemption.
- Core services remain plain Python and container-independent.
- No compatibility or duplicate task path remains.
