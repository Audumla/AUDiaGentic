# Replace the gateway agent-work API with AgentTask

## Goal

Make a small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, identity, store, queue, cancellation path or recovery system.

## Current code to migrate

`agents_gateway_api.py::submit_llm_request` currently owns too much orchestration directly: envelope creation, profile resolution, shared-registry lookup, provider isolation, runtime digest, execution manifest construction, request admission, queue submission and session options. It also relies on a module-level queue manager and many local imports.

AS63 must not merely rename that function. It should leave the existing durable owners in place while extracting one framework-neutral application boundary whose dependencies are supplied explicitly by the gateway host/composition root.

## Boundary

Expose one application API with only currently required operations:

- submit;
- get status/result;
- cancel;
- read existing output/events through AS31/AS57 where needed.

The implementation delegates to the existing request store, queue, dispatch, session, profile-resolution and execution-context owners. ACP, A2A, MCP, CLI and internal workflows call this API rather than importing those internals.

Do not invent interfaces for pure helpers. Use explicit dependencies only for stateful owners and external/platform boundaries.

## Initial mapping

- the existing durable request ID is the AgentTask ID in the first implementation;
- one AgentTask maps to one existing request and one session turn;
- `SubmissionEnvelope` and `ExecutionManifest` are migrated/renamed only as needed; their validation, redaction and context-fingerprint behavior remains authoritative;
- existing request, queue, status, output, cancellation and recovery records remain authoritative;
- no separate task binding or persistence is added.

## Work

1. Characterize the current submission path and list each existing owner it invokes.
2. Define the minimal AgentTask request/result contract from the current validated envelope rather than adding speculative fields.
3. Resolve an Agent Definition and Execution Profile through their public boundaries before admission.
4. Move orchestration behind one application API while reusing existing stores, queue manager, dispatch and session runtime.
5. Supply queue/profile/session/dispatch dependencies from the gateway host/composition root; remove module-global lookup owned by this path where practical.
6. Update every agent-work caller in the same change.
7. Delete `submit_llm_request` and other superseded agent-work APIs, schemas, handlers, fixtures and tests.
8. Keep raw model-completion APIs only when they are demonstrably separate model APIs.
9. Add architecture/search checks proving protocol adapters do not import stores, queues, dispatch or provider internals and no second agent-work path remains.

## Do not add

- a new task service beside the existing gateway application layer when refactoring that layer is sufficient;
- a multi-turn task coordinator;
- task workflows or artifact stores;
- task snapshots, revisions or new IDs;
- provider/protocol branching;
- service locators, compatibility adapters, aliases, legacy handlers or dual routes.

## Reassess before AS64

Prove the API supports current gateway use, persistent sessions and local delegation with the existing request/turn lifecycle. Confirm the gateway host can construct it with fakes for profile resolution, queueing, dispatch and session handling without module-global mutation.

## Acceptance criteria

- One application API owns agent-work submission/status/cancel.
- Existing durable request identity and machinery remain authoritative.
- `SubmissionEnvelope`/`ExecutionManifest` safety behavior is preserved without a duplicate contract hierarchy.
- Stateful dependencies are explicit and composition-root wired.
- All callers use the new contract directly.
- No compatibility or duplicate task path remains.
