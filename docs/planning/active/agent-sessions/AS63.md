# Generalize gateway requests into canonical agent tasks

## Goal

Introduce a provider- and protocol-neutral `AgentTask` submission/result contract above the existing durable gateway request and Interaction Session turn machinery.

Preserve current request storage, queueing, dispatch, idempotency, recovery and session behavior during the first slice. Do not create a second task engine or multi-turn workflow coordinator speculatively.

## Execution prerequisite

AS59 Gate 0, AS60/R1, AS61/R2 and AS62/R3 must be closed before implementation begins. The principal session/output/read/control plans must contain their AS59 local alignment blocks.

## Domain distinction

- AgentTask — caller-visible unit of useful work.
- Interaction Session — persistent two-way context and provider binding.
- Turn — one execution/prompt within an Interaction Session.
- Existing gateway request record — initial durable implementation of one task attempt/turn until later evidence requires separation.

Task ID, request ID and turn ID remain distinct concepts even if initially mapped one-to-one.

## Contract

Define closed, versioned forms for:

- `AgentTaskSubmission`;
- `AgentTaskRef` and task status projection;
- messages/parts sufficient for text first, with typed artifact references rather than arbitrary payloads;
- Agent Definition ID;
- optional Interaction Session ID and continuation intent;
- caller/correlation/idempotency identity;
- execution deadline and bounded metadata;
- result containing final output/artifact references and canonical terminal state.

Do not expose provider/model selection in ordinary AgentTask submission. An explicit operator compatibility path may select an Execution Profile directly during migration.

## Compatibility

Keep `submit_llm_request()` and existing MCP/application calls as compatibility adapters:

```text
submit_llm_request -> AgentTaskSubmission -> existing queue/dispatch/session path
```

All new internal implementation should enter through `submit_agent_task()` after migration. Compatibility adapters must not maintain separate validation, persistence or dispatch logic.

## Steps

1. Consume completed AS62/R3 findings from AS59.
2. Characterize current `SubmissionEnvelope`, execution manifest, request record, queue item, dispatch attempt, session request/turn mapping and public APIs.
3. Add the canonical task contract and adapter into the existing submission pipeline.
4. Resolve `AgentDefinitionSnapshot` before admission and persist its immutable identity/digests through the existing execution manifest/request record.
5. Map a task with an optional session ID to exactly one current turn in the first slice.
6. Preserve AS30/AS47 continuation checks and AS49 explicit resume semantics.
7. Make AS31 final output and AS57 status/output reads project cleanly into task status/result.
8. Add task-level cancellation as a mapping to AS58/current request-turn control path; do not add a second cancellation authority.
9. Rename public/internal LLM-centric types where they represent agent work, but retain raw model-completion APIs separately if they genuinely exist.
10. Add architecture gates preventing A2A/ACP protocol types in the task domain.
11. Update AS59 with R4 findings and any necessary amendments before AS64/AS65/AS66 continue.

## Reassessment gate R4

After proving one task maps to one current turn:

- assess concrete A2A and internal delegation cases requiring `input-required`, multiple turns, detached continuation or multiple artifacts;
- decide whether the existing durable request record can remain task authority or whether a later dedicated task coordinator is justified;
- do not add a multi-turn task state machine unless at least one end-to-end consumer cannot be represented safely by task-to-turn mapping;
- record identity and persistence consequences before AS65/AS66.

Record the R4 decision in AS59 before later protocol work starts.

## Validation

- existing submit/run/status/wait/cancel behavior through compatibility adapters;
- task-to-request/turn identity mapping and redaction;
- Agent Definition resolution failure creates no durable request/process;
- exact session continuation and context mismatch behavior;
- idempotent duplicate task submission;
- cross-project/session authorization;
- task reads create no runtime or lock side effect;
- no duplicate queue, store, lifecycle or cancellation implementation.

## Acceptance criteria

- `AgentTask` is the canonical logical-work request boundary.
- Existing gateway request/session machinery is reused rather than replaced.
- `submit_llm_request` is a bounded compatibility façade.
- Task, session and turn identities are explicit even where initially one-to-one.
- R4 is recorded in AS59 before later protocol work proceeds.
