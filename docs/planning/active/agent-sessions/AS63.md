# Replace the gateway agent-work API with AgentTask

## Goal

Make a small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, identity, store, queue, cancellation path or recovery system.

## Current code to retain and refactor

The existing gateway already has the needed durable machinery:

- `agents_gateway_api.py`: submission/admission/status/cancel orchestration;
- `agents_gateway_client.py`: client boundary used by transport adapters;
- request store, queue manager, dispatch, progress and recovery modules;
- `SubmissionEnvelope` and `ExecutionManifest` execution-context contracts;
- session request/turn/runtime stores and controls;
- `agents_gateway_mcp.py`: AUDiaGentic operational MCP over the gateway client.

Refactor these in place. Do not place a new task service beside them.

## Boundary

Expose one framework-neutral application API/client with only currently required operations:

- submit;
- get status/result;
- wait where the caller transport supports it;
- cancel;
- list/overview for operator surfaces;
- session open/continue/close through the existing session authority;
- read existing output/events through AS31/AS57 where needed.

ACP, A2A, management MCP, CLI and internal workflows call this API. The API depends explicitly on existing gateway/request/session owners and never imports protocol or provider internals.

## Identity and mapping

- the existing durable request ID is the AgentTask ID initially;
- one AgentTask maps to one existing request and one session turn;
- existing request, queue, status, output, cancellation and recovery records remain authoritative;
- `ExecutionManifest` remains the resolved execution record; do not add AgentTask snapshots or copied definitions;
- no separate task binding or persistence is added.

## Management MCP disposition

`agents_gateway_mcp.py` remains an AUDiaGentic operational/management adapter:

- rename tools and metadata from `agent_llm_*` to AgentTask/session terminology where the old names are superseded;
- continue calling the gateway client/public API rather than stores, queues or dispatch directly;
- keep transport-only wait caps in the MCP adapter;
- declare `propagate: audiagentic` only;
- add a descriptor test proving it cannot enter provider runtime MCP projection.

Do not reuse this server as AS66 runtime delegation. A harness receiving submit/list/overview/session-admin tools could recursively dispatch into the gateway and gains operator scope it should not have.

## Application wiring

The current module-level queue manager, gateway profile selector and function-local service imports are composition concerns. While refactoring the application API:

- construct the queue manager, Execution Profile resolver, dispatch dependency, stores and session dependencies at the gateway service host/composition root;
- pass them explicitly to the application service/client implementation;
- keep protocol adapters dependent on the public client/port;
- do not introduce a DI container or service locator;
- do not refactor unrelated modules solely for stylistic consistency.

## Work

1. Characterize every submit/status/wait/cancel/run/list/session caller and transport.
2. Rename/generalize the existing public agent-work contract and client in place.
3. Resolve an Agent Definition before admission.
4. Reuse `SubmissionEnvelope`/`ExecutionManifest`, renaming only fields that genuinely change domain meaning.
5. Decide direct provider/model execution explicitly: remove it from AgentTask or retain it as a separate operator/raw-execution API. It must not bypass Agent Definition selection silently.
6. Update every agent-work caller, management tool, schema, descriptor, test and document in the same change.
7. Delete `submit_llm_request`, `agent_llm_*` and other superseded agent-work APIs after callers migrate.
8. Reuse existing cancellation, status, output, idempotency, redaction and recovery owners.
9. Replace touched module-global dependency lookup with explicit composition-root wiring.
10. Add architecture/search checks proving no second agent-work entry path and no provider-propagated gateway management server remain.

## Do not add

- a new task service beside the existing gateway application API when refactoring that API is sufficient;
- a multi-turn task coordinator;
- task workflows or artifact stores;
- task snapshots, revisions or new IDs;
- provider/protocol branching in the application API;
- service locators, compatibility adapters, aliases, legacy handlers or dual routes;
- provider access to gateway list/overview/config/session-administration tools.

## Validation

Retain and extend tests for:

- async submit/status/wait/cancel and blocking transport cap behavior;
- durable request ID continuity as AgentTask ID;
- prompt redaction, digesting, idempotency and execution manifest behavior;
- queue admission, concurrency, stale-profile rejection and recovery;
- persistent session FIFO, close and timeout behavior;
- management MCP calls only through the public client;
- descriptor propagation excludes providers;
- direct provider/model bypass is removed or isolated behind its separately named operator API;
- fake injected dependencies can exercise the application boundary without global registry/queue mutation.

## Reassess before AS64

Prove the refactored API supports current gateway use and local delegation with the existing request/turn lifecycle. Add new task machinery only if a demonstrated later protocol cannot map safely to it.

## Acceptance criteria

- One application API owns agent-work submission/status/cancel.
- Existing durable request identity and machinery remain authoritative.
- `ExecutionManifest` remains the only request-level resolved execution record.
- The operational MCP remains management-scoped and thin.
- All callers use the new contract directly.
- Stateful dependencies are composition-root supplied, with no new globals or container.
- No compatibility or duplicate task path remains.
