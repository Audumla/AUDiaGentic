# Replace the gateway agent-work API with AgentTask

## Goal

Make a small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, identity, store, queue, cancellation path or recovery system.

## Boundary

Expose one framework-neutral application API with only currently required operations:

- submit;
- get status/result;
- cancel;
- read existing output/events through AS31/AS57 where needed.

ACP, A2A, MCP, CLI and internal workflows call this API. The API depends explicitly on existing gateway/request/session owners and never imports protocol or provider internals.

## Initial mapping

- the existing durable request ID is the AgentTask ID in the first implementation;
- one AgentTask maps to one existing request and one session turn;
- existing request, queue, status, output, cancellation and recovery records remain authoritative;
- no separate task binding or persistence is added.

## Work

1. Characterize current submission, request, queue, dispatch and session-turn paths.
2. Rename/generalize the existing public agent-work contract and API in place.
3. Resolve an Agent Definition before admission.
4. Update every agent-work caller in the same change.
5. Delete `submit_llm_request` and other superseded agent-work APIs, schemas, handlers, fixtures and tests.
6. Reuse existing cancellation, status, output and recovery owners.
7. Keep raw model-completion APIs only when they are demonstrably separate model APIs.
8. Add architecture/search checks proving no second agent-work entry path remains.

## Do not add

- a new task service beside the existing gateway application API when renaming/extending that API is sufficient;
- a multi-turn task coordinator;
- task workflows or artifact stores;
- task snapshots, revisions or new IDs;
- provider/protocol branching;
- service locators, compatibility adapters, aliases, legacy handlers or dual routes.

## Reassess before AS64

Prove the renamed API supports current gateway use and local delegation with the existing request/turn lifecycle. Add new task machinery only if a demonstrated later protocol cannot map safely to it.

## Acceptance criteria

- One application API owns agent-work submission/status/cancel.
- Existing durable request identity and machinery remain authoritative.
- All callers use the new contract directly.
- The API is DI-ready and protocol neutral.
- No compatibility or duplicate task path remains.
