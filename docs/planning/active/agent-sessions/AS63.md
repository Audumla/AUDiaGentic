# Replace the gateway agent-work API with AgentTask

## Goal

Make a small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, identity, store, queue, cancellation path or recovery system.

## Current code to retain and refactor

The existing gateway already has the needed durable machinery:

- `agents_gateway_api.py`: submission/admission/status/cancel orchestration;
- `agents_gateway_client.py`: client boundary used by transport adapters;
- request store, queue manager, dispatch, progress and recovery modules;
- `SubmissionEnvelope` and `ExecutionManifest` execution-context contracts;
- session request/turn/runtime stores and controls;
- `agents_gateway_mcp.py`: current MCP projection over the gateway client.

Refactor these in place. Do not place a new task service beside them.

## Boundary

Expose one framework-neutral application API/client with the existing required operations:

- submit;
- get status/result;
- wait where the caller transport supports it;
- cancel;
- session open/continue/close through the existing session authority;
- read existing output/events through AS31/AS57;
- list/overview only for authorized operator consumers.

ACP, A2A, MCP, CLI, harness delegation and internal workflows call this API through appropriately scoped adapters. The API depends explicitly on existing gateway/request/session owners and never imports protocol or provider internals.

## Identity and mapping

- the existing durable request ID is the AgentTask ID initially;
- one AgentTask maps to one existing request and one session turn;
- existing request, queue, status, output, cancellation and recovery records remain authoritative;
- `ExecutionManifest` remains the resolved execution record;
- no separate task binding or persistence is added.

## Gateway MCP projections

Harnesses need a runtime path to submit and control delegated AgentTasks. Do not remove provider access wholesale.

Define two operation scopes over the same gateway client/application API:

### Runtime scope

Available to an authorized running Agent Definition/session:

- submit/delegate to permitted agents or skills;
- status/result/wait/cancel for tasks owned by or shared with the caller;
- authorized session continuation where required.

The runtime caller must not see or control unrelated tasks/sessions.

### Operator scope

Available to AUDiaGentic CLI/operator surfaces:

- global request/session listing;
- gateway overview and diagnostics;
- broader administrative close/control where authorized;
- future reload/configuration operations.

Use one MCP module with proven consumer-specific tool projection only if the existing descriptor/materialization model supports it clearly. Otherwise split into two thin MCP adapters over the same gateway client. Do not duplicate validation, dispatch or persistence.

The current `agents_gateway_mcp.py` comment and descriptor propagation disagree. Resolve this by characterizing intended consumers and tests. Neither the comment nor descriptor is automatically authoritative.

## Application wiring

While refactoring the application API:

- construct the queue manager, Execution Profile resolver, dispatch dependency, stores and session dependencies at the gateway service host/composition root;
- pass them explicitly to the application service/client implementation;
- keep protocol adapters dependent on the public client/port;
- do not introduce a DI container or service locator;
- do not refactor unrelated modules solely for stylistic consistency.

## Work

1. Characterize every submit/status/wait/cancel/run/list/session caller and transport, including provider/harness consumers.
2. Rename/generalize the existing public agent-work contract and client in place.
3. Resolve an Agent Definition before ordinary agent-work admission.
4. Reuse `SubmissionEnvelope`/`ExecutionManifest`, renaming only fields that genuinely change meaning.
5. Decide direct provider/model execution explicitly: remove it from AgentTask or retain it as a separately named operator/raw-execution API.
6. Define runtime and operator authorization/tool subsets.
7. Update every caller, MCP tool, schema, descriptor, test and document in the same change.
8. Delete `submit_llm_request`, `agent_llm_*` and other superseded names after callers migrate.
9. Reuse existing cancellation, status, output, idempotency, redaction and recovery owners.
10. Replace touched module-global dependency lookup with explicit composition-root wiring.
11. Add architecture tests proving one AgentTask path, bounded runtime access and no cross-caller/global administration.

## Do not add

- a second task service or store;
- a multi-turn task coordinator, workflow or artifact store;
- task snapshots, revisions or new IDs;
- provider/protocol branching in the application API;
- service locators, compatibility adapters, aliases, legacy handlers or dual execution routes;
- unrestricted provider access to global list/overview/configuration or unrelated sessions.

## Validation

Retain and extend tests for:

- async submit/status/wait/cancel and blocking transport cap behavior;
- durable request ID continuity as AgentTask ID;
- prompt redaction, digesting, idempotency and execution manifest behavior;
- queue admission, concurrency, stale-profile rejection and recovery;
- persistent session FIFO, close and timeout behavior;
- runtime harness submission and result retrieval through the public client;
- runtime caller ownership/authorization isolation;
- operator list/overview access;
- direct provider/model bypass removed or isolated behind a separately named operator API;
- fake injected dependencies without global registry/queue mutation.

## Reassess before AS64

Prove the refactored API supports current gateway use and local delegation with the existing request/turn lifecycle. Add new task machinery only if a demonstrated later protocol cannot map safely to it.

## Acceptance criteria

- One application API owns agent-work submission/status/cancel.
- Existing durable request identity and machinery remain authoritative.
- `ExecutionManifest` remains the only request-level resolved execution record.
- Harnesses have bounded runtime gateway access.
- Operator and runtime scopes use the same gateway logic without sharing privileges.
- All callers use the new contract directly.
- Stateful dependencies are composition-root supplied, with no new globals or container.
- No compatibility or duplicate task path remains.
