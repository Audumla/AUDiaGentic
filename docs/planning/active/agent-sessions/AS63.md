# Replace the gateway agent-work API with AgentTask

## Goal

Make a small provider-neutral `AgentTask` API the sole agent-work entry point over the existing durable request, queue and session-turn machinery.

Do not create a second task engine, identity, store, queue, cancellation path or recovery system.

## Current code to retain and refactor

The existing gateway already has the needed durable machinery:

- `agents_gateway_api.py`: submission/admission/status/cancel orchestration;
- `agents_gateway_client.py`: client boundary used by transport adapters;
- request store, queue manager, dispatch, progress and recovery modules;
- `SubmissionEnvelope` and `ExecutionManifest` execution-context contracts;
- session request/turn/runtime stores and controls;
- `agents_gateway_mcp.py`: gateway MCP over the gateway client.

Refactor these in place. Do not place a new task service beside them.

## Boundary

Expose one framework-neutral application API/client with only currently required operations:

- submit;
- get status/result;
- wait where the caller transport supports it;
- cancel;
- list/overview for operator surfaces;
- session open/continue/close through the existing session authority;
- read existing output/events through AS31/AS57 where needed.

ACP, A2A, management MCP, runtime gateway MCP/extension, CLI and internal workflows call this API through scoped adapters. The application API depends explicitly on existing gateway/request/session owners and never imports protocol or provider internals.

## Identity and mapping

- the existing durable request ID is the AgentTask ID initially;
- one AgentTask maps to one existing request and one session turn;
- existing request, queue, status, output, cancellation and recovery records remain authoritative;
- `ExecutionManifest` remains the resolved execution record;
- no separate task binding, snapshot or persistence is added.

## Gateway projections

The same AgentTask/session application API may support separate adapter projections:

### Operator projection

May expose global list/overview, administration and unrestricted operator-authorized controls.

### Harness runtime projection

May expose only the operations needed for agent capability use:

- permitted AgentTask submit/delegate;
- status/result/wait/cancel for owned or delegated work;
- permitted agent/skill description;
- authorized session continuation where required.

The exact split may be one MCP module with explicit scoped tool registration or two thin MCP modules. Choose the smallest design supported cleanly by the existing descriptor/auth model. Do not duplicate application logic.

## Foundation composition wiring

Use the AS59 foundation composition facility only at startup/composition roots.

Runtime startup constructs and registers the concrete application dependencies:

- Execution Profile and Agent Definition resolvers;
- queue manager;
- request/session stores;
- dispatcher/provider boundary;
- execution-context builder;
- authorization/audit dependencies;
- session runtime/control dependencies.

The built graph supplies the AgentTask application service/client to gateway hosts and protocol adapters. Core service methods receive their dependencies through constructors or explicit parameters and never resolve them from the graph.

- remove `_QUEUE_MANAGER` and touched module-global service selectors;
- remove function-local imports that are acting as stateful dependency lookup;
- retain local imports used only to avoid cycles for pure/stateless helpers where appropriate;
- do not add request/session scopes, decorators, auto-wiring or child containers in this item;
- register shutdown/finalization only for application-owned resources that already require cleanup.

## Work

1. Characterize every submit/status/wait/cancel/run/list/session caller and transport.
2. Rename/generalize the existing public agent-work contract and client in place.
3. Resolve an Agent Definition before admission.
4. Reuse `SubmissionEnvelope`/`ExecutionManifest`, renaming only fields that genuinely change domain meaning.
5. Decide direct provider/model execution explicitly: remove it from AgentTask or retain it as a separate operator/raw-execution API. It must not bypass Agent Definition selection silently.
6. Update every agent-work caller, MCP projection, schema, descriptor, test and document in the same change.
7. Delete `submit_llm_request`, `agent_llm_*` and other superseded agent-work APIs after callers migrate.
8. Reuse existing cancellation, status, output, idempotency, redaction and recovery owners.
9. Build the concrete AgentTask service/client through runtime composition and inject it into all touched hosts/adapters.
10. Remove touched module-global queue/profile/service lookup.
11. Add architecture/search checks proving one agent-work path and no container lookup from core services.

## Do not add

- a new task service beside the existing gateway application API;
- a multi-turn task coordinator;
- task workflows or artifact stores;
- task snapshots, revisions or new IDs;
- provider/protocol branching in the application API;
- service locators, compatibility adapters, aliases, legacy handlers or dual routes;
- a second DI/container mechanism;
- task/session scopes without a demonstrated lifecycle need.

## Validation

Retain and extend tests for:

- async submit/status/wait/cancel and blocking transport cap behavior;
- durable request ID continuity as AgentTask ID;
- prompt redaction, digesting, idempotency and execution manifest behavior;
- queue admission, concurrency, stale-profile rejection and recovery;
- persistent session FIFO, close and timeout behavior;
- operator and runtime MCP projections calling only the public client;
- runtime authorization limiting target/task/session access;
- fake injected dependencies exercising the application boundary without global mutation;
- startup graph shutdown/finalizer behavior for owned gateway resources;
- direct provider/model bypass removed or isolated behind a separately named operator API.

## Reassess before AS64

Prove the refactored API supports current gateway use and local delegation with the existing request/turn lifecycle. Add new task machinery or DI scopes only if a demonstrated later protocol cannot map safely to it.

## Acceptance criteria

- One application API owns agent-work submission/status/cancel.
- Existing durable request identity and machinery remain authoritative.
- `ExecutionManifest` remains the only request-level resolved execution record.
- Operator and harness runtime surfaces are scoped adapters over the same client.
- Stateful dependencies are built by runtime startup through the foundation composition facility.
- Core services remain plain Python and container-independent.
- No global service lookup, compatibility path or duplicate task path remains.
