# Isolate default GPT sessions by client identity, not process or project

## Description

Ensure each logical client/chat has its own GPT-auto default session. A shared machine gateway and project must not cause two distinct clients to inherit or redirect to one another's default, even when their icons, leases, or provider URLs differ.

## Steps

- Define and require a stable caller-owned logical client identity per chat/client, distinct from the process-wide GatewayClient cache.\n- Carry that identity through lease acquisition and submit admission.\n- Keep the default binding key scoped by logical client, canonical project, agent, provider surface, and schema generation.\n- Reject or quarantine ambiguous legacy bindings rather than attaching another client's session.\n- Restrict provider conversation-owner lookup so implicit defaults never adopt another client's provider conversation.

## Detailed Solution & Technical Design

The current binding hash includes client/project/agent, but get_gateway_client caches one service client per process and can therefore collapse multiple logical chats into one lease identity. Add an explicit client identity parameter/context at the inbound chat boundary and make the cache key include it, or use a per-client client object. Persist the logical client key in protected request provenance for audit. When a default binding's session or URL is missing, create a replacement for that exact client; do not call global conversation ownership resolution unless the continuation was explicit.

## Code Samples & Guidance

client_instance_id = logical_chat_client_id\nclient-default-key = H(client_instance_id, canonical_project, agent_id, provider_surface)

## Validation

Create two logical clients in one process and verify distinct icons, leases, binding files, gateway sessions, and provider conversations. Verify explicit continuation still works, while implicit selection never follows another client's binding or URL. Test legacy/ambiguous bindings fail closed.

## Effort & Risk

High: crosses client caching, service leases, admission, and provider ownership; must preserve deliberate explicit continuation.

## Standards

SH33; AS08; AS49; per-client default-session requirement.

## Acceptance Criteria

- Two clients in one IDE/process cannot share an implicit default.\n- Explicit session continuation remains the only cross-client attachment path.\n- Provider URL recovery cannot silently adopt another client's session.\n- Protected provenance identifies the logical client without exposing it publicly.
