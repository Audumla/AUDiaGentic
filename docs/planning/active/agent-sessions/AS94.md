# Live turn read surface combining status and output

## Description

One read surface letting a caller observe a live turn: lifecycle metadata from the polling buffer and assistant output from the relay, presented through one cursor envelope.

The two remain separate channels. They may share an outer envelope and cursor, but keep distinct event kinds, retention behaviour and source sequences. Assistant text never merges into lifecycle evidence.

## Steps

1. Define the bounded public envelope: request id (the sole identity — AS63's landed implementation confirmed `AgentTask` is a handle wrapping the existing durable `request_id`, not a second ID space, so the envelope carries request id only, not a separate task id), session id, turn id, public sequence, timestamp, channel (`status|output`), the event payload, next cursor, has-more, gap, truncated, delivery state.
2. Combine **AS93**'s metadata poll and **AS87**'s output read into one ordered page, or one operation with explicit channel selection. Do not build a second store — both sources already own their own truth.
3. Support reconnect from a cursor without duplicating already-delivered events.
4. Own only outer cursor syntax and context binding: reject malformed or oversized cursors, and validate that the cursor's request/session/turn context matches. Delegate domain-specific gap outcomes to their owning source rather than re-deriving them — AS93 decides metadata-buffer generation/restart and retention-expiry gaps, AS87 decides output truncation, retention loss, and corrupt/missing indexed output events (RV926). AS94 surfaces whichever gap outcome the source reports.
5. Never claim durable replay for in-memory metadata. Output durability is exactly what the relay proves and no more. The final durable record stays retrievable after terminalization through the existing API.
6. Reading changes nothing: no runtime creation, no turn lock, no lifetime renewal, no queue advance, no cancel/steer/resume/close side effect.
7. Use bounded pagination. Do not add SSE, WebSocket or push in this item.

## Validation

- Status and output events stay in their declared channels and are individually ordered.
- Reconnect from a cursor delivers no duplicate accepted events.
- A metadata restart gap and an output truncation gap are each deterministic and distinguishable.
- Malformed or oversized cursor and page requests are rejected.
- No runtime creation, turn lock, queue mutation or lifetime renewal — asserted directly.
- Client disconnect and reconnect while the provider continues working.
- The final durable record stays readable after the live stream ends.

## Acceptance Criteria

- An in-project caller can observe a live turn without controlling it — there is no caller-identity concept here, only project scoping (see threat_model_correction_2026_08_05).
- Status and output stay separate channels with distinct kinds, retention and sequences — assistant text never merges into lifecycle evidence.
- Reconnect from a cursor delivers no duplicate accepted events.
- Metadata-restart and output-truncation gaps are each owned by their source (AS93 and AS87 respectively, RV926) and are deterministic and distinguishable from one another; AS94 owns only outer cursor syntax and request/session/turn context binding.
- Reading has no execution side effect — no runtime creation, turn lock, queue mutation or lifetime renewal.
- No third store is created; both channels read from their existing owners.
- Durable replay is never claimed for in-memory metadata, and the final durable record stays readable after the live stream ends.
- Protocol adapters consume this surface rather than reading transports, output files or event stores directly.

## Threat Model Correction 2026 08 05

**This item previously deferred an authorization model to AS101. That model is gone — read this before implementing.**

The deployment is local, internal, non-hostile, not externally facing, with one shared gateway serving multiple projects. AS101 has been rewritten from a caller-authorization model to **project isolation**, and the caller-authentication, lease-validation and protocol-id-cannot-authorize requirements are dropped entirely.

**What this item should consume from AS101 instead:** a read must be scoped to the requesting project. That is the only isolation boundary. Within a project there is no per-caller filtering — a harness may observe another harness's turn, and that is intended.

**What does not change:** the side-effect-free property (no runtime creation, no turn lock, no lifetime renewal, no queue mutation) stays exactly as specified. It was never a security constraint — it is a correctness constraint about reads not perturbing execution, and it is the most important thing this item asserts.

**Simplification available:** with no lease model to consult, the read path needs only the project context already carried on the request. Do not build a caller-identity concept for this item.
