# Guard plan-set integrity so merges cannot silently destroy planning

## AS59 disposition

Disposition: new  
Authority: AS59  
Position: Do first — it is small, unblocked, and every other item's references
depend on the invariants it enforces.

- This is the recurrence guard for the failure AS59's Gate 0 had to clean up by
  hand. Without it the same loss happens on the next concurrent merge.
- It touches no runtime code. It is a CI/test-only item.

## Why

On 2026-08-02, merge `de14198d7` joined two divergent lines of the same branch,
both of which had edited the plan tree. The merge silently destroyed real
planning work:

- `AS60.md` existed on both sides with entirely different content (an
  add/add conflict). The merge kept one and discarded "Refactor current agent
  profiles into execution profiles" — an item refined over ten commits and
  referenced by AS47, AS59 and AS61.
- `AS29.md`, `AS31.md` and `AS49.md` were edited on both sides. The merge kept
  one side's blob wholesale, dropping ~30 lines of precedence and layering
  constraints from each.
- `AS19.md` and `AS30.md` were edited on one side and moved to `completed/` on
  the other. The merge took the move and dropped the edits, orphaning a forward
  increment that AS47 and AS49 both depend on (now AS69).
- `AS59.md` ended up existing simultaneously in `active/` and `completed/` with
  two unrelated contents under one ID.

None of this produced a conflict marker, a failing test, or any other signal.
It was found only by reading the plan set end to end. Separately, thirteen
completed items were deleted rather than transitioned by `fb42d847b`, leaving
references in live items pointing at nothing.

Both failure modes share one root cause: plan files are hand-authored, so IDs
are allocated by guesswork and nothing validates the result.

## Work

1. Add a test asserting **ID uniqueness** across the entire `docs/planning/`
   tree — no ID may appear in two files, in any plan, in any state directory.
   This alone would have caught both the AS59 and AS60 collisions.
2. Add a test asserting **filename matches frontmatter `id`** for every item.
3. Add a test asserting **every `AS##`/`PC##`/`HA##`/... reference inside an
   active item resolves** to an existing item file in any state directory.
   Reference-from-completed may warn rather than fail — history legitimately
   cites deleted items.
4. Add a test asserting **`blocked-by` targets exist** and that the graph is
   acyclic.
5. Add a test asserting **no item file exists in more than one state
   directory** (`active/`, `completed/`, and any others).
6. Add a test asserting **required sections are present and non-empty** on every
   active item, per `CREATING_PLANS.md` §7:
   - `Validation` must exist and be non-empty on every item;
   - `Standards` must exist and be non-empty on any item whose text references
     `src/` or a `.py` path — §3 states plainly that items shipped with empty
     Standards sections "correlated directly with standards violations in the
     implementation";
   - `Acceptance criteria` must exist and be non-empty.

   A heading with an empty body must fail. The codex item template emits empty
   `Standards`/`Detailed Solution`/`Code Samples` headings, and four items
   carried an empty `Standards` heading for months while appearing to have one
   — presence of the heading is not compliance.
7. Wire all of the above into `.github/workflows/ci-tests.yml` so a merge that
   breaks them fails before landing.
8. Document in `docs/planning/CREATING_PLANS.md` that IDs are allocated through
   `plan_create_item` and never by writing a file directly, and state what to do
   when the ag-planning MCP is unavailable (record the intent in an existing
   item's notes; do not invent an ID).

## Optional, only if steps 1-8 prove insufficient

A `.gitattributes` merge strategy for `docs/planning/**` that refuses automatic
resolution and forces manual conflict handling. Prefer the tests first — they
catch the outcome regardless of how the tree got there, and they also catch
hand-authoring mistakes that have nothing to do with merges.

## Validation

- a deliberately duplicated ID fails the suite;
- a file whose name and `id` disagree fails;
- an active item referencing a nonexistent ID fails;
- a `blocked-by` cycle fails;
- the same ID in `active/` and `completed/` fails;
- an item with an empty `Standards` heading that references `src/` fails;
- an item with no `Validation` section fails;
- the current tree passes after AS59's Gate 0 repair and this session's
  section backfill.

## Acceptance criteria

- The four defects found by hand during AS59 Gate 0 are all caught
  automatically by CI.
- Plan-ID allocation policy is written down where item authors will read it.
- No runtime code is touched.

## Standards

- `arch-standards` §7 Enforcement — "architecture rules must have proportionate
  automated checks". This item is that check for the planning tree: the
  invariants already exist as doctrine in `CREATING_PLANS.md`, they are simply
  unenforced.
- `arch-standards` §4 Public Contracts — the guard reports failures with clear,
  actionable messages naming the offending file and ID.
- No `src/` code is touched: tests, CI workflow, and `CREATING_PLANS.md` only.
  Standards that govern runtime layering do not apply.
