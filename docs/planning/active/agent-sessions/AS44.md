# Add Pi turn steering and queued follow-up

## Goal

Add interactive control beyond baseline prompt/cancel while keeping one authoritative transport, one agents FIFO, and explicit unsupported behavior.

## Dependencies

AS40/AS41 validated Pi RPC baseline; AS29 generic capability declaration; AS30 stable binding; AS19 control idempotency; AS21/AS31 lifecycle/output. AS58 external exposure is separate.

## Steering capability

Define a provider-neutral typed `STEER_TURN` action with:

- active session/turn/request identity;
- client idempotency ID;
- bounded steering text only;
- accepted, unsupported, already-terminal, rejected, uncertain dispositions;
- exact ordering relative to native prompt/tool events;
- no provider-native command escape hatch.

Implement for Pi RPC only if native behavior is proven during model activity and tool execution. Clarify whether steering is accepted while waiting, cancelling, or settling. Repeated accepted steering returns the original result and must not append twice.

Steering never opens a new turn, bypasses queue/FIFO, writes output directly, or terminalizes the current turn.

## Queued follow-up capability

Define follow-up as a distinct agents-owned future turn request, not steering. Specify:

- target session generation/binding;
- new AUDiaGentic request/turn identity;
- FIFO position and deduplication key;
- cancellation before dispatch;
- rejection when binding/context/session reusability is unsafe;
- persistence/restart behavior;
- interaction with an active turn, closing session, replacement, and resume.

Reuse existing gateway queue/request persistence. Do not create a Pi-specific queue or hidden prompt dispatcher. Persist queued follow-up only when AS30 identity/context and recovery semantics make replay safe.

## Provider behavior

Pi RPC may receive steering through native control and follow-up through the normal next-turn prompt path after AS21 marks the session reusable. Pi ACP and other surfaces remain unsupported unless independently proven. Hooks/plugins cannot implement either action.

## Validation

- steer during model activity and tool execution;
- steer while waiting/cancelling/settling;
- steer after terminal;
- duplicate steer and transport-loss uncertainty;
- follow-up FIFO after current turn;
- duplicate and cancelled follow-up;
- session closes/fails/replaces before dispatch;
- gateway crash/restart with persisted queued work;
- unsupported Pi ACP/other surface;
- no second queue/prompt path/lifecycle authority;
- all effects visible only through AS19/AS21/AS31.

## Acceptance criteria

- Steering and follow-up are separate generic capabilities.
- Steering is exactly-once/idempotent and cannot bypass the active transport.
- Follow-up uses the existing queue and a new normal turn.
- Unsupported surfaces fail deterministically.
- AS58 can expose the actions without Pi-specific API fields.
