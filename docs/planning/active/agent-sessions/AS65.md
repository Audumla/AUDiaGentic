# Expose AUDiaGentic interaction sessions through an external ACP façade

## Goal

Expose selected logical agents and their AUDiaGentic-owned Interaction Sessions to external Agent Client Protocol clients without raw-proxying or leaking the underlying provider ACP/native session.

ACP is an external interactive-session adapter over canonical agents services. It is not the internal domain model and not a second session runtime.

## Execution prerequisite

AS59 Gate 0 and AS64 reassessment gate R5 must be closed before implementation begins. AS57/AS58 must be available as the protocol-neutral read/control authorities, and AS59 must record no unresolved external-ACP passthrough plan.

## Dependencies

- AS19 provider-neutral session transport/control/observation contracts;
- AS29 exact resolved Session Surface capabilities;
- AS30 protected session bindings and ownership;
- AS31 canonical assistant-content lane/final output;
- AS47 exact same-generation continuation;
- AS49 explicit linked-generation resume where supported;
- AS57 authorized status/output reads;
- AS58 capability-gated controls;
- AS60-AS64 Execution Profile, Role, Agent Definition, AgentTask and effective capabilities.

## Boundary

```text
External ACP client
  -> AUDiaGentic ACP server adapter
  -> canonical AgentTask/InteractionSession application services
  -> SessionRuntime
  -> AgentSessionTransport
  -> provider-private ACP/RPC/CLI/native adapter
```

The external ACP session ID is AUDiaGentic-owned and maps through AS30/session services. It is never the raw provider session reference.

## Initial ACP operations

Implement only operations supported by the selected stable ACP specification and proven by canonical services, initially:

- initialize/capability negotiation;
- create/open session for a published Agent Definition;
- prompt/turn submission;
- session updates from AS31/AS57 projections;
- cancel and proven controls through AS58;
- close/detach;
- load/resume only where AS29/AS30/AS49 exact semantics can be mapped honestly;
- permission response only where correlation and default-deny behavior are proven.

Unsupported operations must return explicit protocol-compliant unsupported responses. Do not emulate provider-native behavior or silently create a new conversation for resume/load.

## Capability projection

Generate the ACP capability view from:

- Agent interface publication policy;
- effective capability snapshot;
- AS29 frozen surface/control/content capabilities;
- AS30 ownership/topology;
- AS57/AS58 available application operations.

Do not advertise a capability because the underlying harness uses ACP. Validate the façade against a non-ACP fake/native transport as well.

## Streaming and observations

Map canonical lanes only:

- AS31 assistant output -> ACP agent message chunks/final;
- AS57 bounded status/tool milestones -> appropriate ACP session updates;
- AS58 correlated permission/control state -> ACP request/response where supported.

Do not expose raw provider frames, hidden reasoning, native event names, provider refs, unrestricted tool payloads or internal diagnostics.

## Security and authorization

- authenticate the external client through existing gateway client/lease mechanisms;
- authorize exact Agent Definition, project, workspace and session access;
- apply Role tool/permission policy before materialization;
- bind every request to exact session generation and execution/composition context;
- preserve owned/adopted/external close semantics;
- apply rate, queue, timeout and payload bounds through existing gateway owners;
- audit bounded generic ACP actions without protocol payload leakage.

## Steps

1. Consume completed AS64/R5 findings from AS59 and characterize the stable ACP SDK/schema version chosen.
2. Define a protocol adapter component depending only on agents public application services.
3. Add external ACP session/turn ID bindings without modifying AS30 provider-ref identity rules.
4. Implement capability projection and explicit unsupported behavior.
5. Implement prompt and session update mapping from canonical task/session/output services.
6. Implement cancellation/close and only proven controls through AS58.
7. Add optional load/resume after AS49 exact semantics are available; otherwise advertise unsupported.
8. Add service lifecycle, configuration and endpoint publication through existing component/gateway infrastructure.
9. Add compatibility/conformance tests with a real ACP client where practical.
10. Update AS59 with R6 findings before AS66 begins.

## Reassessment gate R6

Before AS66:

- run one ACP-backed harness and one non-ACP/fake transport through the same external ACP façade;
- identify any ACP operation that cannot be expressed by canonical services and decide whether to extend the neutral services or leave it unsupported;
- confirm no provider-native ACP type or payload has entered agents core;
- review whether external ACP and current AS57/AS58 MCP/client APIs duplicate public operations and consolidate shared application logic.

Record the R6 decision in AS59 before AS66 starts.

## Validation

- session open -> multiple two-way turns -> close;
- client disconnect/reconnect without killing reusable session unless policy requires;
- streaming ordering/backpressure/gap behavior from canonical lanes;
- cancellation and permission default-deny;
- exact continuation and context mismatch;
- unsupported load/resume does not open fresh history;
- cross-project/agent/session authorization;
- provider ACP and non-ACP fake behavior parity;
- no raw provider refs/native frames/reasoning leakage;
- external ACP reads/controls use one canonical application authority.

## Acceptance criteria

- External ACP clients can drive AUDiaGentic-owned Interaction Sessions.
- The façade is provider neutral and works independently of underlying ACP use.
- Raw backend ACP is never passed through.
- Capabilities are advertised only when canonically and evidence-backed supported.
- R6 findings are recorded in AS59 before A2A implementation proceeds.
