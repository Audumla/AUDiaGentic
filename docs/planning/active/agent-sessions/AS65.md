# Expose AUDiaGentic sessions through ACP

## Goal

Add one external Agent Client Protocol adapter over AUDiaGentic-owned sessions.

Do not raw-proxy an underlying harness ACP session and do not add another session, task, output or control authority.

## Boundary

```text
ACP client
  -> ACP protocol adapter
  -> approved framework-neutral agents/gateway APIs
  -> existing request/session/runtime owners
```

The adapter is wired at the runtime composition root. It imports no stores, queues, provider adapters, registries or internal services.

## Foundation composition adoption

Runtime/bootstrap registers the ACP endpoint factory and constructs each adapter from the approved public ports already present in the application graph:

- Agent Definition lookup;
- AgentTask/gateway client;
- session read/output/control ports;
- authorization/audit context;
- endpoint configuration.

The ACP adapter receives these dependencies explicitly. ACP SDK types remain inside the adapter package. Do not resolve dependencies from a global graph during request handling and do not create an ACP-specific child container or service registry.

## Initial scope

Implement only operations already supported by canonical APIs:

- initialize/capabilities;
- open a session for an Agent Definition;
- submit a turn;
- read assistant output and bounded status;
- cancel and close;
- permission or resume only when AS58/AS49 already support them.

Return protocol-compliant unsupported results for everything else. Do not emulate missing behavior.

## Work

1. Pin one ACP schema/SDK version inside the adapter component.
2. Translate ACP requests to existing public application operations.
3. Use AUDiaGentic task/session IDs as external ACP identities where the protocol permits; add only a small in-memory correlation map when translation genuinely requires it.
4. Use AS31/AS57 for output/status and AS58 for controls.
5. Advertise only proven capabilities.
6. Validate the same adapter with one ACP-backed and one fake/non-ACP transport.
7. Register adapter construction and endpoint configuration through the foundation composition/bootstrap path.
8. Add tests proving the adapter can be constructed with fake public ports and contains no direct store/provider imports or graph lookup.

## Do not add

- raw provider ACP passthrough;
- ACP-specific durable session/task storage;
- another output/event/control path;
- provider-name branching;
- ACP types in agents core;
- direct internal-module imports;
- global composition lookup, shims, alternate ACP routes or compatibility handlers.

## Reassess before AS66

Confirm the adapter remains thin and provider neutral. Leave unsupported operations unsupported. Any missing canonical operation must be added to its existing owner, not implemented inside the ACP adapter.

## Acceptance criteria

- External ACP clients can drive AUDiaGentic-owned sessions.
- Runtime constructs the adapter through the foundation composition bootstrap.
- The adapter depends only on approved injectable public APIs.
- Existing session, task, output and control authorities remain singular.
- No provider ACP data, global service lookup or compatibility path leaks through the boundary.
