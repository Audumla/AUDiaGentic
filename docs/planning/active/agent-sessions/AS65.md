# Expose AUDiaGentic sessions through ACP

## Goal

Add an external Agent Client Protocol adapter over AUDiaGentic-owned sessions.

Do not raw-proxy the underlying harness ACP session and do not add a second session runtime.

## Boundary

```text
ACP client
  -> ACP adapter
  -> AgentTask/session/read/control services
  -> existing SessionRuntime and provider-neutral transport
```

The ACP adapter is wired with application-service interfaces. It must not import concrete stores, provider adapters or global registries.

## Initial scope

Implement only what current canonical services support:

- initialize/capabilities;
- open session for an Agent Definition;
- prompt/turn;
- assistant output and bounded status updates;
- cancel and close;
- permission or resume only when already proven by AS58/AS49.

Unsupported ACP features return unsupported. Do not emulate them.

## Work

1. Pin one ACP schema/SDK version inside the adapter component.
2. Map external ACP IDs to AUDiaGentic session/task IDs, never provider refs.
3. Use AS31/AS57 for output/status and AS58 for controls.
4. Advertise only proven capabilities.
5. Validate the same adapter with one ACP-backed and one fake/non-ACP transport.
6. Reuse existing authentication, project, queue and lifecycle services.

## Do not add

- raw provider ACP passthrough;
- another output/event store;
- provider-name branching;
- protocol types in agents core;
- ACP-specific session persistence beyond small ID bindings if required.

## Reassess before AS66

Confirm the adapter remains thin and provider neutral. Leave unsupported operations unsupported rather than expanding the domain speculatively.

## Acceptance criteria

- External ACP clients can drive AUDiaGentic sessions.
- The adapter depends only on injectable application-service ports.
- Existing session, output and control authorities remain singular.
