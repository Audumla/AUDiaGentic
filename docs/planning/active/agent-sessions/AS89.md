# Explicit session resume as a new linked generation

## Description

Add the generic request layer for explicitly resuming a dead provider session, creating one new linked generation while the terminal source stays terminal.

The provider half is already proven: `AcpSessionTransport.open_resumed()` exists, refuses to fall back to a fresh session when the agent does not advertise `loadSession`, and was proven against real `pi-acp` in Docker (hard-kill the original process, resume by ref in a new one, assert prior turn content actually replays). What is missing is everything above it — there is no resume request path at all.

## Steps

1. Add one explicit resume request taking the terminal source session id plus a client idempotency key. Ordinary continuation and task submission never invoke resume. (The coordinator already exists in `SessionRuntime._resume_session()` — this item hardens it, it does not build a second layer.)
2. Require the source to be terminal, in the same canonical project, with a binding carrying a stable opaque provider ref. (Already enforced in `gateway/session/resume.py` — verify, do not rebuild.)
3. Require the resolved surface to declare `resume-by-ref: supported`, with a matching ref namespace and compatible surface version. Compare the frozen execution and composition context from the binding-context item. Unknown values reject. **Add the one missing check: live surface-version compatibility against the currently resolved surface version.**
4. Create a new session id/generation with a `RESUMED_FROM` link to the source binding. The source record and its outcome stay immutable and terminal. (No schema change needed — `predecessor-binding-id` and `relation` already exist.)
5. Dispatch exactly one provider-local resume through `providers_api`. ACP `loadSession`, RPC resume and App Server thread reopen are different adapters; none is a fallback for another.
6. Persist transactionally. Provider resume succeeded but persistence failed -> detach/close and remove provisional state (already handled — best-effort close, delete uncommitted successor, repair indexes, IO-AGW-119). Provider resume failed or is uncertain -> expose no live generation, do not retry automatically.
7. Enforce idempotency: a repeated resume with the same key returns the original result and cannot create a second successor. **The load-bearing residual work is closing the `TODO(AS49)` race** — serialize/claim the `(project_id, control_id)` operation before the provider side effect and finalize it transactionally with successor persistence. No second idempotency schema/store.
8. Register typed errors **by reusing the existing canonical vocabulary** (CON-AGW-110/114/115/123/108, RES-AGW-111/118, UNS-AGW-112/117, VER-AGW-113, IO-AGW-119). Define predecessor uniqueness/branching semantics first; only then decide whether an "already-resumed" error exists (same-key repetition stays idempotent success).

## Validation

- Resume succeeds only from a terminal source with a validated capability.
- The source stays terminal and immutable; the successor is a new generation with a `RESUMED_FROM` predecessor link.
- A missing or invalid ref cannot open an unrelated session.
- An unsupported or uncertain operation never creates a fresh conversation.
- A duplicate idempotent request cannot create two successors — including two concurrent first-seen requests racing past preflight.
- Persistence rollback leaves no usable orphan binding or transport.
- Ordinary continuation and task retry never invoke resume.
- One provider-agnostic gateway test asserts exact-ref forwarding and no successful successor on resume failure. (Provider-level pi-acp Docker proof is already-landed evidence, referenced not duplicated.)
- The live surface-version compatibility check is asserted: a stale stored surface-version against the currently resolved surface version rejects.
