# Explicit session resume as a new linked generation

## Description

Add the generic request layer for explicitly resuming a dead provider session, creating one new linked generation while the terminal source stays terminal.

The provider half is already proven: `AcpSessionTransport.open_resumed()` exists, refuses to fall back to a fresh session when the agent does not advertise `loadSession`, and was proven against real `pi-acp` in Docker (hard-kill the original process, resume by ref in a new one, assert prior turn content actually replays). What is missing is everything above it — there is no resume request path at all.

## Steps

1. Add one explicit resume request taking the terminal source session id plus a client idempotency key. Ordinary continuation and task submission never invoke resume.
2. Require the source to be terminal, in the same canonical project, with a binding carrying a stable opaque provider ref.
3. Require the resolved surface to declare `resume-by-ref: supported`, with a matching ref namespace and compatible surface version. Compare the frozen execution and composition context from the binding-context item. Unknown values reject.
4. Create a new session id/generation with a `RESUMED_FROM` link to the source binding. The source record and its outcome stay immutable and terminal.
5. Dispatch exactly one provider-local resume through `providers_api`. ACP `loadSession`, RPC resume and App Server thread reopen are different adapters; none is a fallback for another.
6. Persist transactionally. Provider resume succeeded but persistence failed -> detach/close and remove provisional state. Provider resume failed or is uncertain -> expose no live generation, do not retry automatically.
7. Enforce idempotency: a repeated resume with the same key returns the original result and cannot create a second successor.
8. Register typed errors for: unsupported capability, source-not-terminal, stale binding, identity mismatch, context mismatch, version incompatibility, already-resumed, provider rejection, uncertain submission, persistence failure.

## Validation

- Resume succeeds only from a terminal source with a validated capability.
- The source stays terminal and immutable; the successor is a new generation with a `RESUMED_FROM` predecessor link.
- A missing or invalid ref cannot open an unrelated session.
- An unsupported or uncertain operation never creates a fresh conversation.
- A duplicate idempotent request cannot create two successors.
- Persistence rollback leaves no usable orphan binding or transport.
- Ordinary continuation and task retry never invoke resume.

## Acceptance Criteria

- Resume is explicit. Ordinary continuation, task retry and protocol reconnect never trigger it.
- A successful resume creates exactly one linked successor generation while the source stays terminal and immutable.
- No fallback route exists — not CLI, not account, not session name, not "latest". An unsupported or uncertain resume never opens a fresh conversation.
- A duplicate idempotent request returns the original result and cannot create a second successor.
- Persistence rollback leaves no usable orphan binding or transport.
- Provider-native resume details and refs stay private behind the provider API.
- Resume and same-generation continuation remain distinct operations.
