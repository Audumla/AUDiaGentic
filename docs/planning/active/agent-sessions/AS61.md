# Add minimal reusable role contracts

## Goal

Introduce provider/model-independent roles that define how an agent should behave regardless of the Execution Profile used to materialize it.

A Role is reusable policy and behavior, not a runtime, model, session or externally addressable agent.

## Execution prerequisite

AS59 Gate 0 and AS60 reassessment gate R1 must be closed before implementation begins. AS59 must record that Execution Profile remained a narrow execution/admission mapping and that behavioral/tool/public-agent fields were excluded.

## Initial scope

A Role may define only:

- identity metadata for operators: role ID, name, description and generation/version;
- bounded system/developer instructions or references to managed instruction assets;
- tool/MCP capability policy expressed through existing tool/provider contracts;
- permission/approval defaults through existing policy contracts;
- required effective capabilities;
- bounded output expectations such as a named output contract/reference.

Provide typed extension points, but defer full memory, planning, workflow, delegation graph and autonomous scheduling frameworks until a concrete consumer requires them.

## Requirements model

Define closed requirement expressions sufficient for the first slice:

- `all_of` capabilities;
- `any_of` alternatives;
- optional bounded constraints such as minimum context, text/vision input and streaming requirement.

Unknown capability is unsupported. Roles never declare that a provider/model supports something; they only require or restrict capabilities.

## Resolution and snapshots

Define:

- `RoleDefinition` — persisted reusable role;
- `RoleSnapshot` — immutable resolved role plus digest/generation;
- `RoleRequirements`;
- `ToolPolicy` and `PermissionPolicy` references or minimal typed values;
- `resolve_role(project_root, role_id)` and shared-mode authority if required by existing gateway ownership.

Do not add deep arbitrary dictionary merge. Initial role composition is one Role per Agent Definition. Overrides, inheritance and multiple-role stacking are out of scope unless R2 proves a concrete need.

## Steps

1. Consume completed AS60/R1 findings from AS59.
2. Characterize existing prompt/tool/MCP/permission configuration paths and reuse their owners rather than creating a parallel tool registry.
3. Add Role schema/model/store/resolver and immutable snapshots.
4. Add deterministic digest/generation covering behaviorally relevant, non-secret fields.
5. Add requirement validation as a pure service consuming an effective-capability snapshot supplied later by AS64; use fakes until AS64 lands.
6. Add config CRUD/read surfaces only where current Execution Profile CRUD patterns justify them.
7. Add redacted public/operator projections excluding full sensitive instructions where policy requires.
8. Add architecture gates preventing provider/model/surface selection in Roles.
9. Update AS59 and any affected plans before closing R2.

## Reassessment gate R2

Before AS62, demonstrate:

- one Role applied to at least two Execution Profiles;
- one Execution Profile used by at least two Roles;
- no provider-name branching in Role resolution;
- tool and permission policy can be composed through existing public seams;
- no need for Role inheritance or multiple-role stacking in the demonstrated cases.

If inheritance is genuinely required, add a separate reviewed plan with deterministic linearization and conflict semantics. Do not add ad hoc YAML merge behavior.

Record the R2 decision in AS59 before AS62 starts.

## Validation

- schema and store round trip;
- stable digest/generation;
- instruction/tool/permission bounds and redaction;
- missing Role and malformed requirement errors;
- all/any requirement evaluation with unknown unsupported;
- Role reuse across fake Pi ACP and non-ACP execution snapshots;
- no provider/model/surface/runtime/session fields in Role definitions;
- architecture tests for dependency direction.

## Acceptance criteria

- Role is a distinct reusable behavioral layer.
- Roles are Execution Profile independent.
- Role requirements are closed, typed and default-deny for unknown capabilities.
- No duplicate tool, permission or instruction authority is created.
- R2 findings are recorded in AS59 before AS62 begins.
