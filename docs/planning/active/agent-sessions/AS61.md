# Add minimal reusable roles

## Goal

Add a small provider-independent `Role` that can be used with different Execution Profiles.

A Role may contain:

- instructions or references to managed instruction assets;
- references to existing tool/MCP policy;
- references to existing permission/approval policy;
- simple required capabilities;
- optional output guidance.

A Role does not own tools, MCP servers, permissions, provider/model selection, session surfaces, queues, runtime behavior or protocol settings.

## Boundary

Expose Role lookup through one narrow public API only where current storage/I/O requires it. Keep concrete loading behind that boundary and inject it into callers. Do not add a service wrapper around pure validation or create another tool, MCP, permission or instruction registry.

## Work

1. Characterize and reuse existing instruction, tool, MCP and permission owners.
2. Add one simple Role definition and the minimum storage/resolution needed.
3. Support one Role per Agent Definition.
4. Support only capability checks required by demonstrated Roles.
5. Update all callers directly; delete superseded names, paths, handlers, fixtures and tests in the same change.
6. Add architecture checks preventing provider/runtime fields and concrete-store imports in consumers.

## Do not add

- copied tool or MCP declarations;
- role inheritance or stacking;
- arbitrary merge behavior;
- policy revisions or overlays;
- memory/workflow/delegation frameworks;
- service locators, global registries or compatibility paths.

## Live behavior

Do not add live Role mutation. A different Role applies to a future task or new session unless an existing harness path already supports a safe change without new infrastructure.

## Reassess before AS62

Prove one Role works with two Execution Profiles and one Execution Profile works with two Roles. Remove every field without a current consumer. Confirm callers can use a fake Role boundary without importing stores or provider code.

## Acceptance criteria

- Role is a small reusable behavioral definition.
- Existing instruction, tool, MCP and permission owners remain singular.
- No provider/runtime configuration leaks into Role.
- The boundary is DI-ready without adding a container or unnecessary interface.
- No legacy or parallel Role path remains.
