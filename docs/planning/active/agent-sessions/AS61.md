# Add minimal reusable roles

## Goal

Add a small provider-independent `Role` that can be used with different Execution Profiles.

For this item, a Role contains only:

- instructions or references to managed instruction assets;
- simple required capabilities where a demonstrated role needs them;
- optional output guidance;
- an optional reserved runtime-tool-policy reference with no runtime effect.

A Role does not own or alter:

- management MCPs used by AUDiaGentic CLI/admin;
- runtime MCP servers or tools materialized into a harness;
- harness permissions;
- provider/model selection, session surfaces, queues, runtime behavior or protocol settings.

Each harness continues to use its existing configured/default runtime tools, MCP servers and permissions.

## Boundary

Expose Role lookup through one narrow public API only where current storage/I/O requires it. Keep concrete loading behind that boundary and inject it into callers. Do not add a service wrapper around pure validation or create a tool, MCP, permission or instruction registry.

Management MCP adapters may expose Role CRUD through the owning public API when required by the CLI. That does not make management MCP part of Role execution and must not duplicate Role validation or persistence.

## Foundation composition adoption

If Role storage or lookup is stateful, register its concrete implementation in the foundation composition builder and inject the public Role lookup into Agent Definition resolution and management adapters.

- runtime/bootstrap selects the concrete Role repository/lookup from approved configuration;
- the Role model and pure validators remain ordinary Python and do not depend on the composition framework;
- MCP tools receive the Role public API from their adapter composition root rather than constructing or globally locating it;
- tests substitute the Role lookup at graph build time;
- do not create a Role-specific container, global singleton, decorator or runtime registration path.

## Work

1. Characterize existing instruction handling and reuse its owner.
2. Add one simple Role definition and the minimum storage/resolution needed.
3. Support one Role per Agent Definition.
4. Support only capability checks required by demonstrated Roles.
5. Leave runtime tool/MCP/permission policy as an inert optional placeholder/reference; do not resolve or enforce it.
6. Keep management MCP concerns limited to thin CRUD/config adapters over the Role public API.
7. Register any stateful Role lookup/repository in the foundation composition bootstrap and inject it into current consumers.
8. Update all callers directly; delete superseded names, paths, handlers, fixtures and tests in the same change.
9. Add architecture checks preventing provider/runtime fields, concrete-store imports and composition lookup inside domain/application code.

## Do not add

- copied runtime tool, MCP or permission declarations;
- management MCP definitions inside Role;
- runtime tool-set normalization, merging or overrides;
- runtime tool-policy resolution or enforcement;
- role inheritance or stacking;
- arbitrary merge behavior;
- policy revisions or overlays;
- memory/workflow/delegation frameworks;
- service locators, global registries or compatibility paths.

## Live behavior

Do not add live Role mutation. A different Role applies to a future task or new session unless an existing harness path already supports a safe change without new infrastructure.

## Reassess before AS62

Prove one Role works with two Execution Profiles and one Execution Profile works with two Roles. Remove every field without a current consumer. Confirm current harness runtime tool sets are unchanged and a fake Role boundary can be supplied through the foundation graph without loading concrete storage.

## Acceptance criteria

- Role is a small reusable behavioral definition.
- Existing harness runtime tool, MCP and permission configuration remains authoritative and unchanged.
- Management MCP remains only an admin/config adapter over the Role public API.
- Runtime tool policy is at most an inert placeholder for a future owning plan.
- No provider/runtime configuration leaks into Role.
- Stateful Role dependencies are built by runtime through the foundation composition bootstrap.
- Role/domain code contains no composition-framework lookup.
- No legacy or parallel Role path remains.
