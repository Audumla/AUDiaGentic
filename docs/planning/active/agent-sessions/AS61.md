# Add minimal reusable roles

## Goal

Add a small provider-independent Role that can be used with different Execution Profiles.

A Role may contain:

- instructions;
- allowed tools/MCP capabilities;
- permission defaults;
- required capabilities;
- optional output guidance.

A Role must not contain provider, model, session surface, queue, runtime or protocol settings.

## Service boundary

Expose Role lookup through one small `RoleService` or equivalent interface. Keep storage and file loading behind it. Consumers receive the service explicitly so later IoC/DI wiring does not require changing domain logic.

## Work

1. Reuse existing instruction, tool, MCP and permission owners.
2. Add one simple Role definition, store and resolver.
3. Support one Role per Agent Definition.
4. Support only simple required-capability checks.
5. Do not add inheritance, role stacking, arbitrary merge, policy revisions, memory/workflow systems or delegation graphs.
6. Avoid direct concrete-store imports from agent/task services.

## Live changes

Do not build a generic role-revision system. A caller may select a different Role for a future request/session where current gateway behavior allows it. Existing live-session mutation remains unchanged unless a concrete harness feature requires more.

## Reassess before AS62

Prove one Role works with two Execution Profiles and one Execution Profile works with two Roles. Remove any field without a current consumer. Confirm a fake RoleService is sufficient for composition tests.

## Acceptance criteria

- Role is a small reusable behavioral definition.
- Existing tool, MCP, permission and instruction infrastructure is reused.
- No provider/runtime configuration leaks into Role.
- Consumers use a clear DI-ready role service boundary.
