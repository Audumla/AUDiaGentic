# Explicitly resume a dead provider session as a new linked generation

## Description

Add explicit resume-after-death only for an exact AS29 surface whose installed version, identity scope, and native resume operation are validated. Preserve terminal history by creating a new AUDiaGentic session generation linked to the terminal source binding. Never reactivate the source record, resume implicitly, select “latest”, or silently create a fresh conversation.

## Dependencies

- AS29 exact surface capability `resume_by_ref` and compatibility predicate.
- AS30 protected binding, predecessor relation, identity/project/context fingerprints, and resume transaction.
- SH02 immutable execution context and SH07 durable terminal authority.
- A provider-local native resume adapter registered through `providers_api`.

## Steps

1. Add an explicit public/application resume request containing the exact terminal source `session-id`. Ordinary prompt continuation never invokes resume.
2. Resolve the source record and require it to be terminal, protected, readable in the same canonical project, and associated with an AS30 binding containing a stable opaque provider ref.
3. Resolve the exact current AS29 surface and require validated `resume_by_ref`, matching ref namespace, compatible surface version, same provider identity context, same project, and same SH02 execution context. Unknown fingerprints or evidence reject the request.
4. Create a new AUDiaGentic session ID/generation and `RESUMED_FROM` binding linked to the source binding. The source record and source outcome remain immutable and terminal.
5. Dispatch exactly one provider-local native resume operation through `providers_api`. ACP `loadSession`, RPC resume, App Server thread reopen, or CLI resume are different private surface adapters; none is an automatic fallback for another.
6. Persist the new record/binding transactionally. If provider resume succeeds but persistence fails, detach/close according to ownership and remove provisional binding/index state. If provider resume fails or is uncertain, do not expose a live new generation and do not retry automatically.
7. Return typed errors for unsupported capability, source-not-terminal, stale/missing binding, identity mismatch, project/context mismatch, version/ref incompatibility, already-resumed conflict, provider rejection, uncertain submission, and persistence failure.
8. Enforce idempotency so repeated client resume requests with the same control/request ID return the original result and cannot create duplicate successor generations.
9. Probe each provider surface independently before promotion. A successful probe resumes known history by exact ref, rejects an invalid ref without opening unrelated history, and proves close/detach cleanup.

## Files

- Existing agents gateway application/request schema and session workflow.
- AS30 binding service/index and v2 session schema.
- AS29 resolver and provider-private resume operation contracts exposed through `providers_api`.
- Focused unit, integration, race, crash, and provider Docker fixtures.

Do not add provider-name branching, CLI fallback heuristics, transcript matching, UI selection, “continue latest”, or another session-generation store.

## Validation

- explicit resume succeeds only from a terminal source with exact validated capability;
- source remains terminal and immutable;
- successor has a new AG ID/generation and `RESUMED_FROM` predecessor binding;
- same project, provider identity, execution context, ref namespace, and version compatibility are enforced;
- missing/invalid ref cannot open an unrelated session;
- unsupported or uncertain operation does not create a fresh conversation;
- idempotent duplicate cannot create two successors;
- persistence rollback leaves no usable orphan binding/transport;
- real installed-version provider probe is required before enabling support.

## Acceptance criteria

- Resume is explicit and never triggered by ordinary continuation.
- A successful resume creates exactly one linked successor generation while preserving source terminality.
- No surface, CLI, account, project, session name, or “latest” route is used as fallback.
- Unsupported, mismatched, stale, or uncertain resume fails deterministically.
- Provider-native resume details remain private behind `providers_api`.

## Effort & Risk

Mid, evidence-gated work. Main risks are corrupting terminal history, duplicate successors, and claiming exact resume where the provider only opens a new conversation.

## Standards

Use the canonical AS29 capability snapshot, AS30 transaction/index, SH02 context identity, SH07 terminal authority, idempotency primitives, redaction, and provider API boundary.

### Real proof landed (2026-07-29, same session, later)

Per direct user correction — do this kind of proof in Docker, never by installing packages on the host (`pi-acp`/`uv sync --extra acp` mutate the environment). Built `tests/integration/providers/test_pi_acp_resume_live.py` + `tests/docker/Dockerfile.pi-acp-resume-e2e` (env gate `AUDIAGENTIC_PI_ACP_RESUME_E2E_DOCKER`), following the exact `Dockerfile.pi-rpc-tap-e2e` pattern. Speaks raw JSON-RPC over the real `pi-acp` bridge's stdio directly (same technique as `test_pi_rpc_tap_transcript_e2e.py`), not the python SDK client — proves the wire behavior of the actual process, independent of `AcpSessionTransport`'s own already-unit-tested logic.

Proof shape, deliberately structural rather than LLM-recall-based (small local models are unreliable narrators of their own memory): process #1 opens a session, sends one prompt turn ("Reply with exactly: OK"), then is **hard-killed** (`proc.kill()`, not `terminate()` — proves real death, not a bridge special-casing clean shutdown). A brand-new process #2 is spawned pointing at the same `--session-dir`, calls `session/load` with process #1's session id, and the test asserts turn 1's "OK" content actually replays via `session/update` notifications *before* `session/load`'s response arrives — this is what ACP's spec says a genuine resume does, distinct from a bridge that accepts the call but silently starts fresh (see the capability-reference doc's "Persisted resume is not live attachment" warning).

**Built and ran the image twice** (`docker build -f tests/docker/Dockerfile.pi-acp-resume-e2e ...` then `docker run --rm ...`) — both runs: exit 0, single test passed (no xfail branch taken, meaning `agentCapabilities.loadSession` really was advertised). **Real result: pi-acp's resume works — proven on linux-amd64.** `pi.yaml`'s `pi-community-acp.identity_operations.resume-by-ref` flipped from `unsupported` to `supported` with a citing comment. Not yet proven on windows-amd64/macOS — the identity_operations map has no per-platform granularity in the current model (unlike controls/evidence, which do), so this is a known coarseness worth flagging for whoever next touches AS29's shape, not something to silently work around here.
