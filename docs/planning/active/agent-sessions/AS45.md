# Add compaction, retry, and deep session-inspection evidence

## Goal

Expose useful long-session observability that is not part of baseline lifecycle, while retaining small generic semantics and typed provider-specific extensions where no honest common meaning exists.

## Compaction evidence

Where exact correlated evidence exists, model:

- compaction requested;
- started;
- completed;
- failed;
- triggering reason/policy code;
- source and resulting context generation/identity;
- affected session/turn/request correlation;
- observed time/order/confidence.

Do not infer compaction from context-size changes, pause duration, output gaps, or summaries. A compaction event does not terminalize a turn or imply session reusability.

## Retry evidence

Where observable, model:

- retry proposed/selected/started;
- cause category;
- attempt/generation;
- backoff/decision metadata;
- whether execution reuses the same provider turn, opens a new provider turn, or creates an AS30 replacement relation;
- terminal result.

Do not conflate transport reconnect, provider internal retry, AUDiaGentic request replay, AS30 resume, or replacement. Unknown relationship remains explicit.

## Session inspection

Define safe provider-neutral reads only for stable state not already available through AS21/AS31/AS30, such as bounded context/compaction counters, provider-declared phase, outstanding permission/tool IDs, or retry state where exact semantics are proven.

Inspection reads:

- are authorized and project/context scoped;
- use the frozen AS29 capability snapshot;
- return typed unsupported/degraded results;
- expose no raw provider ref, prompt, hidden reasoning, tool arguments/results, secrets, config paths, or arbitrary native payload;
- never control or become transport/lifecycle authority.

## Sources

Pi RPC events/reads are preferred when correlated. Pi hooks/plugins may supplement as observers. Pi ACP remains independently validated. Other providers use AS54 probes and AS46 child plans. Provider-specific fields remain typed optional extensions outside shared lifecycle/status contracts.

## Persistence and replay

Persist only when restart/replay semantics are defined and useful. Include evidence source, sequence/correlation, generation, and redaction. Duplicate/replayed/contradictory evidence is idempotent/conservative and cannot mutate lifecycle directly.

## Validation

- compaction success/failure and missing correlation;
- provider internal retry vs AG retry/replacement distinction;
- duplicate/out-of-order/contradictory observer evidence;
- restart/replay where persistence is enabled;
- inspection running/terminal/degraded/unsupported states;
- capability matrix across Pi RPC and Pi ACP;
- hooks/plugins cannot control or directly change lifecycle;
- no provider-native leakage.

## Acceptance criteria

- Generic evidence vocabulary remains small and semantically defensible.
- Compaction/retry relationships are explicit rather than inferred.
- Inspection reuses AS29/AS30 authorization and binding context.
- No new store, lifecycle projector, transport, or control path is introduced.
