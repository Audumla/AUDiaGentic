# Implement singular lifecycle decisions and layered status projection

## Goal

Make validated correlated evidence the only input to provider-neutral lifecycle decisions, and expose a small layered status snapshot without creating another durable state machine. This plan is the canonical lifecycle and status-projection work item.

## Authority

- SH07 durable request state remains request authority.
- The session store/TransitionEngine remains AUDiaGentic session authority.
- Agent-jobs workflow records remain workflow authority.
- Provider transports remain execution owners.
- AS21 is a pure/ephemeral projection layer only; it never terminalizes, persists a competing state record, releases locks, or dispatches controls.

## Pure lifecycle evidence and decision contract

Consolidate a provider-neutral reducer module such as `agents_session_lifecycle_projection.py` with closed frozen types equivalent to:

```python
EvidenceKind = Literal[
    "turn-started", "activity", "waiting", "tool-active", "tool-completed",
    "permission-wait", "terminal-success", "terminal-cancelled",
    "terminal-failed", "transport-closed", "transport-error",
    "finalization-committed", "finalization-failed", "blocking-work-cleared",
]

CoarseSessionState = Literal[
    "active", "waiting", "completing", "available", "failed", "unknown"
]
```

`SessionLifecycleEvidence` must include session/turn/request correlation, strict sequence, timestamp, validation state, and source. `SessionLifecycleDecision` must include coarse state, accepts-new-turn, session-reusable, turn-terminal, dependent-work-releasable, evidence state, and bounded reason.

## Projection rules

- Empty, rejected-only, candidate-only, mixed-turn, missing-correlation, stale, duplicate/lower-sequence contradiction, or unresolved conflict projects conservative `unknown` with every release/reuse flag false.
- Turn started/activity/tool active projects `active`.
- Waiting/permission wait projects `waiting`.
- Terminal provider evidence without finalization projects `completing`.
- Only terminal success + finalization committed + blocking work cleared may project `available` with every reuse/release flag true.
- Terminal cancelled + finalization committed may mark turn terminal and dependent work releasable; session reuse additionally requires blocking work cleared and no close/failure evidence.
- Terminal failed, transport error/close, or finalization failed projects failed unless contradictory. Dependent work is releasable only after the owning durable authority has finalized or failed finalization.
- Process liveness, prompt return, EOF, output silence, final-looking text, resource inactivity, and control acknowledgement never imply available/terminal.
- Duplicate/replayed evidence is idempotent. Out-of-order or contradictory evidence reduces confidence rather than being voted away.

## Ephemeral evidence registry

Maintain a lock-protected `SessionEvidenceProjection` keyed by `(session_id, request_id)`:

- accept only AS19 accepted scalar evidence;
- map canonical activity/tool/waiting statuses to lifecycle evidence;
- preserve positive source sequence or allocate a strict local sequence;
- never infer terminal success/failure from observer activity;
- retain the latest decision for read-only runtime/status projection;
- clear entries on session close;
- do not persist a second lifecycle record.

## Layered status contract

Define or consolidate provider-neutral foundation status types:

- scopes: execution-request, session, turn, workflow;
- lifecycle: pending, active, waiting, completing, available, terminal, unknown;
- outcome: success, failed, cancelled, interrupted, rejected, timed-out, expired, abandoned, superseded, or equivalent established values;
- evidence confidence/acceptance;
- bounded wait reasons;
- decision flags and frozen `AgentStatusSnapshot`.

Lifecycle and outcome must remain separate. `interrupted` is terminal outcome, never a lifecycle value. `replay-required` is a recovery/decision flag, never an outcome or fabricated wait reason.

## Materialization rule

A status field/value may exist only when the producing adapter has a named:

- evidence source;
- correlation rule;
- freshness/validation rule;
- redaction rule;
- focused proof.

Otherwise omit the dimension or leave it unavailable. Do not add generic thinking/generating/streaming/progress/health detail merely for UI convenience. Broad activity and byte/token progress remain deferred until exact validated evidence routes exist.

Canonical v1 dimensions may include lifecycle, outcome, decision flags, evidence acceptance/contradiction, durable reason code, bounded wait reason, dispatch/progress phase, generation/attempt, and observed/projected timestamps.

## Durable-authority precedence

Provide pure adapters that combine AS21 decisions with public/redacted SH07 durable facts:

- durable completed/failed/cancelled/interrupted states always win for terminal lifecycle/outcome;
- running/queued records may use AS21 decisions when available;
- no durable fact and no decision returns pending/unknown conservatively;
- cancellation request/acknowledgement remains active until durable terminal authority commits it;
- request/session/workflow consumers consume snapshots exactly once and do not parse provider event names or phase prose.

AS56 owns final public request-status response integration/versioning.

## Availability and health rules

Rename any runtime boolean called `available` that merely means a handle exists to `live-handle-available` or equivalent. Canonical session `available` means the strict AS21/AS30 reusable-session decision.

Health is separate and may expose only evidence-backed unknown/healthy/degraded/disconnected values at the correct scope. Silence never means unresponsive.

## Files

- `foundation/transports/agent_status.py` or existing canonical status contract;
- `agents_session_lifecycle_projection.py` and pure adapters;
- session runtime evidence registry/status read projection;
- SH07/agent-jobs compatibility adapters where existing public seams permit;
- focused lifecycle/status/architecture tests.

Do not add provider-specific code, persistence, MCP tools, event-bus state, or another recovery authority.

## Validation

Table-driven tests must cover:

- active, waiting, completing, available, failed, and unknown;
- candidate/rejected-only evidence;
- mixed turns, missing correlation, duplicate/lower sequence, out-of-order and contradictory evidence;
- terminal before finalization and commit-before-available;
- cancel with/without commit/cleared work;
- finalization failure and transport close/error;
- identical fake ACP/native evidence producing identical decisions/snapshots;
- durable SH07 completed/failed/cancelled/interrupted precedence;
- interrupted remains distinct from failed/cancelled;
- cancellation acknowledgement remains nonterminal;
- capability-less fields do not appear;
- no content, native payload, raw provider ref, ACP type, or provider status name crosses the projection.

## Acceptance criteria

- Exactly one lifecycle reducer and layered status projection exist.
- Decisions are deterministic, conservative, replay/idempotency safe, and transport independent.
- Terminal availability requires finalization commit and cleared blocking work.
- Durable request authority wins terminal conflicts.
- No status projection writes a durable competing state.
- Public consumers can use provider-neutral snapshots without provider-specific parsing.
