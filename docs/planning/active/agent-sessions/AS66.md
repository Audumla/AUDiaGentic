# Publish logical agents and tasks through A2A

## Goal

Expose selected AUDiaGentic agent definitions as interoperable A2A agents and allow AUDiaGentic to call remote A2A agents through the same canonical task model.

A2A is a task-oriented external protocol adapter. It does not replace the gateway, session runtime, execution profiles, roles, AS29 surface capabilities, AS30 bindings, observability or output authorities.

## Dependencies

- AS62 logical agent definitions, identity, skills and interface policy;
- AS63 canonical agent-task submission/status/result;
- AS64 effective capability snapshots;
- AS31/AS57 canonical content and status reads;
- AS58 canonical controls;
- AS30/AS47/AS49 interaction-session identity and continuation semantics where tasks use persistent context;
- AS65 findings where ACP/A2A share application seams.

## Server surface

For each A2A-enabled agent definition:

- generate a bounded Agent Card from logical identity, advertised skills, supported content modes, authentication scheme and endpoint information;
- accept A2A messages/tasks and map them to `AgentTaskSubmission`;
- create or continue an interaction session only according to explicit task/session policy;
- project working/input-required/completed/failed states from canonical task/lifecycle services;
- project assistant output and artifacts from AS31/task result services;
- map cancellation through AS58/current task control;
- persist explicit bindings between A2A context/task IDs and AUDiaGentic task/session IDs without reusing provider refs.

Provider, model, selected harness surface, launch command and raw session identity remain private implementation details.

## Client and delegation transport

Add an A2A client transport behind an internal `AgentTaskService`/delegation port:

- discover/describe configured remote agents from explicit trusted Agent Card sources;
- submit bounded tasks/messages/artifacts;
- stream or poll task status/results;
- cancel where supported;
- preserve remote task/context identity as opaque external refs;
- apply authentication, allowlists, budgets, timeouts and audit.

Local agent-to-agent dispatch should use direct internal task submission when possible. Remote or third-party agents use A2A. Callers should not need to know which transport was selected.

## Harness access to delegation

Do not inject the A2A SDK directly into Pi, Codex, Claude Code or OpenCode.

Expose a narrow AUDiaGentic delegation capability through existing MCP/tool installation paths only after base server/client behavior is proven. Initial tools may include:

- `agents_find`;
- `agents_describe`;
- `agents_delegate`;
- `agents_task_status`;
- `agents_task_result`;
- `agents_cancel`.

The tool layer invokes the canonical task service, which selects local dispatch or A2A transport. Tool descriptions provide mechanics; a bounded role/delegation policy or skill instructs when delegation is permitted.

## Delegation policy

Initial policy is deterministic/default-deny:

- explicit allowed source agent/role;
- explicit allowed target agents/skills;
- bounded subtask and artifact sizes;
- no secret, credential, hidden-reasoning or unrelated workspace disclosure;
- depth/recursion limit;
- task, token/cost/time budgets;
- source agent remains responsible for the original request;
- returned results are advisory until validated;
- no automatic broad network discovery or arbitrary Agent Card registration from harnesses.

Begin with gateway-controlled workflows. Model-directed delegation is enabled only per role/agent policy after tooling and audit are proven.

## Streaming and task semantics

Map canonical events rather than raw harness events:

- task accepted/working/status -> A2A task status;
- AS31 assistant deltas/final -> A2A message/artifact updates;
- permission or missing information -> `input-required` only where the caller can respond and correlation is preserved;
- terminal result -> completed/failed/cancelled plus final artifacts.

Coalesce high-frequency internal events, preserve terminal/input-required events, bound buffers and allow detached continuation/reconnect according to the A2A task contract. Do not automatically kill a persistent task/session merely because one streaming client disconnects.

## Steps

1. Complete AS65 R6 and AS63 R4 decisions.
2. Select and pin a current A2A SDK/spec version behind a component-local adapter.
3. Add Agent Card projection from `AgentDefinitionSnapshot` and effective capabilities.
4. Add A2A server executor mapping to canonical task services.
5. Add task/context ID bindings, authorization and redaction.
6. Add status/output/artifact streaming and reconnect behavior.
7. Add A2A client transport for trusted configured remote agents.
8. Add local-vs-remote dispatch abstraction.
9. Add optional MCP delegation tools and a minimal delegation policy/role extension.
10. Add end-to-end implementer -> reviewer proof with one local and one remote/wrapped agent.
11. Document how existing ACP-to-A2A wrappers may be used as compatibility/test targets but are not runtime authorities.

## Reassessment gate R7

After the first end-to-end proof:

- review whether task-to-turn mapping is sufficient or AS63 needs a dedicated multi-turn task coordinator;
- review whether Agent Skill schema maps cleanly to real Agent Cards and revise without leaking runtime details;
- review local direct dispatch versus A2A semantic parity;
- review delegation security, recursion, budgets, artifact/workspace transfer and failure handling;
- decide which third-party A2A/MCP bridges remain useful as test fixtures or optional adapters;
- decide whether broader discovery, push notifications or additional transports are justified by demonstrated use.

## Validation

- Agent Card correctness/redaction/stability;
- task submission, streaming, reconnect, cancellation and final artifact;
- optional persistent context across multiple tasks only when policy/session binding allows;
- A2A IDs cannot be used as provider session refs;
- local and remote dispatch produce equivalent canonical task results;
- cross-project/agent/skill authorization;
- malformed/untrusted Agent Card and authentication failure;
- bounded buffering, backpressure and disconnected client continuation;
- MCP delegation default-deny, recursion and budget enforcement;
- no raw ACP/provider events, hidden reasoning, secrets or unrestricted filesystem data;
- end-to-end two-agent collaboration.

## Acceptance criteria

- Selected agent definitions are discoverable and callable through A2A.
- AUDiaGentic can invoke trusted remote A2A agents through the canonical task service.
- Local and remote agents share one task/delegation abstraction.
- Harnesses receive delegation through controlled tools/policy rather than protocol coupling.
- Existing gateway/session/transport/output authorities remain singular.
- R7 findings and any follow-on plans are recorded.
