# Add A2A and controlled agent delegation

## Goal

Publish selected Agent Definitions through A2A and allow AUDiaGentic to call explicitly configured remote A2A agents through the same AgentTask authority.

A2A is a protocol adapter/remote transport, not another runtime, task engine, registry or workflow system.

## Boundaries

- AS63 owns the AgentTask API and bounded runtime gateway access used by harnesses.
- AS62 owns Agent Definition lookup and publication eligibility.
- AS66 adds logical target discovery, delegation authorization and local-versus-remote routing.
- A2A server/client are protocol adapters wired at the composition root.
- Harness extensions/runtime MCPs call the bounded gateway/delegation API, not raw A2A.

Do not create a second task submission path or require a separate gateway MCP when the AS63 runtime surface can be extended cleanly with discovery/delegation operations. Split adapters only when harness integration or tool projection requires it; keep one application authority.

## Harness-facing capability

A running harness needs enough gateway capability to request another AUDiaGentic agent. The minimal logical contract is:

- find/describe permitted agents or skills when selection is needed;
- delegate/submit a bounded task;
- status/result/wait/cancel when asynchronous;
- continue an authorized linked interaction when required.

This may be exposed through:

- the AS63 runtime gateway MCP projection;
- a Pi extension calling the same application API;
- an OpenCode plugin/custom tool calling the same API;
- another provider-native integration with equivalent authorization.

Do not force a duplicate dedicated delegation server if extending the bounded runtime gateway surface is cleaner.

## What remains operator-only

Harness-facing access must not expose:

- Execution Profile, Role or Agent Definition CRUD;
- provider configuration or model credentials;
- global request/session listing;
- gateway-wide overview, reload or configuration;
- unrelated callers' task/session control;
- raw A2A URLs or protocol methods.

## Initial A2A scope

- generate a basic Agent Card from Agent Definition identity, skills and proven interface facts;
- accept an A2A message/task and submit existing AgentTask work;
- expose existing status, final output and cancellation;
- call explicitly configured trusted remote Agent Cards;
- use direct local dispatch for local agents;
- keep A2A identifiers separate only where the protocol requires them.

Do not add broad discovery, push notifications, multiple transports, new task stores or multi-turn task machinery until demonstrated.

## Harness integration order

1. Prove the bounded runtime gateway/delegation contract with one existing harness path.
2. Pi extension using the familiar subagent-style call where it improves UX.
3. Runtime MCP projection for Claude Code, Codex and OpenCode through existing provider materialization.
4. OpenCode plugin/custom tool only if it adds proven value beyond MCP.

For every harness and launch path, prove the capability reaches the child:

- one-shot/direct CLI;
- AUDiaGentic harness runner;
- ACP/RPC bridge;
- daemon/wrapper path where present.

A provider-wide `mcp_config` declaration or direct-CLI test does not prove an ACP/RPC bridge receives the tools.

## Runtime tool policy interaction

AS66 adds or extends only the explicit gateway/delegation capability. It does not implement general Role-driven tool selection.

- Existing harness default/configured runtime tools remain unchanged.
- Gateway/delegation access is added only for Agent Definitions permitted to delegate.
- Do not normalize or replace the rest of the harness tool set.
- If exact request-owned isolation is required but unavailable, fail closed or mark that launch path unsupported.

## Safety

Start default-deny with:

- explicit source Agent Definition and allowed target/skill;
- task ownership scoped to the calling agent/session;
- bounded task text and selected artifacts/context;
- recursion depth;
- timeout and cancellation;
- authorization/audit correlation;
- no credential, raw environment or unrestricted project-root transfer.

Reuse current authorization, policy, redaction and audit owners. Do not create a second security or budget framework.

## Work

1. Prove local agent-to-agent delegation through the AS63 runtime gateway API without A2A.
2. Add logical agent/skill discovery only where a caller needs it.
3. Define target authorization and local-versus-remote routing behind the application boundary.
4. Add the A2A server adapter over AgentTask/Agent Definition public APIs.
5. Add one trusted remote A2A client transport.
6. Extend or project the runtime gateway capability into each supported harness.
7. Validate materialization and visibility independently for each launch path.
8. Prove implementer -> reviewer locally, then remotely.
9. Prove runtime callers cannot invoke operator/admin operations or control unrelated tasks.
10. Reassess whether one-task/one-turn remains sufficient.

## Do not add

- a separate A2A task store/runtime;
- a duplicate delegation task service;
- raw A2A SDK use in harnesses or agents core;
- automatic network discovery;
- a new workflow engine;
- copied definitions or snapshot stores;
- complex delegation graphs, catalogue infrastructure or budget systems;
- direct internal-module imports, shims or compatibility routes;
- broad runtime tool-policy management.

## Validation

Required proofs:

- local delegation uses existing AgentTask request/turn/status/output/cancel owners;
- remote A2A maps to the same logical result without another durable task engine;
- only published Agent Definitions produce Agent Cards;
- only trusted remote endpoints are callable;
- delegation target authorization is default-deny;
- runtime gateway operations are available to the harness;
- operator/admin operations and unrelated tasks are unavailable;
- direct CLI and each ACP/RPC/daemon bridge independently expose the intended tools;
- cancellation and timeout propagate across local and remote calls;
- recursion is bounded and audited;
- Pi/OpenCode/Claude/Codex integrations consume the same logical contract even when their mechanisms differ.

## Acceptance criteria

- Local and remote delegation use the same canonical AgentTask authority.
- Harnesses can request AUDiaGentic agents through bounded gateway/delegation access.
- A2A is replaceable behind one narrow injected remote transport boundary.
- Runtime and operator scopes share gateway logic without sharing privileges.
- Existing gateway/session/output/control/security owners are reused.
- Provider launch-path support is evidence-based and fails closed when unsupported.
- The first implementation is small, tested and demonstrable.
