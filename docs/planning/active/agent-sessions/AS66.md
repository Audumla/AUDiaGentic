# Add A2A and controlled agent delegation

## Goal

Publish selected Agent Definitions through A2A and allow AUDiaGentic to call explicitly configured remote A2A agents through the same agent-work API.

A2A is a protocol adapter/remote transport, not another runtime, task engine, registry or workflow system.

## Boundaries

Use existing public APIs where possible:

- the AS63 agent-work API submits, reads and cancels local work;
- one narrow delegation API selects local agent work or remote A2A transport;
- the A2A server/client and harness MCP/extensions are protocol adapters wired at the composition root.

Do not create a global agent registry. Local agents come from the Agent Definition owner. Remote agents come from explicit trusted configuration; add a separate catalogue only if a demonstrated second consumer and lifecycle require one.

## Initial A2A scope

- generate a basic Agent Card from Agent Definition identity, skills and proven interface facts;
- accept an A2A message/task and submit existing AgentTask work;
- expose existing status, final output and cancellation;
- call explicitly configured trusted remote Agent Cards;
- use direct local dispatch for local agents;
- keep A2A IDs separate from provider-session references.

Do not add broad discovery, push notifications, multiple transports, new task IDs/stores or multi-turn task machinery until a demonstrated case requires them.

## Harness delegation

Expose only the tools needed for the first proof:

- `agents_find` or `agents_describe` only if the model must choose among multiple permitted targets;
- `agents_delegate`;
- status/result/cancel only when delegation is not handled synchronously by the first implementation.

Integration order:

1. Pi extension using the familiar subagent-style call where practical.
2. Shared MCP adapter for Claude Code, Codex and OpenCode.
3. OpenCode plugin/custom tool only if it adds proven value beyond MCP.

Use one simple per-Agent/Role delegation mode only when needed: `audiagentic-only`, `prefer-audiagentic`, `native-allowed` or `native-only`. Do not build a policy engine around these values.

## Safety

Start default-deny with explicit source/target permission, bounded task/context/artifact input, recursion depth, timeout and cancellation. Reuse current authorization, policy and audit owners. Do not create a second security or budget framework.

## Work

1. Prove local delegation through the AS63 API first.
2. Add the A2A server adapter.
3. Add one trusted remote A2A client transport.
4. Add the minimum harness extension/MCP projection.
5. Prove implementer -> reviewer locally, then remotely.
6. Reassess whether existing one-task/one-turn behavior remains sufficient.
7. Delete any superseded delegation route, handler or test in the same change.

## Do not add

- a separate A2A task store/runtime;
- a general AgentDelegation framework when one small application operation suffices;
- raw A2A SDK use in harnesses or agents core;
- automatic network discovery;
- a new workflow engine;
- copied definitions or snapshots;
- complex delegation graphs, catalogue infrastructure or budget systems;
- direct internal-module imports, shims or compatibility routes.

## Acceptance criteria

- Local and remote delegation use the same canonical agent-work authority.
- A2A is replaceable behind one narrow injected remote transport boundary.
- Harnesses delegate through thin extension/MCP adapters.
- Existing gateway/session/output/control/security owners are reused.
- The first implementation is small, tested and demonstrable.
