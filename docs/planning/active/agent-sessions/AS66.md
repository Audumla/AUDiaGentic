# Add A2A and controlled agent delegation

## Goal

Publish selected Agent Definitions through A2A and allow AUDiaGentic to call explicitly configured remote A2A agents through the same AgentTask authority.

A2A is a protocol adapter/remote transport, not another runtime, task engine, registry or workflow system.

## Boundaries

Use existing public APIs where possible:

- the AS63 AgentTask API submits, reads and cancels local agent work;
- one narrow delegation operation selects local AgentTask work or remote A2A transport;
- the A2A server/client are protocol adapters wired at the composition root;
- the harness-facing delegation extension/runtime MCP is a separate activity capability projected into providers through the existing component/provider materialization path.

Do not create a global agent registry. Local agents come from the Agent Definition owner. Remote agents come from explicit trusted configuration; add a separate catalogue only if a demonstrated second consumer and lifecycle require one.

## Management versus runtime MCP

The harness delegation surface is a runtime capability, not a management MCP.

It must:

- expose only bounded delegation operations needed by the running agent;
- use a dedicated activity server or provider extension with provider propagation;
- be materialized through existing component activity-MCP projection and provider launch-surface APIs;
- use request-owned/exact MCP isolation where the provider launch path supports it;
- carry caller/session identity and authorization context without exposing admin configuration.

It must not expose:

- Execution Profile/Role/Agent Definition CRUD;
- provider configuration or model credentials;
- gateway list/overview/reload/admin functions;
- arbitrary AgentTask submission to unrestricted targets;
- raw A2A protocol methods or remote URLs.

Do not reuse `ag-agents-mgmt`, the current profile-resolution `ag-agents`, or `ag-agents-gateway` as the delegation server.

## Initial A2A scope

- generate a basic Agent Card from Agent Definition identity, skills and proven interface facts;
- accept an A2A message/task and submit existing AgentTask work;
- expose existing status, final output and cancellation;
- call explicitly configured trusted remote Agent Cards;
- use direct local dispatch for local agents;
- keep A2A IDs separate from provider-session references and existing AgentTask IDs where the protocol requires its own identifier.

Do not add broad discovery, push notifications, multiple transports, new task stores or multi-turn task machinery until a demonstrated case requires them.

## Initial harness delegation surface

Start with the minimum useful contract:

- `agents_delegate(target_or_skill, task, bounded_context)`;
- optional `agents_describe` only when the model must choose among multiple permitted targets;
- status/result/cancel only when the first implementation is asynchronous and cannot return the bounded result directly.

Target resolution, permissions, recursion limits and local-versus-remote routing remain behind the application boundary. The model sees logical agents/skills, not provider IDs, profile IDs, process details or A2A endpoints.

## Harness integration order

1. Pi extension using the familiar subagent-style call where practical.
2. Dedicated activity MCP for Claude Code, Codex and OpenCode through the existing provider projection path.
3. OpenCode plugin/custom tool only if it adds proven value beyond the activity MCP.

For every harness and launch path, prove the tool actually reaches the child:

- one-shot/direct CLI;
- AUDiaGentic harness runner;
- ACP/RPC bridge;
- daemon/wrapper path where present.

A provider-wide `mcp_config` declaration or direct-CLI test does not prove the ACP/RPC bridge sees the delegation tool. Follow the harness viability guidance and test each bridge independently.

## Runtime tool policy interaction

AS66 adds only this explicit delegation capability. It does not implement general Role-driven tool selection.

- Existing harness default/configured runtime tools remain unchanged.
- The delegation server is added only for Agent Definitions explicitly allowed to delegate.
- Do not normalize or replace the rest of the harness tool set.
- If exact request-owned tool isolation is required but unavailable for a launch path, fail closed or mark that path unsupported; do not silently expose management or ambient tools.

## Safety

Start default-deny with:

- explicit source Agent Definition and allowed target/skill;
- bounded task text and selected artifacts/context;
- recursion depth;
- timeout and cancellation;
- authorization/audit correlation;
- no credential, raw environment or unrestricted project-root transfer.

Reuse current authorization, policy, redaction and audit owners. Do not create a second security or budget framework.

## Work

1. Prove local delegation through the AS63 API first without A2A.
2. Define one narrow delegation application operation and authorization contract.
3. Add the A2A server adapter over AgentTask/Agent Definition public APIs.
4. Add one trusted remote A2A client transport.
5. Add a dedicated Pi extension and/or activity MCP projection for harness calls.
6. Validate materialization and visibility independently for each supported launch path.
7. Prove implementer -> reviewer locally, then remotely.
8. Prove the runtime delegation surface cannot call management/admin APIs.
9. Reassess whether existing one-task/one-turn behavior remains sufficient.
10. Delete any superseded delegation route, handler or test in the same change.

## Do not add

- a separate A2A task store/runtime;
- a general AgentDelegation framework when one small application operation suffices;
- raw A2A SDK use in harnesses or agents core;
- automatic network discovery;
- a new workflow engine;
- copied definitions or snapshot stores;
- complex delegation graphs, catalogue infrastructure or budget systems;
- direct internal-module imports, shims or compatibility routes;
- management MCP exposure to providers;
- broad runtime tool-policy management.

## Validation

Required proofs:

- local delegation uses existing AgentTask request/turn/status/output/cancel owners;
- remote A2A maps to the same logical result without creating another durable task engine;
- only explicitly published Agent Definitions produce Agent Cards;
- only explicitly trusted remote endpoints are callable;
- delegation target authorization is default-deny;
- management tools are absent from the provider-visible tool inventory;
- empty and disjoint runtime MCP sets behave correctly where exact isolation is claimed;
- direct CLI and each ACP/RPC/daemon bridge independently expose the intended delegation tool;
- cancellation and timeout propagate across local and remote calls;
- recursion is bounded and audited;
- Pi/OpenCode/Claude/Codex integrations consume the same logical delegation contract even when their extension mechanisms differ.

## Acceptance criteria

- Local and remote delegation use the same canonical AgentTask authority.
- A2A is replaceable behind one narrow injected remote transport boundary.
- Harnesses delegate through a dedicated thin runtime extension/activity MCP.
- Management MCPs remain inaccessible to launched providers.
- Existing gateway/session/output/control/security owners are reused.
- Provider launch-path support is evidence-based and fails closed when tool isolation/materialization is unsupported.
- The first implementation is small, tested and demonstrable.
