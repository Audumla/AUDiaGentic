# Roll out remaining harness session surfaces through the proven platform

## Description

This deferred parent owns the complete backlog of additional harness surfaces after the named Pi, OpenCode, and Codex plans. Each exact surface is implemented through a separate successor plan and pull request using the canonical platform; this file is not a multi-provider implementation bucket.

## Goal

Integrate remaining harnesses without changing the canonical architecture or collapsing distinct product modes into one provider capability.

## Relationship to concrete plans

This is the parent/backlog owner for surfaces that do not already have a concrete carried-forward plan. Use these concrete plans first:

- AS55 — OpenCode ACP;
- AS50 — Codex ACP;
- AS51 — Codex App Server;
- AS54 — observer recipe/probe matrix.

Create a successor plan/PR per additional exact surface. Do not implement multiple unrelated providers directly inside AS46.

## Candidate rollout

After probe/value review, consider independently:

- Claude ACP;
- Claude CLI hooks as observer route;
- Gemini ACP;
- Gemini CLI hooks;
- Qwen ACP;
- Cline ACP and Cline SDK/CLI as separate surfaces;
- Goose ACP/API;
- Copilot ACP;
- Kilo ACP;
- OpenHands Canvas/WebSocket/API;
- OpenCode native server/CLI/plugin route;
- Continue structured one-shot mode;
- other validated candidates from AS54.

Aider, Plandex, Roo, terminal UIs, editor-hosted threads, and unresolved routes remain process-only/O0 when locally owned and otherwise unsupported until a machine-consumable correlated route is proven.

## Per-surface child-plan requirements

Every child plan must define:

1. exact provider/surface ID, mode, version, and platforms;
2. native protocol/launch/ownership and process isolation;
3. AS29 descriptor entry and registered factories only after probe;
4. AS30 provider ref scope, identity context, open/attach/resume/discovery rules;
5. AS19 neutral observation mapping and AS54 recipe;
6. AS21 lifecycle/status expectations and limitations;
7. AS31 content channels/bounds or explicit disabled set;
8. generic internal controls/capabilities and typed unsupported behavior;
9. cleanup/recovery/external ownership semantics;
10. Windows/Linux/Docker and transcript/conformance tests;
11. obsolete provider-specific path deletion.

## Prohibitions

- no provider-name branch in agents/gateway;
- no new session store, lifecycle engine, event bus, capability registry, content store, output selector, process manager, or recovery authority;
- no assumption that CLI, ACP, app server, SDK, extension, hook, editor, and underlying provider session share identity;
- no hooks/plugins as transport/control owner;
- no promotion from documentation without exact probe evidence;
- no fallback to prose/terminal scraping.

## Completion

AS46 completes only when every listed candidate is either:

- implemented by a completed child plan;
- split into a named pending successor with full scope;
- explicitly classified unsupported/removed with evidence and documentation.

Landing one provider does not complete AS46.

## Acceptance criteria

- Every candidate in this plan has a completed child plan, a fully scoped pending successor, or an evidence-backed unsupported/removed disposition.
- Each implemented child uses AS19/AS21/AS29/AS30/AS31 without provider-name branches or duplicate authorities.
- Distinct CLI, ACP, app-server, SDK, extension, hook, editor, and provider-thread identities remain separate unless exact equivalence is proven.
- No candidate is promoted from documentation alone.
- AS46 closes only when the entire remaining-surface inventory is dispositioned.
