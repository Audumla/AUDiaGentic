# Recover stale GPT-auto DOM and classify provider failures safely

## Description

When a live ChatGPT conversation reports a DOM error marker, the gateway must distinguish a transient/stale UI marker from a confirmed terminal provider failure. It must preserve the active request while provider activity or complete response evidence remains credible, and expose bounded evidence for diagnosis.

## Steps

- Replace broad immediate error-page terminalization with a typed provider-observation diagnostic that records matched selectors, bounded visible text, URL, target/page identity, correlation counts, activity labels, and observation time.
- Evaluate completion and fresh provider activity before treating an error marker as terminal; require error evidence stability across a bounded window and no contradictory activity.
- Renew the activity lease whenever provider activity arrives, including after a prior lease-expiry diagnostic; lease expiry must enter reconciliation, not force terminal failure.
- On a complete correlated response, persist the response artifact before any failure transition.
- Perform at most one same-conversation refresh/re-read without resubmitting the prompt; preserve unresolved binding when proof is unavailable.
- Keep authentication/rate-limit/provider-terminal failures fail-closed with explicit classifications and bounded diagnostics.
- Keep public status slim; expose detailed evidence only through agent_task_diagnostics.

- Add measurement-only initial-response instrumentation: record prompt-submit, CDP navigation/target observation, first user-message correlation, first DOM mutation, first provider activity, response-started, first assistant text, and terminal timestamps for every GPT-auto attempt.
- Derive initial-response latency from attempt start/send confirmation to first credible provider activity/response-started; report p50/p95 from characterization runs rather than hard-coding a threshold from one sample.
- Add an explicitly experimental, disabled-by-default recovery policy for no-response/blank/stale pages. After a configurable observation grace, capture a pre-refresh snapshot and perform at most one same-conversation refresh/reread only when there is no activity, no correlated response, and the page is blank/loading/non-composer; never refresh or resubmit while activity, generation, tool/thinking signals, or a correlated response exists.
- Record refresh attempted/result and post-refresh first-signal latency in protected diagnostics so the experiment can be judged before enabling automatic recovery.

- Classify the visible ChatGPT `Message delivery timed out. Please try again.` state as a distinct delivery-timeout observation, separate from generic error-page/error-alert and from the old project landing-page failure.
- When that observation is stable and the request has not already produced a correlated terminal response, allow one provider-side Retry-button recovery (`[data-testid="regenerate-thread-error-button"]`, with visible-text/aria fallback) and return to normal observation. Do not inject or submit the prompt again.
- Record retry eligibility, click/activation result, pre/post URL and message counts, and first post-retry activity/response timestamps in protected diagnostics; exhaust the allowance as an explicit recoverable failure rather than looping.

## Detailed Solution & Technical Design

AS119 owns provider observation recovery. In snapshot.py/PageObservation, retain the exact matched DOM signal identity and bounded text evidence instead of only boolean error_present. In turn.py, order response-complete and activity reconciliation ahead of response-failed; an error marker alone is provisional. A provisional marker must remain present for the configured error-stability interval and be accompanied by no fresh activity, no generating/tool/thinking signal, and no newly correlated terminal response before EXT-GPTAUTO-003 is emitted. Activity after activity.lease-expired-diagnostic renews the lease and returns the turn to observing. If response evidence is complete, the existing OutputStore terminal ordering wins. Persist protected attempt diagnostics with provider URL, target/page, selector IDs, counts, message IDs, text digest/length, matched policy, and timestamps; sanitize the public projection to classification, reason code, activity type/sequence, and bounded evidence metadata.

Initial-response experiment: the existing turn.response-start-timeout-seconds (currently 120) remains a safety ceiling, not evidence of failure. Add a separate experimental observation block in gpt-auto defaults (for example turn.initial-response-observation-grace-seconds, turn.initial-response-refresh-enabled=false, turn.initial-response-refresh-attempts=1, turn.initial-response-refresh-cooldown-seconds) and validate these as provider configuration. The watcher records monotonic elapsed values plus UTC event timestamps and CDP observation facts: target/page identity, URL, ready state, document title, body/message counts, composer/stop controls, DOM signal labels, and bounded digests/lengths—not full DOM or prompt text. A refresh is eligible only after the grace interval and only if the last observation is blank/stale or lacks the submitted-turn correlation and no provider activity has been seen. Refresh re-reads the same conversation URL, does not click send, and returns to normal observation. Any activity or response evidence cancels the refresh path. The experiment is diagnostic-first and must demonstrate successful recovery on controlled live runs before its enabled flag is changed.

The current live tab is a conversation URL and exposes `Message delivery timed out. Please try again.` plus `button[data-testid="regenerate-thread-error-button"]` with text `Retry`. This is provider UI recovery, not a caller retry. Add a dedicated DOM signal/policy (for example `delivery-timeout-retry`) that captures the exact selector and bounded visible text. In the turn watcher, evaluate this signal after checking for a complete correlated response and while preserving any fresh activity; then invoke a provider-owned `retry_delivery_timeout(page)` action that clicks the existing Retry control once. Fence it with an attempt-local boolean and a cooldown/stability window. The action must not call submit(), type into the composer, or create a new user message. After activation, continue polling the same conversation and correlate only the original turn. If Retry is absent, disabled, ambiguous, or the single allowance is consumed, emit a precise recoverable diagnostic with `retry-available`/`retry-attempted` fields and let normal failure/reconciliation decide. Keep this path experimental and configuration-gated until live evidence proves it recovers a timed-out delivery without duplicate turns.

## Effort & Risk

## Standards

AS119; AS92 canonical status semantics; GP48 diagnostic meaning/evidence; AS102 public sanitization and bounds.

## Acceptance Criteria

- A transient/stale error marker cannot terminalize an active turn while provider activity or a complete correlated response is present.
- A confirmed stable provider-terminal error still fails closed with EXT-GPTAUTO-003 and a precise reason.
- Activity received after lease expiry renews the request and prevents false failure.
- Diagnostics identify the exact matched signal and bounded evidence without exposing paths, prompts, or full output.
- Recovery never submits the same prompt twice.
- Full response artifacts are persisted before successful terminalization.

- Initial-response latency is recorded for every attempt with explicit event names and no synthetic activity increments.
- The response-start ceiling is not treated as proof of provider failure when CDP activity or correlated response evidence is present.
- Experimental refresh is disabled by default, bounded to one same-conversation reread, never resubmits, and is vetoed by any credible activity/response.
- Diagnostics show whether refresh was eligible/attempted/succeeded and include bounded CDP observation metadata without DOM dumps, paths, prompts, or full output.
- Automatic recovery is not enabled until controlled live evidence demonstrates that refresh resolves a stale/blank page without causing duplicate submissions or false terminalization.

- `Message delivery timed out` is identified distinctly from generic error-page and recorded with bounded UI evidence.
- A single existing Retry control can be activated without typing or resubmitting the prompt.
- Any activity or complete correlated response prevents unnecessary retry.
- Retry outcome and post-retry latency are durable diagnostics, while public status remains slim.
- Exhausted/ambiguous retry fails with a precise recoverable classification and cannot loop or create duplicate turns.
