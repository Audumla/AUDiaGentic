## Goal

Rename the existing provider/model execution configuration to `ExecutionProfile` without changing queue, admission or session behavior.

The project YAML, agents public CRUD API, and `ag-agents-mgmt` MCP are one configuration-management path. Shared-gateway mode resolves additional admission facts; it is not a second management authority.

An Execution Profile contains only provider/model, selected AS29 surface or provider default, launch parameters, queue/admission settings and existing session-lifetime settings. It does not own Role, runtime tools, permissions, skills or ACP/A2A publication.

## Public boundary and composition

Provide one narrow Execution Profile public API/resolver, returning one schema-validated shape
(`ResolvedExecutionProfile`) regardless of which concrete implementation produced it. Project and
shared modes have different concrete implementations behind that one contract — but they are not
a composition *binding* selected by stable ID (RV888 correction against AS59, 2026-08-04):

- **Project-local resolution stays a plain function.** It is stateless — reads
  `execution-profiles.yaml` fresh, holds no connection, needs no shutdown — so there is nothing
  for composition to own. Management MCP/CLI call CRUD/config APIs directly, as today.
- **The shared-gateway registry becomes a composed singleton in a second composition root**,
  specific to the gateway-service process entrypoints (`agents_gateway_service_process.py::main()`,
  `commands/gateway.py::cmd_gateway`) — not a binding in the shared `composition.yaml` selected by
  project/shared implementation IDs. Install/uninstall become that root's construction/shutdown,
  the same pattern `runtime.application-host` already uses for `InteractionBackend`. This is the
  "later roots are deliberate" case Stage 1's own test docstring anticipated
  (`test_the_launcher_is_the_only_caller_of_the_composition_root`), not a new mechanism.
- Gateway admission calls whichever resolver its process composed; it does not branch on registry
  presence itself, and it does not know which root built it.
- Core code does not import stores, concrete registries or the composition graph.

Why not one binding with two implementation IDs (the first design considered, before RV888):
project-vs-shared is not a per-deployment config choice a project operator makes — it is
determined by which process is running. Modeling it as a binding conflates AS59's own
binding-vs-composed-singleton distinction ("conflating them is the other way a composition root
becomes a container").

## Steps 2 And 7 Landed 2026 08 04

**Implemented per RV888's corrected design.**

Step 2 (one public resolver contract): `ResolvedExecutionProfile` now validates itself against a new `resolved-execution-profile.schema.json` at construction (`__post_init__`), registered in `canonical_ids.py`'s `CANONICAL_SCHEMA_IDS`. `agents_gateway_profiles.resolve_for_admission(project_root, execution_profile_id)` is the one contract: it always returns a `ResolvedExecutionProfile`, resolving via the shared-gateway registry when one is installed for this process, otherwise via project-local `execution-profiles.yaml` wrapped through `snapshot_from_resolved_profile()`. `agents_gateway_api.submit_execution_request` calls it instead of inlining the registry-presence branch. Persisted-record semantics are deliberately unchanged: `gateway-profile-id` and friends still persist as `None` in embedded mode -- extending staleness protection to embedded-mode records would be a real behavior change and was kept out of this item's scope.

Step 7 (composition): `runtime/bootstrap/gateway_service_composition.py` is a second composition root -- a composed singleton, not a binding with project/shared implementation IDs (the corrected shape, not the first one considered). Its sole caller is `agents_gateway_service_host.py`; `GatewayServiceHost.create()` builds the graph before constructing the host (with exception-safety so a failure in between still uninstalls the registry), `close()` calls `graph.shutdown()`. `foundation/composition/config.py`'s `namespace` became a parameter so this root's own `gateway-service-composition.yaml` never collides with the launcher root's `composition.yaml`. New architecture tests mirror Stage 1's: sole-caller, no-python-paths, config/contributions agreement, error-code registration.

**Honest gap, not glossed over:** the acceptance-criteria line "no module-global registry getter/setter survives in touched code" is not fully met. `get_gateway_registry()`/`set_gateway_registry()` still exist and are read by `resolve_for_admission()` and (for the embedded-mode-persistence decision) by `submit_execution_request` directly. Composition now owns *construction* of the registry (one configured path, no legacy fallback -- that acceptance-criteria line IS met), but the *access* seam is still a module global because `agents_gateway_api` exposes its surface as free functions, which cannot receive an injected dependency without a signature change (AS59's own root-cause finding). Reshaping that surface is explicitly AS63's scope per AS59's disposition table, not this item's. Full `tests/unit` green except two pre-existing unrelated failures.

Remaining for this item: step 5 (AS29 surface selection, correctly deferred), and closing the global-getter gap if/when AS63's surface reshaping lands. Do not mark this item completed while `get_gateway_registry`/`set_gateway_registry` remain read directly outside the composition root.
