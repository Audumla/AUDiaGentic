# Rename current agent profiles to execution profiles

## Goal

Rename the existing provider/model execution configuration to `ExecutionProfile` without changing queue, admission or session behavior.

Do not collapse the two current deployment authorities:

- project-local configuration selects an execution-profile ID in embedded/project mode;
- the shared gateway registry is authoritative for provider, model, execution parameters, generation and queue limits in shared mode.

Expose both through one framework-neutral resolution boundary. Do not create a third profile authority.

An Execution Profile contains only:

- provider and model;
- selected AS29 session surface;
- launch/execution parameters;
- concurrency, queue and existing session-lifetime settings.

It does not contain role instructions, tool sets, permissions, skills, ACP/A2A publication or copied capability claims.

## Current code to migrate

Characterize and migrate together:

- `components/agents/models.py::AgentProfile` and `AgentProfilesStore`;
- `components/agents/agents_api.py` project-local load/save/resolve operations;
- `components/agents/agents_gateway_profiles.py` shared-gateway registry, lane key and immutable admission value;
- `agents_gateway_api.py` profile resolution and module-level registry access;
- configuration paths, MCP/CLI callers, schemas, error codes, tests and documentation.

The immutable `GatewayProfileSnapshot` behavior is currently required for stale-generation rejection and queue-lane identity. Keep that behavior, but use simple terminology such as `ResolvedExecutionProfile`; do not introduce a broader snapshot hierarchy or persist copied profile definitions.

## Boundary and wiring

Provide one narrow execution-profile resolver/public API that returns the active resolved execution facts required by admission. It may use the project store or shared-gateway authority according to the current deployment mode.

- Callers do not import YAML stores or concrete registries.
- The shared gateway host/composition root supplies the active registry/resolver explicitly.
- Remove module-global registry selection where this migration can do so without introducing a container.
- Do not add a service locator or new registry.

## Work

1. Inventory every `AgentProfile`, gateway-profile, registry, config key, dotted path, API, test and ID use.
2. Define the exact authority rule for embedded/project and shared-gateway modes in the public resolver contract.
3. Rename models, APIs, stores, immutable admission value, configuration, documentation and tests in place.
4. Preserve generation/digest, stale-work rejection and queue-lane behavior.
5. Add exact AS29 surface selection; AS29 remains capability authority.
6. Update every caller in the same change.
7. Delete old Agent Profile names, paths, schemas, handlers, fixtures and tests.
8. Replace direct concrete-store and module-global registry lookup with explicit resolver dependencies at application/composition boundaries.
9. Add architecture/search tests proving no old terminology or second profile authority remains.

Do not add migration aliases, legacy config readers, dual writes, fallback field names or compatibility handlers. An exception requires a documented external obligation approved before implementation.

## Active session data

A live session records only the minimum active execution facts already required for continuation and cleanup: execution-profile ID, provider, model, surface, existing generation/digest fields and execution-context identity. Do not store a copied Execution Profile.
