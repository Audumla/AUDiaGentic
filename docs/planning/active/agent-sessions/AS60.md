# Implement real ACP client-side fs/terminal execution (thaw AS28's control-only scope)

## Description

`AcpAgentSessionTransport`'s session client (`foundation/transports/acp.py`) implements `request_permission` for real (forwards to the observer via `turn.emit(...)`, defers the decision to an injectable `policy_fn`, defaults to deny) but stubs `write_text_file`, `read_text_file`, `create_terminal`, `terminal_output`, `release_terminal`, `wait_for_terminal_exit`, and `kill_terminal` as hard `raise NotImplementedError`, on the theory that AS28's scope was "control/observation only."

That theory is wrong. In ACP the client is the execution backend for filesystem and terminal operations — the agent has no shell or filesystem of its own; it can only act by asking the client to do it. Refusing these calls doesn't narrow the transport to "observation only," it makes any tool-using prompt strand: the agent sends the request over stdout and blocks waiting for a response, and when none arrives it eventually gives up and tears the session down. This was found directly, not theorized: a real Docker e2e run driving Pi through a tool-invoking prompt via the raw JSON-RPC harness produced a clean child-process EOF (not a hang) at exactly this point — the agent gave up waiting.

This affects the real dispatch path, not a side branch. `AcpAgentSessionTransport.prompt()` (via `agents_gateway_session_dispatch.py`'s `dispatch_prompt`) is the actual mechanism `SessionRuntime` uses to send real prompts and get real responses for orchestrated/headless coding work through the agents gateway — not a passive observer sitting beside some other execution path. Since editing files and running commands is the point of dispatching a coding task, this stubs out the mainline case, not an edge case. It was never caught by AS49/AS41's extensive test-writing because every test built this session used plain-text-only prompts ("Reply with exactly: OK") — none exercised a tool-using turn through the real transport.

## Steps

1. Implement `write_text_file`/`read_text_file` against the session's real project root (the `cwd` passed at `session/new`), following the same real-execution + `turn.emit(...)` forwarding pattern `request_permission` already uses — no separate "observation" mechanism needed, forwarding the real operation's outcome through the existing sink IS the observation.
2. Implement `create_terminal`/`terminal_output`/`wait_for_terminal_exit`/`release_terminal`/`kill_terminal` as a real bounded subprocess execution backend scoped to the session's project root, again forwarding start/output/exit through `turn.emit(...)`.
3. Route both fs and terminal operations through the same default-deny `policy_fn` gate `request_permission` already has — a caller that wants to allow tool execution supplies a policy; the default stays conservative.
4. Decide and document bounds: output byte limits (mirror `MAX_PAYLOAD_BYTES`/`MAX_TOTAL_BYTES`), path confinement to the project root (reject writes/reads outside `cwd`), and process lifetime/kill semantics for terminals that outlive their turn.
5. Update `docs/reference/AGENT_TRANSPORTS.md` if/when it's created (see note below — it doesn't exist despite RV512 asking for it); until then, `acp.py`'s own docstring is the authoritative description and has been updated to reflect the soft-freeze framing and this item.
