# Rename current agent profiles to execution profiles

## Goal

Rename the existing provider/model profile to `ExecutionProfile` without creating a second store or changing gateway behavior.

An Execution Profile contains only:

- provider and model;
- selected AS29 session surface;
- launch/execution parameters;
- concurrency, queue and existing session-lifetime settings.

It does not contain role instructions, tools, permissions, skills, ACP/A2A publication or copied capability claims.

## Service boundary

Migrate the existing profile API/store into one `ExecutionProfileService` or equivalent public boundary. Callers depend on that boundary, not YAML/files or concrete registry classes. Keep current composition wiring until the later IoC/DI refactor; do not add a container here.

## Work

1. Inventory every current `AgentProfile`, gateway-profile, registry, config key, dotted path, API, test and ID use.
2. Rename models, APIs, stores, configuration, documentation and tests in place.
3. Preserve existing generation/digest and queue-lane behavior where already used.
4. Add exact AS29 surface selection; AS29 remains capability authority.
5. Update every caller in the same change.
6. Delete old Agent Profile names, paths, schemas, handlers, fixtures and tests after migration.
7. Remove direct concrete-store imports from consumers where the existing API can be injected instead.
8. Add architecture/search checks proving no production or test references to the old terminology remain.

Do not add migration aliases, legacy config readers, dual writes, fallback field names or compatibility handlers. An exception requires a documented external obligation approved before implementation.

## Active session data

A live session records only the minimum active execution facts already required for continuation and cleanup, such as execution-profile ID, provider, model, surface and existing execution-context identity. Do not store a copied Execution Profile.

## Reassess before AS61

Confirm:

- the profile remains execution/admission configuration only;
- no second profile store exists;
- one-shot and persistent-session behavior is unchanged;
- no extra execution-variant abstraction is needed;
- the service can be faked without loading provider config;
- the old Agent Profile API/config path is fully deleted.

## Acceptance criteria

- `ExecutionProfile` replaces current production `AgentProfile` terminology.
- Existing profile infrastructure is migrated, not duplicated.
- AS29 owns surface capabilities.
- No Role or Agent Definition fields enter Execution Profile.
- Consumers use a clear DI-ready profile service boundary.
- No legacy aliases, shims, handlers, dual routes or compatibility tests remain.
