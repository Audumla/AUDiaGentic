# Rename current agent profiles to execution profiles

## Goal

Rename the existing provider/model execution configuration to `ExecutionProfile` without changing queue, admission or session behavior.

The project YAML, agents public CRUD API, management MCP tools and AUDiaGentic CLI are one configuration-management path. They all manage the same project Execution Profile definitions; they are not parallel definitions or separate authorities.

Shared-gateway mode has a distinct runtime authority for admitted execution facts such as provider, model, execution parameters, generation and queue limits. Preserve that deployment behavior behind the same framework-neutral resolution boundary. Do not create another profile definition or management path.

An Execution Profile contains only:

- provider and model;
- selected AS29 session surface;
- launch/execution parameters;
- concurrency, queue and existing session-lifetime settings.

It does not contain role instructions, tool sets, permissions, skills, ACP/A2A publication or copied capability claims.

## Current code to migrate

Characterize and migrate together:

- `components/agents/models.py::AgentProfile` and `AgentProfilesStore`;
- `components/agents/agents_api.py` project-local load/save/CRUD/resolve operations;
- management MCP and CLI adapters that call that same public API;
- `components/agents/agents_gateway_profiles.py` shared-gateway registry, lane key and immutable admission value;
- `agents_gateway_api.py` profile resolution and module-level registry access;
- configuration paths, schemas, error codes, tests and documentation.

The immutable `GatewayProfileSnapshot` behavior is currently required for stale-generation rejection and queue-lane identity. Keep that behavior, but use simple terminology such as `ResolvedExecutionProfile`; do not introduce a broader snapshot hierarchy or persist copied profile definitions.

## Boundary and wiring

Keep one owned project configuration API for Execution Profile management and one narrow execution-profile resolution API for admission.

- CLI and MCP remain thin adapters over the same project configuration API.
- They do not own profile persistence, validation or alternate definitions.
- Admission callers do not import YAML stores or concrete registries.
- The shared gateway host/composition root supplies the active runtime resolver explicitly.
- Remove module-global registry selection where this migration can do so without introducing a container.
- Do not add a service locator or new registry.

## Active session data

A live session records only the minimum active execution facts already required for continuation and cleanup: execution-profile ID, provider, model, surface, existing generation/digest fields and execution-context identity. Do not store a copied Execution Profile.
