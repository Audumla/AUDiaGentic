# Decide the long-term relationship between entity registries and the composition graph

## Description

Raised 2026-08-03 while implementing AS59 Stage 1. The question asked was whether the existing
`foundation/registry_utils.Registry` should back the composition graph, or be migrated onto it.

**Neither, for now.** Recorded here so the question is not re-opened ad hoc, and so the part of
it that *is* real has an owner.

### Why composition does not use `Registry`

`Registry` provides `get(key)`, mutable `register()`, alias resolution, a lazy loader and
`reset()`. AS59's Non-Negotiable Rules forbid a runtime `get()`, mutable registration, a service
locator and a hidden global container. Building the composition graph on `Registry` would import
the exact property AS59 exists to remove. The built graph is frozen after construction and
exposes no lookup method.

### Why they are not duplicates

They answer different questions and share none of the four properties `arch-standards` §3
requires before unifying types:

| | `Registry` | Composition graph |
|---|---|---|
| Question | which entities exist (languages, provider descriptors, tags, hosts, secret schemes) | which implementation is constructed, in what order, with what lifetime |
| Population | lazy loader / discovery | explicit contribution list at the composition root |
| Lifetime | mutable, resettable, process-global | built once, frozen, finalized in reverse order |
| Ownership | the owning component | the composition root |

Unifying them would produce one abstraction worse at both jobs.

### What is genuinely open

Nine module-global `Registry` instances are import-time globals with lazy loaders, and
`reset_all_registries()` is the mechanism TE02 step 10 cannot make converge. That is the same
class of defect composition treats — shared mutable process state whose population order is
emergent — one layer up, in the entity catalogue rather than the service graph.

The plausible end state is that composed services *own* their entity registries as instance
state instead of reading module globals, which removes the need for a global reset entirely.
That cannot be attempted before composed services exist, which is why this is not AS59 Stage 1
scope.

## Steps

1. Do not act on this until AS59 Stage 1 (items 1-5) has landed and at least one real service has
   been migrated into the graph — without a composed consumer there is nothing to own a registry.
2. Re-measure first: confirm `reset_all_registries()` is still the convergence blocker for TE02
   step 10 at that point. If TE02 step 10 has been solved another way, this item may be
   unnecessary and should be closed rather than implemented.
3. Pick one registry as the probe — `providers/surfaces/registry.py` is the strongest candidate,
   because it is the one AS74/TE02 identified as not reliably repopulating after reset (pi's
   import-time `surface.py` registration is never restored).
4. Make that registry instance state owned by a composed service; leave the other eight alone.
5. Measure whether the parallel-suite flakiness attributable to that registry disappears. Only
   then decide whether the remaining eight are worth converting.
6. If the probe does not improve convergence, record that and stop — do not convert the rest on
   the strength of the theory alone.

## Standards

- `arch-standards` §3 Ownership and Abstraction — types unify only when ownership, lifecycle,
  validation and semantics all match. They do not here; this item records why rather than
  leaving the merge question open.
- `arch-standards` §3 Evidence-led scope — the conversion is not attempted before a composed
  consumer exists, and stops if the probe does not measure an improvement.
- AS59 Non-Negotiable Rules — no service locator, no runtime `get()`, no hidden global container.

## Acceptance Criteria

This item is **deferred by design**. It is satisfied by either outcome, and both are
acceptable closes:

- **Closed as unnecessary** — TE02 step 10 resolves the registry churn another way, and the
  measurement in step 2 shows no remaining convergence problem attributable to module-global
  `Registry` instances. Record the measurement and close.
- **Closed as implemented** — the probe registry (`providers/surfaces/registry.py`) is owned by a
  composed service, and repeated parallel runs show measurably improved convergence. The
  remaining eight registries are then either converted on the same evidence or explicitly left
  alone with a recorded reason.

In both cases:

- The decision recorded in this item's Description — that composition does not use `Registry`,
  and the two are not unified — still holds, or is explicitly overturned here with a rationale.
- No conversion is done on the strength of the theory alone: step 5's stop condition was
  honoured.
- `arch-standards` §3's four-property test (ownership, lifecycle, validation, semantics) is
  re-applied if any merge of the two concepts is proposed.

## Revised 2026-08-03 by AS59's granularity rule

AS59 now states Rule 0: **composition binds component public surfaces and foundation
capabilities, never internal collaborators.** That settles a question this item left slightly
open, and narrows it.

The nine `Registry` instances are component-internal entity catalogues. They are therefore **not
composition candidates and never will be** — not "deferred until a composed consumer exists", as
this item originally put it. No binding should ever name a language registry, a provider
descriptor registry or a surface renderer registry.

What survives the narrowing is the part that was always the real point: those registries are
*module globals* rather than instance state owned by the component that uses them. The fix is for
the owning component to construct and hold its registry behind its own public surface — which is
component-internal work, invisible to the composition graph, and available whether or not that
component's surface is ever composed.

So the probe in step 3 stands unchanged, but its justification changes: it is not preparation for
composing a registry. It is testing whether component-owned instance state removes the need for a
process-global reset. If it does, the same treatment may be worth applying to the other eight; if
it does not, step 5's stop condition applies and this item closes.

This also means the item is **no longer sequenced behind AS59 Stage 1**. It was gated on "a
composed consumer existing"; under Rule 0 no such consumer is required. It is gated only on TE02
step 10 still being an open problem when someone picks it up.
