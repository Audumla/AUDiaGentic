# Redaction and sanitization contract for public projections

## Description

Extend the existing operational-record redaction enforcement to cover the new session read surfaces, so one mechanism governs what reaches a public projection.

**Reframed 2026-08-05.** This is **not** a security-hardening item and should not be read as one. `OBSERVABILITY_STANDARDS` already requires it independently of any threat model — "Do not persist raw secrets, stdout/stderr dumps, or unredacted exception text", "no raw prompts, outputs, secrets", and a denylist rejecting `prompt-body`, `output`, `prompt_body`, `raw_output`. That rule exists because operational records are small, shared, pasted into issues and committed — not because callers are hostile.

So this is observability hygiene with an existing enforcement mechanism, and it is a **standing obligation on every new surface**, not a late gate that features wait behind.

## Steps

1. Start from the existing mechanism, do not invent a second one. `CON-OPR-002` already rejects denylisted fields on operational records; the standards already name the denylist. Extend that enforcement to the new metadata-polling, live-read and control-audit surfaces.
2. Define the allowlist shape per new public surface: what a status event, a metadata event, an output event and a control audit record may each carry.
3. Keep the unknown-field default at exclude-rather-than-include.
4. Keep the composition-identity rule: lifecycle facts carry digest prefixes, never Role instruction text or raw Agent Card content — this is about record size and noise as much as anything else.
5. Add the architecture test that fails when a new field reaches a public surface without an allowlist entry.

## Detailed Solution & Technical Design

**What stays, and why it stays even with non-hostile users:**

- **Secrets, credentials, tokens, authorization headers, key-bearing URLs.** Logs and records get shared, pasted and committed. This has nothing to do with the caller's intent.
- **Raw stdout/stderr dumps, unredacted exception text, stack traces.** Record-size and signal-to-noise, explicitly required by the standards.
- **Content/evidence lane separation** — assistant text stays out of lifecycle evidence. This is an *architectural* rule (one owner per lane, §3), not a privacy rule. It stays for the same reason it was written.

**What is no longer framed as a security requirement:**

- Redaction of prompts and assistant output from surfaces the project's own users read. Within a project, a user reading their own project's prompts is not a disclosure — it is the intended use. The rule against putting them in *operational records* still holds on the record-hygiene grounds above, but it is not a confidentiality boundary and should not be specified as one.
- Provider ref opacity. Keeping raw provider refs out of public surfaces remains correct as an §6 boundary rule (provider internals stay provider-private), not as a secret-protection rule.

## Validation

- Each denylisted category is proven absent per category per surface.
- An unknown field is excluded by default, proven by injecting a deliberately unexpected field.
- Secrets, credentials and tokens never reach any record, log or projection.
- Composition identity appears as digest prefixes only.
- Assistant content stays out of lifecycle evidence — asserted as a lane-separation invariant.
- The existing `CON-OPR-002` mechanism was extended, not duplicated — asserted by there being one enforcement point.
- The architecture test fails when a new unallowlisted field reaches a public surface.

## Effort & Risk

Medium. The risk is that a single enforcement point is bypassed by a surface that formats its own output; the architecture test in step 6 is the control, and it must assert reachability rather than merely scanning for known-bad strings.

## Standards

- `arch-standards` §3 Ownership and Abstraction — one redaction authority.
- `arch-standards` §4 Public Contracts — unknown fields are excluded by default.
- `observability-standards` — assistant content is a separate lane from lifecycle evidence; redaction applies to every persisted event.

## Acceptance Criteria

- One enforcement point governs every public projection; no surface formats its own output around it.
- Secrets, credentials, tokens, raw stdout/stderr and unredacted exception text are absent from every record, log and projection.
- Unknown fields are excluded by default.
- Assistant content and lifecycle evidence remain separate lanes.
- Composition identity appears as digest prefixes only.
- The existing operational-record mechanism was extended rather than duplicated.
- An architecture test fails when a new unallowlisted field reaches a public surface.
