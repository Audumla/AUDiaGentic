# Add minimal capability checks

## Goal

Validate that the selected harness surface and model can satisfy the current Role and published interface.

AS29 remains the sole harness/session-surface capability authority.

## Design

Use a small in-memory resolved value or pure check. Do not create an effective-capability store, registry, snapshot hierarchy or broad model catalogue.

Initial model facts should be limited to demonstrated needs such as:

- text;
- vision;
- tool calling;
- context limit where required.

Unknown means unsupported.

## Service boundary

Keep capability resolution/checking as pure functions where possible. Add an injected model-fact source only if model facts require I/O or replaceable storage. Do not introduce an interface merely to wrap a pure function.

## Work

1. Reuse AS29's resolved surface facts.
2. Locate existing model metadata before adding fields.
3. Add only facts required by current Roles, ACP or A2A publication.
4. Apply Execution Profile and Role restrictions.
5. Return a simple resolved capability result for the current admission decision.
6. Persist only existing IDs/digests where current continuation logic requires them; do not persist a copied capability object.

## Reassess before AS65

Remove speculative model facts and any abstraction with no current consumer.

## Acceptance criteria

- Role requirements fail before launch when unsupported.
- AS29 capability truth is not duplicated.
- Capability logic is small, testable and DI-ready where I/O exists.
- No new capability registry/store is introduced.
