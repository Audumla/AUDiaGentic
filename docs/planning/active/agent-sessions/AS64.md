# Compose model, surface and policy capabilities into one effective snapshot

## Goal

Provide one immutable effective-capability snapshot used to validate role requirements, agent publication and protocol behavior without duplicating AS29 session-surface truth.

## Capability sources

Compose only from authoritative sources:

1. AS29 resolved session-surface capabilities and evidence;
2. bounded model capability facts;
3. execution-profile restrictions and configured limits;
4. role/agent policy restrictions;
5. environment/platform validation where already owned by existing contracts.

The composition is subtractive/default-deny: unknown is unsupported, restrictions may remove capability, and no higher layer may invent provider/model support.

## Initial model capability vocabulary

Keep the first version deliberately small and typed:

- text input/output;
- vision input;
- tool/function calling;
- structured output where proven;
- reasoning mode as a configurable feature, not hidden-reasoning exposure;
- context/token limit metadata;
- supported model input/output media needed by current roles/skills.

Do not build a broad public model catalogue. Facts may come from provider/model configuration or validated probes and must carry provenance/maturity.

## Contract

Define:

- `ModelCapabilitySnapshot`;
- `EffectiveCapabilitySnapshot`;
- stable digest/generation;
- capability provenance and effective constraints;
- pure `compose_effective_capabilities(...)`;
- pure `validate_role_requirements(...)`.

Keep session mapping/control capabilities distinct from public work skills. Internal capability identifiers may be grouped by family but must remain closed and documented.

## Steps

1. Complete AS63 mapping proof or use the AS62 snapshot consumer if AS63 is still in progress.
2. Inventory existing provider/model metadata and capability declarations; reuse rather than duplicate.
3. Add the minimal model capability contract and source resolver.
4. Compose AS29 surface facts with model facts and execution/policy restrictions.
5. Persist only the effective snapshot digest and bounded public facts needed for exact session-generation continuation; retain full immutable snapshot where existing manifest/storage policy permits.
6. Use the snapshot to validate role requirements during agent-definition resolution.
7. Use it to gate ACP/A2A publication plans, but do not implement protocol servers here.
8. Add architecture tests ensuring AS29 remains sole owner of session-surface facts and roles remain requirement-only.

## Reassessment gate R5

Before AS65:

- review every model fact added and remove speculative/unverifiable entries;
- confirm unknown defaults to unsupported;
- confirm the vocabulary is sufficient for current roles and intended ACP/A2A publication;
- decide whether model facts should remain provider configuration data or warrant a reusable model registry. Create a registry only if multiple real consumers and independent lifecycle justify it.

## Validation

- deterministic composition/digest;
- surface supported + model unsupported resolves unsupported;
- policy restriction removes otherwise supported capability;
- unknown/missing evidence remains unsupported;
- role all/any/constraint validation;
- context/media constraint handling;
- no hidden reasoning or raw provider capability leakage;
- session continuation detects effective-capability drift through immutable generation/digest rules.

## Acceptance criteria

- One effective-capability snapshot exists for agent resolution and publication.
- AS29 remains the sole session-surface capability authority.
- Model capability work is minimal, evidence-backed and default-deny.
- Roles state requirements, not support claims.
- R5 findings are recorded before external protocol adapters begin.
