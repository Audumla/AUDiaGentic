# Execute the layered agent-runtime refactor in controlled order

## Goal

Track and govern the transition from the current overloaded agent-profile/request terminology to the layered model agreed for AUDiaGentic:

1. provider session surface — exact harness interface and validated capabilities;
2. execution profile — reusable provider, model, selected surface, execution and admission mapping;
3. role — reusable instructions, tools, permissions and capability requirements;
4. agent definition — identity and public skills composed from one execution profile and one role;
5. interaction session — persistent two-way continuity over one resolved generation;
6. agent task and turn — external work identity and one execution within a session;
7. protocol adapters — ACP for interactive session clients and A2A for task-oriented agent clients.

This item is the execution-order authority for AS60-AS66 and the required amendments to existing AS items. It does not implement runtime behavior itself.

## Architectural invariants

- AS29 remains the sole declaration/resolution authority for exact provider session-surface capabilities.
- AS19 remains the sole provider-neutral transport/control/observation contract.
- AS30 remains the sole durable AUDiaGentic-to-provider session binding/index authority.
- AS31 remains the sole assistant-content lane/final-output authority.
- AS21 remains lifecycle/reuse authority.
- Existing shared-gateway ownership, isolation, process supervision, leases, queues and recovery remain with their current owners.
- No new parallel profile, capability, session, binding, event, output or process registry may be introduced.
- `SessionRuntime` remains the interaction-session execution owner unless a later evidence gate proves a real need for one runtime instance to host multiple independent sessions.
- Existing internal names may be changed without compatibility guarantees, but external/config migrations must be explicit and bounded.

## Execution order

### Gate 0 — characterize and freeze baseline

Before AS60 implementation:

- inventory every current use of `AgentProfile`, `GatewayProfileSnapshot`, `agent_profile_id`, `SubmissionEnvelope`, `submit_llm_request`, `SessionRuntime`, session IDs/generations, request IDs and turn IDs;
- inventory all current AS items that use profile/request/session terminology;
- run the nearest profile, gateway, session, transport, binding, output and shared-service tests;
- record the baseline files, tests and existing partially implemented behavior in AS60-AS66 rather than creating duplicate paths.

### Stage 1 — AS60 execution-profile refactor

Rename and clarify the existing provider/model profile as `ExecutionProfile`. Preserve behavior. Add explicit surface selection only through AS29. Migrate gateway-owned snapshots/registries and project-local configuration.

**Reassessment gate R1:** after AS60, review whether execution profile has remained a narrow execution/admission mapping. If role, public-agent identity, tool policy or A2A fields have leaked into it, stop and correct boundaries before AS61.

### Stage 2 — AS61 role contracts

Add minimal reusable roles containing instructions, tool policy, permission policy and capability requirements. Avoid memory, planning, workflow and delegation frameworks beyond small extension points.

**Reassessment gate R2:** prove at least two execution profiles can use one role and one execution profile can use two roles without provider-specific branching or deep untyped merge semantics.

### Stage 3 — AS62 agent-definition composition

Add logical agent identity, role/execution-profile references, skills and interface publication policy. Resolve one immutable snapshot and validate role requirements against effective capabilities.

**Reassessment gate R3:** review the composition schema using at least Pi ACP and one non-ACP/native or fake surface. Confirm the logical agent can change execution profile without changing public identity/skills unless explicitly versioned.

### Stage 4 — amend existing session plans and persistence

Before AS63, update AS19, AS29, AS30, AS31, AS47, AS49, AS57 and AS58 terminology/dependencies:

- replace execution-config uses of agent profile with execution profile;
- add immutable agent-definition/role/execution-profile snapshots or digests to session generation context;
- retain AS30 interaction-session binding semantics;
- retain AS47 exact-context same-generation continuation;
- retain AS49 explicit resume into a new linked generation;
- state that AS57/AS58 are protocol-neutral read/control services beneath future ACP/A2A adapters.

Do not supersede those items unless the amendment review proves an item is fully absorbed. Record any supersession explicitly in both the old and replacement item.

### Stage 5 — AS63 agent-task contract

Generalize the public domain boundary from LLM prompt request to agent task while retaining the existing request/turn stores and `submit_llm_request` compatibility adapter during migration.

**Reassessment gate R4:** prove one task maps cleanly to one current turn without losing current behavior, then assess whether multi-turn A2A tasks require a later durable task coordinator. Do not build one speculatively.

### Stage 6 — AS64 model/effective capability composition

Introduce the smallest model capability source needed to validate role requirements and public agent interfaces. Compose AS29 surface facts, model facts, execution restrictions and policy into one immutable effective-capability snapshot.

**Reassessment gate R5:** if model capabilities cannot be made evidence-backed and bounded, keep unknown as unsupported and defer broad model catalog work.

### Stage 7 — AS65 external ACP façade

Expose AUDiaGentic-owned interactive sessions to external ACP clients using AS19/AS30/AS31/AS57/AS58 services. Never raw-proxy an underlying provider ACP session.

**Reassessment gate R6:** validate with one native ACP-backed harness and one non-ACP/fake transport to prove the façade is genuinely provider neutral.

### Stage 8 — AS66 A2A agent/task surface

Publish selected agent definitions as A2A agents, generate Agent Cards, map A2A tasks/messages/artifacts to the canonical task service, and project bounded output/status from existing lanes.

**Reassessment gate R7:** begin with deterministic gateway orchestration. Add MCP delegation tools or model-directed delegation only after identity, authorization, recursion, workspace/artifact and budget policies are proven.

## Validation

- execution proceeds in the listed order unless this tracker records an approved deviation;
- every reassessment gate records findings and any plan changes before the next stage begins;
- no stage introduces a parallel authority owned by an existing AS item;
- migrations are one-way after compatibility windows close;
- architecture/AST tests enforce dependency direction:
  - protocol adapters -> agents public services;
  - agents -> provider-neutral foundation contracts;
  - providers -> private protocol/native adapters;
  - agents core must not import A2A, ACP-native or provider-native types;
- documentation diagrams and terminology are updated at each gate rather than deferred to the end.

## Acceptance criteria

- AS60-AS66 and amended existing items form one executable, non-overlapping plan sequence.
- Each reassessment gate has a recorded decision.
- The final domain model contains distinct execution profile, role, agent definition, interaction session, task and turn concepts.
- External ACP and A2A are adapters over canonical services, not alternate runtimes.
- Existing session persistence, isolation, observability, bindings and output work is reused rather than replaced.
