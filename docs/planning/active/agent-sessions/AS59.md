## Goal

## Simple domain model

- `SessionSurface`: exact harness interface and capability truth; AS29 owns it.
- `ExecutionProfile`: provider, model, selected surface, launch parameters and admission settings.
- `Role`: instructions and simple capability requirements. Runtime tool policy is placeholder-only in this sequence.
- `AgentDefinition`: one Execution Profile plus one Role, identity and skills.
- `InteractionSession`: persistent two-way context.
- `AgentTask`: one requested unit of work.
- ACP: external interactive-session adapter.
- A2A: external agent-task adapter and remote transport.
- management MCP: AUDiaGentic admin/configuration adapter over a component public API.
- runtime MCP: capability server materialized into a harness for the running agent to use.

## MCP boundary

Management MCPs and runtime MCPs are separate concerns.

### Management MCPs

Management MCPs are inbound AUDiaGentic administration/configuration adapters used by the CLI or an operator. They:

- call the owning component's framework-neutral public API;
- manage AUDiaGentic configuration and state;
- do not define a second configuration authority;
- use `propagate: audiagentic` unless a deliberately scoped runtime projection is defined;
- are not handed wholesale to a launched provider merely because they use MCP transport.

### Runtime MCPs

Runtime MCPs are tools/capabilities made available to a launched harness or agent. They:

- are selected from component activity servers and materialized through provider/runtime configuration;
- use provider launch-surface isolation and request-owned runtime materialization where supported;
- may expose a scoped gateway/delegation capability to the harness;
- must not expose unrelated global administration merely because the same application API serves operators.

Do not merge management and runtime MCP configuration, permissions or ownership. They may call the same application service through different scoped adapters.

## Terminology rule

Do not introduce a hierarchy of stored snapshots or configuration revisions.

Use:

- `active configuration`: IDs and concrete execution facts currently bound to a live session;
- `resolved`: a short-lived immutable value produced for admission or launch;
- existing generation/digest fields only where current code already requires stale-config, queue-lane or execution-context checks.

The existing immutable gateway admission value and AS29 resolved surface value are valid because they protect current correctness. Do not generalize them into Role/Agent snapshot stores or copied definition trees.

## Foundation manual DI rule

AUDiaGentic will add a small manual dependency-composition facility under `foundation`, bootstrapped by runtime startup. It is infrastructure, not a component and not owned by `agents`.

The initial facility must remain deliberately small:

- one startup builder/composition API;
- explicit registration of instances or factories by a stable service key/type;
- singleton/application lifetime only in the first implementation;
- deterministic duplicate/missing/cycle errors;
- optional ordered shutdown callbacks/finalizers for application-owned resources;
- a built service graph that is immutable after startup;
- no decorators, reflection auto-wiring, module scanning, hidden global container or injection into arbitrary functions.

The container/registry may be used only at composition roots and adapter startup. Application/domain services receive concrete dependencies through constructors or explicit parameters. They must never call `container.get(...)` or a global `resolve(...)` during normal work.

A later library such as Dishka may replace the builder and lifetime implementation. Core service constructors and public ports must not depend on foundation-container types.

## Runtime bootstrap and configuration

Runtime owns bootstrap:

```text
startup configuration
        ↓
runtime bootstrap selects enabled service contributions/implementations
        ↓
foundation composition builder constructs the application graph
        ↓
root hosts/adapters receive ready services
        ↓
shutdown closes the graph in reverse dependency/order
```

Rules:

- configuration selects implementations and options; it must not become arbitrary dotted-path code injection;
- components expose approved public factories/contributions through existing descriptor/plugin mechanisms;
- runtime gathers those contributions and performs the final wiring;
- foundation knows nothing about agents, providers, MCP, ACP or A2A;
- components do not own or replace the root container;
- tests can build a graph with fake services without loading project YAML or starting processes.

The first implementation does not require task/session scopes. Add scopes only after a demonstrated lifecycle needs them.

## Migration rule

Follow `docs/standards/ARCHITECTURE_STANDARDS.md` and `ARCHITECTURE_GUIDELINES.md`:

- backward compatibility is not maintained by default;
- a rename or move updates all production callers, tests, configuration, dotted paths and documentation in the same item;
- delete obsolete APIs, aliases, shims, fallbacks, dual routes and compatibility tests in the same change;
- do not add legacy readers or temporary adapters unless a documented external obligation is approved before implementation;
- migrations must leave one production path.

## YAGNI rules

Do not add unless a demonstrated current requirement needs it:

- snapshot stores or snapshot registries;
- generic policy revision/overlay systems;
- role inheritance or multi-role stacking;
- cross-harness runtime tool-policy normalization;
- a shared management/runtime MCP abstraction;
- task/session/request DI scopes;
- automatic constructor inspection or decorator injection;
- child containers or mutable runtime re-registration;
- a separate runtime registry or runtime/session fan-out;
- a second task store, queue, lifecycle engine, output lane or binding index;
- raw ACP passthrough;
- a separate A2A runtime;
- compatibility shims, legacy handlers, dual writes or deprecated aliases.

Prefer direct migration of existing code over parallel abstractions.

### Suggested shape

Names are not mandatory, but the responsibilities should remain this small:

```text
foundation/composition/
  definitions.py   # service key, registration/factory records
  builder.py       # register/build/validate
  graph.py         # immutable built graph + close()

runtime/bootstrap/
  services.py      # config-driven root wiring
```

Avoid a generic framework. A few explicit classes/functions are sufficient.

### Stage 1 acceptance

- Foundation composition code has no component/domain imports.
- Runtime startup owns the root graph.
- At least one gateway startup path receives dependencies from the graph.
- No global container is exposed.
- Services remain plain Python and can be manually constructed in tests.
- Shutdown is deterministic.
- Replacing the builder with Dishka later would not require rewriting service constructors.
