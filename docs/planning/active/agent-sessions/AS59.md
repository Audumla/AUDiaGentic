## Effort & Risk

**First push (items 1-5): M, low risk.** Both target directories are greenfield, so there is no
migration to get wrong. The only file with existing behavior at stake is `launcher.py`, and only
its startup block moves — argparse and dispatch are untouched, and the existing CLI tests are
the regression proof. The builder is self-contained and fully unit-testable without any
product code.

The one place this could go wrong quietly: item 3's builder is easy to over-build. The
`Foundation Facility` section's exclusion list (no decorators, no reflection, no runtime
`get()`, no child containers, no scopes) is the guard, and it is a review checklist, not a
test — so it needs enforcing by reading the diff, not by running the suite.

**Second push (items 6-9): M, moderate risk.** The gateway profile registry migration is
lower risk than it looks because `GatewayProfileRegistry` is already a Protocol with two
implementations. The queue manager is the harder half: it has no Protocol yet, is constructed
at import time, and twelve tests currently reassign it by hand. Removing the global without
first giving those tests an injected replacement will break all twelve at once.

**Sequencing risk, and the reason for the 1-5 boundary:** items 1-2 committed alone *freeze*
two contracts against a consumer that does not exist yet, and no test can report that the
shape is wrong — the schema parses, the dataclass constructs, and any test written for them
was written from the same guess. The shape only becomes falsifiable once item 3 consumes it.

This is a verification argument, not a standards violation: items 1-2 are specified by an
approved owning plan item, so `arch-standards` §3's evidence-led clause is satisfied on its
face. What applies is the weaker second clause — "design seams so a later owning item can
extend them deliberately" — and an unconsumed contract is a seam designed blind.

So the mitigation is procedural and it is a preference with a stated cost, not a
prohibition: keeping items 1-5 in one push means the contracts are exercised before they
land. Splitting for a smaller review surface is legitimate; the cost is that item 3 will
likely amend items 1-2, and the history shows a contract changed once before first use.

## Standards

- `arch-standards` §1 Dependency Boundaries — the composition root may wire any
  layer; foundation must import no component or runtime orchestration. The
  string-keyed binding map is permitted *only* as composition-root wiring, and
  §1's "a registry does not remove a dependency" still applies. See this item's
  Standards reconciliation section.
- `arch-standards` §2 Extensions and Configuration — implementation selection is
  configuration-declared; code supplies typed factories, not dotted paths.
- `arch-standards` §3 Evidence-led scope — build only bindings with a current
  replaceable implementation. No speculative scopes, plugin framework or generic
  service catalogue.
- `arch-standards` §4 Public Contracts — missing, duplicate and cycle errors are
  `AudiaGenticError` with stable codes; no compatibility alias or dual route.
- `arch-standards` §7 Enforcement — every invariant in Stage 1 work item 8 needs
  a proportionate architecture test.

### Item 1 — composition config schema

A `composition` namespace on `load_layered_config`, package default shipped in
`src/audiagentic/config/`. Two keys only, both already fixed by the
`Separate Composition Configuration` section above: `roots` (list of service IDs) and
`bindings` (service ID → implementation ID). Parsing rejects any value containing `.py`,
`:` or a dotted path segment resolvable as a module — that rejection **is** the architecture
test for "no Python paths in composition YAML" (item 8, bullet 6), so it is written as
validation code, not only as a test assertion.

Why this cannot ship alone: a schema with no builder has no failure mode a test can
exercise beyond "the YAML parses", which proves nothing about composition.

### Item 2 — typed contribution records

The quadruple already specified above — service ID, implementation ID, required service IDs,
factory — as a frozen dataclass. Service and implementation IDs are `NewType`-style typed
strings, not bare `str`, so that a binding map keyed by the wrong one fails at type-check
rather than at graph-build. Contributions are collected from an explicit built-in list at
the composition root, per the `Service Contributions` section; **no discovery, no scanning.**

Why this should not ship alone: the record's shape is only *falsifiable* once the builder
consumes it. Committed first, a wrong field set — say `required` as a flat tuple when the
builder turns out to need per-parameter binding names — produces no failing test, because
the record and its test were written from the same guess.

### Item 3 — builder, graph, errors, finalizers

The substance of the push. Ordered sub-steps:

1. Index contributions by service ID; reject duplicate implementation IDs for one service.
2. Apply configured bindings; unknown service ID and unknown implementation ID are two
   distinct errors with distinct codes.
3. Walk from configured roots only; anything unreachable is never constructed. This is what
   keeps the graph honest as bindings accumulate — an unreachable binding is dead config, not
   a live dependency.
4. Detect cycles during the walk and report the **participating service IDs in order**, not
   just "a cycle exists".
5. Construct in dependency order, recording construction order as it goes.
6. Freeze the built graph; no `get()`, no post-build mutation.
7. Finalize in reverse construction order, and continue through a failing finalizer rather
   than abandoning the remaining ones.

All four error classes (unknown service, unknown implementation, duplicate, cycle) are
`AudiaGenticError` with registered codes — which means AS72's catalogue registration must
not be skipped for these, or Stage 1 lands four more unregistered codes.

## MCP boundaries

Management MCPs and harness runtime MCPs are separate projections over public APIs.

- Management MCPs expose configuration and operator functions.
- Runtime MCPs expose bounded capabilities to a launched harness.
- Harnesses require scoped gateway access for discovery/delegation/task status
  and permitted continuation.
- Operator-only global listing, overview, configuration, credentials and
  unrelated-task control remain unavailable to harnesses.

## Separate Composition Configuration

Composition has its own typed configuration concern. Do not add DI fields to
component, provider, Execution Profile, Role or Agent Definition schemas.

Configuration selects stable implementation IDs only:

```yaml
composition:
  roots:
    - runtime.application-host
  bindings:
    runtime.application-host: runtime.default-host
    agents.execution-profile-resolver: agents.project-yaml
```

No Python paths, constructors, dependency lists, secrets or domain data belong
in this YAML.

Only genuinely replaceable services need selectable bindings. Do not create a
binding for every class or helper.

### Standards reconciliation

ARCHITECTURE_GUIDELINES §1 forbids "a service locator, an arbitrary
`dict[str, Callable]`, a string or dotted-path lookup" used to conceal a
forbidden dependency. A string-keyed service-ID → implementation-ID map is
permitted here **only** because ARCHITECTURE_STANDARDS §1 grants the composition
root access to any layer, and because resolution happens once at build time.
This must be made explicit, not assumed:

- only the composition root may read bindings;
- there is no runtime `get()`;
- ARCHITECTURE_STANDARDS §1's "a registry does not remove a dependency" still
  holds — resolved bindings remain dependency edges for architecture review.

Add an architecture test for the first bullet alongside the others below.

## Service Contributions

Code contributes typed implementation factories:

```text
service ID + implementation ID + required service IDs + factory
```

Runtime collects contributions, applies configured bindings and builds only the
graph reachable from configured roots.

The first implementation may use an explicit built-in contribution list at the
composition root. Pluggy integration can replace contribution collection later.
Do not build package scanning, a second plugin system or speculative
contribution lifecycle now.

## Foundation Facility

Add only:

- typed service/implementation IDs;
- factory registrations;
- configured binding selection;
- deterministic missing, duplicate and cycle errors;
- application lifetime;
- immutable built graph;
- reverse-order shutdown/finalizers;
- build-time test substitutions.

Do not add decorators, reflection auto-wiring, runtime `get()`, mutable
registration, child containers or task/session scopes.

Services remain plain Python and receive dependencies through constructors or
explicit parameters.

## Runtime Application Host And Legacy Exemption

Stage 1 wraps and reduces the existing `launcher.py` startup path; it does not
create a parallel startup path.

Add one runtime-owned root such as:

```text
runtime.application-host
```

The host:

- owns process startup/shutdown only;
- receives migrated services from composition;
- invokes existing construction paths for code not yet migrated;
- contains no new business logic;
- is not injected into domain/application services;
- is not a forwarding façade or catch-all API.

### Bounded legacy exemption

Existing unmigrated code may temporarily retain current globals, import-time
registration and direct construction only when all are true:

1. it remains behind `runtime.application-host` or an existing startup path
   called by that host;
2. the current plan item does not materially refactor it;
3. no new caller depends on the legacy access pattern;
4. no new global, locator, compatibility shim or duplicate route is added;
5. tests record the remaining exemption surface.

Once a service is touched by AS60-AS66, it leaves the exemption permanently and
becomes a configured composition dependency. Do not move migrated code back
behind legacy lookup.

This is an incremental architecture exception under the repository standards,
not a second architecture.

## Composition candidate criteria and assessment (2026-08-03)

Assessed 2026-08-03, then revised the same day when the owner set the granularity rule. The
revision is the important part: the first assessment asked *whether* each global was a good
candidate, which was the wrong question. The right question is *at what boundary composition
happens at all*.

## Rule 0 — granularity. Compose at type boundaries, not at collaborators

**A composition binding names a component's public surface or a foundation capability. Nothing
else is a candidate.** A component's internal collaborators are constructed by that component and
never appear in the graph.

This is a hard bound on the graph's size. The number of bindings tracks the number of
component/capability boundaries — order tens, permanently — not the number of classes. "Many small
injections" is the failure mode this rule exists to prevent, and it is a failure mode that arrives
quietly: each individual injection looks reasonable, and the graph is a container before anyone
decides it should be one.

It also explains every result below without needing the other criteria. The two things that
qualified are both boundaries. Everything that failed is an internal.

## Remaining criteria, applied only after Rule 0 passes

1. **Genuine choice** — two or more implementations configuration should select between. Without
   this it is not a *binding*; it may still be a composed singleton (see below).
2. **Isolatable seam** — a declared interface at the boundary, so consumers depend on a shape.
3. **Bounded blast radius** — injecting it does not force a public API redesign.
4. **Lifetime worth owning** — deterministic construction and shutdown ordering matters.

Criteria 1 and 4 are independent reasons and produce different designs. 1 gives a **binding**
(config selects between implementations). 4 gives a **composed singleton** (the graph owns the
lifetime; no binding entry, because there is nothing to choose). Conflating them is the other way
a composition root becomes a container.

- `_QUEUE_MANAGER` — one implementation, no interface, reachable only through 13 module-level free

- `_gateway_registry` (superseded by RV888, see above) — `None` is a *meaningful value*

- `_SESSION_RUNTIME` — one implementation, so a lifetime candidate at most; 3 read sites, all

All three are internals, and every one of those observations is a symptom of that rather than three

## The barrier is the boundary's shape, not the collaborators behind it

`agents_gateway_api` exposes its whole surface as module-level free functions, and a free function
cannot receive an injected dependency without a signature change. Under Rule 0 this stops being an
obstacle and becomes a statement about *what to fix*: the agents component does not currently
present a composable public surface. Giving it one is AS60/AS63's work, and when it exists the
queue, session runtime and profile registry are constructed **behind** it — they never become
bindings themselves.

## This facility is deliberately temporary

A real DI engine may replace it later. Nothing here should be grown toward one in the meantime:
no decorators, no reflection auto-wiring, no runtime `get()`, no mutable registration, no child
containers, no scopes, no discovery, no plugin lifecycle. Rule 0 keeps the binding set small
enough that swapping the engine stays a bounded change — which it would not be if the graph had
absorbed every collaborator in the codebase.

The existing note that "Pluggy integration can replace contribution collection later" stands as a
possibility, not a plan, and is subject to §3's two-independent-consumer bar before anything is
built for it.

## Item 6 has no viable candidate today, and the reason is structural

Item 6 asked to "migrate one real gateway dependency into composition: the queue / Execution
Profile resolver path needed by AS60/AS63". Both halves were checked against the tree. Neither
qualifies, and a third candidate was checked and also rejected.

**Queue manager** — one implementation, no interface, and reachable only through 13 module-level
free functions with 18 external callers. Rejected earlier; see the candidate assessment section.
Already owned elsewhere: AS63's disposition in the table above reads "Owns removing
`_QUEUE_MANAGER` from touched paths."

**Gateway profile registry** — looked like the strong candidate (a `GatewayProfileRegistry`
Protocol, two implementations, one read site and two write sites in `src`). It is not one, for a
reason only visible on reading the semantics rather than counting call sites:

- `None` is a *meaningful value*, not an unset dependency. `get_gateway_registry()` returns
  `GatewayProfileRegistry | None`, and `agents_gateway_api.py:294-303` documents `None` as
  "embedded mode (no registry installed)" with the queue's own embedded-compatibility fallback
  covering it. A build-time binding cannot express "deliberately absent".
- It is installed and uninstalled *at runtime* by the gateway service host
  (`agents_gateway_service_host.py:94` installs, `:225` sets it back to `None`).
- It is *hot-swapped* while the process runs: `reload_profile_registry()` re-reads config and
  replaces the instance under a lock, raising `CON-AGW-102` when none is installed.

So it is runtime mode state with a live swap protocol, not a configured implementation choice. A
frozen build-time graph cannot hold it without either breaking reload and the host's
install/uninstall cycle, or keeping the global and gaining nothing.

**Session runtime** (`_SESSION_RUNTIME`, checked as a fallback candidate) — one implementation, so
not a binding; it is a *lifetime* candidate (`atexit` registered inside a lazy getter). But its 3
read sites are inside the same free functions, so it hits the identical injection barrier.

### The root cause, stated plainly

`agents_gateway_api` exposes its entire surface as module-level free functions. **You cannot
inject a dependency into a free function without changing its signature.** That is why every
gateway candidate scores badly on blast radius — it is one property of the component, not three
separate problems.

Reshaping that surface is AS60 (Execution Profile) and AS63 (AgentTask) work. Doing it here would
be AS59 deciding the agents component's public API on their behalf, with neither consumer built.

recorded scope), the gateway client to `shared-gateway/SH11` Slice B (already its recorded scope),

This is the evidence-led outcome, not a shortfall: item 6 assumed a suitable candidate existed,

## Item 6: the premise was a granularity error, not a missing candidate

Item 6 asked to "migrate one real gateway dependency into composition: the queue / Execution
Profile resolver path". Under Rule 0 — compose at component/foundation type boundaries, never at
internal collaborators — the queue manager and the Execution Profile resolver were never
candidates. They are internals of the agents component.

This is a better answer than the one first recorded here. The original finding was "no gateway
service qualifies, because `agents_gateway_api` is all free functions and injection would need a
public API redesign". True, but it framed the free-function surface as an obstacle. It is not an
obstacle; it is the actual subject. **The agents component does not currently present a
composable public surface.** When it does — AS60/AS63's work — that surface is the binding, and
the queue, session runtime and profile registry are constructed behind it. They never become
bindings themselves, at any point, however the API is reshaped.

Stage 1's mechanism is proven without item 6: the graph has a real edge, a Protocol-typed
dependency at a genuine foundation-capability boundary, and a real process routed through it.

## How later contributions are added (item 9, second half)

Append a `ServiceContribution` to `builtin_contributions()` in `runtime/bootstrap/composition.py`
and name its implementation in `composition.yaml`. No discovery, no scanning, no plugin lifecycle
— and none should be added until at least two independent contributors exist outside the
composition root, per §3's two-consumer bar.

Before adding any contribution, apply Rule 0 first: if the thing being added is not a component
public surface or a foundation capability, the answer is no, regardless of how convenient the
injection would be.

Two shapes remain distinct. A boundary with a genuine implementation choice gets a **binding**. A
boundary with one implementation but a lifetime worth owning gets a **composed singleton** with no
binding entry.

## Expected size of the graph

Rule 0 predicts order-tens of bindings at steady state — roughly one per component public surface
plus one per composed foundation capability. If the binding count starts tracking class count,
Rule 0 has been breached somewhere and the graph is becoming the container this item forbids. That
is the number to watch during AS60-AS66, and it is deliberately cheap to check.

It is also what keeps a later swap to a real DI engine bounded: a few dozen boundary bindings can
be re-expressed in another framework; a graph that had absorbed every collaborator could not.

## Rv888 Gateway Registry Lifecycle Correction 2026 08 04

**RV888 correction, 2026-08-04:** item 6's `_gateway_registry` rejection reason "installed and uninstalled at runtime" does not hold under inspection -- `GatewayServiceHost` is constructed exactly once per gateway-service process (before `serve_forever()`, torn down once in `finally`), which is ordinary constructor/destructor lifecycle, not runtime mode-switching. Whether the registry is present is fixed for that process's entire operational life, determined by which entrypoint launched it -- exactly the shape a build-time composition choice needs.

`_gateway_registry` is reopened as a candidate, but as a **composed singleton in a second, gateway-service-process-specific composition root** -- not a binding with project/shared implementation IDs selected by component-profile. That first-considered shape conflates Rule 0's binding/composed-singleton distinction, which this document itself already warns against ("criteria 1 gives a binding... criteria 4 gives a composed singleton... conflating them is the other way a composition root becomes a container"). Project-vs-shared-gateway is not a per-deployment config choice; it is determined by which process is running (CLI harness vs. the dedicated gateway-service process).

The corrected shape: project-local resolution stays a plain function (stateless, nothing to own, no composition needed); the shared-gateway registry becomes a composed singleton in a second composition root specific to the gateway-service process entrypoints (`agents_gateway_service_process.py::main()`, `commands/gateway.py::cmd_gateway`), with install/uninstall as that root's construction/shutdown -- the same pattern `runtime.application-host` already uses for `InteractionBackend`. This second root is not a new mechanism: `test_the_launcher_is_the_only_caller_of_the_composition_root`'s own docstring says "One process adopts the host in Stage 1; later roots are deliberate." This is that deliberate later root, and its trigger condition is exactly what this item's own item-6 disposition table already named for reopening ("AS63 / SH11 if the surface is reshaped") -- which is what AS60 is now doing.

Audited the other three rejected candidates against this same lifecycle-vs-mutability lens -- none are affected. `_QUEUE_MANAGER` and `_SESSION_RUNTIME` were rejected for the free-function-surface barrier (no Protocol, no injection point at all), unrelated to lifecycle. `agents_gateway_client._CLIENT` was rejected on ownership (SH11 Slice B), not lifecycle. The 9 module-global `Registry` instances were rejected on Rule 0 component-internal grounds (AS76), unrelated. Only `_gateway_registry`'s disposition changes. Full reasoning: RV888. AS60 owns implementing the corrected shape.
