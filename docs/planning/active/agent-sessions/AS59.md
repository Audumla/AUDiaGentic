## Mcp Boundaries

Management MCPs and harness runtime MCPs are separate projections over public APIs.

- Management MCPs expose configuration and operator functions.
- Runtime MCPs expose bounded capabilities to a launched harness.
- Harnesses require scoped gateway access for discovery/delegation/task status
  and permitted continuation.
- Operator-only global listing, overview, configuration, credentials and
  unrelated-task control remain unavailable to harnesses.

actual consumer and operation. Do not keep or remove a server by naming
convention alone. Concrete modules: `agents_manage_mcp.py`, `agents_mcp.py`,
`agents_gateway_mcp.py`.

# Stage 1: config-driven composition

## Separate Composition Configuration

Composition has its own typed configuration concern. Do not add DI fields to
component, provider, Execution Profile, Role or Agent Definition schemas.

Configuration selects stable implementation IDs only:

```yaml
composition:
  roots:
    - runtime.application-host
  bindings:
    runtime.application-host: runtime.default-host
    agents.execution-profile-resolver: agents.project-yaml
```

No Python paths, constructors, dependency lists, secrets or domain data belong
in this YAML.

Only genuinely replaceable services need selectable bindings. Do not create a
binding for every class or helper.

### Standards reconciliation

ARCHITECTURE_GUIDELINES §1 forbids "a service locator, an arbitrary
`dict[str, Callable]`, a string or dotted-path lookup" used to conceal a
forbidden dependency. A string-keyed service-ID → implementation-ID map is
permitted here **only** because ARCHITECTURE_STANDARDS §1 grants the composition
root access to any layer, and because resolution happens once at build time.
This must be made explicit, not assumed:

- only the composition root may read bindings;
- there is no runtime `get()`;
- ARCHITECTURE_STANDARDS §1's "a registry does not remove a dependency" still
  holds — resolved bindings remain dependency edges for architecture review.

Add an architecture test for the first bullet alongside the others below.

## Service Contributions

Code contributes typed implementation factories:

```text
service ID + implementation ID + required service IDs + factory
```

Runtime collects contributions, applies configured bindings and builds only the
graph reachable from configured roots.

The first implementation may use an explicit built-in contribution list at the
composition root. Pluggy integration can replace contribution collection later.
Do not build package scanning, a second plugin system or speculative
contribution lifecycle now.

## Foundation Facility

Add only:

- typed service/implementation IDs;
- factory registrations;
- configured binding selection;
- deterministic missing, duplicate and cycle errors;
- application lifetime;
- immutable built graph;
- reverse-order shutdown/finalizers;
- build-time test substitutions.

Do not add decorators, reflection auto-wiring, runtime `get()`, mutable
registration, child containers or task/session scopes.

Services remain plain Python and receive dependencies through constructors or
explicit parameters.

## Runtime Application Host And Legacy Exemption

Stage 1 wraps and reduces the existing `launcher.py` startup path; it does not
create a parallel startup path.

Add one runtime-owned root such as:

```text
runtime.application-host
```

The host:

- owns process startup/shutdown only;
- receives migrated services from composition;
- invokes existing construction paths for code not yet migrated;
- contains no new business logic;
- is not injected into domain/application services;
- is not a forwarding façade or catch-all API.

### Bounded legacy exemption

Existing unmigrated code may temporarily retain current globals, import-time
registration and direct construction only when all are true:

1. it remains behind `runtime.application-host` or an existing startup path
   called by that host;
2. the current plan item does not materially refactor it;
3. no new caller depends on the legacy access pattern;
4. no new global, locator, compatibility shim or duplicate route is added;
5. tests record the remaining exemption surface.

Once a service is touched by AS60-AS66, it leaves the exemption permanently and
becomes a configured composition dependency. Do not move migrated code back
behind legacy lookup.

This is an incremental architecture exception under the repository standards,
not a second architecture.

## Configuration Ownership

- Composition YAML selects implementation IDs and roots.
- Domain/component/provider configuration remains owned by its existing subsystem.
- Factories receive configuration APIs/repositories as ordinary dependencies.
- Foundation composition does not parse domain YAML or understand agents/providers.
- Runtime owns final graph construction and shutdown.
