## Simple domain model

- `SessionSurface`: exact harness interface and capability truth; AS29 owns it.
- `ExecutionProfile`: provider, model, selected surface, launch parameters and admission settings.
- `Role`: instructions and simple capability requirements. Runtime tool policy is placeholder-only in this sequence.
- `AgentDefinition`: one Execution Profile plus one Role, identity and skills.
- `InteractionSession`: persistent two-way context.
- `AgentTask`: one requested unit of work.
- ACP: external interactive-session adapter.
- A2A: external agent-task adapter and remote transport.
- management MCP: AUDiaGentic admin/configuration adapter over a component public API.
- runtime MCP: capability server materialized into a harness for the running agent to use.

## MCP boundary

Management MCPs and runtime MCPs are separate concerns, but both may call the same framework-neutral component/application APIs with different authorization and exposed operations.

### Management MCPs

Management MCPs are inbound AUDiaGentic administration/configuration adapters used by the CLI or an operator. They:

- call the owning component's framework-neutral public API;
- manage AUDiaGentic configuration and system-wide state;
- do not define a second configuration authority;
- use `propagate: audiagentic` when all exposed operations are operator-only;
- may expose global list/overview/reload/configuration and unrestricted administrative operations.

### Runtime MCPs

Runtime MCPs are tools/capabilities made available to a launched harness or agent. They:

- are selected from component activity servers and materialized through provider/runtime configuration;
- use provider launch-surface isolation and request-owned runtime materialization where supported;
- may call AUDiaGentic application APIs, including the AgentTask/gateway API, when the harness needs to request another agent capability;
- expose only operations authorized for the calling Agent Definition/session;
- are not management APIs merely because both use MCP transport.

Do not merge management and runtime MCP permissions or expose an operator-wide API merely because a harness needs bounded gateway access.

## Gateway access from harnesses

A launched harness must have a supported way to request AUDiaGentic agent capabilities. MCP is the common path for harnesses without a stronger extension/plugin integration.

The runtime-facing gateway/delegation surface may include:

- find/describe permitted Agent Definitions or skills;
- submit/delegate a bounded AgentTask;
- status/result/wait/cancel for tasks created by or explicitly shared with the caller;
- session continuation only where authorized and supported.

It must not automatically include:

- global request/session listing;
- gateway-wide overview or reload;
- Execution Profile, Role or Agent Definition CRUD;
- provider/model configuration or credentials;
- access to unrelated callers' tasks/sessions.

The same underlying gateway client/application API may serve both operator and runtime adapters. Use one MCP server with consumer-scoped tool projection only if the existing descriptor/materialization system can prove the tool and authorization subsets cleanly. Otherwise use two thin adapters over the same API. Do not duplicate gateway business logic.

## Runtime tooling scope

Runtime tool, MCP and permission configuration is not cleanly unified across harnesses today.

For AS60-AS66:

- run each harness with its existing configured/default runtime tools, MCP servers and permissions;
- preserve the required bounded gateway/delegation access used to request AUDiaGentic agents;
- do not copy, normalize, merge or override the rest of the runtime tool set through Role or Agent Definition;
- permit only an optional reserved placeholder/reference for future general runtime tool policy, with no runtime effect;
- do not add a general runtime tool-policy service, registry, schema expansion or cross-harness abstraction.

The runtime gateway/delegation surface is a required agent capability, not general tool-set management.

## Terminology rule

Do not introduce a hierarchy of stored snapshots or configuration revisions.

Use:

- `active configuration`: the IDs and concrete execution facts currently bound to a live session;
- `resolved`: a short-lived immutable in-memory value produced for admission or launch;
- existing generation/digest fields only where current code already requires stale-config, queue-lane or execution-context checks.

The existing immutable gateway admission value and AS29 resolved surface value are valid because they protect current queue/session correctness. Do not generalize them into Role/Agent snapshot stores or copied definition trees.

Persist only the minimum required to continue or audit a session safely. Do not copy full definitions into session records.

## Service-boundary rule

This work must support the planned IoC/DI refactor without implementing a container here.

- Application/domain callers depend on small service or port interfaces, not concrete YAML stores, provider adapters or global registries.
- Concrete stores, provider integrations and protocol adapters are wired at composition roots.
- Prefer constructor injection or explicit parameters.
- Remove touched module-global selectors such as gateway profile registry and queue-manager lookup when the owning item can wire them explicitly.
- Do not add service locators, hidden singleton lookup or module-import registration as part of AS60-AS66.
- Do not invent interfaces for one-line pure functions; add a boundary only where there is state, I/O, replaceable policy or an external system.

## Migration rule

- backward compatibility is not maintained by default;

- do not add legacy readers, handlers or temporary adapters unless a documented external obligation is approved before implementation;

## YAGNI rules

Do not add unless a demonstrated current requirement needs it:

- snapshot stores or snapshot registries;
- generic policy revision/overlay systems;
- role inheritance or multi-role stacking;
- cross-harness runtime tool-policy normalization;
- a shared management/runtime permission model merely because both use MCP;
- a separate runtime registry or runtime/session fan-out;
- a second task store, queue, lifecycle engine, output lane or binding index;
- raw ACP passthrough;
- a separate A2A runtime;
- raw A2A protocol tools inside harnesses;
- a DI framework or container in this plan sequence;
- compatibility shims, legacy handlers, dual writes or deprecated aliases.

Prefer direct migration of existing code over parallel abstractions.
