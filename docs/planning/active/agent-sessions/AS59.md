# Stage 1 architecture: config-driven composition

## Principle

The composition root is driven by a **dedicated composition configuration**, separate from:

- component product configuration;
- provider/harness configuration;
- Execution Profiles, Roles and Agent Definitions;
- runtime task/session data.

Do not add DI fields to those existing schemas.

## Composition configuration contract

Composition configuration selects implementations by stable IDs. It never contains Python import paths, constructors or arbitrary code.

Illustrative shape:

```yaml
composition:
  roots:
    - runtime.gateway-host
  bindings:
    agents.execution-profile-repository: agents.project-yaml
    agents.role-repository: agents.project-yaml
    agents.agent-definition-repository: agents.project-yaml
    agents.task-service: agents.default
    agents.session-service: agents.default
```

The exact file/namespace must use the existing configuration loader and precedence system, but it is a distinct `composition` concern. Do not bury these bindings in `agents.yaml`, provider YAML, project profiles or component options.

Only bindings with a real replaceable implementation need configuration. Mandatory internal services may have one declared default implementation.

## Service and implementation declarations

A service contract has a stable ID, for example:

```text
agents.task-service
agents.execution-profile-repository
providers.session-surface-resolver
foundation.process-service
```

An implementation has a stable ID, for example:

```text
agents.default
agents.project-yaml
agents.shared-gateway
providers.default-session-surface-resolver
```

Factories are code-owned and contributed through a typed plugin/contribution API. Configuration only selects IDs.

```text
plugin/component code
    -> contributes ServiceImplementation(id, provides, requires, factory)
composition config
    -> selects implementation IDs for service IDs
foundation builder
    -> validates and builds graph
```

No component owns the container or performs final wiring. Runtime owns graph construction.

## Foundation composition facility

Add a small framework-neutral facility under `foundation` with:

- typed service keys/contracts;
- typed implementation/factory contributions;
- config-selected bindings;
- deterministic missing, duplicate and cycle errors;
- application lifetime initially;
- immutable built graph;
- ordered shutdown/finalizers;
- test overrides supplied at build time.

Do not add:

- decorators or reflection auto-wiring;
- module scanning;
- arbitrary dotted imports from config;
- global `get()`/service locator access;
- mutable registration after startup;
- task/session scopes in the first implementation.

Services remain plain Python and receive dependencies through constructors or explicit parameters.

## Runtime bootstrap

Runtime startup performs this sequence:

```text
load enabled plugins/components
    -> collect typed service implementation contributions
load and validate dedicated composition configuration
    -> select implementation IDs
foundation composition builder
    -> validate and build application graph
start configured root hosts/adapters
    -> close graph on shutdown
```

The composition system must support internal and external plugins without editing central wiring code: a plugin contributes an implementation factory and configuration selects it by ID.

A future Dishka migration should replace graph construction/lifetime mechanics, not service contracts, implementation IDs, domain config or service constructors.

## Adoption rule

Every stateful service or external adapter created or materially refactored by AS60-AS66 must use this composition path.

Pure dataclasses, validation and deterministic transformations remain ordinary code.
