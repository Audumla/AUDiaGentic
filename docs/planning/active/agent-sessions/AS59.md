## Domain model

- `SessionSurface`: exact harness interface/capability truth; AS29 owns it.
- `ExecutionProfile`: provider, model, selected surface, launch/admission settings.
- `Role`: instructions and minimal demonstrated requirements.
- `AgentDefinition`: Execution Profile + Role + logical identity/skills.

- `AgentTask`: one unit of work.
- ACP/A2A: protocol adapters over canonical services.

Runtime tool policy remains deferred. Harnesses keep their existing configured/default tools except for the scoped gateway/delegation capability added later.

## MCP boundaries

Management MCPs and harness runtime MCPs are separate projections over public APIs.

- Management MCPs expose configuration and operator functions.
- Runtime MCPs expose bounded capabilities to a launched harness.
- Harnesses require scoped gateway access for discovery/delegation/task status and permitted continuation.
- Operator-only global listing, overview, configuration, credentials and unrelated-task control remain unavailable to harnesses.

Gate 0 must classify `ag-agents-mgmt`, `ag-agents` and `ag-agents-gateway` by actual consumer and operation. Do not keep or remove a server by naming convention alone.

## Terminology

- `resolved`: short-lived immutable admission/launch value.
- `active configuration`: minimal execution facts bound to a live session.

Preserve existing generation/digest values used for queue/session correctness. Do not create Role/Agent snapshot stores or copied definition trees.

# Stage 1: config-driven composition

## Separate composition configuration

Composition has its own typed configuration concern. Do not add DI fields to component, provider, Execution Profile, Role or Agent Definition schemas.

Configuration selects stable implementation IDs only:

```yaml
composition:
  roots:
    - runtime.application-host
  bindings:
    runtime.application-host: runtime.default-host
    agents.execution-profile-resolver: agents.project-yaml
```

No Python paths, constructors, dependency lists, secrets or domain data belong in this YAML.

Only genuinely replaceable services need selectable bindings. Do not create a binding for every class or helper.

## Service contributions

Code contributes typed implementation factories:

```text
service ID + implementation ID + required service IDs + factory
```

Runtime collects contributions, applies configured bindings and builds only the graph reachable from configured roots.

The first implementation may use an explicit built-in contribution list at the composition root. Pluggy integration can replace contribution collection later. Do not build package scanning, a second plugin system or speculative contribution lifecycle now.

## Foundation facility

Add only:

- typed service/implementation IDs;
- factory registrations;
- configured binding selection;
- deterministic missing, duplicate and cycle errors;
- application lifetime;
- immutable built graph;
- reverse-order shutdown/finalizers;
- build-time test substitutions.

Do not add decorators, reflection auto-wiring, runtime `get()`, mutable registration, child containers or task/session scopes.

Services remain plain Python and receive dependencies through constructors or explicit parameters.

## Runtime application host and legacy exemption

The current entry point in `launcher.py` is already the effective composition root. Stage 1 wraps and reduces it; it does not create a parallel startup path.

Add one runtime-owned root such as:

```text
runtime.application-host
```

The host:

- owns process startup/shutdown only;
- receives migrated services from composition;
- invokes existing construction paths for code not yet migrated;
- contains no new business logic;
- is not injected into domain/application services;
- is not a forwarding façade or catch-all API.

### Bounded legacy exemption

Existing unmigrated code may temporarily retain current globals, import-time registration and direct construction only when all are true:

1. it remains behind `runtime.application-host` or an existing startup path called by that host;
2. the current plan item does not materially refactor it;
3. no new caller depends on the legacy access pattern;
4. no new global, locator, compatibility shim or duplicate route is added;
5. tests record the remaining exemption surface.

Once a service is touched by AS60-AS66, it leaves the exemption permanently and becomes a configured composition dependency. Do not move migrated code back behind legacy lookup.

This is an incremental architecture exception under the repository standards, not a second architecture.

## Configuration ownership

- Composition YAML selects implementation IDs and roots.
- Domain/component/provider configuration remains owned by its existing subsystem.
- Factories receive configuration APIs/repositories as ordinary dependencies.
- Foundation composition does not parse domain YAML or understand agents/providers.
- Runtime owns final graph construction and shutdown.
