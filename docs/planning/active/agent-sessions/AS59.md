# Govern and align the layered agent-runtime refactor

## Goal

Make the active agent-sessions plan set one executable, non-contradictory sequence while transitioning from the current overloaded agent-profile/request terminology to the layered model agreed for AUDiaGentic:

1. provider session surface — exact harness interface and validated capabilities;
2. execution profile — reusable provider, model, selected surface, execution and admission mapping;
3. role — reusable instructions, tools, permissions and capability requirements;
4. agent definition — identity and public skills composed from one execution profile and one role;
5. interaction session — persistent two-way continuity over one resolved generation;
6. agent task and turn — external work identity and one execution within a session;
7. protocol adapters — ACP for interactive session clients and A2A for task-oriented agent clients.

This item is the execution-order, terminology, amendment, precedence and reassessment authority for AS60-AS66 and every pre-existing AS item affected by those additions. It does not implement runtime behavior itself.

## Immediate precedence and blocking rule

Until the affected older files are mechanically amended during Stage 4, this item overrides only their conflicting terminology, dependency and ownership statements. Their proven behavioral requirements remain in force.

No implementation may begin from AS60-AS66 or continue an affected older item unless the executor first checks this file's disposition table and applies the stated amendment. A contradictory older clause is treated as superseded by the corresponding AS59 amendment, not as an alternative implementation option.

This rule exists to avoid a temporary period in which both `AgentProfile` and `ExecutionProfile`, or both LLM-request and AgentTask authorities, are implemented in parallel.

## Architectural invariants

- AS29 remains the sole declaration/resolution authority for exact provider session-surface capabilities.
- AS19 remains the sole provider-neutral transport/control/observation contract.
- AS30 remains the sole durable AUDiaGentic-to-provider interaction-session binding/index authority.
- AS31 remains the sole assistant-content lane/final-output authority.
- AS21 remains lifecycle/reuse authority.
- Existing shared-gateway ownership, isolation, process supervision, leases, queues and recovery remain with their current owners.
- No new parallel profile, capability, session, binding, event, output, task, process or protocol registry may be introduced.
- `SessionRuntime` remains the interaction-session execution owner unless a later evidence gate proves a real need for one runtime instance to host multiple independent sessions.
- Existing internal names may be changed without compatibility guarantees, but external/config migrations must be explicit and bounded.
- AS60 renames and narrows the current profile authority; it must not create a second profile store or registry.
- AS61-AS62 compose behavior and public identity above execution profiles; they must not move provider/model/surface truth out of AS29/AS60.
- AS63 introduces the canonical task boundary but initially reuses the existing durable request, queue and turn authorities.
- AS65 and AS66 are protocol adapters over canonical application services, never alternate runtimes or raw protocol proxies.

## Canonical terminology and ownership

| Concept | Canonical owner | Meaning |
|---|---|---|
| Provider | providers component | Harness/provider family such as Pi, Codex or OpenCode |
| Session Surface | AS29/providers | Exact version/platform interface such as Pi ACP or Pi RPC and its validated capabilities |
| Execution Profile | AS60/agents gateway registry | Reusable provider, model, selected surface, execution/admission parameters and generation |
| Role | AS61/agents | Reusable instructions, tools, permission policy and capability requirements |
| Agent Definition | AS62/agents | Logical identity, skills and interface policy composed from one execution profile and one role |
| Effective Capability Snapshot | AS64 | Frozen composition of AS29 surface facts, model facts, execution restrictions and policy |
| Interaction Session | AS19/AS21/AS30/SessionRuntime | Persistent two-way continuity over one resolved generation |
| Agent Task | AS63 | Caller-visible unit of work; initially maps to one existing request/turn |
| Turn | existing session runtime | One execution inside an interaction session |
| Provider Session Ref | AS30/providers | Protected opaque identity returned/validated by an exact surface |
| External ACP | AS65 | Interactive session façade owned by AUDiaGentic |
| A2A | AS66 | Agent/task interoperability surface owned by AUDiaGentic |

`Runtime Instance` is not a new durable registry in this sequence. The current live interaction-session handle already owns the transport/process-related materialization. A separate runtime-instance lifetime may be introduced only after a reassessment proves a concrete one-runtime-to-many-session requirement.

## Authoritative disposition and amendment table

### AS19 — keep; amend terminology and snapshot inputs

Preserve:

- sole neutral `AgentSessionTransport`, prompt, result, observation and control contracts;
- sole normalized evidence ingress;
- provider-private ACP/native adapters;
- `SessionRuntime` FIFO, cancellation, timeout, observer and cleanup behavior.

Amend:

- replace any execution-config use of `agent profile` with `execution profile`;
- accept immutable `AgentDefinitionSnapshot`, `RoleSnapshot`, `ExecutionProfileSnapshot` and later `EffectiveCapabilitySnapshot` references/digests where correlation or policy requires them;
- do not make AS19 resolve roles, model capabilities, Agent Cards, A2A tasks or public ACP sessions;
- retain `SessionRuntime`; do not rename it to a general runtime manager in this sequence.

Conflict override: any AS19 wording implying the old Agent Profile remains the long-term logical-agent identity is superseded.

### AS21 — keep; no composition ownership

Preserve lifecycle, terminality and reuse authority.

Amend only consumers and correlation fields needed to carry immutable agent/execution/role generations. AS21 must not resolve roles, profiles, skills, model capabilities, ACP or A2A semantics.

### AS29 — keep; remain sole harness/session-surface capability authority

Preserve the exact surface/version/platform resolver, transport factories, identity/mapping operations, controls, lifecycle observation, content channels, ownership and validation evidence.

Amend:

- execution profiles select one explicit AS29 surface or provider-declared default through the resolver;
- AS29 supplies only surface/harness capability facts to AS64;
- AS29 does not own model capability truth, role requirements, agent skills, public Agent Cards or interface publication policy.

Conflict override: any new-plan field that copies or manually declares harness/session-surface capabilities is invalid; AS29 remains authoritative.

### AS30 — keep; rename AG session to interaction session where helpful

Preserve protected provider-session bindings, generations, opaque refs, ownership, exact continuation/attach/resume/replace rules and the binding index.

Amend session-generation context to persist or bind immutable identifiers/digests for:

- agent definition;
- role;
- execution profile;
- resolved AS29 surface;
- effective capability snapshot;
- existing execution/project/identity fingerprints.

Do not introduce a runtime-binding index. The binding remains between an AUDiaGentic interaction-session generation and the exact provider session/thread identity.

Conflict override: changing role, execution profile or agent definition never silently mutates a live generation; it requires explicit fresh/replacement/resume semantics as applicable.

### AS31 — keep; canonical content source for all interfaces

Preserve its separate content lane, output relay/storage, final-output selector, bounds and redaction.

Amend:

- name Agent Task/Turn correlation where AS63 adds the task identity;
- declare AS31 output as the sole assistant-content input for AS65 ACP updates and AS66 A2A message/artifact projection;
- prohibit ACP/A2A adapters from parsing provider-native frames or creating separate output stores.

### AS47 — keep; extend exact continuation compatibility

Preserve same-generation continuation, exact project/execution context, FIFO and live-handle reuse rules.

Amend continuation checks to include immutable:

- agent-definition generation/digest;
- role generation/digest;
- execution-profile generation/digest;
- resolved surface identity;
- effective-capability digest.

An external ACP client or A2A task may continue a generation only through the same canonical check. A changed composition cannot be silently re-resolved into an existing session.

### AS49 — keep; explicit new-generation resume only

Preserve terminal source immutability and explicit provider-native resume into a new linked interaction-session generation.

Amend the successor context to freeze the resolved Agent Definition, Role, Execution Profile and Effective Capability snapshots. Resume must not silently upgrade to a changed role/profile/agent definition unless an explicit policy and compatibility operation is added in a later plan.

### AS57 — keep; protocol-neutral read service

Preserve authorized, bounded status/output reads and no-side-effect semantics.

Amend:

- identify it as the canonical read service beneath AS65 and AS66;
- add task identity/cursors only through AS63-compatible contracts;
- do not add ACP frames, A2A events, SSE/WebSocket semantics or protocol-native stores to AS57.

### AS58 — keep; protocol-neutral control service

Preserve generic validated controls, authorization, idempotency, ownership and acknowledgement-vs-lifecycle separation.

Amend:

- identify it as the canonical control service beneath AS65 and AS66;
- ACP and A2A adapters translate their requests to AS58 actions and canonical results;
- no protocol adapter bypasses AS58 to call provider controls directly.

### Existing profile and shared-gateway plans/code — amend through AS60, do not duplicate

The existing `AgentProfile`, project profile file, `GatewayProfileRegistry`, `GatewayProfileSnapshot`, lane-key and reload/staleness behavior are the baseline to rename/migrate into Execution Profile concepts.

AS60 must characterize and extend those exact stores, schemas and services. It must not introduce a second execution-profile registry beside them.

### Existing request/queue/recovery plans/code — amend through AS63, do not replace initially

The current durable gateway request, submission envelope, queue, dispatch, recovery, idempotency and request-to-turn mapping remain authoritative in the first Agent Task slice.

AS63 adds a canonical Agent Task contract and compatibility mapping. It does not create a second task store/coordinator unless reassessment R4 proves one is required for multi-turn A2A semantics.

## New-item boundaries

### AS60 — Execution Profile refactor

Supersedes only the old **name and semantic claim** that the provider/model mapping is a complete Agent Profile. It does not supersede existing registry, generation, queue-lane, reload, execution-manifest or profile persistence behavior; those are migrated in place.

### AS61 — Roles

Adds one new reusable behavior/policy layer. It may reference tool identifiers and capability requirements, but it may not launch harnesses, select provider/model/surface, own session state or advertise protocol endpoints.

### AS62 — Agent Definitions

Adds logical identity, skills and interface publication policy and composes one Role with one Execution Profile. It does not own execution queues, provider transports, session bindings, content or lifecycle.

### AS63 — Agent Tasks

Adds the protocol-neutral public work contract. Initially `one AgentTask = one existing gateway request = one session turn`; multi-turn task orchestration remains deferred behind R4.

### AS64 — Effective capabilities

Composes existing authoritative facts. It is not another mutable capability registry. Unknown remains unsupported. AS29 owns surface facts; the model source owns bounded model facts; role owns requirements; policy may only restrict.

### AS65 — External ACP façade

Exposes AUDiaGentic-owned interaction sessions through ACP. It uses AS19/AS30/AS31/AS57/AS58 and cannot raw-proxy a provider ACP process, expose provider session refs or become a second lifecycle authority.

### AS66 — A2A surface

Publishes selected Agent Definitions and maps A2A work to Agent Tasks. It uses existing task/session/content/status/control services and cannot become a second orchestrator, session store, artifact store or capability registry in its first slice.

## Execution order

### Gate 0 — characterize and freeze baseline

Before AS60 implementation:

- inventory every current use of `AgentProfile`, `GatewayProfileSnapshot`, `agent_profile_id`, `SubmissionEnvelope`, `submit_llm_request`, `SessionRuntime`, session IDs/generations, request IDs and turn IDs;
- inventory all current AS items that use profile/request/session terminology;
- add any affected item not listed above to this disposition table before editing code;
- run the nearest profile, gateway, session, transport, binding, output and shared-service tests;
- record baseline files, tests and already-landed behavior in AS60-AS66 rather than creating duplicate paths.

Gate 0 completion requires a contradiction report with every affected plan classified as `keep`, `keep/amend`, `partially superseded`, `fully superseded` or `unaffected`.

### Stage 1 — AS60 execution-profile refactor

Rename and clarify the existing provider/model profile as `ExecutionProfile`. Preserve behavior. Add explicit surface selection only through AS29. Migrate gateway-owned snapshots/registries and project-local configuration in place.

**Reassessment R1:** confirm execution profile remains a narrow execution/admission mapping. If role, public-agent identity, tool policy or A2A fields leaked into it, stop and correct boundaries before AS61.

### Stage 2 — AS61 role contracts

Add minimal reusable roles containing instructions, tool policy, permission policy and capability requirements. Avoid memory, planning, workflow and delegation frameworks beyond small extension points.

**Reassessment R2:** prove at least two execution profiles can use one role and one execution profile can use two roles without provider-specific branching or deep untyped merge semantics.

### Stage 3 — AS62 agent-definition composition

Add logical agent identity, role/execution-profile references, skills and interface publication policy. Resolve one immutable snapshot and validate role requirements against effective capabilities.

**Reassessment R3:** review the composition using at least Pi ACP and one non-ACP/native or fake surface. Confirm a logical agent can change execution profile without changing public identity/skills unless explicitly versioned.

### Stage 4 — mechanically amend affected existing plans and persistence

Before AS63 implementation:

- update the affected AS files using this amendment table;
- update terminology/dependency diagrams and acceptance criteria, not only prose notes;
- add immutable composition snapshots/digests to AS30/AS47/AS49 session-generation requirements;
- mark any partially superseded clause in the old item and name the exact replacement;
- delete duplicate implementation steps rather than leaving both paths executable.

No item may be marked fully superseded unless all of its still-useful behavior is assigned to a named replacement and its state/header clearly records the disposition.

### Stage 5 — AS63 agent-task contract

Generalize the public domain boundary from LLM prompt request to Agent Task while retaining existing request/turn stores and `submit_llm_request` compatibility during migration.

**Reassessment R4:** prove one task maps cleanly to one current turn without losing behavior, then assess whether multi-turn A2A tasks require a later durable task coordinator. Do not build one speculatively.

### Stage 6 — AS64 model/effective capability composition

Introduce the smallest model capability source needed to validate role requirements and public interfaces. Compose AS29 surface facts, model facts, execution restrictions and policy into one immutable snapshot.

**Reassessment R5:** if model capabilities cannot be evidence-backed and bounded, keep unknown unsupported and defer broad catalog work.

### Stage 7 — AS65 external ACP façade

Expose AUDiaGentic-owned interactive sessions to external ACP clients using canonical services. Never raw-proxy an underlying provider ACP session.

**Reassessment R6:** validate with one native ACP-backed harness and one non-ACP/fake transport to prove provider neutrality.

### Stage 8 — AS66 A2A agent/task surface

Publish selected Agent Definitions as A2A agents, generate Agent Cards, map A2A tasks/messages/artifacts to the canonical task service, and project bounded output/status from existing lanes.

**Reassessment R7:** begin with deterministic gateway orchestration. Add MCP delegation or model-directed delegation only after identity, authorization, recursion, workspace/artifact and budget policies are proven.

## Validation

- execution follows this order unless this tracker records an approved deviation;
- every reassessment records findings and plan changes before the next stage;
- every executor checks the authoritative disposition table before touching an affected item;
- no stage introduces a parallel authority owned by an existing AS item;
- migrations are one-way after bounded compatibility windows close;
- architecture/AST tests enforce dependency direction:
  - protocol adapters -> agents public services;
  - agents -> provider-neutral foundation contracts;
  - providers -> private protocol/native adapters;
  - agents core must not import A2A, ACP-native or provider-native types;
- documentation diagrams and terminology are updated at each gate rather than deferred;
- contradictions between an older item and AS59 fail plan validation until the older item is mechanically amended or explicitly marked partially superseded.

## Acceptance criteria

- AS60-AS66 and amended existing items form one executable, non-overlapping plan sequence.
- Gate 0 records a complete affected-plan contradiction/disposition report.
- Each reassessment gate has a recorded decision.
- The final domain model contains distinct Execution Profile, Role, Agent Definition, Interaction Session, Agent Task and Turn concepts.
- External ACP and A2A are adapters over canonical services, not alternate runtimes.
- Existing session persistence, isolation, observability, bindings, output, queue and recovery work is reused rather than replaced.
- No active plan leaves both the old Agent Profile authority and the new Execution Profile/Agent Definition authorities executable at the same time.
