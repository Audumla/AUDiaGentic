# Fix the Windows close() child-process orphan race

## Description

`tests/unit/foundation/transports/test_acp_session_subprocess.py::test_close_kills_child_process_no_orphan` fails reproducibly on Windows today: the child process is still alive immediately after `close()` returns.

This is the entire remaining scope of child-process supervision. A characterization pass on 2026-08-04 confirmed the rest is built and tested: the adopt/observe/stop contract, identity-safe stop (refuses PID reuse, refuses external processes), the Windows kill-on-close Job Object, idempotent handle release ordered last in `close()`, honest POSIX/Windows guarantee documentation, session diagnostic projection of `child-pid`/`child-creation-identity`, and the architecture test forbidding direct OS signalling outside `foundation/system/`.

## Steps

1. Characterize the exact race before changing anything. The suspect sequence is in `AcpAgentSessionTransport.close()`: `proc.terminate()` -> `await wait(timeout=CANCEL_GRACE_SECONDS)` -> `proc.kill()`, followed by `close_kill_job()`. Determine whether the gap is a missing final wait after `kill()`, or the test's liveness check racing normal OS teardown latency.
2. Fix the real cause. If it is teardown latency rather than a leak, the fix is in the transport's close contract (close should not return until the child is confirmed gone or a bounded deadline expires), not in loosening the test.
3. Re-run the full transport suite plus the Windows subprocess tests.
