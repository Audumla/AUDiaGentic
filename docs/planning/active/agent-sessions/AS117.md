# Make durable gateway sessions mandatory without forcing provider transport

## Description

Every admitted gateway request must receive a durable gateway session identifier and session record. Provider-side persistent session attachment remains a separate, capability-driven concern; a full-isolation one-shot provider must retain its approved CLI transport.

## Steps

1. Split durable gateway-session identity from provider conversation transport selection in admission and dispatch.
2. Allocate and persist a gateway session for every new request, including one-shot queue requests, and bind every request record to it atomically.
3. Preserve provider transport selection: only explicit continuation/keep-alive or a provider-specific capability chooses SessionRuntime/ACP/CDP.
4. Migrate current request/session assumptions and remove sessionless dashboard fallback once all new requests satisfy the invariant.
5. Add admission, restart/recovery, dashboard, cancellation, and cross-provider regression tests.

## Detailed Solution & Technical Design

`session-id` currently carries two incompatible meanings: durable gateway correlation and selecting the live provider-session route. Introduce a durable gateway session allocation at admission for all new requests, then add a separate immutable transport selection fact to the admitted request/session binding. Queue dispatch uses the transport fact, not mere session-id presence. A one-shot Pi request therefore receives a durable session/timeline/dashboard grouping but continues through `pi --print`; an explicit conversation continues through its provider session only where the provider declares and validates that surface. Provider metadata is attached to the durable gateway session whenever such a provider session is opened.
