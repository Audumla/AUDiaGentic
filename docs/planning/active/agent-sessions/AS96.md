# Complete the Pi RPC tap evidence mapping

## Description

Finish mapping Pi's tapped RPC frames into the neutral evidence pipeline as enrichment on the session the ACP transport already drives — never as a second lifecycle authority.

Most of this is built. The generic interfaces landed (`PreSpawnHook`, `AuxiliaryObservationSource` in `foundation/transports/acp.py`), the Pi-specific wiring landed (`adapters/pi/rpc_tap_evidence.py` — frame mapper with a closed vocabulary, tap observation source, pre-spawn hook), the threading through `prepare_provider_session_transport` landed with a signature guard so only Pi gets a hook, and Pi's ACP-evidence inventory entry is validated on linux-amd64.

## Steps

1. Re-scope per RV977: reduce AS96 to "optional Pi-private, fail-open auxiliary evidence for transcript-proven facts". Do NOT add a source tag or an ACP-wins precedence rule to the shared evidence sink — emit auxiliary Pi observations with `sequence=None` (the sink already accepts unsequenced evidence), since a Pi-local counter is not a canonical turn sequence.
2. Do not promote Pi tap observability to a generic feature; keep the tap as adapter-private enrichment that no generic capability depends on.
3. Extend the frame mapper beyond the four transcript-proven frame types (`agent_start`, `message_update`, `turn_end`, `agent_end`) only as each additional type gains its own proof. `tool_execution_*`, `compaction_*`, `queue_update`, `auto_retry_*` are declared unsupported/out-of-scope for this item — `TRANSPORT_UNKNOWN` is terminal for this item, not an implied obligation.
4. Finish the remaining process-tree cleanup and crash/restart coverage for the tap listener (bounded fail-open cleanup/crash proof).
5. Update Pi's surface evidence declaration to the level actually proven, per platform — and only claim a unique fact (e.g. model thinking) if a real transcript proves it.

## Codebase Verification 2026 08 05

**Verified against the tree. Step 1's "add a source tag" needs a design correction — the obvious implementation is wrong.**

`StatusEvidenceSourceKind` (`foundation/transports/harness_status_observer.py:21`) is documented as **"Source mechanism for a status observation"** with four values: `transport-observation`, `managed-hook`, `managed-plugin`, `structured-output`. `StatusEvidence` (line 50) carries it as `source_kind`.

**The trap:** the natural-looking fix is to add a fifth value such as `transport-auxiliary` for tap-origin evidence. That is wrong. ACP frames and Pi RPC tap frames are **both** the `transport-observation` *mechanism* — they differ in *origin within that mechanism*, not in mechanism. Adding a fifth enum value would collapse two distinct axes into one field, and §3 permits unifying types only when ownership, lifecycle, validation and semantics all match. Mechanism and origin share none of those.

**Do this instead:** add a separate, narrow origin field to `StatusEvidence` (an identifier for the publishing source within a mechanism), leave `source_kind` meaning exactly what it means today, and implement ACP-wins-on-conflict as a precedence check against that new field in `harness_status_evidence.py::accept()` (line 108).

**Why the conflict is real and not theoretical:** `accept()` validates monotonic sequence ordering, and the ACP transport and the tap allocate sequence numbers from independent counters for the same turn. Without an origin field the sink cannot express "ACP wins" — it can only express "first arrival wins", which is arrival-order-dependent and therefore non-deterministic across runs.

**Bounded by prior art:** `normalize_harness_status_observation` already drops `TERMINAL`/`TRANSPORT_ERROR` observations from every source before they reach evidence, so the tap can only currently affect `ACTIVITY` (-> `model-thinking`). The conflict surface is small today — which is exactly why this is worth fixing before step 3 widens the mapped frame vocabulary on top of it.
