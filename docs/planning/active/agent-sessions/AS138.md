# Capture latest GPT-auto DOM response on failed requests

## Description

When a GPT-auto request reaches a terminal failure or interruption after a provider response is visible in the bound conversation DOM, capture the latest request-scoped assistant response as diagnostic failure output. Preserve the failure lifecycle and success/output semantics: this evidence must never promote a request to completed or populate the verified success response field.

## Steps

- Define a separate failure-response diagnostic artifact and public projection field with explicit provenance and truncation limits.
- Capture the latest assistant response only from the request's validated provider binding and current turn correlation; record DOM state and failure classification alongside it.
- Persist the diagnostic artifact before terminalizing the failed request and expose it through the failure/status diagnostics surface without duplicating the success output.
- When the bound DOM shows the exact provider network error ('A network error occurred. Please check your connection and try again.'), do not click Retry; retain the same session and submit one bounded follow-up prompt asking ChatGPT to complete the previous request, including the original request text when safe and available.
- Capture request-scoped DOM snapshots, activity transitions, recovery prompts, and follow-up outcome in the timeline/logs for diagnosis.
- Cover provider error alerts, provider-binding observation failures, interrupted recovery, missing-tab recovery, and no-response cases.
- Run focused unit/integration tests plus live CDP validation against failed BigCherry requests.

Add a workflow-configured provider-error continuation policy, classify generic request/error alerts separately from exact network-error alerts, preserve failure evidence and timeline state, then submit one bounded same-session continuation only for a validated non-terminal durable session.

## Detailed Solution & Technical Design

Add a request-owned failure evidence channel distinct from completion.output/response-artifact. The capture operation must use the existing validated CDP snapshot and request turn correlation, never a document-global or unrelated tab. Store bounded response text, digest, capture timestamp, provider session reference, DOM signals, and whether the response was complete or partial. On failed or interrupted transitions, best-effort capture may enrich diagnostics but must not change the terminal outcome or success artifact. Failure capture must be non-fatal and redacted and capped.

Extend GptAutoRecoveryConfig with provider-error-followup-enabled, provider-error-followup-max-attempts, and provider-error-followup-prompt-template. Dispatch merges DOM and policy evidence, excludes network-error-alert from the generic branch, preserves failure-response evidence, records provider.turn.failure-recovered and provider.followup.submitted, and recursively continues the same session with a bounded attempt counter. Completion evidence remains authoritative and terminal provider/auth/session failures remain fail-closed.

## Effort & Risk

Requires coordinated provider, durable-record, and projection changes. Main risk is accidentally turning best-effort diagnostic capture into a success signal or capturing unrelated conversation text.

## Standards

- Preserve request, session, and provider binding correlation.
- Failure capture is best-effort and non-terminalizing.
- Keep diagnostic evidence separate from verified success output.

## Acceptance Criteria

- A gateway restart preserves the original queued/running request and session identity.
- Recovery first matches an existing CDP tab by durable provider conversation identity, including mutable ChatGPT URL slugs.
- If the matching tab is absent but the durable provider conversation URL exists, recovery opens a replacement tab on that exact conversation.
- Recovery observes the existing provider turn without resending the original prompt.
- A response completed while the gateway was down is captured into the original request and terminalized correctly.
- If no durable provider identity exists, recovery fails closed without guessing or duplicate submission and records an actionable recovery diagnostic.
- Focused tests and a post-restart live CDP validation pass.
