# Consolidation: AS29 session-surface capability families and the provider capability model are the same pattern — share one abstraction

## Notes

Raised from provider-capability-model (PC01/RV845) + AS19 (RV846). Maintainer steer: not fixed to the plans; looking for simplification/consolidation across the session/launch/observation/capability cluster. This proposes convergence, not a claim AS29 is wrong — AS29's rigor is a feature to preserve.

## Findings

1. TWO PARALLEL CAPABILITY-FAMILY MECHANISMS. AS29 declares 'generic external-management capability families' as typed family/action records, with declaration separate from executable validation, dispatched by typed family/action and never by provider name, resolved from a catalogue-like surface. That is architecturally identical to the provider capability model (PC): typed families [managed-reconcile/cli-lifecycle/generated-surfaces], declaration-vs-proof, no provider-name branch, a config catalogue. We are on track to build/maintain the SAME machinery twice — once for provisioning (PC) and once for session/control/observation (AS29). Recommend: ONE capability-family abstraction (typed family + action + declaration + validation-state + no-name-branch dispatch) shared across domains; AS29 session controls (state/cancel/interrupt/steer/permission/follow-up/attach/resume/close) become capability families in the SESSION domain of that one system, not a separate parallel type hierarchy.

2. DECLARATION OVERLAP with `launch`/observation. AS29 session_surfaces sections for transport-factory, lifecycle-observation-source, and generic-controls overlap the PC `launch` capability (interaction/observability channels + recipes) and the capability-driven observation steer (RV846). Today the provider declares its session/launch/observation surface in up to three places (PC launch capability, AS29 session_surfaces, AS27 inventory). Converge on ONE provider declaration (capability model), with AS29's ResolvedSessionSurface being the immutable, version/platform-RESOLVED view derived from it — not a second authored declaration. This directly reconciles AS29's 'session_surfaces is the sole declaration owner' with RV846's 'observation is capability-driven': same source, one owner, expressed as capabilities.

3. PRESERVE AS29's DOMAIN RIGOR (do not over-merge). The session domain legitimately needs more than provisioning: exact surface/version/platform resolution, an immutable frozen-per-generation snapshot, strict redaction (no factories/commands/tokens/raw event names), and platform-specific validation ceilings. Consolidation = share the family/action + declaration/proof + dispatch CORE; KEEP session-domain specializations (version/platform freeze, ResolvedSessionSurface immutability, redaction) as that domain's rules. Do NOT flatten session capabilities into project-level provisioning semantics.

4. DECLARATION vs PROOF seam is already correct and shared: AS29/PC declare; AS54 proves (recipes A/B/C/D, validation_state, effective_level); AS19 is the neutral evidence/mapper. Keep this exactly — it is the model for the whole capability system (declaration in the catalogue, proof in the probe matrix). PC's 'evidence-only tier' should follow the SAME seam rather than mirroring proof into the descriptor (RV845).

## Conclusion

Converge the two capability-family mechanisms onto one shared abstraction (typed family/action + declaration/validation-state + no-name-branch dispatch), with a provisioning domain (PC families) and a session domain (AS29 families). Make the provider capability model the single DECLARATION source for launch/observation/session surface; AS29 ResolvedSessionSurface = the immutable version/platform-resolved VIEW derived from it; AS54 = the shared PROOF matrix; AS19 = the neutral mapper. Preserve AS29's version/platform freeze, immutability, and redaction as session-domain rules. This removes a whole duplicated capability-declaration stack while keeping AS29's guarantees. Coordinate: PC01 (capability/family core), AS19 (RV846, observation source), AS29 (session families + resolved view), AS54 (proof). Large cross-plan design reconciliation — do before AS29/AS19 lock their 'sole owner' contracts.
