# Idempotency rule underspecified for ID collision; stale AS101 attribution

## Notes

External adversarial review 2026-08-09. Confirmed AS95 correctly needs NO residue from the dissolved AS103 — it already owns cooperative duplicate-control idempotency, and the retired anti-replay/tamper machinery would be over-building. But two gaps remain. (1) The rule 'repeated requests with the same client control id return the original result' is underspecified: it does not say what happens when the same control ID arrives with a DIFFERENT session, turn or action. As written an accidental ID reuse could alias a completely unrelated control request onto an earlier result. This is ordinary correctness for cooperative retries, not hostile-replay defence, so it belongs here even under the non-hostile deployment model. (2) Stale AS101 attribution appears in both the verification and threat-model-correction sections; the underlying rules (project targeting, ownership-mode legality, acknowledgement != lifecycle) are all still correct and should be retained, but stated directly rather than attributed to an item that no longer owns them.

## Findings



## Conclusion

Two edits. (1) Specify the collision case explicitly: same control ID + same canonical request -> return the original result; same control ID + different session/turn/action -> reject as an idempotency conflict and do not dispatch. (2) Restate the project-targeting and ownership rules directly, removing the AS101 attribution. No AS103 residue is to be added here. Confirmed independent of AS93/AS94 — AS95 works against the frozen surface snapshot and live provider transport, so it can proceed in parallel and must not be sequenced behind the read chain.
