# Add client-facing capability advertisement to the diagnostics projection (sponsor-approved 2026-07-18)

## Notes



## Findings

The AS28/AS19/AS27 layering resolves harness capability internally (declaration → providers_api resolution → gateway behavior), but no item owns the CLIENT-facing advertisement: a gateway caller (MCP tool, remote operator, agent-jobs) cannot ask "what can this session/request actually do?" and must instead attempt cancel/steer/resume and learn from errors. That contradicts the layering principle — callers should adapt to capability exactly the way the gateway does.

Proposed design (sponsor approved): extend AS16's read-only projection with a `capabilities` section on session_compute / request status, sourced ONLY from the resolved AS19/AS28 declaration for the session's surface+version at open time — never inferred from adapter behavior, never populated for an unresolved surface (absent means unknown, mirroring AS16's absent-not-false rule):
```json
"capabilities": {
  "surface-id": "opencode-acp",
  "version": "<resolved>",
  "controls": ["cancel-turn"],            
  "observation-mechanism": "transport-observation",
  "supported-statuses": ["..."],
  "evidence-tier": "<declared, AS19>"
}
```
`controls` lists AS28 SessionControlAction values the resolved declaration proves; the section is captured once at session open (immutable with the SH02 context identity, consistent with AS08) and projected, not re-resolved per status call. Redaction rules unchanged — enum/id values only. Consumers: MCP status/wait outputs, SH04 service_status per-session rows, agent-jobs decision to offer cancel/steer affordances.

Dependency: resolvable declarations arrive with AS19/AS28; until then the section is simply absent — AS16 can land the projection shape immediately with a None source and wire the real source when AS19's resolver exists.

## Conclusion

Extend AS16 scope with the declaration-sourced capabilities section (absent-when-unresolved); wire the source after AS19 lands.
