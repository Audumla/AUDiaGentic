# Implement per-harness status-observer recipes and probes

## Description

Turn AS19's generic observer platform into an explicit, version-gated recipe for every known harness surface/mode. The matrix records declared capability, validation state, and effective production level independently: documented candidates guide probes, while only validated capability may enable status evidence or state management in production. ACP/native transports remain attach-only, hooks use Hindsight-style controlled reconciliation after proof, and unresolved surfaces retain conservative process-only policy without heuristic completion.

## Steps

0. Implement AS28 and the rebased AS19 first. Every harness recipe receives AS28 `PreparedSessionTransport` and neutral `TransportObservation`; every observer adapter returns only AS19 `StatusEvidence | None`; AS21 alone projects state. An ACP surface is a provider-declared transport capability, not a type in gateway or observer code.
1. Use these fixed recipes; do not create a harness-specific gateway path.

**Recipe A — declared transport observation (ACP or native).** Add `providers/adapters/<provider>/status_observer.py` with `build_status_observer(...) -> TransportObservationObserver`; its lease owns `observe_transport(observation: TransportObservation) -> StatusEvidence | None` and returns `{}` for `launch_environment`. Add a YAML observer declaration only after its exact surface/version probe:
```yaml
harness_status_observers:
  - surface_id: <provider>-acp-or-native
    version_constraint: <exact-probed-version>
    mechanism: transport-observation
    supported_statuses: [<only-proven-canonical-enum-values>]
    correlation_fields: [provider_session_ref, turn_or_request_ref]
    event_ordering: per-turn
    adapter_ref: audiagentic.components.providers.adapters.<provider>.status_observer:build_status_observer
```
The AS28 provider transport factory, not agents, maps ACP/native frames to `TransportObservation`. The observer maps only that neutral vocabulary; unknown observations return `None`. It writes no config, plugin, hook, or ingress command.

**Recipe B — managed native hook.** The provider adapter computes stable `ManagedHooksEntry` instances and invokes the existing `providers_api.manage_hook_entries(...)`, exactly as Hindsight does:
```python
ManagedHooksEntry(
    managed_id='agents-status-observer-<provider>-<native-event>',
    event='<proven-native-event>',
    command=(f'{sys.executable} -m audiagentic.components.agents.harness_status_emitter '
             f'--provider <provider> --surface <surface> --event <native-event>'),
    timeout=2,
)
```
Use ownership scope `agents/status-observer/<provider>/<surface>`. `plan`/`status` make no write; `apply` reconciles this desired set; `prune` calls the same public family with empty entries. The command reads only AS19's per-session endpoint/token/binding environment, submits one bounded record to loopback ingress, and exits zero on delivery failure. It can observe only—never invoke AS28 control actions. Add `hooks_config` and YAML only after the versioned probe proves project-scoped reader/writer/remover, event spelling, environment inheritance, stdin payload, and reload behavior.

**Recipe C — structured CLI output.** Add `providers/adapters/<provider>/status_observer.py` only after an isolated run proves a stable line protocol. The AS28 transport factory emits bounded neutral `TransportObservation` values; the adapter maps them to evidence. It never regexes prose or treats EOF/silence as terminal. No persisted hook/config artifact is written; absent schema means no evidence.

**Recipe D — unresolved/external.** This is a production policy, not a claim that a product has no capability. Add no runtime observer adapter, YAML observer declaration, configuration writer, or native control claim until a versioned probe passes. Record `capability_facts` with `declared_capability`, candidate source(s), exact source/version, `validation_state: probe-required|blocked|unsupported`, `effective_production_level: O0`, limitation, and probe anchor. Recipe D prohibits unsupported instrumentation and heuristic terminal inference: human UI/terminal scraping, resource inactivity, output silence, EOF, and final-looking prose must never complete a turn. It permits locally owned/adopted process lifecycle as O0 health evidence and explicitly leaves official hooks/plugins, RPC/API event streams, structured output, and status APIs eligible for their own A/B/C probe recipes. Remote, cloud-managed, editor-hosted, and externally managed instances do not automatically have O0 because the gateway may not own/adopt their process.

## Detailed Solution & Technical Design

1. Maintain a provider-neutral observability inventory in providers services that records each surface's declared protocol/capability, local validation state, effective production observation level, lifecycle source, and exact probe anchor/version/mode. Its conformance gate remains the sole authority for transport-observation publication eligibility.

2. Split upstream platform support from AUDiaGentic local validation evidence. Add or retain distinct descriptor fields: supported_platforms is a vendor/product capability fact and may list Windows/macOS/Linux for OpenCode native ACP; validated_platform_evidence contains only exact local probe evidence. A surface is publisher-eligible only when its selected execution platform is in validated_platform_evidence, validation_state is VALIDATED, level is O1+, and lifecycle_source is transport. Product support alone must not promote validation, effective level, or eligibility.

3. Make resolver outcomes deterministic and safe: a surface with broad vendor support but no current-platform local probe resolves unsupported/no observer lease rather than publishing heuristic or invented evidence. Surface selection/launch remains separately allowed where provider configuration supports it; observability publication has its own proof gate.

4. Inventory and provider descriptors must name launch command/version/mode, protocol surface, correlation proof, test fixture/probe path, and known unsupported/unknown events. Do not place raw provider event names or generic prose parsing in agents code. AS29 turns a passing exact surface probe into a declaration; AS27 only inventories and enforces it.

5. Build the documentation matrix from the same vocabulary, explicitly labeling product support, local probe evidence, and effective production capability as distinct. Existing docs can record candidate native ACP/RPC/adapter routes but must state O0/probe-required until tested.

6. Tests: inventory schema integrity; platform product support does not imply publish eligibility; targeted validated-platform evidence is required; resolver returns no lease on unsupported/unprobed platform; exact version/mode anchor required; a non-validated surface cannot claim O1 or transport publisher; descriptor/runtime consistency; docs/schema tests if local convention supports them.

## Validation

Each known harness has exactly one explicit recipe in this item. Recipe A declarations have a pinned ACP probe, no config write, and adapter-only mapping; Recipe B declarations have a proven project-scoped config reader/writer/remover, owned IDs, non-vetoing emitter, apply/prune proof, and binding correlation; Recipe C has a proven structured schema and never parses arbitrary text; Recipe D has no implementation artifact and a conservative evidence record. No row may claim O2/O3, populate `supported_statuses`, or write a provider config from documentation alone. The full matrix verifies every provider/harness has a declared route or an explicit unsupported fallback, so the gateway never has to guess. The matrix must preserve `declared_capability`, `validation_state`, and `effective_production_level` separately. Documentation alone may populate candidate facts and a probe recipe, never a production declaration, `supported_statuses`, config mutation, or control claim. `local-openai` is excluded from harness rows.

## Effort & Risk

Complex multi-harness rollout, controlled by immutable per-row gates. The high risk is treating a matrix row as permission to implement guessed hooks or assuming ACP parity. The mitigation is deliberate: Recipe A is attach-only, Recipe B writes only owned entries after a versioned probe, Recipe C rejects prose, and Recipe D is a successful conservative outcome. Do not mark AS27 complete until every row has an evidence record; implementation-capable rows remain pending until their own Docker proof.
