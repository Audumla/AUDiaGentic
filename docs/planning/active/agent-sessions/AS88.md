# Freeze session context on the binding and enforce it on continuation

## Description

Record what a session generation was created with, and refuse to continue it as something else.

One item, because the two halves are meaningless apart: persisting context nobody checks proves nothing, and checking context nobody persisted is impossible. They were split across two items that each named the other as a dependency.

## Steps

1. Evolve the session binding record in place — one schema version — adding composition identity to the existing protected `binding` object: `agent-definition-id`, `role-id`, `execution-profile-id`, each with its generation-or-digest, plus the effective-capability digest once the capability resolver exists. IDs and digests only. No parallel record, no alias fields.
2. Resolve and persist that context with the binding inside the same open transaction that already writes the AS29 surface. A failed persist still closes the provisional owned transport and leaves no index entry — unchanged.
3. On same-generation continuation, compare the stored snapshot against the requested one before dispatch: project, provider, model, component profile, runtime digest, execution-context fingerprint, selected surface, Agent Definition, Role, Execution Profile.
4. A mismatch is a registered error raised before prompt submission. Never silently open, replace, resume, attach or select another surface.
5. Continuation additionally requires: reusable lifecycle state, no active turn, exact generation, exact live-handle binding. Process liveness alone never authorizes continuation.
6. Records created before this item have unknown composition context. Unknown rejects exact-compatibility operations rather than defaulting to permitted.
7. Extend the forbidden-fallback list with: changed Execution Profile, changed Role, changed Agent Definition, skill-name substitution.

## Codebase Verification 2026 08 05

**Verified against the tree. One real ambiguity found in this item's own step 1 — resolve it before implementing.**

**Current `agent-execution-session.schema.json` shape:**

- Top-level properties: `binding`, `close-reason`, `closed-at`, `contract-version`, `created-at`, `error`, **`execution-profile-id`**, `idle-timeout-seconds`, `last-activity-at`, `max-lifetime-seconds`, `model-id`, `provider-id`, `provider-metadata`, `request-ids`, `session-id`, `state`, `turn-count`, `updated-at`.
- `binding` sub-properties: `binding-id`, `created-at`, `execution-context-fingerprint`, `generation`, `identity-context-fingerprint`, `ownership`, `predecessor-binding-id`, `provider-id`, `provider-ref-key`, `provider-session-ref`, `ref-namespace`, `relation`, `surface-id`, `surface-version`.

**The ambiguity:** step 1 says to add `execution-profile-id` (plus its digest) into the binding's composition block — but **`execution-profile-id` already exists at the session record's top level**. Adding a second copy inside `binding` would create two sources of truth for the same fact, which is precisely what §3's one-owner-per-durable-artifact rule forbids, and it is the kind of near-duplicate field that later diverges.

**Resolve it this way** (stated here so it is not re-litigated mid-implementation): keep the existing top-level `execution-profile-id` as the single source of that id, and add only the *digest* alongside the other composition digests in the binding. The binding's composition block then carries `agent-definition-id`, `role-id` and their digests plus an `execution-profile-digest`, and reads the profile id from the top level. If instead the whole set genuinely belongs in one block, the top-level field must be **removed** in the same change, not left in place — §4 forbids keeping both.

**Two things already exist that this item and AS89 both need:** `binding.predecessor-binding-id` and `binding.relation` are already in the schema, so the linked-generation machinery has schema support today — neither item needs to add it. `execution-context-fingerprint` and `identity-context-fingerprint` are already persisted and defaulted (`bindings.py:96-97`, `:143-144`), so the execution-context half of step 3's comparison has its inputs already.
