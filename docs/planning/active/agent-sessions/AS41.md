## Goal

Turn the read-only RPC event stream tapped by AS40 into richer AS19 evidence layered onto the session `pi-acp` already drives, without introducing a second control/lifecycle authority. State inspection, final-output retrieval, cancellation, and close continue to be served by the existing `AcpAgentSessionTransport`/`pi-acp` path; this item only widens the evidence available for that same session.

## Dependencies

AS40 complete with pinned real/synthetic tap transcripts and proven byte-transparency. AS29 `pi-community-acp` surface's evidence quality remains candidate/O0 for tap-derived kinds until the evidence matrix below passes for each platform. This item does not create or promote a `pi-rpc` surface.

## Lifecycle Mapping

Map only events proven by Pi's exact RPC transcript/source (reusing the AS27 probe evidence), potentially including message/tool/turn-level detail the ACP `sessionUpdate` vocabulary currently drops (per the gaps already catalogued in docs/reference/PROVIDER_CAPABILITY_REFERENCE/harnesses/profiles/pi-acp-status-mapping.md §4.2 -- `file-change`, `terminal-output`, `plan-update`, partial tool-call detail, compaction, retries, queue state). Pi parsing and native identifiers stay in the Pi adapter. Emit bounded neutral observations with provider-safe correlation, source sequence/order, observed time, and correlation quality, explicitly correlated to the same turn/session the ACP transport is already reporting on -- tapped evidence must never be attributed to a different session generation than the ACP stream it accompanies. The AS19 generic mapper/evidence sink and AS21 projector remain the only route to normalized lifecycle/status.

Do not assume Pi RPC permission events because Pi ACP or documentation contains them. Missing settled/terminal/correlation evidence downgrades confidence/effective capability instead of inventing completion. If the tap disconnects or errors mid-session, evidence quality degrades to what the ACP stream alone already provides -- it must never be treated as session failure.

## State Inspection

State inspection continues to be served by the existing ACP-derived path; this item only adds tap-sourced corroborating evidence (e.g. more granular in-flight tool/message detail) to the same state signal, and must not introduce a second, potentially divergent state source. Where tap evidence and ACP evidence would imply different states for the same turn, ACP evidence (the actual control-plane source) wins; tap evidence is enrichment, never override.

## Final Output Retrieval

Where the tap proves a richer or earlier-available signal for final/partial assistant text than the ACP stream alone, feed it into AS31's existing output-event/final-selector path as an additional evidence source correlated to the same turn -- not a second output channel. Cover: normal assistant text; incremental/partial text; tool-only turn; cancel before/after partial text; provider end without final text; tap disconnect mid-turn (falls back to ACP-only evidence, no data loss beyond reduced granularity); duplicate/out-of-order tap events. Raw Pi message objects, session refs, hidden reasoning, and tool payloads remain private.

## Cancellation

No new cancellation path. `CANCEL_TURN` continues to route exclusively through `AcpAgentSessionTransport.control()` (already ACCEPTED per pi-acp-status-mapping.md §2.4) -- the tap is read-only and must never issue commands. This item may use tap evidence to corroborate that an accepted cancellation actually reached the underlying Pi process (i.e. observe the abort take effect in the RPC stream), improving confidence without adding a control path.

## Close

No new close path. Session close continues through the existing ACP transport's `CLOSE_SESSION` handling; this item ensures the tap and its socket/shim are torn down as part of that same close (per AS40's cleanup requirements), not as an independent lifecycle.

## Capability Maturity

Update the AS29 `pi-community-acp` surface snapshot to reflect improved evidence quality/coverage only to the proven level. There is no separate Pi RPC surface or support matrix to maintain -- tap-derived evidence strictly augments the existing surface's declared capability.

## Acceptance Criteria

- Tapped RPC evidence enriches the existing pi-acp-driven session's AS19 evidence; it never establishes a second lifecycle authority.
- Pi events enter lifecycle only through AS19, correlated to the same session/turn the ACP stream reports.
- Generic clients need no Pi-specific vocabulary.
- Control (prompt/cancel/close) remains exclusively owned by the existing ACP transport; the tap never issues commands.
- Tap disconnect/failure degrades evidence richness only, never session outcome.
