## Goal

Turn the read-only RPC event stream tapped by AS40 into richer AS19 evidence layered onto the session `pi-acp` already drives, without introducing a second control/lifecycle authority. State inspection, final-output retrieval, cancellation, and close continue to be served by the existing `AcpAgentSessionTransport`/`pi-acp` path; this item only widens the evidence available for that same session.

## Dependencies

AS40 complete with pinned real/synthetic tap transcripts and proven byte-transparency. AS29 `pi-community-acp` surface's evidence quality remains candidate/O0 for tap-derived kinds until the evidence matrix below passes for each platform. This item does not create or promote a `pi-rpc` surface.

## Lifecycle Mapping

Map only events proven by Pi's exact RPC transcript/source (reusing the AS27 probe evidence), potentially including message/tool/turn-level detail the ACP `sessionUpdate` vocabulary currently drops (per the gaps already catalogued in docs/reference/PROVIDER_CAPABILITY_REFERENCE/harnesses/profiles/pi-acp-status-mapping.md §4.2 -- `file-change`, `terminal-output`, `plan-update`, partial tool-call detail, compaction, retries, queue state). Pi parsing and native identifiers stay in the Pi adapter. Emit bounded neutral observations with provider-safe correlation, source sequence/order, observed time, and correlation quality, explicitly correlated to the same turn/session the ACP transport is already reporting on -- tapped evidence must never be attributed to a different session generation than the ACP stream it accompanies. The AS19 generic mapper/evidence sink and AS21 projector remain the only route to normalized lifecycle/status.

Do not assume Pi RPC permission events because Pi ACP or documentation contains them. Missing settled/terminal/correlation evidence downgrades confidence/effective capability instead of inventing completion. If the tap disconnects or errors mid-session, evidence quality degrades to what the ACP stream alone already provides -- it must never be treated as session failure.

## State Inspection

State inspection continues to be served by the existing ACP-derived path; this item only adds tap-sourced corroborating evidence (e.g. more granular in-flight tool/message detail) to the same state signal, and must not introduce a second, potentially divergent state source. Where tap evidence and ACP evidence would imply different states for the same turn, ACP evidence (the actual control-plane source) wins; tap evidence is enrichment, never override.

## Final Output Retrieval

Where the tap proves a richer or earlier-available signal for final/partial assistant text than the ACP stream alone, feed it into AS31's existing output-event/final-selector path as an additional evidence source correlated to the same turn -- not a second output channel. Cover: normal assistant text; incremental/partial text; tool-only turn; cancel before/after partial text; provider end without final text; tap disconnect mid-turn (falls back to ACP-only evidence, no data loss beyond reduced granularity); duplicate/out-of-order tap events. Raw Pi message objects, session refs, hidden reasoning, and tool payloads remain private.

## Cancellation

No new cancellation path. `CANCEL_TURN` continues to route exclusively through `AcpAgentSessionTransport.control()` (already ACCEPTED per pi-acp-status-mapping.md §2.4) -- the tap is read-only and must never issue commands. This item may use tap evidence to corroborate that an accepted cancellation actually reached the underlying Pi process (i.e. observe the abort take effect in the RPC stream), improving confidence without adding a control path.

## Close

No new close path. Session close continues through the existing ACP transport's `CLOSE_SESSION` handling; this item ensures the tap and its socket/shim are torn down as part of that same close (per AS40's cleanup requirements), not as an independent lifecycle.

## Capability Maturity

Update the AS29 `pi-community-acp` surface snapshot to reflect improved evidence quality/coverage only to the proven level. There is no separate Pi RPC surface or support matrix to maintain -- tap-derived evidence strictly augments the existing surface's declared capability.

## Acceptance Criteria

- Tapped RPC evidence enriches the existing pi-acp-driven session's AS19 evidence; it never establishes a second lifecycle authority.
- Pi events enter lifecycle only through AS19, correlated to the same session/turn the ACP stream reports.
- Generic clients need no Pi-specific vocabulary.
- Control (prompt/cancel/close) remains exclusively owned by the existing ACP transport; the tap never issues commands.
- Tap disconnect/failure degrades evidence richness only, never session outcome.

### Tap-wiring architecture decision — resolved with the user (2026-07-29)

Discussed the AS28-vs-AS41 conflict above directly. Landed on inversion of control, not either of the two options first proposed: the transport (`AcpSessionTransport`/`AcpAgentSessionTransport`) accepts an optional `PreSpawnHook` (`foundation/transports/acp.py`) — `on_environment_ready(environment) -> hook_state` called once the launch environment is finalized, right before the child spawns; `on_close(hook_state)` called symmetrically on transport close. The transport never learns "tap" exists, never exposes `AcpLaunch`/environment upward, and never owns tap-specific logic — it just calls an interface someone else implements. **Built and tested this session**: the hook mechanism itself (threaded through both transport classes, best-effort — a broken hook never blocks open or breaks close), 9 new unit tests (`test_acp_session.py` — call-with-environment, symmetric close, hook-failure-does-not-block-open, on_close-failure-does-not-raise, no-hook-is-a-no-op; `test_acp_agent_session_transport.py` — forwarding through the wrapper unchanged). All existing + new ACP transport tests pass (67/67, 21/21).

This is now recorded as a standing architectural direction for this codebase generally, not just this one case — see memory `project_inversion_of_control_direction`.

**Second design correction, found by direct verification (2026-07-29, later same session)**: checked whether `agents_gateway_sessions.py` has any explicit ACP knowledge at all — it doesn't (grepped; only comments enforcing the negative, "no AcpLaunch/AcpSessionTransport construction here"). That makes the `_TapPreSpawnHook`-in-the-gateway framing above wrong too: naming anything "tap" or Pi-specific in the gateway file, or adding a Pi-specific `_SessionHandle` field, would itself be the exact kind of leak AS28 exists to prevent. The hook must be *constructed* where ACP is already a known concept (`public_execution.py`/`adapters/pi/acp.py`), never in the gateway. That surfaced a real gap in `PreSpawnHook` itself: it's one-directional (setup/teardown only) — nothing let a tap consumer actually *deliver* observations back afterward, and the gateway's only observation channel is the per-turn `sink` callback `AcpAgentSessionTransport` already owns.

**Resolved and built**: a second, equally generic, equally provider-blind interface, `AuxiliaryObservationSource` (`foundation/transports/acp.py`, right beside `PreSpawnHook`) — `async def poll(self, ag_session_id, turn_id) -> TransportObservation | None` (correlation ids passed in by the caller, since the source is set up once at spawn, before any turn/turn_id exists) plus `close()`. `PreSpawnHook.on_environment_ready`'s return value may optionally implement this. `AcpSessionTransport` exposes it via a new `hook_state` property; `AcpAgentSessionTransport.prompt()` duck-checks for `hasattr(aux_source, "poll")` and, if present, runs a drain loop concurrently with the real ACP turn, feeding whatever it polls through the *exact same* `sink` callback ACP's own `_wrapped_sink` already uses — cancelled (with a bounded await) in the turn's `finally` block alongside the existing cancel-signal teardown. The caller (gateway) sees one observation stream; it never learns a second source exists. Built and tested: 1 new end-to-end test proving a fake aux source's observation arrives through the same sink, correctly turn-correlated, alongside ACP's own native events for that turn (`test_auxiliary_observation_source_drained_through_same_sink`). Full transport suite still green (68/68).

### Real cause of the tool-call proof-gathering stall found, and it's bigger than this item (2026-07-30)

The `test_real_pi_rpc_transcript_captures_tool_call_frame_types` EOF (reported as unresolved above) is not a model-reliability or budget issue. Added stderr capture + a stderr-dump-on-crash env var to the shim so the failure would carry the real crash reason, then investigated why a tool-invoking prompt strands at all — root cause found by reading the transport, not by more Docker runs.

`AcpAgentSessionTransport`'s ACP `Client` implementation (`foundation/transports/acp.py`) has `request_permission` built correctly — real forwarding via `turn.emit(...)`, real decision via an injectable `policy_fn` — but `write_text_file`/`read_text_file`/`create_terminal`/`terminal_output`/`release_terminal`/`wait_for_terminal_exit`/`kill_terminal` are hard `NotImplementedError` stubs, written under the belief that AS28's scope was "control/observation only." That belief is wrong: in ACP the client is the execution backend for fs/terminal, so refusing those calls doesn't narrow scope to "observation," it makes any tool-using turn strand — the agent asks the client to act, gets no answer, and eventually gives up (a real child-process EOF, matching exactly what the proof-gathering test observed). Filed as **AS68** (new item, not this item's scope — this is a core AS28-era gap, not a tap-evidence-enrichment gap) with the concrete fix (implement the seven stubs for real, following `request_permission`'s own pattern).

Consequence for AS41 specifically: even after AS68 lands, the raw one-directional JSON-RPC harness this session's tool-call proof-gathering test uses still can't answer agent-initiated fs/terminal requests (it only reads for a response matching a specific outgoing request id). Real tool-call tap-frame proof needs that test rewritten to drive the real `AcpAgentSessionTransport` (which will handle the round-trip correctly once AS68 lands), not raw JSON-RPC — tracked in AS68's Files/Dependencies, not duplicated here.
