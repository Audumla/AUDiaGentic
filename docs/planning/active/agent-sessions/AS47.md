# Bind shared live sessions to immutable execution context

## Description

Complete only the agents-owned session integration that remains after SH04 moved GatewayApplication and SessionRuntime into the standalone shared service. Bind every live/durable session generation to its immutable SH02 execution context so a second authorized client can continue it without silently changing provider, model, component profile, runtime digest, or project. Shared-gateway/foundation retain service, lease, discovery, request, worker, and lifecycle ownership.

## Steps

1. Reuse the existing SH02 `ExecutionManifest` and context fingerprint as the immutable execution-context identity. Do not introduce another context or identity record.
2. On session creation, persist the project identity and the exact manifest/fingerprint linkage through the AS30 binding/session record.
3. On every same-generation continuation, compare the stored snapshot with the requested provider, model, component profile, runtime digest, project, provider identity context, and execution context before dispatch.
4. Reject any mismatch through one registered stable error before prompt submission; do not silently open, replace, resume, or select another surface.
5. Preserve the existing per-session FIFO, request ownership, owned/external cleanup, and live-handle lifetime rules.
6. Consume SH06 worker isolation, SH07 durable request recovery, and SH10 drain/lease behavior through their public seams; do not duplicate them in agents.
7. Route provider launch and continuation operations only through `providers_api` and the frozen AS29 surface snapshot.
8. Add standalone two-client, changed-context, project-isolation, concurrent FIFO, service-failure, and no-orphan tests.

## Existing Baseline And Implementation Rule

SH04/shared-gateway owns service, leases, discovery, workers, drain, and generic lifecycle. AS30 owns the binding schema/index and identity fingerprints. AS47 adds no second session/context record. It passes the resolved SH02 execution manifest/fingerprint and project identity into AS30 open/continuation checks and proves two-client continuation through the existing standalone service.

## Acceptance Criteria

- Client B can continue Client A's still-valid generation only with exact project, provider, model, component profile, runtime digest, identity context, and execution-context match.
- Mismatch fails with a stable registered error before prompt dispatch.
- Continuation uses the same AS30 binding/live handle and preserves FIFO.
- Polling/status reads do not create runtimes or take the turn lock.
- Service/worker failure follows existing SH recovery and leaves no owned child orphan.
