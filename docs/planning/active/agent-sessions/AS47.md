# Bind shared live sessions to immutable execution and agent-composition context

## Description

Complete only the agents-owned Interaction Session integration that remains after SH04 moved GatewayApplication and SessionRuntime into the standalone shared service. Bind every live/durable session generation to its immutable SH02 execution context and AS60-AS64 composition context so a second authorized client can continue it without silently changing provider, model, component profile, runtime digest, project, Execution Profile, Role, Agent Definition, Session Surface or effective capabilities. Shared-gateway/foundation retain service, lease, discovery, request, worker and lifecycle ownership.

## AS59 alignment and precedence

Disposition: keep/amend  
Authority: AS59

- AS47 remains the sole same-generation continuation compatibility item.
- Same-generation continuation means reusing the existing AS30 Interaction Session binding and live handle; it is not resume, replacement, attach-by-provider-ref or new task orchestration.
- Preserve SH02 `ExecutionManifest` and fingerprint as execution-context authority. Add immutable public IDs/generations/digests from AS60 Execution Profile, AS61 Role, AS62 Agent Definition and AS64 effective capabilities through the AS30 record; do not add another context store.
- AS47 does not resolve mutable current definitions during continuation. It compares the requested resolved snapshots with the frozen session-generation context.
- A changed Agent Definition, Role, Execution Profile, selected AS29 surface, model, provider, project or incompatible effective-capability digest is rejected before prompt submission.
- AS21 alone decides reusable/active/terminal state. Process liveness or possession of a session ID cannot authorize continuation.
- AS63 AgentTask may submit a new turn into the continued session, but AS47 does not create a second task/session coordinator.
- AS65 external ACP and AS66 A2A clients use this same continuation service and receive AUDiaGentic IDs; no protocol adapter may bypass compatibility checks.
- No implementation under AS47 proceeds before AS59 Gate 0 confirms all continuation/resume/attach plans have distinct ownership.

## Steps

1. Reuse the existing SH02 `ExecutionManifest` and context fingerprint as the immutable execution-context identity. Do not introduce another execution context or identity record.
2. On session creation, persist project identity and exact manifest/fingerprint linkage through AS30, together with immutable Agent Definition, Role, Execution Profile and effective-capability IDs/generations/digests once AS60-AS64 land.
3. On every same-generation continuation, compare the stored snapshot with the requested provider, model, component profile, runtime digest, project, provider identity context, execution context, selected Session Surface, Agent Definition, Role, Execution Profile and effective capabilities before dispatch.
4. Reject any mismatch through one registered stable error before prompt submission; do not silently open, replace, resume, attach or select another surface.
5. Preserve the existing per-session FIFO, request ownership, owned/external cleanup and live-handle lifetime rules.
6. Consume SH06 worker isolation, SH07 durable request recovery and SH10 drain/lease behavior through public seams; do not duplicate them in agents.
7. Route provider launch and continuation only through `providers_api`, the frozen AS29 surface snapshot and the existing live AS30-bound transport.
8. Require AS21 reusable state, no active turn, exact generation and exact live-handle binding before accepting continuation.
9. During the AS63 compatibility window, one new AgentTask maps to the existing request/turn path. Task identity does not alter session compatibility.
10. Add standalone two-client, changed-context, changed-composition, project-isolation, concurrent FIFO, service-failure, external ACP client, A2A caller and no-orphan tests using the same continuation seam.

## Detailed Solution & Technical Design

Continuation input should carry or resolve immutable snapshot references before entering the session lock:

```text
interaction-session-id
session-generation
project identity
execution-context fingerprint
agent-definition id/generation/digest
role id/generation/digest
execution-profile id/generation/digest
resolved-surface identity/version/platform
effective-capability digest
```

Validation order:

1. authenticate/authorize caller and canonical project;
2. load AS30 session generation/binding;
3. compare immutable execution and composition context;
4. verify live handle belongs to the binding/generation;
5. query AS21 reusable state and active-turn status;
6. acquire existing FIFO/turn path;
7. dispatch one turn through AS19 transport.

No current profile/role/agent definition may be re-resolved after step 2 to “upgrade” an existing session. A compatible alias or public Agent ID is insufficient without matching frozen digests.

## Files

Agents session store/runtime/dispatch and SH04 public application/client seams only; existing SH02 execution-context contracts; AS30 record/binding fields; AS60-AS64 immutable snapshot contracts consumed by reference; targeted unit/integration/Docker tests. No new daemon, discovery, PID journal, startup lock, generic service store, worker framework, session store, task store or protocol-specific continuation store.

## Validation

Client A opens a keep-alive fake-ACP session through the standalone service and exits; Client B continues the same generation with exact context and FIFO semantics. Changed Execution Profile, Role, Agent Definition, effective capabilities, selected surface, provider/model/component profile/runtime digest or Project B are rejected. Service/worker failure resolves deterministically through SH owners and leaves no owned child orphaned.

Additional protocol-neutral proof:

- an external ACP façade client and an A2A-originated task receive identical compatibility decisions;
- neither protocol can continue by presenting only its own context/session/task ID;
- status/output polling creates no runtime and does not renew execution lifetime;
- no provider-native resume or “latest” operation is invoked on continuation failure.

It passes resolved SH02 and AS60-AS64 immutable context into AS30 continuation checks and proves multi-client continuation through the existing standalone service.

## Acceptance Criteria

- Client B can continue Client A's still-valid generation only with exact project, provider, model, component profile, runtime digest, identity context, execution context, Session Surface, Agent Definition, Role, Execution Profile and effective-capability compatibility.
- Mismatch fails with a stable registered error before prompt dispatch.
- Continuation uses the same AS30 binding/live handle and preserves FIFO.
- AS21 reusable state is mandatory; process liveness alone is insufficient.
- Polling/status/output reads do not create runtimes, take the turn lock or renew lifetime.
- ACP/A2A adapters consume this service and cannot bypass it.
- Service/worker failure follows existing SH recovery and leaves no owned child orphan.
