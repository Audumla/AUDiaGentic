# Generic session and turn controls

## Description

Expose the validated generic session controls through one protocol-neutral application surface, so a caller can cancel, interrupt or close a live turn without reaching into a provider transport.

A control result is an acknowledgement only. It never terminalizes a task, marks a session reusable, releases a queue slot or fabricates output — subsequent lifecycle evidence decides what actually happened.

## Steps

1. Define typed requests for the actions already proven per surface: cancel turn, interrupt turn, close/detach session, and respond-to-permission where the surface supports it. Closed payloads only — no provider-native command escape hatch.
2. Expose a per-session capability view derived from the frozen surface snapshot, so a caller can see which actions this session actually supports before invoking one. A stale client view cannot force an unsupported action — dispatch revalidates against the binding's frozen snapshot.
3. Dispatch through the authoritative live transport via `providers_api`. One application service owns dispatch; adapters translate into this closed contract and never call an underlying protocol method directly.
4. Return canonical dispositions: accepted, unsupported, already-terminal, rejected, uncertain. Repeated requests with the same client control id return the original result. Never auto-retry an uncertain provider submission.
5. Keep acknowledgement separate from lifecycle: the response says the control was accepted, not that its effect occurred.
6. Add the matching closed operations to application, service, client and MCP so all four return the same canonical result.

## Validation

- An accepted action dispatches through the authoritative transport and returns an acknowledgement.
- Unsupported, already-terminal, rejected and uncertain each return their distinct canonical disposition.
- A stale capability view cannot invoke an action the frozen snapshot does not support.
- A duplicate control id returns the original result and does not dispatch twice.
- An acknowledgement changes no lifecycle state and releases no queue slot — asserted directly.
- All four surfaces (application/service/client/MCP) return the same result for the same request.
- Owned, adopted and external ownership modes get correct close/detach behaviour.

## Codebase Verification 2026 08 05

**Verified against the tree. The control vocabulary already exists — this item wires it up, it does not define it.**

`SessionControlAction` already declares `CANCEL_TURN`, `INTERRUPT_TURN`, `STEER_TURN`, `RESPOND_PERMISSION` and `CLOSE_SESSION`, and `foundation/transports/acp.py` (from line 1658) already implements the dispositions for the ACP transport:

- `CANCEL_TURN` -> ACCEPTED when the transport is alive, UNSUPPORTED otherwise (per-turn cancel signal at line 1484).
- `INTERRUPT_TURN` / `STEER_TURN` -> UNSUPPORTED (no ACP protocol support).
- `RESPOND_PERMISSION` -> default-deny, delegated to the session transport.
- `CLOSE_SESSION` -> idempotent delegation to the underlying close.

So step 1's typed requests map onto an existing closed enum, and the accepted/unsupported disposition split this item requires is already the transport's behaviour. The missing layer is the application service and the four parity surfaces, exactly as scoped.

**Clarification on this item's steering exclusion:** `STEER_TURN` exists in the enum and must **stay** — removing it would be a contract change for no benefit. "Steering is excluded" means this item adds no steering *capability* and exposes no steering request; the enum value continues to resolve UNSUPPORTED, which is the correct honest answer and already tested. Do not read the exclusion as an instruction to delete the enum member.

**`RESPOND_PERMISSION` defaults to deny today.** Step 1 lists it as in-scope "where the surface supports it" — note that surfacing it means changing a default-deny into a caller-supplied decision, which is a security-relevant behaviour change and belongs behind AS101's authorization model. Sequence it accordingly, or leave permission response out of this item's first cut.

## Threat Model Correction 2026 08 05

**This item previously deferred an authorization and topology-validation model to AS101. That model is gone — read this before implementing.**

The deployment is local, internal, non-hostile, not externally facing, with one shared gateway across multiple projects. AS101 is now project isolation, not caller authorization. Dropped: lease validation, cross-caller rejection, the protocol-id-cannot-authorize rule.

**What this item consumes instead:** a control must target a session in the requesting project. Within a project, a harness may cancel or close another harness's session — they are peers, and the shared gateway exists to make that possible.

**What does not change, and is the substance of this item:**

- Ownership-mode legality (owned / adopted / external) stays. Refusing to signal an external process is a correctness rule about not killing something we do not own — nothing to do with hostile callers.
- Acknowledgement-is-not-lifecycle stays, and remains this item's most important assertion.
- Dispatch through the authoritative transport only, with no provider-native escape hatch, stays as a §6 boundary rule.
- Idempotency by client control id stays — it prevents accidental double-dispatch on a cooperative retry, which is a real failure mode.

**Reconsider `RESPOND_PERMISSION` in light of this.** My earlier note said to sequence it behind the authorization model. With that model gone, the question is simpler: a permission response is a normal in-project operation, and the current default-deny can become caller-supplied without a new security layer. It can stay in this item's first cut.
