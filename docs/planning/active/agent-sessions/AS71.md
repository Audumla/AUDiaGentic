## Remaining failures — this item's scope

### 1. Order-dependent: `test_as41_observability_tap_threading.py` (3 tests)

```text
tests/unit/providers/test_as41_observability_tap_threading.py::TestObservabilityTapThreading
  test_pi_gets_hook_when_tap_requested_on_a_platform_with_evidence
  test_pi_no_hook_when_tap_not_requested
  test_pi_no_hook_without_request_runtime_root
```

Symptom: `assert prepared.transport is not None` fails with
`PreparedSessionTransport(transport=None)`.

Confirmed behaviour:

- pass when run alone;
- pass with the whole `tests/unit/providers` directory;
- pass after `tests/unit/agents` and after `tests/unit/memory`;
- fail only in the full `tests/unit` run.

So an earlier module leaves process-global state that makes
`prepare_provider_session_transport(..., "pi", SurfaceHint("pi-community-acp",
platform_hint="linux-amd64"))` stop resolving.

Prime suspect, not yet proven: provider enablement routes through
process-global component-implementation registration —
`services/config/provider_config.py:105-113` explicitly "falls back to a direct
state write **if the implementation descriptor is not registered in this
process**", and this repo has a documented one-component-profile-per-process
constraint (`VAL-COMP-010`). A test that registers components, or registers them
under a profile, changes the branch later tests take.

Do not "fix" this by reordering tests or adding a sleep. Find the leaked global,
and give it an explicit reset fixture owned by whoever owns that global.

### 2. `test_hindsight_provision.py::test_reconcile_populates_pi_host_block`

Fails in isolation too — a genuine capability-declaration gap, not pollution.

`reconcile_hindsight(root, ["pi"])` returns
`state: FAILED, action_needed: "provider MCP config does not support remote
entries"`, raised at
`services/capabilities/managed_mcp_family.py:70-78` (`CON-PMCP-001`), because
`pi.yaml`'s `mcp:` block declares no `capabilities: [remote]` — and no provider
descriptor in the tree declares it.

The nuance that makes this a **decision, not a typo**: pi's declared
`format: mcp-json` reader/writer *does* implement remote entries
(`foundation/mcp/json_format.py:62-65, 84-87` handle `type: http` / `url`). So
the machinery can write a remote entry; what is unproven is whether **pi itself
consumes** one.

`BLOCKING decision` — resolve before implementing:

- **(a)** Probe real pi with a remote MCP entry. If it honours it, declare
  `capabilities: [remote]` on `pi.yaml`'s mcp mechanism and cite the probe.
  This is the evidence-led path and matches AS29's "unknown means unsupported".
- **(b)** If pi does not honour remote entries, the Hindsight recipe is wrong to
  request one for pi, and the fix belongs to the memory/Hindsight plan, not here.

Do not flip the capability flag without the probe. A capability declaration is a
factual claim under `arch-standards` §3.
