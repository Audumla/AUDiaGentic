# Persist durable provider-session bindings and capability-gated mappings

## Description

Make the Interaction Session generation ↔ provider-session/thread relationship a first-class durable binding governed by the AS29 resolved Session Surface.

Agents owns the protected binding record and durable binding index. Providers own construction/validation of opaque provider refs and execution of capability-gated surface operations. AS30 must not redefine AS19 transport/control contracts, AS52/existing foundation process ownership, AS21 lifecycle projection, AS31 content, AS60 Execution Profiles, AS61 Roles, AS62 Agent Definitions, AS63 Agent Tasks, or provider configuration.

The gateway may always persist an opaque ref returned by a validated open operation. It may attach, resume, discover, share, or replace only when the exact resolved provider/harness surface explicitly declares and validates that operation for the same identity, project, and immutable execution/composition context.

## AS59 alignment and precedence

Disposition: keep/amend  
Authority: AS59

- AS30 remains the sole durable Interaction Session generation to provider-session binding/index authority.
- Rename conceptual `AG session` references to `Interaction Session` where this does not change wire/schema compatibility. Existing external field names may migrate only through explicit schema versions.
- AS30 must persist or bind immutable composition identity supplied by AS60-AS64: Agent Definition ID/generation/digest, Role ID/generation/digest, Execution Profile ID/generation/digest, and effective-capability digest.
- These composition fields are authorization/compatibility evidence only. AS30 does not load, resolve, merge, or mutate Agent Definitions, Roles, Execution Profiles or capability sources.
- Existing SH02 execution-context fingerprint remains authoritative for workspace/provider/model/component/runtime context. Composition digests supplement it; they do not create a competing execution-context record.
- Same-generation continuation uses AS47 and requires exact binding, execution context, composition context and AS21 reusable state.
- Resume remains AS49 explicit new-generation `RESUMED_FROM`; replacement remains explicit and cannot be disguised as resume.
- A2A task IDs, external ACP session IDs and harness delegation IDs are mappings above AS30. They cannot replace the AUDiaGentic Interaction Session ID or provider binding ID.
- AS65 external ACP and AS66 A2A may authorize through AS30 public application seams but may never read or expose raw provider refs.
- Do not create a Runtime Instance store or separate runtime binding here. Current live materialization remains one-to-one with the Interaction Session generation unless an AS59 reassessment proves otherwise.
- No implementation under AS30 proceeds before AS59 Gate 0 confirms schema/store ownership and all competing session persistence plans are amended or blocked.

5. Evolve the existing session schema in place. Replace any legacy top-level `provider-session-ref` with one required protected `binding` object. In the next schema version after AS60-AS64 are available, include or reference immutable composition context:

Use the repository's actual naming convention and correct the illustrative typo above during implementation; do not ship duplicate alias fields. Store public IDs/digests only, never raw Role instructions, tools, model secrets, provider credentials or Agent Card content.

6. Define `provider-ref-key` as `SHA-256(provider id + surface id + surface ref namespace + AS29 identity-context fingerprint + exact opaque provider session ref)`. Store exact `surface-version` for compatibility evidence, but do not include executable version in the stable key unless the surface explicitly declares a version-specific ref namespace. Resume/attach compatibility is decided by resolved surface capability plus compatibility predicate.

7. Add bounded read migration beside existing session-store schema validation. Legacy records migrate conservatively and gain no attach, resume, discovery, sharing or replacement entitlement. Records created before AS60-AS64 may have unknown composition context; unknown context must reject continuation/resume/attach where exact compatibility is required unless an explicit one-time migration can derive the immutable values without re-resolving changed configuration.

8. Keep `agents_gateway_session_bindings.py` as the sole owner of `create_open_binding`, `attach_binding`, `resume_binding`, `replace_binding`, binding retirement, and index rebuild. Use the existing project-local binding index; do not add an agent/task/runtime index for the same provider ref.

9. Protect every binding-index read-modify-write with the existing cross-process lock and atomic-write helpers. On unreadable index, rebuild only from validated Interaction Session records under the project lock; never discover provider sessions during recovery.

10. Enforce ownership and attachment rules. A provider-ref key may have at most one active owned binding. Additional non-owning attachments are allowed only when the exact surface validates `attach_existing` and `concurrent_attachments`. Collision checks must re-read protected records and compare provider, surface, identity context, composition context and exact opaque ref.

11. Add provider contract/API support only for surface operations, not AUDiaGentic binding mutation. Providers may open, attach, resume, or replace at the resolved surface and return or validate opaque refs. AS30 mutates AUDiaGentic records and indexes. `providers_api` refuses operations whose AS29 capability is missing or unvalidated.

12. Forbid all fallback behavior: no alternate surface, alternate account, alternate project, display name, most-recent session, CLI continue/latest, interactive picker, transcript matching, UI scraping, endpoint-family inference, changed Execution Profile, changed Role, changed Agent Definition, or skill-name substitution.

13. Refactor SessionRuntime open transaction: resolve exact AS60/AS62 composition snapshot and AS29 surface → create `SessionBindingIntent(OPENED)` → provider opens transport/session → provider returns opaque ref → persist protected record including immutable composition context → atomically update binding index → expose live handle. If persistence fails, legally close the owned transport, remove provisional index state, record cleanup failure if needed, and never expose an unbound usable handle.

14. Refactor AS47 same-generation continuation. Reuse the current generation only when the binding matches exactly, identity/project/execution/composition contexts are compatible, the live handle still belongs to that binding, and AS21 says no turn is active and the session is reusable. A stored ref, session ID, Agent ID or A2A context ID alone is insufficient.

15. Refactor AS49 resume. Resume never mutates a terminal source record back to active; it creates a new Interaction Session ID/generation, records `RESUMED_FROM`, links `predecessor-binding-id`, calls provider resume only when `resume_by_ref` is validated, preserves source terminality, and requires explicit compatible composition policy. If exact resume is unsupported or the requested Agent/Role/Execution Profile changed incompatibly, require explicit replacement or new-session creation.

16. Refactor external/live attach. Attach requires `attach_existing`, explicit `external` or `adopted` ownership, exact opaque ref, compatible identity/project/execution/composition context, safe observability state, and `concurrent_attachments` when another binding exists. External ACP clients attach to AUDiaGentic Interaction Sessions, not directly to provider ACP sessions.

17. Keep replacement explicit. `REPLACED` means AUDiaGentic deliberately opened a different provider session because the old binding could not legally or safely continue. It creates a new binding, links predecessor, leaves source terminal, and must not be reported as successful resume. Changing Execution Profile, Role or Agent Definition normally requires explicit replacement/new session unless a documented compatibility predicate proves semantic identity.

18. Emit redacted binding lifecycle facts containing binding ID, relation, generation, ownership, provider, surface, surface version, ref-key prefix, predecessor binding ID, composition digest prefixes and outcome. Never emit raw provider ref, raw identity context, Role instructions, tool policy, opaque-ref-derived paths, attach secrets, cloud conversation tokens or raw Agent Card data.

19. Add generic tests for legacy migration, current schema validation, open persistence rollback, protected ref redaction, exact identity/project/execution/composition matching, denied unadvertised operations, duplicate owner race across processes, allowed owner-plus-attachment, denied unsupported concurrency, resume source terminality, replacement-is-not-resume, index corruption/rebuild, stable ref key across compatible upgrades, changed Role/Profile/Agent rejection, external/adopted/owned close behavior, no latest/name/UI/transcript fallback, and continuation denied while active but allowed when observable reusable.

20. Add a probe checklist per harness surface as evidence: open returns a stable machine ref, exact resume resumes expected history, invalid resume does not open unrelated sessions, attach joins the same live session, non-owned close detaches, discovery returns exact refs in scope, concurrency allows only valid observer/interactive behavior, and observability distinguishes process-live from turn-complete. Missing or failed probes keep the operation disabled.

21. Platform acceptance: run direct Windows and Linux jobs for migration, duplicate-ref race, owner-plus-attachment race, stale lock, index rebuild, owned/external close, compatible upgrade identity stability, composition-context separation and identity-context separation. Run Linux Docker crash/race tests for record/index atomicity and no provider-session discovery during recovery.

## Validation

AS30 is complete when:

1. current session records contain one explicit protected binding.
2. Raw provider refs never appear in events, paths, filenames, metrics or ordinary diagnostics.
3. Surface operations are denied unless AS29 resolves validated support for that exact provider/surface/identity/project/context.
4. Unknown capability defaults to unsupported.
5. Open-only surfaces cannot attach, resume, discover, share or replace.
6. Exact resume creates a new linked generation and preserves source terminality.
7. Same-generation continuation and attach consume AS21 state; process liveness alone never authorizes reuse.
8. Concurrent clients cannot create duplicate owned bindings.
9. External/adopted close detaches or follows transferred authority instead of blindly terminating.
10. Provider-ref identity is scoped by AS29 identity context and ref namespace.
11. Compatible harness upgrades do not accidentally create duplicate binding identity.
12. Recovery rebuilds state only from protected AUDiaGentic records and never discovers external provider sessions.
13. No harness capability is inherited without exact probe evidence.
14. Every post-AS64 persistent generation freezes composition identity/digests.
15. Changed incompatible Agent Definition, Role, Execution Profile or effective capability cannot silently continue or resume a generation.
16. External ACP/A2A IDs remain mappings above the binding and expose no provider ref.

## Effort & Risk

This is a complex AS slice because it combines schema migration, durable indexing, capability enforcement, composition compatibility and cross-process races.

Primary risks:

- treating a stored opaque ref as permission to resume or attach;
- mixing provider-owned surface operations with AUDiaGentic binding mutation;
- confusing process liveness with session reusability;
- allowing changed role/profile/agent composition to reuse incompatible history;
- leaking protected refs or composition details;
- creating parallel stores for tasks, protocols or runtime instances;
- treating editor threads, terminal sessions, ACP sessions, A2A tasks and underlying harness sessions as one identity.

## Standards

- Durable records use existing schema validation and atomic-write helpers.
- Cross-process coordination uses the existing locking primitive.
- Opaque provider refs are protected data.
- All operation support is evidence-backed and versioned through AS29 resolved surfaces.
- Unknown capabilities default to unsupported.
- Runtime code consumes normalized capabilities and does not branch on harness names.
- Session workflow state remains in the existing TransitionEngine.
- AS30 owns binding/index state; providers own opaque-ref construction/validation and surface operation execution.
- AS60-AS64 own composition definitions/resolution; AS30 persists immutable references/digests only.

## Existing baseline to preserve

Characterize existing protected bindings, migration, hashed provider-ref keys, duplicate-owner rejection, terminal index retirement, redacted public projections, cross-process locking and conservative provider contracts before editing. Extend them rather than adding a second store/index.

## Remaining completion focus

- close any open-path rollback ghost;
- hold the binding-index lock across validated scan/build/write;
- refuse attach/resume/discovery while required identity, execution or composition fingerprints are unknown;
- require stable opaque machine refs for persistent bindings;
- integrate exact AS29 surface snapshots and AS60-AS64 immutable composition snapshots;
- complete race/crash/platform proofs;
- keep provider operations separate from AUDiaGentic binding/index mutation.

## Acceptance criteria

- One protected AS30 binding/index implementation owns all durable AUDiaGentic-to-provider identity.
- Persistently bound sessions always have a stable opaque machine ref; transient unbound sessions cannot continue, attach, resume, discover or replace.
- Exact surface, identity, project, execution-context and composition-context gates precede every mapping operation.
- Open failure rolls back the record/index and legally closes the provisional owned transport.
- Resume creates a linked generation, attach respects ownership/concurrency, and replacement is never reported as resume.
- Raw provider refs never appear in public records, logs, events, metrics, paths or filenames.
- Multi-process race/crash and index-rebuild tests pass on required platforms.
