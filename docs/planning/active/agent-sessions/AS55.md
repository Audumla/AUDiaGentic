# Implement the OpenCode ACP session-surface vertical slice

## Description

Deliver the first version-pinned OpenCode ACP implementation through the canonical AS19, AS21, AS29, AS30, and AS31 boundaries. OpenCode ACP is one explicit surface. It does not fall back to OpenCode CLI/server/plugin routes, and it does not inherit identity or resume behavior from them.

This plan proves transport, identity, lifecycle observation, cancellation, close, binding, and cleanup. User assistant content remains disabled until the AS31 content-specific probe proves a safe channel.

## Steps

1. Characterize the current OpenCode provider descriptor, `providers/adapters/opencode/acp.py`, shared ACP parser/transport, process supervision, and tests. Reuse existing launch and bounded callback behavior; do not create another subprocess launcher or JSON-RPC parser.
2. Pin the exact OpenCode executable/package version independently for each supported platform. A mismatched/unprobed version resolves the surface as unsupported and performs no hook/plugin/config write.
3. Add or consolidate a provider-private `session_control.py` composition adapter. Its transport factory:
   - invokes only the existing provider-local ACP launch builder;
   - wraps the shared ACP transport in the AS19 `AgentSessionTransport` contract;
   - maps raw ACP frames privately to bounded neutral `TransportObservation` values;
   - exposes typed controls only when the exact probe proves them;
   - accepts no raw callback or provider-native type from agents.
4. Register one AS29 `opencode-acp` surface declaration. Before probe completion it remains a candidate with `validation_state: probe-required`, effective lifecycle `O0`, no resume/attach/discover/share claims, and empty content channels.
5. Run the exact platform probe before promoting any field. Record version, executable path/package digest, command, platform, identity behavior, returned opaque ref, ownership, ordering, correlation, lifecycle events, cancellation semantics, close semantics, and descendant cleanup.
6. Probe sequence:
   - initialize/open in an isolated project/runtime;
   - obtain and protect the exact provider session ref if one is returned;
   - execute two correlated turns through the shared gateway/session path;
   - induce a safe tool call and permission request when the installed version supports them;
   - issue cancellation during an active turn and distinguish acknowledgement from terminal/idle evidence;
   - close the owned session and prove child/descendant cleanup;
   - attempt invalid/stale operations and prove no latest/name/UI fallback.
7. Promote only observed capabilities in the AS29 declaration. Examples:
   - `open_new` and `returns_opaque_ref` only if proven;
   - `resume_by_ref`, `attach_existing`, `discover_existing`, and concurrent attachment remain unsupported unless separately and exactly proven;
   - lifecycle level contains only events actually present with sufficient ordering/correlation;
   - cancellation mode reflects observed cooperative/forced behavior;
   - content channels remain `[]` for this plan.
8. Feed neutral observations through the AS19 generic mapper. Do not add an OpenCode-specific neutral observation observer or second resolver/registry. Unknown, duplicate, stale, uncorrelated, or undeclared events produce no lifecycle advancement.
9. Use AS30 for open transaction persistence and rollback. A failed binding persist must close the provisional owned transport and leave no active record/index entry. Raw provider refs never enter logs, public status, filenames, or diagnostics.
10. Keep permissions default-deny unless a separately declared generic permission-control capability and handler are proven. This plan does not invent an OpenCode-specific permission policy.
11. Keep user assistant text out of lifecycle evidence and public metadata. Observing text in ACP creates only an AS31 candidate fact; enable no `assistant-text` channel until bounds, ordering, redaction, final-output selection, and crash behavior are tested under AS31.
12. Add architecture enforcement forbidding ACP/OpenCode native imports or branches under agents. Provider/foundation adapters may use native ACP types privately.

## Validation

- exact version/platform selection and conservative mismatch behavior;
- no hook/plugin/config write;
- private raw ACP-to-neutral mapping;
- generic neutral-to-evidence mapping;
- per-turn ordering, duplicate/stale rejection, and request/turn correlation;
- two-turn FIFO through the shared session path;
- tool and permission phases only when actually observed;
- cancellation acknowledgement remains nonterminal;
- deterministic close and owned descendant cleanup;
- AS30 binding persistence/rollback and protected-ref redaction;
- invalid resume/attach/discovery fail without fallback;
- AS21 projection from proven evidence;
- content absent from status/timeline and AS31 channels empty;
- no ACP/OpenCode native imports or branches in agents;
- Windows direct proof and Linux Docker proof are recorded separately.

## Effort & Risk

Complex first vertical slice. The primary risks are overclaiming ACP events, leaking provider identity, duplicating the ACP stack, and treating control acknowledgement as completion.

## Standards

Evidence is authoritative over documentation. Reuse the existing provider launch builder, shared ACP parser/transport, provider API boundary, AS19 generic mapper, AS29 declaration owner, AS30 binding owner, AS21 projector, and AS52/foundation cleanup.
