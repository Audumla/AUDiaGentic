# Integrate role selection into job submission and gateway execution

## Description

**Consumed from `role-capabilities/RO03` on 2026-08-03 (RV886).** RO03 is superseded by this item.

Allow MCP and event-triggered jobs to specify an `agent-role-id` through thin protocol adapters.
Resolve the role into the immutable launch manifest through the framework-neutral agents public
API **before dispatch**, persist its identity and provenance with the request, and have
context-isolated workers materialize that manifest.

Explicit agent-profile selection and existing workflow-profile semantics are preserved. MCP and
event modules do not resolve roles and do not inspect component or provider internals — they
translate parameters and call the public API, per `arch-standards` §8.

## Steps

1. Extend submission contracts and events with an optional `agent-role-id`, and state the
   precedence rules (AS61 owns the precedence definition; this item implements it).
2. Resolve and validate role intent at the authoritative boundary; carry the resolved
   manifest and fingerprint through the request rather than re-reading publisher process state.
3. Make context-isolated workers enable only the declared components, features, MCP surfaces and
   permissions from the manifest.
4. Include safe role and capability identity in lifecycle events and timelines — identity and
   fingerprint, never the full manifest and never secrets.
5. Add documented compatibility behaviour for callers that supply no role during migration.
6. Test MCP, event, retry/resume, session and cross-project paths.

## Validation

Carried from RO03:

- A role-submitted job executes with **exactly** its resolved capability set, from another
  process.
- Retries and resume keep the **same** manifest — assert equality of fingerprint and effective
  capability set, not merely that the job succeeds.
- Callers without a role follow the documented migration default.
- Conflicting explicit profile and role requirements **fail before dispatch**, not at launch.
- Architecture checks prove MCP and event adapters only translate parameters and call the public
  role/gateway APIs.
- All role resolution and policy is independently testable **without MCP**.

Added on consumption:

- No capability set is derived a second time anywhere downstream of the authoritative boundary —
  the anti-drift constraint, asserted directly.
- Lifecycle events and timelines carry role identity and fingerprint but no secrets and no full
  manifest.

## Effort & Risk

Medium once AS77's contracts exist — unchanged from RO03's assessment.

Primary risk, carried verbatim: resolving twice at different boundaries and producing drift. The
mitigation is structural rather than procedural — there is one resolution call site, and the
validation asserts no second derivation exists.

Secondary risk added on consumption: the migration default for role-less callers is the kind of
compatibility path `arch-standards` §4 requires to be removed rather than kept. It is acceptable
here because it is bounded and AS79 owns its removal — but it must be named as temporary in code
and not become the permanent default by neglect.

## Standards

- `arch-standards` §8 Protocol Adapter Boundaries — MCP and event modules translate and call the
  public API; they own no resolution, policy or persistence.
- `arch-standards` §1 Dependency Boundaries — adapters depend on framework-neutral public APIs.
- `arch-standards` §4 Public Contracts — the role-less migration default is a bounded
  compatibility path with a named owner for its removal (AS79), not an indefinite dual route.
- `arch-standards` §6 Platform and Provider Boundaries — the gateway stays requester-blind; it
  transports and enforces the manifest without interpreting role semantics.
- `arch-standards` §7 Enforcement — the anti-drift constraint carries an automated check.
- `CREATING_A_COMPONENT` §2 and §6.
- AS59 Rule 0 — no composition binding is added by this item.

## Acceptance Criteria

- A role-submitted job executes with **exactly** its resolved capability set, verified from a
  different process than the one that submitted it.
- Retry and resume reproduce the **same** manifest — asserted by equality of fingerprint and
  effective capability set, not by the job merely succeeding.
- The capability set is derived **once**, at the authoritative boundary. No consumer downstream
  re-derives it, and an automated check proves no second derivation site exists. This is the
  defect the item exists to prevent.
- Conflicting explicit profile and role requirements fail **before dispatch**, not at launch.
- Callers supplying no role follow the documented migration default, and that default is named in
  code as temporary with AS79 recorded as the owner of its removal.
- MCP and event adapters only translate parameters and call the public role/gateway APIs — proven
  by architecture test, per `arch-standards` §8.
- All role resolution and policy is independently testable without MCP.
- Lifecycle events and timelines carry role identity and manifest fingerprint only — never the
  full manifest, never secrets.
- No composition binding is added by this item (AS59 Rule 0).
- Explicit agent-profile selection and existing workflow-profile semantics are unchanged for
  callers that do not use roles.

## The single defect this item exists to avoid

RO03 named it precisely and it is carried over as the item's organising constraint: **resolving
twice at different boundaries produces drift.** The manifest is resolved once, at the
authoritative boundary, then *transported* — through the request record, through retries, through
resume, into the worker. No consumer re-derives it from publisher process state.

The gateway transports and enforces the resolved manifest. It does not own role semantics.

## Composition boundary (added on consumption)

Under AS59 Rule 0, nothing in this item becomes a composition binding. Role resolution is reached
through the agents component's public surface. If that surface is not yet composable when this
item starts, that is AS60/AS63's work and not a reason to add a binding for the resolver.

Specifically: do **not** inject the resolver into the MCP adapters. §8 says adapters call an
owning public API; the public API reaches the resolver internally.

## Persistence shape

The request record carries the manifest **fingerprint and role identity** as durable fields. Whether
the full manifest is persisted alongside them, or re-derivable from the fingerprint, is an open
design question for this item — with one constraint fixed in advance: retry and resume must
reproduce the *same* manifest, so a fingerprint that cannot reconstruct or verify its manifest is
insufficient.
