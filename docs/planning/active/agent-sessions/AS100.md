# A2A publication and bounded agent delegation

## Description

Publish selected Agent Definitions over A2A, let AUDiaGentic call explicitly configured remote A2A agents, and give a running harness a bounded way to delegate work to another AUDiaGentic agent.

A2A is a protocol adapter and a remote transport. It is not a second task engine, runtime, registry or workflow system — all delegation resolves to the existing task authority.

## Steps

1. Prove local agent-to-agent delegation through the existing task API first, with no A2A involved. This is the part that must work before any protocol is added.
2. Add logical agent/skill discovery only where a caller genuinely needs to select a target.
3. Define target authorization and local-versus-remote routing behind the application boundary.
4. Add the A2A server adapter over the task and Agent Definition public APIs: generate a basic Agent Card from Agent Definition identity and skills, accept a message/task and submit existing task work, expose existing status/output/cancellation.
5. Add one trusted remote A2A client transport behind a narrow injected boundary, with explicitly configured endpoints only — no network discovery.
6. Give the harness the bounded gateway capability it needs: find/describe permitted agents, delegate a bounded task, check status/result, cancel. Project it through the existing runtime MCP surface rather than standing up a duplicate delegation server.
7. Prove the capability actually reaches the child for each launch path — direct CLI, harness runner, and the ACP/RPC bridge. A provider-wide MCP declaration does not prove a bridge-launched child receives the tools.
8. Bound delegation: recursion depth, timeout, cancellation propagation, and task ownership scoped to the calling agent.

## Validation

- Local delegation uses the existing task request/status/output/cancel owners — no second durable task engine.
- Remote A2A maps to the same logical result as local.
- Only published Agent Definitions produce Agent Cards; only configured endpoints are callable.
- The harness can reach the delegation operations; operator-only operations (profile/role CRUD, provider configuration, global request listing, gateway overview, unrelated callers' tasks) remain unavailable to it.
- Direct CLI and each ACP/RPC bridge independently expose the intended tools.
- Cancellation and timeout propagate across local and remote calls; recursion is bounded.
- The graph can substitute a fake remote transport without changing delegation code.

## Standards

- `arch-standards` §8 Protocol Adapter Boundaries — the A2A server is an adapter over public APIs.
- `arch-standards` §3 Ownership and Abstraction — one task authority; no A2A task store.
- `arch-standards` §3 Evidence-led scope — no push notifications, multi-transport support or multi-turn task machinery until demonstrated.

## Acceptance Criteria

- Local and remote delegation resolve to the same canonical task authority; no second durable task engine, store or runtime exists.
- Local delegation works before any A2A protocol is involved.
- Only published Agent Definitions produce Agent Cards, and only explicitly configured endpoints are callable — no network discovery.
- A running harness can reach the delegation operations, including full cross-harness visibility within its project (`agent_task_list_requests`, `agent_task_gateway_overview` stay propagated and unfiltered by caller — that is intended, not a leak).
- Operator-only operations — profile/role CRUD, provider configuration and credentials — remain unavailable to the harness-facing surface. This is the real, valid split step 6 owns: operator versus runtime capability, not visibility scoping between harnesses.
- The delegation capability is proven to reach the child on each launch path independently — a provider-wide MCP declaration is not accepted as proof for a bridge-launched child.
- Cancellation and timeout propagate across local and remote calls; recursion depth is bounded.
- The remote transport is replaceable by a fake without changing delegation code.

## Codebase Verification 2026 08 05

**Corrected 2026-08-05 after the deployment model was stated. My earlier reading of this as an operator-tool leak was wrong.**

`agent_task_list_requests` and `agent_task_gateway_overview` are propagated to every harness (`agents.yaml` lines 143-144, server `propagate: providers` line 151). I originally called this a §6 boundary defect requiring caller-scoped variants. **That is not the requirement.** Every harness within a project *should* be able to enumerate other harnesses' work — they are peers inside a project, and that visibility is the point of a shared gateway.

**The real boundary is the project, and it is owned by AS101.** The genuine defect there is a queue-lane collision, not a visibility leak: lanes key on `(profile_id, generation, config_digest)` with no project component, so two projects with a same-named identically-configured profile share one lane and its concurrency limit.

**Consequences for this item:** drop the caller-scoping work entirely. Do not add per-harness filtering to either tool, and do not move them to the management server. What this item still owns from the same area is step 6's operator/harness split — profile and role CRUD, provider configuration and credentials stay off the harness-facing surface. That distinction is about *operator vs runtime capability*, which remains valid, not about hiding peers' work from each other.

The delegation authorization in step 8 (recursion depth, timeout, task ownership scoped to the calling agent) also stays — those are bounding controls against runaway delegation, not defences against a hostile caller, and they hold regardless of threat model.
