# Compose execution profiles and roles into logical agent definitions

## Goal

Introduce the logical agent as a small immutable composition of one Execution Profile and one Role, plus identity, advertised skills and interface-publication policy.

The Agent Definition is the externally meaningful entity. Provider, model, harness surface and launch details remain implementation details.

## Execution prerequisite

AS59 Gate 0, AS60/R1 and AS61/R2 must be closed before implementation begins. AS59 must record that one Role composes cleanly with multiple Execution Profiles and that no competing agent/profile expansion plan remains executable.

## Contract

Define:

- `AgentDefinition` — persisted composition;
- `AgentDefinitionSnapshot` — immutable resolved composition;
- `AgentIdentity` — stable ID, name and description;
- `AgentSkill` — bounded advertised work capability, initially metadata plus supported input/output contract references;
- `AgentInterfacePolicy` — whether internal, ACP and A2A adapters may publish the agent;
- references to exactly one `ExecutionProfile` and one `Role` in the first version;
- immutable IDs, generations/digests and effective-capability digest in the resolved snapshot.

Do not add arbitrary nested overrides. Permit only small explicitly typed overrides proven necessary by R3, such as display metadata or a stricter tool deny-list.

## Resolution

Resolution order is fixed:

1. resolve Agent Definition;
2. resolve immutable Execution Profile snapshot;
3. resolve immutable Role snapshot;
4. resolve exact AS29 Session Surface without launching;
5. compose model/surface/policy capabilities through AS64 or a fake seam until AS64 lands;
6. validate Role requirements;
7. return one redacted immutable `AgentDefinitionSnapshot`.

Resolution failure launches no process and creates no session/task.

## Skills and roles

Keep the distinction:

- Role — internal behavior and policy;
- Skill — externally advertised unit of useful work;
- runtime capability — technical support resolved from surface/model/configuration.

Do not publish technical facts such as `resume-by-ref`, `stdio`, provider names or raw session controls as Agent Skills.

## Steps

1. Consume completed AS61/R2 findings from AS59.
2. Add schemas/models/store/resolver for Agent Definitions.
3. Migrate public submission selection from Execution Profile ID toward Agent Definition ID while retaining an explicit Execution Profile compatibility path until AS63.
4. Add immutable snapshot/digest fields to SH02 execution context and AS30/AS47 session-generation checks without changing session behavior.
5. Add Skill and interface-policy projections but no protocol server implementation in this slice.
6. Add validation that ACP publication requires a usable interactive session surface and A2A publication requires at least one Skill and task/output support; final protocol capability checks land in AS65/AS66.
7. Add architecture gates preventing provider-native data in Agent Definitions and preventing agents core from importing ACP/A2A SDK types.
8. Verify the AS59-mandated amendments to AS19, AS29, AS30, AS31, AS47, AS49, AS57 and AS58 are present before closing R3.
9. Update AS59 with all R3 findings and any plan changes before AS63 starts.

## Reassessment gate R3

Before AS63:

- resolve the same logical agent identity against at least two Execution Profiles in tests or fixtures;
- prove public identity/Skills remain stable when implementation changes unless the Agent Definition generation changes intentionally;
- prove one Execution Profile can materialize multiple differently behaved agents through distinct Roles;
- review whether one Role/one Execution Profile remains sufficient;
- review the first Skill schema against intended A2A Agent Card projection, without coupling the domain model to the A2A SDK.

Record the R3 decision in AS59 before AS63 begins.

## Validation

- schema/store/snapshot round trip;
- exact missing/stale Role and Execution Profile errors;
- requirement mismatch launches no process;
- immutable digests captured in session execution context;
- no raw instructions/secrets/provider refs in public projection;
- interface policy defaults disabled/private;
- Skills remain work-oriented, not transport capability duplicates;
- same logical definition resolves deterministically across shared/embedded gateway modes.

## Acceptance criteria

- Logical agents are explicit compositions, not overloaded Execution Profiles.
- Agent Definitions are the source for future ACP/A2A publication.
- Existing session runtime still executes through provider-neutral contracts.
- Session generations freeze Agent Definition, Role and Execution Profile identity/digests.
- R3 findings are recorded in AS59 before AS63 begins.
