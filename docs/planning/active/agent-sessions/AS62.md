# Compose execution profiles and roles into agents

## Goal

Add `AgentDefinition` as a small logical composition:

- stable ID, name and description;
- one Execution Profile;
- one Role;
- optional advertised skills;
- whether internal, ACP or A2A publication is enabled.

Provider, model, surface and launch details remain inside the Execution Profile.

## Service boundary

Expose resolution through one small application service/port, for example `AgentDefinitionService` or `AgentResolver`. Callers depend on that interface, not on stores, YAML loaders or provider implementations.

Use constructor-injected dependencies or explicit function parameters. Do not introduce a DI container in this item; keep the boundary ready for the later IoC/DI refactor.

## Work

1. Add one simple Agent Definition model, store and resolver.
2. Resolve its Execution Profile, Role and AS29 surface before launch.
3. Validate the Role's requirements.
4. Record only the active IDs and execution facts needed by the existing session/execution manifest.
5. Add skills and interface flags as metadata only; AS65/AS66 implement protocols.
6. Update submission callers to select an Agent Definition where the new domain requires it; do not retain a second direct Execution Profile work path.
7. Keep persistence, resolution and publication behind separate small interfaces where they are already separate concerns.
8. Delete any superseded agent-selection APIs, fields, handlers and tests in the same change.

## Do not add

- persisted Agent/Role/Profile copies;
- nested snapshot objects;
- arbitrary overrides;
- multiple roles;
- inheritance;
- a new session or runtime store;
- service locators or global registries;
- migration shims, aliases or dual agent-selection paths.

## Reassess before AS63

Prove the same logical agent can use another Execution Profile without changing its public identity, and that one Execution Profile can back agents with different Roles.

Confirm callers can be tested with fake service implementations without importing concrete stores or provider adapters.

## Acceptance criteria

- Agent Definition is the externally meaningful composition.
- Resolution launches no process until validation passes.
- Existing session runtime and persistence are reused.
- Callers depend on a small agent-resolution service boundary suitable for later IoC/DI wiring.
- No superseded direct-selection route or compatibility handler remains.
