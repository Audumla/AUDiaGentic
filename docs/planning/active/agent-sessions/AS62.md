# Compose execution profiles and roles into agents

## Goal

Add `AgentDefinition` as a small logical composition:

- stable ID, name and description;
- one Execution Profile reference;
- one Role reference;
- optional advertised skills;
- optional internal, ACP and A2A publication flags.

Provider, model, surface and launch details remain in the Execution Profile. Runtime tool/MCP and permission ownership remains with existing component/provider materialization.

## Boundary

Expose one narrow Agent Definition lookup/resolution API. It receives the Execution Profile, Role and AS29 provider APIs explicitly and returns a short-lived resolved value for admission. It does not own provider execution, session creation, task dispatch, protocol publication or runtime tool materialization.

Do not split lookup, resolution and publication into separate services unless existing ownership or a second current consumer requires it.

## Publication flags

Publication flags are authorization/visibility metadata only:

- `internal`: may be selected by AUDiaGentic callers;
- `ACP`: eligible for AS65 external ACP exposure after capability validation;
- `A2A`: eligible for AS66 Agent Card/task exposure after capability validation.

They do not:

- install or select MCP servers;
- grant management MCP access;
- alter the harness default/configured runtime tools;
- imply the selected session surface supports ACP/A2A;
- bypass AS64/AS65/AS66 validation and authorization.

AS66 may separately authorize the dedicated runtime delegation capability for a source agent. That is not a generic Agent Definition tool-set field.

## Work

1. Add the minimal Agent Definition model and storage.
2. Resolve its Execution Profile and Role through their public APIs.
3. Resolve the selected AS29 surface through `providers_api` without launching.
4. Validate current Role requirements.
5. Record only active IDs and execution facts already required by the session/execution manifest.
6. Update agent-work callers to select an Agent Definition.
7. Delete superseded direct Execution Profile work-selection APIs, fields, handlers, fixtures and tests in the same change.
8. Add architecture checks preventing provider-native data, protocol types, management MCP configuration and concrete-store imports.
9. Add tests proving publication flags do not change runtime MCP projection or provider permissions.

## Do not add

- copied Agent/Role/Profile definitions in session records;
- snapshot objects or definition versioning infrastructure;
- arbitrary overrides;
- multiple roles or inheritance;
- a new session/runtime store;
- publication registries;
- runtime tool/MCP lists;
- management MCP access flags;
- service locators, global registries, migration shims or dual selection paths.

## Reassess before AS63

Prove one Execution Profile can back two agents with different Roles. Prove an Agent Definition can be edited to reference another compatible Execution Profile while retaining its stable public ID, without adding versioning infrastructure. Confirm publication flags do not alter the selected harness tools and callers can use fake public APIs without provider/store imports.

## Acceptance criteria

- Agent Definition is the logical agent selected by agent-work callers.
- Resolution launches no process and creates no durable task/session.
- Publication eligibility is separate from protocol implementation and runtime tool materialization.
- Existing session runtime, provider MCP projection and persistence remain unchanged.
- The public boundary is small and DI-ready.
- No direct Execution Profile agent-work path or compatibility handler remains.
