# Compose execution profiles and roles into agents

## AS59 disposition

Disposition: keep  
Authority: AS59  
Position: Composition track, position 5.

- Sole Agent Definition composition/lookup owner. Publication flags are visibility metadata only.
- Blocked by AS61's reassessment.

## Goal

Add `AgentDefinition` as a small logical composition:

- stable ID, name and description;
- one Execution Profile reference;
- one Role reference;
- optional advertised skills;
- optional internal, ACP and A2A publication flags.

Provider, model, surface and launch details remain in the Execution Profile. Runtime tool/MCP and permission ownership remains with existing component/provider materialization.

## Boundary

Expose one narrow Agent Definition lookup/resolution API. It receives the Execution Profile, Role and AS29 provider APIs explicitly and returns a short-lived resolved value for admission. It does not own provider execution, session creation, task dispatch, protocol publication or runtime tool materialization.

Do not split lookup, resolution and publication into separate services unless existing ownership or a second current consumer requires it.

## Foundation composition adoption

Runtime/bootstrap must build the stateful Agent Definition repository/lookup and its resolver through the foundation composition graph.

- inject Execution Profile lookup, Role lookup and the approved provider/session-surface API into the resolver;
- keep the Agent Definition model and pure composition validation container-free;
- expose the resolved Agent Definition service as a root dependency for AgentTask, ACP and A2A wiring;
- management MCP/CLI adapters receive the public CRUD API from their adapter composition root;
- no caller may import concrete stores or call a global graph/service lookup.

## Publication flags

Publication flags are authorization/visibility metadata only:

- `internal`: may be selected by AUDiaGentic callers;
- `ACP`: eligible for AS65 external ACP exposure after capability validation;
- `A2A`: eligible for AS66 Agent Card/task exposure after capability validation.

They do not:

- install or select MCP servers;
- grant management MCP access;
- alter the harness default/configured runtime tools;
- imply the selected session surface supports ACP/A2A;
- bypass AS64/AS65/AS66 validation and authorization.

AS66 may separately authorize the runtime gateway/delegation capability for a source agent. That is not a generic Agent Definition tool-set field.

## Work

1. Add the minimal Agent Definition model and storage.
2. Resolve its Execution Profile and Role through their public APIs.
3. Resolve the selected AS29 surface through `providers_api` without launching.
4. Validate current Role requirements.
5. Record only active IDs and execution facts already required by the session/execution manifest.
6. Register the stateful lookup/resolver in foundation composition and inject it into AgentTask and adapter roots.
7. Update agent-work callers to select an Agent Definition.
8. Delete superseded direct Execution Profile work-selection APIs, fields, handlers, fixtures and tests in the same change.
9. Add architecture checks preventing provider-native data, protocol types, management MCP configuration, concrete-store imports and runtime graph lookup.
10. Add tests proving publication flags do not change runtime MCP projection or provider permissions.

## Do not add

- copied Agent/Role/Profile definitions in session records;
- snapshot objects or definition versioning infrastructure;
- arbitrary overrides;
- multiple roles or inheritance;
- a new session/runtime store;
- publication registries;
- runtime tool/MCP lists;
- management MCP access flags;
- service locators, global registries, migration shims or dual selection paths.

## Reassess before AS63

Prove one Execution Profile can back two agents with different Roles. Prove an Agent Definition can be edited to reference another compatible Execution Profile while retaining its stable public ID, without adding versioning infrastructure. Confirm publication flags do not alter the selected harness tools and fake profile/role/provider dependencies can be supplied through the foundation graph.

## Validation

- `tests/unit/agents/test_agent_definitions.py` (new) — one Execution Profile
  backing two agents with different Roles; an Agent Definition re-pointed to a
  different compatible Execution Profile while keeping its stable public ID, with
  no versioning infrastructure introduced.
- A test asserts publication flags (`internal`/`ACP`/`A2A`) change neither the
  runtime MCP projection nor provider permissions.
- Resolution launches no process and creates no durable task or session —
  assert by fake provider that `open`/`prompt` are never called.
- Fake profile, role and provider dependencies are supplied through the
  foundation graph at build time.
- An architecture test asserts no provider-native data, protocol type,
  management-MCP configuration, concrete-store import or runtime graph lookup.
- `python -m pytest tests/unit` green with the superseded direct Execution
  Profile work-selection path deleted.

## Acceptance criteria

- Agent Definition is the logical agent selected by agent-work callers.
- Resolution launches no process and creates no durable task/session.
- Publication eligibility is separate from protocol implementation and runtime tool materialization.
- Existing session runtime, provider MCP projection and persistence remain unchanged.
- Stateful lookup/resolution is built at runtime through foundation composition.
- Domain/application code contains no container or graph lookup.
- No direct Execution Profile agent-work path or compatibility handler remains.

## Standards

- `arch-standards` §3 Ownership and Abstraction — one narrow Agent Definition
  lookup/resolution API. Do not split lookup, resolution and publication into
  separate services without a second current consumer.
- `arch-standards` §3 Evidence-led scope — no snapshot objects, definition
  versioning, inheritance or override machinery; record only IDs and execution
  facts the session/execution manifest already requires.
- `arch-standards` §1 Dependency Boundaries — the resolver is composed at the
  runtime root with Execution Profile, Role and `providers_api` injected; no
  caller imports concrete stores or resolves from the graph.
- `arch-standards` §6 Platform and Provider Boundaries — publication flags are
  authorization metadata only and must not alter runtime MCP projection or
  provider permissions.
- `arch-standards` §4 Public Contracts — the direct Execution Profile
  work-selection path is deleted, not aliased.
