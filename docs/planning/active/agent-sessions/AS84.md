# Role capability vocabulary and launch manifest resolver

## Description

Resolve a Role's declared capability requirements into a validated, immutable launch manifest with a stable fingerprint.

This is the mechanism only. Policy — which capabilities are privileged, what presets exist, what fails closed on escalation — is deliberately excluded and belongs to the policy-gates item at the end of the sequence. Building the resolver first and the policy later is the split that lets this item finish.

## Steps

1. Define the typed capability vocabulary. Evidence-gated per term: no capability term without a Role in this repo that demonstrably needs it. Start from what already exists rather than inventing a parallel model — the provider capability catalogue (`descriptors/capability_catalogue.py`, domains exec/mcp/lsp/perm/model/surface/acp/hook/plugin/file/cli/obs) and AS29 surface capabilities are the two existing sources this consumes.
2. Build the resolver: role requirements + provider/surface evidence -> manifest. Pure read; mutates no process-global registry.
3. Produce a stable fingerprint. The same inputs produce the same manifest and fingerprint across processes.
4. Enforce dependency closure and conflicts. Unknown or missing evidence resolves to unsupported — there is no permissive default.
5. Add explain output showing why each capability was selected or rejected.
6. Ship the reviewer/implementer/research role fixtures as tests, not as product presets.

## Detailed Solution & Technical Design

Two narrow provider facts already exist and are the concrete backbone of the first vocabulary terms — both already have public read APIs, so the resolver needs no new provider internals for them:

- `providers_api.get_provider_execution_isolation_tier(provider_id)` -> full-isolation (codex, local-openai, qwen, pi, opencode) / partial-isolation (aider, continue, goose) / no-isolation.
- `providers_api.get_provider_mcp_launch_isolation_tier(provider_id)` -> `exact` (pi, opencode only) / `additive` / `unsupported`. This is the real mechanism behind "run this role in isolation with only its own MCP config".

Start the vocabulary from these two plus AS29 surface facts. Every further term needs its own demonstrated Role.

- Missing evidence resolves to unsupported, with no permissive fallback anywhere.
- Every vocabulary term traces to a demonstrated Role.
- No provider-name conditionals in the vocabulary.
- The resolver imports no component or provider internals; `providers_api` is the only approved cross-component import.
- Resolution mutates no process-global registry — asserted directly, not by inspection.

## Effort & Risk

Large and the most semantically demanding item in the set. Two named risks:

- **Vocabulary sprawl.** A vocabulary spanning components, features, MCP, permissions and resources grows to cover hypothetical cases. The per-term evidence bar is the control.
- **Becoming a second capability model.** The provider catalogue owns provider capabilities and AS29 owns surface capabilities. This item owns neither and must consume both. A capability the provider catalogue cannot express is a change raised there, not a local vocabulary extension here.

## Acceptance Criteria

- A role plus project/provider/surface evidence resolves to an immutable manifest with a stable fingerprint, reproducible across processes.
- The manifest contains only what the role requires — unrelated components and MCP surfaces are absent from it, not merely disabled.
- Missing or unknown evidence resolves to unsupported. No permissive fallback exists anywhere in the resolver.
- Every vocabulary term traces to a demonstrated Role that needs it, and the vocabulary contains no provider-name conditionals.
- The resolver imports no component or provider internals; `providers_api` is the only approved cross-component import.
- The resolver is not a composition binding and mutates no process-global registry — both asserted directly.
- Provider capability facts come from the provider catalogue and surface facts from AS29. No second capability model is defined for either.
- Role fixtures ship as tests, not as product presets.
- No policy is implemented here — privileged-capability authorization, escalation behaviour and presets are absent by design.

## Codebase Verification 2026 08 05

**Verified against the tree. The Detailed Solution's domain list was slightly wrong — corrected here with the real inventory, which is the concrete starting point for step 1.**

Loaded via `capability_catalogue.load_catalogue()`. The catalogue exposes exactly three public members — `kinds_by_id`, `kinds_by_domain`, `families` — and holds **13 domains / 20 kinds**:

| Domain | Kinds |
|---|---|
| `acp` | `acp` |
| `cli` | `cli-install` |
| `exec` | `execution-isolation`, `launch`, `launch-isolation` |
| `ext` | `host-extensions` |
| `file` | `agent-files` |
| `hook` | `hooks` |
| `lsp` | `lsp-config`, `lsp-self-support` |
| `mcp` | `mcp` |
| `model` | `model-config-projection`, `model-local-state`, `models` |
| `obs` | `obs-transport-observability` |
| `perm` | `permissions` |
| `plugin` | `plugins` |
| `surface` | `surface-instruction`, `surface-skill`, `surfaces` |

The earlier list in this item omitted `ext` and gave domains without kinds. **Kinds, not domains, are the useful unit for step 1** — a role requirement maps to a kind (`execution-isolation`, `launch-isolation`, `permissions`), not to a domain.

**`CapabilityKind` already carries an `authority` discriminator** — `provisioned` / `operational` / `evidence-only`. That distinction is directly load-bearing for this item's least-capability rule: an `evidence-only` kind describes an observed fact and can never be *requested* by a role, whereas a `provisioned` kind can. Use the existing discriminator rather than inventing a parallel one; §3 forbids a second model over the same facts.

The two isolation-tier read APIs named in the Detailed Solution are confirmed present on `providers_api` and are the right first vocabulary terms: `get_provider_execution_isolation_tier` and `get_provider_mcp_launch_isolation_tier`. Note both are **provider-wide** facts, not per-capability entries in this catalogue — so the vocabulary will need to consume from two shapes (descriptor-level tiers and catalogue kinds), which is worth designing for explicitly rather than discovering mid-implementation.
