# Role capability vocabulary and launch manifest resolver

## Description

Build the mechanism-only role manifest resolver required by AS85: typed vocabulary, immutable Role/evidence/manifest, pure deterministic resolution, and stable fingerprint. No presets, escalation, fallback, or policy selection.

## Steps

1. Make Role frozen/slots with canonical tuple of typed requirement IDs; reject duplicates/unknowns — steps 1+2 are one invariant: immutable Role values + store-only replacement.
2. Encapsulate RoleStore with replace/upsert/load and remove direct _roles mutation and duplicated role_api parsing — no window exists where resolver could see mutable state.
3. Define config-owned vocabulary mapping requirement IDs to evidence predicates, dependencies, and launch contributions; enforce authority discriminator (evidence-only kinds rejected at Role boundary).
4. Expose one narrow typed providers_api evidence read; agents must not import descriptor/catalogue internals.
5. Snapshot evidence once at boundary; pure resolver receives Role + Vocabulary + Evidence.
6. Return immutable manifest and separate explanation; canonicalize before hashing and exclude prose/time. Fingerprint scope explicitly excludes governance_policy, recommended_tools, mutable metadata fields from manifest inputs.
7. Add agents-owned manifest schema/version; no legacy aliases without approved obligation.
8. Replace substring allowlist architecture test with AST/scope-aware checks.
9. AS85 consumes only supplied manifest/fingerprint.

## Detailed Solution & Technical Design

Use frozen CapabilityRequirement, LaunchCapabilityEvidence, LaunchContribution, and RoleManifest types. Vocabulary is data, not provider-name branching. Resolver validates dependency closure, returns all unmet requirements in deterministic order, and never returns partial success. Fingerprint canonical JSON with sorted keys and normalized tuples using the repository digest. Explanation stays outside the digest. Resolver performs no I/O, registry access, mutation, or clock reads.

Steps 1+2 are one invariant: Role must be frozen/slots AND RoleStore must enforce store-only replacement (no _roles mutation, no aliasing of mutable instances) in a single commit — no window exists where the resolver could see mutable state.

Fingerprint scope is explicitly limited to typed requirement IDs. Governance_policy, recommended_tools, and mutable metadata fields on the broader Role model are excluded from fingerprint material by design; those may survive as advisory/preset data but never enter the mechanism-only resolver.

## Acceptance Criteria

- A role plus project/provider/surface evidence resolves to an immutable manifest with a stable fingerprint, reproducible across processes.
- The manifest contains only what the role requires — unrelated components and MCP surfaces are absent from it, not merely disabled.
- Missing or unknown evidence resolves to unsupported. No permissive fallback exists anywhere in the resolver.
- Every vocabulary term traces to a demonstrated Role that needs it, and the vocabulary contains no provider-name conditionals.
- The resolver imports no component or provider internals; `providers_api` is the only approved cross-component import.
- The resolver is not a composition binding and mutates no process-global registry — both asserted directly.
- Provider capability facts come from the provider catalogue and surface facts from AS29. No second capability model is defined for either.
- Role fixtures ship as tests, not as product presets.
- No policy is implemented here — privileged-capability authorization, escalation behaviour and presets are absent by design.
- (RV938) Evidence-only capabilities are rejected at the Role boundary — not just documented but enforced. Fingerprint explicitly excludes governance_policy, recommended_tools, and metadata fields.

## Codebase Verification 2026 08 05

**Verified against the tree. The Detailed Solution's domain list was slightly wrong — corrected here with the real inventory, which is the concrete starting point for step 1.**

Loaded via `capability_catalogue.load_catalogue()`. The catalogue exposes exactly three public members — `kinds_by_id`, `kinds_by_domain`, `families` — and holds **13 domains / 20 kinds**:

| Domain | Kinds |
|---|---|
| `acp` | `acp` |
| `cli` | `cli-install` |
| `exec` | `execution-isolation`, `launch`, `launch-isolation` |
| `ext` | `host-extensions` |
| `file` | `agent-files` |
| `hook` | `hooks` |
| `lsp` | `lsp-config`, `lsp-self-support` |
| `mcp` | `mcp` |
| `model` | `model-config-projection`, `model-local-state`, `models` |
| `obs` | `obs-transport-observability` |
| `perm` | `permissions` |
| `plugin` | `plugins` |
| `surface` | `surface-instruction`, `surface-skill`, `surfaces` |

The earlier list in this item omitted `ext` and gave domains without kinds. **Kinds, not domains, are the useful unit for step 1** — a role requirement maps to a kind (`execution-isolation`, `launch-isolation`, `permissions`), not to a domain.

**`CapabilityKind` already carries an `authority` discriminator** — `provisioned` / `operational` / `evidence-only`. That distinction is directly load-bearing for this item's least-capability rule: an `evidence-only` kind describes an observed fact and can never be *requested* by a role, whereas a `provisioned` kind can. Use the existing discriminator rather than inventing a parallel one; §3 forbids a second model over the same facts.

The two isolation-tier read APIs named in the Detailed Solution are confirmed present on `providers_api` and are the right first vocabulary terms: `get_provider_execution_isolation_tier` and `get_provider_mcp_launch_isolation_tier`. Note both are **provider-wide** facts, not per-capability entries in this catalogue — so the vocabulary will need to consume from two shapes (descriptor-level tiers and catalogue kinds), which is worth designing for explicitly rather than discovering mid-implementation.
