# External ACP server adapter over AUDiaGentic sessions

## Description

Expose AUDiaGentic-owned sessions to an external ACP client through one thin protocol adapter.

This is an adapter over AUDiaGentic's own sessions — never a raw proxy to an underlying harness's ACP session. It adds no session, task, output or control authority.

## Steps

1. Pin one ACP schema/SDK version inside the adapter package.
2. Translate ACP requests into the existing public application operations. Use AUDiaGentic task and session ids as the external identities where the protocol permits; add a small correlation map only where translation genuinely requires one.
3. Implement only what the canonical APIs already support: initialize/capabilities, open a session for an Agent Definition, submit a turn, read output and status, cancel and close. Everything else returns a protocol-compliant unsupported result — never an emulation.
4. Read through **AS94** (the live turn read surface) and control through **AS95** (the generic controls surface). Never touch provider transports, output files or event stores directly.
5. Construct the adapter at the composition root from approved public ports. No graph lookup during request handling.
6. Advertise only capabilities that are actually proven.

## Validation

- The load-bearing test: the adapter is constructed entirely from fake public ports, with no concrete store, provider adapter or graph lookup imported. This proves the boundary, not just the behaviour.
- The same adapter drives one ACP-backed and one fake non-ACP transport, producing identical canonical results.
- Every operation outside the implemented scope returns a protocol-compliant unsupported result; assert per operation, and assert nothing is emulated.
- Reads and controls go through the canonical surfaces — assert by fake that no provider transport, output file or event store is touched directly.
- No ACP SDK type appears outside the adapter package.

## Standards

- `arch-standards` §8 Protocol Adapter Boundaries — the governing standard. The adapter translates parameters and serializes results; it owns no domain validation, persistence, state transition, dispatch or provider selection.
- `arch-standards` §1 Dependency Boundaries — wired at the composition root; no graph lookup during request handling.
- `arch-standards` §4 Public Contracts — unsupported stays unsupported; a missing canonical operation is added to its owner, never implemented inside the adapter.

## Acceptance Criteria

- External ACP clients can drive AUDiaGentic-owned sessions.
- The adapter is constructible entirely from fake public ports, importing no concrete store, provider adapter or graph lookup — this is the load-bearing proof, not the behaviour tests.
- Session, task, output and control authorities remain singular; the adapter owns none of them.
- Operations outside the implemented scope return protocol-compliant unsupported results, and nothing is emulated.
- Reads go through the live read surface and controls through the generic control surface — never through provider transports, output files or event stores.
- No ACP SDK type appears outside the adapter package.
- A missing canonical operation is added to its owner, never implemented inside the adapter.

## Notes

Supersedes AS65.

**Hard dependency, not just coordination: this item cannot start before AS94 and AS95 exist**, since it is a thin composition over both — there is no independent read or control mechanism for it to build. Authorization of external callers is deliberately not here — it belongs to AS101 (project isolation), which covers every read and control entry point at once rather than being re-specified per protocol.
