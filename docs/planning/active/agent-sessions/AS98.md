# Codex ACP session surface through the managed bridge

## Description

Expose the Codex ACP harness as a validated gateway session surface with explicit model selection and reasoning effort. Profile model ids use gpt-5.6-luna[low|medium|high|xhigh|max], and the launch adapter translates the suffix into process-local CODEX_CONFIG without mutating user-global Codex settings. Keep the bridge package pinned while the managed auxiliary-install seam remains pending.

## Steps

1. Characterize the installed Codex CLI, the `codex-acp` bridge, the existing launch builder, package ownership, model arguments and ACP initialization.
2. Represent the CLI and the bridge as separately probed managed dependencies through the existing provider lifecycle and toolchain machinery. Add a provider-owned dependency type only if the current typed recipe genuinely cannot express the lifecycle — do not add a generic installer for one consumer.
3. `plan` and `status` mutate nothing. `apply` installs and reconciles the pinned dependencies. `prune` removes only owned packages and preserves unrelated global ones.
4. Production launch resolves managed executable paths and validated versions. It never runs an implicit `npx -y`, never auto-downloads at session start, and never mutates packages during a launch. A missing or mismatched dependency fails with a registered error.
5. Register the surface and its provider-private transport factory. Raw ACP stays private.
6. Prove model fidelity: request two distinct supported model ids and observe the effective model from authoritative bridge evidence. Apply the exact requested model or reject before execution — never record the requested value as effective without proof.
7. Prove two-turn memory, deterministic close and owned process-tree cleanup. Keep resume disabled until the bridge proves it independently.

## Acceptance Criteria

- Codex ACP launches only from managed, validated dependencies.
- Production never performs an implicit `npx -y` or any network installation at session start.
- The requested model is actually applied and reported from authoritative evidence, or the request fails before dispatch. The requested value is never recorded as effective without proof.
- A missing bridge is distinguishable from a missing CLI; prune preserves unrelated packages; apply is idempotent.
- Two-turn memory, deterministic close and owned process-tree cleanup are proven for the exact pinned versions.
- Resume stays disabled until independently proven.
- Codex ACP remains a separate surface and identity from Codex CLI; Codex details stay provider-private.

**Platform-scoped gates replace the original vague "wait until the core lifecycle and ACP proof path are less volatile" (RV923).**

That deferral reason did not survive scrutiny. The adjacent plans show the opposite of volatility: AS89 records ACP resume-by-ref already proven against real `pi-acp`; AS90 states most child supervision is already built and narrows the remaining generic problem to one specific Windows `close()` race; AS97 records OpenCode ACP already has a validated real end-to-end anchor with only behavioural proof coverage outstanding.

There is concrete, isolated work available now.

If this item's initially promoted evidence is Linux, its own proposed Linux Docker fixture proves close and cleanup independently and AS90 need not block closure at all. Only a Windows-platform promotion of that specific acceptance criterion waits on AS90.

**AS97 is coordination, not a dependency** — useful shared common-ACP evidence on control/permission/cancel semantics, but this item should not wait for it.
