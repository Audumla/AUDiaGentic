# Separate queued session work from dispatch-claimed running state

## Description

Correct gateway lifecycle reporting when a request has been dispatch-claimed but is waiting behind another active turn in the same gateway session. A request must remain queued until it owns an executable session turn and provider work has begun.

## Steps

- Identify the queue admission boundary where a request is marked running.\n- Keep queued state while waiting for the session turn lock/serialization gate.\n- Transition to running only after the request owns the turn and provider execution begins.\n- Preserve activity, watchdog, cancellation, and terminal transitions across the queued-to-running boundary.\n- Add session/request diagnostics showing queue position or wait reason without exposing private internals.\n- Ensure one active provider turn per session while allowing unrelated sessions to run concurrently.

## Detailed Solution & Technical Design

The live reproduction shows req_e0b45a76b0254f83 was marked running immediately after dispatch claim, with activity sequence 0, while req_dbb511cb377b4823 was actively processing the same session ses_7c836144483a4df6. Separate dispatch ownership from execution ownership: the queue may claim a worker/request for durable progress, but the request lifecycle remains queued until the session scheduler grants the turn slot. The session turn runner should emit an explicit turn-start transition at the point it acquires the per-session execution gate and is about to call the provider. Watchdog policy must treat queued waits as admission waiting, not provider inactivity; cancellation must remove queued work without sending a provider stop unless the turn actually started. Public status can remain queued with bounded wait metadata, while protected diagnostics retain dispatch-claimed and turn-start timestamps.

## Validation

Verify a request on a different session can run concurrently. Test queued cancellation, watchdog behavior while queued, turn-start timestamp/activity sequencing, restart recovery, and terminal transitions. Assert dispatch-claimed is not sufficient for running.

## Effort & Risk

Medium/high: changes lifecycle semantics and watchdog interpretation; must preserve durable worker ownership and avoid falsely reporting queued work as stalled.

## Standards

AS92 lifecycle semantics; session turn serialization; bounded public status; protected diagnostics.

## Acceptance Criteria

- A dispatch-claimed request waiting on a busy session is reported queued.\n- Running begins only after session turn ownership/provider start.\n- Queued waits do not generate provider inactivity failures.\n- One session cannot execute two provider turns concurrently.\n- Different sessions remain independently schedulable.\n- Cancellation and restart recovery remain correct.
