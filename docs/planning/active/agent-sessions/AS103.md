# Cursor and control-token integrity for paged reads

## Description

Make paged reads fail clearly on a malformed, stale or mismatched cursor, so a caller can distinguish a service restart from a bad request.

**Rescoped 2026-08-05 after the deployment model was stated: local, internal, non-hostile users, not externally facing.** This item previously specified tamper-evident cursor tokens and replay-safe control keys. Against a non-hostile local caller there is nothing to make tamper-evident — signing a cursor defends against an attacker this deployment does not have, and `arch-standards` §3 forbids building for requirements that do not exist.

What survives is the robustness half, which was always the genuinely useful part: a cursor that no longer means what the caller thinks should produce a clear typed error or a deterministic gap, never silently wrong data.

## Steps

1. Reject malformed and oversized cursors before parsing, with a registered code.
2. Distinguish the failure modes with distinct codes so a caller can act on them: malformed input, a generation that no longer matches (service restarted), and a cursor belonging to a different request/session/turn.
3. Keep the deterministic-gap behaviour for the restart case. A valid cursor from a prior generation is a normal, expected outcome on a shared long-lived gateway — it returns a gap, not an error.
4. Bound page size and cursor length.

## Detailed Solution & Technical Design

Deliberately **not** in scope, with the reason recorded so it is not re-added by habit:

- Cursor signing, HMAC or any tamper-evidence mechanism.
- Replay protection on control idempotency keys.
- Any foundation crypto/integrity seam introduced for this purpose.

All three defend against a caller forging or replaying a token. The stated deployment has no such caller. If the gateway ever becomes externally facing, raise that as its own item against that requirement.

The idempotency keys themselves stay — they prevent *accidental* double-dispatch on retry, which is a real failure mode with cooperative callers. It is only the anti-replay hardening that is dropped.

## Validation

- A malformed or oversized cursor is rejected before parsing, with a distinct registered code.
- A cursor from a prior generation returns a deterministic gap, not an error — this is the common case after a gateway restart and must not surface as a failure.
- A cursor naming a different request, session or turn is rejected with its own code, distinguishable from the restart case.
- Page size is clamped.
- No signing or integrity mechanism was added.

## Effort & Risk

Small. The risk is scope creep back toward integrity machinery — the Detailed Solution's exclusion list is the control.

## Standards

- `arch-standards` §3 Ownership and Abstraction — one integrity mechanism, not one per surface.
- `arch-standards` §4 Public Contracts — distinct registered codes for distinct failures.

## Acceptance Criteria

- Malformed, stale and mismatched cursors each produce a distinct, registered, actionable outcome.
- The restart case remains a deterministic gap rather than an error, preserving the behaviour the read surfaces depend on.
- Page size and cursor length are bounded.
- No cursor signing, HMAC or replay-protection mechanism exists — asserted by absence, since the temptation is to add it "while we're here".
- Idempotency keys still prevent accidental double-dispatch.
