# Expose capability-gated external session controls

## Goal

Expose validated AS19/AS29 generic session controls through the shared gateway application/client/MCP surface without provider-native commands, provider-name branches, or a second lifecycle/control authority.

## Dependencies

- AS19 typed control actions, idempotency, and dispositions;
- AS29 immutable generic capability snapshot and handler registration;
- AS30 binding/project/context/ownership authorization;
- AS21 terminal/reuse authority;
- validated provider handlers such as Pi RPC AS41/AS44 or Codex App Server AS51;
- AS57 read surface for clients that need to observe results.

## Discoverable capability snapshot

Expose a redacted per-session capability view derived from the frozen AS29/AS30 snapshot. Include generic family/action, supported/unsupported state, maturity/evidence level, bounded constraints, and ownership/topology limits. Exclude adapter refs, commands, config paths, raw native names, provider refs, tokens, and unvalidated candidate actions.

Capabilities do not change during a session generation. A stale client snapshot cannot force an unsupported action; dispatch revalidates against the binding's frozen snapshot.

## External request contract

Define typed requests for only accepted generic actions, initially as proven:

- cancel turn;
- interrupt turn;
- steer turn;
- respond to correlated permission;
- close/detach session;
- queued follow-up where AS44 is implemented;
- optional state/inspection reads remain read operations, not controls.

Each request includes canonical project/session/turn/request identity, client control ID, action, and closed bounded payload. No native command/payload escape hatch.

## Authorization and topology

Validate:

- authenticated active gateway client lease;
- canonical project root;
- exact AS30 session generation/binding;
- requested turn/current-turn relationship;
- ownership mode and whether action is legal for owned/adopted/external topology;
- exact frozen AS29 capability and validated provider handler;
- outstanding correlated permission request where applicable;
- payload size/type and policy.

Cross-project, stale generation, wrong binding, provider-ref guessing, and unauthorized external attachment controls fail before provider dispatch.

## Dispatch and idempotency

Use one agents application service that dispatches typed action through `providers_api`/the authoritative live transport. Persist or index idempotency by `(binding/session generation, turn, action, client-control-id)` using existing durable request/idempotency primitives if restart semantics require it.

Return canonical accepted, unsupported, already-terminal, rejected, uncertain, and authorization/conflict errors. Repeated requests return the original result. Do not retry uncertain provider submissions automatically.

## Lifecycle and audit

A control result is an acknowledgement only. It cannot terminalize SH07/session state, release locks/queue slots, mark session reusable, or fabricate output. Subsequent AS19 evidence and durable authorities determine effects.

Record bounded redacted audit/timeline facts: AG IDs, generic action, disposition, timestamp, actor/client lease ID, policy/authorization result, and stable error code. Never record native command/payload, raw provider ref, permission secret, steering/follow-up content beyond the existing protected request record policy, or provider raw response.

## Provider rollout

Start with fake transports and independently validated Pi RPC/Pi ACP capabilities. Enable real Pi actions only after AS40/AS41/AS44 proof; Pi ACP remains unsupported where not proven. Codex App Server actions use AS51 proof. No adapter is selected by provider name in agents; AS29 factory/handler registration controls dispatch.

## Service/client/MCP parity

Add matching closed operations to gateway application, service transport, client, and MCP schemas. All surfaces return the same canonical result and authorization behavior. A capability read may show unsupported actions, but invoking one returns explicit unsupported without side effect.

## Validation

- capability snapshot redaction/immutability;
- authorized accepted action through fake transport;
- unsupported, already-terminal, rejected, uncertain, malformed, stale, and unauthorized cases;
- cross-project/binding/generation/turn rejection;
- idempotent duplicate and restart behavior;
- permission correlation/default-deny;
- owned/adopted/external close/detach semantics;
- topology/loopback policy;
- API/client/service/MCP parity;
- acknowledgement never changes lifecycle or releases work;
- no provider-native values above adapters;
- real actions enabled only after exact platform/version probe.

## Acceptance criteria

- External clients discover and invoke only generic validated actions.
- One authoritative transport/provider handler executes each control.
- Unsupported actions fail explicitly without fallback.
- Audit is bounded/redacted.
- Controls remain separate from lifecycle evidence and terminal authority.
