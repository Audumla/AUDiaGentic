# Select a role at job submission and carry its manifest to the worker

## Description

Let a submitted job name a role, resolve it into a launch manifest once at the authoritative boundary, persist its identity and fingerprint with the request, and have the worker materialize exactly that manifest.

The single defect this item exists to prevent: **resolving twice at different boundaries produces drift.** The manifest is resolved once and then transported — through the request record, through retries, through resume, into the worker. Nothing downstream re-derives it.

## Steps

1. Add an optional `agent-role-id` to the submission contract and events. Implement the precedence rule already documented in `config/components/agents.yaml`'s `agents/role-precedence` contribution: explicit `agent-role-id` first, then the role carried by `agent-id`; execution-profile selection composes independently rather than overriding.
2. Resolve the manifest once, at the authoritative boundary, before dispatch. Carry the manifest and fingerprint through the request record.
3. Have the worker enable only what the manifest declares.
4. Put role identity and manifest fingerprint on lifecycle events and timelines — identity and fingerprint, never the full manifest.
5. Add a documented, explicitly temporary default for callers that supply no role, naming the policy-gates item as the owner of its removal.
6. A role requirement contradicting an explicitly selected Execution Profile fails before dispatch, per the already-published precedence doctrine.

## Validation

- A role-submitted job executes with exactly its resolved capability set, verified from a different process than the one that submitted it.
- Retry and resume reproduce the same manifest — asserted by equality of fingerprint and effective capability set, not by the job merely succeeding.
- The capability set is derived once. An automated check proves no second derivation site exists.
- Conflicting explicit profile and role requirements fail before dispatch, not at launch.
- Role resolution is independently testable without MCP.
- MCP and event adapters only translate parameters and call the public API.
