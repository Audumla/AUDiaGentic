# Per-agent-profile prompt templates replacing hardcoded default_build_prompt

## Description

src/audiagentic/components/providers/adapters/base_runner.py:91-110 (`default_build_prompt`) hardcodes the prompt sent to every `mode: cli` provider with no custom adapter.py (pi is the current example) as an f-string: job-summary framing text followed by an optional 'Prompt body: {prompt_body}' suffix. This is not configurable per agent profile and not easy to edit without a code change. Replace it with a templated prompt keyed to the agent profile, reusing the repo's existing templating primitive instead of inventing a new one.

The repo already has exactly the machinery needed: src/audiagentic/foundation/templates.py::render_template(template: str, context: dict) -> str is a custom regex-based `{dotted.path}` placeholder renderer (not str.format/Jinja2/string.Template) already used for prompt generation via src/audiagentic/components/agent_jobs/prompt_templates.py, which wraps it as render_prompt_template(template_text, values) and additionally provides the file-loading convention: load_prompt_template(project_root, *, tag, provider_id, template_name=None) resolves project-local .md overrides under .audiagentic/prompts/<tag>/... with a packaged-template fallback via load_packaged_prompt_template, and load_prompt_from_file(project_root, template_path, source_label="") loads an explicit path with containment safety. Reuse this exact stack — do not build a second templating/loader mechanism.

## Steps

1. Add an optional `prompt-template` field to the agent-profile schema (.audiagentic/config/agent-profiles.yaml profiles[].prompt-template — a template tag/name, following the same tag convention load_prompt_template already uses for agent-job prompts). Absent/null means use the packaged default template (see step 2) — this must reproduce today's behavior exactly, not a new default.
2. Author the packaged default template as a real template file (not another hardcoded f-string) whose rendered output is byte-identical to today's default_build_prompt for the same inputs. Store it wherever load_packaged_prompt_template's convention expects packaged templates to live (check agent_jobs/prompt_templates.py's actual packaged-lookup path before picking a location — reuse it, don't invent a parallel packaged-template directory). Placeholders needed: {title}, {job-id}, {packet-id}, {provider-id}, {model}, {workflow-profile}, {prompt-body}. NOTE: today's function only appends the ' Prompt body: ...' suffix when prompt_body is truthy; render_template has no conditional syntax (None -> empty string per its own contract) — resolve this discrepancy explicitly (e.g. two packaged template variants selected by whether prompt_body is present, or accept a harmless trailing 'Prompt body: ' when empty and confirm no test currently depends on the old exact-absence behavior) rather than silently changing behavior. Add a regression test asserting default-template output is byte-identical to the current hardcoded output for representative inputs (including prompt_body present and absent).
3. Add the project-local override path using the SAME load_prompt_template(project_root, tag=..., provider_id=..., template_name=...) convention already established for agent-job prompts, so provider execution prompts and agent-job prompts share one override mechanism/directory convention rather than a second one.
4. In base_runner.py, replace default_build_prompt's f-string body with: resolve the active agent profile's prompt-template (falling back to the packaged default), build the substitution context dict from packet_ctx/provider_cfg, call render_prompt_template(template_text, context), return the result. Verify FIRST (do not assume) whether packet_ctx already carries the resolved agent profile id at the point this runs, or whether that needs threading through from gateway dispatch / providers_api.execute_provider_turn — trace the actual call chain before wiring this up.
5. Add tests: (a) default/no-override profile produces byte-identical output to the pre-change hardcoded function (the regression test from step 2); (b) a profile with a custom prompt-template renders using that template instead; (c) a custom template referencing an undefined placeholder surfaces render_template's existing VAL-TPL-001 error clearly rather than crashing opaquely; (d) missing/absent prompt-template on a profile falls back cleanly.
6. Update docs describing agent-profile fields to mention prompt-template and point at the packaged default + override location.

2026-07-20 design discussion (user + Claude) — templating-engine choice, decided:
- Do NOT consolidate foundation/templates.py's render_template (dotted-path, string-coercing, used for prompt text) with foundation/workflow/actions.render (whole-placeholder typed-value-preserving, full str.format semantics, used for workflow action config substitution). That consolidation was already evaluated and deliberately stopped under EDJ21, guarded by tests/unit/foundation/test_actions_render_compat.py's characterization tests. AG16 should just consume render_template/render_prompt_template as-is, matching the existing agent-job prompt pattern — do not reopen the EDJ21 decision.
- Do NOT adopt a general third-party templating library (e.g. Jinja2) for this item. Both existing renderers have committed behavioral contracts (typed-value passthrough; structured AudiaGenticError/VAL-TPL-001 on missing path) that a stock library doesn't map onto without a wrapper layer anyway, and this item's actual gap (no conditional support for the optional 'Prompt body:' suffix, see step 2) doesn't need a full template language to solve — handle it narrowly (two template variants selected by presence/absence, a small targeted conditional extension, or resolving it at the Python call site before rendering).
- FORWARD-LOOKING CONSTRAINT (user, 2026-07-20): a proper templating library is expected to be adopted at some later stage across this templating surface generally (not scoped to AG16 specifically) — so AG16's implementation must keep the templating usage behind a clean, narrow seam: call sites should go through render_prompt_template/render_template's existing function-call boundary only, pass a flexible/open context dict (not a fixed hardcoded set of named parameters baked into base_runner.py's call site), and avoid coupling any call site to render_template's specific regex/placeholder-syntax internals beyond what's already exposed by its public API. The goal is that swapping the underlying renderer later is a contained, single-module change, not a call-site-by-call-site migration. Do not build any library-swap abstraction now beyond this — just avoid closing off the option.
