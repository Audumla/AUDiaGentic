# Aggregate agent profiles: pool multiple agents to fulfill requests from any available member

## Description

Extend agent profiles to support aggregation: a single aggregate profile groups multiple sub-profiles (e.g., three instances of mid-coder at different concurrency limits, or a mix of lite-coder + mid-coder + supp-coder). A request submitted to an aggregate profile can be claimed and fulfilled by ANY free member of the pool. If all members are busy, the request queues globally across the pool; as soon as any member becomes free, it picks up the next queued request, regardless of which member was specified or which other members are still busy. This provides implicit load-balancing and resilience: if one agent profile is saturated, requests spill over to siblings automatically without caller involvement.

Observed need 2026-07-20: discovered that long-running implementation tasks (SH08 Slice A rewrite) timeout at the gateway's 280s boundary, and orchestrating multiple retries or fallbacks across named profiles requires explicit caller logic. An aggregate profile would handle that implicitly: if mid-coder times out mid-work, the request could auto-spill to lite-coder or supp-coder without losing progress tracking, since all three are 'equivalent' (same provider, model family, just different resource/concurrency classes).

## Steps

1. Deeper analysis FIRST (do NOT implement yet) — determine whether this belongs in the agent-profile layer, the gateway queue/dispatch layer, or the job-orchestration layer. Options: (a) aggregate as a profile variant in .audiagentic/config/agent-profiles.yaml with a members: [list] field, routing decided at submission time; (b) aggregate defined at gateway queue manager level (pools of execution lanes sharing a name), routing decided inside the queue; (c) aggregate as a job-orchestration / job-controller feature where an aggregate job request spawns sub-jobs against each member and winner-takes-all. Each has different implications for persistence, recovery, concurrency limits, and caller visibility.
2. Document the desired semantics: if a request is submitted to an aggregate and member A claims it but times out, does the same member auto-retry, does it fail over to member B, or does it require a new submission? What happens to partial work (file edits, git commits) if the request fails over mid-task? How does the caller see which member actually completed the work?
3. Prototype or design the schema changes: profile records, queue/lane records, job records — what fields are needed to track 'this request came from an aggregate' and 'this work was completed by member X of aggregate Y'?
4. Evaluate against the existing gateway concurrency/lane/dispatch model: is aggregation orthogonal to lane-keyed queues (SH07 C2) or does it interact with them in ways that complicate the model? Does it require changes to the GatewayExecutionLaneKey or admission policy?
5. Implement against the chosen design: schema updates, dispatch logic, queue manager logic, tests proving load-balancing and resilience behavior.
