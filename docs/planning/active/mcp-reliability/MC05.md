# Replace Git fingerprint with process identity in Agents status hook

## Description

The Agents status hook computes a runtime fingerprint by spawning `git rev-parse`. This was designed for gateway diagnostics (SH15) to detect whether a live MCP process needed restarting after code changed.

Problems:

- Runs git inside a status request — causes Pi timeouts in Git-heavy repos
- A Git commit doesn't prove the process restarted
- Fails in non-Git environments (wheel installs, containers without .git, non-Git projects)

Recommended replacement identity:

```
{
  "runtime-version": "0.1.1",        // from package metadata
  "build-id": "optional-packaged-build-id",  // embedded at build time, never reads Git
  "process-instance-id": "generated-at-startup",
  "started-at": "2026-07-23T03:17:00Z",
  "owner-epoch": 4
}
```

This answers: which build is installed? Is this still the old running process? Did ownership transfer or restart? When did it start?

['Remove _git_source_stamp() and its Git dependency entirely', 'Add process-instance-id generated at gateway startup (not during status calls)', 'Add started-at timestamp at gateway startup', 'Add runtime-version from package metadata', 'Define build-id contract (optional, embedded at wheel/container build time)', 'Expose process identity and owner-epoch in gateway status', 'Test wheel install, source checkout, non-Git project, and container environments']

## Detailed Solution & Technical Design

### Original design (SH15) — why it was wrong

The original shape was:

```
{
  "version": "0.1.1",
  "source-stamp": "372ba71d56e4"
}
```

The stated purpose: detect that a live MCP process needed restarting after code changed.

Two fundamental flaws:

1. **Ran `git rev-parse` inside a status request** — blocks the status path with a subprocess
2. **A Git commit doesn't prove the process restarted** — if the repo is dirty, `rev-parse` returns the same SHA even though the live code changed
3. **Non-Git environments fail**: wheel installs, non-Git projects, containers without `.git`, other project subdirectories

### Replacement identity model

```
{
  "runtime-version": "0.1.1",           // from package metadata (importlib.metadata)
  "build-id": "optional-packaged-build-id",  // embedded at wheel/container build time, never reads Git at runtime
  "process-instance-id": "generated-at-startup",
  "started-at": "2026-07-23T03:17:00Z",
  "owner-epoch": 4                       // existing managed-service ownership generation
}
```

### Field semantics

- **runtime-version**: installed package version from `importlib.metadata.version("audiagentic")`. Always present.
- **build-id**: optional immutable identifier embedded when the wheel/container is built. May be a commit hash in CI, but **runtime code never invokes or reads Git**. Absent for local/sourced installs — that's fine.
- **process-instance-id**: random UUID generated once when gateway starts. Proves whether this is still the same running process (if it changes, the process restarted).
- **started-at**: ISO timestamp from `datetime.now(timezone.utc)` at gateway startup. Combined with process-instance-id, answers "did it restart?"
- **owner-epoch**: existing managed-service ownership generation counter. Answers "did ownership transfer?"

### What this answers (operationally)

1. Which build is installed? → runtime-version (+ build-id if available)
2. Is this still the old running process? → compare process-instance-id and started-at
3. Did ownership transfer or restart? → owner-epoch change + instance-id change
4. When did it start? → started-at

### Build-id contract

- Optional field — wheel installs from PyPI may not have one
- CI pipeline can embed `build-id` via PEP 639 or custom metadata at build time
- Runtime never reads Git — only reads embedded metadata if present
- Remove the requirement that source-stamp is always 12 hex characters

### Test environments

1. **Wheel install**: runtime-version valid, build-id may be absent, no Git subprocess
2. **Source checkout**: runtime-version from editable install, no Git subprocess
3. **Non-Git project**: runtime-version valid, no Git errors
4. **Container without .git**: runtime-version valid, no Git subprocess
