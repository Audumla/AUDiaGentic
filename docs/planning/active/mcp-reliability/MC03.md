# Improve MCP startup and timeout diagnostics

## Description

Pi currently reports generic server-unavailable or MCP -32001 timeout results. Improve diagnostics to identify:

- Server name
- Command and module identity without secrets
- Initialization versus tool-call phase
- Elapsed time
- Process exit status
- Whether stderr was captured

Diagnostics must remain out of the model-visible result when they could expose paths or credentials.

## Steps

['Add server-name identification to error diagnostics', 'Include command/module identity (redacted) in safe diagnostics', 'Distinguish initialization vs tool-call phase failures', 'Add elapsed time and process exit status to diagnostics', 'Capture stderr in diagnostics log (not model-visible)', 'Verify no path or credential leakage in user-facing output']

## Detailed Solution & Technical Design

### Key fact that shapes this design

AUDiaGentic never spawns or supervises configured MCP servers live. `component_mcp_launch()` (foundation/mcp/launch.py) only returns the argv tuple written into mcp.json / OPENCODE_CONFIG_CONTENT; the harness (pi or opencode, a third-party process) spawns and owns the JSON-RPC connection at session time. The generic 'server unavailable' / MCP -32001 errors originate inside the harness's own MCP client and are opaque to us from outside a live session -- AUDiaGentic cannot retrofit instrumentation onto a connection it doesn't hold.

So diagnostics cannot be 'wrap the existing launch' -- they require a new, first-party preflight/health-check capability: AUDiaGentic spawns each configured server command itself, speaks the MCP stdio handshake, and observes it directly. This is what actually produces the phase/timing/exit-status data MC03 wants; it then gets surfaced (a) proactively before writing a server into the harness config, and (b) reactively as a diagnose command when a user/agent hits a generic harness-side error.

### Module placement (one shared implementation, not per-provider)

New `foundation/mcp/diagnostics.py`:
- `McpLaunchDiagnostic` dataclass: `server_name`, `phase` (`"initialization" | "tool-call"`), `elapsed_ms`, `process_exit_status`, `stderr_captured: bool`, `error_class` (generic, stable taxonomy: `spawn-failed`, `initialize-timeout`, `initialize-rejected`, `crashed`, `ok`).
- Internal-only counterpart carries `command` (redacted), `module_identity`, `stderr_tail: list[str]` (last N lines) -- never constructed into the model-visible result.
- `probe_mcp_server(command: Sequence[str], *, cwd, env, timeout) -> McpLaunchDiagnostic`: spawns via the existing `supervised_process.spawn_supervised` (same primitive agents_gateway_worker.py already uses for descendant-tree safety), writes the MCP `initialize` request to stdin, reads stdout until a JSON-RPC response with matching id arrives or timeout elapses, records elapsed time and exit status on failure, tears down via `SupervisedProcess.close()`.
- Phase boundary is exactly the `initialize` response: failing before it is `initialization`; a later timeout on an actual tool call (only reachable if a caller drives one) is `tool-call`.
- Redaction: reuse the same discipline as `mcp_exclusive_patch.py`'s anchor-based rigor -- an explicit denylist of flag patterns (`--api-key=`, `--token=`, `Authorization:`, etc.) plus a generic `KEY=value` env-var scrubber, applied only when constructing the internal `command` field; the model-visible result never carries argv or env at all.

### Provider adapters supply only identity, not protocol logic

`components/providers/adapters/{pi,opencode}/mcp_surface.py` gain a thin `diagnose_mcp_surface(surface_request) -> list[McpLaunchDiagnostic]` that iterates the resolved `McpLaunchServerEntry` list and calls the shared `probe_mcp_server` once per entry -- no provider reimplements the handshake or timing loop.

### Entry points

1. Proactive: `providers_api` gains a narrow `diagnose_provider_mcp_servers(project_root, provider_id)` a caller (CLI command or MCP tool) can invoke before/independent of a harness launch.
2. Reactive: when a harness session reports a generic MCP failure back through the agents gateway, the gateway can attach a one-shot diagnostic run for the implicated server_name so the user gets 'ag-planning failed during initialization after 15230ms, exit -9' instead of a bare -32001.

### What this explicitly does NOT do

No attempt to instrument or parse the harness's own live stdio traffic -- that would require either patching the harness (out of scope, unlike the narrow mcp-exclusive patch which touches CLI argument parsing, not protocol traffic) or a proxying MCP layer between harness and server (a much larger, unproposed architecture change). This proposal is deliberately scoped to preflight/reactive probing only.
