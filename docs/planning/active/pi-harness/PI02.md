# Resolve installed Pi adapter version ambiguity

## Description

The system-global adapter observed during diagnosis was 2.10.0. Pi's private agent package contained 2.11.0. Resolver precedence must be explicit and tested. Avoid silently patching one copy while Pi loads another.

Status output should report which adapter path and version Pi actually loaded.

## Steps

['Document resolver precedence for pi-mcp-adapter', 'Test that patched version matches loaded version', 'Add adapter path and version to status output', 'Prevent silent version mismatch between patched and loaded copies']

## Detailed Solution & Technical Design

### Observed problem

- **System-global adapter**: 2.10.0 (found via `pip show pi-mcp-adapter` or similar)
- **Pi's private agent package**: 2.11.0 (bundled within Pi's node_modules)
- Which one does Pi actually load? Currently ambiguous.
- Risk: AUDiaGentic patches the system-global copy, but Pi loads its own bundled copy — patch has no effect.

### Resolver precedence — needs explicit documentation

```
1. Pi's private node_modules (bundled with Pi installation)
2. System-global pip package (if Pi falls back to PATH resolution)
3. Explicitly configured adapter path (via AUDIAGENTIC env vars, if supported)
```

This order must be documented and tested. The current behavior may vary by Pi version and installation method.

### Status output requirements

Status output should report:

- **Adapter path**: full filesystem path to the loaded pi-mcp-adapter (e.g., `/home/user/.pi/agent/node_modules/pi-mcp-adapter`)
- **Adapter version**: exact version string (e.g., `2.11.0`)
- **Resolver used**: how this adapter was discovered (bundled, system-global, explicit)

### Version mismatch test

```
1. Determine which copy Pi actually loads (inspect resolved path)
2. Compare with the copy that AUDiaGentic patches
3. If they differ, report a warning or error
4. Ensure patches apply to the correct copy
5. Test that patched behavior is actually active in Pi runs
```
