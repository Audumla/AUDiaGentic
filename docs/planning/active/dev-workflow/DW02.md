# Move git and forge access from foundation to the source_control component

## Description

`foundation/system/git.py` (310 lines of git operations: worktrees, branches, refs, bundles, merge, ancestry, fetch) and `foundation/system/forge.py` (GitHub pull-request reads and three writes through `gh`) are external-tool integrations, not base-level reusable capability. Foundation is for domain-neutral primitives (contracts, events, paths, logging, workflow); `system/` must not become a utilities folder (foundation README). Move both into `components/source_control/` and expose them through an approved platform public API, `source_control_api`, which `project/worktrees` calls. Several other components already shell out to git on their own (agents `code_drift`, release `local_release`, project `runtime/install`, ledger `conversion`, source_control `git_commits`, foundation `paths/project`), which is the independent-consumer evidence for one shared owner. Migrating those is out of scope here; each becomes its own follow-up.

## Steps

1. Define the API first. Group the worktree flows' needs into a small set of cohesive Git-owned operations in `source_control_api` (inspection, refs and history, safety checks, worktree and ref mutations, fetch and publish, merge, bundle preservation) and forge operations (repository identity, PR read and list, PR create, title edit, auto-merge). Keep the ~30 low-level helpers internal. Never expose `run_git`: the two direct callers (`merge-base`, `bundle list-heads`) get named, bounded operations. Returned types (`PullRequest`, `RepositoryIdentity`, worktree entry) are part of the public contract and must not require importing source_control internals. Worktree eligibility, rollback, lifecycle sequencing and removal policy stay in `project`.
2. Fix the drain-fence authority (see Notes) before moving anything: one shared storage location for writers and readers, a worktree-neutral name, marker identity unchanged or migrated.
3. Record the approval in the Approved cross-component APIs table. The existing `source_control_api.py` already serves repository context, dependency status and install/uninstall, and the gateway admission-context code uses it, so the entry must describe the module's real contract, or a new narrow public module must be approved. Use the component identifier `source-control` in configuration and ownership references, and `source_control` only as the Python package name.
4. Move `git.py` and `forge.py` into the component as internal modules. Keep the stable codes `EXT-GIT-*` and `EXT-FORGE-*` unchanged: the factory's third argument is the public error kind, `source_control` is invalid there (underscores are prohibited), and `source-control` would change the emitted error envelope. Decide explicitly whether to change the kind. Move all nine resolution entries to `src/audiagentic/config/components/source-control/error-resolutions.yaml`.
5. Point the 11 `project/worktrees` modules and their 10 test files at the API, including monkeypatched test seams. Delete `foundation/system/git.py` and `forge.py` in the same change: no alias, re-export or shim.
6. Rewrite the source_control README to state that it owns git and forge access.
7. Correct DW01's Standards sentence and docs/guides/WORKTREES.md.
8. Add an AST-based architecture check (standard 7): foundation imports no component; every import of `source_control_api` comes from a permitted layer; no component imports source_control internals; no form of the removed foundation import remains, including `from audiagentic.foundation.system import git, forge`; no re-exports or shims; existing source_control consumers stay permitted.

## Acceptance Criteria

- `foundation/system/git.py` and `forge.py` are gone, with no alias, re-export or shim, under any import form.
- `source_control_api` exposes a bounded set of cohesive operations, not `run_git` or the ~30 raw helpers, and its returned types import nothing from source_control internals.
- The Approved cross-component APIs entry describes the module's actual contract, with owner, permitted callers and boundary; `source-control` is the component identifier in config and ownership references.
- Error codes `EXT-GIT-*` and `EXT-FORGE-*` are unchanged; all nine resolutions live in the source-control resolutions file; `test_error_resolutions.py` passes; any change to the emitted error kind is an explicit, recorded decision.
- One authoritative drain-fence location is used by both writers and the MCP resolver; the fence is worktree-neutral, stays in foundation (not source_control) or at a composed boundary covering every entry point, and is covered by tests for alternate state roots, interrupted removal, retained fences and MCP rejection.
- The AST architecture check exists and passes.
- Git and forge error semantics, unknown-state refusal and all worktree behaviour are unchanged, including monkeypatched test seams.
- The source_control README and DW01 and WORKTREES.md match the new ownership.
- Remaining direct git users are recorded as follow-ups (below).

## Notes

Design points to settle before coding, and to put to GPT for review:
- `worktree_drain.py` is imported by `foundation/mcp/worktree.py` (the resolver every MCP call goes through). Foundation may not import a component, so the drain marker either stays in foundation as a generic path fence (rename it, it is not git-specific) or the resolver takes the check as an injected seam. Recommend keeping the marker in foundation under a neutral name; confirm it passes the domain-neutral test.
- API shape: the standards want a narrow surface, not a catalogue. git.py has about 25 helpers and forge.py a few; group by the worktree flows' needs and keep the rest internal.
- Other git users (agents code_drift, release local_release, project runtime/install, ledger conversion, foundation/paths/project) are follow-up items. Do not widen this one.
- DW01's Standards line 'foundation owns the git/process/locking mechanics' contradicts the standards docs and is corrected here.
- Backward compatibility is not maintained: update every caller and delete the old modules in the same change.

GPT design review (reviewer-gpt-agent, 2026-11-05): direction approved; two P1s and four P2s, all folded into the steps and acceptance criteria above.

P1 drain fence: `finish()` accepts `state_root` and writes the marker there, while the MCP resolver checks the default user-state directory, so a fence written under another root is invisible to the resolver. This was found by the reviewer and must be verified in code before relying on it. Renaming alone does not satisfy standard 3: remove the worktree-specific responsibility or keep it as a generic path-admission primitive. Do not move it into source_control: worktree admission policy belongs to project, not git transport. Injection must not hide a forbidden dependency.

P1 API size: the flows use almost the whole git helper set. Prefer a smaller number of cohesive operations; the API exposes git and forge capability and must not become a second worktree orchestration service.

Follow-ups, out of scope here: agents/gateway/service/code_drift.py, release/local_release.py, project/runtime/install.py, ledger/conversion.py, ledger/current_events.py and source_control/git_commits.py. One exception needs a decision: `foundation/paths/project.py` calls git for checkout discovery and HEAD inspection. DW02 therefore does not remove every git subprocess from foundation; moving those functions into a component would reverse the dependency direction, so it needs a bounded documented exception or a separate migration design.

Backward compatibility is not maintained: update every caller and delete the old modules in the same change.

Verified after the review: `finish()` takes `state_root` (default `user_state_dir()`) and passes it to `worktree_drain.begin/end` (finish.py lines 276, 303, 353, 423), while `foundation/mcp/worktree.py:59` calls `is_draining(resolved)` with no state root. In production the two agree because the default is the same directory; they diverge only when a caller passes an explicit `state_root`, as tests do, so the fence is untested against the real resolver. The fix is still required: one shared storage location, not a parameter that can disagree.
