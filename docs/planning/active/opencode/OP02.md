# Prove OpenCode ACP isolation capabilities

## Description

Prove OpenCode ACP isolation capabilities:

- Pin tested OpenCode and bridge versions
- Verify whether the bridge supports exact config-home isolation for every launch
- Test ambient/global MCP sentinels
- If exact isolation cannot be guaranteed, report unsupported before launching rather than silently using an additive surface

## Steps

['Pin OpenCode and ACP bridge versions in tests', 'Test exact config-home isolation for every launch', 'Test ambient/global MCP sentinels', 'Implement fail-closed reporting when exact isolation cannot be guaranteed']

## Detailed Solution & Technical Design

### Pin tested versions

- **OpenCode**: pin the exact version tested (e.g., `opencode@0.8.2`)
- **ACP bridge**: pin the exact bridge version that connects OpenCode to the ACP protocol
- These pins go in test configuration, not just CI — they should be reproducible locally

### Exact config-home isolation test

Does every OpenCode ACP launch get its own isolated config-home?

```
1. Set up a known MCP server in the global/default OpenCode config
2. Launch OpenCode ACP with `exclusive=true` (or equivalent) pointing to a clean config-home
3. Verify the job does NOT see the globally-configured MCP server
4. Verify the job only sees MCP servers from its isolated config-home
5. Repeat with multiple concurrent launches — each should be isolated
```

### Ambient/global MCP sentinel test

```
1. Place a known sentinel MCP server in OpenCode's global config (e.g., `~/.opencode/mcp.json`)
2. Launch an isolated OpenCode ACP session with a clean ephemeral config
3. Verify the sentinel is NOT contacted or visible to the job
4. If the sentinel IS visible, exact isolation is broken — report as unsupported
```

### Fail-closed when isolation cannot be guaranteed

If testing reveals that OpenCode's bridge does NOT support exact config-home isolation:

1. Mark the provider's isolation capability as `unsupported` in its capability declaration
2. Before launching an isolated job, check the capability
3. If `exact` isolation is required but provider reports `unsupported`, reject the job with a clear error
4. Do NOT silently fall back to additive (non-isolated) mode — the user must know

### What "additive surface" means

If OpenCode always adds global MCP servers on top of request-specific ones, that's an **additive** model — not exact isolation. This is a capability gap, not a bug. It just needs to be reported honestly rather than silently used.
