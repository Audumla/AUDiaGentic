# Measure OpenCode resource cost separately from correctness

## Description

OpenCode remains usable but is heavier than Pi in memory and context usage.
Keep Pi as the preferred lightweight agent harness where it passes capability requirements.
Do not encode preference as provider-name branching; express it through capability and resource evidence.

## Steps

['Measure OpenCode memory and context usage separately from correctness tests', 'Document resource cost evidence in provider capability reference', 'Express harness preference through capability/resource evidence, not provider-name branching']

## Detailed Solution & Technical Design

### Why measure separately?

OpenCode remains usable but is heavier than Pi in memory and context usage. Resource cost is an operational concern, not a correctness concern — measure it independently so we can make informed trade-offs.

### What to measure

- **Memory footprint**: baseline memory per session, peak during active turns, steady-state
- **Context window usage**: how much of the model's context window OpenCode consumes per turn vs. Pi
- **Startup time**: time from launch to first tool call available
- **CPU utilization**: during idle and active periods

### Expressing preference through evidence, not branching

```
// BAD — hardcoded provider-name branching:
if provider == "opencode":
    prefer_pi_for_lightweight_tasks()

// GOOD — capability/resource-based:
if job.resource_budget < provider.resource_cost("opencode"):
    select_provider_with_resource_fit()
```
