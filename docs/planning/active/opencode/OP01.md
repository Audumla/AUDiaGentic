# Complete HA01 OpenCode ownership migration

## Description

Complete HA01 OpenCode ownership migration. Runtime still contains OpenCode install/materialization and runner code.

Classify every mutation as:

- executable/runtime asset
- provider config
- model projection
- managed MCP
- generated surface
- user-owned content

Provider adapters should own OpenCode serialization and launch mechanisms.
Runtime should compose approved public provider APIs and retain only harness lifecycle assets.
Remove duplicate writers and compatibility fallbacks after migration.

## Detailed Solution & Technical Design

### Classification of every OpenCode mutation in runtime

Audit `src/audiagentic/runtime/harness/opencode/` and classify each mutation as:

1. **Executable/runtime asset**: the OpenCode binary, launch script, or process management
2. **Provider config**: API keys, model configurations, endpoint URLs — belongs to provider adapter
3. **Model projection**: selecting which models are available — belongs to foundation/project
4. **Managed MCP**: MCP server declarations for this harness — belongs to foundation projection
5. **Generated surface**: materialized `mcp.json`, launch configs — belongs to provider serializer
6. **User-owned content**: user preferences, custom configurations — belongs to project component

### Current problem

- Runtime contains install/materialization and runner code that should be owned by the OpenCode provider adapter
- Duplicate writers: both runtime and provider may write similar config files
- Compatibility fallbacks: old code paths for previous versions that are no longer needed
- Runtime is directly serializing OpenCode-specific config instead of delegating to the provider

### Target architecture after migration

```
Runtime (runtime/harness/opencode/):
  - Lifecycle management (install, refresh, uninstall)
  - Process supervision (launch, health-check, stop)
  - Ephemeral runtime-root allocation
  - Request cleanup

Provider adapter (providers/opencode/):
  - Serialization of OpenCode-specific config (config-home, MCP format, etc.)
  - Launch mechanism (command-line construction, environment setup)
  - ACP materialization
  - Capability declarations
```

### Migration approach

1. **Audit**: enumerate every file mutation in `runtime/harness/opencode/` and classify
2. **Move**: transfer serialization and launch logic to provider adapter via public API
3. **Remove**: delete duplicate writers and compatibility fallbacks
4. **Verify**: runtime only uses approved public provider APIs — no direct config writing
