# Rate-limit circuit breaker: pause new gpt-auto admissions on conversation-load failure and refresh periodically until it recovers

## Description

ChatGPT rate-limits by replacing a conversation with "Could not load this ChatGPT conversation". The gateway treats that as a per-request failure, not as a provider-wide condition. Observed 2026-11-18: four requests in state running for one project against a configured project-capacity of 2 (global 5); two of them (radiance-bump-readiness, rsp01-d352) started, never submitted (submission-proven false, activity_seq 0) and have no open browser tab; new requests kept being admitted and started. Existing recovery (gpt-auto-defaults.yaml: conversation-load-failure-recovery-enabled, max-attempts 2; dispatch.py conversation-load-reconcile) retries a bounded two times, with no periodic refresh until the page returns and no pause on new admissions. GP10 (rate-limit-dialog recovery) is still pending.

Owner direction (revised 2026-11-18: the pause is gpt-auto-specific, not provider-neutral): on a conversation-load failure treat the gpt-auto harness as rate-limited; stop starting new requests, let running ones finish, and refresh the affected conversation periodically (about every 20s, configurable) until it loads again.

## Steps

- gpt-auto-owned hold (not a generic provider concept: this error exists only in the gpt-auto harness). The gpt-auto runtime keeps the hold state. While held, it does not open a new chat or submit a new turn; turns already running continue to completion. A request that reaches the gpt-auto transport while held waits inside the adapter (bounded, visible in its journal) and resumes when the hold clears. The core queue is not changed and gains no rate-limit concept; the cost is that a waiting request still occupies its queue slot, which is acceptable because the hold is brief and the slot is what limits concurrency.
- gpt-auto adapter: on conversation-load-failed or rate-limit-dialog raise the hold; refresh the affected tab every `conversation-load-refresh-interval-seconds` (default 20) until the conversation loads and the original turn is observable again; clear the hold after a configurable number of consecutive healthy loads.
- Replace the fixed max-attempts bound with an overall deadline (configurable) after which the request goes to the existing unresolved-recovery path, never silently abandoned.
- Active versus stuck, so stuck requests never block healthy ones but ChatGPT is never overloaded (owner direction 2026-11-18). Finding: the per-project cap counts only requests holding a capacity reservation during an executing turn; a request in provider recovery, or between turns, releases its slot while still marked running, so four requests ran for one project against a cap of 2. Keep that: a stuck request must not hold a slot. Add a gpt-auto page-load budget that counts what actually touches ChatGPT: a request is "active" while it is typing, submitting, observing or refreshing a page. The budget limits concurrent active page operations (config, default equal to the project capacity) and spaces refreshes (default 20s per conversation, configurable). A recovery retry takes a budget slot only for the duration of its refresh, so recovering requests can no longer multiply load, and a stuck request (no submission or no provider activity past its lease) is demoted to slow polling and shown as stuck instead of retrying at full rate.
- Requests that never submitted and have no tab are detected and failed to the recovery path rather than staying running (ties to GA28).
- Doctor reports an open hold and its age.

## Detailed Solution & Technical Design

Config keys under the gpt-auto workflow recovery block: conversation-load-refresh-interval-seconds, conversation-load-recovery-deadline-seconds, rate-limit-hold-healthy-loads, page-operation-budget. The hold lives in the gpt-auto runtime with a durable marker under the gpt-auto provider state so a restart does not release it early. Related: GP10, GA25, GA26, GA28, AS119.

## Validation

Tests: a load failure raises the gpt-auto hold, new chat opens and turn submits wait while running requests finish; the tab is refreshed on the configured interval and the hold clears after healthy loads; the page-load budget bounds concurrent page operations including recovery refreshes and a stuck request does not hold a slot; a never-submitted tabless request reaches recovery. Live: induce a load-error page on a test conversation.

## Effort & Risk

Large. Risk: a hold that never clears starves all work, so it needs a visible state in doctor, a maximum hold age with operator override, and a durable marker.

## Standards

Follow ARCHITECTURE_STANDARDS.md. The core queue and gateway stay unchanged by this item (no rate-limit concept in core); detection, the hold and the refresh all live in the gpt-auto adapter; settings in config with schema; errors registered with resolutions.

## Acceptance Criteria

- While a provider hold is open no new request starts and running requests are not disturbed.
- The affected conversation is refreshed at the configured interval until it loads, then admissions resume.
- A stuck request never holds a project slot, and the number of concurrent ChatGPT page operations is bounded by the page-load budget, including recovery refreshes.
- A request that never submitted and has no tab does not stay running.
- Doctor shows the hold and its age.
