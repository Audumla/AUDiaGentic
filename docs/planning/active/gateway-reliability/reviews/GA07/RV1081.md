# Live dispatching callback repeats default-key removals under prepared state

## Notes

- The trace makes no claim that the original BigCherry prompt was sent; do not replay it.
- Do not broaden the exception to recovered/claimed prepared requests.

## Findings

- After allowing the first fresh prepared callback's validated removal list, the next live failure still reports CON-AGW-125 prepared recovery evidence cannot be removed before dispatch.
- Trace and sink code show the second callback is the exact prepared->dispatching write; while the session metadata is still stage=prepared, the callback repeats the remove-list for submission-proven and prior message/terminal fields.
- The fresh_prepared_dispatch branch already verifies current prepared stage, request owner, matching pending turn, no takeover/recovery claim, and false-or-absent submission proof. The remaining generic removal fence must only bypass for this branch when the remove-list does not intersect actually present recovery evidence except exact false defaults.
- The unit scenario's first callback modeled the live remove list but its second callback did not, so it failed to catch this duplicate guard.

## Conclusion

Extend the narrowly validated default/absent removal exception to the fresh prepared->dispatching transition and update the test's second callback to use the same removal list. Keep prepared recovery/takeover removals rejected.
