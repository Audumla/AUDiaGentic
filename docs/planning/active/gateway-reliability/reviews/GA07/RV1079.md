# Live trace exposed fresh prepared checkpoint defaults and transition guard failures

## Notes

- Use bounded trace facts only; do not log prompt/response/credentials.
- Do not relax the ambiguous submission or recovery fences.

## Findings

- A fresh GPT-auto session binding explicitly persists submission-proven=false; the initial prepared checkpoint must treat only this exact false default (or absence) as no prior side effect. It must continue rejecting true, malformed, or any existing recovery evidence.
- The prepared checkpoint sink can remove false default metadata during the prepared write. The subsequent prepared-to-dispatching transition must allow submission-proven to be absent or exactly false while still requiring exact request ownership, matching pending turn ID, prepared stage, and no recovery claim/generation or recovery-required state.
- The live trace demonstrated the first guard was passed after the first patch and then the remove-keys guard failed; after that, a unit regression reproduced the next transition guard failure. These sequential failures were not visible in static inspection alone.

## Conclusion

The remaining checkpoint predicates were overfitted to absent metadata rather than the provider adapter's exact false defaults and checkpoint removal callback. Fixes are in the working tree and require final live verification with a fresh reviewer request.
