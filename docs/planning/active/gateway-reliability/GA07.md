# Bounded reconciliation before accepting terminal request failure

## Description

Before exposing a terminal failed request as final, perform a bounded provider/session recheck that can recover visible completion or prove the request is not recoverable without replaying ambiguous work. Status reads must remain responsive while recovery is scheduled.

## Steps

- Define failure classifications and reconciliation budget.
- Recheck durable session binding and provider/CDP evidence.
- Recover visible response or safe pre-submit retry.
- Use a durable per-request reconciliation claim with lease, stale-claim takeover and unresolved cooldown.
- Enforce recovery admission disposition before diagnostics mutation or provider capture.
- Schedule status-triggered reconciliation off the status request path.
- Add unit, integration, concurrency and live validation coverage.

## Detailed Solution & Technical Design

Extend the existing recovery journal and per-request mutation lock with reconciliation claim lease/cooldown semantics. Automatic status recovery requires explicit submission-proven metadata, claims the request before provider capture, and uses a unique attempt id. Provider capture remains no-resubmit and request-first. Status polling schedules one daemon recovery worker per request and returns the compact lifecycle immediately; the worker is fenced by the durable claim journal. Prompt-virtualization adoption remains separate and requires exact terminal same-conversation evidence.
