# Orphaned gpt-auto requests cannot be captured, recovered or abandoned

## Description

When the process hosting an automatic/embedded gateway exits while a gpt-auto provider-session request is running (here: the MCP client process died during a session restart), the request is left lifecycle=active, activity=orphaned, and none of the recovery tools can settle it: agent_task_complete_from_provider fails with CON-AGW-154 (reason provider-config-unavailable), agent_task_recover abandon fails with CON-AGW-145 (no recoverable diagnostic evidence), and agent_task_cancel only marks it best-effort while it stays running. The orphan also keeps holding its gateway session, so follow-up turns in that session are blocked and the ChatGPT answer that was produced is unreachable through the gateway.

## Steps

1. Reproduce: submit a long gpt-auto request through an embedded gateway, kill the hosting process mid-response, start a new MCP client.
2. Make complete_from_provider resolve the provider config from the request's frozen snapshot/session binding instead of live project config.
3. Let recover abandon/reconcile act on orphaned provider-session requests using the durable session binding as evidence.
4. Release the gateway session once the orphan is settled.
