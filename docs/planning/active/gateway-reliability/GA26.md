# Keep retained GPT conversations recoverable after failed automatic resume

## Description

Automatic continuation of a durable GPT conversation can be permanently poisoned by a cached failed resume control ID. A transient pre-submit readiness failure also must not destroy an otherwise retained conversation. Recover silently through existing bounded rehydrate/readiness policies without duplicating a provider prompt.

## Steps

1. Reproduce the unsent failure and failed-control replay using persisted trace and live CDP.
2. Correct automatic resume attempt identity/recovery classification while preserving explicit control idempotency, source locking, context and active-turn fences.
3. Retain transient pre-submit recovery only when exact conversation identity is durable; keep genuine auth/config/binding errors distinct.
4. Focused regression tests and live continuation/restart validation using the same native conversation.

## Detailed Solution & Technical Design

Reuse existing source-session resume lock and immutable control records. Ordinary automatic retry keys include the queue's persisted recovery attempt. Cached failed controls are treated as transient only when durable lookup proves EXT-AGW-118; manual replay and definitive refusal semantics are unchanged. An explicit new prompt may reopen a safe terminal local session (including deliberate close/expiry) through its retained provider binding, but promptless recovery cannot undo deliberate closure and unresolved sends never replay.
Provider readiness retention keeps a proven-unsent exact conversation in RECOVERING under live owner rather than falsely READY or FAILED. After the existing immediate retry, queue deferral uses normal recovery bounds. Empty, fresh assistant renderer candidates with exact current-prompt/conversation evidence remain pending observation; original terminal adoption/ownership proof stays unchanged. No new recovery loop, state store, timer or registry.
