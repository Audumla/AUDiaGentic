# Model source and vendor desired-state management

## Description

Refactor model management around concrete sources/vendor accounts, cached catalogs, optional apply semantics, and consistent model-domain tool names.

## Steps

- Define remote-account sources as concrete vendor/account catalogs and local-endpoint sources as directly declared model endpoints.
- Rename model tools to model_source_*, model_vendor_*, model_inventory, and model_projection_* without provider prefixes.
- Add optional apply=false to source/vendor mutations; default remains desired-state-only.
- Unify source catalog refresh into model_source_catalog_refresh(source_id=None) for one/all refreshable sources.
- Preserve schema validation, atomic desired-state writes, secret-reference-only storage, cache freshness, and connector failure fallback.

## Detailed Solution & Technical Design

Canonical desired state remains .audiagentic/config/model-sources.yaml validated by model-sources.schema.json. A remote-account source has source_id, canonical vendor_id, connector, endpoint/options, api-key-ref, discovery mode, filters, enabled state, and optional limits/capabilities; multiple sources may share a vendor. Static-catalog data is package-maintained, list-api data is explicitly fetched and cached under .audiagentic/runtime/providers/source-catalogs, and ordinary projection never fetches network data. Mutations write desired state atomically. apply=true persists the validated desired-state change first, then runs model projection; it returns the desired-state diff plus per-provider projection results and drift/errors. It does not roll back model-sources.yaml on projection failure; model_projection_apply is the retry/recovery operation. Source CRUD remains schema-validated and must reject immutable/unknown fields according to the public patch contract while preserving secret-reference-only storage. model_source_remove/disable with apply prunes only source-owned managed IDs. Vendor enable/disable updates every source with that vendor_id and optionally applies.

## Validation

- Remote/local source schema and atomic CRUD tests pass.\n- One/all source catalog refresh uses explicit network boundary and cache fallback.\n- Optional apply persists desired state, returns per-provider projection failures/drift, and never claims full apply success when projection fails.\n- A later model_projection_apply can converge previously failed providers.\n- Optional apply does not activate disabled providers.\n- Vendor grouping supports multiple sources sharing one vendor ID.\n- Removed provider-prefixed model tool names are absent from MCP declarations.

## Effort & Risk

Large: changes public tool signatures and model desired-state/projection sequencing. Atomic write plus apply failure needs explicit result semantics so desired state is not silently rolled back or misreported.

## Standards

Source desired state, catalog retrieval, provider activation, and provider model projection remain distinct. Never persist literal credentials; preserve managed ownership boundaries.
