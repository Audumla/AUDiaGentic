# Unified capabilities: descriptor schema + dual-read loader (compat shim)

## Description

CLEAN-CUT (revised): build the SINGLE-READ unified `capabilities:` descriptor loader — NO dual-read shim. `capabilities:` is the only shape the loader accepts; legacy flat blocks (automation_capabilities, capability_facts, mcp_config, permissions, host_capabilities, model_config, plugin_config, hooks_config, language_servers_config, surfaces, on_lsp_enabled, ...) are removed in the SAME coordinated change (PC03 rewrites all 16 providers; PC04 deletes the legacy parsing). The descriptor exposes ProviderDescriptor.capabilities plus typed @property accessors (mcp_config, permissions, host_extensions(), on_lsp_enabled, ...) that project from the normalized view, so the ~107 raw-field call sites across 35 files keep working unchanged. Mechanism parsing is catalogue-driven per PC01's mechanism_schema. This item no longer builds a compatibility shim; it lands together with PC01/PC03/PC04 as one coordinated, suite-green change.

## Detailed Solution & Technical Design

GOAL: make the merged `capabilities:` block READABLE and normalise it + the legacy flat blocks into ONE internal representation, so nothing downstream (registrar, families, providers_api, providers query) changes. No YAML migrated here.

1. Capability record (new, in descriptors/base.py or capability_catalogue.py):
   @dataclass(frozen=True) class Capability: kind: str; mechanism: Any; modes: tuple[str,...]=(); evidence: CapabilityEvidence|None=None
   `mechanism` is the typed object the kind's mechanism_schema names — a ManagedConfigSpec (mcp/model/plugin/hooks/language-servers), a HostCapability, a ProviderPermissions, an AgentFile, a resolved callable, or a small struct. Reuse existing types: ManagedConfigSpec (foundation/toolchains/config/managed_config.py), HostCapability/ProviderPermissions/AgentFile/CapabilityEvidence (base.py).

2. Normalized view on ProviderDescriptor. Add ProviderDescriptor.capabilities: tuple[Capability,...] populated at load. Keep the existing typed accessors working by projecting FROM the normalized view: automation_capability(family_id) -> find the Capability whose catalogue-kind.family_id matches; host_extensions(host) -> filter kind=='host-extension' list entries; permissions -> the single kind=='perm-declaration' mechanism. Existing call sites stay unchanged.

3. Mechanism parsing is catalogue-driven, not per-field. A single mechanism loader switches on catalogue_kind.mechanism_schema:
   - 'managed-config-spec' -> build ManagedConfigSpec (resolve reader/writer/remover dotted refs, exactly as loader.py does today for mcp_config)
   - 'callable-ref'        -> resolve one dotted callable (as on_lsp_enabled today)
   - 'permissions-struct' / 'host-capability' / 'agent-file' -> build the existing dataclass
   - 'cli-install-recipe'  -> existing CliInstallRecipe / cli_recipe path
   - 'surfaces-struct'     -> the surfaces dict
   Validate the parsed mechanism against the kind (cardinality single vs list; required sub-fields per mechanism_schema).

4. Dual-read in descriptors/loader.py. For each provider: if `capabilities:` present, parse it via the mechanism loader; ALSO parse any legacy flat keys (automation_capabilities, capability_facts, host_capabilities, permissions, mcp_config, model_config, plugin_config, hooks_config, language_servers_config, cli_install, surfaces, on_lsp_enabled...) and project them into the SAME Capability list. Forbid declaring the same catalogue-kind in both shapes (VAL-PCAP-012). Emit identical normalized descriptors either way.

5. Derive automation_capabilities. Today ProviderAutomationCapability is hand-declared AND field-presence is separately checked (automation_registry eligibility). Under the normalized view, presence of an automation-kind Capability + its catalogue family_id IS the declaration — synthesize ProviderAutomationCapability from (catalogue family_id, pin contracts, modes). Legacy explicit automation_capabilities still accepted (dual-read) and must equal the synthesized one (else VAL-PCAP-012).

6. Evidence sourcing. capability_facts.py's payload/markdown renderers now read Capability.evidence from the normalized view instead of the separate capability_facts tuple; behaviour identical for legacy-shape providers.
