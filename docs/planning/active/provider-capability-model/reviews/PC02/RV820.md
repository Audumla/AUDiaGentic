# Needs explicit field-mapping table + mechanism typing strategy

## Notes

PC02 is correctly identified as the highest-risk item. The main design gap is the dynamic-typing of mechanism and the lack of a clear field-mapping table (which legacy fields go under which catalogue kinds). Recommend adding an explicit mapping table as a blocking prerequisite — something like: mcp_config -> mcp-config kind, host_capabilities -> ext-declaration kind, permissions -> perm-declaration kind, etc. Without this table, the dual-read implementation is ambiguous.

## Findings

1. HIGHEST-RISK ITEM ACKNOWLEDGED — BUT RISK IS UNDERSTATED: PC02 edits loader.py (719 lines) and base.py (289 lines), which are the foundation of the entire providers layer. The plan says 'dual-read means zero behaviour change until PC03' — this is correct in theory, but the dual-read branch itself must be proven equivalent, which is the risk. The normalization-equivalence test is the right safety net, but WRITING that test requires parsing both shapes and comparing deep structures — that test itself is non-trivial.

2. CAPABILITY DATACLASS DESIGN HAS A SUBTLE PROBLEM: The plan proposes `Capability.mechanism: Any` where the type depends on the catalogue's mechanism_schema. This means the mechanism field is dynamically typed — sometimes ManagedConfigSpec, sometimes HostCapability, sometimes a callable. The existing codebase uses SEPARATE typed fields (mcp_config: ManagedConfigSpec | None, host_capabilities: tuple[HostCapability,...]) which are statically typed. Moving to a dynamically-typed mechanism means downstream code loses type safety. The plan mentions 'accessors project from the normalized view' but doesn't show how `mcp_config` accessor works when the value is buried inside a Capability tuple.

3. PROVIDER DESCRIPTOR HAS ~30 FIELDS — THE PLAN ONLY ADDRESSES CAPABILITY ONES: base.py has fields like `launches`, `execution`, `interactive`, `acp`, `surfaces`, `deprecated`, `annotations`, `session_surfaces` that are NOT capabilities in the current model. The plan says 'Keep genuinely orthogonal fields that are NOT capabilities' but doesn't enumerate which fields stay flat. The executor needs an explicit list of what's IN capabilities: vs what remains as top-level fields.

4. DERIVING ProviderAutomationCapability FROM CATALOGUE IS UNPROVEN: The plan says 'presence of an automation-kind Capability + its catalogue family_id IS the declaration — synthesize ProviderAutomationCapability'. But ProviderAutomationCapability carries payload_contract, result_contract, ownership_scope_required (automation_capabilities.py:17-28). These values are NOT in the catalogue — they're per-provider declarations. The plan doesn't explain where payload_contract comes from when synthesizing. This is a design gap.

5. MECHANISM PARSING IS CATALOGUE-DRIVEN — BUT THE CATALOGUE DOESN'T EXIST YET: PC02 depends on PC01's catalogue, which has the issues identified in RV819. If PC01's catalogue design is reworked, PC02's mechanism parsing must follow.

6. DUAL-READ VAL-PCAP-012 GUARD: The plan proposes forbidding the same kind in both shapes. This is correct and important. But the error message should be clear about WHICH shape to keep — the plan doesn't specify the migration guidance.
