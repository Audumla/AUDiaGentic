# MISSED CAPABILITY: managed-hooks family is orphaned — no catalogue kind for hooks_config

## Notes

Code-verified against the SHIPPED PC01 catalogue (src/audiagentic/config/providers/_capabilities.yaml + _families.yaml, both now built). This is the 'capability we missed'.

FACTS:
- _families.yaml declares family `managed-hooks` (payload/result contracts, modes [apply,prune,status]) at lines 31-34.
- _capabilities.yaml has NO kind whose family_id == managed-hooks. Every other automation family has a kind (cli-lifecycle->cli-install, managed-mcp->mcp-config, model-projection->model-config, generated-surfaces->surface-render, language-server->lsp-automation, plugin-entry->plugin-config). managed-hooks is the ONLY family with no kind — an orphaned family declaration.
- codex.yaml lines 233-239 declare a REAL hooks_config ManagedConfigSpec (~/.codex/hooks.json, reader/writer/remover, codex-hooks-json, restart-required). There is a managed_hooks_family.py handler and contracts/managed_hooks.py. DE01 built managed-hooks recipe steps.
- PC02's OWN field classification (PC02 notes, CAPABILITY list) includes hooks_config as capability field #10.

CONSEQUENCE: when PC03 migrates codex, hooks_config has no catalogue kind to become. Its capability_fact (if any) would fail VAL-PCAP-009, and the automation-capability synthesis for managed-hooks has no kind to hang on — codex hooks provisioning silently loses its declaration surface.

## Findings

Add the missing automation kind to _capabilities.yaml (this is a defect in the PC01 deliverable; fix there, consume in PC03). Exactly parallel to mcp-config:

  hook-config:
    domain: hook
    authority: automation
    family_id: managed-hooks
    cardinality: single
    mechanism_schema: managed-config-spec

(name `hook-config` matches the domain: hook already reserved in CapabilityKind.domain; alternatively `managed-hooks` as the kind id — pick one and keep it canonical.) Then in PC03, codex's hooks_config migrates to a `hook-config` capabilities entry with modes [apply,prune,status]. Add a PC01 VALIDATION so this class of bug can't recur: assert every automation family in _families.yaml is referenced by at least one catalogue kind (orphaned-family check) — it would have caught managed-hooks at load. Also audit whether managed-hooks contracts (provider-managed-hooks-payload/v1) have JSON schemas present, since VAL-PREC-style contract resolution will look for them.

## Conclusion

Confirmed missed capability: managed-hooks family has no catalogue kind, so codex's hooks_config cannot migrate. Add a `hook-config` automation kind (family_id: managed-hooks, mechanism_schema: managed-config-spec) to _capabilities.yaml and add an orphaned-family validation to PC01 so it can't recur.
