# Provider-named catalogue kinds (obs-opencode-*) are an anti-pattern; over-decomposed surface-skill/instruction kinds

## Notes

Code-verified against shipped _capabilities.yaml + opencode.yaml lines 273-301. Two catalogue-design defects surfaced while reviewing the final taxonomy.

## Findings

1. PROVIDER-NAMED KINDS (must fix). _capabilities.yaml declares kinds `obs-opencode-acp` and `obs-opencode-cli-session` — provider instance names baked into canonical kind ids. This does not scale (every harness×surface would mint a new kind: obs-codex-acp, obs-pi-acp, ...) and violates provider-neutrality of the taxonomy. ROOT CAUSE: VAL-PCAP-009 forced opencode's provider-named facts (hinv-opencode-*) to resolve to a catalogue kind; the fix taken was to add provider-named KINDS rather than neutralize the FACTS. FIX: (a) replace both with ONE neutral evidence-only kind, e.g. `obs-harness-status` (authority: evidence-only, mechanism_schema: none); (b) opencode declares TWO evidence instances under that one kind, distinguished by subject/fact_anchor (external:harness-observability/opencode-acp and /opencode-cli-session) — uses the member-scoped multi-valued evidence model from RV825; (c) add a PC01 VALIDATION: a catalogue kind id must be provider-neutral — reject any kind id containing a known provider_id token — so this class of contamination can't recur. Note: the sibling acp-* kinds ARE neutral and are fine.

2. SURFACE KINDS OVER-DECOMPOSED. surface-render (field: surfaces; automation generated-surfaces = the renderer), surface-skill (field: skill_surface_path = where per-skill files land), surface-instruction (field: instruction_file = the managed instruction file). skill/instruction are surface TARGET PATHS (inputs to rendering), not independent capabilities — the 3-way split is a fossil of the old taxonomy and forces the PC03 'surfaces split matrix' (up to 3 facts/provider). But a naive merge into surface-render breaks providers like claude that declare skill_surface_path + instruction_file with NO surfaces dict (custom adapter renders). RECOMMEND: two kinds not three — keep `surface-render` (automation, only when a declarative surfaces dict exists) and fold surface-skill + surface-instruction into ONE operational `surface-targets` kind, mechanism {skill_path?, instruction_file?}, present whenever either path exists regardless of renderer. Removes the awkward surface-instruction:boolean-set kind and aligns with the PC04 keep-orthogonal-vs-kind contradiction (residual #2).

## Conclusion

Two catalogue corrections before PC03 migrates opencode: (1) replace provider-named obs-opencode-* kinds with one neutral obs-harness-status kind carrying two member-scoped evidence instances, and add a provider-neutrality validation; (2) consolidate surface-skill + surface-instruction into one surface-targets operational kind, keeping surface-render as the declarative renderer. Both are defects in the shipped PC01 catalogue; fix there, consume in PC03.
