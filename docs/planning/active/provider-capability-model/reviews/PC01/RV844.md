# FINAL taxonomy: naming (provisioned + bare nouns), boundary rule, and full-field gap check

## Notes

Consolidated record of all naming/structural decisions taken with the user. Supersedes the naming in the shipped _capabilities.yaml/_families.yaml. Component findings RV841 (hooks), RV842 (isolation tiers + alignment), RV843 (obs-neutral + surfaces) fold into this. The shipped catalogue must be updated to match.

TERMINOLOGY (user decisions):
- Authority tier 'automation' -> 'provisioned' (it is NOT automation: nothing auto-runs; the harness reconciles declared resources only when code is registered). Field automation_capabilities -> provisioned_capabilities.
- Kind ids: bare resource nouns; drop the '-config' suffix (domain+tier already give context).

BOUNDARY RULE (pin in PC01, quotable):
`capabilities:` describes what a provider can do and what the harness manages or reads ABOUT those capabilities. A provider's IDENTITY, LIFECYCLE, and LAUNCH WIRING (name, url, access_mode, deprecation, isolation tiers, launch/exec specs) stay orthogonal fields — they are not capabilities. Classify by CONSUMER, not topic: consumed by a family handler -> provisioned; read by a component decision/listing -> operational; read by nothing but the fact renderer -> evidence-only; consumed as launch/admission wiring or pure identity -> orthogonal.

THREE-DOMAIN NAMING BOUNDARY (do NOT unify): the word 'capability' names three UNRELATED concepts in this codebase. (1) PROVIDER capabilities — this model. (2) LSP PROTOCOL capabilities — coding_lsp/lsp_constants.py (textDocument methods, client/server caps); external spec term. (3) SESSION capabilities — agents gateway AS33 (per-session runtime snapshot). Only (1) is governed by this catalogue. Keep our usage precise ('provider capability'); never fold (2)/(3) into the catalogue.

FEATURES vs CAPABILITIES (PC05): foundation 'features' (FEATURE_SCOPE_IMPLEMENTATION, enable/disable gating) are a PROJECTION of provider capabilities, not a separate list. feature_mapping._CAPABILITIES is a parallel field->kind table (a 4th enumeration) and is retired in PC05 — impl features derive from capability instances. Capabilities = declaration; features = enable-gated projection.
