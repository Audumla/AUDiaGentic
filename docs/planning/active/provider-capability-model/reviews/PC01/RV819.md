# Blocking: namespace contradiction + FamilyPin coverage gap + incomplete off-taxonomy audit

## Notes

This item needs rework before implementation. The three blocking issues are: (1) the open-vs-closed namespace contradiction, (2) the FamilyPin coverage gap (only 4 of 7+ automation families have pins), and (3) the incomplete off-taxonomy ID audit. Recommend splitting into: PC01a (catalogue authorship + off-taxonomy audit across all 16 providers) and PC01b (enforcement validators), with PC01a landing first to establish the ground truth.

## Findings

1. DESIGN CONTRADICTION WITH TAXONOMY DOC: The taxonomy doc (capability-id-taxonomy.md:16) explicitly states: 'the capability-id namespace is open per MA19/MA20 — a new evidence subject adds a row here, it does not require a schema change, and no code may switch on this table.' PC01 proposes closing the namespace with a validated catalogue that REJECTS off-taxonomy IDs (VAL-PCAP-009). This directly contradicts the stated design intent. The plan must either (a) explain why the open-namespace policy should be reversed, or (b) redefine what 'closing the namespace' means — e.g., the catalogue is authoritative for KNOWN kinds but external: evidence-only kinds are still allowed.

2. FamilyPin RECONCILIATION SCOPE IS NARROWER THAN CLAIMED: PC01 says 'for every kind with authority==automation, assert catalogue.family_id maps to a registered FamilyPin'. But _REGISTRARS (automation_registry.py:47-70) only has 4 Pattern A pins: cli-lifecycle, generated-surfaces, model-projection, self-provided-lsp. The managed-mcp, plugin-entry, and language-server-projection families are 'generic families' (automation_registry.py:43-46 comment) invoked through providers_api, NOT through the FamilyPin mechanism. So the reconciliation would ONLY cover 4 families, not all automation kinds. The catalogue lists `mcp-config` with `family_id: managed-mcp` — but managed-mcp has no FamilyPin to reconcile against. This is a fundamental gap in the design.

3. `mcp-launch-isolation` CAPABILITY IS MISSING FROM TAXONOMY: pi.yaml declares `capability_id: mcp-launch-isolation` (pi.yaml:71) but this ID is not in the taxonomy doc's definitions. PC01 would reject it with VAL-PCAP-009. The plan acknowledges 'off-taxonomy ids' but only mentions pi's `vendor-key-injection` and `model-config-surface` — it misses `mcp-launch-isolation` (pi) and the `acp-*` ids in codex.yaml (codex.yaml:145-200). A full audit of ALL off-taxonomy IDs across ALL 16 providers is needed before the catalogue can be authored.

4. `host-extension` vs `ext-declaration` DISCREPANCY: codex.yaml:66 and claude.yaml:55 use `capability_id: host-extension`, but the taxonomy doc defines `ext-declaration` as the canonical ID (taxonomy.md:95). PC01's catalogue would need to either accept BOTH (adding `host-extension` as an alias) or the plan must include renaming these in PC03. This isn't mentioned.

5. `surfaces` vs `surface-render`/`surface-skill`/`surface-instruction`: codex.yaml:102 and claude.yaml:91 use `capability_id: surfaces`, but the taxonomy defines three separate IDs. Again, PC01 doesn't address this discrepancy.

6. MECHANISM_SCHEMA STRING REFS ARE UNRESOLVED: PC01 lists mechanism_schema values like 'managed-config-spec', 'host-capability', 'permissions-struct' etc. These are described as 'ref' strings but there's no existing resolution mechanism. The plan should clarify whether these are just documentation strings or if there's a schema registry that validates them.

7. CORRECT PART: The core idea — a loadable YAML catalogue that provides metadata about capability kinds, validated against code — is sound. The one-way validation direction (catalogue checked against pins, never pins derived from catalogue) correctly preserves VAL-PREC-009. The problem is the SCOPE of what's being reconciled.
