# Cross-plan usage: the evidence-only tier duplicates dedicated subsystems — make the provider capability model actionable-only

## Notes

Reviewed how the capabilities are used across the active plans (agent-sessions AS19/AS27/AS40/AS41/AS50/AS54/AS55, harness-runtime-ownership HA06, mcp-launch-isolation MI08, model-endpoint-management MO, role-capabilities RO01). Two findings materially condense the model.

## Findings

1. THE EVIDENCE-ONLY TIER MOSTLY DUPLICATES PURPOSE-BUILT SUBSYSTEMS. The evidence-only kinds exist only because opencode.yaml carried obs-*/acp-* capability_facts that VAL-PCAP-009 forced to resolve to a catalogue kind. But those facts MIRROR dedicated systems that own the real evidence:
   - obs-harness-status: HA06 is explicit — harness observation capability lives in src/audiagentic/components/providers/services/harness_observability_inventory.py (AS27), a rigorous per-surface evidence matrix (validation_state, effective_production_level, recipe A/B/C/D, probe_anchor) consumed by AS19's harness-status-observer. opencode's obs-* facts even anchor AT that file. So obs-harness-status is a redundant mirror -> DROP from the provider capability model; the observation subsystem owns it.
   - acp-support: ACP presence is a channel of the `launch` capability (descriptor.launches.*.interaction/observability = [acp,...]); ACP VALIDATION is in the AS27 inventory + AS54 surface matrix. The acp-* facts (acp-stdio-transport/live-session/session-resume/shared-live-session) are ACP session-capability claims owned by AS54/agent-sessions (and overlap agents-gateway session capabilities, AS33). -> DROP acp-support from the provider capability model; launch declares the channel, AS54/AS27 hold the evidence.
   - execution-isolation / launch-isolation: isolation is owned by mcp-launch-isolation (MI08). The tier VALUES stay orthogonal (admission authority); their provenance belongs to MI08, not the descriptor. -> DROP the evidence kinds (confirm MI08 owns provenance).
   - model-local-state / model-config-projection: model discovery/state provenance -> fold into `models` capability provenance or model-endpoint-management (MO). (confirm)
   RESULT: the provider capability model becomes ACTIONABLE-ONLY — PROVISIONED (managed resources) + OPERATIONAL (read declarations). Evidence/provenance lives in the purpose-built subsystems that capabilities REFERENCE. This resolves the ORIGINAL complaint that started this work (capability_facts as a disorganized dumping ground): the fix is not a better evidence catalogue in the descriptor, it is to stop mirroring subsystem evidence into the descriptor at all.

2. ROLE-CAPABILITIES (RO01) IS A CONSUMER, NOT A DUPLICATE. RO01 defines agent ROLES = execution intent + required/optional capabilities, and its step 2 vocabulary explicitly REFERENCES 'provider execution capabilities, permissions, components, features, MCP tools' without provider-name conditionals. So our provider capability ids are an INPUT to role-capabilities. Implication: capability ids must be stable, typed, provider-neutral, and referenceable by RO01. Do NOT merge role-capabilities into this model (4th distinct 'capability' concept alongside the 3 profiles); DO keep our ids clean enough for RO01 to compose. This is a cross-plan contract: PC must not rename kinds after RO01 starts referencing them without coordinating.

## Conclusion

STILL A PROPOSAL, not decided (2026-07-28 status check). The evidence-only tier was NOT collapsed -- acp-support, model-local-state, model-config-projection, obs-opencode-acp, obs-opencode-cli-session, execution-isolation, launch-isolation all still exist as evidence-only kinds and are actively used (e.g. opencode's obs-opencode-acp/obs-opencode-cli-session, pi/opencode's model-local-state). The AS19/AS29/AS27 cross-plan convergence this review proposed was never taken up (out of scope for this session's provider-side work; those are agent-sessions-plan items). RV843's narrower, provider-side-only recommendation (neutralize obs-opencode-* to one obs-harness-status kind; this does NOT require AS19/AS29 changes) is the more tractable near-term piece -- carried to PC07. The larger cross-plan proposal (observation capability-driven, AS19:115 revision) remains a live design question for whoever picks up agent-sessions AS19/AS29, not blocking further provider-capability-model cleanup.
