# Session resumability as a first-class capability, surfaced in session status

## Description

Clients (and this session's own live testing) are currently seeing gpt-auto sessions reported as "not resumable" with no reliable, explicit signal telling a caller whether a given session actually can be resumed. This needs to be a harness/provider capability -- determined by whichever harness/provider owns the session -- surfaced directly in session status, not something a caller has to infer from error codes after a failed resume attempt.

## Steps

- Reuse the existing closed-namespace capability catalogue (src/audiagentic/config/providers/_capabilities.yaml `kinds:`) rather than inventing a parallel mechanism. There is already a partial, UNINTEGRATED precedent: the `acp` capability kind's `mechanism.feature` enum includes `session-resume` (codex.yaml:116, opencode.yaml:174 both declare it, currently marked evidence.note="planned... Not implemented"). Decide whether resumability belongs as a value within that existing `acp`/session-resume feature space, or needs its own catalogue kind (e.g. `session-resumability`) if it must apply to non-ACP providers like gpt-auto too -- gpt-auto is not an ACP provider, so the existing acp-scoped feature likely does not cover it and a provider-neutral kind is probably needed.
- Unify the two currently-separate "can this provider resume" mechanisms found in this codebase: (a) the capability-catalogue acp/session-resume declaration (static, evidence-only, not consumed by resume logic), and (b) session_surface.py's `SessionIdentityOperation.RESUME_BY_REF` / `ResolvedSessionSurface.identity_operations`, which IS what resume.py's `validate_resume_eligibility` actually consumes today. These should not remain two independent, disconnected "is resumable" signals.
- Surface a `resumable` (or similarly-named) field in the client-facing session status projection -- api.py's `request_runtime_status` (~line 586-624) and/or sessions.py's `session_runtime_status()`/`_session_runtime_status()` (~line 687/1013) are the concrete places this currently gets built, alongside `session` status fields. No existing precedent flows a capability-catalogue entry directly into this dict today; the closest analog (identity_operations -> resume.py's eligibility gate) does the check but doesn't project the answer back to the caller ahead of an actual resume attempt.
- Determine resumability HARNESS/PROVIDER-side, not caller-side -- the owning harness/provider is the only party with the evidence to know. For gpt-auto specifically: should be resumable by default (browser tabs are retained, provider_session_id + chat_url/reconciliation-by-provider-session-id is durable), EXCEPT the real edge case the user identified: the ChatGPT conversation was deliberately deleted (a real cleanup action taken to control test-chat proliferation in projects). In that case resumability must correctly flip to false/not-resumable -- gpt-auto cannot just always claim resumable=true unconditionally.
- The deleted-conversation case needs a real existence check, not an assumption -- likely at resume-attempt time via find_conversation_page-style lookup (or a lighter existence probe), following this project's established evidence discipline (GP06's reviewed correction applies here too: only positive evidence should downgrade a resumability claim, never silence/staleness alone).
- Decide precedence/consistency with GP06 (session lifecycle states): once GP06 introduces closed-with-runtime-owner-lost or a new interrupted session state, resumability status should compose cleanly with those states rather than duplicating or contradicting lifecycle information.

## Detailed Solution & Technical Design

This is seeded for further exploration, not a finished design -- the user explicitly asked for this to be captured now with enough seed information for follow-up (including possibly a dedicated live gpt-auto session/chat doing exploratory design work against this item specifically) rather than fully fleshed out in this pass. Key open questions for that follow-up: exact catalogue kind shape (new kind vs extending acp's feature enum for non-ACP providers), exact field name/shape in the status projection, whether resumability should be a plain boolean or a richer enum (e.g. resumable / not-resumable / unknown-needs-check), and how the deleted-conversation existence check should be performed cheaply (without requiring a full CDP round-trip on every status query).

## Validation

A session status query must return an explicit resumability signal before any resume is attempted, not just an error after a failed attempt. A gpt-auto session whose underlying ChatGPT conversation was deliberately deleted must report not-resumable, verified against positive evidence (a real existence check), not an assumption. Existing resume.py eligibility behavior must not regress once unified with the capability-catalogue declaration.
