# Executable capability catalogue + enforcement (no descriptor YAML churn)

## Description

Promote the markdown capability taxonomy (docs/reference/PROVIDER_CAPABILITY_REFERENCE/model/capability-id-taxonomy.md) into an authoritative, loadable catalogue and add validation that ties every provider capability declaration to it. Enforcement-first landing: closes the open capability_id namespace and binds each kind to its domain/authority/mechanism-schema WITHOUT changing any provider YAML shape. After this item an ad-hoc capability_id (e.g. pi's 'vendor-key-injection', 'model-config-surface') fails validation instead of silently accreting.

Catalogue lives as a YAML index (config/providers/_capabilities.yaml) loaded at startup, but is a DECLARATIVE index validated against the code-owned FamilyPins — it never becomes the authority for families (recipe_definitions.FamilyPin stays in code; VAL-PREC-009 preserved).

## Steps



## Detailed Solution & Technical Design

GOAL: one loadable catalogue that (a) closes the capability_id namespace, (b) binds each kind to domain/authority/cardinality/mechanism-schema, and (c) is validated AGAINST the code-owned FamilyPins so config can never redefine a family.

1. CapabilityKind (new, src/audiagentic/components/providers/descriptors/capability_catalogue.py). Frozen dataclass:
   - id: str                     # canonical, e.g. 'mcp-config' (was free string)
   - domain: str                 # 'cli'|'mcp'|'lsp'|'model'|'surface'|'exec'|'hook'|'plugin'|'ext'|'perm'|'file'|'obs'|'acp'|'depr'
   - authority: Literal['automation','operational','evidence-only']
   - family_id: str | None       # set iff authority=='automation'; MUST match a code FamilyPin
   - cardinality: Literal['single','list']  # permissions=single, host-extension=list
   - mechanism_schema: str       # ref: 'managed-config-spec' | 'host-capability' | 'permissions-struct' | 'callable-ref' | 'boolean-set' | 'none'

2. Catalogue index config/providers/_capabilities.yaml enumerating every kind currently in capability-id-taxonomy.md (cli-install, cli-probe, mcp-config, mcp-remote, lsp-config, lsp-self-support, lsp-mcp-receive, model-catalog-refresh, model-config, model-connectors, model-vendor-injection, surface-render, surface-skill, surface-instruction, exec-adapter, hook-lsp-enabled, ext-declaration, perm-declaration, file-agent, depr-status). Loaded once by a catalogue loader; the markdown doc becomes generated-from / checked-against this file (PC04).

3. Catalogue-vs-code reconciliation (the critical guarantee). automation_registry._REGISTRARS exposes each family's FamilyPin (recipe_definitions.FamilyPin, code-owned). At catalogue load, for every kind with authority=='automation', assert catalogue.family_id maps to a registered FamilyPin AND (when the kind declares contracts) they equal pin.contracts. Direction is one-way: catalogue validated against pins, NEVER pins derived from catalogue — keeps VAL-PREC-009 non-tautological (see FamilyPin docstring). A catalogue automation-kind with no matching code pin fails load.

4. Enforcement validators (extend descriptors/capability_facts.py + automation_capabilities.py):
   - VAL-PCAP-009 (new): every capability_fact.capability_id must be a catalogue kind id (or an 'external:'-prefixed evidence-only id whose kind is authority=='evidence-only'). Rejects today's off-taxonomy ids (pi 'vendor-key-injection','model-config-surface').
   - VAL-PCAP-011 (new): a declared automation family_id must have a catalogue kind whose family_id equals it.
   - Keep existing checks (empty/dup id, evidence tiers, subject resolves).

5. Reconcile existing off-taxonomy ids. Audit all 16 YAMLs for capability_ids not in the catalogue. Two fixes: add the missing kind to the catalogue (e.g. a 'model-vendor-injection' evidence-only kind that covers pi's vendor-key-injection) OR rename the fact to the canonical id. Do this as catalogue authorship, not YAML restructure — restructure is PC03.
