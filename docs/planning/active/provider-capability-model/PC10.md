# Provider activation bootstrap and lifecycle operations

## Description

Use a one-time initial provider activation selection during first install/initial startup, then make provider feature state and current support availability authoritative. Remove persistent reconciliation-policy runtime behavior.

## Steps

- Add an explicit non-persistent launch option for initial provider selection (recommended shape: --providers <id>[,<id>...]); do not store the option as a runtime policy.
- At initial startup, probe eligible providers and enable only selected/detected providers; never install missing providers as a side effect of selection.
- Persist resulting provider feature state and mark bootstrap selection consumed; subsequent launches must not consult an allowlist/prompt policy.
- Remove runtime calls from reconcile_provider/reconcile_all_providers to get_reconciliation_policy and resolve_reconciliation_policy; make provider_reconcile deterministic.
- Align provider_install so installation does not silently seed activation unless explicitly requested; separate install result from enable result.
- Add provider_enable/provider_disable and split lifecycle dispatch into provider_install/provider_uninstall/provider_update; remove generic repair.
- Migrate existing reconciliation-policy data once for compatibility, materialize feature state, then remove/ignore old policy.
- Migrate launcher, launch command, provider config, MCP declarations, APIs, and tests.

## Detailed Solution & Technical Design

The bootstrap input is an explicit, non-persistent launch option parsed by the launcher/launch command (recommended --providers with a comma-separated canonical provider ID list). It is consumed only when provider feature state has not yet been initialized. Launch probes selected/eligible providers, enables selected providers that are available, reports selected-but-unavailable providers without installing them, and persists feature state. Runtime modules must not load/evaluate/mutate startup-selection/reconciliation-policy data. provider_reconcile(provider_id=None) verifies current enabled providers and repairs projections; unavailable enabled providers are disabled/pruned; disabled providers are not auto-enabled. provider_install returns support installation state only; provider_enable is the activation operation. Existing persisted reconciliation-policy is a one-time migration input only.

## Code Samples & Guidance

provider_reconcile(provider_id: str | None = None); provider_enable(provider_id: str); provider_disable(provider_id: str); provider_install(provider_id: str); provider_uninstall(provider_id: str); provider_update(provider_id: str). Startup policy resolution remains an internal launch/configuration path, not a provider runtime MCP tool. Public operations return structured result with provider_id, changed, activation/support state, projection results, and error/action_needed.

## Validation

- Static boundary test proves runtime provider reconciliation/lifecycle modules do not import or call startup-policy helpers.
- Runtime MCP operations behave identically regardless of stale/malformed/absent startup-selection data after bootstrap.
- Bootstrap consumes the selection exactly once and persists provider feature state.
- Subsequent launches and explicit provider_reconcile calls never prompt or consult an allowlist.
- Existing reconciliation-policy data is migrated/consumed once and cannot alter later runtime activation decisions.
- Enabled-but-unavailable providers are disabled/pruned based on support probes, independent of startup-selection data.

## Effort & Risk

Large: crosses feature state, lifecycle recipes, reconciliation, surfaces, MCP synchronization, and model projection. Requires careful ordering and backward-incompatible MCP metadata update.

## Standards

Activation, installation, projection, and model-source desired state are separate axes. Use lifecycle/event ownership boundaries and fail closed on contradictory state.

## Acceptance Criteria

- Startup activation selection is consumed once and persisted as provider feature state.
- Runtime lifecycle/reconcile paths never read startup policy or prompt/consult an allowlist.
- Stale, malformed, or absent bootstrap-selection data cannot change runtime behavior after bootstrap.
- Enabled but unsupported providers are disabled/pruned from support evidence independently of bootstrap data.
- Static boundary and migration/idempotency tests pass.

## Notes

Hard boundary: startup selection is not runtime state. After bootstrap, no runtime provider module may read, evaluate, or mutate reconciliation-policy/allowed-providers/decided-providers. Add architecture/static-call-site tests to prevent reintroduction.
