# Complete migration, documentation, and host/Docker isolation gates

## Description

Delete obsolete shared-launch paths, update architecture guidance, and run a layered validation matrix proving default native usability and job isolation for Pi and OpenCode. Separate branch-pre-existing registry pollution from regressions introduced by this plan and fix any pollution that invalidates full-suite confidence.

## Steps

1. Remove obsolete collectors, duplicate preparation helpers, shared job-config assumptions, stale request-runtime fields, compatibility aliases, and tests for deleted behavior.
2. Update `CREATING_A_HARNESS.md` so collection is foundation-owned, providers materialize, ACP/direct composition is provider-local, and every job route must prove exclusivity.
3. Document durable native/default versus ephemeral job artifact ownership, cleanup, concurrency, and capability reporting.
4. Add a provider/launch-kind capability table for Pi direct, Pi ACP, OpenCode direct, and OpenCode ACP, including tested versions/platforms and unsupported outcomes.
5. Stabilize provider registry tests so isolated-pass/full-suite failures cannot be dismissed as pollution. Reset registries with owning fixtures or remove illegal process-global mutation; do not hide failures with order dependence or retries.
6. Run focused unit, architecture, MCP stdio, harness integration, gateway session, concurrency, and failure-path suites.
7. Run the repository’s full host suite using its canonical runner, then all non-mutating Docker suites. Run opt-in real Pi/OpenCode gates in disposable homes/containers where dependencies exist.
8. Record exact commands, counts, skips, environment limitations, and failures. Do not call a subset “all tests.”
9. Record an unreleased ledger change event with every implementation file and all associated `MI01`–`MI08` plan item IDs; complete items only after their own validation evidence passes.
