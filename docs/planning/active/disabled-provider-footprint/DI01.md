# Purge disabled provider project footprint

## Description

Ensure disabling an installed provider removes its AUDiaGentic-owned project footprint while leaving the provider CLI installed, and that re-enable recreates required artifacts.

## Steps

1. Inventory provider descriptors, managed config specs, lifecycle recipes, and Docker fixtures. 2. Implement descriptor-driven purge using ownership and artifact abstractions. 3. Add parametrized install/enable/disable/re-enable/component-sync/disable coverage. 4. Validate provider-specific and shared files are handled without hardcoded provider lists.

## Detailed Solution & Technical Design



## Code Samples & Guidance



## Files

Provider lifecycle services, reusable managed configuration/artifact helpers, Docker lifecycle tests.

## Validation

Focused unit suite and source compilation pass. Docker lifecycle matrix is implemented and collected for all descriptor-declared Docker-installable providers, but execution is currently blocked by the existing Docker base/real-install environment: missing `ps` in the base image and provider npm install failures (including Qwen).

## Effort & Risk

Large: provider config formats and user-owned content require fail-safe ownership handling.

## Standards



## Acceptance Criteria

- Disabling an installed provider removes all AUDiaGentic-owned project artifacts for that provider while preserving user-owned content and the provider CLI installation.
- Re-enabling the provider recreates the required owned configuration and generated surfaces without duplicate or stale entries.
- Descriptor-, recipe-, and ownership-driven lifecycle tests cover every Docker-installable provider and pass in the supported Docker environment.
- No provider-specific branches or central hardcoded provider lists are introduced.



## Notes

Implementation remains descriptor-, recipe-, and ownership-driven. No provider IDs, provider branches, or new capability kinds were added to central code.
