# Expose descriptor-driven MCP and harness catalogs through public APIs

## Description

MP03 slice 1. Add typed read-only catalog APIs without constructing launch sessions or importing adapter implementations.

## Steps



## Detailed Solution & Technical Design

Derive MCP rows from component declarations: canonical ID, managed ID, owner component, description, transport, entrypoint provenance, configuration-required flag, available/installed/configured states, exposure eligibility and dependency summary. Detect duplicate IDs and managed-ID collisions explicitly. External declarations list requirements but never run commands/probes during catalog listing. Expose harness catalog through providers_api: provider ID, supports durable MCP registration, launch capability, supported config scopes, CLI presence and availability reason. Harness eligibility is capability-driven, not every provider and not hardcoded pi/opencode. Distinguish native MCP clients from full AUDiaGentic interactive harness support. Hidden/internal or management servers must be explicitly classified; do not bypass propagate restrictions.

## Code Samples & Guidance



## Files

foundation/components/base.py,loader.py; components/project/project_api.py; components/providers/providers_api.py and descriptor/capability services; descriptor catalogs only, not adapter imports.

## Validation

Read-only tests monkeypatch write/network/process launch to fail; duplicate-ID fixtures; component/MCP identity distinctions; providers with MCP config but no full harness, harness with unsupported MCP, missing CLI, disabled components; JSON stable ordering; no unrelated provider adapter imports.

## Effort & Risk



## Standards

MP03 boundaries and repository architecture standards; public APIs only; owner configuration semantics; no git stash.

## Acceptance Criteria

Available IDs come from one canonical descriptor set; installed/configured/available are not conflated; new supported harness or MCP appears via metadata without launcher edits. Detailed MCP and harness item-help payloads must provide owned help metadata, setup requirements, supported options/capabilities, config fields with secret-safe defaults, examples, availability limitations and documentation links; metadata is shared with CLI/help rendering rather than duplicated prose in launcher.
