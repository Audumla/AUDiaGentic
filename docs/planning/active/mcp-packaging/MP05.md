# Define component-owned configuration requirements and safe generic onboarding prompts

## Description

MP03 slice 2. Configuration questions are declarative, owned by each MCP component and validated through its public API.

## Steps



## Detailed Solution & Technical Design

Inventory existing configuration schema/status hooks before adding a versioned requirement projection: namespaced key, type, label/help, required/conditional dependency, default, enum, scope, sensitive flag and validation reference. Provider metadata describes separate harness-config requirements. Resolve supplied config file plus canonical existing config/profile/environment/default precedence; prompt only for unresolved required fields on interactive TTY. non-interactive or no TTY returns missing key names before writes. yes may approve known nonsecret defaults but never invent missing values or licenses/auth. Secrets use masked input and environment/secret references, never plaintext command arguments, stdout, journals or checked-in files; explicit protected local secret storage only if an existing backend supports it. Validate local structure separately from optional bounded remote connectivity; report configured versus reachable truthfully.

## Code Samples & Guidance



## Files

component-owned config/public APIs; foundation neutral requirement contracts; config schema validation infrastructure; proposed commands input renderer; no provider-specific questions in generic CLI.

## Validation

TTY/non-TTY tests, enums and conditional schemas, missing/invalid inputs before side effects, secret redaction and no argv leakage, cancelled prompt no writes, scope/profile precedence, malformed config and incompatible schema versions; at least planning plus one service-dependent MCP.

## Effort & Risk



## Standards

MP03 boundaries and repository architecture standards; public APIs only; owner configuration semantics; no git stash.

## Acceptance Criteria

Adding component configuration questions requires descriptor/schema and owner validator changes, not launcher branches; no indefinite automation prompts. Requirement fields supply human help including type, default/required/conditional status, scope, accepted values and secret handling; never include live secret values in help or JSON descriptions.

## Notes

Depends on catalog/identity slice. Keep execution-profile, workflow-profile, component-profile and role selection separate; do not create alternate configuration stores.

Current grammar: keyword-based management commands and trailing help; preserve shipped legacy flags without introducing new flag aliases.
