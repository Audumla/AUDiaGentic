# Define component-owned configuration requirements and safe generic onboarding prompts

## Description

MP03 slice 2. Configuration questions are declarative, owned by each MCP component and validated through its public API.

## Steps

1. Inventory actual configuration fields for planning and one service-dependent MCP using existing owner schemas and feature-option resolution.
2. Project a minimal owner-provided field description for catalog/help and missing input.
3. Resolve supplied config through canonical owner precedence, validate all values before mutation, and return missing/invalid field names.
4. Let CLI collect TTY input and repeat the same public validation; non-TTY never prompts.

## Detailed Solution & Technical Design

Present trigger: installation may require component configuration, and per-item help must explain it. Reuse owner schemas, foundation/features config resolution and existing config/status public contracts; get_option_provenance alone is feature/implementation provenance, not a universal component configuration loader. Do not turn it into a second resolution engine. Keep onboarding request/result/field projections in components/project/onboarding/contracts.py; provider requirements and native format semantics stay providers-owned. Extend existing declarative owner metadata only for fields required by actual MCPs, referencing canonical owned schema keys rather than maintaining two schemas. No new foundation ConfigRequirement policy, generic secret backend, validator dotted-path field or arbitrary callback registry. If an existing public owner config API is needed, wire its narrow public surface deliberately at the composition root under current dependency rules; no project import of another product component's internals, no per-MCP switch in launcher, no generalized service locator. Prefer existing shared schema validation for structural/conditional requirements; owner API retains business validation and persistence. CLI converts answers only; owner resolves precedence and validates. Explicit nonsecret config input overrides existing owner-resolved values only according to that owner's existing contract; profile/environment/default precedence is not redefined by onboarding. Accept references for sensitive values through existing supported mechanisms, never literal secrets in argv/help/output/log/journal. If required secret-reference support does not exist, return an actionable unsupported requirement rather than invent storage. No implicit auth, network probes or toolchain installation. Dry-run validates without creating state.

Concrete existing primitives verified by review: foundation/features/base.py:OptionSchema, features/options.py:validate_option and resolve_options, and features/config_status.py completeness projection. Completeness is not validation (evaluate_config explicitly does not reject invalid values). Planning API get/set config demonstrates owner validation but does NOT authorize importing Planning into Project. For planning MVP reuse existing schema/status data and lifecycle, no arbitrary validator needed. Extend neutral option schema only where an actual owning field requires it; do not duplicate a broad requirements taxonomy in foundation. Any future specialized owner operation must use explicit allowed public composition.

MP10 supplies the actual tool/help rollout: three new Project MCP tools remain always noninteractive and use server project/process-profile plus existing owner-resolved configuration. Missing fields return names and safe owner action guidance; no literal-secret or arbitrary config payload parameter is added speculatively. CLI config FILE remains its documented optional owner-validated input. Rich item help projects actual owner requirements without inventing defaults or overriding typed API schema.

## Code Samples & Guidance

Proposed project-owned value projection (not implemented):

```python
@dataclass(frozen=True)
class ConfigField:
    key: str                 # canonical owner-schema key
    value_type: str
    help: str
    required: bool
    sensitive: bool

@dataclass(frozen=True)
class RequirementCheck:
    missing: tuple[str, ...]
    invalid: tuple[str, ...]

# CLI input answers go back through the owning public operation:
check = onboarding.check_configuration(request)
if check.missing and not stdin.isatty():
    return render_missing_fields(check)
```
Conditional/default/enum/help information is projected from the actual owner schema when present, not a new mandatory field taxonomy. No custom validator reference is supplied by callers.

## Acceptance Criteria

Requirement fields supply human help including type, default/required/conditional status, scope, accepted values and secret handling; never include live secret values in help or JSON descriptions.
