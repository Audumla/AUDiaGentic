# Require AudiaGenticError message text to be config-sourced, not inline Python strings

## Description

ARCHITECTURE_GUIDELINES.md §3 currently only requires that error CODES be registered in the owning component's error-resolutions.yaml with resolution/guidance text; it does not require the exception's own message= text to be sourced from config. In practice, message= is hardcoded inline in Python at every AudiaGenticError call site across the codebase (confirmed for gpt_auto: turn.py, chat.py, config.py). This was surfaced 2026-08-16 while fixing a real, actively-misleading error message (EXT-GPTAUTO-004's inline text falsely implied "no prompt was sent" when a prior turn had actually completed) -- the fix touched a hardcoded Python string, and the user flagged that error messages should live in config so they can be corrected, reviewed, and audited without a code change/redeploy, and so message text doesn't drift from the config-driven resolution text describing the same error.

## Steps

- Decide the exact mechanism: extend error-resolutions.yaml's per-code entries to carry both `message` (the technical/diagnostic text, config-sourced) and `resolution` (the existing operator-guidance text) as distinct keys, OR introduce a `get_error_message(code, **context)` templating helper (a `get_error_message` function already exists in errors.py per this session's investigation -- check whether it's the right seam to extend, e.g. with format-string interpolation for details like state/reason).
- Update ARCHITECTURE_GUIDELINES.md §3 to state the new requirement explicitly, alongside the existing code-registration rule.
- Establish the pattern via gpt_auto as the reference implementation first (smallest, most recently touched, and the item that surfaced this need) -- migrate its AudiaGenticError call sites (turn.py, chat.py, config.py; see this session's audit for exact line numbers) to source message text from error-resolutions.yaml instead of inline strings.
- Scope the wider codebase migration (every other component's AudiaGenticError call sites) as an explicit follow-on, not part of this item's initial deliverable -- this item establishes the standard and one reference migration; a broader sweep is separate work.
- Add a validation rule (mirroring the existing VAL-PCAP-style pattern used elsewhere in this codebase for closed-namespace enforcement) that fails a call site using an inline message= where a config-sourced message is available/required, so the standard is enforced rather than just documented.

## Schema Design: Nested message/resolution structure

Extend error-resolutions.yaml to nest both message (technical/diagnostic text, config-sourced) and resolution (operator-guidance text) under each error code. This keeps semantically-related information together and mirrors the conceptual grouping in error responses.

### Current Structure
```yaml
EXT-GPTAUTO-001: "ChatGPT was not ready before the login timeout..."
```

### New Structure (Option A: Nested)
```yaml
EXT-GPTAUTO-001:
  message: "ChatGPT was not ready before the login timeout. Check network connectivity and sign-in status."
  resolution: "Sign in to chatgpt.com in the automated browser profile; increase login_timeout_seconds if sign-in genuinely takes longer."
EXT-GPTAUTO-003:
  message: "gpt-auto could not prove the submitted prompt before the deadline."
  resolution: "Do not resubmit automatically. Check the failure-reason in details; some reasons (provider-still-generating) require retry only after confirmation of prompt-absence."
```

### Reasoning for Option A
- **Readability**: Nested structure visually groups message + resolution as a unit, making their relationship explicit
- **Backward compatibility**: Existing code can be migrated incrementally; old flat structure and new nested structure can coexist during transition
- **Extensibility**: The nested map can carry additional metadata in future (e.g., `severity`, `auto_recovery_suggested`)
- **Maintainability**: Reduces YAML key collisions/confusion (no need for naming conventions like `ERROR-CODE-message` vs `ERROR-CODE-resolution`)

## Function Design: errors.py Changes

### 1. Modify `get_error_message(code: str) -> str | None`
Extend to load message text from config. Return None if code has no registered message.

```python
def get_error_message(code: str) -> str | None:
    """Load technical/diagnostic message text for an error code from config.
    
    Returns None if the code has no configured message. Do not raise; callers
    that require a message must use make_error() which will enforce at
    construction time.
    """
    entry = _ERROR_RESOLUTIONS.get(code)
    if isinstance(entry, dict) and "message" in entry:
        return entry["message"]
    return None
```

### 2. Modify `get_error_resolution(code: str) -> str | None`
Update to handle nested structure (backward-compatible with flat strings).

```python
def get_error_resolution(code: str) -> str | None:
    """Load operator-guidance resolution text for an error code from config.
    
    Handles both legacy flat strings and nested message/resolution dicts.
    Returns None if code not registered.
    """
    entry = _ERROR_RESOLUTIONS.get(code)
    if entry is None:
        return None
    if isinstance(entry, dict):
        return entry.get("resolution")
    # Legacy: if entry is a string, treat it as resolution text
    return entry
```

### 3. Modify `make_error()` to accept optional message_id

```python
def make_error(
    *,
    prefix: str,
    component: str,
    number: int,
    kind: str,
    message: str | None = None,  # NEW: optional; sourced from config if None
    details: Mapping[str, Any] | None = None,
) -> AudiaGenticError:
    """Create an AudiaGenticError, with message sourced from config if not provided.
    
    If message is None, it is loaded from config via get_error_message(code).
    If the code has no configured message, raises ValueError (enforces the
    standard: all codes must have config-sourced messages).
    
    If message is provided explicitly, it is used as-is (allows override for
    truly dynamic messages, though this is discouraged and should be rare).
    """
    if prefix not in ERROR_CODE_PREFIXES:
        raise ValueError(f"unknown error prefix {prefix!r}; valid prefixes: {sorted(ERROR_CODE_PREFIXES)}")
    _validate_kind(kind)
    
    code = f"{prefix}-{component.upper()}-{number:03d}"
    _validate_code(code)
    
    # If message not provided, load from config
    if message is None:
        message = get_error_message(code)
        if message is None:
            raise ValueError(
                f"Error code {code!r} has no configured message in error-resolutions.yaml. "
                f"Add a message entry under {code} in the appropriate component's error-resolutions.yaml. "
                f"See ARCHITECTURE_GUIDELINES.md §3."
            )
    else:
        if not message:
            raise ValueError("error message must not be empty")
    
    return _Error(
        code=code,
        kind=kind,
        message=message,
        details=redact_details(details),
        _validated=True,
    )
```

### 4. Update `make_error_factory()` to support config-sourced messages

```python
def make_error_factory(
    prefix: str, 
    component: str, 
    kind: str,
    use_config_message: bool = True,  # NEW: default True
) -> Callable[..., AudiaGenticError]:
    """Create an error factory that optionally sources messages from config.
    
    Args:
        use_config_message: If True (default), messages are loaded from config.
                           If False, caller must provide explicit message strings
                           (legacy behavior, not recommended for new code).
    """
    def _factory(
        code_number: int, 
        message: str | None = None,  # NEW: optional if use_config_message=True
        **details: Any
    ) -> AudiaGenticError:
        # If config-sourced messages are required and caller didn't provide one, OK
        # (make_error will load it); if caller provides one anyway, it overrides config.
        return make_error(
            prefix=prefix,
            component=component,
            number=code_number,
            kind=kind,
            message=message,  # None if not provided, make_error will load from config
            details=details or None,
        )
    return _factory
```

### Templating / Dynamic Interpolation

For messages that need dynamic interpolation (e.g., "Provider {provider_id} is not installed"):
1. Store the template in error-resolutions.yaml as a Python format string: `"Provider {provider_id} is not installed; check PATH and reinstall."`
2. Pass format arguments as details dict keys
3. Interpolate in make_error AFTER redaction:

```python
# In make_error, after loading message from config:
if message and '{' in message:
    # Safe interpolation: use only details dict that has already been redacted
    try:
        message = message.format(**{k: v for k, v in redact_details(details or {}).items() if isinstance(v, str)})
    except (KeyError, ValueError):
        # If template is incomplete or invalid, use original and log a warning
        # Do NOT raise; the error object must be constructible
        pass
```

## Risks & Edge Cases

### Risk 1: Secret Leakage in Template Interpolation
**Issue**: If a template references `{auth_token}` or similar, and the value contains credentials, the interpolated message becomes a leaked secret.

**Mitigation**:
- Do NOT use templating for sensitive values
- Redact secret-shaped strings from details dict before interpolation (already done via `redact_details()`)
- Document in ARCHITECTURE_GUIDELINES.md that messages must not contain user secrets or API keys
- Use generic placeholders in messages (e.g., "[credential]" rather than the actual secret name)

### Risk 2: Explicit message= Override Conflict
**Issue**: If a code has a configured message but a caller passes message= explicitly, which wins?

**Resolution**: 
- Explicit message parameter always wins (caller can override if needed for truly dynamic cases)
- This is permissive (allows transition) but enforced by future validation: a new VAL-code will warn at call-site if both exist and differ
- Document in guideline: prefer config-sourced messages; explicit message= is allowed only for temporary backward-compat or truly unavoidable dynamic text

### Risk 3: Validation Timing (Config-load vs Call-site)
**Issue**: Should enforcement run at boot (when error-resolutions.yaml loads) or at each AudiaGenticError construction?

**Resolution**: 
- **Config-load time** (boot): Validate that every error code referenced in code has both message and resolution entries (via a VAL-code that loads the yaml and cross-checks against code references) -- this is a one-time gate
- **Call-site time** (constructor): make_error() raises ValueError if message is None and code has no configured message -- this enforces at runtime that no code path can construct a messageless error
- Rationale: Boot-time validation catches missing entries early; call-site validation prevents runtime surprises

### Risk 4: Dynamically Generated Messages
**Issue**: Are there error messages that cannot be pre-defined because their text depends on runtime state (e.g., a list of invalid options)?

**Inventory of gpt_auto error messages**:
- EXT-GPTAUTO-001: static (ready timeout message)
- EXT-GPTAUTO-002: static (no response timeout message)
- EXT-GPTAUTO-003: static (proof failed message)
- EXT-GPTAUTO-004: static (reconciliation failed message)
- EXT-GPTAUTO-013: static (CDP failure message)
- VAL-GPTAUTO-001: config validation failure -- **this is semi-dynamic** (reason varies by field), but can be addressed by moving the specific reason to details dict, keeping message generic

**All gpt_auto messages are either fully static or can be split (generic message + dynamic details)**. No blocking dynamic-message cases found in this component.

## ARCHITECTURE_GUIDELINES.md §3 Update

Add to the existing Error, Logging, and Redaction Practice section:

**New requirement:**
"Error message text (the message= argument to AudiaGenticError constructors) must be sourced from the component's error-resolutions.yaml config file, not hardcoded inline in Python. Register each error code with both a message entry (technical/diagnostic text) and a resolution entry (operator-guidance) in the nested error-resolutions.yaml structure. Call sites must use make_error() without an explicit message parameter, allowing the message to be loaded from config at construction time. Inline message= strings are permitted only for backward compatibility during migration and must not be used in new code; use the details dict to capture dynamic information instead. This requirement applies to all public error codes; internal/test errors may continue using inline messages if necessary."

### Updated make_error()
```python
def make_error(
    *,
    prefix: str,
    component: str,
    number: int,
    kind: str,
    message: str | None = None,  # NEW: optional; loads from config if None
    details: Mapping[str, Any] | None = None,
) -> AudiaGenticError:
    """Create an AudiaGenticError, sourcing message from config if not provided.
    
    Args:
        message: If None, loaded from config via get_error_message(code).
                If config has no message, raises ValueError (enforces standard).
                If provided, used as-is (allows rare override for dynamic text).
    
    Raises:
        ValueError: If code is invalid format, if code is not registered,
                   or if message is None and code has no configured message.
    """
    if prefix not in ERROR_CODE_PREFIXES:
        raise ValueError(f"unknown error prefix {prefix!r}; valid prefixes: {sorted(ERROR_CODE_PREFIXES)}")
    _validate_kind(kind)
    
    code = f"{prefix}-{component.upper()}-{number:03d}"
    _validate_code(code)
    
    # Load message from config if not provided
    if message is None:
        message = get_error_message(code)
        if message is None:
            raise ValueError(
                f"Error code {code!r} has no configured message in error-resolutions.yaml. "
                f"Add a message entry under {code}. See ARCHITECTURE_GUIDELINES.md §3."
            )
    elif not message:
        raise ValueError("error message must not be empty")
    
    return _Error(
        code=code,
        kind=kind,
        message=message,
        details=redact_details(details),
        _validated=True,
    )
```
