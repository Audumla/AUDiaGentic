# SA01 — Add secret scanning and push protection

## Description

Introduce mandatory developer-side and CI secret scanning for current changes and complete Git history. Based on SEC-01 from the security audit.

## Steps

1. Add Gitleaks configuration (`.gitleaks.toml`) with exact-scope allowlist conventions
2. Add pre-commit integration (`.pre-commit-config.yaml`) for staged-file scanning
3. Add pull-request CI scan workflow (`.github/workflows/security-secret-scan.yml`)
4. Add scheduled full-history scan workflow
5. Document GitHub secret scanning and push protection settings in `docs/security/SECRET_SCANNING.md`
6. Add scanner regression fixtures under `tests/security/`
7. Ensure Markdown, NDJSON, YAML, JSON, TOML, TypeScript, Python, shell scripts, logs, fixtures, and workflow files are included in scan targets
8. Verify CI fails on verified secret patterns in any tracked file type

## Files

- `.gitleaks.toml` (new)
- `.pre-commit-config.yaml` (new)
- `.github/workflows/security-secret-scan.yml` (new)
- `docs/security/SECRET_SCANNING.md` (new)
- `tests/security/` (new directory)

## Validation

- [ ] Current tree passes Gitleaks scan
- [ ] Full history passes or produces a reviewed remediation list
- [ ] Synthetic current-branch secret fails CI
- [ ] Synthetic historical secret fails scheduled scan
- [ ] Markdown and NDJSON files are scanned
- [ ] A test secret committed to a throwaway branch is detected
- [ ] A secret added and then removed in a later commit is still detected by the history scan
- [ ] Any allowlist entry has exact file and line scope, documented reason, owner, and expiry/review date

## Effort & Risk

Mid complexity. Requires CI workflow configuration and Gitleaks setup. Low risk — scanning is additive and non-destructive.

## Standards

- SEC-01 — No evidenced repository-wide automated secret protection
