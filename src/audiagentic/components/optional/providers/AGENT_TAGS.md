# Agent Tags (Prompt Trigger Tags)

Agent tags are the actions that providers execute when a user invokes the AUDiaGentic bridge. Each tag is a fully self-contained unit. Tags are **owned by components** — any installed component can declare its own set of tags, and the providers component surfaces them automatically on every installed provider.

## How it works

1. A component declares its tags in its detailed config YAML under the `agent-tags` key.
2. When the providers component reconciles, it loads all tags from all installed component configs.
3. Each tag's `skill.md` and `surface-contributions` are pushed to every installed provider surface.
4. Provider surfaces are regenerated by running `skill_surfaces`.

Tags and providers are **mutually ignorant** — a tag does not name any provider, and a provider does not name any tag. The surface manager bridges them at runtime.

## Adding a new tag to an existing component

### 1. Create the tag directory

```text
src/audiagentic/config/prompt-triggers/tags/<your-tag-name>/
```

Use a short, lowercase, hyphen-separated name.

### 2. Write `descriptor.yaml`

```yaml
type: prompt-trigger-tag
contract-version: v1
tag-id: my-tag                    # canonical name used everywhere
display-name: My Tag              # human-readable label
description: One-line description of what this action does
aliases:                          # shorthand forms users can type
  - mt
  - mytag
directives:                       # key=value options accepted in the prompt header
  - id
  - target
  - context
  - output
  - template
  - model
  - model-alias
requires-body: true               # false = prompt body is optional
is-generic-tag: false             # true = adhoc fallthrough (at most one across all tags)
is-review-tag: false              # true = review semantics (at most one across all tags)
skill-content-file: skill.md      # relative to this directory

# Project files this tag installs
files:
  - path: .audiagentic/skills/my-tag/skill.md
    lifecycle: required-managed
    description: my-tag canonical skill source

# Rule blocks pushed into every installed provider surface (no provider names here)
surface-contributions:
  - id: my-tag/doctrine
    kind: rule
    title: My tag action doctrine
    content:
      body: |
        When this action is triggered: describe what the provider should do.

# Prompt templates installed into .audiagentic/prompts/my-tag/
prompts:
  - name: default
    content-file: prompts/default.md
```

### 3. Write `skill.md`

Must have YAML frontmatter followed by structured sections:

```markdown
---
name: my-tag
description: One-line description for skill metadata.
---

# My Tag skill

Trigger:
- first non-empty line resolves to `my-tag` or a configured alias (`mt`, `mytag`)

Do:
- describe what the provider should do when this action is triggered

Do not:
- describe what must not happen
```

The `Trigger:`, `Do:`, and `Do not:` sections are parsed by the surface renderer. Each item must start with a `- ` list marker.

### 4. Add prompt templates (optional)

If your `descriptor.yaml` lists prompts, create the referenced files:

```text
src/audiagentic/config/prompt-triggers/tags/<your-tag-name>/prompts/default.md
```

### 5. Declare the tag in the owning component's config

Tags are not discovered by directory walk — they must be declared by a component. Add an entry to the component's detailed config YAML:

```yaml
# e.g. config/execution/jobs/agent-jobs.yaml
component-id: agent-jobs

agent-tags:
  - config: prompt-triggers/tags/implement/descriptor.yaml
  - config: prompt-triggers/tags/plan/descriptor.yaml
  - config: prompt-triggers/tags/my-tag/descriptor.yaml   # ← add here
```

The path is relative to the config root (`src/audiagentic/config/`).

### 6. Regenerate provider surfaces

```sh
python -m audiagentic.components.optional.providers.skill_surfaces --project-root .
```

The new tag appears automatically on every installed provider surface.

## Adding tags to a new component

If you're creating a new component that has its own actions:

1. Create the tag descriptor files as above.
2. In your component's detailed config YAML, add the `agent-tags` key:

```yaml
# config/my-component/my-component.yaml
component-id: my-component

agent-tags:
  - config: prompt-triggers/tags/my-action/descriptor.yaml
  - config: prompt-triggers/tags/my-other-action/descriptor.yaml

surface-contributions:
  - id: my-component/doctrine
    kind: rule
    title: My component doctrine
    content:
      body: |
        Component-level rules go here (not tag-specific).
```

3. Register the component in `config/foundation/components/` with `config:` pointing to your detailed config.
4. When the providers component reconciles, your tags are picked up automatically.

---

## Removing a tag

1. Remove its entry from the owning component's `agent-tags` list.
2. Delete the tag directory from `config/prompt-triggers/tags/`.
3. Run surface regeneration — stale provider skill files are pruned automatically.

---

## Modifying an existing tag

Edit `descriptor.yaml` or `skill.md` in the tag's directory, then run surface regeneration. Changes propagate to all providers.

---

## Project-level skill overrides

A project can override any tag's `skill.md` by placing a file at:

```
.audiagentic/skills/<tag-id>/skill.md
```

The project-local file takes precedence during surface generation. The `descriptor.yaml`, `surface-contributions`, and `agent-tags` declarations are not overridable at project level.

## Discovery chain

```text
providers reconcile / skill_surfaces run
  └─ load_all_tags()
       └─ register_all_components()         # scans config/foundation/components/**/*.yaml
       └─ for each ComponentDescriptor:
            └─ read its config YAML
                 └─ agent-tags: [...]       # declared tag refs (relative paths)
                      └─ load_tag_from_yaml(config_root / entry["config"])
                           └─ register(TagDescriptor)

  └─ load_surface_contributions()
       └─ component surface-contributions   # unchanged
       └─ load_tag_surface_contributions()  # per-tag contributions from registry
       └─ build_summary_contributions()     # dynamic canonical-tags + aliases summary
```

## Tag registry internals

| File              | Role                                                              |
| ----------------- | ----------------------------------------------------------------- |
| `tags/base.py`    | `TagDescriptor` dataclass                                         |
| `tags/registry.py`| In-process store; `all_tags_loaded()`, `tag_alias_map()`, etc.   |
| `tags/loader.py` | Scans component configs for `agent-tags`, loads referenced descriptors |
| `tags/__init__.py` | Triggers load on import |

`prompt_syntax.py` and `skill_surfaces.py` both read from the registry — they never reference provider or tag names directly.
